# 内容改写手册（去 AI 味 · 读者视角）

给改写 agent 用。目标不是「写得更漂亮」，是**让读者读得懂、照做不出错、并且能感觉到有个人在带他**。

本仓库 `content/` 下 478 篇可校验文章，历史问题是 79% 共用同一个骨架：`这一课你要会 → 为什么 → 讲解 → 跑一遍 → 动手 → 检查一下 → 常见误区 → 小结`。读得懂，但作者不在场，谁都能写，读完记不住任何人。

## 一、三条硬规则

1. **第一屏必须是工件，不是结论。**
   能跑的坏代码 + 它真实的输出 + 一个具体的「我猜错了」反应。可以是：真实报错原文、真实计时输出、真实探针输出、真实的表/配置片段。
   前 300 字不出现「我们先来看」「好比」「就像」「这一关在解决什么」。

2. **数字要么本机实测，要么标出处。**
   - 实测就贴真实输出（含机器/版本条件）。
   - 否则写清「这是 2017 年机械硬盘的量级，今天的 SSD 不一样」这类限定。
   - 禁止：`通常`、`往往`、`绝大多数`、`90% 的场景`、`极难`、`很快`——除非紧跟数据。
   - **绝对禁止编造真实公司/线上事故**。没有真实经历就写「我在自己练手项目里」，并承认例子是玩具。

3. **删掉三件套。** `## 常见误区`（你以为/其实/怎么验证）、`## 小结`、`## 这一课你要会` 全部删除。
   结尾改成 `## 还差的` 或 `## 这一版没做的`：写你**确实没解决**的部分，指名具体缺口，不要复述正文。

## 二、结构（建议，不强制）

```markdown
## <一个具体现象的短标题，可以带数字或报错片段>
（工件：代码/命令 + 真实输出 + 我当时猜了什么、错在哪）

## <第二个环节，承接上一个问题的下一步>
（继续同一条叙事线，不要换例子）

## 跑一遍        ← 可保留，见门禁
## 动手          ← 可保留，见门禁
## 检查一下      ← quiz，必须恰好 1 个，见门禁
## 还差的        ← 取代「小结」
```

- **一篇文章只用一个贯穿对象**。别在 `Student` / `Account` / `User` 之间跳。
- 表格只在**真的并列比较**时用；两行三列的装饰性表格删掉。
- `sketch` / `mermaid` 图：能删就删。留的图必须是读者需要的那次判断，不能在 `^~` 这类分支上漏掉关键路径还写「看不懂没关系」。

## 三、内容上必须自己查证的点

每篇至少核一遍这五类，2026-11 这一轮已查出的一批典型错：

- **版本/平台默认值**：InnoDB 页 16KB（不是 4KB）、PostgreSQL 8KB；Let's Encrypt 证书 90 天（不是一年）；`RestartSec` 默认 100ms；kubectl 1.18+ 要 `--dry-run=client`。
- **方向性说法**：是「列被转换」还是「常量被转换」；是「客户端能确认」还是「服务端不知道」；`set -e` 下回滚代码是不可达代码。
- **`NULL` / 空集语义**：`COUNT(列)` 跳过 NULL、`COUNT(*)` 不跳；`SUM` 空集返回 NULL；`NULL = NULL` 是 UNKNOWN。
- **索引/排序语义**：`location /api` 能匹配 `/api/users`；排序键并列时顺序未定义；行值比较必须同向。
- **依赖顺序**：本文用到的语法是否在**前面的课**讲过（record 在 java 第 35 课、装饰器在 python 第 15 课、LEFT JOIN 在 mysql 第 05 课）。没讲就换写法，或明写「这里先照抄，第 N 课解释」。

## 四、门禁（必须全绿才算完成）

```bash
# 全库结构与块 JSON（必跑，478 篇）
node scripts/check-content.mjs

# 课程：code-challenge / quiz / run 块结构 + 代码执行
python scripts/verify_course.py --dir content/courses/<线>            # java / python / spring / spring-handmade
python scripts/verify_course.py --no-run --dir content/courses/mysql  # 本机 SQL 跑不了，只能 --no-run
```

**块规则**（改了会红）：

| 块 | 要求 |
| --- | --- |
| `<!-- run -->` | 课程里会**真执行**并与下面的 ```text 输出**逐字比对**（不 strip 前导空格，所以 print 不要带缩进）。改代码就必须同步改输出，或整段删掉该 run 块 |
| `code-challenge` | 至少 1 个，不能删。`kind` 只允许 `fill/order/bug/run/sql-write/sql-fix`；`bug` 要 `code`+`bugLine`；`order` 要 `lines`+`answer`（排列） |
| `quiz` | **恰好 1 个**，不能删、不能加。JSON 里**不能有裸 ASCII 双引号**，中文引号用「」 |
| `sql-write` | 必须有 `dataset`/`expectHash`/`starter`。**不要改 expectHash**（本机 `paideia_e2e` 建不了库，改了无法验证）。可以改 `title`/`goal`/`trap`/`explain`/`starter` 让它与正文一致 |

reading 线（`content/reading/**`）不受七小节约束，只受 `check-content.mjs` 的 frontmatter 与块 JSON 校验，可以自由删 quiz/图。

## 五、操作坑

- **行尾**：`content/` 下文件多为 **CRLF**。跨多行替换用 `apply_patch` 可能失败，直接整篇 `write` 更稳（写进去的行尾与工具一致即可，git 会提示 `LF will be replaced by CRLF`，正常）。
- **中文引号**：quiz / code-challenge 的 JSON 里出现 `"` 会被 JSON 解析吞掉导致 error，统一用「」。
- **不要改 frontmatter 的 `minutes` 之外的字段**（`title`/`category`/`order`/`prerequisite` 保持），`minutes` 降到与篇幅相符（一般 16–22）。
- **只动 `content/` 下你被指派的文件**。仓库里有并发会话在改 `backend/`，不要碰。

## 六、验收标准（复审 agent 会按这个挑）

站在「刚学到这里、手上有一台机器」的读者角度问：

1. 第一屏有没有一条能粘贴就跑的命令/代码，和它真实的输出？
2. 有没有一句「我原来以为是 X，实际是 Y」的判断，是**这篇独有**的？
3. 照抄会不会失败？失败的地方有没有提前说清前提（版本、依赖、数据）？
4. 有没有数字没有出处？有没有 `通常/往往`？
5. 结尾是不是在复述正文，而不是交代没做完的部分？
6. 读者读完能回答「所以我现在该去动什么」吗？
