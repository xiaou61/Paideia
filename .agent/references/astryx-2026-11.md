# Astryx 调研与融合建议（2026-11-17）

> 对象：https://github.com/meta/astryx
> 结论一句话：**不要把 Astryx 当依赖引入，只借它的三条经验**——agent-ready 的单一规范源、页面级 patterns 层、以及「开放内部、定制而不包裹、引导而非强禁」的 API 原则。

## 一、Astryx 是什么（事实）

- Meta 内部沉淀 8 年、支撑 13000+ 应用后开源的**设计系统**；MIT 许可；约 29.7k star；官方标注 **Currently in Beta**。
- 技术形态：**React 19 + StyleX** 编写；消费方引入**预编译 CSS + 类型化组件**，无需自己装样式库。
- 规模：150+ 无障碍组件、7 套主题（neutral / butter / chocolate / matcha / stone / gothic / y2k）、CLI、Storybook、Sandbox。
- 包结构：`@astryxdesign/core`、`/cli`、`/build`、`/theme-*`。
- 定位：**「人 + AI 助手共用同一套工具」**——文档与 CLI 都是为 agent 设计的（可直接被编码助手调用）。
- 主题机制：**CSS 自定义属性覆盖**；不锁定样式（可用 `className` + Tailwind 覆盖）；**swizzle** 可把组件源码 eject 出来自持。

## 二、它真正解决的问题

不是"再给一套 UI 组件"，而是给**大规模多人 + 大量 AI 生成代码**的场景提供三样东西：

1. **单一可信规范源**：组件 API、示例、约束收敛成一份机器可读的清单 + 一个 CLI，人和 AI 都不用去翻源码猜用法。
2. **组合层模板（patterns）**：除原子组件外，直接给"列表页/详情页/表单向导"这类页面级模板，减少每个团队重复拼装。
3. **明确的 API 哲学**：open internals（不藏底层）、customize without wrapping（用 className/属性定制，不套壳）、guidance over enforcement（靠文档与示例引导，不靠 lint 硬禁）。

## 三、三条可借鉴经验 → Paideia 具体映射

### REQ-001 | Agent-ready 单一规范源（推荐先做，零运行时）

- Astryx 做法：CLI（`@astryxdesign/cli`）+ 单一文档源 + Storybook/Sandbox，组件清单与用法可被程序读取。
- Paideia 现状：单一出口 `frontend/packages/ui/src/index.ts` 已经是"唯一入口"的好底子；但**组件 API、Props、用法的说明是隐性的**（散在各 `.tsx` 里、ui-kit 只做可视化展览），AI 每次都要读源码。
- 建议落法：
  - 写一个 `scripts/gen-ui-manifest.mjs`：扫 `index.ts` 的导出 + 各组件的 Props 类型，生成 `docs/ui-manifest.md`（或 `.agent/references/ui-manifest.md`），列出组件名、Props、一句话用途、示例文件位置。
  - ui-kit 的页面清单复用**同一份元数据**，避免"展览页"和"文档"两处各写一遍。
  - 挂到 `package.json` 的 `pnpm ui:manifest`，CI/提交前可校验是否漂移。
- 成本：约 0.5 人日；**零运行时依赖**；与现有 index.ts 单一出口天然契合。

### REQ-002 | Patterns 页面级模板层

- Astryx 做法：除原子组件，直接提供页面级 patterns（表格页、详情页、表单向导、导航）。
- Paideia 现状：只有 `AppShell` / `PageHeader` / `Section` 这类"壳与区块"，**页面级组合每次重拼**；admin 的列表/详情/表单最重复，最容易沉淀。
- 建议落法：`frontend/packages/ui/src/patterns/{list-page,detail-page,form-wizard}.tsx`，先在 ui-kit 里展示并对照，再挑 admin 的一个真实页面替换验证（不做大迁移）。
- 成本：约 2–3 人日/个；不引新依赖；要遵守"packages/ui 纯展示层"约束（模板只吃 props，不认识 core/router）。
- 开放点：放 `packages/ui`（共享、随皮肤走）还是新开 `@paideia/patterns`（边界更清、但多一个包）——建议先内置于 `packages/ui`，规模变大再拆。

### REQ-003 | API 原则（评估，不急着改）

- open internals：`index.ts` 现在**只导出封装件**，底层 `@base-ui/react` 原语不透出。真需要扩展时只能改 ui 包。可评估"双出口"：`@paideia/ui`（成品）+ `@paideia/ui/primitives`（底层原语），把扩展权交回使用方。
- customize without wrapping：样式走 `className` / 数据属性，不鼓励再包一层。
- guidance over enforcement：不新增 lint 硬禁，用文档 + 单测示例引导（与现有 `source-coverage.test.ts` 等守卫并存，不替代）。
- 成本：主要是评审与文档，不改运行时；建议**随 REQ-001 的文档一起表述**，不单独立项。

## 四、坚决不做的（及理由）

- **不把 Astryx 作为运行时依赖**：与现有 17 套皮肤形成两套主题体系；StyleX 与 Tailwind 两套样式范式互斥；官方 Beta 有稳定性风险；会把桌面产物重新拉大。
- **不引入 StyleX**：现有整套令牌与 `globals.css` 单一颜色来源都会失效。
- **不把 swizzle/eject 当常规路径**：会把设计系统的维护成本转嫁给每个使用方，和"单一出口"的治理目标相反。

## 五、风险与兼容性

- 生成式 manifest 会随源码演进漂移 → 必须配一个 `--check` 模式进 CI，否则文档很快失真。
- patterns 若混入业务依赖（router/data 获取），会违反"packages/ui 纯展示层" → 模板必须是纯 props，数据由调用方注入。
- 双出口（primitives）一旦放出去，底层 API 就变成事实契约，后续升级 Base UI 要考虑兼容 → 先只做评估，不急着放。

## 六、建议的落地顺序

1. **REQ-001**（0.5 人日、零运行时、先把"隐知识"变成单一清单）——性价比最高，先做。
2. **REQ-002**（挑 1 个 patterns 先做列表页，替换 admin 一个页面验证）——见效最直观。
3. **REQ-003**（把 API 原则写进文档与 REQ-001 的清单，评估双出口但暂不实现）。
