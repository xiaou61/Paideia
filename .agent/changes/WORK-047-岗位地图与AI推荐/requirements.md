# 岗位地图与 AI 推荐需求

## 目标

`/learn` 现在是 **22 条线平铺**：理论 14 条、实战 5 条，按 `sort_order` 排。对"我知道自己要学什么"的人是够用的；对"我是后端，我该学哪些"的人，它给的是一张**没有主次的清单**。

本项把 `/learn` 从"清单"改成"**地图**"：

1. **先选岗位**：后端开发 / 算法与 AI / 数据开发 / 前端开发（在建）。
2. **再看三段**：这个岗位的**核心**、**进阶**、**选读**，每条线带自己的进度。
3. **最后听一句建议**：AI 告诉你"接下来先学这三条，因为……"，理由必须引用你的真实状态。

## 非目标

- **不做硬权限**。岗位不影响你能不能访问任何内容，只影响**展示顺序与推荐**。这与身份层的既有裁决一致（身份管推荐，不管权限）。
- **不新建内容线**。前端岗位目前没有内容——本项**只暴露这个缺口**，不在这期补（补内容是一个独立的内容工程）。
- **不让 AI 决定优先级**。核心/进阶/选读是确定的规则；AI 只负责**解释与措辞**，不负责排序。这条是硬约束：模型不可用时推荐必须照常出，只是没有那句话。
- **不做 A/B 实验与埋点优化**。没有用户量支撑统计显著性。
- **不改学习轨道的通关规则**。进度仍按 `LearningProgressRules`。

## 实现选择

Agent 依据已批准边界和仓库既有模式做出：

- **岗位用代码枚举 + 代码映射**，不建表。理由与身份配置同一条：映射要调参时才该建表，现在没有数据可调。
- **岗位存进既有的 `target_role`**，不新增列。它本来就是"目标岗位"，只是没人用它推荐。
- **推荐打分在客户端做**（纯函数）。轨道与进度本来就在同一个接口里返回，服务端再算一遍等于把同一份逻辑写两遍。纯函数才能单测。
- **AI 只生成理由**，不参与排序。一次调用覆盖三条推荐，走既有积分与限流；失败、无积分、未配置一律降级为"无理由"，不报错。
- **推荐按天缓存**（同岗位同一天只花一次钱），存在前端本地，不上服务端。
- **默认岗位是后端开发**：线上唯一真实内容最厚的一档，且与现有 22 条线的分布一致。

## 功能需求

- **REQ-001** `/learn` 顶部有岗位选择器（4 个岗位），当前岗位全程高亮；切换后立即重排，不刷新页面。
- **REQ-002** 选中岗位后，轨道按**三段**呈现：核心 / 进阶 / 选读。每段内按"该岗位的推荐顺序"排，而不是按 `sort_order`。
- **REQ-003** 每条线显示：名字、一句话（"学了能干什么"）、进度（已过 / 总关）、以及一个明确的下一步动作。
- **REQ-004** 页面有**推荐卡**：给出 3 条"接下来先学这些"，每条带一句理由，理由必须引用真实状态（未开始 / 学到一半 / 前置已满足）。
- **REQ-005** 推荐**可解释**：卡上能展开看到打分依据（岗位权重、进度、是否卡在前置上）。
- **REQ-006** 未设岗位时用默认岗位，并给一句可点击的提示（"默认按后端开发推荐，点这里换"）。
- **REQ-007** AI 不可用（无积分 / 未配置 / 超时 / 报错）时，推荐卡照常显示，理由位置退化为规则生成的短句，**不出现错误提示**。
- **REQ-008** 岗位不影响访问：任何岗位下都能通过知识库或直接 URL 打开任意轨道。
- **REQ-009** 措辞：核心/进阶/选读三段各有一句说明"这一段是什么、为什么这么分"；推荐卡说明"推荐依据是岗位 + 你的进度，每天更新一次"。

## 质量要求

- **打分函数是纯函数**，同输入同输出，不依赖时间以外的外部状态；时间只用于"最近学过"的衰减，且可在测试里注入。
- **边界明确**：零进度、全部学完、岗位没有对应内容、目标岗位为空，四种情况都要有确定结果。
- **AI 不阻塞首屏**：推荐卡先出规则结果，理由加载完成后再补上。
- **可读性**：三段地图在窄屏下纵向堆叠，不出现横向滚动。
- **措辞统一**：同一个概念在全页只用一种叫法（"线"不叫"轨道/课程/专题"混用）。

## 约束与依赖

- 依赖 WORK-024 的轨道与关卡、WORK-038 的 `theory/practice` 模式、WORK-034 的进度统计。
- 依赖 WORK-009 的积分与平台凭据；AI 调用必须走既有的预留-结算，不得直连上游。
- 前端不得硬编码轨道 id，一律按 slug。
- 公开仓库与公开站点：提示词里不得出现任何用户私有数据以外的内容。

## 验收标准

- **AC-001** 选"后端开发"后，页面出现三段，且核心段包含 `java-from-zero`、`spring`、`redis`。
- **AC-002** 切换岗位后，三段的成员与顺序都发生变化（至少一个 slug 换段位）。
- **AC-003** 某条线进度从 0 变成全部通过后，它从推荐里消失，下一条递补。
- **AC-004** 推荐理由里出现具体的数字或状态词（"还没开始"/"6 关中过了 2 关"），不是空泛的鼓励。
- **AC-005** 断网或 AI 报错时，推荐卡仍在，且没有任何错误横幅。
- **AC-006** 同一天同一岗位第二次进入页面，不再产生新的 AI 调用。
- **AC-007** 打分函数单测覆盖：零进度 / 全部通过 / 岗位无内容 / 岗位为空 四种输入。
- **AC-008** 窄屏（412px）下三段地图无横向溢出。
- **AC-009** 岗位不影响访问：未选岗位的用户仍能打开任意 `/learn/<slug>`。

## 假设

- 岗位共 4 个；前端岗位承认内容为空，页面显示"内容建设中"而不是空白。
- 推荐条数固定 3 条。少于 3 条可推荐时给几条算几条。
- "每天更新一次"指本地缓存的自然日，不是服务端定时任务。

## 待确认问题

由 Agent 先行定案，**批准本需求即视为确认**：

- **Q-001 岗位清单** → 后端开发 / 算法与 AI / 数据开发 / 前端开发（在建）。
  不定"测试开发""运维"两个岗位：它们能对应到的内容与后端高度重合，再列两个只会让选择器变长、收益为零。真要加，等有了专属内容再加。
- **Q-002 岗位为空时的处理** → `target_role` 为空时用 `backend` 并提示可切换，**不弹窗强制选**。理由：强制选择会让"只想随便看看"的人卡在第一步。
- **Q-003 AI 推荐的调用时机** → 页面进入时自动调用，但**按「岗位 + 自然日」缓存**；手动"换一批"会强制刷新并花第二次积分。
  理由：推荐卡是这一页的核心价值，藏在一个按钮后面等于没人点；按天缓存把成本压到每用户每天一次。
- **Q-004 前端岗位的空状态** → 显示"这个岗位的内容还在建设中，当前先按后端开发推荐"，而不是给一个空地图。**这是一个真实的缺口，不是文案问题**，写在这里以免被当成已完成。
