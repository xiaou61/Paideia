# 提案 · 岗位地图与 AI 推荐

## 摘要

把 `/learn` 从"22 条线的平铺清单"改成"**先选岗位、再看三层地图、最后读一句建议**"。

三块交付：

1. **岗位地图**：4 个岗位 × 22 条线的映射表（代码里的常量），把每条线标成该岗位的**核心 / 进阶 / 选读**。
2. **推荐打分**：纯函数，输入（岗位、每条线的进度、最近学习时间），输出排好序的 Top 3 与每条的分数构成。
3. **AI 建议**：一次调用，把 Top 3 加上用户的真实状态交给模型，让它写三句"为什么现在学这个"。**它不参与排序。**

## 分期

**S1 · 岗位地图**（纯前端，无 AI）

- 岗位枚举 + 映射表 + 打分纯函数 + 单测。
- `/learn` 改成三段式；岗位选择器放在页头。
- 验收点：切岗位，三段的成员与顺序都变。

**S2 · 推荐卡**（仍无 AI）

- 推荐卡展示 Top 3 与**规则生成的理由**（"你还没开始这条" / "6 关过了 2 关"）。
- 验收点：AI 完全不可用时，这一版就是最终形态。

**S3 · AI 建议**

- 后端一个端点：入参是岗位 + Top 3 + 进度摘要，出参是三条一句话理由。
- 走既有积分；失败降级为 S2 的规则理由。
- 按「岗位 + 自然日」缓存。

**S4 · 措辞与验收**

- 22 条 `summary` 从"讲什么"改写成"学了能干什么"（内容侧，走导入脚本）。
- 三段说明、推荐卡说明、空状态文案。

## 关键取舍

**一、映射放代码，不建表。**
另一条路是建 `role_tracks(role, slug, tier, order)`，能按数据调。放弃它的理由与身份配置同一条：现在的映射是**编辑判断**，没有用户数据可调参；建表只会多一个要维护、要同步、要写管理端界面的载体。真到了要按数据调的那天，迁移是一次性的。

代价：改映射要发版。可接受——映射一年大概改两次。

**二、打分在客户端。**
轨道与进度在同一个接口里一起返回，服务端再算一遍等于同一套规则写两处。客户端算的好处是**改规则即刻生效、纯函数可单测**，坏处是规则是公开的（开源仓库）——但"后端核心是 Java 那条线"本来就不是秘密。

**三、AI 只写理由，不排序。**
这条是本项最重要的边界。理由有三：

- **可测**。排序一旦交给模型，测试就只能写"返回了三条"，等于没测。
- **稳定**。同一个人今天和明天看到的顺序不该跳变——那会让人怀疑推荐是随机的。
- **省钱**。排序需要模型理解全部 22 条线与用户状态，提示词会很大；让它只看 Top 3 写三句话，一次调用几百 token 就够。

**四、推荐卡放页面顶部，三段之前。**
直觉是"先看全貌再看建议"，但这一页的**首要问题是"我该从哪开始"**。把建议放在 22 条线之后，等于让用户先自己解决这个问题再看答案。

代价：新用户第一眼看到的是"推荐"而不是"地图"，可能对覆盖面缺少感知。应对是三段就在下面，一屏内能看到核心段。

**五、不新建"岗位"表，也不新增 profile 列。**
`target_role` 已经存在且全链路透传。唯一的改动是给它一组固定取值（现在它是自由文本）。

**六、前端岗位承认是空的，不做假象。**
给了空地图比不给更糟——用户会以为"平台就这么点东西"。做法是选中时显示"内容建设中，先按后端推荐"，并保持地图可用。

## 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 映射里没有某条线 | 新增轨道后忘了标岗位，它会从所有岗位里消失 | 打分函数对"未标岗位"的线给一个兜底（归到"选读"），并有单测钉住 |
| AI 理由空洞 | 模型只会写"这条很重要，建议学习" | 提示词强制引用入参里的具体数字；AC-004 用一个具体断言守它 |
| 岗位与身份混淆 | 用户已有"身份"（求职/读研），再加"岗位"会以为是同一件事 | 岗位选择器上写明"岗位只影响推荐顺序，不影响能看什么" |
| 前端岗位长期为空 | 挂着一个空岗位 | 记在报告与需求里；补内容单独立项 |
| 积分消耗 | 每次进页面都可能触发 | 按「岗位 + 自然日」缓存，`换一批` 才强制刷新 |
