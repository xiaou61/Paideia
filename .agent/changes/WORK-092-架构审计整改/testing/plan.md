# 架构审计整改：首批测试计划

## 测试范围

首批已批准的 AC-001～003。分别验证 MCP 工具组边界、前端会话隔离和桌面渲染器启动边界。AC-004～007 不在已批准的实施计划中。

## 环境与前置条件

- 独立工作树 `work/WORK-092`，使用合成账号、夹具数据与本地端口。不使用生产或共享数据库。
- 桌面需锁定的 Rust 依赖、Windows 工具链和编译期内嵌的前端产物；窗口实测需隔离的 Windows 用户环境，不读写正式配置、系统协议与真实账号。

## 验收矩阵

| 验收标准 | 正向检查 | 反向或边界检查 |
| --- | --- | --- |
| AC-001 | 允许的工具组与无组限制的旧配置行为不变 | 合成无匹配组不列出工具，执行入口也不调用夹具处理器 |
| AC-002 | 例行令牌续期保持同一会话；学习者端和管理端接收各自账号数据 | 切换账号时不保留旧缓存、结果、临时草稿或待发送进度；迟到旧请求不以新身份重试 |
| AC-003 | 正式模式使用内嵌资产；显式开发模式使用临时缓存 | 已占端口的正式模式不启动渲染；拒绝非预期来源，正式构建不进入开发模式 |
| AC-004～007 | 后续批次 | 本轮不执行 |

## 自动化检查

- MCP：模块化守卫和 `McpViewsTest`、`McpViewRegistryTest`、`McpToolInvokerTest`，不启动数据库或外部 MCP 服务。
- 前端：认证与知识进度定向测试、受影响包类型检查、学习者端和管理端使用合成 HTTP 的 Chrome 回归。
- 桌面：`prepare-renderer` 生成内嵌资产；Rust 默认、开发特性及正式资产特性的定向检查；OAuth 原生桥入口用调用夹具验证，不实际访问提供方。

## 人工检查

在隔离 Windows 用户环境中检查：正式窗口正常加载、端口已占用时只显示启动失败提示、开发窗口无正式缓存、正式 OAuth 点击后打开系统浏览器并能完成回跳。缺少环境时分别记录未验证。

## 回归范围

保留有效 MCP 凭据的现有角色与读写判定、例行续期、浏览器 OAuth 跳转和既有桌面外链行为。不更改后端认证接口、CORS 或桌面回环来源。

## 已知缺口

未确认独占数据库，不跑真实后端 e2e；不了解现场安装或 OAuth 测试配置时，不用当前系统用户代替隔离环境。
