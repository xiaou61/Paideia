# 架构审计整改：首批安全边界提案

## 推荐方案

| 范围 | 推荐方案 | 验收 |
| --- | --- | --- |
| 外部 MCP 权限 | 在 MCP 内明确区分「未限制工具组」和「没有允许的工具组」。发现层对不可见的指定组沿用现有未找到行为，执行层在调用工具前独立核验；保留空白名单、默认组、角色与读写范围的既有语义，不改其他消费者的工具目录。 | REQ-001 / AC-001 |
| 两端会话隔离 | 每次建立或结束登录会话时切换前端查询/变更实例，并卸载旧页面。不只处理缓存：会话切换后，旧认证响应不得更新新会话，旧请求也不得用新凭据重放。一次登录内例行续期保留缓存。 | REQ-002 / AC-002 |
| Tauri 启动边界 | 正式构建只有成功启动自身的回环服务才创建窗口；端口不可用时给出启动错误，不猜测其他页面归属。Vite 仅允许由显式调试入口选用，不读取正式端的会话缓存；窗口限制到预定的渲染来源。保留固定 origin、嵌入资产与正常 OAuth 链路。 | REQ-003 / AC-003 |

## 备选方案与取舍

- **修改共享工具目录的空集语义**：能统一表达拒绝，但会波及内部 AI 工具筛选，而且不能代替请求级授权。本轮收敛在 MCP，代价是两层入口共用一条 MCP 授权规则而不是改变公共接口。
- **仅在退出时清查询缓存**：改动最少，但不能约束旧请求的重放、旧会话认证回调和组件本地状态。选择按登录会话重新挂载，代价是切换账号后重新加载受保护数据；正常续期不清空。
- **保留端口复用或换端口**：前者省掉开发配置，但 HTTP 页面特征不能证明所有权；后者可绕开占用，却改变既有 CORS 契约。选择固定 origin 加明确启动模式，端口被占用时正式版不自动启动。

## 交付边界

- 顺序：MCP → 学习者和管理端 → Tauri，各用合成数据独立回归和本地提交。
- 现有后端 API、角色、数据库和 CORS 不变；不发布、不推送、不接触生产。WORK-044 的合法访问语义保留；WORK-088 至 WORK-091 的写作功能不在首批内，前端回归检查既有登入、登出和受保护路由，不修改关联工件。
- 第二、三批仍按已批准需求排队；不在这份提案批准或执行数据迁移、发布脚本改造或线上验证。
