# 架构审计整改

## 背景

用户在收到 Paideia 架构审计后要求「你可以新开一个work 然后开始按照你说的这些开始修复吧，开始吧。」本项以审计基线 `f1edceed` 为起点。

## 目标

保持模块化单体和共享前端，优先保护授权与账号数据边界，再处理丢写、扣分不一致和失败恢复。按优先级分切片验证，不把未实测的生产风险当作已发生事故。

## 已确认事实

- 外部 MCP 的工具组约束存在未默认拒绝的边界情形；账号角色和令牌范围是独立检查，仍须保留。
- 学习者端共用进程内查询缓存，切换账号没有隔离旧会话；管理端也有全局客户端，首批核对并覆盖两个入口。服务端的数据归属过滤不能代替客户端隔离。
- Tauri 正式构建与开发 renderer 共用部分启动逻辑。正式桌面端在无法确认自己持有本地 renderer 时，不应挂载它或交付任何会话数据。
- 审计另外识别了笔记自动保存与学习进度并发丢写、AI 预留积分缺少持久恢复、导入任务重启后存在卡死窗口、发布失败未完整恢复版本、生成图漂移。线上备份恢复能力和外部传输安全尚未核实。

## 需求

- REQ-001（首批）外部 MCP 工具可见与可调用范围均不得超过当前授权。
- REQ-002（首批）查询、待处理变化及可见页面状态不得跨账号泄漏。
- REQ-003（首批）正式桌面端只加载自己启动的渲染页面。
- REQ-004（第二批）编辑中的新版本不被旧保存覆盖；学习进度并发提交不丢已完成项。
- REQ-005（第二批）AI 预留、结算及退回可对账、可恢复；导入中断后任务能终止或安全续跑。
- REQ-006（第三批）发布失败后恢复同一版本的前端和后端，减少部署漂移。
- REQ-007（第三批）将可自动检测的架构漂移和边界回归纳入最小检查。

## 验收标准

- AC-001：正向授权照常；授权不允许的工具在发现和调用两层都拒绝；空配置的既有默认语义、角色和读写范围继续有效。
- AC-002：学习者端与管理端覆盖同一窗口 A 登出、B 登录、A 的延迟响应到达；B 不会看到 A 的数据，A 的旧回调不污染 B；同一会话例行续期不用重新加载全部数据。
- AC-003：正常启动保留共享界面和 CORS 契约；使用本地无凭据测试夹具模拟监听失败，正式模式停止启动，开发模式仅在明确配置时允许使用开发渲染页面；不会向其他页面注入会话数据。
- AC-004：延迟第一次写入后继续编辑，成功最终保存最新版本；失败不显示已保存、不丢草稿。两个并发请求提交不同进度项，最终两项都存在。
- AC-005：结算写入失败或进程中断可恢复，重复恢复不多扣不多退；未完整收到回复不显示正常完成。导入中断可恢复，重试不新增重复草稿，过期工作者不能覆盖新结果。
- AC-006：在隔离环境模拟健康检查失败，前端、后端与基线清单恢复到同一已验证版本；并发发布被串行化；明确数据库迁移兼容与不能自动回滚的边界。
- AC-007：结构图与代码一致，检查失败能阻拦对应变更；验证说明不把未跑的检查当作通过。备份异地性、隔离恢复、外部 HTTPS 和运维端点暴露作为核查项；如需访问或调整线上，单独授权。

## 约束与依赖

- 不接触生产数据，不推送、不部署；只在批准范围内本地修复。安全验证用合成数据和测试夹具；公开仓库工件不记录真实令牌、地址或复现脚本。
- 首批不新增公共接口、改动账号角色定义或迁移数据库。后续若涉及迁移与部署，须确认兼容性与回滚方案后再实施。数据库验证统一走 `scripts/test-db.sh`，不并行复用远程测试库。
- 先验收首批安全修复，再推进数据完整性和发布保障；每批可独立提交和验证，未执行的验收不得勾选。

## 关联工作项

- WORK-044 提供外部工具权限与凭据约定；修复只收紧越界路径，保留已有授权模型。WORK-088 定义自动保存体验，WORK-089、WORK-090、WORK-091 共用工作台或文档契约；修复笔记时维持导航、手动保存、配对与分类难度，不依赖这些旧工作项重新验收才可开展。

## 用户决定

- 需求范围已确认；首批在独立 Git worktree 上开展，工件及通过验证的首批切片可做本地提交。后两批保留在本工作项，具体设计和高风险变更不随首批一起批准。

## 实现选择

- 保留现有模块边界，按验收标准分别验证；具体机制在提案和设计中确定。

## 待确认问题
