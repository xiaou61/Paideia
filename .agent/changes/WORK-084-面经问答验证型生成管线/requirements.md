# 面经问答验证型生成管线 需求

## 背景

现有面经抽取（WORK-025）本质是**一次单发提示**：一次 LLM 调用产出 JSON → `EssayQuestionParser` 校验长度/挡拒答 → `EssayCollectionService.render()` 拼成条目。答案完全来自模型参数记忆，**无 grounding、无 verification**。技术类答案（并发、JVM、React、MySQL）存在「似是而非」的事实错误风险，而提示词只能改格式与风格，不能保证正确性（2026-11-19 用户已认可「验证型 harness」方向）。

## 已确认事实

- 管线位置：`backend/paideia-ai/src/main/java/io/github/xiaou61/ai/internal/essay/EssayExtractionPrompt.java`（当前 `VERSION="essay-extract-v4"`）、`EssayQuestionParser.java`、`EssayCollectionService.java`（`render()` 约第 259 行）。
- 前端展示：`frontend/packages/knowledge/src/entry-body.ts`（`formatEssayAnswer` 等，已在提交 00528e36 上线）。
- 项目常驻规则（`.agent/rules/always.md`）会约束本设计：
  - AI 编排**只允许 AgentScope Java**（D-09），不叠加 Spring AI / LangChain4j。
  - DeepSeek 上**工具调用与结构化输出不能在同一次调用里并用**，「调工具 + 返回结构化结果」必须拆成两次调用。
  - **平台持有 Key、用户按积分消耗**；多采样/多轮会放大成本，需记账与封顶。
  - **本期不做向量化检索 / 语义检索 / RAG**，架构需为将来保留接入位；内容检索本期用 MySQL 全文检索承担。
  - AI 模块需自补：用量与成本记账、模型限流、提示词版本管理、可抓取指标。
- 面经是**后台批量入库**，非实时，延迟与 token 成本可容忍；正确性收益会沉淀进长期内容。

## 用户决定

- 2026-11-19：方向确定为「验证型 harness」（draft → verify → revise 一类），而非单纯提示词美化。
- 2026-11-19：**校验依据允许联网抓官方文档做 ground truth**（用户选择）。这构成对「本期不做向量化检索 / 语义检索 / RAG」项目规则的**例外**——仅限「答案核验时只读抓取权威文档」，不新建向量库、不建内容语义索引；如不被认可则回退为「仅模型内部校验」。
- 2026-11-19：**低置信答案进人工复核队列**（用户选择），需要管理端新增复核页面与状态流。
- 2026-11-19：**试点范围只对新抓取面经生效**（用户选择），存量内容保持现状。
- 2026-11-19（m00392）：**「答对」的口径只要求事实无误**——不要求覆盖考点完整、也不要求可读性打分。判定以「答案中的事实/机制陈述是否成立」为准，可读性由既有排版修复（00528e36）承担。
- 2026-11-19（m00392）：**接受 strict 模式**（proposal → design → tasks 逐门槛），并要求进入 design 阶段。

## 目标

让入库的面经答案具备可核验的正确性：对可疑答案先自检、必要时修订或拦截，降低事实错误流入知识库，同时不把原本正确的答案改坏。

## 非目标

- 不做通用的多轮聊天产品形态。
- 不改面经的抓取 / 切题环节（WORK-025 范围）。
- 本期不引入向量库 / 语义检索（除非用户明确裁决放开）。

## 功能需求

- REQ-001 **校验回路**：对每条「题目 + 草稿答案」执行「自检 →（可选）依据核验 → 修订或保留 → 记录判定」的有限轮流程，轮数与 token 有上限。
- REQ-002 **判定与置信**：产出结构化判定（通过 / 需修订 / 存疑）与理由，供后续分流。
- REQ-003 **分流与兜底**：按判定走「直接入库 / 修订后入库 / 进人工复核 / 不入库」（具体档位待定）。
- REQ-004 **可观测**：每次校验记录 token、耗时、判定、所用依据，纳入 AI 用量记账。
- REQ-005 **可配置与可回退**：校验开关、模型、轮数、预算可配；关闭后回落现有单发管线，行为与现状一致。

## 质量要求

- 不因校验把原本正确的答案改坏（需回归对比）。
- 成本与延迟有上限；批量入库可接受数倍成本但要有封顶与级联（便宜先跑、可疑再升级）。
- 判定可解释、可复现（采样策略/温度固定或记录）。

## 约束与依赖

- AgentScope Java；工具轮与结构化轮分离（DeepSeek 限制）。
- 遵守计费与限流；不新增向量库（除非裁决）。
- 依赖 WORK-025 的抽取产物与 WORK-009 的计费链路。
- 外部依据抓取：只读、来源白名单（官方文档 / MDN / 语言或框架官方站点）、必须缓存、失败降级到内部校验；不得把外部内容大段原样抄入条目（版权与风格）。
- 本条外部依据能力是「本期不做 RAG」规则的**受控例外**（仅核验用途），需在需求批准时一并确认；如批准，同步在 `.agent/rules/always.md` 记录该例外边界。

## 关联工作项

- WORK-025（面经抽取）：在本工作项在其答案上增加校验，不改变抽取契约。
- WORK-009（AI 网关与积分配额）：复用用量记账与配额链路。

## 验收标准

- AC-001 在一批人工标注样本上，校验后的事实错误率相对现状下降（需先建标注集与基线）。
- AC-002 校验不引入可观的正向改坏率（正确 → 错误）。
- AC-003 每条处理有可追溯记录（判定、依据、用量）。
- AC-004 关闭校验时行为与现状一致。

## 假设

- 面经答案的主要风险是「事实/机制错误」，而非格式（排版问题已由 00528e36 单独修复）。

## 实现选择

以下是**方案层的实现取舍**（不是用户决定，最终在 proposal/design 中定稿并随其批准）：

- 采用**三级级联**而非全量多轮：便宜的内部自检当闸门，只有可疑项才升级到「联网依据核验 + 修订」，仍不确定的交人工。
- 外部依据由**确定性 Java 代码**检索/抓取片段后喂给模型，**不让模型自主调用工具**——规避 DeepSeek「工具调用与结构化输出不能同一次调用」的限制，也缩小 SSRF/版权面。
- 复用现有 `UpstreamGuard`（https + 公网 IP）与域名白名单做外发闸；抓取失败降级为内部修订，校验自身异常进人工复核而非静默放行。
- 复核队列**不复用条目状态**（条目只有 draft/published），另建 `ai_essay_verifications` 表与状态流，采纳时才 `createCollected`。
- 关闭开关（`verify.enabled=false`）时与现状逐条一致；不回填存量条目。

## 待确认问题

（无。Q1 已于 2026-11-19 定为「只要求事实无误」；Q2 已确认 accept strict。）

## 评测与标注（AC-001 的落地口径）

- 判定标签只有三类：**事实无误 / 事实错误 / 无法判定**；「覆盖考点是否完整」「措辞可读性」不作为判定维度（只作为修订建议，不影响通过）。
- 标注集：从新抓取候选里抽 30~50 条，由人工按上述三类标注，作为基线（现状单发管线）与校验后管线的对比集；样本与标注结果落在 `.agent/changes/WORK-084-面经问答验证型生成管线/eval/`。
- 通过线：校验后「事实错误」占比相对基线下降，且「正确→错误」的正向改坏率不高于 5%（AC-002）。

## 范围变更（2026-11-19，TASK-001 基线后裁决）

- 实测基线（58 条抽样，Java 22 / 前端 18 / 测试 8 / 数据 10）事实错误率 **1.72%（1/58）**，远低于驱动「外部依据检索 + 人工复核队列」的量级。
- 按「只要求事实无误、成本可控」口径缩范围：本期**只实施内部自检管线**（TASK-002/003/004）；**外部依据检索与人工复核队列转为后续可选，不阻塞本期**。
- `always.md` 的「受控例外（联网抓白名单文档）」保留记录，但本期不启用（`verify.external=false`）。
- 受影响验收：AC-003（复核队列）本期不验收；AC-001/002 以「内部自检 + 关闭开关回归」验证；AC-004 不变。
