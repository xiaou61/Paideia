# MCP 网关补全需求

## 本项状态与本轮变化

- **2026-10-27 建项**。用户读 Uber《设计 Uber 的 MCP 管理平台：MCP Gateway》后问
  「他们设计的这个 mcp gateway 我们可以用到吗」与「我们差什么东西呢？是不是可以新开一个 work」。
- 结论是**不照搬 Uber 的四项扩展期特性**（AutoCrawler / 响应投影 / Code Mode / 第三方 server 代理），
  理由是量级与前提都不成立，逐条依据见 `research.md`。
- 本项只收**调研中实测发现、且在本项目量级下真实成立**的缺口。没有一项是"Uber 有所以我们也要有"。
- **2026-10-27 用户五项裁决**（见下），范围已定，可以进入实施。
- 本文件只写期望行为与边界；缺口依据、取舍理由与实测数字在 `research.md`，实现方式在
  proposal / design。

## 已确认事实

2026-10-27 读码与实测（数字均可复算，方法见 `research.md` 的「测量方法」）：

| 项 | 事实 |
| --- | --- |
| 工具总数 | 57 个（56 个业务工具 + `find_tools` 内部元工具） |
| 工具组 | 12 个：`knowledge` `note` `assessment` `learning` `account` `assistant` `sql` 与 6 个 `admin_*` |
| 权限分布 | `ADMIN` scope 41 个；学习者可读约 12 个；学习者可写 4 个 |
| 全量 schema 体积 | 序列化约 **13 KB / 粗估 7.2k tokens**（`/mcp/x/all` 的上界） |
| 外部按需发现 | **无**。`find_tools` 只在内部 harness（`AgentToolBridge`），外部 MCP 未暴露 |
| `outputSchema` | 57 个工具里只有 **2 个**非 null（`note_create`、`assistant_draft_note`） |
| 凭据数量上限 | **无**。`PatService.create` 不做任何计数校验 |
| 凭据级配额 | **无**。只有 `McpRateLimiter` 的 120 次/分钟/token（单实例内存） |
| 凭据用量视角 | **无**。表里只有 `last_used_at`，没有调用次数、工具分布或 token 消耗 |
| 视图缓存 | `ConcurrentHashMap`，键 = `视图名｜工具组｜角色`，**无淘汰、server 从不 close** |
| 外部返回体上限 | **无**。`McpToolInvoker` 不截断，长度只受各工具自身 `limit` 约束 |
| 工具启用开关 | **无**。注册即在权限允许时可用 |
| MCP 指标 | **无**。`McpToolInvoker` 只打审计日志，没有 Micrometer 计数器 |
| 跨域覆盖 | 简历、面试、复习会话、记忆、训练营、知识图谱、速递（学习者侧）、题目作答 **全部为 0 个工具** |
| 前端 | `/settings/mcp` 有凭据页（建/吊销/工具组勾选），**无用量、无配额** |
| 测试 | `paideia-mcp` 单测 34 条；`McpAdminIntegrationTest` 5 条（需真库）；e2e 1 个文件 |

## 用户决定

2026-10-27 五项裁决，逐条对应调研给出的待确认问题：

1. **范围：四个域全做**（简历 / 面试 / 复习 / 记忆）。不缩减为先做一两个。
2. **优先级：Track B 与 Track D 本期就做**，不只做 Track A。
3. **Track C（工具启用开关）本期不做**。理由：我们没有"第二个写工具的人"，也没有工具数破百的规模，
   这一条是 Uber 的组织问题而不是我们的技术问题。等触发条件出现再补。
4. **配额单位：每日调用次数**。不按积分——`assistant_ask` 已经走积分预留-结算，
   再叠一层积分配额会让两套账互相解释不清。
5. **返回体上限**：数值在 design 里定，本项要求"必须存在且截断可见"，不要求先量分布。

## 实现选择

以下由 Agent 依据已批准边界与仓库既有模式选定，记录理由；不替代用户对产品范围的决定。

- **四个域的工具放在各自拥有数据的模块里**，不新建集中的工具模块：`ModularityTest`（Spring Modulith）
  禁止跨模块访问 `internal` 包，硬要集中就得给 `ResumeDocumentService` 等开一圈公开端口，
  而"集中"本身没有价值——工具已经按 `toolset` 分组了。
- **每域只做 2 个工具**（共 8 个，上限 12）：真正高频的是"看一眼我有什么"与"读其中一条"，
  写操作只有记忆域天然需要。不为了凑覆盖度加工具。
- **不做计费类工具**（简历 analyze/propose、面试 review）：它们各是一次真实上游调用、要扣积分，
  外部助手要分析就该用自己的模型。
- **记忆写入用 `rememberText` 而不是 `rememberStructured`**：后者要 `kind` 枚举，
  让外部模型猜我们的内部枚举，猜错的后果是一条归错类的记忆。
- **计数器按 (token_id, day) 分行存在新表**，不在 `mcp_access_tokens` 上加列：
  每日配额要问"今天的计数"，单行累计值靠 `updated_at` 判断跨天有竞态；
  且凭据表每次认证都读，不该成为写热点。
- **返回体截断放在 `McpToolInvoker`**：那里是外部调用的唯一必经之路；
  放各工具里 57 个各写一遍必然漏，放 `McpViewRegistry` 则内部 harness 也会被影响。
- **截断只裁 `text` 不裁 `structured`**：截断 JSON 会让客户端拿到非法结构。

## 待确认问题

以下在实施中已按上文「实现选择」自行决定，**不需要再裁决**，记录在此供复查：

1. **每日配额的日切时区**：按 UTC。与项目"时间一律存 UTC"的约定一致，
   但北京时间用户会在早上 8 点"跨天"。若要改成北京时间日切，改
   `McpToolInvoker` 与 `McpTokenController` 两处 `LocalDate.now(ZoneOffset.UTC)`，
   **两处必须同时改**，风险大于收益，本期不做。
2. **指标是否需要 Grafana 面板**：本期只做到"进 Prometheus 抓取"（实测可抓），
   没加面板。REQ-015 因此只满足一半，已在报告里如实记录。

## 目标

1. 外部助手能用上平台的主要能力，而不只是知识库与笔记：覆盖简历、面试、复习、记忆四域。
2. 一个凭据失控时能被发现和限制：有调用量、有每日配额、有单次返回体上限。
3. MCP 的运行状况能被观测：调用量、错误率、耗时、被拒原因，进既有 Prometheus + Grafana。
4. 上述改动不破坏现有 57 个工具的清单、权限与调用行为。

## 非目标

- **不做 AutoCrawler / IDL 自动发现**：我们是单体、57 个手写工具、带业务语义；自动生成的描述
  会丢掉"这个工具不该替用户写笔记"这类归属约束，正是启动期校验在挡的东西。
- **不做响应投影（GraphQL 式字段裁剪）**：57 个工具只有 2 个有 `outputSchema`。前置条件是先补齐
  结构化输出，那是另一件事，且当前没有消费者提出需求。
- **不做 Code Mode / CLI**：我们是纯 DB 读写、无 shell 环境。本项的"返回体上限"会先把
  "响应是否真的很大"这件事量出来，之后才有讨论依据。
- **不做工具启用开关（原 Track C）**：用户裁决本期不做。工具注册即在权限允许时可用，
  依赖既有的 scope / role / toolsets 三层过滤兜底。
- **不做 OAuth 2.1 授权服务器、动态客户端注册**（沿用 WORK-019 的裁决）。
- **不做 MCP resources / prompts / sampling / elicitation**（沿用 WORK-019）。
- **不做多实例共享限流**（需 Redis；仍是单机单实例）。
- **不做第三方 MCP server 代理**（Uber 的 Jira/Google 场景；我们没有这类接入需求）。
- **不做工具市场、跨用户共享工具、工具版本管理**。
- **不修视图缓存无淘汰**：凭据数在个位数到几十，内存代价以 MB 计；加淘汰要处理
  "正在被请求使用的 server 被关闭"的竞态，修错的代价比不修大。触发条件见 research。

## 需求

### Track A：跨域能力补全（用户能直接感知）

- **REQ-001**：简历域提供工具：列出本人简历、读取简历全文、取得分析结果。只读，归属本人。
- **REQ-002**：面试域提供工具：读取本人面试会话列表与单次评分。只读，归属本人。
- **REQ-003**：复习域提供工具：读取待复习条目与复习计划。只读，归属本人。
- **REQ-004**：记忆域提供工具：列出本人记忆、写入一条记忆。写入属于 `WRITE` scope。
- **REQ-005**：以上四域各自成组（`resume` / `interview` / `review` / `memory`），不与既有组混用；
  组名必须与工具名前缀一致（`ToolCatalog` 启动校验的硬约束）。
- **REQ-006**：新增工具一律不进默认视图（`defaultGroup=false`），学习者默认视图 `/mcp` 的工具数
  必须保持现状不变。
- **REQ-007**：新增工具的数量上限为 12 个；超出时按"用户最可能问"的优先级取舍，不为了凑覆盖度加工具。

### Track B：凭据治理（失控时能被发现和限制）

- **REQ-008**：每个凭据记录累计调用次数、错误次数、最后调用时间；在凭据页可见。
- **REQ-009**：凭据支持每日调用上限（可空 = 不限）；超限后拒绝调用并给出可读原因，不消耗上游。
- **REQ-010**：单个用户的凭据数量设上限 20，创建时超限返回明确错误。
- **REQ-011**：工具返回体设字符上限；超出时截断并附"已截断"标记，不静默丢内容。
- **REQ-012**：计数与配额判定必须与既有 `mcp.audit` 审计日志一致：被拒的调用也要留痕（含拒绝原因）。
- **REQ-013**：配额与计数持久化在数据库，重启后不清零（凭据是长期凭据，重启清零等于没有上限）。

### Track D：可观测

- **REQ-014**：MCP 调用计入 Micrometer 指标：按工具组、结果（成功/工具错误/被拒）计数，按工具记耗时。
- **REQ-015**：指标进既有 Prometheus 抓取，且在 `admin_ops_summary` 或 Grafana 有可见位置。
- **REQ-016**：被拒调用（限流、配额、权限、视图不存在）按原因分类计数，不能都算成一种错误。

### 横切

- **REQ-017**：既有 57 个工具的清单、工具组、scope、只读/破坏性标注、权限过滤结果全部不变。
- **REQ-018**：`ToolCatalog` 启动校验继续通过：无重名、命名前缀与工具组一致、schema 为 object、
  只读与破坏性不矛盾。
- **REQ-019**：所有新工具遵守既有归属纪律：`userId` 只来自 PAT，参数里的归属字段被 `sanitize` 删除，
  越权访问返回"没有找到"而不是区分"不存在"与"不是你的"。
- **REQ-020**：`/settings/mcp` 页面能展示本项新增的可见信息，且不新增需要用户理解的新概念。

## 验收标准

- **AC-001**：外部凭据可以列出并读取本人简历；读取他人简历返回"没有找到"。
- **AC-002**：外部凭据可以读取本人面试会话与评分；不含他人数据。
- **AC-003**：外部凭据可以读取待复习条目与复习计划。
- **AC-004**：外部凭据可以列出本人记忆并写入一条；写入后在学习者端记忆页可见。
- **AC-005**：学习者默认视图 `/mcp` 的工具数与改动前一致，且不含任何新增工具。
- **AC-006**：四个新组各自只返回本组工具；`/mcp/x/all` 含新增的只读工具。
- **AC-007**：凭据页显示每个凭据的调用次数、错误次数与最后调用时间，数字与审计日志条数一致。
- **AC-008**：把某凭据的每日上限设为 N，第 N+1 次调用被拒绝且返回可读原因；上游一次未被调用。
- **AC-009**：创建第 21 个凭据被拒绝，错误信息说明上限。
- **AC-010**：构造一个返回超过上限的工具调用，返回体被截断并带"已截断"标记。
- **AC-011**：配额与计数在应用重启后不清零。
- **AC-012**：Prometheus 能抓到 MCP 调用计数与耗时指标，且被拒调用按原因分开计数。
- **AC-013**：既有 57 个工具的清单与权限过滤结果与改动前逐条一致（快照对比）。
- **AC-014**：`paideia-mcp` 既有 34 条单测与 `McpAdminIntegrationTest` 5 条全部通过。
