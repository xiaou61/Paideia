# 助手对象化提案

## 要解决的问题

用户的原话是「整个系统和 AI 的集成度实际上真的很低」以及「**什么东西都能和我的这个智能助手进行交互**」。
实测现状支持这个判断：学习者端 32 条路由里有 AI 交互的不超过 8 条，而且集中在简历 / 面试 / 训练营三块
"AI 专题"；上下文只接在 3 个地方（条目页的 `entryId`、`/progress` 的 `study-log`、`/practice/sql` 的
`sql-workbench`）；其余 20 多页里打开助手，它不知道你在看什么。

关键不是"少几个按钮"，而是**上下文模型按页面类型建模**：`PageContext` 是 kind 联合，加一个页面就要改类型、
改序列化、改后端措辞。这条结构决定了"铺满全站"的成本高到没人愿意做。

## 两条候选路线

| 路线 | 形态 | 代价 | 事实依据 |
| --- | --- | --- | --- |
| A. 插槽化（每个功能点一个 AI） | 每页一个"生成/总结/解释"按钮，各配一种上下文 kind | 页面数线性增长；模型永远不知道页面上的其它东西；用户必须想到"这里有 AI" | **Moodle 4.5 的做法**（Provider + Placement），也是本项目今天的形态 |
| B. 对象化（`@` 引用 + 工具执行） | 任何对象都是一个 `type:id`，页面只负责递过去；助手用工具操作对象 | 要先有对象 URI 规范与附件栈；写操作要确认闸 | **Continue / VS Code Copilot Chat / Zed / Cursor / Obsidian Copilot** 的做法；MCP Resources 把"URI + 宿主选界面"写进了规范 |

## 推荐：B，但保留 A

理由三条：

1. **用户要的就是 B**（"什么都能和助手交互"），A 无论怎么铺都到不了。
2. **B 的后半段本项目已经有了**：`ToolCatalog`（管理端按组 content 15 / users 6 / review 5 / ai 5 …）
   加上内部 `find_tools` 与外部 `/mcp`。缺的只有"引用"这一半，所以增量比看起来小。
3. **A 不是错**，它是"零思考入口"：摘要按钮、`/progress` 上那三个提问按钮都属这一类。保留它们，
   与 B 并存——B 管"任意对象"，A 管"不用想"。

## 一期做什么（最小可验证）

- 附件模型与序列化（纯函数 + 单测）
- 通用 `<Attach>` + 面板附件条 + 附着即打开面板
- 四页接入：条目正文选区、关卡地图、笔记（含未保存草稿）、到期复习
- 注入边界措辞收口到服务端一处，提示词版本升到 `assistant-chat-v2`

## 一期不做什么

向量检索、自动上下文推断、`@` 选择器、回复引用可点、工具入参吃 uri、写动作确认闸、附件落 `ai_runs.attrs`
—— 全部登记在 `design.md` 的"已知缺口"里，按 3 → 4 → 5 → 2 → 1 的顺序补。

## 成功判据

同一个用户在任意页面上，都能把眼前那一条东西递给助手，助手回答里看得出它读到了；点了之后有可见反馈；
不额外产生一次上游调用（附着 ≠ 发送）。
