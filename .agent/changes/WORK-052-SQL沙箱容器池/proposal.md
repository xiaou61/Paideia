# SQL 沙箱容器池提案

> 本提案在实现与上线之后补齐（2026-10-29），内容按**实际落地结果**编写，不追溯虚构当时的比较过程。
> 需求编号见 `requirements.md`。

## 摘要

SQL 练习每次执行要 3.5–4.2 秒。拆开看：起容器 1.1 秒、拷 78MB 基准 datadir 1.05 秒、
mysqld 初始化约 2 秒，而用户数据集只有 **1.4 KB**。慢的从来不是查询，是"每次都给用户开一台新机器"。

方案是把执行层从"一次性容器"换成"常驻容器池"：预热后每次执行只做
建库 → 建受限账号 → 灌数据集 → 跑 SQL → 删库删账号。实测端到端降到 **0.35–0.42 秒**，
沙箱内 `durationMs` **226–290 ms**。

## 推荐方案

**N 个常驻容器 + 每次执行一个临时库与一个受限账号**（N 默认 2，配置项 `sandbox.sql-pool-size`）。

核心机制三件：

1. **容器常驻**：启动脚本拷一份基准 datadir、起 mysqld、然后 `sleep` 保持存活；省掉每次的
   起容器、拷 78MB、mysqld 初始化三段固定成本。
2. **执行期隔离**：每次执行生成唯一的库名与账号名，`GRANT ALL ON <库>.* TO <账号>@localhost`，
   执行结束（成功或失败）删库删号。口令走 `MYSQL_PWD` 环境变量，不上命令行。
3. **回落是设计的一部分**：池关闭/拿不到槽位/容器异常/执行超时，一律返回 empty，
   由 `DockerCodeRunner` 继续走原来那条一次性容器路。SQL 练习不能因为池而不可用。

归属：全部改动在 `paideia-sandbox` 一个模块内，不新增表、不改接口形状、不改前端。
唯一外溢是部署配置新增三个 `sandbox.*` 键。

## 范围

- 只动 SQL 执行路径（普通查询与 `EXPLAIN FORMAT=TREE` 两条脚本），Java/Python 的代码沙箱不动。
- 不改判题口径：仍是 `--xml`，`NULL` / `DECIMAL` / 多结果集语义不动。
- 不改配额、不改墙钟上限（`sqlTimeoutMs` 仍是 20 秒）。

## 备选方案

| 方案 | 最强的理由 | 为什么没选 / 放弃了什么 |
| --- | --- | --- |
| **现状：一次性容器，不改** | 隔离最强：一人一个容器，别人的 SQL 连"库名"都看不到 | 4 秒里 3 秒多是固定成本，用户体感是"点一下等 4 秒"。放弃它换来 10 倍延迟 |
| **复用容器但每次重启 mysqld** | 保住容器级隔离，不放松任何边界 | 只能把 4 秒压到约 3 秒，因为 mysqld 初始化本身约 2 秒。目标"毫秒级"达不到 |
| **池化 + 共享只读账号（或 root）** | 能到约 150ms，比落地的 250ms 再快 100ms | 同容器内用户之间只剩"库名"一层，`SHOW DATABASES` 能看到别人的临时库。用隔离换 100ms 不值得，未采纳 |
| **池化 + 每次独立库与受限账号（采纳）** | 省掉全部固定成本，同时保留账号级隔离 | 代价：多用户共享一个 mysqld，一个用户的查询可能把 mysqld 弄挂、连带同容器的其他人。用健康判定 + 容器替换 + 回落兜住 |

## 风险与缓解措施

| 风险 | 缓解 |
| --- | --- |
| 一个用户的 SQL 把 mysqld 弄挂，同容器其他人一起失败 | 执行异常即销毁该容器，下一个请求重建；本次请求回落一次性容器 |
| 并发：2 个容器、每容器 1 并发，第 3 个并发的请求 | 拿不到槽位最多等 `sqlPoolAcquireTimeoutMs`(1500ms) 就回落一次性容器——慢但确定，而不是排队到未知时长 |
| 内存：容器里 tmpfs 的 datadir 计入内存，512m 时 mysqld 被静默 OOM | `sql-memory` 默认 1g，`--memory-swap` 同步给；这个缺陷已在线上踩到并修掉 |
| 长跑后 mysqld 内存增长 / 日志膨胀 | 未测（只跑了不到一小时）。无空闲回收；症状会是执行变慢或容器被 OOM，届时靠容器替换兜底 |
| 泄漏：临时库与账号没删干净 | 执行结束无条件 `DROP DATABASE IF EXISTS` + `DROP USER IF EXISTS`；20 次连跑后实测 0 残留库 0 残留账号 |
