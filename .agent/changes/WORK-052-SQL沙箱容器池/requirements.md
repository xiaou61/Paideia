# SQL 沙箱容器池需求

## 目标

把 SQL 练习的执行时间从**秒级降到毫秒级**。

线上实测（2026-10-28，同一句 `SELECT COUNT(*) FROM orders` 连跑三次）：
**3.80 / 4.24 / 3.47 秒**，接口自报 `durationMs=3256`。同一 token 打分类树接口只要 145 毫秒。

拆开之后，这 4 秒花在这几件事上——**每一件都是"因为容器是新的"**：

| 阶段 | 实测 |
| --- | --- |
| `docker run` 起容器 | 1.1 秒 |
| 容器内 `cp -a /opt/datadir-base /tmp/data`（78 MB）+ chmod | 1.05 秒 |
| mysqld 初始化 InnoDB 到能接受连接 | 约 2 秒（代码注释：启动 mysqld 本身就要 3 秒上下） |
| 灌数据集 + 跑用户 SQL | 几十毫秒（数据集只有 **1.4 KB**） |

**结论：慢的不是查询，是"每次都给用户开一台新机器"。**

## 非目标

- **不改判题口径**：结果仍是 `--xml`，`NULL` / `DECIMAL` / 多结果集的语义一个都不动。
- **不改前端**：接口形状与配额口径不变。
- **不做多机调度**：池只在本机，不跨机器。
- **不放松容器参数**：`--network=none`、`--read-only`、`--cap-drop=ALL`、`--pids-limit`、
  `--secure-file-priv`、`--local-infile=0`、`--skip-log-bin` 全部保留。

## 这个需求必须先承认的代价

> **隔离从"每次一个干净容器"降为"多用户共享一个 mysqld，靠数据库隔离"。**

这是本项唯一真正重要的取舍，写在这里以免被当成纯性能优化：

1. **同实例的其他库对这个连接是可见的**（现在连的是 root）。所以**必须**为每次执行建一个
   独立 MySQL 账号，只授权给本次的库，执行完连同库一起删。不做这件事，池化就等于把
   所有用户的临时库放在一起互相可见。
2. **一个用户的 SQL 可能把 mysqld 弄挂**（递归 CTE 打满、超大排序爆内存）。容器级内存上限
   仍在，但一旦 mysqld 挂了，**同容器里并发的其他人一起失败**。所以需要健康检查、摘除与重建。
3. **CPU/内存从"独占"变成"共享"**：`--cpus=1` 现在是几个用户分。必须限制每个池容器的
   并发执行数，否则一个慢查询会拖慢同容器的所有人。

## 已确认事实

| 项 | 事实 | 依据 |
| --- | --- | --- |
| 每次执行都起新容器 | `docker run` + `cp -a` 78MB datadir + 起 mysqld + 灌数据 + 查询 | `DockerCommand.SQL_SCRIPT` |
| 数据集极小 | `orders-public.sql` 只有 **1.4 KB**（3 表 12 列、几行数据） | 文件大小 |
| 容器限制写死 | `--cpus=1`、`--memory=512m`、`--pids-limit=128`、只读根、tmpfs 768m | `SandboxProperties` |
| 墙钟上限 20 秒 | `sqlTimeoutMs=20000`，注释里写明"启动 mysqld 本身就要 3 秒上下" | 同上 |
| 有两条脚本要一起改 | 普通执行与 `EXPLAIN FORMAT=TREE` 各一份，只差最后一行 | `SQL_SCRIPT` / `SQL_EXPLAIN_SCRIPT` |
| 每日配额 | 每人 SQL 500 次/天，另一档 1000 | `/sandbox/status` 实测 |

## 实现选择

已按下面的形式落地（`SqlContainerPool`，317 行）：

- **池 = N 个常驻容器**，每个容器里 mysqld 已就绪。每次执行只做：建库 → 建受限账号 → 灌数据集
  → 跑 SQL（或 EXPLAIN）→ 删库删账号。库名与账号名每次执行唯一，口令走 `MYSQL_PWD`
  环境变量而不是 `-p`（`-p` 会把口令留在他人的命令行上）。
- **每次执行一个库名 + 一个账号**，账号只对该库有权限。这是池化的**前置条件**，不是可选项。
- **池耗尽时最多等 `sqlPoolAcquireTimeoutMs`（默认 1500ms），超时直接回落一次性容器**，
  而不是排队——排队会让 p99 变得不可预测。
- **健康检查放在冷路径**：容器一旦就绪就信任它，健康由真正的执行判定（`docker exec` 报
  「容器不存在/没在跑」才回收并重建）。原先每次执行前 ping 一次，实测这台机器上
  `docker exec` 偶超 3 秒，一次超时就把健康容器判死、一半请求回落，比不做池化还慢。
- **回落路径保留**：Docker 不可用、池起不来、池内执行异常，一律走现有的
  "起一个干净容器"那条路——功能不能因为池而不可用。
- **配置项**：`sql-pool-size`（默认 2，0 = 关闭池化）、`sql-pool-acquire-timeout-ms`（默认 1500）、
  `sql-memory`（默认 1g，512m 会让 mysqld 被 OOM 静默杀掉）。

## 功能需求

- **REQ-001** 预热后的 SQL 执行：沙箱内 p50 ≤ **300 ms**、p95 ≤ 600 ms；端到端（含公网往返）
  p50 ≤ 500 ms（线上实测，同一查询）。
  *原目标 p50 ≤ 150ms 未采纳*：实测差的那约 100ms 是每次执行建/删受限账号的成本，
  压掉它就必须放弃 REQ-002 的"每次一个受限账号"，等于放宽隔离——不拿安全边界换体感。
- **REQ-002** 每次执行使用**独立的库与独立的数据库账号**；执行结束（成功或失败）必须清理。
- **REQ-003** 任何一次执行都看不到别的用户的库：`SHOW DATABASES` 只能看到自己的与系统库。
- **REQ-004** 池内执行失败 / 容器不健康 / 池耗尽超时 → 回落到一次性容器，用户侧不报错（除既有超时语义）。
- **REQ-005** 容器数量稳定：连续 20 次执行后 `docker ps` 的池容器数不变，无泄漏。
- **REQ-006** 两条路径都受益：普通执行与 `EXPLAIN` 走同一个池。
- **REQ-007** 容器参数一个都不放松（见非目标）。
- **REQ-008** 保留每次执行的审计记录字段（`durationMs`、退出码、超时/内存标记）。

## 质量要求

- 池的容量、单容器并发数、空闲回收时间是配置项，不是写死的常量。
- 池自身要有可观测性：当前空闲数、使用中数、重建次数——至少打日志，能回答"为什么这次慢了"。
- 并发正确性：同一毫秒内两个请求不能拿到同一个库名。

## 约束与依赖

- 依赖宿主有 Docker；本机开发环境没有 Docker，所以**本项的真实验证只能在服务器上做**。
- 依赖既有的配额与墙钟语义，不新增配额维度。

## 验收标准

- **AC-001** 同一查询连跑 10 次，沙箱内 p50 ≤ 300ms、p95 ≤ 600ms，端到端 p50 ≤ 500ms（线上实测）。
- **AC-002** 执行中的用户在 `SHOW DATABASES` 里看不到其它用户的库（要有真实断言，不是"设计上应该"）。
- **AC-003** 杀掉一个池容器后，下一次请求仍然成功（自动重建或回落）。
- **AC-004** 连续 20 次执行后池容器数不增长，库里也不留 `practice_*` 残留。
- **AC-005** `EXPLAIN` 路径同样 ≤ 400ms。
- **AC-006** 池全部不可用时，SQL 练习仍能执行（回落路径），只是慢。
- **AC-007** 结果与现在逐字节一致：同一批 SQL 的 XML 输出与改造前相同。

## 假设

- 一次查询本身在毫秒级（数据集只有 1.4 KB），所以池化后的耗时主要由进程启动与 SQL 客户端开销构成。
- 池容器数与并发上限可以按 4 核机器定一个小值（例如 2–4 个容器、每容器 1 并发）。
