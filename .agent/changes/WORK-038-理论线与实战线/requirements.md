# 从零开始分层：理论线与实战线需求

## 目标

把「从零开始」从"一张扁平的轨道列表"变成两条目的明确的路，并先把"学完能验收"这件事做通：

1. **理论线**：读完能解释、能判断、能做对选择题。产出是理解。
2. **实战线**：做完有一个能验收的东西（跑出正确结果的查询、通过的检查、能演示的功能）。产出是作品。
3. **分类不做门禁**：理论不拦实战，用户可以从任何一边进。顺序由排列与文案表达，不靠锁。
4. **理论侧今天无法"完成"**（阅读线没有动手题，而通过判定要求两类记录都有），本项修掉它。

## 本项状态与本轮变化

- **2026-10-26 建项起草（draft）**，只写需求，不改代码。
- 起因：用户提出"理论放理论、实战放实战"，并追问"实战该弄什么、理论该弄什么"，最后确认「全部都要弄」。
- 讨论中确认的一条：**不做"理论完成才解锁实战"**。理由是它和 2026-10-26 刚做的「关卡全部默认解锁」（`ee5a074`）是同一种机制，而现有数据模型只在轨道内部表达前置，跨轨道依赖要另加一套语义。

## 用户决定

- **2026-10-26**：分成理论与实战两类，理论放理论、实战放实战。
- **2026-10-26**：不做"理论完成才解锁实战"的门禁。
- **2026-10-26**：四类实战（SQL、读代码、调试、项目式）与四块理论补充「全部都要弄」。
- **2026-10-26**：沙箱限流都提到 **1000**（代码与 SQL 各 1000）。
- **2026-10-26**：四个待确认问题一起定，按以下口径实现：
  1. 理论完成**只认小测 ≥80%**，不引入"读完"这种不可靠信号；
  2. 实战**不进复习排期**（复习的对象是概念，实战的产出是作品）；
  3. 项目式实战**只做 Java 与 Python**（沙箱已有镜像），SQL 项目由 SQL 实战线覆盖；
  4. 项目式实战**不允许运行时联网**，第三方依赖只用镜像预装。

## 实现选择

- **分类用字段不用新表**：`learning_tracks` 增加 `mode`（theory / practice），默认 theory。理由：现有 `kind` 表达的是载体形态（有无可运行代码），和"理论/实战"是两个正交轴，改语义会波及导入脚本与既有 14 条轨道。
- **配对靠引用不靠层级**：实战轨道可用一个可空字段指向它假定的理论轨道（展示"建议先看 X"，不产生门禁）。
- **完成判定按 mode 分支**：理论＝小测每块 ≥80%；实战＝该轨道的验收项全部通过。既有课程的"动手+小测都过"语义保持不变。
- **实战形态分级落地**：SQL（基础设施已有）→ 读代码（块已有）→ 调试（run 题型，不改沙箱）→ 项目式（改沙箱，最后做）。
- **项目式实战放最后**：它是唯一需要放开多文件与构建工具的一项，安全面与资源面都要重新定，不能和内容一起做。

## 需求

### 分类与导航

- **REQ-001**：`learning_tracks` 增加 `mode` 列（`theory` / `practice`），已有 14 条轨道全部迁为 `theory`；导入脚本从 frontmatter 的 `line_mode` 读取，缺省 `theory`。
- **REQ-002**：`GET /learn/tracks` 返回 `mode`；`/learn` 分两栏（理论 / 实战），每栏独立显示条数与进度；实战栏为空时显示明确空状态，不是空白。
- **REQ-003**：实战轨道可声明 `theoryTrackSlug`（可空）；地图页在标题下显示「建议先看 X」的可点链接。**这是提示，不构成限制**。
- **REQ-004**：新增实战入口要同时进导航栏或账号菜单，并按既有规则给 `@paideia/identity` 的 `preferredNav` 补 key（联合字面量，不加编译不过）。

### 完成判定

- **REQ-005**：理论轨道的关卡，只要小测每块 ≥80% 即算通过，不要求动手题。**该规则只对 `mode=theory` 生效**。
- **REQ-006**：实战轨道的关卡按轨道声明的验收方式判定（SQL 判题全对 / run 题型输出一致 / 项目式验收通过）；未声明验收方式的实战关卡不允许保存。
- **REQ-007**：既有 3 门课的判定语义不变（动手 + 小测都过）；已 `passed` 的记录不因本项被降级。
- **REQ-008**：理论关卡通过后仍进入既有复习排期（1/3/7/21 天），与课程一致。

### SQL 实战

- **REQ-009**：新增一条 SQL 实战轨道，8–10 道递进题（筛选与空值、聚合、多表、窗口、留存/复购），每题带参考 SQL、反模式与期望哈希，隐藏数据集参与判定。
- **REQ-010**：期望哈希由既有脚本生成并与前端判题逐字节一致（`sql_judge.py` 与 `sql-judge.ts` 的规范串口径不变）。
- **REQ-011**：修正 SQL 日限的配置漂移——线上是 `20`，与 WORK-035 REQ-020 定的 500 不一致。该项只改配置，不改代码默认值。

### 读代码实战

- **REQ-012**：新增至少一条读代码实战轨道，用 `code-tour` / `code-map` 块组织，选题必须来自真实代码（本仓库或公开开源项目），并在文末标明来源与许可。
- **REQ-013**：读代码实战不依赖代码执行；沙箱不可用时仍可完整作答。

### 调试实战

- **REQ-014**：调试实战用 `run` 题型实现：给一段有缺陷的代码与期望输出，用户改到输出一致即通过。**不引入测试框架，不改沙箱执行协议**。
- **REQ-015**：调试题的初始代码必须真能跑（不报语法错），缺陷是逻辑/边界问题；每题的期望输出要说明"为什么是这个值"。

### 项目式实战

- **REQ-016**：沙箱支持一次提交**多个文件**（含入口文件与允许的依赖声明），在隔离容器内构建并运行，返回构建失败与运行失败两类可读结果。
- **REQ-017**：项目式实战的验收由**预置测试**判定，不依赖 AI 评分；测试通过即通过，失败要指出失败的用例名而不是只给一句"不通过"。
- **REQ-018**：多文件执行必须设资源上限（文件数、总大小、CPU 时间、内存、输出大小），超限返回明确原因；镜像与依赖来源受控，不允许运行时联网拉包。

### 理论补充

- **REQ-019**：新增四块理论线——并发、JVM、数据库原理、系统设计与分布式，每条 5–6 篇，格式与既有阅读线一致。
- **REQ-020**：新增理论线与新增实战线要在同一次导入里成对出现（理论 + 对应实战），不允许只有理论没有实战的配对声明。

## 验收标准

- **AC-001**：`/learn` 分两栏，理论栏 14+ 条、实战栏至少 3 条；两栏的条数与进度各自正确。

- **AC-003**：一条只有小测的理论关卡能通过，`learning_progress.status='passed'` 且 `review_due_at` 被写入（需反向验证：把该关的小测改成 79% 不通过）。
- **AC-004**：课程关卡仍要求动手 + 小测都过（挑一门课做回归，改前改后断言语义一致）。
- **AC-005**：SQL 实战 10 题在线上全部可判，正确答案通过、反模式答案不通过（逐题跑一遍，记录通过与否）。
- **AC-006**：读代码实战在 `/sandbox/status` 为不可用时仍能完整作答。
- **AC-007**：调试实战至少 3 题，初始代码可运行、错误答案不通过、修正后通过。
- **AC-008**：项目式实战提交 3 个文件能构建运行；提交 21 个文件被拒并给出原因；运行超时被终止且返回可读原因。
- **AC-009**：`GET /learn/tracks` 在实战栏为空时不报错，前端显示空状态而不是空白页。
- **AC-010**：新增入口出现在导航栏并可点达（逐条对照 `router.tsx` 与 `NAV`）。
- **AC-011**：全量后端测试、学习者端 e2e、线上 e2e 均无新增失败。
