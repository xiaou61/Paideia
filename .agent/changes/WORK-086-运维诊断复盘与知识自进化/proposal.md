# 运维诊断复盘与知识自进化 提案

## 摘要

不推翻 WORK-042/043/049/085 的诊断链路，补三层：

1. **证据说人话**：把证据窗口从「现在 − 1 小时」改成「事件发生的那段时间」，日志分「异常/生命周期/上下文」三段采集，补上重启、连接池、OOM、负载这几组能解释「为什么」的指标，模板为空时用应用侧签名兜底。
2. **报告可读**：邮件升级为 `multipart/alternative`，HTML 由 Markdown 渲染（内联样式），附 `.md` 附件；报告格式仍是 Markdown，管理端渲染不变。
3. **复盘与知识闸门**：诊断 → 一键生成复盘草稿 → 人工编辑 → **确认入库** → 只把 APPROVED 的复盘注入后续诊断，并记录「这次参考了哪几条复盘」。

一句话：**让诊断看得见现场，让经验只在被确认后才复用。**

## 方案取舍

### 邮件渲染

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 自写极简 Markdown→HTML | 零依赖 | 表格、嵌套列表、代码块要自己兜；边界一多就是长期维护面 | 否 |
| **commonmark-java + 内联样式后处理** | 成熟、Apache-2.0、无传递依赖、表格扩展独立 | 多一个依赖（约 1 MB） | **选** |
| 无头浏览器截图后内嵌 | 保真 | 多一个进程/依赖，邮件里不能选中文字，体积大 | 否 |
| Thymeleaf 模板 + 手工解析 Markdown | 样式最可控 | 等于自己写解析器 | 否 |

HTML 只用**内联 style**（邮件客户端会剥 `<style>`），渲染后对 `h2/table/th/td/pre/code/blockquote` 做一次属性注入；纯文本版本保留现有 `toPlainText` 作为兜底。

### 知识载体

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 直接检索历史 `ops_diagnoses.report_md` | 零新表 | 报告是「当时的猜测」，无法人工修订；没有审批状态；混入未验证结论 | 否 |
| **独立 `ops_postmortems` 表 + APPROVED 闸门** | 可编辑、可审批、可归档；检索面干净 | 多一张表与一套 CRUD | **选** |

### 知识检索

- 用 MySQL FULLTEXT（`WITH PARSER ngram`）匹配「告警名 + 根因关键词 + 日志签名」，再叠加「同 alertName 最近 N 条」的结构化过滤。
- 不用向量检索：项目规则明确本期不做（`.agent/rules/always.md:29`），且复盘量级（几十到几百条）用全文 + 结构化过滤足够。

### 证据窗口

| 方案 | 问题 |
| --- | --- |
| 保持 `now − 1h` | 事件持续 > 1h 或延迟诊断时窗口错位；看不到重启前后的因果 |
| 只用告警 `startsAt` | 手动诊断/模板触发没有告警时间 |
| **incident.first_seen 优先，降级触发时刻** | 需要给 `collect()` 传窗口；改动面可控 |

## 切片

### 切片 A：证据说人话（REQ-001~004）

- `OpsEvidenceCollector` 接受 `EvidenceWindow`（start/end/来源），日志三段查询、每 unit 配额、签名去重；新增指标与重启聚合；`formatTraces` 用同一窗口。
- 独立可验证：拿 2026-11-19 14:10–14:30 的真实窗口跑一次手动诊断，证据里必须出现 4 次重启。
- 不改表、不改前端、不改邮件 ⇒ 单独部署即可见效。

### 切片 B：报告可读（REQ-005）

- 新增 `OpsDiagnosisEmail.html(...)` + `conclusion(...)`；`OpsDiagnosisMailer` 改 multipart + 附件；`pom` 加 commonmark。
- 独立可验证：本地/测试 SMTP 收信看 HTML；断网/渲染异常时仍收到纯文本。

### 切片 C：复盘与知识闸门（REQ-006~008）

- 迁移建 `ops_postmortems`、`ops_diagnoses` 加 `knowledge_ids`；`PostmortemService/Mapper/Controller`；前端复盘编辑/列表页；诊断时召回注入。
- 依赖 A（签名/窗口用于召回），但不依赖 B。
- 独立可验证：走一遍「诊断 → 生成复盘 → 编辑 → 确认 → 下次诊断带 `<knowledge>`」。

### 横切：安全与降级（REQ-009/010）

- 每个切片自带：ADMIN + 回环、redactor、失败降级、日志字段。不单独排期。

## 依赖与顺序

1. 切片 A 先做（B、C 的证据质量都依赖它）。
2. 切片 B 与 C 可并行，但 C 的验收要用 A 的证据。
3. C 依赖 WORK-085 的 FULLTEXT 索引（已上线）。

## 风险与回滚

| 风险 | 回滚方式 |
| --- | --- |
| 证据变长导致诊断变慢/贵 | 配置项 `paideia.ops.diagnosis.evidence-window-minutes` 与分段配额可回退到旧值；最坏把 `logs-mode` 切回 `errors-only` |
| HTML 邮件被判定为垃圾邮件 | 配置 `paideia.ops.mail.html-enabled=false` 一键回纯文本 |
| 复盘被误确认 | `ARCHIVED` 立即退出检索；`knowledge_ids` 能定位哪次诊断用了它 |
| 迁移失败 | 只有新增表/新增列，不改既有列；回滚 = 停用端点，表保留无害 |

## 工作量粗估

| 切片 | 后端 | 前端 | 迁移 | 测试 |
| --- | --- | --- | --- | --- |
| A 证据 | 中（采集器重构 + 指标目录） | 无 | 无 | 单测 + 真实窗口回放 |
| B 邮件 | 小（渲染 + multipart） | 无 | 无 | 单测 + 收信实测 |
| C 复盘/知识 | 中大（CRUD + 召回 + 注入） | 中（两页 + 入口） | 1 个迁移 | 单测 + 隔离测试 |

## 不做什么

- 不做自动修复/自动重启/自动改 prompt。
- 不做向量检索、跨主机采集、日志长期归档。
- 不把复盘写进 Git，不做对外分享链接。
