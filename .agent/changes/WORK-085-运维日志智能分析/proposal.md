# 运维日志智能分析（AIOps 补齐）提案

## 摘要

在**不推翻** WORK-028/042/043/049 现有运维体系的前提下，补齐文章里唯一缺的两层——**日志模板聚类**与**基于模板频次的异常检测**——并把它做成结构化证据喂给现有 LLM 诊断。聚类按用户定向放在 **Loki 侧**（启用 Loki 3.7 的 pattern ingester，DPL/Drain 算法），应用侧 `paideia-ops` 只做「读模板/频次 → 判三类异常 → 组证据 → 入库/触发诊断」，不重写聚类引擎、不新增常驻进程、不把原始日志直灌模型。全量纳入 REQ-001~010。

## 推荐方案

**分层落点（对齐文章分工：日志平台存查、聚类降噪、异常检测找偏离、LLM 只解释）：**

1. **采集/清洗（沿用）**：journald → Alloy → Loki 不动；仅确认日志里带稳定字段（level、traceId、logger、关键业务字段）供模板抽取（REQ-001 只做「核对+补字段」，不新建采集）。
2. **聚类（Loki 侧）**：在 `deploy/ops/loki-config.yaml` 启用 `pattern_ingester`（Loki 3.7 DPL/Drain 聚类），把日志聚成模板并产出 `loki_patterns_*` 指标；在 Grafana 加一块「日志模板/频次」面板做人工可见。这是 REQ-002 的落点。
3. **模板库与基线（应用侧 MySQL）**：`paideia-ops` 新增周期性「模板同步器」，从 Loki pattern API / `loki_patterns_*` 指标拉当前窗口的模板与频次，落 MySQL（模板表 + 按时的频次基线表 + 异常事件表），手写 MyBatis、迁移用 14 位时间戳（REQ-003）。
4. **三类异常检测（应用侧）**：在 `paideia-ops` 新增 `PatternAnomalyDetector`，按 REQ-004 判：①模板频次显著偏离基线 ②新模板出现 ③模板突然消失。判定结果落「异常事件表」并写一条 `ops-textfile` 指标供 Grafana 展示与告警（REQ-004/006）。
5. **证据接入诊断（复用现有骨架）**：扩展 `OpsEvidenceCollector`，新增「日志模板摘要」证据段（Top 模板 + 异常模板 + 时间线），仍受现有 `maxEvidenceChars`/`maxLogLines` 约束；`OpsDiagnoser` 只读这段压缩摘要，不读原始日志（REQ-005）。异常事件可复用 `OpsDiagnosisService` 的冷却/单飞/邮件闭环触发一次诊断（REQ-006）。
6. **结构化知识闭环（不向量化）**：异常事件表 + 诊断结论 + 人工 helpful 评分（WORK-043 已有）构成可检索历史，检索走 MySQL 全文（REQ-007，遵守「本期不做向量化」）。
7. **最小服务拓扑**：以一份配置/小表维护 app → MySQL / Redis / RustFS / Laya / Tempo 的依赖，供诊断「影响面」说明，不引入 CMDB（REQ-008）。
8. **可降级与成本**：pattern ingester 未启用或 Loki 不可达时，证据标「未知」、诊断照常（REQ-009）；LLM 调用纳入 WORK-009 计费与封顶（REQ-010）。

**为什么最满足需求**：把最贵、最不准的「LLM 读原始 TB 级日志」换成「读几十~几百条模板摘要」，同时复用已有采集、告警、诊断、评分四条链路，新增面最小；且聚类放在 Loki 内建能力上，避免重复造轮子。

## 范围

- 做：REQ-001~010 全部；Loki pattern ingester 启用与容量实测；`paideia-ops` 模板同步/三类检测/证据扩展/新表与新迁移；Grafana 模板面板与异常指标；MySQL 全文检索的知识闭环；最小拓扑。
- 不做：替换现有监控栈；AI 自动修复；多机/集群 AIOps；向量库/语义检索（除非另获裁决）。

## 备选方案

- **A. 全应用内 Java 聚类（自实现 Drain）**：最灵活、可深度定制。放弃原因：重复造轮子、需把日志整批拉进应用（带宽/内存/正确性风险大），且用户已定向 Loki 侧；Loki 内建 DPL 更省。
- **B. 独立聚类服务（如外挂 Vector/自建分析进程）**：隔离性好。放弃原因：单机场景多一个常驻进程的 systemd/内存/端口运维成本，收益不抵复杂度。
- **C. 纯 Grafana 告警规则（不自建检测）**：最省事。放弃原因：「新模板出现」「模板消失」在 PromQL 里表达繁琐且无法产出结构化证据喂 LLM；仅作为展示/告警补充。
- **D. 现状（固定 LogQL 错误计数 + 周对比）**：就是当前，正是本项要填的缺口——它只回答「有没有错误」，回答不了「哪类日志变了、变了多少、什么消失了」。

## 交付拆分

1. **切片一（可见性）**：启用 Loki pattern ingester + Grafana 模板面板 + 容量/内存实测。可独立验证（能看到模板与频次）。
2. **切片二（模板库+检测）**：`paideia-ops` 模板同步 + 三张表/迁移 + 三类异常检测 + 单测/构造用例。可独立验证（AC-002）。
3. **切片三（接入诊断+告警）**：证据段扩展 + 异常触发既有诊断闭环（冷却/单飞/邮件）。可独立验证（AC-003/004）。
4. **切片四（知识闭环+拓扑）**：MySQL 全文检索知识闭环 + 最小服务拓扑。可独立验证（REQ-007/008）。

## 风险与缓解措施

- **Loki pattern ingester 属较新/实验特性**：先小流量开启、设内存上限、灰度观察，若不稳定可一键关闭回到现状（REQ-009 的开关就是为此）。
- **模板基数爆炸**：限制模板库容量与保留，按频次截断，仅保留 Top-N + 异常模板。
- **误报/噪音**：阈值初期保守、先观察一周再收紧；异常事件先只告警不自动改任何东西。
- **成本**：LLM 只吃模板摘要，显著低于读原始日志；纳入 WORK-009 封顶。
- **脱敏**：模板抽取与证据组装前做脱敏，凭据/令牌/PII 不入模板库、不入证据、不入响应。
