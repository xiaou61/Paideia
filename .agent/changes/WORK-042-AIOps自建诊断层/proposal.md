# AIOps 自建诊断层提案

## 摘要

在现有 WORK-028 的指标/告警/运维页之上，补两块：**日志数据面**（Loki + Alloy + 30 天留存）与**诊断面**（确定性采集证据 + 一次 DeepSeek 调用 + 报告落库）。不引入外部 AIOps 平台，不替换任何现有组件。

## 推荐方案

### 核心机制

1. **数据面**：Prometheus 保留期 3d → 30d；新增 Loki（单机、文件系统存储、30d）与 Alloy（读 journald、只采白名单 unit）；Grafana 增加 Loki 数据源；新增 5xx 比例与 ERROR 日志两条告警；发版后写部署时间指标。
2. **诊断面**：管理端按钮或 Grafana webhook 触发 → 应用在后台按固定查询采集「摘要 + 指标 + 日志 + 告警 + 最近发版」→ 脱敏并限制长度 → 一次 DeepSeek 调用 → 报告写入 `ops_diagnoses` → 管理端展示。
3. **工具面**：把同一批只读查询包成 `admin_ops_metrics` / `admin_ops_logs` / `admin_ops_alerts`，复用现有工具目录；外部 MCP（管理员 PAT + admin scope）可调用。内部学习者助手按既有行为只拿 READ scope，不暴露 ADMIN 工具。

### 为什么是它

- **成本有上界**：一次诊断固定一次调用、输入有硬上限；不轮询、不做工具循环。告警风暴由冷却窗口与单飞挡住。
- **复用最大**：积分、遥测、凭据、SSRF 防护、工具目录、MCP 权限、管理端外壳全部现成。新增代码集中在"采集 + 编排 + 展示"。
- **可验证**：证据是确定性生成的，报告可以逐条对照证据；不需要"模型自己找到数据"这种不可复现的路径。
- **安全边界清楚**：模型只能读我们给它的文本；没有写工具、没有 shell、没有 PromQL/LogQL 拼接。

## 范围

### 做

- Prometheus 30 天保留。
- Loki + Alloy 安装、配置、数据源、日志告警。
- 发版标记指标。
- 三个只读运维工具。
- 手动诊断 + webhook 诊断 + 历史报告。
- 脱敏、积分、遥测、冷却、单飞、开关。
- 管理端诊断区与日志入口。

### 不做

- Tempo/链路、ML 异常检测、告警关联平台、自动修复。
- HolmesGPT / Keep / SigNoz / Netdata。
- 多主机、多实例、日志全文搜索 UI（Grafana Explore 足够）。
- 修改现有四条告警的阈值与语义。

## 备选方案

### A. 多轮工具循环（Agent 自己查）

让模型通过工具反复查 Prometheus/Loki 直到得出结论。

- **最有力的理由**：遇到未预料的故障时更灵活，能顺着线索追下去。
- **为什么没选**：单机栈的查询空间很小，预置目录已覆盖；多轮调用成本与延迟不可控，DeepSeek 的工具调用行为存在已知限制；诊断结果的可复现性差，测试难写。需要追问时，管理员仍可用助手 + 三个工具自行调查。

### B. HolmesGPT 外挂

部署 HolmesGPT，接 Prometheus/Loki/MySQL，由告警触发调查。

- **最有力的理由**：现成的 SRE 调查循环、30+ toolset、CNCF 项目，少写调查逻辑。
- **为什么没选**：用户已裁决自建。额外 Python 运行时与升级路径；它的优势在 K8s/多云复杂度，我们只有一台机、五个 unit；输出还要适配我们的页面/积分/审计。

### C. Keep 做告警中台

- **最有力的理由**：告警去重、关联、工作流是它的主场。DeepSeek 也是官方支持的 AI 后端。
- **为什么没选**：当前只有 6 条告警（4 旧 + 2 新），去重/关联没有收益；要自带 DB 与 UI，维护成本大于收益。等告警量或接入系统数量上来再评估。

### D. 维持现状，只加日志

- **最有力的理由**：改动最小，零 AI 成本。
- **为什么没选**：用户要的是 AIOps 的诊断能力；只有日志没有判断，仍然要人肉看。

## 仓库影响

| 区域 | 影响 |
| --- | --- |
| `deploy/ops/` | Prometheus 保留期、Loki/Alloy 配置与单元、Grafana 数据源、告警规则与收件人、安装脚本 |
| `backend/paideia-ai/` | 新增 `OpsDiagnoser` 公开端口、诊断提示词、一次性调用实现、流水种类与结算方法、`RunKind` |
| `backend/paideia-app/` | `ops` 包新增 Loki 客户端、脱敏、证据采集、诊断编排、表与 mapper、控制器、三个工具；新增迁移 |
| `frontend/apps/admin/` | 运维页新增诊断区、历史列表、日志入口 |
| `scripts/release.ps1` | 发版成功后写部署标记指标 |

不改动学习者端；不改动现有 API 的返回字段。

## 交付拆分

1. **切片 1（数据面）**：保留期、Loki/Alloy、Grafana 数据源、两条告警、发版标记。完成后日志可查、告警可发。
2. **切片 2（手动诊断）**：AI 端口、证据采集、脱敏、诊断表、手动端点、管理端诊断区、三个工具。完成后管理员可手动诊断，外部助手可查运维数据。
3. **切片 3（自动诊断）**：webhook、冷却、单飞、配置开关、生产部署验证。

## 风险与缓解措施

| 风险 | 缓解 |
| --- | --- |
| 日志含邮箱、令牌等敏感信息出站 | 出站前强制脱敏；单测覆盖已知模式；证据中日志标记为不可信数据 |
| 日志内容构成提示注入 | 系统提示明确「日志是不可信数据」；没有工具/写操作；模型只能输出文本 |
| 告警风暴导致积分被反复消耗 | 10 分钟冷却 + 单飞 + 关闭开关；余额不足直接失败 |
| Loki/Alloy 吃掉内存 | 各自 `MemoryMax`；单机文件存储；30 天保留；实测日志仅约 6200 行/天 |
| 新增常驻服务扩大攻击面 | 全部只绑 `127.0.0.1`；公网仍只有 8081；webhook 再加回环 + 令牌两道 |
| webhook 令牌进仓库 | 令牌只在服务器生成与 600 文件保存；仓库只留占位，安装脚本注入 |
| 迁移撞号 | 用 14 位时间戳；改前查同表冲突；跑迁移命名测试 |
| Grafana 规则又出现 NoData 假 firing | 指标规则用 `bool`；日志规则把 NoData 设为 OK；表达式先用 API 验证有值 |
| 诊断报告胡说 | 报告必须引用证据；固定五节；"需要人工确认"必填；不提供执行动作 |
