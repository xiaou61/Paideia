# 管理端 MCP 工具需求

## 本项状态与本轮变化

- **2026-10-26 建项**。用户在调研管理端 MCP 覆盖面后指示「可以的给我补充吧，开始吧」。
- 本文件只写期望行为与边界；分组命名、角色贯通方式与缓存键等实现细节在 proposal / design。
- 交付目标是把管理端 49 个端点按意图收敛成 38 个工具，**不是**把 REST 接口 1:1 包一层。

## 已确认事实

2026-10-26 读码与配置实测：

| 项 | 事实 |
| --- | --- |
| 本机 MCP 服务器 | 配置 8 个；本会话真正挂上 6 个（github、drawio 未连上），约 81 个工具 |
| Paideia 自有 MCP | 注册 15 个工具；默认视图 `/mcp` 只露 12 个（3 个写工具需 `/write`） |
| 管理类工具 | **0 个**。`ToolScope.ADMIN` 注释写明「当前没有工具使用，为将来预留」 |
| admin scope | `PatService.create` 直接拒绝，返回「不支持 admin 权限范围」 |
| 角色贯通 | `McpToolInvoker.contextOf` 把角色写死为 `null`；视图缓存键只有「视图名\|工具组」 |
| 管理端端点 | 49 个，分布在 9 个控制器、14 个管理端页面 |
| 管理端鉴权 | 靠 `SecurityConfiguration` 的路径规则 `hasRole("ADMIN")`，控制器不加方法注解 |
| 工具命名 | 启动期校验：`^[a-z][a-z0-9]*_[a-z][a-z0-9_]*$`，且名字必须以工具组前缀开头，最长 128 字符 |
| 工具组白名单 | 建 PAT 时以逗号字符串存库；组名改名会让已发凭据失配 |

## 用户决定

- **2026-10-26 补管理端，前台用户侧暂不考虑**。原话：「这个 mcp 分为后台管理和前台用户的，前台用户的这种，暂时不考虑，就说后台管理」。
- **2026-10-26 直接开始实现**。原话：「可以的给我补充吧，开始吧」。
- 按 2026-10-26 调研给出的分组与数量方案执行：按意图合并为 38 个工具，分「只读 / 非破坏写 / 破坏性写」三批交付。

## 实现选择

以下由 Agent 依据已批准边界与仓库既有模式选定，记录理由；不替代用户对产品范围的决定。

- **管理工具单独成组**，不混进 `knowledge` / `note` 等学习者工具组：一个视图等于一份能力清单，混组会让「学习者视图」的语义取决于调用者的角色。
- **管理工具一律声明 `ToolScope.ADMIN`**，包括写工具。原因：`ToolCatalog` 的角色过滤只作用于 `ADMIN` scope 的工具；若写工具声明为 `WRITE`，非管理员只要建一个带 `admin_*` 工具组 + write 的凭据就能看见并调用它。
- **admin scope 由「账号角色 + 显式勾选」共同决定**：管理员才允许建带 admin scope 的 PAT；非管理员请求 admin scope 直接拒绝，不静默降级。
- **角色在每次请求时从账号表解析**，不在 token 行里存快照：改角色后旧凭据必须立刻失去管理能力。解析通过 `paideia-platform` 的纯接口 + `paideia-app` 装配，保持 mcp 不 import 业务包。
- **视图缓存键包含角色**：MCP SDK 在构建 server 时固化工具清单，缓存键漏角色会把管理员视图的清单服务给非管理员（或反之）。
- **破坏性工具单独标注** `destructive=true` 且 `idempotent=false`，让客户端据此二次确认；工具描述里写明不可撤销。
- **不新增管理端 REST 端点**：工具直接调用既有服务层，管理端页面与 MCP 共用同一份校验。

## 目标

- 管理员用一个 PAT 就能通过 MCP 读管理端全部只读视图、执行非破坏写与破坏性写。
- 非管理员即使猜到工具名、伪造工具组路径，也看不到、调不动任何管理工具。
- 管理端页面与 MCP 对同一操作的校验一致（不能改自己角色、不能删自己、调积分必须写原因等）。
- 学习者默认视图的工具数量与行为不变。

## 非目标

- 不做前台用户侧的 MCP 扩展（用户已明确暂不考虑）。
- 不做管理端页面本身的新功能；页面不因本项变化。
- 不做管理工具的批量操作、事务编排或跨域组合动作。
- 不把 Grafana iframe 代理做成工具：它依赖会话 Cookie，PAT 架构不可用。
- 不做「内容导入轨道」工具：`POST /tracks` 的注释明确写着管理端维护界面本项不做，导入走脚本。

## 需求

- REQ-001：管理工具必须与学习者工具分组隔离，学习者默认视图不出现任何管理工具。
- REQ-002：只有 `ADMIN` 角色可以创建带 admin scope 的 PAT；非管理员请求该 scope 时返回明确错误，不静默降级。
- REQ-003：PAT 的角色在每次请求时从账号表解析；账号被降权后，旧 PAT 立即失去管理能力。
- REQ-004：视图清单与工具调用都必须校验角色；清单不可见与调用不可用使用同一份过滤链。
- REQ-005：视图缓存必须按角色区分，不同角色的工具清单不得互相复用。
- REQ-006：工具按意图覆盖管理端 49 个端点的能力，合并规则记录在 design；不要求 1:1。
- REQ-007：只读工具不得改变任何状态；写工具必须声明 `WRITE` 语义（scope 为 ADMIN）并在描述中写清整行覆盖还是增量。
- REQ-008：破坏性工具必须标注 `destructive=true`、`readOnly=false`、`idempotent=false`，描述里写明不可撤销。
- REQ-009：管理工具的每次调用都进入既有 `mcp.audit` 审计日志（含 tokenId、userId、工具名、视图、耗时）。
- REQ-010：管理工具复用既有服务层校验，不绕过「不能操作自己」「调积分必须写原因」「只有社区数据集可下架」等规则。
- REQ-011：管理端 REST 契约不变；本项不新增、不修改任何 HTTP 端点。
- REQ-012：前端凭据页可以勾选管理工具组；组名与后端工具组一一对应。
- REQ-013：工具目录启动校验必须通过：命名前缀、无重名、schema 为 object、只读与破坏性不矛盾。
- REQ-014：学习者默认视图的工具清单数量与既有一致（12 个），不因本项增减。

## 验收标准

- AC-001：非管理员建 PAT 时请求 `admin` scope，接口返回 400 且不落库；管理员请求成功并返回含 `admin` 的 scopes。
- AC-002：管理员用 admin scope 的 PAT 访问 `/mcp/x/admin_content`，工具清单只含 `admin_content_*` 只读工具。
- AC-003：同一个管理视图路径，非管理员 PAT 返回 404（未知视图），不返回空清单。
- AC-004：管理员先访问、非管理员后访问同一路径，后者的清单不包含管理工具（缓存不串角色）。
- AC-005：非管理员即使知道工具名，直接调用 `admin_*` 工具返回错误，且不执行业务逻辑。
- AC-006：`/mcp/x/admin_content` 不含写工具；`/mcp/x/admin_content/write` 含写工具且不含其他组的工具。
- AC-007：38 个管理工具的命名、工具组、scope、破坏性标注全部通过目录启动校验。
- AC-008：学习者默认视图 `/mcp` 仍为 12 个工具，且不出现任何 `admin_` 前缀工具。
- AC-009：调积分工具在缺少原因、调整自己时返回错误；删号工具在操作自己时返回错误。
- AC-010：下架数据集工具对非社区数据集返回错误，不更新状态。
- AC-011：前端凭据页显示 7 个管理组，未勾选时凭据不会获得管理工具。
- AC-012：既有学习者侧 e2e 与后端单测不回归。
