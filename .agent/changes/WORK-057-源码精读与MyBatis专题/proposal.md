# 方案 · 源码精读（第三方源码 + MyBatis 专题）

## 要解决的问题

现有「源码解读」是知识库里的两个分类，正文用 `code-tour` 摘录几段代码。读者看不到文件上下文，
也没有"改条件看链路变化"的互动；入口还藏在知识库里。用户要一个独立的、读第三方项目的源码精读区。

## 候选方案

| 方案 | 做法 | 成本 | 结论 |
| --- | --- | --- | --- |
| A. 只补内容 | 新开知识库分类，MyBatis 写 24 篇，全部用现有 `code-tour` | 最低（只写内容） | **不采用**：就是用户已经否掉的形态——看不到整文件、互动只有预测题 |
| B. 独立入口 + 新块 + 整文件快照 | `/source` 三条路由；新块 `source-walk` 整文件 + 步骤 + 状态 + 开关；源码锁定 3.5.19 随前端发布 | 中（1 个新块 + 3 个页面 + 内容） | **采用** |
| C. 页面内真跑 MyBatis | 沙箱里编译并执行读者改过的代码 | 高（Maven 离线依赖、数据库、10 秒墙钟、镜像体积） | **推迟**：与 WORK-055 同类问题；形态未验证前不背这个成本 |

## 选定方案 B 的关键取舍

1. **整文件而不是摘录**：读者能看到方法前后的上下文与 import，这是"读源码"和"读文章"的区别。
2. **互动是数据驱动**：开关/分支在内容里声明，步骤带 `when`；组件只做过滤与呈现，不写 `if (第四章)`。
3. **零后端改动**：章节仍是 `knowledge_entries`，进度仍是 `/api/v1/learning/entries/{id}`；
   源码是静态文件。唯一后端改动是静态白名单加一条 `GET /source/**`。
4. **版本锁定**：快照锁 `mybatis-3.5.19`，行号与 GitHub permalink 都对得上；升级是独立动作。
5. **删除旧线**：不迁移——迁移会把"本项目的代码"混进第三方精读，语义不成立。

## 与已有机制的关系

- 复用：块注册表与错误边界（WORK-014）、`quiz` / `code-challenge`（排序/填空/找错）、
  `MarkdownBody`、服务端进度端口、内容导入脚本（WORK-040）。
- 不复用：`code-tour`。它的契约是"每步自带 code"，改成整文件会波及既有内容与单测。
- 先例：`/books`（WORK-046）的"顶层入口 + 父分类 + 固定 slug 路由"。
