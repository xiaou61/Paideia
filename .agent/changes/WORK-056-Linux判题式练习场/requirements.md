# Linux 判题式练习场需求

## 用户诉求（原话）

> 「其实 Linux 相关的我在想我们现在有了一个 sql 练习场，是不是也可以加一个 Linux 练习场，就是给每个人限制他们的这个文件沙箱呢？你感觉呢？能不能这样搞」

> 「继续吧」（2026-10-29，在本项评估给出之后）

## 目标

让 `content/reading/linux-from-zero/` 的 19 关里那些**靠敲命令才学得会**的内容可以真跑、真判：学习者提交一串命令，系统在一个一次性容器里执行，按**执行后的最终状态**判定对错，并告诉他"你改了哪些文件""哪一步输出的和期望不一样"。

判据是**状态**，不是输出字符串——这是与现有 `run` 题型（比对 stdout）最本质的区别：`chmod 640 x` 的正确性在权限位上，不在它的输出里。

## 非目标

- **不做交互式终端**（不用 ttyd/xterm.js，不做 WebSocket 会话）。
- **不做每人一个持久容器/持久文件沙箱**。每次提交一个新容器，用完即弃——隔离靠销毁，不靠限额与回收。
- **不做文件系统快照/分支**（LayerFS 那条路 2026-10-23 已评估不采用）。
- **不让练习容器出网**。因此「网络：端口、连通性与防火墙」「SSH」两关**只读不练**。
- **不改 SQL/Java/Python 既有的判题与配额口径**。
- 本项**不改任何已上线课程正文**；练习题作为新的围栏块后加。

## 实现选择

以下由 Agent 依据已批准边界与仓库既有模式决定，不逐条回问：

1. **判题式，不是终端式**。提交一段命令序列（`bash` 脚本体）→ 容器里执行 → 再跑一道判定脚本。重复一次的成本是一个容器启动（约 1 秒），与 SQL 沙箱同量级。
2. **保持 `--network=none` 不动**。开网络等于给每个注册用户一个可发请求的出口（扫描/爆破/外联的跳板），而它换来的只是两关的练习。这一条是可回退的范围决定：真要练网络，回到本条重新评估。
3. **判题脚本随题走**（放在内容文件的围栏块里），由作者写，和现有 `code-challenge` 的 `cases` 同级。理由：题的判定口径属于内容，不属于代码；代码只提供"把 judge 跑起来并收集结果"的能力。
4. **镜像用 `debian:12-slim` 加 Linux 线用到的那批工具**（coreutils、procps、grep/sed/gawk、findutils、util-linux、systemd 仅用于 `systemd-analyze verify`），按 digest 钉住。不用 alpine 是因为 BusyBox 的命令行为与教学里讲的 GNU 版本有差异（`sed -i`、`ps` 的列、`find -printf`），会让"照着课敲却报错"。
5. **判定口径**：judge 退出码 0 = 通过；非 0 = 未通过，并把 judge 的 stderr 原样回给学习者（它才是可解释的失败信息）。另外回报 `docker diff` 的文件变更列表，让学习者看到自己动了什么。
6. **一次提交 = 一段脚本**，不拆成"每敲一条命令起一次容器"——后者表达不了"先建目录再改权限"这种跨命令状态。

## 功能需求

- **REQ-001**：新增语言标识 `shell`；`paideia.sandbox.shell-image` 留空时该语言不可用，`/status` 不返回它，前端不渲染运行按钮。
- **REQ-002**：一次提交执行一段脚本（长度上限沿用 `maxCodeChars`），随后执行该题自带的判定脚本；两者在**同一个容器、同一个文件系统**内，中间不重置状态。
- **REQ-003**：判定结果必须区分三种结局：**通过**（judge 退出 0）、**未通过**（judge 退出非 0，带 stderr）、**未能判定**（超时、容器启动失败、输出超限）。
- **REQ-004**：返回学习者的脚本输出（stdout/stderr 分开、按 `maxOutputBytes` 截断并显式标注"已截断"）、judge 的 stderr、以及容器内文件变更摘要（新增/修改/删除）。
- **REQ-005**：演练题必须带有"初始状态"（seed）：一组初始文件与目录，由题目声明，在脚本执行前铺好。
- **REQ-006**：复用现有并发与配额：全局 2、每人 1、按语言计日配额；被 `RunSlot` 或配额拒绝的请求不产生容器。
- **REQ-007**：前端新增 `shell` 题型（`code-challenge` 的新 `kind`），具备：编辑器、运行按钮、输出区、判定徽标（通过/未通过/未能判定）与"文件变更"列表；语言不可用时整块降级为原始文本，不渲染运行按钮。
- **REQ-008**：内容侧至少覆盖 Linux 线的**六道**题，分别命中不同能力：权限（`chmod`/`umask`）、管道与重定向、文本处理（`grep`/`sed`/`awk`）、进程与信号、Shell 脚本（`set -euo pipefail` + 引号）、综合（systemd unit 用 `systemd-analyze verify` 判）。

## 质量要求

- **隔离不弱于现有 Java/Python 沙箱**：本文列出的 `DockerCommand` 参数一个都不能少；新增参数必须有注释说明它在挡什么。
- **判定可复现**：同一份脚本 + 同一个 seed + 同一个 judge，判定结果必须稳定；judge 里不许依赖时间、随机数、网络。
- **失败可解释**：任何"未能判定"都要有一句人话说明原因（超时 / 镜像缺失 / judge 自身报错），不能只给一个布尔值。
- **不新增表**：审计复用 `code_run`（新增 `shell` 语言值即可）。

## 约束与依赖

- 硬依赖：`paideia-sandbox` 已具备的一次性容器能力（`DockerCommand` / `DockerCodeRunner` / `RunSlot` / `SandboxQuotaService`）——已存在，不新建模块。
- 内容依赖：`content/reading/linux-from-zero/` 已上线（19 关）。
- 部署依赖：镜像要预拉到目标机（沙箱镜像不联网拉取），并写进部署说明。
- 规则约束：本仓库是公开仓库，练习题与 judge 不得包含真实凭据或内网地址。

## 关联工作项

- **WORK-015**（代码沙箱）：本项复用它的隔离参数、并发闸与配额，不重复实现。
- **WORK-032**（MySQL 实训）：同一套"一次性容器 + 判题"模式的前身，本题型是它的通用化。

## 验收标准

- **AC-001**：`shell-image` 为空时，`GET /api/v1/sandbox/status` 的 `languages` 不含 `shell`；页面上的 shell 题不显示运行按钮。
- **AC-002**：提交一段能达成目标的脚本 → 判定"通过"，且文件变更列表非空。
- **AC-003**：提交一段不达成目标的脚本 → 判定"未通过"，页面显示 judge 的 stderr。
- **AC-004**：提交 `while true; do :; done` → 墙钟上限内被终止，判定"未能判定（超时）"，宿主负载回落后其他用户仍可正常运行。
- **AC-005**：提交 `yes` 之类无限输出 → 输出被截断到上限并标注"已截断"，接口不因此变慢或报 500。
- **AC-006**：同一用户并发提交两次 → 第二次返回 `TOO_MANY_REQUESTS`，且**不消耗**日配额。
- **AC-007**：容器内 `curl`/`wget` 对外访问失败（`--network=none` 生效）；`id` 显示非 root。
- **AC-008**：一次提交无法读取上一次提交留下的任何文件（每次都是新容器）。
- **AC-009**：`systemd-analyze verify` 类题目：unit 文件写错时报出具体行，判定"未通过"。
- **AC-010**：审计表里能查到每次执行的 `code_hash` 与耗时，且不含提交的明文脚本。

## 假设

- 学习者愿意"提交一段命令"而不是"一行一行敲"。19 关的正文本来就是这么写的（一次给一串命令 + 真实输出），所以这是顺着内容的形态走。
- 每道题的 seed 都很小（几个文件、几 KB），不需要压缩传输或快照。
