# 数据大屏需求

## 用户原始诉求

2026-10-27，在 WORK-043（AIOps 完整化）收口后，用户提出：

> 「其实我还想就是我们现在有这么多数据了，能做出来一个可视化的类似于数据大屏的那种数据流转的界面吗？这个当做一个新的 work，要求非常详细，然后还有些实用性的这种。」

并明确先做完 WORK-043 的 P2–P5 再开这一项。

关键点有三个：**数据大屏**（不是普通报表页）、**数据流转**（数据从哪来到哪去，不是只有终点数字）、**实用性**（看完能判断点什么，而不是好看的图）。

## 已确认事实

调研于 2026-10-27，全部是生产库与线上进程的实测值，不是估算：

- **生产库有 44 张业务表**（不含 Flyway 与种子）。真实的量级极不均衡：

  | 表 | 行数 | 时间跨度 | 说明 |

  | `refresh_tokens` | 4609 | 持续 | 每次登录/刷新一行，是最大的表 |
  | `digest_items` | 535 | 10-21 ~ 10-27 | 每日速递条目，6 天数据 |
  | `learning_track_stages` | 196 | 静态 | 课程结构 |
  | `knowledge_entries` | 187 | 静态 | 知识条目 |
  | `mcp_access_tokens` | 70 | 持续 | MCP 凭据 |
  | `ai_runs` | 55 | 10-19 ~ 10-27 | AI 调用流水 |
  | `knowledge_entry_views` | 55 | 10-19 ~ 10-27 | 条目浏览计数（按 user+entry 聚合，非明细） |
  | `code_runs` | 50 | 10-18 ~ 10-26 | SQL/代码沙箱运行 |
  | `ai_credit_ledger` | 50 | 持续 | 积分流水 |
  | `resume_documents` | 37 | 10-18 ~ 10-27 | 简历 |
  | `ai_messages` | 45 | 持续 | 对话消息 |

- **真实的「数据流转」三条链，都有落库痕迹**：
  1. **速递链**：RSS/GitHub/HackerNews 抓取 → `digest_items`（535）→ AI 压缩（`ai_runs.kind='digest'`）→ 前端 `/digest` 展示 → `knowledge_entry_views` 记不到它（速递点开是外链）。
  2. **AI 链**：用户提问 → `ai_conversations` → `ai_messages`（45）→ `ai_runs`（55，含 tokens/credits）→ `ai_run_spans`（5，子调用分段）→ `ai_credit_ledger`（50）扣费。
  3. **学习链**：`knowledge_entry_views`（55）→ `learning_progress`（20）→ `question_attempts`（1）→ `concept_mastery_state`（1）→ `review_sessions`（3）。
- **监控侧已有的四类数据**（WORK-028/042/043 建的，全部只绑回环）：Prometheus（9090，保留 30 天）、Loki（3100）、Tempo（3200，trace）、Grafana（3000）。
- **管理端已有 14 个页面**，其中 `AiRunsOverviewPage`（分桶趋势/概览/采集健康/赞踩）、`OpsPage`（七组状态 + AI 诊断 + Grafana iframe）、`IncidentsPage`（事件时间线）已覆盖「单点数字」与「运维视角」，**没有任何一页回答"数据整体怎么流、在哪一步掉了"**。
- **学习者端导航已有四个分组**（learn/knowledge/practice/job），共 12 项。加第 13 项之前要先想清楚它是不是管理端专属。
- **生产数据量很小**：2 个用户、55 次 AI 调用、535 条速递。任何「按用户分组」的图都只有 2 个点，「按天趋势」最多 6–8 个点。**这是设计约束，不是缺陷**——大屏必须在小数据量下依然有意义，而不是靠编造数据撑场面。

## 用户决定

用户在提出需求时已明确的唯一硬约束：**"要求非常详细，然后还有些实用性的这种"**。

其余实现选择由 Agent 给出默认方案（见「实现选择」），批准方案即视为确认。需要用户在批准前拍板的三项已列入「待确认问题」。

## 实现选择

- **位置：管理端 `/analytics`（新页），不改学习者端**。理由：数据大屏的受众是"看平台整体"的人（管理员），而 2 个用户的平台上给学习者看"平台数据"没有意义；同时避免学习者端导航从 12 项再增一项。
- **形态：单页多区（5 个区块），不是独立大屏站点**。理由：现有 `apps/admin` 已有壳、导航、鉴权与 `@paideia/ui`；单独建一个 Vite 应用要多一套构建、部署与鉴权，收益为零。
- **数据来源分两层，明确标注"实时"与"落库"**：
  - **落库层（MySQL 聚合）**：业务量、流转漏斗、各表增长——这些 Prometheus 里没有。
  - **监控层（Prometheus 代理）**：请求速率、错误率、AI 成功率、延迟——复用 `OpsSummaryService` 已有的 `PrometheusClient`，不新建数据通路。
  - **不用 Grafana iframe 承载大屏**：现有 OpsPage 的 iframe 需要 Grafana 口令，大屏要一进来就能看。Grafana 仍作为"下钻"链接。
- **"数据流转"用一张固定的泳道图（6 条链）**，每条链是"源 → 处理 → 落库 → 消费"，节点上标**真实行数/速率**，边标**通过率**。数字来自 SQL 聚合，不用前端拼。图用手写 SVG + CSS 动画（不用引入图表库的 sankey，理由见 `proposal.md`）。
- **新增一个只读聚合接口 `GET /api/v1/admin/analytics/overview`**，ADMIN 权限，一次返回 5 个区块的数据。不做多个细粒度接口：大屏是"一屏看全"，分 10 次请求会让各区块数字互相矛盾。
- **不新增表**：所有数据都能从现有表聚合出来。若某项确实无法聚合（例如"速递被点开过几次"根本没记录），**如实显示"未采集"并列入后续工作**，不新增埋点表来撑这个页面。理由：为了大屏而加埋点是**倒因为果**——大屏的价值是暴露"哪些数据没采集"，然后由真实需求决定要不要补。
- **刷新：前端 60 秒轮询 + 手动刷新按钮**，不做 SSE/WebSocket。理由：聚合查询较重（10+ 张表），大屏是"看一眼"的场景，60 秒足够；真需要实时的部分（请求速率）本来就来自 Prometheus 的 `rate(...)`。
- **小数据量下的显示纪律**：任何"趋势"图在数据点 < 3 时显示"数据不足（N 个时间点）"，而不是画一条看起来正常的线；任何"按用户"分组只有 ≤2 个点时改用"总量"表述。这条写进验收标准。

## 背景

项目至今做的所有可视化都是**单点视角**：

- `OpsPage`：现在主机/服务/备份怎么样（七组状态卡）。
- `IncidentsPage`：某一次故障从触发到恢复发生了什么。
- `AiRunsOverviewPage`：AI 调用在某个时间桶里花了多少 token/钱。
- `/digest`、`/knowledge`：用户看到的内容本身。

缺的是**横向视角**：数据从哪进来、经过哪几步、在哪一步掉得最多、哪张表在涨、哪条链路其实一直是空转的。这也正是用户说的"数据流转"。

这个问题在数据量小时不显眼，但有两类真实用途：

1. **判断某个功能到底有没有被用**。生产上 `question_attempts` 只有 1 行、`concept_mastery_state` 只有 1 行、训练营三张表全为 0——这不是"没问题"，是**这三个功能上线后没人用过**。这件事在任何现有页面都看不出来。
2. **判断采集本身缺什么**。例如"速递被打开过几次"没有任何埋点；"AI 记忆被召回了几次"在 `ai_runs.attrs` 里有但没进聚合。大屏能把"没有数字"变成"明确的空白格"，而不是让人以为数据是好的。

## 目标

1. 一屏看清**六条数据链**各自的规模与流失点，而不是六个孤立的总数。
2. 能回答**"哪些功能上线了但没人用"**，并且这个判断来自落库数据而不是印象。
3. 能看清**各表的增长速率**，据此判断哪些需要归档/清理（`refresh_tokens` 4609 行已经是最可能的候选）。
4. 能**下钻**：从任一大屏数字跳到对应的明细页（AI 运行列表、事件列表、速递页、Grafana）。
5. 明确标出**未采集的数据**（灰格 + 原因），把它当成需求输入而不是视觉瑕疵。
6. 不破坏现有任何页面；不新增公网端口；不新增表。

## 非目标

- 不做实时流（秒级刷新、WebSocket、SSE）。大屏的时效单位是分钟。
- 不做给学习者看的"个人数据看板"（那是另一个受众与另一套口径；需要时单开）。
- 不做 Grafana 的替代：趋势与告警下钻仍跳 Grafana。
- 不为了填满大屏而新增埋点表或事件采集。**未采集就显示未采集。**
- 不做多租户/多实例口径（当前单机单实例）。
- 不做"预测""同比环比显著性检验"这类需要足够历史才能成立的统计（现存最长数据 8 天）。
- 不引入图表库（详见 `proposal.md` 的备选方案对比）；用 SVG + CSS。

## 功能需求

### Track A：数据流转主视图

- **REQ-001**：六条链各自渲染为一段"源 → 处理 → 落库 → 消费"的横向泳道，节点上显示**真实计数**（来自 SQL 聚合），边上显示通过率。
- **REQ-002**：六条链固定为：① 知识内容（条目/分类/关系/浏览）② 每日速递（抓取/压缩/展示）③ AI 对话（会话/消息/运行/积分）④ 学习闭环（浏览/进度/答题/掌握度/复习）⑤ 简历（文档/版本/优化）⑥ SQL 练习（数据集/运行）。
- **REQ-003**：每条链的"断点"要可见：某一步是 0 或远小于上一步时，该节点与边用警示色标出，并在悬停/点击时说明"上一步 X、这一步 0，说明这一步没有发生或没有采集"。
- **REQ-004**：链上节点可点击跳转到对应明细页（已存在页面优先，不新建列表页）。

### Track B：业务量与时序

- **REQ-005**：按天（近 14 天）显示四条主线的新增量：AI 运行数、速递条目数、条目浏览次数、简历数。数据不足 3 天时如图显示"数据不足"。
- **REQ-006**：显示各表的**当前行数与近 7 天增量**，按行数排序，并标出"只增不减"的表（`refresh_tokens`/`ai_runs`/`ai_credit_ledger`/`digest_items`）与它们的归档候选状态。
- **REQ-007**：时序图的时间轴必须按**北京时间的自然日**切桶（与速递的 07:00 结算一致），不是 UTC 日。

### Track C：功能使用度（回答"上线了但没人用"）

- **REQ-008**：列出**所有用户可见功能**及其"近 7 天是否有任何落库痕迹"，三态：有数据 / 无数据（已采集但为 0） / 未采集（没有埋点）。三态视觉必须可区分。
- **REQ-009**：`users` 表只有 2 行这件事必须显式呈现（"当前 N 个账号"），因为所有"每用户"指标的分母就是它。
- **REQ-010**：未采集项要给出**具体缺什么**（例如"速递条目点击：`digest_items` 没有浏览记录表"），让后续决定是否补。

### Track D：AI 与成本

- **REQ-011**：显示 AI 运行的场景分布（`kind` 维度）、成功率、平均耗时、token 与积分消耗；数据来自 `ai_runs`，与 `AiRunsOverviewPage` 的口径必须一致（复用同一套 SQL 语义，不另起一套）。
- **REQ-012**：显示积分收支两侧：发放（ADJUST）与消耗（各 kind 的净额），并标出当前余额合计。

### Track E：监控层摘要与下钻

- **REQ-013**：显示来自 Prometheus 的四个实时值：HTTP 请求速率、5xx 比例、P95、AI 成功率；这些直接复用 `OpsSummaryService` 的查询，不重复定义。
- **REQ-014**：监控层不可达时该区块显示"Prometheus 不可达"，其余区块（来自 MySQL）**照常显示**——两层的失败必须互不牵连。
- **REQ-015**：每个区块有下钻入口：AI → `/ai-runs/list`，运维 → `/ops/panel`，事件 → `/ops/incidents`，速递 → 学习者端 `/digest`，Grafana → 现有代理。

## 质量要求

- 单次 `GET /overview` 的 P95 响应 **< 800ms**（10+ 张表聚合，含一次 Prometheus 往返）。超过就分区块懒加载，但**首屏 5 个区块的数字必须来自同一次查询**，否则会互相矛盾。
- 所有聚合查询走索引或小表全扫；单条 SQL 不允许扫 `refresh_tokens` 以外的全表（它 4609 行、无业务字段，可全扫）。
- 页面在 1280×720 与 1920×1080 下都不出现横向滚动；窄屏（<1024）退化为单列堆叠而不是隐藏区块。
- 任何数字为 0、未采集、不可达时，**不能显示成 0 或空白**：必须区分"确实是 0"与"没采集"。
- 不新增公网端口；不改 `SecurityConfiguration` 的现有放行规则。
- 所有时间显示用浏览器本地时区，存储与传输仍 UTC。

## 约束与依赖

- 权限：ADMIN。复用 `/api/v1/ops/admin/**` 的既有规则或新增一条同级规则；不开放给学习者。
- 不新增表、不新增埋点。所有数据来自现有 44 张表 + Prometheus。
- 前端不引入图表库（现有依赖里没有；`mermaid` 是 devDependency 且用于文档）。
- 后端聚合放在 `paideia-app` 的 `ops` 或新建 `analytics` 包，不得反向依赖业务模块的内部实现（`ModularityTest` 会拦）。跨模块读取必须走公开接口或直接 SQL——**这里选直接 SQL**（只读聚合，不违反任何模块的封装语义，也不引入新的模块依赖）。
- 复用 `PrometheusClient`；不新建 HTTP 客户端。
- 迁移：**不需要**。

## 验收标准

- **AC-001**：`GET /api/v1/admin/analytics/overview` 返回五个区块（flows/volume/usage/ai/monitoring），ADMIN 200、学习者 403、匿名 401。
- **AC-002**：六条链全部渲染，每条的节点数字与直接 SQL 查询结果一致（抽查 6 个数字逐一核对）。
- **AC-003**：至少一个真实"断点"被正确标出——生产上学习闭环链的第 3–4 步（`question_attempts`=1、`concept_mastery_state`=1）、简历链的版本数，二者至少一个在界面上有警示色与说明。
- **AC-004**：功能使用度区块里 `camp_*` 与 `ai_interview_evaluations` 显示"无数据（已采集）"而不是"未采集"；"速递点击"显示"未采集"并说明缺什么。
- **AC-005**：时序图在数据点 < 3 时显示"数据不足"，不画假线；切桶按北京自然日（抽查一天，看它与 `digest_items.edition_date` 对齐）。
- **AC-006**：Prometheus 不可达时监控区块显示不可达，其余四块照常显示（用 `paideia.ops.prometheus-url` 指到死端口验证）。
- **AC-007**：单次请求 P95 < 800ms（本地连生产库的实测，或导出数据后在测试库上测）。
- **AC-008**：1280 宽与 1920 宽无横向滚动；<1024 退化为单列。e2e 断言。
- **AC-009**：`GET /admin/analytics` 在管理端导航里有入口（按项目规则：新页面必须有导航项）。
- **AC-010**：现有页面 0 回归——管理端 e2e 全量、学习者端受影响文件、后端 `Ops*Test` 全绿。

## 假设

- 生产数据量在可预见期内保持这个量级（2 用户、百级行），因此**不需要**预聚合表或物化视图。
- `refresh_tokens` 的增长（4609 行）是正常的（每次刷新一行），不需要在大屏上报警，只需标注为归档候选。
- "数据流转"的价值主要来自**暴露空白**，而不是展示精确的实时数字；因此聚合口径的"大致正确"比"绝对实时"重要。

## 待确认问题

1. **受众**：这个页面只给管理员（推荐），还是也要给学习者一个精简版？影响导航入口与权限。
2. **是否允许为此新增埋点**：推荐**不新增**，先如实显示"未采集"，等看几轮再决定补哪些。若用户希望一次补齐（例如速递点击、AI 记忆命中），需要单独评估埋点成本与隐私边界。
3. **刷新强度**：推荐 60 秒轮询。若要 10 秒级，需要把聚合拆成预计算，代价是引入一张快照表——这与"不新增表"的默认选择冲突。
