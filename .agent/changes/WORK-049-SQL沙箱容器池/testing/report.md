# WORK-049 验证报告

**结论先说**：池化上线了，**端到端从 3.5–4.2 秒降到 0.35–0.42 秒（约 10 倍）**，
沙箱内部从 3256ms 降到 226–290ms（约 13 倍）。

**但 AC-001 里写的"p50 ≤ 150ms"没有达到**——实测容器内 p50 约 250ms。差的那 100ms
是每次执行多出来的"建账号 / 授权 / 删账号"，那是 REQ-002 隔离要求的代价，不是实现没做好。
要不要为这 100ms 放宽隔离，需要用户决定（见最后一节）。

## 实施中修掉的三个真缺陷

都是"不真连上线就看不见"的那一类：

1. **`sql-memory: 512m` 会让 mysqld 被 OOM 静默杀掉。** `/tmp` 的 tmpfs 里那份 78MB datadir
   也计入容器内存，加上 mysqld 约 350MB 常驻就超了。日志里**一行错误都没有**，表现是
   "mysqld 进程凭空消失"。线上 yml 已改成 1g（备份 `application.yml.bak-sqlpool-*`）。
2. **启动脚本拼出了 `&;`** —— `String.join("; ")` 把「后台符号」和「分号」连在一起，
   是 sh 语法错误，容器起来就退出。表现是每次执行都等满 30 秒就绪超时再回落，
   **比不做池化还慢一倍（实测 33 秒）**。
3. **残留容器占名字。** 上一次进程留下的同名容器（512m 时代起的、mysqld 早已死掉）会让
   `docker run --name` 失败，而失败输出被静默吞掉。现在建容器前无条件按名字删一次，
   且 docker 命令的非零输出改打 WARN。

另外**热路径上不再做健康检查**：原来每次执行前 ping 一次容器，而这台机器上 `docker exec`
偶尔超过 3 秒，一次超时就被判成"容器坏了"并重建——实测一半请求因此回落。现在容器一旦
就绪就信任它，健康由真正的执行判定（exec 报"容器不存在/没在跑"才回收）。

| 阶段 | 改造前 | 改造后 |
| --- | --- | --- |
| 起容器 | 1.1 s | 0（常驻） |
| 拷 78MB datadir | 1.05 s | 0（常驻） |
| mysqld 初始化 | 约 2 s | 0（常驻） |

## 未覆盖与已知限制

| 项 | 原因 | 影响 |
| --- | --- | --- |
| p50 ≤150ms | 每次执行多三步账号管理（建号/授权/删号）约 100ms | 要压到 150ms 内就得放弃"每次一个受限账号"，改用共享只读账号或直接 root——**那是放宽隔离**，不擅自做 |
| 并发 | 只测了单人顺序执行 | 两个用户同时打、池只有 2 个容器：第二个会等，第三个回落一次性容器 |
| 大结果集 | 只测了 `COUNT(*)` | 返回大量行时序列化与传输另有一段，未测 |
| 池容器长期存活 | 只跑了不到一小时 | 长时间运行后 mysqld 内存增长、日志膨胀未知；没有空闲回收 |
| AC-007 逐字节对比 | 未做 | 两条路径共用同一套解析，风险低 |

## 需要用户决定的一件事

**要不要为了那 100ms 放宽隔离？** 现在的 250ms 里，约 100ms 花在"建一次性的库和账号"上。
放弃它（改用共享账号或 root）能到约 150ms，代价是同一容器里的用户之间不再有账号边界——
只剩下"各自的库名"这一层。我的建议是**保持现状**：250ms 与 150ms 对用户是同一档体感，
而隔离是安全边界，不该拿体感去换。
