# 记忆的少而准需求

## 用户原始诉求

2026-10-28，用户先问「我们目前的记忆是怎么存储的」，在得知当前实现后要求深度优化，并要求把评测体系一起搭起来。
四件事由用户当场裁决：

1. **方向是"少而准"，不是越多越好。**
2. **淘汰策略按时间来筛选。**
3. **半自动提案要做**（助手提议、用户确认）。
4. **金集由 Agent 自己标注**（授权 Agent 直接写标注，不需要用户逐条过）。

## 已确认事实

以下每条都在仓库里核对过（2026-10-28）：

1. **两张表、无向量、严格私有**：`ai_memories_structured`（`V6` + `V12` 加列）与 `ai_memories_text`（带 ngram 全文索引）。
   所有查询在 SQL 里带 `user_id`（`MemoryMapper` 每条语句的 `WHERE`）。
2. **召回没有相关性排序**：`MemoryStore.recall`（`MemoryStore.java:146`）结构化那一路是
   `selectStructuredRecent(userId, 8, 0)`，即**恒取最近 8 条、与本轮输入无关**；全文那一路按关键词过滤后
   仍 `ORDER BY created_at DESC`。`RECALL_LIMIT = 8` 是两路各自的上限。
3. **判重池固定 40 条**：`MemoryStore.DEDUP_POOL_LIMIT`，更早的记忆不参与判重。
4. **自动整理每 6 轮一次**：`MemoryProperties.roundsPerExtraction = 6`（0 表示关），`maxTokens = 2048`、
   `temperature = 0.2`、超时 60 秒；游标 `ai_conversations.last_memory_extract_message_id`，条件 UPDATE 抢。
5. **写入前只有长度校验**：`MAX_STRUCTURED_CHARS = 512`、`MAX_TEXT_CHARS = 1024`，**没有任何敏感信息检测**。
6. **没有任何淘汰**：两张表既无 TTL 列也无清理任务。对比 `ai_telemetry` 有 `TelemetryRetentionPurger`
   做 90 天清理——记忆这一路没有对应物。
7. **唯一键 `uk_ai_memory_structured_ref (user_id, kind, ref_id)`** 只服务自评桥的覆盖语义；
   `NULL` 的 `ref_id` 不参与去重。
8. **现成的两处评测数据**：`AssistantConversationController.java:200` 把本轮召回条数写进
   `ai_runs.attrs.memoryHits`；`ai_feedback` 有 `trace_id` 且唯一键是 `(user_id, trace_id)`。
   两者可 join，但线上真人账号只有两个，样本不足以支撑结论。
9. **live 测试有现成门槛**：`@EnabledIfEnvironmentVariable(named = "DEEPSEEK_API_KEY", matches = ".+")`
   （见 `DigestWeeklyPromptLiveTest`），没有凭据时整类跳过。
10. **概念金集是推导出来的，记忆没有等价物**：`scripts/build-concept-gold-set.mjs` 按"题在哪一课就考哪一课"
    从课程结构生成；"这段对话里哪些该记"没有客观结构可推，只能构造 + 人工标注。

## 用户决定

- **D-01** 记忆的方向是**少而准**：宁可漏一条，不可错一条。
- **D-02** 淘汰策略**按时间**筛选。
- **D-03** **半自动提案要做**：助手提议，用户确认后才成为正式记忆。
- **D-04** **金集由 Agent 标注**，用户不逐条复核。
- **D-05** 沿用旧裁决：**不做向量检索**，不引入外部记忆服务。
- **D-06** 本项开为独立工作项（`WORK-050`）。

## 实现选择

- **相关性排序不引向量**：结构化按 `kind` 权重 + 时间衰减，全文用 MySQL 全文的相关性分数（`MATCH ... AGAINST`
  本来就返回 score，现在只用于过滤、没用于排序）再叠加同样的权重与衰减。理由：规模只有几十行，
  向量的收益近乎零而索引维护成本是永久的。
- **淘汰以"最近一次被召回"为准，不只看创建时间**：只按 `created_at` 淘汰会误删"我爱用 Java"这种长期事实。
  因此新增 `last_used_at`，召回时批量刷新，淘汰看 `COALESCE(last_used_at, created_at)` 与按 `kind` 分档的 TTL。
- **半自动走新增的 `PROPOSE` 动作，不把现有的直写改成半自动**：把存量路径改成"全部先问"会让不打开面板的用户
  永远没有记忆。改成"模型不确定时才提议"是增量，且正好服务"少而准"。
- **候选独立成表**而不是塞进正式表加一个 `status` 列：候选与记忆的保留期、查询方式、删除语义都不同，
  混在一张表会让"召回"永远要带一个 `status = 'accepted'` 条件，而这个条件迟早会被漏掉。
- **评测用 JUnit + 环境变量门槛**，不用新脚本语言：与既有 live 测试同一套开关，且报告能进 `target/`。
- **评测先于改造**：先用现状跑出基线，再改代码，最后复测。没有基线的"优化"不可证伪。

## 目标

1. 召回从"最近 8 条"变成"最相关的 8 条"，且每次进提示词的内容更少但更准。
2. 长期不再被召回的记忆自动消失，记忆库规模有上界。
3. 模型不确定的候选不再直接成为事实，改由用户一次点击决定。
4. 记忆写入前挡住敏感信息，不让口令、连接串、证件号变成永久记忆。
5. 有一套可重复执行的离线评测，能回答"这次改动到底让记忆变好还是变坏了"。

## 非目标

- 不做向量检索、不引入 embedding、不引外部记忆服务。
- 不按身份（persona）切分记忆——"记忆一份全属于你"仍是既定裁决。
- 不改记忆的隐私边界：仍然严格按 `user_id`，不做任何跨用户共享。
- 不做记忆的导入导出、不做记忆的全文搜索界面（面板已有列表与删除）。
- 不改自动整理的触发节奏（仍是每 6 轮一次）。

## 功能需求

- **REQ-001** 候选与记忆在落库前必须过一遍敏感信息检测（手机号、证件号、银行卡形态、常见密钥/令牌形态、
  含口令的连接串）。命中的**不落库**，并在候选表留一条"已拒绝"的记录，说明被拒原因，让用户知道"它没记"。
- **REQ-002** 全文那一路的召回必须按相关性排序，`created_at` 只作为同分时的次序，不再是主排序键。
- **REQ-003** 结构化那一路不再"恒取最近 8 条"：按 `kind` 权重与本轮输入的相关度排序，时间只做衰减因子。
- **REQ-004** 超过 TTL 且长期未被召回的记忆被淘汰；被持续召回的记忆不被淘汰。TTL 按 `kind` 分档。
- **REQ-005** 召回时刷新被召回条目的"最近使用时间"。刷新必须批量、幂等，且不阻塞回答的流式产出。
- **REQ-006** 自动整理遇到"不确定该不该记"的条目时写入候选表，正式表不新增行。
- **REQ-007** 候选的三种终态都要能落地：接受（进正式表）、拒绝（删除）、超时（过期清理）。
  候选过期清理必须有日志与计数，不允许无限增长。
- **REQ-008** 记忆面板显示待确认候选，每条带来源（哪段对话、模型给的理由），并提供接受/拒绝。
- **REQ-009** 提供离线评测：金集 + 可重复执行的执行器，输出提取、召回、端到端、成本四组数字。
- **REQ-010** 评测不得污染常规构建：没有上游凭据时整组跳过，并**明确输出"未评测"**，
  不允许以"0 条通过"的形式呈现为成功。
- **REQ-011** 候选表与淘汰逻辑都要进注销级联清单（注销后该类数据不留残余）。
- **REQ-012** 记忆总开关的语义扩展：关掉后不召回、不整理、不写候选、也不接受候选。
  现有闸（`ai_user_settings.memory_enabled`）不能被绕开。

## 质量要求

- **precision 优先**：提取侧 precision 目标 ≥ 0.85，recall 目标 ≥ 0.60。宁可漏，不可错。
- **召回噪声有界**：每次 8 条里无关条目不超过 2 条。
- **不增加上游调用次数**：召回排序与淘汰都不能让单轮多一次上游请求。
- **成本有界**：自动整理摊到每轮的 token 增量不超过现状的 1.5 倍。
- **幂等与并发**：同一会话并发不重复整理（现有条件 UPDATE 抢游标的机制不能退化）；
  淘汰任务重复执行不产生额外删除。
- **隐私一致**：候选内容与正式记忆同等级别，只有本人可读；管理端不提供候选的全局浏览。
- **可观测**：过滤命中数、淘汰删除数、候选接受/拒绝数各留一条可见的计数（日志或指标）。

## 验收标准

- **AC-001** 构造一条含手机号 / 含 `password=...` 连接串的候选，写入后两张正式表里**没有**该串，
  候选表有 1 行标记为被拒且给出原因。
- **AC-002** 金集里指定的查询，召回的 8 条中目标记忆排在第一位（改前不保证，改后必须）。
- **AC-003** 6 个月前写入且从未被召回的一条 `weak_topic` 被淘汰任务删除；同期的 `preference` 保留。
- **AC-004** 6 个月前写入但每轮都被召回的 `preference` **不**被删除。
- **AC-005** 淘汰任务连续执行两次，第二次删除 0 行；单批不超过配置上限。
- **AC-006** 自动整理产出一条 `PROPOSE` 时，正式表无新增行、候选表有 1 行。
- **AC-007** 面板上接受候选后，正式表出现该条、候选表该行消失、`source` 记为 `auto`。
- **AC-008** 拒绝候选后，两张表都没有该条。
- **AC-009** 超过 TTL 未处理的候选被清理，且清理有日志与计数。
- **AC-010** 评测报告包含提取 / 召回 / 端到端 / 成本四组数字，且同一金集连跑两次，
  提取 precision 与召回 Recall@8 的差异不超过 5 个百分点。
- **AC-011** 没有 `DEEPSEEK_API_KEY` 时评测整组 skipped，输出明确写"未评测"，不出现"0 条通过"。
- **AC-012** 注销账号后，候选表与两张记忆表都没有该用户的行。
- **AC-013** 关掉记忆总开关后：不召回、不自动整理、写候选被拒、接受候选被拒（四条各有用例）。

## 假设

- 线上记忆表行数很少（未量；按上线时间与两个真人账号推算）。若实际规模大一个量级，
  淘汰的批量大小与索引要重估，但不改需求。
- TTL 起点按 `weak_topic` 90 天、`entry_understanding` 90 天、`goal` 180 天、
  `preference` 365 天、全文那一路 180 天取值。批准本需求即视为确认这组分档，之后调值不算需求变更。
- 金集是**构造的**，不是线上真实语料——线上会话太少。它衡量的是"在这个构造分布上准不准"，
  不等于"在真实用户上准不准"。

## 待确认问题

无阻断项。以下由 Agent 定案，**批准本需求即视为确认**：

- **Q-001 排序公式的具体权重**（`kind` 权重、衰减半衰期、全文 score 的归一化方式）。
  理由：这是数值调参，写在需求里会僵化；它由评测基线决定，改数值不算范围变化。
- **Q-002 `PROPOSE` 由模型自己判断"不确定"**，而不是由规则（内容过短、缺少 `kind` 等）触发。
  理由：规则能覆盖的边界很窄，而"这条该不该长期记"本来就是模型的判断对象；规则作为兜底保留。
- **Q-003 候选的有效期取 14 天**。理由：面板不是每天都会打开，7 天太短；再长会让过期候选挤占注意力。
- **Q-004 淘汰任务每小时一轮、每批 500 行**，与 `TelemetryRetentionPurger` 同一节奏与批量。
  理由：两处同类任务用同一套参数，运维只需要记一组数字。
