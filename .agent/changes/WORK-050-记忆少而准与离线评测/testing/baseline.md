## 三个必须记下来的发现

**① AC-010 的「两次差异 ≤ 5 个百分点」按现在的金集达不到。**

分母只有 14–17，**一条用例翻转就是 6–7 个百分点**。实测两次的 precision 与 recall 都超了容差，
而这不是"功能坏了"，是**样本量不足以支撑这个精度**。三条出路（TASK-012 复测前要定）：

- 跑 3 次取均值，容差加在均值上（成本 ×3）；
- 金集扩到 100 条以上（成本一次性，但标注工作量翻倍）；
- 容差放宽到 10 个百分点并写明理由。

**这一条要回到 `requirements.md` 确认**——改验收标准不是实现自由。

**② `PROPOSE` 不存在时，模型会撞在解析器上。**

第一次跑有 3 例失败：EX-019「不是合法 JSON」、EX-028／EX-029「缺少 store」。
第二次跑只剩 EX-038「缺少 store」。这些用例的共同点是**内容处于"该不该记"的灰区**——
模型想表达"我拿不准"，但四种动作里没有这个词，于是吐出的 JSON 结构不完整，被解析器整次拒绝。
这是 TASK-008（加 `PROPOSE`）最直接的证据：**缺这个动作不是"少一个功能"，是让整次整理作废**。

**③ 同一个 `maxTokens=2048` 会截断。**

EX-019 那次是「内容不是合法 JSON」——不是模型不会写 JSON，而是输出被 `max_tokens` 截断。
它与项目已知的「思考 token 吃满 `max_tokens` 会静默返回空」是同一个坑的不同表现。
TASK-008 升提示词版本时把 `maxTokens` 提到 3072，并在复测里看失败率是否归零。

## 一个金集自身的修正（已落在文件里）

首版金集给 EX-022 / EX-024 标了 `forbidAdd`，实测模型在那两例里除了 DELETE 还写了一条新事实
（「改考研」「最近在学英语」），被判为 precision 扣分。**这是标注过严，不是模型错**：
删掉一条过时的目标，本来就会连带产生一条新的目标。现已改为分别期望一条 ADD，
并把 `forbidAdd` 只留在"同一件事的第二次说法"那 8 条 UPDATE 用例上。

修正前后：precision 0.688 → 0.706，`该 UPDATE 却 ADD` 2/37 → 0/39。

## 召回侧基线（同一时刻、改动前的排序）

生成方式：`cd backend && ../scripts/test-db.sh mvn -B -pl paideia-app -am -Dtest=MemoryRecallEvalTest -Dsurefire.failIfNoSpecifiedTests=false test`，
报告落在 `paideia-app/target/memory-eval/recall-report.md`。30 条用例，每例一个独立用户、独立库表清理。

| 指标 | 改动前 | 说明 |
| --- | --- | --- |
| 首位命中率 | **0.267（8/30）** | 该想起的那条排在第一位 |
| Recall@8 | 1.000（30/30） | 都进了前 8，但位置随机 |
| MRR | 0.622 | 平均倒数排名 |

**怎么读这组数字**：现在的召回按 `created_at DESC` 取前 8，所以"该想起的那条几乎总能进来"（金集里每例只有 2–4 条记忆，
上限就够宽），但**它经常排在后面**——也就是说 8 条里前几条往往是"新但无关"的东西，而模型最先看到的是它们。
首位命中率 0.267 就是"少而准"要修的那处：不是召回不到，是召回的顺序没有意义。

> 指标口径修正记录：报告第一版把"Recall@8"误标成"首位命中率"（两者都算 30/30 的假象）。
> 现在分别输出：首位命中率（rank==1）、Recall@8（rank>0）、MRR。上表是修正后的数字。

## 复测（提示词 v2 + PROPOSE，同一金集）

| 指标 | 基线与复测 | 方向 |
| --- | --- | --- |
| 调用失败 | 1–3 → **0** | 好：灰区不再吐结构不完整的 JSON |
| precision | 0.706 / 0.647 → **0.769** | 好 |
| recall | 0.857 / 0.786 → **0.714** | **差**：更保守，漏得更多 |
| propose 命中率 | 0.000 → **0.833（5/6）** | 好：半自动提案真的在发生 |
| 错 UPDATE 率 | 0 → 0.111（1/9） | 差：有一次改错了目标 |
| delete 命中率 | 1.000 → 0.750 | 差：漏删一条 |
| skip 正确率 | 1.000 → 1.000 | 持平 |

**怎么读**：这是一次明确的取舍，方向和 D-01（少而准）一致——precision 上升、recall 下降、
失败归零、提案可用。但 **recall 掉了 14 个百分点**，不能只说"变好了"：
说明 v2 在"该记的没记"上更保守，而金集里那 4 条漏记要看具体是哪几条（报告逐条结果里有）。
"错 UPDATE" 的 1 次也要盯住：它比漏记更危险（改到了不该改的那条）。

以上三条是 TASK-012 复测报告的输入，验收时不能只引用 precision 一个数字。

## 金集扩容与 AC-010 复验（120 条）

40 条金集上两次跑差 −5.9 / −7.1 个百分点，判为不达标。根因不是功能，是**分母太小**
（14–17，一条用例翻转即 6–7 个点）。按用户裁决扩到 120 条（ADD 36 / UPDATE 24 / DELETE 12 /
PROPOSE 18 / 无操作 30），每个分母 ≥ 24，一条翻转 ≤ 4.2 个点。同一份 v2 代码连跑两次：

| 指标 | 第 1 次 | 第 2 次 | 差 |
| --- | --- | --- | --- |
| precision | 0.857（30/35） | 0.816（31/38） | **−4.1 pp** |
| recall | 0.789（30/38） | 0.816（31/38） | **+2.7 pp** |
| update 命中率 | 0.917（22/24） | 0.917（22/24） | 0 |
| 错 UPDATE 率 | 0.115（3/26） | 0.080（2/25） | −3.5 pp |
| delete 命中率 | 0.750（9/12） | 0.833（10/12） | +8.3 pp |
| propose 命中率 | 0.778（14/18） | 0.778（14/18） | 0 |
| skip 正确率 | 1.000（30/30） | 1.000（30/30） | 0 |
| 调用失败 | 0 | 0 | 0 |

**AC-010 达成**（两项主指标都在 5 pp 以内）。召回侧不参与这项比较：它由 SQL 排序决定，
没有模型参与，两次输出必然一致。

扩容后的分布比 40 条时更接近真实使用：多了 12 条"一次提问/一句抱怨"的灰区用例，
PROPOSE 分母从 6 涨到 18，`propose 命中率` 这个数字才有意义。
