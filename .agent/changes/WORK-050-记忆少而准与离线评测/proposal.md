# 提案 · 记忆的少而准

## 摘要

现在的记忆能写、能召回、能删，但**没有任何东西能回答"它有没有变好"**：召回恒取最近 8 条、写入不做内容过滤、
记忆只增不减、模型不确定的判断直接成为事实。本项先建离线评测把现状量下来，再按"少而准"改四处：
写入过滤、召回排序、时间淘汰、半自动提案。改完用同一套金集复测并如实记录差异。

**排序上有一条硬约束：先测量，再改。** 没有基线的改动，事后无法区分"变好了"和"只是变了"。

## 推荐方案

两线串行、五个切片：

- **S1 测量**（写代码前完成）：三份金集 + 评测执行器 + 用**现状代码**跑出基线，数字进工件。
- **S2 安全与召回**：敏感信息过滤（REQ-001）+ 召回相关性排序（REQ-002/003/005）。
- **S3 淘汰**：`last_used_at` 迁移 + 淘汰任务（REQ-004）+ 注销级联（REQ-011）。
- **S4 半自动**：`PROPOSE` 动作与提示词 v2（REQ-006）+ 候选表与三种终态（REQ-007）+ 面板（REQ-008）。
- **S5 复测**：同一金集重跑，出对比报告；端到端与成本一并记录。

S2 与 S3 无依赖，可以并行；S4 依赖 S1 的金集（提示词 v2 要能用同一批用例判断"提议得对不对"）。

## 范围

**做**：三份金集与一个评测执行器；敏感信息过滤；召回排序（结构化与全文两路）；`last_used_at` 与 TTL 淘汰；
`PROPOSE` 动作与候选表；候选的面板与三个端点；注销级联补表；提示词升 v2。

**不做**（与需求的非目标一致）：向量检索、按身份切分、跨用户共享、记忆导入导出、改整理节奏。

## 备选方案

| 方案 | 内容 | 为什么不选 |
| --- | --- | --- |
| A · 只做排序与淘汰 | 跳过评测，直接改 | 改完只能说"感觉更准了"。WORK-033 的教训是：没有指标时，Recall@3 = 0.3962 这种数字会被当成已交付 |
| B · 先建评测再改（**推荐**） | S1 先跑基线 | 唯一能证明"变好了"的路径；代价是多花一轮改代码前的工作 |
| C · 引入向量检索 | 用 embedding 做语义召回 | 几十行数据的规模下收益近乎零；MySQL Community 不能对 `VECTOR` 排序；索引维护是永久成本 |
| D · 半自动用通知而非候选表 | 推一条站内信让用户去确认 | 通知没有持久状态，用户不在就丢了；候选表能承载"过期丢弃"，也能被面板一次列全 |

## 仓库影响

- **`paideia-ai` · memory 包**：`MemoryStore`（召回排序、`touch` 批量刷新、淘汰入口）、新增 `MemoryCandidateStore`、
  新增 `MemoryRetentionPurger`（对照 `TelemetryRetentionPurger`）、`MemoryProperties` 加 TTL 与候选有效期。
- **`paideia-ai` · 提示词与解析**：`MemoryExtractionPrompt` 升 `memory-extract-v2`（加 `PROPOSE` 动作与"不确定就问"的规则）、
  `MemoryCandidateParser` 认新动作、`MemoryExtractionService` 分流到正式表或候选表。
- **`paideia-ai` · 敏感信息过滤**：新增一个纯函数（`SensitiveContent`），在 `MemoryStore` 的两个写入入口与候选写入前调用。
- **`paideia-ai` · 面板与工具**：`AiMemoryController` 加候选的三个端点；`MemoryTools` 的 `memory_remember` 也要过同一个过滤器。
- **`paideia-app` · 迁移**：`V<时间戳>__memory_last_used_and_candidates.sql`（加列 + 建表 + 索引）。
- **`paideia-app` · 集成测试**：注销级联、候选端点、开关语义。
- **前端 · 学习者端**：记忆面板加"待确认"区（接受/拒绝），客户端加三个方法。
- **测试资源**：`backend/paideia-ai/src/test/resources/golden/memory/` 下三份 JSON（提取 / 召回 / 端到端问题）。
- **工作量最重的一处**：金集标注。70 条用例要一条条写对话与期望，没有结构可以推导。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 金集是我构造的，不是真实语料 | 指标可能只反映"我设想的对话" | 用例里混入真实会话的形状（短问、上下文缺失、方言化表达）；报告里明写该局限，不宣称代表线上 |
| 评测要吃真上游，结果非确定 | 两次跑数字会漂 | 每项跑 2 次取均值，报告里写离散度；AC 只要求差异 ≤ 5 个百分点 |
| 淘汰误删长期有效的事实 | 用户觉得"它又忘了我" | 以"最近被召回"而非创建时间为准；TTL 分档；先灰度观察删除计数再加闸 |
| 排序权重重调不出效果 | 白改一轮 | S1 的基线必须先跑；若基线已经接近上限（如 Recall@8 已 0.95），S5 只记录不硬凑提升 |
| `PROPOSE` 让模型变保守，几乎不提议 | 半自动形同虚设 | 金集里单独一组"该提议/不该提议"的用例；提议率作为报告的一项数字 |
| 候选表成为第二个垃圾场 | 无限增长 | 14 天过期清理 + 每小时任务 + 计数日志（与淘汰同一套机制） |
