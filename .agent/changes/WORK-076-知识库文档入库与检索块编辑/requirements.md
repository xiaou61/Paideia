# 需求

## 背景与调研

起因：看到腾讯开源的企业级 AI 知识库 WeKnora（v0.9.0，Go+Vue，MIT），想评估它对 Paideia 是否有用。

调研结论（2026-11-06，来源：WeKnora GitHub 仓库与官方文档、Paideia 源码）：

- **Paideia 与 WeKnora 是同一物种，不应引入 WeKnora 本体**：技术栈（Paideia 是 Spring 模块化单体）、领域（Paideia 是学习平台）都不对齐，引入等于并跑第二套知识库+助手+沙箱。
- 但 WeKnora 有三处设计，恰好补在 Paideia 现存的缺口上，值得借鉴并落地：
  1. **文档摄入 → Wiki 蒸馏**：WeKnora 支持 PDF/Word/PPT/Excel/CSV/HTML/EPUB/XMind 等，用 `anydoc` 在进程内解析 Office，`docreader` 单独做文档解析；把原始文档蒸馏成「互相链接、带来源引用、按目录组织的 Wiki 页」，还带知识图谱。Paideia 目前**只能存图片与 PDF 附件、不做任何文本解析，知识条目全部由管理员手写 markdown** —— 这是最实的能力缺口。
  2. **检索单元（chunk）可编辑 + 版本回滚**：WeKnora 允许在界面上直接编辑检索切片，每个版本有快照、可 diff、可一键回滚，保存后自动重建索引。Paideia 的 `ai_knowledge_chunks` 完全由条目正文机械切分派生，**不能单独编辑，且下一次增量索引会把任何手工修改覆盖掉**；条目本身也没有修订历史。
  3. **目录树 / Wiki 浏览 / 图谱视图**：WeKnora 上传文件夹保留目录结构，提供 wiki 浏览器与交互式图谱。Paideia **已经有分类树（`knowledge_categories` 自关联）、概念图谱（`knowledge_concepts`+`knowledge_concept_edges`+前端 `concept-graph-layout`）与 `/graph` 页面** —— 这一块大部分已具备，价值主要在「上传保留目录树」和「wiki 阅读/浏览页」，不应重造。

### Paideia 现状事实（源码核对）

- 知识库 `paideia-knowledge`：分类（自关联树）、条目（markdown 正文，`status` draft/published，`source`/`fingerprint` 字段由 V24 提供）、条目关系、概念/概念边/条目-概念关联、自评、学习进度、学习轨道、附件（`knowledge_files`，本地/S3 存储）、搜索日志。
- 附件 `FileService`：**只允许 png/jpeg/gif/webp/pdf**（`MediaTypeSniffer` 白名单），只做魔数校验与存储，**不做文本抽取**。
- RAG（WORK-072）：表 `ai_knowledge_chunks`（`entry_id`、`chunk_index`、`title`、`content`、`content_hash`、`embedding LONGBLOB`、`dimension`、`updated_at`；唯一键 `(entry_id, chunk_index)`）。`Chunker` 按段落机械切块（maxChars/overlap，块首拼标题）；`KnowledgeRagService` 只索引已发布条目，按内容 hash 增量，**变更时整条目 delete+insert**，Java 精确余弦检索，`retrieveContext` 注入 `[[entry:id]]` 前 Top-K。**无 rerank、无混合检索、无块编辑**。
- 管理端条目接口：create/update/delete，发布=把 `status` 置 published 的 PUT；**无条目修订历史、无块级编辑、无回滚**。
- 前端 `@paideia/knowledge`：已有 `category-tree`、`concept-graph-layout`、关系邻域、学习进度、正文目录等；`/graph` 页面已存在。

## 目标

1. 让管理员能把**原始文档**（首期 PDF）导入知识库，系统解析出文本、用模型蒸馏成「知识条目草稿」（标题+正文 markdown+建议分类/概念），进入现有 `knowledge_entries` 的 draft 状态，管理员审核后发布，并自动进入现有 RAG 索引。
2. 让管理员能**查看并编辑单个检索切片**，编辑后只重建该块向量；手工编辑不被后续增量索引覆盖；每次编辑留快照，可 diff、可回滚。
3. 在**不重造**现有分类树与概念图谱的前提下，补齐「上传保留目录树」和「按目录浏览/阅读 wiki 页」的入口，让蒸馏出的内容可以被像手册一样翻阅。

## 非目标

- 不引入 WeKnora、Go 服务、独立向量库、rerank、GraphRAG、混合检索。
- 不做学习者私有文档上传（除非「待确认问题 Q1」改判）。
- 首期不做图片 OCR、音视频等多模态。
- 首期不做 HTML WYSIWYG，Markdown 仍是唯一正文格式。
- 不改动现有对话/积分/记忆链路的行为。
- 不重做现有概念图谱与分类树可视化。

## 用户与工作流程

- 主要用户：管理员（当前知识库内容治理的唯一角色）。学习者只消费发布后的内容。
- 流程（文档入库）：管理员上传文档（或整目录）→ 系统解析文本 → 模型蒸馏出条目标题/正文/分类/概念 → 落为 draft 条目 → 管理员在管理端审阅、修订、发布 → 发布后自动进入 RAG 索引。
- 流程（块编辑）：管理员进入某条目的「检索块」视图 → 编辑某块 → 保存（只重建该块向量）→ 历史里可看到 diff 并回滚。

## 功能需求

### A. 文档入库与 Wiki 蒸馏

- **REQ-101 文档解析**：管理端支持上传文档并抽取纯文本。首期至少支持 **PDF**；解析在本机完成，不依赖外部云服务。
- **REQ-102 蒸馏为条目草稿**：把解析文本交给现有 AI 能力，产出结构化结果：标题、正文（Markdown）、建议分类、建议关联概念；落为 `knowledge_entries` 的 `draft` 条目，**不自动发布**。
- **REQ-103 来源溯源**：每个由文档生成的条目必须记录来源（复用 `knowledge_entries.source` 与 `fingerprint`），能回看到原始附件。
- **REQ-104 目录树保留**：上传整个目录时保留其目录结构，映射为 `knowledge_categories` 的子节点（已存在的同名分类复用）。
- **REQ-105 幂等去重**：同一文档重复导入按内容指纹识别，不重复生成条目（可选择「更新」或「跳过」）。
- **REQ-106 失败可见**：解析/蒸馏失败要有可见的失败状态与错误原因，并支持重试；失败不得留下半截条目或孤儿附件。
- **REQ-107 用量记账**：蒸馏调用模型产生的用量走现有 AI 计费/观测链路，不绕过积分与追踪。

### B. 检索块可编辑 + 版本回滚

- **REQ-201 块查看**：管理端可按条目查看其 RAG 切片列表（内容、序号、更新时间）。
- **REQ-202 块编辑**：允许编辑单个切片的文本；保存后**只重建该块的向量**，不重建整条目。
- **REQ-203 编辑不被覆盖**：被手工编辑的块在后续增量索引时保持不变（需要「手动/锁定」标记）；当条目正文再次变更、导致自动切分结果与手工块冲突时，必须提示而不是静默覆盖。
- **REQ-204 版本历史**：每次块编辑保存快照；可查看 diff、可一键回滚到任一历史版本。
- **REQ-205 回滚即重索引**：回滚后对应块的向量同步重建，检索结果随之更新。

### C. 目录 / 浏览 / 图谱

- **REQ-301 复用分类树**：浏览沿用现有 `knowledge_categories` 树，不新建导航模型。
- **REQ-302 Wiki 阅读页**：提供按目录浏览已发布条目的阅读视图，正文渲染复用 `MarkdownBody`，保持与现有条目页一致的渲染与样式。
- **REQ-303 图谱复用**：条目/概念关系展示沿用现有概念图谱与 `/graph`，不重造。

## 质量要求

- **QR-001 数据隔离**：文档入库与块编辑仅管理员可用；不得把来源文档内容泄漏给无权限用户（沿用现有附件读端点已知取舍，不新增越权面）。
- **QR-002 降级**：embedding 或模型不可用时，块编辑保存不阻塞正文编辑，明确提示「向量重建暂不可用」，与 WORK-072 的降级语义一致。
- **QR-003 一致性**：条目发布/下架后，其块索引随之增删（复用现有增量索引语义）。
- **QR-004 可观测**：导入与蒸馏任务有状态与耗时记录，纳入现有 AI 运行观测。

## 约束与依赖

- 遵循项目常驻规范：仅 MySQL、手写 MyBatis、迁移用 14 位时间戳文件名、生产迁移只建结构、UTF-8/UTC 时间等。
- 复用现有 `ai_knowledge_chunks`、`knowledge_entries`、`knowledge_files`、现有 embedding（Ollama bge-m3）与 AI 计费链路，尽量少加依赖。
- 依赖 WORK-072（RAG 基础）与 WORK-004（知识库结构）已达成的能力。

## 用户决定

（2026-11-06 用户逐项确认）

- **Q1 文档归属**：仅管理员上传，解析后生成知识条目草稿，管理员审核发布。**不做学习者私有文档上传**（不进本期范围，避免私有数据隔离与隐私评审扩张）。
- **Q2 首期格式**：仅 **PDF**（外加现有图片附件能力不变）。Word/PPT/Excel 留待后续工作项。
- **Q3 蒸馏产物**：生成 **知识条目草稿**，进入现有 `knowledge_entries`（draft→审核→published）并自动进入现有 RAG 索引；**不新建独立 wiki 表**。
- **Q4 块编辑范围**：**管理员单块覆盖编辑 + 版本回滚**；不做条目级版本历史，不做块的拆分/合并/重排。

## 实现选择

- 文档解析优先走本地库（PDF 用本地解析库抽取文本），不引外部 OCR 服务。
- 蒸馏复用现有 AgentScope/模型调用端口，结构化输出落 `knowledge_entries` 草稿。
- 块编辑通过在 `ai_knowledge_chunks` 上增加「手动覆盖」标记与快照表实现，最小改动现有 RAG 服务。
- 目录树保留：上传时后端按相对路径层级创建/复用分类。

## 验收标准

- **AC-101**：上传一个 PDF，能抽取到可读文本并生成至少 1 条 draft 条目；条目正文为 Markdown，含来源记录。
- **AC-102**：蒸馏结果可按现有流程发布为 published 并出现在 RAG 检索结果中。
- **AC-103**：重复上传同一 PDF 不产生重复条目（指纹去重）。
- **AC-104**：上传一个含子目录的文件夹，生成对应的分类树层级。
- **AC-105**：解析/蒸馏失败时界面显示失败状态与原因，可重试，且不残留半截条目。
- **AC-201**：管理端能看到某条目的全部块；编辑单块后只有该块向量变更，其他块不变。
- **AC-202**：条目正文再次变更触发增量索引时，被手工编辑的块不被覆盖；冲突时给出提示。
- **AC-203**：块编辑历史可见 diff，回滚后块内容与检索结果恢复为历史版本。
- **AC-204**：embedding 不可用时保存块编辑不报 500，给出降级提示，正文不受影响。
- **AC-301**：可按分类树浏览已发布条目；正文渲染与现有条目页一致。
- **AC-302**：不新增第二套分类/图谱模型，现有 `/graph` 与分类树行为不变。
