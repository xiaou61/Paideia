# AIOps 缺口修复提案

## 摘要

不新增能力面，只把 WORK-042/043 留下的断点接上：事件能关闭、历史能复用、告警能聚拢、阈值只有一份、重启能补诊断、评测有真实证据。全部改动落在既有 `ops` 包、Grafana provisioning 与管理端事件页，**零迁移、零新依赖、零新服务**。

核心判断：这八条不足里，只有第一条是「坏了」，其余都是「没做完」。所以先修坏的那条（一行配置），再按「让下一次故障更省」的顺序补：历史复用 > 同期事件 > 复用窗口 > 其余。

## 推荐方案

### 总体结构（改动点标 ★）

```
Grafana 17 条规则 ──★resolved 也投递──> OpsHookController
      ★阈值来自 ops-thresholds.conf        │
                                           ▼
                              ops_incidents ──★手动关闭──> RESOLVED
                                   │
                              ▼ OpsDiagnosisService
                         ★同实例 600s 内复用，不新开
                         ★重启后补一次漏掉的诊断
                                   │
                    ★OpsIncidentContext（历史同类 + 同期 OPEN）
                                   ▼
                        证据 v4（新增 <context>，仍 ≤12k）
                                   ▼
                      OpsDiagnoser（一次调用，不变）
                                   ▼
              管理端事件页：★关闭按钮 ★分页/时间筛选 ★Grafana 深链
```

### 六个 track 与优先级

| 阶段 | 内容 | 为什么排这里 |
| --- | --- | --- |
| P0 | resolved 投递（REQ-001） | 现网事件关不上，事件历史正在失真；一行配置 |
| P1 | 手动关闭、分页（REQ-002/003） | 没有兜底手段，关不上就只能改库 |
| P2 | 历史同类 + 同期事件 + 复用窗口（REQ-004/005/006） | 直接降低重复故障的推理成本与告警风暴花费 |
| P3 | z-score、阈值单一来源、重启补诊断（REQ-007/008/009） | 提高检测质量与恢复能力，动部署，风险最高 |
| P4 | 金集、live、深链、日志单元（REQ-010–014） | 让「准不准」有证据；体验与扩展性 |

### 为什么是这套

- **不加服务**：全部落在已有进程与已有表；对比 Keep 要自带 DB/UI/worker，HolmesGPT 要跑在 K8s，本项目单机单服务没有这个预算。
- **不改模型调用形态**：仍是「一次采证 + 一次调用」，积分可预估；agent 循环明确列为非目标（升级分水岭见需求件）。
- **风险集中在两处**：Grafana provisioning（改错会丢告警）与 systemd 环境变量（改错应用起不来）。两处都用「安装时检查 + 渲染后校验 + 可回滚文件」处理。

### 参考做法（借什么，不借什么）

| 来源 | 事实 | 借什么 |
| --- | --- | --- |
| PagerDuty / Incident.io 事件模型 | 事件有 triggered/acknowledged/resolved 与时间线 | 手动关闭复用 RESOLVED + 时间线，不引入 ACK 状态机 |
| Keep | 告警去重/关联/富化 | 「同期 OPEN 事件进证据」这一条最小关联；不部署 |
| HolmesGPT | 每轮把历史经验与工具结果一起给模型 | 「历史同类事件 + 上次结论 + 评分」进证据；不做工具循环 |
| Google SRE Workbook（burn-rate） | 多窗口多燃尽率 | 不变；本次只补 z-score 作为方差错口的补充 |
| Prometheus 录制规则 | 一次录制、多处消费 | z 值也走录制规则，证据与告警读同一序列 |

## 范围

### 做

- resolved 投递、手动关闭、分页与时间筛选。
- 证据新增 `<context>`：历史同类事件（同指纹 3 条 / 同告警名补 2 条）与同期 OPEN 事件（5 条）。
- 同实例 600 秒内已有 DONE 诊断时不再新开。
- CPU / 5xx / P95 的 z-score 录制规则、证据与告警条件。
- 阈值单一来源（`ops-thresholds.conf` → Grafana 规则 + 应用环境变量）。
- 重启补诊断（OPEN + 6h 内 + 无 DONE + 每次启动 ≤1 条）。
- 金集 12 → ≥20，live 命令与归档；事件页 Grafana 深链；日志单元可配置。

### 不做

- agent 式调查循环、自动修复、外部 AIOps 平台、常驻 ML 服务。
- 把诊断移出应用进程（升级路径，不在本项）。
- 按路由维度的基线与告警（基数与噪音不可控）。
- 事件分派、值班表、ACK、升级通知。
- 新表、新迁移、新依赖。

## 备选方案

### A. 只改配置（只做 REQ-001）

最有力：最短、零风险。为什么不够：事件关上了，但历史仍然不复用、告警仍然聚不拢，下一次同类故障还是从零推理。

### B. 引入 Keep 做告警关联

最有力：现成的去重/关联/富化/工作流。为什么没选：多一套 DB/UI/worker，单管理员 + 20 条规则用不上；license 非标准。我们用一条 SQL 解决「同期事件」，覆盖了本项目 80% 的关联价值。

### C. 阈值继续两份 + 构建期校验脚本

最有力：不动部署，零风险。为什么没选：只防「改了一边」，不解决「改了一处要重启两边」；AC-008 要求的是修改后两侧一致。代价是多一个安装期渲染步骤，但 `install-ops.sh` 已有令牌占位符先例。

### D. 重启后不补诊断，靠人工

最有力：零成本。为什么没选：应用重启（发版、OOM）恰好是最常见的「故障期间诊断缺失」场景；补诊断有 6 小时与每次 1 条的上限，成本可控。

## 交付拆分

1. **P0**（0.5 天）：REQ-001，配置 + 现网复核。
2. **P1**（1 天）：REQ-002/003，关闭入口与分页。
3. **P2**（2 天）：REQ-004/005/006，证据上下文与复用窗口。
4. **P3**（1.5 天）：REQ-007/008/009。
5. **P4**（2 天）：REQ-010–014。
6. **收口**（0.5 天 + 窗口）：回归、部署、快烧演练、报告。

合计约 **6–8 个工作日**；P0/P1 可先单独上线。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| Grafana 改收件人后丢告警 | 只改一个布尔值；安装后 `grep` 校验；部署前备份 `/etc/grafana/provisioning` |
| 阈值占位符未渲染 | 安装脚本渲染后检查残留 `__`，有则非零退出；规则文件先备份 |
| 环境变量名绑定失败导致应用读不到阈值 | 用 Spring 宽松绑定的大写无短横线形式，安装后从 `/actuator/env` 或日志核对；失败则回退 drop-in |
| 证据变长导致 12k 被日志挤掉 | context 自身 ≤2000 字符，且计入 nonLogChars；超预算先截 context |
| 关联窗口把真正不同的第二个根因吞掉 | 默认 600s 可配；被跳过的告警仍进「同期事件」证据；时间线写明复用编号 |
| 重启补诊断在发版时重复花钱 | 只补「无任何 DONE」的事件；每次启动 ≤1 条；6 小时窗口；开关可关 |
| 金集扩到 20 条后 live 更贵 | live 只在改提示词/证据后手动跑；prompt 模式仍在 CI 免费跑 |
