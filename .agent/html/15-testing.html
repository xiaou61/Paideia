12 / 工程规范

什么才算「跑过了」

这页回答：改完一处，跑哪几条测试就够？为什么绿色的构建不能当证据？

先看一个具体场景

你修了一个「过期令牌没有返回 401」的 bug。跑了一遍测试，全绿，提交了。

问题是：这遍绿说明了什么？如果本来就没有一条测试覆盖那个分支，绿只能说明「原来的测试还认识这个代码」。所以这个仓库对「跑过了」有明确要求——不是「跑了一遍」，是「改坏的时候它必须变红」。

三环：按固定开销，不按用例数量

贵的不是用例，是每次运行的固定开销。后端集成测试要连数据库、起上下文；纯函数测试跑完是 0.1 秒。所以内环的设计目标是「不启上下文、不进网络」。

环什么时候跑跑什么预算（实测）
内环每改完一处mvn -pl <模块> -am test -Dtest=<类>；前端 pnpm --filter <包> test< 30 秒
外环一个切片收口（= 提交前）非 app 全模块（88 秒 / 410 条）+ 四个守卫类（46 秒 / 9 条）+ 前端 typecheck/test + 改动那一端的 e2e< 4 分钟
全量交接 / 改跨模块契约 / 改 schema / 发版带 -WithTests后端全量 -T 1C + 对应端 e2e< 5 分钟
没有「发布前」这一档。这个项目上线就是随手跑一次部署脚本，不存在「攒批次、一次跑全量」的节点。所以不要把任何检查挂在一个虚构的阶段上——那只会变成永远不跑。

e2e：先选文件，别默认全量

学习者端全量是 61 条 / 2 分 36 秒，但单条边际成本只有约 2.4 秒、固定启动约 20 秒——所以跑一个文件是 13–54 秒，全量是 156 秒。三种选法：

  • playwright test e2e/<名字>.spec.ts —— 改哪个页面就跑对应文件
  • playwright test --grep "<片段>" —— 只验一条路径，实测 13 秒
  • playwright test --last-failed —— 修完失败只重跑失败的

三端全量只在动了共享包（@paideia/ui / core / auth / knowledge）或发版前跑。

四条「证据」的定义

1 必须用独占的测试库，共用库跑出来的红不是缺陷 任何碰数据库的验证都走 scripts/test-db.sh。它给这一轮分配 paideia_run_<时间>_<pid>，成功自动删、失败保留库名并打印。同机可能有别的会话在跑，共用库会互相删数据——造出「单类全绿、全量报红」那种红，它既不是产品缺陷，也不能当证据。
2 看结果先看 Skipped 列 没配数据库口令时，集成测试是跳过而不是失败，BUILD SUCCESS 照样成立——曾经有一次「115 条测试全绿」其实是 115 条一条没跑。这个坑在这个项目里被记过两次。
3 不用 H2 替代 MySQL 项目完全放开 MySQL 专有特性：upsert、JSON 列与算子、SKIP LOCKED、全文检索。这些在 H2 上要么没有、要么行为不同——用 H2 跑绿了，等于证明了一份不存在的兼容性。
4 修 bug 要做反向验证 先把修复临时改回坏的样子，确认新测试确实变红，再改回来。没做这一步，你得到的只是一条「能通过」的测试，而不是「能发现这个 bug」的测试。

四道守卫：它们替你记住容易忘的事

接口变了必须做的两件事

  1. 标 @ApiAccess（在控制器类或方法上）。不标 → ApiSurfaceTest 红；标错 → ApiContractTest 红（它真的会去发请求，验证声明的 ADMIN 确实 403）。
  2. 在 ApiWalkthroughTest 里加一段真实调用。不加 → 覆盖断言红，并且点名是哪条端点没被打到。

跑完会更新响应结构快照 src/test/resources/api-shape.json。改字段（改名 / 增删 / 改类型）时快照会红并逐条列差异；确认是有意变更后，用 -Dapi.shape.update=true 重新生成，review 那份 diff 再提交。

测试里最容易骗自己的两件事

  • 用桩把真问题盖住。把上游端口桩掉之后，「每轮都调一次上游、但只上报最后一轮 token」这种缺陷永远不会被发现——测试证明的是分支走对了，不是账记对了。
  • 把「当前是错的」写成绿的。掌握度算法有一条测试，断言的是「信息增益目前低于随机」——它是如实记录缺陷，不是认可那个行为。写这种测试时必须在测试名或注释里说清楚：它保护的是「知道这件事」，不是「就这样吧」。

并发会话：两件必须各占一份的东西

1 数据库：每个会话一个独占库 由 test-db.sh 自动分配，不要手工指定共用库。
2 端口：PAIDEIA_BACKEND_PORT / PAIDEIA_APP_PORT / PAIDEIA_ADMIN_PORT 不覆盖的话，e2e 的 reuseExistingServer 会静默复用别人的服务——测试是绿的，但打的是别人的进程和别人的库。

接口自查：二十秒走一遍

ApiWalkthroughTest 是一个手动跑的端到端自查：自己注册账号、把 69 步（覆盖 62 个端点）走一遍、注销收尾、比对结构快照，并在 .agent/testing/runs/ 留一份报告。它不改部署脚本、不接 CI。

五个已经踩到的坑，读一遍能省半天：

  • RequestMappingHandlerMapping 有两个 Bean（Actuator 也注册了一个），注入必须带 @Qualifier。
  • 业务端点不要用不写 method 的 @RequestMapping：它会响应所有动词，按方法枚举的检查会静默跳过它。
  • 附件接口按字节嗅探类型，白名单是 png / jpeg / gif / webp / pdf。
  • 注销后 access 令牌仍可用（到期才失效）——断言「立刻 401」是错的。
  • 共用测试库会与 e2e 的 devdata 漂移，表现为 Flyway checksum mismatch。自查请用独立库。

自查清单

  • 跑的是 scripts/test-db.sh 吗？Skipped 是 0 吗？
  • 新逻辑有测试吗？修 bug 做了反向验证吗？
  • 新端点标了 @ApiAccess、加进了 ApiWalkthroughTest 吗？快照 diff 看过吗？
  • 改了共享包，跑的是三端 e2e 而不是一个文件吗？
  • 并发会话下，端口和库都是自己的吗？
