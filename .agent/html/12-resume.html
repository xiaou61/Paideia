12 / 求职者面

让 AI 改简历，但不能让它编

这张图回答：上传一份 PDF 到产出一版新简历，中间有几道人工动作？模型写出来的东西凭什么能信？

先看一个具体场景

你把 PDF 简历传上去，立刻看到九条体检结论：「工作经历第 2 条没有量化结果」「项目里写了『精通』但没证据」——每条都指到具体位置，没有总分。

你点「优化」，它给出十二条改写提案，每条都是「原文 / 建议」并排。默认一条都不采纳，你勾了其中五条，点「定稿」。这时系统会拦下其中一条——因为它把「参与」改成了「主导」，那是身份字段被升级。

这里真正难的四件事

一、体检不出分数

九项检查，每项只回答「通过 / 待改」，并给出位置。不调用模型、不出 0–100 分。

理由是校准：0–100 分无法校准——没人能说清 72 分和 75 分差在哪。而一个假精确的分数会诱导用户把精力放在刷分上，而不是去修那几条具体的毛病。

九项里每一项都写清了「什么样的简历该被判待改」，不写「建议优化」这种放之四海皆准的话。日期格式、联系方式是否可点、意向是否明确、经历是否有量化……都是可以直接判的。

二、提案默认不采纳

模型给的改写全部以 accepted = false 落库。用户主动勾选才进定稿。这条不是交互偏好，是责任划分：简历是求职者的对外材料，AI 只出建议，写不写进去必须由本人签字。

每条提案的结构是「原文 / 建议 / 变更类型 / 闸门状态 / 违规点」，不是一段整体替换——所以用户能只采纳一半，也能看到某个字段被拒的具体原因。

三、事实闸门：在落库之前拦住「编」

整个工作项里最重要的一段代码，在用户点「定稿」之后、落库之前。四条检查对应四类真实失真：

相似度阈值（0.35 那一类）没有理论依据，只能靠夹具校准。所以它被写成常量并在验证报告里记录实测——而不是散落在代码里的魔法数字，也不是拍一个「看起来很科学」的值。

四、版本链：任何一次定稿都不覆盖旧版

documents → versions → proposals 三层：文档是身份，版本是不可变快照，提案挂在版本上。resume_edit_history 记人工改动。不提供「删除中间版本」——简历的价值恰恰在于能回退到「投上一家时用的那一版」。

身份化：求职者是一个「面」，不是一种权限

这个子系统承载了 WORK-010 的裁决：用户可以选择「求职者」身份，页面与推荐跟着变，但身份不是权限。

→身份 ≠ role，两个正交轴身份永远不写进 role 字段。role 决定「能不能做」，身份只决定「默认做什么、先给你看什么」。
→页面优先，身份当默认你在简历页，行为就是简历行为；身份只在没有场景时提供默认。所以「同一个面试官行为 × 你的记忆」才是个性化产生的地方。
→记忆一份全属于你不按身份切成两份——切换身份不该丢上下文，也不该出现「跨身份传记忆」这种新问题。
→一期不做硬门槛不做「求职者才能看简历页」这种限制。推荐可以偏，权限不能。

设计取舍

  • 为什么拆成三次调用而不是一次：解析要输出结构化数据、分析要输出分类、提案要输出逐条改写——三种输出的形状和失败处理都不同。合并成一次，失败了就全废；分开之后，解析成功但分析失败时用户至少能看到结构化结果。
  • 为什么三笔消耗分开记：一次求职 = 解析 + 分析 + 提案。用户要能看出「改一份简历到底花了多少」，合成一类就永远算不清。
  • 为什么闸门在「定稿」而不是「生成」时跑：生成时拦，用户看不到提案被拒的理由；定稿时拦，用户可以看着违规点改那一句再提交。
  • 为什么不做「一键全采纳」：那等于把责任从用户手里拿走。现在的设计里，责任边界是一条清晰的线：AI 出建议，人签字，机器只校验事实越界。

读图要点

  • PDF 解析失败要有兜底。扫描件（纯图片）抽不出文字时应当明确告诉用户「这份看不出来」，而不是给一份空结构化结果让他以为解析成功。
  • 闸门不判断「写得好不好」。它只判断「有没有超出原文的事实」。写得平淡但真实，可以通过；写得漂亮但编了数字，必须拦。
  • 版本链不可变，但可以「从旧版本派生」。回退不是覆盖，是再开一个新版本。
  • 这个子系统的 AI 调用是「贵」的那一类（要读整份简历），所以每一次都要预留-结算，和对话同一条账务管线。
