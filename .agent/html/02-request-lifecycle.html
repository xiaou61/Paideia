02 / 请求链路

一次请求的一生

这张图回答：一个 HTTP 请求从浏览器到数据库，经过哪几道闸？被拒绝时，401、403、402、429 分别是哪一层拒绝的？

先看一个具体场景

你隔了一晚上再打开网页，页面正常刷新出来了，屏幕上什么都没发生。但后台其实经历了一次「令牌过期 → 被拒绝 → 悄悄换一张 → 重试成功」，全程你无感。

理解这条链路只需要理解一件事：短的令牌容易过期，长的令牌不能天天拿出来用。所以短的用来干活，长的只用来换短的。

只有换不到新令牌时，你才会看到「登录已失效，请重新登录」。如果有人拿着同一张长期令牌第二次来换，系统会认为令牌被盗用，把整条会话作废——那是防盗用，不是 bug。

它内部是怎么做到的

鉴权只有一层，且是无状态的：SecurityFilterChain 解析 JWT，不查数据库、不建会话（SessionCreationPolicy.STATELESS）。「这段代码关不关得住」由规则的声明顺序决定——Spring Security 按顺序取第一条匹配的规则，写反了不会报错，只会在某天表现为越权。这是全项目最危险的一类错误，没有之一。

过了鉴权之后还有第二条闸：业务闸。积分不足（402）不是授权问题，是业务规则，由 CreditService.reserve 在 Service 层抛出，位置在 Controller 之后、调用上游之前。

登录与刷新：一条链、一把锁

登录失败要被限流，按账号和来源地址两个维度分别计数——只按 IP 挡不住撞库，只按账号挡不住扫号。刷新令牌用「家族」组织：每次轮换签发新的、旧的立刻作废；如果旧的被再用一次，说明有第二个人拿着同一个令牌，于是整条家族链一起吊销。

读图要点

  • 无 Cookie、纯 Bearer。这样才能让浏览器 SPA 和 Electron 桌面壳共用一套认证。代价是任何「浏览器自己发起的请求」都拿不到凭据——<img>、iframe 导航、Service Worker 注册都是（见 10 与 09）。
  • 业务码与 HTTP 状态是两个维度。BizException 带 ErrorCode，由 GlobalExceptionHandler 映射成 HTTP 状态，同时把业务码写进响应体。映射必须穷尽：历史缺陷是一个 switch 掉了 default，业务码 40200 正确而 HTTP 变成了 500。
  • 未知路由要显式 404。否则 @ExceptionHandler(Exception.class) 会把它兜成 500——「路径写错了」看起来像「服务端崩了」，还会掩盖「本该存在的端点不存在」。
  • 响应体统一由 ApiResponseBodyAdvice 包一层，异常路径带 traceId，前端报错截图可以直接拿去查日志（见 09）。
  • 登出只吊销 refresh 家族，已签发的 access 在剩余寿命内仍然有效。这是无状态 JWT 的固有代价，不是漏洞；要立刻失效就得引入令牌黑名单，那会变成有状态。
  • 前端守卫不是授权边界。路由守卫只决定「显示什么」，/api/** 上的规则才决定「能做什么」。静态资源放行也不等于数据放行。

代码在哪

  • backend/paideia-security/…/SecurityConfiguration.java — 全部规则与顺序，注释里写了每条「必须排在谁之前」
  • backend/paideia-account/…/login/LoginService.java — 登录、失败限流
  • backend/paideia-account/…/token/TokenService.java — 签发、轮换、家族吊销
  • backend/paideia-account/…/support/RateLimiter.java — 计数窗口
  • backend/paideia-web/…/GlobalExceptionHandler.java、ApiResponseBodyAdvice.java — 错误映射与包装
改这一层之前先读 10。新增一条 /admin/** 规则时，位置比内容更容易出错；已经有一次真缺陷是「把 /sandbox/admin/** 写在 /sandbox/** 之后」，任何登录用户都能下架别人的数据集——它不报错，是契约测试抓到的。
