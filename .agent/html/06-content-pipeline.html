06 / 内容线

内容生产线

这张图回答：平台上的内容从哪来？哪些是人写进去的，哪些每天自己长出来？为什么速递一天只允许调一次 AI？

先看一个具体场景

早上八点，你还没起床，系统自己出去转了一圈：Hacker News、几个技术 RSS、GitHub 趋势榜。抓回来几十条，它只调一次 AI，把这一堆压成摘要并逐条打分，然后按热度排好。

九点你打开「每日速递」，看到一屏今天的内容。另一条线是面经：抓完先进草稿箱，管理员看过才放出来——因为抓来的东西可能是垃圾。

它内部是怎么做到的

三条互不干扰的源：人工文稿（markdown，脚本导入）、抓取（面经，进草稿）、聚合（新闻 / GitHub，落速递表）。前两条最终都变成 knowledge_entries，第三条不进知识库——速递是独立的两张表，因为它每天过期、且不属于学习路径。

「一天只调一次 AI」是硬约束，不是优化：抓回来的几十条会被压缩成一次摘要调用，摘要、去重、0–100 重要度打分在同一轮里完成。这条约束决定了这套系统的成本上限是「每天几分钱」而不是「随流量线性增长」。

读图要点

  • 定时任务从不用「每 24 小时」。速递用带时区的 cron（默认北京 08:00，可配），因为 fixedDelay=24h 的锚点是「上次跑完」，会随重启漂移。
  • 异常必须吞掉并记录。@Scheduled 抛出的异常只会让 Spring 打一行错误，下一轮照旧——所以每个任务都自己记成功/失败，指标挂在 ScheduledTaskMetrics 上。没有这个指标，「昨晚跑没跑」只能靠猜。
  • 重启后要能补当天内容。换成 cron 之后重启不再自动补，所以额外的启动任务带着「今天已经有内容就跳过」的判断。少了这个判断，部署完就要等一整晚。
  • 抓取永远先落草稿。面经是外部文本，相关性判定也可能错；直接发布等于让抓取失败的垃圾内容上线。管理员复查后才进知识库。
  • GitHub 趋势页经常超时（生产机访问不到时是常态），所以是「页面优先 + Search 兜底」，兜底条件是「最近 3 天、≥50 星、最多 30 条」。不要以为那是主路径。
  • 抓来的正文是不可信输入。它会被喂给模型做摘要——这是整条生产线唯一的安全风险面（提示注入）。读这一层时先看它对输入做了什么，而不是看它画得多漂亮。
  • 速递的「今天」按北京时间算，与库里的 UTC 存储是两个概念。跨时区显示的 bug 十次有九次出在这里。

代码在哪

  • backend/paideia-ai/…/digest/DigestJob.java — 每日采集调度、启动补跑判断
  • backend/paideia-ai/…/digest/DigestCollectionService.java — 三源汇总、去重、调用摘要
  • backend/paideia-ai/…/digest/GithubTrendingSource.java、GithubStarHistory.java — 趋势页与兜底
  • backend/paideia-ai/…/essay/EssayCollectionJob.java、NowcoderEssaySource.java — 面经抓取
  • backend/paideia-ai/…/decision/TechEssayFilter.java — 判定服务调用
  • scripts/import-course.mjs — 人工内容导入
  • backend/paideia-app/…/ops/ScheduledTaskMetrics.java — 定时任务的成功/失败计数
这条线上最贵的错误是「重复采集」。每条内容都有一个指纹（标题+链接一类的哈希），靠唯一键覆盖。改采集逻辑时如果弄丢了指纹，第二天就会出现一堆标题相同的重复条目，而且是每天多一批。
