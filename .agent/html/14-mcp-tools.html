14 / 对外能力

让外面的 AI 读你的数据

这张图回答：我在编辑器里问 AI「我这周学了什么」，它凭什么能拿到真实数据？它会不会顺手把我别人的数据也读走？

先看一个具体场景

你在自己的编辑器里接上了 Paideia 的 MCP 服务，问了一句「我这周学了什么」。AI 列了一下它能用的工具，挑了一个「查学习记录」的，拿到了真实数据，然后回答你。

整个过程中，你从来没有在这个对话里输入过密码——它用的是一串你亲手创建的访问令牌。这串令牌只属于你，也只会拿到你的数据。

它内部是怎么做到的

核心是一份工具目录、两条出口：应用内部的助手用同一份目录（它调工具走进程内），外面的客户端走 /mcp。两条路共用工具定义，但登录方式与限流完全不同——这是刻意的，因为外部客户端的威胁模型不一样。

一次外部调用，七步，顺序固定

三道护栏各自防什么

1视图校验防「猜」工具清单是按令牌的权限域裁出来的。校验的是「你有没有被呈现过这个工具」，而不是「工具存不存在」。这样即使有人知道某个工具的名字，只要它不在你的视图里，就是未知工具。
2限流防「一次失控」记在内存里，是护栏不是计费依据。多实例部署时每个实例各算各的（总量会翻倍），但代价是漏放几次，而不是错杀用户——这个取舍写在代码注释里。
3配额防「长期失控」按令牌查当天累计次数，落库。它回答的是「这个令牌今天已经用了很多次」，而不是「刚才那一秒太快了」。

PAT 是一条平行于登录态的通道

外部客户端不在浏览器里，没有 JWT 可带。所以有一套独立的令牌：创建、命名、吊销、记录每次调用的用量。它和登录态互不替代——你在网页上登录用的是 JWT，你的编辑器用的是 PAT。

改工具清单时要同时想两件事：「应用内助手能不能调它」和「这个外部令牌能不能调它」。这是两条独立的授权路径，只改一处会留下一个沉默的缺口。

设计取舍

  • 为什么不做「把全部 API 都转成 MCP 工具」：工具越多，模型挑错的概率越高，每次对话塞进去的 schema 也越贵。现在只挑「读自己的数据、做自己的事」这一层，写操作只保留明确安全的几个。真实数字是：全部工具的 schema 加起来还在安全区，但没有理由为了完整性把选择成本也一起放大。
  • 为什么参数里的 userId 是「删除」而不是「校验」：校验要穷尽所有别名与嵌套形式，删掉是确定性动作。归属只认令牌。
  • 为什么截断要标记：不标记的话，AI 会把「前 200 条」当成全部，然后给你一个自信的错答案。截断本身不是问题，不告诉它才是。
  • 为什么两条出口共用目录：工具定义只有一份，改一处两边同时生效。代价是两条路的鉴权与限流必须各自实现——那是必要的不对称。

读图要点

  • 工具名只能用下划线。上游模型对工具名的字符集有限制，带点或短横线会在某些模型上直接失败——这条在真连上游时才发现，桩测试看不出来。
  • 工具结果必须逐条发回。合并成一条，模型会漏读中间那几项。
  • 审计与计数不能分叉。二者在同一个收尾处写，否则会出现「日志记了但计数没记」的对不上账。
  • 令牌泄露的处理只有吊销。它是随机串，没有「改密码」——所以管理界面上要能一眼看到「最近用过的时间」。
