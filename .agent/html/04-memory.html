04 / 记忆

记忆：什么时候被写，什么时候被读

这张图回答：助手「记得你」这件事，是靠什么触发的？关掉记忆开关之后，已经写进去的数据去哪了？

先看一个具体场景

你跟助手说「我不爱看视频，只看文字」。这句话当时不会立刻改变什么。你们接着聊，聊到第六轮的时候，后台趁你没注意，把这句话提炼成一条短记忆存起来。

下次你随口问「推荐点东西看看」，它在开头就把这条记忆翻出来塞进提示词——于是推荐里没有视频。你不用再说一遍，也看不见这个过程。

它内部是怎么做到的

记忆不是「一个开关」，是三个开关 + 三条写入路径 + 一条读取路径。这张图把四者放在一起：实线是数据流，虚线是开关对它的影响。

记忆在提示词里的位置

这一点决定了「为什么它有时候像记得、有时候像忘了」。每次请求发给上游的内容是分段的，顺序固定：

1系统提示 + 场景说明公共行为，同场景所有人一样
2记忆片段（≤ 8 条）只要命中关键词就进来；命中不了就是没有
3对话历史窗口按条数截断，越老越先掉出去
4当前页面上下文你在哪篇文章里问的，这个信息只在当轮存在
5你这一句话最后才是本体

两张表、两个上限

表放什么上限怎么进提示词
ai_memories_structured键值式的短记忆（偏好、目标、约束）512 字符每轮都参与召回，最常用
ai_memories_text一段话的长记忆（背景、经历）1024 字符按关键词命中才进

两张表都带 user_id，严格私有。「记忆是全局的」这句话指的是跨身份、跨页面都生效，不是所有人共享——这一条被误解过一次，所以写进图里。

设计取舍：为什么不用向量检索

  • 规模不需要。一个人的记忆量级是几十到几百条，关键词 + 时间排序已经够用；向量库在这里只会多一套要备份、要迁移的外部依赖。
  • 数据库不支持。项目只用 MySQL，社区版不能对 VECTOR 列做排序。真要上向量就得引入第二个数据库。
  • 代价是召回不精确。所以有两条补救：自评变化会写一条结构化记忆（保证「你哪块弱」这种关键信息一定在），以及手动「记住这条」让用户能把重要的事钉死。
  • 判重为什么全喂给模型，而不是先检索再判。检索判重会在「说法不同但意思相同」时失效（「不爱看视频」vs「偏好文字」）。把最近 40 条直接给模型看，准确率更高，代价是每次整理多几百 token。
  • 为什么关掉不删。用户关开关的心理预期是「别再用它」，不一定是「销毁它」。真要销毁有一个明确的清空动作，两步分开。

读图要点

  • 提取本身要花钱（虽然不贵），所以走独立的 MEMORY_EXTRACT 流水。用户在积分面板上能看出「没聊几次为什么花了钱」。
  • 提取在异步线程里跑。所以它失败不影响你这一轮的回答；但也意味着「刚说完就想让它记住」不会立刻生效，最快也要等下一轮或第 6 轮。
  • 游标是条件 UPDATE 抢的（<=> 比较），并发或重复触发都不会把同一段对话提取两次。这条有反向验证过。
  • 已知缺口：写入前没有 PII / 密钥过滤。用户把 token 粘进对话，提取路径可能把它写成一条记忆。这是读代码就知道该补、但确实还没补的一项。

代码在哪

  • backend/paideia-ai/…/memory/MemoryStore.java — 召回（RECALL_LIMIT = 8）、写入、判重池
  • backend/paideia-ai/…/memory/MemoryExtractionService.java — 触发条件与游标抢占
  • backend/paideia-ai/…/memory/MemoryProperties.java — roundsPerExtraction = 6
  • backend/paideia-ai/…/memory/SelfAssessmentMemoryBridge.java — 自评 → 记忆的桥
  • backend/paideia-ai/…/settings/AiSettingsStore.java — 三个开关与「清空并关闭」
  • db/migration/V6__create_memory_tables.sql、V12__memory_auto_extraction_and_settings.sql
别把「记忆」和「会话历史」混为一谈。历史是逐字的消息记录，按窗口截断；记忆是从历史里提炼出来的短句。注入提示词时两者是两段不同的内容，开关也是分开的。调参时先分清是哪一段给多了或给少了。
