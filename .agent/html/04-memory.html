04 / 记忆

记忆：什么时候被写，什么时候被读

这张图回答：助手「记得你」这件事，是靠什么触发的？关掉记忆开关之后，已经写进去的数据去哪了？

先给结论

记忆不是「模型自己决定记什么」，而是三条明确的写入路径加一条自动的读取路径。读取一直是自动的（每一轮都用你这句话当关键词去找），只有写入需要触发条件。所以「加个开启个性化记忆的开关」这个需求如果按字面理解会做错——召回本来就在跑，缺的是写入的自动化程度。

两张表：ai_memories_structured（短结构，512 字符以内）与 ai_memories_text（长文本，1024 字符以内）。两张都带 user_id——「记忆是全局的」指的是跨身份、跨页面都生效，不是所有人共享。这一条被误解过一次，值得写进图里。

读图要点

  • 写入路径一：手动。用户说「记住这条」，明确意图，直接落库。可带结构（键值式的短记忆）或长文本。
  • 写入路径二：每满 6 轮自动提取（异步）。不阻塞对话；用一条带条件的 UPDATE 抢游标（extracted_upto 一类的列配 <=> 比较），并发或重复触发都不会重复提取同一段。判重不靠检索，而是把最近 40 条结构化记忆全喂给模型，让它判断「这条已有」还是「这条是新的」——重复时用覆盖，不追加。
  • 写入路径三：自评变化。改一次知识点自评就写一条结构化记忆。这是「你哪块弱」能进脑子而不只是进表的唯一桥；没有它，助手只能在你问的时候临时去查自评表。
  • 读取：每轮都跑，最多 8 条。全文索引可用时走全文检索，否则退化成 LIKE。召回结果不重新打分排序——这是已知限制，不是设计意图。
  • 开关是三个，不是一个：总开关、引用已存记忆、引用对话历史。清空并关闭是一个端点，避免「先删后关」中间被打断导致数据又被写回来。
  • 提取本身要花钱（虽然不贵），所以走独立的 MEMORY_EXTRACT 流水。用户在积分面板上能看出「没聊几次为什么花了钱」。
  • 已知缺口：写入前没有 PII / 密钥过滤。用户把 token 粘进对话，提取路径可能把它写成一条记忆。这是这份导读里唯一一处「读代码就知道该补、但确实还没补」的地方。

代码在哪

  • backend/paideia-ai/…/memory/MemoryStore.java — 召回（RECALL_LIMIT = 8）、写入、判重的池子
  • backend/paideia-ai/…/memory/MemoryExtractionService.java — 每轮触发条件与游标抢占
  • backend/paideia-ai/…/memory/SelfAssessmentMemoryBridge.java — 自评 → 记忆的桥
  • backend/paideia-ai/…/settings/AiSettingsStore.java — 三个开关与「清空并关闭」
  • backend/paideia-app/src/main/resources/db/migration/V6__create_memory_tables.sql、V12__memory_auto_extraction_and_settings.sql
别把「记忆」和「会话历史」混为一谈。历史是逐字的消息记录，按会话窗口截断；记忆是从历史里提炼出来的短句。注入提示词时两者是两段不同的内容，开关也是分开的（引用记忆 / 引用历史）。调参时先分清是哪一段给多了或给少了。
