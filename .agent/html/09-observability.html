09 / 运维

怎么知道它正在变坏

这张图回答：出了问题怎么被发现的？指标、日志、链路三者怎么汇到一起？一次纯后端发版为什么是六十秒而不是二十分钟？

先看一个具体场景

凌晨一点，某个接口开始大量报错。系统自己发现「按这个速度烧下去，本月的可用性预算撑不过两天」，于是触发一条告警。

告警打到应用里，先生成一条事件；诊断器把指标、日志、最近一次发版拼起来，写出一段人话结论。你第二天早上看到的不是一堆曲线，而是「哪个接口、从几点开始、可能跟什么有关」。

它内部是怎么做到的

三类数据各有分工，缺一类就会得出错误结论：只看指标会知道「在变坏」但不知道「为什么」；只看日志会淹没在噪音里；只看链路只知道「慢」，不知道「整体是否可接受」。

运营视图：从行为事件聚合，不从业务表实时算

管理端有一个数据大屏（点击、搜索、速递打开率、学习完成量）。它不直接对业务表跑实时聚合，而是读行为事件表：digest_item_clicks、knowledge_search_log 这类「谁在什么时候做了什么」的记录。

1业务表只回答「现在的状态」，事件表才回答「发生过什么」「这周有多少人搜过 Redis」在业务表里没有答案——搜索日志是独立写入的。
2大屏只读，不写避免运营视图的查询压力反噬业务；也避免「在看板上一改，业务数据跟着变」这种事故。
3聚合口径写在查询里，不写在界面上同一个数字在两处算出不同结果，是最难解释的 bug。

设计取舍：四个看起来奇怪的决定

  • 指标只允许本机读。/actuator/prometheus 会暴露 JVM 内部结构与业务维度标签，不能像 health 那样整体放行。前提是进程前面没有反向代理——一挂反代，远端地址都变成回环，这条白名单立刻失效，那时必须改成独立回环管理端口。
  • Grafana 反代整体放行，安全边界交给 Grafana 自己。试过三条路都不行：要求 ADMIN（iframe 导航不带 Authorization → 401）、加 ?ticket=（静态资源与子请求不带查询串 → 逐个 401）、只放行 /public/**（dashboard API 又 401）。根因是本项目无 Cookie、纯 Bearer，而 Grafana 是 SPA。
  • 用燃尽率而不是阈值。阈值在「一直小错」和「突然大错」之间只能顾一头；燃尽率把两者统一成「预算还能撑多久」。
  • 发版用 jar c0fm，不是 cfm。cfm 会 deflate 嵌套的 jar，Spring Boot 4 直接起不来——这个字符是发版链路上最贵的一次事故（真断过六分钟）。

读图要点

  • SLO 规则最常见的三个坑，演练时全踩过：5xx 速率在无请求时是空集被当成 NoData、SLI 无样本时算出 NaN 被当数值、protobuf 省略的 status 零值被写成空串。改规则时先想「没有数据时它会怎样」。
  • 告警 webhook 不是「免鉴权」。它只允许回环来源，并再做一次常量时间令牌比较——机器到机器，没有 JWT。
  • 别用 pnpm -r build 发版。它会把 Electron 桌面壳一起打（首次还要下载 Electron），近二十分钟。纯后端改动用 -SkipWeb。
  • 服务器上的 exploded/ 与 exploded.manifest 由脚本维护，不要手工删——删了下次就退化成全量传输。
  • 健康检查有两个：公开的 /actuator/health 与需要登录的 /api/v1/health。探活要用前者。
