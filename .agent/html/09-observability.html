09 / 运维

怎么知道它正在变坏

这张图回答：出了问题怎么被发现的？指标、日志、链路三者怎么汇到一起？一次纯后端发版为什么是六十秒而不是二十分钟？

先给结论

三层数据各有分工：指标回答「是否在变坏」（Prometheus，按本机来源读取）、日志回答「发生了什么」（Loki）、链路回答「慢在哪一步」（Tempo，traceId 从 SSE 的 done 事件一路对到用户的那次点击）。

告警不是「阈值超了就叫」，而是 SLO 燃尽率：按错误预算的消耗速度触发，能在「一直小错」和「突然大错」两种情况下都合理报警。规则文件有配套的单元测试，改规则先跑测试。

发版：只传差异

读图要点

  • 指标端点只允许本机读。/actuator/prometheus 会暴露 JVM 内部结构与业务维度标签，不能像 /health 那样整体放行。注意这条白名单的前提是「进程前面没有反向代理」——一旦挂了反代，远端地址都变成回环，白名单就失效了，那时必须改成独立的回环管理端口。这句话写在代码注释里，不是修补计划。
  • Grafana 反代是整体放行的，安全边界交给 Grafana 自己的登录。试过而放弃的三条路：要求 ADMIN（iframe 导航不带 Authorization 头 → 401）、加 ?ticket=（静态资源与子请求不带查询串 → 逐个 401）、只放行 /public/**（dashboard API 又 401）。根因是本项目无 Cookie、纯 Bearer，而 Grafana 是 SPA，需要一套跨请求自动携带的会话。
  • 告警 webhook 不是「免鉴权」。它只允许回环来源，并在控制器里再做一次常量时间令牌比较——机器到机器，没有 JWT。
  • SLO 燃尽率告警有一类共同的坑，演练时全踩过：5xx 速率在无请求时是空集被当成 NoData、SLI 无样本时算出 NaN 被当数值、protobuf 省略 status 零值被写成空串。改规则时先想「没有数据时它会怎样」。
  • 别用 pnpm -r build 发版。它会把 Electron 桌面壳一起打（首次还要下载 Electron），近二十分钟。纯后端改动用 -SkipWeb，前端没改时脚本本来就会跳过那 80 秒。
  • jar c0fm 不是 jar cfm。cfm 会 deflate 嵌套的 jar，Spring Boot 4 直接起不来——真断过六分钟。这个字符是发版链路上最贵的一个字符。
  • 服务器上的 exploded/ 与 exploded.manifest 由脚本维护，不要手工删。删了下次发版就退化成全量传输。
