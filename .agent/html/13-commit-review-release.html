13 / 工程规范

提交、评审与发布

这页回答：什么时候该提交？哪些事要单独授权？一次发版实际发生了什么？

先看一个具体场景

你改完了一个切片：后端三处、前端一处，测试跑绿了。接下来有三件不同的事——提交、推送、部署。它们不是一回事，授权也不同。

动作谁决定粒度失败/后悔的代价
本地提交改完一轮能独立验证的工作就提交一个切片一次可改、可 reset，代价最小
推送必须单独授权一次明确的指认公开仓库，提交即公开
部署必须单独授权一条命令线上中断；可回滚但有损

为什么提交要切小

这个仓库可能同时有多个会话在改同一个工作区。攒着不提交，会让「哪些改动属于谁」变得不可判定，也让误操作的回退范围变大。分笔提交把回退粒度压到一轮——出问题时你能只扔掉那一轮。

同时这也是一条工程纪律的另一面：不要用一个「顺手改」把无关文件卷进本次提交。提交时说得出「这一笔在做什么」；说不出来就该拆。

并发会话：一个会话一棵树

提交前必须做的一件事：扫一遍暂存区

这不是形式主义，是发生过的事故。本仓库是公开仓库：一旦凭据进入 Git 历史，删文件不解决问题（历史、fork、缓存仍可检索），只有轮换凭据才算处理完。而且并发会话会把你的工作区改动卷进它的 git add——所以不能只扫自己写的文件，要扫 git diff --cached。
  • 禁止进入任何被跟踪文件：凭据、密钥、令牌、密码、私钥、连接串、服务器地址。包括源码、配置、文档、.agent/ 工件、更新历史、提交信息、Issue 与 PR 正文。
  • 本地敏感配置放被忽略的文件（.env.local、application-local.yml、*.local.*），仓库里只留占位示例。
  • 引用密钥只写环境变量名，不写值。

评审：按区间，不按 commit

审查用 ocr，由人发起，不装钩子、不接 CI——避免每个 commit 都消耗模型额度。三条口径：

1 审区间，不逐 commit 逐 commit 会重复计费，而且拆碎的提交单独看会丢掉完整意图、产生误报。
2 只修 critical 与 high medium / low 不修、也不积压。报告仍然全量归档——它是证据，与「改哪些」是两件事。
3 运维与一次性脚本不进审查范围 排除 deploy/**、scripts/**、*.ps1、*.sh、*.py、*.mjs。一次实测里 84 条 high 有三成落在这类文件上，人肉筛掉每次都要重做。content/ 不在排除清单里。

报告写到 .agent/reviews/<YYYY-MM-DD>-<范围>.md 并随仓库提交。报告里只记范围、结论与证据，不回显 provider / api_key 之类的配置。

发版：一条命令，只传差异

  • jar c0fm 不是 jar cfm。少了那个 0，嵌套 jar 会被 deflate，Boot 4 直接起不来——真断过六分钟。这是发版链路上最贵的一个字符。
  • 别用 pnpm -r build 发版。它会把 Electron 桌面壳一起打（首次还要下载 Electron），近二十分钟。前端没改时脚本本来就会跳过。
  • exploded/ 与 exploded.manifest 由脚本维护，不要手工删；删了下次退化成全量传输。
  • 没有「发布」这个节点。改完随手部署即可，不需要攒批次——所以也不要把检查挂在一个虚构的「发布前」阶段上。
  • 回滚有损。增量发版是覆盖式的，回滚要重新走一遍旧版本；数据库迁移不自动回退。

每次实际修改都要留一行

改完追加 .agent/history/updates.md：变更、决策、依据、验证、本地提交边界、远端推送状态。它不是流水账——半年后「这条规则为什么存在」的答案在这里，而不在提交标题里。

写的时候注意一条：heredoc 里有反引号时要用 <<'EOF'（带引号），否则反引号会被当命令替换执行，内容静默丢失。

自查清单

  • 这一笔说得清「在做什么」吗？无关文件被卷进来了吗？
  • git diff --cached 扫过凭据了吗？
  • 并发会话在工作区里时，我提交的路径是显式列出来的吗？
  • 是推送/部署吗？——有单独授权吗？
  • updates.md 追加了吗？

权威清单在哪

  • AGENTS.md — 「节奏」与「保密规则」两节
  • .agent/rules/always.md — 提交授权、审查工具与报告归档
  • .agent/notes/dev-workflow.md — 发版耗时拆解、工作树磁盘占用
  • scripts/release.ps1 — 发版全流程
  • .agent/history/updates.md — 每条规则与每次变更的来历
