五十九张表怎么分家

这张图回答：这些表是按什么分组长的？为什么全库只有 14 条外键——它省下了什么，又要求你手工补什么？

先看一个具体场景

你点「注销账号」。最常见的做法是数据库里的外键自动帮你把关联数据一起删掉——但这里没有那么多外键，所以程序必须拿着一张写着表名的清单，一张一张去删。

清单漏了一张，你的数据就会留在库里，而且不会有任何报错、任何测试变红。这就是「只有 14 条外键」这个选择的真实代价。

它内部是怎么做到的

表按模块分域，因为模块之间本来就不许互相读表。全库 59 张表、14 条真实外键：外键只出现在「同一个域内、且关系不会跨模块」的地方（比如分类树的父子、条目到分类）。跨模块的关联一律由应用层保证——ai_memories_text.user_id 指向 users.id 这件事数据库不知道，只有删用户的代码知道。

这是刻意的取舍：外键会锁住迁移顺序与删除顺序。代价是删用户变成一份手工维护的表清单，漏一张就是隐私事故。

真正有约束的那 14 条

读图要点

  • 看不到边 ≠ 没关系。这份图只画数据库层面真实存在的约束。要找关联得读 mapper 与实体。
  • 删用户是清单作业。AccountDeletionService 与各模块的注销监听器各管一段，表清单就是安全边界。新增一张带 user_id 的表，必须同时把它加进对应清单——否则用户注销后数据还在，而且没有任何测试会红。
  • ai_model_credentials 是个陷阱。生成图里能看到它，因为 V4__create_ai_tables.sql 确实建了它；但它已被 V20261022180940__drop_ai_model_credentials.sql 删除（平台凭据改造后不再落库）。看生成清单时不要把它当活表。
  • 迁移文件名是 14 位时间戳，不是递增号。递增号是并行会话共享的命名空间，实测两个分支都写 V25 会让整个应用起不来（Found more than one migration with version 25）。MigrationVersionFormatTest 同时挡纯数字号与同秒重复。
  • 迁移只建结构，测试数据在 db/devdata。MigrationSeedOverlapTest 会把「生产迁移往种子表插行却不显式给 id ≥ 900」变成构建失败——这类 bug 只在零数据新库上出现，开发库和生产库永远看不出来。
  • 时间列一律由应用写 UTC。JDBC 上 connectionTimeZone=UTC 与 forceConnectionTimeZoneToSession=true 两个参数缺一不可，只配一个会让时间再偏 8 小时。
  • 改 schema 前先看有没有人在改同一张表：git log --all --oneline -- backend/paideia-app/src/main/resources/db/migration。时间戳解决了「版本号撞车」，解决不了「两个分支改同一张表的不同列」这种语义冲突。

代码在哪

  • backend/paideia-app/src/main/resources/db/migration/ — 42 个迁移，图的唯一事实源
  • backend/paideia-app/src/main/resources/db/devdata/ — 开发与测试数据
  • backend/paideia-account/…/user/AccountDeletionService.java — 注销级联的入口
  • docs/architecture/05-database-tables.md — 由脚本生成的完整表清单（含每张表出自哪个迁移）
  • scripts/test-db.sh — 任何碰数据库的验证都从这走，别直接连共用的测试库
