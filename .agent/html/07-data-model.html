五十八张表怎么分家

这张图回答：这些表是按什么分组长的？为什么全库只有 14 条外键——它省下了什么，又要求你手工补什么？

先看一个具体场景

你点「注销账号」。最常见的做法是数据库里的外键自动帮你把关联数据一起删掉——但这里几乎没有外键，所以程序必须拿着一张写着表名的清单，一张一张去删。

清单漏了一张，你的数据就会留在库里，而且不会有任何报错、任何测试变红。这就是「只有 14 条外键」这个选择的真实代价。

它内部是怎么做到的

表按模块分域，因为模块之间本来就不许互相读表。分域的边界不是数据库设计的结果，是代码边界的投影。

账号与身份4users、refresh_tokens、user_identities、learner_profiles所有域都引用它，但只有它自己有真外键
内容与知识12knowledge_entries、knowledge_categories、knowledge_concepts、learning_*唯一有完整外键的一块，见下

迁移文件里一共出现 59 张表，其中 ai_model_credentials 建完又被删掉（平台凭据改造后不再落库），现役 58 张。

其余八个域：一条外键都没有

ai_memories_text.user_id 指向 users.id 这件事，数据库不知道，只有删用户的代码知道。question_attempts.entry_id 也是一样：它确实引用内容条目，但 SQL 里没有约束。

设计取舍：少外键换来了什么

  • 换来了迁移顺序的自由。有外键的表不能随便重建、不能先于被引用表创建；跨模块加一个引用，就要在两个模块的迁移之间建立依赖。项目里有 42 个迁移、多个并行会话，这个顺序约束的代价很高。
  • 换来了删除策略的灵活。注销时要按隐私规则精确决定「哪些留、哪些删、哪些匿名化」，级联删除做不到这种粒度。
  • 代价一：删用户变成清单作业。AccountDeletionService 与各模块的注销监听器各管一段，表清单就是安全边界。新增带 user_id 的表，必须同时加进清单——否则没有测试会红。
  • 代价二：孤儿数据全靠自觉。删了条目，它的浏览记录、掌握度不会自动消失。要么写清理任务，要么接受它作为历史。
  • 代价三：关联查询要靠人。没有外键就没有图形化的关系图，读代码的人得自己去 mapper 里找 entry_id 是怎么用的。

迁移的三条纪律

1 文件名用 14 位时间戳，不用递增号 递增号是并行会话共享的命名空间：两个分支都写 V25，应用会直接起不来。MigrationVersionFormatTest 挡纯数字号与同秒重复；但挡不住「两个分支改同一张表的不同列」这种语义冲突。
2 生产迁移只建结构，测试数据放 db/devdata MigrationSeedOverlapTest 会把「往种子表插行却不显式给 id ≥ 900」变成构建失败。这类 bug 只在零数据新库上出现。
3 时间列一律由应用写 UTC JDBC 上 connectionTimeZone=UTC 与 forceConnectionTimeZoneToSession=true 两个参数缺一不可，只配一个会再偏 8 小时。

读图要点

  • ai_model_credentials 是个陷阱。生成清单里能看到它，因为 V4 确实建了它；但它已被 V20261022180940__drop_ai_model_credentials.sql 删除。看清单时不要把它当活表。
  • 看不到边 ≠ 没关系。要找关联得读 mapper 与实体，别指望从表结构推。
  • 表数会变，而且会变得很明显。加一个迁移就可能变。改完跑一次 node scripts/gen-arch-diagram.mjs，再回来对一遍本页的数字。
  • 改 schema 前先看有没有人在改同一张表：git log --all --oneline -- db/migration。

代码在哪

  • backend/paideia-app/src/main/resources/db/migration/ — 42 个迁移，表结构的事实源
  • backend/paideia-app/src/main/resources/db/devdata/ — 开发与测试数据
  • backend/paideia-account/…/user/AccountDeletionService.java — 注销清单的入口
  • docs/architecture/05-database-tables.md — 由脚本生成的完整表清单（含每张表出自哪个迁移）
  • scripts/test-db.sh — 任何碰数据库的验证都从这走
