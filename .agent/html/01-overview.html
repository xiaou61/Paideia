01 / 全景

它由什么拼成

这张图回答：我打开浏览器点开这个站点，一共用到了哪几台机器、几个进程、哪些外部服务？「11 个模块」是 11 个服务吗？

先看一个具体场景

你打开浏览器输入地址，看到网页；登录、点开一门课、做题、问 AI、写笔记。管理员在另一个页面加了一篇新文章，第二天所有人都看得到。这一整套东西，跑在一台机器上的一个程序里，外面只连着一个数据库和一个 AI 服务。

记住这一句就够：它不是一堆互相调用的微服务。所以不存在「某个服务挂了」，出问题就是那个程序直接报错。

它内部是怎么做到的

部署上是一台机器、一个 Java 进程、一个数据库。十一个 Maven 模块是编译期边界，不是部署单元——它们全部打进同一个 jar，由同一个 systemd 单元跑起来。前端有两个可运行面（学习者端、管理端），构建成静态资源后由这同一个进程提供，管理端挂在 /admin/ 子路径下。

外部依赖只有四个：MySQL（唯一数据源，不可替换）、对象存储（附件，走 S3 协议，有端口抽象）、AI 上游（OpenAI 兼容接口，唯一真正花钱的地方）、以及两个可选增强（面经判定服务、抓取与监控）。

十一个模块，一条向下的依赖链

依赖方向是依赖方 → 被依赖方，而且只许单向下行：底层的模块不需要知道谁在调它。spring-modulith 在构建期挡循环依赖，ModularityTest 在测试期挡「跨模块去引用别人的 internal 包」——所以模块之间只能通过公开契约接口说话，实现类改名不会波及别的模块。

读图要点

  • paideia-app 是唯一的装配点。它依赖全部十个模块，负责把各自登记的 Bean 拼起来。除它之外，没有任何模块依赖别人的「应用层」。
  • paideia-ai 为什么依赖 knowledge 和 sandbox：助手要能读知识库条目、要在 SQL 沙箱里跑自己生成的 SQL。这两个依赖是能力依赖，不是数据依赖——AI 模块没有拿到别人的表。
  • 三个底座模块之间互不依赖。platform（异常、业务码、时间、Clock）、persistence（MyBatis 与会话）、security（JWT 与规则）各自独立，谁也不认识谁。
  • 没有消息队列。全仓的异步只有两种形态：请求线程内的异步任务，和 @Scheduled 定时任务（清理过期状态、抓取、每日速递）。看到架构规则里提到消息中间件时不要去找代码，那是没落地的决策。
  • 外部依赖里最容易误判的是对象存储。它有一个端口接口，本地磁盘实现与 S3 实现可以配置切换——「端口可换」这句话的真假，取决于同一批用例有没有在两种实现上都跑过。

代码在哪

  • backend/pom.xml — 模块清单与依赖声明，图的唯一事实源
  • backend/paideia-app/ — 装配点；启动类、ModularityTest、所有业务编排都在这
  • backend/paideia-platform/ — 异常基类与业务码、Clock
  • frontend/apps/app、frontend/apps/admin、frontend/apps/desktop — 三个可运行端
看图时最容易犯的错：把模块当微服务，然后去找它们之间的 HTTP 调用。没有。所有跨模块调用都是同进程的方法调用，失败不会变成超时，也不会重试——出问题就是一个异常向上抛，由 GlobalExceptionHandler 转成业务码（见 02）。
