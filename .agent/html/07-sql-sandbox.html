07 / 执行沙箱

在别人的服务器上跑你的代码

这张图回答：我写一句 SELECT 点运行，3 秒后拿到结果表和执行计划——中间到底启动了什么？别人上传的数据集为什么不会把我的会话搞坏？

先看一个具体场景

你在 SQL 练习页写了一句 SELECT * FROM orders WHERE user_id = 7，点「运行」。三秒后出现一个结果表，下面还有一棵「执行计划」树：它走的全表扫描，被标成了红字。

如果你写的是 DROP TABLE，会被当场拒绝；如果你跑了个死循环，会在超时后被杀掉，页面告诉你「执行超时」。这背后没有任何一个「你自己的数据库」——每次运行都是一次性的。

这里真正难的四件事

一、容器参数就是安全边界，所以它被拆成一个纯函数

启动容器的命令行是纯字符串拼装，单独一个类。理由写在代码注释里：少写一个加固标志就等于没隔离，而这件事在本地根本测不出来。所以每一条标志都被单元测试钉死。

1没有 -v / --mount代码通过 stdin 进容器，宿主机文件系统不出现。挂载一次，整个沙箱就形同虚设。
2镜像来自配置，不来自请求用户输入永远进不了命令行。这是「命令注入」在这个子系统里的唯一入口。
3--read-only 之后仍要可写 /tmpjavac 要写 class 文件，所以给一个 64 MB 的 tmpfs——只读不等于什么都不能写。
4内存与 CPU 按语言取值SQL 容器的 mysqld 常驻约 348 MB，按 Java 的 256 MB 配会被直接 OOM 杀掉。
5不截断用户的源码截断后的代码编译不过，报错会指向一段用户看不懂的地方——比直接拒绝更糟。

二、代码送进去的时候要分帧，否则会被拼进源码

容器里的脚本是常量，不含用户内容。但它不能简单地 cat > Main.java 把代码和 stdin 一起倒进去：cat 会一直读到 EOF，于是用户传入的程序输入会被追加进源码——变成莫名其妙的编译错误，而程序自己拿到的是 EOF。

解法是分帧：先读一行「源码字节数」，再 dd 恰好那么多字节作为源码，剩下的才是程序的标准输入。

三、数据集上传：三道检查，顺序不能换

白名单本身就是一套设计判断：

  • 为什么自己解析而不交给 MySQL 拒：LOAD DATA、CREATE TRIGGER、PROCEDURE、EVENT 在 MySQL 里都是合法语句。而数据集会被别人的运行反复执行——里面藏一个 TRIGGER，它就在每次别人跑 SQL 时执行一次，等于把「一次性上传」变成「持续执行」。
  • 为什么是白名单不是黑名单：语句种类会随版本增加，黑名单永远会漏。白名单漏掉的后果是「某个合法写法被拒」，可以补；黑名单漏掉的后果是「任意逻辑被执行」。
  • 只做词法层，不做完整解析：一个完整 SQL 解析器是很大的依赖，而这里要挡的只是「语句类型」这一层。剩下的风险由「干跑 + 容器隔离」兜。

四、执行计划的坑：整棵树在一个字段里

实测（真实镜像 + 生产加固参数）发现 mysql --xml 把整棵树塞进一个字段值，拿到的是「1 列 × 1 行」，多行之间是 \n。结构信息不在结果集里，只能从文本还原。

还原出来还不够——判读是字符串匹配，而 MySQL 8 的 TREE 输出没有机器可读的「是否用索引」标记，只有 Index lookup / Table scan 这类文本。所以判读被收进一个纯函数并单测：判错了用户会得到一条假的性能结论。

判定顺序本身是个陷阱：Index scan 含 scan，Table scan 也含 scan——但前者走索引、后者全表扫。所以必须先判 Table scan，反过来会把全表扫描标成「走了索引」。Filter / Sort / Aggregate 也不参与判定，一律标 other，否则「Filter 在上、Table scan 在下」会被误读成「这行走了索引」。

配额与审计：被拒绝的也要留痕

1每人同时只能跑一个执行很贵（一次容器启动 3–5 秒）；并发不设限等于让一个人把整机的容器名额占满。
2当天次数有上限（500）按 UTC 日切。不为「看起来像本地的一天」引入时区——那会让跨时区部署的计数不一致。
3被拒绝的也写审计，但不计入次数审计是为了回答「他为什么被挡」。只在成功时写，用户说「我明明没跑几次」时就无从对账。

逐步录制：为什么只给「能读多少给多少」

可视化调试要把一次执行录成一步一步的状态，再在页面上回放（见 13）。录制这一侧有三条硬约束：

  • 上限 300 步、响应 256 KB。录制器里有硬上限，服务端再兜一次——两边都写，是因为「录制器被换掉」比「服务端被绕过」更可能发生。
  • 超时被杀时，最后一行常常只有半截 JSON。那一行直接丢掉，而不是整批失败：用户要的是「被杀之前发生了什么」，我们要的是「能读多少给多少」。
  • 不截断源码（同上），但截断输出——stdout / stderr 各自截到固定字节数并明确标记。

设计取舍

  • 为什么用容器而不是进程隔离 + 权限降级：用户代码是任意代码，进程级隔离挡不住 fork 炸弹和文件系统探测。容器是这里唯一「便宜的强隔离」。代价是机器上必须有 Docker，没有时整个沙箱能力降级并明确报错。
  • 为什么不做「一个用户的常驻数据库」：那会引入状态、清理、配额和跨用户隔离四件事。每次重建数据集只要几秒，换来的是「永远干净」。
  • 为什么 AI 造数据也要走上传同一条路：它同样是不可信内容。参考解会被真跑一次取期望结果，再走同一套三道检查——不给 AI 开一条后门。

踩过的坑

  • ModularityTest 拦住「跨模块引用 internal 包」。沙箱要把附件交给别的模块读，正解是开一个公开契约接口、把端口移到包根，而不是放宽测试。
  • Clock Bean 缺失只有真启动才报。切片测试里注入 mock 全绿，整个应用起不来——这又一次说明「绿测试不等于能跑」。
  • 懒加载守卫自己也有缺陷。守卫必须反向验证：把懒加载去掉，守卫要变红。只写不舍得跑一次的守卫，等于没有守卫。

代码在哪

  • backend/paideia-sandbox/…/run/DockerCommand.java — 容器命令行（纯函数）与分帧脚本
  • backend/paideia-sandbox/…/run/RunSlot.java — 并发名额
  • backend/paideia-sandbox/…/dataset/SqlStatementGuard.java — 语句白名单
  • backend/paideia-sandbox/…/dataset/SqlDatasetUploadService.java — 三道检查与先试后存
  • backend/paideia-sandbox/…/trace/SandboxTraceService.java — 逐步录制与半截 JSON 处理
  • backend/paideia-sandbox/…/audit/SandboxQuotaService.java — 配额与审计
  • frontend/packages/sql-workbench/src/explain.ts — 执行计划解析与判读（纯函数 + 单测）
这个子系统的验证成本特别高。容器、镜像、Docker 守护进程都不在单元测试里——「真容器干跑」与「真上游 AI 出题」这两条，在开发机没有 Docker 时只能靠结构保证。这属于「没有哨兵」，不是「功能坏了」，但每次改这里都要说清楚是哪一种。
