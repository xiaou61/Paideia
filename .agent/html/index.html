架构导读

它是一个学编程的网站：看课程、做题、复习、问 AI、写笔记、改简历。这份导读不讲代码怎么写，只讲你点下去之后，系统里发生了什么。

十个专题讲「系统怎么跑」，另外四个讲「代码怎么写」。每页最前面是一张「你做了什么 → 系统做了什么 → 你看到什么」的图，不需要任何背景知识；往下是「它内部是怎么做到的」和「设计取舍」——后者才是这套系统为什么长成这样。

怎么读

如果只有十分钟，按 01 → 03 → 05 → 10 读：系统由什么组成、AI 这条主干怎么跑、内容怎么变成学习行为、谁能碰什么。其余六页是按需查的细节。

如果你要动手改代码，11 → 12 → 13 请先读一遍：它们讲的是这个仓库里「什么算做完了」，以及为什么很多规矩看起来别扭。

每页固定四段，从上到下越来越硬：

  • 先看一个具体场景——只有「你」「系统」「你看到的」，不出现代码名词。
  • 它内部是怎么做到的——同一件事换到代码视角，开始出现类名、表名、端点。
  • 设计取舍——为什么这么做、代价是什么、什么时候该改。这一节能看出架构判断，而不只是结构。
  • 读图要点 / 代码在哪——容易踩的点和入口文件。
图全部是手写的 HTML + CSS，没有用任何图表库。打开即渲染、不联网、没有几 MB 的脚本要下载，也不会有「等图慢慢画出来」的卡顿。

这份导读不画什么

写清楚是为了免得有人以为它完整：

  • 不画组件级 C4。在这个规模下，组件图会变成三十个框挤在一起，信息量低于直接读包结构。
  • 不画接口字段。请求与响应的具体结构在代码和契约测试里；要自动生成得引 springdoc，那是另一个决定。
  • 不画前端路由表。路由改得不频繁，一页一图的价值低于维护成本。
  • 不硬造状态机。会话与任务的状态都是枚举字段，没有真正的状态流转时画出来是假的。
  • 不含任何地址、端口映射到主机、凭据。这是公开仓库，图里一律只写服务名。

怎么改

页面是手写 HTML，图是 style.css 里的一组图元拼出来的：.flow（竖排流程）、.steps（谁对谁做了什么）、.layer（分层）、.rules（判定顺序）。没有 JS 负责画图，所以改一个框就是改一行 HTML。

改完跑 node .agent/html/render-check.mjs：它用 chromium 真打开每个页面，检查控制台没有报错、没有任何图横向溢出、侧栏 11 条导航齐全。--shots 可以把每页截图存到系统临时目录。

页面里的数字（模块数、包数、表数、端点数）来自 scripts/gen-arch-diagram.mjs 对 pom.xml / package.json / 迁移文件 / 控制器的抽取，权威副本在 docs/architecture/。数字变了先跑生成脚本，再回来改页面。
