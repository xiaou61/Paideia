一条增量怎么变成屏幕上的字

这张图回答：十六个前端包是怎么分工的？服务端推来的一段文本，经过什么变成带代码块、带可点按钮的回答？

先看一个具体场景

你点了发送，屏幕上开始一个字一个字往外蹦。你已经读过的段落不会闪、代码块在你还没读完的时候不会来回变色，里面那些可点的按钮也是等那一段写完之后才出现的。

这三件事就是「流式渲染」的全部难点：每来一个字都重新画一遍，但不能让你看见重画。

它内部是怎么做到的

结构是「两层叶子 + 一堆领域包 + 两个可运行端」。core 与 ui 不依赖任何其它包——谁都能依赖它们，它们不依赖业务。这不是洁癖：它保证了改一个业务包不会牵连另一个。

渲染流水线

三种块，三种处理

块的状态怎么渲染为什么
已经写完的正常渲染，之后不再重新解析重解析会重新挂交互、重跑高亮，肉眼可见地闪
正在写的尾块切在最后一个完整 token 上，剩下当纯文本半截的 ```、半截的表格、半截的链接都会让解析器吐出畸形结构
围栏交互块JSON 校验通过才渲染组件，否则降级成代码块模型输出的 JSON 不可信；坏数据不应该让整页崩掉

设计取舍：为什么用现成的渲染器

  • 流式 markdown 不是「把文本喂给解析器」这么简单。它要处理每一个前缀的合法性，一旦自己写，就要维护一套语料与逐前缀等价的测试。自研那版最后被换掉，原因就在这里。
  • 选它是因为「未来要平台特有元素」。公式、mermaid 代码块（产品版渲染器支持的）、可点的按钮块，现成方案都是一等公民。
  • 代价是体积与耦合。渲染器 + 高亮 + 插件是主包里最大的一块，升级要跟着它的节奏。所以它是可选包，不是主包硬依赖。
  • 面板宽度写进根变量 --assistant-panel-w。主内容靠这个变量让位，而不是到处写 margin；窄屏退化成抽屉，Ctrl+J 开关。

读图要点

  • 主题令牌只有一份，在 @paideia/ui。管理端与学习者端共用——这也是为什么改一次共享的 Table 能让整个管理端一起换代。
  • Tailwind 的 @source 指错目录会「静默缺样式」：页面能开、类名没生效，构建不报错。真踩过。改多包结构后第一件事是确认它指向了全部包。
  • 每一条用户可见路由都必须在导航栏或账号菜单里有入口。首页快捷卡不算——那排卡片要往下滚才看得见。曾经有三个页面能直达 URL、内容齐全，但导航里一个都没有，用户以为内容少了一大半。
  • 新增一种交互块只需要两件事：写一个组件、在注册表里登记语言名。不要改主渲染器的 if/else。
  • 会话恢复有一个竞态要小心：切换会话时必须 abort 掉在飞的请求，否则旧回答会写进新会话。

代码在哪

  • frontend/packages/assistant/src/sse.ts — 五种事件的客户端解析
  • frontend/packages/assistant/src/session-store.ts、conversation-panel.tsx
  • frontend/packages/ui/src/markdown/markdown.tsx — MarkdownBody
  • frontend/packages/ui/src/markdown/renderers/ — 围栏组件与 schema.ts
  • frontend/apps/app/src/router.tsx — 路由；LearnerHeader 的 NAV 是导航入口清单
  • frontend/packages/identity — preferredNav 的联合字面量类型
改了共享包就要跑三端 e2e。@paideia/ui / core / auth / knowledge 任何一处改动都可能同时影响学习者端、管理端与桌面壳。只改某一个应用时，按页面选一个 e2e 文件就够（十几秒到一分钟），别为了安心跑全量。
