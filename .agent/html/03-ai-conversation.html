03 / AI 主干

一次 AI 对话，与它的账

这张图回答：我敲一句话点发送，到屏幕上出现第一个字，中间发生了什么？积分在哪一步动？为什么一次回答可能花掉好几轮的钱？

先看一个具体场景

你打一句「讲讲 MySQL 索引」，按发送。系统做的第一件事不是去问 AI，而是先从你的余额里冻结一笔钱；冻结不成功，一个请求都不会发出去。然后上游开始一个字一个字吐，你屏幕上就一个字一个字出现。写完后按实际用量结算，冻结的退回，只扣真正花掉的那一点。

线上真实跑过一次：冻结 1000 分，最后实扣 2 分。所以「先冻结」不是多收你钱，是防止有人把额度用超。

它内部是怎么做到的

一次对话 = 公共行为 × 私有数据。公共行为是一份场景提示词加一组场景工具（助手、面试官、导师、点评）；私有数据是这个用户的历史窗口、记忆片段、页面上下文、额度。个性化只发生在两者交叉的地方——「同一个面试官行为 + 你的记忆 → 专门追问你上次答砸的那个知识点」。

第一步：同步阶段只做三件事

控制器在校验、组上下文、预留之后立刻把 SSE 连接交出去，真正的生成在另一个线程里跑。这个分界很重要：只有同步阶段的错误能得到正常的 HTTP 状态码（400 / 402 / 404），连接一旦建立，后面所有的失败都只能以 error 事件推回来。

这里有一个已经修掉的真缺陷：prepare 原本带着 @Transactional，结果被 402 拦下的那一轮，连用户刚发的消息一起回滚丢了。界面因为只有乐观本地状态而看不出来，刷新就消失。现在 prepare 不加事务，reserve 挪到最后。

第二步：异步阶段是一个循环

「工具循环」不是花哨的说法，它是字面意义的 while：模型每轮要么给出最终文本，要么要求调用一个工具；要求调工具时，把结果回填进对话再问一次。每一轮都是一次真实的上游请求，也都计一次费。

第三步：结账

流式回答只有五种事件

事件携带什么界面拿它做什么
thinking推理片段显示成默认折叠的「思考中」
content正文增量追加到气泡，触发重渲染（见 08）
draft笔记草稿弹「要不要存成笔记」
donemessageId + traceId结束态；点赞/点踩靠 traceId 对到那条 run
error一句人话在气泡里显示失败，并提示已退款

设计取舍：三条不能改的理由

  • 为什么必须「先预留后结算」。事后计费意味着你已经把上游的钱花出去了才去问用户有没有钱。并发场景下这是必然透支。预留是唯一能在「发第一个字节之前」拒绝的形状。
  • 为什么平台出钱，而不是让每个用户填自己的 Key。BYOK 会把「注册 → 配 Key → 能用」变成四步，而且 Key 落库就是一个新的密钥管理问题。改成平台凭据 + 积分后，注册即可用；代价是要自己做配额、计价与欠费防护，这三件事现在都在 CreditService 里。
  • 为什么 harness 是自己写的，没有直接用 Agent 框架。框架提供的循环只有几十行，但它会把「第几轮、花了多少 token、哪个工具失败」埋在内部。这套账与观测必须精确到轮，所以循环自己写，只借用框架的模型客户端与流式解析。

读图要点

  • 工具循环的每一轮都是真调用、真花钱。历史缺陷是「每轮都调上游，但只上报最后一轮的 token」，桩掉上游端口的测试永远看不见它。现在每轮落一条 span，账才对得上。
  • 上游有三个硬限制（DeepSeek 系列）：工具名只接受下划线；工具结果必须逐条发回；思考内容不能塞进历史。三条都是踩过之后写进代码的。
  • 线程池是有界的。队列满时任务根本没跑起来，预留到不了结算也没有别的补偿出口——所以那里显式退款并返回 429，而不是让异常被兜成 500（否则用户看着「内部错误」，实际是被白扣了一次分）。
  • 流水分用途记，不是一个总类。用户要能回答「最近改简历花了多少」「自动整理记忆花了多少」——合成一类就永远算不清。
  • 对话的上下文是有预算的。历史窗口会截断、记忆最多进 8 条、页面上下文按当前页给。回答质量下降时，第一件事是看这几段各自给了多少，而不是先怀疑模型。

代码在哪

  • backend/paideia-ai/…/web/AssistantConversationController.java — SSE 端点、五种事件、线程池拒绝时的退款
  • backend/paideia-ai/…/conversation/ConversationService.java — prepare 与 complete
  • backend/paideia-ai/…/conversation/AgentScopeAssistantAnswerer.java — 自写 harness 的循环
  • backend/paideia-ai/…/billing/CreditService.java — reserve / settle / refund 与每种用途的结算
  • backend/paideia-ai/…/billing/CreditLedger.java — 流水种类的定义
  • backend/paideia-ai/…/telemetry/ — ai_runs / ai_run_spans 的写入队列
  • frontend/packages/assistant/src/sse.ts — 客户端解析五种事件
这条链路上所有「只有真跑才看得见」的缺陷都在这一层。桩掉上游的单元测试能证明分支走对了，证明不了「账记全了」「HTTP 状态对了」「用户消息还在」——这三个都是实际跑过一次上游、一次 402 才暴露的。改这里务必真连一次上游。
