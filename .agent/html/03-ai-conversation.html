03 / AI 主干

一次 AI 对话，与它的账

这张图回答：我敲一句话点发送，到屏幕上出现第一个字，中间发生了什么？积分在哪一步动？为什么一次回答可能花掉好几轮的钱？

先给结论

一次对话 = 公共行为 × 私有数据。公共行为是一份场景提示词加一组场景工具（助手、面试官、导师、点评）；私有数据是这个用户的历史窗口、记忆片段、页面上下文、额度。个性化只发生在两者的交叉点上——「同一个面试官行为 + 你的记忆 → 专门追问你上次答砸的那个知识点」。

钱的部分只有一条铁律：先预留，后调用。预留成功才允许向上游发第一个请求；余额不足时直接 402，一个字节都不发给上游。这不是为了记账好看，而是唯一能真正防欠费的形状——事后结算意味着你已经把对方要花的钱花出去了。

同步阶段只做三件事，然后就返回

控制器在校验、组上下文、预留之后立刻把 SSE 连接交出去，真正的生成在另一个线程里跑。这个分界很重要：只有同步阶段的错误能得到正常的 HTTP 状态码（400/402/404），一旦连接建立，后面所有的失败都只能以 error 事件的形式推回来。

异步阶段：工具循环与结算

账本只有四种主要动作

读图要点

  • prepare 不加事务，reserve 是最后一个可能抛异常的动作。早年它带着事务，结果被 402 拦下的那一轮连用户刚发的消息一起回滚丢了——界面因为只有乐观本地状态而看不出来，刷新就消失。
  • 工具循环的每一轮都是真调用、真花钱。历史缺陷是「每轮都调上游，但只上报最后一轮的 token」，桩掉上游端口的测试永远看不见它。现在每轮落一条 span，账才能对上。
  • 上游有三个硬限制（DeepSeek 系列）：工具名只接受下划线；工具结果必须逐条发回；思考内容不能塞进历史。三条都是踩过之后写进代码的。
  • SSE 只有五个事件：thinking、content、draft、done、error。done 带 traceId，用户点赞/点踩时用它把反馈挂到那条 run 上。
  • 线程池是有界的。队列满时任务根本没跑起来，预留到不了结算也没有别的补偿出口——所以那里显式退款并返回 429，而不是让异常被兜成 500（否则用户看着「内部错误」，实际是被白扣了一次分）。
  • 流水按用途分类（对话 / 自动整理记忆 / 面试点评 / 简历 / 训练营 / 复习 / 运维诊断）。分开记是需求：用户要能回答「最近改简历花了多少」，合成一类就永远算不清。
  • 积分面板与扣费是两个入口，同一个余额。余额是账户表的一列，流水是明细；对不上账时先看是不是有一次 RESERVE 没有对应的 SETTLE 或 REFUND。

代码在哪

  • backend/paideia-ai/…/web/AssistantConversationController.java — SSE 端点、五个事件、线程池拒绝时的退款
  • backend/paideia-ai/…/conversation/ConversationService.java — prepare（历史/记忆/提示词）与 complete
  • backend/paideia-ai/…/conversation/AgentScopeAssistantAnswerer.java — 自写 harness 的循环本身，AgentScope 只提供了模型客户端与流式累加器
  • backend/paideia-ai/…/billing/CreditService.java — reserve / settle / refund，以及每种用途的 settle 方法
  • backend/paideia-ai/…/telemetry/ — ai_runs / ai_run_spans 的写入队列与清洗
  • frontend/packages/assistant/src/sse.ts — 客户端解析五种事件
这条链路上所有「只有真跑才看得见」的缺陷都在这一层。桩掉上游的单元测试能证明分支走对了，证明不了「账记全了」「HTTP 状态对了」「用户消息还在」——这三个都是实际跑过一次上游/一次 402 才暴露的。改这里务必真连一次上游，或者至少真跑一次完整的 e2e。
