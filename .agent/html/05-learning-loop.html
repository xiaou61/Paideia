05 / 学习闭环

内容怎么变成一次学习行为

这张图回答：一篇 markdown 文稿是怎么变成「关卡」「练习」「复习」的？「你哪块弱」这个判断是怎么算出来的，它准不准？

先看一个具体场景

你读完一课，点「练一练」做了三道题，错了两道——都跟「索引」有关。系统记下这两次错误，把「索引」这个概念的掌握度往下调了一档。

过两天你打开首页和复习页，发现推给你的题变多了，而且总和「索引」有关。等你连着答对几道，它又慢慢往上调回去。

它内部是怎么做到的

这条链上有三个反直觉的设计：内容是代码、学习线不是表、题目也不是表。三个都是为了「同一份事实只存在一个地方」。

一、内容在仓库里，不在后台里

二、题目没有表：题干就是权威

题目存在条目正文的围栏块里（quiz / sql-challenge 这类），数据库只存「这道题被做过」的证据与状态。这样正文改了，旧统计不会套到新题上——靠的是下面这个四元组：

entry_id哪一篇
block_key正文里第几个围栏块
question_key块内第几题（blockKey#index）
fingerprint题干 + 选项 + 答案的 SHA-256

前三个回答「是哪一道题」，第四个回答「还是不是同一道题」。内容一改，fingerprint 变，历史统计自动失效，不会被错误复用。

判分有两种来源，记录在 judged_by：server 表示服务端按正文里的标准答案判；client 表示代码挑战在客户端跑完上报。后者是信任边界上的一个让步，只用在沙箱题型。

三、掌握度：一个会自我强化的回路

这里有实测过的真缺陷，别当成理论。用生产模型跑离线模拟：信息增益 0.6303，随机选题是 0.7619——比随机低 17.3%。根因是上面的回路：掌握度低 → 能力值低 → 挑简单题 → 答对 → 掌握度只微涨，于是系统长期在 50% 正确率附近震荡，爬不上去。这是一条写成断言「当前是错的」的绿色测试，不是漏测。

训练营：把「学习计划」也做成一组成表的数据

训练营不是课程的同义词，它是一份带日期的计划：若干任务、每个任务下若干题、你的每次尝试都留痕。所以它有自己的一套表（camp_programs / camp_tasks / camp_items / camp_plans / camp_attempts）和一套端点，而不是硬塞进课程结构里。

你→目标选一个方向与周期计划由 AI 生成，一次调用、计 CAMP 流水 计划→任务任务下挂题（来自题库，不另造题） 你→尝试每次作答落 camp_attempts与题库的 question_attempts 是两条记录：一个记「学习行为」，一个记「题目统计」

为什么分成两条答题记录：训练营关心「你今天做完了没」，题库关心「这道题的全站正确率」。合表会让两个统计互相污染——训练营重复做同一道题不该把题目的难度统计带偏。

设计取舍：为什么这么别扭

  • 内容放仓库，是为了能 review。一门课五十多篇，改动要能 diff、能回滚、能跟着代码一起发版。放后台纯手录，改一个字都没有审计。
  • 代价是改内容要跑脚本。所以脚本必须幂等、必须 --dry-run、必须只碰自己负责的分类——删内容时宁可留一条旧课，也不静默删线上数据。
  • 不建题目表，是为了避免两份真相。题库表一旦存在，正文和表就会有一天不一致，而没人知道该信哪个。代价是统计要自己算 fingerprint。
  • BKT 管「会不会」，Elo 管「有多难」。两套模型分工明确，互不替代：一个更新学生状态，一个更新题目属性。
  • 全站默认解锁。不要因为「要有学习路径」而重新引入前置门槛——那是被明确撤销过的方向。

读图要点

  • 复习会话的答案绝不下发。review_sessions.items_json 里带着答案与解析，响应由服务端裁剪成 itemId / 题干 / 选项。把整行 JSON 直接返回是最容易犯的错。
  • 复习出题要花钱。它走 AI 出题 + 积分预留结算，和对话同一条账务管线。
  • 这些表没有外键。删用户时靠 KnowledgeUserDeletionListener 的表清单级联，漏一张就是隐私事故（见 10 的「注销」一节）。
  • 统计以「最后一次写入」为准。并发作答时不做合并，这是简化，写在设计文档里。

  • backend/paideia-knowledge/…/question/PracticeSelector.java — 选题
  • backend/paideia-knowledge/…/question/PrerequisiteDiagnosis.java、QuestionConceptSuggester.java

改内容前先跑 --dry-run。题目在正文里，围栏格式错了不会报错，只会表现为「这道题永远不会被统计」——因为解析不到 question_key。scripts/verify_course.py 与 check_seed_fences.py 就是为这件事存在的。
