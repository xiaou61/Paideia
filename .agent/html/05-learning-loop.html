05 / 学习闭环

内容怎么变成一次学习行为

这张图回答：一篇 markdown 文稿是怎么变成「关卡」「练习」「复习」的？「你哪块弱」这个判断是怎么算出来的，它准不准？

先给结论

内容全部来自仓库里的 markdown（content/courses/、content/reading/），由 scripts/import-course.mjs 走管理端已有的写接口幂等导入——不新增导入接口，也不在启动时读文件。第二次运行应当 created 0 / updated 0。

「学习线」不是一张表，而是分类上的一个标记：knowledge_categories.line_kind 非空即是一条线，线名、slug、顺序都来自分类自己，站就是它下面的已发布条目。所以新增一条线只需要建分类 + 写内容，不改代码、不加迁移。

题目也没有表：题干、选项、答案只存在于条目正文的围栏块里，那是唯一权威。数据库只存「身份 + 证据 + 状态」。

掌握度与选题：一个已知有缺陷的算法

读图要点

  • 题目的身份是四元组：entry_id + block_key + question_key + fingerprint。fingerprint 是「题干 + 选项 + 答案」的 SHA-256——内容一改，旧统计就不会套到新题上。这是这套设计里最关键的防污染机制。
  • 判分有两种来源：judged_by = server（服务端按正文判定）和 client（代码挑战由客户端跑完上报）。后者是信任边界上的一个让步，只在沙箱题型上用。
  • 全站默认解锁。不要因为「要有学习路径」而重新引入前置门槛——那是被明确撤销过的方向，再加回来会挡掉一半用户。
  • 复习会话的答案绝不下发。review_sessions.items_json 里带着答案与解析，响应由服务端裁剪成 itemId / 题干 / 选项。把整行 JSON 直接返回给前端是最容易犯的错。
  • 实际效果有实测数据，而且不好看：信息增益 0.6303，随机选题是 0.7619——比随机低 17.3%。根因是 ability(mastery) 的映射与「专挑难度≈能力」的规则合起来把难度锁死了，BKT 在 50% 正确率附近永远震荡、爬不上去。这是一条写得像断言「当前是错的」的绿色测试，不是漏测。
  • 这些表没有外键。删用户时靠 KnowledgeUserDeletionListener 里那张表清单级联，漏一张就是隐私事故（见 07）。

代码在哪

  • scripts/import-course.mjs — 内容导入；线的声明全部来自课程文件的 frontmatter，脚本里没有写死课名
  • backend/paideia-knowledge/…/learning/LearningLineService.java — 线的投影与站序（服务端唯一真相）
  • backend/paideia-knowledge/…/learning/LearningProgressService.java — 读完一站
  • backend/paideia-knowledge/…/question/MasteryModel.java — BKT
  • backend/paideia-knowledge/…/question/PracticeSelector.java — 选题
  • backend/paideia-knowledge/…/question/PrerequisiteDiagnosis.java、QuestionConceptSuggester.java
  • backend/paideia-ai/…/review/ReviewQuestionGenerator.java — 复习出题（走积分）
改内容前先看 scripts/verify_course.py 与 check_seed_fences.py。题目在正文里，围栏格式错了不会报错，只会表现为「这道题永远不会被统计」——因为解析不到 question_key。改完务必跑一次导入脚本的 --dry-run。
