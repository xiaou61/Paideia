## `Parameter 'userId' not found`

我在练手库里把接口写成这样。`@Param` 的值是故意写成 `arg0` 的，只为复现没有 `-parameters` 时最常见的名字；这不是推荐写法：

```java
List<User> find(@Param("arg0") Long userId);
```

注意：这个 `arg0` 是我写在注解里的，不是 MyBatis 从参数下标算出来的；没有 `-parameters` 时反射也会给 `arg0`，但走的是另一条分支。

SQL 是 `where id = #{userId}`。调用后抛出的原文：

```text
org.apache.ibatis.binding.BindingException: Parameter 'userId' not found. Available parameters are [arg0, param1]
```

我原来以为名字对不上最多取到 `null`。实际 `ParamMap.get` 先 `containsKey`，没有就抛，并把 `keySet()` 原样打出来（`MapperMethod.java:207-212`）。`#{userId}` 里的 `userId` 只是一个 key；真正有哪些 key，取决于方法参数怎么命名、怎么包装。

这条报错里只有一个 `arg0`，却还有一个 `param1`，因为 `hasParamAnnotation` 一旦为 true，单参数也会走 `ParamMap` 分支（`ParamNameResolver.java:130-146`）。下面先把这条链拆开。

## 名字是在第一次调用时定的

`MappedStatement` 和 SQL 文本在启动时解析，但 `ParamNameResolver` 不是。`MapperProxy.cachedInvoker` 用 `methodCache` 做 `computeIfAbsent`，第一次调用某个接口方法时才 `new MapperMethod`（`MapperProxy.java:92-97`）；`MapperMethod.MethodSignature` 的构造里才 `new ParamNameResolver`（`MapperMethod.java:301`）。`methodCache` 在 `MapperProxyFactory` 里（`MapperProxyFactory.java:32`），所以同一个方法的名字只收集一次，后面复用。

这也是为什么报错里的名字看起来像 Java 反射名：它本来就是从 `Method` 上读的（`ParamNameResolver.java:63-67`）。XML 解析阶段不会替你决定 `userId` 还是 `arg0`。

下面这个源码走读按调用顺序排了 7 步。第一步先看 `MapperMethod` 是什么时候创建的，最后两步才到 `PreparedStatement`。

## 名字从哪来：@Param、-parameters、数字

`ParamNameResolver` 的构造函数遍历方法参数，给每个非特殊参数定一个字符串（`ParamNameResolver.java:63-97`）。

1. `@Param` 优先。找到注解就把 `value()` 放进 `names`（`ParamNameResolver.java:76-81`）。
2. 没有 `@Param` 且 `useActualParamName=true`（默认值在 `Configuration.java:115`），取反射里的实际参数名（`ParamNameResolver.java:83-86`）。编译时带 `-parameters`，得到源码里的 `userId`；没带时，JDK 返回 `arg0`、`arg1`。
3. 只有第 2 步拿不到（`name == null`），或者 `useActualParamName=false`，才用数字：`name = String.valueOf(map.size())`（`ParamNameResolver.java:88-92`）。

所以「下标字符串 0」不是常规的第三来源。默认配置下，没带 `-parameters` 得到的是 `arg0`/`arg1`，不是 `0`/`1`。`useActualParamName` 可以在 `Configuration` 上调（`Configuration.java:291-292`）。

数字名也不是参数序号。`map` 只给非特殊参数放名字，`RowBounds`、`ResultHandler` 在 `ParamNameResolver.java:71-74` 被 `continue` 掉；数字取的是 `map.size()`（`ParamNameResolver.java:91`），也就是「已经收了多少个非特殊参数」。类注释里给了一个数字回退的例子：`aMethod(int a, RowBounds rb, int b)` 得到 `{{0, "0"}, {2, "1"}}`（`ParamNameResolver.java:54-57`）——键还是原始下标 0 和 2，名字却是 0 和 1。

两个容易记反的点：

- `useActualParamName=false` 时，`RowBounds` 后面的数字名会前移：签名下标是 2，名字是 `1`。
- 没带 `-parameters`、`useActualParamName=true` 时，实际名仍按原始下标走：同一条签名得到 `arg0`/`arg2`，不会变成 `arg0`/`arg1`。

`param1`/`param2` 也一样：它们按 `names` 的遍历顺序递增（`ParamNameResolver.java:136-144`），不是按原始参数下标。带 `RowBounds` 时，第二个普通参数叫 `param2`，不是 `param3`。通用名只在 `names` 里没有同名 `@Param` 时补（`ParamNameResolver.java:140-143`）。

## 单参数不是「名字随便写」

`getNamedParams` 只有一条快速路径：

```java
if (!hasParamAnnotation && paramCount == 1) {
  Object value = args[names.firstKey()];
  return wrapToMapIfCollection(value, useActualParamName ? names.get(names.firstKey()) : null);
}
```

（`ParamNameResolver.java:130-132`）

条件是两件事同时成立：**没有 `@Param`**，且**只有一个普通参数**。`paramCount` 是 `names.size()`（`ParamNameResolver.java:126`），不是方法签名里的参数个数。所以：

- `find(Long id)`：返回传入的 `Long` 本身，不建 `ParamMap`。
- `find(@Param("arg0") Long userId)`：`hasParamAnnotation=true`，条件不成立，走 else，建 `ParamMap`，里面是 `arg0` 和通用名 `param1`（`ParamNameResolver.java:133-146`）。这就是开头那条报错的来源。
- `find(Long id, String name)`：两个普通参数，走 else。

`hasParamAnnotation` 只要遇到一个 `@Param` 就置 true（`ParamNameResolver.java:77-79`），所以判断条件不是「参数个数 >= 2」。「两个及以上参数才建 ParamMap」是错的；单参数 + `@Param` 也建。`args == null` 或没有普通参数时，`getNamedParams` 直接返回 null（`ParamNameResolver.java:127-129`）。

单参数 + `@Param` 还有一个容易被忽略的后果：它走 else，不调用 `wrapToMapIfCollection`。所以 `find(@Param("ids") List<Long> ids)` 的 map 里只有 `ids` 和 `param1`，没有 `collection`/`list`。我用 3.5.19 的 `ParamNameResolver` 直接跑过，键就是这两个。

## 单参数写 `#{whatever}`，什么时候真能过

单参数没有 `@Param` 时，`getNamedParams` 把原对象直接交出去（`ParamNameResolver.java:130-132`）。执行期 `DefaultParameterHandler` 按这个顺序取值（`DefaultParameterHandler.java:67-83`）：

1. `additionalParameters` 里有同名 key，先取它（`DefaultParameterHandler.java:72-73`，`<foreach>` 的 `__frch_*` 走这里）。
2. 参数对象是 null，值为 null（`DefaultParameterHandler.java:74-75`）。
3. 参数对象本身的类有 TypeHandler，直接把整个对象当值（`DefaultParameterHandler.java:76-77`）。这一步根本不看 `propertyName`。
4. 否则用 `MetaObject.getValue(propertyName)` 按属性名取（`DefaultParameterHandler.java:78-82`）。

所以：

- `find(Long id)` 里写 `#{whatever}` 能取到 `id`，不是因为名字被忽略，而是因为 `Long` 本身有 TypeHandler，第 3 步把整个 `Long` 交了。换成没有 TypeHandler 的 POJO，就会走到第 4 步。
- `find(User user)` 里写 `#{whatever}`，`MetaObject.getValue` 找不到 getter，抛 `ReflectionException`（`MetaObject.java:113-115`、`Reflector.java:382-386`）。我把这条路径单独跑了一遍（JDK 25 + MyBatis 3.5.19），消息的前半段是：

```text
org.apache.ibatis.reflection.ReflectionException: There is no getter for property named 'whatever'
```

- 如果单参数加了 `@Param`，就不会走原对象路径；名字不对时是 `BindingException`，不是 `ReflectionException`（`MapperMethod.java:207-212`）。

`#{user.name}` 也走同一个 `MetaObject.getValue`，`PropertyTokenizer` 按点拆开（`MetaObject.java:113-115`）。所以「单参数 `#{whatever}` 都能取」只在「参数对象本身能被 TypeHandler 处理」时成立；POJO 的名字必须对得上属性。

## 集合和数组会被改名

`wrapToMapIfCollection` 只做三件事（`ParamNameResolver.java:162-177`）：

- `Collection` → `collection`
- 如果还是 `List` → 再加 `list`
- 数组 → `array`
- `actualParamName` 非空时，再补一个实际名（`ParamNameResolver.java:169`、`ParamNameResolver.java:175`）

这条包装只在「单参数 + 没有 `@Param`」的快速路径里调用（`ParamNameResolver.java:132`）。所以：

- `find(List<Long> ids)`，编译带 `-parameters`：map 里是 `ids`、`collection`、`list`。
- 同一个方法没带 `-parameters`：实际名是 `arg0`，map 里是 `arg0`、`collection`、`list`。
- `useActualParamName=false` 时，`actualParamName` 传 null，连 `arg0` 也没有，只剩 `collection`/`list`。
- `find(@Param("ids") List<Long> ids)`：走 else，不调用 `wrapToMapIfCollection`，map 里只有 `ids` 和 `param1`，**没有** `collection`/`list`。我用 3.5.19 的 `ParamNameResolver` 直接跑过，输出是 `{ids=[1], param1=[1]}`。

直连 `SqlSession` 又是另一条路：`DefaultSqlSession.selectList` / `update` 会先 `wrapCollection(parameter)`（`DefaultSqlSession.java:154`、`DefaultSqlSession.java:197`），而 `wrapCollection` 传给 `wrapToMapIfCollection` 的 `actualParamName` 是 `null`（`DefaultSqlSession.java:319-321`）。所以集合/数组参数走那条路径时，只有 `collection`/`list`/`array`，没有 `ids` 这个键。

## 名字进 ParamMap 之后，`#{...}` 怎么消费

SQL 里的每个 `#{...}` 在 `SqlSourceBuilder` 里被换成一个 `?`，同时生成一条 `ParameterMapping`，把括号里的 `property` 记下来（`SqlSourceBuilder.java:88-92`、`SqlSourceBuilder.java:94-114`）。这一步只记录名字、类型和 jdbcType 等配置，不取参数值。

执行到 `DefaultParameterHandler.setParameters` 才按 `ParameterMapping` 逐条取值（`DefaultParameterHandler.java:67-83`），然后：

```java
typeHandler.setParameter(ps, i + 1, value, jdbcType);
```

JDBC 的 `PreparedStatement` 下标从 1 开始，所以源码里是 `i + 1`（`DefaultParameterHandler.java:90`）。`value == null` 且 `ParameterMapping` 没带 `jdbcType` 时，用全局 `jdbcTypeForNull`（`DefaultParameterHandler.java:86-88`，默认 `OTHER` 在 `Configuration.java:126`）。

如果参数被包装成 `ParamMap`，名字对不对在 `get` 那一步就已经决定：没命中就抛 `BindingException`，不会悄悄变成 null（`MapperMethod.java:207-212`）。`ParamMap` 继承 `HashMap`（`MapperMethod.java:203`），所以报错里的 `keySet()` 顺序不是契约；能依赖的是它列出了全部可用 key。

## 还差的

- `RowBounds` / `ResultHandler` 只讲了它们会被跳过（`ParamNameResolver.java:71-74`），没讲 `MapperMethod` 怎么把 `RowBounds` 从 args 里取出来（`MapperMethod.java:312-322`）；分页插件改写 SQL 后 `ParameterMapping` 会不会变，这一篇没碰。
- `${}` 没展开。`SqlSourceBuilder` 只把 `#{` 当 token（`SqlSourceBuilder.java:47`），本文没有验证 `${}` 的替换路径与注入面。
