## 这一关要读什么

上一关讨论的是「查不到就 404」。但服务端凭什么知道请求是谁发的？这一关跟一条带着 `Authorization: Bearer <token>` 的请求，看它从进入安全链到 controller 拿到账号 id 的全过程——以及为什么同一个身份，读路径取不到可以当匿名，写路径取不到必须直接拒绝。

先看装配。这个项目**没有自己写 JWT 过滤器**：`SecurityConfiguration` 里的 `.oauth2ResourceServer(...)` 让 Spring Security 在安全链上装一个 `BearerTokenAuthenticationFilter`。它从 `Authorization` 头取出 `Bearer` 后面的令牌，交给 `JwtDecoder` 验签、校验过期时间与签发者，再交给转换器变成认证对象，最后放进 `SecurityContextHolder`。过滤器本身是框架代码，仓库里能读的是它用的两样东西——解码器与权限转换器。

还有一个容易看漏的顺序问题：`/api/v1/auth/**` 在安全配置里是 `permitAll()`（第 134 行）。登录、刷新这类端点本身不需要令牌，过滤器照常会跑，但没拿到 Bearer 就什么也不设置，请求继续往下走。真正被「拦住」的是登录之后的业务请求——除了少数显式放行的公开读端点，其余都落在 `anyRequest().authenticated()` 上，没有有效令牌直接 401，根本到不了 controller。

把两段放在一起看，`require` 与 `orNull` 不是「一处严谨、一处偷懒」，而是两条不同的失败策略：**读路径允许降级，写路径必须失败关闭**。判断该用哪个，只看一件事——这个身份是不是这次操作的必要条件。
