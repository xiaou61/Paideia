## 先把结论摆出来

AI 的回答是一个字一个字出现的。你已经读过的段落不该闪、代码块不该来回变色、里面的按钮要等那一段写完之后才出现。

这三件事就是流式渲染的全部难点：**每来一小段就重画一遍，但不能让你看见重画**。

```mermaid
flowchart LR
  S["后端：一小段一小段推过来"] --> R["前端：接在一段文字后面"]
  R --> D["只重画这一小段<br/>已写完的段落原封不动"]
  D --> T["半截的东西先按纯文本显示"]
  T --> C["写全之后才变成代码块或交互块"]
```

## 一、为什么要「半截先按纯文本」

markdown 的语法是成对出现的：三个反引号开一个代码块，再三个关掉。

如果只写了一个开头，解析器会吐出一个畸形结构——整篇排版都跟着乱。所以做法是：**切在最后一个完整的位置，剩下的当纯文本**；等闭合符号到了，再把它变成真正的代码块。

这听起来是权宜之计，其实是这个领域唯一靠谱的做法。别人（包括开源同类项目）也是这么处理的，没有更优雅的解。

## 二、已经写完的段落为什么不能重画

重画本身不贵，贵的是它的副作用：重新挂交互、重新跑高亮、重新算布局。表现出来就是**闪**。

所以渲染按块记忆化：内容没变的块直接跳过。这也解释了一个看起来奇怪的要求——传给渲染器的配置对象**必须是稳定引用**。如果每次渲染都新建一个对象，记忆化会全部失效，于是每来一个字都重解析整篇。这不是优化技巧，是正确性。

## 三、为什么用现成的渲染器，而不是自己写

流式 markdown 不是「把文本喂给解析器」这么简单。它要处理**每一个前缀**都合法：任意时刻的渲染结果，必须等于「对当前完整前缀的渲染」。

自己写就要维护一整套语料和逐前缀测试。这里的取舍是：用现成的解析器 + 一个负责「愈合尾巴」的小组件，把精力放在真正属于这个产品的东西上——**可交互的块**。

## 四、可交互的块是数据驱动的

文章里可以出现「可点的代码走读」「当场判分的小测」「动手练习」这类块。它们不是特例，而是一条协议：

1. 作者在 markdown 里写一个带语言名的围栏块；
2. 渲染器按语言名查注册表；
3. 块里的 JSON 过一遍校验，有必填字段、有上限；
4. **校验失败就降级成「提示 + 原始文本」，绝不抛进渲染树**——一段坏内容不该让整篇文章白屏。

新增一种块只需要两件事：写一个组件、在注册表里登记语言名。改主渲染器的判断逻辑，是把协议退化成特例。

## 五、几个看起来不解、其实都有原因的约束

- **块有上限**（比如走读最多 20 步）。超过上限通常意味着「这段该拆成两篇」，而不是「渲染器该支持更大的块」。
- **判定必须在服务端**。SQL 与代码题在沙箱里真跑，参考结果来自真实执行；客户端判分等于把答案一起发出去。
- **编辑器懒加载**。真正的代码编辑器有好几百 KB，只在页面上真有练习块时才下载。守卫这件事也有教训：**懒加载的守卫自己被反向验证抓出过缺陷**——把懒加载去掉，守卫必须变红，否则它守的不是你以为的东西。
