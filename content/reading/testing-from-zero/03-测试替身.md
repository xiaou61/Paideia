## 这一关在解决什么

单测要跑得快、结果稳定，就不能真的连数据库、发 HTTP、等时钟。于是我们用"替身"替换这些依赖。

麻烦在于：替身用错，测试会变成"验证实现细节"，一重构就红，还给你虚假的信心。这一关讲三种替身的区别与选择。

## 讲解

### 三种替身

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| Stub（桩） | 返回预设值，让被测代码能继续 | 库存服务返回 10 |
| Mock（模拟） | 记录调用，用来断言"调用发生/参数正确" | 验证发了一封邮件 |
| Fake（假实现） | 可工作的简化实现 | 内存版仓库、内存队列 |

日常说的"mock"经常把三者混在一起。**选择取决于你要验证什么**：

- 只关心返回值 → 用 Stub；
- 关心"有没有把消息发出去、参数对不对" → 用 Mock；
- 依赖的行为较复杂（查询、保存、分页） → 用 Fake。

### 例子：一个下单服务

```java
class OrderService {
    private final Inventory inventory;
    private final Mailer mailer;

    Result place(Order order) {
        if (!inventory.has(order.itemId(), order.quantity())) {
            return Result.rejected("库存不足");
        }
        inventory.reserve(order.itemId(), order.quantity());
        mailer.send(order.userEmail(), "下单成功");
        return Result.ok();
    }
}
```

只关心"库存不足时不发邮件"：

```java
@Test
void 库存不足时不发邮件() {
    var inventory = mock(Inventory.class);
    when(inventory.has("A", 2)).thenReturn(false);
    var mailer = mock(Mailer.class);

    new OrderService(inventory, mailer).place(order("A", 2));

    verify(mailer, never()).send(any(), any());
}
```

这里的 `mailer` 是 Mock（验证没被调用），`inventory` 是 Stub（提供返回值）。

### 不要 mock 被测对象内部的东西

```java
// 差：把被测类的内部协作全部 mock 掉
when(repo.find(1)).thenReturn(user);
when(validator.check(user)).thenReturn(true);
when(mapper.toView(user)).thenReturn(view);
assertEquals(view, service.get(1));
```

这个测试只证明了"你把这三个调用按顺序写了一遍"，没有任何业务规则被验证。改一个内部实现，测试就红；而真正的 bug（比如权限判断漏了）它发现不了。

**规则：mock 的是边界（数据库、HTTP、时钟、消息队列），不是自己的类。**

### 过度断言交互

```java
verify(repo).save(any());
verify(repo).flush();
verify(cache).put(any(), any());
verify(log).info(contains("saved"));
```

这种测试把"实现步骤"变成了契约。以后换一种缓存实现、少打一行日志，测试就红——但它并没有保护任何用户可见行为。

**只在你真的关心协议时验证交互**：比如"必须发一封邮件""必须调用一次支付网关且金额正确"。

### Fake 比 Mock 更适合仓储

```java
class InMemoryUserRepository implements UserRepository {
    private final Map<Long, User> data = new HashMap<>();

    public Optional<User> find(long id) { return Optional.ofNullable(data.get(id)); }
    public void save(User user) { data.put(user.id(), user); }
}
```

用 Fake 测试"保存后能查到""重复保存是更新不是新增"，既快又不需要数据库。它验证的是**接口语义**，不是 SQL。

但 Fake 有风险：它和真实实现的行为可能不一致（排序、唯一约束、事务）。所以关键路径仍要有集成测试。

### 时钟、随机数、UUID 也是依赖

```java
// 难测：直接读系统时间
if (order.createdAt().isBefore(Instant.now().minusDays(7))) { ... }

// 好测：注入 Clock
if (order.createdAt().isBefore(clock.instant().minus(Duration.ofDays(7)))) { ... }
```

测试里给固定时钟，结果就稳定。随机数与 UUID 同理：需要可预测时注入生成器。

### 什么时候不该用替身

- 依赖是**纯函数/值对象**：直接用真的；
- 依赖很快且无副作用（如 `List`、`String`）：直接用真的；
- 你正在测**集成行为**：替身会把要验证的东西替掉。

## 常见误区

### 误区：依赖都 mock 掉，测试才"单元"

**你以为**：越纯越好。
**其实**：替身太多，测试只剩"调用顺序"，无法证明业务正确。单元测试的边界是"一个行为"，不是"一个类"。
**怎么验证**：数一个测试里的 `when/verify`；超过三四个，通常说明它该改成集成测试或拆逻辑。

### 误区：用了 mock 框架就必须 verify

**你以为**：不 verify 就白 mock 了。
**其实**：Stub 的价值在返回值；没有交互断言的 mock 只是"假数据源"。乱 verify 会把实现细节写成契约。
**怎么验证**：删掉一条 `verify`，看测试还能不能发现真实的业务 bug。

### 误区：Fake 和真实实现永远一致

**你以为**：内存仓库就是数据库的等价物。
**其实**：唯一约束、排序规则、事务隔离、并发行为都可能不同。Fake 通过、真实实现失败，是常见事故。
**怎么验证**：同一组用例分别跑 Fake 与真实数据库（集成测试），看结果是否一致。

## 带走一句

**替身边界（库、HTTP、时钟），不要替身自己的类；只验证你真正关心的交互**——否则测试会锁死实现，却漏掉业务。
