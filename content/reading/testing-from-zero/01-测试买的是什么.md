## 这一关在解决什么

写测试之前先想清楚：**你在为什么付费，买到什么**。

测试的成本是持续的（写一次、维护很久、每次跑都要时间），收益只有一个——**改代码时的信心**。判断一个测试值不值得写，就看它能不能提高这份信心。

## 讲解

### 测试挡的是回归，不是"证明正确"

```java
@Test
void 折扣不会超过原价() {
    assertEquals(100, discount.apply(120, 20));  // 100
}
```

它证明的是"这道题在这个输入下算对了"，不能证明"折扣逻辑对所有输入都对"。测试的本质是**例子**，不是证明。

它真正的作用在以后：某次重构把 `apply` 改坏了，这个例子会立刻红。**没有测试，你要靠用户来发现。**

### 越晚发现的 bug 越贵

```text
写代码时发现 → 改一行
本地测试发现 → 改一行 + 跑一次
代码评审发现 → 解释 + 改 + 重新评审
测试环境发现 → 排查 + 改 + 重新部署
生产发现 → 用户影响 + 回滚 + 复盘 + 修复
```

测试的价值不是"抓住 bug"，而是**把发现时间提前**。提前一步，成本就低一个数量级。

### 分层：不同层买不同的信心

| 层 | 测什么 | 速度 | 稳定性 | 典型数量 |
| --- | --- | --- | --- | --- |
| 单元 | 一个函数/类的逻辑 | 毫秒 | 高 | 多 |
| 集成 | 模块与数据库/HTTP 协作 | 百毫秒–秒 | 中 | 中 |
| e2e | 用户走完一条路径 | 秒–分钟 | 低 | 少 |

"金字塔"说的是：底层多、顶层少。但比例不是教条——**关键路径可以多写 e2e，纯计算逻辑不需要 e2e**。判断标准是：这一层能不能给出你要的信心，且成本可接受。

### 什么样的测试值得写

优先写这三类：

1. **核心业务规则**：钱、权限、状态流转——错了代价最大；
2. **曾经出过 bug 的地方**：每修一个 bug 补一个测试，防止复发；
3. **边界与异常**：空值、零、超限、并发、失败重试。

不必写：

- getter/setter、纯转发；
- 框架已经保证的行为；
- 为了覆盖率而写的"执行一遍不报错"。

### 测试的可读性也是收益

一个测试失败时，读的人要能在 30 秒内知道"哪条业务规则坏了"。

```java
@Test
void 余额不足时拒绝下单并保留原余额() {
    var account = accountWith(100);
    assertThrows(InsufficientBalance.class, () -> order(account, 150));
    assertEquals(100, account.balance());
}
```

名字说清场景与期望，失败信息就自带诊断。**测试名就是文档**，比注释更不容易过期。

### 反馈速度决定你会不会跑

如果跑一次测试要十分钟，本地就不会跑，最后只在 CI 跑——发现时间又晚了一步。

实用做法：

- 单测必须秒级；
- 集成测试按模块分组，本地只跑改动的模块；
- e2e 只在提交前或 CI 跑，按文件/标签筛选。

## 常见误区

### 误区：测试越多越安全

**你以为**：每个方法都写测试，覆盖率上去就稳了。
**其实**：低价值的测试会拖慢反馈、增加维护；一个断言很弱的测试几乎不提供信心。
**怎么验证**：随机删掉几个测试，看有没有人会发现行为变化——没有，说明它们本来就没在保护什么。

### 误区：单元测试能替代集成测试

**你以为**：单测都过了，集成肯定没问题。
**其实**：单测把依赖都替身了，真实的 SQL、序列化、事务、超时都没被验证。集成问题只在集成层暴露。
**怎么验证**：改一个 SQL 的列名，单测全绿，集成/启动才会红。

### 误区：测试是给领导看的

**你以为**：有测试文件、覆盖率达标就行。
**其实**：测试的读者是下一个改代码的人（可能是三个月后的你）。判断标准是"它失败时，我能不能马上知道哪里坏了"。
**怎么验证**：故意改坏一行业务代码，看测试的失败信息是否直接指向问题。

## 带走一句

**测试买的是"改代码时的信心"，越早发现越便宜**——先问这个测试能挡住哪种回归，再决定写不写。
