## 这一关在解决什么

e2e 测试从浏览器/客户端出发，走完一条真实用户路径：登录、打开页面、点按钮、看到结果。

它最接近用户，也最贵、最脆。这一关讲：**测哪几条路径、怎么写才不飘、红了该不该信**。

打个比方：e2e 像交车前亲自试驾一圈。最像真实上路，但最慢、最费油，所以只跑关键几条路线。真实机制就是让浏览器从登录开始点到底，验证前后端接起来是通的。

## 讲解

### 只测"关键路径"

不要为每个按钮写 e2e。值得测的是：

1. **最核心的闭环**：登录 → 核心操作 → 看到结果；
2. **最容易跨层出错的链路**：前端调后端、鉴权、文件上传、支付回调；
3. **曾经出过事故的路径**：修一次补一条。

其余交给单测与集成测试。e2e 数量失控的直接后果是：跑一次十分钟，红了没人看，最后被 `skip`。

### 一个 e2e 只讲一个故事

```ts
test('登录后能从首页进入知识库并打开一条内容', async ({ page }) => {
  await signIn(page)
  await page.getByTestId('home-entry-knowledge').click()
  await page.getByTestId('entry-list').waitFor()
  await page.locator('[data-testid^="entry-link-"]').first().click()
  await expect(page.getByTestId('markdown-body')).toBeVisible()
})
```

步骤按用户动作写，断言放在**用户能看到的层面**：页面出现、标题、URL。不要断言内部状态与请求次数——那属于集成测试。

### 选择器：稳定优先

优先级从高到低：

1. **`data-testid`**：专门给测试用，改样式不影响；
2. **角色 + 名称**（`getByRole('button', { name: '登录' })`）：同时验证可访问性；
3. **文本**：用户可见，但文案一改就坏；
4. **CSS 类/层级**：最脆，样式重构就红。

不要用 `nth-child(3)` 或"第 2 个 div"定位——DOM 稍微一改就错位。

### 等待：等条件，不要等时间

```ts
// 差：固定睡眠
await page.waitForTimeout(2000)

// 好：等到可见
await expect(page.getByTestId('entry-list')).toBeVisible()
```

固定睡眠要么不够（偶发红），要么太多（拖慢）。Playwright 的 `expect` 会自动重试直到超时，这是首选。

### 不稳定测试的五个根因

| 根因 | 表现 | 修法 |
| --- | --- | --- |
| 固定睡眠 | 机器慢时红、快时绿 | 改成等条件 |
| 共享数据 | 并行时互相删数据 | 每个测试造自己的数据，唯一前缀 |
| 顺序依赖 | 单跑绿、全量红 | 测试之间不共享状态 |
| 动画/过渡 | 元素在移动中点不中 | 关动画或等稳定 |
| 外部服务 | 第三方超时 | 打桩或跳过并标注 |

**重试只能掩盖前四个，不能修好它们。** 一个"重跑就绿"的测试，等于没有测试——它不告诉你现在到底坏没坏。

### 登录态：复用，但别共享

每条用例都走一遍登录会拖慢很多。常见做法是全局 setup 登录一次、保存 storage state，用例复用。

注意：

- storage state 里的会话过期时间要够长，但不要无限；
- 不同角色的用例用不同的 state；
- 复用登录态不等于共享数据——业务数据仍要各自造。

### 调试 e2e

- 失败时保留 **trace / 截图 / 视频**，比日志有用；
- 本地复现：`--headed` 或 `--debug` 单步；
- 只跑失败的：`--last-failed`；
- 先修根因，再考虑临时 `skip`，并写清原因与恢复条件。

## 常见误区

### 误区：e2e 覆盖越多越放心

**你以为**：每个页面都写一条，最稳。
**其实**：e2e 的维护成本最高，数量一多就慢、就飘，最后没人跑。覆盖关键路径 + 分层测试才是稳。
**怎么验证**：统计 e2e 数量与单次运行时间；超过几分钟就该收敛。

### 误区：加 `waitForTimeout` 能解决不稳定

**你以为**：睡两秒就好了。
**其实**：只是把概率降低；网络慢、CI 负载高时还会红，而且每次多等两秒。
**怎么验证**：在 CI 上跑十次，看同一条是否仍偶发失败。

### 误区：失败重跑绿了就不是 bug

**你以为**：重试通过说明没问题。
**其实**：可能是竞态、数据污染或时序依赖——这些在线上同样会发生，只是更难复现。重试应该用来收集证据，不是用来结案。
**怎么验证**：看重试前的失败截图与 trace，找出"第一次为什么红"。

## 带走一句

**e2e 只测关键路径，等条件不等时间，红了先查根因**——数量少、断言在用户层，才有人愿意维护。
