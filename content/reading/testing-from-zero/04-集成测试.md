## 这一关在解决什么

单测把依赖都替身了，所以它证明不了：SQL 写对了没有、事务边界对不对、序列化会不会丢字段、迁移能不能在空库上跑起来。

这些只有**让真实部件一起工作**才能验证——这就是集成测试。它更慢、更容易受环境影响，但有些信心只能在这里买。

## 讲解

### 集成的"边界"选在哪

| 范围 | 启动什么 | 能发现 |
| --- | --- | --- |
| 仓储 + 真实数据库 | 数据源、迁移、SQL | 列名、约束、事务、时区 |
| 服务 + 数据库 | 事务、业务规则 | 回滚、并发、脏读 |
| HTTP 层 + 全部 | Web 容器、序列化、鉴权 | 路由、状态码、请求形状 |

范围越大越接近真实，也越慢。**从最小能覆盖风险的边界开始**：验证 SQL 不需要启动整个 Web 容器。

### 用真实数据库，不要用 H2 替代

H2 的 SQL 方言、类型、约束、函数与 MySQL 不同。常见后果：

- 本地 H2 通过，线上 MySQL 报语法错；
- `GROUP BY` 宽松模式掩盖了不合法的查询；
- 时区、`DATETIME` 精度、大小写敏感行为不一致。

**数据库的集成测试必须用同一种数据库**（同版本更好）。用 Testcontainers 或一个专用的测试实例都可以，关键是"和将要部署的是同一个东西"。

### 测试库隔离：每人一个库

多个测试并行、或多个会话共用同一个库，会互相删数据：

```text
会话 A：清空 orders → 插入 3 条 → 断言
会话 B：同一时刻清空 orders → A 的断言看到 0 条
```

解法不是"加锁"，而是**每次运行一个独占库**（例如 `paideia_run_<时间>_<pid>`），跑完删除。这样并行安全，失败时也能保留现场排查。

### 事务回滚：快，但有边界

```java
@Transactional
@Test
void 保存后能按用户查到() {
    repo.save(order(42L));
    assertEquals(1, repo.findByUser(42).size());
}
```

测试方法包在事务里，结束时回滚——不污染数据，也快。

但要注意：

- **被测代码自己开事务/异步线程**时，回滚可能看不到它的写入；
- 自增 id 不会回滚，断言 id 要避免写死；
- 某些 DDL 或存储过程会隐式提交。

### 迁移必须在空库上跑一次

集成测试的库通常由迁移创建。如果迁移只在"已有表"的开发库上验证过，空库可能直接失败（缺依赖、顺序错、种子冲突）。

所以测试前置步骤应该是：

```text
建空库 → 跑全部迁移 → 跑种子 → 再跑测试
```

这同时验证了"新环境能不能起来"，这是部署时最容易出事的一步。

### HTTP 层测试：验证契约

```java
@SpringBootTest(webEnvironment = RANDOM_PORT)
class OrderApiTest {
    @Test
    void 未登录返回401() { ... }

    @Test
    void 访问别人的订单返回404() { ... }
}
```

这一层最值得测的是**容易漏的守卫**：鉴权、参数校验、错误码、序列化字段名。它们不涉及复杂业务，但一个漏配就是线上事故。

### 集成测试的代价管理

- 只启动需要的上下文（切片测试），不要每个测试都 `@SpringBootTest`；
- 按模块分组跑，本地只跑改动模块；
- 测试之间不共享可变状态；数据用唯一前缀；
- 慢的用例打标签，放到提交前/CI 跑。

## 常见误区

### 误区：H2 能代替 MySQL 做集成测试

**你以为**：都是 SQL，差不多。
**其实**：方言、类型、约束、函数、时区都可能不同；测试通过不代表线上能跑。
**怎么验证**：把一条用 MySQL 特有函数的 SQL 放进 H2 测试，看是否直接失败。

### 误区：测试里 `@Transactional` 就万事大吉

**你以为**：回滚了就不会污染。
**其实**：异步任务、独立事务、自增序列、外部副作用（发邮件、写文件）都不受回滚控制。
**怎么验证**：在测试里调用一个 `@Async` 方法，看它写入的数据是否在回滚后还在。

### 误区：集成测试越多越好

**你以为**：越接近真实越放心。
**其实**：它们慢且脆，数量失控会让反馈时间爆炸，最后没人本地跑。把"必须真库"的放集成，其余回到单测。
**怎么验证**：统计一次全量集成测试耗时；超过几分钟就要考虑切片与分组。
