## 这一关在解决什么

测试的一半痛苦来自数据：断言依赖某条 id 为 1 的种子数据、两个测试抢同一行、日期写死到某一天、构造一个用户要填二十个字段。

这一关讲四条能立刻减少痛苦的规则：**每个测试自己造、只造需要的、值要可读、数据要能清理**。

## 讲解

### 不要依赖"库里本来就有"的数据

```java
// 差：依赖种子数据 id=1 存在且字段是某个值
var user = repo.find(1L).orElseThrow();
assertEquals("张三", user.name());
```

问题：

- 种子被改，测试红；
- 别的测试删了 id=1，测试红；
- 并行跑时互相影响；
- 读代码的人不知道 id=1 是什么。

正确做法是**测试自己创建前置数据**：

```java
var user = repo.save(User.create("张三", "zhang@example.com"));
assertEquals("张三", repo.find(user.id()).orElseThrow().name());
```

### 用 Builder 代替一长串参数

```java
User user = aUser().withName("张三").withRole(ADMIN).build();
Order order = anOrder().forUser(user).withAmount(100).build();
```

Builder 的价值不是"少写代码"，而是**让测试只表达与本次相关的字段**。默认值放在 Builder 里，读测试时一眼能看出"这条用例关心的是 role"。

反例：每个测试都 `new User(1, "a", "b", 18, "c", true, ...)`，读者要数参数位置才知道哪个是角色。

### 只造需要的数据

测"余额不足"不需要十笔订单。数据越多，准备逻辑越长，失败时越难判断是准备错了还是断言错了。

```java
// 只需要一个余额 100 的账户
var account = anAccount().withBalance(100).build();
```

### 唯一值：并行安全的低成本做法

```java
String email = "user-" + UUID.randomUUID() + "@test.local";
```

即使两个测试同时插入用户，也不会撞唯一索引。流水号、订单号、手机号同理。

如果断言需要可预测的值，用"测试名 + 计数器"而不是随机数：

```java
String sku = currentTestName() + "-sku";
```

### 时间要可控

```java
var clock = Clock.fixed(Instant.parse("2026-11-04T00:00:00Z"), ZoneOffset.UTC);
var service = new OrderService(clock, repo);
```

写死 `LocalDate.now()` 的测试会在某一天突然红（月末、闰年、时区切换）。注入时钟后，边界用例（"第 7 天到期"）才能稳定验证。

### 清理：三种策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 事务回滚 | 测试包在事务里，结束回滚 | 单库、无异步 |
| 每次重建 | 测试前清表/重建 schema | 集成测试、数据少 |
| 唯一前缀 + 定期清理 | 数据带运行标识，跑完删 | 并行、共享库 |

最差的是"谁也不清理"，最后测试库越来越大、越来越慢，还开始互相污染。

### 种子数据只做"环境"，不做"断言依赖"

种子适合放：字典表、配置项、管理员账号。**不适合放业务数据**——业务数据应该由测试自己造。

判断标准：这条数据被删了，测试还能不能自己重建？不能，就说明它不该是种子。

## 常见误区

### 误区：数据准备越完整越真实

**你以为**：造一整套用户、订单、商品，测试更可信。
**其实**：与本次行为无关的数据只会增加噪音与耗时；真实感应该由集成测试的"真实依赖"提供，不是靠堆数据。
**怎么验证**：删掉一半准备数据，测试是否仍然通过；通过说明那些数据是噪音。

### 误区：用 `LocalDate.now()` 测日期逻辑

**你以为**：今天跑是绿的就行。
**其实**：明天、月末、闰年可能就红；这类测试会成为"某天突然失败"的经典来源。
**怎么验证**：把系统时间调到边界日（或用注入的 Clock）跑一次。

### 误区：测试数据用固定 id 更简单

**你以为**：`id=1` 写起来方便。
**其实**：自增 id 在并行、重建、迁移后都不可控；固定 id 还会和真实数据冲突。
**怎么验证**：并行跑两个都插入 `id=1` 的测试，看谁先失败。

## 带走一句

**测试自己造数据、只造需要的、用唯一值、时间可注入**——数据独立了，测试才能并行、才能稳定。
