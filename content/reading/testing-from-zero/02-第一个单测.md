## 这一关在解决什么

单测是最便宜的一层：毫秒级、无外部依赖、失败信息直接。但写法不对，它会变成负担：改实现就红、一个测试断言十件事、失败后不知道哪儿坏了。

这一关给一个能长期维护的写法模板：**AAA + 一个行为 + 精确断言**。

打个比方：写单测像照一张说明书。先摆好材料，再按一次开关，最后核对结果——三步分开，坏了才知道是哪步出错。真实机制就是 AAA：Arrange 准备、Act 调用、Assert 断言。

## 讲解

### 结构：Arrange / Act / Assert

```java
@Test
void 满减后金额低于零时按零计() {
    // Arrange：准备输入与依赖
    var coupon = new Coupon(FULL_REDUCTION, 100, 150);

    // Act：只调用一次被测行为
    var payable = coupon.apply(80);

    // Assert：断言可观察的结果
    assertEquals(0, payable);
}
```

三段用空行分开（不一定要写注释）。好处是失败时一眼能定位是"准备错了""调用错了"还是"结果不对"。

**Act 只做一次调用**。一个测试里调用两次被测方法，失败时很难判断是哪次出的问题。

### 一个测试只断言一个行为

```java
// 差：一个测试覆盖三件事，失败时不知道哪条坏了
@Test
void 优惠券逻辑() {
    assertEquals(0, coupon.apply(80));
    assertEquals(90, coupon.apply(110));
    assertThrows(IllegalArgumentException.class, () -> coupon.apply(-1));
}
```

拆成三个测试，名字分别说清场景。**测试数量多一点不是问题，失败信息模糊才是问题。**

### 命名：说清"场景 + 期望"

```java
void 余额不足时拒绝下单并保留原余额()
void 空购物车结算返回零元订单()
void 超过库存上限时截断到上限()
```

中文方法名在 JUnit 5 里可以直接用。名字里带**条件**与**结果**，失败时不用打开测试代码就知道坏了什么。

反例：`testApply()`、`test1()`、`shouldWork()`——它们只在写的时候有意义。

### 断言要"精确"，不要"大概"

```java
// 弱：只证明不抛异常
assertNotNull(result);

// 强：证明具体值
assertEquals(90, result.payable());
assertEquals(List.of("A", "B"), result.items());
```

一个测试的强度取决于**断言有多具体**。`assertNotNull` 几乎不提供信息；断具体值、具体集合、具体异常类型，才能挡住回归。

浮点数不要直接相等：

```java
assertEquals(0.1 + 0.2, 0.3, 1e-9);
```

集合比较注意顺序：`assertEquals` 对 `List` 是有序比较，`Set` 无序；不确定顺序时先排序或用 `containsExactlyInAnyOrder`。

### 异常也要断言类型与信息

```java
var ex = assertThrows(InsufficientBalance.class, () -> account.withdraw(200));
assertTrue(ex.getMessage().contains("余额"));
```

只断言"抛了异常"不够——抛的是空指针也会通过。

### 参数化：同一逻辑多组输入

```java
@ParameterizedTest
@CsvSource({
    "100, 20, 80",
    "50,  20, 30",
    "10,  20, 0"
})
void 折扣不会把金额算成负数(int price, int discount, int expected) {
    assertEquals(expected, applyDiscount(price, discount));
}
```

一组输入一个用例，失败时报告会指出是哪一行数据。

### 测试里不要写逻辑

```java
// 差：测试自己也要被测试
for (int i = 0; i < 10; i++) {
    if (i % 2 == 0) {
        assertEquals(i, even(i));
    }
}
```

测试应该"一眼看完"，不要循环、不要条件、不要复用复杂工具方法。重复几行比抽象更可读。

## 常见误区

### 误区：一个测试覆盖越多越好

**你以为**：少写几个测试，省事。
**其实**：失败时无法定位，改一个行为要重写整个测试。一个行为一个测试，维护成本反而低。
**怎么验证**：故意改坏一处逻辑，看有几个测试红、失败信息是否直接。

### 误区：断言"不报错"就算测过了

**你以为**：调用一下没抛异常，说明逻辑对。
**其实**：这只证明"没崩"，不证明"算对了"。没有具体断言的测试，覆盖率再高也挡不住回归。
**怎么验证**：把返回值改成常量，看测试是否还会红。

### 误区：测试代码不用讲究

**你以为**：测试是附属品，能跑就行。
**其实**：测试和业务代码一样会被读、被改；命名混乱、准备逻辑复杂的测试，半年后没人敢动。
**怎么验证**：让同事只看测试名，说这条业务规则是什么；说不出来就说明命名不合格。
