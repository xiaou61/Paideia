## 先把结论摆出来

一个 HTTP 请求进入 Spring 应用后，**顺序是固定的**：

```sketch

      { "id": "advice", "title": "全局异常处理", "sub": "异常在这里变响应", "tone": "blue" },

    { "from": "inter", "to": "advice" },
    { "from": "advice", "to": "ctl" }

```

```text
Filter → DispatcherServlet → HandlerMapping → HandlerAdapter
       → 参数解析 → Controller 方法 → 返回值处理 → 消息转换
       →（异常则走 HandlerExceptionResolver）→ Filter 回程 → 响应
```

大多数"为什么拿不到参数 / 为什么返回的不是 JSON / 为什么切面不生效"的问题，都能在这条链路上找到位置。

先记住三个最容易混的组件：

| 组件 | 管什么 | 什么时候执行 |
| --- | --- | --- |
| Filter | Servlet 层，请求进 DispatcherServlet 之前 | 最早；拿不到 handler，也拿不到方法参数 |
| HandlerInterceptor | Spring MVC 层，handler 已确定之后 | 参数解析前后各一次；能拿到 handler |
| AOP 切面 | Bean 方法调用，发生在 Controller 方法真正被调用时 | 最晚；只包住方法本身 |

**顺序：Filter → Interceptor.preHandle → 参数解析 → AOP → Controller 方法 → AOP 返回 → Interceptor.postHandle → 视图/消息转换。**

## DispatcherServlet 做了哪几件事

它本身不处理业务，只做调度：

1. 通过 `HandlerMapping` 找到"哪个 Controller 的哪个方法"能处理这个 URL；
2. 通过 `HandlerAdapter` 调用那个方法——适配不同风格的 handler（注解式、函数式）；
3. 把返回值交给 `HandlerMethodReturnValueHandler`；
4. 出异常时交给 `HandlerExceptionResolver`。

`HandlerMapping` 的匹配依据是 `@RequestMapping` 里的路径、方法、参数、Header 等条件。**匹配不到就是 404，匹配到但不满足条件可能是 405 或 415。**

## 参数是怎么"变"进来的

`HandlerAdapter` 在调用方法前，会为每个参数找对应的 `HandlerMethodArgumentResolver`：

| 参数写法 | 解析器 | 数据来源 |
| --- | --- | --- |
| `@RequestParam String name` | `RequestParamMethodArgumentResolver` | query string / form |
| `@PathVariable Long id` | `PathVariableMethodArgumentResolver` | URL 模板 |
| `@RequestBody OrderCreateRequest body` | `RequestResponseBodyMethodProcessor` | 请求体 + `HttpMessageConverter` |
| `@RequestHeader` | `RequestHeaderMethodArgumentResolver` | 请求头 |
| 无注解的 `OrderQuery query` | `ModelAttributeMethodProcessor` | 把多个参数绑成对象 |

三个高频坑：

1. **`@RequestBody` 只能读一次流**。在 Filter 或拦截器里读过 `request.getInputStream()`，Controller 里就会拿到空对象。要读就包一层 `ContentCachingRequestWrapper`。
2. **`@RequestParam` 与 `@PathVariable` 名字必须对得上**，或用 `-parameters` 编译参数保留形参名。Spring Boot 的 Maven 插件默认开了，手动 `javac` 可能没开。
3. **JSON 反序列化失败是 400，不是 500**。字段类型不匹配、枚举值不存在、日期格式不对，都会在参数解析阶段抛 `HttpMessageNotReadableException`。

## 返回值：为什么有时是页面，有时是 JSON

关键在**有没有 `@ResponseBody`**（或类上有 `@RestController`）：

- 有 → 返回值交给 `HttpMessageConverter` 写出响应体，`Accept: application/json` 时就是 JSON；
- 没有 → 返回值被当成**视图名**，交给 `ViewResolver` 找模板。

所以一个 `String` 返回值：

```java
@Controller
public class PageController {
    @GetMapping("/hello")
    public String hello() {
        return "hello";          // 视图名 → templates/hello.html
    }
}

@RestController
public class ApiController {
    @GetMapping("/api/hello")
    public String hello() {
        return "hello";          // 响应体 → 纯文本 hello
    }
}
```

同一个返回值，两种完全不同的结果。**先看类上的注解，再看方法上的。**

## 异常去哪了

默认情况下，异常会一路抛到 `DispatcherServlet`，然后：

1. 找 `@ExceptionHandler`（本 Controller 内的优先）；
2. 找 `@ControllerAdvice` 里的全局处理器；
3. 都没有 → 交给容器，返回 500。

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError notFound(OrderNotFoundException ex) {
        return new ApiError("ORDER_NOT_FOUND", ex.getMessage());
    }
}
```

**注意**：如果异常已经被全局处理器接住并返回了正常响应，事务是否回滚只看异常有没有从 `@Transactional` 方法里抛出去——两者是独立的。详见上一篇「事务失效」。

## 一个具体例子：登录请求为什么返回 400

请求：

```text
POST /api/v1/auth/login
Content-Type: application/json

{"identifier": "admin"}
```

Controller：

```java
@PostMapping("/api/v1/auth/login")
public LoginResponse login(@RequestBody LoginRequest body) { ... }
```

`LoginRequest` 里 `password` 标了 `@NotBlank`，但方法参数上**没有 `@Valid`**，所以校验根本没跑，请求进入方法后拿到 `null` 密码，业务层抛了 `IllegalArgumentException`，全局处理器把它映射成了 400。

两次排查点：

1. 先看**参数解析**有没有失败（`HttpMessageNotReadableException` / `MethodArgumentNotValidException`）；
2. 再看**业务层**抛了什么（日志里的异常类型）。

两者的 400 长得很像，但原因完全不同。

## 常见误区

### 误区：`@ResponseBody` 是"返回 JSON"的开关

**你以为**：加上它就一定返回 JSON。
**其实**：它只是"把返回值交给消息转换器"。返回 `String` 且客户端 `Accept: text/plain` 时就是纯文本；没有合适的转换器还会 406。
**怎么验证**：用 `curl -H 'Accept: application/xml'` 请求同一个接口，看 Content-Type 与响应体怎么变。

### 误区：拦截器能拿到方法参数

**你以为**：`preHandle` 里能直接取到 Controller 的参数。
**其实**：`preHandle` 在参数解析**之前**执行，此时参数还没绑定。要拿参数得用 `HandlerMethodArgumentResolver`，或从 `HttpServletRequest` 自己解析。
**怎么验证**：在 `preHandle` 里打印 `request.getParameterMap()`——query 参数有，`@RequestBody` 的内容没有。

### 误区：全局异常处理器接住了，事务就一定回滚了

**你以为**：异常被 `@ExceptionHandler` 处理掉，说明事务知道出错了。
**其实**：事务回滚看的是异常有没有从 `@Transactional` 方法里**抛出去**。处理器只是在异常到达 DispatcherServlet 之后才介入。
**怎么验证**：写一个 `@Transactional` 方法抛异常 + 全局处理器返回 200，观察数据库是否回滚。

## 小结

请求链路可以压缩成一句话：**Filter 管进出，DispatcherServlet 管调度，HandlerAdapter 管参数与返回值，消息转换器管序列化，异常解析器管兜底。** 排查时先判断问题落在哪一段：404 在 HandlerMapping，400 多半在参数解析或校验，415 在消息转换器，500 才轮到业务代码。
