## 先把结论摆出来

**`@Transactional` 是一个切面，所以它只在"调用经过代理"时生效；它的回滚只对"抛出去的 RuntimeException 和 Error"默认生效。**

这两条覆盖了绝大多数"加了注解但没用"的现场：**代理没被经过** → 事务根本没开（自调用、非 public、`final` 方法）；**异常没抛出去** → 事务开了但不回滚（吞异常、抛受检异常）。

## 事务到底是谁在管

`@Transactional` 自己不做事，它靠三样东西：**代理**（拦截方法调用）、**事务管理器**（`PlatformTransactionManager`，真正去 `begin` / `commit` / `rollback`）、**连接绑定**（把同一事务的数据库连接绑到当前线程的 `ThreadLocal`，让多个 DAO 共用一条连接）。所以事务是**线程绑定**的，异步线程里不会自动传过去——这也是 `@Async` 加 `@Transactional` 经常出错的原因。

## 失效场景一：自调用

```java
@Service
public class UserService {

    public void register(User user) {
        save(user);            // 自调用，绕过了代理
    }

    @Transactional
    public void save(User user) {
        userRepository.save(user);
        auditRepository.log("register");
    }
}
```

`register` 从外部调用时经过了代理，但代理检查的是 `register` 有没有事务注解——没有，直接转发。内部调 `save` 是 `this.save`，普通方法调用，事务不生效。两条插入各自自动提交，中间失败就只回滚一半。

解决办法和第四篇一样：把 `save` 拆到另一个 bean，或注入自己。

## 失效场景二：方法不是 public

Spring 的默认代理只拦截 **public** 方法。`protected`、`private`、包级私有都不拦。

原因在 CGLIB：它靠生成子类覆写方法，`private` 子类看不见，`final` 不能覆写；JDK 代理则只认接口里的 public 方法。这类失效**不报错**，最难查。

## 失效场景三：异常被吞掉

```java
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    try {
        accountDao.debit(from, amount);
        accountDao.credit(to, amount);
    } catch (Exception e) {
        log.error("转账失败", e);     // 吞掉了
    }
}
```

事务管理器靠"方法是否抛出异常"判断要不要回滚。异常被 catch 住，方法正常返回，代理认为一切顺利，于是 `commit`。正确做法是记完日志继续抛，或手动标记回滚：`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。

## 失效场景四：受检异常默认不回滚

默认规则是：**遇到 `RuntimeException` 和 `Error` 回滚，遇到受检异常（`Exception` 的子类但不是 `RuntimeException`）提交。**

```java
@Transactional
public void importData(File file) throws IOException {
    throw new IOException("读文件失败");   // 受检异常 → 不回滚
}
```

要让它回滚，显式写 `@Transactional(rollbackFor = Exception.class)`。**实际项目里建议统一这么写**——"该不该回滚"该由业务决定，而不是由"它是不是受检异常"这种语言层面的分类决定。`rollbackFor` 只影响回滚，异常照样抛给调用方。

## 失效场景五：同一个类里两个事务方法互相调

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        saveItems(order);                       // 自调用
        throw new IllegalStateException("库存不足");
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveItems(Order order) { ... }
}
```

`saveItems` 标了 `REQUIRES_NEW`，看起来该开独立事务、不受外层回滚影响。但自调用让它完全不生效，最后一起没了。**传播行为只有在"经过代理"时才有意义。**

## 传播行为是什么

传播行为（propagation）回答一个问题：**当前已经在一个事务里了，新方法要怎么参与？**

| 传播行为 | 已有事务时 | 没有事务时 |
| --- | --- | --- |
| `REQUIRED`（默认） | 加入 | 新建一个 |
| `REQUIRES_NEW` | 挂起外层，新建独立事务 | 新建一个 |
| `NESTED` | 建保存点，可单独回滚 | 新建一个 |
| `SUPPORTS` | 加入 | 不用事务 |
| `NOT_SUPPORTED` | 挂起外层，不用事务 | 不用事务 |
| `MANDATORY` | 加入 | 抛异常 |
| `NEVER` | 抛异常 | 不用事务 |

日常 95% 用 `REQUIRED` 就够。需要区分的只有两处：日志、审计这类"主流程失败也要留记录"的操作用 `REQUIRES_NEW`；`NESTED` 是保存点（外层还能整体回滚），`REQUIRES_NEW` 是真正独立的另一个事务，这两个最容易被记混。

## 只读事务有什么用

```java
@Transactional(readOnly = true)
public List<Order> listByUser(Long userId) { ... }
```

`readOnly = true` 做两件事：**告诉驱动这是只读的**（某些数据库可以走更优路径，比如不生成回滚段）；**给 Hibernate 一个信号**，不要做脏检查、不维护一级缓存的快照——查询多、实体大的场景省得不少。

它**不会**阻止你写数据库（MySQL 不会因此报错），所以不是安全措施；真正的只读权限要在数据库账号层配。实际价值在于：类里大部分方法是查询时，把 `readOnly = true` 放在类上、写方法单独覆盖，最省事。

## 一个具体的排查顺序

事务没生效时按这个顺序查：**① 这个方法是不是从外部经过代理调用的（打 `this.getClass()`）？② 方法是不是 public、类或方法是不是 `final`？③ 异常真的抛出去了吗、是 `RuntimeException` 吗？**

第 1 步就能挡掉一半问题。用 `TransactionSynchronizationManager.isActualTransactionActive()` 确认事务开没开：返回 `true` 但没回滚，问题在异常类型；返回 `false`，问题在代理。

## 常见误区

### 误区：`@Transactional` 加在类上，类里所有方法都有事务

**你以为**：类级注解会覆盖所有方法，包括 private 的辅助方法。
**其实**：类级注解只是给 public 方法一个默认值。非 public 方法代理拦不到，`final` 方法也拦不到。类级注解省的是重复书写，不是扩大范围。
**怎么验证**：类上标 `@Transactional`，在 private 方法里打 `isActualTransactionActive()`，从同类 public 方法调它，返回 `false`。

### 误区：捕获异常后再抛出去，事务照样回滚

**你以为**：`try-catch` 之后 `throw e` 和没 catch 一样。
**其实**：这取决于抛出去的实际类型。`catch (Exception e) { throw e; }` 重新抛的还是那个 `IOException`，仍是受检异常，默认不回滚。只有实际抛出的对象是 `RuntimeException` 才会回滚。
**怎么验证**：用 `catch (Exception e) { throw e; }` 包住一个 `IOException`，观察数据是否被提交。

### 误区：`REQUIRES_NEW` 能保证"内层失败不影响外层"

**你以为**：内层独立事务，它失败了自己回滚，外层继续。
**其实**：内层 `REQUIRES_NEW` 回滚后，异常会继续往外抛。外层没捕获，外层也会回滚。要真隔离，外层必须捕获内层的异常——而这时又要小心别吞掉本该暴露的问题。
**怎么验证**：内层 `REQUIRES_NEW` 抛 `RuntimeException`，外层不捕获，两张表都没数据；外层捕获后再看，内层回滚、外层提交。

## 小结

`@Transactional` 靠代理生效，所以自调用、非 public、`final` 都会让它失效；回滚靠异常，所以吞异常和受检异常会让它不生效。传播行为只在经过代理时才有意义。排查顺序：先确认有没有代理，再确认方法可见性，最后确认异常类型。
