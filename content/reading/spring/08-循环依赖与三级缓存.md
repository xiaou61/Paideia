## 先把结论摆出来

**循环依赖能不能被 Spring 解决，取决于"能不能先拿到一个还没初始化完的对象"。**

- 字段注入 / setter 注入 + 单例 → 能解决，靠三级缓存；
- 构造器注入 → 解决不了，因为对象必须先把依赖传进来才能创建；
- prototype 作用域 → 解决不了，Spring 不为它缓存早期引用。

打个比方：三级缓存像盖楼时先搭的"施工电梯"，让人先上去干活，楼再慢慢补齐；它不是标准做法，只是应急通道。机制上，Spring 把一个刚 `new` 出来、字段还没填完的对象提前暴露出去，等依赖方拿到引用，再回头把它补完整。

Spring Boot 2.6 之后**默认禁止循环依赖**，启动会直接失败。所以今天更该问的不是"三级缓存怎么工作"，而是"为什么我的代码会出现循环依赖，以及怎么拆掉它"。三级缓存是理解框架的入口，不是鼓励你依赖它。

## 什么是循环依赖

```java
@Service
public class OrderService {
    @Autowired
    private PayService payService;
}

@Service
public class PayService {
    @Autowired
    private OrderService orderService;
}
```

`OrderService` 需要 `PayService`，`PayService` 又需要 `OrderService`。如果"创建 A 之前必须先完整创建 B，创建 B 之前又必须先完整创建 A"，就永远开始不了。

Spring 的解法是：**先把 A 的"空壳"暴露出去，再回头把 B 注进去，最后把 A 补完整。**

## 三级缓存是什么

| 缓存 | 名字 | 存什么 |
| --- | --- | --- |
| 一级 | `singletonObjects` | 完全初始化好的单例 |
| 二级 | `earlySingletonObjects` | 提前暴露的"半成品"（可能已被 AOP 代理） |
| 三级 | `singletonFactories` | 生产半成品的 `ObjectFactory` |

创建 `A` 的过程（简化）：

```text
1. new A()                       // 实例化，此时字段都是 null
2. 把 A 的 ObjectFactory 放进三级缓存
3. 给 A 注入依赖 → 发现需要 B
4. 去创建 B
   4.1 new B()
   4.2 把 B 的 ObjectFactory 放进三级缓存
   4.3 给 B 注入依赖 → 发现需要 A
   4.4 一级、二级都没有 A
   4.5 三级缓存里有 A 的工厂 → 调用工厂，拿到 A 的早期引用
   4.6 把早期引用放进二级缓存，从三级缓存移除
   4.7 B 注入这个早期 A，B 初始化完成，进入一级缓存
5. A 拿到 B，注入完成
6. A 初始化完成，进入一级缓存
7. 清理 A 在二级、三级缓存里的残留
```

**关键在第 4.5 步**：B 拿到的是 A 的引用，不是 A 的副本。之后 A 继续初始化（填充剩余字段、执行 `@PostConstruct`），B 手里那个引用看到的是同一个对象。

## 为什么需要第三级，而不是两级

如果只缓存"半成品对象"，AOP 会有问题：**代理对象必须在注入之前决定**。

假设 `A` 需要被事务或切面代理：

- 两级缓存只能存"原始对象"或"最终代理"其中之一；
- 如果存原始对象，B 注入的是原始对象，之后 A 被代理，B 手里就不是代理了，切面失效；
- 如果存最终代理，此时 A 还没初始化完，代理生成时机不对。

三级缓存存的是**工厂**：等到真正有人需要早期引用时（第 4.5 步），才调用 `getEarlyBeanReference`。这个方法会给需要代理的 Bean 提前生成代理，不需要的返回原对象。**延迟到"有人要"才决定，是第三级存在的理由。**

## 为什么构造器注入解决不了

```java
@Service
public class OrderService {
    private final PayService payService;
    public OrderService(PayService payService) { this.payService = payService; }
}

@Service
public class PayService {
    private final OrderService orderService;
    public PayService(OrderService orderService) { this.orderService = orderService; }
}
```

创建 `OrderService` 必须先有 `PayService`；创建 `PayService` 必须先有 `OrderService`。**连"空壳"都创建不出来**，三级缓存无从下手。启动直接报 `BeanCurrentlyInCreationException`。

Spring Boot 2.6+ 的默认行为：

```text
The dependencies of some of the beans in the application context form a cycle:
┌─────┐
|  orderService
↑     ↓
|  payService
└─────┘

Action:
Relying upon circular references is discouraged and they are prohibited by default.
Update your application to remove the dependency cycle between beans.
As a last resort, it may be possible to break the cycle automatically by setting
spring.main.allow-circular-references to true.
```

注意最后一句：**可以打开开关，但那是"最后手段"**，不是推荐配置。

## 真正该做的：把环拆掉

三种常见拆法：

### 1. 抽第三个 Bean

把两边都需要的逻辑抽出来，谁都不再依赖对方：

```text
OrderService → OrderCalculator ← PayService
```

`OrderCalculator` 只依赖数据，不依赖两个 Service。

### 2. 用事件代替反向调用

`OrderService` 创建订单后发布事件，`PayService` 监听：

```java
public record OrderCreated(long orderId) {}

// 发布方只依赖 ApplicationEventPublisher
eventPublisher.publishEvent(new OrderCreated(id));

// 监听方只依赖事件
@EventListener
public void onOrderCreated(OrderCreated event) { ... }
```

依赖方向变成单向，环自然消失。

### 3. `@Lazy` 延迟注入（临时手段）

```java
@Service
public class OrderService {
    private final PayService payService;

    public OrderService(@Lazy PayService payService) {
        this.payService = payService;
    }
}
```

`@Lazy` 注入的是一个代理，第一次真正调用 `payService` 的方法时才去容器里取。环被打断，代价是多一层代理、启动期错误被推迟到运行期。**只适合过渡，不适合长期架构。**

## 一个排查顺序

启动报循环依赖时：

1. 看异常里的**环**：它会把 `A → B → C → A` 列出来；
2. 判断是构造器注入还是字段注入；
3. 优先抽公共依赖或改事件；
4. 实在拆不动，再考虑 `@Lazy`；
5. 最后才是 `spring.main.allow-circular-references=true`——打开之后相当于回到老行为，问题只是被隐藏。

## 常见误区

### 误区：三级缓存就是"缓存了三个对象"

**你以为**：Spring 存了三个版本的 Bean。

**其实**：三级是 `ObjectFactory`（怎么生产早期引用），二级是"已经生产出来的早期引用"，一级是"完全初始化好的对象"。三者是不同阶段，不是三个副本。

**怎么验证**：读 `DefaultSingletonBeanRegistry#getSingleton(String, boolean)`，能看到从三级到二级再到一级的迁移顺序。

### 误区：能解决循环依赖说明这样写没问题

**你以为**：既然 Spring 能处理，字段注入互相依赖也无所谓。

**其实**：能处理不等于健康。循环依赖通常意味着两个类职责耦合过紧，长期会导致启动顺序脆弱、测试困难、AOP 时序问题。

**怎么验证**：把两个类画出来，问"其中一个能不能不依赖另一个完成自己的核心职责"——答案通常是能，那就是该拆。

### 误区：`@Lazy` 是推荐的修复方式

**你以为**：加个 `@Lazy` 就不报错了，问题解决。

**其实**：它只是把"启动期错误"推迟到"第一次调用"。如果代理目标不存在或初始化失败，错误会在运行时才暴露。

**怎么验证**：给 `@Lazy` 注入的字段在启动后立刻调一次方法，看异常是在启动时还是运行时出现。

## 小结

三级缓存解决的是"单例 + 字段/setter 注入"下"先给半成品、再补完整"的问题；第三级用工厂是为了让 AOP 代理能在正确时机生成。构造器注入、prototype 作用域都不在覆盖范围内。Spring Boot 2.6+ 默认禁止循环依赖，正确的响应是**拆环**：抽公共依赖、改事件、实在不行再 `@Lazy`，而不是打开开关装作没看见。
