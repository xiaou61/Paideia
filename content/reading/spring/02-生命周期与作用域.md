## 第二次报表里，第一个人的名字还在

`report("alice")` 和 `report("bob")` 各跑一次，第二份报表的 owners 里躺着 alice。整段代码只有三处：

```java
public class AuditSupport {
    @PostConstruct
    void auditInit() { System.out.println("[AuditSupport] @PostConstruct（父类）"); }

    @PreDestroy
    void auditClose() { System.out.println("[AuditSupport] @PreDestroy（父类）"); }
}

public class ReportBuilder extends AuditSupport implements InitializingBean, DisposableBean {

    private static int nextId = 1;
    private final int id = nextId++;
    private final List<String> owners = new ArrayList<>();

    public ReportBuilder() { System.out.println("builder ctor #" + id); }

    @PostConstruct
    void init() {
        System.out.println("builder @PostConstruct #" + id + " class=" + getClass().getSimpleName());
    }

    @Override
    public void afterPropertiesSet() { System.out.println("builder afterPropertiesSet #" + id); }

    public void customInit() { System.out.println("builder customInit（initMethod）#" + id); }

    public ReportBuilder add(String owner) { owners.add(owner); return this; }
    public String build() { return "builder#" + id + " owners=" + owners; }
    public int id() { return id; }
}

public class ReportService {
    private final ReportBuilder builder;

    public ReportService(ReportBuilder builder) {
        this.builder = builder;
        System.out.println("ReportService ctor，拿到的 builder #" + builder.id());
    }

    public String report(String owner) { return builder.add(owner).build(); }
}

@Configuration
class Config {
    @Bean(initMethod = "customInit", destroyMethod = "customDestroy")
    @Scope("prototype")
    ReportBuilder reportBuilder() { return new ReportBuilder(); }

    @Bean
    ReportService reportService(ReportBuilder builder) { return new ReportService(builder); }
}
```

跑两次 `report()`：

```text
builder ctor #1
[AuditSupport] @PostConstruct（父类）
builder @PostConstruct #1 class=ReportBuilder
builder afterPropertiesSet #1
builder customInit（initMethod）#1
ReportService ctor，拿到的 builder #1
1) builder#1 owners=[alice]
2) builder#1 owners=[alice, bob]
建过的 builder 个数 = 1
close 之后：@PreDestroy=0，destroy()=0
```

我写下这段时以为 `@Scope("prototype")` 的意思是「每次用到都给一个新的」，所以第二行应该是 `builder#2`。实际只建了一个：`ReportService` 是单例，它的构造器只跑一次，那次注入解析出的实例就一直在字段里躺着，第二个人的名字直接 `add` 到了第一个人的 list 上。

`prototype` 管的是「每次向容器解析这个 bean 时造不造新的」，跟「这个方法被调用几次」没有关系。上面输出里 `ReportService ctor` 排在 builder 的四行回调**后面**，也是同一件事的另一面：依赖先被完整造好、初始化完，才交给依赖它的那个 bean。

（这段是真跑的：JDK 25.0.4 + Spring Framework 6.2.11，纯 `AnnotationConfigApplicationContext`，没有 Boot。下面各段都来自同一个探针工程，按小节截取输出；空行和 JUL 的启动日志我删了，其余逐字照抄。文末有依赖清单和命令。）

## 想每次要新的，就得每次向容器要

把注入改成 `ObjectProvider`，每次调用现取：

```java
public class ProviderService {
    private final ObjectProvider<ReportBuilder> providers;

    public ProviderService(ObjectProvider<ReportBuilder> providers) { this.providers = providers; }

    public String report(String owner) { return providers.getObject().add(owner).build(); }
}
```

```text
1) builder#1 owners=[alice]
2) builder#2 owners=[bob]
第一次 getBean(SlowBean) 之前，建过 = 0
[SlowBean] ctor
第一次之后，建过 = 1
再取一次，建过 = 1
直接 getBean 两次：builder#3 owners=[] | builder#4 owners=[]
```

每个 builder 的 `ctor` / `@PostConstruct` / `afterPropertiesSet` 三行我省了。`SlowBean` 是另一个被 `@Lazy` 标上的单例：`refresh` 之后建过 0 个，第一次 `getBean` 才打印构造器，再取一次数字不变。

| 从哪儿要 ReportBuilder | 拿到的是不是新实例 | 实测到的 |
|---|---|---|
| 单例构造器注入 | 不是，一直是同一个 | 两次 `report()` 都是 `builder#1` |
| `ObjectProvider.getObject()` | 是 | `builder#1`、`builder#2` |
| `getBean(ReportBuilder.class)` 连取两次 | 是 | `builder#3`、`builder#4` |
| `@Bean` 上标 `@Lazy` 的单例 | 不是，但创建被推迟 | refresh 后建过 0 个，第一次 `getBean` 才建 |

`@Lazy` 这一行，我以前的写法是「把启动时的失败推到第一次调用」。测完发现这话一半对一半不对：正常 bean 被 `@Lazy` 标上，只是创建晚一点，随后一切照常，没有失败可言（实测）；只有这个 bean 本身建不出来（缺依赖、构造器抛异常）时，错误才会从启动期挪到第一次取用的地方——这一半是推断，我没构造一个坏 bean 去验证。它推迟的是创建，不是失败。至于拿 `@Lazy` 绕循环依赖，那是另一层机制，第 08 篇讲三级缓存时再说。

## 回调不是一个，是一串

把同一个类去掉 `@Scope("prototype")` 注册成单例，再挂一个只对 `reportBuilder` 打日志的 `BeanPostProcessor`，然后关掉容器：

```java
static class LoggingBpp implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if ("reportBuilder".equals(beanName)) System.out.println("[bpp] beforeInitialization");
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if ("reportBuilder".equals(beanName)) System.out.println("[bpp] afterInitialization");
        return bean;
    }
}
```

```text
builder ctor #1
[bpp] beforeInitialization
[AuditSupport] @PostConstruct（父类）
builder @PostConstruct #1 class=ReportBuilder
builder afterPropertiesSet #1
builder customInit（initMethod）#1
[bpp] afterInitialization
使用期：builder#1 owners=[]
builder @PreDestroy #1
[AuditSupport] @PreDestroy（父类）
builder destroy() #1
builder customDestroy（destroyMethod）#1
close 之后：@PreDestroy=1，destroy()=1
```

`@PostConstruct`、`afterPropertiesSet`、`initMethod` 三个都跑了，销毁侧 `@PreDestroy`、`destroy()`、`destroyMethod` 三个也都跑了。把这三件事当成三选一，是这一节要纠正的一点：不是任选，是然后。父类回调在初始化时排在子类前面，销毁时反过来。

| 时刻 | 容器手里是什么 | 可以做什么 | 别在这里做 |
|---|---|---|---|
| 构造器 | 刚 `new` 出来、字段还空 | 记参数、赋 final 字段 | 用注入进来的依赖 |
| `postProcessBeforeInitialization` | 依赖已注入，对象还能被换掉 | 包装、替换（见下节） | 假设后面的回调一定跑在你手里这个对象上 |
| 父类 `@PostConstruct` | 同上；自动代理要到下一步才套 | 读配置、校验依赖 | 以为 `this` 是代理 |
| 子类 `@PostConstruct` | 同上 | 同上 | 同上 |
| `afterPropertiesSet` | 同上 | 同上 | 同上 |
| `initMethod` | 同上 | 同上 | 同上 |
| `postProcessAfterInitialization` | 自动代理在这一步把对象换成代理，别的 BPP 也可能换掉它 | 加拦截 | 再调业务方法 |
| `@PreDestroy`（子类 → 父类） | 容器还在，可以协作 | 停线程、关连接 | 指望 prototype 也会走到这儿（不会，见下下节） |
| `DisposableBean.destroy()` | 同上 | 同上 | 同上 |
| `destroyMethod` | 同上 | 同上 | 同上 |

这里有个版本坑，编不过而不是警告。把 import 写成 `javax.annotation.PostConstruct`，在 JDK 25.0.4 下 `javac -encoding UTF-8` 的原文：

```text
javaxprobe\JavaxProbe.java:1: 错误: 程序包javax.annotation不存在
import javax.annotation.PostConstruct;
                       ^
javaxprobe\JavaxProbe.java:4: 错误: 找不到符号
    @PostConstruct
     ^
  符号:   类 PostConstruct
  位置: 类 JavaxProbe
2 个错误
```

classpath 上只有 `jakarta.annotation-api` 2.1.1，所以找的是 jakarta 里的那个类。`javax` → `jakarta` 的切换发生在 Jakarta EE 9，Spring Framework 6 起只认 jakarta 命名——这条是官方基线要求，不是我这台机器量出来的；我这台机器量到的是「写 javax 就编译失败」，没有运行时警告可看。

另外 `@Bean` 的 `destroyMethod` 不写时是**推断**：容器会去找一个 public 的无参 `close()`（`shutdown()` 也在候选里，这条我没单独测）。给一个只有 `close()` 的类试一下：

```text
[Holder] ctor inferred
[Holder] ctor optedOut
[Holder] ctor first
[Holder] ctor second
-- 关容器 --
[Holder] close() second
[Holder] close() first
[Holder] close() inferred
```

`inferred` 那个没写 `destroyMethod`，`close()` 被调到了；`optedOut` 上写的是 `@Bean(destroyMethod = "")`，同样有 `close()`，没有被调——显式置空就关掉推断。这也解释了为什么「明明没写销毁方法却被调了」会让人莫名其妙。

至于顺序，`second` 在 `first` 之前销毁（它是后建的，依赖 `first`）。这是当前实现的行为，Spring 文档没有把它写成保证：要靠它决定两个单例的清理先后，换版本或者换创建顺序就会变。要确定性，就自己写一个统一的清理入口。

## 初始化回调里，`this` 还不是容器最后交出去的那个对象

把上面的 `init()` 改成顺手调一行本类方法，容器再加一个 `@Around` 拦它：

```java
@PostConstruct
void init() {
    System.out.println("builder @PostConstruct #" + id + " class=" + getClass().getSimpleName());
    selfProbe();
}
```

```text
builder ctor #1
[AuditSupport] @PostConstruct（父类）
builder @PostConstruct #1 class=ReportBuilder
selfProbe() 执行，this=ReportBuilder
builder afterPropertiesSet #1
ctx.getBean 的类 = ReportBuilder$$SpringCGLIB$$0
AopUtils.isAopProxy = true
-- 从容器外面调 selfProbe()
[aspect] ReportBuilder.selfProbe()
selfProbe() 执行，this=ReportBuilder
```

回调里 `this` 是 `ReportBuilder`，容器交出去的是 `ReportBuilder$$SpringCGLIB$$0`。回调里调 `selfProbe()` 没有 `[aspect]` 行，从容器外面调同一个方法就有。原因是自动代理那条路——`AbstractAutoProxyCreator` 在 `postProcessAfterInitialization` 里把 bean 换成代理，所以换发生在回调之后。

但这不等于「初始化回调一定早于代理」。换个 BPP，在 `postProcessBeforeInitialization` 里直接返回另一个对象（这里用 `TracingReportBuilder extends ReportBuilder`）：

```text
builder ctor #1
[replaceBpp] before 阶段换成 TracingReportBuilder
builder ctor #2
[AuditSupport] @PostConstruct（父类）
builder @PostConstruct #2 class=TracingReportBuilder
builder afterPropertiesSet #2
ctx.getBean 的类 = TracingReportBuilder
```

回调全跑在 #2 上，也就是 BPP 塞进来的那个对象。准确的说法是「回调跑在 before 阶段返回的那个对象上」；「回调早于代理」只是自动代理这一条路径的结论，不是框架对所有 `BeanPostProcessor` 的约束。

这件事值得较真，因为它决定了 `@PostConstruct` 里那一行本类调用到底走不走拦截链：入口不是代理，拦截链就没进来，方法上标了 `@Transactional` 也没人读。以前我写的是「`@PostConstruct` 里调本类事务方法一定不在事务里」，这个「一定」过头了——如果创建这个 bean 的线程本身已经在事务中（比如这个 bean 是某个事务方法第一次用到它时才懒创建的），那它就在那个事务里。这一条我没有实测：本地 `spring-tx` 只有 6.2.7 与 7.0.9 两套，和探针的 6.2.11 对不上，所以只把条件写清楚，不给结论。事务那层在第 05 篇。

## 关掉容器，prototype 一个都没被收尾

回头看第一段输出的最后一行：`close 之后：@PreDestroy=0，destroy()=0`。同一个类注册成单例再关，是 `@PreDestroy=1，destroy()=1`。

容器不知道 prototype 什么时候用完——它是交给你自己拿着用的，所以销毁回调一次都不跑。这条是文档写明的契约（容器无法知道 prototype 的生命周期终点），不是某一版实现的怪癖；第一段里 `建过的 builder 个数 = 1` 和 `销毁回调 0 次` 是同一次运行里的两个计数。

谁来收尾，三条路：用完自己关（`try-with-resources`，或显式调 `close()`）；交给一个单例在它的 `@PreDestroy` 里统一关；或者干脆别让 prototype 持有需要归还的资源。第二种最容易漏——那个单例自己得先能保证在容器关闭时被调。

| 作用域 | 实例谁创建 | 容器会调销毁回调吗 | 前提 / 我测到的 |
|---|---|---|---|
| singleton（默认） | 容器，`refresh` 期间（`@Lazy` 除外） | 会，`@PreDestroy` → `destroy()` → `destroyMethod` | 是：上一节完整输出 |
| prototype | 每次解析时容器创建，之后交给你 | 不会 | 是：`@PreDestroy=0，destroy()=0` |
| request | 容器，每个请求一个 | 会，请求结束时 | 只测了非 Web 上下文里的报错，见下 |
| session | 容器，每个会话一个 | 会，会话失效时 | 未测 |
| application | 容器，每个 `ServletContext` 一个 | 会，上下文关闭时 | 未测 |
| websocket | 容器，每个 WebSocket 会话一个 | 会，会话结束时 | 未测 |

request 这一行我只验证了失败的样子——普通 `AnnotationConfigApplicationContext`（不是 Web 上下文）里取 request 作用域的 bean：

```text
java.lang.IllegalStateException
No Scope registered for scope name 'request'
```

是 `IllegalStateException` 而不是 NPE，也不是返回 null。这几个作用域依赖 Web 容器注册对应的 `Scope` 实现，没有 Web 上下文就是没注册。

顺带把「singleton 就是单例」这句话校准一下。同一个类写两个 `@Bean`、再开第二个容器：

```text
同一容器、两个定义，同一个实例吗 = false
两个容器各取一次，同一个实例吗 = false
```

singleton 的准确含义是「一个容器 + 一个 bean 定义 → 一个实例」。两个定义指向同一个类，在同一个容器里就是两个对象。

## 默认为什么是 singleton

`@Scope` 不写就是 singleton，这是容器给的默认值，不是统计出来的结论。它的合理性可以从后果反推：单例在 `refresh` 期间就被创建，依赖缺了、类型对不上，在启动阶段就抛出来（启动失败那套在第 06 篇）；代价是所有拿到它的地方共享同一份字段。

所以判断只需要问一句：这个字段的值会不会随调用方或请求变化？会，就别把它留在单例的字段里——换成方法参数、局部变量，或者 `ObjectProvider` 现取。

| 症状 | 先看哪 | 实测信号 |
|---|---|---|
| 两个请求的数据串在一起 | 存数据的那个 bean 是不是单例、字段是不是可变 | 同一个实例被两次调用改，`owners=[alice, bob]` 这样累积 |
| 后一个人的数据没了 / 第一个人的数据重复出现 | 注入点拿到的是不是同一个实例 | `建过的 builder 个数 = 1` |
| 每次调用都想要新对象，拿到的却一直是同一个 | 是不是被单例的构造器注入锁死了 | 换成 `ObjectProvider.getObject()` 后变成 `builder#1`、`builder#2` |
| 启动报 `No Scope registered for scope name 'request'` | 是不是在非 Web 上下文里用了 request / session | `IllegalStateException`，不是 NPE |
| `@PostConstruct` 里调本类带注解的方法没生效 | 这次调用是不是从代理入口进来的 | 切面/拦截器日志少一行，`begin` 计数不涨 |
| 编译报 `程序包javax.annotation不存在` | import 是不是 `javax.annotation` | 编译期错误，伴随 `找不到符号: 类 PostConstruct` |
| 关容器时资源没释放 | 这个 bean 是不是 prototype | `@PreDestroy=0，destroy()=0` |
| 没写销毁方法却被调了 `close()` | 是不是 `@Bean` 的 `destroyMethod` 推断 | 想关掉就写 `destroyMethod = ""` |

## 还差的

- **request / session / application / websocket 的销毁时机没测**。我只验证了非 Web 上下文里 request 会抛 `No Scope registered`；Web 上下文里 `@PreDestroy` 到底在请求结束还是响应提交之后跑，这篇没有数据。
- **创建期已经处在事务里的情况没测**。探针的 Spring 版本和本地 `spring-tx` 对不上，`@PostConstruct` 里的事务状态我只写了条件，没有跑出数字。
- **Boot 下的默认值没对照**。这里是纯 Spring Framework 6.2.11：`@Scope` 默认值、`destroyMethod` 推断、`@Lazy` 行为在 Boot 里是否被改过，我没有起 Boot 应用验证。
- **启动耗时一个数都没有**。单例在 `refresh` 期间创建，`@PostConstruct` 慢会拖慢启动——这是机制推断，没量。
- **多实例之间销毁顺序没当契约验证**。实测是创建的反序，但我只试了一种依赖关系，还不能说清它在不同创建顺序下如何变化。
