## 先把结论摆出来

**一个 bean 在容器里要经过四段：实例化 → 属性填充 → 初始化 → 使用与销毁。`@PostConstruct` 落在"初始化"这一段，此时依赖已经注入完，但代理可能还没套上。**

顺序大致是这样：

```text

  ↓
依赖注入（字段 / setter）
  ↓
BeanPostProcessor.postProcessBeforeInitialization
  ↓
@PostConstruct
  ↓
InitializingBean.afterPropertiesSet()
  ↓
自定义 init-method
  ↓
BeanPostProcessor.postProcessAfterInitialization  ← 代理在这一步生成
  ↓
可以使用
  ↓
@PreDestroy / DisposableBean.destroy() / destroy-method
```

记住一个位置就够：**`@PostConstruct` 在代理生成之前跑**。所以在 `@PostConstruct` 里调本类的事务方法，一定不在事务里——那时候还没有代理。

## 作用域有几种，默认为什么是 singleton

| 作用域 | 一个实例的生命周期 | 用在哪 |
| --- | --- | --- |
| `singleton`（默认） | 每个容器一个 | 无状态的服务、DAO、配置 |
| `prototype` | 每次 `getBean()` 一个新的 | 有状态的临时对象 |
| `request` | 每个 HTTP 请求一个 | Web 层，请求级上下文 |
| `session` | 每个会话一个 | 登录用户信息 |
| `application` | 每个 ServletContext 一个 | 全局缓存 |

默认 singleton 是因为**绝大多数 bean 本来就没状态**。Service、DAO、Controller 都是"拿参数、查数据、返回结果"，自己不留东西，一个实例服务所有请求最省内存。

真正需要注意的不是 singleton 本身，而是**你在 singleton 里放了可变状态**。

## singleton 什么时候会咬人

看这段代码：

```java
@Service
public class ReportService {
    private List<String> buffer = new ArrayList<>();   // 可变状态

    public void add(String line) {
        buffer.add(line);
    }

    public List<String> dump() {
        return buffer;
    }
}
```

两个用户同时调 `add`，他们的数据混进同一个 `buffer`。这不是并发 bug 那么"偶发"，而是**只要有两个请求就会串**。

三种处理方式：

1. **把状态变成方法内的局部变量**。这是首选，绝大多数情况都能改；
2. **改成 `@Scope("prototype")`**，每次拿新实例。代价是销毁不受容器管，`@PreDestroy` 不会执行；
3. **用 `ThreadLocal`**，每个线程一份。代价是线程池复用线程时数据会残留，必须在 `finally` 里清。

判断标准：**这个字段的值是否和"当前这个请求"绑定？** 是的话，它就不该是 singleton 的字段。

## `@PostConstruct` 与初始化顺序的实际影响

`@PostConstruct` 最常见的用途是"依赖注入完了，我要基于依赖做点准备"。

```java
@Service
public class CacheWarmer {
    private final ProductDao productDao;
    private Map<Long, Product> cache;

    public CacheWarmer(ProductDao productDao) {
        this.productDao = productDao;
    }

    @PostConstruct
    public void warmUp() {
        cache = productDao.findAll().stream()
                .collect(Collectors.toMap(Product::id, p -> p));
    }
}
```

这里能安全用 `productDao`，因为字段注入和构造器注入都已经完成。

几个真实的坑：

**坑一：`@PostConstruct` 里发远程调用会拖慢启动。** 它同步执行，一个 bean 卡住，整个启动就卡住。预热缓存如果数据量大，应该改成懒加载或异步。

**坑二：`@PostConstruct` 里用 `this` 调事务方法无效。** 前面说过，代理还没生成。要在这时候用事务，注入 `TransactionTemplate` 手动开。

**坑三：父类与子类的 `@PostConstruct` 顺序是先父后子**，但 `@PreDestroy` 反过来，先子后父。如果两处都操作同一个资源，销毁顺序要留意。

## `@Lazy` 解决什么问题

`@Lazy` 让 bean 在第一次被使用时才创建，而不是启动时。

它常被当成"解决循环依赖"的偏方：A 依赖 B，B 依赖 A，给其中一个加 `@Lazy`，注入进去的是一个代理，真正用到时才去拿。

```java
@Service
public class A {
    public A(@Lazy B b) { ... }   // 注入的是 B 的代理，不是 B 本身
}
```

能跑，但**这是把设计问题推到了运行期**。第一次调用才炸，比启动就炸更难排查。正确的做法是看这两个类是不是职责切错了。

`@Lazy` 真正的合理用途是**启动优化**：某些 bean 初始化很贵（连外部服务、加载大文件），但只在少数请求里用到，就标 `@Lazy` 把成本从启动挪到首次使用。

## 一个具体例子：验证初始化顺序

```java
@Component
public class OrderProbe {
    public OrderProbe() { System.out.println("1 构造器"); }

    @Autowired
    public void setDep(Object dep) { System.out.println("2 属性注入"); }

    @PostConstruct
    public void init() { System.out.println("3 PostConstruct"); }

    @PreDestroy
    public void bye() { System.out.println("5 PreDestroy"); }
}
```

再加一个 `BeanPostProcessor` 打日志，启动时会看到 `3` 在 `postProcessAfterInitialization` 之前打印。这就是"代理在 `@PostConstruct` 之后才生成"的直接证据。

## 常见误区

### 误区：`@PostConstruct` 里调本类的事务方法也会开事务

**你以为**：既然依赖都注入了，`@PostConstruct` 里调 `this.save()` 应该正常走事务。
**其实**：事务靠代理实现，而代理在 `@PostConstruct` 之后才生成。这时 `this` 是真对象，调用直接落到方法体，没有拦截器。
**怎么验证**：在 `@PostConstruct` 里调 `TransactionSynchronizationManager.isActualTransactionActive()`，返回 `false`。

### 误区：加了 `@Scope("prototype")` 就万事大吉

**你以为**：prototype 每次新实例，有状态也不怕。
**其实**：prototype bean 的**销毁不受容器管理**，`@PreDestroy` 不会执行，占用的资源（连接、文件句柄）要自己释放。另外如果它被注入到一个 singleton 里，那个 singleton 只会在自己创建时拿一次，之后一直用同一个 prototype 实例——等于退化成了 singleton。
**怎么验证**：在 prototype bean 的 `@PreDestroy` 打日志，正常关闭应用，看不到输出。

### 误区：`@Lazy` 是解决循环依赖的正规方案

**你以为**：加个 `@Lazy` 就修好了循环依赖。
**其实**：它只是把"启动时失败"换成"运行到那一行才失败"，并且注入的是代理，某些场景（比如 `equals`、序列化）行为会变。循环依赖说明两个类的边界没切干净。
**怎么验证**：在 `@Lazy` 注入的那个 bean 上加一个耗时初始化，观察应用能启动但首次调用很慢——成本只是被挪走了。

## 小结

bean 走"实例化 → 注入 → 初始化 → 使用 → 销毁"，`@PostConstruct` 在代理生成之前。默认 singleton 是因为业务 bean 通常无状态；一旦在 singleton 里放了跟请求绑定的字段，就会串数据。`@Lazy` 是推迟成本，不是解决设计问题。
