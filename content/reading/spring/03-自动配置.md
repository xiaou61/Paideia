## 783 行报告里没有我的类

我照着一份 2.x 时代的教程，在 `META-INF/spring.factories` 里登记了自动配置类：

```ini
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
probe.lib.GreeterAutoConfiguration
```

jar 塞进示例工程，`Greeter` 注入不进来。加 `--debug` 再跑，输出 783 行，从头搜到尾，`GreeterAutoConfiguration` 一次都没出现——既不在 `Positive matches`，也不在 `Negative matches`。

把同一行搬进另一个文件 `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，内容只有一行：

```text
probe.lib.GreeterAutoConfiguration
```

同一条命令，报告里多出两条：

```text
   GreeterAutoConfiguration matched:
      - @ConditionalOnClass found required class 'probe.lib.Greeter' (OnClassCondition)

   GreeterAutoConfiguration#greeter matched:
      - @ConditionalOnMissingBean (types: probe.lib.Greeter; SearchStrategy: all) did not find any beans (OnBeanCondition)
```

一条是类级判断，一条是 `@Bean` 方法级判断（`类名#方法名`）。这是我第一处猜错的地方：我以为「没生效」只有一种样子——条件不满足。实际有两种：**没进候选名单**，和**进了名单但条件没过**。报告对两者的记录方式完全不同，所以照着「条件不满足」去查，方向从一开始就错了。

下面的数字都来自同一个探针工程：JDK 25.0.4（Temurin）、Spring Boot 3.5.6、Spring Framework 6.2.11，`WebApplicationType.NONE`（不起 web），依赖用 `mvn -o dependency:copy-dependencies` 拉到 `lib/`，跑法是 `java -cp "out;lib/*" probe.app.DemoApp --debug`。对象只有一个 `Greeter` 和一个 `GreeterAutoConfiguration`，除特别说明外每次只改清单文件或启动参数。

按顺序对下来，先问「它在不在这份报告里」，再问「它被判成了什么」，最后才看条件写错没有：

| 你看到的现象 | 说明卡在哪一段 | 先去看什么 |
| --- | --- | --- |
| 报告里搜不到类名，正负 matches 都没有 | 清单 | 清单文件路径、键名、是不是还写在 `spring.factories` |
| `Negative matches` 里有 `Did not match` | 类级或方法级条件 | 它下面逐条列出的原因（缺类 / 缺属性 / 已有同类型 bean） |
| `Positive matches` 里有 `类名#方法名` | 方法级通过 | 这个 bean 确实会被创建 |
| 类在 `Unconditional classes` 里 | 条件没被算 | 见后面「组合注解」一节 |

## 类级和方法级是两条记录

上面第一段里的两条输出，正好对应两个层级。类级条件的典型输出：

```text
   FancyAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'probe.extra.FancyClient' (OnClassCondition)
```

方法级条件加一个开关型配置就看得出来：

```java
@AutoConfiguration
@ConditionalOnClass(SmsClient.class)
@ConditionalOnProperty(name = "sms.endpoint")
public class SmsAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public SmsClient smsClient(SmsProperties props) {
        return new SmsClient(props.getEndpoint());
    }
}
```

不传属性跑：

```text
   SmsAutoConfiguration:
      Did not match:
         - @ConditionalOnProperty (sms.endpoint) did not find property 'sms.endpoint' (OnPropertyCondition)
```

加 `--sms.endpoint=http://127.0.0.1:9` 再跑：

```text
   SmsAutoConfiguration matched:
      - @ConditionalOnClass found required class 'probe.lib.SmsClient' (OnClassCondition)
      - @ConditionalOnProperty (sms.endpoint) matched (OnPropertyCondition)
```

顺带一个容易看漏的细节：报告里写的是 `types: probe.lib.Greeter`，但我源码里只写了 `@ConditionalOnMissingBean`，没写 value。那个类型是从 `@Bean` 方法的返回类型推出来的——所以把方法返回类型改成接口或父类，判断的类型也跟着变。

## 方法级条件看的是「此刻已登记的定义」，按声明顺序走

这一条我一开始想反了。我以为 `@ConditionalOnMissingBean` 会在「所有 bean 定义都登记完之后」统一检查一遍，实际上它看的是**判定那一刻**容器里已经有的定义。

一个配置类里写两个 `@Bean`，返回同一个类型，都带 `@ConditionalOnMissingBean(Greeter.class)`，先声明的是 `zFirst`：

```java
@Configuration
public class OrderProbeConfig {

    @Bean
    @ConditionalOnMissingBean(Greeter.class)
    public Greeter zFirst() {
        return new Greeter("zFirst");
    }

    @Bean
    @ConditionalOnMissingBean(Greeter.class)
    public Greeter aSecond() {
        return new Greeter("aSecond");
    }
}
```

结果容器里只有一个 `Greeter`，值是 `Greeter(prefix=zFirst)`，报告里第二个方法被判否：

```text
   OrderProbeConfig#aSecond:
      Did not match:
         - @ConditionalOnMissingBean (types: probe.lib.Greeter; SearchStrategy: all) found beans of type 'probe.lib.Greeter' zFirst (OnBeanCondition)
```

注意它不是按 bean 名字排的（`aSecond` 字母序在前），是按**方法声明顺序**：先声明的先注册，后声明的判定时看见了它。跨配置类时，这个顺序由配置类的处理顺序决定，`@AutoConfiguration` 的 `after` / `before` 就是干这个用的（按官方文档；我没做「顺序写反导致抢注」的对照实验）。

## 用户定义为什么赢：一行字节码

给同一个工程加一个 `UserConfig`，里面就一个 `@Bean Greeter`：

```java
@Configuration
public class UserConfig {

    @Bean
    public Greeter greeter() {
        return new Greeter("用户定义");
    }
}
```

启动输出：

```text
[app] Greeter   = Greeter(prefix=用户定义)
[app] Greeter 的 bean 名字 = greeter
```

报告里自动配置那一条变成否：

```text
   GreeterAutoConfiguration#greeter:
      Did not match:
         - @ConditionalOnMissingBean (types: probe.lib.Greeter; SearchStrategy: all) found beans of type 'probe.lib.Greeter' greeter (OnBeanCondition)
```

机制可以落到一个类上：`javap` 看 3.5.6 的 `AutoConfigurationImportSelector`，它 `implements DeferredImportSelector`（4.1.1 的同一类也是）。`Deferred` 的意思是这个选择器在普通 `@Configuration` 处理完之后才导入——所以用户那个 `greeter` 先登记，自动配置的方法级条件才有东西可看。

但这是**实现手段**，不是框架承诺。前提是你的 bean 在处理顺序上确实更早。如果它来自另一个自动配置，或者它自己被扫描的时机更晚，这个「先看见」就不成立，得靠 `after` 排。

## 一处我以为会抛异常，实际是静默生效

`FancyClient` 不在类路径时，直接标在配置类上的 `@ConditionalOnClass(probe.extra.FancyClient.class)` 会老实跳过，这个没问题。同样的条件，我只把它挪进自己写的组合注解：

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@ConditionalOnClass(probe.extra.FancyClient.class)
public @interface ComposedOnFancy {
}
```

配在一个输出 `Greeter` 的配置类上，启动**没有任何异常**，`Greeter` 照样是 `Greeter(prefix=meta)`。报告里它落在这一段：

```text
Unconditional classes:
----------------------

    org.springframework.boot.autoconfigure.context.ConfigurationPropertiesAutoConfiguration
    ...
    probe.lib.MetaAutoConfiguration
```

条件根本没参与判断。把组合注解改成 `@ConditionalOnClass(name = "probe.extra.FancyClient")` 再跑，恢复正常：

```text
   MetaByNameAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'probe.extra.FancyClient' (OnClassCondition)
```

五种写法，只有一种会静默出错：

| 条件写在哪 | 目标类在不在类路径 | 实测结果 |
| --- | --- | --- |
| 直接标在配置类上，`X.class` | 在 | matched |
| 直接标在配置类上，`X.class` | 不在 | Did not match，配置跳过 |
| 组合注解里，`X.class` | 在 | matched |
| 组合注解里，`X.class` | 不在 | 条件消失，进 `Unconditional classes`，配置照常生效 |
| 组合注解里，`name = "…"` | 不在 | Did not match，配置跳过 |

我先前读到的解释是「组合注解里写 `X.class`，缺类会抛 `ArrayStoreException` / `TypeNotPresentException`」。3.5.6 上我没看到任何异常，看到的是条件被整个漏掉。哪个更糟不好说，但**排查方向完全不同**：按异常去查，你会等一个根本不会出现的报错；按漏判去查，你会先发现类进了 `Unconditional classes`。

这个行为属于实现细节，不是文档承诺：文档只承诺「直接标注时 `X.class` 缺类是安全的」，对组合注解只要求用 `name`。至于为什么会被漏判、元注解解析在哪一步丢掉了它，我没挖到具体代码。

## 双重注册：3.5.6 上我测不到两次

常见的提醒是「自动配置类别放在组件扫描能扫到的包里，否则会注册两次」。我把 `DupConfig` 同时登记进 `.imports`、又放在扫描范围内（`scanBasePackages` 同时扫 `probe.dup` 和 `probe.lib`），实测：

```text
[scan] new ScannedThing
[dup] new DupConfig #1 id=2013768748
[dup] DupConfig 实例数 = 1，构造函数执行次数 = 1
[dup] DupConfig 的 bean 名字 = probe.lib.DupConfig
[dup] probe 包下全部 bean 定义 = probe.lib.DupConfig,probe.lib.GreeterAutoConfiguration,greeter-probe.lib.GreeterProperties
```

同包下的普通 `@Component`（`ScannedThing`）被扫到了，说明扫描本身是生效的；而 `DupConfig` 只有一份，bean 名是**全限定名** `probe.lib.DupConfig`（清单加载给的命名），不是 `dupConfig`。

原因能指到具体类：`@SpringBootApplication` 上的 `@ComponentScan` 声明了两个排除过滤器，其一是 `AutoConfigurationExcludeFilter`（`javap -v` 能看到这个引用），它把「在 `.imports` 清单里的类」从扫描结果中排掉。所以「扫描 + 清单」两条路，在这个组合下只会走到一条。

## 写一个自动配置：三步，最容易漏的那步最安静

```java
@AutoConfiguration
@ConditionalOnClass(name = "probe.lib.Greeter")
@EnableConfigurationProperties(GreeterProperties.class)
public class GreeterAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public Greeter greeter(GreeterProperties properties) {
        return new Greeter(properties.getPrefix());
    }
}
```

```java
@ConfigurationProperties(prefix = "greeter")
public class GreeterProperties {

    private String prefix = "hello";

    public String getPrefix() {
        return prefix;
    }

    public void setPrefix(String prefix) {
        this.prefix = prefix;
    }
}
```

第三步是把类名写进清单：

```text
src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

```text
probe.lib.GreeterAutoConfiguration
```

三步里，第二步（`@ConditionalOnMissingBean`）漏了，症状是用户自己的 bean 和自动配置的 bean 同时注册、注入时报候选不唯一；第一步和第三步漏了，症状是**一模一样**的：什么都不发生，不报错、不警告，报告里连这条都没有。

`@ConditionalOnMissingBean` 标在类上和标在方法上不一样：标在方法上只针对这一个 bean，标在类上等于给这个类里所有 `@Bean` 方法都加了一遍。上面这个例子里标在方法上是故意的，因为属性类不需要这个条件。

## 还差的

- **Boot 4.x 只读了 jar，没实跑。** 4.1.1 的 `spring-boot-autoconfigure` 里 `.imports` 只剩 12 条（3.5.6 是 156 条），`spring-boot-jdbc` / `spring-boot-webmvc` / `spring-boot-flyway` 这些新模块各自带清单，所以类名和排序在新版本里会变。本地缺 7 系的 `spring-jcl`，离线起不了 Boot 4 应用，条件报告在 4.x 下的行为我没测。
- **组合注解漏判的成因没定位。** 我只观察到结果（类进 `Unconditional classes`），没查到是元注解解析的哪一步丢掉了条件；Boot 2.x 时代是否真的抛 `ArrayStoreException`，我也没跑旧版本。
- **`after` / `before` 只按文档写。** 没做「两个自动配置互相依赖、顺序写反导致抢注」的对照实验，所以那一节的顺序敏感性是文档结论，不是我的测量。
- **双重注册只测了一种组合。** 类标了 `@Configuration`、在默认扫描范围内、清单也登记了——这个组合只注册一次。类加载器隔离、类没标 `@Configuration`、清单根本没读到这几种情况下排除过滤器还奏不奏效，没验。
- **只用过 `--debug`。** `/actuator/conditions` 与它是同一份报告吗？两者字段是否逐条对应？Actuator 我没起（探针工程是 `WebApplicationType.NONE`），不敢说等价。
