## 先把结论摆出来

**自动配置 = 一份候选清单 + 一堆条件注解。没有魔法。**

你加 `spring-boot-starter-web`，Spring Boot 启动时会去读所有 jar 包里登记的"候选配置类"清单，逐个检查每个配置类的条件是否满足。满足了就把里面的 bean 定义注册进容器，不满足就跳过。

所以"加个依赖就自动配好了"这句话，拆开是三步：

1. **依赖带进来一批候选配置类**（清单写在 jar 里）；
2. **每个配置类上都写着"什么时候我才生效"**（`@ConditionalOnClass` 之类）；
3. **你自己的 bean 优先**（`@ConditionalOnMissingBean`）。

## 候选清单放在哪

早期（Spring Boot 1.x / 2.x）放在 `META-INF/spring.factories`：

```text
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.example.FooAutoConfiguration,\
com.example.BarAutoConfiguration
```

从 Spring Boot 2.7 起引入新位置，3.0 起**只认新位置**：

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

内容是每行一个类名，没有 key：

```text
com.example.FooAutoConfiguration
com.example.BarAutoConfiguration
```

你在网上看到的"自定义 starter 要写 spring.factories"，大多是 3.0 之前的资料。现在写 `spring.factories` 不会被自动配置机制读到（其他扩展点仍在用它，但自动配置不用了）。

清单只是**候选**，不是"这些都会生效"。决定生效与否的是条件注解。

## 条件注解在干什么

每个自动配置类都挂着一串 `@Conditional...`，本质是一组 if：

```java
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public DataSource dataSource(DataSourceProperties props) {
        return DataSourceBuilder.create()
                .url(props.getUrl())
                .username(props.getUsername())
                .build();
    }
}
```

逐条读：

- `@ConditionalOnClass(DataSource.class)`：类路径上有 `javax.sql.DataSource` 才继续。加 `spring-boot-starter-jdbc` 才有，只加 `spring-boot-starter-web` 就没有，所以 web 项目不会莫名创建一个数据源；
- `@ConditionalOnMissingBean(DataSource.class)`：容器里还没有 `DataSource` 才创建。**这一条是你覆盖默认行为的入口**；
- `@EnableConfigurationProperties`：把 `spring.datasource.*` 绑到 `DataSourceProperties` 上。

常见的条件注解：`@ConditionalOnClass`（类路径上有指定类）、`@ConditionalOnMissingClass`、`@ConditionalOnBean`（容器里已有指定 bean）、`@ConditionalOnMissingBean`、`@ConditionalOnProperty`（配置项等于某值）、`@ConditionalOnWebApplication`、`@ConditionalOnResource`。

`@ConditionalOnProperty` 是最常用的开关：

```java
@AutoConfiguration
@ConditionalOnProperty(name = "feature.sms.enabled", havingValue = "true")
public class SmsAutoConfiguration { ... }
```

没配 `feature.sms.enabled=true`，整个配置类不生效。这比在代码里写 `if (enabled)` 干净——bean 根本不会被创建。

## 为什么"我定义的 bean 会赢"

因为几乎所有自动配置的 `@Bean` 方法都带 `@ConditionalOnMissingBean`。

这是 Spring Boot 的一条设计约定：**自动配置只做兜底，用户定义永远优先。**

所以覆盖一个自动配置的 bean，不需要排除自动配置类，只要自己定义一个同类型的：

```java
@Configuration
public class MyConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
                .configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
    }
}
```

`JacksonAutoConfiguration` 里那个带 `@ConditionalOnMissingBean` 的 `ObjectMapper` 就不会创建了。这条规则依赖执行顺序——**用户配置先处理，自动配置后处理**，顺序反了就不成立。Spring Boot 用 `@AutoConfiguration` 的排序保证，你不用操心，但要知道它靠的是顺序。

## 怎么看清到底哪些生效了

三种办法，从粗到细：

**第一种，启动加 `--debug`：**

```bash
java -jar app.jar --debug
```

控制台打印 `ConditionEvaluationReport`，分 `Positive matches`（生效）与 `Negative matches`（未生效），每条带原因，比如"did not find expected property 'feature.sms.enabled'"。

**第二种，Actuator 的 `/actuator/conditions`：**

```bash
curl localhost:8080/actuator/conditions
```

同样的报告，JSON 格式，方便对比两次启动的差异。**第三种**是 `/actuator/beans`，看容器里到底有哪些 bean、来自哪个配置类。

排查"为什么我的配置没生效"，先跑 `--debug` 看 `Negative matches` 里有没有你要的那个类，原因通常写得很直白。

## 写一个自己的自动配置

三步，不需要注册中心：

**第一步，写配置类：**

```java
@AutoConfiguration
@ConditionalOnClass(SmsClient.class)
@ConditionalOnProperty(name = "sms.endpoint")
@EnableConfigurationProperties(SmsProperties.class)
public class SmsAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public SmsClient smsClient(SmsProperties props) {
        return new SmsClient(props.getEndpoint(), props.getToken());
    }
}
```

**第二步，登记到清单**：在 `src/main/resources/META-INF/spring/` 下新建 `org.springframework.boot.autoconfigure.AutoConfiguration.imports`，一行写上 `com.example.sms.SmsAutoConfiguration`。

**第三步，让配置项有提示**（可选）：加 `spring-boot-configuration-processor` 依赖，IDE 里写 `sms.` 会有补全。

这样别人引入你的 jar，只要配了 `sms.endpoint`，`SmsClient` 就有了。

## 常见误区

### 误区：自动配置是"Spring Boot 帮你写好的一份配置"

**你以为**：`spring-boot-autoconfigure` 里是一堆 yml 模板，按需拼起来。
**其实**：它是一批**Java 配置类**，每个都带条件注解。生效的不是配置文本，而是这些类里 `@Bean` 方法注册的对象。
**怎么验证**：`--debug` 启动后看 `Positive matches`，列出的全是 `XxxAutoConfiguration` 类名，不是配置文件。
### 误区：自定义 starter 还要写 `spring.factories`

**你以为**：网上教程都写 `spring.factories`，照抄就行。
**其实**：那是 Spring Boot 2.x 的做法。3.0 起自动配置只读 `AutoConfiguration.imports`，写在 `spring.factories` 里的类不会被自动配置机制加载，而且不报错——你会以为写了但就是不生效。
**怎么验证**：在 `spring.factories` 里登记一个配置类，`--debug` 看它的类名是否出现在报告里；再换到 `AutoConfiguration.imports` 对比。

### 误区：自动配置类总是先于我的配置执行

**你以为**：既然是"自动"，那应该是容器初始化时才补进来。
**其实**：自动配置类在用户配置**之后**处理，否则 `@ConditionalOnMissingBean` 无从判断；这个顺序由 `@AutoConfiguration` 的排序保证。
**怎么验证**：在自定义 `@Configuration` 和自动配置类里各打一行启动日志，看打印先后。

## 小结

自动配置是"候选清单 + 条件注解"：jar 里登记配置类，启动时逐个判断条件，满足就注册 bean。用户定义永远优先，因为自动配置的 bean 都带 `@ConditionalOnMissingBean`。看清发生了什么，`--debug` 比读源码快。
