## 两个 `@Service` 都叫 `UserService`，日志里没有 `APPLICATION FAILED TO START`

我在临时工程里放了两个包：`lab.s4.invoice.UserService` 和 `lab.s4.audit.UserService`，两个类都只有一行 `@Service`，启动类在 `lab.s4`。按我之前的印象，启动失败会有一段 `APPLICATION FAILED TO START`，底下分 `Description` 和 `Action`，照着改就行。实际控制台最后一段是：

```text
2026-11-19T16:33:12.790+08:00  WARN 137056 --- [           main] s.c.a.AnnotationConfigApplicationContext : Exception encountered during context initialization - cancelling refresh attempt: org.springframework.beans.factory.BeanDefinitionStoreException: Failed to parse configuration class [lab.s4.App]
2026-11-19T16:33:12.834+08:00 ERROR 137056 --- [           main] o.s.boot.SpringApplication               : Application run failed

org.springframework.beans.factory.BeanDefinitionStoreException: Failed to parse configuration class [lab.s4.App]
	at org.springframework.context.annotation.ConfigurationClassParser.parse(ConfigurationClassParser.java:194) ~[spring-context-6.2.11.jar:6.2.11]
	at org.springframework.context.annotation.ConfigurationClassPostProcessor.processConfigBeanDefinitions(ConfigurationClassPostProcessor.java:418) ~[spring-context-6.2.11.jar:6.2.11]
	at org.springframework.context.support.AbstractApplicationContext.refresh(AbstractApplicationContext.java:609) ~[spring-context-6.2.11.jar:6.2.11]
	at org.springframework.boot.SpringApplication.run(SpringApplication.java:318) ~[spring-boot-3.5.6.jar:3.5.6]
	... 12 common frames omitted
Caused by: org.springframework.context.annotation.ConflictingBeanDefinitionException: Annotation-specified bean name 'userService' for bean class [lab.s4.invoice.UserService] conflicts with existing, non-compatible bean definition of same name and class [lab.s4.audit.UserService]
	at org.springframework.context.annotation.ClassPathBeanDefinitionScanner.checkCandidate(ClassPathBeanDefinitionScanner.java:361) ~[spring-context-6.2.11.jar:6.2.11]
	at org.springframework.context.annotation.ComponentScanAnnotationParser.parse(ComponentScanAnnotationParser.java:128) ~[spring-context-6.2.11.jar:6.2.11]
```

没有 `Description`，没有 `Action`。我往上翻了两屏才确认：失败不在造对象的时候，而在扫包登记定义的时候。`ClassPathBeanDefinitionScanner.checkCandidate` 按 bean 名判重，两个类的默认 bean 名都是 `userService`，于是直接抛 `ConflictingBeanDefinitionException`。Spring Boot 的失败分析器按异常类型匹配，这条异常没有对应的分析器，所以不生成报告，只把原始堆栈打在 `Application run failed` 后面。

这改变了我排查的第一动作：先看失败停在哪一层，再决定要不要去找那段报告。

下面的日志都来自同一台机器：Spring Boot 3.5.6、Spring Framework 6.2.11、Temurin 25.0.4、Maven 3.9.0，Windows。几种失败放在同一个临时工程的几个包里（`lab.s1` 到 `lab.s8`），每个包一个 `@SpringBootApplication`，逐个启动。这样比在一个项目里连续改四次省事，业务对象一直是同一个 `ReportJob`。

## 同一句「找不到」，两种完全不同的工程状态

`lab.s1` 的 `ReportSink` 只有一个接口，没有任何实现，连 `@Component` 都没有。它的报告是：

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in lab.s1.ReportJob required a bean of type 'lab.s1.ReportSink' that could not be found.


Action:

Consider defining a bean of type 'lab.s1.ReportSink' in your configuration.
```

然后我在 `lab.s2.other` 里加了 `CsvSink implements ReportSink`，带了 `@Component`，启动类放在 `lab.s2.app`。输出除了包名从 `lab.s1` 换成 `lab.s2.app`，一个字没变。原因是 `@SpringBootApplication` 的扫描根是它自己所在的包，`lab.s2.other` 是兄弟包，不在 `lab.s2.app` 下面。

同一个「找不到」，实际是两种状态：

- 真的没有实现类，或实现类漏了 `@Service` / `@Repository` / `@Component`；
- 有实现类，也在某个包里，但那个包不在启动类的扫描子树里。

报错文本不区分这两件事，也不区分「第三方库的类没有注解」。所以对着 `Description` 只能得到「缺一个类型」，接下来要自己排：

1. 这个类型有没有具体实现，实现类上有没有构造型注解；
2. 实现类所在包是不是启动类所在包或它的子包；
3. 是不是第三方类，那得自己写 `@Bean` 方法；
4. 实现类上有没有条件注解，被条件挡掉了（条件装配是第 03 课的内容）。

第 2 条是最容易自己骗自己的：代码里明明有 `@Service`，编译也过了，只是不在这棵树里。

## 一个接口两个实现：候选数是算出来的

`lab.s3` 里 `CsvSink` 和 `PdfSink` 都实现了 `ReportSink`，`ReportJob` 的构造器要一个 `ReportSink`：

```text
Description:

Parameter 0 of constructor in lab.s3.ReportJob required a single bean, but 2 were found:
	- csvSink: defined in file [...\target\classes\lab\s3\CsvSink.class]
	- pdfSink: defined in file [...\target\classes\lab\s3\PdfSink.class]

This may be due to missing parameter name information

Action:

Consider marking one of the beans as @Primary, updating the consumer to accept multiple beans, or using @Qualifier to identify the bean that should be consumed
```

注意 `Description` 第一行的措辞和上一节不同：上一节是 `expected at least 1`，这一节是 `expected single matching bean but found 2`。前者是「一个都没有」，后者是「有好几个」，两句不能当同义句读。

`This may be due to missing parameter name information` 这句我一开始当真了，按 Action 末尾的提示在 pom 里加了 `<maven.compiler.parameters>true</maven.compiler.parameters>` 重新编译。结果那句还在，候选还是 `csvSink,pdfSink` 两个，只是 Action 末尾那几行 `Ensure that your compiler is configured to use the '-parameters' flag` 消失了。原因不复杂：两个候选是按类型匹配出来的两个实现，跟参数名叫什么没关系。真正能解的是 Action 前半句，三选一：`@Primary` 设默认、注入点写 `@Qualifier`、把消费方改成收 `List<ReportSink>`。

## 环：Action 那句建议救不了构造器环

环也分两种，处理方式不一样，但报告长得很像。先看字段注入的环：`ReportJob` 和 `AuditLog` 互相 `@Autowired` 对方的字段。默认配置下两个构造器都打印了，然后才失败：

```text
[ctor] AuditLog
[ctor] ReportJob
2026-11-19T16:33:23.246+08:00  WARN 150748 --- [           main] s.c.a.AnnotationConfigApplicationContext : Exception encountered during context initialization - cancelling refresh attempt: org.springframework.beans.factory.UnsatisfiedDependencyException: Error creating bean with name 'auditLog': Unsatisfied dependency expressed through field 'reportJob': ...
```

对象已经造出来了，是在填字段时发现谁都在等对方。同一个包加上 `--spring.main.allow-circular-references=true`，启动成功。

把注入改成构造器参数，同样的两个类，Action 还是建议打开那个开关：

```text
Action:

Relying upon circular references is discouraged and they are prohibited by default. Update your application to remove the dependency cycle between beans. As a last resort, it may be possible to break the cycle automatically by setting spring.main.allow-circular-references to true.
```

我照做了，结果是：

```text
... Requested bean is currently in creation: Is there an unresolvable circular reference or an asynchronous initialization dependency?

Action:

Despite circular references being allowed, the dependency cycle between beans could not be broken. Update your application to remove the dependency cycle.
```

开关确实打开了，文案从 `prohibited by default` 变成了 `Despite circular references being allowed`，失败没变。构造器必须先拿到参数才能 `new`，没有「半成品」可以提前暴露；`allow-circular-references` 救的是字段和 setter 环，构造器环它救不了。Action 段在这里给了一个做不到的建议。

另一种补法是把其中一端的构造器参数标 `@Lazy`。启动能过，注入进来的是代理：

```text
[ctor] ReportJob, auditLog ... lab.s5lazy.AuditLog$$SpringCGLIB$$0
[ctor] AuditLog
```

它把「启动时解析」推到「第一次调用」，失败从启动挪到了运行期。所以处理顺序是：拆类、用事件解耦、`@Lazy`，最后才是那个只对字段环有效的开关。三级缓存为什么能解字段环、解不了构造器环，第 08 课再展开。

## 端口占用：业务单例都造完了才失败

正常启动时，日志顺序是这样的（只留关键行）：

```text
... o.s.b.w.embedded.tomcat.TomcatWebServer  : Tomcat initialized with port 0 (http)
... w.s.c.ServletWebServerApplicationContext : Root WebApplicationContext: initialization completed in 1712 ms
[ctor] ConstructorProbe
... o.s.b.w.embedded.tomcat.TomcatWebServer  : Tomcat started on port 18867 (http) with context path '/'
... lab.s7.ok.App                            : Started App in 3.319 seconds (process running for 3.825)
```

`Tomcat initialized` 在前，业务单例的 `[ctor]` 在中间，`Tomcat started on port 18867` 在最后。前面的初始化只是把 connector 配好，端口号 0 表示让系统挑，真正绑上去是收尾阶段。

把 18080 先占住，再让应用启动到同一个端口：

```text
... Tomcat initialized with port 18080 (http)
... Root WebApplicationContext: initialization completed in 1401 ms
[ctor] ConstructorProbe
... WARN ... ConfigServletWebServerApplicationContext : Exception encountered during context initialization - cancelling refresh attempt: org.springframework.context.ApplicationContextException: Failed to start bean 'webServerStartStop'

APPLICATION FAILED TO START

Description:

Web server failed to start. Port 18080 was already in use.

Action:

Identify and stop the process that's listening on port 18080 or configure this application to listen on another port.
```

`[ctor]` 已经打出来了，说明单例全造完了才轮到绑端口。这类失败和依赖注入无关，报错里也不会出现任何 bean 名；先看 `Description` 里的 `Port`，不要一头扎进 `@ComponentScan`。

## 环境阶段：同一个 `server.port` 写在四个地方

环境阶段一般不失败，但它决定后面每一层看到什么值。我把 `server.port` 分别写在四个地方，每次只改一个层，端口从启动日志里读：

| 写在哪儿 | 启动日志里的 `Tomcat started on port` |
| --- | --- |
| `src/main/resources/application.yml` | `18081` |
| 再加 `application-prod.yml`，并 `--spring.profiles.active=prod` | `18084` |
| 上面基础上加环境变量 `SERVER_PORT=18082` | `18082` |
| 上面基础上再加命令行 `--server.port=18083` | `18083` |

四行合起来是一件事：命令行 > 环境变量 > 配置文件，profile 文件覆盖同名默认键。注意 `SERVER_PORT` 是环境变量名的形式（点换下划线、转大写），不是 Spring 在读 `server.port` 这个字符串。

完整优先级表在官方文档的 Externalized Configuration 里，还有系统属性、`SPRING_APPLICATION_JSON`、jar 外 `config/` 目录这些层。上面四层是我在这台机器上量的，其余层没量。

## 症状 → 先看哪

| 日志里先出现的字符串 | 先查什么 | 为什么是这条 |
| --- | --- | --- |
| `ConflictingBeanDefinitionException: ... bean name 'userService' ... conflicts with ...` | 两个类的简单名是否相同；给其中一个显式命名（`@Service("invoiceUserService")`）或收窄扫描范围 | 冲突在扫包时按 bean 名判，发生在定义阶段；`allow-bean-definition-overriding=true` 也救不了（我加过，同一条异常照旧） |
| `required a bean of type 'X' that could not be found` | ① 有没有实现和构造型注解 ② 实现类包在不在启动类子树 ③ 第三方类是否漏了 `@Bean` ④ 条件注解是否挡掉 | 同一条文本至少覆盖「没实现」和「实现了没扫到」两种情况，文本不区分 |
| `required a single bean, but 2 were found` | 候选是不是同一接口的两个实现；`@Primary` / `@Qualifier` / `List<T>` | 按类型注入要求候选唯一；`-parameters` 提示可能不是你的原因 |
| `... form a cycle ...` 或 `Requested bean is currently in creation` | 注入方式是构造器还是字段/setter；构造器环只能拆或 `@Lazy` | `allow-circular-references` 只对能提前暴露半成品的字段/setter 环有效 |
| `Failed to start bean 'webServerStartStop'` + `Port ... was already in use` | 端口占用；换端口或停掉占用进程 | 收尾阶段才绑端口，此时业务单例已经造完，与依赖注入无关 |

## 动手

1. 在你的工程里临时造两个同简单名的 `@Service`，启动一次，确认输出里没有 `APPLICATION FAILED TO START`；然后把其中一个改成 `@Service("invoiceUserService")`，再启动，看失败是不是换到了下一层（缺 bean、参数名、或另一个环）。
2. 造一个构造器环，加 `--spring.main.allow-circular-references=true`，对比两次的 Action 段：从 `may be possible to break the cycle automatically` 变成 `Despite circular references being allowed`，两次都启动失败。再把其中一端的参数改成 `@Lazy`，看注入进去的类名带 `$$SpringCGLIB$$`。

## 还差的

- 只在 Spring Boot 3.5.6 / Framework 6.2.11 / Temurin 25.0.4 / Windows 上跑过。本机 m2 里有 Boot 4.1.1，但本文的日志、默认值和 Action 文案都没在 4.x 上重跑，Boot 4 的失败分析器措辞可能不同。
- 只测了三种失败类型：同名 bean、缺 bean/候选不唯一、环。没测 `allow-bean-definition-overriding=true` 对「两个 `@Bean` 方法同名」的效果（本文只证明它救不了两个同名 `@Service`），也没测条件装配（`@ConditionalOnProperty` 缺配置项、`@ConditionalOnClass`）导致的「找不到 bean」。
- 配置优先级只量了四层（jar 内默认、profile 文件、环境变量、命令行）；系统属性、`SPRING_APPLICATION_JSON`、外置 `config/` 目录、`@TestPropertySource` 都没量。
- 没测 `@Lazy` 用在带 `@Transactional` 或其他 AOP 代理的环上会怎样。本文那个代理只是普通的 CGLIB 子类，没验证过被代理的方法调用是否符合预期。
- 我手里没有一批真实项目的失败样本，所以不给「各阶段失败占比」这类数字；本文只有可复现的三种阶段和几条日志。
