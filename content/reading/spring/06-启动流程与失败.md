## 先把结论摆出来

**Spring Boot 的启动就是一句话：准备好环境，创建容器，把 bean 定义全都注册进去，然后一次性实例化所有非懒加载的单例。**

`SpringApplication.run()` 按顺序做五件事：**准备环境**（读命令行、环境变量、配置文件，拼成有序属性源）→ **创建容器** → **加载 bean 定义**（扫包、读 `@Configuration`、读自动配置清单）→ **刷新容器**（实例化单例、生成代理、启动内嵌 Tomcat）→ **回调**（`ApplicationRunner` / `CommandLineRunner`）。

**启动失败几乎都发生在第四步**，因为那一步才真正去"造对象"，依赖找不到、有环、有冲突全在这时候炸。

## 第四步为什么最脆弱

因为 bean 定义阶段只是"登记说明书"，不校验可行性。就像餐厅先收了一堆点单，到厨房真正开火才发现某道菜的原料没了。

`refresh()` 里最关键的是 `finishBeanFactoryInitialization`：遍历所有非懒加载的 singleton 定义逐个创建，任何一个失败，整个启动就中止。报错长这样：

```text
APPLICATION FAILED TO START

Description:

Parameter 0 of constructor in com.example.OrderService required a bean of type
'com.example.UserDao' that could not be found.
```

**这个报告是 Spring Boot 帮你总结的**，比底层堆栈好读。往上翻还有 `Action:` 段，常直接告诉你该怎么改。

## 失败一：bean 找不到

最常见的一句：`required a bean of type 'X' that could not be found`。按这个顺序查：

1. **类上加注解了吗**？`@Service`、`@Repository`、`@Component` 三选一，或者有 `@Bean` 方法；
2. **包在扫描范围内吗**？`@SpringBootApplication` 默认只扫它自己所在的包及其子包。启动类在 `com.example`，`com.other.Foo` 就扫不到；
3. **是不是第三方库的类**？那不会有 `@Component`，得自己写 `@Bean` 方法；
4. **是不是条件注解把它挡了**？比如某个自动配置因为缺配置项没生效。

第 2 条踩得最多。项目拆模块后启动类跑到子模块里，另一个模块的 `@Service` 静默不被扫描——不报错，只在注入时报"找不到"。

## 失败二：bean 冲突

```text
Parameter 0 of constructor in com.example.OrderService required a single bean,
but 2 were found:
  - alipayChannel: defined in file [...]
  - wechatChannel: defined in file [...]
```

含义是"我要一个，你给我两个"。三种处理：`@Primary` 设默认、`@Qualifier` 指定名字、改成注入 `List` 或 `Map`。

还有一种更隐蔽的：**同名 bean 被定义两次**，报 `A bean with that name has already been defined and overriding is disabled`。Spring Boot 2.1 起**默认禁止 bean 覆盖**（`spring.main.allow-bean-definition-overriding=false`），两个 `@Service` 都叫 `OrderService`（哪怕在不同包）会直接失败。**不建议打开这个开关**：能启动，但哪个生效取决于加载顺序，属于"能跑但结果不确定"。改类名或显式指定 bean 名字才是解法。

## 失败三：循环依赖

```text
The dependencies of some of the beans in the application context form a cycle:

   orderService
      ↓
   userService
      ↑
```

Spring Boot 2.6 起**默认禁止循环引用**；构造器注入的循环依赖在任何版本都会失败。三种处理，按推荐度排：**拆类**（互相依赖通常说明有个共同职责该单独拎出来）、**用事件解耦**（`ApplicationEventPublisher` 加 `@EventListener`）、**`@Lazy`** 打补丁（能跑，但把失败从启动推到了运行期）。

打开 `allow-circular-references=true` 是最后手段：它靠提前暴露半成品对象实现，那些对象在别处被用到时可能还没初始化完。

## 配置从哪来：优先级

同一项配置在多个地方都有值时，**越靠后越优先**：

| 优先级 | 来源 |
| --- | --- |
| 低 | `application.properties` / `application.yml`（jar 内） |
| ↓ | `application-{profile}.yml`（jar 内） |
| ↓ | `application.yml`（jar 外，与 jar 同目录或 `config/` 下） |
| ↓ | `application-{profile}.yml`（jar 外） |
| ↓ | 操作系统环境变量 |
| ↓ | 命令行参数 `--server.port=9090` |
| 高 | `@SpringBootTest(properties=...)` |

两条推论：**profile 文件覆盖默认文件**，不管在 jar 内还是 jar 外；**环境变量和命令行参数赢过所有配置文件**，部署到容器里改配置用环境变量最省事，不用重新打包。环境变量名要转换：`server.port` 对应 `SERVER_PORT`（点换下划线、转大写）。

## Profile 怎么用

Profile（配置档）是"同一份代码在不同环境用不同配置"的机制，文件名里带 profile 后缀就算：`application-dev.yml`、`application-prod.yml`。

切换方式（优先级从低到高）：`spring.profiles.active` 写在 yml 里 → 环境变量 `SPRING_PROFILES_ACTIVE` → 命令行 `--spring.profiles.active=prod`。代码里也能给配置类加 `@Profile("dev")`，让它在别的环境不存在。

**一条纪律：不要用 `@Profile` 表达"环境差异"以外的东西。** 用它开关功能（比如"这个租户要不要开短信"）会让配置越来越难推理，那种开关应该用 `@ConditionalOnProperty`。

## 一个排查启动问题的固定动作

启动失败时按这个顺序做：**读 `APPLICATION FAILED TO START` 下面的 Description 和 Action → bean 找不到就查扫描包路径 → bean 冲突就加 `@Primary` / `@Qualifier` 或改类名 → 循环依赖就拆类或用事件 → 还不明白就加 `--debug` 看条件评估报告。** 第一步能解决八成问题，因为失败分析器就是专门写来翻译这些常见错误的。

## 常见误区

### 误区：启动类放哪都行，反正会扫全项目

**你以为**：`@SpringBootApplication` 会扫描整个 classpath。
**其实**：它只扫**启动类所在包及其子包**。启动类在 `com.example.app`，`com.example.other` 里的 `@Service` 就扫不到，而且不报错——直到有地方注入它时才失败。
**怎么验证**：把启动类往上挪一层包，或者加 `@ComponentScan("com.example")` 显式扩大范围，观察原本"找不到"的 bean 是否出现。

### 误区：打开 `allow-bean-definition-overriding` 就能解决 bean 冲突

**你以为**：允许覆盖，后定义的赢，问题就没了。
**其实**：谁"后"取决于加载顺序，而这个顺序受扫描顺序、配置类排序影响，不稳定。同一个包在不同机器上可能表现不同。
**怎么验证**：在两个同名 bean 里各打一行构造器日志，多次启动观察哪一行出现——不固定就说明不能依赖这个行为。

### 误区：`@Profile` 就是"按环境切换配置"的开关，可以随便用

**你以为**：任何"要不要启用"的判断都可以用 `@Profile`。
**其实**：`@Profile` 表达的是"当前是哪个环境"，而环境是部署时决定的。用它表达功能开关，会让"这个 bean 为什么不存在"变成要同时看环境变量和代码的推理题。
**怎么验证**：翻一遍项目里的 `@Profile`，看有没有哪个其实是功能开关（比如 `@Profile("sms")`）——那些应该换成 `@ConditionalOnProperty`。

## 小结

启动是"准备环境 → 建容器 → 登记 bean 定义 → 一次性实例化 → 跑 Runner"，失败几乎都在实例化那一步。三类高频失败：bean 找不到（先查扫描包）、bean 冲突（`@Primary` / `@Qualifier` / 改类名）、循环依赖（拆类或用事件）。配置优先级记一条：命令行 > 环境变量 > 外部配置文件 > jar 内配置文件。

读完这六篇，回自己项目做两件事：随便挑一个 `@Service` 打一行 `this.getClass()`，再找出一个自调用的地方。这两个动作覆盖这条线一半的实际价值。
