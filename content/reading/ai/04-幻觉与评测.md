## 12 条题全过，其中 8 条是错的

我搭了一个内部文档问答的玩具版本（语料就是这个仓库的规则文档，没有接真实产品），给它写了 12 条题，答案都能在文档里查到。第一版判定就是这一行：

```python
answer = "e2e 的耗时几乎全在固定启动上：全量 61 条、2 分 36 秒，每条边际成本约 2.4 秒。"
subject = ["e2e"]                                   # 问题的主语
print(any(s in answer.lower() for s in subject))    # True
```

12 条，全过。

然后我把同一批回答按「说出口的每条判断站不站得住」重新打了一遍，有 8 条的 F1 不到 0.5：

```text
12 条样本，两种判定
关键词判定（主语在不在）：12/12 通过
其中 claimF1 < 0.5 的：8 条  Q2, Q3, Q10, Q7, Q12, Q4, Q6, Q8
```

同一批回答，两个判定给出相反的结论。差别不在样本，在**判的是什么**：关键词判的是「有没有在说这件事」，而问题问的是「那个槽填了没有」。

我把这 12 条按「回答是怎么坏掉的」分成四类，每类 3 条跑分。下面的 P、R、F1 都是脚本真跑出来的（Python 3.11.5、本机、12 条样本）：

```text

Q5  A      1.00    1.00     1.00          通过
Q9  A      1.00    1.00     1.00          通过
Q11 A      1.00    1.00     1.00          通过
Q2  B      1.00    0.00     0.00          通过
Q3  B      1.00    0.00     0.00          通过
Q10 B      1.00    0.00     0.00          通过
Q1  C      0.75    0.50     0.60          通过
Q7  C      0.67    0.00     0.00          通过

Q4  D      0.33    0.00     0.00          通过
Q6  D      0.00    0.00     0.00          通过
```

A 是答对，B 是每句都真但没回答被问的那个槽，C 是框架对、被问的那个值是错的，D 是给了具体数字但没依据。

## 一个字都没说错，F1 是 0

B 类里那条问「e2e 只跑一个文件大概多久」的，回答原文是：

```text
e2e 的耗时几乎全在固定启动上：全量 61 条、2 分 36 秒，每条边际成本约 2.4 秒，
固定启动约 20 秒。所以改哪端就跑哪端的文件，别默认全量。
```

三个数字都对（`AGENTS.md:21` 写的就是全量 61 条 / 2 分 36 秒、单条约 2.4 秒、固定启动约 20 秒），语气也对，结论也实用。但它从头到尾没回答「只跑一个文件要多久」——那个区间是 13–54 秒，就在同一行写着。

这条的分数是 P 1.00 / R 0.00 / F1 0.00。**P 满分是因为它一句谎都没说；F1 是 0 是因为它答的是另一个问题。**

这就是我想扭转的一件事：聊「幻觉」时容易只想着「它编了个不存在的 API」。但真用起来更难抓的是这种——回答里每个事实都能在文档里找到，用户读完还觉得挺专业，然后拿它给的数去估时间：估出来 2 分 36 秒，而真实的单文件是 13–54 秒。它不谎报，它跑题。

## 把「对」拆成两个数

所以判定得拆成两问，各自可数：

- **忠实度 P** = 说出口的 claim 里，站得住的占多少。分母是回答自己的 claim 数，所以编得越多、P 越低。
- **覆盖度 R** = 这道题必须填的槽里，被正确填上的占多少。分母是题目的槽数，跟回答长短无关。

F1 = 2PR/(P+R)，P+R 为 0 时记 0。这三行就是全部实现：

```python
def score(item):
    claims = item["claims"]
    prec = sum(1 for c in claims if c["truth"]) / len(claims)   # 忠实度
    hits = 0
    for slot, want in item["slots"].items():
        if any(c["truth"] and c["slot"] == slot and norm(c["value"]) == norm(want)
               for c in claims):
            hits += 1
    rec = hits / len(item["slots"])                              # 覆盖度
    f1 = 0.0 if prec + rec == 0 else 2 * prec * rec / (prec + rec)
    return prec, rec, f1
```

`norm()` 只是去空白 + 转小写。每道题的 `slots` 是「必须填的槽及其正确值」，每条 claim 的 `truth` 是「这条判断站不站得住」。

这里有个口径问题得说清：**truth 是按这个仓库的规则文档判的，不是按上游工具手册判的。** C 类那条回答把迁移文件写成 `V25__add_index.sql`，我判它错——因为 `AGENTS.md:36` 明写「不要用 `V25__` 这种递增号，用 14 位时间戳」，`MigrationVersionFormatTest` 会把纯数字版本号变成构建失败。但 Flyway 自己的默认命名规则允许版本号写 25（按文档）。工具允许、这个仓库不允许，两件事。判 truth 时不区分这层，就会把「不符合项目约定」算成「模型幻觉」，或者反过来把「违反上游规范」当成合格。

## 三种病，一个分数分不开

把 12 条按类宏平均：

| 类 | P 均值 | R 均值 | F1 均值 | 病在哪 | 该动什么 |
| --- | --- | --- | --- | --- | --- |
| A 答对 | 1.00 | 1.00 | 1.00 | — | 别动 |
| B 跑题 | 1.00 | 0.00 | 0.00 | 事实都对，就是没答被问的槽 | 改问法/提示词，把槽写进约束 |
| C 细节错 | 0.64 | 0.17 | 0.20 | 框架对，关键值错 | 加依据、核对那个值 |
| D 编数 | 0.28 | 0.00 | 0.00 | 具体数字没出处且不对 | 让它去查，别让它记 |

看第二行和第四行：**B 和 D 的 F1 都是 0.00，但 P 一个 1.00 一个 0.28。** 只报 F1 的话，这两类完全分不开，而它们的修法正好相反——B 不该加检索（事实已经对了），D 不该改提示词（缺的是依据）。

C 类更阴：门槛从 0.4 扫到 0.8，Q1 在 0.4 到 0.6 这三档都通过（F1 0.60），是唯一被放过的错答——而它错的那个值，恰好就是问题问的那个值。

## 症状 → 先看哪

| 症状 | 先量什么 | 判据（都是我这 12 条的数） |
| --- | --- | --- |
| 通过率很高，用户却说它答非所问 | R（覆盖度） | B 类三条全是 P 1.00、R 0.00。R 掉到 0 而 P 满，说明它说的是同一主题的另一件事 |
| P 掉下来，但回答读起来很顺 | 逐条标哪条 claim 不成立 | D 类 Q6 两条 claim 全不成立（P 0.00）：它把 PostgreSQL 页写成 4KB、InnoDB 也写成 4KB，正解是 8KB 和 16KB |
| 分数卡在门槛线上 | 被问的那个槽的值 | 门槛设 0.6，Q1 正好 0.60 通过；它的错就是问题问的那个槽 |
| 想用「通过率差几个点」判断改好没有 | Wilson 95% 区间 | n=12 时一题 8.3 个点；75% 的区间是 46.8%–91.1%，50% 的区间是 25.4%–74.6%，两段重叠——撑不起「变好了」 |
| 关键词判定天天全绿 | 判定实现本身 | 我这里 12/12 全过，包括 3 条编造的。绿的不是模型，是判定太松 |
| 同一个问题问几次答案都一样 | 别把它当证据 | 一致性只说明这组采样参数下输出稳定，不提供外部依据 |

最后一行是原稿写反了的地方。我之前写「答案一致说明模型很自信」——这是把两件事混了：输出稳定说明概率分布集中，跟「它有没有依据」没关系。把温度调到 0 也只是压缩采样随机性，服务端的批处理与浮点归约顺序仍可能让同一输入输出不同（按文档，我没在不同服务上实测）。

## 12 条样本能定多大的结论

一题就是 8.3 个百分点，所以任何「涨了几个点」都得换算成区间再看。12 条样本的 Wilson 95% 区间（脚本里 `wilson()` 算的）：

```text
 6/12 = 50.0%  ->  [25.4%, 74.6%]
 8/12 = 66.7%  ->  [39.1%, 86.2%]
 9/12 = 75.0%  ->  [46.8%, 91.1%]
10/12 = 83.3%  ->  [55.2%, 95.3%]
 动一题 = 8.3%
```

这张表回答的是「10–30 条够不够」：够用来抓**掉到 0 的那种崩**（12 条里有 8 条 F1 是 0.00，一眼就能挑出来），不够用来分辨 0.50 和 0.75。要 8 个点的分辨率，得把样本量往上抬一个量级，那时一条错的影响才降到 1% 以下。

原稿写「10–30 条就足够发现大部分回归」——「大部分」是我编的，没有数据。能站住的说法是上面这个：它够抓硬崩，不够排名次。

## 跑一遍

完整脚本在 12 条数据上跑（`$env:TEMP` 下，没进仓库），核心就是上面那两个函数加一个区间计算：

```python
def wilson(k, n, z=1.96):
    p = k / n
    d = 1 + z * z / n
    c = p + z * z / (2 * n)
    h = z * ((p * (1 - p) / n + z * z / (4 * n * n)) ** 0.5)
    return ((c - h) / d, (c + h) / d)
```

按类汇总的真实输出：

```text
类     条数    P均值    R均值   F1均值     关键词通过
A      3    1.00    1.00     1.00       3/3
B      3    1.00    0.00     0.00       3/3
C      3    0.64    0.17     0.20       3/3
D      3    0.28    0.00     0.00       3/3

关键词判定：12/12 通过，其中 claimF1<0.5 的有 8 条
Q2, Q3, Q10, Q7, Q12, Q4, Q6, Q8
```

12 条样本、31 条 claim；脚本两百多行，大部分是这批数据本身。要换成你自己的语料，改的是 `ITEMS`，不是判定函数。

## 动手

1. 先给你手上的问答挑 10 条真实问题，每条写清「必须填的槽 + 正确值」。写不出槽，说明这道题还没法判，先别进评测集。
2. 拿 3 条错的回答（编的、跑题的、细节错的各一条），跑同一套 P/R/F1。如果跑题的拿到 F1 0 而 P 1.00，说明判定口径是对的；如果它在 0.5 以上，先改判定，别改模型。
3. 记下你设的通过门槛，然后回头找「正好压线」的那几条。Q1 的 0.60 就是压线通过，这类样本是门槛的漏洞，不是模型的水准。

## 还差的

1. **没有真跑模型**。12 条回答是我手写的，用来把四种形态固定住。真实模型在这批题上的错误分布、以及它会不会造出我没预设的第五种形态，我不知道。所以本文凡是涉及「模型会怎么错」的判断，都只能标按文档。
2. **claim 切分是人工标的**。真实流水线里这一步要么写规则、要么上另一个模型，两种都会切错；切分误差对 P 的影响有多大，我没测。这批数据里每条回答的 claim 都是我照着答案原文一条条列出来的。
3. **样本小，truth 还带着这个仓库的口径**。12 个话题、31 条 claim，一条判错就动 8.3 个百分点。而且 truth 按本仓库规则判，换一份语料要整套重标——尤其是「工具允许但项目约定禁止」这类，我这次是手工分开的，没有做成机制。
4. **槽匹配是字符串相等，不是语义等价**。「16 KB」和「16kb」能过，「十六 KB」过不了。真跑起来得靠人工判或模型判，两种我都没跑。按文档，模型判定会偏爱长答案和格式整齐的答案——这句我没法证实也没法证伪，只能标按文档。
5. **生成侧那条防线没做**。引用来源、结构化输出、工具调用（让程序去查而不是让它记）都能降低 P 掉下来的概率，但它们属于第 05 课的内容，这篇一个字都没实现。多轮追问下 R 会不会掉、上下文变长后 P 会不会跟着掉，也都没有数据。
