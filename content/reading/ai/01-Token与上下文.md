## 同一句客服回复，中文 121 个 token，英文 79 个

我写了一段客服话术，又把它译成英文，想知道「同一件事」在中英两种写法里各要多少 token。本机 Python 3.11.5，tiktoken 0.13.0，编码用 cl100k_base（GPT-4 那一代）和 o200k_base（GPT-4o 那一代）。

```python
import tiktoken

ZH = ("您好，关于您反馈的订单 20261119-4471 一直显示「已发货」但物流没有更新："
      "我们查到包裹在 11 月 16 日 03:12 交给承运商，之后承运商的分拣中心有一次扫描漏记。"
      "您可以再等 24 小时；如果仍然没有更新，我这边直接为您补发一份，不需要您退回原件。")
EN = ("Thanks for reporting that order 20261119-4471 still shows Shipped with no tracking updates. "
      "We see the parcel handed to the carrier at 03:12 on 16 November, and one scan at the "
      "carrier sorting hub is missing. Please wait another 24 hours; if there is still no update, "
      "we will send a replacement at no cost and you can keep the original.")

for name, text in (("中文", ZH), ("英文", EN)):
    counts = " / ".join(
        f"{enc} {len(tiktoken.get_encoding(enc).encode(text))}"
        for enc in ("cl100k_base", "o200k_base")
    )
    print(f"{name} {len(text)} 字符, {len(text.encode('utf-8'))} 字节 | {counts}")
```

```text
中文 133 字符, 331 字节 | cl100k_base 121 / o200k_base 98
英文 336 字符, 336 字节 | cl100k_base 79 / o200k_base 79
```

我原本猜两边差不多：订单号、时间、补发条件一个不少，说的完全是同一件事。实际是 121 对 79，这段中文多花 53% 的输入 token。换成 o200k 差距缩到 24%，方向没变。

原因不在模型看不看得懂，在词表怎么切：英文常见词大多整词一个 token（336 个字符只用 79 个），中文常被切成两三个片段（133 个字用掉 121 个）。

字节数会骗你：中文 133 字占 331 字节，英文 336 字符占 336 字节，按字节算两边几乎一样，按 token 算中文多出五成。

## 「1 个 token 等于多少字」这句话没有答案

这篇的上一版写着「中文大约 1 个字 ≈ 1 个 token，英文大约 4 个字符 ≈ 1 个 token」。后半句还站得住，前半句已经是过期的默认值。

- 英文 4 字符一个 token：上面那段 336 字符 → 79 token，4.25 字符/token，两个编码数出来一样。
- 中文 1 字一个 token：这是 cl100k 上的量级（133 字 → 121 token，0.91 token/字）；换 o200k 是 0.74；文本里英文、数字、代码越多，这个数越低。
- 单字层面根本没法换算：`订单` 2 个字 1 个 token，`已发货` 3 个字 3 个 token，`魑魅魍魉` 4 个字在 cl100k 是 12 个 token、在 o200k 是 7 个，`龘` 1 个字 2 个 token。

所以预算只有一条正确做法：拿你真实要发出去的那份文本，用目标模型的分词器数一遍。

## 跑一遍

存成 `count_tokens.py`，参数传文件路径（`tiktoken` 要你自己 `pip install`，我用的是 0.13.0）：

```python
import sys, tiktoken

path = sys.argv[1]
text = open(path, encoding="utf-8").read()
chars, size = len(text), len(text.encode("utf-8"))
print(f"{path}: {chars} 字符 / {size} 字节")
for enc in ("cl100k_base", "o200k_base"):
    n = len(tiktoken.get_encoding(enc).encode(text))
    print(f"  {enc}: {n} token（{n / chars:.2f} token/字符）")
```

在仓库里挑三份不同文体的材料跑：

这份输出能直接回答三个判断：

| 症状 | 先看什么 | 实测依据 |
| --- | --- | --- |
| 按「只放 4000 字」写死预算，有时爆窗口、有时大量浪费 | 材料的文体 | 中文文档 0.73–0.77 token/字符，代码 0.32；同样 4000 字，中文约 3000 token，代码约 1300 token |
| 按 UTF-8 字节估预算，换个材料就偏 | 别用字节 | 中文文档 0.38 token/字节，代码 0.30；三份样本里字节比字符更接近，但样本太少，我不敢当规律 |
| 同一份文本，在两个模型上预算对不上 | 分词器版本 | 同一篇中文文档，cl100k 4120、o200k 3323，差 24% |

## 8 万字的手册其实装得进 128k

拿上面的密度倒推：一份 8 万字的话术手册，按客服话术那种密度（0.91 token/字）约 72,800 token；换成文档那种密度（0.73）约 58,400 token。128k 窗口我按 128,000 token 算（有的厂商规格写 131,072，去看它自己的那一页），8 万字手册占掉 57%。

所以，如果窗口是 128k 这个量级，8 万字的中文手册不会因为「装不下」被拒；先卡住你的是账单和注意力。真正拦人的是另外三件事，这篇只能把前两件的账算清：

1. **账单**：一次调用输入 72,800 token，一天一万次就是 7.28 亿输入 token。单价去看你自己那个模型的价目表——我不在这里抄数字，因为几个月就会过期一次——乘法是固定的：token 数 × 单价。输入和输出是两个单价，分开乘。
2. **延迟**：输入越长，等到第一个 token 的时间越长。这条我没在本地量到，见「还差的」。
3. **中间那段被略过**：下一节。

顺带纠一个容易写反的：带推理的模型会把思考过程也算成输出 token，`max_tokens` / `max_completion_tokens` 卡得太紧时，预算被思考吃光，接口返回空内容。这条按厂商文档写，本地测不出来。

## 越聊越贵，是因为每轮都把前面的原样重发

OpenAI 的 chat completions 这类接口是一次性请求：这次调用要带上的消息，你得自己拼好发过去。所以第 N 轮的输入里，躺着前 N-1 轮的全部内容。也有产品替你存会话，但计费照样按带进去的 token 算。

假设每轮新增 300 token（用户一句、助手一句短的），第 N 轮单次输入约 300N，前 N 轮累计发送约 300·N(N+1)/2：

| 轮数 | 这一轮输入 | 前 N 轮累计 |
| --- | --- | --- |
| 1 | 300 | 300 |
| 5 | 1,500 | 4,500 |
| 10 | 3,000 | 16,500 |
| 20 | 6,000 | 63,000 |

「第 20 轮是第一轮的十几倍」这句话只对了一半：单次输入是 20 倍，累计发送是 210 倍。账单看后者。

三种处理，代价不同：

- **滑动窗口**，只留最近 6 轮：最省事，代价是用户三十轮前提过的约束会丢。
- **摘要**，把早期对话压成一段背景：保住结论，丢掉细节和原话；用户回头说「我刚才不是这么说的」时，你需要原话。
- **只带结构化状态**：把「岗位=Java 后端、城市=杭州、阶段=已投 3 家」抽成字段，不带原始对话。前提是你知道后续每一步需要哪些字段，否则只是换一种方式丢信息。

判断标准很土但有效：这轮要生成的那句话，需要知道哪些事实？只带那些。

## 中间那段最容易被略过

Liu 等人的 Lost in the Middle（arXiv:2307.03172，TACL 2024）做过系统实验：关键信息放在长上下文的开头或结尾，模型答对的概率高于放在中间，准确率随位置呈 U 形。他们测的是 2023 到 2024 年那批模型，任务主要是多文档问答和键值检索。

两个推论，第二个比第一个重要：

1. 同一份资料，把关键的几行放开头或结尾，比堆在中间靠得住。别指望「它反正全读过了」。
2. 这是信息位置效应，不是指令优先级。system 提示里写在「最后」的那句，在请求中依然排在所有 user 消息之前，离上下文末尾还很远。真要强调一条约束，就在最后那条 user 消息里再说一遍，别只写在 system 的末尾。

## 截断：按 token 切，但 token 不是完整的字

我原以为 token 一定对应完整的字符，切在 token 边界不会切坏汉字。测一下：

```python
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
s = "承运商的分拣中心"
ids = enc.encode(s)
print(len(ids), [enc.decode(ids[:k]) for k in (1, 7, 10)])
```

```text
10 ['�', '承运商的分�', '承运商的分拣中心']
```

10 个 token，切在第 7 个之后解码得到 `承运商的分�`——「拣」被拆成两个 token，各占一半字节。截断长度是准的，截断点上可能有个半个字。

比半个字麻烦的是结构。切在 JSON 中间，模型拿到坏 JSON，可能自己补一段看起来合理的字段；切在多轮对话中间，模型看到半句提问就去回答。原则只有一条：切点落在整轮消息、整段、整个对象的边界上，宁可少给一条完整资料，不给半条。

## 还差的

1. 只量了两个分词器（cl100k_base、o200k_base）。Qwen、DeepSeek、Llama 的词表不同，同一段中文的 token 数我没测，它们文档里的换算口径我也没验。
2. 钱只算到 token 数为止。单价、缓存折扣、批处理折扣都没进这份笔记——价目表变得比我更新笔记快，所以故意不写数字。要算钱，拿这里的 token 数乘你自己价目表的单价。
3. 「推理 token 计入输出上限、卡紧了返回空」是按厂商文档写的，本地测不出来；要验证得真调 API，抓返回体里的 usage 字段。
4. Lost in the Middle 的 U 形没有复现，只按论文写。论文测的是 2023–2024 年那批模型，现在带推理的模型是不是还这样，我不知道。
5. token/字符比只覆盖了中文文档、代码和这篇自己，没覆盖表格、日志、JSON、图片。图片按分辨率和切片算 token，是另一套规则，这篇完全没碰。
