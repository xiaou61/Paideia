## 先把结论摆出来

模型不是按"字"处理文本，而是按 **token**。token 是词表里的一个片段，可能是一个字、一个词、半个词。

三件事由它决定：

1. **花多少钱**：计费按输入 + 输出 token 数；
2. **能塞多长**：上下文窗口是 token 上限，不是字符数；
3. **怎么截断**：超长时你截掉的可能是关键信息，而且截在词中间会让效果变差。

**中文大约 1 个字 ≈ 1 个 token（不同模型有差异），英文大约 4 个字符 ≈ 1 个 token。** 需要精确值时用分词器估算，不要凭字数猜。

## 上下文窗口是什么

上下文 = 这一次调用里模型能看到的全部内容：

```text
系统提示词 + 历史消息 + 检索到的资料 + 用户问题
```

全部加起来不能超过窗口上限。超出时的选择只有三个：

- **截断**：丢掉最早的历史或最长的资料；
- **摘要**：把历史压成一段话再放进去；
- **检索**：不把所有资料都塞进去，只放相关的几条。

**产品上最常见的错误**是"把整篇文档都塞进去"。文档一大，成本按 token 线性涨，而模型对中间部分的注意力反而会下降——这就是"丢了中间"（lost in the middle）现象。

## 为什么"长上下文"不是万能解

窗口变大只解决了"塞得下"，没解决三件事：

1. **成本**：每次调用都要为全部输入付费，长文档反复调用非常贵；
2. **延迟**：输入越长，首 token 时间越长；
3. **准确性**：中间部分的信息更容易被忽略，关键约束放在开头或结尾更可靠。

所以工程上的默认策略是：**能用检索就用检索，别用长上下文硬塞**。

## 输出也是 token，而且是贵的那种

计费通常输入便宜、输出贵（输出要逐 token 生成）。这带来两个实践建议：

- **限制输出长度**：`max_tokens` 设小一点，既省钱也防跑题；
- **结构化输出**：要求返回 JSON 而不是一段散文，能显著减少无用 token。

注意：**思考型模型的思考过程也吃 token**（有的模型把思考算进 `max_tokens`）。设得太小时会出现"返回空内容"——不是模型坏了，是预算被思考吃光了。

## 历史管理：对话为什么越聊越贵

多轮对话每轮都要把之前的消息再发一遍。到第 20 轮时，输入可能已经是第一轮的十几倍。

三种控制手段：

- **滑动窗口**：只保留最近 N 轮；
- **摘要压缩**：把早期对话压成一段"背景"；
- **只带必要状态**：把"用户的目标"抽成结构化字段，别带原始对话。

**判断标准**：如果模型只需要知道"用户想找 Java 工作"，就不需要带前面关于 Python 的十轮对话。

## 一个成本估算的例子

假设输入 3000 token、输出 300 token，每天调用 1000 次：

```text
每次 ≈ 3300 token
每天 ≈ 330 万 token
```

按每百万 token 几元到几十元的价格区间，日成本在十几元到上百元之间。**如果不做截断和摘要，输入很容易翻三倍**——成本是按比例涨的，不是"稍微贵一点"。

## 常见误区

### 误区：上下文窗口大，就可以无限塞

**你以为**：窗口 100 万 token，随便放。
**其实**：成本线性涨、延迟升高、中间信息容易丢。大窗口是"能放"，不是"该放"。

### 误区：token 就是字

**你以为**：按字数算钱。
**其实**：英文一个词可能拆成多个 token，中文标点与生僻字也各有代价。精确预算要用分词器。

### 误区：`max_tokens` 设大点更保险

**你以为**：反正用不完不收费。
**其实**：有的模型按上限预留资源；更重要的是思考 token 会吃预算，设太小会返回空。要按任务实际需要设置，并留出思考余量。

## 小结

模型按 token 处理，窗口按 token 限长，成本按输入 + 输出计。长上下文解决"放得下"，不解决成本、延迟与中间信息丢失。历史要窗口化或摘要化。下一课：注意力到底在做什么。
