## 一次抽取 1939 token，我估的是 700

先数一遍，再谈选型。同一份合同、同一份系统提示词，两套分词器各数一次：

```python
import pathlib
import tiktoken

encs = {n: tiktoken.get_encoding(n) for n in ("cl100k_base", "o200k_base")}
texts = {n: pathlib.Path(n).read_text(encoding="utf-8") for n in ("system_prompt.txt", "contract.txt")}

for name, text in texts.items():
    han = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    print(f"{name}: {len(text)} 字符（汉字 {han}）")
    for enc_name, enc in encs.items():
        n = len(enc.encode(text))
        print(f"  {enc_name:<12} {n:>5} token   每 token {len(text) / n:.2f} 字符")

print()
totals = {k: sum(len(e.encode(t)) for t in texts.values()) for k, e in encs.items()}
print(f"一次抽取的输入：cl100k {totals['cl100k_base']} / o200k {totals['o200k_base']}")
gap = totals["cl100k_base"] - totals["o200k_base"]
print(f"相差 {gap} token，占 cl100k 的 {gap / totals['cl100k_base']:.1%}")
```

```text
system_prompt.txt: 858 字符（汉字 258）
  cl100k_base    462 token   每 token 1.86 字符
  o200k_base     395 token   每 token 2.17 字符
contract.txt: 1398 字符（汉字 1140）
  cl100k_base   1477 token   每 token 0.95 字符
  o200k_base    1066 token   每 token 1.31 字符

一次抽取的输入：cl100k 1939 / o200k 1461
相差 478 token，占 cl100k 的 24.7%
```

本机 Python 3.11.5、tiktoken 0.13.0，文本是上一篇那份合同 `HT-2026-0137` 和那套 8 字段的系统提示词。

我原本按「1400 字的合同大概 700 token」估，实际 1477，差 2.1 倍。那个估算用的是「1 token 当 2 个汉字」的口诀；换成中文合同加这套分词器，实测 0.95 字符/token——一个汉字要一个多 token，比口诀算多了一倍。

同一份合同换 `o200k_base`，少 411 token。**分词器是报价的一部分**：两家都说「输入每百万 token 多少钱」，先把你的文本在两套分词器下各数一遍，再比。

## 每成功任务成本是 c 除以 p

设单次调用成本 `c`，单次通过率 `p`，失败就重试，最多 `k` 次：

```text
E  = p·1 + q·p·2 + q²·p·3 + … = (1 - q^k) / p      q = 1 - p
s  = 1 - q^k                                        最终成功率
每份成本       = c · E
每成功任务成本 = c · E / s = c / p
```

最后一步是关键：成功的那 `s` 份要把失败件的钱一起摊掉，`k` 在分子分母里同时出现，约掉了。**重试上限不改变每成功任务成本**，它只改三件事：失败件数、延迟、人工量。

把这份任务的参数丢进账本（每天 1000 份、最多试 3 次、输入 1939 token）：

```python
N = 1000            # 每天抽多少份
MAX_TRY = 3         # 每份最多试几次
IN_TOK = 1939       # 实测：系统提示词 462 + 合同 1477
PREFIX = 462        # 实测：其中稳定的前缀
REVIEW_MIN = 2.0    # 一份失败件人工看几分钟
CNY_PER_HOUR = 30
FX = 7.1

A = dict(name="A", pin=1, pout=4, out=189, p=0.45)    # $1/$4 每百万
B = dict(name="B", pin=3, pout=12, out=65, p=0.90)    # $3/$12 每百万


def attempt_cost(c):
    return IN_TOK * c["pin"] / 1e6 + c["out"] * c["pout"] / 1e6


def attempts(p):
    """封顶 MAX_TRY 次，每份平均试几次。"""
    return (1 - (1 - p) ** MAX_TRY) / p


def per_success(c):
    return attempt_cost(c) / c["p"]


def daily(c):
    return attempt_cost(c) * attempts(c["p"]) * N


def hours(c):
    return N * (1 - c["p"]) ** MAX_TRY * REVIEW_MIN / 60


for c in (A, B):
    print(f"{c['name']} 每次尝试 ${attempt_cost(c):.5f}  期望 {attempts(c['p']):.3f} 次  "
          f"每成功 ${per_success(c):.5f}  失败 {N * (1 - c['p']) ** MAX_TRY:.0f} 份  "
          f"人工 {hours(c):.2f} 小时")

print(f"单价之比 {B['pin'] / A['pin']:.0f}:1  每成功任务之比 "
      f"{per_success(A) / per_success(B):.2f}:1")
print(f"单次成本之比 {attempt_cost(A) / attempt_cost(B):.4f}  "
      f"通过率之比 {A['p'] / B['p']:.4f}")
print(f"A 的通过率掉到 {B['p'] * attempt_cost(A) / attempt_cost(B):.1%} 就翻盘")
```

单价是示意值（两组差三倍），`out` 是后面实测的输出长度，两个通过率是假设值——这两项必须换成你自己评测集的数。跑出来：

```text
A 每次尝试 $0.00269  期望 1.852 次  每成功 $0.00599  失败 166 份  人工 5.55 小时
B 每次尝试 $0.00660  期望 1.110 次  每成功 $0.00733  失败 1 份  人工 0.03 小时
单价之比 3:1  每成功任务之比 0.82:1
单次成本之比 0.4085  通过率之比 0.5000
A 的通过率掉到 36.8% 就翻盘
```

我猜的是「单价三倍，每成功成本也就三倍上下」。实际 0.82:1，便宜的那家低 18%。拆开看：A 的期望尝试次数是 B 的 1.67 倍，单次成本只有 0.41 倍，两项相乘 0.68；A 的最终成功率是 0.83、B 是 0.999，再一折算，落到 0.82。

最后两行是判据：

```text
A 的每成功成本更低  ⟺  c_A / c_B  <  p_A / p_B
```

两个比值摆在一起就能判，不用背「成本三角」那种东西。A 在这里赢得不宽：通过率从 45% 掉到 36% 就输。任何一家给你「便宜三倍」的报价，先问通过率，再拿这条式子算一遍。

## 同一件事，三种口径，三个结论

上面的账只算了 token。真实上线时财务、老板、你自己要的是三个不同的数：

| 口径 | A | B | 什么时候该用 |
| --- | --- | --- | --- |
| token 账（每天烧多少 token） | $4.99/天 | $7.32/天 | 只有 token 预算时；答「这个月账单多少」 |
| 每成功任务账 | $0.00599 | $0.00733 | 换模型、换提示词做比较；答「哪种做法更省」 |
| 含人工账 | ¥201.8/天 | ¥53.0/天 | 决定上线哪个；答「这方案划不划算」 |

同一组参数，A 在第一行便宜 31.8%，第二行便宜 18.3%，第三行贵 3.8 倍。**先定口径再谈选型**，否则两个人拿同一份数据能吵一下午，而且吵的都是对的。

含人工账要三个我没法替你定的数：汇率（这里 7.1）、人工单价（30 元/时）、失败件处理时长（2 分钟）。这三个值一动，结论跟着动：

```text
复核 0.5 分钟、30 元/时：A ¥77.0   B ¥52.2   A/B 1.5
复核 2.0 分钟、30 元/时：A ¥201.8  B ¥53.0   A/B 3.8
复核 2.0 分钟、60 元/时：A ¥368.2  B ¥54.0   A/B 6.8
复核 4.0 分钟、60 元/时：A ¥700.9  B ¥56.0   A/B 12.5
```

从 1.5 倍到 12.5 倍，token 那一半完全没变。「贵模型不划算」这句话，得先补上「一件失败你算它多少人工」，否则它不是一个判断，只是一个立场。

## 重试上限改的是失败件数

```text
单次通过率  A 每成功      A 人工小时   B 每成功
35%         $0.00770      9.15         $0.00733
41%         $0.00657      6.85         $0.00733
45%         $0.00599      5.55         $0.00733
55%         $0.00490      3.04         $0.00733
75%         $0.00359      0.52         $0.00733
```

A 那一列从 35% 到 75% 差了 2.1 倍，35% 那一行直接输给 B；B 那一列不动，因为它本来就在 90%。人工小时更陡：45% 那一行是 5.55 小时，已经是半个多工位；35% 是 9.15 小时，一个人整天就交代在失败件上了。

45% 这个读数还顺手纠了一类错表。如果你手上那张写着「单次通过率 45%、平均尝试 4.0 次、最终成功率 65%」，三个数互斥：

- 单次通过率 45%，平均尝试最多 `1 / 0.45 = 2.22` 次（这是不限次重试的上界，封顶 4 次是 2.02 次），不是 4.0；
- 封顶 4 次时最终成功率是 `1 - 0.55⁴ = 90.8%`，不是 65%；
- 想凑出 65% 的成功率，单次通过率得是 `1 - 0.35^(1/4) = 23.1%`。

这三个量里定下两个，第三个就定了。**一张成本表里三个比例都在自由浮动，说明它没算过。**

```text

out3.txt    264 字符   189 token
```

中文键名比英文键名贵 55%，再加两段话贵到 2.9 倍——字段一个没多。这 189 token 是**每份合同都要重发一次**的输出，一天 1000 份就是 18.9 万 token 的输出量。

把 A 的输出从 189 压到 65：

```text
A 只吐 JSON：每成功 $0.00489，每天 $4.07
  输出占单次成本 28.1%  <- A 啰嗦（189 token）
  输出占单次成本 11.8%  <- A 紧凑（65 token）
  输出占单次成本 11.8%  <- B 紧凑（65 token）
```

同一个模型、同一份输入，只改输出写法：每成功任务成本从 $0.00599 掉到 $0.00489，是 B 的 66.7%，每天从 $4.99 掉到 $4.07。前面的账里 A 只赢 18%，改完输出后赢 33%。

「输出占单次成本 28.1%」这个读数，比「输出单价是输入的 4 倍」有用得多：单价告诉你单价，占比告诉你该动哪一边。**输出贵不贵，看它占多少，不看它标多少。**

## 缓存省的是前缀那一段，不是整张账单

这段账单里稳定不变的只有系统提示词那 462 token，占一次输入的 23.8%。缓存能省的**上限**就是：

```text
省下的比例 = 前缀占比 × (1 - 读倍率)
           = 23.8% × (1 - 0.1) = 21.4%
```

```text
前缀占输入 23.8%
  读0.1/写1.25：省 21.4%
  读0.5/无写入价：省 11.9%
  前缀每次都变：贵 6.0%
```

三个读数的意思是：按文档示例代码的读写乘数算省 21.4%；换一代只有对折折扣的缓存省 11.9%；前缀每次请求都变（把时间戳、用户 ID、随机抽样塞进提示词开头），每次都得按写入价付一遍，反而贵 6.0%——比不开缓存还差。

`读 0.1 / 写 1.25` 这两个乘数来自官方文档里的示例代码，不是协议常量；不同代际、不同模型的折扣以你的价目表为准。字段形状按 2026-11-19 的文档：OpenAI 的 [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) 是自动匹配、从 1024 token 起、按 128 token 递增，用量在 `input_tokens_details.cached_tokens`，较新代际另有 `cache_write_tokens`，价目表上 cached-input 与 cache-write 是两行，写入价是那一档的价、不是叠加费；Anthropic 的 [cache_control](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) 是显式断点，5 分钟 TTL（命中即刷新）或 1 小时，写入与命中各有独立价。**这些是文档，不是我的实测**——环境里没有 API key。

TTL 还会吃掉一块：同样 1000 份摊在 12 小时里，5 分钟 TTL 意味着 144 次重写前缀，省下来的从 21.4% 掉到 17.5%。

所以「开缓存能省一半」这种话要拆开：省的是前缀那一段里的那部分，`23.8% × 90%`。前缀只占 5% 的时候，缓存开到天上去也就省 4.5%。

## 多轮工具循环：输入按轮数长

```text
第 1 轮 1939，第 8 轮 3759，八轮合计 22792
是单次输入的 11.8 倍
```

每轮多 260 token（一次工具返回的量级，假设值），八轮总输入是单次的 11.8 倍；第 8 轮自己的输入是第 1 轮的 1.94 倍，因为每轮都把历史整段重发一遍。这是接口形状决定的，不是供应商多收你钱。

能压的只有三处，而且都是缓解不是解决：轮数少一点（能一次问清就别拆三次）、工具返回体裁掉用不上的字段、把稳定前缀放最前面让缓存能覆盖到。上下文重发这件事改不掉。

## 现象 → 先看哪

| 现象 | 先量什么 | 用哪个数 |
| --- | --- | --- |
| 账单涨了，抽取量没涨 | 每次尝试的输入 token：提示词变长？重试变多？ | 1939 变成多少 |
| 账单没涨，成功件数掉了 | 单次通过率 p 和失败件人工 | 每成功成本、人工小时 |
| 开了缓存，账单没降 | 前缀是否每次都变；是否短于最小可缓存长度 | 省 21.4% 还是贵 6.0% |
| 输出侧占比突然变大 | 输出写法的 token 数 | 189 还是 65 |
| 上了 Agent 之后成本翻倍 | 轮数、每轮新增多少 token | 11.8 倍还是更多 |
| 预算批了还是超 | 你和财务用的是哪个口径 | token 账还是含人工账 |

这张表里没有一行是「换个更便宜的模型」。六个现象，一个都不是换模型能解决的。

## 动手

1. 用你自己的评测集替掉两个通过率。20 条以上、带判据的样本跑一遍得出 `p_A` 和 `p_B`，再比 `c_A/c_B` 与 `p_A/p_B`。在这之前，本文的 45% 和 90% 只是参数，不是能力。
2. 把输出改成只吐 JSON（`response_format` 那类约束，或提示词里明确禁止解释文字），量改前改后的 `output_tokens`，把 189 和 65 换成你的实测，「输出侧」那张表就变成你的。
3. 在流水线里给失败件打两个时间戳：进人工队列的时间、标记处理完的时间。有了「一件多久」，含人工账才有分母，而不是拿 2 分钟去猜。

## 还差的

- **没有 API key，供应商侧的数字一个都没对过真账单。** 缓存乘数 0.1/1.25 来自文档示例代码，不同代际不一样；字段名、最小可缓存长度（1024 token 起、128 递增）、写入价与读价分两行计费，都按 2026-11-19 的文档写，未实跑。
- **两个通过率是假设值。** 45% 和 90% 只是为了让「三倍单价、接近打平」这个局面具体化，不是任何模型的能力数据。换掉它们，本文全部结论都要重算——这正是前面那条不等式存在的理由。
- **只量了两套 OpenAI 分词器。** Anthropic、Gemini 和各家国产模型的分词器都没量，同一份合同的 token 数会不同，跨家比价前必须各数一遍。本文所有 token 数都是 `cl100k_base`。
- **两处参数没实测。** 八轮循环里「每轮新增 260 token」全凭工具返回体大小，返回一张 JSON 报表和返回一行 ID 差一个数量级；Batch 的 50% 折扣与 24 小时窗口只按 2026-11-19 的文档写（Azure OpenAI 的 Batch 文档写明 50% less 与 24h target），没实跑，失败件怎么退回也没验证。
- **含人工账的三个假设值（汇率 7.1、30 元/时、2 分钟）全是拍的。** 其中任何一个错，三种口径里含人工那行的倍数就变；通过率敏感性表只是展示它有多能变，不是校准过的结论。
