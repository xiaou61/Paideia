## 先把结论摆出来

模型选型最常见的错误，是打开价格页，按"每百万 token 多少钱"排序，选最便宜的那个。这个数字只回答"输入一个 token 多少钱"，不回答"完成一个任务多少钱"。

真正的成本要这么算：

```text
单次任务成本 =
  Σ 每一轮（未缓存输入 × 输入单价
          + 缓存命中输入 × 缓存单价
          + 输出 token × 输出单价）
  + 失败重试的成本
  + 工具、检索、人工复核等外部成本

每成功任务成本 = 总成本 / 成功任务数
```

分母是**成功任务数**，不是调用次数。这个差别决定了选型结论。

三句话概括这一篇：

1. **单价便宜不等于总账便宜**：输出通常比输入贵，重试、工具轮次、上下文累积都会放大成本；
2. **上下文窗口是上限，不是目标**；缓存只对稳定前缀有效；流式只改善首 token 的感知，不降低总时长；
3. **选型看四个数**：每成功任务成本、p95 延迟、任务通过率，以及硬约束（窗口、工具、结构化输出、合规）。

## 成本到底怎么算

一次模型调用的账单由几块组成，很多人只看了第一块。

| 组成 | 说明 | 容易被忽略的点 |
| --- | --- | --- |
| 未缓存输入 | 系统提示词、工具描述、历史消息、检索资料、用户输入 | 每一轮都要重发，Agent 里会累积 |
| 缓存命中输入 | 与上一次请求完全相同的前缀，按缓存价计费 | 只有稳定前缀才命中，写入缓存可能更贵 |
| 输出 | 最终回答、工具调用参数、结构化 JSON、部分模型的思考 token | 输出单价通常是输入的几倍 |
| 重试 | 校验失败、超时、限流后的再次调用 | 失败也要付钱，而且往往付得更多 |
| 外部成本 | 检索、embedding、工具调用、存储、人工复核 | 人工复核经常比 token 贵 |

一个具体的乘法：单次调用输入 5k token，看起来不多；但一个 8 轮的任务，每轮新增 2k（模型输出加工具结果），第 n 轮输入就是 `3k + 2k × n`，第 1 轮 5k，第 8 轮 19k，八轮加起来约 96k。**单次成本的十几倍到二十倍，是 Agent 的常态。**

所以"这个模型每百万 token 只要几毛钱"这句话，只有在你知道"每个成功任务平均消耗多少 token、平均调用几次"之后才有意义。

## 上下文窗口：上限不是目标

上下文窗口（context window）是模型一次能接收的最大 token 数，通常输入和输出共享这个上限。它决定了"能不能把整份文档塞进去"，但不决定"塞进去是否划算、是否答得准"。

三个常见误解：

**第一，窗口大就可以不检索。** 把 150k token 的资料全塞进去，成本是 15k 方案的十倍，延迟更高，而且模型在长上下文中间部分容易漏信息。检索仍然有价值：它不是为了"塞得下"，而是为了"只给相关的"。

**第二，窗口大不等于输出能写长。** 很多模型的最大输出只有几千 token，和窗口是两回事。你让它生成一份很长的 JSON，可能在 `max_tokens` 处被截断，`finish_reason` 是 `length`，解析直接失败。**给结构化输出留足输出预算**，必要时拆成多次生成。

**第三，长上下文可能有阶梯价。** 一些供应商对超过某个阈值的输入收更高单价。选型时要看"你的典型输入落在哪个价格区间"，而不是只看最低档。

一个实用的预算分配（具体数字按任务调整）：

```text
系统提示词 + 工具描述：2k - 5k
对话历史 / 记忆：      5k - 20k
检索资料：             5k - 15k
输出预留：             1k - 4k
```

先定这个预算，再选窗口和模型。**窗口是买得起的空间，不是应该填满的空间。**

## 输入价、输出价、缓存价：三个价格不是一回事

价格页上通常有三列：输入、输出、缓存。它们的行为完全不同。

**输出比输入贵。** 常见比例是 3 到 5 倍，有的模型更高。这意味着"两个模型输入价差不多，但一个更啰嗦"时，总账可能差很多。结构化输出、工具调用参数、JSON 字段名都算输出；部分推理模型还会把思考过程的 token 计入输出。选型时要看**每个任务的平均输出 token**，不能只看输入单价。

**缓存只对稳定前缀有效。** 缓存的工作方式是：请求开头一段内容与之前完全相同，供应商就直接复用计算结果，按更低的价格计费。它要求：

- 前缀逐 token 相同，改一个字就失效；
- 顺序稳定，系统提示词、工具清单、示例放在前面，动态内容放后面；
- 在缓存有效期（TTL）内再次请求；
- 供应商支持，且缓存粒度符合你的请求结构。

很多系统缓存命中率低，原因不是供应商不行，而是把时间戳、用户 ID、随机 ID 放在了系统提示词最前面——每次请求前缀都变，永远命中不了。

一个算账的例子。假设静态前缀 10k token，动态内容 1k，连续调用 10 次；输入单价记为 1，缓存写入按 1.25 倍、缓存读取按 0.1 倍（只是示意，实际比例看供应商）：

```text
不用缓存：11k × 10 = 110k 单位
用缓存：  首次 10k × 1.25 + 1k = 13.5k
          之后 9 次 × (10k × 0.1 + 1k) = 18k
          合计 31.5k 单位
节省约 71%
```

缓存不是"开了就省"：写入缓存可能比普通输入贵，TTL 短、前缀不稳定、请求量太小，都可能让缓存白开。**先看账单里的缓存命中 token 数，再决定要不要为它调整提示词结构。**

## 延迟：首 token 与总时长是两件事

用户感知的延迟和账单上的延迟不是同一个东西。

- **首 token 延迟（TTFT）**：从发请求到收到第一个 token，包含排队、网络、预填充（prefill）。它决定"用户觉得系统有没有反应"。
- **总时长**：首 token 之后，还要按生成速度把剩余 token 吐完。`总时长 ≈ TTFT + 输出 token 数 / 每秒生成 token 数`。
- **p95 延迟**：95% 的请求在这个时间内完成。平均值会掩盖尾部，而用户投诉通常来自尾部。

流式输出（streaming）改善的是**首 token 的感知等待**：用户很快看到字开始出现，不会盯着空白屏幕。但它不减少总生成时间，也不减少成本。一个需要 30 秒才能生成完的回答，流式之后仍然是 30 秒，只是这 30 秒里用户有东西可看。

Agent 的延迟还要再加一层：**总时长是各轮模型时间、工具执行时间、校验与重试时间的累加**。一次 5 轮的任务，每轮模型 3 秒、工具 2 秒，就是 25 秒；如果中间有一次 403 重试、一次格式校验失败重试，很容易超过 35 秒。优化 Agent 延迟，先看"哪一段占得最多"，而不是先换更快的模型。

| 指标 | 用户感受 | 常见优化 |
| --- | --- | --- |
| TTFT 高 | "点了没反应" | 流式、减小输入、换低延迟档、预热连接 |
| 总时长高 | "怎么还没好" | 减少输出、减少轮次、并行工具、截断上下文 |
| p95 高 | "偶尔特别慢" | 查超时与重试、限制工具耗时、排队隔离 |
| 成本高但延迟不高 | 账单痛，体验还行 | 缓存、路由、批量、压缩输出 |

## 能力、成本、延迟：三角只能选两个

模型选型本质上是在三个角之间做取舍：

- **能力**：任务通过率、复杂推理、工具使用、结构化输出稳定性；
- **成本**：每成功任务多少钱；
- **延迟**：TTFT 和 p95 总时长。

没有模型能同时把三个角都做到最好。可行的顺序是：**先定硬约束，再在约束内优化成本。**

硬约束包括：上下文窗口够不够、是否支持工具调用、是否支持严格结构化输出、是否有地域/合规要求、p95 能不能接受。硬约束不满足的模型直接排除，不要用"它便宜"说服自己。

剩下的候选，按任务类型分：

| 类型 | 适合 | 不适合 |
| --- | --- | --- |
| 旗舰模型 | 复杂推理、长链路规划、低容错任务 | 简单分类、大批量抽取 |
| 中档模型 | 大多数生产任务，能力和成本平衡 | 极长上下文、极高并发下的成本敏感场景 |
| 小模型 | 分类、抽取、意图识别、路由 | 多步规划、复杂工具编排 |
| 推理模型 | 数学、代码、需要显式思考的任务 | 低延迟对话、简单格式化 |

"能力"是任务相关的，不是排行榜上的一个总分。一个模型在代码题上强，不代表它在合同字段抽取上强；一个模型写作好，不代表它工具调用稳定。**必须用你自己的评测集测。**

## 路由、批量与流式

这三个手段都能省钱或省时间，但各有代价。

### 路由：简单任务给小模型

路由（routing）是先用规则或一个小模型判断任务难度，再决定用哪个模型。常见形态：

```text
route = classify(request)        # 规则、关键词或小模型
result = call(route.model, request)

if not valid(result) or route.escalate:
    result = call(large_model, request)
```

两种策略：

- **前置路由**：先分类再选模型，便宜但可能分错；
- **级联（cascade）**：先让小模型做，失败或置信度低再升级到大模型。省得更多，但失败那部分要多花一次延迟。

路由的风险是**质量悬崖**：一个复杂问题被误判成简单问题，小模型给出了看似合理但错误的答案，而且没有触发升级。所以路由必须配合校验和监控：按路由分组看通过率，发现某条路由的通过率明显低，就调整分类规则或提高升级阈值。

### 批量：离线任务用批处理

很多供应商提供批量接口（batch），价格通常是实时调用的一半左右，代价是结果不保证即时返回，可能几分钟到几小时。它适合：

- 夜间跑的文档抽取、分类、摘要；
- 离线评测集跑分；
- 历史数据回填。

不适合：聊天、Agent 工具循环、任何用户正在等的请求。批量的失败重试和结果排序也要设计，不能假设"提交了就一定成功"。

### 流式：改善体验，不改变账单

流式适合交互式场景，尤其是输出较长时。它有两个工程约束：

- **结构化输出与流式可能冲突**：有的 API 在流式模式下不支持严格 schema，或者只支持部分 JSON 增量；你需要一个增量解析器，不能等整个 JSON 到了再解析。
- **流到一半发现格式错，重试要重新生成**：已经输出的 token 已经付过钱，重试是第二份成本。所以流式 + 严格结构化输出要先确认供应商支持，再决定是否使用。

| 手段 | 省钱 | 降延迟 | 主要代价 |
| --- | --- | --- | --- |
| 路由 / 级联 | 是 | 有时 | 分类错误、质量悬崖 |
| 批量 | 是 | 否（更慢） | 不适合交互、结果延迟 |
| 流式 | 否 | 改善感知 | 结构化输出受限、重试成本 |
| 缓存 | 是 | 是 | 前缀必须稳定、写入有成本 |
| 截断上下文 | 是 | 是 | 可能丢信息 |

## 怎么用评测集选型

不要用"哪个模型回答得更像人"来选。用一组固定任务、固定判据、固定环境，跑出可比较的数字。

**第一步，建评测集。** 20 到 50 条，覆盖真实输入：正常路径、含糊输入、超长输入、工具报错、权限不足、注入文本。每条写清期望：必须包含什么、必须不包含什么、必须调用哪个工具、输出必须符合哪个 schema。

**第二步，固定变量。** 同一个提示词版本、同一份工具清单、同样的 `max_tokens`、同样的温度。不要给 A 模型配精心调过的提示词，给 B 模型用随手写的版本——那样比的是提示词，不是模型。

**第三步，每个候选跑 2 到 3 次。** 模型有随机性，一次结果可能是运气。看通过率的均值和波动，不要只看最好的一次。

**第四步，算三个数：**

```text
通过率 = 通过用例数 / 总用例数
每成功任务成本 = 总成本 / 通过用例数
p95 延迟 = 95% 请求的完成时间
```

注意第二个公式的分母是**通过用例数**，不是总用例数。一个模型便宜但通过率低，失败重试和人工复核会把总账拉回去。

**第五步，逐条看 diff。** 通过率相同的两个模型，失败在哪类用例上可能完全不同：一个错在格式，一个错在事实。格式错可以靠 schema 和重试修，事实错不能。选那个"失败更容易兜住"的模型。

一个假设的对比（数字只为演示方法）：

| 候选 | 通过率 | 每成功任务成本 | p95 延迟 | 特点 |
| --- | --- | --- | --- | --- |
| C（小模型） | 78% | $0.006 | 4 秒 | 便宜快，但 22% 要人工复核 |
| B（中档） | 92% | $0.017 | 8 秒 | 平衡，失败主要是格式问题 |
| A（旗舰） | 95% | $0.060 | 15 秒 | 最准，但成本是 B 的 3.5 倍 |

怎么选取决于业务：如果 78% 加人工复核可接受、延迟敏感，选 C；如果质量优先、人工贵，选 B；只有当那 3 个百分点能带来明显收益时，才选 A。**没有"最好的模型"，只有"在这个约束下最合适的模型"。**

## 一个具体例子

任务：从每份合同里抽取 8 个字段，输入约 3k token，输出约 500 到 1500 token。每天 1000 份。

两个候选，价格是假设的，只为演示算法：

| | 模型 A（便宜） | 模型 B（贵 3 倍） |
| --- | --- | --- |
| 输入单价 | $1 / 百万 token | $3 / 百万 token |
| 输出单价 | $4 / 百万 token | $12 / 百万 token |
| 单次通过率 | 45% | 90% |
| 平均尝试次数 | 4.0 | 1.05 |
| 每次输出 token | 1500 | 500 |
| 最终成功率 | 65% | 93% |

先算每次尝试的成本：

```text
模型 A：3000 × 1/1e6 + 1500 × 4/1e6
      = 0.003 + 0.006 = $0.009
模型 B：3000 × 3/1e6 + 500 × 12/1e6
      = 0.009 + 0.006 = $0.015
```

再算每任务和每成功任务：

```text
模型 A：0.009 × 4.0 = $0.036 / 任务
        0.036 / 0.65 = $0.0554 / 成功任务
模型 B：0.015 × 1.05 = $0.01575 / 任务
        0.01575 / 0.93 = $0.0169 / 成功任务
```

结果和"单价直觉"相反：模型 A 的单价只有 B 的三分之一，但**每成功任务成本是 B 的 3.3 倍**。原因是 A 通过率低、重试多，而且输出更啰嗦——输出单价是输入的 4 倍，1500 token 的输出把便宜输入省下的钱全吃掉了。

还没算人工。A 有 35% 的任务最终失败，需要人工复核；如果每条复核 2 分钟，1000 份就是约 11.7 小时。按每小时 30 元算，人工成本 350 元，而 A 的 token 成本只有约 55 元。**人工复核的成本，通常是 token 成本的几倍到几十倍。**

再看 Agent 场景，乘数更明显。同样一个任务：

```text
单次调用：输入 5k
8 轮工具循环：第 1 轮 5k，第 8 轮 19k，合计约 96k
```

如果小模型因为不会停、每轮都多绕一次，轮次从 4 涨到 8，输入 token 可能翻三倍。**单价便宜 3 倍，轮次多一倍，总账就回去了。** 所以 Agent 选型一定要用"完整任务"跑，不能只测单步。

这个例子不是让你一律选贵的模型。它说明的是：**选型的单位是"成功任务"，不是"token"。** 如果任务简单、输出短、失败可自动兜住，便宜模型就是对的；如果失败要人工、重试多、输出长，便宜模型可能最贵。

## 常见误区

### 误区：按每百万 token 单价选模型

**你以为**：单价低，总账就低。
**其实**：输出单价、重试次数、输出长度、工具轮次都会改变总账。一个便宜但啰嗦、通过率低的模型，每成功任务成本可能贵几倍。
**怎么验证**：用同一批任务跑两个模型，记录总成本、成功任务数，算 `总成本 / 成功数`，而不是只看单价。

### 误区：输出 token 和输入 token 一个价

**你以为**：输入输出差不多，按总量估就行。
**其实**：输出通常贵 3 到 5 倍，部分推理模型还把思考 token 计入输出。一个爱写长答案的模型，会把输入省下的钱花回去。
**怎么验证**：看账单或 usage 字段里的输入/输出拆分，比较两个模型的平均输出 token 数。

### 误区：上下文窗口越大越好

**你以为**：窗口大，什么都能塞，省得做检索。
**其实**：窗口是上限不是目标。塞得越多，成本越高、延迟越大，模型还可能漏掉中间的信息。长上下文有时还有阶梯价。
**怎么验证**：同一批问题，分别用 10k 和 100k 上下文跑，比较通过率、成本和 p95 延迟。

### 误区：开了缓存就一定省钱

**你以为**：供应商支持缓存，打开开关就能打折。
**其实**：缓存要求前缀稳定、在 TTL 内、顺序不变。把时间戳或用户 ID 放在最前面，命中率会是零；缓存写入还可能更贵。
**怎么验证**：看 usage 里的缓存命中 token 数；把系统提示词第一个词改掉，观察命中率是否归零。

### 误区：流式输出能让回答更快

**你以为**：字开始出现得早，总时间就短了。
**其实**：流式只改善首 token 的感知等待，生成总时长不变。Agent 的总时长还是各轮模型加工具时间的累加，流式也解决不了工具慢。
**怎么验证**：分别记录 TTFT 和总时长，改流式开关，看哪个变了、哪个没变。

## 小结

模型选型不能按单价排序，要按"每成功任务成本"算：输入、输出、缓存、重试、工具轮次、人工复核都要进公式。上下文窗口是上限不是目标；输出通常比输入贵；缓存只对稳定前缀有效；流式只改善感知延迟。能力、成本、延迟三角只能取舍，先定硬约束再优化成本。路由、批量、流式各有代价，不能默认省钱。最后，用固定评测集跑候选，看通过率、每成功任务成本和 p95，逐条比较失败类型——选那个"失败也能兜住"的模型。

这条线到这里结束。下一篇没有更深的模型知识，只有一句提醒：**任何选型结论都要用你自己的任务复测，价格和模型版本都会变。**
