## 12,334 个块里排第 99

我拿这个仓库自己的文档试了一次检索：614 篇 markdown，4,842,051 字符，按 400 字符硬切成 12,334 块，然后问 10 个「答案确实在库里」的问题，看答案所在的块排第几。

问 InnoDB 页大小的那道题，答案原话「InnoDB 页 16KB」就写在 `docs/content-rewrite-playbook.md` 里。它排第 99。

探针是我本机用 stdlib 写的，核心就这些（下面所有数字都是它跑出来的）：

```python
import math, re
from collections import Counter
from pathlib import Path

ASCII = re.compile(r"[a-z0-9][a-z0-9_.\-]*")
CJK = re.compile(r"[\u4e00-\u9fff]+")

def terms(text):
    t = text.lower()
    out = []
    for w in ASCII.findall(t):
        if len(w) >= 2 or w.isdigit():
            out.append(w)
    for run in CJK.findall(t):              # 中文没空格：单字 + 相邻二元组
        out.extend(run)
        out.extend(run[i:i + 2] for i in range(len(run) - 1))
    return Counter(out)

class BM25:
    def __init__(self, docs, k1=1.2, b=0.75):   # k1/b 抄 Lucene 老默认，没调
        self.k1, self.b, self.docs, self.n = k1, b, docs, len(docs)
        self.len = [sum(d.values()) for d in docs]
        self.avg = sum(self.len) / self.n
        df = Counter(w for d in docs for w in d)
        self.idf = {w: math.log(1 + (self.n - c + .5) / (c + .5)) for w, c in df.items()}

    def scores(self, q):
        out = [0.0] * self.n
        for w in terms(q):
            idf = self.idf.get(w)
            if idf is None:
                continue
            for i, d in enumerate(self.docs):
                f = d.get(w, 0)
                if f:
                    out[i] += idf * f * (self.k1 + 1) / (
                        f + self.k1 * (1 - self.b + self.b * self.len[i] / self.avg))
        return out
```

另一半是同一批词项的 TF-IDF 余弦（tf=1+log，向量先 L2 归一化），这一路下面统一叫「余弦」。完整脚本还有块大小/切法两组扫描循环，省了。

```text
语料 614 篇 / 4,842,051 字符 → 12334 块（400 字符硬切、无重叠）
建索引 2160 ms
单次 BM25 打分 70.3 ms
单次余弦打分 27.9 ms

问题                                 BM25     余弦    RRF
InnoDB 页大小是多少                        99    170    125
RestartSec 的默认值是多少毫秒                 73     32     48
code-challenge 在一篇课程里至少要几个            1      1      1
迁移文件名该怎么命名                            6     24     14
服务器上的远程测试库能同时跑两轮吗                     1      1      1
e2e 只跑一个文件要多久                         3      6      3
quiz 块能不能删                            1      1      1
新加一个页面要挂到哪里才算上线                       1      7      2
多个会话同时改仓库怎么避免互相踩                      1      1      1
后端单测跑一遍要多久                          933    920   5101
```

Python 3.11.5、纯 Python 单线程、Windows，本机跑出来的。10 个问题里 2 个彻底哑掉，5 个第一名。我原本以为原因是块切得不好——把 400 字符改成 200，块数翻到 24,385，`recall@3` 从 6 掉到 5；改成 1600，块数 3,306，还是 5。块大小动 8 倍，这个数就在 5 到 6 之间晃。所以我的猜测是错的。

## 这套装置能说明什么、不能说明什么

- **金标**：只要某块包含那句答案原话，就算命中。不判这块拿出来是否真能回答问题——口径很粗。
- **recall@k**：前 k 块里有金标的题目数，满分 10。10 题里动一题就是 10 个百分点，没有置信区间可言，我后面不拿 1 题的差当结论。
- **余弦这一路是词面向量的替身，不是神经 embedding**。本机没装模型和向量库，我没有跑过真 embedding。所以本文所有关于「向量」的话，只对「字符二元组 + TF-IDF + 余弦」成立。

## 哑掉的两题，卡在同一个地方

我把每道题前 5 个 idf 最高的词项打出来，跟金标块对照：

| 问题 | 前 5 高权重词项（idf） | 覆盖率 | 排名 |
| --- | --- | --- | --- |
| InnoDB 页大小是多少 | 小是(9.01) 页大(7.55) 是多(6.35) innodb(5.35) 多少(5.33) | 26.2% | 99 |
| RestartSec 的默认值是多少毫秒 | 少毫(9.01) restartsec(7.92) 值是(6.62) 是多(6.35) 毫秒(5.85) | 23.9% | 73 |
| 后端单测跑一遍要多久 | 多久(7.72) 要多(6.40) 端单(5.11) 一遍(4.43) 跑一(4.42) | 20.5% | 933 |
| code-challenge 在一篇课程里至少要几个 | 篇课(9.01) 要几(8.17) 少要(7.92) 里至(7.72) 程里(6.62) | 38.5% | 1 |
| quiz 块能不能删 | 块能(7.92) 能删(6.68) 能不(5.52) quiz(4.39) 不能(3.41) | 60.7% | 1 |

「覆盖率」= 查询词的 idf 权重里，有多少落在金标块中，算法三行：

```python
total   = sum(bm.idf.get(w, 0) for w in terms(q))                     # 查询词项的总权重
in_gold = sum(bm.idf.get(w, 0) for w in terms(q) if w in gold_terms)  # gold_terms = 金标块里词项的并集
cov     = in_gold / total
```

看第一行。「页大小」被切成「页大」「小是」「是多」——中文没有空格，二元组直接跨过词边界造词。这些词在语料里几乎没人写过，所以 df 只有 1，idf 冲到 9.01，权重全押在它们身上；而文档写的是「InnoDB 页 16KB」，这些词项在金标块里一个都没有。BM25 只好拿「页大」「小是」去匹配别人，排到第 99。

第四行是反例：`code-challenge` 前 5 个词项也全是假词，但覆盖率 38.5%，排第 1——因为金标块里有 `code-challenge` 这个唯一的 ASCII 词项，它一个人就够了。

所以这里坏掉的是**分词**，不是打分公式，也不是块大小。同样的病在余弦那一路也一样重（99 对 170、933 对 920，两路都没救回来）——因为余弦用的还是同一批二元组。

## 只改问法：99 到 1

同一道题，只是把问法换成文档里的原词：

```text
InnoDB 页大小是多少 → BM25 99 / 余弦 170   ；改写成「InnoDB 页 16KB」→ BM25 1 / 余弦 1
RestartSec 的默认值是多少毫秒 → BM25 73 / 余弦 32   ；改写成「默认 100ms」→ BM25 3 / 余弦 6
后端单测跑一遍要多久 → BM25 933 / 余弦 920   ；改写成「88 秒 / 410 条」→ BM25 1 / 余弦 1
```

这是上界实验，不是一个能用的方案：第三行等于是把答案抄进查询。它证明的是 rank 主要被「问法与文档用词是否重合」决定。注意第二行只到第 3——改写也不保证第一名，别把它当开关用。

## 症状 → 先看哪

| 症状 | 先量什么 | 判据（下面都是我这 10 题的数） |
| --- | --- | --- |
| 答案明明在库里，块却排到 50 名以后 | 查询词项覆盖率 | 我 10 题正好被 30% 分开：20.5% / 23.9% / 26.2% 的三题排 933 / 73 / 99；30% 以上的七题都在前 6。覆盖率低 → 查分词和问法；覆盖率高 → 才是排序问题 |
| 换块大小、换切法，名次几乎不动 | 同上，再对一遍块大小扫描 | 说明瓶颈不在切块。我 200 到 1600 全在 5–6 之间晃，继续切是白费 |
| 加了一路召回，结果更差 | 两路各自的 recall@k | 融合不会超过最好的那一路。我这里余弦 @1 只有 4，合完 @1 从 5 掉到 4 |
| 检索命中了，但答错 | 打印实际拼进提示词的块 | 块里没有答案原句 = 假命中，问题仍在检索，别去调提示词 |
| 加大 top-k，召回不涨、字符涨 | 平均拼进提示词的字符数 | 我 3→5 是 1,110→1,860 字符，`recall@5` 与 `@3` 都是 6，白花 68% 的上下文 |

## 我把它拼成混合检索，没变好

把两路排序用 RRF 合并（k=60，取每路前 100 名），再对比粗暴的交错合并：

```text
BM25     recall@1 5/10  @3 6/10  @5 6/10
余弦       recall@1 4/10  @3 4/10  @5 4/10
RRF      recall@1 4/10  @3 6/10  @5 6/10
交错合并     recall@1 5/10  @3 5/10  @5 6/10
```

RRF 的 @3 和 @5 与 BM25 打平，@1 反而从 5 掉到 4；交错合并更差。原因不难推：余弦这一路本身只有 4/10，两路又不互补（两个哑掉的方向是一致的——都卡在同一个二元组分词上），RRF 只在名次上做平均，就把差那一路的噪声调进了前排。

「向量补关键词」这句话在方向上不算错，但它是一个**条件**，不是保证：前提是两路真的互补。我这里的第二路是第一路的弱化版，所以融合只能保平或变差。要提精度得靠 rerank（用一个小模型对候选重排），我没装，这一步是空的。

## 切块：我原以为最难，实测不是

| 块大小（硬切、无重叠） | 块数 | BM25@3 | 余弦@3 | RRF@3 |
| --- | --- | --- | --- | --- |
| 200 字符 | 24,385 | 5 | 4 | 4 |
| 400 字符 | 12,334 | 6 | 4 | 6 |
| 800 字符 | 6,326 | 5 | 4 | 4 |
| 1600 字符 | 3,306 | 5 | 5 | 5 |

切法也换了三种（400 字符）：硬切无重叠 12,334 块 `@3` 6；硬切 20% 重叠 15,364 块 6；按句边界 13,854 块 6。三种全打平。

块数差 8 倍、切法差三种，`@3` 都在 5 到 6 之间摆动，一题的差别。在这个语料和这套词面打分下，切块不是主要瓶颈——这跟「切块最重要」的常见说法相反。我只能推翻到这个范围：换成真 embedding，块大小的作用很可能不同，那部分我没测。

## 什么时候这套不划算

- **语料小**：我这里 top-5 就要拼 1,860 字符。如果只有几百条、每次只查一两个问题，全塞进上下文更省事，也不用维护索引和分词。
- **要精确算数或查库**：让模型调 SQL / 函数，别指望「从资料里读数字」再心算。
- **资料本身是错的**：检索只会让错答案显得更有依据，这不是检索能修的。

一个粗略判断：如果「没有这份资料，模型就答不了」，才值得上检索。

## 动手

1. 在你自己的文档上跑这段探针，先量出 `recall@1 / @3`。没有 baseline 就没有「变好了」这句话。
2. 挑 3 道排得很后的题，算覆盖率。低于 30% 的那几道，先改问法重打一次——如果排名跳上去，你的瓶颈也是分词。
3. 加第二路召回前后，各打一次同样的 10 题。我赌它不会更好；如果你那儿它真赢了，说明你那两路确实互补，那就该留着。

## 还差的

1. **神经 embedding 整段没跑**。本机没装模型和向量库，我测的余弦是字符二元组替身。所以「向量检索擅长语义、对精确串不敏感」这句我只能标按文档，无法证实也无法证伪——它跟我这里的现象（两路都卡在用词重合上）不冲突，但也不是一回事。
2. **中文分词没做**。二元组是替身，jieba 没装。覆盖率 30% 那条分界线很可能是分词造出来的假象；换成按词切分，整体水平大概会上移，分界线在哪我不知道。
3. **金标口径太粗、样本太小**。包含那句话就算命中，不判能否回答问题；10 题、动一题 10 个百分点，没有置信区间。
4. **生成端完全没测**。块拼进提示词之后模型答得对不对、1,860 字符会不会把注意力稀释掉，我一点数据都没有。rerank 也没有模型可跑。
5. **成本只是这个规模下的数**。12,334 块建索引 2,160 ms、单次 BM25 70 ms 是纯 Python 单线程；真上服务得换倒排索引或向量库，那套的延迟和内存我没测。
