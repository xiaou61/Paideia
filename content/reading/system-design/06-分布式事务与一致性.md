## 一笔扣款成功了，订单却没建

```text
trace order-9001       手写故障示意，未连真实服务
POST /checkout  user=7  sku=A100  amount=199.00

account-svc  BEGIN
account-svc  UPDATE account SET balance = balance - 199.00
             WHERE user_id = 7 AND balance >= 199.00;   rows=1
account-svc  COMMIT                                        38ms
order-svc    INSERT INTO orders (id, user_id, status)
             VALUES (9001, 7, 'PENDING');
order-svc    ERROR 2013 (HY000): Lost connection to MySQL server during query
order-svc    ROLLBACK
stock-svc    not called
notify-svc   not called

result       HTTP 500
account      balance 801.00（初值 1000.00）
orders       id=9001 0 rows
retry        同一请求再走一遍 -> balance 602.00
```

这段 trace 不是某家公司的事故，也不是数据库回显；它是我按一次失败顺序手写的，金额和 id 都是占位。错误文本用了 MySQL 客户端常见的 2013 格式，但这里没有真实连接，也没有真实 `XA RECOVER` 输出。

我原来以为：

- 把 `debit()` 和 `createOrder()` 包在一个外层方法里，就是一个事务。实际是每个服务各自拿连接，`account-svc` 的 `COMMIT` 已经生效，`order-svc` 的 `ROLLBACK` 只能回滚自己的库。
- `XA PREPARE` 之后进程崩了，MySQL 会自动回滚。实际是 prepared 分支会留在 InnoDB 的恢复日志里，`XA RECOVER` 还能看到；锁也在，等 `XA COMMIT` 或 `XA ROLLBACK`。
- TCC 只要写 Try、Confirm、Cancel 三个方法。实际还要一张 `(xid, branch)` 控制表，处理空回滚、重复 Cancel、迟到 Try。
- outbox 就是把发 MQ 放进数据库事务。实际是 MQ 不参加本地事务；同一个事务里写的是业务表和 outbox 表，投递是另一个进程。
- 最终一致就是数据总会对。实际要同时做到不丢、重复幂等、乱序收敛；做不到时还要有对账和人工。

后面统一用这条主线：订单 9001 创建，库存 A100 预占，账户 7 扣 199.00，最后发 `order.paid` 通知。开场把扣款放在最前面，是为了让半成品显形；顺序改回“下单 → 库存 → 余额 → 通知”后，失败窗口不会消失，只会换一个位置。

## 先把四个词分开

| 词 | 本文用它表示什么 | 它不表示什么 |
| --- | --- | --- |
| 线性一致 | 每个操作在调用与返回之间某个点原子生效，并尊重真实时间顺序 | “顺序一致”，也不同于“读到自己写” |
| 顺序一致 | 存在一个全序，符合每个客户端自己的程序顺序，但不要求真实时间顺序 | 不保证一个客户端刚写完，另一个客户端立刻读到 |
| 读到自己写 | 同一个会话写完再读，至少能看到自己的写 | 不是跨用户、跨区域的全局一致 |
| 最终一致 | 停止写入后，所有副本最终收敛 | 不承诺多久收敛，也不承诺中间读到什么 |

本文说“强一致”时，指线性一致；如果只是“读到自己写”，会单独写。2PC 给的是原子提交，不是自动的线性一致：它是否隔离，取决于参与者有没有对读写都加锁，以及协调者有没有把决定同步下去。2PC 加严格两阶段锁可以得到可串行化，但这不是 2PC 协议本身白送的，也不等于线性一致。

## 2PC 是协议，XA 是接口

2PC 有两个角色：协调者（coordinator）和参与者（participant）。协调者收集投票、把最终决定落盘、再发送 commit 或 abort；参与者执行本地事务、写 prepare 记录、拿住锁、投 yes 或 no。

第一阶段 prepare：参与者把事务做到“可提交但不提交”，写日志并拿锁，然后投票。第二阶段 commit/abort：协调者先把自己的决定持久化，再通知参与者。参与者按决定提交或回滚，释放锁。

XA 是 X/Open DTP 定义的 TM 与 RM 之间的接口规范；2PC 是协议。MySQL 的 `XA START`、`XA END`、`XA PREPARE`、`XA COMMIT` 是 XA 接口在 MySQL 上的实现。你可以自己写一个 2PC 协调器而不用 XA，也可以用一个 XA 实现，但协调器没有高可用。三者不是同义词。

下面 SQL 未实跑：本机测试账号没有建库权限，语法按 MySQL 8.4 文档写。

```sql
-- 未实跑；按 MySQL 8.4 XA 语句文档
XA START 'order-9001-stock';
UPDATE stock
   SET available = available - 1,
       reserved  = reserved  + 1
 WHERE sku = 'A100' AND available >= 1;
XA END 'order-9001-stock';
XA PREPARE 'order-9001-stock';

-- 协调者收齐所有分支的 yes 后
XA COMMIT 'order-9001-stock';
```

如果 `UPDATE` 影响 0 行，应用应当 `XA END` 后 `XA ROLLBACK`，不要 prepare 一个注定失败的分支。

MySQL 8.4 文档说得很清楚：`XA PREPARE` 把事务放进 `PREPARED` 状态，`XA RECOVER` 会把这种事务列出来；只有 `XA COMMIT` 或 `XA ROLLBACK` 才让它结束（[XA 事务状态](https://dev.mysql.com/doc/refman/8.4/en/xa-states.html)）。MySQL 8.4 默认 `xa_detach_on_prepare=ON`，prepare 之后原会话可以去做别的事，但分支仍然是 `PREPARED`，不会自动有结论。文档还写明，`PREPARED` 状态的元数据锁会跨客户端断开和服务器重启保留，直到显式提交或回滚（[元数据锁](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)）。InnoDB 的行锁同样不会在 prepare 时释放。

| 故障点 | 参与者状态 | 结果 |
| --- | --- | --- |
| prepare 前崩 | 本地事务还没 prepared | 恢复时回滚；协调者收不到 yes，发 abort |
| prepare 后、commit 前崩 | `PREPARED` | 恢复后仍在；`XA RECOVER` 可见；锁不释放，等决定 |
| 协调者在决定落盘前崩 | in-doubt | 参与者不知道 commit 还是 rollback，只能等协调者恢复或人工处理 |
| 协调者在决定落盘后崩 | 决定已持久化 | 恢复后重发 commit 或 abort，参与者最终结束 |
| 网络分区 | 部分参与者收到 commit | 已提交的分支不能撤回；协调者重试，恢复前不是原子可见 |

2PC 的两个真实缺陷：

1. **协调者是逻辑单点。** 可以用 Raft 或数据库复制协调者状态，降低恢复时间；但复制不会消掉 in-doubt，也不会消掉参与者已经持有的锁。
2. **prepare 后长时间占锁。** 协调者慢、网络分区、等人工审批，都会把锁持有时间拉长。别的请求等到锁等待超时后失败，这不是“高可用”，只是把阻塞换成了错误。

所以 2PC 适合：短、低并发、所有参与者都支持 XA、并且在同一个信任域内。它不适合等支付回调、等人工审批、跨第三方系统的流程。

## TCC：三个方法只是接口，正确性在状态表

TCC 把两阶段搬到业务层：

| 阶段 | 账户 user=7 | 库存 A100 |
| --- | --- | --- |
| Try | `balance-199`，`frozen+199` | `available-1`，`reserved+1` |
| Confirm | `frozen-199` | `reserved-1`，`sold+1` |
| Cancel | `balance+199`，`frozen-199` | `available+1`，`reserved-1` |

这里的 `balance` 是**可动用余额**，`frozen` 是已冻结金额；`frozen` 不包含在 `balance` 里，不要再把 `frozen` 加回 `balance`。Try 提交后行锁释放，但冻结额度还在，别的请求只能花 `balance`。

控制表至少要能回答“这个分支有没有 Try 过、现在是什么终态”：

```sql
CREATE TABLE tcc_branch (
  xid        VARCHAR(64)  NOT NULL,
  branch_id  VARCHAR(64)  NOT NULL,
  status     VARCHAR(16)  NOT NULL,  -- TRIED / CONFIRMED / CANCELLED
  amount     DECIMAL(12,2) NOT NULL,
  created_at DATETIME     NOT NULL,
  updated_at DATETIME     NOT NULL,
  PRIMARY KEY (xid, branch_id)
);
```

Try 要先用唯一键占住分支，再改资源；两步在同一个本地事务里：

```sql
-- Try；未实跑
BEGIN;
INSERT INTO tcc_branch (xid, branch_id, status, amount, created_at, updated_at)
VALUES ('g-9001', 'account-7', 'TRIED', 199.00, NOW(), NOW());

UPDATE account
   SET balance = balance - 199.00,
       frozen  = frozen  + 199.00
 WHERE user_id = 7 AND balance >= 199.00;
-- 若 UPDATE 影响 0 行，ROLLBACK，Try 失败
COMMIT;
```

控制行和账户更新在同一个库，才能靠一个本地事务保证“要么都成功，要么都没有”。如果资源在另一个服务里，不能靠这条 SQL 保证原子，必须让那个服务自己也做幂等预留。

重复 Try 撞到唯一键 1062 时，不要直接当失败：

- 读到 `TRIED` 或 `CONFIRMED`：说明第一次 Try 已经成功，返回第一次的成功结果；
- 读到 `CANCELLED`：说明 Cancel 已经先到，拒绝这次 Try，不能预留；
- 并发的两个 Try 会靠唯一键串行化，后到的那个等前一个提交或回滚后再判断。

Cancel 要处理空回滚和重复调用：

```text
-- Cancel；伪代码，未实跑
BEGIN;
INSERT INTO tcc_branch (xid, branch_id, status, amount, created_at, updated_at)
VALUES ('g-9001', 'account-7', 'CANCELLED', 199.00, NOW(), NOW())
ON DUPLICATE KEY UPDATE status = status;

SELECT status FROM tcc_branch
 WHERE xid = 'g-9001' AND branch_id = 'account-7'
 FOR UPDATE;

if status == 'TRIED':
    UPDATE account
       SET balance = balance + 199.00,
           frozen  = frozen  - 199.00
     WHERE user_id = 7 AND frozen >= 199.00;
    UPDATE tcc_branch
       SET status = 'CANCELLED', updated_at = NOW()
     WHERE xid = 'g-9001' AND branch_id = 'account-7' AND status = 'TRIED';
    COMMIT;
elif status == 'CANCELLED':      # 空回滚或重复 Cancel
    COMMIT;
else:                            # CONFIRMED
    ROLLBACK; alert;
```

Confirm 也必须在控制行上做条件判断：

```text
-- Confirm；伪代码，未实跑
BEGIN;
SELECT status FROM tcc_branch
 WHERE xid = 'g-9001' AND branch_id = 'account-7'
 FOR UPDATE;

if status == 'TRIED':
    UPDATE account
       SET frozen = frozen - 199.00
     WHERE user_id = 7 AND frozen >= 199.00;
    UPDATE tcc_branch
       SET status = 'CONFIRMED', updated_at = NOW()
     WHERE xid = 'g-9001' AND branch_id = 'account-7' AND status = 'TRIED';
    COMMIT;
elif status == 'CONFIRMED':
    COMMIT;                      # 幂等
else:                            # CANCELLED 或没有记录
    ROLLBACK; alert;
```

释放或确认时，如果 `UPDATE account` 影响 0 行，不要继续改控制表状态；回滚并告警，说明控制表和账户已经不一致。

三个异常要分别有判据：

| 异常 | 触发 | 错误写法的后果 | 判据与写法 |
| --- | --- | --- | --- |
| 空回滚 | Try 没执行，Cancel 到了 | Cancel 直接 `balance+199`，凭空多钱 | 控制表没有记录时插入 `CANCELLED` 墓碑，返回成功，不动资源 |
| 幂等 | Cancel 或 Confirm 被重试 | 重复退款、`frozen` 变负 | `(xid, branch)` 唯一；读到终态直接返回成功；状态更新带 `AND status='TRIED'` |
| 悬挂 | Cancel 先成功，Try 后到 | 迟到的 Try 又冻结一笔，永远没人确认或取消 | Try 先占控制行；读到 `CANCELLED` 就拒绝；唯一键把 Cancel 和 Try 串行化 |

TCC 的失败表：

| 失败点 | 结果 | 处理 |
| --- | --- | --- |
| Try 执行前崩 | 没有控制记录 | Cancel 走空回滚，写 `CANCELLED`，返回成功 |
| Try 执行中崩 | 本地事务回滚 | 同上；不会留下半条预留 |
| Try 成功但响应丢失 | 控制行是 `TRIED` | 重复 Try 读到 `TRIED`，返回第一次的成功结果 |
| Cancel 重试 | 控制行已是 `CANCELLED` | 直接成功，不再释放第二次 |
| Confirm 在 Cancel 之后到 | 状态是 `CANCELLED` | 冲突，回滚并告警，不能强行确认 |

TCC 的隔离性来自“预留”，不是数据库隔离级别。别的请求能看到 `frozen` 这一列，读接口要把它展示成“处理中”或过滤掉；写接口只检查 `balance`，不要把 `frozen` 加回可用余额。

## Saga：补偿是新的业务操作

Saga 把长流程拆成一串本地事务，每一步提交后立刻生效；某一步失败，就按相反顺序执行前面各步的补偿。订单 9001 的主线可以写成：

| 步骤 | 正向操作 | 补偿操作 |
| --- | --- | --- |
| 1 | 创建订单 9001，状态 `PENDING` | 订单改 `CANCELLED` |
| 2 | 库存 A100：`available-1`，`reserved+1` | `available+1`，`reserved-1` |
| 3 | 账户 7：`balance-199`，写支付流水 | 写退款流水，`balance+199` |

发通知不是第 4 个需要回滚的 Saga 步骤；它用 outbox 异步发，失败重试；是否退款由业务决定。Saga 的边界是“业务上能补偿的范围”，不是整条链路。

如果第 3 步扣款失败：先补偿第 2 步释放库存，再补偿第 1 步取消订单。顺序必须反向，不能先取消订单、再让库存继续占着。如果第 2 步预占失败，只补偿第 1 步。如果第 3 步之后还有必须成功的步骤（例如创建履约单），该步骤失败才补偿 3→2→1；通知本身不在回滚链里，通知失败重试 outbox，不要因为一条通知把已经完成的支付退掉。

补偿不是回滚：

- 退款是一笔新的支付交易，可能失败、可能收手续费、可能延迟到账；
- 释放库存是加回 `available`，不是撤销历史；
- 已经发出的短信、已经寄出的实物，没有真正的“撤销”，只能拦截、退货或人工处理；
- 补偿本身也可能失败，不能静默跳过。

补偿失败的处理要落表：

| 故障 | 处理 |
| --- | --- |
| 某一步补偿失败 | 该步标 `COMPENSATION_FAILED`，按退避重试，超过上限进人工队列并告警 |
| 补偿被重复调用 | 用 `compensation_key` 唯一键或状态机，重复调用返回已补偿 |
| 补偿根本做不到 | 不要放进 Saga；放最后一步，或走人工/售后 |
| 编排器崩溃 | `saga_step` 持久化每一步状态，恢复后从最后一个已落盘步骤继续 |

一个最小状态机是：

```text
STARTED -> DONE -> COMPENSATING -> COMPENSATED
                         \-> COMPENSATION_FAILED -> 人工队列
```

Saga 没有全局隔离。第 3 步已经扣款、订单还没进入稳定终态时，用户能看到“已支付但订单还没履约”；别的请求也可能读到这个中间态。一种做法是加 `PENDING`、`RESERVING` 这类过程状态，对外只展示稳定状态，关键资源先预留而不是直接扣减。但这些是业务补丁，不是 Saga 自带的隔离。

和 TCC 的取舍：

| 维度 | TCC | Saga |
| --- | --- | --- |
| 资源要求 | 必须能预留 | 必须能补偿 |
| 隔离性 | 预留状态挡住重复消费，比 Saga 强 | 基本没有，中间态对外可见 |
| 接口 | Try、Confirm、Cancel | 正向操作、补偿操作 |
| 适合 | 资金冻结、库存预留、较短流程 | 长流程、跨多个服务、可人工介入 |
| 主要坑 | 空回滚、幂等、悬挂 | 补偿失败、补偿不可逆、中间态 |

## outbox：同一个本地事务写业务表和消息表

先把错误写法摆出来：

```text
-- 错：publish 在事务里，但 MQ 不参加这个事务
BEGIN;
UPDATE orders SET status = 'PAID' WHERE id = 9001 AND status = 'RESERVED';
publish('order.paid', ...);
COMMIT;
```

这里有三个失败窗口：

- publish 成功，数据库回滚：消息已经发出去，订单却没改，消费端收到一条“幽灵已支付”；
- 数据库提交，publish 失败：订单已支付，通知永远没发；
- publish 在事务里，不等于 MQ 和数据库在同一个事务里；MQ 没有义务跟着你的 `ROLLBACK` 回滚。

正确做法是把业务写入和待发消息放进同一个本地事务：

```sql
-- 未实跑；按 MySQL 8.4 语法
BEGIN;

UPDATE orders
   SET status = 'PAID'
 WHERE id = 9001 AND status = 'RESERVED';

INSERT INTO outbox (id, topic, payload, status, retry_count, next_retry_at, created_at)
VALUES (
  'evt-9001-paid',
  'order.paid',
  '{"order_id":9001,"version":3}',
  'pending',
  0,
  NOW(),
  NOW()
);

COMMIT;
```

只有 `orders` 和 `outbox` 都提交，事件才存在；两者在同一个库、同一个本地事务里，数据库替你把这一半的原子性做完了。MQ 仍然不在这个事务里，所以还需要一个 relay。

这不等于跨服务强一致：它只保证本地业务和事件一起提交，消费端仍然是最终一致。

```sql
CREATE TABLE outbox (
  id            VARCHAR(64)  NOT NULL,
  topic         VARCHAR(64)  NOT NULL,
  payload       JSON         NOT NULL,
  status        VARCHAR(16)  NOT NULL DEFAULT 'pending',
  retry_count   INT          NOT NULL DEFAULT 0,
  next_retry_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_at    DATETIME     NOT NULL,
  sent_at       DATETIME     NULL,
  PRIMARY KEY (id),
  KEY idx_outbox_pending (status, next_retry_at)
);
```

relay 的最小伪代码：

```text
rows = SELECT id, topic, payload
         FROM outbox
        WHERE status = 'pending' AND next_retry_at <= NOW()
        ORDER BY id
        LIMIT 100
        FOR UPDATE SKIP LOCKED;

for row in rows:
  try:
    publish(row.topic, row.payload)       # 等 broker confirm
    UPDATE outbox
       SET status = 'sent', sent_at = NOW()
     WHERE id = ? AND status = 'pending';
  catch:
    UPDATE outbox
       SET retry_count = retry_count + 1,
           next_retry_at = ...
     WHERE id = ? AND status = 'pending';
```

这段是伪代码；真实 relay 会先把行 claim 成 `sending` 或写 `locked_until`，再在事务外 publish，避免持锁做网络 IO。

如果 publish 成功、标记 `sent` 失败，消息会重复发；如果 publish 失败，行还在 `pending`，下一轮继续。两种情况都不会因为“进程崩了”把已提交事件丢掉，代价是可能重复。**先标记 sent 再 publish 会把重复换成丢失**，不要这么做。

消费端要把去重记录和业务更新放在同一个事务：

```sql
-- 未实跑
BEGIN;

INSERT INTO consumed_messages (consumer, message_id)
VALUES ('order-paid', 'evt-9001-paid');

UPDATE orders
   SET status = 'PAID', version = 3
 WHERE id = 9001 AND status = 'RESERVED' AND version = 2;

COMMIT;
```

四种结果要分开处理：

- 插入 `consumed_messages` 撞唯一键：这条消息处理过，回滚当前事务，然后 ack；
- 业务更新 0 行，且当前 `version >= 3`：旧消息或重复消息，ack；
- 业务更新 0 行，且当前 `version < 2`：乱序，前面的版本还没到，回滚并稍后重试，不能直接 ack 把事件丢掉。
- 业务更新 0 行，且当前 `version = 2` 但状态不是 `RESERVED`：状态机冲突，告警或进人工，不要当成功。

“最终一致”不是一句口号，至少要能验证三件事：

| 条件 | 证据 | 不满足会怎样 |
| --- | --- | --- |
| 消息不丢 | 在数据库不丢盘的假设下：业务和 outbox 同事务；relay 重试；publisher confirm；失败进死信或告警 | 订单已支付，通知永远没发 |
| 重复可幂等 | `consumed_messages` 唯一键、业务唯一键或状态机 | 重复退款、重复发货、重复加积分 |
| 乱序可收敛 | 事件带 `version`，消费端只接受合法状态流转；版本跳跃时重试或缓冲，超过上限进死信或人工 | 后发的旧事件把新状态覆盖回去 |

再加一条对账：每天用支付流水对 `orders`，用 `stock.reserved` 对未完成订单。对账不是“最终一致”的替代品，它是发现永久缺口的手段。没有对账，系统只能声称自己最终会一致，不能证明。

## 同一笔订单，四种方案各怕什么

| 故障 | 2PC / XA | TCC | Saga | outbox |
| --- | --- | --- | --- | --- |
| prepare 后进程崩 | 分支停在 `PREPARED`，锁在；`XA RECOVER` 后等决定 | Try 的本地事务要么已提交为 `TRIED`，要么完全没有 | 已提交步骤不回滚；编排器从持久化状态继续或补偿 | 业务和 outbox 同事务，要么都有，要么都没有 |
| 消息发失败 | 纯数据库 2PC 不覆盖；MQ 也支持 XA 并加入全局事务才覆盖 | Confirm 重试；控制表保证不重复确认 | 补偿重试；通知交给 outbox | 行留在 `pending`，relay 重试 |
| 消费重复 | 不涉及消息消费 | Confirm 或 Cancel 读到终态，返回成功 | 补偿用 `compensation_key` 去重 | `consumed_messages` 唯一键或状态机 |
| 消费乱序 | 不涉及消息消费 | 分支状态机拒绝非法顺序 | 事件版本加状态机 | `version` 检查；版本跳跃时重试，不 ack |
| 补偿失败 | 参与者回滚失败，需要人工检查 | Cancel 重试、告警；不能假装成功 | 标 `COMPENSATION_FAILED`，进人工队列 | 不适用；消费失败进死信 |

## 决策表：先问约束，再选方案

| 数据一致性要求 | 是否跨库 | 能否改业务 | 选哪个 | 代价 |
| --- | --- | --- | --- | --- |
| 单库内原子提交 | 否 | 不需要 | 本地事务 | 没有跨服务成本 |
| 跨库原子提交，短、低并发、同信任域、RM 支持 XA | 是 | 不需要 | 2PC / XA | 协调者高可用、prepare 锁、in-doubt 人工 |
| 跨服务，资源可预留，能接受最终一致，但不想让重复请求花掉冻结金额 | 是 | 能，写 Try/Confirm/Cancel | TCC | 控制表、空回滚、幂等、悬挂、业务侵入 |
| 长流程，步骤可补偿，中间态可展示 | 是 | 能，写正向和补偿 | Saga | 无全局隔离、补偿失败人工、补偿不可逆要排除 |
| 单向状态同步或通知，可等几秒 | 是 | 不需要大改 | outbox + 幂等消费 | relay、去重、乱序处理、清理 |
| 第三方不参与，无法 prepare | 是 | 不能改对方 | 本地记录 + 对账 + 人工 | 没有原子性，只能发现和修 |
| 必须线性一致或读到自己写 | 可能 | 可能要改 | 单库、共识系统或会话粘滞 | 延迟、可用性、分区代价 |

四条否决线：

- 能用一个本地事务解决，就不要跨库。
- 有不可补偿的副作用，就不要塞进 Saga 假装能回滚。
- 外部系统不配合，就不要要求对方 prepare；做本地记录、对账、人工。
- 没有幂等和对账，就不要上任何分布式事务；重试只会把错误放大。

## 验证时看什么

下面三条是验证动作，本文没有在本机实跑；有测试库时再做。

- 2PC：在一个连接里 `XA START`、`XA END`、`XA PREPARE`，断开后用另一个连接 `XA RECOVER`，看分支是否还在；再显式 `XA COMMIT` 或 `XA ROLLBACK`。
- outbox：停掉 relay，提交一笔业务，查 `orders` 和 `outbox` 是否同时出现；重启 relay，看消费端是否只改一次。
- 消费：把同一个 `message_id` 投两次；再把 `version=3` 的消息放在 `version=2` 前面，观察订单是重试等待，还是被旧消息覆盖。
