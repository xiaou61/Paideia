## 先把结论摆出来

**分布式事务不是"一个更大的事务"，而是一组在失败时还能收敛的协议和模式。** 跨网络不存在真正的原子提交，你只能在三种代价里选一种：

```sketch
{
  "title": "跨网络没有原子提交，只有三种代价",
  "rows": [
    [
      { "id": "strong", "title": "强一致", "sub": "慢，还要协调者", "tone": "amber" },
      { "id": "eventual", "title": "最终一致", "sub": "快，但中间看得见不一致", "tone": "blue" },
      { "id": "compensate", "title": "补偿", "sub": "先做，失败再反着做回去", "tone": "green" }
    ]
  ],
  "arrows": [
    { "from": "strong", "to": "eventual" },
    { "from": "eventual", "to": "compensate" }
  ]
}
```

| 方案 | 一致性 | 隔离性 | 主要代价 | 适合什么 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 有（靠锁） | 阻塞、协调者单点、锁持有时间长 | 短事务、低并发、同信任域 |
| TCC | 最终一致 | 业务预留 | 每个服务写三个接口，处理空回滚与悬挂 | 资金、库存等需要预留的资源 |
| Saga | 最终一致 | 基本没有 | 每一步都要能补偿，中间态对外可见 | 长流程、跨多个服务、可人工介入 |
| 本地消息表 / outbox | 最终一致 | 没有 | 只支持单向通知，消费端必须幂等 | 状态同步、事件通知、绝大多数业务 |

一句话选型：**能用本地事务解决就不要跨库；必须跨库时，优先 outbox，其次 Saga，只有短而强的事务才考虑 2PC/TCC。**

## 问题从哪来：一次下单要改四个库

单体应用里，下单是一个本地事务：

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
UPDATE stock SET qty = qty - 1 WHERE sku = 'A100' AND qty >= 1;
UPDATE account SET balance = balance - 199.00 WHERE user_id = 7 AND balance >= 199.00;
COMMIT;
```

四条语句要么全成功，要么全回滚，数据库替你把原子性做完了。

拆成微服务之后，这四件事落在四个库、四个进程里：

```text
订单服务      → order_db
库存服务      → stock_db
账户服务      → account_db
优惠券服务    → coupon_db
```

每个服务只能保证自己的本地事务。订单库提交成功之后，库存服务可能超时、可能失败、可能成功但响应丢了。于是出现各种半成品状态：

| 进行到哪 | 失败点 | 结果 |
| --- | --- | --- |
| 订单已创建 | 扣库存失败 | 有订单，没库存，用户付不了 |
| 订单、库存都成功 | 扣款失败 | 库存被占，钱没扣，商品卖不出去 |
| 三步都成功 | 通知发货失败 | 用户付了钱，货不发 |
| 任意一步超时 | 不知道成没成 | 重试可能重复，不重试可能漏 |

分布式事务要解决的就是这张表。注意它有两个维度，很多人只盯着第一个：

- **原子性**：最终要么全成，要么全败；
- **隔离性**：中间状态会不会被别的请求看到。

2PC 两样都给，但代价大；TCC、Saga、outbox 主要给原子性（而且是最终收敛的），隔离性要靠业务自己补。

## 2PC：用锁和阻塞换原子性

两阶段提交（Two-Phase Commit）有一个协调者（coordinator）和若干参与者（participant）。

**第一阶段：准备。** 协调者问所有参与者"能不能提交"。参与者执行事务但不提交，锁住相关行，写 undo/redo 日志，然后投票 yes 或 no。

**第二阶段：提交或回滚。** 如果所有参与者都投 yes，协调者发 commit；只要有一个投 no，就发 rollback。

MySQL 的 XA 语法大致是这样：

```sql
XA START 'order-9001';
UPDATE stock SET qty = qty - 1 WHERE sku = 'A100' AND qty >= 1;
XA END 'order-9001';
XA PREPARE 'order-9001';

-- 协调者确认所有参与者都 prepare 成功后
XA COMMIT 'order-9001';
```

看起来很美，但失败模式很难缠：

| 故障 | 后果 |
| --- | --- |
| 参与者在 prepare 前崩溃 | 协调者收不到票，超时后回滚，其他参与者释放锁 |
| 参与者 prepare 后、commit 前崩溃 | 它已锁住资源，等协调者恢复后决定提交还是回滚 |
| 协调者在发出 commit 前崩溃 | 所有参与者停在 prepared 状态，**一直持有锁**，直到协调者恢复 |
| 网络分区 | 部分参与者收到 commit，部分没收到，系统停在不确定状态 |

最后一种叫 **in-doubt 事务**。参与者不知道该怎么办，只能等；这期间它锁着的行谁都改不了。对高并发系统来说，这等于把可用性押在协调者身上。

2PC 还有几个固有成本：

- **同步阻塞**：整个事务期间锁不释放，吞吐上不去；
- **协调者单点**：协调者挂了，恢复前所有参与者都在等；
- **锁跨网络**：准备阶段到提交阶段之间的时间被网络往返放大；
- **不适合长流程**：如果要等人工审批、等第三方回调，锁会持有几分钟甚至几小时。

所以 2PC 适合的是：**短、快、低并发、所有参与者都支持 XA、且在同一信任域内**。比如同一个公司内部两个数据库之间转一笔账，操作在毫秒级完成。它不适合"下单后等支付回调"这种流程。

## TCC：把数据库锁换成业务预留

TCC 把两阶段搬到业务层，每个参与服务实现三个接口：

| 阶段 | 做什么 | 例子 |
| --- | --- | --- |
| Try | 检查并**预留**资源 | 冻结 199 元、预占 1 件库存 |
| Confirm | 确认使用预留资源 | 把冻结的钱真正扣掉 |
| Cancel | 释放预留资源 | 解冻 199 元、释放库存 |

以账户为例：

```sql
-- Try：余额够就冻结，不够就失败
UPDATE account
   SET balance = balance - 199.00,
       frozen  = frozen  + 199.00
 WHERE user_id = 7 AND balance >= 199.00;

-- Confirm：冻结转为已扣（钱已经不在 balance 里了）
UPDATE account
   SET frozen = frozen - 199.00
 WHERE user_id = 7 AND frozen >= 199.00;

-- Cancel：解冻，把钱还回可用余额
UPDATE account
   SET balance = balance + 199.00,
       frozen  = frozen  - 199.00
 WHERE user_id = 7 AND frozen >= 199.00;
```

和 2PC 的区别是：TCC 在 Try 之后**不持有数据库行锁**，只持有业务上的"冻结"状态。这样其他请求还能操作这一行（比如查余额），系统不会因为等确认而阻塞。代价是：

1. 每个服务都要实现 Try/Confirm/Cancel 三个接口；
2. 三个接口都必须幂等；
3. 必须处理空回滚与悬挂（下一节讲）；
4. 业务侵入大——不是所有资源都能"预留"，比如已经发出去的短信没法冻结。

TCC 还需要一张事务记录表，记录全局事务和分支状态：

```sql
CREATE TABLE tcc_transaction (
  xid        VARCHAR(64) NOT NULL,
  branch     VARCHAR(64) NOT NULL,
  status     VARCHAR(16) NOT NULL,  -- TRYING / TRIED / CONFIRMING / CONFIRMED / CANCELLING / CANCELLED
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  PRIMARY KEY (xid, branch)
);
```

推进状态用条件更新，重复的 Confirm/Cancel 就不会重复执行：

```sql
UPDATE tcc_transaction
   SET status = 'CONFIRMED'
 WHERE xid = ? AND branch = ? AND status = 'TRIED';
```

影响行数为 0，说明已经确认过或状态不对，直接返回成功即可。

## Saga：一串本地事务加补偿

Saga 的思路最直白：把长流程拆成一串本地事务，每一步提交后立刻生效；某一步失败，就按相反顺序执行前面各步的**补偿**。

以"下单 → 扣款 → 扣库存 → 发货"为例：

| 步骤 | 正向操作 | 补偿操作 |
| --- | --- | --- |
| 1 | 创建订单 | 取消订单 |
| 2 | 扣款 | 退款 |
| 3 | 预占库存 | 释放库存 |
| 4 | 通知发货 | 拦截发货（如果还没发） |

有两种编排方式：

- **编排式（orchestration）**：一个 Saga 协调器按顺序调用各服务，失败时调用补偿。流程集中，容易看全貌，但协调器要持久化状态。
- **协同式（choreography）**：各服务监听事件，自己决定下一步。耦合低，但流程散在各处，出问题难追。

Saga 最容易被低估的是**补偿不是回滚**：

- 退款是一笔新的支付交易，可能失败、可能收手续费、可能 T+1 到账；
- 释放库存不等于库存回到原样——如果这期间被别人买走，释放的是"预留"而不是"已售"；
- 发货一旦发生，补偿只能是"拦截"或"退货"，不是把时间倒回去；
- 补偿本身也可能失败，需要重试、告警、人工介入。

Saga 还没有隔离性。第 2 步扣款成功、第 3 步库存失败的那几秒里，用户看到的是"已支付但没库存"，别的请求也可能读到这个中间态。解决办法通常是：

- 给业务加中间状态（`PENDING`、`RESERVING`），对外只展示稳定状态；
- 关键资源做预留，而不是直接扣减；
- 读接口过滤掉未完成的流程；
- 产品上接受"处理中"，不要假装瞬间完成。

Saga 适合长流程、跨多个服务、能定义补偿、允许最终一致的场景。它不适合"补偿代价极大"或"根本不能补偿"的动作，比如已经寄出的实物、已经发出的短信。

## 本地消息表 / outbox：最常用的最终一致

大多数业务不需要 2PC、TCC、Saga 那么重。它们需要的只是：**A 服务改了数据，B 服务最终也要改，而且不能因为中间失败而丢事件。**

做法是把"业务写入"和"待发消息"放在同一个本地事务：

```sql
CREATE TABLE outbox (
  id         VARCHAR(64) NOT NULL,
  topic      VARCHAR(64) NOT NULL,
  payload    TEXT        NOT NULL,
  status     VARCHAR(16) NOT NULL,   -- pending / sent / failed
  retry_count INT        NOT NULL DEFAULT 0,
  created_at DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_outbox_status_created (status, created_at)
);
```

```sql
BEGIN;

UPDATE orders SET status = 'paid' WHERE id = 9001 AND status = 'paying';

INSERT INTO outbox (id, topic, payload, status, created_at)
VALUES ('evt-9001-paid', 'order.paid', '{"order_id":9001}', 'pending', NOW());

COMMIT;
```

一个 relay 进程轮询 `pending`，发到 MQ 后标记 `sent`：

```text
SELECT * FROM outbox WHERE status='pending' ORDER BY created_at LIMIT 100;
  → publish 到 MQ
  → UPDATE outbox SET status='sent' WHERE id=? AND status='pending';
```

如果 relay 在"publish 成功、标记 sent 失败"之间崩溃，消息会重复发；如果 publish 失败，消息还留在表里，下一轮继续。两种情况都不会丢，代价是可能重复——所以消费端必须幂等（上一篇讲过的去重表 + 状态机）。

outbox 的优点：

- 不需要协调者，不需要跨库锁；
- 不引入新的中间件就能保证"业务成功则事件一定发出"；
- 失败可重试、可查询、可人工补发；
- 延迟可控（轮询间隔），也能换成 CDC 读 binlog 降低延迟。

缺点：

- 只能做单向通知，不适合"必须立刻知道对方结果"的同步决策；
- 消费端必须幂等；
- outbox 表需要清理，否则会膨胀；
- 轮询有延迟，CDC 方案则增加运维复杂度。

**绝大多数"微服务之间同步状态"的需求，outbox 就够了，不需要分布式事务框架。**

## 补偿与悬挂：两个必须写进状态机的坑

TCC 和 Saga 都依赖补偿，而补偿有两个经典故障，必须在设计时写进状态机。

### 空回滚

协调者让分支执行 Cancel，但 Try 根本没执行（比如 Try 超时，协调者以为失败）。Cancel 到了，此时没有资源可释放。

如果 Cancel 直接执行"解冻 199 元"，就会把用户的钱凭空增加。正确做法是：Cancel 先查事务记录，没有 Try 记录就记一条"已取消"，然后直接返回成功，**不做任何资源操作**。

### 悬挂

空回滚之后，迟到的 Try 又到了。如果 Try 正常执行，资源被预留，但协调者已经认为这个分支取消了，永远不会有人来 Confirm 或再次 Cancel——资源就永久冻在那里。

```text
Try（网络延迟，晚到）
  ← Cancel（先到，记录 CANCELLED）
  → Try 到达，必须被拒绝
```

修法还是状态机 + 条件更新：

```sql
-- 只有从未出现过取消记录，才允许 Try
INSERT INTO tcc_transaction (xid, branch, status, ...)
VALUES (?, ?, 'TRYING', ...);

-- 如果该分支已是 CANCELLED，插入或更新失败，Try 直接返回"已取消"
UPDATE tcc_transaction
   SET status = 'CANCELLED'
 WHERE xid = ? AND branch = ? AND status IN ('TRYING', 'TRIED');
```

更简单的做法是给 `(xid, branch)` 建唯一键，用一行记录贯穿整个生命周期：

```text
(无记录) --Try--> TRYING --Confirm--> CONFIRMED
                     ↘ Cancel --> CANCELLED
CANCELLED + 迟到的 Try --> 拒绝（这就是防悬挂）
```

三个动作都必须是幂等的：重复 Try 返回第一次的结果，重复 Confirm/Cancel 直接成功。

## 隔离性：分布式事务里最容易被忽略的部分

2PC 在提交前一直持有锁，所以别的请求看不到中间状态；TCC、Saga、outbox 都没有这个保证。

| 方案 | 隔离性从哪来 | 中间态可见吗 |
| --- | --- | --- |
| 2PC | 数据库行锁 | 不可见（但代价是阻塞） |
| TCC | 业务预留 + 状态字段 | 预留状态可见，需读接口过滤 |
| Saga | 业务状态机 | 可见，且可能持续数秒到数小时 |
| outbox | 无 | 可见，直到消费完成 |

因此使用 Saga/TCC 时，必须回答：

- 别的请求读到"订单已支付但库存未预占"会怎样？
- 报表统计到中间态会不会多算？
- 用户刷新页面看到"处理中"能不能接受？

常见做法是给业务加"稳定状态"和"过程状态"两层：数据库里存细粒度状态，对外接口只暴露稳定状态，或者把过程状态标成"处理中"。

如果你需要严格的跨服务隔离（比如"任何时刻都不能读到未完成的转账"），那就不要用 Saga/TCC 硬凑——要么把这些数据放回同一个数据库用本地事务，要么用单写者/串行化设计。**隔离性是最贵的，通常不值得为它牺牲整个系统的可用性。**

## 一张选型表

| 维度 | 2PC / XA | TCC | Saga | outbox |
| --- | --- | --- | --- | --- |
| 一致性 | 强一致 | 最终一致 | 最终一致 | 最终一致 |
| 隔离性 | 有 | 业务级 | 无 | 无 |
| 延迟 | 高（锁 + 两次网络往返） | 中 | 取决于流程长度 | 低（异步） |
| 业务侵入 | 低（用现成 XA） | 高（三接口） | 中（正向 + 补偿） | 低 |
| 失败处理 | 协调者恢复 | Confirm/Cancel 重试 | 补偿重试 + 人工 | relay 重试 + 消费幂等 |
| 典型场景 | 同域短事务、金融内部转账 | 资金冻结、库存预留 | 订单履约、跨服务长流程 | 状态通知、事件驱动 |

## 什么时候不该上分布式事务

这一段比前面所有方案都重要。以下几种情况，正确答案是"不要用"：

**一、一个数据库能解决。** 如果两个服务的数据其实在同一个库，或者可以放进同一个库，就用本地事务。为了"微服务架构"把本来强关联的数据拆到两个库，再上分布式事务，是自找复杂度。

**二、流程很长、并发很高。** 2PC 的锁扛不住；TCC 要为每个资源设计预留；Saga 要处理大量中间态。先问业务能不能接受最终一致，能就不要强一致。

**三、有无法补偿的副作用。** 短信已发、邮件已发、实物已寄出，这些动作没有真正的"撤销"。把它们放在流程最后一步，或者用"尽力而为 + 人工"处理，不要塞进 Saga 假装能回滚。

**四、外部系统不配合。** 第三方支付、物流、银行接口不会参与你的 XA 或 TCC。你只能做本地记录 + 对账 + 补偿，不能要求对方 prepare。

**五、团队还没有幂等和对账能力。** 分布式事务的每一步都依赖重试，而重试依赖幂等。没有上一篇的幂等键、去重表、状态机，上任何分布式事务框架都只会把重复执行放大。

判断顺序可以固化成四问：

1. 能不能放进一个本地事务？
2. 不能的话，业务能不能接受几秒到几分钟的最终一致？
3. 每个失败步骤有没有可执行的补偿？
4. 有没有对账机制发现"最终没一致"的单？

四问的答案决定你选 outbox、Saga、TCC 还是 2PC，而不是反过来先选框架。

## 一个具体例子：下单、扣库存、支付

把方案落到一条真实链路。假设订单服务、库存服务、支付服务各自独立。

### 步骤与失败处理

| 步骤 | 操作 | 失败时怎么办 |
| --- | --- | --- |
| 1 | 创建订单，状态 `PENDING` | 直接返回失败，不留数据 |
| 2 | 预占库存：`available-1, reserved+1` | 订单置 `CANCELLED`，结束 |
| 3 | 发起支付 | 支付失败：释放库存，订单 `CANCELLED` |
| 4 | 支付成功回调 | 订单 `PENDING → PAID`，写 outbox |
| 5 | 通知履约 | 消费端幂等，失败重试；超过上限进死信 |

库存预占用条件更新，天然防超卖：

```sql
UPDATE stock
   SET available = available - 1,
       reserved  = reserved  + 1
 WHERE sku = 'A100' AND available >= 1;
```

影响行数为 0 就是库存不足。注意这里不需要分布式事务——"不能超卖"是库存行上的本地约束，必须同步成立。

订单状态机：

```text
PENDING --预占成功--> RESERVED --支付成功--> PAID --发货--> SHIPPED
   |                     |
   +--预占失败--> CANCELLED
                         +--支付失败--> CANCELLING --释放库存--> CANCELLED
```

支付回调可能重复，用支付流水号做唯一键；订单状态更新带前置条件：

```sql
UPDATE orders SET status = 'PAID'
 WHERE id = 9001 AND status = 'RESERVED';
```

重复回调影响 0 行，直接返回成功。

### 补偿失败怎么办

假设第 3 步支付失败，需要释放库存，但库存服务此刻挂了。流程不能停在"订单取消、库存还占着"：

1. 把"释放库存"写成一条待办（本地消息表/outbox），由后台重试；
2. 重试有上限，超过后进死信并告警；
3. 每天对账：`reserved` 总量与未完成订单占用量比对，发现差异自动修正或人工处理。

这就是"最终一致"的真实含义：**不是不会失败，而是失败会留下可追踪、可重试、可对账的记录，最终收敛。**

### 对账是最后一道防线

无论用 2PC 还是 Saga，都要有对账：

| 对账项 | 数据来源 A | 数据来源 B | 差异处理 |
| --- | --- | --- | --- |
| 支付金额 | 支付网关账单 | `payments` 表 | 补记或退款 |
| 库存占用 | `stock.reserved` | 未完成订单汇总 | 释放或补占 |
| 订单状态 | 订单库 | 支付/库存事件 | 重放事件或人工修 |

没有对账的"最终一致"，只是"希望它一致"。

## 与上一篇的分工

两篇解决的是不同层次的问题：

| | 第 05 篇 | 第 06 篇 |
| --- | --- | --- |
| 范围 | 单个请求、单次调用 | 多个服务、多个资源 |
| 问题 | 超时后重试会不会重复 | 一步失败，前面几步怎么收场 |
| 工具 | 幂等键、去重表、状态机、退避重试 | 2PC、TCC、Saga、outbox、补偿 |
| 前提 | 无 | 每一步内部都必须是幂等的 |

顺序不能反：**06 的每个正向操作和补偿操作，内部都依赖 05 的幂等。** 没有幂等，Saga 重试补偿会重复退款，TCC 重复 Confirm 会重复扣钱，outbox 重复投递会重复发货。

所以实践中的组合通常是：

```text
outbox（06）+ 消费端去重表（05）+ 状态机（05/06）+ 对账（06）
```

而不是单独上一个"分布式事务中间件"就结束。

## 常见误区

### 误区：分布式事务就是"把本地事务放大"

**你以为**：加一个框架或注解，跨库也能像本地事务一样原子提交。
**其实**：跨网络没有真正的原子提交。2PC 用锁和阻塞换原子性，TCC 用业务预留换，Saga 用补偿换，outbox 用最终一致换。每一种都有中间态和失败路径，必须显式处理。
**怎么验证**：在流程第二步提交后 kill 掉服务，观察系统能否自动收敛；再查有没有补偿任务、死信队列和对账记录。没有这些，"事务"只是表面成功。

### 误区：有了 Saga，就不需要幂等

**你以为**：失败会补偿，重复执行也没关系。
**其实**：Saga 的每一步和补偿都可能被重复调用。没有幂等，重试会重复扣款、重复退款、重复释放库存。补偿不是"撤销键"，它本身也是一次业务操作。
**怎么验证**：把补偿接口连续调用两次，看余额或库存是否只恢复一次；再把正向接口重复调用，看是否产生两条记录。

### 误区：最终一致就是"数据总会对，不用管"

**你以为**：消息会一直重试，最后一定成功。
**其实**：重试有上限，毒消息会进死信；消费者可能永久失败，消息可能被误删。没有对账和告警，"最终"可能永远不到。
**怎么验证**：把消费者改成永久抛异常，观察是否有死信告警、是否有对账任务发现差异、是否能人工补发。三者缺一，就不能声称系统是最终一致的。

## 小结

四种方案可以这样记：

- **2PC**：锁住所有人，等协调者发话。强，但慢且怕协调者挂。
- **TCC**：先冻结，再确认或解冻。不占数据库锁，但要写三个接口，还要防空回滚与悬挂。
- **Saga**：一步步做，失败就倒着补偿。适合长流程，但补偿不是回滚，中间态对外可见。
- **outbox**：业务和消息同库同事务，异步投递、消费幂等。最常用，也最容易被低估。

选型先问四件事：能不能本地事务？能不能接受最终一致？每一步有没有补偿？有没有对账？四问答完，方案基本就定了。

最后一句话：**分布式事务的目标不是"永不失败"，而是"失败也能收敛，并且有人知道它没收敛"。**
