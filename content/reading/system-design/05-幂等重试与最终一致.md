## 3 秒超时、4 秒到账：一笔 199 元被扣了四遍

先把一屏真东西放上来。本机回环（Windows 11 + Python 3.11.5），服务端用一个 sleep 4 秒的 handler 假装支付网关，客户端 3 秒超时，超时后按 0 / 1.2 / 1.2 秒的间隔重试三次，SQLite 当账本：

```text
回环端口 = 47262，服务端处理耗时 4.0s，客户端超时 3.0s

=== A. 不带幂等键：客户端 3 秒超时后按上面的节奏重试 ===
  第 1 次尝试：
  [t= 3.01s] TIMEOUT（没等到响应）                                本次耗时 3.01s
  第 2 次尝试（上一次是超时/409，按退避再打一次）：
  [t= 6.02s] TIMEOUT（没等到响应）                                本次耗时 3.02s
  第 3 次尝试（上一次是超时/409，按退避再打一次）：
  [t=10.24s] TIMEOUT（没等到响应）                                本次耗时 3.01s
  第 4 次尝试（上一次是超时/409，按退避再打一次）：
  [t=14.44s] TIMEOUT（没等到响应）                                本次耗时 3.00s
→ payments 表 4 行，合计 796.0 元；幂等键表 0 行

=== B. 带幂等键 pay-9001-20261119：同样的超时与重试 ===
  第 1 次尝试：
  [t= 3.01s] TIMEOUT（没等到响应）                                本次耗时 3.01s
  第 2 次尝试（上一次是超时/409，按退避再打一次）：
  [t= 3.01s] HTTP 409  {"error":"processing"}              本次耗时 0.00s
  第 3 次尝试（上一次是超时/409，按退避再打一次）：
  [t= 4.22s] HTTP 200  {"payment_id": 1795073814384, "order_id": 9001, "amount": "199.00"} 本次耗时 0.00s
  第 4 次尝试（上一次是超时/409，按退避再打一次）：
  [t= 5.42s] HTTP 200  {"payment_id": 1795073814384, "order_id": 9001, "amount": "199.00"} 本次耗时 0.00s
→ payments 表 1 行，合计 199.0 元；幂等键表 1 行
```

我原来以为这类事故长这样：请求失败 → 重试 → 最多是「多发一次」。实际是 **每一次重试都是一次全新的扣款**：A 组四次尝试、四行 payments、796 元。它们每一笔都「成功」了，只是前三次的响应都在客户端超时之后才写回，客户端看不到。

B 组里有三个细节值得停一下：

- 第 2 次重试拿到 **409**，不是 200。因为第一次请求还在处理中，键在表里、状态是 `processing` 而不是 `done`。这个中间态既不是成功也不是失败，实现时很容易漏掉。
- 第 3、4 次拿到 200，`payment_id` 一模一样的 `1795073814384`。这是回放第一次的响应，不是又扣了一次。
- 键只挡住重复**执行**，不改变「客户端前 3 秒白等」这个事实。它换的是钱不重复，不是体验不变。

示意图（本次实验的参数，不是测量值）：

```text
客户端 3.0s 放弃 ───X─── 响应在半路丢了
服务端 4.0s 才扣完款            ↑ 这 1 秒差就是重复扣款的窗口
```

只要操作会改状态，就把「它已经执行过了」当成默认假设。这不是悲观，是上面那 4 行 payments 的后验概率。

## 键选错，等于没做幂等

幂等的定义简单：同一个请求执行一次和十次，最终状态与返回结果一样。落地时真正决定成败的是**键**。

| 重试时带的键 | 服务端会发生什么 |
| --- | --- |
| 每次请求新生成的 UUID | 每次都是新键，去重表一行都撞不上，等于没做 |
| 当前时间戳 | 同一次操作的两次重试时间不同，永远撞不上 |
| 订单号 + 操作类型（`9001:pay`） | 稳定、天然唯一；代价是同一订单的两次「独立」支付无法区分 |
| 客户端在用户点「支付」那一瞬间生成的 UUID，整次操作复用 | 稳定；前提是这个键被存下来（订单草稿里），而不是每次点击重新生成 |
| 数据库自增 id | 服务端才有，客户端第一次请求时还拿不到 |

规则一句话：**键必须在第一次尝试之前生成，并在所有重试里保持不变。** 前端这里有一种很典型的错法：重试时重新 `crypto.randomUUID()`——那一行代码会把整个幂等设计变成摆设。

服务端那一侧，最小的去重表长这样：

```sql
CREATE TABLE idempotency (
  idempotency_key VARCHAR(64) NOT NULL,
  status          VARCHAR(16) NOT NULL,   -- processing / done
  response_body   TEXT        NULL,
  created_at      DATETIME    NOT NULL,
  PRIMARY KEY (idempotency_key)
);
```

处理流程三步，第二步的每个分支都要有明确动作：

```text
1. INSERT ... ('processing')
   成功  → 我是第一个，往下执行业务
   1062  → 别人先进来了，进第 2 步
2. 读出这一行：
   done       → 原样回放 response_body，别重新执行业务
   processing → 409，让调用方退避后再来（不是失败，也不是重复执行）
   行不存在   → 竞态：重新从 1 开始，或直接 500
3. 业务写完，在同一个事务里把 status 改成 done 并存下响应
```

两个必做项，和上面 409 那个格子是一件事的两面：

- **必须存响应体，不能只存一个「已处理」标记。** 否则重试拿到的是空响应，客户端不知道成功还是失败，又去重试第三次。
- **业务写入和状态更新必须同一个事务。** 先写业务再改去重表，崩在中间就是「钱扣了，键还卡在 processing」——之后每一次重试都拿到 409，直到 TTL 或人工清掉。反方向则可能「标记完成但业务没做」。

所以去重表需要一列时间戳加一个回收动作：`processing` 超过 N 秒的记录，要么当失败允许重试，要么报警让人看。**没有这个回收，processing 就是一个可能永久卡死的状态。**

## 去重放到数据库里，Redis 只当前置

最自然的优化是「用 Redis 的 `SET NX` 挡住重复，省一次数据库往返」。它确实能挡并发，但挡不住时间。下面是本机 Redis 8.6.2 的实测，临时实例 `127.0.0.1:6390`（配置文件里 `save ""` + `appendonly no`，测完 `SHUTDOWN NOSAVE`）：

```text
--- 窗口一：拿到键的 worker 崩了，业务没做 ---
> SET idem:pay-9001 worker-a NX EX 60    -> OK
> SET idem:pay-9001 worker-b NX EX 60    -> (nil)
  worker-a 在 SET 之后、扣款之前被 kill -9（这里用「不再执行任何事」代替）
  2 秒后客户端重试同一笔：SET idem:pay-9001 worker-c NX EX 60 -> (nil)
  键的剩余 TTL：57 秒 —— 这 60 秒里谁也做不了这笔业务

--- 窗口二：TTL 比「客户端退避重试的跨度」短 ---
> SET idem:pay-9002 worker-a NX EX 2     -> OK
  立刻 PTTL：1824 ms
  3 秒后重试：SET idem:pay-9002 worker-b NX EX 2 -> OK
  （返回 OK = worker-b 认为自己是第一个，业务会被执行第二次）
```

两个窗口的方向是相反的，这是关键：

| Redis 里键的状态 | 这次请求看到什么 | 谁来兜底 |
| --- | --- | --- |
| 键刚被抢走，抢到的 worker 随后崩了 | 重试拿到 `(nil)`，被判成「重复，跳过」 | 没人。只能等 TTL（实测剩余 57 秒） |
| TTL 比调用方重试窗口短 | 重试拿到 `OK`，业务被执行第二遍 | 只有业务表上的唯一索引能拦 |
| 两个客户端同一瞬间 SET NX | 一个 `OK` 一个 `(nil)` | 这一层 Redis 是对的，但它只覆盖「同一瞬间」 |

结论不是「Redis 不行」，而是**它的语义只到「这个键现在存在」**：既不知道业务有没有做完，也不负责在过期后阻止第二次执行。所以：

- Redis 可以做第一层过滤，把同一瞬间涌进来的重复请求挡在数据库之前，省掉那一次往返；
- 最终依据必须是**和业务写入在同一个事务里**的唯一索引 / 去重表；
- 键的 TTL 要明显长于调用方可能的重试总时长（我上面那个 2 秒 TTL 对上 3 秒退避，直接漏了）。

补一句按文档而不是实测的部分：Redis 默认用 RDB 落盘，具体丢多少秒取决于 `redis.conf` 的 `save` 策略和最近一次写盘的间隔。我这个实例把持久化关了，所以「重启后键没了」这件事我没法当作测量证据——但它在该发生的时候一定发生，这也是「Redis 不能当唯一依据」的原因之一。

## 重试：只看三类结论，只在一层做

「失败就重试」不是策略，重试要按拿到的结果分类：

| 拿到什么 | 该做什么 |
| --- | --- |
| 超时、连接重置、503、504、429 | 退避后重试 |
| 400、401、403、404、422 | 不重试。重试一万次也不会变对 |
| 409（`processing`） | 不要立刻重试，退避后再来；别当成失败直接执行 |
| 500 | 分不清「处理中崩了」和「没处理」，非幂等写一律按「可能已执行」处理 |

顺带把两个常见的错说法拧正：

- **「GET/PUT/DELETE 是幂等方法，所以重试安全」只是语义约定。** RFC 9110 定义的是「预期效果相同」，它约束的是你的实现**应该**这样，不是框架帮你保证。一个 PUT 里写了 `views = views + 1`，它照样不幂等；反过来，一个带幂等键的 POST 可以安全重试。方法名不是保险。
- **「HTTP 幂等所以重试安全」同理**：真正决定安全的是服务端那一侧的键和唯一索引，不是请求行里的动词。

然后是放大。本机起了四个回环服务，网关 → A → B → 下游，每层最多 3 次尝试，最下游永远返回 503 并计数：

```text
三层嵌套重试（网关 → A → B → 下游，每层最多 3 次尝试）
  客户端只发 1 次请求 → HTTP 503，最下游被打了 27 次
  只让客户端重试 3 次（链路内不重试）→ 最下游被打了 3 次
```

27 是 `3 × 3 × 3`。注意它的含义不是「重试了 27 次」，而是「1 个用户请求变成了 27 个下游请求」——下游本来只是慢，现在是被自己人的重试按在地上。修法不是把每层次数降到 2（那还是 8），而是**选一层负责重试**（一般是入口或消息消费者），其余层拿到失败就快速返回，再配熔断，让下游持续失败时上游直接停手。

抖动的作用是另一件事，也是实测的：

```text
8 个客户端同时失败、都在 200ms 后重试，服务端看到的到达时间跨度：
  固定 200ms，无抖动     ：   7.4 ms
  全抖动 random(0,200ms)： 184.7 ms
```

没有抖动时，8 个客户端在 7 毫秒内一起到；有抖动时摊到 185 毫秒里。这里要说清是哪种抖动——`random(0, cap)` 叫 full jitter，`cap/2 + random(0, cap/2)` 是另一种常见写法，`min(cap, base × 2^attempt) × random(0.5, 1.0)` 又是第三种。它们都只是「把同时变成不同时」，不改变总请求数。

最后是预算。三次约束缺一不可：最大次数、总超时、单次退避上限。回头看第一屏 A 组：

```text
第 1 次尝试 [t= 3.01s]  →  第 2 次 [t= 6.02s]  →  第 3 次 [t=10.24s]  →  第 4 次 [t=14.44s]
```

如果用户在第 10 秒就关掉了页面，第 4 次在 14.4 秒完成的那笔扣款，用户没见过、前端不知道、订单服务也没收到通知——一笔「没有任何人知道」的扣款。**重试的总时长必须小于上游愿意等的时长**，否则重试只是在制造无人认领的副作用。

## outbox：把「两件事一起成功」换成「一件事 + 一个轮询」

支付服务成功后要通知订单服务。两个方向的双写都会坏，而且坏法不同（本机 SQLite，进程崩溃用「不再执行剩下的语句」模拟）：

```text
=== 1. 先提交本库、再发消息，发之前进程被 kill ===
   payments=1 行, orders.status=pending, MQ 实收 0 条 → 用户付了钱，订单永远待支付

=== 2. 先发消息、再提交本库（更糟的那个方向）===
   消费者立刻处理 → applied, changes=1
   payments=0 行, orders.status=paid, MQ 实收 1 条 → 订单已支付，但支付记录不存在

=== 3. outbox：relay 在 publish 成功、标记 sent 之前崩溃 ===
   业务与 outbox 同事务提交：payments=1 行, outbox pending=1 条
   消费者收到第 1 条 → applied, changes=1
   relay 在 UPDATE outbox SET status='sent' 之前崩溃，pending 仍是 1 条
   relay 重启后又发一次 → duplicate, 回滚后 ack（订单不会再改）
   MQ 实收 2 条（重复 1 条），消费成功 1 次、判重 1 次，payments=1 行, orders.status=paid
```

第 1 种是丢，第 2 种是假——两种都在「两件事必须一起成功」这个前提上崩掉。outbox 把这两件事改成一件事加一个可重放的搬运工：

```sql
BEGIN;

INSERT INTO payments(order_id, status) VALUES (9001, 'succeeded');

INSERT INTO outbox(id, payload, status)
VALUES ('evt-9001-paid', '{"order_id":9001,"amount":"199.00"}', 'pending');

COMMIT;
```

relay 只做三件事，注意最后那条 `UPDATE` 的条件：

```text
SELECT id, payload FROM outbox WHERE status = 'pending' ORDER BY created_at LIMIT 100
  → publish
  → UPDATE outbox SET status = 'sent' WHERE id = ? AND status = 'pending'
```

崩溃点就在 publish 和 UPDATE 之间。探针里 relay 崩在那里，重启后同一条消息又发了一次，MQ 一共收到 2 条。**outbox 消除的是「丢」，不消除「重」**，它把问题从「消息可能没了」换成了「消息可能重复」——而重复是幂等能处理的。

所以消费端才是这套东西的另一半：去重记录和业务更新必须同事务，业务更新要带前置状态。

```sql
BEGIN;

INSERT INTO consumed(consumer, msg_key) VALUES ('order-paid', 'evt-9001-paid');

UPDATE orders SET status = 'paid' WHERE id = 9001 AND status = 'pending';

COMMIT;
```

撞唯一键就回滚 + ack；`UPDATE` 影响 0 行不是错误，是「这一步已经做过了」——探针里第二次投递的 `changes=0` 就是这个意思。前置状态条件（`AND status = 'pending'`）让状态机本身成为一层幂等，重复的「支付成功」回调最多把它推进一步。

再补一条按文档写的（我做的是单 relay，没并发）：多实例 relay 并发扫同一批 pending 行，会出现重复投递和乱序，要么加 `SELECT ... FOR UPDATE SKIP LOCKED`（MySQL 8.0+、PostgreSQL 9.5+ 支持），要么就老实跑单实例。

如果你要的是「两个服务、两个库之间怎么完成一件事」，那是下一篇的范围（2PC / TCC / Saga 各付什么代价）；这篇只处理「一个库 + 一个下游」这一层。

## 收敛窗口和对账

这套链路不是瞬间一致的：用户看到支付成功时，订单页可能还是「待支付」。窗口的大小是可以算的：relay 的轮询间隔 + 消费耗时 + 重试带来的额外延迟。我的玩具（0 间隔轮询、单实例、内存库）是毫秒级——**这个数字不能当 SLO**，它把真实环境里真正花钱的部分全省掉了：网络往返、并发下的锁争用、以及从库延迟。

产品上能做的三件事：

- 支付结果页读支付服务的状态，别去读订单状态；
- 订单页轮询或推送，直到状态收敛，而不是让用户手动刷新碰运气；
- 给「支付成功 → 订单可见已支付」打点，p99 从数据里来，先量再定。

还有一格不在最终一致的可接受范围里：**读自己的写**。用户改完昵称立刻刷新，读到从库的旧值，会以为保存失败。对他来说这不是「等一会儿会一致」，而是「你的系统把我的修改弄丢了」。做法是写完之后短时间内路由到主库，或者等从库的同步位点追上，而不是靠时间。

对账是最后一道：拿支付网关的账单对 `payments` 表，把差异分成「多单」（有支付记录、网关没有）和「漏单」（网关有、没有记录）两类，分别走退款和补单。没有对账的最终一致，等于把账挂在一个没人看的表上。

## 还差的

- **MQ 的投递语义只按文档写，没有实跑。** 探针里的「MQ」是一个 Python list。Kafka 那侧我引用的是官方文档的口径：3.0 起 producer 的 `enable.idempotence` 默认开启、`acks` 默认 `all`；幂等生产靠每个分区的序列号去重，broker 只保留最近若干个批次的序列号，超出这个范围的重复它认不出来，所以去重范围是「同一个 producer 会话 × 同一个分区」，不是「全集群按业务键」。而「exactly-once」只覆盖「从 Kafka 读 → 处理 → 写回 Kafka → 提交 offset」这条链路，一旦处理里写了 MySQL 或调了支付网关，落库那一步就不在这个事务里。这两句我都没在本机验证过。
- **支付网关侧的「商户请求号去重」没有 API key，只能按文档描述。** 它对请求号保留多久、跨不跨商户、对同号不同金额的处理方式，取决于具体网关，我没法给你一个能照抄的结论。
- **`kill -9` 是用「不再执行剩下的语句」模拟的。** 真实崩溃还牵涉连接池里的半开事务、数据库的锁等待超时、以及服务端把响应写进一个已断开的 socket 这些行为，我都没测。
- **去重表与 outbox 的清理、并发 relay 没压过。** 保留期取多久、按时间分区还是批量删除、`SKIP LOCKED` 在真实数据量下的争用，都停在「知道该怎么做」的层面。
- **跨机房与时钟偏斜没考虑进来。** TTL、退避、`created_at` 排序在有真实网络延迟和时钟偏差时会发生什么，这篇给不出数。
