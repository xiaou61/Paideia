## 先把结论摆出来

**网络调用失败时，你通常不知道事情到底发生没发生。** 超时不是"失败"，是"结果未知"。在这个前提下，"失败就重试"是一个会重复扣款的危险动作。

所以这一篇的结论只有四句：

1. 绝大多数消息与 RPC 的投递语义是**至少一次**，重复是常态；
2. 想要业务上的"恰好一次"，靠的不是更强的网络，而是**幂等**——同一个请求执行一次和执行多次，结果一样；
3. 重试必须带**上限、退避和抖动**，并且只在一层重试，否则会把下游打死；
4. 跨服务的最终一致，靠**本地事务 + outbox + 下游幂等消费**，不是靠"再发一次消息试试"。

一篇讲清这四件事。下一篇讲多个服务之间怎么组织"全成或全败"，这一篇先把单个请求的重复问题解决掉。

## 失败不是没发生，而是你不知道它发没发生

一次 RPC 调用只有三种真实结局：

| 结局 | 调用方看到什么 | 实际发生了什么 |
| --- | --- | --- |
| 成功 | 正常响应 | 对方处理完了 |
| 明确失败 | 连接被拒绝、4xx | 对方没处理 |
| **未知** | 超时、连接重置、5xx | 可能没收到，可能处理到一半，也可能已经成功只是响应丢了 |

第三种最危险。很多代码把它当成第二种处理：捕获超时，打印"支付失败"，然后让用户重试。可服务端可能已经在 3.1 秒时扣了款，只是响应在路上丢了。

```text
客户端 3 秒超时 ──X── 响应丢失
服务端 4 秒完成扣款 ── 成功
用户点"重试" ── 第二次扣款
```

这不是极端情况。网络抖动、负载均衡摘节点、下游 GC 停顿，都会制造这种"客户端认为失败、服务端已经成功"的窗口。**只要操作会改变状态，就必须假设它可能被执行两次。**

## 幂等是什么：不是"不执行"，是"执行多次效果一样"

幂等的定义很朴素：

```text
f(f(x)) = f(x)
```

对接口来说，同一个请求发一次和发十次，最终状态与返回结果都相同。

注意它不等于"第二次直接拒绝"。查询天然幂等；`UPDATE account SET balance = 100 WHERE id = 1` 也是幂等的（重复执行结果一样）；而 `UPDATE account SET balance = balance - 100` 不是——每执行一次就少 100。

实现幂等最常用的工具是**幂等键**（idempotency key）：调用方为"一次业务操作"生成一个唯一标识，重试时复用同一个键；服务端用唯一索引或去重表保证这个键只被真正处理一次。

关键是键的选择：

| 选什么做键 | 是否合适 | 原因 |
| --- | --- | --- |
| 订单号 + 操作类型 | 合适 | 业务上唯一，跨重试稳定 |
| 客户端生成的 UUID，只生成一次 | 合适 | 同一次操作的所有重试共用它 |
| 每次请求新生成的 UUID | **不合适** | 每次重试都是新键，等于没去重 |
| 当前时间戳 | **不合适** | 重试时间不同，无法识别重复 |
| 数据库自增 id | **不合适** | 那是服务端生成的，调用方重试时还没有 |

一句话：**幂等键必须由调用方在第一次尝试前生成，并在所有重试中保持不变。**

## 去重表：把"只处理一次"落到数据库上

最可靠的去重不是放在内存或 Redis 里，而是和业务数据放在同一个数据库，用唯一索引兜底。一张最小的去重表：

```sql
CREATE TABLE idempotency (
  idempotency_key VARCHAR(64)  NOT NULL,
  status          VARCHAR(16)  NOT NULL,   -- processing / done / failed
  response_code   INT          NULL,
  response_body   TEXT         NULL,
  created_at      DATETIME     NOT NULL,
  updated_at      DATETIME     NOT NULL,
  PRIMARY KEY (idempotency_key)
);
```

处理流程分三步：

```text
1. INSERT INTO idempotency (key, status, ...) VALUES (?, 'processing', ...)
   - 成功：我是第一个，继续执行业务
   - 唯一键冲突（1062）：说明有人先来了，跳到第 2 步
2. SELECT status, response_* FROM idempotency WHERE key = ?
   - done：直接返回当时保存的响应
   - processing：返回 409 或"处理中，请稍后重试"，不要重复执行
   - failed：按业务决定是否允许重试
3. 业务执行完，在同一个事务里把 status 改成 done，并保存响应
```

两个容易漏的点：

- **必须保存响应，而不只是"已处理"标记。** 否则重试拿不到第一次的结果，客户端看到的是空响应或错误。
- **状态更新要和业务写入在同一个事务里。** 如果先写业务、再改去重表，中间崩溃会留下"业务成功但键还是 processing"的记录，后续重试永远卡住；反过来先改去重表再写业务，则可能"标记完成但业务没做"。

去重表会一直增长，需要按时间清理或分区。一般保留 24 小时到 7 天，取决于业务允许客户端重试多久。清理不能影响正在处理中的键。

## 至少一次、至多一次与"恰好一次"

三种投递语义经常被混着说：

| 语义 | 保证 | 代价 | 典型实现 |
| --- | --- | --- | --- |
| 至多一次 | 最多送到一次，可能丢 | 不重试 | 发完即忘 |
| 至少一次 | 一定送到，可能重复 | 需要重试 + 去重 | 绝大多数 MQ、RPC 重试 |
| 恰好一次 | 不丢不重 | 极难跨系统保证 | 单系统事务内、Kafka 事务链路 |

"恰好一次"在跨系统时几乎做不到。Kafka 的事务能做到"消费—处理—提交 offset"在 Kafka 内部原子，但你的处理还要写 MySQL、发短信、调支付网关——这些外部副作用不在 Kafka 的事务里。**消息系统能保证的是"投递"，不是"你的业务只发生一次"。**

工程上的正确目标叫**效果上恰好一次**（effectively-once）：

```text
至少一次投递 + 消费端幂等去重 = 业务效果只发生一次
```

所以不要把精力花在"找一款保证不重复的 MQ"上，花在"重复来了我也不怕"上。

## 重试的四条纪律

重试不是 `catch { sleep(1); retry(); }`。它至少有四条约束：

**第一，只重试安全操作。**

- 读请求、幂等写可以重试；
- 非幂等写必须先有幂等键；
- 明确不可重试的错误（400、401、403、404、422）不要重试，重试一万次也不会变对。

**第二，只重试瞬时错误。**

超时、连接重置、429、502、503、504 值得重试；参数错误、业务规则拒绝不值得。把"余额不足"重试三次，只会让日志更脏。

**第三，必须有预算。**

最大次数、总超时、退避上限，三者缺一不可。一个常见策略：

```text
第 1 次失败：等 100ms ± 随机
第 2 次失败：等 200ms ± 随机
第 3 次失败：等 400ms ± 随机
第 4 次失败：等 800ms ± 随机（封顶 2s）
第 5 次失败：放弃，进入死信或人工处理
```

公式是：

```text
sleep = min(cap, base × 2^attempt) × random(0.5, 1.0)
```

乘一个随机因子叫**抖动**（jitter）。没有抖动时，一次下游故障会让所有客户端在同一毫秒重试，形成整齐的脉冲，把刚恢复的下游再次打挂。

**第四，只在一层重试。**

如果网关重试 3 次、服务 A 重试 3 次、服务 B 再重试 3 次，最坏情况下游会收到 27 次调用：

```text
客户端 → 网关（3 次）→ 服务 A（3 次）→ 服务 B（3 次）
最坏放大 = 3 × 3 × 3 = 27
```

这叫**重试风暴**。下游已经过载时，重试会继续增加它的负载，形成拥塞崩溃。正确做法是选一层负责重试（通常是入口或消息消费者），其他层快速失败；同时配合熔断，在下游持续失败时直接拒绝，不再放大流量。

## 一个支付例子：从重复扣款到最终一致

假设用户下单后调用支付服务，支付服务再通知订单服务。把上面所有概念放进一条链路。

### 没有幂等键时

```text
1. 客户端 POST /payments {order_id: 9001, amount: 199.00}
2. 支付服务扣款成功，写 payments 表，返回响应
3. 响应在返回途中丢失，客户端 3 秒超时，判定失败
4. 客户端自动重试同一个请求
5. 支付服务再扣一次 199.00
```

用户被扣了 398 元，订单只标记了一笔。对账时才发现，退款又要走一轮人工流程。

### 加上幂等键

客户端在第一次请求前生成键 `pay-9001-20261026`，所有重试都带同一个键：

```text
1. 支付服务 INSERT idempotency(key='pay-9001-20261026', status='processing')
2. 调用支付网关，把 key 作为商户请求号传下去（网关侧也去重）
3. 扣款成功，同一个事务里：
   - UPDATE payments SET status='succeeded' WHERE order_id=9001
   - UPDATE idempotency SET status='done', response_body='...' WHERE key=...
4. 客户端重试，INSERT 撞唯一键 → 读到 done → 原样返回第一次的响应
```

这里有三层幂等：客户端复用键、支付服务用去重表、支付网关用商户请求号。任何一层重试，都不会产生第二笔扣款。

### 通知订单服务：outbox

支付成功后要告诉订单服务"已支付"。直接"先提交数据库，再发 MQ"有两个失败窗口：

```text
先提交 DB，再发 MQ：
  DB 成功，MQ 发送失败 → 用户付了钱，订单永远待支付

先发 MQ，再提交 DB：
  MQ 成功，DB 回滚 → 订单收到"已支付"，但支付记录不存在
```

这叫**双写问题**。解法是把消息和业务写在同一个本地事务里：

```sql
BEGIN;

UPDATE payments
   SET status = 'succeeded'
 WHERE order_id = 9001 AND status = 'processing';

INSERT INTO outbox (id, topic, payload, status, created_at)
VALUES ('evt-9001-paid', 'order.paid', '{"order_id":9001,"amount":"199.00"}', 'pending', NOW());

COMMIT;
```

然后用一个 relay 进程轮询 `outbox`，把 `pending` 的消息发到 MQ，发送成功后标记 `sent`。如果 relay 在"发送成功、标记失败"之间崩溃，消息会重复发送——没关系，消费端幂等。

```text
relay：SELECT * FROM outbox WHERE status='pending' ORDER BY created_at LIMIT 100
      → 逐条 publish
      → UPDATE outbox SET status='sent' WHERE id=? AND status='pending'
```

订单服务的消费者用消息 id 或订单号做去重，并且把"去重记录 + 订单状态更新"放在同一个事务里：

```sql
BEGIN;

INSERT INTO consumed_messages (consumer, msg_key) VALUES ('order-paid', 'evt-9001-paid');

UPDATE orders
   SET status = 'paid'
 WHERE id = 9001 AND status = 'pending';

COMMIT;
```

如果 `consumed_messages` 插入撞唯一键，说明这条消息处理过：回滚当前事务，然后直接 ack 返回。注意：去重记录必须和业务更新同事务，否则"记了已消费但订单没改"或"订单改了但没记已消费"都会出问题。

### 最终一致的时间窗口

这套链路不是瞬间一致的。用户可能先看到"支付成功"，订单页还显示"待支付"，几百毫秒到几秒后才变。产品上要接受这个窗口：

- 支付结果页直接展示支付服务的状态，不依赖订单状态；
- 订单页轮询或推送，直到状态收敛；
- 给这个窗口定一个 SLO，例如 p99 小于 2 秒；
- 每天用支付网关账单与 `payments` 表对账，修正漏单、多单。

**最终一致不是"不管"，是"知道它多久会一致，以及不一致时谁来修"。**

## 状态机：让重复请求自然变成空操作

比"记住处理过"更稳的做法，是让业务状态只允许单向流转：

```text
created → paying → paid → shipped
              ↘ failed
paid → refunded
```

每次更新都带上前置状态：

```sql
UPDATE orders SET status = 'paid'
 WHERE id = 9001 AND status = 'paying';
```

重复的"支付成功"回调再来一次，`status` 已经是 `paid`，影响行数为 0，天然幂等。应用看到 0 行就知道"这次不用做任何事"，而不是报错或重复发货。

状态机还有两个好处：

1. 非法流转会被数据库拦住，不依赖每个调用方都记得检查；
2. 排查时看一眼状态就知道流程停在哪一步。

配合唯一约束（订单号、支付流水号、消息 id），大部分重复问题在数据层就解决了，不需要应用层写复杂的判断。

## 去重表怎么设计才不拖垮系统

去重表本身也是表，设计不好会成为新的瓶颈：

| 设计点 | 建议 | 原因 |
| --- | --- | --- |
| 主键 | `(consumer, msg_key)` 或单独 key | 唯一索引是去重的核心 |
| 行宽 | 只存必要字段，响应体可截断 | 大字段会让索引和缓存变重 |
| 保留期 | 按业务重试窗口设定，定期清理 | 无限增长会拖慢插入与备份 |
| 清理方式 | 按时间分区或批量删除 | 大事务删除会锁表 |
| 热点 key | 同一 key 并发时靠唯一索引串行化 | 不要先查后插，存在竞态 |
| Redis 前置 | 可以做第一层过滤 | Redis 会丢数据/过期，DB 唯一索引才是最终依据 |

如果只用 Redis `SETNX` 做幂等，会有两个风险：Redis 重启或过期后键没了，重复请求会再次执行；以及"SETNX 成功但业务没执行完就崩溃"，键却已经存在，后续重试被误判为已处理。前者靠 DB 兜底，后者靠"处理中"状态和超时回收。

## 什么情况下"最终一致"不可接受

最终一致很好用，但不是所有场景都能等：

| 场景 | 能不能最终一致 | 原因 |
| --- | --- | --- |
| 支付成功后发短信/积分 | 可以 | 晚几秒无损失 |
| 订单状态同步到报表 | 可以 | 有对账兜底 |
| 秒杀库存扣减 | **不可以只靠最终一致** | 超卖是真实损失，必须在库存行上做强约束 |
| 机票/座位选座 | **不可以** | 同一个座位不能卖两次 |
| 用户刚改完资料立刻刷新 | 不可以（读自己的写） | 需要读主库或等待同步 |
| 审计与资金流水 | 不可以 | 必须立即持久化，可追溯 |

库存这类资源，正确做法不是"消息最终会扣对"，而是**在数据库里做条件更新**：

```sql
UPDATE stock
   SET available = available - 1,
       reserved = reserved + 1
 WHERE sku = 'A100' AND available >= 1;
```

影响行数为 0 就是库存不足。消息可以异步，但"不能超卖"这条约束必须同步落在资源行上。**最终一致处理的是流程，不是资源竞争。**

还有一条最容易被忽略：**读自己的写**。用户改完昵称，页面立刻刷新却读到从库的旧值，用户会以为保存失败。这不是"最终一致可以接受"的范围——对这个用户，必须让他读到自己的修改。做法是写完后几秒内路由到主库，或者等待从库同步位点追上，而不是让用户反复刷新碰运气。

## 常见误区

### 误区：接口超时就是失败，可以直接重试

**你以为**：超时说明请求没成功，重试一次没有副作用。
**其实**：超时只说明调用方没等到响应，服务端可能已经处理完，只是响应丢了。对扣款、下单、发货这类非幂等操作，重试就是第二次执行。
**怎么验证**：让服务端在处理成功后故意延迟 4 秒再返回，客户端设 3 秒超时并自动重试，观察数据库里是否出现两条业务记录或两笔扣款。

### 误区：用了消息队列就有"恰好一次"

**你以为**：MQ 保证消息不重复，消费端不用去重。
**其实**：绝大多数 MQ 是至少一次投递；Kafka 的 exactly-once 只在 Kafka 事务覆盖的链路内成立，消息一旦要写 MySQL、发短信、调第三方支付，就不在同一个事务里了。业务效果仍然要靠消费端幂等。
**怎么验证**：让消费者在处理成功后、提交 offset 前崩溃，重启后看同一条消息是否再次投递；再查所用 MQ 的官方文档里 delivery guarantee 的原文。

### 误区：幂等就是加个 Redis SETNX，过期了也没关系

**你以为**：Redis 去重又快又简单，键过期就代表可以重新处理。
**其实**：Redis 可能丢数据、可能提前过期；更麻烦的是"SETNX 成功、业务还没执行完进程就崩了"，键已存在，重试会被误判为已处理。幂等的最终依据应该是数据库唯一约束，Redis 只能做前置过滤。
**怎么验证**：在 SETNX 成功后、业务提交前 kill 进程，重启后发同一个请求，看它是被拒绝还是能正确完成；再模拟 Redis 重启丢键，看重复请求会不会再次落库。

## 小结

这一篇的链条是：

```text
超时 = 结果未知
  → 默认至少一次，重复是常态
  → 用幂等键 + 去重表 + 状态机，让重复请求变成空操作
  → 重试只在瞬时错误上做，带指数退避、抖动、上限，且只在一层重试
  → 跨服务通知用本地事务 + outbox，消费端幂等
  → 最终一致要有收敛时间 SLO、对账和人工兜底
```

记住两句话：**能重试的前提是幂等；能最终一致的前提是能对账。**
