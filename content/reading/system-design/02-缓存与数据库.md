## 先把结论摆出来

缓存和数据库之间**不存在免费的一致性**。你能选的只有两件事：

1. **接受多长的不一致窗口**（毫秒？秒？分钟？）；
2. **脏数据最坏会脏成什么样**（多看到一个旧值，还是永久错）。

业界默认做法是：**先更新数据库，再删除缓存**。它不保证强一致，但把"永久不一致"的概率压到很低。

## 为什么不是"更新缓存"

四种写法，只有一种常被推荐：

| 写法 | 问题 |
| --- | --- |
| 先更库，再更缓存 | 两个写操作并发时，旧值可能后写、覆盖新值 |
| 先更缓存，再更库 | 缓存成功、库失败 → 缓存永远是新值，库是旧的 |
| 先删缓存，再更库 | 删完到更库之间，别的请求把旧值又读回缓存 |
| **先更库，再删缓存** | 窗口最小，最坏是"读到一个已过期的旧值" |

"删"比"更"好，因为**删除是幂等的**：删两次和删一次一样，并发删也不会互相覆盖；而"更新"会被乱序覆盖。

## 那个"极小的窗口"到底是什么

```text
1. 线程 A 读缓存 → 未命中
2. 线程 A 查数据库 → 得到旧值 v1
3. 线程 B 更新数据库 → v2，并删除缓存
4. 线程 A 把 v1 写回缓存      ← 脏了
```

A 在第 2 步读到的是旧值，第 4 步才写进缓存，把 B 刚删掉的脏数据又放了回去。

概率很低（要求读线程恰好在"查库"和"写缓存"之间被挂起），但**不是零**。缓解手段：

- 缓存加**过期时间**——这是最重要的兜底，让脏数据最多停留一个 TTL；
- 延迟双删（更库后隔几百毫秒再删一次）——有效但引入睡眠，别滥用；
- 用**消息队列/订阅 binlog** 异步删缓存——把删缓存与业务解耦，失败可重试。

## 该问的三个问题

设计缓存前先回答：

1. **不一致的窗口能接受多长？** 商品详情 5 秒旧值无所谓；账户余额不行。
2. **读多还是写多？** 读多写少才值得缓存。写比读还多时，缓存只会增加复杂度。
3. **缓存挂了会怎样？** 如果缓存全丢就直接把数据库打挂，那这个缓存是"不能丢的依赖"，得考虑降级。

第三条最容易被忽略：缓存本来是"加速"，做成了"必须"，就等于把数据库暴露在缓存故障面前。

## 一个具体例子

```text
// 更新
updateProduct(id, data);
cache.delete("product:" + id);

// 读取
Product p = cache.get(key);
if (p == null) {
    p = db.find(id);
    cache.set(key, p, 60, TimeUnit.SECONDS);   // 有 TTL 才有兜底
}
```

三点值得注意：

- 删缓存放**事务提交之后**（`@Transactional` 方法返回后），否则事务还没提交，别的线程可能把旧值读回缓存；
- TTL 不是可选项，它是"删缓存失败"和"并发窗口"的统一兜底；
- 缓存 key 要能按维度失效（`product:42`），不要只用一个全局 key。

## 常见误区

### 误区：先删缓存再更库更安全

**你以为**：先让缓存失效，再改库，读的一定是新值。
**其实**：删完到更库之间有空隙，别的请求会把旧值重新读进缓存，而且这次写入可能比你的删除更晚生效。
**怎么验证**：并发跑"删缓存—更库"与"读缓存—查库—写缓存"，观察缓存里能否出现旧值。

### 误区：双写（同时写库和缓存）能保证一致

**你以为**：两边都写一遍就一致了。
**其实**：两个写不是原子操作。任何一侧失败、或两个请求交错，都会造成长期不一致。
**怎么验证**：人为让第二次写缓存失败，观察数据库与缓存是否分叉。

### 误区：缓存命中率越高越好

**你以为**：命中率是缓存唯一的指标。
**其实**：命中率 99% 也可能很糟——如果那 1% 的未命中集中在同一秒，数据库照样被打穿。还要看**未命中的时间分布**。
**怎么验证**：按秒统计未命中次数，看是否有尖峰。
