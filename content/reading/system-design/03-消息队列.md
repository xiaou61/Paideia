## 先把结论摆出来

消息队列只干三件事：

```sketch

```

1. **削峰**：把瞬时高峰摊平，让下游按自己的速度消费；
2. **解耦**：上游不需要知道下游有几个、是谁；
3. **异步**：把"不必立刻完成"的事挪出主流程。

它同时带来四个新问题：**重复、乱序、积压、以及"消息丢了没人知道"**。

所以判断标准不是"要不要用它"，而是"**这四个问题我能不能处理**"。

## 削峰：先算清两件事

削峰的价值 = 高峰流量 ÷ 下游处理能力。但你要先回答：

- **消息可以堆多久？** 堆一天和堆十分钟，需要的存储与运维完全不同；
- **堆积期间用户看到什么？** "已提交，稍后通知"和"接口卡住等结果"是两个产品。

如果业务要求立刻返回结果，消息队列就帮不上——它只能异步。

## 解耦的代价是"看不见"

同步调用时，谁在调谁一目了然；换成消息，**调用关系从代码里消失了**。

后果：

- 改消息体格式时，不知道谁在用（除非有契约管理）；
- 出问题时，链路上多跳了一个中间件，排查路径变长；
- 下游挂了，上游完全无感——可能是好事，也可能是"用户以为成功了其实没处理"。

**至少要做两件事**：消息体版本化（加字段可以，删改要兼容），以及一个能看到"消息堆积/失败"的监控。

## 重复与幂等

绝大多数队列保证的是**至少一次**，也就是可能重复投递。所以消费者必须幂等：

```text
// 错：重复消息会发两条通知
onMessage(msg) { sendSms(msg.userId, msg.text); }

// 对：按业务唯一键去重
onMessage(msg) {
    if (!processed.insertIfAbsent(msg.messageId)) return;   // 已处理过
    sendSms(msg.userId, msg.text);
}
```

幂等键要选**业务上唯一**的东西（订单号、消息 id），不能选"当前时间"或"自增序号"。

## 顺序：只有"同一实体"才需要

全局有序几乎没有必要时，需要的是**同一个订单/同一个用户的处理顺序**。

做法：按实体 id 做**分区**（kafka 的 partition key、RocketMQ 的顺序消息）。同一 key 落同一分区，分区内有序。

注意：扩分区数量时会破坏顺序（key 到分区的映射变了），所以**分区数要在起步时想清楚**，别频繁改。

## 积压时先看什么

```text
1. 消费速率 vs 生产速率：是"消费变慢"还是"生产暴增"
2. 单条处理耗时：是不是某类消息把消费线程卡住了
3. 是否在重试：失败重试会放大积压
4. 分区数够不够：消费并发上限 = 分区数
```

**最常见的真因是第 2 条**：某类消息调用了慢接口，把消费线程占满，其他消息跟着排队。

## 常见误区

### 误区：加了消息队列性能就变好

**你以为**：异步了，接口就快了。
**其实**：你只是把工作挪到了别处。如果下游处理不过来，积压最终还是会影响业务（比如通知晚了半小时）。
**怎么验证**：压测上游接口，同时看队列积压曲线与下游消费速率。

### 误区：消息不会丢，不用管

**你以为**：队列是可靠存储。
**其实**：生产失败、broker 落盘策略、消费失败重试次数耗尽——每一段都可能丢。业务要能回答"这条消息没了会怎样"。
**怎么验证**：故意让消费者抛异常超过重试上限，看是否有死信队列或告警。

### 误区：顺序消息处处都要

**你以为**：必须保证全局顺序。
**其实**：全局顺序会把消费并发压到 1。绝大多数场景只需要"同一实体有序"。
**怎么验证**：问业务"不同订单之间的处理顺序有意义吗"。
