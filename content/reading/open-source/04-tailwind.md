## 一句话定位

**Tailwind 不提供组件，只提供"单一职责的工具类"**：`flex`、`p-4`、`text-sm` 各管一件事，你在 HTML 里把它们拼出来。

## 它解决什么问题

传统 CSS 的核心痛点是**命名与作用域**：

- 给一个东西起名字（`.card-inner-wrapper`），起名很难，而且名字会随时间失真——改了内容忘了改名。
- 样式与结构分离，但实际使用中它们耦合得很紧：要看懂一个按钮的样子，得在两个文件之间跳。
- 删除样式不敢删：`grep` 不到引用，但可能是动态拼出来的类名。
- 全局作用域：一个 `.title` 改了，可能影响十几个页面。

Tailwind 的取舍是：**放弃"语义化类名"，换"样式与结构同处一地 + 没有全局作用域 + 没用到的样式不生成"。**

## 核心机制

1. **工具类原子化**。一个类只做一件事。`p-4` 是 `padding: 1rem`，`text-sm` 是 `font-size: 0.875rem`。样式直接写在标记上，不需要跳文件。
2. **样式在构建时生成，不是运行时**。它扫描源码里出现的类名字符串，只产出**实际用到**的 CSS。这解决了"CSS 文件越加越大"的老问题。
3. **设计令牌集中在配置里**。`p-4` 里的 `4` 来自间距表，`text-sm` 来自字号表。改令牌就改全站，且不会出现"这个按钮的间距是 13px，那个是 14px"。
4. **变体前缀表达状态与断点**。`hover:bg-blue-600`、`md:flex`、`dark:bg-gray-900`、`disabled:opacity-50`——都是同一套前缀语法，不需要写多个 CSS 选择器。
5. **代价是标记变长**。一长串类名是它的主要批评点，也是它刻意的取舍：**你换来的是"不用起名、不用跳文件、删代码即删样式"**。

## 什么时候该用

- 组件化前端（React/Vue/Svelte），样式跟着组件走
- 需要严格的设计一致性（令牌化）
- 迭代频繁的产品界面（改样式不用改两个文件）
- 已有一套设计令牌（Figma 变量能直接映射到配置）

## 什么时候别用

- **内容型站点（博客、文档）**。这类站的样式主要来自正文排版，`@tailwindcss/typography` 能覆盖大半，但写长文时反复拼类名反而更慢。
- **团队不接受长类名**。这是审美与习惯问题，硬推会引发持续摩擦；`@apply` 能缓解但会退回"给样式起名"的老路。
- **必须支持很老的浏览器**。Tailwind v4 用了现代 CSS（`@layer`、`color-mix()`），IE 完全不支持。
- **只需几十行 CSS 的小页面**。引入构建链路不划算。

## 替代品

| 场景 | 替代 |
| --- | --- |
| 想要工具类但留在 JS 里 | CSS-in-JS（styled-components、emotion）——运行时开销更大 |
| 想要工具类但零运行时 | Vanilla Extract、CSS Modules |
| 组件库自带样式 | MUI、Ant Design（帮你把样式决定好了，定制要覆盖） |
| 完全手写 CSS 但要作用域 | CSS Modules、Scoped CSS（Vue） |

## 一个容易踩的坑（本仓库真实遇到过）

Tailwind v4 用 `@source` 指令告诉它去哪扫描类名。**`@source` 指错目录时不会报错，只会静默缺样式**——页面看起来"少了点东西"，控制台干干净净。本仓库升级 v4 时踩过一次：`@source` 指向了 `./src`，而实际组件在 `../../packages/ui/src`，结果共享组件的样式全部没生成。

守卫办法是在 CI 里断言一个已知类名出现在产物 CSS 里，而不是靠肉眼看页面。
