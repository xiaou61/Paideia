## 一句话定位

**SQLite 不是一个"轻量版 MySQL"，而是一个库**：它没有服务端进程、没有网络协议，你的程序直接读写一个文件。

## 它解决什么问题

大部分应用并不需要独立的数据库进程。它们需要的是：**能存结构化数据、能写 SQL 查询、事务可靠、零运维。**

独立数据库（MySQL/PostgreSQL）在单机小应用上带来的成本是实实在在的：多一个进程要守、多一套账号要管、多一层网络要排查、多一次部署要协调。而收益（并发写入、远程访问、独立扩容）在小应用上一样都用不到。

SQLite 的取舍是：**把这些能力全部去掉，换一个文件。**

## 核心机制

1. **进程内库**。你的程序 `dlopen` 它，函数调用直接读文件，没有 IPC、没有网络往返。一次查询的固定开销从"建立连接 + 序列化 + 网络"降到几次内存访问。
2. **单文件 = 完整数据库**。表、索引、schema、事务日志都在一个文件里（`journal`/`WAL` 是旁边的临时文件）。备份就是 `cp`，迁移就是 `scp`。
3. **WAL 模式让读不阻塞写**。默认的回滚日志模式下写会锁住读；开 `PRAGMA journal_mode=WAL` 后写追加到 `-wal` 文件，读继续走主文件，读写并行。这是它敢用于"读多写少"Web 应用的关键。
4. **写入永远是串行的**。没有 MVCC 写并发，任一时刻只有一个写事务。这不是缺陷而是设计：省掉了一整套锁管理器与版本清理。
5. **类型是"弱"的**（`INTEGER`/`REAL`/`TEXT`/`BLOB`/`NULL` 五个存储类）。一个声明为 `INTEGER` 的列可以存字符串。这对从 MySQL 迁过来的人是最大的意外。

## 什么时候该用

- 桌面应用、移动应用（Android/iOS 内置它，全球部署量最大的数据库）
- 单机 Web 服务、内部工具，读多写少
- 数据分析的中间存储、ETL 的暂存区
- 测试环境：不用起服务，一个临时文件就是一套完整 schema
- 需要"零运维、能拷走"的任何场景

## 什么时候别用

- **多台机器同时写**。文件锁在共享文件系统上不可靠（NFS 上会损坏数据库，官方明确警告）。
- **持续高并发写入**。写入串行会立刻成为瓶颈；量级参考是每秒几次到几十次事务，不是几千次。
- **需要细粒度权限**。它是文件权限，没有"这个用户只能读这张表"。
- **需要严格类型**。如果你的正确性依赖"这列不能存字符串"，得靠 `CHECK` 约束自己兜。
- **需要网络访问**。它没有网络协议；跨机器要么挂共享盘（别做），要么自己套一层服务。

## 替代品

| 场景 | 替代 |
| --- | --- |
| 需要真并发写 + 网络 | PostgreSQL、MySQL |
| 嵌入式但要有列式/分析能力 | DuckDB（分析型，也是进程内） |
| 键值缓存 | Redis、LMDB |
| 文档型但要好运维 | 直接用 Postgres 的 JSONB |

## 出处

- **许可证**：Public Domain（作者 D. Richard Hipp 明确声明放弃版权，可自由用于商业闭源产品，无署名义务）
- **仓库**：https://github.com/sqlite/sqlite（官方镜像；主仓在 https://sqlite.org）
- **对应版本**：3.45（WAL 模式与 `STRICT` 表均在此版本可用）

## 一个常见的误判

"SQLite 只能用于原型"——这是错的。它的问题从来不是"不够正式"，而是**并发模型不匹配**。如果你的写入是串行的（桌面应用、单机服务、离线优先的移动端），它能撑到每秒数万次读，而且可靠性比很多自建方案都高：断电测试做了二十年。
