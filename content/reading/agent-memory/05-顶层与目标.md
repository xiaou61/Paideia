## 一、最贵的一层，只能放很小一坨

顶层是「每次会话自动加载」的那部分。它最方便，也最贵，原因有三个：

1. **占 token。** 每次请求都要付，跟会话数量成正比；
2. **错误会复利。** 一条错笔记进了顶层，会被每一次会话信任；
3. **越长越不被遵守。** 原文引用 Claude Code 的文档：指令文件越长，遵循度越低。

所以顶层的设计目标不是「装下更多」，而是「用最少的字，指向最多的东西」。Claude Code 的 auto memory 就是这么做的：每次只加载 `MEMORY.md` 的**前 200 行或 25 KB**，超出部分留在下层，需要时再读。

换个说法：**顶层是目录，不是仓库。** dreaming 在这里的主要工作反而是「往下搬」——把细节沉到下层，只在顶上留一个标题和一条链接。

```text
顶层（每次注入）      当前目标 / 一条关键规则 / 「细节在哪」的链接
中层（按需读）        wiki 页面、代表性笔记
底层（按需搜）        完整 transcript、原始文档
```

## 二、整理不是把知识堆起来，是修连接

原文里有一个容易忽略的细节：第二轮 dreaming 干的事，是修补上一轮留下的窟窿。某个任务的 wiki 里，有 9 条链接指向一个根本不存在的页面（`escrow-agreement`）；第二轮把这 9 条链接改指到同一个文档的真实页面（`buyer-form-escrow-agreement`），并新增了 3 个页面（其中一个是索引页）。

规模上：38 个条目、225 条链接 → 41 个条目、278 条链接。

这件事的意义在于：**记忆系统里「死链」和「错事实」是同一类问题**——都让下一次会话走空。整理不光在写新内容，也在把已有的连接修对。

## 三、记忆长成什么样，取决于它服务什么目标

这一节是全篇最有工程味道的部分，因为它说明「给什么指令」会直接改变记忆的结构。

任务是模拟一次公司收购，给一批合同，最后按「简报是否准确描述条款」打分。第一版的指令很朴素：让模型根据文档建 wiki，没说条款是重点。

结果是多个 agent 同时往一张共享的条款表里写，互相覆盖：

| | 建法 | 57 条评分事实保住了多少 |
| --- | --- | --- |
| 第一版 | 多 agent 共写一张 `provisions.md`，条款被总结进表 | 41 条（72%） |
| 第二版 | 每份合同由单个 agent 独立建页，条款逐字引用 | 57 条（100%） |

改进不是人想出来的，是一个循环跑出来的：让 Claude 反思失败、提出指令怎么改、重建 wiki。它自己得出的结论是「条款必须逐字保留，且不该多人共写一张表」。

这个案例点出一件比「怎么写 prompt」更底层的事：**记忆的组织方式应该跟着目标走。** 目标是「准确复述合同条款」，那结构就必须是「一份合同一页、原文优先」；如果目标是「快速比较不同合同的差异」，那结构又该是另一套。

## 四、还没解决的问题

原文最后很诚实地列了三个开放问题，值得原样记住，因为它们就是你会在自己项目里撞上的：

**一、什么时候写。** 在线写，能抓住当下的显著性，但**分散当前任务的注意力**；离线整理，不打扰干活，但结果**不能马上用**。这是纯粹的成本权衡，没有标准答案。

**二、怎么保证不过期。** 记忆会随环境变化漂移，模型也可能一开始就写错。全量校验太贵，所以要么挑「容易变」的校验，要么按访问频率调节整理节奏。

**三、评估看什么。** 不能只看「存进去了没有、取出来了没有」，至少还要看三件事：

- 旧记忆是否**仍然正确**；
- 检索是否真的**省下了动作**（而不是把搜文档换成搜记忆）；
- 整理的开销，能不能换来持续的收益。

## 五、这套东西对你我的直接启示

把全篇压成三条可以马上落地的原则：

1. **顶层保持小，只放索引和目标。** 每次注入的内容都要能回答「它帮我省了哪次搜索」。答不出来就往下搬。
2. **任何二手结论都要能回到一手记录。** 笔记、wiki、摘要都是缓存，必须留一条回到 transcript 的路；否则错了没人能发现。
3. **记住了不等于学会了。** 判断标准是「下一次同类任务少走了几步」，不是「库里有多少条」。

## 常见误区

### 误区：把记忆全量塞进系统提示词

**你以为**：反正窗口够大，全放进去最保险。
**其实**：每条都付 token，错误全量复利，而且指令越长遵循度越低。Claude Code 的 200 行 / 25 KB 上限就是被这三件事逼出来的。
**怎么验证**：把顶层内容删到只剩「目标 + 索引」，看任务成功率有没有掉。多半不掉。

### 误区：多 agent 并行写同一份记忆更快

**你以为**：几个 agent 一起写，速度快、覆盖全。
**其实**：41/57 那个案例就是互相覆盖的结果——共享表还顺手把条款总结掉了，丢的是事实。
**怎么验证**：看写入冲突。只要有「后写的覆盖先写的」，就该改成一人一页或加锁。
