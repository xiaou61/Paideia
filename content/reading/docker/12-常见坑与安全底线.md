## 这一关在解决什么

前面十一关讲的是"怎么用对"。这一关讲**怎么不把自己坑了**：六个最常见的坑，加上一组"跑不可信代码时必须有"的硬参数。

判断标准很简单：**出了事，最坏能到什么程度？** 一个 `-v /:/host` 加 `--privileged` 的容器出事，等于把宿主 root 交出去。

## 为什么容器不是安全边界

因为它共享宿主内核（第 01 关）。默认配置下还有三个放大项：

- 容器内是 **root**；
- 容器能**出网**（可以当跳板扫描、爆破、发垃圾邮件）；
- 常被挂上 **`/var/run/docker.sock`**（等于把 Docker 控制权给它，而 Docker 控制权等于 root）。

所以安全的做法不是"有 Docker 就放心"，而是**把每一项都往回收**。

## 讲解

### 坑一：密钥被烤进镜像

```dockerfile
ENV API_KEY=sk-live-xxxx          # ✗ 进镜像，docker inspect 可见
ARG DB_PASSWORD                   # ✗ 进构建历史，docker history 可见
COPY .env /app/.env               # ✗ 文件进镜像层，删了也还在下一层
RUN curl -H "token: xxx" ...      # ✗ token 在一次性的层里，但构建历史记着命令
```

四个位置都会持久化。**正确的做法**是运行期注入：

```text
$ docker run --env-file /etc/app/secrets.env 应用
```

或者用密钥管理（Vault、云厂商的 secrets、K8s Secret）。`--env-file` 那个文件本身要 `600` 且不进仓库。

已经烤进去了怎么判断？`docker history --no-trunc 镜像` 能看见完整的构建命令，`docker inspect` 能看见 `ENV`。**删掉之后重建镜像**——只删 Dockerfile 里那行不会自动清掉旧镜像里的层。

### 坑二：`--privileged` 与挂载 `docker.sock`

```text
$ docker run --privileged ...                       # ✗ 几乎等于不隔离
$ docker run -v /var/run/docker.sock:/var/run/docker.sock ...   # ✗ 等价于给宿主 root
```

挂载 `docker.sock` 的容器可以创建新的容器、挂载宿主根目录、读所有其他容器的环境变量——这是 CI、监控、构建工具惯用的"方便"做法，也是最常见的一类提权路径。**除非这个容器是完全可信的**（比如自己写的部署工具），不要挂。

`--privileged` 关掉了几乎所有的隔离（能看所有设备、能改内核参数、能挂载）。需要某个特定能力时，用 `--cap-add=NET_ADMIN` 这种**点对点**的方式，而不是整体放开。

### 坑三：端口默认开在公网

```text
$ docker run -d -p 5432:5432 postgres:16      # ✗ 0.0.0.0，公网可达
$ docker run -d -p 127.0.0.1:5432:5432 postgres:16   # ✓ 只给本机
```

容器里的数据库默认只听容器网络、是安全的；把它 `-p` 出去反而开了一扇公网门。要么不映射（同网络容器直接连），要么绑 `127.0.0.1` 走 SSH 隧道或反代（Linux 线第 15、16 关）。

### 坑四：`latest` 与不钉版本的基础镜像

```dockerfile
FROM node:latest        # ✗ 明天可能换一个大版本，构建结果不可复现
FROM node:20.11.1-slim  # ✓ 至少钉到次版本
FROM node@sha256:...    # ✓✓ 钉到内容
```

生产镜像的基础层用 digest（第 03 关）。理由是"昨天验过的隔离参数，今天不该配一个不同的基础镜像"。

### 坑五：构建上下文把一切都送进去

`docker build .` 会把**整个目录**（受 `.dockerignore` 约束）送给 daemon。没有 `.dockerignore` 时：

- `node_modules`、`target`、`.git` 让构建慢几倍；
- 本地 `.env`、`*.pem`、`.aws/` 可能被 `COPY . .` 烤进镜像。

一个具体的自查：

```text
$ docker build --progress=plain -t x . 2>&1 | grep -i "transferring context"
```

这个数字应该是几 MB，不该是几百 MB。

### 坑六：日志与卷悄悄吃满磁盘

```text
$ docker system df          # 四项：Images / Containers / Local Volumes / Build Cache
$ docker system df -v       # 按项展开
```

最常见的三个大户：**没有日志上限**（第 09 关）、**停止的容器**（第 02 关）、**孤儿卷**（第 05 关）。清理：

```text
$ docker system prune              # 删停止的容器、未用的网络、构建缓存
$ docker system prune -a           # 连未用镜像一起删（较激进）
$ docker system prune -a --volumes # 连未用卷一起删（会丢数据，确认后再执行）
```

**`--volumes` 要格外小心**：它删的是"没有被任何容器使用"的卷，包括你刚停掉的那个数据库的卷。

### 跑不可信代码时的硬参数

如果容器里跑的是别人写的代码（在线判题、用户上传的脚本），默认配置**远远不够**。一组最小可用的参数：

```text
$ docker run --rm -i \
    --network none \
    --read-only \
    --tmpfs /tmp:rw,size=64m,exec \
    --cap-drop=ALL \
    --security-opt no-new-privileges \
    --memory 256m --memory-swap 256m \
    --cpus 0.5 \
    --pids-limit 64 \
    --user 65534:65534 \
    --stop-timeout 0 \
    镜像 命令
```

每一条都在关一扇门：

| 参数 | 关掉什么 |
| --- | --- |
| `--network none` | 出网（不能当跳板、不能下载东西） |
| `--read-only` | 改根文件系统（只能写 `/tmp` 的 tmpfs） |
| `--tmpfs /tmp:size=64m,exec` | 可写目录的大小；`exec` 是因为编译要执行生成的文件 |
| `--cap-drop=ALL` | 所有特权能力（绑定低端口、改网络、挂载…） |
| `--security-opt no-new-privileges` | setuid 提权 |
| `--memory`/`--memory-swap` 相等 | 内存 + swap 总上限（第 09 关） |
| `--pids-limit` | fork 炸弹 |
| `--user 65534` | 以 nobody 运行，而不是 root |
| `--stop-timeout 0` | 不用等优雅退出（不可信代码不给它拖延机会） |

再加一层**应用侧**的保护：墙钟超时后 `docker kill`、输出截断（否则一个 `yes` 能把日志写爆内存）、每人并发 1、每日配额。

这类系统真正的加固还要叠 **seccomp 白名单**（限制可用的系统调用）与 **gVisor**（`--runtime=runsc`，把系统调用转到用户态内核）。前四条参数是"够用"的基线，后两层是"防内核漏洞逃逸"的正式方案。

### 一份上线前的自查清单

| 检查 | 命令 | 期望 |
| --- | --- | --- |
| 不以 root 运行 | `docker exec 容器 id -u` | 不是 `0` |
| 没有烤进去的密钥 | `docker history --no-trunc 镜像 \| grep -i -E 'pass\|token\|key'` | 无输出 |
| 端口没开到公网 | `docker ps --format '{{.Ports}}'` | 没有 `0.0.0.0:` 的内部服务 |
| 日志有上限 | `docker inspect 容器 --format '{{json .HostConfig.LogConfig}}'` | 有 `max-size` |
| 数据在卷里 | `docker inspect 容器 --format '{{json .Mounts}}'` | 关键路径都在 |
| 镜像钉了版本 | `docker image inspect 镜像 --format '{{index .RepoDigests 0}}'` | 有 digest |
| 有资源上限 | `docker inspect 容器 --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'` | 非 0 |
| 基础镜像有已知漏洞 | `trivy image 镜像` | 高危数量可接受 |

## 常见误区

### 误区：镜像里删掉密钥文件就干净了

**你以为**：`RUN rm .env` 之后镜像里就没有了。
**其实**：镜像分层（第 03 关），删除只是上层的一个标记，下层的数据仍在，`docker save` 导出后能直接翻出来。**唯一干净的做法是让它从未进过任何一层**：用 `.dockerignore` 排除，运行时注入。
**怎么验证**：`docker save 镜像 -o x.tar && tar -xf x.tar`，在各层的 `layer.tar` 里 `grep` 那个密钥——还在。

### 误区：`docker` 组只是免 sudo 的便利

**你以为**：加组是常规操作。
**其实**：**在 `docker` 组里等于拥有宿主 root**（第 02 关）。多用户机器上这等于给所有人 root，只是绕了一圈。真正的方案是 rootless Docker 或把需要 Docker 的人限制在专用机器上。
**怎么验证**：`docker run --rm -v /:/host alpine cat /host/etc/shadow` 能读到口令哈希，就是证据。

### 误区：容器跑了就没人能进来

**你以为**：隔离了，安全。
**其实**：容器暴露的端口和宿主上的服务一样会被扫到、被爆破；镜像里装的老版本依赖、默认口令、绑 0.0.0.0 的数据库，都是真实风险。**能出网的容器被攻破后还能反过来当攻击源**，这在云上会被直接封机器。
**怎么验证**：`docker ps --format '{{.Names}} {{.Ports}}'` 逐个确认来源范围；`trivy image 镜像` 看依赖漏洞；`docker exec 容器 ss -lntp` 看它真的在听什么。
