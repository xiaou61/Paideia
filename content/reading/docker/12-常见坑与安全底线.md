## 111：端口映射写对了，还是连不上

```text
$ docker run -d --name practice-db -p 127.0.0.1:3306:3306 \
    paideia-sandbox-mysql:8.0
$ mysql -h 127.0.0.1 -P 3306 -uroot
ERROR 2003 (HY000): Can't connect to MySQL server on '127.0.0.1:3306' (111)
```

容器是 `Up` 的，`docker ps` 的 PORTS 列明明写着 `127.0.0.1:3306->3306/tcp`，宿主上那个端口也确实被占着，可一连上去立刻被拒——111 是 ECONNREFUSED，意思是包送到了，只是那头没人接。

原因不在网络。这个镜像里 mysqld 的命令行带着 `--skip-networking`（`DockerCommand.java:196`，池子里那份在 `:232`），它只开了一个 unix socket，从来没听过 TCP。`-p` 从来不负责让容器里的进程开始监听，它只把宿主的一个端口指过去；指到一个没人听的端口，得到的就是 111。

（这台机器没装 Docker。下面所有 `docker` / `mysql` 回显都是标准形态，一条也没跑过；引用的秒数与行号来自仓库里的代码和注释。）

于是这一关就顺着这一个念头走：我想连上这台容器看一眼数据。而它被造出来，恰恰是为了不让人连——里面跑的是陌生人写的 SQL，它得在没有网络、看不到宿主文件、不是 root 的条件下算完。我每拆一道墙，「看一眼」就换回一个具体后果，而且这四道墙是一条链：拆掉第一道，后面三道才开始算数。

## 墙一：`-p` 改的是可达性，不是监听

要让那个 3306 连得上，得同时做两件事：去掉 `--skip-networking`，再决定把端口露给谁。只做第一件，容器内就监听了所有地址（MySQL 8.0 里 `bind-address` 默认是 `*`），但外面仍然只有同一个 docker 网络里的容器能连；只做第二件，就是开头那个 111。

| 端口怎么写 | 谁能连进来（前提是容器里的进程真的在听 TCP） |
| --- | --- |
| `--network=none`，不写 `-p` | 谁都连不进来。只有容器内 loopback 与 unix socket |
| 默认 bridge，不写 `-p` | 同一个 bridge 网络里的容器，按容器 IP 连 |
| `-p 3306:3306` | 宿主所有网卡，再加上面两种 |
| `-p 127.0.0.1:3306:3306` | 只有宿主 loopback，再加上面两种 |

左边那列有个前提，别把它跳过：`--skip-networking` 时这四种写法**全部**是 111，因为目标端口上根本没有监听。

露出去之后，宿主的防火墙不是你想的那道防线。Linux 上 Docker 自己往 iptables 里写转发规则，已发布的端口走的是 DNAT 加 FORWARD，宿主的 `ufw` 那条 INPUT 链根本看不到这些包：`ufw status` 里写着 `deny (incoming)`，3306 照样通。要拦只能往 `DOCKER-USER` 链里写规则——这是 Docker 文档明确交代的位置，不是发行版差异。

仓库自己的选择是反过来的：`--network=none` 加 `--skip-networking`，容器根本不出网也不听 TCP，代码走 stdin 进去（`DockerCommand.java:295-331` 那串参数）。真要看那个练习库，正道是进容器里用它的 socket：

```text
$ docker exec -it <容器名> mysql --socket=/tmp/m.sock -uroot
```

`docker exec` 的细节在第 10 关。池化之后容器名是写死的那一个，账号与库名每次现起现删（`SqlContainerPool.java:344-353`）。

## 墙二：那个 root 的口令是空的

镜像构建期跑的是 `mysqld --initialize-insecure`（`images/mysql/Dockerfile:18`），它的意思就是「初始化但不设口令」，于是 `root@localhost` 是空口令——MySQL 8.0 参考手册里这个参数的定义就是这么写的。构建完之后那份 datadir 被 `chmod -R a-w`（`:19`），跑起来时 mysqld 以 `999:999` 而不是 root（`DockerCommand.java` 的 SQL 路径），所以「容器里以 root 跑」这个担子在这里已经被拿掉了。

平时它无害：socket 在容器里，TCP 被 `--skip-networking` 关着，外面走不到。墙一拆了之后，它就是唯一的门，而门是空的。这也是为什么这四道墙有先后顺序——空口令单独存在不叫漏洞，配上「能连进来」才叫。

口令本身留在哪里，也是一样的道理：位置换了不等于没了。

| 口令写在哪 | 谁能看见 | 仓库的选择 |
| --- | --- | --- |
| 命令行参数（`mysql -pPASS`、`docker run ... -e`） | 宿主与容器里的 `ps` 都能看到当时的 argv | `SqlContainerPool.java:329`：走 `MYSQL_PWD` 环境变量，不走 `-p` |
| 环境变量 | 容器内同 uid 的进程或 root 能读 `/proc/<pid>/environ`；`docker inspect` 能看到所有 `-e` 的值 | 同样用 `MYSQL_PWD`——它换来的是「不进 argv」，不是「不可见」 |
| `ENV`、被展开的 `ARG` | `docker inspect` 的 `Config.Env`、`docker run <镜像> env` 直接打印；被展开进 `RUN` 的 build arg 会跟着那条命令进 `docker history --no-trunc` | 密钥运行时注入，不进镜像 |
| 构建期写进某一层再 `RUN rm` | 上一层还在：`docker save` 解开逐层 `grep` 找得到 | `.dockerignore` 排掉，让它从未进过上下文 |

第三条要写成条件句：`ARG` 本身不进镜像配置，所以「`ARG` 一定泄露」是错的；但 Docker 文档对 build arg 的告警原话就是它的值会留在镜像历史里，只要它被展开进任何一条 `RUN` 就会被 `docker history --no-trunc` 翻出来。结论「别用 `ARG` 传密钥」与该值以什么形状被记录无关。

## 墙三：能执行 `docker` 的那个进程

判题沙箱没挂 `/var/run/docker.sock`：它是从 Java 里开一个 `docker run` 子进程。`DockerCodeRunner.java:19-22` 写了理由——当前部署是 systemd 加裸 jar，宿主本来就有 Docker；`docker run` 自己就是个独立进程，崩了不拖累 JVM；少一个部署单元、少一套内网鉴权。同一段注释也写了已知限制：应用一旦容器化，这条路就没有 socket 可用，必须改成独立的 runner。

但这不是降权。那个 Java 进程能跑 `docker run`，说明它在 `docker` 组里或者就是 root；在没有 userns-remap、也不是 rootless 的机器上，这两个身份都等于宿主 root。判据很直白：

```text
$ docker run --rm -v /:/host alpine cat /host/etc/shadow
```

能读到口令哈希，就说明这条路是宿主 root，不必再争。`docker` 组不是「省一个 sudo」，是「把 root 分发出去」；宿主 `docker ps` 报 `permission denied while trying to connect to the Docker daemon socket` 时，`sudo` 能把命令跑通，但它只是把这个事实盖住了。

那「不挂 socket」到底买到了什么？买的是**攻击面**，不是**权限**：容器里的代码再多一个洞，也够不到 daemon。这笔账值得算，但它不能推出「所以判题容器是安全的」——真正的门在别处，在 `DockerCommand.java:16-17` 那两条：没有 `-v` / `--mount`，代码从 stdin 进容器，宿主文件系统不出现；镜像来自配置、不来自请求，用户输入永远进不了命令行。第二条才是这类系统的命门：只要用户输入拼不进 argv，就少掉一整类注入。

同一件事的另一面是「你钉住的是哪一版」。沙箱把镜像写成 digest：`application.yml` 里是 `paideia-sandbox-mysql@sha256:e2eafb6…`，Dockerfile 里是 `mysql:8.0@sha256:7dcddc…`。`:latest` 的问题不是「不够新」，是两台机器拉到的东西可以不一样——你的安全结论是绑在具体那一份上的，标签漂了结论就没了。

## 墙四：`--rm` 只在它自己想退出的时候生效

`DockerCodeRunner.java:245-251` 那段注释是这个形状：强杀宿主上的 docker CLI 只是第一步，CLI 被 SIGKILL 之后来不及通知 daemon，容器仍由 daemon 管着，`--rm` 只在容器自己退出时生效；不补这一刀，一个 `while(true)` 会带着 0.5 CPU / 256MB 一直跑，超时约束形同虚设。所以它在强杀之后还要从 `--cidfile` 里读出容器 id，补一条 `docker rm -f`（`:329-353`）；删除失败只 `log.warn`，因为「超时」这件事不该被改写成 500。

`--cidfile` 自己还有个前提：路径必须不存在，已存在时 `docker run` 直接返回 125（`:70-71`）。这是「冷启动没问题、重启一次就全挂」的那类坑。

池化之后这条边界又换了一次形状。`SqlContainerPool.java:23-26` 把代价写得很清楚：隔离从「每次一个干净容器」降成「多个用户共享一个 mysqld」，所以每次执行要现建一个库、一个只对那个库有权的账号，跑完连库带账号一起删。这时挡在用户之间的是 MySQL 的库级授权，不是容器的隔离——两者不是一回事。

收尾时容易骗自己的几个动作：

| 动作 | 结果 |
| --- | --- |
| `docker rm -f <id>` 一个已经停掉的容器 | 能删。上面那段兜底用的就是它 |
| `docker ps` 里看不到它 | 可能只是停了，`docker ps -a` 看状态；`Exited (137)` 是内核杀的 |
| `docker container prune` | 只删已停止的容器，不动卷 |
| `docker system prune --volumes` | 停止的容器先被删掉，它原本占着的卷在同一条命令里就成了候选 |

## 症状 → 先看哪

| 看到 | 先看 | 为什么 |
| --- | --- | --- |
| PORTS 列是 `0.0.0.0:3306->3306/tcp` | `-p` 前面有没有写 `127.0.0.1:` | 不写就绑所有网卡，宿主防火墙不在这一层 |
| 宿主连 3306 报 111，容器 `Up` | `docker exec <容器> ss -lntp` 有没有 `:3306` | 没在听 TCP，就不是映射写错，是进程没开 |
| 容器里 `docker ps` 能跑 | `docker inspect --format '{{json .Mounts}}' <容器>` 找 socket | 挂了 `/var/run/docker.sock`，那个容器就是宿主 root |
| 宿主 `docker ps` 报 `permission denied ... docker daemon socket` | `id -nG` 里有没有 `docker` | 加组等于分 root；`sudo` 只是不让你看见这件事 |
| `docker run` 一行就返回 125，容器没起来 | `--cidfile` 指的是不是已经存在的路径 | `DockerCodeRunner.java:70-71` 记的就是这一条 |
| 超时之后 `docker ps -a` 里它还在跑 | `--rm` 只在容器自己退出时生效 | 杀 CLI 不通知 daemon，得另补 `docker rm -f` |

## 还差的

- 本机没装 Docker。上面每一条回显——`ERROR 2003 (HY000) ... (111)`、`docker inspect` 的输出形状、`ufw status` 与 `DOCKER-USER` 的关系、125 那个退出码——都是照标准形态写的，一条都没跑过。仓库里那些耗时（`--initialize` 17.89 秒、启动到可查询 4.4–4.7 秒、起容器 1.1 秒 / 拷 datadir 1.05 秒 / InnoDB 初始化约 2 秒、一次 SQL 3.5–4.2 秒、池化后约 120 毫秒）是别人记在注释里的，我也没复现。
- 防火墙那段限定在 Linux、默认 iptables 后端、用 ufw 的机器。nftables 后端、rootless、`--iptables=false` 这三种形态行为不同，我一个都没验。
- 两个我没实跑的细节：`docker history` 里被展开的 build arg 究竟长什么样（BuildKit 与经典 builder 我没各看一遍，只按官方文档的告警写结论）；`system prune --volumes` 内部先删容器还是先算卷，文档没明说，表里写的是它表现出来的事实形状。
- 池化之后用户之间的边界只到 MySQL 库级授权（`GRANT ALL ON 那个库.*`）这一层。一个能连上共享 mysqld 的人，还有没有别的入口看到别人的库，我没查。
- 镜像钉了 digest，但 digest 钉住的只是「构建机当时那一份」；它并不说明那一份里没有已知漏洞。漏洞这一维本文没量过。
