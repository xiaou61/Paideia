## 这一关在解决什么

压测环境没问题，一上服务器就报 `Connection refused`：应用起来时数据库还没就绪。
你在 `command` 前面加了 `sleep 5`，好像好了；换台机器又挂了。

**结论先说**：`sleep` 是在赌"它一定在 5 秒内起来"。正确做法是**让容器自己回答"我好了"**
（healthcheck），让依赖**等这个回答**（`depends_on: condition: service_healthy`）。

## 讲解

### 容器"running"不等于"能用"

`docker ps` 显示 `Up 3 seconds` 只说明**主进程还活着**。数据库的主进程活着的头两三秒里，
3306 端口往往还没开始监听：

```text
$ docker run -d --name db mysql:8
$ docker logs db | tail -3
2026-10-29 09:00:01 [Note] Server hostname (bind-address): '*'
2026-10-29 09:00:01 [Note] ready for connections. Version: '8.0.36'  socket: '/var/run/mysqld/mysqld.sock'
```

第二行出现之前，谁连都是 `Connection refused`。这中间的时间**不固定**——冷启动、磁盘慢、
数据没初始化完，都能让"5 秒"不够。

### HEALTHCHECK：把"能用"写成命令

```dockerfile
HEALTHCHECK --interval=5s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://127.0.0.1:8080/actuator/health || exit 1
```

四个参数分别是什么：

| 参数 | 含义 | 设错的后果 |
| --- | --- | --- |
| `--interval` | 多久查一次 | 太密浪费 CPU，太疏启动变慢 |
| `--timeout` | 单次超时 | 太短会把"忙但活着"判死 |
| `--start-period` | **启动宽限期**：这段时间内的失败不计入 retries | 不设的话，慢启动应用会被反复判 unhealthy |
| `--retries` | 连续失败几次才算 unhealthy | 设为 1 时一次抖动就翻脸 |

`start-period` 是最容易漏的：它是"我第一次启动可能很慢，给我 20 秒"的声明。

状态在 `docker ps` 里能直接看到：

```text
$ docker ps --format "table {{.Names}}\t{{.Status}}"
NAMES    STATUS
app      Up 12 seconds (healthy)
db       Up 15 seconds (healthy)
```

### Compose 里等"健康"，不是等"启动"

```yaml
services:
  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p$$MYSQL_ROOT_PASSWORD"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy   # 关键：等健康，不等启动
```

`depends_on` 有三种写法，差别很大：

- `depends_on: [db]` —— 只保证**启动顺序**，不等就绪（旧行为，常见坑）
- `condition: service_started` —— 同上
- `condition: service_healthy` —— **等健康检查通过**（要 db 先定义 healthcheck）

### 应用侧也要"等"，但要有上限

编排只是减少概率，真正稳的做法是应用自己带重试：

```java
// Spring Boot：数据库连接失败时重试，而不是直接退出
@Configuration
public class DbRetryConfig {
    @Bean
    public DataSource dataSource(DataSourceProperties props) {
        HikariConfig config = props.initializeDataSourceBuilder().type(HikariConfig.class).build();
        config.setInitializationFailTimeout(60_000); // 最多等 60 秒
        config.setConnectionTimeout(5_000);
        return new HikariDataSource(config);
    }
}
```

`initializationFailTimeout` 是**有上限的等待**：等得到就正常启动，等不到就失败退出，
不会永远挂着——这正是 `sleep` 做不到的（sleep 是无条件等待，且不知道对方到底有没有好）。

## 动手

```text
$ docker compose up -d db
$ docker inspect --format '{{.State.Health.Status}}' $(docker compose ps -q db)
starting
$ sleep 20 && docker inspect --format '{{.State.Health.Status}}' $(docker compose ps -q db)
healthy
```

然后故意把 app 的 `depends_on` 改成 `condition: service_started`，观察它是否开始偶发
`Connection refused`——**这就是 sleep 式启动顺序的真实表现**。

## 常见误区

### 误区：`depends_on` 写了就有顺序保障

**你以为**：写了 `depends_on: [db]` 就一定先起 db 再起 app。
**其实**：它只保证**创建顺序**，db 的进程起来了但端口没监听时，app 照样连不上。
真正的"依赖就绪"要 `condition: service_healthy`，而且健康检查得写对（查端口/接口，不是查进程名）。

### 误区：健康检查就用 `curl` 首页

**你以为**：能返回 200 就是健康。
**其实**：首页 200 可能只是个静态页，数据库连接池早炸了。健康检查要查**依赖就绪**的接口
（Spring 的 `/actuator/health` 会连数据库、Redis），而不是"服务还活着"。

## 小结

三句话：`Up` 不等于能用；`HEALTHCHECK` 把"能用"写成可判定的命令（别忘了 `start-period`）；
Compose 里用 `condition: service_healthy` 等单位就绪，应用侧再用有上限的重试兜底。
`sleep` 任何时候都不是答案——它只是把概率问题藏起来。
