## CI 昨天绿今天红，digest 却换了

把这类故障压缩成发布记录，只有三行（示意，不是某家公司的真实事故，也不是本机输出）：

```text
昨天 09:12  CI 绿  image=registry.example.com/paideia/api@sha256:<完整 digest A>
今天 09:12  CI 红  image=registry.example.com/paideia/api@sha256:<完整 digest B>
回滚目标     image=registry.example.com/paideia/api:latest
```

今天再查一次同一个标签：

```bash
$ docker image inspect --format '{{json .RepoDigests}}' registry.example.com/paideia/api:latest
["registry.example.com/paideia/api@sha256:<完整 digest B>"]
```

这是示意输出，不是本机跑出来的；真实值是完整的 64 位十六进制。代码一行没改，digest 却已经是 B；昨天的 A 没有写进发布记录，回滚时手里只有 `latest`，而它不是昨天那个 A。

> 本机没有 Docker、trivy、grype、syft、cosign。下面的命令按官方文档核对，输出只写标准形态；本仓库的真实配置会单独标出来源。

这不是「镜像坏了」，而是发布记录只记了一个可变别名，没有记内容地址。tag 可以改指，digest 不能；回滚要找回的是 digest，不是 tag 的名字。

## tag 是别名，digest 是内容

| 名字 | 长什么样 | 会不会变 | 用途 |
| --- | --- | --- | --- |
| tag | `mysql:8.0` | 发布者可以改指 | 给人读、给命令用 |
| digest | `sha256:<64 位十六进制>` | 内容变才变 | 锁定某一份内容 |
| image ID | `sha256:<config 哈希>` | 本地镜像不同 | 本机定位，不是发布坐标 |

看一个镜像的仓库 digest：

```bash
$ docker image inspect --format '{{json .RepoDigests}}' registry.example.com/paideia/api:1.8.0
["registry.example.com/paideia/api@sha256:<完整 digest>"]
```

这是标准输出形态，本机没跑。若输出是 `[]`，这个镜像就没有可用的仓库 digest：本地构建后还没 push 时会是这个结果。`{{.Id}}` 仍然有值，但它是本地镜像 ID，不是仓库里的 manifest digest。回滚要存的是 push 之后那个 digest。

### latest 只是普通 tag

`latest` 不会因为 `1.9.0` 推上来就自动指过去。它只是发布者手动维护的一个标签：有人 `docker push registry.example.com/paideia/api:latest`，它才更新；没人推，它就停在旧内容。Docker Hub 不替你更新这个指针。

所以「latest 就是最后被推上来的版本」不成立。它可能是最新，也可能停在旧内容。共享环境（测试、预发、生产、CI 缓存）用 digest；`latest` 只放在「随时愿意重来」的本地试验里。

## 钉 digest，还要钉对层级

本仓库的沙箱 Dockerfile 是这样钉基础镜像的：

```dockerfile
# backend/paideia-sandbox/images/mysql/Dockerfile
FROM mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b
```

写这篇时我用 Docker Hub registry API 查了这个 digest，返回的 `Content-Type` 是 `application/vnd.oci.image.index.v1+json`：它是多架构 index，不是某一个平台的 manifest。钉 index，amd64 和 arm64 机器会各自选对应平台的 manifest；钉成某个平台的 manifest，换架构就可能报 `no matching manifest`。

| 钉哪个 | 拉取时发生什么 | 适合 |
| --- | --- | --- |
| index digest | 按当前机器的 platform 选 manifest | 多架构发布 |
| platform manifest digest | 只认一个平台，换架构可能拉不到 | 单一架构、需要精确固定 |

有 buildx 时，用 `docker buildx imagetools inspect` 看 `MediaType` 是 index 还是 manifest。没有 buildx 的 Engine 不一定有这条命令，先别假设它可用。

本仓库另一个真实例子在 `backend/paideia-app/src/main/resources/application.yml`：

```yaml
sql-image: paideia-sandbox-mysql@sha256:e2eafb6ea161ddda420bde0f8d5ec3b0b03115811ea9507a23710034ef6d0a4f
```

这是判题环境的一部分：基础镜像悄悄更新，判分行为就可能跟着漂移。把镜像固定到 digest，是把「今天判题用的到底是哪一份」写进配置。

注意，digest 保证的是**内容一致**，不是**行为一致**。平台、运行时、环境变量、挂载配置、外部服务都可能变；把 tag 换成 digest 后，仍然要跑同一组启动和健康检查。把「内容没变」当成「行为没变」，是另一个坑。

## 先选工具，再谈扫描

`trivy`、`grype`、`syft`、`cosign` 都不是 Docker 自带。只装 Docker Engine 的机器上，第一条命令先遇到的不会是漏洞，而是 `command not found`。`docker scout` 也不是 Engine 的核心子命令：它要 Scout 插件或 Docker Desktop 的能力；没装时常见报错是 `docker: 'scout' is not a docker command.`，独立 CLI 也可能是 `command not found`。

| 你要回答的问题 | 工具 | 最小命令 | 退出码或前提 |
| --- | --- | --- | --- |
| 本地快速看漏洞 | Trivy | `trivy image <镜像>` | 默认发现漏洞也退出 0 |
| CI 门禁 | Trivy 或 Grype | `trivy image --exit-code 1 ...` / `grype ... --fail-on high` | Trivy 加 `--exit-code 1` 才返回 1；Grype 策略失败 2；执行错误 1 |
| 生成 SBOM | Syft | `syft <镜像> -o spdx-json=...` | 0 成功、1 失败；不做通过/失败判断 |
| 用 SBOM 匹配漏洞 | Grype | `grype sbom:... --fail-on high` | 命中阈值 2；执行错误 1；默认 0 |
| 组织策略、持续监控 | Docker Scout | `quickview` + `enroll` + `repo enable` | 需要登录和插件；缺 attestation 是 `No data` |
| 验签名、验来源 | cosign | `cosign verify ...` | 验不过返回非 0 |

`docker scan` 已经停止支持，旧教程里让你跑它的段落可以直接跳过。新流水线用 Docker Scout，或者 Trivy/Grype 这套独立工具。

## 扫描器看见的是包和 secret，不是运行时

Trivy 的 `image` 扫描默认开 `vuln` 和 `secret`：它会比对 OS 包、语言包里的已知漏洞，也会找镜像里的明文凭据。它默认**不做**配置检查；配置检查要显式开 `--scanners misconfig`，或者对 Dockerfile、K8s YAML 目录跑 `trivy config .`。

```bash
# 本地快查
$ trivy image --severity HIGH,CRITICAL mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b

# CI 门禁：没有 --exit-code 1，有 HIGH 也返回 0
$ trivy image --exit-code 1 --severity HIGH,CRITICAL mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b

# 配置检查：镜像配置，或 Dockerfile/K8s 文件
$ trivy image --scanners misconfig mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b
$ trivy config .
```

输出开头是 OS 和语言包分组，末尾给一行 `Total: ...`；具体数字取决于 digest 和当天漏洞库，我不在这里贴一个假数。

所以「扫描器只能发现已安装包的 CVE」说得太满。准确的说法是：**默认的漏洞扫描发现不了运行时配置错误**，比如容器默认以 root 运行、根文件系统可写、capability 给得太宽。Grype 只做漏洞匹配，Syft 只出 SBOM，它们本来就不负责配置检查。

## SBOM 只回答「有没有这个组件」

SBOM 是配料表，不是判决书。它回答「镜像里有没有这个组件、版本是多少」；要回答「事故当天我有没有中」，还得拿 SBOM 去匹配当天漏洞库。

```bash
$ IMAGE='mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b'
$ syft "$IMAGE" -o spdx-json=mysql-8.0-7dcddc01.spdx.json
$ grype sbom:mysql-8.0-7dcddc01.spdx.json --fail-on high
```

文件名里带上 digest 的前 8 位，是为了让这份 SBOM 和那一份内容绑定。不要用 `mysql-8.0-latest.spdx.json` 这种名字；tag 一动，文件就不知道对应谁了。每次构建重新生成，别拿上个月的 SBOM 代表今天推的镜像。

Grype 的退出码要单独记：默认发现漏洞也返回 0；加 `--fail-on high`，命中 HIGH 返回 **2**；扫描本身出错返回 **1**。CI 里如果写 `grype ... --fail-on high || exit 1`，会把「策略失败」和「工具失败」混成同一个 1。只看「非 0 就红」没问题；要在脚本里区分原因，就别把 2 吞掉。

Syft 不判断通过/失败，只返回 0 或 1。不要给它加 `--fail-on`，它没有这个语义。

## Docker Scout：No data 不是通过

Scout 的入口不是一条裸命令。先登录，确认插件在，再看 policy：

```bash
$ docker login
$ docker scout version
$ docker scout quickview mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b

# 要让 Scout 持续看这个组织/仓库，还要这两步
$ docker scout enroll <ORG>
$ docker scout repo enable --org <ORG> <ORG>/<repo>
```

`quickview` 依赖登录态和 Scout 插件；没有 `docker login`，或者 Engine 上没装插件，它不会给你一份可比较的报告。一次 `quickview` 也不等于持续监控：要让 Scout 在新镜像推上来时重新评估，得 `enroll` 组织并用 `repo enable` 打开仓库。

Policy 结果依赖 SBOM/provenance attestation。镜像没有对应 attestation 时，结果显示 `No data`，不是通过。Docker 官方 quickstart 里的形态是：

```text
Policy status FAILED (2/6 policies met, 2 missing data)
? │ Supply chain attestations │ No data
```

这是官方示例的输出形态，不是本机输出。看到 `No data` 先补 SBOM/来源证明，不要把它当成绿色。

## 构建期凭据：ARG 不是秘密通道

下面这种写法留痕：

```dockerfile
ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > /root/.npmrc \
 && npm ci
```

`ARG` 的值会进构建历史/provenance，`docker history --no-trunc` 能看到展开后的命令。`--build-arg` 只是把值送进构建，不是秘密通道；删掉 `ARG` 也不会把已经写进层的文件删掉。

正确做法是 BuildKit secret：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:22-bookworm-slim@sha256:<完整 digest>
WORKDIR /app
COPY package*.json ./
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
COPY . .
```

构建时把文件挂进去：

```bash
$ docker build --secret id=npmrc,src=.npmrc -t api .
```

需要 BuildKit。新版 `docker build` 默认走 BuildKit；老环境先确认 `docker buildx version`，或者显式用 `docker buildx build`。`<完整 digest>` 要换成一个真实的 64 位十六进制 digest；不要写 `sha256:9a3b...c41f` 这种带省略号的，Docker 会报 `invalid reference format`。

`.dockerignore` 是第二道门：

```text
.git
.env
.npmrc
*.pem
*.key
node_modules
```

BuildKit secret 只保证挂载的文件不落层；如果 `COPY . .` 把 `.npmrc` 也复制进去，照样进镜像。也不要在 `RUN` 里把 secret `cat` 到日志。

## digest 不证明是谁构建的

digest 只证明内容没变，不证明谁构建的、从哪来、构建过程有没有被改。攻击者可以给你一个固定 digest，内容稳定但来路不明。供应链要补的是签名和来源证明。

用 cosign 签 digest，验的时候同时钉身份和 issuer：

```bash
$ cosign sign --yes ghcr.io/acme/api@sha256:<完整 digest>

$ cosign verify ghcr.io/acme/api@sha256:<完整 digest> \
    --certificate-identity 'https://github.com/acme/api/.github/workflows/release.yml@refs/heads/main' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

keyless 不是「没有身份」。它用 OIDC 身份换 Fulcio 的短期证书，签名事件写进 Rekor；验证时必须同时钉 `--certificate-identity` 和 `--certificate-oidc-issuer`。只跑 `cosign verify`，等于只验「某个 Sigstore 证书签过」，不验「是不是你的流水线」。GitHub Actions 里还要给 job `id-token: write`，否则 cosign 拿不到 OIDC token。

公共 Sigstore 免费，但不是你的 SLA。强合规或断网环境用 key-based（自管密钥）或私有 Fulcio/Rekor 部署；这部分的运维成本要提前算进去。

SBOM 和来源证明也要签：

```bash
$ cosign attest --yes --predicate mysql-8.0-7dcddc01.spdx.json \
    --type spdxjson ghcr.io/acme/api@sha256:<完整 digest>

$ cosign verify-attestation --type spdxjson \
    ghcr.io/acme/api@sha256:<完整 digest> \
    --certificate-identity '<你的 workflow identity>' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

`cosign sign` 签的是镜像 digest；`cosign attest` 签的是 SBOM 或 provenance 声明。两个都要。Scout 的 supply chain policy 看的是它认识的 attestation；只做镜像签名，不会自动补上这些数据。签名对象也用 digest，不要用 tag——tag 可能在 sign 和 verify 之间被移动。

## 跑一遍

下面这些命令我没在本机跑过；这台机器没有 Docker、trivy、grype、syft、cosign。你在有 Docker 的 Linux 机器上按顺序跑，输出以你机器的 digest 和当天漏洞库为准。

```bash
# 1. 先看仓库 digest；这个镜像要先按 backend/paideia-sandbox/images/mysql/build.sh 构建
$ docker image inspect --format '{{json .RepoDigests}}' paideia-sandbox-mysql:8.0

# 2. 扫真实 digest，并让 CI 失败
$ trivy image --exit-code 1 --severity HIGH,CRITICAL \
    mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b

# 3. 生成 SBOM，再用 Grype 匹配；命中 HIGH 时退出码是 2
$ syft mysql:8.0@sha256:7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b \
    -o spdx-json=mysql-8.0-7dcddc01.spdx.json
$ grype sbom:mysql-8.0-7dcddc01.spdx.json --fail-on high
$ echo $?

# 4. 验签：identity 和 issuer 都要换成你自己的
$ cosign verify ghcr.io/acme/api@sha256:<完整 digest> \
    --certificate-identity '<你的 workflow identity>' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

如果 `grype` 返回 2，那是策略失败；返回 1 是扫描本身失败。Trivy 不加 `--exit-code 1`，有 HIGH 也返回 0——这类门禁看起来在跑，实际什么都没拦住。

## 还差的

这篇没有给出一条能直接复制的 CI YAML。不同平台的登录、缓存、权限不同，照抄 YAML 比照抄命令更容易错；这里只把命令和退出码钉住。

也没有做 CVE 可达性分析。扫描器报 HIGH 不等于可利用，VEX、运行时调用链、组件是否在请求路径上，这些都不在本文范围内。

私有 registry、离线漏洞库、私有 Sigstore 的部署细节也没展开；公共 Sigstore 的可用性边界只点到为止。真实上线前，还得按你的合规要求补 SLA、密钥托管和审计。

最后，本文所有 Docker/扫描/签名命令都没有在本机执行过；输出形态按官方文档写，真实数字要以你机器的 digest 和当天漏洞库为准。
