## 这一关在解决什么

`FROM mysql:8` 或 `image: app:latest` 这类写法到处都在用，看起来最省事。
但某天重新拉一遍，行为变了；再某天，基础镜像里爆出一个 CVE，你不知道自己有没有受影响。

**结论先说**：标签是**可变的指针**，digest 才是**内容地址**。要 reproducible，
钉 digest；要安全，扫镜像 + 知道里面到底装了什么（SBOM）。

## 讲解

### 标签 vs digest：一个是别名，一个是哈希

```text
$ docker pull mysql:8
8: Pulling from library/mysql
Digest: sha256:9a3b...c41f
Status: Downloaded newer image for mysql:8

$ docker images --digests mysql
REPOSITORY  TAG  DIGEST                     SIZE
mysql       8    sha256:9a3b...c41f         590MB
```

`mysql:8` 这个标签今天指向 `9a3b...`，三个月后维护者推了新补丁，同一个标签就指向另一个 digest。
**你什么都没改，跑的东西变了。**

钉住写法：

```dockerfile
FROM mysql:8@sha256:9a3b...c41f
```

```yaml
# compose
services:
  db:
    image: mysql:8@sha256:9a3b...c41f
```

本仓的 SQL 沙箱镜像就是钉 digest 的（`paideia-sandbox-mysql@sha256:e2ea...`），
因为它是判题环境的一部分：**判分结果不能因为基础镜像悄悄更新而漂移**。

### `latest` 的真实代价

| 你以为 | 实际 |
| --- | --- |
| latest = 最新最稳 | 它只是"最后被推上来"的那个标签，可能是半成品 |
| 不用记版本号，方便 | 两台机器 `docker pull` 时间不同 → 版本不同 → 行为不同 |
| 回滚时知道回哪 | 回滚时没有"旧 latest"可回，只能靠 digest |

**纪律：`latest` 只允许出现在"我随时愿意重来"的地方**（本地试验），
任何共享环境（测试、预发、生产、CI 缓存）都不该有。

### 扫描：知道镜像里有什么

```text
$ docker scout quickview mysql:8
$ trivy image --severity HIGH,CRITICAL mysql:8
2026-10-29T09:12:01 INFO  Detected OS: debian 12.5
2026-10-29T09:12:03 INFO  Number of language-specific files: 12
mysql:8 (debian 12.5)
Total: 47 (HIGH: 12, CRITICAL: 3)
```

扫描器做两件事：读镜像里的**包清单**（dpkg/apk/npm/jar…），与漏洞库比对。
所以它只能发现"**已安装的包**有已知 CVE"，发现不了配置错误（比如以 root 跑）。

### SBOM：镜像的"配料表"

```text
$ syft mysql:8 -o spdx-json > mysql-8.spdx.json
$ grype sbom:mysql-8.spdx.json
```

SBOM（软件物料清单）回答"这个镜像里有哪些组件、什么版本"。它的价值在**事故当天**：
新爆一个 CVE，你不用重新扫所有镜像，只要查 SBOM 里有没有那个组件。

### 依赖与基础镜像的三条纪律

1. **基础镜像钉 digest**，升级是一次显式的改动（有 diff、有记录）。
2. **构建期也钉版本**：`pip install` 不带版本号等于赌仓库今天的解析结果。
3. **镜像里不留构建凭据**：`.npmrc`、`.git`、带 token 的 `settings.xml` 一律不进镜像
   （`--secret` 或构建参数传，构建后不留痕）。

## 动手

```text
# 1. 找到你正在用的镜像的 digest
$ docker images --digests | grep <镜像>

# 2. 扫一遍
$ trivy image --severity CRITICAL <镜像>:<tag>

# 3. 验证钉住：改 tag 成 digest 重新 pull，行为应完全一致
$ docker pull <镜像>@sha256:...
```

## 常见误区

### 误区：只用官方镜像就安全

**你以为**：`library/*` 的官方镜像审核过，放心用。
**实情**：官方镜像只保证"构建方式公开"，不保证零漏洞——它同样带着一整套系统包，
同样会积累 CVE。而且**官方镜像也会更新标签指向**，你的"没改过"和"没变过"是两件事。

### 误区：扫描报了 200 个 HIGH，说明这个镜像不能用

**你以为**：数字越大越危险。
**实情**：要分"能不能触达"。一个只在构建期用的 `curl` 带的漏洞，与运行期暴露的 8080
上的库漏洞，风险完全不同。**先修 CRITICAL 且可触达的，再把其余记成已知风险**，
而不是看到 200 就换镜像——通常换完还是 180。

## 小结

标签是别名、digest 是内容，共享环境一律钉 digest。扫描器回答"装了哪些包、有没有已知 CVE"，
SBOM 回答"事故当天我有没有中"。三条纪律：钉版本（基础镜像与依赖）、不进凭据、把
"可触达的 CRITICAL"当作必修项。
