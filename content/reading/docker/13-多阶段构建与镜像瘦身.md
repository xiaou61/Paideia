## 我的镜像 782MB，用它只跑一个 jar

第一次把自己的 Spring Boot 项目打成镜像，推上测试机，运维问我："你这镜像怎么快 800M？"

我 `docker images` 一看：

```text
REPOSITORY   TAG      IMAGE ID       CREATED        SIZE
demo         single   9f2c1e7a4b31   2 minutes ago  782MB
```

一个 80MB 的 jar，镜像 782MB。我当时第一反应是"jar 里依赖太多"，翻了半天依赖树，没找出问题。

真正的原因在 `docker history`：

```text
$ docker history demo:single
IMAGE          CREATED BY                                      SIZE
9f2c1e7a4b31   CMD ["java" "-jar" "target/app.jar"]            0B
8b1d...        RUN /bin/sh -c mvn -q -DskipTests package        612MB
3c9a...        COPY . . # buildkit                             41.2MB
1a7f...        WORKDIR /app                                    0B
f0e2...        FROM maven:3.9-eclipse-temurin-21               0B
```

612MB 在 `mvn package` 那一层。里面是 Maven 自己、整个 JDK、下载下来的 `.m2` 依赖，还有编译出来的 `target/`。这些东西编译完就没用了，但因为是同一条 `RUN` 产生的层，它们全留在镜像里。

## 一个阶段等于"构建现场 + 运行产物"一起打包

出问题的那版 Dockerfile 很朴素：

```dockerfile
FROM maven:3.9-eclipse-temurin-21
WORKDIR /app
COPY . .
RUN mvn -q -DskipTests package
CMD ["java", "-jar", "target/app.jar"]
```

它能跑，问题在于把两件事塞进了一个镜像：

| 镜像里有什么 | 构建时需要 | 运行时需要 |
| --- | --- | --- |
| Maven 发行版（约 90MB） | 要 | 不要 |
| 完整 JDK（含 `javac`、`jlink`） | 要 | 只要 JRE |
| `~/.m2` 依赖缓存 | 要 | 不要 |
| 源码、`.git`、`target/` | 要 | 只要那一个 jar |

下面几行都是"运行时不要"的东西。另外还有一层隐性代价：镜像里带着编译器、包管理器和源码，等于把攻击面也一起发布出去了。

## 两个 FROM，只把 jar 搬过去

Docker 的规则很简单：**最终镜像只有最后一个 `FROM` 阶段的内容，前面阶段只作为 `COPY --from` 的来源存在**，构建完就丢。

于是把它拆成两段：

```dockerfile
# 阶段一：构建。这里的任何东西都不会进最终镜像
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -q -DskipTests dependency:go-offline
COPY src ./src
RUN mvn -q -DskipTests package

# 阶段二：运行。只拷一个 jar 进来
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/target/app.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

关键只有一行 `COPY --from=build`。同一个项目重新构建，`docker images` 从七百多 MB 掉到两百 MB 出头（具体数字取决于你的依赖量，你可以自己前后对比一次）。

改动之后有几件事值得确认，别只看体积：

```bash
$ docker run --rm -p 8080:8080 demo:multi
$ curl -s localhost:8080/actuator/health    # 起来了吗
$ docker history demo:multi | head -5       # 还有没有 mvn 层
```

## 中间那两行 COPY 不是随便拆的

```dockerfile
COPY pom.xml .
RUN mvn -q -DskipTests dependency:go-offline
COPY src ./src
```

这不是为了好看。Docker 的层缓存是**按指令顺序逐条匹配**的：某条指令和它依赖的文件没变，就复用缓存层，从第一条变化的指令开始往后全部重跑。

所以：

- 先拷 `pom.xml`、下依赖 —— 依赖清单没变，这一层就一直命中
- 再拷 `src` —— 改一行代码，只重跑编译

我第一次写多阶段的时候是这么干的：

```dockerfile
COPY . .
RUN mvn package
```

结果每次改一行 Java，构建都要重新下载全部依赖，三四分钟起步。把 `COPY . .` 放在依赖下载之前，这条优化就白做了——这是多阶段构建里最容易白干的地方。

顺便说一句 `.dockerignore`。`COPY . .` 会把 `target/`、`.git`、`node_modules` 一起送进构建上下文，第一次构建可能光传上下文就几十秒。加一个 `.dockerignore`，写上 `target`、`.git`、`.idea`，立刻能感觉到差别。

## 我踩过的三个坑

**坑一：distroless 没有 shell。** 看文档说 `gcr.io/distroless/java21` 才 90MB，我直接换上去，结果容器起不来想进容器看一眼，`docker exec -it xxx sh` 报 `exec: "sh": executable file not found`——它真的没有 shell。后来我的顺序改成：先用 `-jre` 镜像跑稳定，确认日志和监控够用，再考虑换 distroless。

**坑二：alpine 不是"更小的同一个东西"。** `eclipse-temurin:21-jre-alpine` 体积小一半，但它用 musl libc。我遇到的是容器内 DNS 解析行为和宿主机不一致，表现为"连数据库偶尔超时"，本地复现不出来。这类问题排查成本远高于省下的那 100MB，除非你有明确的体积压力，否则不值得。

**坑三：别用 `--from=0` 这种数字写法。** 它依赖阶段顺序，中间插入一个阶段就悄悄拷错东西。给阶段起名（`AS build`）然后 `COPY --from=build`，改起来安全得多。

## 还能再小，但要拿排查能力换

| 运行镜像 | 大致体积 | 代价 |
| --- | --- | --- |
| `eclipse-temurin:21-jre` | ~230MB | 有 shell，能进容器排查 |
| `eclipse-temurin:21-jre-alpine` | ~120MB | musl libc，native 库与 DNS 行为可能不同 |
| `gcr.io/distroless/java21` | ~90MB | 没有 shell，只能靠日志与远程 debug |
| `jlink` 自建运行时 | ~50MB | 要手写模块列表，漏一个模块运行时就报错 |

这张表里的体积是官方镜像的量级，会随版本变，别当固定值用。

我的建议只有一条：**镜像瘦身放在最后做**。项目还在频繁改、还在天天进容器看状态的时候，`-jre` 就是对的答案；等服务和排查手段都稳定了，再往 distroless 或 jlink 走。

## 前后端一个仓库时，多阶段可以有三层

前端产物直接并进后端 jar，最终镜像里只有一个文件，连 nginx 都不需要：

```dockerfile
FROM node:20 AS frontend
WORKDIR /web
COPY web/package*.json ./
RUN npm ci
COPY web/ .
RUN npm run build

FROM maven:3.9-eclipse-temurin-21 AS backend
WORKDIR /app
COPY pom.xml .
RUN mvn -q -DskipTests dependency:go-offline
COPY src ./src
COPY --from=frontend /web/dist ./src/main/resources/static
RUN mvn -q -DskipTests package

FROM eclipse-temurin:21-jre
COPY --from=backend /app/target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

`npm ci` 和 `pom.xml` 的依赖层各自独立缓存，前端改代码不会触发 Maven 重下依赖。

## 一句话

多阶段构建解决的不是"镜像太大"，是"构建环境和运行环境混在一起"。判断有没有做对，看两条：`docker history` 里不该有 `mvn` 层，`COPY --from` 拷过去的应该只有产物。

还有一个我一直没做的优化：`-DskipTests` 让我在镜像构建里跳过了测试。正确做法是测试在 CI 跑，镜像只负责打包——但这要求 CI 和镜像构建用同一个 JDK 版本，否则可能出现"CI 过了、镜像里行为不一样"。这个坑我还没踩到，先记在这里。
