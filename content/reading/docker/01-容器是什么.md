## 这一关在解决什么

"容器是轻量虚拟机"这句话错在哪儿？为什么容器里 `uname -r` 显示的是宿主的内核？为什么容器里装不了内核模块、起不了 systemd、`kill -9` 也不一定灵？

答案都在一句话里：**容器不是一台机器，是一组被隔离的进程。**

## 为什么会有容器

虚拟机的问题是"重"：每个 VM 都要装一整套操作系统，启动要几十秒，内存至少几百 MB，一台机器能跑的 VM 数量有限。而真实需求往往只是"我想要一个干净的、跑着特定版本软件的环境"。

容器把"隔离"从**虚拟硬件**降到了**进程**这一层：同一批内核，给每个进程组一套自己的视图。代价是隔离强度不如 VM，换来的是秒级启动和几 MB 的额外开销。

## 讲解

### 三件东西的关系

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **镜像**（image） | 只读的文件系统快照 + 启动配置 | 一份安装光盘 |
| **容器**（container） | 镜像 + 一层可写层 + 正在跑的进程 | 从光盘装出来且正在运行的系统 |
| **仓库**（registry） | 存镜像的地方 | 应用商店 |

所以 `docker run` 做的是：找到镜像 → 在它上面加一层空的"可写层" → 用镜像里声明的命令启动一个进程。这个进程就是容器的全部——**进程退出，容器就退出**。

这条推论极其重要：

```text
$ docker run -d nginx          # 主进程是 nginx 的 master
$ docker run -d alpine sleep 5 # 5 秒后主进程退出，容器 Exited
```

`docker ps -a` 里那一堆 `Exited (0)` 的容器，绝大多数是"主进程跑完了"，不是"容器坏了"。

### 隔离靠什么：namespace 与 cgroup

内核提供两套机制，各管一件事：

| 机制 | 管什么 | 效果 |
| --- | --- | --- |
| **namespace** | 看得见什么 | 自己的进程表（PID）、网卡与端口（net）、挂载点（mnt）、主机名（UTS）、IPC、用户映射（user） |
| **cgroup** | 能用多少 | CPU 配额、内存上限、IO 带宽、进程数上限 |

namespace 让容器里的 `ps` 只看到自己的进程、`ip a` 只看到自己的网卡、`hostname` 是自己的名字。cgroup 让它跑不超过 1 核、内存超了被杀——这两点正是"看起来像一台独立机器"的来源。

**但它们共享同一个内核**。所以：

- `uname -r` 在容器和宿主里**完全一样**；
- 容器里不能 `modprobe`（内核模块属于内核，不共享不了）；
- 内核漏洞可以导致逃逸（这也是 gVisor、Kata 这类"更强的隔离"存在的原因）；
- 容器里**没有 init 系统**（没 systemd），因为没有开机流程，第一个进程直接就是你的程序。

### 和虚拟机的对比

| | 虚拟机 | 容器 |
| --- | --- | --- |
| 隔离层 | 硬件虚拟化 | namespace + cgroup |
| 内核 | 每个 VM 一个 | **共享宿主内核** |
| 启动时间 | 数十秒 | 几十毫秒到几秒 |
| 体积 | GB 级（含完整 OS） | MB 级（只含应用与依赖） |
| 能装别的 OS 吗 | 能（Linux 上跑 Windows） | **不能**（Linux 容器必须跑 Linux 程序） |
| 隔离强度 | 强 | 较弱，需要额外加固 |
| 一台机器能跑几个 | 几个到几十个 | 几十到几百个 |

**"能不能跑 Windows 容器"这条是硬分界**：容器共享内核，所以在 Linux 宿主上只能跑 Linux 程序。想在 Linux 上跑 Windows 程序，得用 VM。

### 容器的第一个进程：PID 1 的特殊性

容器里主进程的 PID 是 `1`。PID 1 在 Linux 上是个特殊角色：

- **它是信号的最后一道防线**：内核不会给 PID 1 投递它没有注册处理器的信号。所以容器里的 PID 1 如果没写信号处理，`docker stop` 发的 SIGTERM **可能被忽略**，等 10 秒后被 SIGKILL 强杀（第 09 关那套"先礼后兵"，这次是 Docker 在替你做）。
- **它负责回收孤儿进程**：容器内如果有进程 fork 后父进程先死，那个子进程会交给 PID 1 收养。如果 PID 1 不是个正经 init（比如是一个 shell），它不会 `wait`，于是容器里堆起僵尸进程。

所以有两条实践：

1. **主进程直接是应用**（`CMD ["java", "-jar", "app.jar"]` 这种 exec 形式），不要写成 shell 形式（`CMD java -jar app.jar` 会被包成 `/bin/sh -c "..."`，sh 变成 PID 1 并可能吞掉 SIGTERM）。
2. 应用自己启动子进程、需要处理僵尸的，加一个微型 init：`docker run --init`，或镜像里用 `dumb-init`/`tini`。

Java 服务还有个具体后果：**Spring Boot 的优雅停机依赖 SIGTERM**。如果 PID 1 是 shell 并且没转发信号，你看到的"每次重启都要等 10 秒然后被强杀"就是这个原因。

### 容器不是安全边界（默认不是）

默认的容器有这么几个"不隔离"的地方：

| 默认行为 | 风险 | 缓解 |
| --- | --- | --- |
| 容器内是 root | 逃逸后直接是宿主 root（配合内核漏洞） | `--user 1000:1000` 或镜像里 `USER` |
| 挂载 `/var/run/docker.sock` | 等于给了宿主 root 权限 | **不要挂**，除非完全信任 |
| `--privileged` | 几乎等于不隔离 | 永不使用，除非明确知道代价 |
| 默认网络能出网 | 被用作扫描/爆破的跳板 | `--network=none` 或出口策略 |

生产上把容器当"打包工具 + 资源限制"，不当"安全沙箱"。真要跑不可信代码（比如在线判题），得再叠一层：gVisor（`--runtime=runsc`）、seccomp 白名单、只读根文件系统、断网。

## 常见误区

### 误区：容器里可以随便装东西，反正隔离了

**你以为**：容器是个沙盒，装什么都行。
**其实**：容器内默认是 **root**，而且共享宿主内核。一个容器内的 root 加上内核漏洞，就有机会影响宿主（这也是"不要把 docker.sock 挂进容器"的原因——那等于把宿主 root 直接交出去）。真正跑不可信代码要额外的隔离层，不是"有 Docker 就安全"。
**怎么验证**：容器里 `id` 显示 `uid=0(root)`；`ls -l /var/run/docker.sock` 如果被挂载进去，装个 docker 客户端就能操作宿主的全部容器。

### 误区：容器里的"重启"会保留我改的东西，所以可以直接在生产容器里改配置

**你以为**：`docker restart` 之后改动还在，凑合能用。
**其实**：可写层在 `restart` 时确实保留，但**任何一次"用同一个镜像重新 run"或 `compose up` 重建容器，改动全部消失**，而且没有人知道生产上那份配置和代码里的不一样。这是"能跑，但下次部署就神秘故障"的典型来源。
**怎么验证**：`docker inspect 容器 --format '{{.Image}}'` 看它用的镜像；改动的文件不在 `Mounts` 里，就注定会丢（第 05 关）。

### 误区：容器启动快，所以适合放数据库随时开关

**你以为**：既然秒级启动，数据库也可以随便重启。
**其实**：容器启动快不代表**应用**启动快。MySQL 冷启动要初始化 InnoDB、恢复 redo 日志，实测几秒到几十秒；而如果数据在容器可写层里（没挂卷），删容器就是删库。数据库容器必须挂卷，而且重启策略要谨慎。
**怎么验证**：`docker run --rm mysql:8` 起来后 `docker inspect` 看 `Mounts` 是否为空——空就说明数据在可写层，`docker rm` 即丢。
