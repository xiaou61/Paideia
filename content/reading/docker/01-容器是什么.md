## `nginx -v` 跑完，容器为什么是 `Exited (0)`

```text
$ docker run -d --name web nginx:1.30 nginx -v
<container-id>

$ docker ps
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES

$ docker ps -a
CONTAINER ID   IMAGE        COMMAND     CREATED         STATUS                    PORTS   NAMES
<container-id> nginx:1.30   "nginx -v"  10 seconds ago  Exited (0) 9 seconds ago          web
```

（标准输出形态；这台机器没装 Docker，下面的回显我没有在本机跑过。列宽由终端和内容决定，不固定。）

`docker ps` 默认只列运行中的容器，`-a` 才列已经退出的。这里不是 nginx 崩了：`nginx:1.30` 的默认 `CMD` 是让 nginx 在前台跑，但我在镜像名后面写了 `nginx -v`，它覆盖了默认 `CMD`，成为 `ENTRYPOINT` 的参数。`nginx -v` 打印版本后立刻退出，退出码 0；主进程退出，容器就进入 `Exited (0)`。`-d` 只把容器放到后台，不会让一条已经跑完的命令继续活着。

这就是容器的第一层事实：它不是一台小虚拟机，是一组被隔离的进程。镜像提供只读文件系统和默认命令；`docker run` 在镜像上叠一层可写层，启动主进程。主进程在，容器在；主进程退出，容器退出。

## 同一个 web，换一条命令就活着

`web` 这个容器还占着名字，先删掉再重来：

```text
$ docker rm web
web

$ docker run -d --name web nginx:1.30
<container-id>

$ docker ps
CONTAINER ID   IMAGE        COMMAND                   CREATED        STATUS        PORTS   NAMES
<container-id> nginx:1.30   "/docker-entrypoint.…"   5 seconds ago  Up 4 seconds          web

$ docker stop web
web

$ docker ps -a
CONTAINER ID   IMAGE        COMMAND                   CREATED        STATUS                    PORTS   NAMES
<container-id> nginx:1.30   "/docker-entrypoint.…"   8 seconds ago  Exited (0) 1 second ago           web
```

这次 `docker run` 没有覆盖命令，nginx 按镜像里的 `CMD` 在前台运行，所以 `docker ps` 能看到 `Up`。`docker stop` 只停进程，容器、名字、可写层还在；`docker ps -a` 仍能看到它。要把它从磁盘上删掉，还得 `docker rm web`。

`docker start web` 会重新启动这个已经存在的容器，保留它的可写层和配置；`docker run` 则是从镜像创建另一个新容器。两者不是同义词。`docker restart web` 是 stop 再 start，也不创建新容器。

镜像本身不会被 `docker rm` 删掉。容器删了，镜像还在；这一点在第 03 关会看得更清楚。

## 隔离的是视图和额度，不是内核

容器里的 `uname -r` 和宿主一样，`hostname` 不一样；`ps` 只看到自己 PID 命名空间里的进程，`ip a` 只看到自己的网卡。这些是 namespace 在做隔离。CPU、内存、IO、进程数上限由 cgroup 管。

| 机制 | 管什么 | 容器里的表现 |
| --- | --- | --- |
| namespace | 进程能看见什么 | 自己的 PID 表、网卡与端口、挂载点、主机名、IPC、用户映射 |
| cgroup | 进程能用多少 | CPU 配额、内存上限、IO 带宽、进程数上限 |

它们没有给容器一个新内核。默认情况下，容器里不能 `modprobe` 加载内核模块，也不会有 systemd 当 init；镜像的 `ENTRYPOINT`/`CMD` 直接成为 PID 1。容器里的用户默认是 root，除非镜像写了 `USER`，或者运行时加了 `--user`。

## 容器默认不是安全边界

把容器当打包工具和资源限制，不要默认把它当沙箱。下面几件事会改变风险：

| 默认或常见做法 | 风险 | 处理 |
| --- | --- | --- |
| 容器内进程是 root | 配合内核漏洞，逃逸后可能落到宿主 root | 镜像里写 `USER`，运行时用 `--user` |
| 挂载 `/var/run/docker.sock` | 容器里的进程能通过 Docker API 启动一个挂载宿主根目录的特权容器，等于交出宿主 root | 不要挂，除非完全信任这个容器 |
| `--privileged` | 接近关闭隔离 | 除非明确知道代价，不要用 |
| 默认 bridge 网络能出网 | 被拿来扫描或爆破外部目标 | `--network=none`，或在出口做策略 |

真要跑不可信代码，再加 gVisor（装了 `runsc` 之后用 `--runtime=runsc`）、seccomp 白名单、只读根文件系统、断网这些层。它们是额外加固，不是 Docker 默认送的。

## PID 1 不是普通进程

容器主进程的 PID 是 1。Linux 对 PID 1 有个特殊规则：进程没有注册处理器的信号，默认动作不会生效。所以 `docker stop` 先发容器的 stop signal：默认是 SIGTERM，镜像可以用 `STOPSIGNAL` 改（nginx 官方镜像就是 SIGQUIT），运行时也能用 `--stop-signal` 覆盖。Linux 容器默认等 10 秒（Windows 容器 30 秒），超时后再发 SIGKILL。`--timeout` 可以改等待时间。

nginx 自己处理这个信号（官方镜像是 SIGQUIT），正常停止时可以是 `Exited (0)`。如果进程被 SIGTERM 的默认动作终止，退出码是 143；如果 PID 1 不处理 stop signal，Docker 等到超时后发 SIGKILL，退出码是 137。退出码的细节在第 02 关。

shell 形式（`CMD java -jar app.jar`）会先起 `/bin/sh -c`。有些 shell 会把单条命令 `exec` 掉，让应用阴差阳错成为 PID 1；但这是实现细节，不是你能依赖的行为。需要确定信号到应用，就用 exec 形式（第 04 关）。Spring Boot 开了 `server.shutdown=graceful` 之后依赖 SIGTERM；信号到不了，就会等到超时再被杀。

应用如果自己 fork 子进程，PID 1 还要回收孤儿进程。不是 init 的 PID 1 不会 `wait`，容器里就会堆僵尸。`docker run --init` 会加一个微型 init；也可以在镜像里用 `tini`/`dumb-init`。

## 和虚拟机的分界

| | 虚拟机 | 容器 |
| --- | --- | --- |
| 隔离层 | 虚拟硬件，每个 VM 一套内核 | namespace + cgroup，共享宿主内核 |
| 内核 | 各自独立 | 共享宿主内核 |
| 能跑什么 | Linux 宿主可以跑 Windows VM | Linux 容器只能跑 Linux 程序；Windows 容器需要 Windows 宿主 |
| 启动路径 | 引导内核，再启动 init | 直接启动进程 |
| 体积 | 含完整操作系统 | 含应用、依赖和它需要的用户态文件，内核用宿主的 |
| 隔离强度 | 强 | 默认较弱，需要额外加固 |

“容器里跑的是另一个操作系统”这句话只对了一半：文件系统可以长得像 Ubuntu、Alpine 或 Debian，但系统调用进的是宿主内核。所以 `uname -r` 一样，也不能在容器里换内核。
