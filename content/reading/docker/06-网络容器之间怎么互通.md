## 这一关在解决什么

应用容器要连数据库容器，配置文件里该写 `localhost` 还是容器名？为什么两个容器在同一个宿主机上却 ping 不通？为什么 `localhost:3306` 在应用容器里连不上？

答案是：**每个容器有自己的网络命名空间，`localhost` 指的是它自己**。这一关讲清 Docker 的四种网络模式、端口映射和容器名解析。

## 为什么容器有"自己的网卡"

因为 network namespace（第 01 关）。一个容器启动时，Docker 给它配一张虚拟网卡、一个私有 IP、一套自己的路由表。所以：

- 容器里 `127.0.0.1` 是**容器自己**；
- 容器里 `ss -lntp` 看到的是容器里的监听；
- 宿主上 `ss -lntp` 看不到容器里的端口（除非做了端口映射）。

## 讲解

### 四种网络模式

| 模式 | 命令 | 特点 | 什么时候用 |
| --- | --- | --- | --- |
| **bridge**（默认） | `--network bridge` | 每个容器一个私有 IP，通过 NAT 出网 | 绝大多数场景 |
| **自定义 bridge** | `--network mynet` | 同上，**并且能用容器名互相解析** | 多容器协作（推荐） |
| **host** | `--network host` | 与宿主共用网络命名空间，端口直接占用宿主的 | 性能敏感、或需要绑宿主特定位 |
| **none** | `--network none` | 只有一个 loopback | 完全离线、跑不可信代码 |

还有一个 `container:<名字>`：共享另一个容器的网络命名空间，常用于排查（下面讲）。

### 默认 bridge 的坑：不能用名字互相访问

```text
$ docker run -d --name db postgres:16
$ docker run --rm alpine ping db
ping: bad address 'db'
```

默认的 `bridge` 网络**没有内置 DNS**，容器之间只能用 IP 访问，而 IP 每次重建都可能变。这就是"以前能连，重建之后连不上"的原因。

解法是建一个自定义网络，所有相关容器接进去：

```text
$ docker network create appnet
$ docker run -d --name db --network appnet postgres:16
$ docker run -d --name api --network appnet myapp:v1
```

之后 `api` 里直接连 `db:5432` 就行——Docker 在自定义网络里跑了一个内置 DNS（容器内看到的是 `127.0.0.11`），把容器名与网络别名解析成容器 IP，**重建容器、IP 变了也会自动更新**。

想给容器起别名（比如都叫 `db`）：

```text
$ docker run -d --network appnet --network-alias database postgres:16
```

`database` 这个名字在 `appnet` 里同样能被解析。

### 容器怎么访问宿主

三种情况：

```text
# 1. Linux 上：用 bridge 网关地址
$ ip -4 addr show docker0 | grep inet      # 常见 172.17.0.1
# 容器内访问 http://172.17.0.1:8080

# 2. Docker Desktop（Mac/Windows）：有专门的主机名
$ curl http://host.docker.internal:8080

# 3. 加一条 hosts 记录（最通用，Linux 也能用）
$ docker run --add-host host.docker.internal:host-gateway ...
```

`host-gateway` 是 Docker 提供的特殊值，会被解析成"宿主在这个网络里的地址"，比手动写死网关 IP 稳。

### 端口映射与"外面能不能连"

```text
$ docker run -d -p 8080:80 nginx                  # 0.0.0.0:8080 → 容器 80
$ docker run -d -p 127.0.0.1:8080:80 nginx        # 只给本机
$ docker run -d --network host nginx              # 直接用宿主 80
```

三条纪律（与 Linux 线第 15 关同一套判断）：

- 不写宿主 IP = 公网可达。内部服务一律 `127.0.0.1:` 或干脆不映射。
- **`--network host` 下 `-p` 无效**：容器直接用宿主网络，端口该冲突就冲突（`port is already allocated` 也变成宿主的抢占）。
- 容器之间互相访问**不需要端口映射**——同一网络里直接连容器端口。映射只是"给容器外面的世界开个门"。

### 排查网络：四条命令

```text
$ docker network ls
$ docker network inspect appnet                 # 看哪些容器接了进来、各自 IP
$ docker exec api getent hosts db               # 在容器里验证名字解析
$ docker exec api sh -c 'ss -lntp || netstat -lntp'   # 容器里谁在监听
```

第一条与第二条回答"它们是不是在同一个网络里"——**这几乎总是根因**。第三个用 `getent hosts` 而不是 `ping`：精简镜像里常常没有 `ping`，而 `getent` 一般都有。

### 共享另一个容器的网络来排查

镜像里没装工具（第 04 关说过不该装），但你想在**同一个网络命名空间**里看端口和抓包：

```text
$ docker run --rm -it --network container:api nicolaka/netshoot
# 现在这个容器里 ss/curl/tcpdump 都作用于 api 的网络
```

`--network container:名字` 不新建网络，直接复用目标容器的。这是"不往生产镜像里塞工具"的正解。

### 断开出网

```text
$ docker run --network none --rm alpine ping 1.1.1.1      # 不通
$ docker run --network none --rm alpine ip a              # 只有 lo
```

这是跑不可信代码时的必要条件：**没有网络，就没有把它当跳板去扫描/爆破/发垃圾邮件的可能**。本站的代码沙箱也是靠 `--network=none` 关掉出网的。

## 常见误区

### 误区：`--network host` 更快更省事，生产也这么用

**你以为**：绕开 NAT 性能好，端口也不用管。
**其实**：`host` 模式让容器失去网络隔离：容器能监听宿主的任何端口、能访问宿主所有的 loopback 服务（包括只绑 127.0.0.1 的管理接口），端口冲突也变成直接抢占。多个容器想用同一个端口时完全做不到。它只在"性能敏感 + 单实例"的少数场景里值得。
**怎么验证**：`--network host` 下 `ss -lntp` 看到的就是宿主的全部监听；再起一个同端口的容器会直接失败。

### 误区：容器里连不上宿主，是因为防火墙没开

**你以为**：宿主服务绑了 `127.0.0.1`，从容器访问不到，是防火墙问题。
**其实**：`127.0.0.1` 在容器里是容器自己，压根到不了宿主。宿主上只绑回环的服务**在设计上就不该给容器访问**（这是好事）。要访问就把宿主服务绑到 `172.17.0.1` 或 `0.0.0.0`（后者要配防火墙），或者用 `--network host`、`--add-host`+具体地址。
**怎么验证**：容器里 `ip route` 看默认网关（通常是 `172.17.0.1`），用那个地址访问宿主服务能通，说明网络层是通的，问题在绑定地址。

### 误区：容器 IP 可以写进配置文件

**你以为**：`jdbc:mysql://172.17.0.3:3306` 能用就写死。
**其实**：容器每次重建都会重新分配 IP，`172.17.0.3` 明天可能是另一个容器。**永远用容器名/服务名**（自定义网络或 Compose 会提供 DNS），或者用固定 alias。
**怎么验证**：`docker rm -f db && docker run -d --name db ...` 之后 `docker inspect --format '{{.NetworkSettings.Networks.appnet.IPAddress}}' db`，IP 多半变了。
