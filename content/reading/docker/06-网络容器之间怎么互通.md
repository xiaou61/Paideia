## 两条都写着「连不上」，原因不是同一个

应用日志里是这一段：

```text
api  | java.net.ConnectException: Connection refused
api  |   at com.mysql.cj.jdbc.exceptions.SQLError.createCommunicationsException(SQLError.java:174)
api  |   ... jdbc:mysql://127.0.0.1:3306/paideia
```

如果 `api` 镜像里有 `ping`，换到另一个容器里执行 `ping db`，看到的是：

```text
$ docker exec api ping db
ping: bad address 'db'
```

看起来都是「连不上」，但一条卡在 TCP，一条卡在 DNS。

第一条：`127.0.0.1` 在 `api` 容器里指 `api` 自己。它去连自己身上的 3306，那里没有进程监听，内核直接回 RST，于是 `Connection refused`。这个连接从来没到过 `db` 容器。我一开始把两条都归成「网络不通」，先去翻防火墙；其实第一条连防火墙都没到。

第二条：`db` 这个名字没有被解析成 IP，TCP 连接根本没发起。`bad address` 是 Alpine/BusyBox 的 `ping` 的说法；glibc 镜像可能写 `Name or service not known`，意思一样。

分辨方法：

- `Connection refused`：地址有了（不管是 IP 还是解析出来的），TCP 到了某个地址，但那个地址的端口没人监听，或者只监听了别的地址。
- `bad address` / `Name or service not known`：卡在 DNS，连 IP 都还没拿到。

`ping` 本身也不是可靠的判据：ICMP 可能被禁，精简镜像可能没装 `ping`。要确认名字，用 `getent hosts`；要确认端口，用 `ss -lntp` 或 `curl`。

> 本机没装 Docker，下面 `$` 开头的命令和输出是 Docker Engine 默认配置下的标准形态，不是本机回显。容器 IP、宿主端口和容器 ID 会随环境变化。

## `localhost` 是容器自己

Docker 给每个容器一个独立的 network namespace：一张虚拟网卡、一个私有 IP、一张自己的路由表。在默认 bridge 和自定义 bridge 里，`127.0.0.1` 指向这个 namespace 的 loopback，不会指向宿主机。只有 `--network host` 是例外——那时容器用的是宿主的网络命名空间，`localhost` 也跟着变成宿主的 loopback。

（下面假设你有一个叫 `api` 的应用容器；后文会用 `alpine:3` 起一个替身来验证网络。）

```text
$ docker exec api getent hosts localhost
127.0.0.1       localhost
```

`getent hosts localhost` 返回 `127.0.0.1`，这说明不了端口通不通；它只证明这个名字指向 loopback。要看你连的端口有没有人听，得看监听列表：

```text
$ docker run --rm --network container:api --entrypoint ss nicolaka/netshoot -lntp
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 0      128    0.0.0.0:8080        0.0.0.0:*
```

`api` 的监听列表里没有 3306。应用却去连 `127.0.0.1:3306`，当然被拒。这里的 `Connection refused` 不是网络不通，是「地址对了，端口没有服务」。

宿主上 `ss -lntp` 看不到容器内部**未发布**的端口，这也是为什么在宿主上查不到 3306，不代表容器里没有。宿主上能查到的是已经 `-p` 发布出来的宿主端口。

如果 `api` 和 `db` 在同一个自定义网络里，配置应该写 `db:3306`，不是 `localhost:3306`，也不是宿主 IP。

## 默认 bridge 没有名字，自定义网络才有

先看那个起不来的数据库容器为什么会退出：

```text
$ docker run -d --name db postgres:16
$ docker ps -a --filter name=^db$
CONTAINER ID   IMAGE          STATUS                     NAMES
...            postgres:16    Exited (1) 2 seconds ago   db

$ docker logs db
Error: Database is uninitialized and superuser password is not specified.
       You must specify POSTGRES_PASSWORD to a non-empty value for the
       superuser. For example, "-e POSTGRES_PASSWORD=password" on "docker run".
```

`docker run -d` 成功只代表容器被创建并启动过，不代表它还在跑；`-d` 不会把退出码打给你。PostgreSQL 官方镜像在没有 `POSTGRES_PASSWORD`（也没有 `POSTGRES_HOST_AUTH_METHOD=trust`）时会立刻退出。容器已经退出时，`ping db` 也会失败，但那是「容器没在跑」，不是「DNS 不通」。先 `docker ps -a` 看状态，再 `docker logs` 看原因。

补上口令，并把它接进自定义网络：

```text
$ docker network create appnet
$ docker run -d --name db --network appnet -e POSTGRES_PASSWORD=change-me postgres:16
$ docker run -d --name api --network appnet alpine:3 sleep 3600

$ docker ps --filter name=db
CONTAINER ID   IMAGE          STATUS         PORTS     NAMES
...            postgres:16    Up 5 seconds             db
$ docker exec api getent hosts db
172.18.0.2      db
```

这里用 `alpine:3` 当应用容器的替身，只为验证网络；换成你的应用镜像，结论一样。`change-me` 只是本地练手的占位口令，别拿去生产。`172.18.0.2` 是示例；你的网络地址池可能不同。`appnet` 已经存在时，`docker network create` 会报 already exists，直接复用即可。

`getent` 不在镜像里时，用后面的 netshoot 共享网络命名空间来查（见「排障」第 3 步），不要把它当成 DNS 失败。

为什么这样就通了：自定义 bridge 网络里，Docker 跑了一个内置 DNS，容器内看到的地址是 `127.0.0.11`。它把容器名、`--network-alias` 声明的别名解析成容器 IP。重建容器、IP 变了，解析结果跟着更新，配置文件里不需要写 IP。

```text
$ docker exec api cat /etc/resolv.conf
nameserver 127.0.0.11
options ndots:0
```

默认 `bridge` 没有这个内置的容器名 DNS。两个容器都接默认 bridge 时，只能靠 IP 互访；`--link` 是官方标为 legacy 的遗留方案，新部署不要用。

```text
$ docker run -d --name db-default -e POSTGRES_PASSWORD=change-me postgres:16
$ docker run --rm --network bridge alpine:3 ping -c1 db-default
ping: bad address 'db-default'
```

想在自定义网络里加别名：

```text
$ docker run -d --name db2 --network appnet --network-alias database -e POSTGRES_PASSWORD=change-me postgres:16
$ docker exec api getent hosts database
```

怎么验证：`docker network inspect appnet` 看 `Containers` 里有没有两个容器；`getent hosts db` 看名字解析；`cat /etc/resolv.conf` 看是不是 `127.0.0.11`。三条里任何一条不对，先修网络归属；`getent` 本身不存在时按上一条用 netshoot。

## 同网络不需要 `-p`，`-p` 是给外面的

`-p` 做的是「在宿主上监听一个端口，把流量转发到容器端口」。同一自定义网络里的容器互相访问，走的是容器网络，不经过宿主，所以不需要 `-p`。

```text
$ docker run -d --name web --network appnet nginx:1.30
$ docker run --rm --network appnet curlimages/curl -sI http://web:80
HTTP/1.1 200 OK
```

`web` 没写 `-p`，临时 curl 容器仍然能访问 `web:80`。反过来，宿主上 `curl http://127.0.0.1:8080` 不会通，因为 8080 根本没被发布：

```text
$ docker port web
# 没有输出
```

`-p` 的格式第 02 关已经拆过，这里只补默认绑定地址的区别：

| 写法 | 宿主绑定 | 谁能访问 | 用途 |
| --- | --- | --- | --- |
| `-p 8080:80` | `0.0.0.0:8080` | 所有能到达宿主 8080 的来源 | 对外服务；还要公网 IP、安全组、防火墙、NAT 都放行 |
| `-p 127.0.0.1:8080:80` | `127.0.0.1:8080` | 只有宿主本机 | 内部服务、反向代理后端 |
| `-p 0.0.0.0:8080:80` | `0.0.0.0:8080` | 同第一行，只是写明了绑定地址 | 想让人一眼看出绑所有 IPv4 接口 |

第一行在启用 IPv6 的 daemon 上可能同时监听 `[::]`；`-p 0.0.0.0:...` 是明确的 IPv4 全接口。

把上面的 8080 换成 80，就是 `-p 80:80`、`-p 127.0.0.1:80:80`、`-p 0.0.0.0:80:80` 三种写法；区别只在宿主绑定地址，与宿主端口号无关。

第一行默认绑 `0.0.0.0` 是对的，但「绑了 `0.0.0.0`」不等于「公网一定可达」。`-p` 只负责宿主上的监听和转发；云主机的安全组、宿主防火墙、NAT、有没有公网 IP，任何一层没放行，外面都进不来。反过来，只给内网或本机用的服务，仍然应该写 `127.0.0.1:8080:80`，不要因为「反正有防火墙」就默认绑所有接口。

怎么验证公网可达：从另一台机器 `curl -v http://<公网IP>:8080` 或 `nc -vz <公网IP> 8080`；在宿主上 `curl 127.0.0.1:8080` 只能证明本机这一段通。

怎么验证：

```text
$ docker run -d --name web-pub -p 8080:80 nginx:1.30
$ docker port web-pub
80/tcp -> 0.0.0.0:8080

$ docker run -d --name web-local -p 127.0.0.1:8081:80 nginx:1.30
$ docker port web-local
80/tcp -> 127.0.0.1:8081
```

`docker port` 给出的是 Docker 记录的绑定地址。宿主上 `ss -lntp | grep 8080` 可能看到 `docker-proxy`，也可能什么都看不到（daemon 用纯 iptables 转发时没有用户态进程），所以判断映射以 `docker port` 和实际 `curl` 为准。

`EXPOSE` 不是端口映射。Dockerfile 里写：

```dockerfile
FROM nginx:1.30
EXPOSE 80
```

`EXPOSE` 只是告诉读镜像的人「这个镜像打算监听 80」，同时写进镜像元数据；它不会在宿主上开端口。`docker run` 不写 `-p` 时，`docker port` 仍是空的。

```text
$ docker inspect --format '{{json .Config.ExposedPorts}}' web
{"80/tcp":{}}
```

能从元数据里看到 `80/tcp`，但那只是声明。`docker run -P` 会把所有 `EXPOSE` 的端口随机发布到宿主，这是另一个行为，日常别拿它代替明确的 `-p`。

## 容器访问宿主：查网关，别背 `172.17.0.1`

容器要访问宿主上的服务，得用「宿主在这个容器所在网络里的地址」。默认 bridge 在默认地址池下是 `172.17.0.1`；你新建的第一个自定义 bridge 在默认地址池下是 `172.18.0.1`，第二个可能是 `172.19.0.1`。地址池可以配置，所以不要背。

查法有两种：

```text
$ docker network inspect appnet --format '{{(index .IPAM.Config 0).Gateway}}'
172.18.0.1

$ docker exec api ip route | grep default
default via 172.18.0.1 dev eth0
```

精简镜像里可能没有 `ip`，那就用宿主上的 `docker network inspect`。两条命令的结果应该指向同一个地址。

拿到网关地址还不够，宿主上的服务必须监听在这个地址（或 `0.0.0.0`）上：

```text
$ ss -lntp | grep 8080
LISTEN 0 128 127.0.0.1:8080 0.0.0.0:* users:(("java",pid=...))
```

这里只绑了 `127.0.0.1`，容器访问 `http://172.18.0.1:8080` 会 `Connection refused`。把服务改绑到 `172.18.0.1` 或 `0.0.0.0`，容器才能到；绑 `0.0.0.0` 时要用防火墙或安全组限制来源，别把它顺手暴露到公网。绑 `172.18.0.1` 后，宿主本机也要用这个地址访问，不能再写 `127.0.0.1`。

Docker Desktop（Mac/Windows）默认提供 `host.docker.internal`，不用背网关：

```text
$ docker run --rm curlimages/curl -s http://host.docker.internal:8080
```

Linux 上没有这个默认名字，用 `--add-host` 把特殊值 `host-gateway` 映射进去（Docker 20.10+）：

```text
$ docker run --rm --add-host host.docker.internal:host-gateway curlimages/curl \
    -s http://host.docker.internal:8080
$ docker run --rm --add-host host.docker.internal:host-gateway \
    --entrypoint getent nicolaka/netshoot hosts host.docker.internal
```

`host-gateway` 解析出来的仍然是这个网络的网关地址，只是不用你手写。怎么验证：容器里 `getent hosts host.docker.internal` 看名字，宿主上 `ss -lntp` 看服务绑在哪个地址，两边对得上才算通。

## 三种网络模式，`host` 什么时候值得用

Docker 自带三种网络驱动：

| 模式 | 命令 | 网络命名空间 | 容器名解析 | 典型用途 |
| --- | --- | --- | --- | --- |
| **bridge**（默认） | `--network bridge` | 独立 | 没有内置 DNS | 单容器、临时排查 |
| **自定义 bridge** | `--network appnet` | 独立 | 内置 DNS，按容器名/别名 | 多容器协作，默认选它 |
| **host** | `--network host` | 与宿主共用 | 容器名没有意义 | 性能敏感、必须用宿主端口/协议 |
| **none** | `--network none` | 只有 loopback | 没有 | 离线、跑不可信代码 |

`host` 值得用的场景很具体：你要避开 NAT 转发、对吞吐或延迟敏感，或者容器必须直接使用宿主的网络身份（某些协议、广播、原始套接字）。少一层 NAT 不等于你的应用一定更快，瓶颈可能在别处；要拿自己的负载测。代价也很具体：

- 容器不再有独立的网络隔离，能直接看到宿主的所有网卡和 `127.0.0.1` 上的服务；
- 端口冲突变成宿主级冲突，两个容器不能同时监听同一个端口；
- `-p` 在 `host` 模式下没有意义，Docker 会忽略它（可能给一条 warning）；
- 多副本部署没法用，每个副本都要抢同一个端口。

如果痛点是「多个容器想用同一个端口」，`host` 不是解法，反而让冲突更直接；这种场景应该用 bridge + 不同宿主端口，或让上游反向代理分流。

怎么验证：`docker run --rm --network host --entrypoint ip nicolaka/netshoot addr` 看到的是宿主网卡；`ss -lntp` 看到的是宿主全部监听。再起一个同端口的容器，第二个会直接失败。`--network host` 的结论按 Linux Engine 写；Docker Desktop 的 host 网络支持跟版本有关，别直接套。

`none` 更简单：只有 `lo`，没有默认路由。

```text
$ docker run --rm --network none --entrypoint ip nicolaka/netshoot addr
1: lo: <LOOPBACK,UP,LOWER_UP> ...
$ docker run --rm --network none --entrypoint ping nicolaka/netshoot -c1 1.1.1.1
# 预期：Network is unreachable
```

预期就是「只有 lo，对外请求失败」。跑不可信代码时，这是把出网口关掉，而不是靠应用层自觉。注意它只关网络，不是完整沙箱；文件系统、权限和资源限制还要另外做（第 17 关）。

## 排障：先看容器活没活，再看在不在一个网

按这个顺序，别一上来就查防火墙：

1. **容器还在跑吗？**

```text
$ docker ps -a --filter name=^db$
$ docker inspect --format '{{.State.Status}} {{.State.ExitCode}}' db
```

`Exited` 就先看 `docker logs db`。容器退出时 `ping`、`getent`、`curl` 都会失败，但根因不在网络。

2. **两个容器在同一个网络里吗？**

```text
$ docker network inspect appnet
```

看 `Containers` 段里有没有 `db` 和 `api`。少一个，就用 `--network appnet` 重建，或者对运行中的容器执行 `docker network connect appnet db`。`docker network connect` 只加网络，不会改端口和启动参数。

3. **名字能解析吗？**

```text
$ docker exec api getent hosts db
$ docker exec api cat /etc/resolv.conf
```

解析失败、`resolv.conf` 里又没有 `127.0.0.11`，说明 `api` 不在自定义网络里，或者用了 `--network none`/`host`。`getent` 不存在时，别往业务镜像里装包；用 `docker run --rm --network container:api --entrypoint getent nicolaka/netshoot hosts db`，在共享网络命名空间的临时容器里查。

4. **端口在监听吗，监听在哪个地址？**

```text
$ docker run --rm --network container:db --entrypoint ss nicolaka/netshoot -lntp
$ docker run --rm --network container:api --entrypoint ss nicolaka/netshoot -lntp
```

`db` 里如果看到 `127.0.0.1:5432`，别的容器连不进来——它只监听了容器自己的 loopback。这种情况加 `-p` 也救不了，因为转发目标不是容器的 loopback。要让同网络容器访问，服务得监听 `0.0.0.0:5432` 或 `[::]:5432`。这是「容器内监听地址」的问题，不是 `-p` 的问题。

`ss`/`netstat` 在精简镜像里可能没有。这时候用共享网络命名空间的办法，不要为了排障往生产镜像里塞工具：

```text
$ docker run --rm -it --network container:api nicolaka/netshoot
# 在这个容器里：
$ ss -lntp
$ curl -sI http://localhost:8080
$ getent hosts db
```

`--network container:api` 让临时容器复用 `api` 的网络命名空间，所以这里的 `localhost`、`ss`、`curl` 看到的都是 `api` 的网络。目标容器必须在运行；这个模式也不能再配 `-p`。

## 还差的

- 没讲 Docker Compose 的服务名解析：Compose 默认会建 `<项目名>_default` 网络，服务名就是网络别名；本篇只覆盖 `docker run`。
- 没覆盖 IPv6 和双栈端口绑定：`-p` 在启用 IPv6 的 daemon 上是否同时监听 `[::]`，取决于 `ip6tables`/`ipv6` 配置。
- 没覆盖跨主机网络：Swarm overlay、Kubernetes CNI 的 DNS 和网关是另一套，不能拿本篇的单机 bridge 结论直接套。
- 没验证 rootless Docker、Podman 的网关地址和 DNS 行为；它们的网络实现与 rootful Docker Engine 不完全一样。
- 没在真机上跑过：本篇所有 `$` 回显都是标准形态，不是实测；不同 Docker 版本的报错措辞、`ss` 是否存在会有差异。
