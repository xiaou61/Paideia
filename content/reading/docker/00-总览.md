## 这条线写给谁

写给**听说过 Docker、会 `docker run` 一条命令、但说不清自己在跑什么**的人。

也写给**在服务器上被"容器里没有 vim""数据怎么没了""端口映射了还是连不上"折磨过**的人：这些都有确定的答案，不需要试。

## 为什么值得学

因为"在我机器上能跑"这个问题的根源是**环境不固定**。Docker 把"运行环境"变成一个有版本号、能复制、能回滚的产物（镜像）。同一份镜像在谁的机器上、在测试环境、在生产环境跑出来是一样的，除非你显式给了不同的参数。

对后端工程师还有一层直接好处：本地想同时跑 MySQL 5.7 和 8.0 对比一个行为，不用装两遍数据库，起两个容器就行，用完删掉，宿主干干净净。

## 一个前提

需要一台能跑 Docker 的机器：

```text
$ docker version
Client: Version 27.x ...
Server: Version 27.x ...
```

能看到 `Server:` 段就说明 Docker 守护进程在跑。看不到 Server 段，或者报 `permission denied while trying to connect to the Docker daemon socket`，是"没装好"或"当前用户不在 docker 组"——后者见 12 关的安全讨论，**不要用 `sudo` 糊过去就该反思**。

本机不方便装的话，也可以先用一台云服务器。**不要在生产机上练 `docker system prune -a`**——它删掉的东西不可恢复。

## 常见误区

### 误区：Docker 就是"轻量虚拟机"

**你以为**：容器是更小更快的虚拟机。
**其实**：虚拟机里有完整的内核，靠硬件虚拟化隔离；容器**共享宿主的同一个内核**，用一个进程的 namespace 与 cgroup 做出"看起来独立"的效果。所以容器里 `uname -a` 看到的是宿主的内核版本，容器里也起不了自己的内核模块。
**怎么验证**：宿主和容器里各跑 `uname -r`——完全一样；再 `cat /proc/1/cgroup` 观察容器进程被放在哪个 cgroup 里。

### 误区：容器"启动了"就等于服务正常

**你以为**：`docker ps` 里 `Up 3 seconds` 就是好了。
**其实**：`Up` 只说明容器里的主进程还在跑。一个 Java 服务可以在"正在启动、还没监听端口"的状态下保持 `Up` 两分钟，也可以启动失败后因为主进程是 shell 而依然活着。真正的判据是**端口能连上、健康检查通过**。
**怎么验证**：`docker ps` 的 `STATUS` 列如果显示 `(healthy)` 才算是应用层通过（需要在 Dockerfile 里定义 `HEALTHCHECK`）；否则自己 `docker exec ... curl 127.0.0.1:端口`。

### 误区：容器里的东西改了就生效了，下次还在

**你以为**：`docker exec` 进去改了配置文件，就跟改服务器一样。
**其实**：容器的可写层是**临时的**——容器一删，改动全没；容器重建（`docker compose up` 更新镜像时）也会回到镜像的原始状态。正确的改法是**改 Dockerfile 或挂载配置文件**，让它变成镜像/卷的一部分（第 05 关）。
**怎么验证**：`docker exec -it 容器 sh -c 'echo x >> /app/config.yml'`，然后 `docker restart` 容器——**重启还在**（可写层没丢）；但 `docker rm` 之后在同一个镜像上重新 `run`，改动就没了。如果重启也没了，说明这个路径是被挂载进去的（`docker inspect` 的 `Mounts` 里能看到）。
