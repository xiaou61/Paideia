## 容器退出后，/data 里的 x 还在不在

同一个 `-v /data`，加不加 `--rm`、删不删容器，结果不一样：

```text
$ docker run --rm -v /data alpine touch /data/x
$ docker volume ls -q
（没有多出这一次的卷）

$ docker run --name keep -v /data alpine touch /data/x
$ docker volume ls -q
<hash>

$ docker rm keep
$ docker volume ls -q
<hash>
```

（本机没装 Docker，`<hash>` 和「没有多出」是按卷生命周期写的标准形态；`docker volume ls` 的真实输出取决于你机器上已有的卷，我没有跑。）

第一组里 `--rm` 把容器和它创建的**匿名卷**一起删了；第二组只删容器，匿名卷还在，但名字是一串哈希，你已经不知道它原来属于谁。能跨重建复用的是**命名卷**；匿名卷只是「容器走了、卷留下」的残留物。

验证：跑完第一组 `docker volume ls -q` 看数量有没有增加；第二组在 `docker rm` 之前 `docker inspect keep --format '{{json .Mounts}}'` 看 `Type` 和 `Name`，`docker rm` 之后再 `docker volume ls -q` 看那一只还在。

## 匿名卷和命名卷，先分清

| 操作 | 匿名卷 | 命名卷 |
| --- | --- | --- |
| `docker rm 容器` | 保留，变成哈希孤儿 | 保留 |
| `docker rm -v 容器` | 删除 | 保留 |
| `docker run --rm` | 删除 | 保留 |
| `docker volume rm 名字` | 可以删 | 可以删 |

「卷不会被容器生命周期带走」只对命名卷是可用承诺。匿名卷在 `docker rm` 时也默认留下，但它没有稳定的名字，清理时只能靠 `docker volume ls -f dangling=true` 去猜。`docker rm -v` 和 `docker run --rm` 删的都是匿名卷，不会碰命名卷。

验证：`docker inspect 容器 --format '{{json .Mounts}}'`，`Type` 是 `volume` 时看 `Name`：有名字的是命名卷，一串哈希的是匿名卷；`docker volume inspect <名字>` 的 `Mountpoint` 是它在宿主的真实路径。

## 三种存储，先看写到哪

| 类型 | 写在哪 | 生命周期 | 典型用途 |
| --- | --- | --- | --- |
| **可写层** | 容器根文件系统的 upperdir（overlay2/overlayfs） | 跟容器同生共死 | 临时文件、进程 pid |
| **命名卷** | `/var/lib/docker/volumes/<名字>/_data` | 独立于容器，`docker rm` 不影响 | 数据库数据、上传文件 |
| **绑定挂载** | 宿主的任意目录 | 宿主目录在，数据就在 | 配置文件、开发时代码热更新 |

可写层属于容器本身：`docker rm` 删掉它；用同一个镜像重新 `docker run` 得到的是镜像原始状态。它也不适合放数据库和日志：在 overlay2/overlayfs 下，修改已有文件要先把它 copy-up 到上层；数据库和日志改的正是已有的大文件，第一次写就要付这个复制成本。

验证：`docker diff 容器` 看可写层改了什么；它不会列出命名卷或绑定挂载里的内容。再用 `docker inspect 容器 --format '{{json .Mounts}}'` 看哪些路径是挂载。

## 命名卷：Docker 管的存储

```text
$ docker volume create pgdata
$ docker run -d --name pg -e POSTGRES_PASSWORD=x \
    -v pgdata:/var/lib/postgresql/data postgres:16
$ docker volume inspect pgdata --format '{{.Mountpoint}}'
$ docker inspect pg --format '{{json .Mounts}}'
```

`-v 卷名:容器内路径`。卷第一次使用时会自动创建，`docker volume create` 不是必须的；多个容器可以同时挂同一个命名卷，但数据库这种应用要自己保证不打架。

卷的内容在宿主 `/var/lib/docker/volumes/pgdata/_data`，但不建议直接进去改——用容器访问它，权限和属主才是对的。

验证：`docker volume inspect pgdata` 看 `Mountpoint`；`docker inspect pg --format '{{json .Mounts}}'` 看 `Type` 是 `volume`、`Name` 是 `pgdata`、`Destination` 是 `/var/lib/postgresql/data`。

删卷要 `docker volume rm pgdata`，或 `docker system prune --volumes` / `docker volume prune`。后者会删所有没被容器使用的卷，包括有名字的卷；执行前先用 `docker volume ls` 和 `docker system df -v` 的 `Local Volumes` 看清楚。

## 绑定挂载：直接映射宿主目录

```text
$ docker run -d -v /etc/paideia:/etc/paideia:ro myapp:v1
$ docker run -d -v "$(pwd)":/app -w /app node:20 npm run dev
```

`-v 宿主绝对路径:容器内路径:选项`。常用的选项是 `ro`（只读）。

和卷的关键差别：

- **宿主路径必须自己管**：备份、权限、磁盘空间都是你的责任。
- **`-v` 路径不存在时会静默建目录**：`-v /a/b:/x` 在宿主上创建一个空目录再挂进去；`--mount` 会检查 `source`，路径不存在直接报错。打错路径却静默成功，比报错难发现。
- **跨机器部署时不好用**：绑定挂载要求每台宿主机都有同一个目录和同样的权限；Swarm/K8s 里能写 hostPath/bind，但调度到别的节点就对不上。跨机器用卷或对象存储更稳。

`--mount` 的写法更啰嗦但更明确：

```text
$ docker run -d \
    --mount type=bind,source=/etc/paideia,target=/etc/paideia,readonly \
    --mount type=volume,source=pgdata,target=/var/lib/postgresql/data \
    postgres:16
```

验证：`docker inspect 容器 --format '{{json .Mounts}}'` 看 `Type` 是 `bind` 还是 `volume`；把 `source` 改成一个不存在的路径，`--mount` 应该直接报错，`-v` 则会建一个空目录。

### SELinux：`:z` 和 `:Z`

在 Fedora / RHEL / CentOS 这类 SELinux enforcing 的宿主上，宿主目录默认带 `user_home_t` 之类的标签，容器进程是 `container_t`，直接挂进去会被拒绝，表现是 `Permission denied`，不是普通的 Unix 权限问题。

| 写法 | SELinux 标签 | 宿主路径不存在时 |
| --- | --- | --- |
| `-v /srv/app:/app:ro` | 不改标签；enforcing 下会被拒（除非策略额外放行） | 静默建目录 |
| `-v /srv/app:/app:ro,z` | 共享标签，多个容器可读 | 静默建目录 |
| `-v /srv/app:/app:ro,Z` | 独占标签，只给这个容器 | 静默建目录 |
| `--mount type=bind,source=/srv/app,target=/app,readonly` | **不支持 `z`/`Z`** | 报错 |

`:z` 是共享（多个容器都要挂时用），`:Z` 是独占（只给一个容器，别让别的容器再挂同一目录）。`--mount` 语法没有 `z`/`Z` 选项；需要 SELinux 重打标签时，用 `-v ...:z`，或者先手动 `chcon`。`--security-opt label=disable` 能绕过，但等于关掉这层隔离，不建议当默认。

验证：在 SELinux 宿主机上 `ls -Z /srv/app` 看标签；不加 `:z` 跑容器，看是不是 `Permission denied`；加上 `:z` 再 `ls -Z`，标签应该变成容器可读的那一类（较新的 container-selinux 上是 `container_file_t`）。没有 SELinux 的机器（Ubuntu、Windows、macOS）复现不了这个失败。

### 挂文件比挂目录脆

`-v "$(pwd)/config.yml:/etc/app/config.yml"` 看起来最精确，但有两个坑（Compose 里可以写相对路径 `./config.yml`）：

- 宿主上这个文件必须先存在；不存在时 `-v` 会创建一个**同名目录**，容器里读到的就是目录，报 `Is a directory`。
- 编辑器「保存时替换文件」（写临时文件再重命名）会换掉 inode，容器里的挂载点还指着旧文件，改了不生效。

稳妥做法是挂目录，而不是单个文件；一定要挂文件，就用 `--mount`（至少路径不存在会报错），改完重启容器，或者接受「编辑后要重新挂载」。

验证：`docker exec 容器 cat /etc/app/config.yml`，报 `Is a directory` 就是挂成了目录；在宿主保存一次后 `docker exec 容器 stat /etc/app/config.yml` 看 inode/时间有没有变。

## 权限：用数字 uid 比对

容器里的进程以某个 uid 运行，挂载进去的文件在宿主上有另一个属主。两边**用数字 uid 比对**，不是名字：

```text
$ id
uid=1000(lzf) gid=1000(lzf)

$ ls -n
drwxr-xr-x 2 1000 1000 4096 ... data

$ docker run --rm -v "$(pwd)":/app alpine id
uid=0(root) gid=0(root)
```

如果容器里进程是 uid 101（比如官方 Nginx 镜像的 worker），而宿主目录属于 1000、权限是常见的 755，写就会失败。要复现，得让命令真的以非 root 跑。下面是在 Linux 宿主上的命令：

```text
$ docker run --rm --user 101:101 -v "$(pwd)":/app nginx touch /app/x
touch: cannot touch '/app/x': Permission denied
```

这里要注意：nginx 官方镜像默认的 master 是 root，worker 才是 uid 101；`docker run --rm -v "$(pwd)":/app nginx touch /app/x` 里的 `touch` 走的是容器默认用户 root，所以**会成功**（只要宿主目录对 root 可写）。拿默认 nginx 演示「非 root 写不进去」，现象站不住。

三种解法，按推荐度排：

1. **让容器以你的 uid 运行**：`docker run --user "$(id -u):$(id -g)" ...`（开发环境最省事）。
2. **调整宿主目录权限**：`chown -R 100:100 ./data`（要知道容器用户的 uid）。
3. **让镜像里的用户与宿主 uid 一致**：Dockerfile 里 `RUN useradd -u 1000 app`（构建期确定，最干净）。

不要用 `chmod 777` 解决——它把权限问题变成了安全问题（Linux 线第 04 关）。

验证：容器里 `id` 看 uid/gid；宿主 `ls -n` 看属主数字；两边对上，才有写权限。

## `VOLUME` 的构建期陷阱

`VOLUME /data` 不只是「运行时创建一个匿名卷」。它还会影响构建：

```dockerfile
# 不推荐：初始化写在 VOLUME 之后
FROM alpine:3.20
VOLUME /data
RUN printf 'seed\n' > /data/seed.txt
```

老 builder（`DOCKER_BUILDKIT=0`，如果你那版还支持）会**丢弃** `VOLUME` 之后 `RUN` 写进该目录的内容；BuildKit 会保留，但运行时只要挂的是一个已经有数据的卷，镜像里的 `/data` 还是会被旧卷遮住。

所以需要预置数据的初始化，必须放在 `VOLUME` **之前**：

```dockerfile
FROM alpine:3.20
RUN mkdir -p /data && printf 'seed\n' > /data/seed.txt
VOLUME /data
```

验证：用老 builder 构建后 `docker run --rm 镜像 cat /data/seed.txt`，文件不在；用 BuildKit 构建，第一次 `docker run --rm` 能看到 `seed`。再建一个已有数据的命名卷挂到 `/data`，`cat /data/seed.txt` 又看不到了——旧卷遮蔽了镜像内容。

本仓库的 MySQL 沙箱镜像就是按这个思路绕的：`backend/paideia-sandbox/images/mysql/Dockerfile` 把预初始化的 datadir 放在 `/opt/datadir-base`，而不是官方镜像常用的 `/var/lib/mysql`；注释写的是「后者在容器里常被覆盖成卷，容易误挂」。`mysql:8.0` 官方镜像声明了 `VOLUME /var/lib/mysql`，你 `RUN` 写进去，运行时也会被卷盖住。

## `tmpfs`：到上限是 ENOSPC，不是 OOM

```text
$ docker run --rm --tmpfs /tmp:size=8m alpine \
    sh -c 'dd if=/dev/zero of=/tmp/x bs=1M count=16'
dd: error writing '/tmp/x': No space left on device
```

（本机没装 Docker，这段是标准形态，没有实跑。）

`size=8m` 是硬上限，写到 8MB 左右返回 `ENOSPC`（`No space left on device`），不是 OOM。只有 cgroup 内存上限先到（比如 `--memory` 比 `size` 小，或进程其他内存已经占满额度），才可能被 OOM Killer 杀掉：

```text
$ docker run --name oom --memory=16m --tmpfs /tmp:size=64m alpine \
    sh -c 'dd if=/dev/zero of=/tmp/x bs=1M count=64'
Killed
$ docker inspect oom --format '{{.State.OOMKilled}}'
true
```

两个上限要一起设：tmpfs 里写进去的页也计入容器内存。不写 `size` 时，Docker 文档给的默认上限是宿主总内存的 50%；不写 `--memory` 时默认没有容器级内存上限。`/dev/shm` 是另一个默认 64MB 的 tmpfs，不受 `--tmpfs /tmp` 影响。

验证：`docker run --rm --tmpfs /tmp alpine df -h /tmp` 看 `Size`；`docker inspect 容器 --format '{{json .HostConfig.Tmpfs}}'` 看配置；`docker inspect 容器 --format '{{.State.OOMKilled}}'` 看是不是真的 OOM。

## 备份一个卷

卷不在宿主的普通路径下，备份要绕一下：起一个临时容器，把卷和目标目录都挂进去。

```text
$ docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
    tar -czf /backup/pgdata-$(date +%F).tar.gz -C /data .
```

恢复就是把方向反过来（`tar -xzf`），最好在一个空卷上演练一次。只看 tar 包大小不算，要能列出来、解出来、再让应用读一次。

验证：`tar -tzf pgdata-<日期>.tar.gz | head` 看文件列表；恢复到一个新卷后 `docker run --rm -v 新卷:/data alpine ls -la /data` 对比。

## 生产用卷，开发用 bind

绑定挂载把「宿主机目录结构」变成部署契约的一部分：迁移、扩缩容、多机部署都被绑死，目录权限、磁盘满、误删也都是你的责任。生产用命名卷，开发用绑定挂载（热更新方便），是更稳的默认。

验证：`docker inspect 容器 --format '{{json .Mounts}}'` 看 `Type`；`docker volume inspect 卷名` 看 `Mountpoint`——卷也有宿主路径，只是由 Docker 管理，不随项目目录变化。

## 跑一遍：看两个字段

```text
$ docker run --rm -v /data alpine touch /data/x
$ docker volume ls -q
$ docker run --name keep -v /data alpine touch /data/x
$ docker inspect keep --format '{{json .Mounts}}'
$ docker rm -v keep
$ docker volume ls -q
```

第一遍看 `docker volume ls -q` 有没有多出卷；第二遍看 `.Mounts` 里的 `Name` 是不是哈希；`docker rm -v` 之后再 `ls`，这一只匿名卷应该消失。命名卷重复同样的步骤，`docker rm -v` 后它还在。

## 还差的

- 本机没装 Docker，所有 `docker run`/`docker volume` 回显都是标准形态；`<hash>` 没有真实值，`docker volume ls` 的数量取决于你机器上已有的卷。
- SELinux 的 `:z`/`:Z` 没有实跑；这台机器不是 SELinux enforcing 宿主，复现需要 Fedora/RHEL/CentOS。
- `tmpfs` 默认 50% 内存、到 `size` 报 `ENOSPC`、先撞 `--memory` 才 OOM，这三条按 Docker 文档写，没有在本机量过。
- `VOLUME` 在老 builder 与 BuildKit 下的差异没有实跑；新版 Docker 可能已经不支持 `DOCKER_BUILDKIT=0`。
- 没有验证 rootless / userns-remap 下的 uid 映射；启用后宿主看到的属主会变，卷里已有文件的权限也可能要重新处理。
