## 这一关在解决什么

"容器一删，数据库就空了""改了容器里的配置，重建之后又变回去""`/data` 目录在宿主机上找不到"——这一关讲清楚容器的**三种存储**，以及数据该放哪一种。

一句话结论：**容器的可写层只适合放"重建就重建"的东西；要留下的数据必须放进卷或绑定挂载。**

## 为什么可写层靠不住

因为可写层属于容器本身（第 01 关）：容器删了它就没；`docker compose up` 用新镜像重建容器时，新容器拿到的是**镜像原始状态**，不是你上次改过的状态。

更隐蔽的是**性能**：可写层走 overlay2，写大文件比宿主原生文件系统慢。数据库、日志、上传文件都不该放这里。

## 讲解

### 三种存储

| 类型 | 写在哪 | 生命周期 | 典型用途 |
| --- | --- | --- | --- |
| **可写层** | `/var/lib/docker/overlay2/…` | 跟容器同生共死 | 临时文件、进程 pid |
| **命名卷**（named volume） | `/var/lib/docker/volumes/<名字>/_data` | **独立于容器**，`docker rm` 不影响 | 数据库数据、上传文件 |
| **绑定挂载**（bind mount） | 宿主的任意目录 | 宿主目录在，数据就在 | 配置文件、开发时代码热更新 |
| **tmpfs** | 内存 | 容器停止即丢 | 缓存、临时敏感数据 |

### 命名卷：Docker 管理的存储

```text
$ docker volume create pgdata
$ docker run -d --name pg -e POSTGRES_PASSWORD=x -v pgdata:/var/lib/postgresql/data postgres:16
$ docker volume ls
$ docker volume inspect pgdata
```

`-v 卷名:容器内路径`。卷的内容在宿主 `/var/lib/docker/volumes/pgdata/_data`，但**不建议直接进去改**——用容器去访问它。

卷的三个特征：

- **第一次使用时会自动创建**，不用先 `docker volume create`。
- **被多个容器同时挂载是允许的**（但应用层要自己保证不打架，数据库不能这么干）。
- **`docker rm` 容器不会删卷**；删卷要 `docker volume rm pgdata`，或 `docker system prune --volumes`（后者会删所有没被使用的卷，**慎用**）。

### 绑定挂载：直接映射宿主目录

```text
$ docker run -d -v /etc/paideia:/etc/paideia:ro myapp:v1
$ docker run -d -v "$(pwd)":/app -w /app node:20 npm run dev
```

`-v 宿主绝对路径:容器内路径:选项`。选项常用 `ro`（只读）。

和卷的关键差别：

- **宿主路径必须自己管**：备份、权限、磁盘空间都是你的责任。
- **路径不存在时**：`-v /a/b:/x` 会**自动创建一个空目录**并挂上去（旧行为）；用 `--mount` 语法时则要求路径必须存在，否则报错。后者更安全，因为"打错路径却静默成功"是很难发现的事故。
- **只适合宿主与容器同机**：跨机器的部署（比如 Swarm/K8s）用不了绑定挂载，只能用卷或对象存储。

`--mount` 的写法更啰嗦但更明确：

```text
$ docker run -d \
    --mount type=bind,source=/etc/paideia,target=/etc/paideia,readonly \
    --mount type=volume,source=pgdata,target=/var/lib/postgresql/data \
    postgres:16
```

日常用 `-v` 够；脚本里、生产配置里建议 `--mount`，因为路径拼错会立刻报错。

### `tmpfs`：放内存里

```text
$ docker run --tmpfs /tmp:size=64m,exec nginx
```

适合"写得多、但不重要、不该落盘"的数据（缓存、编译中间产物）。注意它**占的是容器的内存额度**——写满会触发 OOM，额度要和 `--memory` 一起算（第 09 关）。

### 权限：最常见的一类"Permission denied"

容器里的进程以某个 uid 运行，挂载进去的文件在宿主上有另一个属主。两边**用数字 uid 比对**，不是名字：

```text
$ id
uid=1000(lzf) gid=1000(lzf)

$ docker run --rm -v "$(pwd)":/app alpine ls -ln /app
-rw-r--r--  1 1000  1000  ...
```

如果容器里进程是 uid 100（比如官方 Nginx 镜像），而宿主目录属于 1000，写就会失败：

```text
$ docker run --rm -v "$(pwd)":/app nginx touch /app/x
touch: cannot touch '/app/x': Permission denied
```

三种解法，按推荐度排：

1. **让容器以你的 uid 运行**：`docker run --user "$(id -u):$(id -g)" ...`（开发环境最省事）。
2. **调整宿主目录权限**：`chown -R 100:100 ./data`（要知道容器用户的 uid）。
3. **让镜像里的用户与宿主 uid 一致**：Dockerfile 里 `RUN useradd -u 1000 app`（构建期确定，最干净）。

**不要用 `chmod 777` 解决**——它把权限问题变成了安全问题（Linux 线第 04 关）。

### 备份一个卷

卷不在宿主的普通路径下，备份要绕一下：起一个临时容器，把卷和目标目录都挂进去。

```text
$ docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine \
    tar -czf /backup/pgdata-$(date +%F).tar.gz -C /data .
```

恢复就是把方向反过来（`tar -xzf`）。这一步要**真演练一次**，只看文件大小不算（Linux 线第 19 关）。

### 匿名卷与它的坑

镜像里写了 `VOLUME /var/lib/mysql` 时，`docker run` 会自动创建一个**匿名卷**（名字是哈希）。它的问题是：

- `docker rm` 容器**不删卷**，于是每次 run 都留一个孤儿卷；
- 孤儿卷很难判断该不该删（名字是哈希，看不出属于谁）。

```text
$ docker volume ls -f dangling=true      # 列出所有孤儿卷
$ docker volume prune                    # 删掉它们
```

`docker system df -v` 里 `Local Volumes` 那一行经常是磁盘被吃掉的真凶之一。

## 常见误区

### 误区：数据放在容器里，只要不删容器就行

**你以为**：不删就没事，出事再说。
**其实**：`docker compose up -d` 在镜像变了时会**重建**容器（不是重启），可写层直接丢弃；`docker system prune` 会删掉所有停止的容器。这两件事都是日常操作，不是意外。判断标准只有一个：**这份数据能不能接受丢**——不能就必须挂卷。
**怎么验证**：`docker inspect 容器 --format '{{json .Mounts}}'`，输出为空说明所有数据都在可写层里，随时会丢。

### 误区：绑定挂载比卷更方便，生产也用绑定挂载

**你以为**：路径看得见、改起来直观，生产也这么干。
**其实**：绑定挂载把"宿主机目录结构"变成了部署契约的一部分，迁移、扩缩容、多机部署全被绑死；而且目录权限、磁盘满、误删都是你的责任。**生产用卷，开发用绑定挂载**（热更新方便）是更稳的默认。
**怎么验证**：`docker volume inspect 卷名` 看 `Mountpoint`——卷其实也有宿主路径，只是由 Docker 管理、不会随项目目录结构变化。

### 误区：`-v ./config:/etc/app/config.yml` 挂一个文件很稳

**你以为**：单文件挂载最精确。
**其实**：宿主上**这个文件必须先存在**，否则 Docker 会创建一个**同名目录**并挂上去，容器里读到的是一堆奇怪的东西（`Is a directory`）。编辑器的"保存时替换文件"（写临时文件再重命名）还会让容器里的挂载点指向旧 inode，改了不生效。
**怎么验证**：`docker exec 容器 cat /etc/app/config.yml` 报 `Is a directory`，或者改了宿主的文件容器里看不到——都是这个原因。稳妥做法是挂**目录**，而不是单个文件。
