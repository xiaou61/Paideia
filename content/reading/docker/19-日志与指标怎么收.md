## 30G 的 /var/lib/docker 和 3.7G 的 json.log

一台 40G 盘的机器，一周里 `/var/lib/docker` 涨到 30G。几条命令把范围缩到一个文件：

```text
$ df -h /var/lib/docker
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        40G   30G  8.0G  79% /

$ docker info --format '{{.LoggingDriver}}'
json-file

$ docker inspect --format '{{.LogPath}}' app
/var/lib/docker/containers/7d6ac83a89a0.../7d6ac83a89a0...-json.log

$ ls -lh /var/lib/docker/containers/7d6ac83a89a0.../*-json.log
-rw-r----- 1 root root 3.7G Nov 19 09:11 7d6ac83a89a0...-json.log
```

（这是一台 40G 盘机器上的现场值。这台开发机没装 Docker，下面的命令我按官方文档的标准形态写，没有在本机实跑。）

我第一反应是应用把日志写进了可写层，删容器就能回收。这个判断只对了一半：删容器确实会删掉可写层和这个 json.log，但 3.7G 不在可写层里——它在宿主上的 `/var/lib/docker/containers/...`，由日志驱动写。更关键的是，镜像层一点没变。

## 镜像层只读，写日志撑大的是可写层

镜像层是只读的。容器启动后，任何写入都落在容器自己的可写层（storage driver 的 upperdir）；`docker diff` 能看到哪些文件被改，`docker ps -s` 的 `SIZE` 是可写层的大小。删容器，可写层一起删；镜像层不变。

日志这里还有第三种落盘位置：`json-file` 驱动把 stdout/stderr 写到宿主上的 `*-json.log`，既不是镜像层，也不是容器可写层。它的大小不出现在 `docker ps -s` 里；要算它，直接 `ls -lh` 那个路径，或者 `du -sh /var/lib/docker/containers`。

## 默认的 json-file 没有上限

Docker 默认日志驱动是 `json-file`，默认不轮转、没有 `max-size`。官方文档的口径是默认没有 log rotation；一个打日志很欢的服务能把宿主盘写满。

```text
$ docker inspect --format '{{json .HostConfig.LogConfig}}' app
{"Type":"json-file","Config":{"max-file":"3","max-size":"50m"}}
```

`Config` 为空（`{}` 或 `null`）就是没设上限；上面是设了 50MB × 3 的样子。`max-file` 是文件总数，包含当前文件，所以 50m × 3 的上限约 150MB。

## 先看驱动，再看 LogPath

`docker inspect --format '{{.LogPath}}'` 在 `json-file` 驱动下有值；`local`、`journald`、`syslog`、`gelf`、`fluentd` 这些驱动下可能是空字符串；空字符串交给 `xargs`，GNU `xargs` 默认会跑一次不带参数的 `ls -lh`，列出当前目录，看起来像「日志目录里就这些」，其实是假象。要它不跑，GNU 用 `xargs -r`，但别依赖这个可移植性。

正确的顺序是先看驱动：

```text
$ driver=$(docker info --format '{{.LoggingDriver}}')
$ path=$(docker inspect --format '{{.LogPath}}' app 2>/dev/null)
$ echo "driver=$driver path=$path"
driver=json-file path=/var/lib/docker/containers/.../...-json.log
```

如果 `path` 为空，就别 `ls` 它；用 `docker logs` 或去对应驱动的目的地找。`local` 驱动没有 `LogPath`，但 `docker logs` 仍然能读它自己的本地文件。

## 限制大小：单容器、Compose、daemon.json

单容器：

```text
$ docker run -d --log-opt max-size=50m --log-opt max-file=3 --name app demo
```

Compose：

```yaml
services:
  app:
    image: demo
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

daemon 级默认：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

`max-size` 是单个文件的上限，`max-file` 是保留的文件总数。`json-file` 的写入是按行追加，轮转发生在写入过程中，所以正在写的文件可能略超 `max-size`，上限是「约」不是「精确」。

## 改了 daemon.json，已有容器不会自动变

`/etc/docker/daemon.json` 里的 `log-driver`/`log-opts` 是 daemon 的默认值，只对之后新建的容器生效。已经存在的容器保留它创建时的 `HostConfig.LogConfig`；`docker update` 也改不了日志配置，只能删掉重建。

重启 daemon 也要挑时间：`systemctl restart docker` 默认会停掉正在跑的容器，只有带 `always`/`unless-stopped` 这类重启策略的会回来；`on-failure` 还要看退出码。开了 `live-restore` 才可能让容器在 daemon 重启期间继续跑。`live-restore` 也有边界：它不支持 Swarm 模式，rootless 也不支持；daemon 升级或配置不兼容时仍然可能失效。

## 换了驱动，docker logs 还能看吗

分三种情况：

- `json-file`、`local`、`journald`：`docker logs` 直接支持。`local` 的官方默认是 20MB × 5 个文件（共 100MB），压缩开启；`docker logs` 读的就是这份本地文件。
- `syslog`、`gelf`、`fluentd`、`awslogs`、`splunk` 等不支持读取的驱动：Docker 20.10 起默认启用 dual logging，在本地留一份缓存（官方默认 5 个文件 × 20MB），所以 `docker logs` 还能看到最近的日志。权威副本在远端；本地缓存是环形的，量大了会丢旧行，也可能滞后。
- `none`：没有日志，`docker logs` 没有输出。

所以「换了驱动，日志根本不落本地」在 20.10+ 不成立；准确说法是「本地只剩一份有上限的缓存，`docker logs` 不再是全量」。要关掉这份缓存，可以在 `--log-opt` 里加 `cache-disabled=true`（Compose 里是 `options: cache-disabled: "true"`），但关掉之后 `docker logs` 对不支持读取的驱动就直接报错。

本仓库的 ops 链路是 journald → Alloy → Loki：`deploy/ops/alloy-config.alloy` 只采白名单 unit 的 journald，`deploy/ops/loki-config.yaml` 保留 720h。应用是 systemd 单元，日志直接进 journald，不经过 Docker。这个链路说明「权威副本在采集端」：`journalctl`/Loki 是查询入口，保留期由 journald/Loki 决定；`docker logs` 只是本地缓存。如果容器改用 `--log-driver=journald`，日志会进 journald；但本仓库的 Alloy 白名单按 `_SYSTEMD_UNIT` 过滤，容器日志的 unit 标签跟 `paideia.service` 不是一回事，要接进 Loki 得先改 `alloy-config.alloy` 的 relabel 规则。留在 `json-file`，Alloy 不会去读 `/var/lib/docker/containers`。

## docker stats 只是当下

`docker stats --no-stream` 的真实表头是：

```text
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O         BLOCK I/O       PIDS
7d6ac83a89a0   app    3.21%   412MiB / 1GiB       40.23%  12.1MB / 8.2MB  120MB / 64MB    37
```

`docker stats` 的表头容易被记少两列：`CONTAINER ID` 和 `PIDS`。`PIDS` 是当前进程/线程数，排查 fork 炸弹和线程泄漏时有用；`MEM USAGE / LIMIT` 的 `LIMIT` 有 `--memory` 时是 cgroup 上限，没设时显示宿主内存。

`docker stats` 是即时快照，不是历史。要看「内存一直在涨」，得把 `docker stats --no-stream --format` 定期抓走，或者上 cAdvisor → Prometheus。`docker stats` 本身不保存趋势。

## 应用侧：日志走 stdout，时间戳别混

容器里的应用把日志写到 stdout/stderr，由日志驱动接管。不要写 `/var/log/app.log`：那是可写层，容器删了就没了；要保留就挂 volume，但那就不是「容器日志」而是「应用自己管文件」，轮转、权限、备份都归你。

`docker logs` 默认不加时间戳。你看到的时间（例如 `2026-10-29T09:10:01.221Z INFO ...`）是应用自己打的；要加 daemon 收到日志的时间，用 `docker logs -t`。排查「日志延迟/顺序」时，这两个时间不是一回事：应用时间可能来自业务时钟，`-t` 是 daemon 的时间。

每行一条结构化日志，至少带 `level`、`traceId`/`requestId`、logger 名。多容器混在一起时，没有关联 ID 的日志只能按时间猜。

## 动手

下面这套用 `max-size=1m`、`max-file=2`，先灌 5MB 再停。别再用 `sleep 5` 等 1MB：按每行约 30 字节、`sleep 0.01` 5 秒约 500 行算，只有十几 KB，到不了轮转。

```text
# 1. 先确认驱动与 LogPath（app 换成你要查的容器名）
$ driver=$(docker info --format '{{.LoggingDriver}}')
$ path=$(docker inspect --format '{{.LogPath}}' app 2>/dev/null)
$ if [ -n "$path" ]; then ls -lh "$path"; else echo "driver=$driver, LogPath 为空"; fi

# 2. 1MB 一份、保留 2 份，快速灌 5MB
$ docker run -d --name flood \
    --log-opt max-size=1m --log-opt max-file=2 \
    alpine sh -c 'yes 0123456789abcdef | head -c 5000000; sleep 30'

# 3. 看轮转后的文件
$ docker inspect --format '{{.LogPath}}' flood
$ ls -lh /var/lib/docker/containers/$(docker inspect -f '{{.Id}}' flood)/

# 4. docker logs 仍然能读；然后收尾
$ docker logs --tail 5 flood
$ docker rm -f flood
```

如果在第 2 步之后立刻 `ls`，可能只看到当前文件；写入是异步的，等一两秒再看。`max-file=2` 时应该看到 `-json.log` 和一个 `.1` 轮转文件，两个都在 1MB 上下。

## 还差的

- 这台机器没装 Docker，开头的 30G/3.7G 是现场值，后面的命令按官方文档的标准形态写，没有在本机实跑。
- 没有验证 dual logging 在 `syslog`/`fluentd` 具体版本上的缓存行为；默认 5 × 20MB 来自官方文档，实际会受驱动吞吐影响。
- 没有测 `local` 驱动在高压下的压缩 CPU 开销；只说默认压缩，没有量。
- 没有接入 cAdvisor/Prometheus，也没有做日志脱敏、保留策略和跨机查询；这篇文章只到 Docker 自带的日志与 `stats`。
- 没有验证 `live-restore` 在 daemon 升级、Swarm、rootless 下的行为；它不适用于后两者，升级时也可能失效。
