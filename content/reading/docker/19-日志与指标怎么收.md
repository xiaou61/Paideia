## 这一关在解决什么

服务出问题，`docker logs app` 一片空白；或者更糟——**磁盘满了**，`/var/lib/docker` 涨到几十 G，
排查半天发现是某个容器的日志文件没轮转。

**结论先说**：容器的 stdout/stderr 被容器运行时接管，默认写成宿主上的 **json-file**，
**不轮转、不限大小**。所以两件事必须做：配 `max-size`（防写满磁盘），
再决定是继续用 json-file 还是换日志驱动/采集器。

## 讲解

### stdout 是容器的"唯一出口"

容器里的应用**不应该写日志文件**（写进可写层的话，容器一删就没了，还撑大镜像层）。
正确姿势是打到 stdout/stderr，由运行时接管：

```text
$ docker logs -f --tail 100 app
2026-10-29T09:10:01.221Z  INFO 1 --- [main] o.s.b.w.embedded.tomcat.TomcatWebServer : Tomcat started on port 8080
```

`docker logs` 读的就是宿主上的文件：

```text
$ ls -lh /var/lib/docker/containers/<id>/<id>-json.log
-rw-r----- 1 root root 3.7G Oct 29 09:11 ...-json.log
```

**3.7G，没有轮转限制**。默认驱动 `json-file` 就是这样：一直写。

### 第一件必做：限制大小

单容器（`docker run`）：

```text
$ docker run -d --log-opt max-size=50m --log-opt max-file=3 --name app demo
```

Compose：

```yaml
services:
  app:
    image: demo
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

守护进程级默认（推荐，一劳永逸）：

```json
// /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
```

改完要 `systemctl restart docker`——**重启 docker 会重启所有容器**，选时间点。

### 第二件：决定日志往哪去

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| 继续 json-file + `docker logs` | 单机、排障为主 | 日志随容器删除而丢失，不能跨机查 |
| 换驱动（`local`） | 单机且不想撑爆磁盘 | `docker logs` 仍可用；`local` 自带压缩与轮转 |
| 采集器（Promtail / Fluent Bit）→ Loki / ES | 多机、需要按字段查 | 多一个组件要维护 |
| 直接打到远程（`--log-driver=syslog/gelf`） | 已有集中日志系统 | 驱动一忙就阻塞应用写日志 |

小白最常问"为什么 `docker logs` 在生产看不到"：因为生产换了驱动或上了采集，日志根本不落本地了。
**换驱动前先在文档里写清楚"以后去哪看日志"。**

### 指标：容器本身也有

```text
$ docker stats --no-stream
CONTAINER  CPU %  MEM USAGE / LIMIT   MEM %   NET I/O        BLOCK I/O
app        3.2%   412MiB / 1GiB       40.2%   12MB / 8MB     0B / 0B
db         18.7%  1.2GiB / 2GiB       60.1%   30MB / 22MB    120MB / 64MB
```

`docker stats` 是**即时快照**，不是历史。要看趋势要采集（cAdvisor → Prometheus），
或者至少把 `/sys/fs/cgroup` 的数值定期抓走。**排查"内存一直在涨"必须有历史**，
`docker stats` 只能看到此刻。

### 日志的三条纪律

1. **应用只写 stdout**，不写文件（容器里写文件等于给自己挖坑）。
2. **每行是结构化的一行**（JSON 或固定前缀），便于按字段过滤——`grep 关键字` 是最低效的手段。
3. **关联 ID 打进去**（traceId / requestId），否则多容器一混，你分不清哪行属于哪个请求。

## 动手

```text
# 1. 看默认日志文件有多大、在哪
$ docker inspect --format '{{.LogPath}}' <容器> | xargs ls -lh

# 2. 设上限后重启，验证轮转生效
$ docker run -d --log-opt max-size=1m --log-opt max-file=2 --name flood alpine \
    sh -c 'while true; do echo "$(date) stress"; sleep 0.01; done'
$ sleep 5 && ls -lh /var/lib/docker/containers/$(docker inspect -f '{{.Id}}' flood)/

# 3. 看到两个 1MB 文件就够了：轮转生效
$ docker rm -f flood
```

## 常见误区

### 误区：`docker logs` 看不到就是"应用没打日志"

**你以为**：日志空 = 代码没输出。
**实情**：三种常见原因：① 换过日志驱动（不再落本地）；② 应用写的是文件而不是 stdout；
③ 进程被 OOM kill，连缓冲都没刷出去。排查顺序就是这三条。

### 误区：日志随便打，出事再 grep

**你以为**：日志越多越好恢复现场。
**实情**：没有关联 ID 的多容器日志，等于一堆无法拼起来的碎片；而 3G 的日志文件，
`grep` 一次要几十秒，事故当下根本等不起。**日志的价值在结构，不在数量。**

## 小结

记住三件事：容器日志走 stdout；默认 json-file **无上限**，必须配 `max-size/max-file` 或换驱动；
`docker logs` 只代表"本地 json-file"，上了采集器就要知道新入口在哪。指标要历史，
`docker stats` 只是当下。
