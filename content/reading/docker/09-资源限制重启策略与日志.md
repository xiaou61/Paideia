## 512m 的 SQL 容器，死在 InnoDB 初始化之后

`backend/paideia-sandbox` 里那个执行学习者 SQL 的容器，内存该给多少，仓库里有两句话：

```text
backend/paideia-sandbox/src/main/java/io/github/xiaou61/sandbox/internal/run/SandboxProperties.java:48
 * 2026-10-28 实测：512m 起不来、1g 正常。--memory-swap 必须同时给，否则 swap 会兜住 OOM。

backend/paideia-app/src/main/resources/application.yml:236
    sql-memory: 512m
```

`SandboxProperties.java:50` 里那个字段的默认值是 `1g`，但 yml 的 512m 会在启动时绑上去——运行时生效的是 512m。于是仓库里一条路径写着「512m 实测起不来」，另一条路径正把 512m 传下去。

我第一反应是那条注释过期了：镜像改过，实测时用的东西现在没了。把 `DockerCommand.of` 拼出来的整条命令读完，才发现两个数都没写错——**这台容器上还有第二份内存账**：

```text
# 参数与顺序抄自 DockerCommand.java:295-331，镜像 digest 省略；本机没有 Docker，没有实跑
docker run --rm -i \
  --network=none --read-only \
  --tmpfs /tmp:rw,size=768m,exec \
  --user 999:999 --cap-drop=ALL --security-opt=no-new-privileges \
  --memory=512m --memory-swap=512m \
  --cpus=1 --pids-limit=128 \
  --ulimit nofile=1024 --ulimit nproc=128 \
  --stop-timeout=0 -e TZ=UTC \
  --entrypoint sh paideia-sandbox-mysql@sha256:e2eafb6… -c '<分帧脚本>'
```

`--memory=512m` 是这台容器的顶，`--tmpfs ... size=768m` 却写着 768m。两行不矛盾，是因为它们量的不是同一样东西：**tmpfs 里的页是拿容器的内存额度换的**，它不额外给你 768MB。那个 768m 是个到不了的上限，先到的是 512m。

`SandboxProperties.java:46-47` 把账算得很平：`/tmp` 里那份 78MB 的 datadir 副本也计入容器内存，mysqld 常驻约 350MB（`application.yml:232` 记的是 348MB，启动到可查询 3.3 秒），InnoDB 初始化期还有临时分配。512m 就是这么没的，而容器被杀时应用日志里一行报错都没有。

所以这一篇的判断只有一句：**同一台容器上，`--memory` 是唯一的内存天花板，其它以 MB 为单位的数字（tmpfs 的 size、`/dev/shm`）都不是新额度；而 CPU、进程数、停止超时是另外三件事，各有各的顶。** JVM 在容器里怎么读这个顶是第 16 关的事，这里不展开。

## 同一条命令上的四个旋钮

| 参数 | 它管的那一件事 | 到顶时你会看到 |
| --- | --- | --- |
| `--memory` / `--memory-swap` | 整台容器的内存硬顶，tmpfs 里的页也算在里面 | `Exited (137)` 且 `OOMKilled=true`，应用日志里没有异常 |
| `--cpus` | 可用算力的硬顶（CFS 配额） | `docker stats` 的 CPU% 顶在 100%×N，墙钟被拉长 |
| `--pids-limit` | 容器内 task 数上限，**线程也算一个 task** | `clone()` 返回 `EAGAIN`（errno 11） |
| `--stop-timeout` | SIGTERM 之后等多久发 SIGKILL | `0` 就是不给它收尾 |

### 内存与 swap 必须成对写

只写 `--memory` 时，docker 会把 swap 上限按同样大小补上，容器总可用是 `2 × --memory`（前提是宿主有 swap、cgroup 记了 swap；这两条不成立时这个上限没有意义。出处：docker run 的 `--memory-swap` 说明）。

这条命令里两处都写成等值，等于**禁掉 swap**。原因不是省内存，是禁掉之后内存超了会立刻以 137 的形状暴露，而不是先换出、GC 变慢，然后你在一堆超时里找原因。`SandboxProperties.java:48` 后半句「--memory-swap 必须同时给，否则 swap 会兜住 OOM」说的就是这个。

### `--cpus` 是封顶，`--cpu-shares` 是排队

- `--cpus=1` 不是「给它一个核」，是「它最多用掉一个核的算力」。宿主空着，它也还是一个核。
- `--cpu-shares` 默认 1024，只在几个容器抢同一批核时才起作用；空闲时它不拦任何东西。要「至少保证多少」用它，要「不许超过多少」用 `--cpus`。

配额会直接改变「能不能在超时前跑完」。本仓另一档留了实测（`SandboxProperties.java:93`）：Spring 项目容器 0.5 核时一次跑 55 秒（起 Spring 上下文占 22 秒），2 核约 15 秒；那一档的墙钟上限是 90 秒（`SandboxProperties.java:86`）。同一个任务差 3.7 倍，配 0.5 核不是「慢一点」，是稳定踩超时。

### `--pids-limit` 挡的不只是 fork 炸弹

pids cgroup 数的是 task，线程也占一个名额。所以这个上限对多线程服务比对脚本更紧：`application.yml:238-239` 记着「mysqld 是多线程的，64 不够（实测启动期就要几十个线程）」，SQL 那档给到 128；同一份文件里 java/python 与 shell 都是 64。

到顶时 `clone()` 拿到 `EAGAIN`（errno 11），进程侧看到的是 `Resource temporarily unavailable`（标准形态，未实跑）。内存和 CPU 都很空却冒这个错，就该往这个旋钮上想。

### `--stop-timeout=0` 和不写 `--restart` 是同一个决定

沙箱的每次执行都挂在一次 HTTP 请求上：超时必须立刻死，不给它自己收尾的机会，所以 `--stop-timeout=0`（`DockerCommand.java:322-323`）。同理这条命令里**没有** `--restart`，走默认的 `no`——重启只会把用户已经失败的那次执行重放一遍，还占着 `max-concurrency: 2` 的并发闸（`application.yml:223`）。

长期跑的容器是另一回事：

| 策略 | 什么时候会把它拉起来 | 什么时候别用 |
| --- | --- | --- |
| `no`（默认） | 从不 | 服务型容器，崩了只能靠人发现 |
| `on-failure[:N]` | 非 0 退出时，最多 N 次 | 退出码经常是 0 的任务（它不会重启） |
| `always` | 退出就重启，守护进程重启也会拉起来 | 手动 `docker stop` 是明确意图时 |
| `unless-stopped` | 除「手动停过」以外都重启 | 一次性任务、沙箱这类 |

`always` 与 `unless-stopped` 只在一个场景里不同：**你手动停过它，然后重启了 docker 守护进程**。前者拉起来，后者不拉。日常服务用 `unless-stopped`，理由就这一条。

两个配套动作：

```text
$ docker update --restart unless-stopped api
$ docker inspect --format '{{.RestartCount}} {{.State.Status}}' api
```

`docker update` 能改 `--restart`、`--memory`、`--cpus`、`--pids-limit`，改不了 `--tmpfs`、`--read-only`、`--log-opt`——这些是创建期参数。这条限制决定了下一节那件事只能在**创建时**做。

## 这台容器没有日志可以轮转

`--rm` 加上秒级生命周期，`docker logs` 能读的东西在容器退出时就一起没了（`--rm` 删的是容器和它的可写层，json-file 的日志文件跟着目录走）。所以对沙箱容器来说「日志轮转」不是问题，问题被换成了「这次执行的输出你打算怎么留」。

真正需要配保留策略的是活很久的那个进程。本仓的应用**不是容器**：`scripts/release.ps1:469` 停的是 `systemctl stop paideia`，`:484` 再 `start`，日志进 journald；再由 alloy 按白名单 unit 采集（`deploy/ops/alloy-config.alloy:3`、`:29`），推进 Loki，保留 720 小时（`deploy/ops/loki-config.yaml:39`）。这条链上每一环都有自己的保留策略，不存在「日志反正会留在那儿」。

容器那一路要配的话，作用范围从窄到宽有三处。单次运行：

```text
$ docker run -d --name api --log-opt max-size=50m --log-opt max-file=3 myapp:v1
```

Compose 里：

```yaml
services:
  api:
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

全局，写 `/etc/docker/daemon.json` 再重启守护进程：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

`max-size` / `max-file` 是 `json-file` 与 `local` 两个驱动的参数，其它驱动的参数名不同。全局配置只对**之后新建**的容器生效：已有容器的 `LogConfig` 在创建时就定下来了，重启守护进程不会改它。

日志驱动决定了 `docker logs` 能不能读：

| 驱动 | `docker logs` 能读吗 |
| --- | --- |
| `json-file`（默认） | 能。默认不轮转，文件会一直长 |
| `journald` | 能，它去读 journal |
| `local` | 能；这个驱动默认就带大小上限，磁盘上的格式不是 JSON，外部工具直接读不了 |
| `fluentd` / `awslogs` / `syslog` / `none` | 不能，要去日志的去处看 |

（支持 `docker logs` 的是 json-file、journald、local 三个，出处是 docker 当前 CLI 参考的 logging driver 一节。）

## 症状 → 先看哪

| 看到 | 先看 | 为什么 |
| --- | --- | --- |
| `Exited (137)` 且 `OOMKilled=true` | `--memory`，以及同一台容器上的 tmpfs、共享内存 | cgroup 内存到顶，内核动手，应用日志里没有异常 |
| `Exited (137)` 且 `OOMKilled=false` | `docker kill`、`docker stop` 超时、宿主 OOM | 同样是 SIGKILL，但动手的未必是这台容器的 cgroup |
| `Restarting (1) 3 seconds ago` | `docker logs --tail 50` | 反复重启=启动就崩；重启策略只决定它崩几次 |
| 容器没了，`docker logs` 也空 | 是不是 `--rm` 已经把它删了 | 退出即删，日志跟着走；要留输出得在它退出前收 |
| `/var/lib/docker` 把根分区写满 | `docker system df`，容器的 `LogPath` | json-file 默认不轮转，这是默认行为，不是故障 |

## 还差的

- 本机没有 Docker。上面所有回显——`Exited (137)`、`OOMKilled=true`、`Resource temporarily unavailable`、`docker logs` 的空输出——都是标准形态，没有一条是我跑出来的。
- `512m` 与 `1g` 那对矛盾我没能判定谁对。注释记的是 2026-10-28 的实测，yml 里生效的是 512m，而沙箱默认 `enabled: false`（`application.yml:210`），线上也没开，没有真实流量可验。
- swap 上限依赖宿主是否开了 swap、cgroup 是否记了 swap。这条我只按文档写，没在 cgroup v1 与 v2 上各验一遍。
- `--pids-limit` 打到上限时的确切报错文本我没验；errno 11 与 `Resource temporarily unavailable` 是从 `clone(2)` 的 EAGAIN 推的。
- journald 自己的 `SystemMaxUse` 与 Loki 实际占多少磁盘，本文没量，只写了保留策略在哪一行。
