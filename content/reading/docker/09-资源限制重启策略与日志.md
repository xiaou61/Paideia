## 这一关在解决什么

容器跑着跑着整个宿主卡死；`docker ps` 里一个容器反复 `Restarting`；某天早上磁盘满了，发现是某个容器的日志有 40GB。

这三件事对应这一关的三块：**资源限制**、**重启策略**、**日志轮转**。三者都是"设一次、长期有效"的配置，也都是"不设时会一直没事，直到某天出事"的类型。

## 为什么容器默认几乎不限制

因为 Docker 的默认值是"能用多少用多少"：内存不设上限、CPU 不限、日志不轮转。它的假设是"你会在部署时显式配置"。

在开发机上这没问题。在生产机上，一个内存泄漏的容器会把宿主内存吃光，然后 **OOM Killer 挑最大的进程杀**——它可能杀的不是这个容器，而是同机上的数据库。

## 讲解

### 内存：`--memory`

```text
$ docker run -d --memory 512m --memory-swap 512m myapp:v1
```

- `--memory`：内存硬上限，超过就 OOM Kill（容器内进程收到 SIGKILL，退出码 `137`）。
- `--memory-swap`：**内存 + swap 的总和**。设成和 `--memory` 相等等于禁用 swap；设成 `-1` 表示不限制 swap。**不设时默认是 `--memory` 的两倍**，也就是容器还能用 512m 的 swap——这会让"内存超了"表现成"变慢"而不是"被杀"，更难查。

**容器里 `free -m` 的数字是宿主的**，不是容器的限额。要看真实限制：

```text
$ cat /sys/fs/cgroup/memory.max            # cgroup v2
$ cat /sys/fs/cgroup/memory/memory.limit_in_bytes   # cgroup v1
$ docker stats --no-stream 容器
```

`docker stats` 的 `MEM USAGE / LIMIT` 那一列才是"用了多少 / 上限多少"。

**JVM 的坑**：JDK 8u191 之后认 cgroup 限制，但默认只按物理内存的一个比例取堆。所以要么给容器留足余量，要么显式设：

```text
-XX:MaxRAMPercentage=70
```

不设时常见结局：容器限 1G、JVM 默认堆按宿主 32G 算，一加压就 OOM。

### CPU：`--cpus` 与 `--cpu-shares`

```text
$ docker run -d --cpus 1.5 myapp:v1        # 最多用 1.5 个核
$ docker run -d --cpu-shares 512 myapp:v1  # 权重，不是上限
```

两个概念完全不同：

| 参数 | 含义 | 超了会怎样 |
| --- | --- | --- |
| `--cpus` | **硬上限**（配额） | 被 throttle，变慢 |
| `--cpu-shares` | **相对权重**（默认 1024） | 只在 CPU 争抢时按比例分配，空闲时可以用满 |

`--cpus 1.5` 在 `docker stats` 里会看到 `CPU %` 稳定在 150% 附近——**CPU 百分比是按单核算的**，400% 就是 4 个核。

### 进程数：`--pids-limit`

```text
$ docker run -d --pids-limit 100 myapp:v1
```

防止 fork 炸弹把宿主拖死。这个限制比内存更"必须"：一个失控的进程会瞬间创建几千个进程，宿主连 `docker stop` 都执行不进去。

### 重启策略

| 策略 | 行为 |
| --- | --- |
| `no`（默认） | 不重启 |
| `on-failure[:N]` | 非 0 退出才重启，最多 N 次 |
| `always` | 总是重启（包括手动 `docker stop` 后的守护进程重启） |
| `unless-stopped` | 除了**手动停过的**，其他情况都重启 |

`always` 与 `unless-stopped` 的差别只在"我手动停了它，然后重启了 Docker 守护进程"这个场景：`always` 会把它拉起来，`unless-stopped` 不会。**日常用 `unless-stopped`**——手动停是明确意图，不该被守护进程推翻。

两个配套：

```text
$ docker update --restart unless-stopped 容器     # 改正在跑的容器
$ docker run --stop-timeout 30 ...                # docker stop 等 30 秒（默认 10）
```

`--stop-timeout` 对"优雅停机需要时间"的服务很重要（Spring Boot 要等在处理完的请求、关闭连接池）。10 秒不够就被 SIGKILL，日志里表现为"重启后发现有半截事务"。

反复 `Restarting` 说明**启动就崩溃**，不是重启策略有问题——去看 `docker logs`。把 `on-failure:3` 这种带上限的策略用在"我还不确定它稳不稳"的阶段，可以避免无限重启掩盖真实错误。

### 日志：默认不轮转，这是磁盘杀手

默认日志驱动是 `json-file`，**没有大小上限**。一个打日志很欢的服务能在几周内写出几十 GB，然后宿主的 `/var/lib/docker` 把根分区撑满。

全局配置（`/etc/docker/daemon.json`）：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

改完要重启 docker 守护进程，**且只对之后新建的容器生效**。

单容器配置：

```text
$ docker run -d --log-opt max-size=50m --log-opt max-file=3 myapp:v1
```

Compose 里：

```yaml
services:
  api:
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

查看与清理：

```text
$ docker logs --tail 200 -f api         # 看
$ docker logs --since 10m api
$ docker system df                      # 看日志/卷/镜像各占多少（BUILD-CACHE 那行也常是大头）
```

`docker logs` 只能读 `json-file` 与 `journald` 驱动；用 `local` 驱动时日志在磁盘上的格式不同，仍可用 `docker logs` 读，但外部工具读不了。

更正规的做法是让应用自己写日志文件并配轮转（Linux 线第 13 关），容器只负责跑。

### 在 Compose 里写资源限制

```yaml
services:
  api:
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 1g
        reservations:
          memory: 256m
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

Compose V2 支持 `deploy.resources.limits`（不需要 Swarm）。它比较新的写法，用 `docker compose config` 确认一下是否被接受，比用早已废弃的 `mem_limit`/`cpus` 顶层键更稳。

### 看实时用量

```text
$ docker stats                 # 类似 top，实时刷新
$ docker stats --no-stream     # 拍一张
$ docker inspect 容器 --format '{{.State.OOMKilled}} {{.HostConfig.Memory}}'
```

`docker stats` 的 `MEM USAGE` 与 `LIMIT` 的比值长期超过 80%，就该调整上限或查泄漏了。

## 常见误区

### 误区：容器里 `free -m` 看到的内存就是我的上限

**你以为**：容器里看到 32G 空闲，说明够用。
**其实**：`free`、`top` 读的是宿主的内核数据，**容器限制它们看不到**（cgroup 层面的限制不会体现在 `/proc/meminfo`）。所以"容器里看着内存很宽裕，结果被 OOM 杀掉"是常态。判断只能看 `docker stats` 的 `LIMIT` 或读 `/sys/fs/cgroup/memory.max`。
**怎么验证**：`docker run --memory 256m alpine sh -c 'free -m; cat /sys/fs/cgroup/memory.max'`——前者显示宿主总量，后者显示 268435456。

### 误区：`--memory` 设了就一定只吃这么多

**你以为**：512m 就是 512m。
**其实**：不设 `--memory-swap` 时它默认是 `--memory` 的两倍，容器可以用 swap 把一部分内存"挪出去"，表现是变慢而不是被杀。另外 `tmpfs` 挂载、共享内存（`/dev/shm`，默认 64m）也计入内存额度，设得太小会以各种奇怪的方式失败（比如 MySQL 初始化时被静默杀掉）。
**怎么验证**：`docker inspect 容器 --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}'` 两个值是否相等。

### 误区：`restart: always` 是"高可用"

**你以为**：设了自动重启就不用管了。
**其实**：它只处理"进程退出"这一种失败。容器反复重启恰恰说明有确定性 bug（配置错、依赖没起、端口被占），无限重启只会掩盖它，还让日志被重复的启动错误刷满。`on-failure:3` + 告警比 `always` 更能暴露问题。
**怎么验证**：`docker inspect --format '{{.RestartCount}}'`、`docker ps` 的 `Restarting (1) 3 seconds ago` 状态；`docker events --filter container=名字` 能看到重启事件流。
