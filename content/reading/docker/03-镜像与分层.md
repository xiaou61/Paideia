三个日常困惑：


- 为什么拉一个 1GB 的镜像，第二次几乎瞬间完成？
- 为什么 `docker image ls` 里每个镜像都写着 1GB，磁盘却没被吃光？
- 为什么 Dockerfile 里删了文件，镜像反而更大了？

答案都是一个词：**分层**。

## 为什么是分层

因为镜像的绝大部分内容在不同版本之间是相同的（操作系统的基础文件、语言运行时）。如果每个版本都存一份完整副本，仓库和磁盘都会被浪费几十倍。

分层把镜像切成"一层一层的差异"，每层只记录相对上一层的改动。**相同内容的层只存一份、只传一次**，在多个镜像之间共享。

## 讲解

### 镜像 = 有序的只读层

```text
$ docker image ls
REPOSITORY   TAG       IMAGE ID       CREATED        SIZE
nginx        1.27      a8b8d3c1e5f7   2 weeks ago    192MB
myapp        v1        4c1d2e3f4a5b   3 hours ago    421MB
```

`SIZE` 是**这个镜像所有层加起来**的大小，不是它在磁盘上**独占**的大小。两台镜像共享的层只算一次。

看一个镜像由哪些层构成：

```text
$ docker history nginx:1.27
IMAGE          CREATED       CREATED BY                                      SIZE
a8b8d3c1e5f7   2 weeks ago   CMD ["nginx" "-g" "daemon off;"]                0B
<missing>      2 weeks ago   STOPSIGNAL SIGQUIT                              0B
<missing>      2 weeks ago   EXPOSE map[80/tcp:{}]                           0B
<missing>      2 weeks ago   RUN /bin/sh -c set -x && apt-get update ...     50MB
<missing>      2 weeks ago   COPY docker-entrypoint.sh /                    8KB
<missing>      2 weeks ago   ADD file:... in /                              74MB
```

**每条 `RUN`/`COPY`/`ADD` 产生一层**，`CMD`/`EXPOSE`/`ENV` 这类只改元数据、不产生文件，所以 SIZE 是 `0B`。

底层实现叫 **overlay2**（联合文件系统）：它把多层目录"叠"成一个视图，读文件时从上往下找第一个存在的。这也解释了容器的可写层——容器启动时在最上面加一层可写的，所有改动都写在这里。

### 三条由分层推出的结论

**1. 拉取快是因为层已经在本地了。**

```text
$ docker pull openjdk:21-jdk     # 第一次：下载所有层
$ docker pull openjdk:21-jdk-slim # 大概率秒完成：底层相同的层被复用
```

日志里的 `Already exists` 就是"这层我有了"。

**2. 构建缓存也是按层算的。**

改了一行代码，只有 `COPY` 那一层之后的所有层需要重建；前面的 `apt-get install` 层直接复用（第 04 关的核心）。

**3. 在后面的层里删文件，删不掉它占的空间。**

```dockerfile
RUN apt-get install -y build-essential && make        # 这一层装了 300MB 工具链
RUN apt-get remove -y build-essential                 # 这一层只记录"删了"，上层那 300MB 还在
```

因为下层是只读的，删除只是在上层记了一条"这个文件被删了"的标记。真正的做法是**在同一条 `RUN` 里装、用、删**：

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends build-essential \
    && make \
    && apt-get purge -y --auto-remove build-essential \
    && rm -rf /var/lib/apt/lists/*
```

`rm -rf /var/lib/apt/lists/*` 也在同一条命令里——这是最经典的一行优化，能省几十 MB。

### 标签（tag）与摘要（digest）

```text
$ docker image ls --digests
REPOSITORY   TAG    DIGEST                          SIZE
nginx        1.27   sha256:6db391d1c0cf...          192MB
```

- **tag** 是可变的指针，`nginx:1.27` 今天和三个月后可能指向不同的镜像（维护者会重新发布）。
- **digest** 是内容的哈希，**唯一确定一个镜像**，不会变。

所以生产环境钉版本要钉 digest：

```text
$ docker pull nginx@sha256:6db391d1c0cf...
```

`latest` 只是一个**默认标签**，既不代表最新也不代表稳定——它只是"没写 tag 时用的那个名字"。`nginx:latest` 可能比 `nginx:1.27` 还旧，完全取决于维护者最后一次推什么。

### 常用命令

```text
$ docker pull nginx:1.27          # 拉
$ docker push 我/应用:v1           # 推（第 08 关）
$ docker tag myapp:latest myapp:v1  # 给同一个镜像加第二个名字（不复制，只是多一个标签）
$ docker rmi nginx:1.27           # 删镜像（有容器在用会拒）
$ docker image prune -a           # 删所有没被容器使用的镜像
$ docker image inspect nginx:1.27 --format '{{.Architecture}}/{{.Os}}'
```

`docker tag` 只是加名字，不产生新镜像——这点在"我构建了 v1 又 tag 成 latest，会不会重复占空间"这个问题上的答案是：不会。

### 镜像大小从哪来

一个"就一个 Java 服务"的镜像做到 2GB，通常是这几处：

| 来源 | 典型大小 | 处理 |
| --- | --- | --- |
| 基础镜像选了完整发行版 | `ubuntu:24.04` ≈ 78MB，`openjdk:21-jdk` ≈ 500MB | 换 `-slim`/`-alpine`/`-jre` 变体 |
| 构建工具留在运行镜像里 | Maven、gcc 几百 MB | **多阶段构建**（第 04 关） |
| 包管理器的索引缓存 | `/var/lib/apt/lists` 几十 MB | 同一层里 `rm -rf` |
| 构建产物与源码 | `target/`、`node_modules` | `.dockerignore` 排除 |
| 日志、临时文件误入镜像 | 不定 | 运行时目录挂卷 |

## 常见误区

### 误区：`docker rmi` 能立刻回收磁盘空间

**你以为**：删镜像就腾出空间。
**其实**：镜像被容器引用（包括**已退出的容器**）时删不掉；`docker image prune -a` 也只删"没有被任何容器使用"的。真正的大头常常是停止的容器与构建缓存：`docker system df -v` 能按项列出，`docker system prune -a` 才能一起收。
**怎么验证**：`docker system df` 里 `RECLAIMABLE` 那一列才是能回收的量；`docker ps -a` 看有多少 Exited 容器。

### 误区：镜像 ID 前面的 `<missing>` 是层丢了

**你以为**：`docker history` 显示 `<missing>` 说明镜像损坏。
**其实**：那是"层在别的镜像里、本地没有独立的标签指向它"，属于正常显示。真正需要关心的是 `docker image ls` 能不能列出、容器能不能起。
**怎么验证**：`docker image inspect 镜像 --format '{{.RootFS.Layers}}'` 能看到完整的层哈希列表，数量与 `history` 对得上就没问题。

### 误区：`docker build` 每次都是全量重来

**你以为**：改了代码就要重新装依赖。
**其实**：构建缓存是按层匹配的——**某一层之前的所有指令没变，就不用重建**。所以把"装依赖"放在 copy 源码之前，改代码时依赖层直接命中缓存（第 04 关的具体写法）。反过来说，`COPY . .` 太早会让每次改动都击穿后面所有层的缓存，这才是"构建要十分钟"的真凶。
**怎么验证**：构建日志里 `CACHED` 标记；`docker build --progress=plain` 能看到每一层是否命中。
