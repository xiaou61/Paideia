## `docker rmi nginx:1.30` 报 image is being used by stopped container

```text
$ docker ps -a
CONTAINER ID   IMAGE        COMMAND                   CREATED       STATUS                   PORTS   NAMES
<container-id> nginx:1.30   "/docker-entrypoint.…"   2 hours ago   Exited (0) 2 hours ago           web

$ docker rmi nginx:1.30
Error response from daemon: conflict: unable to delete <image-id> (must be forced) - image is being used by stopped container <container-id>
```

（标准输出形态；本机没装 Docker，未实跑。报错文字随版本可能略有差异。）

`web` 已经停了，镜像还是删不掉。停止的容器仍然引用镜像，因为它随时可以 `docker start`。先 `docker rm web`，再 `docker rmi nginx:1.30`。容器和镜像不是一回事：删容器不等于删镜像，删镜像也不等于删掉所有引用它的容器。

如果你给同一个镜像打过多个 tag，`docker rmi` 可能只移除你点名的那个 tag，镜像本身还在。`-f` 可以强删，但停止的容器会留下一个指向缺失镜像的引用，之后也起不来；先删容器才是干净的处理。

## 2026 年的 `docker image ls` 有两种默认表

`docker images` 是 `docker image ls` 的别名。Docker 28 及更早默认是下面这张老表；Docker 29 的 CLI 默认换成新视图，全新安装还默认 containerd 镜像存储。你看到哪一种取决于版本，不是镜像坏了。

```text
# Docker 28 及更早（或显式 --format）
REPOSITORY   TAG     IMAGE ID       CREATED        SIZE
nginx        1.30    <12-char-id>   <时间>         <累计大小>

# Docker 29 默认新视图
IMAGE        ID             DISK USAGE   CONTENT SIZE   EXTRA
nginx:1.30   <12-char-id>   <磁盘占用>    <内容大小>      <标记>
```

列宽不是固定宽度：CLI 按当前内容对齐。`IMAGE ID` 默认只显示 12 位，`--no-trunc` 才显示完整；脚本里不要按空格切列，用 `--format` 指定字段。

老视图的 `SIZE` 是镜像和所有父层的累计大小，不是它在磁盘上独占的大小。多个 tag 指向同一个镜像时，每一行都会显示同样的 `SIZE`，但磁盘只存一份。新视图把 `DISK USAGE` 和 `CONTENT SIZE` 分开：前者是本机快照的实际占用，后者是镜像内容的大小，两者不相等是正常的。

## 一摞只读层，history 里能看到每层的 `CREATED BY`

```text
$ docker history nginx:1.30
IMAGE                    CREATED        CREATED BY                                      SIZE
<image-id>               <时间>         CMD ["nginx" "-g" "daemon off;"]                0B
<missing>                <时间>         STOPSIGNAL SIGQUIT                              0B
<missing>                <时间>         EXPOSE map[80/tcp:{}]                           0B
<missing>                <时间>         COPY docker-entrypoint.sh /                     <层大小>
...
```

`docker history` 从新到旧列出每一层的 `CREATED BY`。`RUN`、`COPY`、`ADD` 会产生文件系统层；`CMD`、`EXPOSE`、`ENV`、`STOPSIGNAL` 这类只改元数据，`SIZE` 是 `0B`，但历史里仍占一行。默认会截断长命令，`--no-trunc` 看全；`SIZE` 是这一层的增量，不是整个镜像的累计。

`IMAGE` 列不是层哈希，是这一行历史对应的本地镜像 ID。拉下来的镜像没有为每个中间步骤保留独立镜像；BuildKit 构建的步骤也可能没有。所以这里常见 `<missing>`，BuildKit 构建的镜像还可能显示 `buildkit.dockerfile.v0`。它不表示层丢了。

要核对层，看 `docker image inspect --format '{{.RootFS.Layers}}'`。`history` 的行数不等于层数：`CMD`/`ENV` 这些元数据行没有对应的文件系统层，不能直接拿总行数去比；先把元数据行排除，再看文件系统步骤。

`docker image ls` 里的 `<none>` 是另一回事：它是没有仓库名或标签的镜像。默认看到的多是 dangling（重建 tag 后留下的旧镜像），`--all` 还会带出中间层。最常见的原因是重建同一个 `repo:tag`，tag 移到新镜像，旧镜像变成 `<none>:<none>`；`docker load` 进来没有标签也会这样。默认视图（包括 Docker 29 的新视图）不显示未打标签的镜像，`--all` 才看得到。它和 `history` 的 `<missing>` 不是同一个标记。

## 层怎么叠：overlay2 与 containerd

Linux 上传统的 Docker 存储驱动是 `overlay2`：把只读层和一个可写层联合挂载。读文件从上层往下找，写文件触发 copy-up，删除在上层写一个 whiteout 标记，下层数据仍在。所以“在后面的层里删文件”不会回收前面层占的空间。

Docker Engine 29.0 起，全新安装默认 containerd 镜像存储，使用 `overlayfs` snapshotter；从旧版升级上来的 daemon 仍可能是 `overlay2`。`docker info` 的 `Storage Driver` 一行会显示 `overlay2` 或 `overlayfs`。命令形态不变，但别把 `overlay2` 当成所有机器的唯一答案。

容器启动时在镜像最上面加一层可写层，所有运行时改动写在这里。`docker stop` 再 `docker start` 会保留这层；`docker rm` 删掉它；用同一个镜像重新 `docker run` 会得到一层新的、干净的可写层。

## 标签会动，digest 不会

`tag` 是一个可变的指针。`nginx:1.30` 今天指向 1.30.x 的某个补丁，维护者重新发布后可能指向另一个；`latest` 只是没写 tag 时用的默认名字，不代表最新，也不代表稳定。

`digest` 是镜像内容的哈希，指向确定的内容。生产环境要复现“昨天到底是哪个镜像”，就钉 digest：

```text
$ docker image inspect nginx:1.30 --format '{{index .RepoDigests 0}}'
nginx@sha256:<digest>

$ docker pull nginx@sha256:<digest>
```

`RepoDigests` 来自仓库；本地 `docker build` 且还没 push 的镜像可能是空的。`docker tag` 只是给同一个镜像再加一个名字，不复制内容；`docker rmi` 删掉一个 tag 时，如果还有其他 tag 指向它，镜像仍然在。

## 改一行代码，为什么整层重建

先在 `nginx:1.30` 上加一个自己的首页。下面三行 `FROM`/`COPY` 先照抄，第 04 关再逐条讲：

```dockerfile
FROM nginx:1.30
COPY index.html /usr/share/nginx/html/index.html
```

构建两次：

```text
$ docker build --progress=plain -t web:v1 .
...
#7 [2/2] COPY index.html /usr/share/nginx/html/index.html
#7 CACHED
```

（`#7` 这个节点号随 Dockerfile 和内部步骤变，不要把它当固定值。耗时行我略掉了。）

BuildKit 在 Docker Desktop 和 Docker Engine 23.0 起是默认 builder。老 builder 的命中提示是 `---> Using cache`，BuildKit 是下一行的 `CACHED`。看到 `CACHED`，说明这一层的输入没变，直接用了缓存。

改 `index.html` 后，`COPY` 层的内容哈希变了，`COPY` 这一层和它后面的所有层都重建；前面的 `FROM nginx:1.30` 层仍然复用。把 `COPY . .` 放在安装依赖之前，每次源码变动都会把依赖层打穿；正确顺序是稳定在前、易变在后，`.dockerignore` 把 `.git`、`node_modules` 这类无关文件挡在构建上下文外（第 04 关）。

`docker build --no-cache` 会让所有层重跑，适合验证“从零构建是否还成立”，不适合日常代替修 Dockerfile。BuildKit 的 cache mount 和跨机器缓存导出在第 14 关，这一篇只讲层缓存。

## 删镜像之前先看引用

```text
$ docker ps -a --filter ancestor=nginx:1.30
$ docker rm web
$ docker rmi nginx:1.30
$ docker system df
```

`docker image prune -a` 只删没有被任何容器使用的镜像；停止的容器也算使用，所以它不会替你解决开头那个冲突。`docker system prune -a` 会删停止容器、未使用镜像和构建缓存，执行前先看 `docker system df` 的 `RECLAIMABLE`，确认没有还要保留的停止容器。
