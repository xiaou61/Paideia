## 先把结论摆出来

Java 里没有"忘记 free"，所以泄漏只有一种形状：**对象已经不需要了，但还有引用链把它连到 GC Root**。

三种最常见的持有者：

1. **静态集合**：`static Map` 只往进放、不清理；
2. **未注销的监听器/回调**：注册了但对象销毁时没移除；
3. **线程池与 ThreadLocal**：任务里塞了大对象，池不销毁，ThreadLocal 的 value 跟着线程活着。

三者的共同点是**生命周期比业务对象长**。

## 先分清"泄漏"和"用得多"

| 现象 | 结论 |
| --- | --- |
| GC 后能降回稳定低值 | 用得多，不是泄漏 |
| GC 后一次比一次高 | 泄漏（或有无限增长的缓存） |
| 涨到某个上限后稳定 | 可能是容量设计问题 |

只有第二行才需要 dump。**先看 GC 日志，再决定 dump**——这一步能省掉大部分无效排查。

## 三个工具的分工

| 工具 | 看什么 | 有停顿吗 |
| --- | --- | --- |
| `jstat -gcutil <pid> 1000` | 各代使用率随时间变化 | 几乎没有 |
| `jstack <pid>` | 线程栈：谁在阻塞、线程在干什么 | 有短暂停顿 |
| `jmap -histo:live <pid>` | 各类对象数量与占用 | **会触发 Full GC** |
| `jmap -dump:live,format=b,file=x.hprof <pid>` | 完整堆快照 | 大堆会停几十秒 |

**顺序**：`jstat` 确认有泄漏 → `jmap -histo:live` 看哪类对象异常多 → 必要时 dump。

`jmap -histo:live` 里的 `live` 很关键：没有它就只统计已分配，包含等待回收的垃圾，会把数字看得虚高。

## 一个具体的泄漏现场

```text
static final Map<String, Session> CACHE = new ConcurrentHashMap<>();

void onLogin(Session s) {
    CACHE.put(s.userId(), s);       // 只写不删
}
```

用户越多、内存越高，而且**GC 后降不下来**——因为这些对象全都能从静态字段走到。

这类问题的修法不是调参数，而是：

- 换带过期的缓存（Caffeine 的 `expireAfterAccess`）；
- 或者显式在退出时删除。

**判据**：任何 `static` 的集合，都要能回答"什么时候从这里移除"。

## ThreadLocal 为什么容易漏

线程池里的线程是长期存活的。`ThreadLocal` 的值挂在线程对象上：

```text
线程 → ThreadLocalMap → value（可能是大对象）
```

你 `set` 了但没 `remove`，这个 value 就跟着线程活到线程销毁——在池里几乎是永远。

**纪律只有一条**：`try { set } finally { remove }`。

## 类加载器泄漏

比对象泄漏更隐蔽：一个本该回收的 `ClassLoader` 被引用住，它加载的**所有类**连同静态字段都下不来。

常见触发：

- 动态创建的 `URLClassLoader` 用完没 close；
- 热部署/重复初始化框架；
- 线程上下文类加载器（`Thread.currentThread().setContextClassLoader`）被线程池里的线程持有。

症状是**元空间持续增长**（`OutOfMemoryError: Metaspace`），而堆看着正常。

查法：

```text
jcmd <pid> GC.class_histogram | grep -i classloader
jcmd <pid> GC.class_stats            # 需要 -XX:+UnlockDiagnosticVMOptions
```

## 一个排查清单

```text
1. jstat -gcutil 1 秒一次，看老年代使用率是否单调上涨
2. 涨 → jmap -histo:live，看哪一类占比异常
3. 该类是业务对象 → 去找"谁持有它"（MAT / VisualVM 打开 dump 看 GC Root 路径）
4. 元空间涨而堆正常 → 查 ClassLoader
5. 修完再跑同一段压测，确认"回收后"不再上涨
```

**第 5 步经常被跳过**：改完不验证，下次同样的泄漏换个位置再来一次。

## 常见误区

### 误区：Java 有 GC，不会内存泄漏

**你以为**：不用手动释放，就不会漏。
**其实**：GC 只回收不可达对象。被静态字段、线程、注册表引用住的对象永远可达。
**怎么验证**：把一个大对象放进 `static List`，反复触发 GC，看它是否还在。

### 误区：`jmap -histo` 的数字越大越可疑

**你以为**：对象最多的类就是泄漏源。
**其实**：`String`、`byte[]` 这类本来就多。要看的是**与你预期不符**的增长（比如业务 DTO 有几百万个）。
**怎么验证**：间隔一段时间跑两次，比较增量而不是绝对值。

### 误区：调大堆能"解决"泄漏

**你以为**：给够内存就不 OOM 了。
**其实**：泄漏是持续增长，加多少都会到顶，只是把事故推迟、把单次停顿拉长。
**怎么验证**：观察 Full GC 后的水位是否随堆增大仍持续上涨。
