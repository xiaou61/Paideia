## 先把结论摆出来

`OutOfMemoryError` 有四种常见形态，**报错文本直接告诉你问题在哪一块**：

| 报错里写的 | 发生在哪 | 加 `-Xmx` 有用吗 |
| --- | --- | --- |
| `Java heap space` | 堆 | 有用（除非是泄漏） |
| `Metaspace` | 类元数据 | 没用（调 `-XX:MaxMetaspaceSize`） |
| `unable to create native thread` | 线程栈 + 系统限制 | 没用，反而更糟 |
| `Direct buffer memory` | 堆外直接内存 | 没用（调 `-XX:MaxDirectMemorySize`） |

**看到 OOM 先读报错，不要先看启动参数。**

## 堆：对象住的地方

所有 `new` 出来的对象都在堆上（逃逸分析优化掉的除外）。堆是 GC 的主要战场。

```text
-Xms2g -Xmx2g     # 初始与最大相等：避免运行期扩容带来的停顿
```

两个设成相等是少数**几乎总是对**的建议：动态扩容会触发 Full GC，而且扩容本身有代价。

## 元空间：类的元数据

JDK 8 之后，类的结构信息（方法字节码、常量池、注解）放在**元空间**，用的是本地内存而不是堆。

它的大小取决于**加载了多少个类**，而不是你 new 了多少对象。增长失控的典型原因：

- 运行时生成类（动态代理、CGLIB、脚本引擎、反射框架）——每个新类都会占元空间；
- 热部署/反复重载（开发期常见）；
- **类加载器泄漏**：本该回收的 ClassLoader 被别的东西引用住，它加载的所有类都跟着下不来。

`OutOfMemoryError: Metaspace` 在线上通常意味着"类被不断生成或不断泄漏"，重启只能缓解。

## 线程栈：每个线程一块

每个线程有自己的栈，默认 512KB–1MB（`-Xss`）。

`unable to create native thread` 的成因链通常是：

```text
线程数太多 → 虚拟内存（或进程数上限）耗尽 → 创建新线程失败
```

这时加堆**会让情况更坏**：堆越大，留给线程栈的地址空间越少。

要查的是线程数：

```text
jstack <pid> | grep -c '^"'        # 当前线程数
ps -o nlwp= -p <pid>               # Linux 上也行
```

线程数异常增长的典型原因：线程池被反复创建（每次请求 new 一个池）、阻塞任务把池占满后上游还在加线程。

## 直接内存：堆外那部分

`ByteBuffer.allocateDirect()`、NIO、Netty 用的都是堆外内存。它**不受 `-Xmx` 限制**，但受物理内存和 `-XX:MaxDirectMemorySize` 限制。

它的大小在堆 dump 里**看不到**（堆 dump 只有堆），所以"堆看着正常但进程 RSS 一直涨"是它的典型症状。

```text
-XX:MaxDirectMemorySize=512m      # 明确设上限，别依赖默认（默认约等于最大堆）
```

## 一张对照表

| 症状 | 先看什么 |
| --- | --- |
| 堆 dump 里对象不多，但 RSS 很高 | 直接内存 / 元空间 / 线程栈 |
| `jstat` 老年代持续上涨，Full GC 降不下来 | 堆内泄漏 |
| 线程数持续增长 | 线程池被反复创建、或任务阻塞 |
| 类数量持续增长 | 动态生成类 / ClassLoader 泄漏 |

## 常见误区

### 误区：只要不是 heap space 的 OOM 就与内存无关

**你以为**：元空间、直接内存的报错是"别的问题"。
**其实**：它们都是内存，只是不在堆里。查的方向完全不同——一个是类加载，一个是 NIO 缓冲。
**怎么验证**：把 `-XX:MaxMetaspaceSize` 调小，复现一次，看报错文本。

### 误区：`-Xmx` 设得越大越安全

**你以为**：内存给足就不会 OOM。
**其实**：泄漏给多少都会满，只是晚一点；而且堆越大，一次 Full GC 的停顿越长，单次故障的爆炸半径更大。
**怎么验证**：看 GC 日志里的停顿时间随堆大小怎么变。

### 误区：堆 dump 能解释所有内存问题

**你以为**：`jmap -dump` 出来就什么都能查。
**其实**：堆 dump 只含堆。直接内存、元空间、线程栈都不在里面。后三者要看 `jcmd` 的 `VM.native_memory`（需开启 NMT）或系统层面的 RSS。
**怎么验证**：对比 `jmap -histo` 的对象总量与进程 RSS，差额就是堆外的部分。
