## 先把结论摆出来

**`jstack` 给的是"某一瞬间，每个 Java 线程分别停在哪个栈帧、在等什么"的快照。它不是性能分析器，也不能告诉你历史。**

读 dump 只需要回答四个问题：

1. **有没有死锁？** 先搜 `Found one Java-level deadlock`，有就直接定位；
2. **线程都卡在哪一类状态？** `RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING` 各有多少；
3. **卡在等谁？** 锁对象、线程池队列、下游 socket、还是 GC；
4. **这个状态是持续的，还是刚好被我抓到？** 一次 dump 不算证据，间隔几秒抓两三次对比。

最重要的一条：**`RUNNABLE` 不等于在烧 CPU。** socket 读、文件读、epoll 等待在 JVM 里都显示 `RUNNABLE`，因为线程确实"可运行"，只是内核还没给它数据。判断 CPU 高不高，要配合 `top -H` 和 `nid`，不能只看线程状态。

## 线程状态先分清

Java 层只有六种线程状态，`jstack` 会把它们写在每个线程的第二行：

| 状态 | jstack 里的样子 | 典型栈 | 含义 |
| --- | --- | --- | --- |
| `NEW` | 一般不出现 | 无 | 创建了但没 `start()` |
| `RUNNABLE` | `java.lang.Thread.State: RUNNABLE` | 业务方法、`socketRead0`、`epollWait` | 正在跑，或在内核里等 IO |
| `BLOCKED` | `BLOCKED (on object monitor)` | `waiting to lock <0x...>` | 等 `synchronized` 监视器 |
| `WAITING` | `WAITING (parking)` / `WAITING (on object monitor)` | `LockSupport.park`、`Object.wait` | 无限期等待，需要别人唤醒 |
| `TIMED_WAITING` | `TIMED_WAITING (sleeping)` / `(parking)` | `Thread.sleep`、`parkNanos` | 有超时的等待 |
| `TERMINATED` | 一般不出现 | 无 | 已结束 |

几个容易混淆的点：

- **`BLOCKED` 只对应 `synchronized`。** `ReentrantLock` 等不到锁时显示的是 `WAITING (parking)`，栈里是 `AbstractQueuedSynchronizer.parkAndCheckInterrupt`。看到 `BLOCKED` 就去找监视器，看到 `parking` 就去找 `ReentrantLock` / `Condition` / 线程池。
- **`WAITING` 不等于死锁。** 线程池的空闲 worker 全部停在 `LinkedBlockingQueue.take`，状态就是 `WAITING (parking)`，这是正常待命，不是故障。
- **`TIMED_WAITING (sleeping)` 是主动睡。** 业务代码里出现 `Thread.sleep`，尤其是请求链路上，通常意味着有人在用睡眠等结果。
- **`RUNNABLE` 是最容易被误读的状态。** 它只表示"没有被阻塞在 Java 锁/等待上"，不代表正在占用 CPU。

## jstack 输出结构

一个典型的线程段：

```text
"order-import-3" #35 prio=5 os_prio=0 cpu=1234.56ms elapsed=3600.12s tid=0x000002a1c0a5e800 nid=0x3f2c waiting on condition  [0x000000c8b7efe000]
   java.lang.Thread.State: WAITING (parking)
        at jdk.internal.misc.Unsafe.park(Native Method)
        - parking to wait for  <0x0000000712a3b4d8> (a java.util.concurrent.locks.AbstractQueuedSynchronizer$ConditionObject)
        at java.util.concurrent.locks.LockSupport.park(LockSupport.java:211)
        at java.util.concurrent.LinkedBlockingQueue.take(LinkedBlockingQueue.java:435)
        at java.util.concurrent.ThreadPoolExecutor.getTask(ThreadPoolExecutor.java:1062)
        at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1127)
        at java.util.concurrent.ThreadPoolExecutor$Worker.run(ThreadPoolExecutor.java:617)
        at java.lang.Thread.run(Thread.java:833)
```

逐字段拆开：

| 字段 | 含义 | 排查时怎么用 |
| --- | --- | --- |
| `"order-import-3"` | 线程名 | 第一眼的信息，线程池一定要命名 |
| `#35` | Java 线程 id | 对应 `Thread.getId()` |
| `prio=5` | Java 优先级 | 很少是问题 |
| `os_prio=0` | 操作系统优先级 | Linux 上通常都是 0 |
| `cpu=1234.56ms` | 该线程累计 CPU 时间 | 结合 `elapsed` 看占比 |
| `elapsed=3600.12s` | 线程存活时间 | 判断是不是长期驻留的池线程 |
| `tid=0x...` | JVM 内部线程指针 | 一般不用 |
| `nid=0x3f2c` | **操作系统线程 id（十六进制）** | 和 `top -H` 对应 |
| `waiting on condition` | JVM 层状态摘要 | 和 Java 状态互相印证 |
| `[0x...]` | 栈指针 | 一般不用 |

`nid` 是定位 CPU 热点的关键：`top -H -p <pid>` 显示的是十进制线程 id，`jstack` 显示十六进制，需要转换。

```bash
top -H -p 12345
# 假设看到线程 16172 占用 98% CPU
printf '0x%x\n' 16172
# 0x3f2c
jstack 12345 | grep -A 40 'nid=0x3f2c'
```

`jstack -l` 会额外打印 ownable synchronizers，也就是 `ReentrantLock`、`ReentrantReadWriteLock` 等 AQS 锁的持有情况：

```text
   Locked ownable synchronizers:
        - <0x0000000712a3b4d8> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
```

没有 `-l` 时，`ReentrantLock` 的持有者信息不完整，排查锁竞争会很难。

## 死锁自动检测

`jstack` 会在 dump 末尾自动检测 Java 级别的死锁，输出大致如下：

```text
Found one Java-level deadlock:
=============================
"transfer-a":
  waiting to lock monitor 0x00000000d8e8d0a8 (object 0x00000000d8e8d0a0, a com.example.Account),
  which is held by "transfer-b"
"transfer-b":
  waiting to lock monitor 0x00000000d8e8d0b8 (object 0x00000000d8e8d0b0, a com.example.Account),
  which is held by "transfer-a"

Java stack information for the threads listed above:
===================================================
"transfer-a":
        at com.example.TransferService.transfer(TransferService.java:42)
        - waiting to lock <0x00000000d8e8d0a0> (a com.example.Account)
        - locked <0x00000000d8e8d0b0> (a com.example.Account)
"transfer-b":
        at com.example.TransferService.transfer(TransferService.java:42)
        - waiting to lock <0x00000000d8e8d0b0> (a com.example.Account)
        - locked <0x00000000d8e8d0a0> (a com.example.Account)
```

读法是"环"：

1. `transfer-a` 持有 `0x...d0b0`，等 `0x...d0a0`；
2. `transfer-b` 持有 `0x...d0a0`，等 `0x...d0b0`；
3. 两个人各持一把、各等对方那把，环闭合，谁也走不了。

这就是**锁顺序死锁**：两个线程以相反顺序获取同一组锁。修法不是"加大超时"，而是统一锁顺序：

```java
void transfer(Account from, Account to, long amount) {
    Account first = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to : from;
    synchronized (first) {
        synchronized (second) {
            // 扣款、入账
        }
    }
}
```

按账户 id 排序后再加锁，所有线程的获取顺序一致，环就不可能形成。

死锁检测的边界：

- `jstack` 能检测**监视器死锁**和**ownable synchronizer 死锁**（需要 `-l`）；
- 它检测不了"逻辑死锁"：线程 A 等一个永远不会到来的消息，线程 B 等 A 的结果，状态上可能都是 `WAITING`，但没有锁环；
- 它检测不了数据库行锁、分布式锁、连接池耗尽这类 JVM 外部的等待；
- 它只反映抓取瞬间，偶发死锁可能抓不到，需要多次 dump 或接入 `ThreadMXBean.findDeadlockedThreads()` 做持续监控。

`ThreadMXBean` 的用法：

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();
if (ids != null) {
    for (ThreadInfo info : bean.getThreadInfo(ids, true, true)) {
        log.error("deadlock: {}\n{}", info.getThreadName(), info);
    }
}
```

把这段挂到定时任务或健康检查里，比等用户报障再抓 dump 可靠得多。

### 死锁之外：活锁与饥饿

dump 里没有死锁段，不代表没有"卡住"。还有两种形态：

- **活锁**：线程都在 `RUNNABLE`，反复重试同一个冲突操作（比如 CAS 一直失败、事务一直回滚重试），CPU 有占用但业务没有进展。`jstack` 不会报死锁，需要结合业务日志、重试计数和火焰图判断。
- **饥饿**：低优先级任务长期排不上，或者某个线程一直抢不到锁。dump 里可能看到少数线程反复持有锁，另一些线程长期 `WAITING`。优先级队列、非公平锁、线程池隔离不当都可能造成饥饿。

这两种问题靠单次 dump 很难定性，通常要结合指标和多次采样。

## CPU 高和阻塞是两条完全不同的排查线

线上"服务变慢"通常分两类，排查入口完全不同：

| 现象 | 典型状态 | 先看什么 |
| --- | --- | --- |
| CPU 打满、吞吐下降 | `RUNNABLE` 多，且 `top -H` 有热点线程 | 线程栈里的热点方法、GC、JIT |
| CPU 不高、请求挂起 | `BLOCKED` / `WAITING` 多 | 锁持有者、线程池、下游 IO、死锁 |

### CPU 高的排查顺序

```bash
# 1. 找进程
top -p $(pgrep -f 'java.*my-service')

# 2. 找进程内最忙的线程
top -H -p <pid>

# 3. 十进制转十六进制
printf '0x%x\n' <线程id>

# 4. 在 dump 里定位
jstack <pid> | grep -A 40 'nid=0x<十六进制>'

# 5. 如果不是业务线程，看 GC 和 JIT
jstat -gcutil <pid> 1000
```

常见的高 CPU 线程类型：

- **业务线程**：停在某个业务方法里，可能是死循环、正则回溯、大 JSON 序列化、频繁创建对象；
- **GC 线程**：名字通常是 `GC Thread#N`、`G1 Young RemSet Sampling`，说明 CPU 花在回收上，去看 GC 日志和分配速率；
- **JIT 编译线程**：`C2 CompilerThreadN`，大量编译通常发生在启动或流量突增时，持续高 CPU 要怀疑代码缓存或去优化；
- **VM Thread**：安全点操作、GC、偏向锁撤销等，通常和 GC 或 safepoint 有关；
- **日志/监控线程**：某些 agent 在采样，确认是不是监控本身的开销。

如果热点线程停在 `socketRead0` 却显示 100% CPU，先怀疑采样误差或把 `top` 的线程 id 对错了；socket 读本身不烧 CPU。

### 阻塞的排查顺序

```bash
jcmd <pid> Thread.print -l > dump1.txt
sleep 5
jcmd <pid> Thread.print -l > dump2.txt
sleep 5
jcmd <pid> Thread.print -l > dump3.txt
```

先数状态：

```bash
jstack <pid> | grep 'java.lang.Thread.State' | sort | uniq -c | sort -rn
```

输出大致是：

```text
     42    java.lang.Thread.State: WAITING (parking)
     18    java.lang.Thread.State: RUNNABLE
      6    java.lang.Thread.State: BLOCKED (on object monitor)
      2    java.lang.Thread.State: TIMED_WAITING (sleeping)
```

然后按状态找原因：

- **大量 `BLOCKED`**：找 `waiting to lock <0x...>`，再到同一份 dump 里搜 `- locked <0x...>`，找到持锁线程，看它卡在哪。持锁线程可能在做慢查询、等下游、或者也在等另一把锁。
- **大量 `WAITING (parking)` 在线程池队列上**：空闲 worker，正常；如果队列里还有任务却没人处理，说明 worker 都被别的东西占住了，或者池太小。
- **大量 `WAITING` 在 `Future.get` / `CompletableFuture.join`**：请求线程在等异步结果，去看下游任务为什么慢。
- **大量 `RUNNABLE` 在 `socketRead0`**：在等下游 IO，检查连接池、超时、DNS、TLS；这不是 CPU 问题。
- **大量 `TIMED_WAITING (sleeping)`**：有人在用 `sleep` 轮询或退避，检查是不是重试策略过于激进。

判断"持续"还是"瞬时"：把三次 dump 的线程名和栈顶方法对比。同一个线程连续三次都停在同一个帧，才是持续卡住；每次都不同，可能只是采样到了不同请求。

## jcmd 比 jstack 更值得先学

`jstack` 是一个薄封装，`jcmd` 能做的事更多，而且在容器、精简 JRE 里通常更可靠：

| 命令 | 作用 |
| --- | --- |
| `jcmd -l` | 列出本机所有 Java 进程 |
| `jcmd <pid> Thread.print` | 等价于 `jstack` |
| `jcmd <pid> Thread.print -l` | 带 ownable synchronizers |
| `jcmd <pid> VM.version` | JVM 版本与参数 |
| `jcmd <pid> VM.flags` | 启动参数 |
| `jcmd <pid> GC.heap_info` | 堆使用概况 |
| `jcmd <pid> GC.class_histogram` | 类实例统计（可能触发 Full GC） |
| `jcmd <pid> VM.native_memory` | 本地内存（需开启 NMT） |
| `jcmd <pid> JFR.start` | 启动飞行记录 |

容器里如果 Java 进程是 PID 1，直接 `jcmd 1 Thread.print -l`；如果 `jstack` 报 "Unable to open socket file"，通常是权限或 `/tmp` 挂载问题，换 `jcmd` 或用 `kill -3 <pid>`（输出到进程 stdout，注意别把日志刷爆）。

`jstack -F` 是强制模式，进程已经挂死、普通 attach 失败时才用。它可能让进程短暂停顿，而且栈信息不一定完整，不要作为首选。

## 线程池线程一定要命名

默认线程工厂生成的名字是 `pool-1-thread-1`、`pool-2-thread-3`。一个服务里有十几个线程池时，这些名字等于没有信息：你不知道 `pool-3` 是订单导入还是对账，也不知道 `thread-7` 属于哪个业务。

```java
ThreadFactory factory = new ThreadFactory() {
    private final AtomicInteger seq = new AtomicInteger(1);

    @Override
    public Thread newThread(Runnable task) {
        Thread thread = new Thread(task, "order-import-" + seq.getAndIncrement());
        thread.setDaemon(false);
        return thread;
    }
};
```

JDK 21 可以更简洁：

```java
ThreadFactory factory = Thread.ofPlatform()
        .name("order-import-", 1)
        .factory();
```

命名建议包含三部分：**业务名 + 角色 + 序号**，例如 `order-import-worker-3`、`settle-batch-1`。多租户或分片场景可以再加租户/分片标识，但不要把用户输入直接拼进线程名（长度和注入都要考虑）。

命名之后，dump 里能直接看出：

- 哪个池的线程最多；
- 哪个池的线程全在等锁；
- 哪个池的线程数超过了预期；
- 哪个任务把 worker 占住了。

没有命名时，至少用 `jstack | grep '"pool-' | sort | uniq -c` 粗略统计，但这只能告诉你"池很多"，不能告诉你"哪个业务"。

## 常见栈形态对照

下面这些栈在 dump 里反复出现，认熟了能省很多时间。

### 空闲的线程池 worker

```text
"order-import-3" #35 ... WAITING (parking)
        at jdk.internal.misc.Unsafe.park(Native Method)
        - parking to wait for  <0x...> (a java.util.concurrent.locks.AbstractQueuedSynchronizer$ConditionObject)
        at java.util.concurrent.locks.LockSupport.park(LockSupport.java:211)
        at java.util.concurrent.LinkedBlockingQueue.take(LinkedBlockingQueue.java:435)
        at java.util.concurrent.ThreadPoolExecutor.getTask(ThreadPoolExecutor.java:1062)
        at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1127)
        at java.util.concurrent.ThreadPoolExecutor$Worker.run(ThreadPoolExecutor.java:617)
        at java.lang.Thread.run(Thread.java:833)
```

这是正常的待命状态。`getTask` 在等队列里的下一个任务。数量等于池的空闲线程数，不需要处理。

### 等 synchronized 监视器

```text
"order-worker-2" #40 ... waiting for monitor entry  [0x...]
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.OrderService.update(OrderService.java:88)
        - waiting to lock <0x0000000712a3b4d8> (a com.example.OrderService)
        - locked <0x0000000712a3b5a0> (a com.example.OrderRepository)
```

`order-worker-2` 已经持有 `OrderRepository`，在等 `OrderService` 的监视器。到 dump 里搜 `- locked <0x0000000712a3b4d8>`，找到持有 `OrderService` 的线程，看它在干什么。如果它也在等 `order-worker-2` 持有的锁，就是死锁。

### 等 ReentrantLock

```text
"order-worker-5" #43 ... WAITING (parking)
        at jdk.internal.misc.Unsafe.park(Native Method)
        - parking to wait for  <0x0000000712a3b6c8> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
        at java.util.concurrent.locks.AbstractQueuedSynchronizer.parkAndCheckInterrupt(AbstractQueuedSynchronizer.java:833)
        at java.util.concurrent.locks.AbstractQueuedSynchronizer.acquireQueued(AbstractQueuedSynchronizer.java:864)
        at java.util.concurrent.locks.ReentrantLock$NonfairSync.lock(ReentrantLock.java:209)
        at com.example.Inventory.reserve(Inventory.java:55)
```

注意状态是 `WAITING (parking)` 而不是 `BLOCKED`。要加 `-l` 才能看到持有者：

```text
   Locked ownable synchronizers:
        - <0x0000000712a3b6c8> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
```

### 等队列的 Condition

`ArrayBlockingQueue.put` / `take` 在队列满或空时，线程状态是 `WAITING (parking)` 或 `TIMED_WAITING (parking)`，栈停在 `ConditionObject.await`，不是 `BLOCKED`：

```text
"producer-3" #48 ... WAITING (parking)
        at jdk.internal.misc.Unsafe.park(Native Method)
        - parking to wait for  <0x0000000712a3c1f8> (a java.util.concurrent.locks.AbstractQueuedSynchronizer$ConditionObject)
        at java.util.concurrent.locks.LockSupport.park(LockSupport.java:211)
        at java.util.concurrent.locks.AbstractQueuedSynchronizer$ConditionObject.await(AbstractQueuedSynchronizer.java:1630)
        at java.util.concurrent.ArrayBlockingQueue.put(ArrayBlockingQueue.java:352)
        at com.example.ImportService.submit(ImportService.java:31)
```

生产快、消费慢时，大量生产者会停在这里；这是有界队列的背压，不是故障。但如果队列长期满、生产者一直不返回，就要看消费者是不是卡在别处，或者池太小、下游太慢。消费快、生产慢时，消费者会停在 `take` 上，同样正常。

### 等连接池

连接池耗尽时，业务线程通常停在 `HikariPool.getConnection` 的等待逻辑上，状态是 `WAITING` 或 `TIMED_WAITING`。看到一批线程卡在这里，不要第一反应是"把连接池调大"：先看有没有连接泄漏（借了没还）、慢 SQL 是不是占住了连接、连接池上限是不是小于并发线程数。连接池是有限资源，调大只是把压力推给数据库。

### 等下游 IO

```text
"http-nio-8080-exec-7" #52 ... RUNNABLE
        at sun.nio.ch.Net.poll(Native Method)
        at sun.nio.ch.NioSocketImpl.park(NioSocketImpl.java:184)
        at sun.nio.ch.NioSocketImpl.timedRead(NioSocketImpl.java:280)
        at sun.nio.ch.NioSocketImpl.implRead(NioSocketImpl.java:304)
        at sun.nio.ch.NioSocketImpl.read(NioSocketImpl.java:350)
        at java.net.Socket$SocketInputStream.read(Socket.java:966)
        at com.mysql.cj.protocol.ReadAheadInputStream.fill(ReadAheadInputStream.java:112)
```

`RUNNABLE`，但线程实际上在等 MySQL 返回数据，不占 CPU。这类线程多，说明瓶颈在下游，不在 JVM。检查连接池是否耗尽、SQL 是否慢、超时是否过长。

### 主动 sleep

```text
"retry-worker-1" #60 ... TIMED_WAITING (sleeping)
        at java.lang.Thread.sleep(Native Method)
        at com.example.RetryJob.run(RetryJob.java:31)
```

`sleep` 是主动让出 CPU，通常不是故障。但如果它出现在请求链路上，或者 sleep 时间很长，就要问"为什么需要睡"：是不是在等一个可以用事件/回调替代的条件。

### GC 与编译线程

```text
"GC Thread#0" os_prio=0 cpu=45678.90ms elapsed=3600.12s tid=0x... nid=0x... runnable
"VM Thread" os_prio=0 cpu=12345.67ms elapsed=3600.12s tid=0x... nid=0x... runnable
        at VMThread::run
```

逐段读：

1. **先看死锁段。** `transfer-a` 持有 `0x...d0b0`，等 `0x...d0a0`；`transfer-b` 持有 `0x...d0a0`，等 `0x...d0b0`。环闭合，两个线程永久卡住。这解释了"转账接口超时"。
2. **再看其他线程。** `http-nio-8080-exec-7` 在 `socketRead0` 等 MySQL，说明还有一个下游延迟问题，但它不是转账线程，可能是另一个接口。不要把所有线程都归因于死锁。
3. **看空闲池。** `order-import-1` 停在 `LinkedBlockingQueue.take`，是空转等任务，正常。如果它显示有任务在队列里却没人处理，才需要看池大小。
4. **看 GC。** `GC Thread#0` 有 CPU 时间，但没有 GC 暂停信息；需要 `jstat` / GC 日志确认它是不是在频繁回收。单看 dump 不能下结论。
5. **结论**：直接原因是锁顺序死锁；次要问题是下游 IO 延迟；`order-import` 池正常。修复死锁后，再单独查 MySQL 慢查询。

如果只抓了一次 dump，你能看到"卡住"，但不能确认"卡了多久"。连续三次抓到同样的 `transfer-a` / `transfer-b` 栈，才能确认是持续性死锁，而不是恰好撞上一次慢操作。

另外，这段 dump 里 `transfer-a` 和 `transfer-b` 的累计 CPU 都只有 100 多毫秒，说明它们不是 CPU 热点；`BLOCKED` 加上死锁段，已经足够定位。反过来说，如果一份 dump 里所有线程都是 `RUNNABLE` 且 CPU 很高，就不该在锁上找原因，而应该回到 `top -H` 和热点方法。**先判断故障类型，再选工具**，不要拿一份 dump 解释所有问题。

## 抓 dump 的时机与代价

`jstack` 和 `jcmd Thread.print` 都需要 JVM 走到安全点（safepoint）才能拿到一致的线程快照。安全点意味着应用线程会在某个位置短暂停下，所以：

- 对普通服务，一次 dump 的停顿通常在几毫秒到几十毫秒；线程数很多、堆很大、正在 GC 时会更长；
- 不要在高峰期连续抓几十次，抓取本身可能把延迟推高；
- 最好在服务健康时也抓一份基线，出事时才有"正常长什么样"的对照。

实际操作建议：

```bash
# 文件名带时间，避免覆盖
jcmd <pid> Thread.print -l > dump-$(date +%H%M%S).txt
sleep 5
jcmd <pid> Thread.print -l > dump-$(date +%H%M%S).txt
```

容器里要注意 PID 命名空间：宿主机上的 `jstack <宿主机pid>` 和容器内的 `jcmd 1` 看到的不是同一个进程号。优先 `docker exec` / `kubectl exec` 进容器，用容器内的 PID；如果容器里没有 JDK 工具，可以用 `jattach`，或者把 `jcmd` 从同版本 JDK 拷进去。权限上，抓取用户要和 Java 进程用户一致，否则 attach 会失败。

`kill -3 <pid>` 也能打印线程栈，但它输出到进程的 stdout，可能混进业务日志，还可能被日志采集放大。只在 attach 完全失败时用，并提前确认输出位置。

线程栈本身也可能包含敏感信息：SQL 语句、URL、文件路径、内部类名。dump 文件不要随手传到公开渠道，按日志同样的级别保管。

## 一套固定的排查顺序

```text
1. jcmd -l / ps 确认进程和 PID
2. jcmd <pid> Thread.print -l > dump1.txt
3. 搜 "Found one Java-level deadlock"           → 有则先修锁顺序
4. 统计线程状态数量                              → 判断是 CPU 型还是等待型
5. CPU 高：top -H -p <pid> → printf %x → grep nid
6. 等待型：找 waiting to lock 的持有者、
   找线程池队列、找 socketRead0/Future.get
7. 间隔 5 秒再抓 2 次，对比同一线程是否仍在同一帧
8. 需要热点/分配/锁竞争细节时，再用 JFR / async-profiler
9. 修复后复跑同一场景，确认线程状态和延迟恢复
```

第 7 步是很多人跳过的：**单次 dump 只能证明"此刻"，不能证明"一直"。** 第 8 步也要注意分工：`jstack` 回答"谁在等谁"，JFR / async-profiler 回答"CPU 花在哪个方法、对象分配在哪里"，两者不能互相替代。

## 常见误区

### 误区：RUNNABLE 就是在跑，CPU 高就是它

**你以为**：状态是 `RUNNABLE` 的线程一定在消耗 CPU。
**其实**：`RUNNABLE` 包含正在运行和"可运行但在等内核 IO"两种情况。`socketRead0`、`epollWait`、文件读都显示 `RUNNABLE`，但线程可能一点都不占 CPU。判断热点必须用 `top -H` 找到高 CPU 的 `nid`，再回到 dump 里定位。
**怎么验证**：起一个只做阻塞 socket 读的线程，`jstack` 看它是 `RUNNABLE`，同时 `top -H` 看它的 CPU 占用接近 0。

### 误区：看到 BLOCKED 就是死锁

**你以为**：线程卡在 `BLOCKED`，一定是死锁。
**其实**：`BLOCKED` 只表示在等监视器。持锁线程可能正在做一次慢查询、写日志、等下游，过一会儿就释放。死锁要求存在等待环，而且 `jstack` 会在末尾单独打印死锁段。大量 `BLOCKED` 更常见的含义是"某段临界区太慢"或"锁粒度太粗"。
**怎么验证**：看持锁线程的栈，如果它在做业务/IO 而不是在等另一把锁，就不是死锁；再看多次 dump 是否一直不释放。

### 误区：抓一次 dump 就够了

**你以为**：一份 `jstack` 能还原整个事故。
**其实**：dump 是瞬间快照。偶发死锁、短时锁竞争、周期性的 GC 停顿，都可能刚好错过。至少间隔几秒抓两三次，比较同一线程是否持续停在同一帧，才能区分"持续卡住"和"刚好采样到"。
**怎么验证**：对同一个服务连续抓三份，比较线程名和栈顶；持续问题三份几乎一样，瞬时问题每份都不同。

### 误区：jstack 能看到所有线程

**你以为**：`jstack` 列出的是进程里的全部线程。
**其实**：它只列 Java 线程。纯 native 线程（没有 Java 栈帧的）不会出现；虚拟线程默认也不一定逐个展示。要判断操作系统线程总数，用 `ps -o nlwp= -p <pid>` 或 `ls /proc/<pid>/task | wc -l`；要 dump 虚拟线程，JDK 21 可以用 `jcmd <pid> Thread.dump_to_file -format=text /tmp/threads.txt`。
**怎么验证**：对比 `jstack | grep -c '^"'` 与 `ps -o nlwp= -p <pid>`，两个数通常不相等。

### 误区：`jstack -F` 是最稳的抓取方式

**你以为**：普通 `jstack` 失败时，加 `-F` 强制抓一定更好。
**其实**：`-F` 走的是强制 attach，可能让目标进程停顿，栈信息也可能不完整；它适合进程已经挂死、普通方式完全失败的情况。首选应该是 `jcmd <pid> Thread.print -l`，再退到 `kill -3`，最后才考虑 `-F`。
**怎么验证**：在正常服务上分别用 `jstack`、`jcmd`、`jstack -F` 抓取，比较耗时和栈帧完整性；不要在线上随意对核心服务做强制 attach。

## 小结

`jstack` 的价值是"关系"：谁持有锁、谁在等锁、谁在等队列、谁在等下游。它不负责告诉你 CPU 热点，也不负责历史趋势。

记住四件事：

1. **先搜死锁段**，有环就先修锁顺序；
2. **`RUNNABLE` 不等于忙**，CPU 高要用 `top -H` + `nid` 定位；
3. **`BLOCKED` 只对应 `synchronized`**，`ReentrantLock` 看 `WAITING (parking)` 和 `-l`；
4. **一次 dump 只是快照**，至少抓三次，看是否持续。

线程池线程命名、`jcmd` 替代 `jstack`、`ThreadMXBean` 持续检测死锁，这三件事应该在写代码和搭监控时就做好，而不是等出事再补。
