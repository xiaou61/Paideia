## 先把结论摆出来

**先看指标，再选收集器。** 三个数决定一切：


- **吞吐**：应用线程干活的时间占比；
- **停顿**：单次 GC 让应用停多久（直接影响接口 P99）；
- **占用**：GC 自己吃掉多少内存与 CPU。

三者的关系是互相挤的：停顿短通常要多花 CPU、多占内存。**你只能挑两个。**

现代默认值的选择：

| 场景 | 选什么 |
| --- | --- |
| 大多数服务（默认） | G1 |
| 堆很大（几十 GB）、要求停顿几毫秒 | ZGC / Shenandoah |
| 批处理、离线任务、只在乎总时长 | Parallel |
| 只在单核/小内存容器里 | Serial（默认可能已经是它） |

## 分代假设：为什么可以分两代

GC 的设计建立在一个观察上：**绝大多数对象很快就会死**。

于是堆分成年轻代和老年代：

- **年轻代**：新对象都在这。大部分 E 区对象在下一次 Minor GC 前就死了，回收成本很低（复制存活对象即可）；
- **老年代**：活过几轮 Minor GC 的对象被"晋升"过来。这里死得少，回收代价高。

前提是"对象早死"。**如果业务大量创建长生命周期对象（大缓存、大集合），分代假设就不成立**，这时 GC 会一直忙而回收不到东西。

## G1 凭什么成为默认

G1 把堆分成很多大小相等的 Region，按"垃圾最多"优先回收（Garbage First）。它的目标是**可控的停顿**：

```text
-XX:MaxGCPauseMillis=200     # 目标停顿，不是保证
```

注意是**目标**而不是保证：JVM 会为了达成它调整回收多少 Region，但对象实在太多时就做不到。

G1 的两个常见误解：

- **"G1 不会 Full GC"**：会。晋升失败、并发模式失败时仍然会退化成一次 Full GC，而且这次通常很长；
- **"Mixed GC 就是 Full GC"**：不是。Mixed 只回收部分老年代 Region。

## ZGC 换了什么思路

ZGC 把停顿压到毫秒级，代价是更多地依赖并发标记与"指针染色"，CPU 占用更高、堆外元数据也更多。

它适合**大堆 + 低延迟**：堆几十 GB 时 G1 的停顿会到几百毫秒，ZGC 仍能保持个位数毫秒。

它不适合：小堆（收益不明显）、CPU 已经很紧张的服务（并发阶段要抢核）。

## 什么时候不该调

下面这些"调优"通常是在给别的问题打补丁：

| 你在调 | 真正的问题可能是 |
| --- | --- |
| 加大年轻代 | 对象存活时间本来就长（该去掉缓存/大对象） |
| 提高晋升阈值 | 年轻代里塞着本该短命的大对象 |
| 加 `-XX:MaxTenuringThreshold` | 对象在一两轮 Minor 后就该死了，不是阈值问题 |
| 换更"高级"的收集器 | 分配速率太高，先看看是不是在循环里创建对象 |

**先量分配速率**：如果每秒分配几百 MB，换什么收集器都只是延缓。

## 一个具体的参数集

```text
-Xms4g -Xmx4g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-Xlog:gc*:file=/var/log/app/gc.log:time,uptime:filecount=5,filesize=50M
```

前两行定容量，第三行给目标停顿，第四行**开日志**——没有日志的调优都是猜。

## 常见误区

### 误区：收集器越新越好

**你以为**：ZGC 比 G1 新，所以该换成 ZGC。
**其实**：ZGC 用更多 CPU 换更低停顿。小堆或 CPU 紧张的服务换了反而更慢。
**怎么验证**：同一份压测，两种收集器各跑一次，比较吞吐与 P99。

### 误区：GC 停顿长就加大堆

**你以为**：堆大一点，GC 次数少，停顿就少。
**其实**：堆越大，单次 Full GC 要扫的对象越多，停顿越长。次数与单次时长是两件事。
**怎么验证**：固定负载，改 `-Xmx`，观察 GC 日志里的单次停顿。

### 误区：GC 偶发卡顿可以忽略

**你以为**：一天几次 Full GC 无所谓。
**其实**：Full GC 通常伴随"世界停止"，几秒的停顿会让上游超时、熔断触发、甚至雪崩。它往往不是一个独立问题，而是内存压力积累的信号。
**怎么验证**：把 GC 停顿时间叠加到接口 P99 曲线上看是否有对应尖峰。
