## 先把结论摆出来

读 GC 日志只需要回答两个问题：

```sketch

      { "id": "trend", "title": "回收后还剩多少", "sub": "一直往上涨就是泄漏", "tone": "amber" }

    { "from": "often", "to": "trend" }

```

1. **回收之后还剩多少？** 剩下的降不下来 = 对象真的活着（泄漏或缓存太大）；
2. **回收花了多久？** 时间越来越长 = 要么对象多，要么回收器在做无用功。

**"剩下多少"决定是不是内存问题，"花多久"决定用户受不受影响。** 两件事分开看，就不会被一堆数字淹死。

## 先开日志

```text
-Xlog:gc*:file=/var/log/app/gc.log:time,uptime:filecount=5,filesize=50M
```

老版本（JDK 8）是 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:...`。JDK 9 之后统一成了 `-Xlog`，别混用。

## 一条日志该看哪几个数

G1 的一条典型日志（简化）：

```text
[12.345s][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause)
   1234M->456M(2048M) 12.3ms
```

四个关键位置：

| 位置 | 含义 |
| --- | --- |
| `Pause Young` / `Pause Full` | 年轻代 / 整堆 |
| `1234M->456M` | **回收前 → 回收后**（最重要的两个数） |
| `(2048M)` | 堆容量 |
| `12.3ms` | 本次停顿 |

## 判断一：回收后剩下多少

把多次 Full GC 的"回收后"值排一排：

```text
Full GC 后：456M → 512M → 589M → 703M → 812M ...
```

**单调上涨 = 有东西一直活着**。两种可能：

- 真的需要（大缓存、大集合）；→ 调容量或改设计
- 不需要但被引用住（泄漏）；→ 去做堆 dump 找持有者

如果 Full GC 后能回到一个稳定的低值（456M → 470M → 455M），那不是泄漏，只是分配速率高。

**这一条是全文最重要的判据**：不看"涨"，只看"回收后能不能降回来"。

## 判断二：停顿花在哪

| 现象 | 含义 |
| --- | --- |
| Minor GC 频繁（每秒多次）但每次很短 | 分配速率高，通常无害；除非把 CPU 吃满 |
| Minor GC 间隔越来越短 | 年轻代被长命对象塞满，晋升变多 |
| 偶发一次很长的 Full GC | 晋升失败或并发模式失败——**这才是要查的** |
| 每次停顿都在涨 | 堆在变大或对象图变复杂（可达性分析更慢） |

## 判断三：是不是"回收器在空转"

一个容易误判的情况：GC 次数多、CPU 高，但回收后内存没什么变化。

这说明**回收器一直在尝试，但回收不到东西**。原因通常是老年代几乎全是活对象（缓存、连接池、大集合），每次 GC 都在做无用功。

这时的正确做法不是调参数，而是**问这个缓存该不该这么大**。

## 一个具体的排查顺序

```text
1. 统计 Full GC 次数与每次"回收后"的值     → 有没有泄漏
2. 看最长的一次停顿是多少                  → 有没有影响 P99
3. 看 Minor GC 频率                        → 分配速率是否异常
4. 看是否有 "to-space exhausted" /
   "concurrent mode failure"               → 收集器退化的信号
5. 有怀疑再去 dump                         → 找持有者
```

**第 1、2 步看日志就够，不需要 dump。** 直接 `jmap -dump` 一个大堆服务会停顿几十秒，别一上来就做。

## 常见误区

### 误区：堆使用率高就是有问题

**你以为**：用了 90% 很危险。
**其实**：GC 后能降回 40% 就是健康的——高水位只是说明还没到 GC 时机（或者收集器还没来得及跑）。
**怎么验证**：看"回收后"而不是"回收前"的值。

### 误区：GC 次数多说明内存泄漏

**你以为**：GC 一多就是泄漏。
**其实**：分配速率高也会让 Minor GC 频繁。区分方法还是看回收后能不能降下来。
**怎么验证**：对比 GC 频率与业务 QPS，QPS 涨 GC 涨通常是正常的。

### 误区：日志太吵，生产上关掉

**你以为**：GC 日志影响性能。
**其实**：`-Xlog:gc*` 的写盘开销很小，而它是唯一能事后还原"当时内存怎么变的"证据。关掉等于出事时没有任何现场。
**怎么验证**：开着日志跑一次压测，看吞吐差异——通常在百分之几以内。
