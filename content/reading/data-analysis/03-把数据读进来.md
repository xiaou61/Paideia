## 这一关在解决什么

读数据看起来是最没技术含量的一步，但它是**最便宜的一次排错机会**。类型读错、编码读错、日期读错，后面所有计算都建立在错的前提上，而且往往不报错。

这一关按"读进来之后先看什么"的顺序，讲四个最常见的坑。

打个比方：读数据像收快递，先验货再签收。真实机制是：类型、编码、日期、范围这四关不过，后面全是在错的前提上加工。

## 讲解

### 坑一：类型是推断出来的

```python
df = pd.read_csv('orders.csv')
print(df.dtypes)
```

CSV 没有类型信息，pandas 自己猜。常见的猜错：

| 数据 | 猜成 | 问题 |
| --- | --- | --- |
| `00123` | int `123` | 前导零丢了，订单号/邮编变成另一个值 |
| `1,200` | object | 千分位逗号让整列变字符串 |
| `2026-11-04` | object（有时 datetime） | 取决于格式与版本，后面做不了时间运算 |
| `3.10` | float `3.1` | 版本号被当成小数 |

对策不是"全部转成字符串"，而是**逐列声明**：

```python
df = pd.read_csv('orders.csv', dtype={'order_no': 'string', 'amount': 'float64'}, parse_dates=['created_at'])
```

### 坑二：编码

中文 CSV 在 Windows 上常是 GBK，`read_csv` 默认 UTF-8，直接报 `UnicodeDecodeError`，或者读出一串乱码。

```python
df = pd.read_csv('data.csv', encoding='gbk')
# 不确定时：先试 utf-8-sig（带 BOM 的 UTF-8），再试 gbk
```

`utf-8-sig` 是专门处理带 BOM 文件的。Excel 导出的 UTF-8 CSV 开头常有一个不可见字符。不处理的话，第一列列名会变成 `\ufeffid`，后面 `df['id']` 报 KeyError。

### 坑三：日期时间

日期读成字符串，`df['date'].max()` 会按字典序比较，`2026-9-30` 大于 `2026-10-01`。必须显式转：

```python
df['created_at'] = pd.to_datetime(df['created_at'], errors='coerce', utc=True)
```

`utc=True` 很关键：带时区的数据统一到 UTC，避免"跨零点的订单算到前一天"。展示时再转本地时区。

转换后立刻检查两件事：

```python
df['created_at'].isna().sum()      # 有多少行转失败
df['created_at'].min(), df['created_at'].max()  # 有没有 1970 或 2999 这种哨兵值
```

### 坑四：读到的是"样本"，不是"全量"

`SELECT * FROM orders` 看起来是全量，但如果：

- 表按时间分区，只查了近 30 天；
- 数据同步任务每天跑，昨晚失败，今天缺一天；
- 有软删除 `deleted_at`，但没加过滤条件；

你拿到的就是一份**有偏样本**，而且没有任何报错。读完之后必须确认：

```sql
SELECT MIN(created_at), MAX(created_at), COUNT(*) FROM orders;
```

再和"应该有多少"对一下。对不上就先别分析。

### 读进来后的五分钟检查

```python
df.shape                      # 多少行多少列
df.head(5)                    # 长什么样
df.dtypes                     # 类型对不对
df.isna().sum()               # 每列缺多少
df['id'].is_unique            # 主键唯一吗
df.duplicated().sum()         # 整行重复有多少
```

这五行能挡掉大部分"后面越算越不对"的情况。**先花五分钟，省后面两小时。**

### SQL 侧的同一件事

```sql
SELECT COUNT(*) AS rows,
       COUNT(DISTINCT order_id) AS orders,
       MIN(created_at) AS first_at,
       MAX(created_at) AS last_at
FROM orders
WHERE deleted_at IS NULL;
```

`rows` 与 `orders` 不相等，说明一行不是一笔订单；时间范围不对，说明取数条件有问题。**先确认数据形状，再写业务查询。**

## 常见误区

### 误区：`dtype` 不重要，能算就行

**你以为**：反正 pandas 会自动转换。
**其实**：它不会自动转，只会让字符串参与运算时报错，或者更糟——把数字当字符串排序，把版本号当小数。
**怎么验证**：`df.dtypes` 里出现 `object` 的列，如果是金额、日期、id，逐个确认是否该转。

### 误区：`errors='coerce'` 之后没有报错就说明数据干净

**你以为**：没抛异常就是对的。
**其实**：`coerce` 把错误变成 `NaN`，异常被吞掉了。必须统计新增缺失数，再抽样看那些行原本是什么。
**怎么验证**：转换前后各数一次 `notna()`，差值就是被吞掉的行数。

### 误区：SQL 查出来的就是全量

**你以为**：没有 `LIMIT` 就是全部。
**其实**：分区、同步延迟、软删除、权限过滤都会让结果少一截，而且查询本身完全成功。
**怎么验证**：`COUNT(*)` 与业务方预期对比；再看 `MAX(created_at)` 是不是"昨天"。
