## 这一关在解决什么

两个系统各有一份数据，要放在一起看，就要 join。join 的问题不在语法，而在**行数会变**：

- 一对多连接让左表的行被复制，金额被重复计算；
- 键的类型或写法不一致，连接"成功"但匹配率很低；
- 空值不等于空值，匹配不上。

这一关给一套 join 前必做的检查。

## 讲解

### 四种连接，先想清楚要保留谁

| 类型 | 保留 | 典型用途 |
| --- | --- | --- |
| inner | 两边都有的 | 只看有订单的用户 |
| left | 左表全部 | 所有用户 + 他们的订单（没订单的为空） |
| right | 右表全部 | 较少用，通常换成 left 调换顺序 |
| outer | 两边全部 | 对账、找只在一边出现的记录 |

pandas 对应 `how='inner' / 'left' / 'right' / 'outer'`；SQL 是 `JOIN` / `LEFT JOIN` / `RIGHT JOIN` / `FULL OUTER JOIN`。

**默认 `merge` 是 inner**。如果你想要"所有用户，包括没下单的"，忘了写 `how='left'` 就会悄悄少掉一批人。

### 连接前先看键的基数

```python
orders['user_id'].is_unique      # False：一个用户多笔订单
users['user_id'].is_unique       # True：用户表主键
```

这就是一对多：`users.merge(orders, on='user_id')` 之后，行数等于订单数，**用户表里的属性（城市、注册时间）会被复制到每一笔订单上**。

这通常是想要的；但如果你先按用户聚合了金额，再 join 订单明细，金额就会被重复加。

一个自检：

```python
before = len(left)
merged = left.merge(right, on='key', how='left')
print(before, len(merged))   # 变多了？说明右表键不唯一
```

pandas 的 `validate` 参数能直接挡住意外的一对多：

```python
left.merge(right, on='key', how='left', validate='one_to_one')
# 报错：Merge keys are not unique in right dataset
```

不确定时先写 `validate='one_to_many'` 或 `'many_to_one'`，比事后查金额对不上省事。

### 键的写法必须先统一

```text
users.user_id      orders.user_id
-----------------  ----------------
"U001"             "U001 "        ← 尾部空格
1001               1001.0         ← 一边字符串一边浮点
"北京"             "北京市"
```

join 不会报错，只会匹配不上。连接前统一：

```python
users['user_id'] = users['user_id'].astype('string').str.strip()
orders['user_id'] = orders['user_id'].astype('string').str.strip()
```

然后检查匹配率：

```python
merged = left.merge(right, on='key', how='left', indicator=True)
merged['_merge'].value_counts()
```

`indicator=True` 会加一列 `_merge`，取值 `both` / `left_only` / `right_only`。**匹配率异常是键没对齐的最快信号。**

### 空值不参与等值匹配

SQL 里 `NULL = NULL` 的结果是 `NULL`（不是 true），所以空键的行 join 不上。pandas 的 `merge` 也把 `NaN` 视为不相等。

如果业务上"空"表示同一类（比如"未知渠道"），连接前先填成一个明确的值：

```python
df['channel'] = df['channel'].fillna('unknown')
```

但要想清楚：把所有未知渠道并成一类，可能把不同来源混在一起。

### 过滤条件放 WHERE 还是 ON

```sql
-- 左连接 + ON 里过滤：保留所有用户，只连接「已支付」订单
SELECT u.user_id, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.user_id AND o.status = 'paid';

-- 左连接 + WHERE 里过滤：实际变成 inner join 的效果
SELECT u.user_id, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.user_id
WHERE o.status = 'paid';
```

第二条会把"没有已支付订单"的用户过滤掉（因为 `o.status` 是 `NULL`，条件不成立）。**左连接要保留左表全部时，右表的过滤条件必须写在 `ON` 里。**

### 对账：连接后必做的一步

```python
print('左表金额', left['amount'].sum())
print('连接后金额', merged['amount'].sum())
```

如果金额被放大，说明右表键不唯一导致行复制。这不是"join 有 bug"，而是一对多连接的正常结果——只是你的汇总口径要改成"先去重再连接"，或者按右表粒度重新算。

## 常见误区

### 误区：join 之后行数不变

**你以为**：连接只是把列拼过来。
**其实**：一对多、多对多都会增加行数；多对多还会做笛卡尔积。行数变了，金额、计数都会被放大。
**怎么验证**：连接前后各 `len()` 一次；不相等就查右表键是否唯一。

### 误区：没报错就说明连接对了

**你以为**：代码跑通、结果有数，就是对的。
**其实**：键类型不一致时 join 完全成功，只是大部分行匹配不上，结果里大量空值。
**怎么验证**：`indicator=True` 看 `left_only` 的占比；超过预期就查键。

### 误区：`NULL` 会和自己匹配上

**你以为**：两边都是空，应该算同一条。
**其实**：等值比较里 `NULL` 不成立。需要匹配空值时，要么填成明确的值，要么用 `IS NULL` 单独处理。
**怎么验证**：构造两行键为 `NaN` 的表做 merge，看结果行数。
