## 先把结论摆出来

**`ctx` 不是一个全局单例，而是一棵"上下文树"。** 根上下文（root）是所有插件共享的；每个插件拿到的 `ctx` 是它自己那一层，通过原型继承父层。注册、服务、事件都落在"当前这一层"上。

这带来一个关键能力：**作用域隔离**。`ctx.isolate('shell')` 能让一块子树拥有自己的 `shell` 实现，跟父层、跟别的子树互不干扰。同一个进程里，"全局的"和"只对某个 agent 生效的"就是靠这个区分开的。

## 上下文是个"代理"

`ctx.name` 这种读法背后不是普通字段，而是一次**服务解析**：`ctx` 是一个代理，读属性等于问"这个作用域里有没有叫 name 的服务"。所以同一行 `ctx.shell`，在不同作用域的上下文里可能解析到不同的实现——这正是隔离的基础。

三个改变作用域的方法，都**不改父层**，只返回子上下文：

```ts
// 1. extend：加一点元数据，其它照旧继承
const child = ctx.extend({ agentId: 'a1' })

// 2. isolate：给某个服务名开独立作用域
const isolated = ctx.isolate('shell')   // 这里的 ctx.shell 可换成别的实现

// 3. intercept：为下面的插件合并某个服务的配置
const withConfig = ctx.intercept('shell', { timeoutMs: 30_000 })
```

传同一个 `label` 给两次 `isolate`，两块子树就加入同一个隔离作用域——这就是第 5 关说的"两个分组各用各的 shell 却互不串味"的底层做法。

## 读、写、提供：三个容易混的动词

- **`ctx.get('name')`**：只读，不要求 `inject`。默认 `strict: true`，只返回"提供方当前处于 active"的实现，否则 `undefined`。
- **`ctx.provide('name', value)`**：注册一个归当前 fiber 所有的服务，返回注销函数。fiber 卸载时自动撤销。
- **`ctx.set('name', value)`**：**覆盖**一个已经提供的服务的值。只有提供它的那个 fiber 才允许 set，给没提供的名字 set 会抛异常。

记忆口诀：`provide` 是"开一个服务"，`set` 是"给已有服务换值"，`get` 是"读一下有没有"。

## 为什么要这棵树

因为一个真实应用里，"谁的作用域"差别很大：

- **全局的**能力（比如模型适配器、文件系统）应该全应用共享。
- **单个 agent 的**能力（比如它专属的工具集、它的临时配置）只能对它自己生效。

如果所有注册都落在同一个扁平空间里，"给 agent A 加的插件"就会漏给 agent B。有了上下文树，`agent.ctx` 这一层上的注册天然只属于那个 agent——这也是 DSH 能做"每个会话一套能力"（agent preset）的原因。

## 常见误区

### 误区：`ctx` 就是一个全局对象，在哪儿拿到都一样

**你以为**：反正都是 `ctx`，A 插件和 B 插件拿到的应该是同一个。

**实际上**：它们拿到的是同一棵树上的**不同层**，各自继承父层、互不覆盖。在 A 的上下文里 `provide` 的服务，不一定在 B 的上下文里可见（取决于是否同一作用域）。

**所以**：注册时要问"我这个东西该落在哪一层"——全局共享，还是只对当前插件/当前 agent 生效。落错层，要么漏给不该拿的人，要么别人看不到。

### 误区：隔离就是"复制一份"，会很重

**你以为**：`isolate` 是把服务复制一份，越用越占资源。

**实际上**：隔离只是"换一个解析标签"，服务的实现对象还是那一份，只是读它的时候走了不同作用域。它解决的是可见性问题，不是复制问题。

**所以**：需要"同一能力、不同实现/不同配置"时，用隔离；需要"同一份实现多处用"时，本来就不需要隔离。
