## 先把结论摆出来

**子智能体就是"另一个 agent"，委派走 `ctx.subagents` 这个服务。** 后端可以是本进程里的新 agent（`spawn`）、带父历史的分叉（`fork`），也可以是外部执行（Claude Code、Codex、ACP、SDK）。

每个本地子智能体有自己的**持久会话**，最多有一个在线 activation。它跑完把结果交回父级，父级可以选择"通知模型"还是"只拿结果"。

## 两种本地委派：spawn 与 fork

- **spawn**：开一个全新的子会话，从零开始干活。
- **fork**：把父的"已完成轮次"历史种子给子会话，子继承父的上下文再往下走。

模型侧看到的就是两个委派工具（`tool-subagent`），后端由 `ctx.subagents` 按名字选。外部后端（Codex / Claude Code 等）只提供一个"执行句柄"，不接受后续多轮消息。

## 结果怎么回给父级

每条委派是一个 **activation**（执行期记录），拿到的对象里有 `result`（最终结果的 promise）和 `dispose()`（取消并释放）。结果交付有两种：

- `delivery: 'parent'`：把结果作为一条消息**通知模型**，模型能看到"子任务完成了，结果是这样"。
- `delivery: 'caller'`：只把结果**返回给调用方**（比如 workflow），不往父模型注入消息。

生命周期事件是 `subagent/start` 与 `subagent/end`，按"发起委派的父级"做作用域过滤——所以一个父级的监听者只会看到自己的委派。

## 父子之间还能说话

本地子智能体支持相邻通信：`sendMessage` 可以把消息发给**直接父级或直接子级**。

- 目标正在跑：在最近的步骤边界插入（引导）。
- 目标空闲：叫醒它开始新一轮。
- 目标不在线：从持久化里**冷恢复**再送。

外部执行不接受后续消息。`interrupt` 可以打断一个正在跑的子，但会保留它已经发布的成果和子级。

## Agent Teams：更"多智能体"的形态

实验性的 `ctx.agentTeams` 在"可继续子智能体"之上加了：持久 roster（谁在队里）、共享任务 DAG、以及点对点的 inbox 消息。它适合把一件大活拆成几块并行推进，但属于进阶能力，默认不启。

## 常见误区

### 误区：子智能体就是一个函数调用

**你以为**：委派就是把任务丢给一个函数，跑完返回值。

**实际上**：每个本地子智能体是一个有自己会话、自己的 turn/step、自己的工具集的完整 agent，还能被中途引导、被中断、被再次恢复。它比"函数调用"重得多，也因此能承担真正独立的子任务。

**所以**：简单计算别开子 agent；需要"另一个上下文里独立跑一段、带自己的工具与回忆"时才委派。

### 误区：多智能体一定比单智能体强

**你以为**：拆成多个 agent 一起干，总比一个大 agent 强。

**实际上**：每个子 agent 都有独立的上下文、成本和收尾开销；协调不好反而更乱、更贵。多智能体的价值在"任务能清晰切块且彼此少依赖"，不是数量越多越好。

**所以**：先问"这活能不能一个 agent 干完"；不能，再考虑拆，并想清楚结果怎么汇总。
