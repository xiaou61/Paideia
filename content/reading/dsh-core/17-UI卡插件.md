## 先把结论摆出来

**想在对话里显示一张自定义卡片，不是去改前端页面，而是凑齐三件套：**

1. 一族**可回放的事件**（比如 `review/start`、`review/progress`、`review/end`）；
2. 一个 **ConversationNodeDefinition**，把事件折叠成"一张卡的状态"；
3. 一个 **React 渲染器**，注册到 `conversation.chat.node` 这个 slot 上。

卡片内容必须能从事件历史重放出来——这和前面"模型可见即已记录"是同一个道理，只是这次约束的是"**客户端可见即已记录**"。

## 第一步：先定一族事件

卡片的数据来源必须是事件，而不是某个前端变量。所以先设计事件（并合并进 `SessionEventMap`），每条都带一个**稳定业务 id**（这里叫 `reviewId`）：

```ts
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'review/start':    { reviewId: string; turn: number; step: number; title: string }
    'review/progress': { reviewId: string; turn: number; step: number; completed: number }
    'review/end':      { reviewId: string; turn: number; step: number; summary: string }
  }
}
```

为什么必须有稳定 id：客户端回放时，要从一堆事件里认出"这几条属于同一张卡"。只靠"最近一个没完成的"去猜，页面上会有多张卡时就全乱了。

## 第二步：写 Definition

Definition 是一个对象，关键就四个函数：

- `match(event)`：**身份提取器，不是折叠**。它只返回这张卡属于哪个 `(kind, id)`、是 `start` 还是 `update`。
- `start(context, match)`：用第一条事件初始化 State。
- `update(context, match)`：后续事件更新 State（返回新的不可变对象）。
- `buildViewNode(context)`：把 State 变成渲染器可以直接用的数据（`key` 要稳定，`anchorSeq` 选能排序的证据）。

```ts
const reviewDefinition: ConversationNodeDefinition = {
  kind: 'review-job',
  target: 'chat',
  match: (event) => {
    if (event.type === 'review/start') return { id: String(event.data.reviewId), role: 'start' }
    if (event.type === 'review/progress' || event.type === 'review/end') {
      return { id: String(event.data.reviewId), role: 'update' }
    }
    return null
  },
  start: (_ctx, match) => ({
    title: match.event.data.title, completed: 0, status: 'running',
  }),
  update: (ctx, match) =>
    match.event.type === 'review/end'
      ? { ...ctx.state, completed: 100, status: 'completed', summary: match.event.data.summary }
      : { ...ctx.state, completed: match.event.data.completed },
  buildViewNode: (ctx) => ({
    key: ctx.key, kind: 'review-job', id: ctx.id, target: 'chat',
    anchorSeq: ctx.start?.event.seq ?? 0,
    location: ctx.start?.location ?? { kind: 'unresolved' },
    visibility: 'visible',
    data: ctx.state,
  }),
}
```

如果同一类事件也会被内置的通用 Definition 匹配（比如"问题回答"），就给它加 `exclusive: true` 认领，避免同一事件被两方各渲染一次。

`publication` 控制发布节奏：结构/终态用 `immediate`，高频进度用 `animation-frame`，只攒着不显示用 `none`。

## 第三步：注册渲染器

渲染器只读 `node.data`，不扫事件、不碰会话——这保证它便宜、可回放：

```tsx
function ReviewNodeView({ node }) {
  const text = node.data.summary ?? `${node.data.title}: ${node.data.completed}%`
  return <p>{text}</p>
}

export const inject = ['uiConversation', 'slots']
export function apply(ctx) {
  ctx.uiConversation.events.register(reviewDefinition)
  ctx.slots.inject('conversation.chat.node', () =>
    ctx.slots.register({ name: 'conversation.chat.node', key: 'review-job' }, ReviewNodeView),
  )
}
```

## 常见误区

### 误区：做卡片就是写个 React 组件塞进页面

**你以为**：在对话页加个组件，把数据塞进去就行。

**实际上**：DSH 的对话是"事件流 → 定义折叠 → target node → 渲染器"的分层。只写组件，刷新或重连后卡片就没有可重放的数据来源了。真正让它"活"的，是事件族 + Definition；组件只是最后那层薄薄的呈现。

**所以**：先设计事件和 Definition，再写渲染器。渲染器越薄越好。

### 误区：match 里可以直接把事件算成最终状态

**你以为**：`match` 收到事件，顺手把该更新的都更新了最省事。

**实际上**：`match` 会被每条事件调用一次，它必须足够轻（只认身份），不能扫描整个窗口或做重计算——否则每次增量都会变慢。折叠是 `start`/`update` 的职责，且要能按日志顺序确定性重放出同一结果。

**所以**：`match` 只认 id，`update` 才改 State；State 里只放累计事实，不塞临时引用。

## 全套收尾

到这里，**十七关**就走完了。把它们分成三层看：

- **地基（1–6）**：插件、服务、effect、事件、配置、工具接入——知道 DSH 是怎么拼起来的。
- **往里钻（7–12）**：上下文作用域、能力 seam、请求旅程、工具流水线、提示词与会话、扩展点地图——知道每一环的内部机制。
- **加餐（13–17）**：会话持久化、子智能体、沙箱权限、换模型、带 UI 卡的插件——把这套机制用到五个真实场景。

贯穿始终的还是那一句：**DSH 把"能力"和"装配"彻底分开**。插件声明贡献，配置决定组合，一切注册可撤销。理解了这个，你不用记住每一关，只要遇到问题时会问：**这是哪个服务、哪个事件、哪个配置项？**

这，就是从零了解 DSH 核心真正想留给你的东西。
