## 我拦了请求，模型没换

需求很普通：这个会话跑在 `deepseek-official/deepseek-flash` 上，我要它换成另一个 provider 的模型。第一反应是在请求要发出去那一刻改一下配置：

```ts
ctx.on('agent/request', async (payload, next) => {
  const config = await next()
  return { ...config, provider: 'my-provider', model: 'my-model' }
})
```

模型没换。翻到 `packages/core/agent/src/runtime-types.ts:352-366` 才看见两句话：

> Replace the frozen call configuration. a replacement may adjust controls but must keep the provider, model, and reasoning effort selection.
> `@deprecated` Retained for existing listeners; do not add new listeners.

第一句是行为约定：`next()` 交出来的是**已经冻结**的调用配置，能调的是别的控制参数，provider / model / reasoning effort 三项必须原样留着。第二句更直接——这个事件已经废弃，注释写着不要新增监听器。

我错在把 waterfall 当成「能改一切」。它不是。waterfall 能改的只是那一次请求里**允许你动的旋钮**，而模型选择是挂在**步骤**上的，早在这之前就定了。

以下内容都是按代码读出来的，未在运行时验证。版本 `0.2.2-rc.5`，commit `2e39e70`，行号对得上这个树。

## 换模型是一次记账，不是一次拦截

正确的位置是一个方法调用：

```ts
agent.model.select({ provider: 'my-provider', model: 'my-model' })
```

`packages/core/agent/src/model-selection.ts:113-116` 里它的全部工作是往会话日志追加一条 `model/selection`，一个字段都不碰请求。生效时机写在 `packages/core/agent/README.zh.md:52`：从下一个尚未开始准备的步骤开始；已经准备好的步骤连同它的重试保留当时捕获的选择（`runtime-types.ts:347` 的 `retained across retries`）。

这个设计不是随手定的。`docs/architecture.zh.md:134` 那句「模型可见即已记录」是硬约束：每个模型请求都要能从日志重建。所以「换模型」这种会改变模型所见内容的事，只能先进日志、再由日志投影出去，不能是某次请求上的临时覆盖。

它还有一个能直接观察到的后果：换完路线之后，模型会在历史里读到一条 user 消息（`model-selection.ts:140`）：

```text
[model changed: assistant turns above this point were generated by
 deepseek-flash; the session continues with my-model]
```

只有 provider / model 真的变了才追加；只改 reasoning effort 不追加（同文件 `150-153`）。也就是说，换模型这件事在语义上被记成了一句话写进对话，而不是一个悄悄生效的开关。

顺带把配置那条路也排除掉：`packages/bundle/base/cordis.patch.yml:90-94` 里那行 `agent-default-model` 的注释是 "the default for Agents created by entry points. consumers read it at creation time"。它只在**创建 agent 时**读一次，改了对已经跑起来的会话没有任何作用。这三个落点（请求、日志、配置）管的是三个不同时间点，选错就会出现「改了没反应」。

## 症状 → 先看哪

地图的价值不在「有这张表」，在于它能替你把「已经跑完的」和「还没开始的」分开。下面每一行右边一列，是这个挂点为什么不能换成隔壁那个。

| 手上的症状 | 先看哪 | 为什么不是隔壁那个 |
| --- | --- | --- |
| 只想把每次工具返回记进日志，不改结果 | `tools/result`（emit，拿到的是冻结快照，监听器抛错被包含） | `tools/post-execute` 是 waterfall，你在结果定稿前动它，动的是别人吃到的结果 |
| 想拒掉某一次工具调用 | `tools/pre-execute` 返回 `deny` | `tools/result` 发生在跑完之后，拦不住；`ask` 在没有审批支持时会**变成**拒绝，不是先放行再问 |
| 想给结果补一段再喂回模型 | `tools/post-execute`（accept / replace / enrich / block） | `tools/execute` 只允许换 `exec.signal`，调用身份不可变，改不了内容 |
| 想给工具加超时或重试 | `tools/execute` | 它在 dispatch 之后，拿不到「还没开始跑」的时机；`tools/pre-execute` 手里又没有进程 handle |
| 想让活着的会话换模型 | `agent.model.select()`，再在 `agent/pre-step` 里读 `modelSelection` | `agent/request` 的契约禁止改 provider / model，且已废弃；改 patch 默认值只影响之后创建的 agent |
| 想在轮次快结束时兜住一个失控轮次 | `agent/turn-stopping`（serial）里 `agent.cancel()` | 它不是「停止轮次」的开关：它跑在轮次即将关闭的那条边界上，你想让轮次**继续**反而是在这里 `steer` |
| 想换掉 shell 的执行实现 | 换 `shell` 那一行的插件（一个 `ShellExecutor` 子类，如 `packages/shell/bash-local/src/index.ts:97`） | `ctx.shell` 上没有 register 方法；一个 context 里加载第二个会抛（`packages/shell/shell/src/index.ts:38-40`）。`registerBackend` 是 `ctx.terminals` 的，见 `packages/experimental/terminal-panel/src/index.ts:34` |

表格最后一行是最容易被文档带偏的：`docs/architecture.zh.md:157` 写的是「注册 `ctx.shell` 后端」，而代码里根本没有这个注册动作——所谓「注册后端」是把提供 `ctx.shell` 的那个插件换掉。

## 边界：三种「挂不上去」

- **一个 context 只能有一份 shell 实现。** `ShellExecutor` 的注释写得很直白：加载第二个会抛，这是 cordis 对重复服务的标准行为。所以「同时挂两个 shell 后端」不是配置没写对，是这里没有这个位置。要两个互不影响的实现，得在组合层用 `isolate` 给组各自一份服务实例（`docs/cordis-tutorial/06-composition-and-hmr.zh.md:21`）。
- **已经开始的步骤改不了路线。** `select()` 从下一个未准备的步骤生效；当前步已经捕获了选择。指望在工具调用的中间换模型，只会看到下一条请求才变。
- **`agent/request` 有洞。** 迁移说明 `docs/upgrade-guide/v0.2.1-alpha.4/session-model-selection/guide.zh.md:16` 明写：压缩这类辅助调用不分发该事件。所以想「统一干预所有模型调用」的监听器天生漏一块。

## 跑一遍

想确认某个 `agent/*` 事件到底是能改、只能看、还是要排队，不用猜，直接从契约上把 `@mode` 注释和签名一起抠出来。在 DSH 检出根目录存成 `probe-events.mjs` 再 `node probe-events.mjs`：

```js
import fs from 'node:fs'
const src = fs.readFileSync('packages/core/agent/src/runtime-types.ts', 'utf8')
const out = []
let mode = '?'
for (const line of src.split('\n')) {
  const m = line.match(/@mode\s+(\w+)|'(agent\/[a-z/-]+)'\(this/)
  if (!m) continue
  if (m[1]) mode = m[1]
  else out.push(`${m[2].padEnd(26)} ${mode}`)
}
console.log(out.join('\n'))
```

`0.2.2-rc.5` 上的实际输出：

```text
agent/created              serial
agent/disposed             emit
agent/status               emit
agent/inbox/inserted       emit
agent/inbox/claimed        emit
agent/inbox/discarded      emit
agent/pre-step             waterfall
agent/request              waterfall
agent/request-error        waterfall
agent/assistant-stream     emit
agent/turn-stopping        serial
agent/error                emit
```

读法只有三条：`emit` 只能看，监听器改不了任何东西；`waterfall` 能改，但必须 `await next()` 把链交下去，能改的范围由各自的注释限定；`serial` 是排队执行，顺序有意义，但别拿它当「一定会拦住」。

再往下捞一层，验证注释和实现是否一致：`packages/core/agent-loop/src/agent.ts:402` 就是 `await this.dispatch.serial('agent/turn-stopping', { turn, signal })`，和上面表里的 `serial` 对得上。这一条我核过，其余事件我没有逐个追到分发点。

## 还差的

- **没有运行时验证。** 全部结论来自源码、README 与升级说明，我没有真起一个 harness 去 `select()` 之后翻日志确认它排在第几个事件。`model/selection` 之后你在 UI 上看到什么顺序，我说不出来。
- **只覆盖了 Host 侧。** 客户端那几条扩展点（`ConversationNodeDefinition`、`settings.section`、slot ledger）在 `docs/architecture.zh.md:166-167`，本文一行没讲。
- **`isolate` 只到文档口径。** 「两个组各看一个 shell 提供方」是教程说的，我没验证这种情况下 HMR 重载会发生什么。
- **「加载第二个 ShellExecutor 会抛」没实测。** 那是 `packages/shell/shell/src/index.ts:38-40` 的注释，我没真的加载两次去接那个错误。
- **表里少了半张。** `ctx.webhookRuntime`、`ctx.goals`、`ctx.sessionTitle`、`SessionEventMap` 扩展这几行都在这张图上，本文只挑了和「拦截」有关的讲，换成会话持久化或后台任务时会用到另外半边。
