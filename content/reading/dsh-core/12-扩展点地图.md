## 先把结论摆出来

**改 DSH 不用改内核——因为它没有"需要打补丁的特权内核"。** 每一处扩展都挂在**已经文档化的扩展点**上：某个服务、某个事件、或某个配置项。你要做的第一件事，不是想"改哪段代码"，而是查一张地图：**这个需求，属于哪个服务或事件？**

## 一张精选的扩展点地图

| 我想…… | 挂在哪里 |
| --- | --- |
| 加一个模型提供方 | 在 `ctx.llm` 上注册适配器 |
| 给模型加一种能力 | 在 `ctx.tools` 上注册（schema 自动进提示词） |
| 让某个会话有不一样的能力集 | 组装 agent preset，服务行用 `isolate` |
| 加 shell 执行 / 换个执行后端 | 注册 `ctx.shell` 后端 |
| 加持久终端 | 注册 `ctx.terminals` 后端 + `tool-terminal` |
| 加一条不用模型轮次的命令 | 在 `ctx.commands` 上注册 |
| 管理后台任务 | 在 `ctx.jobs` 上注册 |
| 加文件访问或文件策略 | 注册 `ctx.fs` 提供方，或监听 `fs/*` 事件 |
| 限制启动的进程 | 用 `ctx.sandbox` 后端 |
| 拦截一次请求 / 工具 / 轮次 | 用对应的 `agent/*`、`tools/*` 事件；`agent/turn-stopping` 停轮次 |
| 加一段模型可见的上下文 | `agent.inject()`，落到下一次获准的请求 |
| 加持久会话状态 | 扩展 `SessionEventMap`，从日志渲染与回放 |
| 让注册只对单个 agent 生效 | 用该 agent 的 `agent.ctx` |

不用背全表，**记住这张表存在**就够了：遇到需求先来查，而不是先动代码。

## 三选一：服务、事件、还是新插件

- **要"用一项能力"** → 走**服务方法**（`ctx.xxx.do()`）。直接、可类型检查。
- **要"拦一下 / 加策略 / 观察"** → 走**事件**（尤其 waterfall）。不知道有谁在听，也不用改别人。
- **要"换实现 / 组装不同能力"** → 走**配置项 + 插件**（改 `cordis.yml` / patch 层）。

口诀：**能力调用找服务，插一脚找事件，换零件找配置。**

## 边界：什么时候不该做成插件

插件化不是免费的。多一个插件，就多一个装配点、一条依赖、一份需要被理解的配置。所以：

- **一个功能没有第二种实现、也不会被替换** → 直接写成普通代码，别拆插件。
- **一个简单的工具** → 一个文件写完，不用拆成"定义/提供方/消费方"三角色（第 8 关）。
- **只是想过一下手** → 先看现有事件能不能听，别急着新造一个服务。

判断标准始终是那一句：**将来有没有可能把它换成别的、或者独立演进？** 有，才值得插件化。

## 常见误区

### 误区：想改行为，就得去改"核心代码"

**你以为**：有些需求太底层，只能改内核。

**实际上**：DSH 的设计就是"没有特权内核"，一切都能从配置替换、从事件扩展。你要改的东西，大概率已经是一个服务或事件，只是你还没找到它。

**所以**：先查扩展点地图。真找不到，再考虑"是不是该加一个新的服务/事件"——那也是挂在旁边，而不是改现有内核。

### 误区：插件越多越"架构化"

**你以为**：把每样东西都做成插件，系统就更灵活。

**实际上**：过度的插件化会让"这座应用"变得没人能一眼看懂（还记得第 1 关和第 8 关说的"不要预防性拆分"）。灵活来自**边界切在能替换的地方**，不是来自数量。

**所以**：默认写直的代码；只有当替换/演进真的会发生，才把它变成插件或 seam。

## 主线小结：十二关

主线十二关走完，把它压成一句话：

> **DSH 把「能力」和「装配」彻底分开**——插件只声明自己贡献什么，配置决定哪些上场。

按这个视角回看：

1. **插件**（`apply(ctx)`）：没有主程序，插件就是构成应用的那一块。
2. **服务**：能力登记成 `ctx.<key>`，认名不认实现，`inject` 决定加载顺序。
3. **effect**：每个注册都可撤销，所以卸载与热更新才安全。
4. **事件**：五种分发让插件"不认识对方也能插一脚"，waterfall 负责拦截与委托。
5. **配置与组合**：`cordis.yml` 就是应用，schema 先校验，`id` 决定热更新，patch 层只改自己那行。
6. **工具**：一个小插件 + `ctx.tools` 注册，真实 Agent 只是更多这样的插件。
7. **上下文**：`ctx` 是一棵作用域树，`isolate` 让"只对这个 agent 生效"成为可能。
8. **seam**：定义 / 提供方 / 消费方三角色，换提供方就换掉整个能力。
9. **请求旅程**：turn → step → 模型 → 工具，`agentLoop` 只负责串服务。
10. **工具流水线**：注册只是入场，策略、审批、结果修剪都在流水线上。
11. **提示词与会话**：模型看到的，是注册出来的提示词 + 日志投影的历史，且可见即已记录。
12. **扩展点地图**：改行为先查地图，用服务/事件/配置去挂，而不是改内核。

主线到这里就完整了。接下来还有五关"加餐"，把这套机制落到五个具体场景：会话持久化、子智能体、沙箱权限、换模型实战、带 UI 卡的插件。
