## 先把结论摆出来

**一次对话由若干 turn 组成，一个 turn 又由若干 step 组成。** 一个 **step** = 一次模型请求 + 它发起的工具调用；一个 **turn** = 用户说一句话之后，一直到"不再欠任何工作"为止。

驱动这一切的是 **agent loop**（`ctx.agentLoop`）。它本身不知道模型是谁、工具有哪些，只是把 `ctx.llm`、`ctx.tools`、`ctx.systemPrompt`、`ctx.sessions` 这几个服务串成一条流水线，并在中间留出可以拦截的事件点。

## 走一遍：从输入到回答

简化成 8 步，去掉细节，只留主干：

1. **领输入**：用户的消息进 inbox，loop 在 `turn/start` 领取它。
2. **组装提示词**：`ctx.systemPrompt` 把提示词段落和工具 schema 拼成这次请求要用的系统提示。
3. **准入判断**：`agent/pre-step` 是一个 waterfall，可以改写或拒绝这批输入；拒绝就关掉一个"不含 step"的轮次。
4. **开始一步**：`step/start`。
5. **决定怎么发**：`agent/request` 也是一个 waterfall，插件可以替换这次模型调用的配置（用哪个模型、什么参数）。
6. **记消息、派生历史**：把接纳的用户消息写进会话，再从**会话日志**里派生"模型该看到的对话历史"。
7. **流式请求**：`llm/stream` 把请求交给模型适配器，边生成边流出。
8. **工具或多走一步**：模型说"要调工具"，就走工具流水线把结果拿回来；只要还欠工具结果、或者又有新输入，就回到第 4 步再走一个 step。都不欠了，`turn/end` 收尾（`agent/turn-stopping` 会在这里把要停的轮次停掉）。

一句话记：**step 解决"这一轮问模型要什么"，turn 决定"一共问几轮、什么时候算完"。**

## 谁在开车：四个服务的分工

| 服务 | 管什么 | 你能改什么 |
| --- | --- | --- |
| `ctx.agents` | 活跃 agent 的句柄与创建/恢复 | 新建、fork、恢复一个会话 |
| `ctx.agentLoop` | 具体的主循环（唯一实现） | 一般不改，靠事件扩展 |
| `ctx.llm` | 模型适配器注册表 | 换模型 / 加提供方 |
| `ctx.tools` | 工具注册与执行流水线 | 加工具、加策略 |
| `ctx.systemPrompt` | 提示词段落与工具 schema 组装 | 加一段提示词 / 变量 |
| `ctx.sessions` | 只追加的会话日志 | 扩展会话事件、加投影 |

关键点：**loop 不依赖任何具体实现，只依赖这些服务**。所以你可以换模型、加工具、改提示词，而不用碰 loop。

## 扩展点：哪些能拦、怎么拦

- `agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 都是 **waterfall**：观察型的监听者必须 `next()` 往下委托，有决策权才短路（第 4 关的纪律）。
- `agent/turn-stopping` 是 **serial** 事件：按顺序问"这个轮次该停吗"，第一个给出结论的说话。
- 想"这次请求注入一点额外上下文"，用 `agent.inject()`，它会落到下一次获准的请求里，而不是硬塞进当前这轮。

## 常见误区

### 误区：模型一轮就答完了

**你以为**：用户问一句、模型答一句，就是一个来回。

**实际上**：模型可能先要调几个工具、看到结果再继续，才给出最终回答。这中间的每一步都是一次模型请求（一个 step），全部合起来才是一个 turn。对话越长、工具越多，step 越多。

**所以**：排查"怎么这么慢/这么贵"时，要看**一共走了几个 step**，而不是只看"问了一句"。

### 误区：想影响模型行为，就得改主循环

**你以为**：要让模型换个说法、换套工具，得去改 agent loop 的代码。

**实际上**：loop 只负责串流程。换模型改 `ctx.llm` 的提供方；加能力注册到 `ctx.tools`；改提示词注册到 `ctx.systemPrompt`；拦截请求监听 `agent/request`。没有一项需要碰 loop。

**所以**：先找"该挂的服务或事件"，而不是"该改的循环"。
