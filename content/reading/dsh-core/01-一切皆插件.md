## 先把结论摆出来

**DSH 里没有"主程序"这种东西。** 你找不到一个 `main()` 把模型、工具、会话统统 new 出来。它能跑起来，是因为一份配置列出了一串插件，框架按顺序把它们挂上去；每个插件只干一件事：用框架给的 `ctx` 把自己的贡献登记进去。

一个插件最常见的样子，就是一个导出 `apply` 的函数：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
```

没有框架启动代码，没有 `new`，没有"注册表初始化"。**插件描述"我贡献什么"，配置描述"装哪些 plugin"。**

## 为什么是这个设计

如果把"能力"和"装配"写在一起，那么每换一个模型、加一个工具，都要去改那段启动代码，改到最后没人敢动。DSH 反过来做：

- **插件只声明自己的贡献。** 它不知道自己被装在哪个应用里，也不知道旁边还有谁。
- **配置负责组合。** 哪几个插件上场、以什么顺序、给什么参数，全写在一份 YAML 里。

这条分工带来一个直接好处：**同一份插件代码，可以被不同的应用、不同的部署形态复用，只改配置。** 你在 DSH 里看到的桌面版、无界面版、Web 版，本质都是"同一批插件 + 不同的配置层"。

## 插件是怎么被装上的

一份 `cordis.yml` 就是一个"插件清单"，每一项是一个 `name`（模块路径或 NPM 包名），框架把它挂上去：

```yaml
- name: './hello.ts'
```

启动时发生三件事：

1. 启动器创建一个根 `Context`，挂上 **Loader** 插件。
2. Loader 读 `cordis.yml`，解析 `./hello.ts`，把它当子插件挂上。
3. 框架调用你的 `apply(ctx)`。

## 插件的三种形态

函数最常见，但框架接受三种写法：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

// 1. 函数插件：导出 apply
export function apply(ctx: Context) {}

// 2. 对象插件：一个带 apply 方法的对象
export const objectPlugin = {
  name: 'object-plugin',
  apply(ctx: Context) {},
}

// 3. 类插件：Service 的子类（第 2 关讲它怎么对外提供服务）
export class MyService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'myTutorialService')
  }
}
```

在你需要**对外公开一项能力**之前，一直用函数形态就够了。对象形态只是把 `apply` 收进一个对象里，方便带别的元数据；类形态是为了做"服务"——那是下一关的事。

## 三个容易踩的细节

### 1. `name` 只是显示名，不是身份

导出的 `name` 只在诊断信息里用来标识"这是哪个插件"，它不参与依赖解析，也不要求唯一。真正决定"装哪一个"的，是 `cordis.yml` 里的 `name`（模块路径）。

### 2. "解析失败"和"执行失败"是两回事

- `apply` 里抛异常：**整个进程带着错误退出**，插件加载失败会明确报错，不会被悄悄跳过。
- 模块**根本找不到**（路径或包名拼错）：框架通过 logger 报告，不会让进程崩。但启动早期这条报告可能在控制台开始工作之前就丢了。

所以"我加了一项却毫无反应"时，第一个怀疑对象永远是**拼写**。

### 3. 清单里的先后，不代表加载的先后

各项是**并发启动**的。真正决定谁先就绪的是"谁依赖谁"（`inject`，下一关），不是它在 YAML 里排第几。把两行对调，运行结果不变。

## 常见误区

### 误区：插件就是"被主程序调用的模块"

**你以为**：总得有个主程序，先启动框架，再依次调用各个插件。

**实际上**：没有主程序。插件自己就是构成应用的那一块，`cordis.yml` 才是"应用"本身。所谓启动，是 Loader 插件去逐个挂载别的插件。

**所以**：读 DSH 的入口时，别找 `main()`，去找 `cordis.patch.yml`——那份 YAML 就是这座应用的蓝图。

### 误区：插件写得越多越好、越通用越好

**你以为**：既然插件化，那每样东西都应该抽成一个可复用插件。

**实际上**：多一个插件就多一个装配点和一条依赖。插件化的价值在于**把边界切在"能替换"的地方**，不在于拆得越碎越好。一个功能如果没有第二种实现、也不需要被替换，写成普通代码往往更省事。

**所以**：判断要不要做成插件，只问一句——**将来有没有可能把它换成别的？** 没有，就先别拆。
