## 先把结论摆出来

**模型说"我想调这个工具"，只是流水线的第一句话。** 真正执行前，`ctx.tools` 会让这次调用依次经过：策略前处理 → 执行 → 策略后处理 → 结果观测。策略拦截、人工审批、结果太大落盘，全都挂在这条线上，而不是写死在每个工具里。

所以第 6 关写的 `defineTool` 只是让工具"能被调用"；这一关讲的是"被调用之后还会经过什么"。

## 四个阶段，各自能干什么

- **策略前处理（pre-execute）**：工具还没执行，这里最适合"拦"。危险命令、越权参数、不该在某作用域发生的调用，都在这里被拒或改写。
- **执行（execute）**：真正调用 `execute(args)`。`defineTool` 已经先按 `parameters` 校验过参数，所以这里拿到的 `args` 是类型对、值合法的。
- **策略后处理（post-execute）**：结果已经拿到，但还没交给模型。脱敏、截断、把超大文本落盘，都在这里做。
- **结果观测（tools/result）**：结果物化时发出，旁观的插件（日志、审计）可以看，但改变不了主流程。

其中 `tools/pre-execute`、`tools/execute`、`tools/post-execute` 都是 **waterfall**（第 4 关）：只观察的监听者必须 `next()`，有决策权才短路。忘记 `next()`，就会把工具的正常执行吞掉。

```ts
// 示意：在工具执行前加一道策略（payload 以子系统文档为准）
ctx.on('tools/pre-execute', (call, next) => {
  if (call.name === 'bash' && looksDangerous(call.arguments)) {
    throw new Error('blocked by policy')
  }
  return next()   // 放行，交给下游
})
```

## 审批：把"要不要放行"交给用户或策略

有些操作不能自动放行，要人点头。这走的是 `approval/request` 这个 **waterfall**：一个监听者可以替用户作答、也可以往下传；**如果没有任何回答方，这次审批以 `unavailable` 关闭失败**，不会默认通过。

上层的"权限预设"把这件事简化成两档：

- `workspace-write`：只能改工作区，敏感操作要审批。
- `danger-full-access`：放开限制。

切换预设会写一条 `permission/preset` 事件，同时把"沙箱模式"和"审批策略"两个选项一起贯通——所以你看到的"切换权限",背后其实是两个 seam 一起变。

## 结果太大怎么办

工具返回的东西可能很长（比如一次命令输出几万行）。`spill-policy` 是 `tools/post-execute` 的消费方：它判断"这份结果是否超过阈值"，超了就把正文存进 `ctx.spillStore`，只把定位信息和取回提示交给模型。模型不直接吃下整份大文本，上下文就不会被一次工具调用撑爆。

## 常见误区

### 误区：工具安全靠工具自己写 if 判断

**你以为**：每个工具在 `execute` 开头自己检查一下参数是否危险就够了。

**实际上**：这样每个工具都要重写一遍策略，且散落各处、无法统一。DSH 的做法是把策略挂到**流水线**上：一处 `tools/pre-execute`，管住所有工具。工具只管"怎么执行"，"该不该执行"由外层决定。

**所以**：安全与权限写在流水线的监听者里，别塞进每个工具的 `execute`。

### 误区：审批是"弹个框问用户"，和插件作者无关

**你以为**：审批是产品 UI 的事，写插件不用管。

**实际上**：审批是一个服务 seam（`ctx.approval`）+ 一个 `approval/request` waterfall。你的插件可以决定"这次调用要不要审批"，也可以替用户回答。没有回答方时它是直接失败的。

**所以**：做敏感能力时，要主动接入审批，而不是假设"反正有人会拦"。
