## 先把结论摆出来

**`cordis.yml` 不是"配置文件"，它就是这座应用。** 应用长什么样，取决于这份清单里列了哪些插件、各自给什么参数。每一行是一个条目，可以带 `config`（参数）、`id`（稳定身份）、`disabled`（临时停用）。

参数不是随便塞的：插件导出一个 **schema**，框架在跑 `apply` 之前先按它校验，**配置不合法就拒绝启动，并把错在哪条字段报出来**。插件绝不会在配置残缺的情况下跑起来。

## 带 schema 的配置

插件导出的 `Config` 既是 TypeScript 类型，也是运行时校验器：

```ts
import Schema from '@deepseek-ai/schemastery'

export interface Config {
  greeting: string
  targets: string[]
}

export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  targets: Schema.array(String).default(['world']),
})

export function apply(ctx: Context, config: Config) {
  for (const target of config.targets) console.log(`${config.greeting}, ${target}!`)
}
```

给 `targets` 传个字符串会怎样？

```yaml
- name: './config-demo.ts'
  config:
    targets: 'not-an-array'
```

框架直接报 `ValidationError: invalid config: $.targets expected array but got not-an-array`，插件进入 **FAILED**。没传的 `greeting` 则会被默认值补上——`apply` 拿到的永远是完整且校验过的配置。

还有两个常用能力：

- **`volatile` 字段**：插件每次操作都去读的字段，用 `.volatile()` 标记，改它时**只更新引用、不重新挂载插件**。
- **`!!js` 计算值**：`config` 与 `disabled` 里可以写表达式，像 `greeting: !!js process.env.DEMO_GREETING ?? 'Hello'`，在加载时求值。这让"按环境决定装不装"变成一行配置。

## id、disabled、分组、隔离

`id` 是条目的**稳定身份**。表面上可有可无，实际上它决定了热更新能不能优雅：

- 有 `id`：框架能分辨"这是改了一个已有条目"还是"删掉一个、加一个新"。只挂载/卸载变化的那部分。
- 没 `id`：每次读清单都会生成一个新 id，**任何一次编辑都会被当成"先删后加"整条重挂**。

`disabled: true` 只是把插件卸载、但**保留条目**；改回原值后，插件以及所有因依赖它而 PENDING 的插件都会重新就绪。

还有两个进阶结构：

- **分组（group）**：把一串条目当一个单元一起加载/卸载。
- **隔离（isolate）**：给一个分组一份"某服务名的独立实例"。于是两个分组可以各用各的 `shell` 提供方，互不串味。

## 热更新（HMR）：卸载 + 加载 = 替换

因为卸载会回卷 effect（第 3 关），加载又遵循依赖（第 2 关），所以**热更新在机制上就是"先卸、再装"**。DSH 的 HMR 插件监听文件，保存时执行这一过程。改一个插件文件：

```
hello from my first plugin
[I] hmr reload plugin at hello.ts
hello from my EDITED plugin
```

旧实例先卸载（它的所有 effect 回卷），新代码再加载、`apply` 重跑。**这也是为什么 id 重要**：HMR 靠 id 认出"还是同一个条目，只是内容变了"。

## 诊断"为什么它没生效"

依赖驱动加载的另一面：如果 `inject` 指的服务没人提供，插件就一直 PENDING、**不输出任何东西，也不报错**——因为 PENDING 是合法状态，提供方可能只是还没挂上来。

可以直接查：

```ts
import { FiberState, type Context } from '@deepseek-ai/cordis'

export function apply(ctx: Context) {
  setTimeout(() => {
    for (const runtime of ctx.registry.values()) {
      for (const fiber of runtime.fibers) {
        if (fiber.state === FiberState.PENDING) {
          console.log(`${fiber.name} is PENDING — 缺少它 inject 的服务`)
        }
      }
    }
  }, 500)
}
```

**"加了没反应"的排查顺序就三条**：先查模块名拼写（第 1 关）→ 再查是不是卡在 PENDING（缺服务）→ 再查配置有没有过 schema。

## patch 层：不改原始清单，也能改写

真实 DSH 里，你的个人配置不会去改框架自带的那份清单，而是写一个 **patch 层**（`cordis.patch.yml`）。它是一串"按 id 定位的补丁条目"：覆盖某个条目的 `config`、`disabled`，或者往清单里插入新条目。加载时，补丁层在基础层之后应用。

```yaml
# 例：把默认模型换成另一个 provider（按 id 命中，不碰其余配置）
- id: agent-default-model
  config:
    provider: magpie
    model: workbuddy/deepseek-v4.1-flash
```

## 常见误区

### 误区：配置写错最多"不生效"，不会有大问题

**你以为**：YAML 嘛，填错了顶多这个插件不干活。

**实际上**：配置是要过 schema 的。类型错了插件直接 FAILED，如果它恰好是核心服务（比如模型 provider），整个应用就起不来。而"不报错的那些"往往更麻烦——比如 PENDING，看起来像"没生效"，其实是"一直没启动"。

**所以**：改配置后先看日志里有没有 ValidationError，再确认目标插件到了 ACTIVE。

### 误区：热更新等于"改了就自动对"

**你以为**：保存文件就完事了，数字会自己对上。

**实际上**：HMR 只是"卸载旧实例 + 加载新代码"。如果你的插件有 effect 之外的裸资源（第 3 关），或者新代码引入了没人提供的依赖，热更新会表现为"改了没反应"甚至泄漏。它放大的是你原本就写对/写错的东西。

**所以**：HMR 让迭代变快，但它不修复设计问题。资源都走 effect、依赖都声明清楚，热更新才是安全的。
