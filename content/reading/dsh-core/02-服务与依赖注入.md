## 先把结论摆出来

**插件 A 要用插件 B 的能力，绝不 import B。** 它只认一个**服务名**：B 把能力登记成 `ctx.<名字>`，A 通过 `ctx.<名字>` 取用。A 和 B 从头到尾不知道对方的文件在哪。

在 DSH 里，`ctx.tools`（工具注册表）、`ctx.llm`（模型）、`ctx.agents`（智能体协调）都是这种"服务"。插件消费的是**名字**，不是实现，所以配置可以随时把某个服务的提供方换掉，消费方一行不用改。

## 提供一个服务

写一个类，继承 `Service`，在构造函数里用 `super(ctx, '名字')` 把它登记到当前上下文：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    greeter: GreeterService
  }
}

export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')
  }

  greet(who: string) {
    return `Hello, ${who}!`
  }
}

export const name = 'greeter'

export function apply(ctx: Context) {
  ctx.plugin(GreeterService)
}
```

这里有两件事同时发生，分工很干净：

- **运行时**：`super(ctx, 'greeter')` 以名字 `greeter` 注册这个实例。此后任何插件都能通过 `ctx.greeter` 访问它。注册是一个 effect（第 3 关细讲），提供方卸载时这个服务就没了。
- **编译时**：`declare module` 那段用 TypeScript 的声明合并，把 `greeter` 加进 `Context` 接口，让 `ctx.greeter` 在各处都能过类型检查。**它不生成任何代码**——删掉它，运行时照样工作，只是消费方失去了类型提示。

## 消费一个服务

消费方用 `inject` 列出它需要的服务名：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'consumer'
export const inject = ['greeter']

export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))
}
```

关键在 `inject` 的语义：**框架会让这个插件一直停在 PENDING，直到 `inject` 里的每一项都就绪。** 所以进到 `apply` 里，`ctx.greeter` 一定已经存在。

这也解释了一个反直觉的现象：**`cordis.yml` 里的顺序无所谓。** 把 `greeter` 和 `consumer` 两行对调，输出照样是 `Hello, world`。决定什么时候启动的是依赖，不是文件顺序。

如果彻底删掉 `greeter` 提供方，`consumer` 会一直 PENDING，不输出任何东西——**不报错，也不运行一半**。这是第 5 关要专门诊断的一种状态。

## 依赖不是"启动时查一次"，而是一直跟着

`inject` 不是一个开机自检。**运行期间如果依赖的服务消失**（比如提供方被卸载、被热替换），每个依赖它的插件也会跟着卸载；等服务恢复，它们再重新加载。

这带来一个很重要的能力：**服务可以被替换。** DSH 里有个典型例子——卸载本地 shell 提供方 `dsh-bash-local`，挂上另一个提供 `shell` 的插件，所有 `inject: ['shell']` 的插件会自动重启，改用新实现。消费方完全不知道底层换了人。

## 可选依赖：用 `ctx.get` 而不是 `inject`

`inject` 是**硬依赖**：缺了就永远起不来。如果某项能力缺失时插件仍能工作，就别写进 `inject`，改在用到的地方探测：

```ts
export function apply(ctx: Context) {
  // 没有提供方时是 undefined，插件照常运行
  const greeter = ctx.get('greeter')
  console.log(greeter?.greet('maybe') ?? 'no greeter available')
}
```

区别是**你要哪种行为**：硬依赖让"缺东西"立刻显形（插件不启动）；可选依赖让插件在缺东西时降级运行。别把"其实可以没有"的东西写成 `inject`，否则整条链会因为一个可选能力而卡住。

## 命名：全局一个扁平空间

所有服务名共享一个扁平命名空间。DSH 已经占用了 `tools`、`llm` 这类"好听的短名"，所以写自己的服务时，加一个能识别的前缀（比如 `myapp-stats`），别硬抢通用词。

## 常见误区

### 误区：服务就是"单例对象"，拿一次存起来最省事

**你以为**：`const t = ctx.tools` 存到模块级变量里，以后一直用这个引用就行。

**实际上**：服务会随提供方卸载而消失、随新提供方而重建。如果你在某个瞬间缓存了引用，之后提供方被热替换，你手里的就是一份"已经失效"的旧对象。

**所以**：服务应该**每次用的时候通过 `ctx` 取**，或者干脆把逻辑写进 `apply` 的闭包里、跟着插件一起生灭。缓存"能力引用"是这类框架里最隐蔽的 bug 来源之一。

### 误区：把所有依赖都写进 inject 最保险

**你以为**：反正声明得越多越安全，缺了就让框架等我。

**实际上**：`inject` 里每多一项硬依赖，就多一个"可能永远起不来"的理由。一个可选能力被写成硬依赖，会让整个插件白白停在 PENDING。

**所以**：只有"没有它就没法工作"的才写 `inject`；"有更好、没有也能跑"的用 `ctx.get` 探测。这是设计意图，不是偷懒。
