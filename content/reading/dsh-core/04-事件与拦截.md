## 先把结论摆出来

**服务是"我点名调用你"，事件是"我喊一声，谁听谁处理"。** 发事件的插件不需要知道有谁在监听，监听者也不需要被发事件的人认识——这正是"插件能悄悄插一脚"的机制。

事件有五种分发方式，各有各的语义。其中最像"拦截器"的一种叫 **waterfall**：每个监听者收到参数和一个 `next()`，它可以往下委托，也可以**不调 `next()` 直接返回**、把后面整条链短路掉。

## 声明、发出、监听

事件的类型也靠声明合并来登记。把事件名和它的参数签名写进 `Events` 接口，`emit` 和 `on` 就都有了完整类型：

```ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    'stats/report'(name: string, count: number): void
  }
}

export function apply(ctx: Context) {
  // 监听：ctx.on 是 effect，卸载时自动移除
  ctx.on('stats/report', (name, count) => console.log(name, count))

  // 发出
  ctx.emit('stats/report', 'tool_call', 1)
}
```

命名用 `namespace/action` 的习惯（`tools/result`、`agent/request`），让一个扁平的事件空间仍然可读。

## 五种分发方式

选哪种不是风格问题，而是**事件的约定**——它决定了监听者能不能返回值、能不能并发、能不能彼此短路：

| 模式 | 怎么调 | 语义 |
| --- | --- | --- |
| emit | `ctx.emit(name, ...)` | 同步广播，不等也不收返回值 |
| parallel | `await ctx.parallel(name, ...)` | 所有监听者并发跑，一起等 |
| serial | `await ctx.serial(name, ...)` | 按顺序跑并等待；第一个非 `null`/`false`/`undefined` 的返回值胜出，后面不再执行 |
| bail | `ctx.bail(name, ...)` | serial 的同步版 |
| waterfall | `ctx.waterfall(name, ...args, next)` | 环绕中间件，见下 |

**一句话记法**：`emit` 是"通知一声"；`parallel`/`serial`/`bail` 是"要一个结果"；`waterfall` 是"把处理权一层层往里传"。

## waterfall：可以委托，也可以否决

waterfall 是最需要想清楚的一种。每个监听者拿到 `(...args, next)`：调 `next()` 就执行下游，不调就直接返回、短路整条链。

```ts
ctx.on('demo/transform', async (input, next) => {
  const downstream = await next()      // 先让下游处理
  return downstream.toUpperCase()      // 再包装它的结果
})

ctx.on('demo/transform', async (input, next) => {
  if (input.includes('blocked')) return '** blocked **'  // 不调 next：短路
  return next()
})
```

这里有一条**硬纪律**：

> **只做观察或标注的 waterfall 监听者，必须调用 `next()`。** 不调就是"有意短路"。一个忘记调 `next()` 的日志监听者，会悄无声息地把下游所有默认行为吞掉。

DSH 用它来处理"可能被协作插件包装或直接回答"的决策：`agent/request` 允许插件替换这次模型调用的配置，`approval/request` 允许策略替用户答复批准请求。它们都是"谁有决策权谁才短路，没决策权必须往下传"的形态。

## 常见误区

### 误区：事件就是"更松耦合的调用"，随便用哪个都行

**你以为**：能 emit 就 emit，反正最后都会被执行。

**实际上**：分发模式是事件**公开约定的一部分**。把一个本该 `serial`（要第一个有效结果就停）的事件用 `emit` 发，监听者的返回值会被直接丢掉，整个"取结果"的逻辑就失效了。反过来乱用 `waterfall` 又容易把不该拦的流程拦掉。

**所以**：先想清楚"这件事需不需要返回值、要不要短路、要不要并发"，再去选模式。模式选错，比不写事件更糟。

### 误区：waterfall 监听者只要处理自己的部分就够了

**你以为**：我只管我关心的输入，其它情况自然有人管。

**实际上**："其它情况"的默认行为恰恰挂在链的末端（你调用 `next()` 之后才会到）。你不调 `next()`，就不只是"没处理"，而是"把别人也挡了"。

**所以**：写 waterfall 监听者的默认姿态是 `return next()`；只有当你**确实要接管这个决策**时，才直接返回。
