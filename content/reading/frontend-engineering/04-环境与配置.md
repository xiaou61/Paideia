## 这一关在解决什么

同一份源码，要跑在三个地方：

```text
开发   本机，接口打 http://localhost:8080
测试   测试服，接口打 https://test.example.com
生产   线上，接口打 https://api.example.com
```

最容易踩的三个坑：

- 把地址写死在代码里，切环境要改代码、要重新提交、要重新发版；
- 把密钥写进 `.env`，以为"只有构建工具能看到"——其实打包之后**全在用户的浏览器里**；
- 用 `process.env.API_URL`，本地能跑，构建后是 `undefined`。

这一关讲清楚：环境变量在前端到底是怎么"进"到代码里的，以及什么能放、什么绝对不能放。

## 讲解

### 关键事实：前端的环境变量是"构建时替换"

后端读环境变量是在**运行时**：进程启动，`process.env.DB_PASSWORD` 有值。

前端没有这个过程。浏览器里跑的是静态文件，没有"环境变量"这种东西。构建工具做的是**字符串替换**：

```js
// 源码
const base = import.meta.env.VITE_API_BASE

// 构建后（VITE_API_BASE=https://api.example.com 时）
const base = "https://api.example.com"
```

所以：

- 换环境 = **换构建时的值 + 重新构建**，不是改个文件就生效；
- 构建日志、构建缓存、`dist/` 里都能看到这个值——**它没有任何秘密可言**。

### `.env` 文件的加载顺序

Vite 按这个顺序读，**后面的覆盖前面的**：

```text
.env                 所有环境共用
.env.local           本机私有（必须 gitignore）
.env.production      只在 production 模式生效
.env.production.local
```

推荐的最小配置：

```text
# .env                （提交到 Git，放公共默认值）
VITE_API_BASE=/api

# .env.local          （不提交，放本机专属）
# VITE_API_BASE=http://localhost:8080
```

### `VITE_` 前缀是一道安全闸

Vite 只把 **`VITE_` 开头**的变量注入前端代码。不带前缀的（比如 `DB_PASSWORD`）在构建时就读不到——这是有意设计的保护：防止你把服务端的变量文件直接拿来用，然后被打进包里。

但这道闸只防"误用"，不防"故意"。**带 `VITE_` 前缀的一切，用户都能看到**：

```js
// 这段代码等于把 key 印在页面上
const key = import.meta.env.VITE_MAP_API_KEY
```

浏览器 DevTools 里搜一下 JS 文件就能找到。

所以规则很硬：

| 能不能放前端 | 例子 |
| --- | --- |
| 能 | 接口地址、功能开关、版本号、公开的第三方 key（有限流保护的那种） |
| 不能 | 数据库密码、JWT 签名密钥、云存储的 Root 密钥、任何"拿到就能花你钱"的凭证 |

如果某个 key 必须在前端用（比如地图 SDK），那就把它当成**公开信息**处理：在服务商后台配好域名白名单与调用限额，让它即使被抄走也花不了多少钱。

### 真的需要"换环境不重新构建"怎么办

有些团队要求：一份 `dist` 制品，从测试灰度到生产都用它。这时候构建时替换就做不到。

标准解法是**运行时配置**：把配置放在一个单独的、不参与构建的文件里，页面启动时先读它。

```html
<!-- public/config.json，部署时由运维替换 -->
{ "apiBase": "https://api.example.com", "env": "prod" }
```

```js
const config = await fetch('/config.json').then((r) => r.json())
```

代价是多一次请求、启动时要等它，而且这个 `config.json` 同样是人人都能看到——它只解决"同一份代码多环境部署"，不解决"藏秘密"。

取舍很清楚：**要严格一致就一次构建到处部署（运行时配置）；要简单就用构建时变量（每个环境各构建一次）**。两者都能用，别混着用。

## 常见误区

### 误区：`.env` 不进 Git，所以里面的东西是安全的

**你以为**：`.env` 被 gitignore 了，密钥只在本地和服务器上。
**其实**：gitignore 只保护"不进仓库"。构建时凡是注入到前端代码里的值，都会被打进 `dist/`，最终下发到每个用户的浏览器。**安全性由"是否进入产物"决定，不由"是否进入 Git"决定**。
**怎么验证**：构建之后在 `dist/assets/*.js` 里搜你的密钥值。搜得到，就说明它已经公开了。

### 误区：用 `process.env.XXX` 和 `import.meta.env.XXX` 差不多

**你以为**：都是读环境变量，换个写法而已。
**其实**：浏览器里没有 `process`。有些构建配置会用 `define` 把 `process.env.XXX` 也替换掉，一旦没配全，运行时就抛 `process is not defined`——而且往往只在某个懒加载的页面里出现。前端读环境变量统一用 `import.meta.env`，这是标准。
**怎么验证**：在源码里写 `console.log(process.env)`，dev 下大概率就是空的或报错。真正被替换的只有构建配置里显式声明过的键。

### 误区：把地址写成相对路径 `/api` 就不用管环境了

**你以为**：同源相对路径，开发和生产都通吃。
**其实**：相对路径确实省事，但它要求**前端和后端在同一个域名下**。前端放 CDN、后端在另一个域名时，`/api` 会打到 CDN 上，直接 404。而且跨域后还要处理 Cookie、CORS。相对路径是一个前提很强的选择，不是免费的。
**怎么验证**：看部署拓扑——前端与接口是不是同一个域名。不是，就必须有一个明确的 `apiBase` 配置项。
