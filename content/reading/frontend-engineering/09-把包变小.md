## 这一关在解决什么

构建完成，产物一行：

```text
dist/assets/index-8f3a2c.js   1,842.33 kB │ gzip: 512.11 kB
```

`gzip 512KB` 意味着：4G 弱网下光下载就要 5 秒以上，低端手机解析执行还要 2–3 秒。这段时间页面是白的。

体积膨胀的原因通常不是"你写得多"，而是三件事：

- 整包引入了一个只用一两个组件的库；
- 所有页面都编进了首屏包，包括用户永远不点的设置页；
- tree shaking 没生效，打进了一堆死代码。

这一关讲：体积怎么量、怎么砍，以及哪些砍法其实没意义。

## 讲解

### 先量，再砍

不看构成就优化，通常优化错地方。构建完先看组成：

```bash
npx vite build
npx vite-bundle-visualizer    # 生成一张「谁占了多少」的图
```

常见的"体积大户"分布大致是这样：

| 类别 | 典型占比 | 能不能砍 |
| --- | --- | --- |
| 图表库 / 富文本编辑器 | 30–50% | 换轻量替代、或懒加载 |
| UI 组件库 | 20–40% | 按需引入 |
| 日期/工具库 | 5–15% | 换原生 API 或用 dayjs 换 moment |
| 业务代码 | 20–30% | 分包后按需加载 |

**先找出占前三位的那几个包**，通常砍掉它们就够了。在全项目里找"可以优化的地方"往往收益极小。

### tree shaking 的三个前提

tree shaking 的意思是：`import` 了但没用到的导出，构建时被删掉。它不是自动的，需要三个条件：

**① 必须是 ESM**。CommonJS 是运行时 `require`，打包器无法静态判断哪些导出被用到，只能整个保留。

**② 包必须声明无副作用**。包的 `package.json` 里：

```json
{
  "sideEffects": false
}
```

或者精确列出有副作用的文件：

```json
{
  "sideEffects": ["*.css", "./src/polyfill.js"]
}
```

没这一项时，打包器不敢删——万一某个模块被 import 只是为了执行它的副作用（注册全局、打补丁）呢。

**③ 你的 import 方式要能静态看穿**：

```js
// 能摇：只取两个具名导出
import { debounce, throttle } from 'lodash-es'

// 摇不掉：整个对象都进来了
import _ from 'lodash'
_.debounce()

// 摇不掉：require 一个变量
const name = 'lodash'
require(name)
```

注意 `lodash` 与 `lodash-es` 的差别：前者是 CommonJS 版本，整个库都会进来（约 70KB gzip）；后者是 ESM 版本，只取用到的那几个函数（约 2KB）。**同一个库，两个包名，体积差 30 倍**。

### 懒加载：只在需要时下载

```tsx
import { lazy, Suspense } from 'react'

const SettingsPage = lazy(() => import('./pages/Settings'))

function App() {
  return (
    <Suspense fallback={<Skeleton />}>
      <Routes>
        <Route path="/settings" element={<SettingsPage />} />
      </Routes>
    </Suspense>
  )
}
```

`import()` 会让构建工具把 `Settings` 及其依赖**单独打成一个 chunk**，只有用户真的进入这个路由时才下载。首屏包因此瘦一圈。

**路由级懒加载是性价比最高的一刀**：改动小、收益大（通常能砍掉 30–50% 首包），而且用户几乎感知不到——他们本来也不会一次点开所有页面。

往下一层是"组件级懒加载"：弹窗、富文本编辑器、图表这类**点开才需要**的重型组件，同样值得拆出去。

```tsx
const Editor = lazy(() => import('./components/RichEditor'))
// 用户点「编辑」时才下载这 300KB
```

### 不要拆太碎

懒加载有成本：每次加载一个新 chunk 就是一次网络往返（虽然 HTTP/2 能复用连接，但仍有延迟）。把项目拆成 200 个小 chunk，用户点一个页面要串行等 5 个请求，反而更慢。

实用的粒度是：

- **路由级**：必须拆；
- **重组件**（> 100KB 且非首屏必需）：拆；
- **普通组件**：不拆，它们应该待在所在路由的 chunk 里。

### 几个常见的大头，和对应的替代

| 现状 | 问题 | 替代 |
| --- | --- | --- |
| `moment`（约 70KB gzip） | 全量 locale、可变 API | `dayjs`（约 3KB）+ 按需 locale，或原生 `Intl.DateTimeFormat` |
| 整个 UI 库全量引入 | 只用 10 个组件 | 按需引入 / 手动 import 具体路径 |
| 图标库 `import * as Icons` | 几千个图标全进包 | 具名导入单个图标（现代图标库都支持） |
| `lodash` | CommonJS，摇不动 | `lodash-es` 或直接用原生方法 |
| 首屏就引入图表库 | 首屏根本用不到 | 懒加载 |

## 常见误区

### 误区：gzip 压缩了，体积就不是问题

**你以为**：500KB 压到 150KB，已经可以了。
**其实**：压缩只减少**传输**时间，不减少**解析与执行**时间。浏览器要先把压缩包解开，再解析 JS，再执行——低端手机上一句 1MB 的 JS 执行 2 秒是常态，这段时间主线程被占住，页面点了没反应。
**怎么验证**：DevTools Performance 面板录一次首屏，看 Scripting 那一条占了多久。这个数字比 Network 上的传输时间更能说明用户感受。

### 误区：`import { x } from 'lib'` 就一定按需引入

**你以为**：我只导入了 `x`，那包里其他东西不会被带进来。
**其实**：能不能摇掉取决于这个库**是不是 ESM、有没有声明 sideEffects**。一个 CommonJS 的库，你只用一个函数，整个库照样进来。
**怎么验证**：`vite build` 后看 visualizer 里这个库占了多少。如果你只用一个函数，它却占了几十 KB，说明摇树没生效——换 ESM 版本或改用具体子路径导入。

### 误区：拆得越细加载越快

**你以为**：每个组件一个 chunk，用户只下需要的。
**其实**：chunk 越多，请求越多、串行等待越长，而且共享代码会被复制到多个 chunk 里（除非正确配置共享 chunk）。首屏需要的内容被拆成 10 个文件，比合成 1 个慢。
**怎么验证**：打开 Network 面板看首屏的请求瀑布。如果是一串串行的小请求，说明拆过头了。

## 带走一句

**体积优化的顺序永远是：先量出前三名大户，再砍它们**——按猜测优化，十次有九次砍在不影响首屏的地方。
