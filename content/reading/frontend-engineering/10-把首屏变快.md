## 这一关在解决什么

包变小了，首屏仍然慢。因为首屏时间不是"JS 有多大"一件事决定的，而是一条链：

```text
DNS → TCP/TLS → 请求 HTML → 解析 → 请求 CSS/JS → 执行 JS → 请求数据 → 绘制内容
```

任何一环慢，用户看到的都是白屏。这一关讲这条链上真正值得动的几个点，以及一个残酷事实：**大部分首屏慢，是因为关键资源在排队，而不是因为代码慢**。

## 讲解

### 先认识三个指标

不量化就没有优化。三个 Core Web Vitals 指标够用：

| 指标 | 衡量什么 | 合格线 |
| --- | --- | --- |
| **LCP** | 首屏最大内容（通常是标题图或主区块）出现的时间 | < 2.5 秒 |
| **CLS** | 页面加载中布局跳动的程度 | < 0.1 |
| **INP** | 用户操作到界面响应的延迟 | < 200 毫秒 |

用 Lighthouse 在"Slow 4G + 4 倍 CPU 降速"下跑一次，比在自己的开发机上点十次都有说服力。

### 关键渲染路径：谁在挡路

浏览器要画出首屏，最少需要：HTML（结构）+ CSS（样式）+ 一点 JS（如果需要渲染内容）。

会挡路的：

```html
<!-- 阻塞解析：浏览器必须等它下载并执行完才继续 -->
<script src="/app.js"></script>

<!-- 阻塞渲染：样式没到之前不画（这是必要的，否则会闪无样式页面） -->
<link rel="stylesheet" href="/app.css" />
```

不会挡路的：

```html
<!-- 异步下载，下载完就执行（执行时仍会短暂占用主线程） -->
<script src="/app.js" async></script>

<!-- 下载完等 HTML 解析完再按顺序执行 -->
<script src="/app.js" defer></script>

<!-- 预加载：只是提前下载，不执行 -->
<link rel="modulepreload" href="/assets/vendor.js" />
```

现代前端应用通常把入口 `<script>` 标成 `type="module"`，它天然是 defer 行为——所以**首屏白屏的主因往往不是入口脚本阻塞，而是 CSS 打包太大 + 首个数据请求太慢**。

### 缓存：让第二次访问几乎零成本

缓存策略只有一条核心思想：**文件名带 hash 的，永久缓存；不带 hash 的，每次验证**。

```nginx
# 带 hash 的静态资源：内容变了 hash 就变，可以放心缓存一年
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

# HTML 绝对不能长缓存，否则用户永远拿不到新版本
location / {
  add_header Cache-Control "no-cache";
}
```

`immutable` 是给浏览器的保证："这个 URL 的内容永远不会变，别再来问了。" 没了它，浏览器即使有缓存也可能发起一个条件请求（If-None-Match）去确认，多一次往返（虽然只是 304）。

**最常见的缓存事故**是给 `index.html` 也配了长缓存：用户永远停在上一个版本，你发十次版他看到的还是旧的，而他清一次缓存就好了——所以他还以为是自己电脑的问题。

### CDN：把文件搬到用户旁边

静态资源放 CDN，本质是缩短物理距离与 TLS 握手次数。收益主要在两个地方：

- **首字节时间**（TTFB）从 200ms 降到 20ms 量级；
- 高峰期的带宽不再由你的单台服务器扛。

配套的两个优化：

```html
<!-- 提前建立连接：DNS + TCP + TLS，省 100–300ms -->
<link rel="preconnect" href="https://api.example.com" />
<link rel="dns-prefetch" href="https://cdn.example.com" />

<!-- 关键资源提前下载，不阻塞 -->
<link rel="preload" as="font" href="/fonts/inter.woff2" type="font/woff2" crossorigin />
```

`preconnect` 对"首屏紧接着就要请求的第三方域名"有效；对用了十几个第三方脚本的页面，全加上反而会抢带宽——**只给真正关键的 2–3 个域名加**。

### 字体和图片：两个最容易被忽略的大头

**字体**默认行为是"等字体下载完才显示文字"，在中文站点上尤其致命（中文字体动辄几 MB）：

```css
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter.woff2') format('woff2');
  font-display: swap;   /* 先用系统字体显示，字体到了再换 */
}
```

`swap` 会带来一次视觉切换（CLS 的来源之一），但它比"白屏等字体"好得多。更彻底的做法是**不用自定义中文字体**，或者只对标题用、并且做子集化（只保留用到的字）。

**图片**三件事按收益排序：限制尺寸（别把 3000px 的图缩成 300px 显示）、懒加载首屏之外的图、用现代格式（WebP/AVIF 通常比 JPG 小 30–50%）。

```html
<img src="chart.webp" width="800" height="450" loading="lazy" alt="季度营收" />
```

`width`/`height` 写上是防 CLS 的最简单办法——浏览器能提前预留位置，图片到了不会把下面的内容挤下去。

## 常见误区

### 误区：包小 = 首屏快

**你以为**：砍到 150KB 了，首屏应该很快。
**其实**：首屏还要等 HTML、CSS、首个接口请求。一个 100KB 的包如果配上一个 800ms 的接口，用户照样要等一秒多才看到内容。而且首屏渲染往往依赖数据，这段等待是"应用层"的，与包大小无关。
**怎么验证**：Lighthouse 报告里看 LCP 的分解——它会告诉你时间花在"等 HTML""等 CSS""等 JS 执行"还是"等资源加载"上。

### 误区：所有静态资源都该长缓存

**你以为**：缓存越久越好，`max-age` 加到一年。
**其实**：只有**文件名会随内容变化**的资源才能长缓存。HTML 文件名永远叫 `index.html`，给它配一年缓存，等于把用户锁在旧版本里。同理，`/api/config.json` 这类固定路径的文件也不能长缓存。
**怎么验证**：发一次版，然后不清缓存直接刷新页面。看到旧版本，就是 HTML 被缓存了。

### 误区：`preload` 加得越多越快

**你以为**：把关键资源都 preload 一遍，浏览器提前下载，肯定更快。
**其实**：`preload` 会**抢占带宽优先级**。给不关键的资源加了 preload，它会跟真正关键的资源抢连接，反而把首屏关键请求推后。而且 preload 了却没用上时，浏览器会在控制台警告"资源被预加载但未使用"，白下载。
**怎么验证**：加完 preload 对比 LCP。变慢了就说明抢错了；控制台出现 `preloaded but not used` 说明加错了对象。
