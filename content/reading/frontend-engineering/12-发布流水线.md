## 这一关在解决什么

前十一关做出来的东西，最终要经过"发布"这一步才能到用户手上。而发布是最容易靠人记的环节：

```text
1. 本地拉最新代码
2. npm install                ← 忘了会怎样
3. npm run build              ← 用哪个环境变量
4. 把 dist 传到服务器         ← 传到哪、怎么传
5. 重启服务 / 刷 CDN
6. 打开页面看一眼
```

六步里每一步都可能漏。漏第 2 步，构建用的是旧依赖；漏第 3 步的环境变量，接口打到测试环境；第 5 步忘了刷 CDN，用户看到旧版本。

这一关讲的是：把这条链自动化，并且让它**可重复、可追溯、可回滚**。

### 一条最小可用的流水线

```yaml
name: release
on:
  push:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 缓存依赖：命中时这步只要几秒，没缓存要一两分钟
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile   # 等同 npm ci：严格按锁文件
      - run: pnpm typecheck
      - run: pnpm lint
      - run: pnpm test -- --run
      - run: pnpm build

      # 制品：把产物打包，带上版本号
      - run: tar -czf dist-${{ github.sha }}.tar.gz -C dist .
      - uses: actions/upload-artifact@v4
        with:
          name: web-${{ github.sha }}
          path: dist-${{ github.sha }}.tar.gz
```

四件事是关键：

1. **`--frozen-lockfile`**（或 `npm ci`）：装依赖必须严格按锁文件，否则锁文件被悄悄改动，CI 与本地就不一致了。
2. **检查顺序从快到慢**：类型 → lint → 测试 → 构建。前面的便宜且定位准，后面的贵。任何一步失败立即停，不浪费后面的时间。
3. **依赖缓存**：这一步能把流水线从 3 分钟压到 40 秒。缓存的 key 要和锁文件内容绑定，锁文件变了就重新装。
4. **制品带版本号**：`dist-<commit>.tar.gz`，任何一次上线的产物都能对应到唯一一次提交。

### 制品必须不可变

"制品"（artifact）指的是**构建出来的那一份静态文件**，不是源码。核心纪律是：**同一份制品，从测试环境到生产环境不要重新构建**。

```text
构建一次  →  dist-a1b2c3.tar.gz
部署测试  →  用 a1b2c3
部署生产  →  还是 a1b2c3
```

如果每个环境都重新构建一次，那么"测试环境验证通过"这句话就不成立了——你验证的和上线的不是同一份文件（依赖、构建时间、压缩结果都可能不同）。

要"一份制品多环境"，配置就不能写死在产物里，得走第 04 关讲的运行时配置。

### 部署与回滚

三种常见策略，成本与风险递增：

| 策略 | 做法 | 回滚速度 |
| --- | --- | --- |
| 全量替换 | 停服务 → 换文件 → 启动 | 慢（要重新部署旧版本） |
| 蓝绿 | 两套环境，切流量 | 快（流量切回去） |
| 灰度 | 先给 5% 用户，观察后放量 | 快（停止放量） |

对大部分前端项目，最实用的组合是：**全量替换 + 制品保留最近几个版本**。回滚时不用重新构建，直接把上一个版本的制品再部署一次——这就是"制品不可变"的第二个好处：回滚是换标签，不是重新打包。

前端还有一个特殊的回滚陷阱：**HTML 已经缓存了，但 assets 被删了**。用户手里的旧 HTML 会去请求旧 hash 的资源，如果部署时把旧文件删干净，就会 404 白屏。

所以准则里加一条：**部署后至少保留上一版的 assets 一段时间**，或者让带 hash 的资源永久留在 CDN 上（它们的文件名不会冲突）。

### 发布之后看什么

上线不是终点，是观察的开始。发布后十分钟看三样：

- **错误率**：有没有陡增（第 11 关的版本对比）；
- **核心接口成功率 / 延迟**：有没有被新版本打爆；
- **首屏指标**：LCP 有没有变差。

这三项都正常，才算发布成功。没有这三项，你只能靠用户来告诉你。

## 常见误区

### 误区：自动化就是"CI 跑一下测试"，部署还是手工

**你以为**：测试有 CI 就够了，部署手动更快更可控。
**其实**：手工部署的每一步都是"只有某个人知道"的知识，他休假就发不了版；而且手工步骤越多，出错概率越高（漏传一个文件、传错目录）。真正要自动化的恰恰是**部署这一步**，因为它最容易出错且最不该需要人判断。
**怎么验证**：问一句"现在发版要几步、除了你还有谁会"。答案是"只有我会"，就是该自动化了。

### 误区：CI 慢就慢点，反正是机器在跑

**你以为**：三分钟和十分钟没区别。
**其实**：CI 时间直接决定反馈速度，而反馈速度决定开发节奏。一次 15 分钟的流水线，人就不会等它，而是去做别的事——结果是一个错误在 40 分钟后才被发现。慢流水线最常见的三个原因：没缓存依赖、没缓存构建、不带 `-T`/并行跑测试。
**怎么验证**：看每一次 step 的耗时。依赖安装超过 30 秒、构建超过 60 秒，先优化这两项。

### 误区：回滚就是 `git revert` 再发一次

**你以为**：回滚等于把代码改回去，重新走一遍流程。
**其实**：那是最慢的回滚方式（要重新构建、重新部署，期间问题还在）。有不可变制品时，回滚是"把上一个版本的制品再部署一次"，几分钟就能完成，与代码无关。所以**保留历史制品**是回滚能力的前提。
**怎么验证**：试着在测试环境演练一次回滚。如果需要重新构建，说明你还没有真正的回滚能力。

## 带走一句

**发布可以手工一次，但不能手工第二次**——第一次之后就把步骤写成脚本，因为第二次开始，它就是你每周都要付的税。
