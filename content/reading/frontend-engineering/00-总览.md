## 这条线写给谁

写给**已经能写出页面、但每次交付都靠手工**的人。

如果你有过下面这些时刻，这条线就是为你排的：

- 项目里 `node_modules` 有 800MB，但你说不清哪个包是真正在用的；
- 本地 `npm run dev` 一切正常，`npm run build` 之后白屏，报错只有一行 `Unexpected token '<'`；
- 同事改了 `package.json`，你 `git pull` 之后整个项目起不来；
- 想加一个按钮，发现它在三个文件里各写了一遍逻辑，你不知道该信哪一份；
- 上线后发现线上和本地表现不同，但没有任何工具告诉你线上那一份代码是哪次提交打的包。

这些问题都不出现在"页面能不能显示"上，所以最容易被拖到"以后再说"。而它们每多留一个月，修复成本就翻一倍。

## 为什么工程化值得单独学

因为**写页面是一次性的，让页面活下去是每天的事**。

一个前端项目跑到第三个月，代码量大概翻了三倍，参与的人从 1 个变成 3 个。这时候真正决定你还能不能改动的，不是你会不会写组件，而是：

- 依赖装得回来吗（锁文件）；
- 有没有一个命令能证明改动没弄坏别的（测试、类型检查）；
- 同一个问题会在几个地方出现（模块边界）；
- 上线能不能十分钟内回滚（制品与流水线）。

这条线讲的全是这些"看不见但每天都在付钱"的部分。

## 十二关怎么排

分三段：

- **管起来（01–04）**：为什么今天不能再用 `<script>` 拼页面（01）、依赖到底装了什么（02）、`npm run dev` 和 `npm run build` 差在哪（03）、一套代码怎么跑三种环境（04）。这一段结束时，你的项目是"可重复安装、可重复构建"的。
- **可维护（05–08）**：TypeScript 的类型到底在防谁（05）、lint 与格式化该怎么分工（06）、单元/组件/端到端测试各管什么（07）、什么时候该把组件拆开（08）。这一段让改动有安全网。
- **跑得好（09–12）**：把包变小（09）、把首屏变快（10）、线上白屏从哪查（11）、从提交到上线自动化（12）。这一段决定你的页面在真实网络下是什么体验。

## 一个前提

需要先能把一个页面写出来（HTML/CSS/JavaScript 够用），并且用过 `npm` 装包。

不需要：会 Webpack 配置、会写 CI 脚本、买服务器。这些是这条线要讲的内容，不是入场条件。

## 常见误区

### 误区：工程化是"大公司才需要的东西"

**你以为**：就我一个开发、一个页面，配什么构建、测试、CI。
**其实**：工程化里最省事的那几条恰恰是给一个人用的——提交锁文件（别人/三个月后的你能装回同一份依赖）、一条 `npm run build`（不用记命令顺序）、一个类型检查（改完不用手动点十个页面）。团队只是把这些放大了，不是创造了需求。
**怎么验证**：把你现在的项目删掉 `node_modules`、换一台机器重新装一遍。装得回来、跑得起来，说明你已经有一套最小的工程化；装完了版本对不上，那就是它在喊你补课。

### 误区：`npm run dev` 能跑，就等于项目是好的

**你以为**：开发服务器没报错，说明代码没问题。
**其实**：开发服务器为了快，做了很多"宽容"的事：不做压缩、不做 tree shaking、不区分环境、模块按需现编译、错误直接打在浏览器控制台。生产构建是另一套流程，它会暴露 dev 里被掩盖的问题——路径大小写、Node 内置模块被引用、环境变量没替换、依赖只有 CJS 版本。
**怎么验证**：每个功能合入前跑一次 `npm run build && npm run preview`，在预览产物上点一遍主路径。这一条能拦住至少一半的"上线白屏"。

### 误区：包越大越安全，反正只是加载慢一点

**你以为**：多装几个库，功能齐全，用户网速都很快。
**其实**：体积是**每次打开页面都要付**的成本，而且它主要影响的是最慢的那部分用户。1MB 的 JS 在办公网是 0.2 秒，在 4G 弱网下是 8 秒以上，而超过 3 秒的等待，一半人会直接离开。更麻烦的是解析与执行时间——在低端手机上，1MB JS 的执行可能要 2 秒，这段时间页面是卡住的。
**怎么验证**：`npm run build` 之后看产物大小，再用 DevTools 的 Network 面板开"Slow 4G"刷新一次。数字会替你说话。
