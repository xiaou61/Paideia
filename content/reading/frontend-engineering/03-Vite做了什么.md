## 这一关在解决什么

同一条命令的两头，行为完全不同：

```bash
npm run dev     # 改完立刻看到，1 秒内热更新
npm run build   # 等 20 秒，产出一个 dist/ 目录
```

它们不是"同一个程序的两种模式"，而是**两条几乎独立的流水线**。不理解这件事，就会反复遇到同一类问题：

- 本地改代码立刻生效，构建之后页面白屏，控制台只有 `Unexpected token '<'`；
- 本地 `import './Card'` 能跑（因为 Windows 不区分大小写），上线后 404（Linux 区分）；
- dev 里 `process.env.NODE_ENV` 有值，构建后变成 `undefined`。

这一关把这两条流水线各自在做什么讲清楚，以及哪些问题只会在其中一边出现。

### 开发服务器：不打包，只是"按需编译"

老一代打包器（Webpack 4 时代）在开发时也要**先把整个应用打成一个 bundle** 才启动服务器。项目一大，`npm start` 等 30 秒到两分钟是常态，改一行代码又要重新编译受影响的部分。

Vite 换了思路：**开发时根本不打包**。它只做三件事：

1. 起一个普通 HTTP 服务器，把 `index.html` 原样返回；
2. 浏览器按 ESM 规则自己 `import`，每请求一个模块，Vite 就**当场编译那一个文件**（TS→JS、JSX→JS 用 esbuild，毫秒级）；
3. 依赖提前处理一次，缓存起来复用。

所以不管你项目有 10 个文件还是 1000 个，**启动时间几乎不变**——因为启动时它只处理了入口那一个 HTML。

代价也很直接：模块是一个个请求的。所以 Vite 必须解决"请求太多"的问题。

### 预构建：把第三方依赖先揉成一个文件

`node_modules` 里的包有两个麻烦：很多是 CommonJS，而且一个包内部可能有几十个文件。如果每个都单独请求，光 lodash 就能发出上百个请求。

Vite 在首次启动时做一次**预构建**（pre-bundle）：

- 把每个依赖（及其内部文件）合并成**一个 ESM 文件**；
- 把 CommonJS 转成 ESM；
- 结果缓存到 `node_modules/.vite/`，下次启动直接复用。

这也是为什么第一次 `npm run dev` 会看到 "optimizing dependencies"，之后就不见了。改了 `vite.config` 或新增依赖时会重新构建一次。

### HMR：热更新能保留什么，不能保留什么

改一个文件，页面不刷新但效果出现——这叫 HMR（Hot Module Replacement）。机制是：Vite 通过 WebSocket 告诉浏览器"这个模块变了"，浏览器**只替换这一个模块**，并让引用它的地方重新执行。

关键在于"边界"：

| 你改的东西 | 效果 |
| --- | --- |
| 组件（有框架 HMR 插件） | 只重渲染，组件内部的 `useState` 保留 |
| 普通工具函数模块 | 引用它的模块被重新执行，可能整页刷新 |
| CSS | 直接替换样式表，不重载页面 |
| 环境变量 / `vite.config` | 必须重启服务器 |

HMR 保留状态是好事也是陷阱：你在表单里填了半天的内容，改代码后还在——于是你以为"状态没问题"，实际是 HMR 帮你保住了。要验证初始状态，得手动刷新一次。

### 生产构建：全量打包 + 摇树 + 压缩

`npm run build` 走的是完全另一条路：

1. **从入口开始完整解析依赖图**（不是按需，是一次全量）；
2. **tree shaking**：把 `import` 了但没用的导出剔除（前提是 ESM，见第 01 关）；
3. **压缩**：去空格、改短变量名、删死代码；
4. **产出带 hash 的文件名**：`index-QqLrqWYB.js`。

带 hash 是为了长缓存：文件内容变了 hash 就变，浏览器自然会拉新的；内容没变 hash 不变，可以放心让 CDN 缓存一年（第 10 关细讲）。

### 只会在其中一边出现的问题

这张表值得记下来，排查时按它对照：

| 现象 | 只在 dev 出现 | 只在 prod 出现 |
| --- | --- | --- |
| 路径大小写不一致 | 否（Windows/Mac 不敏感） | **是**（Linux 区分） |
| `process.env` 未替换 | 否 | **是** |
| 引用了 Node 内置模块（`fs`） | 一般会报错 | 构建期就失败 |
| 未使用的导出被打进包 | 否 | 否（两者都不该有） |
| 源码里的 `console.log` | 有 | 有（除非配置剔除） |
| 依赖只有 CJS 版本 | 预构建时转换，能用 | 打包器按配置处理，可能失败 |

最常见的一条是**路径大小写**：Windows 下文件系统不区分 `Card.tsx` 和 `card.tsx`，所以 `import './card'` 能跑；Linux 构建时找不到，直接 404 或构建报错。养成"路径与实际文件名完全一致"的习惯，能省掉一整类上线事故。

## 常见误区

### 误区：`npm run dev` 好使，`build` 就不会有问题

**你以为**：开发服务器已经把所有代码跑过一遍了。
**其实**：dev 只编译你**打开页面时实际请求到**的模块，而且是逐个处理的。构建会把整个依赖图一次性走完——那些从没被访问过的页面、只在特定条件下才 import 的模块，第一次见真章就是在构建时。
**怎么验证**：`npm run build && npm run preview`，然后在预览产物上把每个路由都点一遍。`preview` 起的服务器跑的是真产物，不是 dev 服务器。

### 误区：HMR 快，所以构建也一定快

**你以为**：开发时改一行毫秒级生效，打包应该也很快。
**其实**：HMR 的便宜来自"只处理一个文件"。构建必须全量：解析所有模块、跑 tree shaking、压缩、生成 source map。一个中等项目 20–60 秒是正常的。想更快就要靠构建缓存与并行（第 12 关讲）。
**怎么验证**：对比两者的耗时。如果构建时间在 CI 里比本地慢好几倍，通常是没缓存 `node_modules` 和构建产物。

### 误区：`dist/` 里的文件改了就能生效

**你以为**：直接把构建产物传到服务器，改改 HTML 就行。
**其实**：产物是经过压缩与重命名的，文件名带 hash，互相之间的引用写死在代码里。手动改一处，hash 与内容就对不上了，缓存策略随之失效。产物应该是**一次构建、原样部署**，要改就改源码重新构建。
**怎么验证**：随便改 `dist/assets/index-xxx.js` 里一个字符串再刷新——如果页面行为变了但文件名没变，缓存会让一部分用户永远拿到旧版本。
