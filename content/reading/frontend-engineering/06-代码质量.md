## 这一关在解决什么

一个项目的代码质量，最容易被两件事拖垮：

**① 风格争论**。code review 里一半的评论是"这里少个空格""这里该用单引号""函数后面要不要空行"。这类讨论没有对错，只有一致，但它消耗掉大量本该花在逻辑上的注意力。

**② 明显的错**。未使用的变量、`useEffect` 少写依赖、`==` 当成 `===`、`await` 忘了写。这些东西不需要"资深眼光"，需要的是一个每次都跑、不会累的检查。

这一关讲的是：怎么把这两类问题从"人盯"变成"工具挡"，以及在哪几个环节挡。

## 讲解

### 分工：ESLint 管语义，Prettier 管格式

这两个工具经常被混为一谈，但它们回答的问题完全不同：

| | ESLint | Prettier |
| --- | --- | --- |
| 管什么 | 这段代码**可能有问题** | 这段代码**长得不一致** |
| 会不会改代码 | 部分规则可以 `--fix` | 总是格式化，不判断对错 |
| 典型规则 | 未使用变量、`===` 缺失、hooks 依赖 | 缩进、引号、行宽、换行 |

一句话区分：**ESLint 会因为"这写法可能出 bug"报错，Prettier 只因为"这写法跟别人不一样"报错。**

所以风格类规则应该从 ESLint 里关掉，交给 Prettier。标准做法是在 ESLint 配置末尾加一条：

```js
// eslint.config.js
import prettier from 'eslint-config-prettier'

export default [
  // …你的规则
  prettier,   // 关掉所有与格式化冲突的规则
]
```

不加这一条，两个工具会互相打架：Prettier 把长参数换行了，ESLint 说不该换行；改回去 Prettier 又拆开。这种来回最消耗耐心。

### 该开哪些规则

不值得追求"规则全开"。规则越多，噪音越多，最后大家习惯性忽略报错。

按这三类开，覆盖大部分真实问题：

**潜在 bug（必须开）**

```js
'no-unused-vars': 'error',          // 死代码与写错的引用
'eqeqeq': 'error',                  // == 的隐式转换
'no-undef': 'error',                // 拼错变量名
'react-hooks/exhaustive-deps': 'warn' // effect 少依赖——前端最高频的真 bug
```

**可读性（建议开）**

```js
'no-console': ['warn', { allow: ['warn', 'error'] }],
'prefer-const': 'error',
```

**不要开**：任何纯风格规则（缩进、引号、分号）。它们由 Prettier 决定，开在 ESLint 里只会制造冲突。

### 三个关卡：编辑器、提交前、CI

工具跑在哪个环节，决定了它的实际效果：

```text
编辑器  保存时自动格式化 + 实时红线     ← 最快反馈，但可以关掉
提交前  只检查这次改动的文件            ← 挡住大部分
CI      全量检查，不通过就红           ← 真正的门禁
```

**提交前**用 `husky` + `lint-staged`：

```json
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,md}": ["prettier --write"]
  }
}
```

`lint-staged` 的关键是**只处理暂存区的文件**。全量 lint 一个中型项目要几十秒，每次都跑，人会开始用 `--no-verify` 绕过——那就等于没有。

**CI 必须是最后一道**。原因很简单：本地钩子可以被跳过（`git commit --no-verify`），也可以被某些图形化客户端忽略。CI 跑在服务器上，谁都没法绕。

### 一条经验：让检查"修得动"

如果一条规则报错，而它给的修改建议是明确可执行的（像格式、`prefer-const`），那就配 `--fix` 自动改。

如果一条规则经常报"你这里可能有问题"但没给出明确答案，而团队里没人处理——**把它从 error 降成 warn，或者干脆关掉**。一条永远亮着的警告，效果和没有检查是一样的，甚至会训练人忽略所有警告。

## 常见误区

### 误区：格式化是个人自由，不该强制

**你以为**：谁爱怎么写怎么写，反正编译结果一样。
**其实**：格式一致省的是**读代码**的成本。review 时 diff 里一半是空行变化，真正改的那三行就被淹没了；`git blame` 查责任时，格式化提交会污染历史。这跟"自由"无关，是协作成本。
**怎么验证**：把 `prettier --check .` 跑一遍，看有多少文件不符合。超过一半说明从没统一过，这时候一次性格式化 + 单独一个提交（不要混在业务改动里），之后就再也不用管了。

### 误区：本地提交钩子配好了，就不用 CI 了

**你以为**：提交时已经检查过，CI 再跑一遍是浪费。
**其实**：钩子是**可跳过的**——`--no-verify`、图形客户端、在别的目录直接 `git commit`。而且它只检查"改动的文件"，一次重构可能让别的文件与新类型不兼容，那类问题只有全量检查才能发现。
**怎么验证**：故意 `git commit --no-verify` 提交一个类型错误，看 CI 是否拦得住。拦不住，说明你的门禁只存在于自觉里。

### 误区：规则越多越专业

**你以为**：把 ESLint 规则开到 300 条，代码质量自然高。
**其实**：大量规则与项目实际无关（比如强制函数式、禁止 `for` 循环），它们制造的报错会让人形成"红色是正常的"这种习惯。等到真有 bug 的规则报警时，没人看。
**怎么验证**：数一下当前 warn 与 error 的数量。如果长期挂着几十上百个，说明这套规则已经没有约束力了——先清零，再谈加规则。

## 带走一句

**风格交给工具做决定，逻辑交给人和测试做决定**——把 review 的注意力从空格挪到边界条件上，这是这套工具唯一的价值。
