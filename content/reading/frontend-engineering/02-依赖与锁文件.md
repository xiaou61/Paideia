## 这一关在解决什么

打开一个跑了两年的项目，`node_modules` 可能有 800MB、两万多个目录。你能确定的是：**里面 99% 的代码不是任何人写的，而是装进来的**。真正的问题在于下面这三个：

- 你 `git pull` 之后 `npm install`，装出来的东西和同事那台机器**不完全一样**；
- `package.json` 里写着 `"lodash": "^4.17.0"`，你以为是 4.17.0，装进来的可能是 4.17.21；
- 你 `import` 了某个包，`package.json` 里却没有它，但它就是能跑。

这一关讲清楚：`npm install` 在做什么、版本号那个 `^` 到底放行了多少、为什么锁文件必须进 Git。

### `package.json` 只是"我要什么"，不是"装了什么"

```json
{
  "dependencies": {
    "react": "^18.2.0",
    "lodash": "~4.17.21",
    "dayjs": "1.11.10"
  }
}
```

三种写法的放行范围完全不同：

| 写法 | 允许装到 | 含义 |
| --- | --- | --- |
| `1.11.10` | 只有 1.11.10 | 精确锁定 |
| `~4.17.21` | 4.17.x 的最新 | 只接受补丁更新 |
| `^18.2.0` | 18.x 的最新 | 接受次版本更新 |

`^` 是 npm 装的默认。它意味着：今天装是 18.2.0，半年后别人装可能是 18.3.5——**中间所有 18.x 的变更都会被自动吃进来**。语义化版本约定次版本只加功能不改行为，但那是约定，不是物理定律。

还有一条容易忽略：**`0.x` 版本的 `^` 更保守**。`^0.2.3` 只允许 `0.2.x`，因为 0.x 阶段任何改动都算不兼容。看到 `0.x` 的依赖，默认它的 API 会变。

### 锁文件：让两台机器装出同一棵树

`package-lock.json`（npm）、`pnpm-lock.yaml`、`yarn.lock` 记的是**这次实际解析出来的每个包的确切版本与来源**。

区别很直白：

```text
package.json   我允许 18.x
lock 文件      这次装的是 18.3.1，来自 https://registry.npmjs.org/react/-/react-18.3.1.tgz
```

所以：

- **锁文件必须提交到 Git**。它保证 CI、同事的机器、你的机器装的是同一份代码。不提交锁文件，等于每次安装都重新赌一次版本。
- **`npm ci` 而不是 `npm install`**（CI 里）。`ci` 严格按锁文件装，锁文件与 `package.json` 不一致时直接失败；`install` 会顺手把锁文件更新掉——在流水线里这很危险，等于"CI 悄悄改了你的依赖"。
- **升级依赖是一个有意的动作**：`npm update` 或 `npm install react@latest`，改完跑测试，然后提交新的锁文件。而不是让它在你不知道的时候发生。

### `node_modules` 为什么是扁平的一坨

npm 早期是嵌套安装：每个包自己的依赖装在自己目录下。这样隔离性完美，但同一个包可能在几十个路径下各存一份，磁盘直接爆。

npm 3 之后改成**扁平化**：能提到顶层就提到顶层，真有冲突（两个包要不同大版本）才嵌套。

好处是体积小了，副作用是**幽灵依赖**：

```js
// 你的 package.json 里根本没有 lodash
import _ from 'lodash'   // 但能跑，因为某个依赖把它提到了顶层
```

它能跑，是因为别人装了。等那个依赖下个版本不再依赖 lodash，你的代码毫无改动地崩了——而且报错是 `Cannot find module`，看起来像你写错了导入路径。

**判断方法**：`npm ls lodash` 看它是不是被你的直接依赖带进来的；或者用 `pnpm` 这种默认不提升的包管理器，幽灵依赖会直接报错。

### 该不该装这个包：三个问题

安装前先问：

1. **它解决的问题，标准库或浏览器原生有没有**。`left-pad` 这种一个函数一个包的时代已经过去了，`Array.prototype.at`、`structuredClone`、`Intl` 现在都在。
2. **它的依赖树有多大**。一个包装的时候带进来 40 个传递依赖，那 40 个也是你要维护、要审、要等安全公告的。`npm view <pkg> dependencies` 能看直接依赖，`bundlephobia` 这类工具能看最终体积。
3. **它还在维护吗**。最后一次发布是四年前、开放的 issue 上千个没人回——那这个包的成本会由你承担。

## 常见误区

### 误区：`package.json` 写了版本号，装的就是那个版本

**你以为**：`"react": "^18.2.0"`，所以装的是 18.2.0。
**其实**：`^` 允许装 18.x 里最新的一版。只有精确版本（不带 `^`/`~`）才是"就是它"。所以"我本地是好的"这句话，只有配合锁文件才成立。
**怎么验证**：`npm ls react` 看实际装的版本；把 `package.json` 改成 `^18.0.0` 但不动锁文件，再 `npm ci`——装的仍然是锁文件里那个版本。

### 误区：锁文件冲突了，随便选一边就行

**你以为**：`git merge` 冲突，删掉锁文件重新生成最省事。
**其实**：重新生成会按当前 `package.json` 的范围装到最新的可用版本——可能一次带进几十个包的升级，且你完全没测过。锁文件冲突的正确做法是按业务意图合并两边（保留你新增的包 + 同事升级的包），然后跑一次完整安装和测试。
**怎么验证**：`git diff` 冲突的锁文件，通常只有几个包的 `version`/`resolved` 不同。数量少就直接手工选；数量多说明两边都在大改依赖，那本来就应该先对齐再合。

### 误区：装得多说明功能全，删依赖是浪费时间

**你以为**：反正都装进来了，留着没坏处。
**其实**：每个依赖都在三处收费——安装时间（CI 每次跑都要装）、构建时间（打包器要解析它）、安全面（它的漏洞就是你的漏洞）。一个大项目把没用到的依赖清掉，构建时间降一半很常见。
**怎么验证**：`npx depcheck` 列出 `package.json` 里声明了但代码里没导入的包；再看 `npm run build` 前后的耗时对比。
