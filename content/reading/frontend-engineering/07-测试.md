## 这一关在解决什么

前端测试最常见的两种失败：

**① 写了一堆测不到的**。花两天给每个组件写快照测试，UI 一改就红一片，维护成本比 bug 本身还高，最后整个 `__tests__` 目录被跳过。

**② 一个都不写**。每次改完手动点十分钟，点漏一个页面就是线上事故。

问题不在"要不要写测试"，而在**哪种测试测哪一层**。这一关讲：单元、组件、端到端各自能证明什么、证明不了什么，以及一个前端项目最该测的是哪几件事。

## 讲解

### 三层，成本与信心是反的

```text
        e2e        少    慢（几十秒/条）  信心最高：真的点了一遍
   组件测试        中    快（几百毫秒）   信心中等：渲染 + 交互 + 请求 mock
     单元测试      多    极快（毫秒）     信心最低：只证明这个函数对
```

越往下越快、越容易写、越只证明一小块；越往上越慢、越脆、越接近真实用户。

常见的错误是"倒金字塔"：e2e 写了 80 条，跑一次十分钟，其中一半的失败是"等待时间不够"而不是真 bug。正确的形状是小尖顶：**大量单元 + 适量组件 + 少量 e2e**。

### 单元测试：纯逻辑与边界

前端里真正适合单元测试的，是**没有 DOM、没有网络**的东西：

```ts
import { describe, expect, it } from 'vitest'
import { formatPrice, splitNickname } from './format'

describe('formatPrice', () => {
  it('保留两位小数', () => {
    expect(formatPrice(3)).toBe('¥3.00')
  })

  it('负数前面带负号', () => {
    expect(formatPrice(-3.5)).toBe('-¥3.50')
  })

  it('非数字返回占位符而不是 NaN', () => {
    expect(formatPrice(Number.NaN)).toBe('—')
  })
})
```

注意第三个用例：**它测的是"异常输入怎么办"**。边界条件才是单元测试的主战场——金额格式化、日期解析、权限判断、分页计算。这些函数一旦错，影响是全局的，而它们又最容易在重构时被悄悄改坏。

### 组件测试：测行为，不测结构

组件测试用 React Testing Library 这类工具，原则是一句话：**像用户一样找元素、像用户一样操作，然后断言屏幕上出现了什么**。

```ts
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { LoginForm } from './LoginForm'

it('邮箱为空时提示，且不提交', async () => {
  const onSubmit = vi.fn()
  render(<LoginForm onSubmit={onSubmit} />)

  await userEvent.click(screen.getByRole('button', { name: '登录' }))

  expect(screen.getByText('请填写邮箱')).toBeInTheDocument()
  expect(onSubmit).not.toHaveBeenCalled()
})
```

这里用 `getByRole`、`getByText` 而不是 `container.querySelector('.btn-primary')`，差别很大：

- 按 class 查，改样式就断——**测的是实现，不是行为**；
- 按 role 与文本查，等价于"用户能不能看见、能不能点到"——顺带把可访问性也测了。如果 `getByRole('button')` 找不到，说明这个东西对读屏用户也不存在。

**不该测的**：内部 state 变量、某个子组件被渲染了几次、DOM 结构长什么样。这些一改就该变的东西，测了只会变成维护负担。

### 端到端：只测主路径

e2e 用真实浏览器跑完整流程（Playwright / Cypress），成本最高。所以它只该覆盖**"挂了就代表业务挂了"的路径**：

- 能登录；
- 能进主页面并看到数据；
- 能完成一次核心操作（下单、提交、保存）。

一个项目 5–15 条 e2e 是健康区间。超过 30 条，通常会开始出现"为了让它稳定而加的等待与重试"比断言还多的情况。

写 e2e 的两条纪律：

1. **不要用固定 sleep**，用"等到某个可见状态"（`expect(locator).toBeVisible()`）。固定 `waitForTimeout(2000)` 在慢机器上照样失败，在快机器上白等。
2. **用可访问名或 `data-testid` 定位**，不要依赖 DOM 层级和 class。测试应该只关心"用户看到什么"，DOM 结构是随时会变的实现细节。

### 覆盖率不是目标

`--coverage` 报出来的 85% 很容易被当成 KPI，但它只说明"这些行被执行过"，不说明"结果对"。

```ts
it('能渲染', () => {
  render(<ComplexPage />)
})
```

这一条能刷出很高覆盖率，什么也没证明。

判断该测什么的实用标准是：**这段代码坏了，你会不会立刻知道？** 会（比如页面直接白屏），可以不测；不会（金额算错、权限判断反了、日期差一天），必须测。

## 常见误区

### 误区：测试要测实现细节，才能定位问题

**你以为**：断言内部 state 与调用次数，出错时更容易定位。
**其实**：断言实现细节的测试会在**每次合理重构时失败**，而重构后失败一次，人就开始怀疑测试而不是相信测试。它们还证明不了用户能不能用——内部 state 全对、界面显示错，测试照样绿。
**怎么验证**：试着把组件内部改写一遍（不改行为），看测试会不会红。红了说明它测的是实现，不是行为。

### 误区：测完就别动了，测试代码不用维护

**你以为**：测试是一次性投入。
**其实**：测试代码和业务代码一样会腐坏。过期的 mock、写死的等待、只断言"没抛错"的空测试，会让整套测试失去意义，却在 CI 里一直绿——这比没有测试更危险。
**怎么验证**：抽查最近的失败记录。如果失败的测试里有一半是"改了实现导致"而不是"真发现了 bug"，说明该删的没删。

### 误区：e2e 越多越安全

**你以为**：真实浏览器最可信，全用 e2e 最保险。
**其实**：e2e 的成本不只是跑得慢，还有**不稳定**——网络、动画、时间、并发都会让它偶发失败。偶发失败多了，团队就开始"重跑一次看看"，这时候 e2e 已经从门禁退化成噪音。
**怎么验证**：统计一周内 e2e 的失败中，有多少是重跑就过的。比例高，说明该往下沉——把那些细节移到组件测试里。

## 带走一句

**测试的目标不是覆盖率，是"改完敢不敢直接上"**——敢，就说明测到了该测的地方。
