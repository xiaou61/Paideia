## 这一关在解决什么

一个页面组件从 80 行长到 600 行，是这个行业最常见的演化：

```text
第 1 周   能跑就行
第 4 周   加了个筛选，又多 5 个 state
第 8 周   有人加了个弹窗，state 涨到 12 个
第 12 周  没人敢动这个文件，包括写它的人
```

到了这个阶段，"拆不拆"已经不是审美问题：**你每改一处都要把整个文件读完，才能确定不会碰坏别处**。

这一关讲的是拆分的判断依据——不是按行数，也不是按"看起来像不像一个模块"，而是按**变化**。

## 讲解

### 判断依据：这些东西会不会一起变

拆组件时最容易犯的错是"按视觉拆"：页面上有三块，就拆成三个组件。结果三块之间共享 8 个 state，拆完每个组件都要传一堆 props，比不拆还难改。

正确的依据是**变化频率与原因**：

| 现象 | 说明 | 怎么处理 |
| --- | --- | --- |
| 这两个区块总是同时改 | 同一个职责 | 留在同一个组件里 |
| 一个区块三个月没动过 | 稳定，变化少 | 可以独立出去，甚至不用再读它 |
| 加一个功能要动三个区块 | 职责被切碎了 | 合并，或把共享部分提出来 |
| 组件接了 10 个以上 props | 承担了多个职责 | 拆成"容器 + 若干展示组件" |

一句话：**一起变的放一起，不一起变的分开**。

### 三种边界

真实项目里，值得划的边界就这三种：

**① 数据边界：谁拥有这份状态**

状态应该放在**真正需要它的最小公共祖先**上，而不是图省事全提到页面顶层。

```tsx
// 反例：搜索词只有 SearchBar 和 ResultList 用，却提到了页面顶层
function Page() {
  const [keyword, setKeyword] = useState('')
  const [open, setOpen] = useState(false)      // 只有一个弹窗用
  // …8 个类似的 state 全在这
}

// 正例：把「搜索」这块整体收起来，状态跟着它走
function SearchSection() {
  const [keyword, setKeyword] = useState('')
  return (
    <>
      <SearchBar value={keyword} onChange={setKeyword} />
      <ResultList keyword={keyword} />
    </>
  )
}
```

状态一旦上提，页面组件就被迫知道所有细节；下沉之后，页面只负责"把这几块摆在哪"。

**② 展示边界：有没有副作用**

纯展示组件（只接收 props、只返回 JSX）可以随便复用、随便测。带请求、带订阅、带定时器的组件不行。

拆的时候把这两类分开：

```tsx
// 展示：给什么画什么，容易测，容易复用于别处
function UserCard({ user }: { user: User }) { … }

// 容器：负责取数、处理加载/错误，渲染交给展示组件
function UserCardContainer({ id }: { id: string }) {
  const { data, isPending, error } = useQuery(…)
  if (isPending) return <Skeleton />
  if (error) return <ErrorBox error={error} />
  return <UserCard user={data} />
}
```

**③ 复用边界：真的用了两次才抽**

"这个以后可能会复用"是最贵的假设。为一个还没出现的第二处用法做抽象，代价是现在就要维护一层间接，而且大概率抽错——等第二处真来了，你会发现它们需要的 props 完全不同。

规则很简单：**第二次出现时再抽**，且抽出来的是"两次用法共同需要的部分"，而不是第一次用法的完整复制。

### 抽 hook 而不是抽组件

有些逻辑不该变成组件（它不渲染任何东西），该变成 hook：

```tsx
// 组件里混着「取数 + 轮询 + 清理」
function Metrics() {
  const [data, setData] = useState(null)
  useEffect(() => {
    let alive = true
    const load = async () => {
      const r = await fetch('/api/metrics')
      if (alive) setData(await r.json())
    }
    load()
    const timer = setInterval(load, 5000)
    return () => { alive = false; clearInterval(timer) }
  }, [])
  return <Chart data={data} />
}

// 抽成 hook：组件回到「只关心渲染」
function useMetrics(intervalMs = 5000) {
  const [data, setData] = useState(null)
  useEffect(() => {
    // 同样的取数与清理
  }, [intervalMs])
  return data
}

function Metrics() {
  const data = useMetrics()
  return <Chart data={data} />
}
```

判断标准：**这块东西会不会渲染出界面**。会 → 组件；不会 → hook。

### 重构前先有安全网

拆分是"不改行为地改结构"，所以它天然需要能证明"行为没变"的东西：

- 有测试：改完跑一遍，绿了就继续；
- 没测试：先在关键路径上补 3–5 条组件测试，再动手。

没有安全网的重构，本质上是在赌博——而且赌注是别人的功能。这也是第 07 关的意义：**测试的价值在重构那一刻才真正兑现**。

## 常见误区

### 误区：组件行数超过 200 就该拆

**你以为**：行数是硬指标，超了就拆。
**其实**：一个 300 行的纯展示组件（比如一个复杂的报表）如果只有一处用法、内部没有状态纠缠，拆开只会让阅读时要跳三个文件。反过来，一个 80 行的组件如果同时管着取数、表单、弹窗，那才是该拆的。
**怎么验证**：看它的 `useState` 和 `useEffect` 数量。状态与副作用越多，说明承担的职责越多，与行数无关。

### 误区：先把组件拆细，将来好复用

**你以为**：提前拆成小零件，以后哪都能拼。
**其实**：没有第二处用法的抽象，几乎一定会抽错维度——你按"当时的样子"切，而第二处需求往往在另一个维度上。等到那时，你要么改坏第一处的用法，要么在旁边再写一个"差不多但不一样"的组件。
**怎么验证**：翻一下项目里那些"通用组件"目录，看有多少组件只有一个调用点。那些就是提前抽象的产物。

### 误区：prop drilling 只能靠状态管理库解决

**你以为**：props 传了三层，就得上 Redux / Context。
**其实**：大部分"传得深"的问题，根因是**状态放太高**。把状态下沉到真正需要它的那一层（组合组件、把 children 传下去、拆出容器），层级自然就短了。引入全局状态是最后手段，它的代价是"任何地方都能改它"，之后没人能说清一个值为什么变了。
**怎么验证**：先试着把状态挪到最近的公共祖先，看 props 层数会不会降到 2 层以内。多数情况下会。

## 带走一句
