## 拆文件省不了一个 props

最顺手的拆法是按界面块切：左边起始态、中间对话、右边侧栏、下面评分卡。我照着试了一次，先量了起始态那一块的调用点：

```tsx
// frontend/apps/app/src/pages/InterviewPage.tsx:371-387
<StartPanel
  intro={INTERVIEW_INTRO}
  role={role}
  season={season?.label ?? null}
  seasonFocus={season?.focus ?? null}
  busy={busy}
  preparing={preparing}
  adaptive={adaptive}
  onStart={() => { setConfirmStartOpen(true) }}
  resumes={resumeList.data}
  choice={resumeChoice}
  onChoose={setResumeChoice}
  onUpload={(file) => { void uploadResume(file) }}
  uploading={uploading}
  uploadedName={uploadedName}
  resumeError={resumeError}
/>
```

15 个 props。把它们搬到 `StartPanel.tsx` 之后，这 15 行一个字都不用改，父组件只是前面多一行 import。**减少 props 的唯一办法是让拥有这些 state 的那一层一起走**，删文件做不到。

这 15 个 props 分属 4 个变化源，这就是它搬不动的真正原因：

- 画像与求职季 5 个：`intro`、`role`、`season`、`seasonFocus`、`adaptive`。改画像结构、改季节文案，签名都变。
- 简历流程 7 个：`resumes`、`choice`、`onChoose`、`onUpload`、`uploading`、`uploadedName`、`resumeError`。它们背后是 6 个 `useState`（143–148）加一次取简历列表的请求（138）。
- 动作与忙碌 3 个：`busy`、`preparing`、`onStart`。
- 回调则全部反向穿过父组件。

同一个文件里能立刻搬走的只有三个：`Avatar`（1 个参数 `kind`，不读任何 state）、`TipCard`（0 props）、`Step`（3 个静态参数）。搬它们的收益是行数，不是耦合——调用点本来就只传数据。

真到要判断「这块该不该拆」的时候，按这个顺序看：

| 症状 | 先看哪 | 为什么 |
| --- | --- | --- |
| 加一个开关要改 4 个文件 | 这几个 props 的 state 在谁身上 | props 里每一项都是父组件的一个值或动作，换文件不减少 |
| 两处同一段 JSX 已经开始不一样 | 差异是漂移还是需求分叉 | 漂移就抽回来；真分叉就别硬合 |
| 1200 行，但最近 10 个提交没碰过它 | 最近改动集中在哪几个区间 | 不产生连带修改的区块先别动，拆它只多一层间接 |
| props 越加越多，测试也跟着改 | 从 state 到 DOM 最短的那条路径 | 中间隔的层越多，一次改动穿过的文件越多 |

那收益在哪？在同一天那个提交里也能看到反面证据：重构前，积分审计页的分页按钮已经漂成了原生 `<button type="button">`（`0ec1d093` 的父提交，第 265–283 行），其余四页用的是 `@paideia/ui` 的 `Button`。同一段界面，五份拷贝，四份一致一份不一致，而没人发现。抽出来之后这种漂移没有地方发生。

但别把话说过头：抽出来的组件收的是**形状**，不是差异。`query-state.tsx` 的注释里自己写着这句。2026-11-10 加「重试」时，组件本身 +16 行，六个调用点各 +5~6 行——因为文案、`testId`、`onRetry` 这些差异仍然逐点传。抽取不承诺「改一处全站生效」，它承诺的是「形状只有一份，不会各自变形」。

## 15 个 state 分四堆，只有一堆搬得动

按「谁在读」把 15 个 state 分一遍（行号是 `InterviewPage.tsx` 里的）：

| 这一堆 | state | 读它的地方 |
| --- | --- | --- |
| 起始态 | `resumeChoice`(143)、`uploadedName`(144)、`uploadedText`(145)、`uploading`(146)、`preparing`(147)、`resumeError`(148) | 371–387 的调用点、`start()`(279–316)、`uploadResume()`(319–332)、确认弹窗(528、534) |
| 对话 | `conversationId`(127)、`lines`(128)、`input`(129)、`busy`(130)、`error`(131)、`reviewing`(133) | `send()`(220–273)、`review()`(334–349)、对话区 400–489 |
| 评分 | `evaluation`(132) | 500 行的 `EvaluationCard`、186 行的离开拦截条件 |
| 弹窗 | `confirmStartOpen`(167)、`endConfirmOpen`(169) | 511、565 行两个 `Dialog` |

搬得动的是起始态那一堆，但有先后：

- `uploadedName`、`uploading` 只在 384、385 两个属性和 `StartPanel` 内部出现（733–780），页面别处一次都没读。这两个可以连渲染一起下沉，父组件不用知道「上传中」这件事。
- 另外四个不行。`resumeChoice` 和 `uploadedText` 被 `start()` 读（287–291），`preparing` 被确认弹窗读（528、534），`resumeError` 由 `uploadResume()` 写。只把 state 搬走，父组件反而要多传 4 个回调加 2 个 setter——props 从 15 变成 21。

所以判断「状态下沉到哪」不是找最近的公共祖先，是找**它唯一的读者**。找不到唯一读者（比如 `lines.length === 0` 决定整页渲染哪一屏，见 369 行），说明它是页面级状态，别搬。

顺带纠正一个我写过的方向：状态放太高、props 传三层时，先试下沉，别先上 Context。Context 的代价是「任何组件都能改它」，一个值为什么变了就再也说不清。顺序应该是：能不能跟着唯一的读者走 → 走不了就把「读 + 写」包成一个 hook → 还不行才考虑 Context 或 store。

## 不渲染的东西，抽不成组件

页面里有两段逻辑，谁看都觉得该抽出去，但抽成组件是错的：

- 152–164：第一次拿到简历列表时预选默认简历，用 `resumeInitialized` 这个 ref 防止覆盖用户的手动选择。
- 188–198：没出报告就离开时，给 `beforeunload` 挂拦截、卸载时摘掉。

判据只有一条：**它会不会渲染出界面**。会 → 组件；不会 → hook 或纯函数。上面两段都没有返回值。硬做成组件也能跑：`return null` 的函数组件照样挂在树里、照样跑自己的 hooks，框架不拦——但这只说明「能写」，不说明「该写」。它什么都没画出来，只多一层树节点。所以这两段该留成 hook，逻辑留在原地，调用点还是页面那一处。

本仓库 `packages/ui` 里三个导出的 hook 都是这个形状：`useAuth`（`packages/auth/src/auth-context.tsx:162`）、`useTheme`（`packages/ui/src/theme/theme-context.tsx:152`）、`useSourceReading`（`packages/ui/src/markdown/renderers/context.tsx:213`）——都只读 context，都不渲染任何东西。

至于这两段要不要现在抽，我倾向先不抽：`beforeunload` 那段只有 10 行、只被一个页面用、以后不会再出现第二个调用点；真出现第二个页面也要在「离开时拦一下」的时候再抽，那时你才知道两次的共同部分是什么（是拦截逻辑本身，还是那句提示文案）。为一个想象中的第二处用法先抽象，代价是现在就要维护一层间接。

## 跑一遍

```js
import { readFileSync } from 'node:fs'
import { basename } from 'node:path'

function splitProps(body) {
  const out = []
  let depth = 0
  let cur = ''
  for (const ch of body) {
    if ('{(['.includes(ch)) depth++
    if ('})]'.includes(ch)) depth--
    if (ch === ',' && depth === 0) { out.push(cur); cur = ''; continue }
    cur += ch
  }
  out.push(cur)
  return out.map((s) => s.trim()).filter(Boolean).map((s) => s.split('=')[0].trim())
}

function propsOf(text) {
  const found = []
  const re = /^(?:export )?function ([A-Z][A-Za-z0-9]*)\(\{/gm
  let m
  while ((m = re.exec(text)) !== null) {
    const name = m[1]
    const start = m.index + m[0].length
    const typeAt = text.indexOf('}: {', start)
    found.push(`${name}=${typeAt === -1 ? 0 : splitProps(text.slice(start, typeAt)).length}`)
  }
  return found
}

for (const file of process.argv.slice(2)) {
  const text = readFileSync(file, 'utf8')
  const lines = text.split(/\r?\n/)
  if (lines.at(-1) === '') lines.pop()
  const count = (re) => (text.match(re) ?? []).length
  const components = [...text.matchAll(/^(?:export )?function ([A-Z][A-Za-z0-9]*)\(/gm)].map(([, n]) => n)

  console.log(basename(file))
  console.log(`  行数 ${lines.length}（空行 ${lines.filter((l) => l.trim() === '').length}）`)
  console.log(`  import 语句 ${lines.filter((l) => l.startsWith('import ')).length}`)
  console.log(`  useState ${count(/const \[[^\]]*\] = useState/g)} / useEffect ${count(/useEffect\(/g)} / useRef ${count(/useRef[<(]/g)} / useMemo ${count(/useMemo\(/g)} / useCallback ${count(/useCallback\(/g)}`)
  console.log(`  模块级组件 ${components.length} 个：${components.join(' / ')}`)
  console.log(`  props 数：${propsOf(text).join('  ')}`)
  console.log('')
}
```

## 还差的

1. **这页没有 e2e。** `frontend/apps/app/e2e/` 下 28 个 `*.spec.ts` 里没有 interview，所以我上面说的「先补安全网再动手」，在这个文件上我自己没做到：只写了度量脚本，没补测试，也没真拆。真要动它，第一步是补一条「选简历 → 开始 → 发一轮 → 生成点评」的用例。
2. **6 个简历 state 的下沉只是量了依赖，没执行。** 真要搬，`start()`(279–316) 和 `uploadResume()`(319–332) 得一起搬，那会动到「上传失败还要不要继续开面」的行为边界（294 行的注释写着按无简历继续），没有测试不敢改。
3. **脚本有盲区。** 它只认 `const [x, setX] = useState` 这一种写法：`useReducer`、从自定义 hook 里返回的状态、以及用 `useState(() => ...)` 惰性初始化的都数不出来；`props 数` 也只数解构形式，`props` 整个接收再 `props.xxx` 用的组件会显示 0。另外它不统计 `useContext` 读取，所以「共享状态位置」这一项只能人肉看。
4. **行数收益是 git 统计，不是运行时指标。** `--numstat` 数的是改动行数，跟首屏、包体积没关系。抽组件对产物大小与渲染次数的影响我没测——那属于第 09、10 关的范围，这里不给结论。
