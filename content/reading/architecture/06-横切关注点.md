## 先把结论摆出来

鉴权、限流、日志、开关这类"每个接口都要"的东西，放在哪一层，只看一个判据：

**它需不需要知道业务数据？**

- 不需要（谁在请求、来源 IP、路径、耗时）→ 放**最外层**：过滤器、拦截器、网关；
- 需要（"这个人能不能改这条笔记"）→ **贴着数据放**：在服务里，用那条数据本身判断；
- 两者都要 → 拆成两段，外层做粗判（有没有登录），内层做细判（是不是你的）。

先看三个症状：

1. 权限判断写在 Controller 里，靠"记得加一行注解"；
2. 规则写错了不报错，也不生效——直到某天发现任何人都能改别人的数据；
3. 限流按"每个请求都计数"做，正常用户登录几次就被封。

## 四种载体，按"离业务多远"排

| 载体 | 能看到什么 | 适合 |
| --- | --- | --- |
| 过滤器 / 网关 | 请求本身（路径、头、来源） | 认证、CORS、压缩、全局日志、粗粒度限流 |
| 拦截器 / 中间件 | 请求 + 路由 + 会话 | 权限的路径级规则（`/admin/**` 要管理员） |
| AOP / 装饰器 | 方法名、参数、返回值 | 事务、计时、缓存、重试 |
| 服务内部 | 业务数据与不变式 | "这条笔记是不是你的"、"余额够不够" |

**越往外，能看到的业务信息越少，规则越粗；越往里，规则越准，但越容易漏。**

这就是为什么"所有权限都放网关"和"所有权限都写业务代码"都不对：认证（你是谁）在最外层，鉴权（你能不能做这件事）必须在数据旁边。

## 横切规则最危险的失败模式：静默失效

横切的代码不在主流程上，**写错了往往不报错，只是永远不生效**。看三个真实例子。

**例子一：路径规则的顺序。**

Spring Security 按声明顺序取第一个匹配的规则。如果 `/api/v1/knowledge/admin/**` 要管理员这条，写在 `anyRequest().authenticated()` 后面，它就**永远不生效**，而且没有任何警告。表现为：任何登录用户都能改知识库。

所以这类规则必须满足两点：

1. **具体规则写在宽规则之前**；
2. **有一条测试真的去撞它**（用普通用户 token 调管理端写接口，断言 403）。

本项目的安全配置里，每一条 admin 规则上方都写着"必须排在 anyRequest 之前"，并注明"顺序写反这条永不生效、也不会有任何报错"。这不是啰嗦——这是踩过的坑被写成了注释。

**例子二：放行前缀的纪律。**

`/api/v1/auth/**` 整体放行（登录、注册、刷新、验证码）。这个前缀一旦被挂上一个读业务数据的接口，它就会**默默变成公开接口**，没有任何配置会提醒你。

这一类"靠约定而不是靠配置"的规则，只有两个办法守住：注释写清边界，加一条测试遍历该前缀下的端点，断言只有预期的那几个。

**例子三：限流只统计失败。**

登录限流的直觉写法是"每次调用都计数"。结果是：一个正常用户一天登录三次，就被自己的成功次数封了。

正确做法是**只统计失败**，并且按两个维度分别限制：

- 按账号：防止有人盯着一个账号撞库；
- 按来源：防止一台机器换着账号试。

失败后重置的窗口、成功是否清零，都要明确写出来，否则调参时没人知道现在的行为是什么。

## 粗判与细判：一个功能里的两段权限

以"删除一条笔记"为例：

```text
外层（拦截器）：有没有登录？           → 401
服务内（业务）：这条笔记是不是你的？    → 403 / 404
```

为什么不在外层把"是不是你的"也做了？因为外层拿不到笔记，要么再查一次库（多一次查询，还可能有竞态），要么把规则写在路径上（`/notes/{id}` 看不出归属）。

**归属判断必须和读取那条数据在同一个地方**，最好是同一句 SQL 的 `WHERE` 里：

```sql
DELETE FROM notes WHERE id = ? AND user_id = ?
```

影响行数为 0 就返回 404。这样"不是你的"和"不存在"对外表现一致，也不会泄露"这个 id 存在"。

## 限流的三个参数，比"限多少"更重要

限流真正难的不是数值，是这三件事：

1. **按什么维度**：账号、IP、接口、租户。维度选错，限流要么误伤要么形同虚设。
2. **统计成功还是失败**：上面说过，登录这类接口只统计失败。
3. **被限之后返回什么**：明确的状态码（429）+ 还要等多久。不要返回一个含糊的 500，那会让调用方一直重试。

一个提醒：单机限流只在单进程下成立。多实例部署时，要么用共享存储（Redis）计数，要么在网关做，要么接受"每个实例各自限一份"——**最后一个选项经常是可以接受的，但你要知道自己在接受什么。**

## 配置、开关与"改配置+重启"

配置不是一类东西，至少分三层：

| 层 | 例子 | 改动代价 |
| --- | --- | --- |
| 代码常量 | 分页大小上限、密码最小长度 | 发版 |
| 启动配置 | 数据库地址、签名密钥、是否允许临时密钥 | 改配置 + 重启 |
| 运行时开关 | 某个功能灰度、某个模型停用 | 改库 + 下次请求生效 |

判断标准：**它变了要不要让所有实例同时看到？** 要，启动配置就够；不需要，运行时开关更灵活，但要多一套读写与缓存失效。

配置上最容易犯的错是**静默降级**。本项目的签名密钥缺失时，选择的是**启动失败**，而不是随机生成一个：

> 随机密钥的后果是：重启后所有令牌失效、多实例之间无法互验。而"静默用随机密钥"会让这个问题只在运行时暴露。

这就是配置的纪律：**能在启动时发现的错误，不要留到运行时。**

## 日志：记什么，不记什么

日志是横切里最容易被忽视的一处，两个规矩：

- **结构保留、值脱敏**：记"调用了哪个工具、耗时多少、结果多大"有用；记完整请求体、完整模型回答没用，还惹祸。
- **敏感值不进日志**：密码、验证码、签名 URL、令牌。带签名的 URL 等同于读取权限，写进日志等于把权限发给所有能看日志的人。

一条能自我检查的标准：**把日志给一个外部的人看，会不会泄露用户数据？** 会，就说明记多了。

## 开关的三种实现与淘汰机制

| 实现 | 谁能改 | 多久生效 | 适合 |
| --- | --- | --- | --- |
| 代码常量 | 开发 | 发版 | 几乎不变的安全参数、分页上限 |
| 启动配置（环境变量/配置文件） | 运维/开发 | 重启 | 数据库地址、密钥、上游开关 |
| 数据库开关 | 管理员 | 下次请求（或缓存过期） | 灰度、降级、单用户白名单 |

三种的测试成本完全不同：常量在单测里，启动配置在集成测试里，数据库开关则需要**两种状态都测**。所以开关越少越好，每个都要有：

- **所有者**：谁负责删它；
- **过期条件**：什么发布之后它就没用了；
- **默认值**：读不到时是开还是关（这个默认值经常比开关本身更重要）。

一个能执行的做法：开关记录在一个清单里，每次发版检查一遍，超过一个发布周期还在的，问一句"它现在控制什么"。答不上来就删。

## 限流放在哪，以及一个顺序问题

| 位置 | 计数范围 | 适合 |
| --- | --- | --- |
| 单机内存 | 每个实例各自一份 | 单实例、或"每台机器限一份"可以接受 |
| 网关 | 全局限流 | 多实例、按路径/IP 限 |
| 共享存储（Redis） | 全局精确 | 按用户/租户的精确配额 |

顺序也有讲究：**越便宜、越不需要身份的检查越靠外**。

```text
限流（按来源 IP，最便宜）→ 认证（解析令牌）→ 限流（按账号，需要身份）→ 业务
```

把便宜的放前面，能在攻击流量到达鉴权之前就挡掉一部分；而需要账号维度的限流只能放在认证之后。反过来（先认证再按 IP 限流），等于让每个恶意请求都白做一次令牌解析。

## 常见误区

### 误区：横切的东西都放网关

**你以为**：网关是统一入口，所有校验都在那里做最省事。
**其实**：网关看不到业务数据。"这个用户能不能改这条笔记"在网关里要么做不了，要么要再查一次库——而查库的网关就又变成了业务服务。
**怎么验证**：问"这条规则需要读哪张表？"需要读表，就不该在网关。

### 误区：权限在 Controller 里判一次就够了

**你以为**：接口入口处判了角色，里面就安全了。
**其实**：角色只回答"是不是管理员"，回答不了"是不是你的"。真正的越权通常发生在"有权限的人访问了不属于他的数据"。
**怎么验证**：用两个普通用户互相访问对方的资源 id，看是不是 403/404。能读到就是缺归属判断。

### 误区：开关越多越灵活

**你以为**：每个功能都加一个开关，出问题随时关掉。
**其实**：每个开关都是一条新的代码路径，测试要翻倍，组合起来的状态没人验证过。开关过期不删，半年后没人知道它控制什么。

## 小结

横切关注点按"离业务多远"分层：外层做认证与粗限流，业务里做归属与额度，方法级做事务与计时。每个规则都要能被测试撞到，因为它们的典型失败方式是**静默失效**。

配置遵守一条纪律：能在启动时发现的错误，不要留到运行时；日志遵守一条：把日志给外人看不会泄露用户数据。

下一篇讲"看不见的结构"——可观测性。它决定你出事以后是五分钟定位，还是两小时猜。

这条线到这里结束第六篇。它讲的其实是：**横切的代码不在主流程上，所以它坏了也不会有人喊。**
