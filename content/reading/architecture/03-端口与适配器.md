## 先把结论摆出来

**端口是业务对"我需要什么能力"的描述，适配器是这个能力的具体实现。** 业务代码只依赖端口，不 import 任何基础设施 SDK。


它值钱的地方只有一个：**能不能换**。而"以后能换"这句话，只有在**同一个抽象下存在两个实现、并且同一批断言在两个实现上都跑过**时才成立；否则它只是一句口号。

先看三个症状，中了就是没有端口：

1. 业务代码里出现 `S3Client`、`HttpClient`、某个厂商的 SDK、`System.currentTimeMillis()`；
2. 单元测试想跑，必须先起数据库、连对象存储、配好密钥；
3. 领导说"换成另一家"，你先去 `grep` 有多少个文件 import 了旧 SDK。

## 端口长什么样：用业务语言，不用实现语言

反面教材是这样的接口——它只是把 SDK 的方法名换个皮：

```java
interface Storage {
    PutObjectResponse putObject(PutObjectRequest request);
}
```

这个接口什么问题都没解决：业务还是要构造 `PutObjectRequest`，还是知道分片、元数据、桶名。换一个存储厂商，参数结构全变。

正面形状是用**业务需要的最小能力**描述：

```java
public interface FileStorage {
    String put(byte[] content, String contentType);
    Optional<byte[]> read(String id);
    boolean delete(String id);
    default Optional<String> presignedGetUrl(String id, Duration ttl) {
        return Optional.empty();
    }
}
```

四个决定，每个都有理由：

- **`put` 只要字节和类型**。业务不知道也不关心分片、桶、区域。
- **`read` 返回 `Optional`**：文件不存在是**正常可预期的状态**，不是异常。用异常表达"没有"，调用方每次都要 try-catch，还容易吞掉真正的错误。
- **`id` 是不透明标识**。调用方不许解析它、不许假定它等于磁盘文件名。这条约束写在接口注释里，也被契约测试钉住——因为读取端点免鉴权，**id 不可枚举是唯一的安全前提**。
- **`presignedGetUrl` 是 `default` 方法**：端口的必答项仍然只有三个；"能不能直读"是**能力**，不是**义务**。本地磁盘没有"直读"这种东西，返回空，调用方照旧流字节；对象存储实现返回带签名的 URL。这样加一个能力，不会强迫所有实现都写一个假方法。

这就是好端口的形状：**方法少、参数是业务概念、缺省行为有明确语义。**

## 可替换性怎么证明：一份断言，跑两个实现

本项目有一个 `FileStorageContractTest`：同一批断言，跑在本地磁盘实现和 S3 实现上。

它测的不是"代码覆盖率"，而是"这段契约在两种实现下都成立"：

- 存进去再读出来，内容一致；
- 读一个不存在的 id，返回空而不是抛异常；
- id 必须是 UUID，非 UUID 一律当不存在（**安全前提也是契约的一部分**）；
- 删除后再读，返回空。

对象存储那个实现需要真的连上服务，所以它以环境变量为开关**跳过而不是失败**——本机没有隧道时不应该红。这一点很重要：**契约测试不能因为环境缺失而变成"永远不跑"**，也不能因为环境缺失而让人误以为功能坏了。

判断你自己的端口有没有被证明，只问一句：**同一批测试，能不能在第二个实现上直接跑？** 不能，说明测试写的是实现，不是契约。

## 什么时候端口是过度设计

不是所有外部依赖都值得包一层。三个信号说明你包多了：

1. **只有一个实现，且确定不会换**。比如业务只可能跑在 MySQL 上，包一层 `Database` 接口只会让每个查询多绕一次。
2. **端口方法跟具体实现一一对应**。`getPresignedUrlForObjectWithExpiry` 这种名字，说明抽象漏了。
3. **端口数量爆炸**。每个数据库表配一个端口、每个外部接口配一个端口，代码量翻倍，换来的"灵活性"没人用过。

判断顺序：

```text
这个依赖会不会换？
  ├─ 不会，且不跨进程 → 直接用，别包
  ├─ 不会，但要单元测试 → 包一层（主要为了测试）
  └─ 会换 / 有多个环境（本地、测试、生产） → 值得包
```

**测试性**经常比"可替换"更值钱：包一层之后，业务逻辑的测试不用连外部服务，跑得快、结果稳定。这一个理由就够。

## 一个真实的取舍：加能力，还是改契约

前面那个 `presignedGetUrl` 是后加的。当时有两条路：

- **改必答项**：三个已有实现都得实现它，本地实现只能返回空或编一个假 URL；
- **加 default 方法**：本地实现什么都不用做，行为与之前完全一致。

选了第二条。原因是：**端口的必答项越少，实现越容易写对。** 一个实现被迫实现一个它根本不支持的能力，最后一定写出一个"看起来能跑、实际永远返回空"的方法，而这个空值会一路传到调用方，变成一个很难查的 bug。

代价也有，而且真实：默认返回空意味着调用方必须处理两条路径（直读 / 流字节）。这不是"抽象没做好"，而是**本地存储和对象存储的能力本来就不同**——把差异藏在统一接口里，只会让调用方在别处踩到。

## 端口和模块的关系

上一篇说过：接口定义在**调用方**，实现放在**提供方**。

```text
paideia-knowledge/ReviewQuestionPort        ← 我需要"出一道题"
paideia-ai/.../ReviewQuestionGenerator      ← 我来实现
```

同一条规矩也适用于基础设施：`FileStorage` 定义在业务模块里，`LocalFileStorage` / `S3FileStorage` 是它的两个适配器，**用配置选择哪个生效**。业务代码里没有任何一行知道当前用的是磁盘还是对象存储。

这才是端口的完整形态：**业务定义需求，实现可以插拔，选择发生在装配层。**

## 端口的三种粒度

不是所有端口都一样大。按粒度分三层，选择时各有依据：

| 粒度 | 例子 | 稳定性 | 适合 |
| --- | --- | --- | --- |
| 数据访问端口 | `OrderRepository`（按聚合） | 跟着数据模型变 | 要换存储、要脱离数据库测试 |
| 能力端口 | `FileStorage`、`ReviewQuestionPort`、`EmailSender` | 跟着业务需求变 | 业务要"做一件事"，不关心怎么做 |
| 供应商端口 | `ModelClient`、`PaymentGateway` | 跟着外部 API 变 | 同一类供应商有多家、或经常换 |

**粒度越粗越稳，越细越容易泄漏实现。** 一个每张表一个端口的设计，看起来整齐，实际是把数据库结构抄了一遍——表改了端口就要改，调用方也要改。

选择顺序：先问"业务需要的是数据还是要完成一件事"。需要完成一件事（存文件、出题、发信），用能力端口；需要按条件查询、且确实可能换存储，才用数据访问端口。

## 换实现自检清单

准备把一个外部依赖包起来时，过一遍这五条：

1. **有几个实现？** 一个，且确定不换——先别包，或者只为测试包。
2. **接口方法名像谁？** 像 SDK，说明抽象漏了；像业务，说明对了。
3. **两种实现的差异写下来了吗？** 直读、有效期、删除语义、一致性——差异会在某处出现，提前知道比事后踩好。
4. **有契约测试吗？** 同一批断言能在两个实现上跑，才算可替换。
5. **换实现要改几处装配？** 一处（配置）是真端口；到处改是假抽象。

## 一个真实的能力差异表

本地磁盘和对象存储，同一个端口下，行为差得比想象中多：

| 能力 | 本地磁盘 | 对象存储 |
| --- | --- | --- |
| 直读 | 没有 | 预签名 URL，有有效期 |
| 删除 | 立即、幂等 | 通常最终一致，可能产生删除标记 |
| 覆盖 | 直接覆盖 | 覆盖也是新版本 |
| 读不存在 | 返回空 | 可能抛异常或返回空，取决于实现 |
| 成本 | 磁盘 | 按存储与流量计费 |

这张表说明一件事：**端口统一的是调用方的写法，不是能力本身。** 调用方必须知道"直读可能没有""URL 会过期"，否则换实现那天，一个"永远返回空"的分支会让图片全部不显示——而编译、测试可能都是绿的。

## 常见误区

### 误区：端口就是 interface

**你以为**：把类抽成 `interface + impl` 就是端口。
**其实**：接口可以只是"换个文件写实现"，端口的关键是**业务语言 + 依赖方向**。如果接口方法名和 SDK 一模一样，业务还是在依赖那个 SDK 的模型。
**怎么验证**：让一个不懂这个厂商 API 的人读接口，能不能说出"业务需要什么"。说不出来，就是抽象漏了。

### 误区：抽象层可以消除成本

**你以为**：加了端口，换实现就零成本。
**其实**：端口只消除**调用方**的改动，不消除**能力差异**。本地磁盘没有直读、对象存储的 URL 有有效期、不同厂商的一致性语义不同——这些差异一定会在某处出现，要么在端口里，要么在调用方。
**怎么验证**：列一张"两种实现的差异表"。差异为空，说明抽象是假的（你把一个实现当成了标准）；差异很多，说明端口设计要重新看。

### 误区：每个外部依赖都该包一层

**你以为**：包得越多越"架构"。
**其实**：每多一层，就多一处要维护、要测试、要解释的代码。只有"会换""要测试""多环境"三种情况值得包。
**怎么验证**：数一数过去一年真正换过的实现。零次，而端口有十个，那就是自我感动。

## 小结

端口是业务对能力的描述，适配器是具体实现。好端口方法少、参数是业务概念、缺省行为有明确语义；它的价值由**第二个实现 + 同一批契约测试**证明，不是由接口的数量证明。

真正要记住的一句：**抽象不会消除差异，只会把差异挪到一个你看得见的地方。**
