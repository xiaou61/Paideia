## 先把结论摆出来

**架构评审不是挑技术名词，是问五个问题。** 而这五个问题里，至少有三个是在问"**你为什么不做**"。

大多数架构事故不是"没做够"，是"做多了"：三个人做一个后台，先上了微服务、消息队列、CQRS、多租户，最后 80% 的复杂度花在维护这些结构上，业务功能反而没人写。

这一篇给三样东西：评审的五个问题、十个"现在还不该做"的信号、面试里怎么答架构题。

## 五个问题

| 问题 | 好答案的样子 | 坏答案的样子 |
| --- | --- | --- |
| 1. 变化点在哪？ | 具体到"这里会换供应商""这里会多一个调用方" | "以后可能会扩展" |
| 2. 边界对不对？ | 谁能调谁、数据归谁，违反时构建会失败 | "我们约定不跨模块" |
| 3. 最坏情况是什么？ | 数据量、并发、上游挂掉、重试风暴，各有应对 | "量不大，没问题" |
| 4. 失败怎么被发现？ | 有 trace、有指标、有告警，能定位到哪一步 | "看日志" |
| 5. 怎么回滚？ | 具体操作、耗时、会丢什么数据 | "重新发一版修掉" |

**问题一决定要不要加结构**：说不出具体变化点，就不该为它抽象。

**问题二决定结构对不对**：边界要有构建期检查，约定不算。

**问题三决定容量与降级**：不用算到很准，但要知道"十倍流量会先死在哪"。

**问题四决定你能不能睡觉**：没有可观测性的系统，出事只能等用户告诉你。

**问题五决定你敢不敢发**：回滚方案写不出来的发布，本身就是一次赌博。

## 十个"现在还不该做"的信号

按"最常见的过度设计"排序，每一条都附一个反例式的判断：

| 想做的事 | 先问自己 |
| --- | --- |
| 拆微服务 | 团队冲突、扩缩容差异、故障隔离，三个信号有吗？没有就先模块化单体 |
| 上消息队列 | 有跨进程调用方吗？没有就是多一个要运维的组件 |
| 上 CQRS / 读写分离 | 列表页慢，是缺索引还是缺读模型？先加索引 |
| 事件驱动一切 | 订阅方有几个？一个且必须成功，就是普通调用 |
| 多租户 | 现在有几个租户？一个的话，租户 id 只是未来的迁移成本 |
| 自研框架 / 脚手架 | 标准库和现有依赖哪里不够？说不出来就是重造 |
| 给每个类配接口 | 有几个实现？没有第二实现，接口只是多一个文件 |
| 提前加缓存 | 慢在哪里？没测过就加缓存，是用一致性换一个猜测 |
| 分库分表 | 单表多少行、慢查询是哪条？先看索引和执行计划 |
| 插件化 / 平台化 | 有几个插件作者？一个都没有，就先把第一个功能写直白 |

这张表的用法不是"全都别做"，而是**每条都要能说出"现在不做，什么条件下再做"**。说不出来，多半只是焦虑。

## 决策记录：一页纸，写"放弃了什么"

每个重要决定都值得留一页记录，格式固定：

```text
背景：为什么现在要做这个决定（约束是什么）
选项：考虑过哪几条路，各自代价
选择：选了哪条，为什么
放弃：为此放弃了什么（性能？一致性？开发速度？）
重评：什么条件下应该重新考虑（流量？团队规模？供应商变化？）
```

最关键的是**"放弃"这一栏**。半年后有人问"当初为什么不用 X"，答案通常不是"X 不好"，而是"我们当时更怕 Y"。把怕什么写下来，比把选什么写下来更有用。

"重评条件"同样重要：它让这个决定有寿命，而不是变成一条没人敢碰的祖训。

## 面试里怎么答架构题

面试官问"设计一个短链服务""设计秒杀"，真正在看的不是你会不会背组件，是**你会不会从约束出发做取舍**。

一个能得分的答法，顺序是这样：

1. **先问量级**：多少读、多少写、数据留多久。没有量级就没有架构。
2. **找不变式**：短链不能重复、跳转必须快、统计不能丢——这几条决定存储与缓存。
3. **说清最小方案**：一张表 + 唯一索引 + 缓存，先让它跑起来。
4. **指出它会在哪里先坏**：热点 key、缓存击穿、id 生成冲突。每一条给一个应对，并说明代价。
5. **主动说不做什么**：这个阶段不做分库分表、不做多机房，理由是什么。
6. **讲失败与回滚**：缓存挂了怎么降级、写失败了怎么重试、数据错了怎么修。

第 5、6 步最能拉开差距。大部分人只会往前设计，不会说"这里我选择不做"和"这里坏了怎么办"。

## 一次评审的走法（案例）

需求：给现有系统加"导出报表"，数据量十万行，用户点一下要等十几秒。

按五个问题走一遍：

**1. 变化点在哪？** 报表种类会增加（现在三种，以后可能十种），数据源短期不变。结论：导出逻辑要能按报表类型扩展，但不需要为"换数据源"抽象。

**2. 边界对不对？** 导出属于报表能力，读的是业务数据。它不该直接查别的模块的表，应该调对方的查询接口。若查询很重，可以单独建读模型，但那是后话。

**3. 最坏情况？** 十万行 × 并发十个人 = 一次性把数据库打满；内存里拼一个大字符串会 OOM。应对：分批查、流式写、并发限制（同时只允许两个导出任务）。

**4. 怎么发现失败？** 导出任务要有状态（排队/生成中/完成/失败）与耗时指标；失败率超过阈值告警。用户能看到"失败了，重试"而不是一个转圈。

**5. 怎么回滚？** 新功能，关掉入口即可；不涉及数据结构变更，回滚零损失。

**被否掉的方案**：引入消息队列 + 独立导出服务。理由：现在没有跨进程需求，一个数据库任务表 + 后台轮询就能做；上了 MQ 要多一套部署、监控与重复消费处理，换不来任何用户可见的收益。

**被接受的复杂度**：一张任务表 + 一个后台轮询 + 并发上限。这三样都是能在一个进程里说清楚的。

这个案例的要点不是"导出怎么做"，而是**每一个被否掉的复杂度，都有一个明确的"什么时候再考虑"**：并发导出超过十个、单次超过百万行、或者导出拖垮了主库，那时再拆服务。

## 架构债怎么记

过度设计会留下"以后再说"的债，欠着不记，最后没人知道它存在。一页清单，四列：

| 欠什么 | 为什么现在不还 | 还的触发条件 | 影响面 |
| --- | --- | --- | --- |
| 单机限流 | 只有一个实例 | 上第二个实例时 | 限流会被放大 N 倍 |
| 导出同步执行 | 现在只有三种报表 | 单次超过 30 秒 | 接口超时、连接被占 |
| 手写分页 | 数据量小 | 单表超过百万行 | 深分页变慢 |

这张表的作用是**把"已知的将就"和"未知的漏洞"分开**。评审时加一条、还完删一条，比任何架构图都更能说明系统现在的真实状态。

## 常见误区

### 误区：评审就是比谁的名词多

**你以为**：能说出更多架构模式、更多中间件，就显得更专业。
**其实**：评审的价值在于**减少不必要的复杂度**。一个能把"为什么现在不做微服务"讲清楚的人，比一个能背十种架构图的人更可信。
**怎么验证**：评审结束时数一下"删掉了哪些设计"。一个都没删，这次评审大概率只是走流程。

### 误区：设计文档越厚越好

**你以为**：文档写五十页，说明想得周全。
**其实**：厚文档通常意味着没做决定——把所有选项都列上，等于把选择留给实现的人。好文档是一页纸：背景、选项、选择、放弃、重评条件。
**怎么验证**：看文档有没有明确写"我们选了什么、放弃了什么"。没有，就是资料汇编，不是决策记录。

### 误区：架构题有标准答案

**你以为**：面试官心里有一个"正确架构"，答不到就扣分。
**其实**：面试官在看你如何**在约束下取舍**。同样一个问题，日活一千和日活一亿的答案完全不同；能说出"这取决于量级"并且给出两套方案，才算答对。
**怎么验证**：你的答案里有没有出现具体数字与失败场景。全是组件名，就是背的。

## 小结

评审问五个问题：变化点、边界、最坏情况、怎么发现、怎么回滚。大多数过度设计都能用一句"现在不做，什么条件下再做"挡回去。决策记录写清"放弃了什么"和"重评条件"。

这条线到这里结束。十篇讲的其实是同一件事：**架构不是把系统做复杂，而是用最少的结构，把未来确定会发生的那些变化关在该关的地方。**

回到开头那句话：架构是一组会被后来的改动反复惩罚的决定。你现在做的每一个选择，半年后都会以"改这里要不要动那里"的形式回来找你。

这条线到这里结束第十篇。它想说的是：**最好的架构，是让你在需要的时候还能改。**
