## 先把结论摆出来

**可观测性不是"多打日志、装个监控"，而是让系统能回答三个问题：**

```sketch
{
  "title": "可观测性要能回答三个问题",
  "rows": [
    [
      { "id": "what", "title": "发生了什么", "sub": "日志与事件", "tone": "blue" },
      { "id": "why", "title": "为什么", "sub": "链路追踪与指标", "tone": "blue" },
      { "id": "who", "title": "影响了谁", "sub": "SLO 与用户维度", "tone": "green" }
    ]
  ],
  "arrows": [
    { "from": "what", "to": "why" },
    { "from": "why", "to": "who" }
  ]
}
```

1. 一个请求经过了哪几步，每一步花了多久？（**追踪**）
2. 一次失败是哪个环节、哪一类原因？（**归因**）
3. 系统整体是变好了还是变坏了，坏在哪个指标上？（**度量**）

这三件事必须在**设计结构的时候**一起想，因为它们要求代码里留出"步骤"这个单位。事后再补，不是加几行日志，而是要把整条链路拆开重写——成本大约是三倍。

先看三个症状：

1. 用户说"刚才失败了"，你只能回答"我看看日志"，然后在几千行里翻；
2. 账单说这一轮花了三毛钱，你说不出花在模型、工具还是重试上；
3. 接口变慢了，你分不清是模型慢、数据库慢、还是某个工具在等超时。

## 结构：一次请求是一棵树，不是一行日志

最值钱的那个设计决定，是**把一次请求拆成步骤（span）**，并给整棵树一个 id（traceId）。

本项目 AI 调用的步骤类型是固定的：

| kind | 记录什么 | 用来回答 |
| --- | --- | --- |
| `llm` | 第几轮、耗时、输入/输出 token、成本 | 模型慢不慢、贵不贵 |
| `tool` | 工具名、耗时、结果大小、错误类型 | 哪个工具在拖后腿 |
| `retrieval` | 检索来源、命中数 | 是不是检索没找到 |
| `persist` | 写库耗时 | 是不是数据库 |
| `billing` | 预留、结算差额 | 账对不对 |

三条设计纪律，每条都有实际理由：

**纪律一：`name` 只写结构，不写内容。** 工具名原样、模型轮次写成 `llm#2`，**不写提示词、不写参数、不写模型回答**。原因不只是隐私：正文里可能有用户数据，也可能有注入文本；把它写进 trace，等于给自己造了一个"看一眼就中招"的后门。

**纪律二：用 `seq` 而不是时间戳排序。** 同一层的两个工具调用可能有毫秒级重叠，按时间戳排出来的顺序每次都不一样。步骤序号是确定的，排查时才对得上。

**纪律三：`parent_seq` 让步骤成树。** 工具有没有子步骤、重试是不是挂在某一轮下面，靠这个字段表达。本项目的表、mapper、渲染早就支持层级，只缺一个"挂子步骤"的入口——这说明一件事：**结构先留好，能力可以后补；结构后补，要动签名。**

## 失败要分类，不是打一行栈

"失败了"不是一个有用的信息。有用的分类至少是这样：

| 分类 | 例子 | 谁该处理 |
| --- | --- | --- |
| 输入问题 | 参数缺失、格式不对 | 用户 |
| 权限问题 | 未登录、不是你的 | 用户（换个账号） |
| 上游问题 | 模型超时、限流、返回格式坏 | 运维（重试/降级） |
| 编排问题 | 工具循环超过上限、上下文超长 | 开发（改逻辑） |
| 内部问题 | 空指针、SQL 错 | 开发（修 bug） |

分类的直接收益是**给用户的话和给运维的话不一样**：

- 给用户：一句能行动的话（"积分不足，请联系管理员"）；
- 给运维：分类 + traceId + 哪一步失败；
- 永远不要把栈给用户：它既不解决问题，又泄露内部结构。

本项目的模型调用失败时，返回给前端的是分类后的提示，完整信息进 trace 与日志，两者用 traceId 关联。用户报障时只要给你 traceId，你就能直接跳到那一次请求。

## "没有数据"不等于"零"

这是监控里最常见、也最贵的一类错误：**把空集当成 0。**

真实事故：一个 5xx 比例的告警，在某段时间因为没有请求，指标查询返回空集，被判成 0%——于是"错误率 0"，告警不响，实际上那段时间服务根本没在正常处理请求。另一个版本是：某个 SLI 没有样本，平均值算出来是 NaN，被当成一个正常数值写进了面板。

正确的做法：

- **空数据是 NoData**，与 0 分开处理；
- 告警规则里明确：NoData 时是"不告警"还是"按异常处理"（对"服务必须一直有流量"的指标，NoData 本身就是异常）；
- 面板上区分"0"和"没有数据"两种显示。

这条经验可以推广成一个原则：**凡是聚合值，都要问一句"样本为零时它等于什么"。** 平均值、分位数、比率，在零样本时都没有意义。

## 度量：只挑能驱动动作的指标

指标不是越多越好。一个指标该不该留，看它能不能回答"看到它异常，我做什么"：

- 请求量、错误率、P95 延迟 → 能决定扩容、回滚、排查；
- 每轮 token 与成本 → 能决定换模型、改提示词、限流；
- 积分结算差额 → 能发现"上游没返回用量"这类账务问题；
- 登录成功/失败数 → 能发现撞库。

反过来，"今天一共处理了多少字节"这种数字，看到了也不知道做什么，就不该占面板。

## 采样与留存：只采失败是自欺

"成功请求不用存，浪费空间"——听起来很合理，实际会让你**失去基线**：没有成功样本，你无法判断失败率是否异常，也无法比较"新版本是不是真的更好"。

合理的做法：

- 失败**全采**（这是最值钱的数据，进评测集）；
- 成功按比例采，但保证有稳定基线；
- 敏感值脱敏后再存，原文受控存储、有访问审计。

## 事后补的成本为什么是三倍

因为可观测性不是"加日志"，而是三件结构性的事：

1. 代码里要**有步骤边界**（否则只能记"整个请求花了 3 秒"，说不出哪一步）；
2. 每一步要**有统一字段**（否则每个模块自己发明格式，面板拼不起来）；
3. 失败要**有分类**（否则所有异常都是"未知错误"）。

这三件事散落在所有模块里，事后补要一个个改。而设计时一起做，只是"写每段逻辑时顺手记一个 span"。

## 一次请求的 trace 长什么样

一次带工具的 AI 对话，拆开应该是这样一棵树：

```text
run (总耗时、状态、traceId)
├─ llm#1     2.1s   输入 1800 token / 输出 240 token   ¥0.012
├─ tool(search_notes)  0.8s   命中 3 条   结果 4KB
├─ llm#2     1.9s   输入 2600 token / 输出 320 token   ¥0.018
├─ persist   0.03s  写消息 2 行
└─ billing   0.01s  预留 1000 / 实扣 30 / 退还 970
```

有了这棵树，三个问题都变成"看一眼"：

- 慢在哪一步：`tool` 0.8s 占了三分之一，去查这个工具；
- 贵在哪：两轮 `llm` 各占一半，第二轮输入变大（因为带上了第一轮的工具结果）；
- 账对不对：`billing` 里预留、实扣、退还三个数能对上。

如果只记一行"这次请求耗时 4.9 秒"，上面三个问题一个都答不了。

## 日志、指标、trace：三层分工

| 层 | 回答什么 | 保留多久 | 采样 |
| --- | --- | --- | --- |
| 日志 | 这一刻发生了什么（事件流） | 几天到几周 | 全量，但脱敏 |
| 指标 | 整体趋势好不好（聚合） | 几个月到一年 | 本来就是聚合 |
| trace | 这一次具体坏在哪（结构） | 几天，失败全留 | 失败全采，成功按比例 |

三者靠 traceId 串起来：告警（指标）→ 点进去看具体 trace → 需要细节再查同一 traceId 的日志。

**缺少任何一层都会瘸：** 只有日志，趋势看不出来；只有指标，定位不了；只有 trace，没有长期趋势判断依据。

## 告警：优先报症状，不报原因

一条告警该不该有，看它是不是"用户正在经历的坏"：

- **症状告警**（优先）：错误率高、P95 超阈值、核心接口无流量、积分对账差额超限；
- **原因告警**（次之）：CPU 高、磁盘 80%、某个线程池满。

原因是：原因不等于故障（CPU 高可能完全正常），而症状一定意味着有人受影响。原因指标更适合放在面板上供排查，而不是半夜叫醒人。

每条告警还要带两样东西：**一句话说明"看到它先做什么"**，以及**跳到 trace 的入口**。没有这两样的告警，只会制造"收到告警—不知道怎么办—先关掉"的循环。

## 常见误区

### 误区：可观测性就是打日志

**你以为**：日志多打一点，出事总能查到。
**其实**：日志是**事件流**，不是**结构**。它没有步骤、没有父子关系、没有统一的耗时与成本字段。查一个跨五个模块的问题，你要在五份日志里按时间对齐。
**怎么验证**：拿一次真实的慢请求，只用日志回答"哪一步最慢"。答不出来，就是缺结构。

### 误区：平均值够用

**你以为**：平均响应 200ms，性能还行。
**其实**：平均值会掩盖长尾。1% 的用户等 5 秒，平均可能还是 200ms，但那 1% 正是最可能流失的人。
**怎么验证**：同时看 P50 和 P95/P99。差距大，说明有长尾，要按长尾排查。

### 误区：有监控就等于能定位

**你以为**：有面板、有告警，出事看一眼就知道原因。
**其实**：面板告诉你"哪里不对"，不告诉你"为什么不对"。定位靠的是**一次具体请求的完整步骤**——trace。没有 trace 的监控，只能让你更快地知道"坏了"。
**怎么验证**：从告警点进去，能不能直接看到一个失败请求的步骤列表？不能，就是只有监控没有可观测。

## 小结

把一次请求拆成树，给整棵树一个 traceId，每一步记耗时、用量、状态和错误分类；失败要分类，空数据要和 0 分开；指标只留能驱动动作的；失败的样本全采。

一句话检验：**用户报"刚才失败了"，你能在五分钟内说出是哪一步、哪一类原因吗？** 能，说明结构在；不能，说明你只有日志。
