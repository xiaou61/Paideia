## 先把结论摆出来

**模块不是目录，是"一份数据 + 一组用例 + 一个可以整体替换的实现"。**

判断一个模块该不该存在，看三条：

1. 它有**自己的数据**（自己的表，别的模块不直接读写）；
2. 对外只有**一组用例**，不暴露内部结构（不是一堆 getter）；
3. 把它整个删掉，业务会缺一块——不是"少了几个类"。

三条都成立，它才是一个模块；只满足第一条，那是一个数据表；只满足第三那条，那是一段代码。

**先做模块化单体，再谈拆服务。** 微服务只换来三样东西：独立部署、独立扩缩容、团队边界清晰。这三样你都不缺的时候，拆出去只会让每次调用多一次网络往返、每次排查多一个进程。

## 为什么不是一上来就微服务

三个信号，有一个成立才值得考虑拆进程：

1. **团队冲突**：一个模块同时有四五个人在改，天天解冲突；
2. **扩缩容差异明显**：图片处理吃 CPU、订单接口吃 IO，放一起没法分别扩；
3. **故障隔离**：某个模块会挂（对接第三方、跑重任务），不想拖垮主流程。

反过来说，这些**不是**拆的理由：

- "微服务是趋势"——趋势不付你的运维成本；
- "单体太老土"——老土的是没有边界的单体，不是单体本身；
- "数据库压力大"——那是索引、缓存、读写分离的事；
- "代码太乱"——边界没切清楚就拆服务，网络调用会让它更乱。

本项目就是 11 个 Maven 模块跑在**一个进程**里：模块之间边界清楚，部署上只有一个 jar。这个形态让"改一个模块不影响另一个"成立，同时不用付分布式系统的账。

## 边界靠什么守：三种手段，各挡一半

"我们约定不跨模块"是最不可靠的边界。人赶进度的时候一定会跨。所以要看**违反时会不会失败**：

| 手段 | 挡住什么 | 挡不住什么 |
| --- | --- | --- |
| `pom.xml` 声明依赖 | 未声明依赖的模块连编译都过不去；循环依赖直接报错 | Maven 产物会导出全部包，所以"依赖了，但不该用的内部类"照样能 import |
| 把实现放进 `internal` 包 + 构建期模块校验 | 跨模块访问对方内部实现包；模块间循环 | 运行时的行为漂移（接口没变，语义变了） |
| 针对接口的契约测试 | 实现换了以后行为不一致 | 有人绕过接口直接查表（要靠数据库权限或评审） |

第一行那句"产物导出全部包"是关键：很多人以为"不在 pom 里声明依赖"就够了，其实只要依赖了模块 A，A 的**所有** public 类你都能 import。所以内部实现必须靠第二道——本项目用的是 Spring Modulith 的构建期校验，规则只有一句：

```java
ApplicationModules.of(PaideiaApplication.class).verify();
```

出现模块循环、或跨模块访问对方的内部实现包，构建失败。这不是"检查一下代码风格"，是让边界成为**编译期事实**：写错的那一刻就知道，而不是三个月后线上出问题。

## 代码长什么样：端口放在需要它的一方

一个真实例子。知识库模块需要"给某个知识点出一道复习题"，但出题要用模型，而模型能力在 AI 模块里。依赖方向是 `ai → knowledge`（AI 模块依赖知识库），所以**知识库不可能反过来依赖 AI**。

解法是把接口定义在**需要能力的一方**（知识库），实现放在提供能力的一方（AI）：

```text
paideia-knowledge/
  ReviewQuestionPort.java            ← 知识库说：我需要"能出题"这个能力
paideia-ai/
  internal/review/ReviewQuestionGenerator.java
      implements ReviewQuestionPort  ← AI 说：我来实现
```

好处有三层：

- 依赖方向没被破坏（`ai → knowledge` 仍然单向）；
- 知识库的代码里看不到任何模型、HTTP、提示词，它只知道自己要一道题；
- 测试知识库时可以塞一个假实现，不需要模型。

**接口属于调用方，不属于实现方。** 这一条记住，能解决大半模块拆分的依赖倒置问题。

## 跨模块的两条硬规矩

**规矩一：不直接读别人的表。** 需要数据就调接口。原因很实际：表结构是内部实现，一旦被别的模块直接查询，它就变成了隐式契约，改字段名不会有任何编译错误，只会运行时炸。

**规矩二：不共享实体类。** 模块 A 的 `OrderRow`（带数据库映射注解）被模块 B 拿来当返回值，等于 B 依赖了 A 的存储细节。跨模块传的东西应该是自己的 DTO 或值对象，字段少了不要紧，稳定更重要。

这两条都能被上一节的模块校验或数据库账号权限挡住——前提是你真的把它们当规则，而不是当建议。

## 什么时候才拆成进程

模块化单体做扎实之后，拆进程反而变简单了：**接口已经在了，把实现换成一个 HTTP 客户端就行**。判断顺序是：

```text
边界清楚 + 表归属清楚
  → 有独立扩缩容需求（先加机器、加线程、加缓存，看还缺不缺）
  → 有独立部署需求（改它不用发整个系统）
  → 才拆进程
```

先拆哪一类？**无状态、无强事务的**——通知、文件、搜索、报表。它们不参与核心事务，拆出去挂了也只是延迟或降级；等这批拆完、运维流程跑顺了，再考虑拆业务核心。

## 模块之间传什么

边界画好之后，下一个问题马上出现：两个模块之间能传什么？答案是三类，各有各的规矩：

| 传的东西 | 谁定义 | 规矩 |
| --- | --- | --- |
| 值对象 / DTO | 双方协商，通常放调用方或平台层 | 只带字段，不带数据库注解；**字段只加不改** |
| 端口（接口） | **需要能力的一方** | 用业务语言；实现方不得往接口里塞自己的模型 |
| 事件 | 发布方 | 过去式命名；只带标识与必要字段，不带实体 |

三条禁令：

1. **实体不出模块。** 带 `@Table`、带 ORM 注解的类，是存储层的形状，传出去等于把表结构变成跨模块契约。
2. **异常不跨模块原样抛。** 模块 A 的 `OrderNotFoundException` 抛到模块 B，B 就依赖了 A 的内部类型。跨模块用错误码或统一的业务异常。
3. **事务不跨模块传播。** 模块 A 调用模块 B 的接口，B 应该有自己的事务边界。指望"外面的 @Transactional 把 B 也包进来"，等于让 B 的实现细节（它开不开事务、用什么数据源）变成 A 的假设。

## 一个模块的目录清单

一个能长期维护的模块，内部大致长这样：

```text
paideia-knowledge/
  ReviewQuestionPort.java        ← 对外：模块对外的能力
  internal/
    category/                    ← 按子能力分包
    entry/
    file/
    learning/
```

三条自查：

- 模块根目录有几个文件？超过十个，说明对外能力太多，可能该拆；
- `internal` 下有没有"谁都往里放"的包？有，说明子能力没切；
- 外部模块 import 了这个模块几个类？超过五个，说明接口粒度太细，调用方在拼装内部逻辑。

## 模块化单体的代价，要认

它不是免费的，代价有三样：

1. **构建变慢**：11 个模块的编译、测试比一个大目录多花时间；
2. **跨模块没有事务**：两个模块各写各的库，中间状态要靠补偿或事件，不能指望一个 `@Transactional`；
3. **调试多一层**：一个调用要跨模块接口，栈更深，日志更多。

这三样什么时候会让人受不了？**当"跨模块"变成"跨团队"的时候**——那时沟通成本超过了拆分成本，才该拆进程。在这之前，这些代价比分布式系统便宜得多。

## 常见误区

### 误区：分成模块就是要拆服务

**你以为**：模块化的终点是微服务。
**其实**：模块化是**边界**，服务化是**部署**。绝大多数项目需要的是前者，不是后者。一个进程里 11 个模块，改一个模块不影响另一个，这已经解决了 80% 的"代码乱"问题。
**怎么验证**：问自己"拆成两个进程后，我具体获得什么？"如果答案是"更规范""更先进"，那就先别拆。

### 误区：目录分开就是模块

**你以为**：建了 `modules/order`、`modules/user` 目录就算模块化。
**其实**：没有构建期校验的模块只是文件夹。真正的模块要能回答：谁依赖我？我依赖谁？我内部的类谁能用？
**怎么验证**：在订单模块里 import 用户模块的内部类，看构建会不会失败。不会失败，说明你只有目录。

### 误区：抽象出接口就算解耦

**你以为**：给每个类都配一个接口，就是面向接口编程。
**其实**：接口和实现一一对应、且只有调用方自己用，那只是多了一个文件。解耦看的是**依赖方向**：上层依赖抽象、实现可以换、测试可以不连外部服务。
**怎么验证**：把实现换成一个假实现，看要改几处。只改装配一处，是真解耦；要到处改，是假接口。

## 小结

模块化单体的核心只有两步：**按"数据归属 + 用例"切出模块，再用构建期检查把边界钉住**。接口定义在调用方、实现放在提供方，依赖方向就不会被拆弯。

用一个问题检验你的模块是不是真的：**现在把它拆成独立进程，要改几处？** 答案是"换个装配、包一层客户端"，说明边界是真的；答案是"要重构半个月"，说明它只是目录。
