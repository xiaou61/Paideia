## 先把结论摆出来

**部署拓扑是架构的一部分，不是运维的收尾工作。** 它决定三件事：

1. 哪些东西**能直接连到**你的服务（攻击面）；
2. 一个组件挂了，**影响多大**（故障域）；
3. 出问题后**怎么回滚**（发布形态）。

信任边界不是"代码里有没有校验"，而是"**谁能直接连到它**"。同一个接口，绑在回环和绑在公网，是两套安全模型。

先看三个症状：

1. 管理端和用户端在同一个端口、同一套鉴权里，靠路径区分；
2. 某个"内部"监控接口其实对公网可达，只是没人扫到；
3. 一个免鉴权的下载链接，id 是自增数字——等于全站文件可枚举。

## 一个进程还是几个：先问故障域

本项目的选择是**一个 jar 同时提供 API 与前端静态资源**，管理端挂在 `/admin/` 路径下，公网只开一个应用端口。

这个选择换来：

- 部署简单：一次替换、一个进程、一份日志；
- 前端与接口同源：没有跨域、没有单独的静态服务器要维护；
- 版本一致：前端和 API 永远同一次发布，不会出现"新前端配旧后端"。

代价也很清楚：

- **故障域是一个整体**：静态资源服务挂了，API 也一起挂；
- **不能分别扩缩容**：前端流量和 API 流量绑在一起；
- **发布即全量**：没有灰度，替换那一刻所有请求都受影响（单机只能靠"先起新进程、切流量"这种朴素办法）。

什么时候该拆成几个进程？和上一篇讲模块拆分同一个判据：**有独立的扩缩容需求、独立的故障隔离需求、或独立团队**。没有这三样，单进程的简单是真实收益。

## 端口就是信任边界

把服务器的监听面画出来，比任何安全设计文档都直观：

| 面 | 暴露范围 | 为什么 |
| --- | --- | --- |
| 应用端口 | 公网 | 用户要访问 |
| `/actuator/health` | 公网 | 监控探活、部署脚本要用 |
| `/actuator/metrics`、`/actuator/prometheus` | **仅本机来源** | 暴露 JVM 结构与业务维度标签，不能被公网读 |
| 运维面板（Prometheus / Grafana / exporter） | 全部绑回环 | 不需要公网访问 |
| 对象存储数据端口 | 公网（按需） | 预签名直读要用；控制台关闭 |

两个真实的判断值得记住：

**判断一：健康检查和指标不是一回事。** 健康检查只回答"活着吗"，可以公开；指标暴露内部结构、线程池、业务计数，公开等于给攻击者画地图。本项目对指标端点是"只允许本机来源"的访问控制，而不是像 health 一样整体放行。

但这条规则有一个**必须写下来的前提**：

> 一旦本进程前面挂了反向代理，远端地址会变成 `127.0.0.1`，这条白名单就失效了——那时必须改为独立的管理端口。

这就是"信任边界依赖拓扑"的最好例子：**同一条规则，在网络结构变化后会从安全变成不安全**。所以规则旁边要写"它在什么前提下成立、前提变了怎么办"。

**判断二：开一个公网端口不等于只开一个入口。** 对象存储的数据端口如果对外，它就是一个独立的公网入口，有自己的鉴权模型（预签名 URL）。它的安全不靠应用，靠"签名有时效、无法伪造"。所以"公网只开一个应用端口"这句话，在引入对象存储之后就不再准确了——**每次加一个对外组件，都要重画一次信任边界。**

## 免鉴权端点：什么时候可以，前提是什么

本项目有两处免鉴权读端点，理由都是同一个：

**附件读取**：`<img>` 标签不会携带 `Authorization` 头，而本项目不用 Cookie。要求登录就等于图片显示不出来。所以 id 用 UUID、不可枚举，**id 本身就是凭据**。

**分享读取**：`/api/v1/public/shares/{id}`，同样 UUID。而且**只放行 GET**——把 POST 一起放行，就等于给了匿名写入口。

这两条能成立，靠的不是"我们检查得少"，而是三个前提：

1. **id 不可枚举**（UUID，不是自增数字）；
2. **能力有限**（只能读、只能读这一份、且不含作者信息与学习痕迹）；
3. **前提被测试钉住**：存储的契约测试里明确断言"非 UUID 一律当不存在"，因为换实现时最容易丢的就是这条。

**免鉴权不等于不安全，但它对前提的依赖比鉴权接口高得多。** 所以每加一个免鉴权端点，都要把这三条写下来，并想清楚"如果 id 泄露了，最坏会怎样"。

## 密钥与配置：失败要趁早

部署里最容易出事的是配置。两个规矩：

1. **密钥不进仓库**，只放环境变量或被忽略的本地文件；仓库里只有占位示例。
2. **缺关键配置时启动失败，不要静默降级。** 本项目的签名密钥缺失时直接抛异常并给出两条解决路径，而不是随机生成一个——随机密钥的后果是"重启后所有令牌失效、多实例无法互验"，而这个问题只会在运行时暴露。

**能在启动时发现的错误，不要留到运行时。** 这是配置设计里最划算的一条。

## 发布与回滚：形态决定成本

单 jar 部署的回滚很朴素：保留上一个 jar，替换回去、重启。代价是：

- **停机时间**：重启期间请求失败（没有灰度、没有双实例）；
- **数据兼容**：如果这次发布带了一次不可逆的迁移，回滚代码也回不去（上一篇讲的"回滚有损"）。

所以发布计划里必须有三样东西：

1. 这次改了什么数据、回滚会丢什么；
2. 回滚的具体操作（命令、要多久）；
3. 回滚后要不要补数据。

没有这三样的发布，不是"应该没事"，是"出事了只能现场想"。

## 从零到上线的最小清单

一个人维护的服务，上线前至少要有这七样：

1. **进程守护**：挂了会自动拉起（systemd / supervisor），而不是靠人发现；
2. **端口绑定明确**：哪个绑公网、哪个绑回环，写在一张表里；
3. **健康检查**：一个不依赖数据库的存活检查（用于守护/探活），和一个能反映依赖状态的检查（用于发布判断）；
4. **日志落盘与轮转**：日志不轮转会撑满磁盘——这是最常见的"服务突然全挂"的原因之一；
5. **备份与恢复演练**：备份没恢复过等于没有备份；
6. **密钥文件权限**：配置文件 600，只有服务账号能读；
7. **发布与回滚脚本**：一条命令能发、一条命令能回，且都试过。

这七样里最容易省掉的是第 5 和第 7：备份看起来"以后再说"，回滚脚本"应该用不上"。真出事时，这两样决定你是十分钟恢复还是几个小时。

## 多实例时，哪些假设会坏

单机转多实例，代码里这些地方会悄悄失效：

| 假设 | 单机成立 | 多实例后果 |
| --- | --- | --- |
| 本地缓存 | 所有请求看到同一份 | 不同实例看到不同数据，更新后不一致 |
| 单机限流 | 全局限流 | 变成"每个实例各限一份" |
| 本地文件 | 文件在哪都能读 | 上传在 A，下载请求打到 B 就读不到 |
| 内存会话 | 登录状态共享 | 换一个实例就要重新登录 |
| 定时任务 | 一天跑一次 | 每个实例都跑一次 |
| 自增序号 | 全局唯一 | 两个实例发出同样的号 |

这张表的用法：**决定上多实例之前，逐条问"我有没有这个假设"**。有，就先改（共享缓存、共享存储、分布式锁、定时任务加锁），否则扩容会变成加故障。

## 单机的停机时间，怎么压

单进程部署，重启期间请求会失败。三个朴素的办法：

1. **预热 + 快速启动**：把启动时间压到几秒（懒加载、减少启动期扫描），停机窗口就小；
2. **先起新进程再切端口**：新旧两个进程短暂并存，反代切流量，旧进程排空连接后退出；
3. **接受它**：内部系统、低峰发布、有明确维护窗口时，几分钟停机是可以接受的——**只要它是被选择的，不是被忽略的**。

第三种最省钱，前提是你真的评估过业务能不能接受。

## 常见误区

### 误区：部署是运维的事，跟架构无关

**你以为**：代码写好，怎么部署是后面的事。
**其实**：部署形态决定了故障域、发布方式、回滚成本，也决定了你能不能做灰度、能不能多实例。这些都是架构决策，写代码时就该定。
**怎么验证**：问"这个功能上线后，回滚要多久、会丢数据吗？"答不上来，说明部署没被当成设计的一部分。

### 误区：只开一个公网端口就安全

**你以为**：入口收敛到一个端口，攻击面就最小了。
**其实**：端口只是入口之一。免鉴权端点、对象存储、运维面板、CI/CD 的部署通道，每一个都是独立的入口，各有各的鉴权模型。
**怎么验证**：把服务器上**所有**监听端口列出来，逐个问"谁能连、凭什么"。漏掉一个，就是一条没画出来的边界。

### 误区：免鉴权端点一定不安全

**你以为**：所有接口都必须登录。
**其实**：图片加载、公开分享这类场景，强行要求登录会直接让功能不可用。安全的前提可以换成"不可枚举 + 能力受限 + 只读"。
**怎么验证**：把 id 换成自增数字，看还安不安全。不安全，说明你依赖的是 UUID 这个前提，要把它写下来并测试。

## 小结

部署形态决定故障域、发布与回滚成本；端口与网络位置构成信任边界；免鉴权端点靠"不可枚举 + 能力受限"成立，且前提要被写下来、测出来；缺关键配置要启动失败。

一句话检验：**把服务器上所有监听端口列出来，逐个回答"谁能连、凭什么"。** 答不出的那一个，就是你不知道的边界。
