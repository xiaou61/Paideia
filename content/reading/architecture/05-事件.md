## 先把结论摆出来

**解耦解决"谁不该知道谁"，异步解决"谁不该等谁"。这是两个问题，经常被一句"上消息队列"糊在一起。**

- 只是发布方不想知道订阅方 → **进程内事件**就够；
- 还要"不等结果、失败能重试、跨进程" → 才需要消息队列；
- 两个都不需要 → 直接调用最清楚。

先看三个症状：

1. 一个操作触发五件事，代码里排成一串，第三件失败了前两件不会回退；
2. 为了"解耦"，两个模块之间开始用事件通信，结果没人说得清一次请求到底改了什么；
3. 上了消息队列，开始出现"消息丢了""消息重复了""顺序乱了"——而业务代码没做任何准备。

## 两种事件，别混着用

| | 进程内事件 | 跨进程消息 |
| --- | --- | --- |
| 边界 | 同一个事务、同一个进程 | 跨进程、跨网络 |
| 失败 | 与发布方一起回滚 | 发布方不知道，要重试与死信 |
| 顺序 | 同步调用，顺序确定 | 不保证，除非特意设计 |
| 典型用途 | 同一事务里的"一起发生" | 削峰、多订阅方、跨团队 |
| 代价 | 调用链变隐式，调试要追监听器 | 投递可靠性、重复、顺序、运维 |

关键区别在**失败语义**：进程内事件能用"同一个事务"保证"要么都发生、要么都不发生"；跨进程消息永远只能在"先记录、后投递、消费方幂等"这个框架里做。

## 进程内事件的正确用法：同一件事

本项目有两处用得非常典型，值得完整看一遍。

**案例一：注销账号要删散在各模块的数据。** 账号模块是地基，不能反过来依赖笔记、AI、沙盒这些业务模块（依赖方向会反）。所以账号删完自己那两行，只宣布一件事：

```java
// paideia-platform/UserDeletedEvent.java
public record UserDeletedEvent(long userId) {}
```

各模块自己监听、自己删自己的数据，并且必须用：

```java
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
```

为什么必须挂在事务上？因为注销是"**要么全删干净、要么什么都没发生**"的操作。分成两个事务做，会出现"用户没了、记忆还在"的中间状态——而那个用户再也没法登录来删自己的数据了。

**案例二：学习者改了自评，要写进记忆。** 自评在知识库模块，记忆在 AI 模块，而 AI 模块已经依赖知识库（它要检索条目）。知识库如果反过来调 AI，就是循环依赖，构建期直接失败。事件把方向拉回来：知识库只宣布"这个人对这条改了什么"，记忆归 AI 模块自己写。

同样用 `@TransactionalEventListener`，理由也一样直白：**自评回滚了却留下一条记忆，是假记忆。**

这两个案例的共性：

- **同一个事务**：监听方和发布方是"同一件事的两半"；
- **同一个进程**：不跨网络，没有投递可靠性问题；
- **事件很少**：只有"方向必须反过来"的地方才用，不是所有调用都改成事件。

事件放在哪个模块也有讲究：两个事件都放在 `paideia-platform`（所有模块都依赖的公共契约），而不是某个业务模块的包根——否则每个监听方都要多依赖一个模块。

## 跨进程消息：先解决三个问题再上

市场上一说"解耦"就是上 MQ。真到跨进程，你要回答的是三个和业务直接相关的问题：

**问题一：消息丢了怎么办？**

发布方写完数据库、还没发消息就挂了——数据库有、消息没有，下游永远不知道。标准解法是 **outbox**：把"要发的事件"和业务数据写在**同一个本地事务**里（一张事件表），再由一个投递器扫表发送、发完标记。这样"业务成功"与"事件已记录"是原子的，投递可以重试。

**问题二：消息重复了怎么办？**

投递器重试、网络重发、消费方超时重试，都会导致同一条消息被处理两次。解法只有一个：**消费方幂等**。落地方式通常是唯一键（事件 id + 消费方）或业务幂等键（订单号）。注意"至少一次投递"是常态，"恰好一次"只在很窄的条件下成立。

**问题三：顺序要不要保证？**

同一个用户的"创建→修改→删除"如果乱序到达，结果就是错的。要么按业务键分区（同一用户进同一队列），要么在消费方用版本号拒绝旧消息。**不要假设消息队列保证全局顺序**——它通常只保证单分区内有序。

## 什么时候事件是在藏 bug

事件最大的问题不是技术，是**它让调用关系从代码里消失**。三个信号说明你用错了：

1. **一个事件只有一个订阅方，而且订阅方必须成功。** 那它就是一次普通调用，被包装成了隐式调用——排查时你要先找到"谁监听了它"。
2. **事件被当成"延迟执行"用**，发布方默认它一定会发生。跨进程没有这个保证，进程内也要看事务有没有提交。
3. **事件链越接越长**：A 发事件，B 监听后再发事件，C 再监听。一次请求改了什么，已经没人能从入口读出来。

判断标准很朴素：**如果订阅方失败，业务算不算失败？** 算，那就是同步的一部分，别用事件；不算，事件才合适。

## 本项目的选择

目前所有模块跑在一个进程里，没有跨进程调用方，所以**没有引入消息队列**——上了它只会多一处要部署、要监控、要处理重复和顺序的组件，而换来的是零个真实收益。

需要的时候，顺序是固定的：

```text
先 outbox（同库同事务记录事件）
  → 再投递器（重试、标记）
  → 再消费方幂等
  → 最后才考虑换更重的消息中间件
```

反过来做（先上 MQ，再补幂等）通常会在第一次重投时出事故。

## outbox 长什么样

需要跨进程时，最小可靠的形状是一张事件表：

```sql
CREATE TABLE outbox (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  event_type  VARCHAR(64)  NOT NULL,   -- OrderPaid
  payload     JSON         NOT NULL,   -- 只放标识与必要字段
  status      VARCHAR(16)  NOT NULL,   -- pending / sent / failed
  attempts    INT          NOT NULL DEFAULT 0,
  next_at     DATETIME     NOT NULL,   -- 下次可尝试时间
  created_at  DATETIME     NOT NULL,
  KEY idx_pending (status, next_at)
);
```

工作循环只有三步：**扫 pending → 发送 → 标记**。三个细节决定它靠不靠谱：

1. **和业务写在同一个事务里**：业务成功 = 事件已记录。这是 outbox 的全部意义。
2. **至少一次投递**：发送成功、标记失败，下次会重发。所以消费方必须幂等（用事件 id 或业务键做唯一约束）。
3. **失败要退避，不是死循环**：`next_at` 指数退避；超过次数进 `failed`，要有人能看见（告警或面板），否则事件会静默堆在表里。

## 事件的命名与版本

三个小规矩，能省掉后面很多麻烦：

- **过去式命名**：`OrderPaid`、`UserDeleted`，读起来是"已经发生的事实"，不是"请做某事"。后者是命令，语义完全不同。
- **payload 只加不改**：加可选字段，消费方忽略未知字段；不要在同一个事件名里改字段含义。
- **不带实体**：只带 id 和必要字段。带整个订单对象，等于把一个时刻的快照永久固化，之后订单表怎么改都与这份历史不一致。

## 进程内事件的三个坑

用 `@TransactionalEventListener` 时，这三个坑几乎每个人都会踩一次：

1. **同类内部调用不经过代理。** 在同一个类里 `this.publish()`，监听器不会触发（Spring 的代理没被经过）。要么拆到另一个 bean，要么用注入的自身代理。
2. **异步监听丢事务上下文。** 用 `@Async` 把监听器扔到别的线程，事务已经提交或还没提交都不确定；此时再去读数据库，可能读到旧值。
3. **监听器异常会影响发布方。** 默认是同步执行，监听器抛异常会让发布方的事务回滚——这有时是想要的（"同一件事"），有时是灾难（通知失败导致订单失败）。**这个选择必须显式写出来**，不能靠默认。

## 常见误区

### 误区：事件就是异步

**你以为**：用了事件，调用就变成异步了。
**其实**：进程内事件默认是**同步**的——发布方法会等监听器跑完才返回。它换来的只是"发布方不知道订阅方是谁"，不是"不等结果"。真要异步，得显式换线程池或消息队列，而那时失败语义也一起变了。
**怎么验证**：在监听器里 sleep 五秒，看发布接口的响应时间有没有变长。

### 误区：事件越多越解耦

**你以为**：模块之间都用事件通信，耦合最低。
**其实**：事件把**显式依赖**换成了**隐式依赖**——编译期看不出谁依赖谁，改一个事件的字段，所有监听方可能悄悄坏掉。解耦的收益只在"订阅方数量多且互不关心"时成立。
**怎么验证**：数一个事件有几个监听方。只有一个，且它必须成功，就改回直接调用。

### 误区：上了消息队列就不会丢消息

**你以为**：MQ 负责可靠投递，业务不用管。
**其实**：MQ 保证的是"它收到之后尽量送到"。发布方写库成功、发消息前崩溃，这条消息根本不存在。可靠性要从**发布方**开始设计（outbox），再加上消费方幂等，缺一不可。
**怎么验证**：在"写库成功"和"发消息"之间强行 kill 进程，看重启后下游有没有收到。

## 小结

先分清你要的是解耦还是异步。进程内事件适合"同一事务里的两半"，用 `@TransactionalEventListener` 保证一起成功或一起回滚；跨进程消息要先有 outbox、消费幂等和顺序策略，再谈中间件。

一句话检验：**订阅方失败，业务算不算失败？** 算，就别用事件。

下一篇讲横切关注点——鉴权、限流、日志、开关，这些"每个接口都要"的东西该放在哪一层。

这条线到这里结束第五篇。它讲的其实是：**事件不是免费的午餐，它用"看不见的调用"换"解耦"，代价是排查变难。**
