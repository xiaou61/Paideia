## 先把结论摆出来

**分组的依据不是"这些代码用的是同一种技术"，而是"这些代码会因为同一个原因被改"。**

```sketch

  "rows": [
    [
      { "id": "same", "title": "总是一起改的代码", "sub": "背后是同一条业务规则", "tone": "blue" },
      { "id": "mod", "title": "圈成一个模块", "sub": "对外只露一组用例", "tone": "green" },
      { "id": "layer", "title": "按技术分层切开", "sub": "改一次要动三层", "tone": "amber" }
    ]
  ],
  "arrows": [
    { "from": "same", "to": "mod" },
    { "from": "mod", "to": "layer" }
  ]
}
```

- 分层（Controller / Service / Mapper）解决的是"一类代码只做一件事"；
- 分组（按业务能力切包）解决的是"谁会一起改"。

两件事都要做，但顺序不能反：**先按变化切出边界，再在每个边界内部分层。** 反过来的典型结果，是下面这三种症状同时出现。

## 三个症状，指向同一件事

**症状一：改一个需求，横跨五个目录。**

加一个"订单退款"，你要动 `controller/OrderController`、`service/OrderService`、`service/PaymentService`、`mapper/OrderMapper`、`mapper/RefundMapper`、`dto/` 下两个类。文件本身没错，错的是它们分散在一个按技术分层的树里，你看不出哪些是"订单"这个能力的一部分。

**症状二：Service 里直接 new 出 Mapper，或者干脆拼 SQL。**

这是依赖方向反了：上层直接依赖具体的下层实现。后果是这一层没法单独测试（必须连数据库），也没法换存储（SQL 散在业务里）。

**症状三：`common` / `util` 越抽越大。**

一开始只是日期格式化，半年后里面装着金额计算、权限判断、微信签名、Excel 导出。**`common` 是边界的反面**：它把"谁都能用"变成"谁都在改"，最后没人敢动它。

## 两种切法，各有各的时代

| | 按技术切 | 按业务切 |
| --- | --- | --- |
| 长什么样 | `controller/`、`service/`、`mapper/` | `order/`、`payment/`、`user/`，每个里面再分层 |
| 适合 | 小工具、纯 CRUD、团队只有一个人 | 业务规则开始变多、多人协作 |
| 好处 | 新人一眼看懂"请求怎么走" | 改一个需求集中在一个目录；能看出能力边界 |
| 代价 | 需求一多就散；边界不可见 | 需要先想清楚"哪些算同一个能力" |

判断自己现在该用哪种，不用凭感觉，用一个可数的指标：**最近五个需求，每个动了几处、几处分散在不同顶层目录？** 如果普遍超过三处、且分散，说明该按业务切了。

## 依赖只许单向

切完包，第二个问题立刻出现：谁能调谁。

一条纪律够用：**依赖只许朝一个方向，且上层依赖抽象的接口，不依赖具体实现。**

```text
接口层（Controller / Handler）  ← 只负责收参数、校验、返回
    ↓
用例层（Service）                ← 业务规则、事务边界
    ↓
存储层（Mapper / Repository）    ← 只存取数据
```

反方向一律禁止：

- Service 不 import Controller 的任何东西（它不该知道 HTTP）；
- Mapper 不调用 Service（数据层不做业务判断）；
- 业务代码不 import 框架的请求/响应对象（否则换个入口就要改业务）。

**判据很直接：把存储层整个替换掉，业务层要改几行？** 零行说明依赖方向是对的；要改说明所谓分层只是目录摆样子。

## 真正的边界长什么样

只说"按业务切包"还是太虚。看一个具体形状——本项目的后端，11 个 Maven 模块，每个模块内部是"根包放对外接口、`internal` 包放实现"：

```text
paideia-knowledge/
  src/main/java/io/github/xiaou61/knowledge/
    ReviewQuestionPort.java        ← 对外：别的模块只认这个
    QuestionTaggingPort.java
    internal/
      category/  entry/  file/  learning/   ← 实现细节，外部不许 import
```

配合三条规则：

1. **跨模块只依赖对方根包里的接口**（端口），不 import 对方的 `internal`；
2. **模块之间没有循环依赖**，方向在 `pom.xml` 里声明，没声明就编译不过；
3. **`internal` 包外部可见这件事，由构建期检查拦住**（下一篇细讲，因为 Maven 的产物会导出全部包，编译器管不到这一层）。

这套形状的好处是可验证。"订单和支付应该分开"是一句意见；"支付模块不许 import 订单模块的 internal 包，违反就构建失败"是一条能执行的规则。

## 怎么迁移，才不至于推倒重来

已经按技术分层写了一年，不想重写，可以分四步搬：

1. **先建包，不搬代码**：新建 `order/`、`payment/`，把明显属于同一能力的类**物理移动**进去（IDE 的 Move 会自动改 import）。
2. **先搬被动的一方**：DTO、枚举、异常这类"被谁都用"的类先归位，减少交叉引用。
3. **搬 Service 与 Mapper**：一次只搬一个能力，搬完就跑这一块的测试。**不顺手重构逻辑**——搬家和装修分开做，出问题才知道是哪个引起的。
4. **最后收拾 `common`**：把里面的类按归属分下去；确实通用的（日期、金额、字符串）留在原地，并写清"只放无业务含义的工具"。

整个过程不产生新功能，也不改任何行为。**这类"只改结构"的改动最容易在 code review 里被放过，所以要单独提交、单独验证**，不要和功能改动混在一个提交里——混在一起，出问题时你没法判断是结构搬错了还是逻辑改了。

## 一个反例：跨模块直接查表

假设订单模块要看用户等级。两种写法：

```sql
-- 写法 A：订单模块直接查用户表
SELECT level FROM user WHERE id = ?
```

```java
// 写法 B：订单模块依赖用户模块的接口
int level = userLevelPort.levelOf(userId);
```

写法 A 更快、代码更少，但从此**用户表的结构成了订单模块的隐式契约**：用户模块改字段名、加软删除、拆表，订单模块跟着坏，而且没有任何编译错误提醒你——只有运行时。

写法 B 多了一个接口、一次间接调用，换来的是：用户模块能把表改到面目全非，只要接口不变，订单模块一行不用动。

这就是本篇的核心：**边界的价值不是"看起来整齐"，而是"一边变了，另一边不用跟着改"。**

## 怎么定一个能力的边界

"按业务切"听起来对，落到具体项目还是不知道线画在哪。三个可操作的办法：

**名词法。** 把最近十条需求读一遍，反复出现的名词通常是能力：订单、支付、通知、简历。动词（创建、取消、导出）是用例，不是能力；形容词和状态（已支付、草稿）是值对象。

**共变法。** 两个名词是否总是一起改？总是一起改，它们就是一个能力——强行分开只会让每次改动跨两个包。半年没一起改过，才值得考虑切开。

**依赖法。** 画一张"谁 import 谁"的图。出现两种形状要处理：

- **两个包互相 import**：边界画错了，要么合并，要么把公共部分下沉成第三个包；
- **一个包被所有包 import**：它是公共契约（放平台层），或者它是垃圾场（该拆）。

## 一个具体的重构：从技术分层到业务分层

假设现在是这样的：

```text
com.example.shop/
  controller/  OrderController  PaymentController  UserController
  service/     OrderService     PaymentService     UserService
  mapper/      OrderMapper      PaymentMapper      UserMapper
  dto/         OrderDto         PaymentDto         UserDto
```

目标是每个能力一个包、包内再分层：

```text
com.example.shop/
  order/     api/OrderApi.java        internal/{OrderController,OrderService,OrderMapper}
  payment/   api/PaymentApi.java      internal/{PaymentController,PaymentService,PaymentMapper}
  user/      api/UserApi.java         internal/{UserController,UserService,UserMapper}
```

分三个提交做，每个都能单独验证：

1. **只移动**：按能力建包，把类搬进去，不改任何一行逻辑（IDE 自动改 import）。验证：全部测试通过，diff 里只有文件路径变化。
2. **加边界**：给每个包加 `api/` 与 `internal/`，把跨包调用收敛到 `api/` 里的接口；加一条构建期检查（模块校验或架构测试）。验证：故意 import 一次对方的 `internal`，构建应该失败。
3. **清理**：删掉空的原目录，把 `common` 里带业务含义的类分回各能力。

三个提交分开的好处很实际：第二个提交如果让测试红了，你知道是边界加错了，不是搬家搬错了。

## 常见误区

### 误区：分了层就是有架构

**你以为**：项目有 Controller / Service / Mapper 三层，架构就算做好了。
**其实**：分层只保证"一类代码干一件事"，不保证"一组代码属于同一个能力"。三层齐全但所有业务揉在两个巨型 Service 里，改一个需求照样横跨全项目。
**怎么验证**：数一数最大的那个 Service 有多少行、被多少个需求改过。超过一千行、每周都被不同的人改，就是边界没切。

### 误区：目录分好了，边界就有了

**你以为**：建了 `order/`、`payment/` 包，边界自然成立。
**其实**：只要 Java 允许 import，就一定会有人为了省事跨过边界——尤其是在赶进度的时候。边界必须有**构建期的检查**，否则它只是一份建议。
**怎么验证**：在 `payment` 里 import 一下 `order` 的内部实现类，看构建会不会失败。不失败就是没有边界。

### 误区：公共代码都应该抽到 common

**你以为**：两处用到就该抽出来复用。
**其实**：抽到 `common` 等于宣布"它不属于任何业务"，从此谁都能改、谁都不敢删。真正该抽的是**没有业务含义**的东西（日期、金额、字符串处理）；带业务判断的"公共代码"，应该抽成某个能力的对外接口。
**怎么验证**：看 `common` 里有没有出现"订单状态""用户角色"这类业务词。有，就抽错了地方。

## 小结

边界先于分层。分组的依据是"会因为同一个原因被改"，不是"用的是同一种技术"；层内再做 Controller / Service / 存储的分工，依赖只许单向、只依赖接口。

边界的价值可以一句话检验：**一边变了，另一边要不要跟着改？** 要跟着改，就说明边界是假的。

下一篇讲怎么把这条边界变成构建期能拦住的东西——模块化单体。

这条线到这里结束第一篇。它讲的其实是一件很朴素的事：**好结构不是让代码看起来整齐，而是让改动落在你预期的那个地方。**
