## 先把结论摆出来

系统一旦上线，**"以后能改"就比"现在写得漂亮"更重要**。演进有两条铁律：

1. **接口只加不改**：加可选字段、加新端点；不改已有字段的含义、不删、不复用名字。
2. **数据分步迁移**：先扩（新旧并存）、再迁（双写/回填）、后收（删旧）。**回滚通常有损，必须提前设计。**

先看三个症状：

1. 给接口加了一个必填字段，老版本客户端全部报错；
2. 改了一个枚举值的意思，代码不用改，数据全错；
3. 发版失败想回滚，发现迁移已经删了旧列——数据回不来了。

## 接口：什么算兼容，什么算破坏

| 改动 | 兼容吗 | 原因 |
| --- | --- | --- |
| 加一个**可选**字段 | 兼容 | 老客户端忽略未知字段 |
| 加一个新端点 | 兼容 | 没人调用它 |
| 把可选字段改成必填 | **破坏** | 老调用方不传就失败 |
| 改字段含义（同名字、不同语义） | **破坏** | 最危险：编译通过、测试通过、数据错 |
| 删字段 / 改名 | **破坏** | 老调用方拿不到 |
| 改默认值 | 视情况 | 依赖默认值的行为会变 |

**最危险的是第三行**：改语义。它不会有任何报错，只会在某个下游按旧含义解读数据时出错——而那时已经过去了两周。

所以接口契约要有"形状"的记录。本项目用一个快照文件把全部端点的响应字段形状钉住：

```text
api-shape.json
"GET /api/v1/account/profile": ["code", "data.identity", "data.stage", "message", "traceId", ...]
```

任何一次改动让快照变了，测试就会失败，要求开发者**显式 review 这份 diff**。它挡不住"语义改了但字段没变"，但能挡住绝大部分"不小心删了字段/改了类型"。

这也回答了一个常见问题：要不要做接口版本号（`/v2/`）？**如果你的客户端只有你自己，先别做版本，先做到只加不改。** 版本号是给"无法强制升级的外部调用方"准备的；自己家的前后端同步发版，多一个版本只是多一份要维护的代码。

## 数据：三步迁移，不要一步到位

假设要把 `status` 从字符串改成枚举，或者把一列拆成两列。一次改完的写法是：

```sql
ALTER TABLE orders DROP COLUMN status;
ALTER TABLE orders ADD COLUMN status_code INT NOT NULL;
```

上线那一刻，旧代码还在跑（滚动发布），它写的 `status` 没了；旧数据也没迁移；回滚时新列也删不掉。正确形状是三步：

```text
① 扩：加新列（可空），旧代码照常写旧列
② 迁：双写新旧列 + 回填历史数据 + 校验一致
③ 收：读切到新列 → 观察一段 → 删旧列
```

每一步都能停、都能回：

- ① 之后回滚：新列空着，无害；
- ② 之后回滚：旧列仍然是最新（因为双写），无害；
- ③ 之后回滚：**有损**（旧列已删），所以 ③ 之前要确认"真的不需要回去了"。

**回滚有损这件事必须写进发布计划**，而不是等出事才发现。判断标准：这次发布删了什么、改了什么类型、回填覆盖了什么？有一样，回滚就会丢数据。

## 迁移脚本的三条纪律

数据库迁移是"改了就无法撤销"的代码，纪律要比普通代码严：

**纪律一：已应用的迁移不能再改。** 迁移工具会给每个脚本算校验和，改一个字符，已应用的库就会校验失败、启动中止。这看起来麻烦，实际是在保护你：不然开发库、测试库、生产库会各跑一个版本，没人知道线上到底是什么结构。

**纪律二：文件名用时间戳，不用递增号。** 两个人在两个分支上各自写了 `V25`，合并后应用**根本起不来**（"找到两个版本 25 的迁移"），不是某个迁移失败，是整个上下文启动中止。用 `V20261028103045__描述.sql` 这种 14 位时间戳，把撞号概率降到"同一秒"。

**纪律三：迁移不写业务数据，种子数据放另一个目录。** 生产迁移只建结构（可以插配置常量，但要显式写 id 且用一个高段位）；测试/开发数据放 `devdata`。本项目有一条测试专门检查"迁移有没有往种子表插行却不给 id"——这个 bug 只会在**零数据的新库**上出现，生产库和开发库永远看不出来。

## 双写与读切换：怎么知道迁对了

"双写 + 回填"之后，怎么确认新列是对的？只测接口不够，要**对比**：

1. 双写期间，每次写入后比较新旧值是否一致，不一致就记录（不阻断）；
2. 回填历史数据后，抽样比对（或全量校验）；
3. 读切换后，观察一段时间的错误率与业务指标；
4. 确认无误，再删旧列。

这个过程可以压缩，但不能跳过"比较"这一步。没有比较的双写，只是写了两份，不知道哪份对。

## 配置与开关的演进

同一个道理：配置项**改名**等于破坏兼容（旧配置读不到，用默认值，行为变了）。做法也一样——先加新名、同时读两个、日志记录旧名使用情况、迁移完再删旧名。

## 一次具体的接口演进：给响应加字段

假设要给订单详情加一个"是否可退款"。兼容的做法：

```json
// 老版本
{"id": 1, "status": "paid", "amount": 9900}
// 新版本
{"id": 1, "status": "paid", "amount": 9900, "refundable": true}
```

三条纪律：

1. **只加可选字段**，不改原有字段的类型与含义；
2. **前端忽略未知字段**（JSON 反序列化默认就是这样，别自己写严格校验把它变成错误）；
3. **老客户端不传新参数也要能工作**——新参数必须有合理的默认值。

破坏性的做法是把 `status` 从字符串改成对象：`"status": "paid"` → `"status": {"code": 2, "label": "已支付"}`。老前端会拿到一个对象当字符串用，可能显示 `[object Object]`，也可能直接报错——取决于它在哪里用，测试未必覆盖得到。

## 双写期间读哪一边

| 阶段 | 写 | 读 | 目的 |
| --- | --- | --- | --- |
| 扩 | 旧列 | 旧列 | 新列只是存在，不影响行为 |
| 迁（双写） | 新旧都写 | 旧列 | 保证可回滚；同时抽样比对 |
| 验证 | 新旧都写 | **抽样读新列，与旧列比对** | 证明新列是对的 |
| 收 | 新列 | 新列 | 观察一段，再删旧列 |

第三行最容易被跳过，也最不该跳：**没有比对的双写，只是写了两份，不知道哪份对。**

## 回填历史数据：分批、可重入、记进度

一次性 `UPDATE` 几百万行会有三个问题：长事务、锁表、失败后不知道跑到哪。正确形状：

1. 按主键分批（每批几百到几千行），每批一个短事务；
2. 每批可重入（重复跑不会写错），进度记在一个地方（表或日志）；
3. 失败后从上次的进度继续，而不是从头再来。

如果回填逻辑需要调外部服务，那它就不是"迁移"，而是"后台任务"——更不该放在启动时执行。

## 删旧列前的四条检查

1. 新列已经全量回填，且抽样比对通过；
2. 所有读路径都已切到新列（不只是主流程，还有报表、导出、定时任务）；
3. 旧代码已经全部下线（确认没有旧版本实例还在跑）；
4. 回滚预案里明确写了"删了就回不去"，且相关人知道。

四条缺一条，就再等一个发布周期。删列是少数几个**做了就不可逆**的操作，慢一点不丢人。

## 常见误区

### 误区：加字段总是兼容的

**你以为**：只要不删字段，加什么都没事。
**其实**：加**必填**字段、加**改变默认行为**的字段、把字段从"可选"变"总有值"，都可能让老调用方出错。兼容的前提是"老客户端不知道它也能正常工作"。
**怎么验证**：拿上一个版本的客户端（或一份旧请求样例）打新接口，看是否还能通。

### 误区：回滚就是 git revert

**你以为**：代码回滚了，系统就回到之前的状态。
**其实**：代码能回滚，**数据不能**。删掉的列、回填覆盖的旧值、已经发出的外部请求，都不会因为 revert 回来。
**怎么验证**：发布单上写清楚"这次改了什么数据、回滚会丢什么"。写不出来的，说明你没想过这件事。

### 误区：迁移脚本可以事后修

**你以为**：迁移写错了，改一下文件就行。
**其实**：已应用的迁移有校验和，改了会让启动失败；就算你手动改了校验和，其他环境上跑过的还是旧版本，环境之间从此不一致。
**怎么验证**：看迁移目录的提交历史——如果出现"修改已上线迁移"的提交，那是一次隐性事故。

## 小结

接口只加不改，语义变更等于破坏；数据分扩、迁、收三步，回滚有损要提前写进计划；迁移不可回头改、文件名用时间戳、业务数据不进生产迁移。

一句话检验：**这次改动如果上线后必须回滚，会丢什么？** 答不出来，就先别发。
