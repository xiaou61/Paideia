## 现在的坑

终端不是浏览器：没有 DOM，没有样式树，没有自动重排。你能做的只有两件事——**往光标位置写字符**和**发转义序列**。

所以"每帧清屏再重画"是最直觉的做法，也是最糟的做法：流式输出时整屏闪烁、滚动位置丢失、光标乱跳。pi 的界面在长会话里看起来很稳，靠的是一个很老的办法：**把每帧渲染成字符串数组，和上一帧逐行比较，只重画变了的那几行。**

听起来简单，但有几处不做就会露馅。这一讲看它怎么处理这些边界。

组件侧的契约只有一行（`packages/tui/src/tui.ts:123`）：

```ts
render(width: number): string[]
```

组件不知道自己被画在哪、旁边是谁——它只负责"给我宽度，我给你几行字符串"。布局是另一层（`layout.ts` 算盒子），合成是再一层。这个分层让 diff 变得可行：**能比较的只有字符行，没有对象树**。

## 一帧的执行顺序

`packages/tui/src/tui-main-screen.ts` 里的顺序，值得按步读：

1. **先把 overlay 合成进去**（`:271`）。浮层如果留到 diff 之后处理，每帧都会"变"，diff 就永远命中不了。
2. **逐行比较**（`:367-380`）：从 `previousLines` 和 `newLines` 里找第一个和最后一个不同的行。
3. **两次"认输"**：如果终端变窄了、或者第一个变化行在上一帧视口上方，就放弃增量、整屏重绘（`:455-459`）——因为增量渲染只能改"看得见的部分"。
4. **用同步输出包住写入**（`:470` 的 `\x1b[?2026h`）。没有它，终端可能在你写一半时刷新，出现撕裂。
5. **只写变化区间**（`:492`）：把光标移到 `firstChanged`，重画到 `lastChanged`，下面的内容不动。

所以一帧的成本大致是"两次数组比较 + 变化行数"，而不是"整屏字符数"。长对话里这差距很大。

## 三个不做就会错的地方

**一、宽字符与"看起来一样、占格不同"的字符。** 行字符串的"第几个字符"和屏幕的"第几列"不是一回事，所以布局按显示宽度算格子。更细的一层在 `utils.ts:434-448` 的 `normalizeTerminalOutput`：它把泰文/老挝文的 AM 元音换成兼容分解形式、把 tab 展开成固定宽度——原因正是**差分重画会留下没清掉的残格**。这类问题在你只用中英文时遇不到，但只要支持多语言就会撞上。

**二、图片要显式清理。** 终端图片（kitty 协议）不是字符，diff 比对不出来。所以写入前要按变化区间删掉旧图（`deleteChangedKittyImages`，`:471`），否则会留下残影。

**三、终端尺寸变化不是"重画一下"这么简单。** 宽度变了，所有组件的 `render(width)` 结果都会变，行数也可能变，所以**宽度变化一律全量重绘**（`:343-347`）；高度变化通常也全量重绘（`:351-357`），但 Termux 是个例外——软键盘弹出/收起都会改高度，全量重绘会让整段历史在每次开关键盘时重放，所以那里跳过。

## 和真实现的差异

- **这不是虚拟 DOM。** 没有 diff 树、没有 key、没有协调；比较的粒度就是"同一行字符串是否相等"。所以**任何每帧都变的内容都会让 diff 失效**——比如每秒刷新的时间戳、随机的进度动画，最好放在单独的 widget 里，否则整块区域每帧重画。
- **`clearOnShrink` 是个可选项。** 内容变短时，如果不清屏，旧行会残留；pi 给了开关（`:360-365`），默认行为取决于终端能力与场景，不是无条件清屏。
- **滚动是布局层的概念，不是 diff 的。** 视口上方的内容变了，增量渲染够不着，只能全量——这就是 `:455` 那条判断存在的原因。
- **`render()` 必须便宜。** 它每帧都会被调用（哪怕只改了一个字符），组件里做重活会直接变成卡顿。这也是为什么 pi 的 markdown 渲染做了缓存与分段。

## 小结

终端 UI 的核心不是"画得漂亮"，是**让每帧的写尽量少**：渲染成行数组 → 逐行 diff → 只写变化区间 → 用同步输出包住。宽字符、图片、尺寸变化是三个必须单独处理的边界。

如果重来一次，我会先写一个 20 行的"计数器 + 一行日志" demo，用 `\x1b[2K` 逐行重画，再换成 diff——你会立刻看到闪烁是怎么消失的。
