## 现在的坑

你已经把 pi 装好了，问它一句「读一下 README，用一句话总结」，终端开始动：先是一段思考，然后一个工具调用，然后又是思考，最后给答案。

但你**说不清这中间的顺序**：刚才那段是模型在等工具，还是工具跑完了在等模型？为什么有时候一次提问里 `turn_start` 会出现两次？

于是你去翻源码，打开 `packages/agent/src/agent-loop.ts`，看到的是这样的东西：

```ts
await emit({ type: "agent_start" })
await emit({ type: "turn_start" })
```

一排一排的 `emit`，中间夹着 provider 请求和工具执行。道理你都懂，但**哪条 emit 对应界面上哪一块、为什么是这个顺序**，还是拼不起来。

这一讲不读整个循环，只做一件事：**写 30 行扩展，把这些事件按发生顺序打出来**。看到实物，再回去读循环，你会发现它只有五个动作用得着。

## 一页地图

pi 把「一次提问」拆成两层：**循环**负责做事，**事件**负责把"做到哪了"说出去。循环在 `packages/agent` 里，事件是它对外的唯一接口——TUI 和扩展都只是订阅者，不参与决策。

关键的一句：**pi 没有"任务进度回调"这种 API。** 你想知道它干到哪了，只能订阅事件；你想插手，也只能挂在事件上。所以把顺序搞对，是理解后面九讲的前提。

一次提问里你会用到的事件只有六个：

| 事件 | 什么时候发 | 一次提问里出现几次 |
| --- | --- | --- |
| `agent_start` | 一轮 run 开始 | 1 |
| `turn_start` | 一个 turn 开始（一次模型请求 + 它的工具） | ≥1 |
| `tool_execution_start` | 某个工具开始执行 | 有工具才有 |
| `tool_execution_end` | 某个工具结束（带耗时与 `isError`） | 与 start 一一对应 |
| `turn_end` | 这个 turn 的助手消息与工具结果都定稿了 | 与 `turn_start` 一一对应 |
| `agent_settled` | 整个 run 彻底安静，队列也空了 | 1 |

`agent_end` 也在，但它是"这次 run 不再发循环事件"的意思，后面还可能因为重试、压缩或者排队的消息再起一轮 run——所以**别把 `agent_end` 当成"彻底完了"**，那是 `agent_settled`。

## 最小可跑：30 行扩展把事件打出来

### 1. 装一个固定版本

```bash
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.5.0
pi --version        # 应该是 1.5.0
```

需要 Node 22.19 或更新。装完在 `pi` 里用 `/login` 接一个 provider。

### 2. 写扩展

扩展就是一个导出默认函数的 TypeScript 文件，函数拿到 `pi`（`ExtensionAPI`），在上面订阅事件：

```ts
// ~/.pi/agent/extensions/event-trace.ts
import { appendFileSync } from "node:fs"
import { homedir } from "node:os"
import { join } from "node:path"
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent"

const LOG = join(homedir(), ".pi", "event-trace.log")
let seq = 0
const mark = (line: string) => appendFileSync(LOG, `${String(++seq).padStart(2, "0")} ${line}\n`, "utf8")

export default function eventTrace(pi: ExtensionAPI) {
  pi.on("turn_start", () => mark("turn_start"))

  pi.on("tool_execution_start", (event) => {
    mark(`tool_execution_start ${event.toolName}`)
  })

  pi.on("tool_execution_end", (event) => {
    const cost = event.durationMs === undefined ? "did-not-run" : `${event.durationMs}ms`
    mark(`tool_execution_end ${event.toolName} ${event.isError ? "error" : "ok"} ${cost}`)
  })

  pi.on("turn_end", () => mark("turn_end"))
  pi.on("agent_settled", () => mark("agent_settled"))
}
```

写文件而不是打到终端，是因为 TUI 会重绘屏幕，`console.log` 会被冲掉；写到 `~/.pi/event-trace.log` 反而更好读，也能事后对比两次提问的差别。

### 3. 跑一次

扩展放在 `~/.pi/agent/extensions/` 下会被自动发现；只想临时试一次，用 `-e` 直接加载：

```bash
pi -e ./event-trace.ts
```

然后在 pi 里输入：

> 读一下 package.json 里的 scripts，告诉我一共有几条命令。

跑完退出，看日志：

```bash
cat ~/.pi/event-trace.log      # Windows: type %USERPROFILE%\.pi\event-trace.log
```

### 4. 你大概会看到这个形状

```text
01 turn_start
02 tool_execution_start read
03 tool_execution_end read ok 2ms
04 turn_end
05 turn_start
06 turn_end
07 agent_settled
```

注意这是**形状示例，不是逐字输出**（耗时和工具名每次都不一样）。这个形状里有两件事和直觉不一样，正是这一讲要你记住的：

- **一次提问通常是两个以上的 turn。** 模型先回一条"我要读文件"，这是第一个 turn；工具跑完，结果回给模型，模型再回一次，才是第二个 turn。所以 `turn_start` 出现两次是正常的，不是 bug。
- **并行的时候，`tool_execution_start` 会连着出现，`end` 才交错回来。** 如果让 pi 一次读三个文件，日志会长成这样——它是先把一批工具过一遍预检、统一发完 start，再并发执行：

```text
01 turn_start
02 tool_execution_start read
03 tool_execution_start read
04 tool_execution_start read
05 tool_execution_end read ok 2ms
06 tool_execution_end read ok 3ms
07 tool_execution_end read ok 2ms
08 turn_end
```

如果你看到的日志只有 `turn_start` 和 `turn_end`、没有工具事件，那多半是模型选择了直接回答，换个明确要求动文件的问题再试。

## 和真实现的差异

上面这 30 行是"订阅视角"。真实现里有几处值得你知道，免得以后读源码时对不上：

- **事件从哪发出来的。** `runAgentLoop` 在 `packages/agent/src/agent-loop.ts:110`，`agent_start` 与第一次 `turn_start` 在 `:126-127`；之后每个 turn 的 `turn_start` 在 `runLoop`（同文件 `:172`）里的 `:216`；`agent_end` 在 `:329`。
- **工具事件有三条路径。** 正常顺序执行在 `executeToolCallsSequential`（`:540`）里发 start（`:553`）；并行执行在 `executeToolCallsParallel`（`:596`）里先统一发 start（`:608`）再并发；还有一条你可能想不到的——模型输出被 token 上限截断时，`failToolCallsFromTruncatedMessage`（`:488`）会给每个没执行的工具发 start（`:495`），然后直接报错，**故意不执行**，因为参数可能是半截的。
- **`tool_execution_end` 只有一个统一出口**，在 `:931`，所以你订阅它一定能收到结果，即使工具根本没跑（看 `durationMs` 有没有值就能区分）。
- **扩展看到的是一份子集。** `AgentEvent` 的完整定义在 `packages/agent/src/types.ts:528`，里面还有 `message_start` / `message_update` / `message_end`；扩展能订阅的签名在 `packages/coding-agent/src/core/extensions/types.ts:1667-1682`。本讲只订了六个，剩下三个留给 04 讲。
- **pi 故意没做的事**（README 里写的）：没有内置权限系统，不做 sub-agent，不做 plan mode。所以你在事件流里永远看不到"等待审批"或"进入计划模式"这种阶段——它们是第 08 讲要自己写的东西。
- **版本提醒**：`extensions/types.ts` 在 `v1.5.0` 之后到 `main` 已经改了三十多行，行号会漂。你要对着看，先 `git checkout f9a2636`。

## 小结

pi 对外的接口不是函数调用，是**事件流**。一次提问的顺序可以用六个事件背下来：`agent_start → turn_start → (tool_execution_start → tool_execution_end)* → turn_end → 再来一个 turn → agent_settled`。

如果重来一次，我会先写这 30 行订阅器，再回去读 `runLoop`——比一上来啃源码快得多，因为你知道自己在找什么了。

下一讲我们把镜头拉远：这七个包各自负责哪一段，以及为什么 `pi-agent-core` 里**没有** "工具权限""子智能体""计划模式"这些东西。
