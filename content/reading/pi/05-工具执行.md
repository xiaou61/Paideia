## 现在的坑

"并行执行工具"是那种听起来一行 `Promise.all` 就完事的说法。真写起来会立刻遇到四个问题：

1. **参数还没校验，能不能先并发？** 不能——校验失败的工具根本不该跑。
2. **拦截要不要算"执行过"？** 算的话，模型收到的应该是一条错误结果，而不是什么都没有。
3. **结果按什么顺序回给模型？** 按完成时间回，模型会看到乱序的工具结果，下一轮推理就乱了。
4. **什么时候可以提前结束？** 工具自己说"我干完了，别问了"，但这个批次里还有别的工具。

pi 的回答集中在三个函数里：`executeToolCalls`（`:518`）做决策，`executeToolCallsSequential`（`:540`）和 `executeToolCallsParallel`（`:596`）各走一条路。

## 一页地图

单个工具的生命周期是四段，无论顺序还是并行都走同一套：

| 阶段 | 做什么 | 位置 |
| --- | --- | --- |
| 预检 | 找工具、改参数、校验 JSON Schema、`beforeToolCall` 拦截 | `prepareToolCall`，`:718` |
| 执行 | 调 `execute()`，可流式回报 `onUpdate` | `executePreparedToolCall`，`:831` |
| 收尾 | `afterToolCall` 可改结果 / 改错误标记 / 追加 `terminate` | `finalizeExecutedToolCall`，`:869` |
| 广播 | 发一条 `tool_execution_end` | `:931` |

并行模式的特别之处，是它把"预检"和"执行"拆成两段跑：

```text
预检（串行）      执行（并发）           落盘（按源序）
start A  ──┐
start B  ──┼──▶  A 与 B 同时跑  ──▶  toolResult(A), toolResult(B)
start C  ──┘
```

对应源码：`:608` 的循环先把每个工具的 start 都发出去（预检失败的直接就地 end），`Promise.all`（`:656`）并发跑，最后按**助手消息里的原始顺序**发工具结果（`:660-668`）。

所以第 01 讲看到的"start 连发、end 交错"不是 bug，是设计：**执行并发，叙述串行**。

## 三个容易被忽略的边界

**一、拦截也算一次执行。** `beforeToolCall` 返回 `{ block: true, reason }` 时（`:738-757`），pi 不跳过，而是生成一条错误结果、照常发 start/end。模型因此能学到"这个操作被拒了"，而不是"我调了个不存在的工具"。

**二、`terminate` 要看整批。** 判断在 `shouldTerminateToolBatch`（`:700`）：

```ts
return finalizedCalls.length > 0 && finalizedCalls.every((f) => f.result.terminate === true)
```

**全部**都要求终止才停；只要有一个不要，这一批就正常继续。这条规则让"提前结束"不会误伤同批的其他工具。

**三、截断的工具一个都不跑。** 模型输出撞上 token 上限时（`stopReason === "length"`），工具参数可能是半截 JSON，pi 会给每个工具发 start、再发一条错误结果，然后跳过执行（`agent-loop.ts:276-280` → `failToolCallsFromTruncatedMessage`，`:488`）。`tool_execution_end` 里没有 `durationMs`，就是"没真跑"的信号。

## 和真实现的差异

- **参数是"先改后验"。** `prepareToolCallArguments`（`:704`）允许工具自带 `prepareArguments` 把入参整形，然后才 `validateToolArguments`（`packages/ai/src/utils/validation.ts:54`）。校验失败走 immediate 分支，不会进 `execute`。
- **`afterToolCall` 能改的东西比你以为的多**：`content`、`details`、`usage`、`terminate`、`isError` 都能覆盖（`:880` 起的分支）。但源码有一句警告：改了 `content` 却没改 `structuredContent`，两者会不一致——所以它默认把 `structuredContent` 删掉。
- **结果消息是"重新构造"的，不是转发的。** `createToolResultMessage`（`:940`）会补齐空的 `content`、带上 `durationMs`、时间戳。JS 扩展返回的半成品结果不会让 null 流进会话。
- **顺序执行还有一条隐藏路径**：只要批次里**任意一个**工具声明 `executionMode: "sequential"`，整批都转成顺序（`:526-530`）。一个工具的选择会影响全批——写工具时要意识到这一点。

## 小结

工具执行的骨架是四段：预检 → 执行 → 收尾 → 广播。并行模式把预检串起来、执行并发、结果按源序落盘；`terminate` 只在整批一致时才生效。

如果重来一次，我会先写一个"永远返回 terminate"的工具和一个"永远不 terminate"的工具，放同一批里跑，看它到底停不停——比读 `shouldTerminateToolBatch` 更直观。
