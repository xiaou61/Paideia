> **版本**：pi `v1.5.0`（`f9a2636`，2026-11-09 核对）。路径与行号以该 tag 为准。

## 现在的坑

README 的 Packages 表列了 **7 个包**。你照着这 7 个去理解 pi，很容易得出一个错误结论：CLI 是"主程序"，其他都是它的库。

但 `packages/` 下其实有 **12 个目录**。多出来的 5 个（`schema`、`telemetry`、`mcp`、`codemode`、`env`）不在 README 的表里，可它们决定了 pi 的能力边界——比如 `codemode` 和 `mcp` 就是第 05、08 讲里"工具从哪来"的答案。

如果先不看依赖关系，你会把"哪些是必须的、哪些是可选的"搞反。这一讲只做一件事：把 12 个包按**依赖方向**摆成三层，然后记住一句话——**只有两个包是必须的**。

读这张图的顺序是**从下往上**：`pi-coding-agent` 是装配者，它把上面所有东西连起来；越往上越通用、越没有业务假设。

依赖关系是 `package.json` 里写死的，不是我猜的：

| 包 | 依赖的内部包 |
| --- | --- |
| `pi-coding-agent` | agent-core、ai、codemode、mcp、tui |
| `pi-agent-core` | ai、schema |
| `pi-ai` | schema、telemetry |
| `pi-durable` | chord、ai、codemode、schema、telemetry |
| `pi-env` | chord、durable |
| `chord` | schema、telemetry |
| `pi-tui` / `pi-mcp` / `pi-codemode` / `pi-schema` / `pi-telemetry` | 无 |

**只有两个包是必须的**：`pi-agent-core`（循环）和 `pi-ai`（模型）。其余十个都是可选的——不装 `pi-tui`，你可以用 RPC 模式跑；不装 `pi-mcp`，工具少一半但不影响循环；不装 `pi-durable`，会话只活在内存里。这就是"minimal harness"的字面意思。

十二个包都在同一个版本号上（`1.5.0`），monorepo 固定版本发布。只有 `evals` 是 `private: true`，不对外发。

## 和真实现的差异

- **README 的 7 个 ≠ 仓库的 12 个。** README 表只列对外主推的包；`schema`、`telemetry`、`mcp`、`codemode`、`env` 走的是"需要时再引"的路线。这不是隐瞒，是取舍：把内部依赖也列出来，会让"我该装哪个"变模糊。
- **`chord` 不是给 agent 用的。** 它是插件 host 运行时（契约、复制状态、RPC），`durable` 和 `env` 建立在它上面。你读 `pi-agent-core` 时完全不需要理解 `chord`——这本身是个好设计：内核没有被迫依赖持久化。
- **`codemode` 的位置容易被误读。** 它不执行你的代码，而是**执行模型写的 JS，唯一能力是调用被注入的工具**（见 05 讲）。所以它是"工具的组合层"，不是沙箱产品。
- **`env` 是远程执行**：一个部署在 SSH 后面的小 daemon 加客户端。也就是说 pi 的"工具在哪跑"是可以换的——本机、容器、远端。

## 小结

十二个包按依赖分三层：叶子（schema / telemetry / tui / mcp / codemode）→ 运行时（ai / agent / chord）→ 装配（durable / env / coding-agent）。**必须的只有 agent + ai**，其余按需装。
