## 现在的坑

你在 pi 里让它改一个文件，它正读文件呢，你突然想换个思路。于是你再打一句发过去——结果要么被吞了，要么报错：

```
Agent is already processing a prompt. Use steer() or followUp() to queue messages, or wait for completion.
```

（`agent.ts:385-388`）

报错本身是设计：**是 `Agent.prompt()` 不允许并发**。但报错里给的两条路——`steer()` 和 `followUp()`——区别是什么？什么时候该用哪条？

这两条路的差别不在"发消息"，在**消息在时间线上的插入点**。

## 一页地图

```text
turn_start ── 模型请求 ── 工具执行 ── turn_end
                                        │
                        steer()  ───────┤  在下一个 turn 开始前注入
                                        ▼
                                   turn_start ── 模型请求 ── ...
                                                          │
                        没有更多工具、也没有 steer ────────┤
                                                          ▼
                                    followUp() 注入 ── 再走一个 turn
                                                          │
                                                          ▼
                                                   agent_settled
```

一句话区分：

- **steering** = "别按原计划了，往这边走"。它在**当前 turn 结束后、下一个 turn 开始前**被取走（`agent-loop.ts:304`），下一轮模型请求就能看到。
- **follow-up** = "这件事干完，还有一件"。它只在**循环本来要停的时候**才被取（`agent-loop.ts:311`）。

两者都是**普通消息**，不是命令。pi 不解析"取消""改用 X"这种语义，它只是把你说的话排进队列——怎么理解是模型的事。

## 队列怎么排

两个队列各有一个模式（`agent.ts:255-256`）：

```ts
this.steeringQueue = new PendingMessageQueue(runtimeOptions.steeringMode ?? "one-at-a-time")
this.followUpQueue = new PendingMessageQueue(runtimeOptions.followUpMode ?? "one-at-a-time")
```

`PendingMessageQueue`（`:149`）的 `peek()` 决定一次取几条（`:165-169`）：

- `one-at-a-time`（默认）：只取队首一条，剩下的下次再取。
- `all`：一次全取。

`drain()` 就是 "peek + 移除"（`:175`）。所以默认行为下，你连发三条 steering，模型会一条一条地在三个 turn 里看到，而不是一口气收到三句。

队列在循环里被读取的位置只有一个——`createLoopConfig` 里挂的两个回调（`agent.ts:506-517`）：

```ts
getSteeringMessages: async () => {
  if (skipInitialSteeringPoll) { skipInitialSteeringPoll = false; return [] }
  return this.steeringQueue.drain()
},
getFollowUpMessages: async () => this.followUpQueue.drain(),
```

`skipInitialSteeringPoll` 这个开关解决一个边角问题：如果这次 run 本身就是由队列里的 steering 触发的，第一次轮询就不要再取一遍，否则同一条消息会被消费两次。

## 和真实现的差异

- **steering 不会打断正在跑的工具。** 它在当前 turn 的工具批次全部结束之后才注入（`agent-loop.ts:303-306`）。所以你发"停"，工具还是会跑完——想真的立刻停，用 `abort()`，不是 `steer()`。
- **steering 还有第二个轮询点。** 每轮开始前的"准备"阶段可能很久（压缩、加载上下文），准备完会再补一次轮询（`:210-215`），避免期间插入的消息被漏掉。
- **follow-up 不会另起 run。** 它只是在同一个 run 里多走一个 turn（`:311-317`）。真正再发一次 `agent_start` 的是上层会话（重试、压缩后重来），这也是为什么第 01 讲要你用 `agent_settled` 判断"彻底安静"。
- **队列不持久化。** 进程退出，队列就没了；`Agent` 实例上的 `clearSteeringQueue` / `clearFollowUpQueue`（`agent.ts:318-327`）也只清内存。
- **`continue()` 有兜底。** 如果上一条是助手消息，直接 `continue()` 是发不出去的，它会先尝试队列里的 steering，再尝试 follow-up（`agent.ts:403-418`）——这是"用队列里的消息续上"的语义。

## 小结

两条队列的差别只有一个字：**时机**。steering 在 turn 边界插话，follow-up 在循环将停时补活；模式决定一次取一条还是全部；它们都是消息，不是控制指令。

如果重来一次，我会在 01 讲的日志扩展里加上 `steer` / `followUp` 的调用，观察 `turn_start` 的次数怎么变——这是理解"插入点"最快的方式。
