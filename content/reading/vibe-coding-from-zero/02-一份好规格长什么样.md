## 这一关在解决什么

好规格 = **让人和 AI 都能判断"做完了没有"的一段话**。它由四个部件组成：目标、非目标、验收标准、约束。

少一个，就会给 AI 留一块"自由发挥"的空间，而那份空间正是漂移的来源。

## 讲解

### 部件一：目标——一句话说清给谁解决什么

目标回答"为什么做这件事"。写不成一句话，往往说明你还没想清楚。

- 差：做一个用户模块。
- 好：让新用户能用手机号 + 验证码注册并首次登录。

"用户模块"是名词，没法验收；"新用户能注册并登录"是行为，能验收。

### 部件二：非目标——明确不做什么

这是最被忽略、又最能防漂移的部件。**你明确说了不做，AI 就不会顺手做。**

比如登录这件事，非目标可以写：

- 不做第三方登录（微信 / Google）；
- 不做"记住我"；
- 不做密码找回。

非目标不是永远不做，是"这次不做"。写下来，AI 才不会自作主张加一堆你没要的功能。

### 部件三：验收标准——可测，不是"体验要好"

验收标准（acceptance criteria）是"怎么算做完"。最好用 **Given-When-Then** 三段式写，因为它天然可测：

```text
Given 一个未注册的手机号
When  用户请求发送验证码
Then  60 秒内最多发送 1 次，并返回"已发送"

Given 用户收到验证码，在 5 分钟内输入正确
When  提交登录
Then  登录成功，跳转到首页

Given 验证码错误超过 3 次
When  再次提交
Then  拒绝登录，提示"尝试次数过多，请 10 分钟后再试"
```

"体验要好""尽量快"这类话不是验收标准——它们没有判据，AI 和你都没法说"到底达没达到"。

### 部件四：约束——技术上不能碰的红线

约束是"在什么条件下做"，常见四类：

- **技术栈**：只能用现有项目的 Vue 3 + Spring Boot，不引入新框架；
- **性能**：验证码接口 P95 小于 200ms；
- **兼容**：要支持 iOS Safari 15+；
- **合规/安全**：手机号要加密存储，日志里不能出现明文验证码。

漏掉约束，AI 会用默认做法，而默认做法经常正好踩你的坑。

### 拼起来：一份完整的小规格

```markdown
# 手机验证码登录

## 目标
让新用户用手机号 + 验证码完成注册并首次登录。

## 非目标
不做第三方登录；不做"记住我"；不做密码找回。

## 验收标准
- Given 未注册手机号 / When 请求验证码 / Then 60 秒内最多 1 次
- Given 正确验证码、5 分钟内 / When 提交 / Then 登录成功并跳首页
- Given 错误超过 3 次 / When 再提交 / Then 拒绝并提示 10 分钟后重试

## 约束
- 前端 Vue 3，后端 Spring Boot，不引入新框架
- 验证码接口 P95 < 200ms
- 手机号加密存储，日志不得出现明文验证码
```

这一页东西，人和 AI 都能读，也都能拿来判"做完没有"。这才叫规格。

## 常见误区

### 误区：规格就是一长篇散文

**你以为**：把背景、想法、愿景都写下来，越详细越好。
**其实**：散文里混着目标、方案、愿望，AI 分不清哪句是硬要求。规格要的是**可判定的条款**，不是文章。
**怎么验证**：把规格里每一句都问一遍"这句能不能判真假"——不能的，要么是背景，要么该删。

### 误区：规格里把实现方案也写了

**你以为**：连"用哪个表、哪个类"都写进去，AI 才做得对。
**其实**：那是"计划（plan）"，是下一步的事。规格只回答"要什么"；把实现写进规格，等于把选择和验证混在一起，改动时全都得跟着改。
**怎么验证**：把规格里的技术实现删掉，看"做完的判断标准"是否还成立——成立，说明那些本来就该放 plan。

### 误区：验收标准写"体验要好"

**你以为**：这种描述 AI 能懂。
**其实**：没有判据的标准等于没有标准。AI 会挑一个最容易实现的方式交差。
**怎么验证**：让另一个人只看验收标准，判断"这份代码过没过"——他判不了，就说明标准不合格。
