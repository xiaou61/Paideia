## 这一关在解决什么

和 AI 写代码有三种形态：**补全、对话、自主 Agent**。选错形态，比 prompt 写得差更致命——你用"补全"的姿势去干"整项目重构"的活，怎么调 prompt 都没用。

## 讲解

### 三种形态，谁主导、适合什么

| 形态 | 谁主导 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| 补全（autocomplete） | 你主导，它补一小段 | 熟练的样板代码、重复结构 | 只提速一点点 |
| 对话（chat） | 你贴上下文，它给整段 | 写新文件、解释代码、小改动 | 你给不全上下文就答偏 |
| 自主 Agent | 它读文件、跑命令、改多处 | 目标明确、可验证的功能 | 跑偏了很难追 |

判断方法很简单：**这件事需要它"看很多文件、跑命令、改多处"吗？**

- 不需要，只是补一段 → 补全；
- 需要它写一整块，但你知道边界 → 对话；
- 需要它自己翻代码、验证、来回改 → 自主 Agent。

### 基本循环：意图 → 生成 → 验证 → 迭代

不管哪种形态，健康的循环都是这四步，而且每一步都要**可回滚、可验证**：

```text
说清意图  → 让它生成  → 你验证  → 根据结果再迭代
   ↑                                   │
   └────────────── 小步，随时能退 ──────┘
```

关键在"小步"。每一步产出的东西，你都要能回答两个问题：**它做对了吗？做错了能不能退回去？** 答不上来，就说明这一步太大，拆小。

### 一个反例：一次改整个项目

"帮我把这个单体应用改成微服务。"

这句话落到自主 Agent 上，它会：读一堆文件、新建一堆模块、改配置、来回试。你很难验证中间某一步对不对，出了问题也很难退回——因为它一次动了太多东西，git diff 大到你根本看不完。

正确做法是把这件事切成一串"可验证的小步"：先只拆一个边界最清楚的模块，跑通、验证、提交，再拆下一个。**大任务不是不能做，是要先拆成能验证的小步。**

### 形态和任务规模要匹配

- 任务越小 → 越用补全/对话，快；
- 任务越大、越需要验证 → 越要切到"自主 Agent + 规格 + 测试"这套重装备。

别用轻形态干重活（控制不住），也别用重装备干轻活（纯浪费）。

## 常见误区

### 误区：所有活都用最强的 Agent 形态

**你以为**：能力越强越好，一律上自主 Agent。
**其实**：小活上重装备，启动慢、还容易过度改动。**形态要跟任务匹配。**
**怎么验证**：改一行也派 Agent，看它是不是顺手改了别的文件。

### 误区：不看它改了什么

**你以为**：结果对了就行，过程不重要。
**其实**：AI 可能顺手改了无关代码、删了注释、动了配置。结果"看起来对"，但你埋了雷。
**怎么验证**：每次让它改完，先看 `git diff --stat`，再看关键 diff。

### 误区：一次说清就能一次做对

**你以为**：把要求一次讲全，它就该一次做到。
**其实**：越大的任务，越需要中途验证和调整。**迭代不是能力不足，是正常的工作方式。**
**怎么验证**：把一个大任务拆成三次小交付，和一次大交付比，看哪个返工少。

## 带走一句

**先选对形态，再用"意图→生成→验证→迭代"的小步循环走**——下一关讲，怎么把"意图"喂到位，也就是上下文工程。
