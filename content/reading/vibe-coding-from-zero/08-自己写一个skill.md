## 这一关在解决什么

看完 superpowers，你大概会想："我也有几个反复做的流程，能不能也做成 skill。"能。写法不复杂：**一句能被触发的描述 + 机械可查的步骤 + 必要的反例 + 一个"什么时候算完成"的检查。**

难点不在写，在**写得让 AI 该用的时候会想起来用、用了之后真的能照着做**。

## 讲解

### 四个部件

| 部件 | 作用 | 写法要点 |
| --- | --- | --- |
| `description` | 决定"会不会被触发" | 写清"当用户……时使用"，别写"提高效率" |
| 步骤正文 | 决定"能不能照着做" | 编号、可执行、每步有产物 |
| 检查清单 | 决定"怎么算做完" | 每条都能判真假 |
| 反例/边界 | 防止用错场景 | 明确"什么情况别用" |

### 一个完整的例子：提交前检查

```markdown
---
name: pre-commit-check
description: 当用户即将提交代码、或说"提交前检查一下 / 帮我看看能不能提"时使用。
---

# 提交前检查

## 步骤
1. 找到并运行相关测试，**贴出真实输出**；若失败，先修，不进入下一步。
2. 运行 `git diff --stat` 与 `git diff`，逐文件确认改动范围符合预期。
3. 扫描暂存内容：不得出现密钥、令牌、连接串、内网地址、生产数据。
4. 检查提交信息：符合 `<type>: #<单号> <描述>`，且单号对应真实需求。

## 检查清单
- [ ] 测试真的跑了，且有输出
- [ ] diff 看过，没有"顺手改"的无关文件
- [ ] 暂存区无敏感信息
- [ ] 提交信息格式正确、单号可追溯

## 别用的情况
- 只是本地试验、没打算提交；
- 用户明确说"先别检查，我自己来"。
```

这个 skill 不大，但四个部件都齐了：描述说清"什么时候用"、步骤能照着做、清单能逐条对、还写了别用的情况。

### 怎么验证它真的会触发

写完之后别自我感觉良好，拿几个输入测一遍：

- **该触发的**："帮我看看这次改动能不能提交" → 应该命中；
- **该触发的**："提交前跑一下" → 应该命中；
- **不该触发的**："解释一下 git rebase 原理" → 不该命中；
- **不该触发的**："提交信息怎么写"（只是问写法）→ 最好不命中。

命中率不对，就回去改 `description`，不是改正文。superpowers 自己就是这么干的——它的 `writing-skills` 技能专门讲怎么用"先红后绿"的方式迭代 skill 文本，连 skill 本身都要测试。

### 什么时候该做成 skill，而不是写 prompt

满足下面任意两条，就值得做成 skill：

- 这件事你会**反复做**；
- 它有**多个步骤**、容易漏；
- 需要**和其他人 / 其他会话共享**；
- 需要**版本管理**、以后要改。

一次性的、简单的活，用 prompt 就行，不必上 skill。

## 常见误区

### 误区：description 写得越"大气"越好

**你以为**：写"帮助用户提升开发效率"显得通用。
**其实**：太泛的描述让 AI 永远想不起来在具体场景用它。**描述里要有具体的触发场景和用户会说的话。**
**怎么验证**：拿三个真实任务试，看它有没有在正确的时候被读到。

### 误区：步骤写"尽量做好 / 注意质量"

**你以为**：这种要求 AI 能领会。
**其实**：不可执行、不可检查。skill 的步骤要像给新人的 SOP：做什么、用什么命令、产出什么。
**怎么验证**：把步骤交给一个完全不懂背景的人，看他能不能照做——做不下去，就是写得太虚。

### 误区：skill 写完就不用管了

**你以为**：一次写好，永久有效。
**其实**：模型、工具、你的流程都会变，skill 会慢慢失准。要像代码一样，改了就测、坏了就修。
**怎么验证**：三个月后重跑一遍"该触发/不该触发"的测试用例，看命中率变没变。

## 带走一句

**skill 的四件套：能触发的描述、能照做的步骤、能判真假的清单、能防误用的反例**——到这里 skills 这一批就讲完了，最后一批我们收一收心法和边界。
