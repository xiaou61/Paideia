## 这一关在解决什么

**Agent Skill = 一段按需加载的"操作说明书"**：它告诉 AI 在某类任务下该按什么步骤做、守什么检查清单。它把"好习惯"从某个人的记忆里，变成 AI 每次都会读到的文件。

先分清三样容易混的东西：

| 东西 | 一句话 | 类比 |
| --- | --- | --- |
| prompt | 你这次说的话 | 现场口头交代 |
| tool（工具） | AI 能调用的能力 | 给它的工具和电钻 |
| skill（技能） | AI 该怎么做一类事的说明书 | 贴在工具箱里的作业规程 |
| 子智能体 | 另一个干活的 AI | 派一个徒弟去做 |

**工具决定"能做什么"，技能决定"该怎么做"。** 两者不是一回事。

## 讲解

### skill 通常长什么样

一个 skill 就是一个文件夹里的一段说明（多数实现是 `SKILL.md`），核心三块：

1. **名字 + 一句触发描述（description）**：描述决定"什么时候该读它"。例如"当用户要在写代码前把需求梳理清楚时使用"。
2. **步骤正文**：编号、可执行、每步有产物。
3. **检查清单 / 反例**：做完前逐条对；什么情况别用。

一个最小的样子：

```markdown
---
name: pre-commit-check
description: 当用户即将提交代码、或说"提交前检查一下"时使用。
---

# 提交前检查

## 步骤
1. 跑一遍相关测试，贴出真实输出（不是"应该能过"）。
2. 看 `git diff`，确认改动范围符合预期，没有顺手改别的文件。
3. 检查暂存内容里没有密钥、连接串、内网地址。
4. 检查提交信息是否符合团队规范（如 `fix: #123 描述`）。

## 检查清单
- [ ] 测试真的跑了
- [ ] diff 看过
- [ ] 没有敏感信息
```

### 为什么用 skill，而不是每次写长 prompt

- **可复用**：写一次，以后同类任务都能用；
- **按需加载**：不触发时不占常驻上下文，触发时才读；
- **可组合**：一个流程可以由好几个 skill 拼起来（superpowers 就是这样）；
- **可版本管理**：skill 是文件，能进 Git、能 review、能共享给团队；
- **可测试**：能拿"该触发 / 不该触发"的输入去验证它靠不靠谱。

### 触发是关键

skill 有没有用，一半看内容，一半看**它会不会在对的时候被读**。描述写得太泛（"帮助提高效率"）几乎永远不会触发；写得太窄（只认某一句话）又经常漏。描述要回答：**用户在做什么、说什么的时候，该用我。**

## 常见误区

### 误区：skill 就是更长的系统提示词

**你以为**：把要求写进系统提示，效果一样。
**其实**：系统提示常驻、越写越长、越写越互相打架；skill 是按需加载、可单独关掉、可单独测试的模块。长期看，模块化比一段越滚越大的提示词好维护。
**怎么验证**：把一段长提示拆成两个 skill，看是不是本该触发甲的时候不再被乙的内容干扰。

### 误区：skill 装得越多越好

**你以为**：多装点，AI 什么都会。
**其实**：skill 太多会互相竞争触发、互相矛盾；AI 反而更容易读错、走偏。**先装你真正常用的几个，能自己写就自己写。**
**怎么验证**：同时装两个职责重叠的 skill，给一个模糊任务，看它是不是触发了你不想的那个。

## 带走一句

**skill 是"该怎么做"的可复用说明书，工具是"能做什么"**——下一关就拆目前最有名的一套 skill 集：superpowers，看它把哪些工程纪律写成了技能。
