## 这一关在解决什么

把 AI 当成一个"**能干但会自信地犯错**的同事"：它能大幅提速，但你要守住四条边界——**幻觉、许可证、隐私、成本**。守住它们，这套方法才敢用在真项目上。

## 讲解

### 边界一：幻觉——它会一本正经地编

AI 会编出不存在的 API、配置项、参数名、版本号，而且说得非常像真的。**凡是"引用"类的东西，都要核对官方文档。**

- 常用的库、命令、配置：查官方文档，不凭它说；
- 版本号、行为细节：以官方 changelog 为准；
- 不确定的，让它给出处，然后自己去点开看。

### 边界二：许可证——抄来的代码有主

直接让它"照着这个开源项目写"，产出的代码可能带着别人的许可证义务。**要区分两种情况：**

- **参考思路**（选题、结构、做法）：思想通常不受版权保护，可以借鉴；
- **复制代码**：要看清原项目的许可证（MIT、Apache 相对宽松；GPL 有传染性，商用要小心）。

值得说明：superpowers 和 GitHub Spec Kit 都是 **MIT 许可**，可以放心学习、参考。但你项目里引用的其它第三方代码，要单独确认。

### 边界三：隐私与安全——别把敏感信息贴进对话

- 不贴密钥、令牌、数据库连接串、生产数据、用户隐私；
- 日志里不能出现明文密码、验证码、身份证号；
- 涉及安全的代码（鉴权、加密），人必须复核，不能全交给 AI。

### 边界四：成本——自主 Agent 很费

自主 Agent 会读大量文件、反复试错，token 和时间都烧得快。**大任务先小范围试**：先让它做一个最小切片、验证可行，再铺开。别一上来就"整个项目重构"。

### 把方法固化成习惯

学到这儿，整条线的东西可以压成一条日常节奏：

```text
先写规格（要什么/非目标/验收）
→ 定方案
→ 拆小步
→ 每步先测试后实现
→ 完成前验证（测试/diff/复现）
→ 复盘：重复的流程做成 skill
```

**重复出现的部分，就做成 skill。** 这样下次不用重新讲一遍，AI 会在该用的时候自己读。

### 一个务实的心态

这套方法的目标不是"全程不看代码"，而是"**交付可维护的东西**"。你可以少看细节，但关键的地方——验收标准、安全、许可证、最终 diff——要亲自把关。

## 常见误区

### 误区：AI 写的没有版权问题

**你以为**：机器生成的，不存在侵权。
**其实**：如果它是照着某个开源项目"复制"出来的，许可证义务照样跟着代码走。**参考思路和复制代码是两回事。**
**怎么验证**：让它说明这段代码参考了哪里，再去看那个项目的 LICENSE。

### 误区：只是本地贴上密钥，没事

**你以为**：对话是私密的，贴个密钥无所谓。
**其实**：密钥一旦进了日志、进了对话记录、进了提交历史，就可能泄露；进了 Git 历史，删文件也补救不了，只能轮换。**永远不要把密钥贴进对话。**
**怎么验证**：翻一遍你最近的对话和提交，搜 `password` / `token` / `secret`，看有没有漏网。

### 误区：方法学完就一劳永逸

**你以为**：把 SDD 和 skills 用上，以后都顺了。
**其实**：模型在变、工具在变、你的项目也在变。方法要跟着调，skill 要定期测。
**怎么验证**：每季度回看一次：哪些步骤真在帮你、哪些已经变成形式。

## 带走一句

**把 AI 当"能干但会犯错的同事"：守住幻觉、许可证、隐私、成本四条边界，剩下的交给流程**——这条线到这里结束，愿你从"许愿"走到"可控地交付"。
