## 这一关在解决什么

规格驱动开发（Spec-Driven Development，SDD）把"写代码"拆成**四步**：先说清要什么（spec），再定怎么做（plan），再拆成小步（tasks），最后才写并验证（implement）。

每一步只回答一个问题，有产物、有人检查点。**错了只退回上一步，不用整个重来。**

## 讲解

### 四步各回答什么

| 步骤 | 回答的问题 | 产物 | 谁来看 |
| --- | --- | --- | --- |
| spec | 要什么、为什么、怎么算做完 | 规格（目标/非目标/验收/约束） | 你 + AI |
| plan | 用什么技术、怎么实现、影响哪些模块 | 技术方案 | 你确认后再往下 |
| tasks | 拆成哪些能独立完成的小步 | 任务清单（每步可验证） | AI 执行、你抽查 |
| implement | 写代码 + 跑测试 + 对照规格验收 | 可运行的代码 + 验证证据 | 你最终验收 |

### 为什么非要分四步

因为**每一步的错误成本不一样**：

- 规格错了，改几行字；
- 方案错了，重画一张图；
- 任务拆错了，重排一次清单；
- 代码写错了，改一堆文件、跑一堆测试。

分步的意义是让错误尽早暴露在最便宜的那一层。**如果让 AI 一口气从一句话直接生成整个项目，等于把四层的错误全压到最后一层一起爆。**

### 以 GitHub Spec Kit 为例

[Spec Kit](https://github.github.io/spec-kit/) 是 GitHub 开源的 SDD 工具包（MIT，Spec Kit 1.x，本文核对于 2026-11-11，commit `f29319d5`）。它把这四步做成一组斜杠命令：

```text
/speckit-constitution   每个项目一次：定代码质量、测试、可维护性的原则
/speckit-specify        写规格：要什么、为什么
/speckit-plan           技术方案：用什么、怎么实现
/speckit-tasks          拆成可执行的小任务
/speckit-implement      按任务写代码
/speckit-converge       对照规格检查是否收敛，没收敛就继续
```

关键用法：**一条一条跑，每跑完一条先看结果再继续**。产物落在项目的 `.specify/` 目录里，是可以进版本库、能反复回来看的文件。

> 版本提醒：Spec Kit 迭代很快，命令和目录结构会变。抄命令前先看官方文档当前版本；本文钉的是上面的版本，后面行为不一致时以官方为准。

### 对照另一个流派：Kiro

AWS 的 Kiro 用的是同一套思路，只是叫法和文件不同：需求写 `requirements.md`、方案写 `design.md`、任务写 `tasks.md`，需求用 EARS 句式（"当……时，系统应……"）来写，天生可测。

名字不同，骨架一样：**需求 → 方案 → 任务 → 实现，每一步落成一份看得见的东西。**

### 人在哪里插手

SDD 不是"让 AI 自己跑完四步"。真正起作用的是**每一步之间你按下的那次确认**：

- spec 出来，你读一遍：这是我要的吗？非目标对吗？
- plan 出来，你看一眼：技术选型我认吗？影响面我清楚吗？
- tasks 出来，你扫一眼：拆得够小吗？每步能验证吗？
- implement 之后，你验：测试过了吗？验收标准逐条对上了吗？

**没有这些确认，SDD 就退化成了"更长的 prompt"。**

## 常见误区

### 误区：SDD 就是瀑布模型，太笨重

**你以为**：先写死所有需求再动手，需求一变全崩，这不就是老瀑布。
**其实**：SDD 的每一轮是"一个功能"的四步，不是"整个项目"的四年。做完一个功能可以立刻进下一个，规格也能改——它反对的是一边写一边猜，不是反对迭代。
**怎么验证**：拿一个小功能走一遍四步，看是不是几十分钟就能闭环——如果是，它就不笨重。

### 误区：让 AI 一口气跑完四步更高效

**你以为**：反正是 AI 跑，让它从 spec 一路到 implement 最省事。
**其实**：那样你就失去了所有纠错点，四层的错误一起到最后一层爆，返工最贵。**分步的价值就在那几个确认点上。**
**怎么验证**：对比一次"一口气跑完"和一次"每步确认"，看哪个最后改得少。

### 误区：spec 写完就锁死了

**你以为**：规格是合同，签了就不能改。
**其实**：规格是"当前共识"，可以随理解加深而更新；要改就显式地改，并且让代码跟着改。**怕的是偷偷改，不是改。**
**怎么验证**：需求变的时候，先改规格再改代码，看最后文档和代码是不是还对得上。

## 带走一句

**spec 说"要什么"、plan 说"怎么做"、tasks 拆小、implement 写并验，四个确认点一个都别省**——下一关讲，这套东西什么时候值得上、什么时候该缩水。
