## 三个线程加到 3，一个进程只加到 1

```python
import os
import threading
import multiprocessing


counter = 0


def bump_thread(seen):
    global counter
    counter += 1
    seen.append((os.getpid(), threading.get_ident()))


def bump_process():
    global counter
    counter += 1
    print(f"child pid={os.getpid()} counter={counter}", flush=True)


if __name__ == "__main__":
    seen = []
    threads = [threading.Thread(target=bump_thread, args=(seen,)) for _ in range(3)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f"after threads: pid={os.getpid()} counter={counter} seen={seen}")
    p = multiprocessing.Process(target=bump_process)
    p.start()
    p.join()
    print(f"after process: pid={os.getpid()} counter={counter}")
    print(f"start method={multiprocessing.get_start_method()}")
```

```text
after threads: pid=28400 counter=3 seen=[(28400, 1000), (28400, 71628), (28400, 65892)]
child pid=46264 counter=1
after process: pid=28400 counter=3
start method=spawn
```

这是我在 Windows 11 22000 + Python 3.11.5 上跑出来的原文，没有改数字；PID 每次运行都会变，这几个数只用于对照。三个线程的 PID 都是 28400，`threading.get_ident()` 各不相同；子进程的 PID 是 46264；子进程把 `counter` 从 0 加到 1，父进程仍是 3。

我原来以为「进程隔离」就等于「子进程一定从零开始」。这句话只对一半：操作系统给子进程一套独立的地址空间，但 `fork` 出来的子进程一开始看到的是父进程地址空间的副本，不是零。这里看到 0，是因为 Windows 的 `multiprocessing` 默认用 `spawn`：子进程启动一个新的 Python 解释器，重新 import 这个模块，模块顶层的 `counter = 0` 又执行了一遍。**OS 的 `fork` 语义和 Python 的 start method 是两层，不要混。**

`os.fork` 在 Windows 上不存在，`hasattr(os, "fork")` 是 `False`；下面讲 `fork` 时我会明说是 Linux/macOS 的标准形态，不会拿 Windows 的输出冒充。

## 边界落在内核对象上

「进程是资源单位，线程是调度单位」这句话可以当入口，但不能当全部。真正的边界要看内核把哪些结构放进同一个容器。

Linux 里，内核调度的单位是 task，每个 task 有自己的 `task_struct`。同一进程的线程，是一组共享资源的 task（thread group）：

- 同一个 `mm_struct`：虚拟地址空间、页表、内存映射。一个线程 `mmap` 出来的页，另一个线程能直接看到。
- 同一个 `files_struct`：文件描述符表。一个线程 `close(fd)`，另一个线程再用这个 fd 就会失败；一个线程 `open` 的新 fd，其他线程也看得见。
- 同一个 `fs_struct`：当前工作目录、根目录、umask。一个线程 `chdir("/tmp")`，整个进程的相对路径解析都跟着变。
- 同一个 `sighand_struct`：信号处理函数表。一个线程 `sigaction` 改了 handler，其他线程收到同类信号也走新 handler。
- 但每个线程有自己的栈、寄存器上下文、`task_struct` 里的调度状态，以及自己的 signal mask 和 thread-directed pending；process-directed pending 属于整个线程组。

`clone` 是这些共享关系的开关：`CLONE_VM` 共享地址空间，`CLONE_FILES` 共享 fd 表，`CLONE_FS` 共享 cwd/root/umask，`CLONE_SIGHAND` 共享 handler 表，`CLONE_THREAD` 把新 task 放进同一个线程组。glibc 的 `pthread_create` 最终就是走一组带这些标志的 `clone`（新 glibc 也可能走 `clone3`）。Linux 的 `getpid()` 返回线程组 ID（TGID），`gettid()` 才是每个 task 的 TID；`ps -eLf` 里的 `LWP` 是后者，`NLWP` 是线程数。这里说的是 Linux，不是「操作系统都这样」。

Windows 是另一套对象模型：进程对象装虚拟地址空间、句柄表、令牌、环境变量；线程对象装栈、寄存器上下文、TEB/TLS、调度优先级和异常处理器链。调度器调度线程，不调度进程。Windows 没有 `fork`；新进程走 `CreateProcess`，新线程走 `CreateThread` 或线程池。`GetLastError()` 是每个线程一份，这一点和 POSIX 的 `errno` 类似，但 API 不同。

| 边界 | Linux 同进程线程 | Windows 同进程线程 |
| --- | --- | --- |
| 地址空间/页表 | 共享 `mm_struct` | 共享进程地址空间 |
| fd/句柄表 | 共享 `files_struct` | 共享进程句柄表 |
| 当前目录 | 共享 `fs_struct`，`chdir` 影响所有线程 | 进程当前目录，线程共享 |
| 信号/控制事件 | handler 表共享；mask、thread-directed pending 每线程 | 无 Linux 那套 POSIX 信号；Ctrl+C 走 console control event |
| 栈、寄存器、PC | 每线程 | 每线程 |
| TLS、errno | 每线程 | 每线程；`GetLastError` 每线程 |

Linux 的凭证还有一个容易写错的点：POSIX 要求同一进程的线程共享 uid/gid，但 Linux 内核在 task 上保存 credentials，NPTL 的 `setuid` 等 wrapper 会负责同步到所有线程。别把「内核里挂在 task 上」误读成「线程可以各自用不同 uid」。

把两边放回同一张表：

| 资源 | 两个进程 | 同进程两个线程 |
| --- | --- | --- |
| 地址空间/页表 | 各自一套 | 共享 |
| fd/句柄表 | 各自一套；`fork` 后是副本 | 共享 |
| cwd | 各自一份；`fork` 后是副本 | 共享 |
| 信号 handler | 各自一份；`fork` 后继承 | 共享 |
| 栈、寄存器、PC | 每线程一套 | 每线程一套 |
| 故障隔离 | 默认隔离 | 共享地址空间，可能互相影响 |

「进程之间默认隔离」指的是默认不能直接读写对方的虚拟地址；别说成「谁也看不见谁」：有权限的进程还能通过 `ptrace`、`/proc/<pid>`、共享内存、继承的 fd 交互。

## 共享与独占：errno 和 cwd 不在同一边

同一进程的线程共享代码段、全局变量、堆上的对象、打开的文件/句柄、当前目录、环境变量；每个线程独占栈、寄存器、程序计数器、TLS 和 `errno`。

`errno` 是线程局部的：POSIX 的 `errno(3)` 明确写了 setting it in one thread does not affect another；Windows 的 `GetLastError()` 文档也写了 last-error code is maintained on a per-thread basis。TLS 同理，`threading.local()` 里的值每个线程各有一份。

「栈独立」不等于「局部变量一定安全」。局部变量本身在各自栈帧里，别的线程不能直接按名字访问；但如果这个局部变量是一个引用，指向堆上的同一个对象，那个对象仍然是共享的。闭包、回调、把引用塞进队列，都会让「局部」变成「共享」。

共享堆 → 需要同步。但「`count++` 一定丢更新」也要看运行时。C/Java 里对共享变量写普通的 `++` 不是原子操作；CPython 3.11 有 GIL，我用 `sys.setswitchinterval(1e-6)` 跑 4 线程 × 20 万次 `counter += 1`，三次都是 `800000`，没丢；这不是语言保证，换实现、去掉 GIL，或者把读写拆开，结果就会变。下面这个例子故意把读写拆开：

```python
import threading
import time

counter = 0
barrier = threading.Barrier(4)


def bump():
    global counter
    barrier.wait()
    current = counter
    time.sleep(0.01)
    counter = current + 1


if __name__ == "__main__":
    threads = [threading.Thread(target=bump) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f"4 threads each +1, expected=4 actual={counter}")
```

```text
4 threads each +1, expected=4 actual=1
```

这段不是严谨压测，是把交错窗口放大；它证明共享变量的读-改-写不是原子操作，不证明 CPython 的正常 `+=` 一定丢。

## 线程崩了，进程一定死吗

「一个线程崩了整个进程都会死」这句话只对了一部分。看 Python 的工作线程抛异常：

```python
import threading
import time


def boom():
    raise RuntimeError("worker exploded")


if __name__ == "__main__":
    t = threading.Thread(target=boom)
    t.start()
    t.join()
    time.sleep(0.1)
    print("main thread still alive")
```

```text

Traceback (most recent call last):
  File "C:\Users\Lenovo\AppData\Local\Programs\Python\Python311\Lib\threading.py", line 1038, in _bootstrap_inner
    self.run()
  File "C:\Users\Lenovo\AppData\Local\Programs\Python\Python311\Lib\threading.py", line 975, in run
    self._target(*self._args, **self._kwargs)

    raise RuntimeError("worker exploded")

```

所以「线程崩了」要分三种：

- **语言级未捕获异常**：Python 工作线程打印 traceback 后结束，进程继续；主线程未捕获异常才会结束解释器。Java 默认也是未捕获异常终止该线程，JVM 继续（最后一个非 daemon 线程结束后 JVM 才退出）。
- **致命信号/段错误/堆破坏**：例如 C/C++ 解引用空指针，内核给触发故障的线程发 SIGSEGV；默认动作是终止整个进程，共享地址空间让其他线程也活不了。
- **Windows 未处理 SEH 异常**：默认 unhandled exception filter 终止进程；但运行时可能先捕获。

结论：共享地址空间让故障「可能扩散」，但「一个线程崩了进程一定死」是错的；「线程崩了不影响别人」也是错的。要强隔离，用进程/容器。

## 跑一遍：cwd、errno、TLS、fd 和栈

下面这段还是 Windows 11 + Python 3.11.5，`ctypes` 调的是 Win32 API：

```python
import ctypes
import os
import tempfile
import threading


def stack_limit():
    low = ctypes.c_size_t()
    high = ctypes.c_size_t()
    ctypes.windll.kernel32.GetCurrentThreadStackLimits(ctypes.byref(low), ctypes.byref(high))
    return high.value - low.value


if __name__ == "__main__":
    print(f"fork available={hasattr(os, 'fork')}")
    print(f"default thread stack_size={threading.stack_size()}")
    print(f"main stack={stack_limit()} bytes")

    local = threading.local()
    local.value = "main"
    state = {}

    def worker():
        state["pid"] = os.getpid()
        state["ident"] = threading.get_ident()
        state["stack"] = stack_limit()
        local.value = "worker"
        state["tls"] = local.value

    t = threading.Thread(target=worker)
    t.start()
    t.join()
    print(f"worker pid={state['pid']} ident={state['ident']} stack={state['stack']} bytes")
    print(f"tls main={local.value} worker={state['tls']}")

    barrier = threading.Barrier(2)
    errnos = {}

    def errno_worker():
        ctypes.set_errno(11)
        barrier.wait()
        errnos["worker"] = ctypes.get_errno()

    t = threading.Thread(target=errno_worker)
    t.start()
    ctypes.set_errno(22)
    barrier.wait()
    t.join()
    print(f"errno main={ctypes.get_errno()} worker={errnos['worker']}")

    old = os.getcwd()
    os.chdir(tempfile.gettempdir())
    cwd_seen = {}

    def cwd_worker():
        cwd_seen["worker"] = os.getcwd()

    t = threading.Thread(target=cwd_worker)
    t.start()
    t.join()
    print(f"cwd main={os.getcwd()} worker={cwd_seen['worker']}")
    os.chdir(old)

    fd_path = os.path.join(tempfile.gettempdir(), "paideia_fd_probe.txt")
    fd = os.open(fd_path, os.O_RDWR | os.O_CREAT | os.O_TRUNC)

    def close_worker():
        os.close(fd)

    t = threading.Thread(target=close_worker)
    t.start()
    t.join()
    try:
        os.read(fd, 1)
        print("fd read after close: unexpectedly succeeded")
    except OSError as e:
        print(f"fd read after close: OSError errno={e.errno} {e.strerror}")
    os.unlink(fd_path)
```

```text

main stack=2031616 bytes
worker pid=63944 ident=70324 stack=2031616 bytes
tls main=main worker=worker
errno main=22 worker=11
```

这张输出里有三件事：`errno` 主线程 22、工作线程 11，互不覆盖；`cwd` 两边都是 Temp，因为 `chdir` 是进程级；工作线程 `close(fd)` 后主线程 `read` 拿到 EBADF。`threading.local()` 的 main/worker 也各自一份。栈的 2,031,616 字节后面单独说。

`os.open` 在 Windows 上返回的是 CRT fd；这段证明的是同一进程内 fd 共享，不是 Windows 内核句柄表的全貌。Linux 的 fd 表共享有 `clone(2)` 的 `CLONE_FILES` 明确依据。

## fork 的 COW：复制的是页表，不是那几 GB 内存

`fork()` 不是把父进程的几 GB 内存逐字节复制一份。Linux 在 `fork` 时复制 `mm_struct` 和页表，把父子共享的物理页标成只读/COW；任何一方写，才触发缺页，内核给写的一方复制那一页。`fork(2)` 的 man page 把代价说成「复制页表 + 创建 task_struct」，不是「复制全部内存」。

下面这段是 Linux/macOS 的标准形态；Windows 上 `os.fork` 不存在，我没跑。按 `fork(2)` 的 COW 语义，预期是子进程先看到 3，父进程也还是 3；这不是实测输出：

```python
import os

counter = 3
pid = os.fork()
if pid == 0:
    print("child sees", counter)
    counter = 99
    os._exit(0)
else:
    os.waitpid(pid, 0)
    print("parent sees", counter)
```

| 资源 | fork 后子进程 |
| --- | --- |
| 地址空间内容 | 一份 COW 副本 |
| fd 表 | 副本；fd 指向同一个 open file description，共享 offset |
| cwd/root/umask | 副本 |
| 环境变量 | 副本 |
| signal handler 表 | 继承 |
| pending signals | 清空 |
| timers、memory locks、process-associated record locks、AIO contexts | 不继承 |
| 线程 | 只复制调用 fork 的那个线程 |
| PID | 子进程有自己的 PID；父进程拿到子进程 PID |

注意 fd 和 cwd 这两行：线程 `close(fd)` 会影响同进程所有线程；`fork` 的子进程 `close(fd)` 只关自己的副本，但父子 fd 指向同一个 open file description，`read`/`write` 还是共享文件偏移。线程 `chdir` 会影响同进程所有线程；子进程 `chdir` 不影响父进程。

`fork` 只复制调用它的那个线程；在一个多线程进程里，其他线程在子进程里不存在。子进程里的锁可能是「别的线程持有」的状态，所以 `fork` 后到 `exec` 前只能调用 async-signal-safe 函数（`fork(2)` 明确写了这一条）。

`exec` 会替换地址空间；没有 `FD_CLOEXEC` 的 fd 会保留；caught signal handler 重置为 default，ignored 的保持 ignored；cwd 不变。`vfork`/`posix_spawn` 是另一条路，本文不展开。

所以「开一千个进程一定比一千个线程贵」也不能直接说：Linux 的 `fork` 有 COW，真正贵的是 `fork+exec`、页表和映射多；Windows 的 `CreateProcess` 是另一套成本。要看平台和创建路径。

Python 的 `multiprocessing` 把这件事又包了一层：Windows 只能是 `spawn`；Linux 上可能是 `fork`、`spawn` 或 `forkserver`，看 Python 版本和配置。如果是 `fork` 且 fork 发生在 `counter=3` 之后，子进程会先看到 3，再加到 4；如果是 `spawn`/`forkserver`，子进程可能是新解释器或提前 fork 的 server，看到的初值不一定是 3。先打印 `multiprocessing.get_start_method()`，别猜。

## 上下文切换：模式切换不算线程切换

先把两个词分开：模式切换是 CPU 在用户态和内核态之间换；上下文切换是内核把 CPU 从一个 task 换到另一个。`read()` 进内核再返回是模式切换，可能一次线程切换都没有；一次时钟中断也可能只更新调度状态，不换人。

一次线程切换要保存/恢复通用寄存器、PC、SP、FLAGS、浮点/SIMD 状态（按架构和内核策略，有的状态是惰性保存）和内核栈指针。换到另一个进程还要换页表基址（x86-64 的 CR3），TLB 会受影响；同一进程的线程共享页表，少掉地址空间切换这一块，但仍然要进内核、保存寄存器，也可能被迁到另一个核。

成本拆成三块：

1. **直接路径**：保存/恢复上下文、调度器选下一个、更新运行队列。这是内核代码，耗时随内核、CPU 和负载变；我没在 Linux 上量过，不给微秒数。
2. **地址空间**：跨进程切换要换页表，TLB 失效或需要重新填；PCID 可以打标签减少 flush，但不是免费。
3. **缓存局部性**：新线程/进程的工作集不在 L1/L2，要重新从 LLC/内存拉；跨核迁移还会丢缓存。

所以「线程切换一定比进程切换便宜」要加条件：同进程线程少了页表切换，但线程切换仍然有内核路径和缓存成本。数字要在目标机器上量，不能拿别人的微秒数当自己的。

Linux 上看 `vmstat` 的 `cs`、`pidstat -w` 的自愿/非自愿切换；`top` 的 `sy` 不是切换次数，系统调用多、中断多也会抬高 `sy`。Windows 的性能计数器是 `\System\Context Switches/sec`，它给速率，不给单次成本。

按 Linux 内核文档，公平调度器在 6.6 起从 CFS 换成 EEVDF；Windows 是另一套基于优先级的抢占式调度。这些是平台实现，不是「操作系统都这样」。线程数远超核数时，非自愿切换会增多，但吞吐是否下降取决于任务在等还是在算；一个逻辑 CPU 同一时刻跑一个线程，有 SMT 的物理核可以同时持有两个硬件线程。

## 线程栈：8 MiB 是虚拟预留，不是物理占用

Linux 上先看当前限制，不要背一个数：

```bash
# Linux only；我这里是 Windows，没跑过
ulimit -s
ps -eLf | head
vmstat 1 5
pidstat -w 1
```

`pidstat` 来自 sysstat 包，没装就没有；`ps`/`vmstat` 来自 procps。

`ulimit -s` 是 shell 的栈限制；x86_64 上常见默认是 8192 KB，glibc 创建线程时默认栈大小与 `RLIMIT_STACK` 相关，常见是 8 MiB。这是默认值，不是 ABI 保证；这个数我按 glibc 默认值写，没在 Linux 上跑，读者以自己机器的 `ulimit -s` 为准。`pthread_attr_setstacksize` 可以改新线程的栈，`PTHREAD_STACK_MIN` 是下限。线程栈是虚拟地址预留，不是一创建就占满 8 MiB 物理内存；但 32 位进程的虚拟地址空间只有约 3 GiB，3000 个 8 MiB 栈光预留就超过 23 GiB，会在创建线程时失败。

Windows 的 `CreateThread` 用 `dwStackSize` 指定初始 reserve；传 0 用可执行文件的默认值。微软文档说默认每个线程 1 MiB 栈空间，但我这台 `python.exe` 用 `GetCurrentThreadStackLimits` 量到主线程和新线程的边界差都是 2,031,616 字节（约 1.94 MiB）。这说明「Windows 文档默认」和「这个可执行文件的实际默认」不是一回事。`threading.stack_size()` 返回 0 表示用平台默认，上面的输出就是这个 0。

栈溢出是致命错误；不要用递归去试探栈上限。

## 僵尸进程：死了但还没被 wait

Linux 上，子进程 `exit` 后父进程还没 `wait`/`waitpid`，子进程进入 zombie（`ps` 的 `STAT` 是 `Z`）。它已经不再运行，但 PID、退出状态、`task_struct` 还留着。`kill -9` 杀不掉僵尸，因为它已经死了；要父进程回收，或者父进程退出后由 init/reaper 收养。`waitpid(-1, &status, 0)` 是常见回收；显式把 `SIGCHLD` 设为 `SIG_IGN` 或设 `SA_NOCLDWAIT` 可以避免僵尸（POSIX 语义，具体看实现）。

Windows 没有 Linux 这种 zombie 状态：进程退出后，如果父进程还持有进程句柄，内核对象还在，但进程已经不运行；用 `GetExitCodeProcess` 取退出码，`CloseHandle` 释放句柄。Python 的 `Popen.wait()`/`multiprocessing.join()` 会等待子进程结束并取退出状态。

## 怎么选：先隔离，再分算/等，最后看数据

| 场景 | 更适合 | 条件 |
| --- | --- | --- |
| 大量 I/O 等待 | 线程或协程 | 原生线程由内核调度，阻塞调用只阻塞该线程；协程由运行时调度，阻塞调用会卡住 event loop，除非用异步库或线程池 |
| CPU 重计算 | Python 多进程；Java/C++ 多线程 | CPython 有 GIL，CPU-bound 多线程不并行；Java/C++ 线程可多核并行。不是通用 OS 结论 |
| 故障隔离 | 多进程 | 独立地址空间；线程共享地址空间，致命错误可能带走整个进程 |
| 共享大量数据 | 线程 | 进程也能用共享内存/mmap，但要显式建映射并同步；不是只能序列化 |

协程不是「更轻的线程」：调度者不同（运行时 vs 内核）、阻塞语义不同（`await` 让出 vs 阻塞系统调用卡住线程）、并行能力不同（协程不自动多核）。

判断顺序：先问故障隔离；再问在算还是在等；最后问数据共享/复制成本。
