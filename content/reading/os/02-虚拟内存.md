## 先把结论摆出来

程序里用的地址**不是物理内存的地址**，是虚拟地址。CPU 每次访问内存都要先经过一层翻译（页表），把虚拟地址换成物理地址。

这层翻译换来四件事：

1. **隔离**：A 进程写不到 B 进程的内存，越界直接段错误；
2. **每个进程都以为自己有一整块连续空间**，不用关心物理内存碎片；
3. **按需加载**：代码和文件只有真被访问时才进内存；
4. **共享**：只读的代码段、动态库在多个进程间共用同一份物理页。

代价是每次访问多一层索引（由 TLB 缓存摊薄），以及"内存不够"时要在后台换进换出。

## 页表与缺页：一次访问的完整路径

内存被切成固定大小的**页**（常见 4 KB）。页表记录"虚拟页号 → 物理页号"。

一次访问的流程：

1. CPU 用虚拟地址查 TLB（页表的缓存）；
2. TLB 没命中 → 查页表；页表项说"这页不在内存"→ 触发**缺页异常**；
3. 内核把这一页从磁盘（或文件）读进来，更新页表；
4. 重新执行刚才那条指令。

**关键认知**：缺页不是错误，是正常机制。进程刚启动时几乎每一页都要缺一次页，这也是"程序冷启动慢"的一部分原因。

## 内存"不够"是怎么发生的

有虚拟内存之后，"内存不足"有三种完全不同的含义：

| 现象 | 真实原因 |
| --- | --- |
| 机器显示内存快满了，但服务没崩 | 页缓存（文件缓存）占着，内核可随时回收 |
| 服务被 OOM Killer 杀掉 | 进程的常驻集（RSS）确实超了，内核在保命 |
| 越来越慢，最后卡死 | 频繁缺页 + 换页（swap），大量时间在磁盘上 |

**第一条是最容易被误判的**：Linux 的 "free" 里 `buff/cache` 很大通常不是问题，真正该看的是 `available` 和进程的 RSS。

**第三条有个名字叫抖动（thrashing）**：物理内存装不下活跃页，进程刚换进来又被换出去，CPU 都在等磁盘。此时加 CPU 没用，只能加内存或减并发。

## 内存泄漏与"看起来泄漏"

排查时先分清三种：

- **真泄漏**：对象被长期引用，GC 回收不了。表现为堆使用量持续上升、Full GC 后也降不下来。
- **缓存无界**：用 Map 做缓存但没设上限。本质是设计问题，不是 GC 问题。
- **分配速率高**：对象活得短但造得多，GC 频繁。堆不涨，CPU 涨。

判断方法：强制一次 Full GC（`jcmd <pid> GC.run`）后再看堆占用。降下来的是分配压力，降不下来的是真占用。

## 为什么要关心 RSS 而不是"虚拟内存大小"

`top` 里每个进程有两个数：

- **VIRT**：虚拟地址空间大小，包含大量已映射但没真正使用的页。它大得离谱是正常的（JVM 会预留一大片）。
- **RSS**：实际占用的物理内存。**这才是内存预算的依据。**

容器里尤其要注意：`-Xmx` 只是 Java 堆上限，进程总内存 = 堆 + 元空间 + 线程栈 + 直接内存 + GC 结构。容器内存限制只比 `-Xmx` 大一点，就很容易被 OOM Killer 干掉，而 Java 侧看不到 `OutOfMemoryError`——因为它根本没机会抛。

## 动手看一下

```bash
cat /proc/<pid>/status | grep -E 'VmRSS|VmSize'   # RSS 与虚拟内存
cat /proc/<pid>/smaps_rollup | head               # 内存都花在哪
vmstat 1 5                                        # si/so 非零说明在换页
```

`si`（swap in）与 `so`（swap out）持续非零，就是抖动的前兆。

## 常见误区

### 误区：虚拟内存就是 swap 文件

**你以为**：虚拟内存 = 磁盘上那块交换区。
**其实**：虚拟内存是"每个进程的地址空间"这套机制本身；swap 只是它在物理内存不够时的后备。关掉 swap 仍然有虚拟内存。

### 误区：内存占用高就要重启

**你以为**：占得高就是有问题。
**其实**：先看是 RSS 还是页缓存、强制 GC 后是否回落、`si/so` 是否非零。很多"高"是缓存，重启反而让服务变慢。

### 误区：内存泄漏只能靠重启拖到发版

**你以为**：没办法。
**其实**：堆直方图（`jmap -histo:live`）能直接看出哪类对象最多；再顺着引用链找持有者。缓存无界往往几分钟就能确认。

## 小结

虚拟地址经页表翻译成物理地址，换来隔离、连续视图、按需加载与共享。缺页是常态。判断内存问题看 RSS、`available` 与 `si/so`，不要只看 free 的总数。容器内存限制要覆盖堆外的所有部分。下一课：CPU 到底在被谁用掉。
