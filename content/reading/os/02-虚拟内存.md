## 6 GB 的地址空间，16 MB 的工作集

我在 Windows 11（build 22000，15.8 GiB 内存）上跑了一个 Python 进程：先用 `VirtualAlloc` 保留 2 GiB 虚拟地址，再提交并写 4 KiB。本机 Python 3.11.5，`psutil` 7.2.2；没有 `psutil` 就先 `pip install psutil`。

```python
import ctypes
import os
import time

import psutil

MEM_RESERVE, MEM_COMMIT = 0x2000, 0x1000
PAGE_NOACCESS, PAGE_READWRITE = 0x01, 0x04

k = ctypes.windll.kernel32
k.VirtualAlloc.argtypes = [ctypes.c_void_p, ctypes.c_size_t, ctypes.c_ulong, ctypes.c_ulong]
k.VirtualAlloc.restype = ctypes.c_void_p  # 64 位下不设会把返回地址截断

p = psutil.Process()

def rss(tag):
    print(tag, p.memory_info().rss, flush=True)

rss("before")
addr = k.VirtualAlloc(None, ctypes.c_size_t(2 * 1024**3), MEM_RESERVE, PAGE_NOACCESS)
rss("reserve_2GiB")
page = k.VirtualAlloc(ctypes.c_void_p(addr), ctypes.c_size_t(4096), MEM_COMMIT, PAGE_READWRITE)
rss("commit_4KiB")
ctypes.memset(ctypes.c_void_p(page), 0x41, 4096)
rss("write_4KiB")
print("pid", os.getpid(), flush=True)
time.sleep(60)
```

本机输出：

```text
before 17031168
reserve_2GiB 17051648
commit_4KiB 17051648
write_4KiB 17055744
pid 54016
```

另开一个 PowerShell 窗口查这个 PID：

```text
Get-Process -Id 54016 |
  Select-Object Id,
    @{n='VSZ_MB';e={[math]::Round($_.VirtualMemorySize64/1MB,1)}},
    @{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}},
    @{n='Private_MB';e={[math]::Round($_.PrivateMemorySize64/1MB,1)}} |
  Format-List
```

```text
Id         : 54016
VSZ_MB     : 6258.3
WS_MB      : 16.3
Private_MB : 9.5
```

同一台机器上，同样导入这几个模块、但不调用 `VirtualAlloc` 的 Python 进程：

```text
Id         : 69168
VSZ_MB     : 4210.3
WS_MB      : 16.4
Private_MB : 9.6
```

两次是不同进程，工作集有 0.1 MB 级噪声；VSZ 差 6258.3 - 4210.3 = 2048.0 MB，正好是保留的那 2 GiB。

我原来以为 `VirtualAlloc` 2 GiB 就是占 2 GiB 内存。实际是：

- **保留（reserve）** 只记下一段可用的虚拟地址范围，页表项还没建立；RSS 只多了 20,480 字节，是页表/VAD 之类的元数据。
- **提交（commit）** 4 KiB 后，RSS 一点没变；提交只是记账，物理页还没给。
- **写第一个字节** 后，才真的分配一页，RSS 增加 4,096 字节。

所以 `VSZ 6 GB` 和 `工作集 16 MB` 可以同时成立。`VirtualMemorySize64` 是地址空间大小，`WorkingSet64` 是当前在 RAM 里的页，`PrivateMemorySize64` 是私有提交量；三个数回答三个不同问题。

## 地址空间是一张按进程画的 map

以 Linux x86-64 的用户空间为例（段地址受 ASLR 影响，这里只画相对位置）：

```text
高地址
  内核空间                  用户态不可访问
  ────────────────────────
  主线程栈 ↓
  mmap 区 ↓                 共享库、线程栈、大块 malloc
  堆 ↑
  .bss / .data
  .text                     只读、可执行
低地址
```

`malloc` 拿到的地址落在这张图里；它是不是物理内存，图上看不出来。代码段可以只读、可执行，数据段可写，栈和堆各自向对方的方向长；这些区域的保护位不同，跨到未映射页或权限不符的页时硬件才会拦住。同一个页内的越界不会触发缺页，堆越界可能就是这样悄悄写坏的。

地址空间有多大，取决于位数和页表级数：

- 32 位 x86 Linux 默认低 3 GiB 给用户态、高 1 GiB 给内核；32 位进程总共 4 GiB 地址空间。
- 64 位 x86-64 用 4 级页表时是 48 位虚拟地址，总共 256 TiB；Linux 用户态占低 128 TiB，内核占高半区。
- 5 级页表把虚拟地址扩到 57 位，总共 128 PiB。
- Windows x64 在 4 级页表下用户态和内核态也各 128 TiB；32 位 Windows 默认 2 GiB 用户 + 2 GiB 内核，启用 `/3GB` 且程序标记为大地址感知时可到 3 GiB。

这些是地址空间上限，不是物理内存。16 GiB 的机器也能给每个进程 128 TiB 的虚拟范围；物理页仍然只有那么多。

页大小也不是只有一个数：x86-64 的基础页是 4 KiB，硬件还支持 2 MiB 和 1 GiB 大页（2 MiB = 512 个 4 KiB 页），是否启用看 OS 和 CPU；ARM64 可配 4/16/64 KiB 页。MySQL InnoDB 的 16 KiB、PostgreSQL 的 8 KiB 是数据库自己的页，不是 OS 页；别把 buffer pool 的读写单位当成 mmap 的页大小。

所谓「每个进程独占」，是每个进程有自己的用户态页表：同一个虚拟地址在两个进程里可以指向不同物理页；物理页也可以共享（共享库、page cache）。内核空间位于高半区，开启 KPTI 后用户态页表不保留完整内核映射，进入内核时切换页表。

## 页表不是一张表，TLB 也不是页表

48 位虚拟地址拆成 9 + 9 + 9 + 9 + 12 位：前四段各索引一级页表，最后 12 位是 4 KiB 页内偏移。每级 512 项，每项 8 字节，一张表正好 4 KiB。

如果只用一张平表：2^36 个页 × 8 字节 = 512 GiB，每个进程一张，光页表就放不下。多级页表只为用到的地址范围分配下级表，稀疏地址空间才可行。

CPU 访问一个虚拟地址，先查 TLB；命中就直接拿到物理页号，不查页表。TLB 未命中，MMU 才按 CR3 指向的顶层页表走这 4 级（5 级页表就是 5 级）；如果 PTE 的 present 位是 1、权限也允许，就把翻译填进 TLB，继续执行——这不是缺页。

PTE 不只有物理页号：还有 present、writable、user、accessed、dirty、NX 等位。写一个只读页、用户态访问内核页，也会触发异常，只是处理方式不同。

TLB 很小，装不下大工作集。2 MiB 大页让一项覆盖 512 个 4 KiB 页，减少页表层级和 TLB 压力；代价是内部碎片，分配不如 4 KiB 灵活。页表本身也占内存，Linux 在 `/proc/<pid>/smaps_rollup` 的 `PageTables` 里单列。

## 缺页：minor 和 major 是两种事

Linux 把缺页分成 minor 和 major：minor 不需要 I/O，major 需要 I/O。Windows 的说法是 soft fault 和 hard fault，口径接近。

一次访问的完整路径：

1. CPU 用虚拟地址查 TLB；命中就继续。
2. TLB 未命中，MMU 走页表；PTE present 且权限允许，填 TLB，继续，没有异常。
3. PTE 不 present，或权限不符，触发缺页异常；x86 把出错地址放在 CR2。
4. 内核检查这个地址属于哪个 VMA（Windows 里是 VAD）。没有 VMA、或权限根本不允许，发 SIGSEGV（Windows 是 access violation）。
5. 地址合法，按页的来源处理：
   - Linux 的匿名页第一次读：映射共享零页；第一次写：分配一页并清零。这是 minor fault，不需要磁盘 I/O，但要花 CPU 清零。
   - 文件页已经在 page cache：把 PTE 指向它，minor fault。
   - 文件页不在 page cache：从磁盘读，可能顺带 readahead 多页，major fault。
   - 页在 swap：从 swap 读回，major fault；如果 swap cache 里还有这份页，只是重建 PTE，算 minor。
   - COW 页：复制一页；原页驻留时不需要磁盘 I/O，已被换出则先换入，算 major。
6. 更新 PTE，必要时刷新 TLB，返回用户态重试刚才那条指令。

缺页是正常机制，不是错误；只有地址不在任何 VMA、或权限根本不允许（比如写只读代码段）才是段错误/访问违例。COW 的写保护是另一条路径，内核会复制后继续。进程启动时也不是每一页都缺一次：共享库和可执行文件可能已在 page cache，readahead 一次带入多页，启动时的 fault 里有一部分只是 minor；冷启动时真正等 I/O 的是 major fault。

## 1 GiB 的 mmap，只读 4 KiB

这次换一个文件映射：建一个 1 GiB 的文件，只在开头写 4 KiB 真数据，然后映射整个文件，只碰第 0 页。

```python
import mmap
import os
import tempfile

import psutil

path = os.path.join(tempfile.gettempdir(), "paideia_mmap.bin")
with open(path, "wb") as f:
    f.truncate(1024**3)
    f.seek(0)
    f.write(os.urandom(4096))
    f.flush()
    os.fsync(f.fileno())

p = psutil.Process()

def rss():
    return p.memory_info().rss

print("file_size", os.path.getsize(path))
base = rss()
print("rss_before", base)
with open(path, "rb") as f:
    with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as mm:
        after_map = rss()
        print("rss_after_mmap", after_map, "delta", after_map - base)
        _ = mm[0]
        after_touch = rss()
        print("rss_after_touch_page0", after_touch, "delta", after_touch - after_map)
        _ = mm[4095]
        after_last = rss()
        print("rss_after_touch_last_byte_page0", after_last, "delta", after_last - after_touch)

os.remove(path)
```

本机输出：

```text
file_size 1073741824
rss_before 16642048
rss_after_mmap 16646144 delta 4096
rss_after_touch_page0 16650240 delta 4096
rss_after_touch_last_byte_page0 16650240 delta 0
```

映射 1 GiB 只让 RSS 增加 4 KiB（页表和映射元数据）；碰第 0 页再增加 4 KiB；再碰第 4095 字节，RSS 不变，因为还在同一页。这次是 minor fault：文件刚写过，页还在系统文件缓存里，没有磁盘 I/O。

别拿 `truncate` 出来的全零文件做这个实验。我试过一次，读到的零页没有让 RSS 涨，容易误判成「mmap 不占内存」。先用真实数据写第一页，再看工作集。

这里 `psutil` 的 `rss` 在 Windows 上就是 `WorkingSet`；Linux 对应 `/proc/<pid>/status` 的 `VmRSS`。

## fork 之后，物理页并没有立刻复制

Linux 的 `fork()` 先复制页表，不复制私有物理页。对私有可写页，父子的 PTE 都指向同一物理页，两边都标成只读。任何一方写，触发保护性缺页，内核复制这一页（基础页 4 KiB；透明大页开启时可能是 2 MiB）、把这一边的 PTE 改成可写；之后各写各的。只读的 `.text`、共享库页不复制。

这就是 COW（copy-on-write）。它延迟了复制，不是取消了复制：

- `fork()` 本身要复制页表；地址空间越大、映射越多，这一步越贵。
- 子进程如果写遍所有页，物理内存还是会翻倍；COW 只保证「没写就不复制」。
- COW fault 本身不需要磁盘 I/O，但要分配并复制一页，吃内存带宽；原页被换出时，先换入就是 major。透明大页开启时，复制单位可能是 2 MiB，不是 4 KiB。

shell 执行命令时常见 `fork()` 后立刻 `exec()`；子进程还没写几页就把地址空间换掉，所以 COW 复制得很少。`posix_spawn`、`vfork` 还能进一步避开页表复制。

Windows 没有 `fork()`；`CreateProcess` 直接建新地址空间。Python 在 Windows 上 `os.fork` 不存在，`multiprocessing` 默认用 spawn。这段是按 Linux 实现描述的，本机没有跑 fork/COW 实验。

## VSZ 2 GB、RSS 80 MB：申请了不等于占了

在 Linux 上，`ps -o vsz,rss` 显示 VSZ 2 GB、RSS 80 MB，最合理的解释是：地址空间里大部分是未触碰的匿名映射或保留区，当前只有 80 MB 页在 RAM。不是 `ps` 算错了，也不是进程已经占了 2 GB。

| 指标 | 看的是什么 | 容易错在哪 |
| --- | --- | --- |
| VSZ / VIRT | 虚拟地址空间总量，含保留区、映射、共享库 | 不能拿来算物理内存预算 |
| RSS / RES | 当前在 RAM 的页，含共享页和文件映射页 | 多进程相加会重复计算；文件页可回收 |
| PSS | 共享页按共享者数量均摊 | 需要 `/proc/<pid>/smaps_rollup`；不是 `free` 的字段 |
| USS | 只算进程私有、退出可释放的页 | 不含共享；Windows 没有同名指标 |

十个进程各自 RSS 100 MB，不说明总共用了 1 GB：共享的 libc、SSL 库、page cache 页会被每个进程各算一遍。PSS 把共享页按共享者数量均摊，USS 只算私有页；要判断「这个进程退出能省多少」，看 USS 更接近。

Linux 在 `/proc/<pid>/smaps_rollup` 里给 `Pss`、`Private_Clean`、`Private_Dirty`、`PageTables`；Windows 的 `PrivateMemorySize64` 是私有提交量，不是 USS，任务管理器里的 active private working set 也不是严格 USS。

容器里尤其容易把 `-Xmx` 当成进程总内存。`-Xmx` 只是 Java 堆上限；进程还包括元空间、线程栈、直接内存、code cache、GC 结构、页表。JDK 10+ 默认容器感知（8u191+ 有回移），堆上限会参考 cgroup，但堆外仍要留余量。

cgroup v2 的 `memory.current` 把 anon、file cache、内核内存都算进去；看 `memory.stat` 拆分。cgroup 的 `memory.max` 被撞到，内核在 cgroup 内触发 OOM，进程收到 SIGKILL；如果先撞到 Java 堆上限，Java 会抛 `OutOfMemoryError`，这是另一条路径。被 cgroup OOM 杀时，Java 层可能什么都看不到。

Linux 的 OOM killer 也不是按 RSS 排行榜杀人：全局 OOM 看 `oom_score`/`oom_score_adj`，cgroup OOM 看 cgroup 限制；一个 RSS 不大的进程也可能被选中。Windows 没有 Linux 这种 OOM killer，提交限额耗尽时是分配失败或页文件扩张。

## free 里的 buff/cache 不是浪费

Linux `free -h` 的列（字段示意，本文没有在 Linux 上执行）：

| 列 | 含义 |
| --- | --- |
| `total` | 总内存 |
| `used` | 已用口径，别拿 `total - free` 当可用量 |
| `free` | 完全没被使用的页 |
| `buff/cache` | 页缓存、缓冲、可回收 slab 等 |
| `available` | 内核估计的新工作负载可用量 |

`free` 列小是正常的：页缓存占着内存是为了加速文件读写，分配压力上来时干净页可以直接回收。`buff/cache` 里也有不能按干净页那样直接丢的部分：脏页要写回，tmpfs/shmem 页要走 swap，`mlock` 和被 pin 住的页不能回收。判断够不够，看 `MemAvailable`（`free` 的 `available` 列），它是内核的估算，不是精确值。

page cache 和进程 RSS 有重叠：文件页映射进进程会计入 RSS，同时它也是系统 page cache。把 RSS 和 `buff/cache` 相加会重复计算。读一个大文件后 `buff/cache` 涨、`free` 降，不代表泄漏；下次分配会回收干净页。

Windows 任务管理器里 `Available` 才接近可用；`Standby` 是缓存，`Free` 是完全未用，`Commit` 是另一回事。资源监视器里 `Standby` 大也不是浪费。

## swap、overcommit 与 OOM：没有一键安全

- Linux swap 是匿名页的后备；swap 用量高不一定是问题。抖动是工作集装不下：持续 major fault、swap in/out、CPU 等 I/O，吞吐下降。短时 `si`/`so` 非零正常；持续高且伴随 major fault 才是信号。处理是减并发、缩工作集、加内存或换更快后备存储；加 CPU 没用。
- `vm.overcommit_memory=1` 让 `malloc` 更容易成功，但不保证触碰时还有页；`=2` 严格按 `CommitLimit`，可能明明有空闲 RAM 也拒绝分配；`=0` 是启发式。不要把某一个值当万能。
- 关掉 swap 不是安全开关：匿名页少了一条可回收路径，压力直接落到 OOM；swap 在慢盘上确实会抖动。Windows 的 pagefile 同理：禁用会降低 commit limit，可能让分配失败。
- OOM killer 的行为不是契约：全局 OOM 可能选中 RSS 不大的进程，cgroup OOM 在限制内选；`oom_score_adj` 会改变选择。不要承诺「先杀最大的」。

## 跑一遍

上面的保留实验可以原样跑；`psutil` 没装就先 `pip install psutil`。`resource` 模块在 Windows 上不存在，所以不要用 `getrusage` 的 `ru_maxrss` 来对照。

mmap 实验的完整脚本在上面的「1 GiB 的 mmap」一节，文件在系统临时目录，跑完会删除。它会在 Windows 上创建 1 GiB 文件；磁盘空间不够就改成 256 MiB，结论不变。

Linux 上对应看什么（本机没有 Linux，以下未执行，因此不贴输出）：

```bash
grep -E 'VmSize|VmRSS|VmSwap' /proc/<pid>/status
cat /proc/<pid>/smaps_rollup
free -h
vmstat 1 5
```

`smaps_rollup` 里有 `Pss`、`Private_Clean`、`Private_Dirty`、`PageTables`；`free` 看 `available`；`vmstat` 的 `si`/`so` 持续高才说明换页压力。`/proc/vmstat` 里的 `pgmajfault` 是 major fault 累计值。

## 还差的

- 没有 Linux 机器：`free` 的 `MemAvailable`、`/proc/<pid>/smaps_rollup` 的 PSS/USS、`vmstat` 的 si/so、global/cgroup OOM 都没有在本机跑；这些是文档与实现描述，不是实测输出。
- 没有制造 major fault：mmap 实验的文件页刚写过、在 page cache 里，只走了 minor fault；没有在 Windows 上清缓存后冷读，也没有 Linux 的 drop_caches，major fault 的耗时和计数没测。
- 没有做 fork/COW 实验：Windows 没有 `fork`，本机也没有 Linux；COW 的页表复制与写时复制按 Linux 实现描述，未观测。
- 没有测 PSS/USS 和多进程共享页：Windows 的 `PrivateMemorySize64` 不是 USS；只给了定义和 Linux 观测入口。
- 没有验证大页与 5 级页表是否在本机启用：48/57 位、2 MiB/1 GiB 大页是架构文档值，本机 CPU/OS 的实际启用状态未查。
