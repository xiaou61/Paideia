## 先跑一条命令：一个 `ls` 到底进了多少次内核

在测试机或自己的 Linux 服务器上，先确认 `strace` 在不在：

```bash
command -v strace || echo "没装 strace"
```

有就数一次 `ls /` 的系统调用：

```bash
strace -c ls / > /dev/null
```

`-c` 只汇总，不逐行打印；`> /dev/null` 只是把 `ls` 的输出丢掉，`strace` 的汇总仍写在终端上。没装，或者容器/权限不允许 `ptrace`，退一步看一次快照：

```bash
sleep 60 &
pid=$!
cat /proc/$pid/syscall
kill $pid
```

`/proc/<pid>/syscall` 第一列是系统调用号（显示 `running` 时说明采样那一刻不在系统调用里），后面是参数；它只给你采样那一刻的快照，看不到历史。要次数，还是得 `strace -c`。

把 `strace -c` 输出里这四行的 `calls` 抄到下面：

| syscall | 你机器上的 calls | 它在干什么 |
| --- | ---: | --- |
| `openat` |  | 按路径打开目录或文件 |
| `newfstatat` |  | 取文件元数据：大小、类型、权限 |
| `getdents64` |  | 读目录项 |
| `write` |  | 把结果写到标准输出 |

你的机器上可能还有 `close`、`mmap`、`brk`、`statx`，这正常；不同 glibc 和 coreutils 版本走的调用不一样。

一个 `ls /` 为什么要进内核这么多次？因为 `ls` 不是一条系统调用。它要打开目录（`openat`）、读目录项（`getdents64`）、为每个条目取元数据（`newfstatat`）、把结果写出去（`write`）；动态链接器还要打开共享库，locale 也可能要读文件。你看到的一行 `strace`，背后是一次完整的特权级往返。

> 说明：下面这些 Linux 命令按标准形态写，输出会随发行版和版本变化；表中的数字请在你的机器上填。

第一次读可以先跳过这些词：KPTI/PCID、epoll、io_uring、seccomp/namespace/CapEff、scatter-gather DMA。它们各自只影响一段，不影响主线；第二遍再回头看。

## 三句话，先把账挂对

1. **系统调用不是普通函数调用。** 普通调用只压栈、跳转，还在用户态；系统调用要换特权级、换内核栈、查表执行，再切回来。
2. **系统调用是主动的，中断是被动的；异常则是当前指令同步触发的。** `syscall` 是你自己执行的一条指令；硬件中断是设备从外面异步打断；异常是当前指令踩到缺页、除零之类的问题。系统调用在语义上是同步 trap，不是和「异常」并列的第三类，后面会把术语拆开。
3. **每次 syscall 的固定成本不在「缓存被刷掉」。** `syscall` 不刷数据 cache；没开 KPTI 时不换 CR3；开了 KPTI 且 CPU 有 PCID 时也不会把 TLB 全量冲掉。每次真正付的是入口/出口代码、寄存器保存、参数与权限检查、seccomp/LSM/审计钩子，以及 Spectre 缓解；缓存和 TLB 明显变冷主要发生在进程被换下、换到另一个地址空间之后，不该算到每次 syscall 头上。

## 一次系统调用走了哪七步

以 `read(fd, buf, 4096)` 为例：

1. 你的代码调用 libc 的 `read`。它只是包装，不是内核代码；它负责把参数摆好，出错时把 `-errno` 转成 `-1` 并设置 `errno`。
2. libc 把系统调用号放进 `rax`，参数放进 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`。第四个参数用 `r10` 而不是 `rcx`，因为 `syscall` 指令自己要占用 `rcx` 存返回地址。
3. 执行 `syscall` 指令。CPU 切到 ring 0，把返回地址存进 `rcx`、把 `RFLAGS` 存进 `r11`，跳到内核预先登记的入口；入口代码换到内核栈。
4. 内核保存用户态寄存器，按 `rax` 里的调用号查系统调用表，找到 `sys_read`。
5. 内核检查 fd 是否合法、缓冲区是否可写、有没有权限；seccomp、LSM、审计钩子也可能在这里跑。然后读页缓存，或者发起磁盘 IO。
6. 返回时把结果放进 `rax`。如果是错误，返回一个负的 `-errno`（例如 `-EAGAIN`）；libc 把它转成 `-1`，并设置全局 `errno`。
7. 执行 `sysret` 回到用户态，恢复寄存器，继续你的代码。遇到需要完整 `iret` 的状态（例如返回地址不合法、单步标志），内核走慢路径 `iretq`。

```text
用户态：  read() ──┐
                  │ syscall
内核态：           └─> sys_read() ──> 页缓存 / 磁盘
                  ┌─ sysret
用户态：  read() <─┘
```

不同架构的指令不同：x86-64 用 `syscall`/`sysret`，32 位 x86 老办法是 `int 0x80` 或 `sysenter`，ARM64 用 `svc #0`。ARM64 的系统调用号放在 `x8`，参数在 `x0` 到 `x5`，返回值在 `x0`；`svc` 产生同步异常，进入 EL1。名字不同，模型一样：一条特殊指令 + 一个编号 + 一组寄存器。

系统调用号是内核 ABI 的一部分。x86-64 的头文件里是这些值：

```text
/* x86-64: asm/unistd_64.h */
#define __NR_read 0
#define __NR_write 1
#define __NR_openat 257
#define __NR_sendfile 40
```

ARM64 的编号和 x86-64 不同，不要在任何代码里写死数字；用 libc 的包装或 `syscall(__NR_xxx, ...)`。

## 不是所有「系统调用」都真的进内核

`gettimeofday`、`clock_gettime`、`getcpu`、`time` 这类只读调用，内核把实现放进了 vDSO：一段映射到用户态的内核代码。libc 从 auxv 找到 vDSO 地址，能走就直接调用，不切换特权级。所以高频取时间戳比想象中便宜；如果 vDSO 不可用，或这个 clock 不支持 vDSO，libc 会退回真正的系统调用。

这也提醒一件事：**别把「库函数」和「系统调用」划等号。** `printf` 是 libc 函数，它先在用户态缓冲，缓冲区满了或你 `fflush` 时才调用 `write`；`malloc` 大多在用户态管理堆，只有向内核要新页时才调用 `brk`/`mmap`。`getpid` 不是 vDSO，它是一次真正的系统调用（glibc 2.25 以后不再缓存 PID），适合拿来做微基准。

## 贵的不是缓存：一次 syscall 的固定成本

先把一个容易传错的结论拆掉：**`syscall` 不刷数据 cache，也不必然换 CR3。**

- 没有 KPTI 时，内核页本来就在用户页表里，只是页表项的 U/S 位不允许用户访问；`syscall` 不需要换 CR3。
- 开了 KPTI（Meltdown 缓解，常见于 Intel 机器）时，用户页表不再映射内核的大部分地址，进出内核要换 CR3。CPU 支持 PCID 时，内核给用户和内核不同的 PCID，换 CR3 不会把整个 TLB 冲掉；不支持 PCID 的老 CPU 才会付出更大的 TLB 失效代价。
- 数据 cache 从来没有被 `syscall` 指令清掉。内核代码会占一些 cache 行，但这不是「用户数据全部失效」。

每次调用真正固定付的是：入口/出口代码、寄存器保存、栈切换、参数校验、seccomp/LSM/审计钩子，以及 Spectre 缓解（IBRS、retpoline、RSB 填充等，取决于 CPU 和内核配置）。如果这次调用要搬数据，还要加上 `copy_from_user`/`copy_to_user` 的拷贝，这部分随字节数增长。

**线程切换不换页表。** 同一个进程里的线程共享 `mm_struct`，切线程只换寄存器、内核栈、调度器记账，可能还有 FPU/SIMD 状态；页表不变。只有切到另一个进程才换 mm/CR3。切到内核线程时它没有自己的用户 `mm`，Linux 会借用上一个进程的 `active_mm`（lazy TLB）；只要借用的 `active_mm` 没变，就不写 CR3。

所以「减少系统调用次数」仍然值钱，但理由是每次的入口/出口、检查和拷贝，不是「每次刷缓存」。缓存和 TLB 明显变冷，主要出现在线程被抢占、换到另一个进程之后；那是调度器的账，不是每次 syscall 的固定成本。

把三种切换分开：

| 类型 | 发生了什么 | 这笔账记在谁头上 |
| --- | --- | --- |
| 模式切换（用户 ↔ 内核） | 换特权级、换内核栈、保存/恢复寄存器 | 入口/出口代码、检查、Spectre 缓解；不刷数据 cache，不必然换 CR3 |
| 线程切换（同进程） | 保存/恢复线程寄存器、内核栈、调度器记账 | 共享 `mm_struct`，不换页表；可能有 FPU/SIMD 状态保存 |
| 进程切换 | 换 mm/CR3、内核栈、寄存器 | 地址空间变了，TLB 与缓存局部性才会明显受影响 |

要数字，别背常数。下面这段 C 在 Linux 上编译后，能粗略比较一次 `getpid` 系统调用和一次 vDSO `clock_gettime` 的相对成本：

```bash
cat > bench.c <<'EOF'
#define _GNU_SOURCE
#include <stdio.h>
#include <time.h>
#include <unistd.h>
#include <sys/syscall.h>

static long ns(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1000000000L + t.tv_nsec;
}

int main(void) {
    const long n = 1000000;
    volatile long sink = 0;
    long t0 = ns();
    for (long i = 0; i < n; i++) sink += syscall(SYS_getpid);
    long t1 = ns();
    for (long i = 0; i < n; i++) sink += ns();
    long t2 = ns();
    printf("getpid syscall: %.0f ns/call\n", (double)(t1 - t0) / n);
    printf("clock_gettime:  %.0f ns/call\n", (double)(t2 - t1) / n);
    return 0;
}
EOF
cc -O2 bench.c -o bench && ./bench
```

没有 `cc` 就换 `gcc` 或 `clang`。`clock_gettime` 走 vDSO 时不会进内核；如果两者数字接近，先确认 vDSO 是否可用，别急着下结论。这段代码我没有在本机跑（Windows），输出以你的机器为准。

## 阻塞、非阻塞、异步：三种「等」的姿势

`read` 一个没有数据的 socket，内核有三种处理方式：

| 方式 | 行为 | 进程状态 | 适用 |
| --- | --- | --- | --- |
| 阻塞 | 睡到有数据，唤醒后返回 | 可中断睡眠（`S`） | 简单、每连接一线程 |
| 非阻塞 | 立刻返回 `EAGAIN` | 继续跑 | 配合 `epoll` 等就绪通知 |
| 异步 IO | 提交请求，完成后再通知 | 继续跑 | 高并发、大量 IO |

**阻塞不浪费 CPU**：进程被移出运行队列，CPU 去跑别的任务。真正浪费 CPU 的是「非阻塞 + 忙轮询」——一直问「好了吗」，把核占满却什么也没干。

高并发服务器的主流做法是「非阻塞 + 就绪通知」：把几千个 fd 注册到 `epoll`，内核告诉你哪些就绪，你只对就绪的 fd 调 `read`。这样既不用几千个线程，也不用忙等。Go 的 netpoller、Java NIO、Node 的 event loop 都是这个模型的不同包装。

注意：一些语言里的 `async` 只是 `epoll` 或线程池的包装，不等于内核异步 IO。要看它最终用的是哪组系统调用：`epoll_wait`、`io_uring_enter`，还是把阻塞调用丢进线程池。

## 中断与异常：异步和同步是两条线

系统调用是当前线程主动执行一条指令；硬件中断是设备在某个时刻打断 CPU（可能被屏蔽延迟）；异常是当前指令执行时同步触发。三者都会进内核，但来源和返回路径不同。

| 类别 | 例子 | 同步/异步 | 返回哪 |
| --- | --- | --- | --- |
| 硬件中断 | 网卡收包、磁盘完成、定时器 | 异步 | 被打断的指令流 |
| 异常 fault | 缺页、除零、非法指令 | 同步 | 缺页重试当前指令；除零/非法指令给信号 |
| 异常 trap | 断点、单步 | 同步 | 下一条指令 |
| 异常 abort | 双重故障、机器检查 | 同步 | 无法恢复，终止任务或系统 |
| 系统调用（trap 语义） | `read`、`write`、`openat` | 同步、主动 | 下一条指令 |

**术语要拧清：** x86 的 exception 分 fault、trap、abort 三类，trap 不是和 exception 并列的第三类。系统调用在语义上是主动 trap；x86-64 上它由专用 `syscall` 指令实现，不经过 IDT 的异常门，ARM64 的 `svc #0` 则产生同步异常。把「中断 / 异常 / 陷阱」并列成三类，是通俗说法，不是 Intel 手册的分类。

缺页是 fault：内核把页映射好，重新执行刚才那条指令；系统调用是 trap 语义：处理完回到下一条指令。这个区别在调试时很有用——看到「重复执行同一条指令」和「跳到下一条」，就能判断是缺页还是系统调用/断点。

## 中断为什么分上下半部

硬件中断的处理分两半。上半部（hardirq）在本 CPU 关中断或屏蔽同号中断，只做最紧急的事：收下数据、清中断标志、把后续工作排进队列。它要短，因为这段时间别的中断可能被延迟。

中断后的延后处理有好几种，别混：

| 机制 | 运行在 | 能睡眠吗 | 典型工作 |
| --- | --- | --- | --- |
| hardirq | 中断上下文 | 不能 | 收数据、清中断、唤醒下半部 |
| softirq | 中断上下文（或 `ksoftirqd`） | 不能 | 网络协议栈收尾、短小的非阻塞工作 |
| tasklet | 中断上下文（基于 softirq） | 不能 | 驱动里的短小延后工作 |
| workqueue | 进程上下文（kworker） | 能 | 可能阻塞的活、需要睡眠的驱动工作 |
| threaded IRQ | 内核线程 | 能 | 把大部分处理搬出 hardirq |

**softirq 和 tasklet 不能睡眠**：不能拿 mutex、不能做可能阻塞的分配、不能等 IO。可能睡眠的活放 workqueue 或 threaded IRQ。`ksoftirqd` 名字里有线程，但 softirq 回调仍在不可睡眠的上下文里；不要因为它叫「线程」就以为能睡。

看中断情况：

```bash
cat /proc/interrupts | head
```

第一列是 IRQ 号或名字，后面每列是一个 CPU 的计数。现代机器常见 `LOC`（本地 APIC 定时器）、`RES`（重新调度 IPI）、`CAL`（函数调用 IPI）、`TLB`（TLB shootdown IPI）；也可能有老式的 `IO-APIC` 行。你机器上不一样是正常的。`top` 里的 `hi` 是硬中断占用，`si` 是软中断占用；`si` 长期很高，先看 `/proc/softirqs` 里哪一列在涨，常见的是 `NET_RX`，但也可能是别的。

## 中断亲和性：先把 IRQ 和 CPU 编号找对

想把某个设备中断固定到某个 CPU，先找 IRQ 号，再看当前允许的 CPU 列表：

```bash
nproc
grep -n 'eth0' /proc/interrupts
cat /proc/irq/<irq>/smp_affinity_list
```

`<irq>` 换成你在 `/proc/interrupts` 里找到的号，`eth0` 换成你的网卡名。`smp_affinity_list` 里的 CPU 编号从 0 开始：2 核机器只有 `0` 和 `1`，写 `2` 会得到 `EINVAL`。确认后再写：

```bash
sudo sh -c 'echo 1 > /proc/irq/<irq>/smp_affinity_list'
cat /proc/irq/<irq>/smp_affinity_list
```

不能写成 `sudo echo 1 > ...`：重定向是当前 shell 做的，`sudo` 只给 `echo` 提权，写文件仍是你自己的权限。也可以 `echo 1 | sudo tee /proc/irq/<irq>/smp_affinity_list`。

`/proc/irq/24` 不一定存在，IRQ 号也不一定是 24；多队列网卡每个队列可能有自己的 IRQ。还有些中断是内核/驱动管理的（managed affinity），手写会 `EINVAL`/`EPERM`，或者被驱动改回去。生产上不要随手改；先确认是哪个队列、哪个 CPU，必要时看驱动的 RSS/RPS/RFS 配置或 `irqbalance`。

## 缺页：最常见的一种同步异常

程序访问一个还没映射到物理内存的页，CPU 触发缺页异常（fault），内核分配物理页、填内容、修页表，然后重新执行那条指令。整个过程对用户态透明。

- **次缺页**（minor fault）：页在页缓存里，只要建立映射；
- **主缺页**（major fault）：要去磁盘或网络读，慢得多。

`ps -o min_flt,maj_flt -p <pid>` 给的是**自进程启动以来的累计值**，不是速率。一条快照说明不了「现在一直在主缺页」；隔几秒采两次做差，或者用 `pidstat -r -p <pid> 1` 看 `majflt/s`：

```bash
ps -o pid,min_flt,maj_flt -p <pid>
sleep 5
ps -o pid,min_flt,maj_flt -p <pid>
```

主缺页也不只来自换出。首次访问 mmap 的文件页、加载可执行文件和共享库、读网络文件系统，都会产生主缺页。要判断是不是 swap，结合 `/proc/vmstat` 的 `pgmajfault`、`pswpin`、`pswpout` 一起看：

```bash
grep -E 'pgmajfault|pswpin|pswpout' /proc/vmstat
```

`/proc/vmstat` 是全局计数，不是这个进程的；要定位进程，结合 `pidstat -r -p` 或 `/proc/<pid>/stat`。`pgmajfault` 在涨、`pswpin/pswpout` 不涨，说明主缺页可能来自文件页首次访问或 exec，不是 swap。反过来，`pswpin/pswpout` 明显在涨，才更像内存压力导致的换入换出。

访问非法地址时，缺页处理失败，内核给进程发 `SIGSEGV`——这就是段错误的来源。**段错误不是「内存坏了」，是「你访问了不该访问的地址」。** mmap 越过文件末尾再访问，可能拿到 `SIGBUS`，不是 `SIGSEGV`。

## strace：把系统调用摊开看

`strace` 靠 `ptrace` 挂到目标进程上，每次系统调用入口和出口各停一次，目标每次都要等 tracer。**它适合定位「在做什么」，不适合测「有多快」；在高吞吐服务上，`strace -p` 能把延迟显著放大，`-c` 也要等 strace 退出才打印汇总。**

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-p <pid>` | 挂到已运行的进程 |
| `-f` | 跟随子进程与线程 |
| `-tt` | 每行带时间戳 |
| `-T` | 每个调用花了多久，包含阻塞等待 |
| `-c` | 结束时汇总每个调用的次数与总耗时 |
| `-e trace=file` | 只看文件相关（`openat`、`stat`、`unlink`） |
| `-e trace=network` | 只看网络相关 |
| `-e trace=openat,read,write` | 只看白名单里的调用 |
| `-y` | 把 fd 翻译成路径或 socket 地址 |
| `-s 200` | 字符串最多显示 200 字节（默认 32） |

一行输出的形状是 `syscall(参数...) = 返回值 <在内核里待的时间>`；`<...>` 是 `-T` 加的。`-e trace=` 是白名单：你只写 `openat,read,write`，`close` 就不会出现，要看得把 `close` 加进去，或者用 `-e trace=file`。`-T` 的时间**包含阻塞等待**：一个 `read` 等了 2 秒，不代表内核算得慢，可能只是在等网络。

挂不上去先看权限：

```bash
cat /proc/sys/kernel/yama/ptrace_scope
```

| 值 | 含义 |
| --- | --- |
| 0 | 经典模式，同用户可 attach |
| 1 | 只能 attach 自己的后代，或有 `CAP_SYS_PTRACE` |
| 2 | 只有 root / `CAP_SYS_PTRACE` |
| 3 | 不允许 attach |

容器里还受 seccomp 与 `CAP_SYS_PTRACE` 限制；`docker run --cap-add=SYS_PTRACE` 只适合临时调试，不是生产修复。

要在预发或低峰采样，给它一个截止时间：

```bash
timeout -s INT 10 strace -c -p <pid>
```

10 秒后 `timeout` 给 strace 发 `SIGINT`，strace 打印汇总并退出；`timeout` 自己返回 124，这是正常的。生产环境优先 `perf trace -p <pid>`（基于 tracepoint，开销比 ptrace 小，但仍不是零）、`bpftrace` 短时脚本，或 `cat /proc/<pid>/syscall` 这种几乎免费的单次快照（同样受 ptrace 权限限制）。任何 attach 之前，先确认目标能不能承受。

## 系统调用也是安全边界

系统调用是内核暴露给所有进程的接口，也是主要的攻击面之一。容器用 seccomp 过滤允许的调用，用 namespace 隔离资源视图，用 capability 控制权限位；这三件事不是一回事：

- **seccomp** 看的是系统调用号和参数，不看你打开的路径；
- **namespace** 改的是进程能看到的 PID、网络、挂载等视图，不是权限本身；
- **capability** 是权限位，`CapEff` 在 `/proc/<pid>/status` 里，可以用 `capsh --decode=<十六进制>` 翻译。

一个程序在宿主机跑得好，进容器却报 `Operation not permitted`，常见原因是 seccomp 或 capability 挡了某个系统调用，而不是文件权限。排查顺序：先用 `strace` 看是哪次调用返回 `EPERM`，再对照容器的 seccomp profile 与 `CapEff`。`docker run --security-opt seccomp=unconfined` 能临时放开，但等于拆掉一层防护；正确做法是把确实需要的调用加进白名单。Kubernetes 里对应 `securityContext.seccompProfile`。

系统调用号与参数构成稳定的 ABI，但这句话只保证「同一架构的 syscall 接口稳定」，不保证「同一个动态链接二进制能在不同发行版上跑」。glibc、动态链接器和共享库版本会挡：`GLIBC_2.34 not found` 就是典型。跨发行版要么静态链接，要么用容器/同年代的基础镜像；不同架构的调用号也不同，不要写死数字。

## 零拷贝：sendfile 省掉了哪两次拷贝

传统「读文件再发到 socket」：

```text
read(file, buf, n)    // 磁盘 → 页缓存（DMA）→ 用户缓冲区（CPU 拷贝）
write(sock, buf, n)   // 用户缓冲区 → socket 缓冲区（CPU 拷贝）→ 网卡（DMA）
```

冷缓存时，一共 **2 次系统调用、4 次用户态/内核态模式切换、2 次 CPU 拷贝 + 2 次 DMA 拷贝**。这里的「4 次」是模式切换，不是调度器把线程换下去的那种上下文切换；别和上一节的线程/进程切换混为一谈。数据在用户态走了一趟，但应用根本没看它——只是搬运。

`sendfile(out_fd, in_fd, NULL, count)` 把搬运交给内核：

```text
sendfile(sock, file, NULL, n)  // 页缓存 → socket 缓冲区（可能只传描述符）→ 网卡
```

数据不再进用户态，用户缓冲区那次 CPU 拷贝省掉了；系统调用从 2 次降到 1 次，模式切换从 4 次降到 2 次。页缓存到 socket 缓冲区的那次 CPU 拷贝是否也能省，取决于网卡/驱动是否支持 scatter-gather DMA 和内核版本；支持时只传数据块描述符，不支持时仍要拷贝。这就是 Nginx 发静态文件、Kafka 给消费者发日志段时用零拷贝的原因。

**「零拷贝」不是一次拷贝都没有**：DMA 仍然要把数据从磁盘搬到内存、从内存搬到网卡，只是省掉了 CPU 在用户态与内核态之间的来回拷贝。而且它要求「不对内容做修改」——应用层要压缩、加密、改 header，就没法直接用 `sendfile`。`sendfile` 主要用在文件到 socket 的路径；管道之间可以用 `splice`，但那是另一组接口。

## 为什么频繁的小 IO 慢

把一次 `write` 的成本拆开：

- 入口/出口代码与寄存器保存；
- 参数检查、权限检查、seccomp/LSM/审计钩子；
- 数据从用户缓冲区拷进页缓存；
- 更新文件偏移、标记脏页、可能唤醒回写线程；
- 返回时再切一次。

**这些固定成本与字节数无关。** 写 1 字节和写 4 KB，固定部分几乎一样；拷贝部分才随字节数增长。算一笔账（1 MiB 日志，每条 256 字节）：

| 写法 | 系统调用次数 | 固定成本 |
| --- | ---: | --- |
| 每条日志 `write` 一次 | 4096 | 4096 次入口/出口 |
| 攒 8 KiB 再写 | 128 | 128 次入口/出口 |

所以标准库都有用户态缓冲：`stdio` 的 `BUFSIZ`、Java 的 `BufferedWriter`、Python 的 `io.BufferedWriter`。它们的作用就是把多次小写合并成少数几次大写。缓冲要注意及时 `flush`，否则日志会延迟；进程崩溃时，用户态缓冲里的数据也会丢，`fsync` 才能保证落盘。

对应的优化手段：

- **批量**：`writev` 一次写多个缓冲区；`sendmmsg` 一次发多个 UDP 包；
- **缓冲**：应用层攒够再写，但要注意及时 `flush`；
- **异步**：`io_uring` 把提交与完成分开，减少往返；
- **合并**：数据库的组提交、消息队列的批量发送，本质都是摊薄固定成本。

网络侧还有 Nagle 算法：小包先攒着，等 ACK 或攒够再发。它减少小包数量，但会增加延迟，低延迟场景常配 `TCP_NODELAY`。这是「批量」与「及时」的取舍在协议层的体现。

## 一个循环里的两万次 stat

一个 Python 脚本扫描目录，判断每个条目是不是文件，再取大小。先把它写成能直接跑的两个版本：

```python
import os
import sys

root = sys.argv[1]
mode = sys.argv[2] if len(sys.argv) > 2 else "listdir"

def process(path):
    pass

if mode == "scandir":
    with os.scandir(root) as entries:
        for entry in entries:
            if entry.is_file() and entry.stat().st_size > 0:
                process(entry.path)
else:
    for name in os.listdir(root):
        full = os.path.join(root, name)
        if os.path.isfile(full) and os.path.getsize(full) > 0:
            process(full)
```

把上面的代码保存为 `scan.py`。找一个文件多的扁平目录，或者自己造一个：

```bash
mkdir -p /tmp/scan-test
cd /tmp/scan-test
for i in $(seq 1 10000); do : > "f$i"; done
```

先跑 `listdir` 版本，再跑 `scandir` 版本：

```bash
strace -c -f python3 scan.py /tmp/scan-test listdir
strace -c -f python3 scan.py /tmp/scan-test scandir
```

两次都看 `newfstatat` 那一行的 `calls`。按 10000 个普通文件算：

| syscall | `listdir` 版本 | `scandir` 版本 | 为什么 |
| --- | ---: | ---: | --- |
| `newfstatat` | 约 20000 | 约 10000 | `isfile` + `getsize` 各 stat 一次；`scandir` 的 `d_type` 省掉 `is_file` 的 stat，但 `stat().st_size` 仍要一次 |
| `getdents64` | 目录块数 | 基本相同 | 都是读目录项，不随文件数一比一增长 |
| `openat` | 启动 + 打开目录 | 基本相同 | 不随文件数线性增长；大头是解释器启动和导入 |

`scandir` 在读取目录时带回来的是 `d_type`，只告诉你类型（普通文件、目录、符号链接等），**不带文件大小**。所以 `entry.stat().st_size` 第一次调用仍要一次 `newfstatat`；同一个 `DirEntry` 上再调 `stat()` 才命中缓存。`DT_UNKNOWN` 的文件系统上，`is_file()` 自己也会 stat；符号链接默认跟随，`is_file()` 可能为链接目标 stat。**所以 after 里 `newfstatat` 不会消失，只是从每文件 2 次降到 1 次，约等于文件数。**

`getdents64` 的次数取决于目录项占多少块，不是每个文件一次；`openat` 的大头是 Python 启动、导入模块和打开目录，也不会随文件数线性增长。把两次 `strace -c` 的 `calls` 抄进上面的表，你能看到真正随文件数增长的是 `newfstatat`。

**这不是 Python 的锅，是「每个文件多问一次内核」的锅。** 同样的模式在 Java 的 `File.exists()` + `length()`、Shell 的 `for f in *; do [ -f "$f" ]` 里都会出现。
