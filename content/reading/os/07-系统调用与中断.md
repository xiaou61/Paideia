## 先把结论摆出来

**你的程序没有权限直接碰硬件、碰别的进程、碰内核数据结构。它想读写文件、发网络包、开进程，只能"请求"内核代办。这个受控入口就是系统调用。**

```sketch

    [
      { "id": "user", "title": "用户态程序", "sub": "只能请求，不能直接干", "tone": "gray" },

    ]

  "arrows": [
    { "from": "user", "to": "syscall" },
    { "from": "syscall", "to": "kernel" }
  ]
}
```

三句话先记住：

1. **系统调用不是普通函数调用**。普通调用还在用户态，只压栈跳转；系统调用要切换特权级，进入内核执行，再切回来。
2. **中断是硬件或异常打断当前执行流**，系统调用则是一条指令主动"敲门"。两者最终都进入内核，但来源不同：一个是被动的，一个是主动的。
3. **切换本身不贵，贵的是它带来的附带损失**：缓存与 TLB 失效、阻塞与唤醒、每次调用固定的检查与拷贝。所以"每秒几万次小 `read`"会比"一次读一大块"慢得多，哪怕总字节数一样。

## 用户态与内核态：为什么必须有这道墙

CPU 至少有两个特权级（x86 上叫 ring 0 和 ring 3）：

| 状态 | 能做什么 | 你的代码在哪 |
| --- | --- | --- |
| 用户态 | 只能访问自己的地址空间，不能执行特权指令 | 业务代码、运行时、libc |
| 内核态 | 访问全部内存、配置页表、操作设备、关中断 | 内核、驱动 |

这道墙不是礼貌约定，是硬件强制的：

- 页表里每个页有权限位，用户态访问内核页直接触发异常；
- `in`/`out` 这类端口指令、改页表基址、关中断，在用户态执行会报错；
- 想改这些，只能通过内核预先开好的入口。

为什么不让所有程序都跑在内核态？因为一个指针写错就能覆盖别人的内存、一个死循环就能让整机失去响应。**隔离的代价是切换，收益是"一个程序崩了不影响其他程序"。**

## 一次系统调用到底走了哪些步

以 `read(fd, buf, 4096)` 为例：

1. 你的代码调用 libc 的 `read`（它只是个包装，不是内核代码）；
2. libc 把系统调用号放进寄存器（x86-64 是 `rax`），参数放进 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`；
3. 执行 `syscall` 指令。CPU 切换到 ring 0，跳到内核预先登记的入口；
4. 内核保存用户态寄存器与栈，按调用号查系统调用表，找到 `sys_read`；
5. 内核检查 fd 是否合法、缓冲区是否可写、有没有权限，然后读页缓存或发起磁盘 IO；
6. 返回时把结果放进 `rax`。如果是错误，返回一个 `-errno`（例如 `-EAGAIN`），libc 把它转成 `-1` 并设置全局 `errno`；
7. 执行 `sysret` 回到用户态，恢复寄存器，继续你的代码。

不同架构的指令不同：x86-64 用 `syscall`/`sysret`，32 位 x86 老办法是 `int 0x80` 或 `sysenter`，ARM64 用 `svc #0`。**名字不同，模型一样：一条特殊指令 + 一个编号 + 一组寄存器。**

系统调用号是内核 ABI 的一部分，可以在头文件里查到：

```text
$ grep -E '__NR_(read|write|openat|sendfile)\b' /usr/include/x86_64-linux-gnu/asm/unistd_64.h
#define __NR_read 0
#define __NR_write 1
#define __NR_openat 257
#define __NR_sendfile 40
```

`strace` 输出里的 `read(3, ...)`、`openat(AT_FDCWD, ...)` 就是这些调用。你看到的每一个 `openat`，背后都是一次完整的特权级往返。

### 不是所有"系统调用"都真的进内核

`gettimeofday`、`clock_gettime`、`getcpu` 这类只读调用，内核把实现放进了 **vDSO**：一段映射到用户态的内核代码。libc 直接调用它，不切换特权级。所以高频取时间戳比想象中便宜。

这也提醒一件事：**别把"库函数"和"系统调用"划等号。** `printf` 是 libc 函数，它内部可能调用 `write`；`malloc` 大多在用户态管理堆，只有在向内核要新页时才调用 `brk`/`mmap`。

## 上下文切换的成本：贵在哪

"上下文切换"有两个层次，常被混为一谈：

| 类型 | 发生了什么 | 量级 |
| --- | --- | --- |
| 模式切换（用户 ↔ 内核） | 换栈、换特权级、保存/恢复寄存器 | 几十到几百纳秒，开 KPTI 后更贵 |
| 线程/进程切换 | 换页表、换栈、调度器选择下一个任务 | 微秒级，还附带缓存与 TLB 损失 |

具体数字随 CPU、内核版本、安全缓解措施变化很大，不要背常数，记结论：**空系统调用的开销在"百纳秒到微秒"这个区间；真正的大头是切换后缓存不热了。** 原来在 L1 里的数据，换回来时可能已经被挤掉，要重新从内存拉。

安全漏洞的缓解措施会放大这笔成本。Meltdown 之后引入的 KPTI（内核页表隔离）让每次进出内核都要换页表，系统调用密集的程序因此明显变慢。这也是为什么"减少系统调用次数"在有了 KPTI 之后更值钱。

## 阻塞、非阻塞与"等"的三种姿势

`read` 一个没有数据的 socket，内核有三种处理方式：

| 方式 | 行为 | 进程状态 | 适用 |
| --- | --- | --- | --- |
| 阻塞 | 睡到有数据，唤醒后返回 | 可中断睡眠（`S`） | 简单、每连接一线程 |
| 非阻塞 | 立刻返回 `EAGAIN` | 继续跑 | 配合 epoll 等就绪通知 |
| 异步 IO | 提交请求，完成后再通知 | 继续跑 | 高并发、大量 IO |

**阻塞不浪费 CPU**：进程被移出运行队列，CPU 去跑别的任务。真正浪费 CPU 的是"非阻塞 + 忙轮询"——一直问"好了吗"，把核占满却什么也没干。

高并发服务器的主流做法是"非阻塞 + 就绪通知"：把几千个 fd 注册到 `epoll`，内核告诉你哪些就绪，你只对就绪的 fd 调 `read`。这样既不用几千个线程，也不用忙等。Go 的 netpoller、Java NIO、Node 的 event loop 都是这个模型的不同包装。

## 中断与异常：被动进入内核

系统调用是主动的，中断是被动的。按来源分三类：

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 硬件中断 | 网卡收到包、磁盘完成 IO、定时器 | 异步，随时可能发生 |
| 异常 | 缺页、除零、非法指令 | 与当前指令同步 |
| 陷阱 | 系统调用、断点 | 有意触发，处理完继续 |

硬件中断的处理分两半：

- **上半部**（hardirq）：关中断或屏蔽同号中断，只做最紧急的事——收下数据、清中断标志、把后续工作排进队列。要快，因为这段时间别的中断可能被延迟。
- **下半部**（softirq、tasklet、workqueue）：开中断后慢慢处理，比如把网络包交给协议栈、唤醒等待的进程。

看中断情况：

```text
$ cat /proc/interrupts | head -5
           CPU0       CPU1
  0:         42          0   IO-APIC   2-edge      timer
  1:          3          0   IO-APIC   1-edge      i8042
 16:     128331          0   IO-APIC  16-fasteoi   ehci_hcd:usb1
```

`top` 里的 `hi` 是硬中断占用，`si` 是软中断占用。`si` 长期很高，通常是网络收包太猛（可以看 `/proc/softirqs` 里的 `NET_RX`）；`hi` 高则要看具体设备。

**中断亲和性**可以把某个设备的中断固定到某个 CPU：

```bash
cat /proc/irq/24/smp_affinity_list
echo 2 > /proc/irq/24/smp_affinity_list
```

多队列网卡会给每个队列分配不同中断，让多个 CPU 并行收包。这些是网卡与内核配合的结果，应用层通常不用管，但排查"为什么只有一个核在收包"时会用到。

### 缺页：最常见的一种"异常"

程序访问一个还没映射到物理内存的页，CPU 触发缺页异常，内核分配物理页、填内容、修页表，然后重新执行那条指令。整个过程对用户态透明。

- **次缺页**（minor fault）：页在页缓存里，只要建立映射；
- **主缺页**（major fault）：要去磁盘读，慢几个数量级。

`ps -o min_flt,maj_flt -p <pid>` 能看两个计数。一个进程刚启动时主缺页多，跑久了应该趋于平稳；如果持续有主缺页，说明内存在被反复换出，或者访问模式太随机。

访问非法地址时，缺页处理失败，内核给进程发 `SIGSEGV`——这就是段错误的来源。**段错误不是"内存坏了"，是"你访问了不该访问的地址"。**

## strace 怎么用：把系统调用摊开看

`strace` 靠 `ptrace` 挂到目标进程上，每次系统调用进出都停一下，所以开销很大。**它适合定位"在做什么"，不适合测"有多快"。**

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-p <pid>` | 挂到已运行的进程 |
| `-f` | 跟随子进程与线程 |
| `-tt` | 每行带时间戳 |
| `-T` | 每个调用花了多久 |
| `-c` | 结束时汇总每个调用的次数与总耗时 |
| `-e trace=file` | 只看文件相关（`openat`、`stat`、`unlink`） |
| `-e trace=network` | 只看网络相关 |
| `-y` | 把 fd 翻译成路径或 socket 地址 |
| `-s 200` | 字符串最多显示 200 字节（默认 32） |

一个典型输出：

```text
$ strace -tt -T -e trace=openat,read,write -p 18422
10:21:03.114522 openat(AT_FDCWD, "/etc/hosts", O_RDONLY|O_CLOEXEC) = 5 <0.000021>
10:21:03.114601 read(5, "127.0.0.1 localhost\n", 4096) = 22 <0.000004>
10:21:03.114640 close(5)                = 0 <0.000003>
```

`<...>` 里是这次调用在内核里待的时间。注意它**包含阻塞等待**：一个 `read` 等了 2 秒，不代表内核算得慢，可能只是在等网络。

挂不上去先看权限：

```text
$ cat /proc/sys/kernel/yama/ptrace_scope
1
```

值为 1 时，非父进程不能随便 attach。临时改成 0 可以，但这是安全边界，生产上不要长期放开。容器里还受 seccomp 与 `CAP_SYS_PTRACE` 限制。

## 系统调用还是安全边界

系统调用是内核暴露给所有进程的接口，也是最大的攻击面。容器用 seccomp 过滤允许的调用，用 namespace 隔离资源视图。一个程序在宿主机跑得好，进容器却报 `Operation not permitted`，常见原因是 seccomp 或 capability 挡了某个系统调用，而不是文件权限。

排查顺序：先用 `strace` 看是哪次调用返回 `EPERM`，再对照容器的 seccomp profile 与 `CapEff`。`docker run --security-opt seccomp=unconfined` 能临时放开，但等于拆掉一层防护；正确做法是把确实需要的调用加进白名单。Kubernetes 里对应 `securityContext.seccompProfile`。

系统调用号与参数构成稳定的 ABI，所以同一个二进制能在不同发行版上跑；但不同架构的调用号不同，不要在任何代码里写死数字。

## 零拷贝：sendfile 解决了什么

传统"读文件再发到 socket"的写法：

```text
read(file, buf, n)    // 磁盘 → 内核页缓存（DMA）→ 用户缓冲区（CPU 拷贝）
write(sock, buf, n)   // 用户缓冲区 → socket 缓冲区（CPU 拷贝）→ 网卡（DMA）
```

一共 **2 次系统调用、4 次上下文切换、2 次 CPU 拷贝 + 2 次 DMA 拷贝**。数据在用户态走了一趟，但应用根本没看它——只是搬运。

`sendfile(out_fd, in_fd, NULL, count)` 把搬运交给内核：

```text
sendfile(sock, file, NULL, n)  // 页缓存 → socket 缓冲区（可只传描述符）→ 网卡
```

数据不再进用户态，CPU 拷贝可以省掉（支持 scatter-gather DMA 的网卡只收数据块描述符）。系统调用从 2 次降到 1 次，上下文切换减半。这就是 Nginx 发静态文件、Kafka 发消息时用零拷贝的原因。

**"零拷贝"不是一次拷贝都没有**：DMA 仍然要把数据从磁盘搬到内存、从内存搬到网卡，只是省掉了 CPU 在用户态与内核态之间的来回拷贝。而且它要求"不对内容做修改"——要压缩、加密、改 header，就没法直接用。

## 为什么频繁的小 IO 慢

把一次 `write(1 字节)` 的成本拆开：

- 特权级切换与寄存器保存；
- 参数检查、权限检查、审计钩子；
- 数据从用户缓冲区拷进页缓存；
- 更新文件偏移、标记脏页、可能唤醒回写线程；
- 返回时再切一次。

**这些固定成本与字节数无关。** 写 1 字节和写 4 KB，固定开销几乎一样。于是：

| 写法 | 系统调用次数 | 结果 |
| --- | --- | --- |
| 每条日志 `write` 一次 | 10 万次 | 大部分时间在进出内核 |
| 攒 8 KB 再写 | 几十次 | 同样数据，快一个数量级 |

所以标准库都有用户态缓冲：`stdio` 的 `BUFSIZ`、Java 的 `BufferedWriter`、Python 的 `io.BufferedWriter`。它们的作用就是**把很多次小写合并成少数几次大写**。

对应的优化手段：

- **批量**：`writev` 一次写多个缓冲区；`sendmmsg` 一次发多个 UDP 包；
- **缓冲**：应用层攒够再写，但要注意及时 `flush`，否则日志会延迟；
- **异步**：`io_uring` 把提交与完成分开，减少往返；
- **合并**：数据库的组提交、消息队列的批量发送，本质都是摊薄固定成本。

网络侧还有 Nagle 算法：小包先攒着，等 ACK 或攒够再发。它减少小包数量，但会增加延迟，低延迟场景常配 `TCP_NODELAY`。这是"批量"与"及时"的取舍在协议层的体现。

## 一个具体例子：一个循环里的两万次 stat

一个 Python 脚本扫描目录，判断每个条目是不是文件，跑得异常慢。用 `strace -c` 看：

```text
$ strace -c -f python3 scan.py
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 78.42    1.284310          62     20736           newfstatat
  9.11    0.149203          41      3620           getdents64
  5.02    0.082114          55      1492           openat
...
```

两万次 `newfstatat` 就是两万次系统调用。看代码：

```python
for name in os.listdir(path):
    full = os.path.join(path, name)
    if os.path.isfile(full) and os.path.getsize(full) > 0:
        process(full)
```

`os.path.isfile` 一次 `stat`，`getsize` 又一次 `stat`，每个文件至少两次。改成 `os.scandir`：

```python
with os.scandir(path) as entries:
    for entry in entries:
        if entry.is_file() and entry.stat().st_size > 0:
            process(entry.path)
```

`scandir` 在读取目录时就把类型信息带回来了，`is_file()` 多数情况不用再进内核；`stat()` 的结果也缓存在 entry 上。改完再测：

```text
$ strace -c -f python3 scan.py
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 61.20    0.108422          38      2851           getdents64
 22.05    0.039011          41       951           openat
...
```

调用次数从两万多降到几千，耗时跟着下来。**这不是 Python 的锅，是"每个文件多问一次内核"的锅。** 同样的模式在 Java 的 `File.exists()` + `length()`、Shell 的 `for f in *; do [ -f "$f" ]` 里都会出现。

## 常见误区

### 误区：系统调用就是库函数，调用一下没什么成本

**你以为**：`read()`、`write()` 和普通方法一样，调多少次都行。
**其实**：每次都要切换特权级、保存寄存器、做权限检查，固定成本在百纳秒到微秒级。每秒十万次就是几十到几百毫秒的纯开销。
**怎么验证**：用 `strace -c` 数调用次数；或写一个循环调用 `getpid()` 的微基准，对比同样次数的普通函数调用。

### 误区：strace 里耗时长的调用就是内核有问题

**你以为**：某次 `read` 花了 1 秒，说明内核卡了 1 秒。
**其实**：`-T` 的时间包含阻塞等待。等锁、等网络、等磁盘都可能算在里面；`strace` 自身的 `ptrace` 开销还会放大一切。
**怎么验证**：结合 `-tt` 看调用前后的时间线，再对照 `pidstat`、`iostat`、`ss` 判断到底在等什么。

### 误区：阻塞会浪费 CPU，所以都应该用非阻塞

**你以为**：阻塞 = 干等 = 浪费。
**其实**：阻塞的进程会被移出运行队列，CPU 去跑别人，几乎不耗 CPU。真正浪费的是非阻塞下的忙轮询。
**怎么验证**：`top` 看阻塞线程的 CPU 占用接近 0；而一个 `while True: try_read()` 的循环会把单核跑满。

### 误区：用了零拷贝就完全不拷贝数据

**你以为**：`sendfile` 让数据从磁盘直接飞到网卡。
**其实**：DMA 仍要把数据搬进内存、再搬上网卡；省掉的是 CPU 在用户态和内核态之间的那次拷贝。数据一旦需要修改（压缩、加密、加协议头），零拷贝就用不上了。
**怎么验证**：看 `sendfile` 的实现与网卡是否支持 scatter-gather；对同一个文件分别用 `read/write` 与 `sendfile` 压测，观察 CPU 的 `sy` 占比。

## 小结

用户态没有权限直接操作资源，只能通过系统调用请内核代办：一条特殊指令、一个调用号、一组寄存器，进去再回来。中断与异常是被动进入内核的路径，缺页是最常见的一种。切换本身在百纳秒到微秒级，真正贵的是缓存失效、阻塞唤醒和每次调用固定的检查与拷贝。阻塞不费 CPU，忙轮询才费；小 IO 慢在固定成本，解法是批量、缓冲与异步。`strace` 用来看"在做什么"，不要用它下"有多快"的结论；零拷贝省的是用户态那次 CPU 拷贝，不是所有拷贝。

这条线到这里结束。七篇合起来，覆盖了"程序为什么慢、卡、挂"最常见的几层：执行单元、内存、调度、锁、IO、文件系统、内核入口。它不要求你读内核源码，遇到问题先用工具把范围切开。下一步建议挑一个你正在维护的服务，用 `strace -c` 和 `iostat` 各跑一次，把学到的名词对上真实数字。
