## 一个 1 ms 的心跳，在 16 核机器上慢了 10 倍

练手项目里有个采集器：4 个线程按下发任务算数，第 5 个线程每 1 ms 记一次心跳（进度采样、超时看门狗都长这样）。跑在 i5-12500H 上，`os.cpu_count()` 报 16（12 个物理核），CPython 3.11.5。心跳日志印出来的间隔不是 1 ms。

把场景缩到最小：一个 1 ms 的 `time.sleep` 循环，旁边挂 0 / 1 / 4 个纯计算线程，各跑 3 秒，重复三次：

```python
# probe: 一个 1 ms 的 ticker，旁边挂 N 个计算线程
import statistics, threading, time

PERIOD, DURATION, CHUNK = 0.001, 3.0, 20000

def worker(seconds):
    end = time.perf_counter() + seconds
    n = 0
    while True:
        for _ in range(CHUNK):
            n += 1
        if time.perf_counter() >= end:
            break

def ticker(seconds, out):
    end = time.perf_counter() + seconds
    last = time.perf_counter()
    gaps, n = [], 0
    while time.perf_counter() < end:
        time.sleep(PERIOD)
        now = time.perf_counter()
        gaps.append(now - last)
        last = now
        n += 1
    out.append((n, max(gaps), statistics.median(gaps)))
```

`gaps` 是两次醒来之间的真实间隔：

```text
旁边 0 个计算线程: wakes=[2014, 2057, 2000] 中位间隔ms=[1.5, 1.49, 1.5]     最长间隔ms=[2.6, 2.5, 4.4]
旁边 1 个计算线程: wakes=[207, 207, 210]    中位间隔ms=[15.32, 15.33, 15.31] 最长间隔ms=[16.1, 16.1, 16.4]
旁边 4 个计算线程: wakes=[227, 79, 144]     中位间隔ms=[1.53, 11.07, 2.16]  最长间隔ms=[199.5, 261.7, 123.6]
```

挂上第一个计算线程就够了：间隔从 1.5 ms 变成 15.3 ms，3 秒里只醒了 207 次（按 1 ms 该醒 3000 次）。挂四个那组更难看，最长一次隔了 262 ms，而且三次之间飘得厉害。

**我猜错了什么。** 我先怀疑 Windows 的时钟精度。这台机器 `GetSystemTimeAdjustment` 报的增量正好是 15.625 ms，跟 15.3 长得一模一样，看着确实像「定时器被取整到系统节拍上」。但只改一个参数就能把结论推翻：

```text
switchinterval=0.005    计算线程=1: wakes=[215, 217, 214]   中位间隔ms=[15.3, 15.28, 15.28]  最长间隔ms=[16.1, 16.2, 17.3]
switchinterval=0.0005   计算线程=1: wakes=[2030, 2031, 1932] 中位间隔ms=[1.5, 1.49, 1.51]    最长间隔ms=[2.4, 5.7, 2.4]
switchinterval=0.0005   计算线程=4: wakes=[1866, 1835, 1870] 中位间隔ms=[1.52, 1.53, 1.52]   最长间隔ms=[3.2, 2.9, 2.3]
```

同一台机器、同一个 `time.sleep(0.001)`、同一批计算线程，唯一动的是 `sys.setswitchinterval()`：解释器隔多久给别的线程一次拿 GIL 的机会。间隔缩小 10 倍，心跳就回到 1.5 ms；四个计算线程也不再拖它。

所以那 15.3 ms 不是时钟精度，是 GIL 的换手周期。它碰巧落在系统节拍附近，这正是我最初判断错的原因。

先把边界划清：GIL 是 CPython 的实现细节，不是 Python 语言的一部分。换 PyPy、Jython，或者 CPython 3.13 起可选的 free-threading 构建，这一节的数字全部作废。下文所有「只有一把锁」的说法都限定在 CPython + 默认构建。

## 「睡醒」是两段延迟，前一段归内核，后一段归 GIL

`time.sleep(1ms)` 之后发生两件事：内核把这个线程放回可运行队列（决定它最早什么时候能被调度），然后线程要真正执行 Python 字节码，还得等 GIL 的当前持有者放手（在 CPython 里由 `sys.getswitchinterval()` 决定，3.11 默认 `0.005`）。

上面「0 个计算线程」那组量的是前一段：1.5 ms，比参数多 0.5 ms，正常。挂一个计算线程之后，后一段开始主导。

另有一个数值长得几乎一样、原因却完全不同的 15.3 ms：`Event.wait(timeout)` 的超时。同一台机器，每个参数等 50 次取中位数：

| 传入的超时 | `time.sleep` 实际等了 | `Event.wait` 实际等了 |
| --- | --- | --- |
| 0.5 ms | 1.02 ms | 15.29 ms |
| 1.0 ms | 1.49 ms | 15.37 ms |
| 2.0 ms | 2.49 ms | 15.27 ms |
| 5.0 ms | 5.45 ms | 15.33 ms |
| 15.0 ms | 15.44 ms | 15.51 ms |
| 20.0 ms | 20.37 ms | 30.69 ms |

`Event.wait` 那一列不管你要等多久，都先被抬到一档 15.6 ms 的节拍上（20 ms 要两档，所以是 30.69）。这是系统时钟节拍：`GetSystemTimeAdjustment` 报 15.625 ms，Windows 的等待函数按节拍计时。而 `time.sleep` 从 CPython 3.11 起在 Windows 8.1+ 上换成了高精度可等待定时器（[whatsnew/3.11](https://github.com/python/cpython/blob/main/Doc/whatsnew/3.11.rst) 里 bpo-45429 那条），1 ms 就真的给 1.49 ms。这张表我做了两件事：区分「节拍取整」和「等 GIL」，以及提醒自己别把同一个数字当同一个原因。

顺带一条方法论：这张表第一版我还加了一列 `Lock.acquire(timeout)`，三行全是 0.00 ms。不是精度好，是锁本来就没人持有，`acquire` 立刻返回——我测的是空锁的返回时间，不是等待精度。做这种表之前先确认「它到底有没有在等」。

## 一次交接 7.4 µs：1 kHz 的心跳只值一个核的 1.5%

两个线程用 `Event` 来回交棒 20000 轮（A `set` → B `wait` → 下一轮）：

```text
pingpong(Event) 20000 轮: 296.8 ms / 342.9 ms / 297.7 ms   -> 每次交接 7.42 / 8.57 / 7.44 us
单线程同一对 set/wait 20000 轮: 14.7 ms                     -> 每轮 0.74 us
```

跨线程一轮从 0.74 µs 涨到 14.8–17.1 µs，约 20 倍。这个差就是本平台的「让出再回来」一次的价格，里面混着内核的阻塞与唤醒、GIL 的释放与重取、调度器挑下一棒，拆不开（01 里那三段成本是描述，没量过）。

但它小到解释不了任何实用的定时问题：1 kHz 心跳是每秒 2000 次交接，2000 × 7.42 µs = 14.8 ms/s，也就是一个核的 1.5%。要让心跳慢到 15 ms，每次交接得花 7.5 ms，差三个数量级。所以遇到「定时器不准」，先把「上下文切换太贵」这条排掉。

真正贵的是另一种交棒——两个线程都忙等，只靠 GIL 主动换手来互相交接，100 轮：

```text
switchinterval=0.005 : 3055.7 ms -> 每次交接 15278.6 us
switchinterval=0.0005:    2.7 ms -> 每次交接    13.7 us
```

同一个循环，1000 倍。默认 5 ms 就是这个成本的下限：想等 GIL 换手，就得按这个周期等。

## 同一个参数，往两边拧都要付账

4 个纯计算线程跑 2 秒，只改 `switchinterval`：

| `sys.setswitchinterval` | 4 线程 2 秒迭代总数（3 次中位数） | 进程 CPU 时间 | 1 ms 心跳的中位间隔 |
| --- | --- | --- | --- |
| 0.005（3.11 默认） | 90.42M | 2.2 s | 15.3 ms |
| 0.0005 | 14.28M | 6.7 s | 1.52 ms |
| 0.00005 | 12.42M | 6.9 s | 1.52 ms |

调小 10 倍，心跳准了，吞吐从 90.42M 掉到 14.28M（少 84%），进程 CPU 时间从 2.2 s 涨到 6.7 s——2 秒里 4 个线程一共烧掉 6.7 秒 CPU，等于 3.4 个核在忙，多出来的时间全花在抢 GIL 上。所以「心跳不准就把 `switchinterval` 调小」不是免费的，它把吞吐换成了定时精度。

前提得先立住：这些线程加起来只用掉一个核。同样 4 个计算线程，1 / 2 / 4 个线程时 `process_time()/wall` 都是 `1.00`（8 个线程时 `0.99`，wall 拉到 3.76 s）。线程数不是并发数；在 CPython 里加线程不会多出核来。

## 忙等和睡：同一个「每毫秒一次」，2 秒的 CPU 时间差 1.953 秒

采集器最早那版心跳是忙等写法的（为了「准」）：`while True: if perf_counter() >= next: tick()`。三种写法的对比，等 2 秒：

| 写法 | 2 秒里醒了几次 | 实际周期 | 线程 CPU 时间 |
| --- | --- | --- | --- |
| 忙等（循环看 `perf_counter`） | 2000 | 1.000 ms | 1.953 s |
| `time.sleep(0.001)` | 1271 | 1.574 ms | 0.000 s |
| `Event.wait(0.001)` | 131 | 15.272 ms | 0.000 s |

忙等的周期最准，一次不差，代价是 2 秒里烧掉 1.953 秒 CPU——一个核的 97.7%。在 16 核机器上，任务管理器里这个进程顶着 100%，`psutil` 的 `Process.cpu_percent()` 也报 100%（它的基准是单核，16 核满负载能到 1600），你从这两个数里看不出它在空转。

更麻烦的是它不只烧自己那点 CPU，还跟同一个进程里干活的线程抢 GIL。给 4 个计算线程配上空转的邻居，2 秒内算出来的迭代数：

| 4 个计算线程旁边加了什么 | 迭代总数（3 次中位数，括号内为三次） | 相对基线 |
| --- | --- | --- |
| 什么都不加 | 88.96M（86.1 / 89.0 / 92.1） | — |
| +1 个忙等线程 | 57.58M（57.6 / 62.7 / 56.7） | 少 35% |
| +4 个忙等线程 | 36.40M（41.9 / 36.4 / 34.9） | 少 59% |
| +4 个每 1 ms 醒一次的线程 | 67.94M（67.9 / 68.3 / 61.9） | 少 24% |

忙等线程抢的不是核（进程始终只要一个核的时间），是 GIL 的份额：4 个空转的和 4 个干活的平起平坐，干活的就只剩四成。这也解释了为什么「加线程提高吞吐」在 CPU 型 Python 任务上不成立。

（这组每组只采了 3 次。同一个脚本里横向比是稳的，但跨脚本的绝对值会飘——另一次同样条件的基线是 73.6M，不是 88.96M。看方向，别背数。）

## 内核那一侧：时间片、自愿切换、nice

上面量到的都是「进程内 + GIL」。把同一套观察搬到 Linux 上，工具和口径全换一套。这一段是标准形态，我在这台 Windows 机器上跑不了，下面没有本机数字。

时间片不是常量。CFS 的 `sched_latency` 默认 6 ms、`min_granularity` 默认 0.75 ms（内核默认值，随负载和 `/sys/kernel/debug/sched` 下的参数变；Linux 6.6 起换成 EEVDF，01 提过），把它当「现代 OS 时间片几毫秒」的定数背下来是错的。

自愿切换和非自愿切换要分开看，两个来源：

```bash
# 每进程的自愿 / 非自愿切换计数（Linux）
grep ctxt_switches /proc/<pid>/status
# 每秒的速率（需要 sysstat）
pidstat -w -p <pid> 1
```

判据是方向性的，不能颠倒：非自愿切换（`nvcswch/s`）升高，说明线程是被时间片用完或更高优先级任务挤下来的——线程数远多于核数时会这样；自愿切换（`cswch/s`）升高，说明线程自己在让 CPU——等锁、等 IO、等 futex 都会计成自愿。看到自愿切换高就断言「锁竞争」是错的，等磁盘也算。

nice 的方向别弄反：`nice -n 19` 是「更好说话」，优先级更低；`-20` 最高；非特权进程只能往大里调。CFS 里它改的是权重，不是时间片：nice 0 = 1024、nice 1 = 820、nice -1 = 1277（内核 `sched_prio_to_weight` 表，相邻档约 1.25 倍）。

旧文说「等 IO 多的任务优先级会被抬高」，这条我删了。CFS 没有这个动作，它做的是：任务睡醒重新入队时校正一次 `vruntime`，把它放到接近当前最小 `vruntime` 的位置（`place_entity`，也就是 sleeper fairness），效果是「睡了一觉既不吃亏、也不会攒出一笔巨额补偿」，不是「被抬优先级」。给等待 IO 多的进程加 interactive bonus 是更早一代替换式调度器的算法，被不少教材一路抄到了今天。

## load average 和 `wa` 是两个容易读反的数

Linux 的 `/proc/loadavg`（以及 `uptime`）数的是**可运行（R）+ 不可中断睡眠（D）**的线程数，再做指数衰减平均（`man 5 proc`）。它不是 POSIX 指标，Windows 没有对应物——任务管理器里的「处理器队列长度」是另一件事，别拿来对。

所以 load 高不等于 CPU 忙：D 状态的线程（等磁盘、等 NFS、等设备）也计入，这是负载与实际 CPU 脱节的常见来源。找 D 状态：

```bash
ps -eo state,pid,comm,wchan:24 | awk '$1 ~ /^D/'
```

`wa` 也别读成「CPU 在等磁盘」。它是 idle 的一部分：CPU 空着，同时有 IO 在飞。因为它是 idle 的子集，所以「CPU 100%」和「`wa` 高」不会同时成立——100% 里没有 idle 可算。

真遇到问题，按症状找入口比背指标有用：

| 症状 | 先看哪 | 常见误判 |
| --- | --- | --- |
| 某个进程 100%，机器整体很闲 | `process_time()/wall`，或按线程看（Linux `top -H`） | 「CPU 满了」——16 个核里只有 1 个在转 |
| 心跳/超时精度变差，间隔像某个节拍的整数倍 | 同进程有没有吃 CPU 的线程；`sys.getswitchinterval()` | 「时钟精度差」——先分清 `sleep` 和 `Event.wait` |
| 线程加到 4 个，吞吐还是 1 个线程的量 | 是不是 CPython 的 GIL（`process_time()/wall ≈ 1`） | 「核不够，加线程」 |
| 非自愿切换速率高 | 线程数 vs 核数、是否有更高优先级任务 | 「说明有 bug」——满负荷被换下是正常调度，要看它有没有拖慢吞吐或延迟 |
| 自愿切换速率高 | 在等锁还是等 IO（futex / 磁盘） | 「锁竞争」——等 IO 也算自愿 |
| load 2.0 而 CPU 只有 20% | D 状态线程 | 「CPU 排队」——多半是 IO |

## 一次排查的顺序（这次真走了一遍）

1. 先量，别先看任务管理器：`process_time()` 和 `perf_counter()` 一除就知道是「一个核在转」还是「很多核在转」。这一步排掉了「CPU 不够」。
2. 把负载减到 1 个计算线程还复现吗？复现 → 不是核的事，是线程之间互相在等。这一步确认了问题在进程内。
3. 只改一个能影响嫌疑机制的参数，看症状跟不跟着动。这次是 `switchinterval`：10 倍、100 倍各跑一次，15.3 ms 立刻回到 1.5 ms，机制就钉住了。这是最省事的因果实验，比换机器、加日志都快。
4. 最后才轮到内核侧（Linux 上）的计数与 load。前三步没做就翻 `pidstat`，得到的会是一堆看得懂、但解释不了的数。

## 动手：把心跳挪出 GIL

如果心跳真的要 1 ms 级精度，比调参数更省事的是换进程——进程有自己的 GIL，不再跟计算线程排队：

```text
thread create+join x20: median=427.8 us  (min 261.8, max 543.9)
process create+join x8: median=194.6 ms   (min 146.2, max 241.3)   # spawn
```

启动成本差约 400 倍（0.43 ms vs 195 ms），但只在启动时付一次。这台机器上 `multiprocessing.get_start_method()` 是 `spawn`（Windows 默认），子进程要重新 import 一遍模块，195 ms 里有多少是 import、有多少是内核建进程，我没拆。

代价是数据要跨进程搬，这个成本没量。另一侧：多进程之后能不能真用满 12 个物理核，取决于任务拆得开不开，我也没量。

## 还差的

- Linux 那一整套只有标准形态：`pidstat -w`、`/proc/<pid>/status` 的两个计数、nice 对权重的影响，我都没在 Linux 机器上跑过；EEVDF 下的时间片行为更没验。这一段是本篇唯一没有本机数字的部分。
- 15.3 ms 与 3 × `switchinterval` 的对应只来自三个 `switchinterval` 取值，我没读 CPython `take_gil` 的实现，说不出为什么正好是三倍——只有「改了它，症状就变」这一层证据。
- 「4 计算 + 4 忙等」那组每组 3 次采样，跨脚本绝对值能差 10% 以上（73.6M 对 88.96M），只能当方向：忙等邻居确实把产出压低了三到五成，具体百分比不可复现。
- 多进程那条路只量了创建成本，没量换进程之后的吞吐，也没量跨进程搬数据的成本。
- 这台是 4 个 P 核 + 8 个 E 核的异构 CPU，P/E 核怎么分派线程我没测；另外 3.13 的 free-threading 构建（没有 GIL）里这组数字会完全不一样，我没有环境。
