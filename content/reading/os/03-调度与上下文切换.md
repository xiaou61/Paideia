## 先把结论摆出来

CPU 占用只是一个"有人占着"的信号，不区分在**算**、在**等**、还是在**切**。

看到 CPU 高，先分三种情况：

1. **用户态高（us）**：真在计算，可能是业务高峰，也可能是死循环/忙等；
2. **系统态高（sy）**：大量系统调用或上下文切换，常见于线程过多、小 IO 太碎；
3. **等待 IO 高（wa）**：CPU 空闲在等磁盘/网络，占用率看起来不高但服务很慢。

**调度器只决定"下一个轮到谁"，不保证公平，也不保证低延迟。** 理解这一点，就不会指望"加机器"能治好所有慢。

## 时间片与抢占

现代操作系统是**抢占式**调度：每个线程跑一小段时间（时间片，通常几毫秒），时间到了就强制换人。这样单个死循环不会永久霸占 CPU——但这只保证"能轮到"，不保证"轮得快"。

两种常见调度策略：

- **普通时间片轮转**：交互型任务响应好，吞吐一般；
- **优先级 + 动态调整**：等 IO 多的任务优先级会被抬高（因为它不占 CPU，让它快跑完去等），CPU 密集的任务会被压低。

Linux 的 `nice` 值（-20 到 19）影响权重，但**不能用来做精确的延迟控制**。要控制延迟，得靠线程池隔离、限流、或把慢任务挪到独立进程。

## 负载（load average）到底是什么

`uptime` 里的三个数是 1/5/15 分钟的平均负载。它的定义是：**处于可运行状态 + 不可中断等待状态的线程数**。

- 单核机器 load=1 表示刚好跑满；
- 4 核机器 load=4 表示刚好跑满；
- **load 高但 CPU 不高**：大量线程卡在磁盘 IO（不可中断睡眠），这是最容易被忽略的一种"假忙"。

所以看负载要先除以核数，再看 `wa`。

## 上下文切换的账

```bash
vmstat 1 5        # cs 列 = 每秒上下文切换次数
pidstat -w 1      # 按进程看自愿/非自愿切换
```

- **自愿切换**：线程主动让出（等锁、等 IO）。次数多说明锁竞争或 IO 多。
- **非自愿切换**：时间片用完被换下。次数多说明线程数远超核数，或在抢 CPU。

线程池大小的经验值：

- **CPU 密集**：核数 + 1；
- **IO 密集**：核数 × (1 + 平均等待时间 / 平均计算时间)。

这个公式不是定理，是起点。真实值要靠压测调，不是拍脑袋。

## 一次"CPU 100% 但吞吐减半"的排查顺序

1. `top` 看 `us/sy/wa` 的比例；
2. `top -H -p <pid>` 找出烧 CPU 的线程；
3. 把线程 ID 转成十六进制，去 `jstack` 输出里找对应栈（Java）；
4. 如果栈都在同一把锁上 → 锁竞争；都在 GC 线程 → 内存压力；都在业务循环 → 死循环或算法问题。

**第 3 步是关键**：没有栈就只能猜。`top` 给的是"谁"，栈给的是"为什么"。

## 常见误区

### 误区：CPU 使用率低就说明服务不忙

**你以为**：闲着就是没问题。
**其实**：可能全卡在等锁、等数据库、等下游。此时 CPU 低、延迟高，加 CPU 完全无效。

### 误区：提高优先级能解决延迟问题

**你以为**：把关键线程调成高优先级就快了。
**其实**：优先级只影响抢 CPU 的顺序，对锁等待、IO 等待无效；滥用还会让低优先级线程饿死。

### 误区：线程池越大并发越高

**你以为**：多开线程多干活。
**其实**：超过某个点后，切换与缓存失效会让吞吐下降。线程池应按"任务在算什么/在等什么"配置，并用压测确认拐点。

## 小结

CPU 高要分 us/sy/wa，负载要除以核数。上下文切换分自愿与非自愿，分别指向锁/IO 与线程过多。线程池大小是压测出来的，不是拍出来的。排查烧 CPU 的线程必须看栈。下一课：锁用错时的两种死法。
