## 5 个字节写进去了，文件是 0 字节

```python
import os
import sys

f = open(sys.argv[1], "w")
f.write("hello")
if len(sys.argv) > 2:
    f.flush()
os._exit(0)          # 故意不走解释器退出流程，不 close
```

```text
> python child.py log.dat
> python -c "import os; print(os.path.getsize('log.dat'))"
0
> python child.py log.dat flush
> python -c "import os; print(os.path.getsize('log.dat'), open('log.dat','rb').read())"
5 b'hello'
```

同一个 `f.write("hello")`，两次结果一个是 0 字节、一个是 5 字节，差别只有一行 `f.flush()`。

我第一次写这个对照时猜错了。当时想的是「两次都该是 5，只是数据还没到盘、停在内核里」——错在 0 那一次：那 5 个字节连内核都没进，它待在 CPython 的缓冲区里，`os._exit()` 一执行，那块用户态内存跟着进程一起没了。

（Windows 上文本模式会把换行符翻成 CRLF，所以字符串 hello 占 5 字节，后面再带一个换行就是 7 字节。别拿这两个数跟 Linux 上的输出互相比。）

第二版那 5 个字节也不在盘上。它只到了下一层。

## 三层，不是两层

C 的 `write(fd, ...)` 返回成功，意思是「数据交给内核了」；Python 的 `f.write()` 连这一步都还没走到。把三件事分开，账才对得上：

| 调用返回时 | 数据在哪 | 别的进程能读到 | 本进程被 kill | 整机掉电 |
|---|---|---|---|---|
| `f.write()` | CPython `io` 的写缓冲，用户态内存 | 不能 | 丢 | 丢 |
| `f.flush()` | 内核页缓存，那一页被标成脏页 | 能 | 还在 | 丢 |
| `os.fsync()` | 设备报告传输完成 | 能 | 还在 | 看设备自己的缓存刷没刷 |

两个常见的错位都在这张表里：

- 把 `f.write()` 当成「已经交给内核」。对 C 的 `write()` 成立，对 Python 的 `f.write()` 不成立，中间隔着一层 `BufferedWriter`（文本模式下是 `TextIOWrapper` 套 `BufferedWriter`，`f.flush()` 要穿两层才到内核）。
- 把「别的进程能读到」当成「落盘了」。看第二行：能读，掉电照样丢。

`f.flush()` 到底把人送到哪一层，是可以直接看到的：上面 5 字节那一版，另一个进程读到了 `b'hello'`，说明它已经出了本进程，此刻在内核页缓存里。

有三条边界得说清：

1. 这些是 `io` 模块和 CPython 的行为，不是 Python 语言层面的保证。缓冲多大是 `io.DEFAULT_BUFFER_SIZE`（本机 3.11.5 打印出来是 8192），别把 8192 当成所有 Python、所有平台都一样。
2. 缓冲不是「没 flush 就一定还在内存里」。单次写超过缓冲量时 `BufferedWriter` 自己会先吐出去；所以「另一个进程读不到」只在你没写满缓冲时成立。
3. 调了 `os.fsync()` 也只是「设备报告刷完了」。fsync(2) 的 HISTORY 里有一句 older kernels and lesser used filesystems do not know how to flush disk caches——设备到底刷没刷它自己的写缓存，我在这块 NVMe 上验不了（见「还差的」）。

Windows 上 `os.fsync` 落到 FlushFileBuffers；Linux 上 `os.fsync` 和 `os.fdatasync` 分别落到 fsync(2)、fdatasync(2)。

## fsync 的钱按条算

200 条 480 B 的记录，三种写法。同一个脚本（见「跑一遍」），5 轮交错取最小值：

| 写法 | 200 条总耗时 | 每条 | 相对「末尾刷一次」 |
|---|---|---|---|
| 每条 write + flush + fsync | 85.13 ms | 0.426 ms | 55× |
| 200 条写完，flush + fsync 一次 | 1.56 ms | 0.0078 ms | 1 |
| 完全不 fsync | 0.92 ms | 0.0046 ms | 0.59× |

这三个数怎么读：

- 每条 0.426 ms 基本都花在等设备往返上，不是 480 B 的数据传输。换过来就是 2350 条/秒，这已经是这种写法的上限，跟 CPU 快不快没关系。
- 一条一条刷，和攒起来刷一次，差 55 倍。不是「稍微慢一点」，是数量级。
- 完全不 fsync 比「攒起来刷一次」也快不了多少（0.92 对 1.56 ms），因为两者都不等设备；它们的区别只在掉电丢不丢，看上面那张表。

所以「每条记录都 fsync」的日志方案，吞吐是被设备往返锁死的。组提交把 N 个事务的日志攒在一条 flush 上，InnoDB 的 `innodb_flush_log_at_trx_commit`、PostgreSQL 的 `synchronous_commit`/`commit_delay` 调的都是这个 N 和最长等多久。我没有第二台机器去压它们，这里只给机制，不给它们的性能数字。

还有两条 Linux 上容易漏的：

- fsync 只管这个文件。man-pages 6.19 的 fsync(2) 写着 Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk。要让「新建出来的文件名」本身活过掉电，得对目录也 open 一次、fsync 一次。
- `fdatasync` 不是 fsync 的快速版。fdatasync(2) 说的是不刷那些「与后续取数据无关的元数据」，比如 atime/mtime；但文件大小变了（`st_size`）时那块元数据必须刷。所以「fdatasync 一定比 fsync 快」不成立——你这次是追加，就快不了。

## 随机读慢 2.5 倍，这 2.5 倍里没有磁盘

先单独看「一次读多大」。同一个 64 MiB 文件，每点连读 3 遍、7 轮交错取最小值：

| read 块大小 | 读完 64 MiB（3 遍） | 等效带宽 | 每遍 read 次数 |
|---|---|---|---|
| 512 B | 251.2 ms | 0.75 GB/s | 131072 |
| 4 KiB | 186.3 ms | 1.01 GB/s | 16384 |
| 16 KiB | 113.8 ms | 1.65 GB/s | 4096 |
| 64 KiB | 55.0 ms | 3.41 GB/s | 1024 |
| 256 KiB | 41.3 ms | 4.54 GB/s | 256 |
| 1 MiB | 85.5 ms | 2.19 GB/s | 64 |

512 B 到 64 KiB 是 4.6 倍，靠的是把每次 read 的固定开销摊薄。但 1 MiB 那一格反而掉回 85.5 ms，比 64 KiB 慢 1.55 倍——「缓冲区越大越快」在这里不成立。我猜是每次都要新分配 1 MiB 的 bytes、页错误摊在 64 次读上，没验。

这张表测的是「每次 read 的调用开销」，不是盘速：那个 64 MiB 文件是同一进程刚写出来的，还在页缓存里，4.5 GB/s 的等效带宽也不是这块盘顺序读能给到的量级。

然后是顺序和随机。同一文件、同一批偏移（`random.Random(42)` 生成的 4000 个），每次 seek 到位读 4 KiB：

| 打开方式 | 顺序读 | 随机读 | 随机/顺序 |
|---|---|---|---|
| `open(path, "rb")`，默认缓冲 | 50.7 ms | 128.5 ms | 2.53× |
| `open(path, "rb", buffering=0)`，无缓冲 | 80.0 ms | 105.5 ms | 1.32× |

关掉缓冲之后，顺序读从 50.7 涨到 80.0 ms，随机读几乎没动（128.5 → 105.5）。变的只有顺序那边——它原来靠 8 KiB 缓冲把两次 4 KiB 的 read 合成一次系统调用，缓冲一关系统调用翻倍；随机读每次 seek 都把缓冲作废，预读一口都吃不到，所以有没有缓冲都差不多。

所以这 2.5 倍里的大头是应用层（8 KiB 缓冲加预读），不是寻道，也不是「SSD 随机读的固定成本」。同一脚本连跑几遍的比值是 2.40 / 2.53 / 2.67×，无缓冲那行是 1.26 / 1.31 / 1.32×，全程没有读盘。

机械盘上这件事才换性质，但那只是算术、不是我的实测：7200 rpm 转一圈 60/7200 = 8.33 ms，平均等半圈 4.17 ms，再加寻道，随机 IO 的代价这时才落到毫秒级。这台机器只有 NVMe。

## Linux 上我会看哪几个数

这一段是标准形态，未实跑。

```bash
grep -E '^(Dirty|Writeback|WritebackTmp):' /proc/meminfo
```

```text
Dirty:              1236 kB
Writeback:             0 kB
WritebackTmp:          0 kB
```

`Dirty` 是「改了但还没写出去」的页的内存量。它长时间不降，说明回刷追不上产生速度；`Writeback` 非零，说明真有页在飞。

相关默认值按内核文档 Documentation/admin-guide/sysctl/vm.rst：`dirty_writeback_centisecs = 500`（5 秒唤醒一次回刷线程）、`dirty_expire_centisecs = 3000`（脏超过 30 秒的页必须写出去）、`dirty_background_ratio = 10`、`dirty_ratio = 20`。这是文档默认值，发行版会改，我这台是 Windows 没实测。

想看「谁在 fsync」，先确认这个内核有那个 tracepoint，再计数：

```bash
bpftrace -l 'tracepoint:syscalls:sys_enter_fsync'
bpftrace -e 'tracepoint:syscalls:sys_enter_fsync { @[comm] = count(); }'
```

## 症状 → 先看哪

| 症状 | 先看 | 判据 |
|---|---|---|
| 日志吞吐只有几千条/秒 | 是不是每条记录都跟一次 fsync | 上面那张表：单条刷盘 2350 条/秒就是上限，攒批能快 55 倍 |
| fsync 慢，但盘看起来不忙 | `iostat -x` 的 `f/s` 与 `f_await` | iostat(1) 说块层对 flush 请求 executes at most one at a time，f_await 可能被拉成两倍：等当前这条刷完，再刷下一条 |
| 平时正常，偶尔整段卡住 | `/proc/meminfo` 的 `Dirty` 是否逼近 `dirty_ratio` | 按内核文档，脏页过了 `dirty_ratio`，写开始同步回刷，进程被拖住 |
| 读慢，怀疑是盘 | 同一个文件读第二遍快不快 | 第二遍快很多 → 第一次在缺页或读盘；一样慢 → 才轮到盘，或者你的块大小 |
| `%util` 接近 100%，业务却还有余量 | `await`、`aqu-sz`、`r/s` 与 `w/s` | iostat(1) 原话：%util 接近 100% 只在串行服务的设备上意味着饱和，RAID 与现代 SSD 这种并行设备上它不代表性能上限 |
| 应用慢，而盘很闲（`%util` 和 `await` 都低） | 先别看盘 | 在等锁、网络或上游，换盘解决不了 |

## 跑一遍

Windows 11 + Python 3.11.5，`TEMP` 在 C:，内置盘 Micron MTFDKBA512TFH（NVMe SSD），16 线程。

```python
"""IO / 页缓存那一篇的全部数字，出自这一个脚本。
Windows 11 + Python 3.11.5，TEMP 在 C:，内置盘 Micron MTFDKBA512TFH（NVMe SSD）。

机器上还有别的进程，单次采样会抖，所以每个采样点：交错测（一轮里把所有候选各测一遍）、
多轮取最小值。min 的读法是「这套代码最好的时候能到多少」。
"""
import os
import random
import statistics
import time

BASE = os.path.dirname(os.path.abspath(__file__))
LOG = os.path.join(BASE, "log.dat")
REC = b"x" * 480 + b"\n"
N = 200
BIG = 64 * 1024 * 1024
PASSES = 3
ROUNDS = 7


def timed(fn):
    t0 = time.perf_counter()
    fn()
    return (time.perf_counter() - t0) * 1000


def each_sync():
    with open(LOG, "wb") as f:
        for _ in range(N):
            f.write(REC)
            f.flush()
            os.fsync(f.fileno())


def group_sync():
    with open(LOG, "wb") as f:
        for _ in range(N):
            f.write(REC)
        f.flush()
        os.fsync(f.fileno())


def no_sync():
    with open(LOG, "wb") as f:
        for _ in range(N):
            f.write(REC)


def make_big():
    if os.path.exists(LOG) and os.path.getsize(LOG) == BIG:
        return
    chunk = os.urandom(1024 * 1024)
    with open(LOG, "wb") as f:
        for _ in range(BIG // len(chunk)):
            f.write(chunk)
        f.flush()
        os.fsync(f.fileno())


def read_all(bs):
    for _ in range(PASSES):
        n = 0
        with open(LOG, "rb") as f:
            while True:
                b = f.read(bs)
                if not b:
                    break
                n += len(b)
        assert n == BIG


def replay(offsets, bufsize):
    for _ in range(PASSES):
        n = 0
        with open(LOG, "rb", buffering=bufsize) as f:
            for off in offsets:
                f.seek(off)
                n += len(f.read(4096))
        assert n == len(offsets) * 4096


def main():
    modes = (("每条 fsync", each_sync), ("末尾一次", group_sync), ("不 fsync", no_sync))
    acc = {k: [] for k, _ in modes}
    for _ in range(5):
        for k, fn in modes:
            acc[k].append(timed(fn))
    print("1) 200 条 480 B，5 轮")
    for k, _ in modes:
        lo, med = min(acc[k]), statistics.median(acc[k])
        print("   %-8s min %6.2f  median %6.2f ms   单条 %.4f ms" % (k, lo, med, lo / N))

    make_big()
    sizes = (512, 4096, 16384, 65536, 262144, 1048576)
    acc = {bs: [] for bs in sizes}
    for _ in range(ROUNDS):
        for bs in sizes:
            acc[bs].append(timed(lambda: read_all(bs)))
    print("\n2) 读完 64 MiB（每点连读 %d 遍），%d 轮取 min" % (PASSES, ROUNDS))
    for bs in sizes:
        lo = min(acc[bs])
        print("   %-8d %7.1f ms   等效 %5.2f GB/s   %d 次 read/遍"
              % (bs, lo, (BIG * PASSES / 1048576) / (lo / 1000) / 1024, BIG // bs))

    size = os.path.getsize(LOG)
    rnd = random.Random(42)
    seq = [i * 4096 for i in range(4000)]
    rand = [rnd.randrange(0, size - 4096) for _ in range(4000)]
    print("\n3) 4000 次 4 KiB 读 × %d 遍，%d 轮取 min" % (PASSES, ROUNDS))
    for label, buf in (("默认缓冲", -1), ("buffering=0", 0)):
        a, b = [], []
        for _ in range(ROUNDS):
            a.append(timed(lambda: replay(seq, buf)))
            b.append(timed(lambda: replay(rand, buf)))
        print("   %-12s 顺序 %6.1f  随机 %6.1f  随机/顺序 %.2f×"
              % (label, min(a), min(b), min(b) / min(a)))


if __name__ == "__main__":
    main()
```

## 动手

- 复现 0 字节。两版都跑，注意用 `os._exit` 收尾，别让脚本自然结束——自然结束会 `close()`，缓冲就被刷出去了，你什么也看不到。
- 换成你自己的盘。把 `ROUNDS` 调到 3 再跑第 1 段和第 3 段；第 3 段的比值比绝对毫秒更值得看。另外文本模式下 `open(..., buffering=0)` 会直接抛 `ValueError: can't have unbuffered text I/O`，我本机 3.11.5 上验过，别在那里愣住。
- 数一遍线上的 fsync：挑一条写日志/写状态的路径，数一次请求里有几次 `fsync`、是不是每条都刷。按上面那张表，这个数就是吞吐的分母。

## 还差的

- 没踢过页缓存，所以没有「冷读」数字。Windows 上要无缓冲 IO 或管理员工具才能绕开缓存，我没权限；上面所有读都是命中缓存的读，它们证明的是调用开销，不是盘速。
- 没做断电测试。`os.fsync` 之后设备到底有没有把它自己的写缓存刷下去，我这台机器验不了；fsync(2) 的 HISTORY 也只是说老内核和少用的文件系统不知道该怎么刷设备缓存。
- Linux 侧那几个命令（`/proc/meminfo`、`iostat -x`、`bpftrace`）全是标准形态，没在这台机器上跑过；`dirty_*` 那几个默认值抄的是内核文档，不是我这台机器的 `sysctl -a`。
- 机械盘的数字没测——只有 8.33 ms/圈那点算术。Windows 上也没法对目录 `os.fsync`，上面「新建的名字要单独 fsync 目录」那条只在 Linux 语义下成立，Windows 怎么保证目录项落盘我没验。
- 数据库的 sync 策略只讲了机制（组提交、`innodb_flush_log_at_trx_commit`、`commit_delay`），没读它们的源码，也没在它们身上压过测。
