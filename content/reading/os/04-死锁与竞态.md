## 先把结论摆出来

两种完全不同的故障，症状也完全不同：

- **竞态（race condition）**：结果不对，但程序不报错。典型是少加了一次、读到半更新的对象。
- **死锁（deadlock）**：程序卡住，线程都在等。典型是接口突然不响应、重启就好。

**竞态靠"想清楚共享什么"解决，死锁靠"统一获取顺序"解决。** 两者都不是加个 `synchronized` 就能一劳永逸的。

## 死锁的四个必要条件

教科书里的四条，用大白话说：

1. **互斥**：资源一次只能一个人用（锁天然如此）；
2. **持有并等待**：拿到一把锁后，不放手再去要第二把；
3. **不可抢占**：别人不能把锁从你手里抢走；
4. **循环等待**：A 等 B 的锁，B 等 A 的锁。

**四条同时成立才会死锁。** 实际排查里，第 4 条最常见，也最容易破——**给所有锁规定一个全局顺序**：任何线程都必须先拿 1 号锁再拿 2 号锁，不允许反过来。只要顺序一致，循环等待就不可能出现。

### 一个具体的例子

```java
// 线程 A
synchronized (account1) {
    synchronized (account2) { ... }
}

// 线程 B（转账方向相反）
synchronized (account2) {
    synchronized (account1) { ... }
}
```

A 拿着 1 等 2，B 拿着 2 等 1。转账量一大就卡死。

**修法不是加超时，而是按 id 排序后再加锁**：无论谁转给谁，永远先锁 id 小的那个。

## 死锁的现场怎么看

Java 进程卡住时，先拿线程栈：

```bash
jstack <pid> > /tmp/stack.txt
grep -A 20 "Found one Java-level deadlock" /tmp/stack.txt
```

JVM 会直接告诉你"线程 A 持有锁 X，等待锁 Y；线程 B 持有锁 Y，等待锁 X"。**这是最快的确诊方式**，比读代码猜快得多。

没有 JVM 自带检测的语言，就看线程栈里大量的 `waiting to lock` / `futex` 状态，再对照代码里的加锁顺序。

## 竞态为什么更阴险

```java
private int count = 0;

void increment() {
    count++;    // 读 count → 加 1 → 写回，三步不是原子的
}
```

两个线程同时执行，可能都读到 0、都写回 1，加两次只涨了 1。**结果稳定地错，但不报错**，测试数据量小时还看不出来。

三种常见来源：

1. **复合操作不是原子的**：`if (map.containsKey(k)) map.put(k, v)` 中间可能被别人插一脚；
2. **可见性**：一个线程改了变量，另一个线程可能还在读缓存（需要 `volatile` 或锁来建立内存屏障）；
3. **"先检查后使用"**：检查时文件存在，使用时已被删。

**判据**：只要一个状态被两个以上线程读写，就要问"最坏的交错顺序会怎样"。问不出答案的地方，就是 bug 藏身处。

## 修竞态的手段，从轻到重

1. **不要共享**：把状态放到方法局部变量、或每个线程一份（ThreadLocal）；
2. **用不可变对象**：改不了就不需要同步；
3. **用线程安全的数据结构**：`ConcurrentHashMap`、`AtomicInteger`、阻塞队列；
4. **加锁**：范围要小，锁的对象要稳定（不要锁字符串常量或可被外部替换的引用）；
5. **用消息传递代替共享**：投递到单线程执行器，天然串行。

**顺序很重要**：能用前三步就别上锁。锁是最后手段，因为它同时带来死锁与性能问题。

## 锁的三个实用纪律

- **锁的粒度**：临界区只包住必要的那几行，别把网络调用包进去；
- **锁的对象**：`private final Object lock = new Object()`，别锁 `this`、别锁 String 常量（可能被 intern 共享）；
- **必须成对释放**：用 `try/finally` 或语言提供的 `try-with-resources` / `with`，异常路径也要放锁。

## 常见误区

### 误区：加锁就一定安全

**你以为**：每个方法都 `synchronized` 就没问题。
**其实**：锁错对象（多个实例各锁各的）、锁范围过大（吞吐崩）、嵌套顺序不一致（死锁）都会出事。安全来自"共享状态的设计"，不是来自关键字。

### 误区：死锁一定是两个人互相等

**你以为**：只有两方。
**其实**：三个以上线程形成环也一样死。规则仍是"统一顺序"，不是"两个线程时注意"。

### 误区：测试没复现就没问题

**你以为**：跑过就是对的。
**其实**：竞态在小数据、单线程、快机器上最容易藏。需要专门的多线程测试（加大线程数、循环多次、插入随机延迟）才可能暴露。

## 小结

死锁四条件，最实用的是破循环等待：统一加锁顺序。竞态来自非原子的复合操作与可见性，先想"最坏交错"，再用不可变/局部化/并发容器，最后才上锁。锁要小、要固定、要成对释放。下一课：为什么写了文件却没落盘。
