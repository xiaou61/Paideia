## 两个线程各充一千次，余额停在 1001

练手项目里我写了个最朴素的记账：账户就一个 `balance`，充值是把余额读出来、加一、写回去。中间那句 `sleep` 是替真实的「查一次风控」占位。

```python
import threading
import time


class Account:
    def __init__(self, name, balance):
        self.name = name
        self.balance = balance
        self.lock = threading.Lock()

    def __repr__(self):            # 下面几节要直接打印账户
        return f"{self.name}:{self.balance}"


def top_up_naive(acc, times, pause):
    for _ in range(times):
        value = acc.balance          # 读
        time.sleep(pause)            # 真的充值在这里会查一次风控
        acc.balance = value + 1      # 写回「我读到的旧值 + 1」


def run_two(fn, times, *args):
    acc = Account("A", 0)
    threads = [threading.Thread(target=fn, args=(acc, times, *args)) for _ in range(2)]
    start = time.perf_counter()
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return acc.balance, (time.perf_counter() - start) * 1000


if __name__ == "__main__":
    bal, ms = run_two(top_up_naive, 1000, 0.0002)
    print(f"balance={bal} expect={2 * 1000} lost={2 * 1000 - bal} {ms:.0f} ms")
```

Windows 11 + CPython 3.11.5，实际输出：

```text
balance=1001 expect=2000 lost=999 522 ms
```

两千次充值只到账一次。我当时的解释是「没加锁，当然丢」——这句话什么都没解释，它只是把问题换了个说法。要回答的是「丢在哪一步」，而在上面那段代码里，那一步在视觉上是存在的：读是一次赋值，写是另一次赋值，中间还隔着一次真实的等待。

## 把读写挨在一起，一次都没丢

同一件事，去掉中间那次等待，写成 `+=`：

```python
def top_up_tight(acc, times):
    for _ in range(times):
        acc.balance += 1
```

```text
tight  balance=400000 expect=400000 lost=0 16 ms
```

2 个线程各 20 万次，40 万次自增，0 丢。01 讲共享堆时撞过同一件事：4 个线程各 20 万次 `counter += 1`，三次都是 800000。

我第一个念头是 GIL 把 `x += 1` 保护成了原子操作。不是。GIL 保证的是「同一时刻只有一个线程在执行字节码」，它没说「几条字节码之间不会换人」。`sys.getswitchinterval()` 在这台机器上返回 `0.005`：每 5 ms 才有一次「评估要不要换人」的机会。而一次自增要多久？单线程连跑 40 万次用了 16.5 ms，摊下来 41 ns。40 万次总共 16 ms，中间只摊到三次换人机会，没有一次落进那 41 ns 里——就这么点事。

我还试过反向：在读和写之间插一次函数调用，仍然是 0 丢（2 线程 × 20 万次，33 ms，3 次都一样）。这说明的是同一件事，不是「插调用也安全」——换人机会每 5 ms 才来一次，落到窗口里是小概率，不是零概率，5 ms 和 40 万次这两个数刚好凑成了「这次没撞上」。

所以这里真正的结论是：**`+=` 不是原子的，它只是窗口窄到这一次没被观测到**。窗口一宽（一次 IO、一次真实的网络查询），0 丢立刻变成一半。这是 3.11.5 在 Windows 上我量到的行为，不是 CPython 的文档契约；3.13 起官方还提供不带 GIL 的 free-threaded 构建，那种环境下这个窗口会大得多，我没跑过。

## 加锁之后：数对了，时间没了

同一段紧循环，把自增包进锁：

```python
def top_up_locked_fast(acc, times):
    for _ in range(times):
        with acc.lock:
            acc.balance += 1
```

```text
locked fast  balance=400000 expect=400000 lost=0 63 ms
```

同一次运行里，无锁 16 ms、加锁 63 ms。这两个数有抖动（连跑五次分别是 16/16/21/21/24 ms 和 60/70/73/73/77 ms），4 倍这个量级倒是稳的。它不要往外推——三笔账糅在一起了：`with` 多出来的字节码、`acquire/release` 本身、以及两个线程被串行化后少掉的并行。我这个玩具拆不开它们。能说的是方向：锁在这一层是显性成本，不是语法糖。

锁自身的价钱倒是可以单独量：单线程、无竞争，`acquire()` 紧接 `release()`，100 万次平均一对 0.09 µs。所以真正贵的东西从来不是这两条指令。

把第一节那句 `sleep` 挪进临界区，成本就变成可解释的了：

```python
def top_up_locked(acc, times, pause):
    for _ in range(times):
        with acc.lock:
            value = acc.balance
            time.sleep(pause)
            acc.balance = value + 1
```

```text
locked+io  balance=2000 expect=2000 lost=0 1049 ms
locked+io  balance=2000 expect=2000 lost=0 1036 ms
```

数是对的，时间几乎翻倍：不带锁那版 522 ms，带锁 1049 ms / 1036 ms。原因不神秘——那 0.2 ms 现在被锁保护着，第二个线程进不来，做不了任何事，两段等待只能叠成一段。**临界区里只该放不变式真正需要的那几行**；能在锁外拿的快照就在锁外拿，进锁后再用「比较快照再写」兜住冲突。

## 锁保护的是不变式，不是一个字段

转账最容易漏的一点：钱从 A 扣掉和加到 B 上是两次写，中间那一下别的线程看得见。让第三个线程盯着总额（`Account` 还是第一节那个）：

```python
def transfer_once(a, b, times):
    for _ in range(times):
        a.balance -= 1
        time.sleep(0.0001)
        b.balance += 1


if __name__ == "__main__":
    a, b = Account("A", 100), Account("B", 100)
    seen = {"reads": 0, "bad": 0}
    stop = threading.Event()

    def observer():
        while not stop.is_set():
            total = a.balance + b.balance
            seen["reads"] += 1
            seen["bad"] += total != 200

    watcher = threading.Thread(target=observer)
    writer = threading.Thread(target=transfer_once, args=(a, b, 100))
    watcher.start()
    writer.start()
    writer.join()
    stop.set()
    watcher.join()
    print(f"observer reads={seen['reads']} bad_totals={seen['bad']} rest_total={a.balance + b.balance}")
```

```text
observer reads=7648949 bad_totals=7524141 rest_total=200
```

观察线程读了 765 万次，其中 752 万次看到的 A+B 不是 200——因为它正好落在「A 已扣、B 未加」那一小段。写线程停下来之后，总额又是 200。

这是竞态比死锁难认的地方：**事后对账是对的，过程中间是错的**。事后能对上，说明这把锁可能一把都没少加；错的是「两个字段属于同一个不变式，却可以分两次被看见」。按字段配锁（每个 `balance` 一把）等于没锁，锁要跟着不变式走。

## 反过来加锁，两个线程互相等

给两个账户各配一把锁，然后按调用顺序拿：

```python
def transfer_any_order(src, dst, amount, gate):
    with src.lock:
        gate.wait()                # 两边都攥住第一把锁，再往下
        time.sleep(0.05)
        with dst.lock:
            src.balance -= amount
            dst.balance += amount


if __name__ == "__main__":
    a, b = Account("A", 100), Account("B", 100)
    gate = threading.Barrier(2)
    t1 = threading.Thread(target=transfer_any_order, args=(a, b, 5, gate), daemon=True)
    t2 = threading.Thread(target=transfer_any_order, args=(b, a, 1, gate), daemon=True)
    t1.start()
    t2.start()
    t1.join(2)
    t2.join(2)
    print(f"still alive={t1.is_alive()},{t2.is_alive()} balances={a} {b}")
```

```text
still alive=True,True balances=A:100 B:100
```

两次 `join(2)` 各等满两秒（一共四秒）之后两个线程都还活着，余额一分没动：A→B 那笔拿着 A 等 B，B→A 那笔拿着 B 等 A。没有异常，没有超时，就是不动。

死锁的症状不是报错，是「没反应」：接口挂住，线程池被这些不返回的线程占满，CPU 不高，03 里那个 `wa` 也不高——它们在等锁，不是等磁盘。重启确实「好」了，因为进程一死锁就没了。

教科书给的四个条件是互斥、持有并等待、不可抢占、循环等待。它们是必要条件：四个都成立才可能死锁，破掉任意一个就不可能。四条都能破，代价不同——不共享（破互斥）要改数据怎么组织；一次拿全（破持有并等待）要事先知道会用到哪几把锁；`try-lock` 失败就全放并重试（破不可抢占）要写重试循环；定顺序（破循环等待）只需要一个排序函数。所以下面只展开最后一条。

## 卡住时先看栈

不用装什么，同一个进程里就能把现场抠出来：

```python
import faulthandler
import sys

faulthandler.dump_traceback(file=sys.stdout)
```

```text
Thread 0x0000b12c (most recent call first):
  File "deadlock_demo.py", line 21 in transfer_any_order
  ...
Thread 0x00027c54 (most recent call first):
  File "deadlock_demo.py", line 21 in transfer_any_order
```

两帧停在同一行，也就是上面代码里第二次加锁那句 `with dst.lock`（行号跟着排版走，我那个临时脚本里是第 21 行；每帧后面还挂着 `threading.py` 里的三帧，我省掉了）。这就是死锁的完整现场：**每个线程都卡在自己第二次加锁那句上**，而且两句话在同一个函数、同一个位置——只是参数方向相反。

`faulthandler` 在 Windows 上就能用，不需要 JVM 也不需要 py-spy。Linux 上的等价物是 `py-spy dump --pid <pid>`，Java 是 `jstack <pid>`，输出里会有一段 `Found one Java-level deadlock`。这两条是标准形态，我这台是 Windows，没跑过。有个边界要记住：JVM 只报它认识的那类环（monitor 与 `ReentrantLock` 的锁图），由 `wait/notify`、信号量、条件变量拼出来的互等它不报——工具说「没找到死锁」不等于没有。

现场对不上号的时候，按症状去找更快：

| 症状 | 先看哪 | 为什么 |
| --- | --- | --- |
| 接口挂住，重启就好，CPU 与 `wa` 都不高 | 线程栈是否所有帧都停在 acquire / 加锁那一行 | 等锁的线程不烧 CPU，只在等 |
| 余额或计数少了一点，不报错 | 读-改-写是否分成两处，中间有没有 IO 或调用 | 窗口就在中间那一段 |
| 事后对账对、过程中间不对 | 同一不变式的两个字段是否各配了一把锁 | 半更新状态被别人看见了 |
| 加锁后耗时翻倍 | 临界区里是否包住了 IO、网络、`sleep` | 锁内的等待是排他的，只能串起来 |

## 修：把顺序定死，超时只当报警

两个方向都先拿名字小的那把：

```python
def transfer_ordered(src, dst, amount):
    first, second = sorted((src, dst), key=lambda x: x.name)
    with first.lock:
        time.sleep(0.05)
        with second.lock:
            src.balance -= amount
            dst.balance += amount
```

```text
ordered: alive=False,False balances=A:96 B:104 102 ms
```

A 转出 5、B 转出 1，最终 A:96 B:104，两个线程都退出了。环没了，因为「谁先拿锁」不再取决于「谁先被调用」。

这条修法有三个前提，缺一个就漏：

1. 锁得能排全序（有 id、名字这类稳定键）。锁集合是动态算出来的（`locks[i]` 由参数决定）时，排序救不了。
2. 所有路径都得遵守。某个函数内部顺手再拿一把全局锁，顺序就可能和别的路径反着来——这类死锁的特点是两处代码各自看都对，拼起来才死。
3. `acquire(timeout=...)` 不是修法。实测：锁被自己持有时 `acquire(timeout=0.5)` 返回 `False`。它的价值是把永久挂起换成一次可观测、可重试、可告警的失败——环还在，只是你这次能看见了。

## 动手

把第一节的 `top_up_naive` 改成「锁外读快照、锁内比较再写」：

```python
def top_up_cas(acc, times, pause):
    for _ in range(times):
        snapshot = acc.balance       # 慢的活儿放在锁外
        time.sleep(pause)
        with acc.lock:
            if acc.balance == snapshot:   # 期间没人改过，才写
                acc.balance = snapshot + 1
```

先猜它的 `lost` 会是多少，再跑。我这边是 1008 和 1002，也就是 995 上下——离 999 不远，原因很直白：这段没有重试，冲突一次就白丢一笔，只是把「覆盖」换成了「跳过」，耗时也没变（510 ms 与不加锁那版持平，因为该丢的时候它什么都没干）。

所以真正要量的是重试次数：在 `else` 里回到循环开头重读快照，跑完看 `lost` 归零要重试多少次、耗时涨到哪。这两个数才是这段代码能不能上线的依据。

## 还差的

- 没跑 free-threaded 构建。3.13 起官方提供不带 GIL 的可选构建，那种环境下「窗口窄到看不见」这个前提就没了，丢更新会容易得多；这台机器只有 3.11.5 的默认构建。
- `py-spy dump` 和 `jstack` 都是标准形态，未实跑。它们输出的样子会随版本变，照抄前先看一眼 `--help`。
- `faulthandler` 只给 Python 帧。卡在 C 扩展内部锁上（SQLite、OpenSSL 里那些）看不见，那得用另一套工具，这轮没做。
- 只测了 2 个线程、1000 与 200000 两个量级。三个以上账户绕成 A→B→C→A 的环我没造，原理一样但没有输出可引。
- 跨进程的「统一顺序」没碰。进程内可以按名字排，跨进程得落到业务键加单点串行，那是分布式锁的题目，这篇只到 `threading.Lock`。
