## 先把结论摆出来

**文件由两部分组成：inode 和名字。名字不是文件本身。**

- **inode** 存文件的元数据和数据块位置：多大、谁拥有、什么权限、改过几次、数据在磁盘的哪几块。它有一个编号，全文件系统唯一。
- **目录项**（directory entry）是目录这个特殊文件里的一行，内容是"名字 → inode 编号"。你看到的文件名，只存在目录里，不在 inode 里。

由此推出四个日常结论：

1. **改名不改变文件**。`mv a.txt b.txt` 在同一个文件系统里只改目录项，inode 编号、内容、时间戳中的 ctime 之外的东西都不动。
2. **硬链接就是两个名字指向同一个 inode**。删掉其中一个名字，文件还在；链接数归零且没有进程打开它，数据才释放。
3. **软链接是另一个文件**，里面存着目标路径。目标删了，软链接还在，只是打不开。
4. **进程打开文件后，拿到的是 inode 的引用，不是名字**。所以日志文件被 `rm` 之后，进程还能继续写，磁盘空间也不会释放——这是"磁盘满了但 `du` 找不到"的第一大原因。

## 从路径到字节：目录项与 inode

文件系统大致由三块组成：

| 组成部分 | 存什么 | 你能怎么看到 |
| --- | --- | --- |
| 超级块 | 文件系统总体信息：块大小、inode 总数、空闲块 | `dumpe2fs -h /dev/vdb1` |
| inode 表 | 每个文件的元数据与数据块指针 | `stat 文件`、`ls -i` |
| 数据块 | 文件正文、目录内容 | `dd`、`debugfs`（一般不用） |

打开 `/data/logs/app.log` 时，内核做的是逐级查找：

1. 从根目录的 inode 开始，读根目录的数据块，找到名字 `data` 对应的 inode 编号；
2. 读 `data` 目录的数据块，找到 `logs`；
3. 读 `logs` 目录的数据块，找到 `app.log`，拿到它的 inode 编号；
4. 读这个 inode，得到权限、大小和数据块位置；
5. 检查权限，把 inode 放进打开文件表。

**目录本身也是一个文件**，它的"正文"就是一张名字到编号的表。这解释了两件事：目录为什么不能硬链接（会形成环）、为什么一个目录里文件太多时 `ls` 也会慢（要读完整个目录数据块）。

用两条命令把这件事看清楚：

```text
$ ls -li /data/logs/
total 12
131073 -rw-r--r-- 1 app app 4096 Oct 26 10:00 app.log
131074 drwxr-xr-x 2 app app 4096 Oct 26 10:01 archive
```

第一列 `131073` 就是 inode 编号。再看 `stat`：

```text
$ stat /data/logs/app.log
  File: /data/logs/app.log
  Size: 4096            Blocks: 8          IO Block: 4096   regular file
Device: 252,1           Inode: 131073      Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/     app)   Gid: ( 1000/     app)
Access: 2026-10-26 10:00:01
Modify: 2026-10-26 10:00:00
Change: 2026-10-26 10:00:00
```

`Links: 1` 是硬链接计数。`Blocks: 8` 是实际占用的 512 字节块数，8 × 512 = 4096 字节。注意 `Size` 是逻辑大小，`Blocks` 是实际分配——稀疏文件时两者会差很远。

## inode 里有什么，没有什么

| inode 里有的 | inode 里没有的 |
| --- | --- |
| 文件类型（普通、目录、socket、设备） | 文件名 |
| 权限位、所有者、所属组 | 文件路径 |
| 大小、占用块数 | 文件内容（内容在数据块） |
| 三个时间：atime / mtime / ctime | 父目录是谁 |
| 硬链接计数 | — |
| 指向数据块的指针（含间接块） | — |

**文件名不在 inode 里**，这一条能解释 `find / -inum 131073` 为什么可能返回多个路径：每个路径都是一个目录项，指向同一个 inode。

三个时间也常被混：

- **mtime**：文件内容最后一次修改；
- **ctime**：inode 本身最后一次变化（改权限、改所有者、加硬链接都会变）；
- **atime**：最后一次读取。很多挂载选项用 `relatime`，只在 mtime 比 atime 新时才更新，避免每次读都写盘。

`touch` 默认改的是 atime 和 mtime；`chmod` 改的是 ctime。看到"文件内容没变但 ctime 变了"，先想有没有人动过权限或链接。

## 文件系统怎么放数据：块、extent 与碎片

文件内容不会连续占着一整段磁盘，而是按固定大小的块分配，典型是 4 KB。inode 记录的就是"哪些块属于我"。

早期 ext2/ext3 用直接块加一级、二级、三级间接块，大文件要翻很多层指针。ext4 引入 **extent**：用"起始块 + 长度"描述一段连续区域，一个 extent 能覆盖很多块，大文件需要的指针少得多。XFS 同样用 extent，但按 B+ 树组织，更适合大文件与高并发。

分配方式直接影响性能：

- **顺序写**：内核尽量把新块放在上一块后面，机械盘少寻道，SSD 也少元数据更新；
- **随机写**：块散落各处，inode 与块位图反复修改；
- **预分配**：`fallocate -l 10G big.img` 一次占住空间，避免边写边分配，也减少碎片。

看一个文件的碎片程度：

```text
$ filefrag -v /data/big.log
Filesystem type is: ef53
File size of /data/big.log is 1073741824 (262144 blocks of 4096 bytes)
 ext:     logical_offset:        physical_offset: length:   expected: flags:
   0:        0..  262143:      34816..    296959: 262144:             last,eof
```

理想情况是一个 extent 覆盖整个文件；如果 `ext:` 有很多行、每段很短，说明碎片严重。SSD 上碎片对顺序读的影响比机械盘小，但元数据开销仍在。

这也解释了为什么"追加写日志"比"反复改文件中间"快：追加通常落在最后一个 extent 的尾部，改中间则可能产生新块和更多元数据更新。

## 硬链接与软链接：两种完全不同的东西

```bash
ln app.log app-hard.log      # 硬链接：目录里多一行，指向同一个 inode
ln -s app.log app-soft.log   # 软链接：新建一个文件，内容是 "app.log"
```

| 对比项 | 硬链接 | 软链接 |
| --- | --- | --- |
| 本质 | 同一 inode 的另一个名字 | 独立文件，内容是目标路径 |
| inode 编号 | 与目标相同 | 与目标不同 |
| 删除目标 | 文件仍可通过硬链接访问 | 变成悬空链接，打不开 |
| 跨文件系统 | 不行 | 可以 |
| 链接目录 | 不允许（除 `.` 和 `..`） | 可以 |
| `ls -l` 显示 | 普通文件 | `l` 类型，箭头指向目标 |

验证硬链接共享 inode：

```text
$ ln /data/logs/app.log /data/logs/app-hard.log
$ ls -li /data/logs/app*.log
131073 -rw-r--r-- 2 app app 4096 Oct 26 10:00 /data/logs/app-hard.log
131073 -rw-r--r-- 2 app app 4096 Oct 26 10:00 /data/logs/app.log
```

两行第一列相同，`Links` 从 1 变成 2。此时 `rm app.log`，`app-hard.log` 照样能读，inode 的链接数变成 1。

**`cp` 和 `mv` 的区别也在这里。** 同一文件系统内 `mv` 是 `rename`，inode 不变；跨文件系统 `mv` 只能"复制到新位置再删旧名字"，新文件的 inode 是新的，权限、所有者、时间戳要靠工具尽量保留（`cp -a`）。`cp` 永远是新建 inode。所以"移动文件后 inode 变了"不是 bug，是跨了文件系统。

软链接的相对路径容易踩坑：

```bash
ln -s logs/app.log /data/current.log
```

这个 `logs/app.log` 是相对于**软链接所在目录**解析的，不是相对于你执行命令的目录。跨目录建软链接时，要么写绝对路径，要么先 `cd` 到目标目录再建。诊断用 `readlink` 和 `readlink -f`：

```text
$ readlink /data/current.log
logs/app.log
$ readlink -f /data/current.log
/data/logs/app.log
```

`readlink -f` 会一路解析到最终目标；如果中途断了，它返回空。悬空链接用 `find /data -xtype l` 能批量找出来。

## 文件描述符：进程怎么记住一个文件

进程打开文件后，内核给它一个**文件描述符**（fd），是个小整数（0 标准输入、1 标准输出、2 标准错误）。这个整数是进程内 fd 表的索引，表项指向内核的"打开文件描述"，后者再指向 inode。

```text
进程 fd 表            打开文件描述             inode
0  ───────────────→  偏移、读写标志  ───────→  元数据 + 数据块
3  ───────────────→  偏移、读写标志  ───────→  同一个 inode
```

这带来一个容易忽略的事实：**两次 `open()` 同一个文件，得到两个独立的偏移**；而 `dup()` 或 `fork()` 之后，父子进程共享同一个打开文件描述，也就共享偏移。这也是"父进程读了一半，子进程接着读"能成立的原因。

看一个进程打开了什么：

```bash
ls -l /proc/<pid>/fd
lsof -p <pid>
```

输出里 `socket:[12345]` 是网络连接，`/data/logs/app.log (deleted)` 是被删掉但仍打开的文件。fd 有上限：

```text
$ ulimit -n
1024
```

服务端进程常见 `Too many open files`，原因通常是连接或文件没关，而不是上限本身太小。先看 `ls /proc/<pid>/fd | wc -l` 与 `lsof -p <pid> | wc -l`，确认是不是泄漏，再谈调大 `LimitNOFILE`。调大只是把问题推迟。

## 写文件：页缓存、回写与 fsync

`write()` 返回成功，数据只在页缓存里，这一点在上一篇讲过。这里补上文件系统这一层：

1. `write()` 修改页缓存中的页，把它标记为脏；
2. 内核的后台回写线程（ext4 的 `flush`、XFS 的 `xfsaild` 等）定期把脏页写到磁盘；
3. `fsync(fd)` 强制把这个文件的数据和元数据刷到磁盘，并等待完成；
4. `fdatasync(fd)` 只保证数据与"读取数据必需的那部分元数据"，不保证 mtime 之类，通常更快；
5. `O_SYNC` 让每次 `write()` 都等落盘，最慢，除非特殊场景不要用；
6. `O_DIRECT` 绕过页缓存，直接对磁盘做 IO，要求缓冲区和偏移按块大小对齐，数据库自己管缓存时才用。

**只 `fsync` 文件本身，不足以保证"改名"这件事在崩溃后还在。** 目录也是一份数据，`rename` 改的是目录项。可靠的做法是：

```text
写临时文件 tmp
fsync(tmp)
rename(tmp, final)
fsync(目录 fd)
```

少了最后一步，断电后可能出现"文件内容在，但名字没出现"或"名字指向旧内容"。数据库、配置中心写文件时都按这个顺序，不是多此一举。

## 日志式文件系统：崩溃后为什么还能挂上

如果写到一半断电，inode 表和数据块可能处于半新半旧的状态。日志式文件系统（journaling filesystem）的做法是：**先把要改的元数据写进一块连续的日志区，提交后再慢慢覆盖到正式位置。** 崩溃恢复时重放日志，把未完成的修改补完或丢弃。

ext4 有三种日志模式：

| 模式 | 记录什么 | 特点 |
| --- | --- | --- |
| `data=journal` | 数据与元数据都进日志 | 最安全，最慢，很少用 |
| `data=ordered` | 只记元数据，但数据先于元数据落盘 | ext4 默认，兼顾安全与性能 |
| `data=writeback` | 只记元数据，数据顺序不保证 | 最快，崩溃后可能读到旧数据 |

XFS 只对元数据做日志，数据靠回写顺序与 `fsync` 保证。它和 ext4 的差别点到为止：

| 对比项 | ext4 | XFS |
| --- | --- | --- |
| inode 分配 | 格式化时预留固定数量 | 动态分配，按需创建 |
| 扩容/缩容 | 可在线扩容，缩容需卸载 | 可在线扩容，不能缩容 |
| 大文件与并发 | 够用 | 大文件、大目录、高并发写入更强 |
| 典型场景 | 系统盘、通用 | 数据盘、日志与对象存储 |

真正要记住的不是参数，而是：**日志保证的是文件系统结构一致，不保证你刚写的数据不丢。** 数据不丢要靠 `fsync` 与副本。生产上还要区分"机器掉电"与"磁盘坏了"两种情况：日志能救前者，副本才能救后者。

## df 和 du 为什么对不上

`df` 问的是文件系统：总块数、已用、可用。`du` 是遍历目录，把每个文件占用的块加起来。两者口径不同，对不上很常见。五个原因按出现频率排：

| 原因 | 现象 | 怎么确认 |
| --- | --- | --- |
| 已删除但仍被进程打开 | `df` 满，`du` 小很多 | `lsof +L1`、`ls -l /proc/<pid>/fd` |
| 硬链接被重复计算 | `du` 某些目录加起来偏大（默认 du 会去重，但分开跑不会） | `du -l` 或 `find -inum` |
| 稀疏文件 | `ls -l` 很大，`du` 很小 | `du --apparent-size` 对比 |
| 保留块 | `df` 的 Available 比 Free 小 | `tune2fs -l` 看 Reserved block count |
| 挂载覆盖 | 目录里有数据，但被另一个文件系统挂上盖住了 | `findmnt`、`df` 对比挂载点 |

另外两个次要原因：文件系统元数据（inode 表、日志）占空间但不在任何目录里；`du` 默认按 1K 块向上取整，很多小文件会累出差距。

inode 也会用完。此时 `df -h` 显示还有空间，创建文件却报 `No space left on device`：

```text
$ df -i /data
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/vdb1      3276800 3276800      0  100% /data
```

`df -i` 的 `IUse%` 到 100%，说明是小文件太多。清理方向是临时文件、缓存目录、邮件队列这类"数量大、单个小"的东西，而不是找大文件。

定位小文件最多的目录：

```bash
find /data -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head
```

`-xdev` 很关键：不跨文件系统，否则会把 `/proc`、`/sys` 或其他挂载点一起扫进来，结果既慢又假。删海量小文件本身也慢，因为每个文件都要改目录项和位图；数量到百万级时，用 `rsync -a --delete empty/ target/` 往往比 `rm -rf` 快。

## 一个具体例子：磁盘 100%，du 只算出四成

线上告警：`/data` 使用率 100%。登上去看：

```text
$ df -h /data
Filesystem      Size  Used Avail Use% Mounted on
/dev/vdb1       500G  500G     0 100% /data

$ du -sh /data
196G    /data
```

差出来的 300 多 G 去哪了？先找"已删除但仍被打开"的文件：

```text
$ lsof +L1 2>/dev/null | head
COMMAND   PID USER   FD   TYPE DEVICE    SIZE/OFF NLINK    NODE NAME
java    18422  app    7w   REG  252,1 343597383680     0  131456 /data/logs/app.log (deleted)
```

一行就够了：Java 进程的 7 号 fd 打开着一个已删除的 `app.log`，文件逻辑大小 320 GB，链接数为 0。运维在清理日志时用了 `rm`，但进程还开着这个文件，inode 引用还在，数据块一个都没释放。

再确认一下：

```text
$ ls -l /proc/18422/fd/7
lrwx------ 1 app app 64 Oct 26 10:20 /proc/18422/fd/7 -> /data/logs/app.log (deleted)
```

处理有三种：

1. **重启或 reload 进程**：最干净，但要看业务能否中断；
2. **让进程重新打开日志**：多数日志框架支持 `SIGHUP` 或自带 reopen 接口；
3. **临时把文件截断**：`: > /proc/18422/fd/7`。它清空的是同一个 inode，空间立刻释放，但前提是进程以可写方式打开且没有追加偏移问题；对正在写的日志有丢一段的风险。

根治要改日志轮转方式。`logrotate` 的 `create` 模式是"改名 + 通知进程重开"，`copytruncate` 是"复制一份再截断原文件"，后者有丢日志窗口但不需要进程配合。**最怕的是只用 `rm` 又没通知进程**，这正是本例。

顺便区分另一类"df 满"：如果 `lsof +L1` 什么都没有，`du` 也对得上，就看是不是 inode 满了（`df -i`）、是不是有挂载点盖住了目录（`findmnt`）、是不是保留块比例太高。三条命令按顺序试，比盲删文件安全。

## 常见误区

### 误区：文件名是文件的一部分

**你以为**：文件的内容、属性、名字都记在同一个地方，改名等于改文件。
**其实**：名字只存在于目录项里，inode 里没有文件名。硬链接能存在，正是因为多个目录项可以指向同一个 inode。
**怎么验证**：`ln a b` 后 `ls -li a b`，两行 inode 编号相同；`mv a c` 后 inode 编号仍然不变。

### 误区：删除了文件，空间就回来了

**你以为**：`rm` 之后磁盘立刻多出空间。
**其实**：`rm` 只是去掉一个名字并把链接数减一。链接数归零后，还要等所有打开该文件的进程关闭 fd，数据块才释放。
**怎么验证**：`lsof +L1` 看链接数为 0 的文件；或在 `rm` 一个正在被 `tail -f` 打开的大文件前后对比 `df -h`。

### 误区：软链接和硬链接只是写法不同

**你以为**：`ln` 和 `ln -s` 都能给文件起别名，效果差不多。
**其实**：硬链接是同一 inode 的另一个名字，不能跨文件系统、不能链目录；软链接是独立文件，存的是路径，目标删掉就悬空，跨文件系统也能用。
**怎么验证**：`ls -li` 看 inode 是否相同；把目标文件删掉，再分别读硬链接和软链接。

### 误区：数据写进文件并 fsync，改名就一定不会丢

**你以为**：`fsync(file)` 之后 `rename` 是安全的。
**其实**：`rename` 修改的是目录项，目录本身也要 fsync，否则崩溃后可能看不到新名字。
**怎么验证**：在测试机上按"写临时文件 → fsync → rename → 不 fsync 目录"的顺序写，然后强制断电重启，观察目标文件是否存在。生产上直接采用"文件与目录都 fsync"的写法即可。

## 小结

文件等于 inode 加目录项：inode 管元数据和数据块，目录项管名字。硬链接是同一 inode 的多个名字，软链接是存路径的另一个文件。fd 指向打开文件描述，再指向 inode，所以删名字不等于释放空间。写入先到页缓存，落盘要 fsync；rename 的持久化还要 fsync 目录。df 与 du 对不上时，先查已删除但仍被打开的文件，再查硬链接、稀疏文件、保留块与挂载覆盖。ext4 与 XFS 的差异记住"inode 分配方式、扩容缩容、适用场景"三点就够。这些行为都不是故障，是文件系统在按自己的规则工作。
