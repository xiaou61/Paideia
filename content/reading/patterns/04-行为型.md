## 先把结论摆出来

业务代码里出现频率最高的三个模式，恰好对应三种最常见的坏味道：

| 坏味道 | 模式 | 一句话 |
| --- | --- | --- |
| 一长串 `if/else` 分派 | 策略 | 每个分支独立成类，运行时选一个 |
| 几个方法流程一样、中间一步不同 | 模板方法 | 把骨架提到父类，变的那步留给子类 |
| 做完一件事要通知很多方 | 观察者 | 发布事件，订阅者各自处理 |

**三者都不是"让代码更高级"，而是让"改动点"集中。** 判断用哪个的标准是：变的是什么。

## 策略：变的是"整个算法"

```text
// 坏味道：加一种折扣要改这个方法
BigDecimal price(User u, BigDecimal total) {
    if (u.getLevel() == 1) return total;
    else if (u.getLevel() == 2) return total.multiply(new BigDecimal("0.95"));
    else if (u.getLevel() == 3) return total.multiply(new BigDecimal("0.9"));
    ...
}
```

策略版本：

```text
interface DiscountStrategy { BigDecimal apply(BigDecimal total); }

class VipDiscount implements DiscountStrategy { ... }

// 装配处选一个
BigDecimal finalPrice = strategy.apply(total);
```

**价值不在"用了接口"，在于新增折扣只写一个新类**，不碰已有代码，也不会不小心改坏别人的分支。

用 Map 注册实现是最常见的落地方式：

```text
Map<Integer, DiscountStrategy> registry = Map.of(
    1, new NoDiscount(),
    2, new VipDiscount(),
    3, new SvipDiscount());
```

**注意**：策略只能取代"平级选择"。如果分支之间有先后依赖（先判断 A 再判断 B），硬套策略会更难读。

## 模板方法：变的是"某一步"

```text
abstract class ImportTask {
    public final void run() {          // final：骨架不许改
        byte[] raw = download();
        List<Row> rows = parse(raw);
        int ok = save(rows);
        notifyResult(ok);
    }
    protected abstract List<Row> parse(byte[] raw);   // 只有这步变
}
```

关键在 `final`：**骨架固定，子类只能填中间那一步**。这保证了"所有导入都走同一套流程"。

判断什么时候该用：**流程的步骤固定，但某几步对不同数据源不一样**。

**代价**：继承耦合。父类改骨架，所有子类都受影响。现代 Java 里更轻的写法是传入函数/Lambda：

```text
void importCsv(byte[] raw, Parser parser) { ... }
```

**能组合就别继承**——继承是编译期绑定，组合是运行期可换。

## 观察者：变的是"谁关心"

```text
// 坏味道：下单逻辑里塞满了后续动作
void createOrder(Order o) {
    save(o);
    sendEmail(o);
    addPoints(o);
    pushToWarehouse(o);
    updateRecommendation(o);
}
```

每加一个后续动作，都要改这个核心方法。

观察者版本：

```text
void createOrder(Order o) {
    save(o);
    events.publish(new OrderCreated(o));   // 只发一个事件
}

// 各方自己订阅
@EventListener
void onOrderCreated(OrderCreated e) { sendEmail(e); }
```

Spring 的 `ApplicationEventPublisher` + `@EventListener` 就是这个模式的现成实现，**不需要自己造一套**。

**代价要说清**：

- **流程不再线性**：看代码看不出下单之后到底发生了什么；
- **异常边界变了**：默认情况下监听器抛异常会影响发布方（同步执行），需要异步或捕获；
- **调试变难**：事件是隐式的，出了问题要靠日志追。

所以观察者适合"确实有很多不相关的后续动作"，而不是"我想解耦"这种模糊理由。

## 三者的选择标准

问一句话：**你这次要变的是什么？**

- 是"选哪套算法" → 策略；
- 是"流程里的某一步" → 模板方法（或传函数）；
- 是"同一件事有多个下游" → 观察者。

如果答不上来，说明还不需要模式。

## 常见误区

### 误区：事件驱动一定比直接调用好

**你以为**：发布事件就是解耦，越多越好。
**其实**：直接调用是**显式**的，看代码就知道发生了什么。事件是隐式的，链路一长就没人说得清。只有"下游数量多且互不关心"时它才划算。
**怎么验证**：看你的下单流程，如果事件只有一两个订阅者，改成直接调用通常更清楚。

### 误区：策略模式就是抽个接口

**你以为**：写了 `interface XxxStrategy` 就是用了策略模式。
**其实**：真正的策略需要一个**选择点**（注册表或工厂）。如果实现类被写死在业务里 `new`，那只是把 if 换成了 new，没解决问题。
**怎么验证**：加一种实现时，是否需要改业务代码。需要，就说明选择点没抽出来。

### 误区：模板方法比传函数更面向对象

**你以为**：继承是 OO 的正统做法。
**其实**：继承把子类和父类的生命周期绑死。Java 8 之后，传函数/Lambda 能表达同样的"骨架 + 变化点"，且没有继承耦合。
**怎么验证**：看父类里有多少个 `protected abstract` 方法。超过两个，通常可以用组合替代。
