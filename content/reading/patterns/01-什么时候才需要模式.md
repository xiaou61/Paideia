## 先把结论摆出来

**先有变化，才有模式。** 判断一个地方该不该引入模式，只看三个信号：

1. **同一个判断重复出现**：三处 `if (type == "A") ... else if (type == "B")`；
2. **变化点在增长**：今天两种支付方式，下个月要加第三种；
3. **依赖方向错了**：业务代码直接依赖具体实现，换一个实现要改一堆调用方。

三条都没有时引入模式，得到的是**多一层间接、多一个文件、多一处要维护的东西**。

## 反例先看：过度设计的四个信号

| 信号 | 说明 |
| --- | --- |
| 接口只有一个实现 | 而且短期不会有第二个 |
| 抽象类只有一个子类 | 同上 |
| 工厂只造一种产品 | 工厂本身成了多余的间接 |
| 事件/监听只有一个订阅者 | 直接调用更简单 |

这些都是"为了以后可能的变化"提前付的成本。**代码里最贵的不是重复，是错误的抽象**——因为重复是显性的、能看见；错误抽象的代价要等到改动时才会暴露。

## 信号一：同一个判断重复出现

```text
if (type.equals("alipay")) {
    return alipayService.pay(amount);
} else if (type.equals("wechat")) {
    return wechatService.pay(amount);
} else if (type.equals("balance")) {
    return balanceService.pay(amount);
}
```

这段代码有什么问题？**不是"不够优雅"，是每加一种支付方式要改这里**。改动点集中在一个方法里，而且这个方法会无限增长。

这才是有第二个实现、第三个实现、第四个实现的地方——**变化是已经发生的，不是预测的**。

## 信号二：变化点在增长

判断"会不会继续增长"看两件事：

- 业务上是不是在持续接新渠道/新类型（支付、登录、消息推送、导出格式）；
- 历史上是不是已经加了两次以上。

如果答案是"是"，即使现在只有两个实现，抽出来也是合理的。因为**你已经观察到了增长趋势**，不是猜。

如果答案是"不会"，哪怕现在有五个 `if`，也可以先不抽——重复但稳定，比抽象但错位要好。

## 信号三：依赖方向错了

**依赖倒置**的一句话版本：业务逻辑不应该依赖具体实现，应该依赖接口。

```text
// 业务直接依赖具体类：换存储就要改业务
class OrderService {
    private final MySQLOrderRepo repo = new MySQLOrderRepo();
}

// 依赖接口：换存储只改装配处
class OrderService {
    private final OrderRepo repo;
    OrderService(OrderRepo repo) { this.repo = repo; }
}
```

判断标准很直接：**换一个实现（比如测试时换成内存版），需要改几处？**

- 改 1 处（装配）→ 依赖方向是对的；
- 改 N 处（所有 new 的地方）→ 应该引入接口。

这也是"为什么要用依赖注入"的最实在的回答。

## 一个对比

同一段需求："导出支持 CSV 和 PDF，未来可能加 Excel"。

**过度设计的版本**：先定义 `ExportStrategy` 接口、`ExportStrategyFactory`、`ExportStrategyRegistry`、`ExportContext`，再写两个实现。为了两个实现写了六个文件。

**合适的版本**：先写两个方法，在调用处用一个 `if`。等真的要加第三种、且发现 `if` 已经有三处时，再抽接口。

**关键不是"永远不抽"，而是"等变化真的出现再抽"**。第一次出现时抽，你抽出来的形状往往和第二次出现时所需要的不一样。

## 常见误区

### 误区：重复代码一定该抽出来

**你以为**：DRY 是绝对原则，看到重复就抽。
**其实**：两段长得一样但**变化原因不同**的代码，抽在一起之后会互相牵连——改一个业务需求影响另一个。这叫"错误的耦合"，比重复更难维护。
**怎么验证**：抽出来之后，是否出现过"为了不影响 B 场景，在共享方法里加参数"的情况。有，就说明抽错了。

### 误区：设计模式是"高级特性"，用得越多水平越高

**你以为**：代码里模式越多越专业。
**其实**：成熟的代码通常是"大部分地方直白，少数关键位置有清晰的抽象"。满屏接口和工厂往往意味着抽象没找对。
**怎么验证**：数一下一个需求从入口到落库要经过几个类。超过七八个跳转就该问"这层真的需要吗"。

### 误区：等以后要扩展时再重构，现在先不设计

**你以为**：YAGNI 就是不设计，全部硬编码。
**其实**：YAGNI 反对的是"为想象中的需求提前抽象"，不反对"把变化点隔离出来"。识别变化点、保持依赖方向正确，是现在就能做的、成本很低的事。
**怎么验证**：看新增一个同类需求要改几个文件。超过三处说明边界没划好。
