## 先把结论摆出来

模式被误用，通常不是因为"不会写"，而是因为**把模式当成了一种代码风格**。下面这张表是最常见的六种误用，以及更便宜的替代方案：

| 误用 | 症状 | 更便宜的替代 |
| --- | --- | --- |
| 单例滥用 | 到处 `getInstance()`，全局可变状态 | 交给 Spring 管理，或用参数传递 |
| 万能工厂 | 工厂只有一个产品，或产品永远不变 | 直接 `new`，或一个静态方法 |
| 无变化策略 | 策略接口只有一个实现 | 直接调用那个实现 |
| 空观察者 | 只有一个订阅者，且不会增加 | 直接方法调用 |
| 装饰器套同款 | 层层包装的接口行为完全一样 | 去掉包装，保留一层 |
| 为模式而分层 | 一个需求穿过 Controller→Service→Manager→Helper | 合并职责相同的层 |

**判断标准始终是同一个**：变化点在哪？多一个实现会怎样？调用方真的需要不知道实现吗？三个问题都答不上来，抽象就是负债。

## 误用一：单例当全局变量用

```java
public class ConfigHolder {
    private static ConfigHolder instance;
    public static ConfigHolder getInstance() { ... }
    public Map<String, String> cache = new HashMap<>();
}
```

这段代码的问题不是"用了单例模式"，而是：

1. `cache` 是**可变全局状态**，任何地方都能改，测试之间互相污染；
2. 依赖关系被藏起来了：看方法签名不知道它用了 `ConfigHolder`；
3. 并发下还要自己保证线程安全。

在 Spring 项目里，**单例的正确形态是"容器管理的无状态 Bean"**：

```java
@Service
public class ConfigService {
    private final ConfigRepository repository;   // 通过构造器注入
    // 不持有可变共享状态
}
```

如果确实需要缓存，用专门的缓存组件（Caffeine、Redis），而不是一个全局 `HashMap`。

## 误用二：只有一个产品的工厂

```java
public interface NotifierFactory {
    Notifier create();
}

public class EmailNotifierFactory implements NotifierFactory {
    public Notifier create() { return new EmailNotifier(); }
}
```

工厂的价值是"把选择逻辑集中到一处"。当只有一个产品、且创建过程就是 `new` 时，工厂没有承担任何选择：

```java
Notifier notifier = new EmailNotifier();
```

**什么时候工厂才值**：

- 创建过程复杂（需要读配置、组装依赖、选择实现）；
- 调用方不应该知道具体类；
- 产品种类会增长。

## 误用三：策略接口只有一个实现

```java
public interface PriceCalculator {
    BigDecimal calculate(Order order);
}

@Service
public class DefaultPriceCalculator implements PriceCalculator { ... }
```

只有一个实现、短期内也不会有第二个，这个接口只是多了一个文件、多了一次跳转。**等第二个实现真的出现，再抽接口**——那时你会更清楚接口该长什么样。

一个例外：这个接口是**模块边界**（比如 `paideia-knowledge` 暴露给其它模块的端口），即使只有一个实现也必须存在。判断依据是"调用方是否跨模块"，不是"实现有几个"。

## 误用四：为了"以后可能"加的观察者

```java
eventPublisher.publishEvent(new OrderCreated(orderId));
```

如果只有一个监听者，而且业务上明确不会再加，直接调用更清楚：

```java
notificationService.sendOrderCreated(orderId);
```

事件机制的价值是**解耦发布方与订阅方**。只有一个订阅者时，这种解耦没有收益，反而让"这个方法到底做了什么"变得需要跨文件追踪。

## 误用五：装饰器套同款

```java
Service service = new LoggingDecorator(
    new MetricsDecorator(
        new RetryDecorator(
            new ActualService())));
```

装饰器的前提是"每一层都增加一种横切能力"。如果三层里有两层只是转发、没有实际逻辑，就应该删掉。**层数不是专业度的指标，能说清每层加做了什么才是。**

## 误用六：为分层而分层

```text
Controller → OrderService → OrderManager → OrderHelper → OrderRepository
```

一个查询要穿过五层，每层只做一行转发。这不是模式，是**层数膨胀**。常见的真实原因：

- 每层都是不同时间、不同人加的，没人敢删；
- 为了"以后可能换实现"预留；
- 命名上不敢用同一个词（Service/Manager/Helper）。

判断方法很直接：**删掉中间一层，行为会不会变？** 不会变、且没有独立的测试或边界意义，就该合并。

## 三个判断问题（贴在工位上）

1. **变化点在哪？** 现在有几个实现？未来增长有业务依据吗？
2. **调用方需要知道实现吗？** 如果它总是知道，接口没有隔离任何东西。
3. **删掉这层抽象，谁会疼？** 答不出来，说明它没有承担职责。

三个问题里有两个答不上来，就先不抽。

## 一个反例：什么时候"看起来像误用"其实是对的

- **跨模块端口**：只有一个实现，但调用方在另一个模块，必须通过接口隔离（如 `AccountApi`）；
- **测试替身**：为了在测试里替换外部依赖，接口即使只有一个生产实现也合理；
- **框架扩展点**：Spring 的 `HandlerInterceptor`、`Converter` 即使你只写一个，也是框架约定的扩展方式；
- **确实会增长**：产品路线图明确下季度接三个渠道，接口可以先立。

这些都不是"因为模式好听"，而是有**具体的边界或增长依据**。

## 常见误区

### 误区：用了模式就显得专业

**你以为**：代码里接口、工厂、策略越多，设计能力越强。
**其实**：成熟的代码通常**大部分地方直白，少数关键位置有清晰抽象**。满屏模式往往意味着抽象没找对变化点。
**怎么验证**：数一个需求从入口到落库经过几个类；超过七八个跳转就该逐个问"这层真的需要吗"。

### 误区：设计模式是面试造出来的东西，实际没用

**你以为**：模式只存在于八股文里。
**其实**：你每天用的框架里全是模式——Spring 的代理、JDK 的 `InputStream` 装饰器、`Comparator` 策略、`ApplicationEvent` 观察者。问题不在模式本身，而在**在不该用的地方用**。
**怎么验证**：打开 `java.io` 包，数一下 `FilterInputStream` 下面有多少装饰器；再看自己的业务代码，哪些地方真的需要同样的能力。

### 误区：重复代码一定要抽

**你以为**：看到两段相似代码就该合并。
**其实**：如果两段代码**变化原因不同**，合并之后会互相牵连。重复是显性的，错误的抽象是隐性的——后者更难维护。
**怎么验证**：合并后是否出现过"为了不影响 B 场景，在共享方法里加一个开关参数"；有，就说明抽错了。

## 小结

误用的共同点是**抽象没有对应真实的变化点**。单例、工厂、策略、观察者、装饰器、分层，每一种都有它成立的边界：有多个实现、有真实的替换需求、有跨模块的隔离要求。三个判断问题（变化点在哪、调用方要不要知道实现、删掉谁会疼）能挡掉绝大多数"为了模式而模式"的改动。
