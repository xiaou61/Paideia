## 94 个接口，30 个只有一个实现

「一个接口只有一个实现，就是过度设计」——这条规则流传得比它成立的范围广。我想看看自己这个仓库犯了多少，于是在仓库根目录写了个脚本，数 `backend/`（12 个 Maven 模块）里的接口和实现：

```python
import re, pathlib, collections

ROOT = pathlib.Path("backend")
main = [p for p in ROOT.rglob("*.java") if "/src/main/" in p.as_posix()]
test = [p for p in ROOT.rglob("*.java") if "/src/test/" in p.as_posix()]

def read(p): return p.read_text(encoding="utf-8", errors="replace")
def module(p): return p.relative_to(ROOT).parts[0]

IFACE = re.compile(r"^\s*(?:public\s+)?interface\s+(\w+)", re.M)
IMPL = re.compile(r"\bimplements\s+([^{]+)\{")

ifaces = {}
for p in main:
    t = read(p)
    pkg = re.search(r"^\s*package\s+([\w.]+);", t, re.M)
    for name in IFACE.findall(t):
        ifaces[name] = (f"{pkg.group(1)}.{name}", module(p))

def impls_in(paths):
    c = collections.Counter()
    for p in paths:
        for g in IMPL.findall(read(p)):
            for tok in g.split(","):
                tok = re.sub(r"<.*>", "", tok).strip().split(".")[-1]
                if tok in ifaces:
                    c[tok] += 1
    return c

main_impls, test_impls = impls_in(main), impls_in(test)
single = [n for n in ifaces if main_impls[n] == 1]

def used_elsewhere(name):
    fqn, own = ifaces[name]
    return any(module(p) != own and
               re.search(rf"^import\s+{re.escape(fqn)};", read(p), re.M)
               for p in main)

cross = [n for n in single if used_elsewhere(n)]
tested = [n for n in single if test_impls[n]]
neither = [n for n in single if n not in cross and n not in tested]

print("接口声明:", len(ifaces))
print("单实现（只看 src/main）:", len(single))
print("  被别的模块 main import:", len(cross))
print("  测试里另有实现:", len(tested))
print("  两者都没有:", len(neither))
print("  两者都没有的名单:", ", ".join(sorted(neither)))
```

真实输出（Python 3.11.5，Windows 11）：

```
接口声明: 94
单实现（只看 src/main）: 30
  被别的模块 main import: 15
  测试里另有实现: 3
  两者都没有: 13
  两者都没有的名单: AssistantAnswerer, AssistantConversation, ContentClassifier, DocumentDistiller, EmbeddingClient, EntrySummarizer, EssaySource, InterviewReviewer, PostmortemKnowledge, ResumeAnalyzer, ResumeParser, ResumeProposer, RunSink
```

看到 30 的时候我以为找到了 30 处过度设计。往下看两行就知道这个读法错了：一半被别的模块 `import` 了。

`AccountApi` 就是例子。`paideia-account` 里只有一个实现 `AccountApiImplementation`，类本身是包级可见的；`paideia-app` 的 `RoleLookupConfiguration` 通过 `AccountApi` 拿角色（`@Bean RoleLookup roleLookup(AccountApi accounts)`）。把接口删掉、改成直接 `new` 实现，`paideia-app` 要么依赖 account 的内部类，要么依赖整个 account 模块。这里接口不是抽象，是模块之间唯一的一条通道。

再看那 3 个「只在模块内用」的：`CodeRunner` 有 `FakeRunner`（`ShellRunnerTest`）、`NoteApi` 有 `FakeNotes`（`NoteToolsTest`）、`KnowledgeApi` 在测试里也有替身。测试替身就是第二个使用方——它在测试代码里。

所以规则该改成：**不数实现，数使用方——别的模块，或者测试。** 一个都没有，才轮到谈删除。按这个口径，94 个接口里真正「只有一个实现、也没有任何第二个使用方」的是 13 个。

这 13 个里有 12 个在 `paideia-ai`，剩下一个 `PostmortemKnowledge` 在 `paideia-ops`。`paideia-ai` 那 12 个并不都是候选：其中有 6 个直接包着外部依赖——`OllamaEmbeddingClient`、`MysqlRunSink`、`NowcoderEssaySource`、`AgentScopeResumeParser`、`AgentScopeInterviewReviewer`、`LayaContentClassifier`，对应 Ollama、MySQL、Nowcoder、AgentScope、Laya。接口在那儿挡的是「外部系统怎么实现不归这个仓库管」，不是「以后可能加第二个实现」。

**口径要说清**：这个脚本只认文本里的 `implements`。`extends` 抽象类、MyBatis 的 `@Mapper`（运行时代理出来的实现）、把 lambda 传给函数式接口，都不计入。所以同一份数据里「`implements` 命中 0 次」的接口有 58 个，这个数不能当「58 个接口没人实现」用——里面混着 mapper 和 `interface X extends Y`。

## 该用事件的那一处：注销一个账号，5 个模块各删自己的表

数使用方这条规则，在这个仓库里有一处被用到了极限：注销账号。

`AccountDeletionService`（`paideia-account`）在同一个事务里删 refresh token、删画像、删用户行，最后一行是 `events.publishEvent(new UserDeletedEvent(userId))`。这个事件的监听者有 6 个，散在 5 个模块：`paideia-mcp` 两个（`McpUsageUserDeletionListener`、`McpUserDeletionListener`），`paideia-sandbox`、`paideia-note`、`paideia-knowledge`、`paideia-ai` 各一个。

6 个使用方，肯定不是「空观察者」。但数量不是这条链路的理由，方向才是。`UserDeletedEvent` 的类注释写得很直白：注销要删的数据散在各模块，若让账号模块去调它们的 API，账号就会反向依赖所有业务模块，而账号是地基，这个方向不对。事件把「删什么」留在各模块手里。

同一份代码里还有反证的半边：画像（profile）和用户表同库同域，`deleteCascade` 里就是 `profiles.deleteByUser(userId)` 直接删，注释写着「同库同域，直接删，不必绕一圈事件」。

**判据不是「解耦更好」，是「这份数据在谁的模块里」。** 同一个模块内的两个对象之间，事件不解决任何问题，只多一次「跳到别的文件才知道发生了什么」。

这里还有三条默认值必须记清，写反了整条链路就静默失效：

- `@EventListener` 是**同步**的，在发布线程里挨个执行（第 5 课讲过）。它换的是依赖方向，不是并发；要异步得自己加 `@Async` 并配线程池。
- `@TransactionalEventListener` 的 `phase` 默认是 `AFTER_COMMIT`，不是提交前。这里必须显式写 `BEFORE_COMMIT`，因为注销要求「要么全删干净、要么什么都没发生」，分两个事务做会出现「用户没了但记忆还在」的中间状态。
- `@TransactionalEventListener` 在**没有活动事务**时默认不执行。所以「监听器没跑」这个 bug，第一嫌疑是发布点没有事务，不是监听器写错了。

最后一条在这条链路上有个具体收益。`NoteUserDeletionListener` 要删三张表，其中 `note_reports` 里这个人的列叫 `reporter_user_id`（举报人），不是 `user_id`——按 `user_id` 一刀切会直接 SQL 报错。这个知识属于 note 模块，发布方 `paideia-account` 不需要知道 note 有哪几张表、哪一列叫什么。事件真正买到的就是这个：**删表的知识留在拥有那张表的模块里**。

而且这个方向有测试盯着：`CrossModuleContractTest.eventsPublishedOnlyByOwner` 断言 `UserDeletedEvent` 只能由 `paideia-account` 发布、`EntryAssessmentChangedEvent` 只能由 `paideia-knowledge` 发布，扫全仓源码找 `new UserDeletedEvent(`。事件用得多了，方向纪律就变成守卫。

## 同一个病在脚本里：一份活得太久、谁都能改的缓存

单例的病从来不是「只有一个实例」，而是「一份活得比使用方更久、谁都能改的状态」。这件事在 Java 里靠容器管理，在 Python 里就是模块本身。

三个文件，放同一个目录（`cfg.py`、`other.py`、`probe.py`）：

```python
# cfg.py
cache = {}

def load(key):
    if key not in cache:
        cache[key] = "v:" + key
    return cache[key]

def reset():
    global cache
    cache = {}
```

```python
# other.py
import cfg

def touch():
    cfg.load("from-other")
```

```python
# probe.py
import cfg
from cfg import cache
import other

cfg.load("a")
other.touch()
print("两个模块看到同一份:", sorted(cfg.cache))
print("名字拿到的:", sorted(cache))
cfg.reset()
print("reset 之后 cfg.cache:", cfg.cache)
print("reset 之后那个名字:", sorted(cache))
print("还是同一个对象吗:", cache is cfg.cache)
```

真实输出（Python 3.11.5）：

```
两个模块看到同一份: ['a', 'from-other']
名字拿到的: ['a', 'from-other']
reset 之后 cfg.cache: {}
reset 之后那个名字: ['a', 'from-other']
还是同一个对象吗: False
```

前两行是单例想达到的效果：两个模块共用一份缓存，`import` 保证模块只执行一次。第四行是它的病：`reset()` 之后 `cfg.cache` 是空字典，而 `probe` 里那个名字还拿着有两条旧数据的字典。

原因是 `from cfg import cache` 不是「引用变量 `cache`」，是在 import 那一刻，把**那个字典对象**绑到本模块的全局名 `cache` 上。`reset()` 里 `global cache; cache = {}` 换的是 `cfg` 模块的那个名字，指向新对象；`probe` 的名字还指着旧对象。单例的对象换了，拿过它的人不知道。

同一个病的另外两种写法也能真跑出来：

```python
# default.py
def remember(key, seen=[]):
    seen.append(key)
    return seen

print(remember("a"))
print(remember("b"))
print(remember.__defaults__)
```

```
['a']
['a', 'b']
(['a', 'b'],)
```

`seen=[]` 在 `def` 执行的那一刻创建一次，挂在函数对象上，`__defaults__` 里能看见它已经吃到两个元素。第二次调用不是「重新给了个空列表」，是往同一个列表里又塞了一个。

```python
# classattr.py
class Cache:
    data = {}

one, two = Cache(), Cache()
one.data["a"] = 1
print(two.data, one.data is two.data)
```

```
{'a': 1} True
```

`data` 属于类，不属于实例。两个实例共用一个字典，`one.data[...]` 写的是类属性。

三种写法一个病根：**这个对象活多久、谁创建它、谁有权改它，都没写清楚。** 换成 Java，形状完全一样——Spring 的 singleton 是「每个 IoC 容器一个实例」，这是框架的作用域契约，不是 Java 语言的保证；容器也不会替你保证线程安全。一个单例 bean 里放个可变字段，就是所有请求在写同一份数据。

反例也在仓库里：`LocalOnlyAuthorizationManager` 是个枚举单例（`enum ... { INSTANCE; }`），零字段，只做 `isLoopback(String)` 判断，被 `SecurityConfiguration` 用了两次（`.access(LocalOnlyAuthorizationManager.INSTANCE)`）。它没有可变状态，所以「全局唯一」这件事本身不产生任何问题。

顺带一条语言层的事实：枚举实例的唯一性是 Java 语言与序列化规范保证的——反序列化按名字返回同一个常量，反射 `newInstance` 对 enum 直接抛异常。所以枚举单例不需要双重检查加锁加 `volatile` 那一套。这类「语言保证」和前面「Spring 容器有一个实例」这种「框架约定」是两回事，写文档时别混。

## 症状 → 先看哪

| 你看到的 | 先看哪 | 判据 |
| --- | --- | --- |
| 一个接口只有一个实现 | 别的模块 `import` 过它吗？测试里有替身吗？ | 有一条成立，它是通道或接缝，不是多余 |
| 一个 `*Factory` 类里没有任何分支 | 它在选实现、读配置，还是只 `new` 了一下？ | 只是 `new`，那一层类没有选的责任 |
| `getInstance()` 或 Spring 单例旁边有可变字段 | 这个字段被谁写？跨请求写吗？ | 跨请求写，就是全局变量换了身衣服 |
| 事件只有一个监听者，还在同一个模块 | 依赖方向真的需要反过来吗？ | 不需要就直接调；事件换方向，不换并发 |
| 监听器上写 `@EventListener`，又要「跟事务一起成败」 | 发布点有事务吗？它要不要随事务回滚？ | `@EventListener` 不看事务；`@TransactionalEventListener` 默认 `AFTER_COMMIT`、无事务时默认不执行 |
| 一个 `*Manager` 只做一行转发 | 删掉它，编译和测试会报错吗？ | 删完都绿，它就是纯转发 |

## 动手：拿五个数去量自己的仓库

三步，半小时能做完：

1. 上面的脚本在仓库根目录跑一遍，得到五个数：接口数、单实现数、跨模块使用数、测试替身数、两者都没有的数量。只看最后一个。
2. 最后一个数下面的名单，先划掉两类：名字里带 `Port` / `Client` / `Gateway` / `Reader` / `Generator` / `Sink` 的（它们挡着外部系统），以及虽然只在模块内、但构造函数参数是个接口的（它已经在自己内部留了替换点）。
3. 剩下的逐个做「删掉试试」：把接口换成具体类，编译、跑受影响的那个测试文件。

第 3 步的信号很干净：跨模块的立刻编译失败（说明有使用方）；同模块有测试替身的也失败；**只有编译通过、测试通过、并且没有任何 `import` 变化的，才是真多余。** 删之前不用讨论设计原则，让它编译说话。

## 还差的

- `BEFORE_COMMIT` 里监听器抛异常时，事务最后的实际收场我没在本机验证。本机有 JDK 25.0.4，但跑通那条链路要有数据库和完整上下文；正文里依据的是 `UserDeletedEvent` 的注释与 Spring 的事务事件语义，不是实测。
- 那 13 个「没有第二个使用方」的接口，我只看类名和模块位置判断它们在挡外部系统，没逐个读实现核设计意图。`PostmortemKnowledge` 在 `paideia-ops`，我连它干什么都没看。
- 统计是文本匹配，`extends` 抽象类、`@Mapper` 代理、lambda 传给函数式接口都不计入；「命中 0 次」的 58 个里混着 mapper 与 `interface extends interface`，这个数只能当线索。
- 只数了 `backend/`。`frontend/` 里有没有同类的「只有一个实现的 hook 或组件抽象」，我没数。
- Python 三段只证明机制，不证明比例：我没统计过这种写法在真实项目里造成 bug 的频率，也不想编一个。真想有比例，得在自己仓库里按「改过之后出过问题的次数」去数，那是另一件事。
