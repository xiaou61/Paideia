## 先把结论摆出来

你每天都在用设计模式，只是没认出来——因为它们被框架藏进了注解和配置里：

| 你以为在用的注解 | 背后的模式 |
| --- | --- |
| `@Autowired` | 工厂 + 依赖注入 |
| `@Service`（默认单例） | 单例 |
| `@Transactional`、`@Cacheable` | 代理 |
| `@EventListener` | 观察者 |
| `JdbcTemplate` | 模板方法 |
| `@Configuration` + `@Bean` | 工厂方法 |

**学模式的价值不在"写的时候套"，而在"读框架源码时能认出它在干什么"。**

## Spring 里的三个典型

### @Autowired 背后是工厂 + 依赖注入

容器启动时扫描所有被注解的类，把它们实例化成 Bean 注册到一张表里。注入时按类型（或名字）查表。

这就解释了两个常见问题：

- **为什么同一个接口有两个实现会报错**：按类型查到了两个，容器不知道该给哪个；
- **为什么加 `@Primary` 或 `@Qualifier` 能解决**：一个声明"默认选我"，一个声明"按名字选"。

### @Transactional 背后是代理

容器给你注入的对象不是原对象，而是一个代理。代理在调用前开启事务、调用后提交或回滚。

所以事务失效的原因几乎都能归到一句话：**调用没有经过代理**。

- `this.method()` 自调用 → 绕过代理；
- `private` / `final` 方法 → 代理拦不到；
- `new` 出来的对象 → 压根不在容器里；
- 异常被 catch 住了 → 代理看不到异常。

### @EventListener 背后是观察者

`ApplicationEventPublisher.publishEvent(...)` 会通知所有匹配的监听器。默认是**同步**执行——也就是说，它的语义更接近"挨个调用"，只是解耦了调用方与被调用方。

**要异步得自己加 `@Async`**，并且要配线程池。不配的话只是"看起来异步，实际还在同一个线程里排队"。

## 读框架源码时怎么认出模式

看到这几类特征，基本可以对上号：

| 你看到的东西 | 大概率是 |
| --- | --- |
| 一个接口 + 多个实现 + 一个按 key 取实现的地方 | 策略 / 工厂 |
| 调用前有 `before` / 调用后有 `after` 的包装类 | 代理 / 装饰器 |
| 抽象类里有 `final` 方法调 `abstract` 方法 | 模板方法 |
| `List<Listener>` 遍历调用 | 观察者 |
| 一个类里塞着 `static getInstance()` | 单例 |

**这个能力比会写模式更实用**——因为框架代码你改不了，但你必须知道它为什么这样表现。

## 面试问模式，真正在问什么

面试官问"你用过哪些设计模式"时，期待的不是名词列表，而是**你有没有主动做过结构决策**。

好的回答长这样：

> 我们的消息推送一开始是 if/else 按渠道分派，加到第六种渠道时那个方法已经两百行，而且每加一种都要回归测试所有渠道。后来改成每个渠道一个实现类，注册到 Map 里，新增渠道只加一个类加一行注册，老代码完全不动。

这段话里有：**具体的痛点、具体的改动、可衡量的收益**。比背十遍定义有用。

差的回答是"策略模式就是定义一系列算法，让它们可以互相替换"——这是维基百科，不是你。

## 一个反过来的判断

下次你想引入一个模式时，先问三个问题：

1. **现在有几处需要它？** 只有一处 → 等第二处出现；
2. **不加会怎样？** 只是"看着不够优雅" → 不加；
3. **加了之后，改一个需求要动几个文件？** 变多了 → 这个抽象可能错了。

**模式是给"已经痛的地方"止痛，不是给"可能会痛的地方"打麻药。**

## 常见误区

### 误区：用了 Spring 就不需要懂设计模式

**你以为**：框架都封装好了，直接用注解就行。
**其实**：框架本身就是模式的集合。不理解代理，就永远解释不了事务为什么失效；不理解工厂，就解释不了 bean 冲突。
**怎么验证**：随便挑一个你项目里的"注解不生效"问题，看能不能把它归到某个模式的行为上。

### 误区：框架里的模式都值得模仿

**你以为**：Spring 怎么写我就怎么写。
**其实**：框架要适配"所有人的所有场景"，所以抽象层级特别高。业务代码照搬会得到一个更复杂、更难维护的版本。
**怎么验证**：看你项目里有没有"为了模仿框架"而写的一层 `xxxManager` + `xxxFactory` + `xxxProvider`，最后只被调用一次。

### 误区：设计模式是为了让代码更短

**你以为**：模式能减少代码量。
**其实**：模式通常**增加**代码量（多了接口、实现类、注册表），换来的是"改动点集中"。如果你们的代码很少改，模式就是纯成本。
**怎么验证**：统计一个文件目录下新增需求时的改动分布。改动集中在一两个文件里，说明抽象是对的。
