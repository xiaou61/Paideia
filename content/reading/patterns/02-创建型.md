## 先把结论摆出来

创建型模式解决的都是同一个问题：**对象怎么造出来，才能不让调用方知道细节。**

| 模式 | 一句话 | 什么时候用 |
| --- | --- | --- |
| 工厂 | 把"选哪个实现"从调用方挪走 | 构造逻辑复杂、或要按条件选实现 |
| 单例 | 全局只有一个 | **Spring 里不用自己写** |
| 建造者 | 分步拼一个复杂对象 | 参数多、有可选参数、要可读 |

三者的共同点：**把 new 的那一行藏起来**。区别在于藏的是"选哪个""只能一个"还是"怎么拼"。

## 工厂：把选择挪走

最原始的样子：

```text
Payment p;
if (type.equals("alipay")) p = new AlipayPayment(cfg);
else if (type.equals("wechat")) p = new WechatPayment(cfg);
else throw new IllegalArgumentException(type);
```

问题不在于 if 本身，而在于**每个调用方都要重复这段**。工厂把这唯一的一处选择收拢：

```text
Payment p = paymentFactory.create(type);
```

关键是**只有一处需要知道有哪些实现**。加一种支付方式，只改工厂和新增实现类，调用方一行不动。

**不要为工厂而工厂**：如果只有一个实现、构造也简单，直接 `new` 反而更清楚。

## 单例：Spring 已经替你做完了

手写单例的经典版本：

```text
public class Config {
    private static volatile Config instance;
    public static Config getInstance() {
        if (instance == null) {
            synchronized (Config.class) {
                if (instance == null) instance = new Config();
            }
        }
        return instance;
    }
}
```

`volatile` + 双重检查是为了防止指令重排序——**这段代码写错的人比写对的多**。

而在 Spring 应用里，**这整件事是多余的**：

```text
@Service
public class ConfigService { ... }
```

容器保证这个 Bean 只有一个实例（`singleton` 是默认作用域），并且帮你处理了初始化顺序与线程安全。

**单例真正的坑不在"怎么实现"，而在"它有状态"**：单例 Bean 里放一个可变的成员变量，所有请求共享它，就会出现串数据。这是线上最常见的 Spring 事故之一。

## 建造者：参数太多时的解药

```text
// 反例：七个参数，调用处完全看不懂
new Request(url, "POST", true, 30, null, false, 1024);

// 建造者：每一项都可读
Request.builder()
    .url(url)
    .method("POST")
    .timeout(30)
    .build();
```

它解决的问题是**可读性**，不是功能。什么时候值得用：

- 参数超过 4 个，且其中多个是可选的；
- 有"必须成组设置"的参数（设了 A 就必须设 B）；
- 对象创建后不再修改（不可变对象）。

**反例**：3 个必填参数的简单对象上建造者，只会让调用代码更长。

## 三者的边界

一句话区分：

- **工厂**：`new 什么`由内部决定；
- **单例**：`new 几次`由内部限制；
- **建造者**：`怎么拼`由调用方分步决定。

它们可以组合（单例工厂、建造者造复杂对象），但组合越多，代码越难追。

## 一个真实的取舍

项目里要接三种文件存储：本地磁盘、S3、对象存储。三种实现都要读同一个配置。

```text
# 合适：
Storage storage = storageFactory.create(props.getType());
// 工厂内部根据配置选实现，业务代码只认 Storage 接口

# 过度：
StorageFactory factory = new StorageFactoryBuilder()
    .withRegistry(new StorageRegistry())
    .withResolver(new StorageTypeResolver())
    .build();
```

**判据**：工厂内部有多复杂不重要，重要的是**调用方是不是只需要一行**。如果调用方也要理解工厂的装配过程，那这层抽象没起作用。

## 常见误区

### 误区：单例一定线程安全

**你以为**：单例只有一个实例，所以不会有并发问题。
**其实**：单例只保证"实例唯一"，**不保证内部状态安全**。多个线程同时读写单例里的成员变量，问题照样出现。
**怎么验证**：在一个 `@Service` 里加一个 `int counter` 成员，每次请求 `counter++`，并发压测看结果是否小于请求数。

### 误区：建造者能解决所有参数多的问题

**你以为**：参数多就该上建造者。
**其实**：如果那些参数总是成组出现且必填，更好的做法是拆成两个对象，或者用一个参数对象。建造者只对"大量可选参数"最有效。
**怎么验证**：看你的 builder，如果 `build()` 时没有任何校验、所有字段都被调用方填满，那它只是一个更啰嗦的构造函数。

### 误区：工厂一定要用反射/配置驱动

**你以为**：工厂就得能从配置文件动态加载类。
**其实**：绝大多数工厂只是一个 `switch` 或 `map`。反射只在"实现由外部提供"时才需要，会带来启动期错误和调试困难。
**怎么验证**：看你的工厂是不是只是为了"看起来很灵活"而引入了类名字符串配置。
