## 先把结论摆出来

结构型模式都在解决"怎么在不改原对象的前提下加东西"。

| 模式 | 加什么 | 现实中的例子 |
| --- | --- | --- |
| 代理 | 在调用前后**插入逻辑**，接口不变 | Spring AOP、MyBatis Mapper、远程调用 |
| 装饰器 | **层层包**，每层加一点能力 | Java IO 的 `BufferedInputStream` |
| 适配器 | **转换成另一个接口** | 第三方 SDK 包装、旧系统对接 |

最容易混的是代理和装饰器：**代理控制"能不能调"，装饰器叠加"多做什么"**。代理通常只包一层，装饰器可以无损叠很多层。

## 代理：Spring AOP 的地基

代理的本质是：**调用方以为在调原对象，其实调的是一个中间人**，中间人决定要不要转给原对象、以及转之前之后做什么。

两种实现：

- **JDK 动态代理**：只能代理**接口**，用 `Proxy.newProxyInstance` 生成一个实现同接口的类；
- **CGLIB**：生成目标类的**子类**，所以不能代理 `final` 类/方法。

Spring AOP 的选择规则：

- 目标类有接口 → 默认用 JDK 代理；
- 没有接口 → 用 CGLIB；
- `proxyTargetClass=true` → 强制 CGLIB。

**这直接解释了一个高频事故**：一个 `@Service` 类实现了接口，调用方注入的是接口类型，此时用 JDK 代理——**类上直接标注解（比如 `@Transactional`）可能不生效**，因为代理只认接口方法。改成 CGLIB 或在接口上标注解才行。

代理带来的另一个经典问题：**同类内部调用不经过代理**。

```text
@Service
public class OrderService {
    public void outer() { this.inner(); }   // this 是原对象，不是代理

    @Transactional
    public void inner() { ... }              // 事务不会开启
}
```

`this.inner()` 走的是原对象，代理那一层被完全绕过。这就是"加了 `@Transactional` 却没回滚"最常见的成因。

## 装饰器：可以层层累加

Java IO 是教科书级例子：

```text
InputStream in = new BufferedInputStream(
                    new FileInputStream("a.txt"));
```

`FileInputStream` 负责"读字节"，`BufferedInputStream` 负责"加缓冲"。两者都实现 `InputStream`，所以能互相套。

关键点：**装饰器和被装饰对象实现同一个接口**，所以套多少层，调用方都只看到一个 `InputStream`。

什么时候该用装饰器而不是代理：

- 能力是**可叠加**的（缓冲 + 加密 + 校验）；
- 每个叠加都是**独立的、可选的**；
- 不想为每种组合都造一个类（3 种能力 → 8 种组合）。

**代价**：调用栈变深，异常栈里会出现一长串 `...$Decorator`，排查时要往下翻。

## 适配器：让不兼容的接口能一起工作

场景：系统统一用 `Storage` 接口，但要用一个第三方 SDK，它的方法是 `putObject(bucket, key, bytes)`。

```text
class S3StorageAdapter implements Storage {
    private final S3Client sdk;
    public void save(String path, byte[] data) {
        sdk.putObject(BUCKET, path, data);   // 翻译成 SDK 的调用
    }
}
```

适配器不改任何一方：SDK 不动，业务接口不动，中间加一层翻译。

**判断该不该有适配器**：看业务代码里有没有出现第三方的类型。有，就说明缺了这层——**业务不应该认识外部 SDK**，否则换 SDK 要改遍全项目。

## 三者的分界线

```text
代理：    调用方 → [代理] → 原对象        （接口不变，插入横切逻辑）
装饰器：  调用方 → [装饰] → [装饰] → 原对象 （接口不变，能力叠加）
适配器：  调用方 → [适配器] → 第三方       （接口改变，做翻译）
```

一个实用判断：

- **要不要拦/控制** → 代理；
- **要不要叠加可选能力** → 装饰器；
- **要不要翻译一个不同形状的接口** → 适配器。

## 常见误区

### 误区：加了 @Transactional 就一定会有事务

**你以为**：注解加上就生效。
**其实**：注解要被代理拦截才生效。自调用、private 方法、final 类、没被容器管理的对象上，都不会有事务。
**怎么验证**：在事务方法里打日志看是否拿到同一个连接；或用 `TransactionSynchronizationManager.isActualTransactionActive()`。

### 误区：装饰器套得越多越灵活

**你以为**：多层装饰是良好设计。
**其实**：每层都增加调用开销与排查难度。如果这些能力总是同时出现，直接写在一个类里更清楚。
**怎么验证**：看异常栈——出现五六层 `$Decorator` 时，问问这些能力是否真的需要独立可选。

### 误区：适配器只是"多写一层没用的包装"

**你以为**：直接在业务里调 SDK 更省事。
**其实**：适配器的价值是**把外部依赖限制在一个文件里**。没有它，SDK 升级、换供应商、写单元测试都要动业务代码。
**怎么验证**：搜索业务包里有没有出现第三方 SDK 的 import。有就是缺适配器。
