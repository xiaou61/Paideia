## 这条线是干什么的

设计模式最大的问题是它被教成了一门**背诵课**：23 个名字、每个配一个 UML 图、考试默写。结果就是——能背出"策略模式是定义一系列算法并让它们可互相替换"，但真到代码里，看不出来自己写的那个 `if/else` 其实是策略模式该解决的问题。

这条线反过来：**从你写过的代码出发，认出现成的模式，再讲它为什么有用、什么时候是过度设计。**

一个前提：设计模式不是目标，是结果。**先有重复和变化点，才需要模式。** 上来就套模式，通常得到的是更难改的代码。

## 五篇的走法

1. **什么时候才需要模式**：变化点、重复、依赖方向——三个判据；以及过度设计的四个信号；
2. **创建型**：工厂、单例、建造者。重点讲单例在 Spring 里为什么几乎不用自己写；
3. **结构型**：代理、装饰器、适配器。**代理是 Spring AOP 的地基**，装饰器是 Java IO 的地基；
4. **行为型**：策略、模板方法、观察者。这三个是业务代码里出现频率最高的；
5. **模式与框架**：Spring 里那些"看不见的模式"，以及为什么面试问模式其实在问设计能力。

## 一个前提

这条线假设你写过面向对象的业务代码，Java/Python 都行。不要求背 UML，也不要求记住每个模式的定义式描述。

**读的时候对照自己的代码**：找一个超过 200 行、里面全是 `if (type == ...)` 的方法，读完第四篇回来看它。

## 常见误区

### 误区：设计模式是必须用的最佳实践

**你以为**：用了模式代码质量就高。
**其实**：模式是为"已经出现的变化"准备的。没有第二个实现时引入接口，只会多一层跳转。**代码里最贵的不是重复，是错误的抽象。**
**怎么验证**：数一下你的接口有几个实现。只有一个且短期不会有的，那个接口大概率是白加的。

### 误区：面试问设计模式是在考记忆力

**你以为**：背熟 23 个定义就能过。
**其实**：面试官在问"你怎么组织代码"。说得出"这里我用了策略模式，因为支付方式会不断增加，新增一种不该改旧代码"，比背定义有用得多。
**怎么验证**：翻自己的项目，找一个你主动做的结构决策，说清它挡掉了什么未来的改动。

### 误区：单例模式要自己写

**你以为**：需要单例就得写 `getInstance()` 加双重检查锁。
**其实**：Spring 的 Bean 默认就是单例，由容器保证。自己写单例常带来测试困难和初始化顺序问题。
**怎么验证**：在你的 Spring 项目里 `@Autowired` 两次同一个 `@Service`，打印对象哈希——是同一个。
