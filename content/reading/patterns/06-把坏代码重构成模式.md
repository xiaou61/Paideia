## 先把结论摆出来

**模式是重构的结果，不是设计的起点。**

上一篇讲"什么时候才需要模式"，这一篇给三个具体案例：从一段能跑但会越改越痛的代码，一步步走到一个合适的结构。每个案例都会标出：

- 改之前的代码长什么样；
- 触发重构的信号是什么；
- 改之后多了什么、少了什么；
- 什么时候**不该**这么改。

重构的前提是**行为不变**。先有测试（哪怕是几个手工验证的用例），再动结构；否则你是在改需求，不是在重构。

## 案例一：支付方式的 if/else

### 改之前

```java
public PayResult pay(String type, BigDecimal amount) {
    if ("alipay".equals(type)) {
        return alipayClient.pay(amount);
    } else if ("wechat".equals(type)) {
        return wechatClient.pay(amount);
    } else if ("balance".equals(type)) {
        return balanceService.pay(amount);
    }
    throw new IllegalArgumentException("unknown type: " + type);
}
```

### 信号

- 这已经是第三个分支；
- 产品说下个月接第四个渠道；
- 每个分支里还在长自己的校验与重试逻辑。

**变化已经发生，而且在继续增长**——这是引入策略模式的充分条件。

### 改之后

```java
public interface PayChannel {
    String type();
    PayResult pay(PayRequest request);
}

@Component
public class AlipayChannel implements PayChannel {
    public String type() { return "alipay"; }
    public PayResult pay(PayRequest request) { ... }
}

@Service
public class PayService {
    private final Map<String, PayChannel> channels;

    public PayService(List<PayChannel> channels) {
        this.channels = channels.stream()
                .collect(Collectors.toMap(PayChannel::type, Function.identity()));
    }

    public PayResult pay(String type, PayRequest request) {
        PayChannel channel = channels.get(type);
        if (channel == null) {
            throw new IllegalArgumentException("unknown type: " + type);
        }
        return channel.pay(request);
    }
}
```

Spring 会把所有 `PayChannel` 实现注入到 `List` 里，新增渠道只需要加一个 `@Component`，**不用改 `PayService`**。

### 多了什么、少了什么

| | 改之前 | 改之后 |
| --- | --- | --- |
| 新增渠道 | 改 `PayService` 的 if | 新增一个类 |
| 每个渠道的逻辑 | 挤在一个方法里 | 各自独立、可单测 |
| 文件数 | 1 | N+2 |
| 对"只有两种、永远不变"的场景 | 更简单 | 过度设计 |

**最后一行很重要**：如果只有两种支付方式、且业务上明确不会增加，原来的 if/else 更好。模式不是免费的。

## 案例二：参数越来越多的构造器

### 改之前

```java
Order order = new Order(
    userId, items, couponId, null, false, true, "CNY", 30, "备注"
);
```

九个参数，其中两个 `null`、两个布尔。调用方根本记不住顺序。

### 信号

- 构造器参数超过 4–5 个；
- 出现连续同类型参数（两个 `boolean`、两个 `String`），传错顺序编译器不报错；
- 调用处大量 `null` / 默认值。

### 改之后

```java
Order order = Order.builder()
        .userId(userId)
        .items(items)
        .couponId(couponId)
        .currency("CNY")
        .timeoutMinutes(30)
        .remark("备注")
        .build();
```

建造者模式在这里的价值不是"设计模式"，而是**让每个参数有名字、让可选参数可以省略**。

如果参数本身能归成几组（收货信息、优惠信息、支付信息），更好的做法是先抽**参数对象**：

```java
public record OrderCreateCommand(
        long userId,
        List<OrderItem> items,
        CouponSelection coupon,
        ShippingAddress address
) {}
```

**先考虑参数对象，再考虑 Builder**。参数对象表达"这些值属于同一个概念"，Builder 只解决"参数多"。

## 案例三：层层嵌套的审批规则

### 改之前

```java
public ApprovalResult approve(Order order) {
    if (order.amount().compareTo(new BigDecimal("10000")) > 0) {
        if (!order.hasManagerApproval()) {
            return ApprovalResult.needManager();
        }
        if (order.isNewCustomer() && order.amount().compareTo(new BigDecimal("50000")) > 0) {
            return ApprovalResult.needRiskReview();
        }
    } else {
        if (order.isBlacklisted()) {
            return ApprovalResult.rejected();
        }
    }
    return ApprovalResult.approved();
}
```

规则还会继续加：大额、新客、黑名单、地区限制、促销叠加……

### 信号

- 嵌套层级超过三层；
- 每条规则都有自己的"通过 / 拒绝 / 转人工"结果；
- 新规则加进来时，很容易漏掉前面的组合条件。

### 改之后：责任链

```java
public interface ApprovalRule {
    /** 返回 null 表示放行，交给下一条。 */
    ApprovalResult check(Order order);
}

@Component
@Order(1)
public class BlacklistRule implements ApprovalRule { ... }

@Component
@Order(2)
public class AmountRule implements ApprovalRule { ... }

@Service
public class ApprovalService {
    private final List<ApprovalRule> rules;

    public ApprovalService(List<ApprovalRule> rules) {
        this.rules = rules;
    }

    public ApprovalResult approve(Order order) {
        for (ApprovalRule rule : rules) {
            ApprovalResult result = rule.check(order);
            if (result != null) {
                return result;
            }
        }
        return ApprovalResult.approved();
    }
}
```

每条规则独立、可单测、可排序。新增规则只需要加一个类并标 `@Order`。

### 代价

- 规则之间的顺序变成了隐式契约（靠 `@Order`），要写清楚为什么这个顺序；
- 规则多了之后，"哪些情况会走到哪"不再一眼可见，需要日志或测试兜底；
- 简单的两三条规则用责任链反而绕。

## 重构的纪律

1. **先写测试**：至少覆盖现有分支的输入输出；
2. **小步走**：一次只抽一个渠道/一条规则，跑测试，再继续；
3. **不改行为**：重构提交里不夹带需求变更；
4. **允许回退**：如果抽出来发现调用方反而更复杂，就退回去——这说明变化点还没看清；
5. **命名诚实**：`PayChannel` 比 `PayStrategyFactoryImpl` 更容易读。

## 常见误区

### 误区：重构就是重写

**你以为**：要改结构，就得把这块代码推倒重来。
**其实**：重构是**保持行为不变**的小步结构改进。一次抽一个分支、跑一次测试，出问题能立刻定位；推倒重写则同时改变了结构与行为，出错时无法判断是哪一步导致的。
**怎么验证**：看重构提交里有没有夹带"顺手改了个需求"——有就说明它已经不是重构。

### 误区：先设计好模式，代码自然就好维护

**你以为**：一开始就把策略、工厂、责任链都摆好，以后省事。
**其实**：第一次出现时抽象出来的形状，往往和第二次、第三次出现时需要的形状不一样。过早抽象会让你在错误的边界上维护很久。
**怎么验证**：回看半年前"为将来扩展"预留的接口，数一下真正被第二个实现用上的有几个。

### 误区：用了模式就不用写测试

**你以为**：结构清晰了，正确性自然有保障。
**其实**：模式只改变代码组织方式，不改变业务规则。责任链的顺序、策略的选择条件，都需要测试固定下来。
**怎么验证**：给每条规则写一个"命中 / 放行"的用例；重构前后跑同一批用例，结果必须一致。

## 小结

三个案例的共同点：**先观察到重复与增长，再动手抽**。策略解决"选择在增长"，建造者/参数对象解决"参数在增长"，责任链解决"规则在增长"。重构的边界是行为不变；模式的代价是多文件、多一层间接和隐式顺序，只有在变化真的发生时，这笔账才算得过来。
