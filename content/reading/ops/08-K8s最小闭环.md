# K8s 最小闭环：部署、暴露与回滚

## apply 之后 Pod 一直 0/1

第一次把一个 Spring Boot 应用放上集群，`kubectl apply -f app.yaml` 看着是成功的：

```text
deployment.apps/app created
service/app created
```

然后 `kubectl get pods`：

```text
NAME                   READY   STATUS              RESTARTS   AGE
app-7d9f4c8b5-x2vqn    0/1     CreateContainerConfigError   0      12s
app-7d9f4c8b5-h8ktz    0/1     CreateContainerConfigError   0      12s
```

`CreateContainerConfigError` 这个状态名没告诉你任何事。`describe` 往最后翻：

```text
Events:
  Type     Reason     Age   From               Message
  ----     ------     ----  ----               -------
  Warning  Failed     8s    kubelet            Error: secret "app-secret" not found
```

我的 YAML 里写了 `envFrom: secretRef: app-secret`，但我从来没建过这个 Secret——**在 Compose 里用 `env_file: .env` 是文件，在 K8s 里是一个必须先存在的对象**。

这篇按"部署 → 暴露 → 回滚"把闭环跑通，也把这类"看起来 apply 成功了、其实卡在别处"的形态一个个记下来。

## 先对齐几个词

- **Pod**：最小运行单位，通常一个容器。它的 IP 会变，不要依赖。
- **Deployment**：管"跑几个 Pod、用哪个镜像、怎么滚动更新"的声明。
- **Service**：给一组 Pod 一个固定的名字与虚拟 IP，只把**就绪**的 Pod 放进端点名单。
- **Ingress**：对外入口，管域名与路径怎么转到哪个 Service。

## 一个请求进来，先碰到谁

```text
客户端 → Ingress / LoadBalancer → Service（虚拟 IP）→ kube-proxy 转发 → 某个就绪的 Pod
```

顺序要记住，因为最常见的误判就是把它搞反：**不是 Service 指向 Ingress，而是 Ingress 把流量交给 Service，Service 再挑一个 Ready 的 Pod。**

看懂这条链，就明白"Pod 起来了但用户还是 502"是怎么回事——它没进 Service 的端点名单。查这个只需要一条命令：

```text
$ kubectl get endpoints app
NAME   ENDPOINTS   AGE
app    <none>      2m
```

`<none>` 就是"没有 Ready 的 Pod"。Service 存在、Pod 存在，但中间那条线是断的。

## 两个资源：Deployment 与 Service

```yaml
# app.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 2
  selector:
    matchLabels: { app: app }
  template:
    metadata:
      labels: { app: app }
    spec:
      containers:
        - name: app
          image: registry.example.com/app:1.0.0
          ports:
            - containerPort: 8080
          envFrom:
            - secretRef:
                name: app-secret          # ← 这个对象必须先存在
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            initialDelaySeconds: 30
          resources:
            requests: { cpu: "250m", memory: "512Mi" }
            limits:   { cpu: "1",    memory: "1Gi" }
---
apiVersion: v1
kind: Service
metadata:
  name: app
spec:
  selector: { app: app }
  ports:
    - port: 80
      targetPort: 8080
```

三处容易出事的地方，注释里只标了一处，另外两处在这里：

**一、`secretRef` 指向的对象必须已存在。** 建它是一条命令：

```text
$ kubectl create secret generic app-secret --from-literal=DB_PASSWORD=xxx
```

顺序反了就是开头那个 `CreateContainerConfigError`。注意 `kubectl apply -f` 不会替你检查被引用的对象在不在——它只管这个 YAML 本身的语法与字段。

**二、`image` 用 tag，但生产建议用 digest。** 上面写 `app:1.0.0` 是为了好读；如果用 digest，格式是 `app@sha256:<64 位十六进制>`。写 `@sha256:...` 或 `@sha256:abc123` 都会被 API server 拒绝，报 `invalid reference format`——它不是语法错误提示，是镜像引用格式校验失败。

**三、readiness 探针的路径可能根本不存在。** Spring Boot 的 `/actuator/health/readiness` 端点只在"检测到运行在 K8s 里"时默认开启。本地 `docker run` 或 Compose 里访问它会是 404，于是你在本地怎么试都正常，上集群就变成永远 0/1。手动开启要加：

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
```

`initialDelaySeconds: 30` 那个数字也别照抄。Spring Boot 冷启动 20~40 秒很常见，liveness 探针 5 秒就开始探、失败 3 次就重启，结果是"起来就被杀"的死循环。**保险做法是 liveness 的 `initialDelaySeconds` 给到实测启动时间的 1.5 倍**，并用 `startupProbe` 更精确地表达"启动期别探我"。

## 八个命令

```text
$ kubectl apply -f app.yaml                                  # 1. 部署（声明式，幂等）
$ kubectl get pods -o wide                                   # 2. 看 Pod 在哪个节点、什么状态
$ kubectl describe pod app-xxx                               # 3. 排障第一命令（事件在最后）
$ kubectl logs -f app-xxx --previous                         # 4. 日志（--previous 看崩溃前那个容器）
$ kubectl exec -it app-xxx -- sh                             # 5. 进容器
$ kubectl rollout status deploy/app                          # 6. 等滚动更新完成
$ kubectl rollout undo deploy/app                            # 7. 回滚到上一个 revision
$ kubectl get endpoints app                                  # 8. 服务有没有可用后端
```

我原来把第 8 条写成 `kubectl get events`。events 当然要看，但**它的信息密度太低**（整个集群搅在一起、默认只保留一小时），而且真正卡住的时候你需要的是"这个 Service 现在有没有后端"这一个事实。`get endpoints` 给的就是它。

看 events 的正确姿势是带过滤器：

```text
$ kubectl get events --field-selector involvedObject.name=app-7d9f4c8b5-x2vqn --sort-by=.lastTimestamp
```

`rollout undo` 是 K8s 相对单机部署的硬优势：**回滚是一条命令**，而且历史保留（`--to-revision=3` 能回到更早）。单机部署回滚 = 手动改回上一个镜像 tag + 重启，中间还有个"改错了怎么办"的空窗。

## 滚动更新为什么不中断

```text
$ kubectl rollout status deploy/app
Waiting for deployment "app" rollout to finish: 1 out of 2 new replicas have been updated...
```

默认策略是滚动：**起一个新 Pod → readiness 通过 → 摘一个旧的**。

所以不中断的前提不是"配了 rollingUpdate"，而是 **readiness 真的能判断"这个 Pod 能不能服务"**。探针写错（路径 404、或者只查 `/actuator/health` 而它永远 200），K8s 会在应用还没连上数据库时就把流量导过来——用户看到 502，而 `get pods` 全是 `1/1 Running`。

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1           # 允许多起 1 个
    maxUnavailable: 0     # 不允许先少一个（保证容量）
```

`maxUnavailable: 0` 是"零中断"的关键：它禁止"先干掉旧的再加新的"。代价是发布期间需要额外的节点资源（`maxSurge: 1` 就是那份额外资源）。

## 配置与密钥

```text
$ kubectl create configmap app-config --from-env-file=app.env
$ kubectl create secret generic app-secret --from-literal=DB_PASSWORD=xxx
```

三条纪律：

- **不要把 Secret 提交进 git。** 想生成模板看看长什么样，用 `kubectl create secret ... --dry-run=client -o yaml`——注意是 `--dry-run=client`，kubectl 1.18 之后 `--dry-run` 不带值会报错。
- **Secret 只是 base64。** 能 `kubectl get secret -o yaml` 的人就能看到明文（`echo xxx | base64 -d`）。真正的保护来自 RBAC、etcd 加密、外部密钥管理（Vault / KMS）。
- **`create` 出来的对象不受 `apply` 管。** 我这套命令混用了 `create`（命令式）和 `apply`（声明式），实践中最好统一：Secret 用 `apply -f`（值从 `secrets/` 这类被 gitignore 的目录来），或者干脆用 External Secrets Operator 从密钥服务拉。

## 动手

没有集群的话用 `kind` 本地起一个（只要本机有 Docker）：

```text
$ kind create cluster --name demo

# 先故意制造开头那个错误：不建 Secret 直接 apply
$ kubectl apply -f app.yaml
$ kubectl get pods
# 期望看到 0/1 CreateContainerConfigError
$ kubectl describe pod <pod> | tail -5
# 期望看到 Error: secret "app-secret" not found
```

修好之后再走完整闭环：

```text
$ kubectl create secret generic app-secret --from-literal=DB_PASSWORD=dev-only
$ kubectl apply -f app.yaml
$ kubectl rollout status deploy/app
$ kubectl get pods -o wide
$ kubectl get endpoints app            # 这里必须能看到两个 IP

# 改镜像版本，观察滚动；然后回滚
$ kubectl set image deploy/app app=registry.example.com/app:1.0.1
$ kubectl rollout status deploy/app
$ kubectl rollout undo deploy/app && kubectl rollout status deploy/app

$ kubectl port-forward svc/app 8080:80    # 本地验证，不用 Ingress
$ kind delete cluster --name demo
```

`port-forward` 是这套流程里最省事的一步：它绕开 Ingress，直接把你本机的 8080 接到 Service 上。**先用它确认"服务本身是通的"，再去查 Ingress**——否则你会花很多时间在 Ingress Controller 的日志里找一个根本不在那里的问题。

## 三件我原来写错或写漏的事

**一、`kubectl get events` 是我最常给人推荐的排障命令。** 其实它信息密度很低。真正的第一站是 `describe`（末尾的 Events 只针对这个对象）和 `get endpoints`（服务有没有后端）。

**二、"两个资源就够了"。** 最小闭环确实是 Deployment + Service，但只要用了 `secretRef`，Secret 就是第三个必须存在的对象——而这正是新手第一次 `apply` 踩的坑。

**三、`--dry-run -o yaml`。** kubectl 1.18 之后要写 `--dry-run=client`，不带值的写法在部分版本上直接报错。

反过来，真正值得一开始就配的是这三样：`requests`（调度依据）、`readinessProbe` 指向真实就绪端点、`livenessProbe.initialDelaySeconds` 给足冷启动时间。这三样写错，比不会写 YAML 更容易出事故。

## 这一课之后

最小闭环是两个资源加八个命令：Deployment 管副本与更新，Service 管稳定入口；命令是 apply / get pods / describe / logs / exec / rollout status / rollout undo / get endpoints。

滚动更新不中断靠 readiness，回滚是一条命令——这两点是 K8s 相对单机部署的真正优势。Secret 不是加密，别进 git；被引用的对象（Secret、ConfigMap）必须先存在。
