## 一个「校验通过」的坏备份

我做过一次验证：把一份 62030 字节的 SQL 砍掉一半，重新 gzip，然后跑校验。

```text
$ head -c 30000 full.sql | gzip > cut.sql.gz
$ gunzip -t cut.sql.gz && echo "cut.gz: gunzip -t 通过"
cut.gz: gunzip -t 通过

$ gunzip -c cut.sql.gz | tail -1
INSERT INTO orders VALUE
```

`gunzip -t` 通过了，最后一句话停在 `INSERT INTO orders VALUE`——一个永远无法执行的半截语句。

`gunzip -t` 证明的是「gzip 的 CRC 没错」，不是「里面的 SQL 完整」。只要写 gz 的那个进程是正常收尾的，即使它只拿到了一半输入，出来的 gz 也完全合法。

这解释了一件很多人想不通的事：**备份文件在、大小正常、解压不报错、恢复却少了一半数据**。

## 让管道吐出假成功

备份脚本最常见的形状是 `mysqldump ... | gzip > out.gz`。这条命令的退出码，是**管道最后一条命令**的退出码，也就是 gzip 的。

```text
$ set +o pipefail; ( false | gzip > p1.gz ); echo "没有 pipefail 时管道退出码: $?"
没有 pipefail 时管道退出码: 0

$ set -o pipefail; ( false | gzip > p2.gz ); echo "有 pipefail 时管道退出码: $?"
有 pipefail 时管道退出码: 1
```

`false` 代表 mysqldump 失败（密码错、库不存在、连接被掐）。没有 `pipefail` 时整条管道返回 0，cron 认为备份成功，监控上没有一条红。

`set -o pipefail` 是这个脚本的生命线，但它只解决「命令失败了没人知道」，解决不了「文件坏了没人知道」。

## 所以验证只能靠真恢复

RPO、RTO、验证——三个问题里最容易跳过的是第三个，因为它要花时间，而且不产出任何功能。

| 问题 | 含义 | 一个具体的答案 |
| --- | --- | --- |
| RPO | 最多能丢多少数据 | 全量每天 03:15 一次，binlog 归档 → 最多丢几分钟 |
| RTO | 多久必须恢复 | 小服务 1 小时；核心链路 15 分钟 |
| 验证 | 怎么证明可用 | 每季度真恢复到临时实例，比对行数与最新时间戳 |

只答前两个，就会出现「备份一直在跑、从来没人恢复过」。这不是概率问题，是时间问题。

## 恢复演练：四个必须踩到的坑

```bash
# 1. 临时实例：只绑本机回环，别用弱密码
docker run -d --name restore-test --rm \
  -e MYSQL_ROOT_PASSWORD="$(openssl rand -hex 12)" \
  -p 127.0.0.1:3307:3306 mysql:8

# 2. 等它真的能连，而不是 sleep 20
until docker exec restore-test mysqladmin ping -uroot -p"$PASS" --silent; do sleep 1; done

# 3. 先建库再恢复
mysql -h127.0.0.1 -P3307 -uroot -p"$PASS" -e "CREATE DATABASE paideia"

# 4. 恢复并校验
gunzip -c /backup/paideia-2026-11-19T031500.sql.gz | mysql -h127.0.0.1 -P3307 -uroot -p"$PASS" paideia
mysql -h127.0.0.1 -P3307 -uroot -p"$PASS" -e \
  "SELECT COUNT(*) FROM paideia.knowledge_entries; SELECT MAX(created_at) FROM paideia.knowledge_entries;"
```

第三行是新手最常漏的一步。`mysqldump paideia`（不带 `--databases`）导出的文件里**没有** `CREATE DATABASE` 和 `USE`，所以恢复到空实例时第一条命令就死：

```text
ERROR 1049 (42000): Unknown database 'paideia'
```

两个改法，选一个并固定下来：dump 时加 `--databases paideia`（文件自带建库语句），或者恢复前手动 `CREATE DATABASE`。前者的好处是脚本和演练用同一份命令，少一个能对不上的地方。

`-p 127.0.0.1:3307:3306` 这个前缀也不能省。`-p 3307:3306` 在 Linux 上绑的是 `0.0.0.0`，一台公网服务器上，恢复期间任何人都能连上你的生产数据副本。

校验那步的关键是**同时看行数和最新时间戳**。只 count 行数，会漏掉「昨天的数据没进去、总量看起来差不多」这种。

## 备份脚本：把每一步都做成不会静默失败

```bash
#!/usr/bin/env bash
set -euo pipefail

BACKUP_DIR=/backup
TS=$(date +%Y-%m-%dT%H%M%S)
OUT="$BACKUP_DIR/paideia-$TS.sql.gz"
PART="$OUT.partial"

# 两轮备份不许同时跑
exec 9>"$BACKUP_DIR/.lock"
flock -n 9 || { echo "上一轮备份还在跑"; exit 1; }

# 凭据放文件，不要写在命令行里（ps 能看见）
CNF=/etc/paideia-backup/client.cnf      # 权限 0600，内容见下
trap 'rm -f "$PART"' EXIT

if ! mysqldump --defaults-extra-file="$CNF" \
      --single-transaction --quick \
      --routines --events --triggers \
      --databases paideia | gzip > "$PART"; then
  echo "mysqldump 失败，保留现场不产生正式文件" >&2
  exit 1
fi

# 只有到这里才改名，之前任何一步失败都不会留下"看起来正常"的文件
[ -s "$PART" ] || { echo "备份为空" >&2; exit 1; }
gunzip -t "$PART" || { echo "gzip 校验失败" >&2; exit 1; }
mv "$PART" "$OUT"
rsync -a "$OUT" backup-host:/srv/paideia-backup/
```

`/etc/paideia-backup/client.cnf`：

```text
[client]
user=backup
password=从密钥管理取，不写进仓库
```

四处容易写错的细节：

- **文件名的粒度**。`$(date +%F)` 只能到天，同一天跑第二次会 `>` 截断第一次的备份——如果第二次正好是坏的，当天唯一的好备份就没了。精确到秒，或者干脆用校验和命名。
- **先写 `.partial` 再 `mv`**。`mv` 在同一个文件系统内是原子的，监控和 rsync 永远不会看到半成品。
- **`trap ... EXIT` 清现场**。脚本被 `kill`、磁盘满、连接超时，都会留下那个 `.partial`，要清掉。
- **`flock` 防重入**。定时任务和手动执行撞在一起时，两个进程写同一个文件是经典的「备份看起来有、恢复出来是乱的」。

大小断言只能当粗筛。`[ $(stat -c%s "$OUT") -gt 100000 ]` 挡得住「4 KB 的空壳」，挡不住上面那个 30000 字节的截断文件。

## binlog：不做就别承诺「恢复到误删前一刻」

`mysqldump` 备份的是**某一时刻的快照**，它不包含快照之后的变更。想恢复到误删前一刻，必须有 binlog，而且要做三件事：

1. dump 时记录起点：`--source-data=2`（旧版叫 `--master-data`），文件里会写一行 `CHANGE MASTER TO ... MASTER_LOG_FILE='mysql-bin.000123', MASTER_LOG_POS=4567;`
2. 把 binlog 文件本身归档到备份存储（`mysqlbinlog --read-from-remote-server` 或直接同步 binlog 目录），保留时间要覆盖 RPO
3. 演练时真的重放一次：`mysqlbinlog --start-position=4567 --stop-datetime="..." mysql-bin.000123 | mysql paideia`

只做了 1 没做 2，等于记了个打不开的坐标。只做全量备份，能承诺的只有「恢复到备份时刻」，不是「恢复到误删前一刻」。

## 物理备份不能靠 cp

「直接拷数据文件」不是一致性备份。InnoDB 在跑的时候，数据文件和 redo log 处于不同步的状态，`cp -r` 拿到的可能是需要崩溃恢复、甚至恢复不出来的副本。

要么用 `xtrabackup`（备份 + `--prepare` 两步，`--prepare` 不能省），要么用文件系统/云盘的一致性快照。这两个方案的共同点是**有工具保证一致性**，「快」不是它们唯一的好处。

## 主从不是备份

从库是最容易让人放松警惕的东西。主从复制同步的是**语句/行变更**，包括错误：

- `DELETE FROM orders` 会在几十毫秒内复制到从库，从库干净地一起删
- 错误的迁移 `ALTER TABLE ... DROP COLUMN` 一样会复制过去
- 从库早就 `Slave_SQL_Running: No` 了，只是没人看监控——这时它不是备份，是一个更旧的库

复制是**可用性**手段（主库挂了能切），备份是**可恢复性**手段（数据被改坏了能回到过去）。两者不能互相替代。

## 备份放哪、留多久

| 项 | 具体做法 |
| --- | --- |
| 位置 | 本机一份（快速恢复）+ 异地一份（防机器没了） |
| 上传 | `rclone sync /backup remote:paideia-backup`，或 `aws s3 cp --storage-class STANDARD_IA` |
| 加密 | 落盘前 `gpg --encrypt`，或在对象存储侧开 SSE |
| 保留 | 日备 7 天、周备 4 周、月备 6 个月——按 RPO 倒推，不是凭感觉 |
| 过期告警 | 最新备份超过 36 小时就报警。备份静默停止是最常见的故障 |

最后一行那个 36 小时比任何文档都重要。备份脚本停了两周、没人发现，是这类事故里最常见的形态；它不会报错，只会安静地不再产出文件。

## 动手

```text
# 完整演练一次，约 15 分钟
# 1. 找出最新一份（按时间排，不要按名字排）
ls -lt /backup/*.sql.gz | head -3

# 2. 只看最新一份是否完整
LATEST=$(ls -t /backup/*.sql.gz | head -1); gunzip -t "$LATEST" && echo "gz 完整"

# 3. 按上面四步恢复到临时实例，比对行数与最新时间戳
# 4. 记录这一次花了多久——那就是你的真实 RTO
```

第 4 步值得认真记。RTO 不是估出来的，是你恢复过一次、看过表知道的时间。

## 还差的

- **异地那份从没做过恢复演练**。我演练的都是本机那份，异地传输是否损坏、对象存储上的对象是否可读，没验证过。
- **binlog 归档只覆盖 3 天**，而日备保留 7 天——这意味着「前天下午的误删」在全量里找不到、在 binlog 里也没有。这个是参数不匹配，不是技术问题。
- **没做过磁盘写满的演练**。磁盘满时 `mysqldump | gzip` 的行为（gzip 报错、文件半截、`set -e` 退出）只在推演里成立，没实测。
