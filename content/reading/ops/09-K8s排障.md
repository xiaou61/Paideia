## 137 和一条空日志

`apply` 过了 08 那个闭环之后，`get pods` 稳定在这个形态：

```text
$ kubectl get pods
NAME                   READY   STATUS             RESTARTS        AGE
app-7d9f4c8b5-x2vqn    0/1     CrashLoopBackOff   4 (2m12s ago)   7m
```

（这段回显是标准形态：本机没有集群，没实跑。本文所有 kubectl 输出都是这样写出来的，最后一节会再交代一次。）

死因在 `describe` 的最后一段，不在日志里：

```text
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
```

我第一反应是去日志里找 `OutOfMemoryError`，翻了三遍都是空。错了两次：

- `137` 里的 `9` 是 SIGKILL（`128 + 9`，shell 的退出码约定）。进程被内核直接杀掉，`finally` 不会执行，一行 Java 栈也不会写；
- 空日志本身不是线索。SIGKILL 的空、启动失败的空、容器还没创建的空，三件事长得一模一样，要看的方向完全不同。

能提前算出来的是上限。08 那份 `app.yaml` 里 `limits: { memory: 1Gi }`，镜像的 `ENTRYPOINT` 带 `-XX:MaxRAMPercentage=70`（同一组参数在 `content/reading/docker/04-Dockerfile把构建写下来.md:89`；仓库自己的 systemd 部署也是这套，`content/reading/ops/03-systemd把jar变成服务.md:65` 配 `:73` 的 `MemoryMax=1G`）：

```text
1 GiB × 70%       = 716.8 MiB   堆上限
1 GiB − 716.8 MiB = 307.2 MiB   留给元空间、线程栈、直接内存、code cache、GC 结构
```

`OOMKilled` 只说明「这个容器的字节数到顶了」，不告诉你超的是堆还是堆外。上面两行算术是唯一能提前判断的部分，剩下的只能进容器量（NMT、`/proc/<pid>/smaps_rollup`）。

## 三步，每一步只回答一个问题

顺序不是习惯问题，是每一步的前提是上一步的结论：

| `get pods` 里的症状 | 第一步看哪 | 那一步为什么能定论 |
| --- | --- | --- |
| `Pending`，`AGE` 一直涨 | `describe pod` 末尾 Events 里的 `FailedScheduling` | 调度没通过，容器还没被创建——`logs` 必然是空的，不用试 |
| `ImagePullBackOff` / `ErrImagePull` | `describe` 的 Events，`Failed to pull image` 后面那截原文 | 区分三件事：名字或 tag 打错、私有仓库没凭据、仓库限流 |
| `CreateContainerConfigError` | `describe` 的 Events，`Error: secret ... not found` 这类 | 卡在容器创建之前，报的是被引用对象（Secret/ConfigMap），不是你的应用 |
| `CrashLoopBackOff`，`RESTARTS` 在涨 | `describe` 的 `Last State`：`Reason` 与 `Exit Code` | 先分清「自己退的」和「被杀的」；137 与退出码 1 的下一步完全不同 |
| `Running` 但 `READY 0/1` | `describe` 的 Events 里 `Readiness probe failed` 那一行 | 容器在跑，只是没进 Service 端点；这跟崩溃是两码事 |

`get pods` 只回答「它现在处在哪个阶段」：调度、拉镜像、建容器、跑起来、等就绪。`describe` 回答「kubelet 与 scheduler 留下了什么话」。`logs` 回答「进程自己说了什么」——只有确认进程真的跑起来过，第三步才可能有内容。

`Pending` 时硬看日志、`ImagePullBackOff` 时硬看日志，都是在向一个不存在的进程要输出。

### 同一条 `logs`，取决于你什么时候敲

`kubectl logs` 取的是**最近一次实例**的日志，`--previous` 往前退一个实例。哪个是「崩掉的那次」，要看 Pod 此刻在干什么：

- **back-off 等待期**（容器没在跑）：`logs` 就是崩掉那次，`--previous` 是再往前那次；
- **刚重启完的那几秒**（容器在跑）：`logs` 是新实例、可能还什么都没写，`--previous` 才是崩掉那次；
- **从没启动成功过**：`logs` 直接告诉你它在等，不是给你空输出——形如 `container "app" in pod "app-..." is waiting to start: CrashLoopBackOff`。

所以「日志是空的就加 `--previous`」这条经验，在第一种时点上是错的：你加了反而跳到更早的一次崩溃。先看 `describe` 的 `Last State` 和 `RESTARTS` 的时点，比背口诀有用。

## Events 默认只活一小时

`describe` 末尾那段 Events 是 kube-apiserver 存的事件对象，默认保留 1 小时，由 `--event-ttl` 控制。所以「昨天下午那次重启为什么」在事件里查不到；要么当时有告警，要么就得靠日志。

想让事件只属于一个对象，别在 `get events` 的全量输出里翻：

```text
$ kubectl get events --field-selector involvedObject.name=app-7d9f4c8b5-x2vqn \
    --sort-by=.lastTimestamp
```

（标准形态，未实跑。）

这里有个方向容易反：Events 写的是**编排侧对你的动作**——调度失败、拉镜像失败、探针失败、杀容器。应用自己的 `NullPointerException` 只会出现在 `logs` 里。反过来，Events 里没有记录，也不代表编排侧没动过手，只代表那一刻已经超过一小时。

## 探针的默认值，决定了它多快杀你

探针字段不写，不等于「不限制」。httpGet 探针的默认值是 `initialDelaySeconds=0`、`periodSeconds=10`、`timeoutSeconds=1`、`failureThreshold=3`、`successThreshold=1`（[Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)）。

拿 08 的 manifest 套一遍：liveness 只写了 `initialDelaySeconds: 30`，其余走默认。

```text
第 30s 第一次探测 → 失败（1/3）
第 40s 第二次     → 失败（2/3）
第 50s 第三次     → 失败（3/3）→ kubelet 杀容器
```

一个冷启动要 60 秒的 Spring Boot 就死在这一段里，然后 back-off、重启、再死一遍，`RESTARTS` 一路涨。

`startupProbe` 是给这件事准备的：它成功之前，liveness 与 readiness 都不执行，「启动期最长允许多久」变成 `failureThreshold × periodSeconds` 一个明确的数，而不是靠 `initialDelaySeconds` 猜一个值。

readiness 与 liveness 的差别要按机制说：readiness 失败只是把 Pod 从 Service 端点里摘掉，**不重启**；liveness 失败是 kubelet 杀容器，之后跑不跑由 Pod 的 `restartPolicy` 决定——Deployment 的 `restartPolicy` 恒为 `Always`，看起来才像「重启」。

所以 `READY 0/1` 有两种来源，得从 Events 分清：readiness 从来没通过过（路径 404、端口写错、依赖没连上），或者一度通过后来掉了。

## 1Gi 上限与 70% 堆：这台机器上能量出来的部分

JVM 到底怎么算堆，这一节是实测。本机没有容器，先看默认值：

```text
$ java -version
openjdk version "25.0.4" 2026-07-21 LTS
OpenJDK Runtime Environment Temurin-25.0.4+7 (build 25.0.4+7-LTS)
OpenJDK 64-Bit Server VM Temurin-25.0.4+7 (build 25.0.4+7-LTS, mixed mode, sharing)

$ java -XX:+PrintFlagsFinal -version | Select-String "MaxRAMPercentage|MaxHeapSize"
   size_t MaxHeapSize                              = 4242538496                                {product} {ergonomic}
   double MaxRAMPercentage                         = 25.000000                                 {product} {default}
```

（Windows，物理内存 15.8 GiB，Temurin 25.0.4+7。这一组是实测。）

`25.000000` 是默认值；`4242538496` 字节 ≈ 3.95 GiB ≈ 15.8 GiB × 25%。

再显式指定 70%，还是这台机器：

```text
$ java -XX:MaxRAMPercentage=70 -XshowSettings:vm -version
    Max. Heap Size (Estimated): 11.06G
```

（实测，同一台机器：15.8 GiB × 70% = 11.06 GiB。）

这两段合起来说明一件常被写反的事：JVM 不是在「按宿主机内存算堆」，它读 cgroup 的内存上限，有上限就按上限乘百分比。上面 11.06G 的前提是**读不到上限**，也就是容器压根没设 `limits.memory`。从 JDK 10 与 8u191 起容器感知默认开启、默认百分比是 25%，所以 1Gi 上限而不写 `MaxRAMPercentage` 时，堆上限是 256 MiB——偏小，不是「按宿主算」。

「必然被杀」也不成立：被杀的条件是堆 + 非堆越过 `limits.memory`。70% 那组配的是 716.8 MiB 堆，非堆只要小于 307.2 MiB 就到不了顶。

## 仓库里同一个洞（systemd 版）

这个仓库没有 K8s 清单可查：`deploy/` 下 11 个 `.service`、2 个 `.timer`，没有一个 `kind: Deployment`。所以「只设 requests、不设 limits.memory」在这里的等价物是「写了 `ExecStart`、没写 `MemoryMax`」，而它确实在：

- `deploy/ops/ops-textfile.sh:30` 把「没上限」写成 `0`——HELP 原文是 `单元内存上限（0 = 未设上限）`；
- `backend/paideia-ops/src/main/java/io/github/xiaou61/ops/OpsSummaryService.java:110-112` 的注释自己说：「上限为 0 表示该单元没设 MemoryMax……只有 laya 设了上限，其余四个没有」。而 `UNITS` 列表在同一个文件的 `:20-21` 已经是 7 个单元——这句注释停在旧版本，没人跟着改；
- 第二处，水位有两个来源：`deploy/ops/ops-thresholds.conf:11` 的 `UNIT_MEMORY_ERROR=0.90` 会被 `deploy/ops/install-ops.sh:129` 注入成环境变量、并渲染进 Grafana 规则；但 warn 档 `0.75` 是 `backend/paideia-ops/src/main/java/io/github/xiaou61/ops/OpsProperties.java:129` 里的硬编码默认值，conf 里没有这一项。conf 头部（`deploy/ops/ops-thresholds.conf:3-6`）却写着「这里的三个值同时决定两处」——改 conf 只改一半。

两处是同一个毛病：**天花板只有一个来源，水位有两个**。K8s 里它长成「`limits.memory` 一个数、应用自己的阈值另一个数」；systemd 里它长成「conf 一处、Java 默认值一处」。

## 动手

没有集群就用 `kind` 起一个（需要本机有 Docker；这一段我没在 kind 上跑过）：

```text
$ kubectl set resources deploy/app --requests=memory=256Mi --limits=memory=256Mi
```

原命令是 `--limits=memory=64Mi` 单独发，那样会被 API server 拒：08 那份 YAML 里 `requests.memory` 是 `512Mi`，而 `requests` 必须小于等于 `limits`。

改小上限也**不一定**换来 `OOMKilled`：堆跟着百分比走，256 MiB × 70% ≈ 179 MiB，堆变小、启动更慢、Full GC 更频繁，但可能一次都不死。要造 137，得让堆或非堆真的顶到上限——比如用 `-Xmx` 盖掉百分比，或者加一个真吃内存的端点。

再造一个 `Running 但 0/1`。PowerShell 5.1 会吞掉参数里的双引号，所以 patch 写进文件再传：

```text
$ @'
[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/nope"}]
'@ | Out-File -Encoding ascii readiness-patch.json

$ kubectl patch deploy/app --type=json --patch-file=readiness-patch.json
$ kubectl get endpoints app
$ kubectl describe pod <pod> | Select-String "Readiness probe failed"
```

（标准形态，未实跑。`get endpoints app` 期望看到 `ENDPOINTS` 变成 `<none>`。）

这里别用 `--type=merge`：JSON merge patch 对数组是整体替换，`containers` 会被这一条盖掉，`envFrom` 与 `resources` 一起丢，下一次启动直接变成 `CreateContainerConfigError`——从排一个故障变成排两个。

收尾：

```text
$ kubectl rollout undo deploy/app
```

## 还差的

- **没在真集群上跑过。** 所有 kubectl 回显都是按官方文档写的标准形态；`Last State` 的字段顺序、`is waiting to start` 那句原文、`RESTARTS` 的显示格式，都没在具体版本上核对过（写的时候按 1.2x 的形态，没标版本号）。
- **没有 metrics-server 时 `kubectl top` 不存在**，不是「查出来是空的」。这时判断「是不是内存吃紧」要走节点 Conditions（`MemoryPressure`）和 cgroup 计数器，本文没给这条替代路径。
- **三条只说按语义、没实测的**：back-off 的间隔序列、`--previous` 只能退一个实例、容器日志保留几份（kubelet 的 `containerLogMaxFiles`）。我只按 API 字段语义写，没在集群里数过。
- **仓库里那两个洞我只指出位置，没修**：`paideia` 单元不在仓库里（在服务器上，改它得进服务器）；`unitMemoryWarn` 的 `0.75` 要动 Java 代码才能进 conf 的单一来源。
