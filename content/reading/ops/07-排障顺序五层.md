# 排障顺序：从上到下五层

## 一次 502

监控报警：`https://example.com/api/orders` 返回 502，持续约 40 秒，然后自己好了。刷新页面又正常。

这种"自己好的"故障最容易办成糊涂案：你去看日志，日志里什么都没有；重启之后一切正常，于是结论变成"可能是网络抖动"。两周后它再来一次。

我的顺序是固定的，而且不是按"可能性大小"排的，是按**从外到内、从粗到细**排的：

```text
确认谁在疼（本机 vs 外部）
  → 负载 → 内存 → 磁盘 → 网络 → 应用
```

每一层都有一两条命令能给出"这层有没有事"的结论。**"没事"也是结论**——记下来再往下走，不要跳。跳着看是排障最慢的方式：你会在 nginx、应用、数据库之间反复横跳，每次从零开始猜。

## 第 0 步：先确认谁在疼

用 `curl` 把耗时拆开，比看监控曲线快：

```bash
$ curl -s -o /dev/null -w "code=%{http_code} dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n" \
    https://example.com/api/orders
code=502 dns=0.004 conn=0.022 tls=0.041 first=0.238 total=0.238
```

读法：`conn` 和 `tls` 都很小，说明握手没问题；`first`（首字节）用了 238 ms 然后拿到 502。**这说明 nginx 收下了请求、往上打、拿了 502 回来**，问题在内侧。

一个必须避免的习惯：**别用 `/actuator/health` 代表"服务正常"**。健康检查往往只查"进程活着"和一个空查询，接口慢在两秒时它照样 200。要测就测**出问题的那条 URL**：

```bash
# 本机直连目标接口，绕过 nginx
$ curl -s -o /dev/null -w "code=%{http_code} first=%{time_starttransfer} total=%{time_total}\n" http://127.0.0.1:8080/api/orders
code=200 first=1.912 total=1.914
```

本机 1.9 秒——**它慢**。nginx 的 `proxy_read_timeout` 默认 60 秒，1.9 秒不该超时，所以 502 是别的原因（后面第 4 层）。但至少方向定了：问题在内侧，不在入口。这一步花三秒，能省半小时。

## 第 1 层：负载

```bash
$ uptime
 09:40:01 up 12 days,  load average: 8.42, 6.11, 3.20
$ nproc
4
```

`load` 是"正在运行 + 不可中断等待（主要等磁盘 IO）"的进程数。4 核机器上 8.42 已经超过两倍。但**load 高不等于 CPU 忙**：

```bash
$ top -bn1 | head -5
%Cpu(s):  3.2 us,  1.1 sy,  0.0 ni, 94.5 id,  1.2 wa,  0.0 hi,  0.0 si
$ iostat -x 1 3
Device  r/s   w/s   rkB/s   wkB/s  await  %util
sda    2.10  318.40  96.0  41820.0  38.4   98.7
```

`94.5 id`（空闲）却 load 8.42，`%util 98.7` ——**磁盘在饱和**。这一层结论：磁盘 IO 是瓶颈，往下走要看是谁在写。

## 第 2 层：内存

```bash
$ free -h
              total   used   free  shared  buff/cache  available
Mem:           15Gi   13Gi  512Mi   1.2Gi       1.4Gi       1.1Gi
```

看 `available`（1.1Gi），不是 `free`（512Mi）：`buff/cache` 里大部分可以回收，Linux 会拿空闲内存做缓存，这是正常的。

然后查有没有被 OOM 杀掉过。`dmesg -T` 是最直接的，但**普通用户经常读不到内核日志**：

```bash
$ dmesg -T | grep -i "out of memory"
dmesg: read kernel buffer failed: Operation not permitted
$ cat /proc/sys/kernel/dmesg_restrict
1
```

`dmesg_restrict=1`（Ubuntu、Debian 默认）时，非 root 读 `dmesg` 会失败，`grep` 得到空输出——**空输出不等于没有 OOM**。这是排障里最容易骗到自己的一个假阴性。换个入口：

```bash
$ journalctl -k --no-pager | grep -i "out of memory" | tail -5
$ sudo dmesg -T | grep -i "out of memory"
```

这一层结论：没有 OOM 记录，内存也够用 → 内存不是原因。

## 第 3 层：磁盘

```bash
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        79G   74G  5.0G  93% /

$ df -i /
Filesystem      Inodes  IUsed  IFree IUse% Mounted on
/dev/sda2      5242880 612340 4630540   12% /
```

空间 93% 但没满，inode 12% 正常。**两个都要看**：小文件太多时，磁盘还有几百 G，`IUse%` 先到 100%，这时候 `touch` 会报 `No space left on device`，非常反直觉。

查谁在涨（这条命令在根分区上慢，生产上先指定几个可疑目录）：

```bash
$ du -sh /var/log/* /var/lib/docker 2>/dev/null | sort -h | tail -3
2.1G  /var/log/journal
14G   /var/lib/docker
```

我一般先看这三处：`/var/log`（日志没轮转）、`/var/lib/docker`（镜像和容器层）、应用的临时目录（上传/导出文件没清）。这只是"先看"的顺序，不是统计结论——磁盘满往哪儿长，每个部署都不一样。

这一层结论：93% 是慢，但没满，也不是这次 502 的根因。**往下走之前把它记下来**，回头要清。

## 第 4 层：网络

```bash
$ ss -lntp | grep 8080
LISTEN 0  511  127.0.0.1:8080  0.0.0.0:*  users:(("java",pid=12831,fd=87))
```

问题出来了：**它只监听 `127.0.0.1`**。如果 nginx 在同一台机器上跑，能连；如果 nginx 在另一台机器或者容器里，连不上——这就是那个"持续 40 秒的 502"的来源：那段时间 nginx 连接被拒（`Connection refused`），nginx 立刻回 502。

再看连接数和端口状态：

```bash
$ ss -s
Total: 214
TCP:   198 (estab 41, closed 132, orphaned 0, timewait 128)
```

`timewait 128` 不算多（撑满通常是几千），先不用管。要查是谁在频繁短连接：

```bash
$ ss -tan state time-wait | awk 'NR>1{print $4}' | sort | uniq -c | sort -rn | head -3
```

这一层结论：监听地址是根因方向。改成 `0.0.0.0:8080`（或让 nginx 与后端在同一 network 用服务名）之后，502 不再出现。

顺带记一个常见误判：**`ss -lntp` 里出现 `0.0.0.0:8080` 也可能连不上**——云服务器的安全组、防火墙、Kubernetes 的 Service 都是另一层。端口在听只证明进程绑定了，不证明包能到达。

## 第 5 层：应用

前面四层都过了才轮到应用。先看日志，再看线程在干什么：

```bash
$ journalctl -u paideia -n 200 --no-pager | grep -iE "error|exception" | tail
$ PID=$(systemctl show paideia -p MainPID --value)
$ jstack $PID > /tmp/s1.txt; sleep 3; jstack $PID > /tmp/s2.txt; sleep 3; jstack $PID > /tmp/s3.txt
```

**连拍三次是关键**。一次快照只能看到"此刻"，线程可能正好在被调度；三次都停在同一个位置，才是持续热点。对比方法：

```bash
$ grep -A8 '"http-nio' /tmp/s1.txt | grep "at " | sort | uniq -c | sort -rn | head
```

线程栈有三种典型形态，含义完全不同：

| 栈里的样子 | 含义 |
| --- | --- |
| 大量线程在 `java.net.SocketInputStream.read` / `socketRead0` | 在等下游（数据库、HTTP 依赖） |
| 大量线程 `BLOCKED (on object monitor)`，且 `- waiting to lock <0x...>` 指向同一个地址 | `synchronized` 锁竞争 |
| 大量线程 `WAITING (parking)`，栈顶是 `AbstractQueuedSynchronizer.parkAndCheckInterrupt` / `ReentrantLock$NonfairSync` | AQS 系（`ReentrantLock`、`Semaphore`、连接池）在排队 |
| 大量线程 `WAITING (parking)`，栈顶是 `ThreadPoolExecutor.getTask` / `LinkedBlockingQueue.take` | **线程池空闲**，不是问题 |

最后一行要单独强调：`WAITING (parking)` 是**最常见的状态**，因为空闲的池线程就长这样。看到一个应用里 200 个线程全是 `WAITING (parking)`，第一反应不该是"锁竞争"，而是"这个池闲着"。判断要靠栈顶的方法名，不能只看状态。

## 动手

拿一台真实机器按顺序跑一遍，**每层写下结论**：

```bash
$ uptime; nproc
$ free -h; journalctl -k --no-pager | grep -i "out of memory" | tail -3
$ df -h /; df -i /
$ ss -lntp | grep -E ':(80|443|8080)'
$ systemctl status <你的服务> --no-pager | head -20
```

练的是"没事也算结论"这个动作。

## 留个尾巴

这套顺序对"服务变慢/异常"很有效，但它有两个我踩过的盲区：

- **容器里 `df -h /` 只看到容器自己的层**，宿主机满了完全看不出来，得从宿主机或 `crictl` / `docker system df` 看；
- **`load` 在容器里算的是宿主机**（容器共享内核），一个 2 核限额的 Pod 看到 load 8 不代表自己在挨饿，要看 cgroup 的 `cpu.stat`（`nr_throttled`、`throttled_time`）。

这两个盲区的共同点是：**你在容器里看到的数字，有一部分属于宿主机。** 遇到"指标都正常但就是慢"的容器，先怀疑这一层错位。
