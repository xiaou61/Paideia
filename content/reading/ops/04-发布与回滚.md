## 回滚那几行，从来没被执行过

我写过一个 deploy 脚本，里面有一段「起不来就自动回滚」。它长这样：

```bash
set -euo pipefail
ln -sfn "$TARGET" /opt/app/app.jar
systemctl restart app          # ← 就是这一行
for i in $(seq 60); do ... done # 健康检查
PREV=$(ls -t /opt/app/releases/*.jar | sed -n 2p)
ln -sfn "$PREV" /opt/app/app.jar && systemctl restart app
echo "已回滚到 $PREV"
```

我一直以为它是安全的，直到用 `false` 替掉 `systemctl restart` 跑了一次：

```text
$ bash deploy.sh; echo "脚本退出码: $?"
1 切换到新版
2 restart
脚本退出码: 1
```

第 3 步（健康检查）和第 4 步（回滚）**一行都没执行**。

原因很直白：`set -e` 的语义是「任意命令返回非零就立刻退出」。`systemctl restart app` 失败时脚本当场退出，后面的回滚代码是**不可达代码**。

而 `systemctl restart` 恰恰是最容易失败的一步：`ExecStart` 指向的软链断了、权限不对、停止超时、端口被占。也就是说，我那段回滚专门在最需要它的时候失效。

同一个仓库里的发布脚本（PowerShell 版）也没好到哪去：健康检查失败时它只**打印**回滚命令，不执行：

```text
DEPLOY_FAILED 健康检查 90 秒未就绪；回滚：cd /opt/paideia-app && mv -f app.jar.prev app.jar && systemctl start paideia
```

打印是对的（自动化工具在失败现场乱动手更危险），但这个区别必须在文档里说清：**它不是自动回滚，它是一条要人执行的命令**。这两件事混在一起，就是发布当天最贵的一次误会。

## 回滚的前提是「旧的还在，且知道哪个是好的」

```text
/opt/app/
  app.jar -> releases/app-20261119-0315.jar   # 软链接，换它即发布
  releases/
    app-20261119-0315.jar        # 当前（坏）
    app-20261118-1042.jar        # 上一个
    app-20261117-0920.jar        # 上上个
  last-good -> releases/app-20261117-0920.jar  # ← 这个才是回滚目标
```

三样东西缺一不可：

1. **旧产物没被覆盖**——不要 `cp new.jar app.jar`，按版本放目录，用软链指过去；
2. **一个明确的「好状态」标记**——`last-good` 只在健康检查通过后才更新，而不是「第二新的那个文件」；
3. **一条演练过的回滚命令**——不是现场想的，是跑过的。

第二点最容易做错。`ls -t *.jar | sed -n 2p` 选的是「第二新的文件」，不是「上一个已知好版本」。连续坏两次时它就骗你：

```text
$ ls -t *.jar            # app-A 好、app-B 坏、app-C 坏
app-C.jar  app-B.jar  app-A.jar
$ ls -t *.jar | sed -n 2p
app-B.jar                # 回滚到了另一个坏版本
```

## 一份不会静默失效的部署脚本

```bash
#!/usr/bin/env bash
set -euo pipefail

STAMP=$(date +%Y%m%d-%H%M%S)
REL=/opt/app/releases
TARGET="$REL/app-$STAMP.jar"
LAST_GOOD=/opt/app/last-good

[ -f /tmp/app.jar ] || { echo "缺少 /tmp/app.jar"; exit 1; }
mkdir -p "$REL"

# 1) 先校验再落盘，避免把上次残留的包当成这次的
sha256sum -c /tmp/app.jar.sha256 >/dev/null || { echo "包校验失败"; exit 1; }
install -m 644 /tmp/app.jar "$TARGET"

# 2) 没有旧版本就别装作能回滚
if [ ! -L "$LAST_GOOD" ]; then
  echo "首次发布：没有可回退目标，失败时需要人工介入" >&2
fi

# 3) 停 → 换 → 起。不要边跑边换
systemctl stop app
ln -sfn "$TARGET" /opt/app/app.jar
if ! systemctl start app; then
  echo "启动失败，执行回滚" >&2
  [ -L "$LAST_GOOD" ] && { ln -sfn "$(readlink -f "$LAST_GOOD")" /opt/app/app.jar; systemctl start app; }
  exit 1
fi

# 4) 健康检查：超时 + 检查内容，不只是看 HTTP 码
ok=no
for i in $(seq 45); do
  if curl -fsS -m 2 http://127.0.0.1:8080/actuator/health 2>/dev/null | grep -q '"status":"UP"'; then
    ok=yes; break
  fi
  sleep 2
done

if [ "$ok" = no ]; then
  echo "健康检查未通过，回滚到 $(readlink -f "$LAST_GOOD" 2>/dev/null || echo 无)" >&2
  [ -L "$LAST_GOOD" ] || exit 1
  systemctl stop app
  ln -sfn "$(readlink -f "$LAST_GOOD")" /opt/app/app.jar
  systemctl start app
  exit 1
fi

# 5) 只有确认好了才更新 last-good
ln -sfn "$TARGET" "$LAST_GOOD"
echo "发布成功：$TARGET"
```

每一处都对应上面那个失败：

| 写法 | 为什么必须这样 |
| --- | --- |
| `if ! systemctl start app; then ... fi` | 「重启失败」必须进回滚路径。靠 `set -e` 只会退出，不会回滚 |
| 先 `stop` 再换软链再 `start` | 进程还在跑时换掉它自己的 jar，Spring Boot 关机路径上懒加载的类就会读新 jar，报 `NoClassDefFoundError` |
| `curl -m 2` | 不给超时的 `curl` 可能一直挂着；`for` 循环限制的是次数，不是每次的耗时 |
| `grep -q '"status":"UP"'` | `curl -f` 只保证不是 4xx/5xx。端口被别的服务占了、Actuator 返回 200 但 `"status":"DOWN"`，都会被判成成功 |
| `last-good` 软链 | 「第二新」不等于「已知好」。连续坏两次会把回滚带进第二个坑 |
| 首次发布显式报错 | 只有一个包时 `sed -n 2p` 是空的，`ln -sfn ""` 会让脚本在半路死掉，服务停在新版本上 |
| `sha256sum -c` | `/tmp/app.jar` 可能是上次留下的旧包，脚本会「成功」发布错版本 |

## 健康检查检查什么

`/actuator/health` 默认只回 `{"status":"UP"}`，它**不代表业务能用**。至少要让它覆盖数据库和关键外部依赖，并且分开读写：

```yaml
management:
  endpoint:
    health:
      show-details: never          # 别对匿名请求暴露依赖细节
      probes:
        enabled: true              # 打开 /health/liveness 与 /health/readiness
  health:
    db:
      enabled: true
```

发布脚本等的应该是 readiness（能不能接流量），而不是 liveness（进程还活着）。liveness 通过、readiness 不通过，是一个完全正常的状态：它在启动中，或者依赖还没起来。

## 三种发布方式，先问一个问题

选哪种，取决于「回滚这一步要不要动服务器上的文件」：

| 方式 | 回滚动作 | 代价 | 什么时候选 |
| --- | --- | --- | --- |
| 停机发布 | 换软链 + 重启 | 中断几十秒 | 单机、有维护窗口、日活不高 |
| 蓝绿 | 切流量 | 双倍资源 | 不能停机、并且真的有两套环境 |
| 滚动 | 再滚一遍旧版本 | 需要 LB + 健康检查；混跑期要兼容 | 多实例、无状态服务 |

金丝雀是滚动的变体（先给 5% 流量）。它要求能按比例分流，还要有能看得懂的指标——两个都不具备时，金丝雀只是让你更晚发现问题。

小服务用停机发布完全正当。前提是不停机也要满足的那一条：**三分钟内能退回去**。

## 不能靠换 jar 恢复的东西

「回滚代码」只回滚了 jar。下面这几样都不会跟着回去：

- **数据库结构**：`ALTER TABLE ... DROP COLUMN`、`MODIFY` 缩小类型、数据回填，跑完就回不去。纪律是迁移只做加法（加可空列、加表、加索引），删列/改类型拆成两次发布——先上线不依赖新列的代码，确认没问题再删。
- **旧代码能不能在新 schema 上跑**：这是判断一个迁移要不要拆的唯一标准。跑不了，就是这次发布没有回滚能力。
- **配置文件**：服务器上的 `application.yml` 如果被顺手改过，旧 jar 起来还是新配置。所以发版不覆盖配置文件，配置单独版本化、单独回滚。
- **前端产物与缓存 key**：前端静态资源换回去了，用户浏览器和 CDN 还在用新的哈希文件名。灰度时要考虑这一点。
- **消息格式与对外契约**：新版本开始发 `order.created.v2`，回滚后老消费者还在等 v1，队列里的 v2 消息没人认。

## 上线前先演练一次回滚

这一条比任何文档都有效：**发新版之前，先把回滚跑一遍**。

```text
# 1. 当前版本是什么、上一个已知好在哪
readlink -f /opt/app/app.jar; readlink -f /opt/app/last-good

# 2. 只做回滚这一步，看服务能不能起来
ln -sfn "$(readlink -f /opt/app/last-good)" /opt/app/app.jar
systemctl stop app && systemctl start app
curl -fsS -m 2 localhost:8080/actuator/health | grep status

# 3. 计时：从下决心到恢复，真的几分钟？
```

第 3 步的答案就是你的真实 RTO。演练时是 40 秒，出事那天可能是 8 分钟——因为那天你还在想「是不是该回滚」、还在找旧包在哪。

## 还差的

- **蓝绿和滚动没有真做过**。上面那套是单机停机发布，蓝绿的双倍资源成本、混跑期的兼容问题，我只在别人的故障复盘里读过。
- **健康检查只覆盖数据库**。缓存、外部支付接口挂了，readiness 还是通过，用户看到的错误是从业务接口返回的——这层没接进来。
- **配置回滚没实现**。现在只是「发版不覆盖配置文件」，配置被改坏了怎么回到上一版，还是手工操作。
