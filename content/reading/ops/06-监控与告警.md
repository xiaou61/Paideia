## 一条规则都没加载

把原稿里的 YAML 原样存成 `rules.yml`，它的顶层是 `rules:`，而规则文件要求 `groups:`。严格按官方格式解析的工具会直接拒绝，`promtool check rules` 的典型报错是：

```text
$ promtool check rules rules.yml
Checking rules.yml
  FAILED:
rules.yml: yaml: unmarshal errors:
  line 2: field rules not found in type rulefmt.RuleGroups
```

这段报错是 `promtool` 的原文形态；**我这台机器上没装 promtool，没真跑过它**。不过结论可以自己验证，用 Python 的 `yaml` 读一遍就够——顶层不是 `groups:` 的文件，任何按官方格式解析的工具都过不去。

如果这个文件被 `rule_files` 引用，Prometheus 启动或重载时会报规则加载错误；如果它只是没被引用，`/rules` 就是空的，没人会注意到规则根本没生效。

比这更安静的是漏报。做一个纸面演练：48 条告警同时进群，47 条是 CPU 过 80%、磁盘过 70%、5xx 瞬时越界，第 48 条是 `BackupFailed`。周末没看群，两天后翻到第 48 条时，备份已经连续 36 小时没成功。这不是哪家公司的线上事故，是一个按比例摆出来的玩具场景，但它说明：告警的数量和排序，会决定你会不会看见真正要紧的那条。

标题里那句「只报用户已经受影响的事」说得太满。磁盘 85%、备份 36 小时没成功、证书还剩 7 天，用户还没疼，但都有硬截止时间；等用户疼就来不及了。所以不是「响 / 不响」二选一，而是三档。

## 三档：叫醒人 / 进工单 / 只上墙

| 档 | 什么时候用 | 例子 | 去处 |
| --- | --- | --- | --- |
| **page** | 用户已经受影响，或按当前速度即将影响用户 | 1h 5xx 燃尽率 14.4x；`up{job="paideia"} == 0` 持续 2 分钟；磁盘按 6h 趋势 4 小时内写满 | 电话 / 值班群 @ 人 |
| **ticket** | 还没影响用户，但有硬期限 | 磁盘 85%；备份 36 小时没成功；证书 7 天到期；6h 慢燃尽 6x | 工单，工作时间处理 |
| **dashboard** | 趋势和容量规划 | CPU 80%、磁盘 70%、单机 QPS、p95 周趋势 | 只上墙，不叫人 |

这三档的边界不是拍脑袋：page 的主线是「按这个速度，1 小时烧掉月预算的 2%」或「目标已经抓不到」；ticket 的主线是「按这个速度，5 天烧完月预算」或「有硬截止时间」；dashboard 是不需要现在动手的趋势。数字怎么来的，后面「燃尽率」一节算。

几个具体阈值要单独说：

- **磁盘 85% 是 ticket，不是 page**。85% 还没影响用户，但按容量增长可能在几天内写满；page 应该用 `predict_linear(node_filesystem_avail_bytes{mountpoint="/",fstype!~"tmpfs"}[6h], 4*3600) < 0` 这类「4 小时内会写满」的预测。85% 是我给这台机器定的工单线，不是行业标准。
- **证书 7 天是 ticket**。Let's Encrypt 证书有效期是 90 天，自动续期失败后留 7 天手动处理；如果只剩 7 天且自动续期已经坏了，那就该升到 page。
- **备份 36 小时是 ticket**。日备一天一次，36 小时意味着至少漏了一轮；这条线来自上一篇的保留策略，不是随便写的。

四条黄金信号还是起点：延迟、流量、错误、饱和度。前三个直接对应用户是否受影响，饱和度回答「还剩多少余量」。page 只看用户能感知、或马上会感知的部分；CPU 80%、GC 暂停、连接池占用这些原因指标进 ticket 或 dashboard，除非它们能预测用户马上受影响。按症状告警，不按原因告警，说的就是这个分层。

每条告警还要有动作：`service`、`severity` 之外，至少有一个能点开的 `runbook_url` 或一条明确命令。写不出「收到之后做什么」的规则，删掉或降级成 dashboard。

## 指标得先采对

Spring Boot 的 Micrometer 和 Prometheus 客户端库不是一套命名。`http.server.requests` 这个 timer 在 `/actuator/prometheus` 里导出为：

```text
http_server_requests_seconds_count
http_server_requests_seconds_sum
# 开了 percentiles-histogram 后才有：
http_server_requests_seconds_bucket
```

`http_requests_total` 是 client_golang 的习惯。名字写错时，PromQL 不会报错，只会返回空向量；`空 > 0.01` 不成立，规则永远不 firing。这比写错 PromQL 语法更难发现，因为 `/alerts` 页面看起来很干净。

先确认端点真的暴露了：

```text
$ curl -s http://127.0.0.1:8080/actuator/prometheus | grep -c '^http_requests_total'
0
$ curl -s http://127.0.0.1:8080/actuator/prometheus | grep -m1 '^http_server_requests_seconds_count{'
http_server_requests_seconds_count{error="none",...,status="200",uri="/api/v1/knowledge/entries",} 42.0
```

第一行的 `0` 是关键：它不代表应用坏了，只代表名字不对。第二行的标签和数值随请求变，这里只保留形状。如果连 `http_server_requests_seconds_count` 也 grep 不到，先看 `management.endpoints.web.exposure.include` 有没有 `prometheus`；Spring Boot 默认只暴露 `health`。如果 exposure 有 `prometheus` 还是 404，再检查 `micrometer-registry-prometheus` 是否在依赖里。

Paideia 的 `application.yml` 里是：

```text
management.endpoints.web.exposure.include=health,info,metrics,prometheus
management.metrics.distribution.percentiles-histogram.http.server.requests=true
```

第二行不是默认值。Micrometer 默认只给 `_count`、`_sum`、`_max`；没有 `_bucket`，`histogram_quantile()` 返回空，不是 0。Paideia 显式打开直方图，才有 `http_server_requests_seconds_bucket` 可以算 p95。

### `/actuator/health` 不是延迟接口

原稿里有一段：

```text
for i in $(seq 50); do curl -s -o /dev/null -w "%{time_total}\n" http://127.0.0.1:8080/actuator/health; done | sort -n | tail -5
```

`sort -n | tail -5` 取的是最大的 5 个值，接近 max，不是 p95。按 nearest-rank 算，50 个请求的 p95 是升序第 48 个（`ceil(0.95 × 50)`），不是最后 5 个。而且 `/actuator/health` 的耗时只代表 health 自己，可能还包含数据库检查；它不是用户接口的延迟。

没有 Prometheus 时，至少把分位算对：

```bash
for i in $(seq 100); do
  curl -s -o /dev/null -w '%{time_total}\n' http://127.0.0.1:8080/actuator/health
done | sort -n | awk '{a[NR]=$1} END {i=int(NR*0.95); if (i < NR*0.95) i++; printf "n=%d p95=%.4fs max=%.4fs\n", NR, a[i], a[NR]}'
```

这段仍然只测 health。要用户接口的 p95，用已经打开的直方图：

```text
histogram_quantile(
  0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m]))
)
```

按路由分开就加 `by (le, uri)`。平均耗时用 `_sum / _count`：

```text
sum(rate(http_server_requests_seconds_sum[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))
```

### health 默认看不到数据库

`management.endpoint.health.show-details` 默认是 `never`。所以：

```text
$ curl -s http://127.0.0.1:8080/actuator/health
{"status":"UP"}
```

只有总状态，没有 `db` 组件。要看到组件，得显式改：

```text
management.endpoint.health.show-details=when-authorized
management.endpoint.health.roles=ACTUATOR
```

改之前先确认这个端点不是公网可读。Paideia 的 `/actuator/health` 是公开给徽标和 e2e 用的，所以它的配置保持 `show-details: never`；数据库状态看连接池指标（用 Hikari 时是 `hikaricp_connections_*`）和业务错误率，不靠 health 的细节。

## 一份格式正确的规则文件

下面这份规则**我没用 promtool 跑过**（本机没装它）。我用 Python 的 `yaml` 解析检查了结构：顶层是 `groups:`、每个组有 `name` 和 `rules`、每条规则有 `alert` 与 `expr`。这只能证明 YAML 与字段结构是对的，证明不了 PromQL 表达式写得对——那需要真的 Prometheus 跑起来。为了篇幅，两个 group 放在同一个文件；实际部署时把 `meta-monitoring` 拆到单独的 `self.yml`，业务规则文件写坏时它不会一起消失。

```yaml
groups:
  - name: paideia-availability
    rules:
      - alert: ApiErrorBudgetBurnFast
        expr: |
          (
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[1h]))
            /
            sum(rate(http_server_requests_seconds_count[1h]))
          ) > (14.4 * 0.001)
        for: 2m
        labels:
          severity: page
          service: paideia-api
        annotations:
          summary: "API 5xx 正在快速烧错误预算（1h > 1.44%）"
          description: "当前 1h 5xx 比例 {{ $value | humanizePercentage }}，是 99.9% SLO 预算的 14.4 倍燃尽率。"
          runbook_url: "https://example.invalid/runbooks/api-5xx"

      - alert: ApiErrorBudgetBurnSlow
        expr: |
          (
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[6h]))
            /
            sum(rate(http_server_requests_seconds_count[6h]))
          ) > (6 * 0.001)
        for: 15m
        labels:
          severity: ticket
          service: paideia-api
        annotations:
          summary: "API 5xx 持续烧预算（6h > 0.6%）"
          description: "6h 窗口错误率 {{ $value | humanizePercentage }}，按 6 倍燃尽率，约 5 天烧完 30 天预算。"

      - alert: PaideiaTargetDown
        expr: up{job="paideia"} == 0
        for: 2m
        labels:
          severity: page
          service: paideia-api
        annotations:
          summary: "Prometheus 抓不到 Paideia"
          description: "job=paideia 已连续 2 分钟 up=0。先看应用进程和端口，再看网络与 /actuator/prometheus 的访问限制。"

      - alert: BackupTooOld
        expr: time() - paideia_backup_last_success_timestamp_seconds > 36 * 3600
        for: 10m
        labels:
          severity: ticket
          service: paideia-backup
        annotations:
          summary: "备份超过 36 小时没有成功"
          description: "最近一次成功备份在 {{ $value | humanizeDuration }} 前。先看备份脚本退出码和定时任务日志。"

  - name: meta-monitoring
    rules:
      - alert: PaideiaRuleGroupMissing
        expr: absent_over_time(prometheus_rule_group_last_evaluation_timestamp_seconds{rule_group="paideia-availability"}[10m]) == 1
        labels:
          severity: ticket
          service: prometheus
        annotations:
          summary: "paideia-availability 规则组没有出现"
          description: "Prometheus 看不到这个规则组的求值时间。先查 rule_files 路径、挂载和 /rules 页面。"

      - alert: PrometheusRuleGroupStale
        expr: time() - prometheus_rule_group_last_evaluation_timestamp_seconds > 300
        for: 5m
        labels:
          severity: ticket
          service: prometheus
        annotations:
          summary: "规则组 {{ $labels.rule_group }} 超过 5 分钟没求值"
          description: "规则没加载或 Prometheus 卡住时，所有业务告警都会静默。先看 /rules 和 Prometheus 日志。"

      - alert: PrometheusConfigReloadFailed
        expr: prometheus_config_last_reload_successful == 0
        for: 5m
        labels:
          severity: ticket
          service: prometheus
        annotations:
          summary: "Prometheus 最后一次配置重载失败"
          description: "新的抓取配置或规则文件没有生效。看 Prometheus 日志里的 config reload error。"

      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
          service: alerting
        annotations:
          summary: "心跳：这条一直 firing"
          description: "Alertmanager 把它送到外部 dead-man's switch；外部收不到就说明整条告警链路断了。"
```



`for: 2m` / `for: 15m` 是去抖：一次抓取越界不触发，持续到时间才 firing。它不能修复坏指标；名字写错时，等多久都不会响。

`BackupTooOld` 用的是自定义指标，不是 Spring Boot 自带的。备份脚本成功后写一行到 node_exporter 的 textfile collector，例如：

```text
paideia_backup_last_success_timestamp_seconds 1795000000
```

没有这个指标，`time() - 指标` 返回空，规则不会响；这又是一个静默失败。第一次部署时先写一个 0 值，或者再加 `absent_over_time(...[36h])`，否则「从来没有成功过」这条也不会报。

## 燃尽率怎么算

下面按请求成功率算：99.9% 的 SLO，30 天错误预算 = `1 - 0.999 = 0.001 = 0.1%`。如果你的 SLO 是时间可用性，0.1% 是 43.2 分钟，不是请求数，别直接套这个公式。

```text
燃尽率 B = 实际错误率 / 0.001
烧完时间 = 30 天 / B
```

按这个公式，几个数是这样：

| 实际 5xx 比例 | 燃尽率 | 按这个速度烧完 30 天预算 | 1 小时消耗月预算 |
| --- | --- | --- | --- |
| 0.1% | 1x | 30 天 | 0.14% |
| 0.6% | 6x | 5 天 | 0.83% |
| 1% | 10x | 3 天 | 1.39% |
| 1.44% | 14.4x | 约 2.1 天 | 2% |

「1 小时消耗月预算」是按流量和错误率在窗口内不变算的。14.4x / 1h 和 6x / 6h 取自 Google SRE Workbook 的 multiwindow multi-burn-rate 示例；SLO 不是 99.9% 时，倍率要重算。

现在再看原稿那句「连续 5 分钟 5xx > 1%」：

- 1% 不是「超过 SLO」。SLO 允许的是 0.1%，1% 是预算的 10 倍燃尽率；按这个速度持续 3 天，30 天预算就烧完。
- 如果只持续 5 分钟，假设流量平稳，烧掉的预算是 `0.01 × 5 / 43200 / 0.001 ≈ 0.12%`。它可能是尖峰，也可能只是分母太小；5 分钟窗口本身不足以判断严重程度。
- `for: 5m` 只是要求条件连续 5 分钟为真，它不能把「5 分钟的 1%」变成「1 小时的 1.44%」。要判断叫不叫人，看燃尽率和持续时间，不是看一个瞬时比例。

低流量服务还要单独处理：分母只有几十个请求时，1 个 5xx 就能把比例抬过 1.44%。给规则加最小请求量，或者把窗口拉到有统计意义；这个最小量取决于你的流量形状，我没有给一个通用数字。

## 监控自己

告警系统最常见的问题不是「规则写错」，是「没人知道它没在工作」。至少要看这四件事：

1. **抓不到目标**：`up{job="paideia"} == 0` 持续 2 分钟，page。
2. **规则组没加载或没求值**：`absent_over_time(prometheus_rule_group_last_evaluation_timestamp_seconds{rule_group="paideia-availability"}[10m]) == 1`，以及求值时间超过 5 分钟，ticket。
3. **配置重载失败**：`prometheus_config_last_reload_successful == 0`，ticket。新的规则文件没生效时，这条是少数能提前告诉你的信号。
4. **整条链路断了**：`Watchdog` 一直 firing，Alertmanager 把它送到外部 dead-man's switch；外部收不到就说明 Prometheus 或 Alertmanager 没在工作。

第 4 条不能省。`up{job="prometheus"} == 0` 是没用的：Prometheus 挂了，没人算这条规则。`up{job="alertmanager"} == 0` 也不够：Alertmanager 挂了，这条告警也要经过它才能送出来。单机玩具里这是单点；要么用外部服务盯心跳，要么第二台机器/第二个 Alertmanager。没有外部心跳的「监控自己」只是自我安慰。

`promtool check rules` 只检查语法。`rule_files` 没匹配到、容器挂载漏了、文件权限不对，Prometheus 可能照常启动但 `/rules` 是空的。把 `meta-monitoring` 放在单独文件，发版前跑 `promtool check config`，再看 `/rules` 页面和 `prometheus_rule_group_last_evaluation_timestamp_seconds` 有没有数。三步都做了，才算确认规则真的加载了。

如果接了 Alertmanager，再抓它的 `/metrics`，对 `rate(alertmanager_notifications_failed_total[5m]) > 0` 报警；但这条同样要靠外部心跳兜底。最后发一条测试告警，用 `amtool alert add` 或 Alertmanager 的测试接口，确认手机真的收到；只在大屏上看到 firing 不算。

## 指标、日志、追踪各管一段

| 想问的问题 | 用什么 | 它答不了什么 |
| --- | --- | --- |
| 现在整体慢不慢、错多少 | 指标（Prometheus） | 单请求为什么慢 |
| 这个请求慢在哪一段 | 追踪（Tempo/Jaeger） | 没被采样的请求 |
| 这一行日志说了什么、哪个用户 | 日志（Loki/ES） | 聚合趋势 |

三者不能互相顶替：指标看不到单请求细节，日志算聚合趋势很贵，追踪有采样。告警主要建在指标上，日志和追踪用来定位，不用来当告警数据源。

## 最小可用组合

先写 `prometheus.yml`：

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: paideia
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["127.0.0.1:8080"]
  - job_name: prometheus
    static_configs:
      - targets: ["127.0.0.1:9090"]
```

这里的 `127.0.0.1` 是 **Prometheus 进程看到的地址**，不是宿主机的地址。三种跑法对应三种写法：

| Prometheus 跑法 | `targets` 写什么 | 适用 |
| --- | --- | --- |
| 宿主机二进制，或 `--network host` | `127.0.0.1:8080` | Paideia 这种只允许回环来源的端点 |
| bridge + `host.docker.internal` | `host.docker.internal:8080` | Docker Desktop；Linux 要加 `--add-host=host.docker.internal:host-gateway`，且端点允许容器网段 |
| bridge + 宿主机内网 IP | `192.168.0.10:8080`（示例） | 应用监听 `0.0.0.0`，且端点允许内网来源 |

Paideia 的 `/actuator/prometheus` 由 `LocalOnlyAuthorizationManager` 锁在回环。在 Linux 的 bridge 网络里，第二种、第三种来源都不是 `127.0.0.1`，会拿到 403；Docker Desktop 的转发实现不同，先在目标机上验证。要么让 Prometheus 用 `--network host`，要么直接把 Prometheus 跑在宿主机上；不要为了图省事把 local-only 改成 `permitAll`。

```bash
# 1) 目录与配置
sudo mkdir -p /opt/prometheus/data /opt/prometheus/rules
sudo chown -R 65534:65534 /opt/prometheus/data
# /opt/prometheus/prometheus.yml 和 /opt/prometheus/rules/paideia.yml 按上面写好

# 2) Prometheus：host 网络才能抓到 Paideia 的回环端点
docker run -d --name prometheus --network host \
  -v /opt/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro \
  -v /opt/prometheus/rules:/etc/prometheus/rules:ro \
  -v /opt/prometheus/data:/prometheus \
  prom/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/prometheus \
  --web.listen-address=127.0.0.1:9090 \
  --web.enable-lifecycle

# 3) Grafana：也只绑回环；密码从 0600 的 env 文件读
sudo mkdir -p /opt/grafana
sudo chown -R 472:472 /opt/grafana
sudo install -m 600 /dev/null /opt/grafana.env
printf 'GF_SECURITY_ADMIN_PASSWORD=%s\n' "$(openssl rand -hex 16)" | sudo tee /opt/grafana.env >/dev/null
docker run -d --name grafana --network host \
  -v /opt/grafana:/var/lib/grafana \
  --env-file /opt/grafana.env \
  -e GF_SERVER_HTTP_ADDR=127.0.0.1 \
  grafana/grafana
```

`-v /opt/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro` 挂的是单个文件，不是空目录。原稿的 `-v /opt/prom:/etc/prometheus` 会把镜像自带的 `prometheus.yml` 盖掉；目录里没有同名文件时，容器启动就报 `open /etc/prometheus/prometheus.yml: no such file or directory`。

`--network host` 下 `-p` 不生效，Prometheus 直接监听宿主机端口，所以必须用 `--web.listen-address=127.0.0.1:9090` 把它限制在回环地址；Grafana 用 `GF_SERVER_HTTP_ADDR=127.0.0.1`。如果不走 host 网络，`-p 9090:9090` 在 Linux 上绑的是 `0.0.0.0`，公网机器上等于把 Prometheus 的查询接口裸露；Grafana 的 `-p 3000:3000` 同理。用 `-p 127.0.0.1:9090:9090`，或者干脆 SSH 隧道：

```bash
ssh -L 3000:127.0.0.1:3000 user@host
```

Prometheus 没有登录，9090 只要可达，任何人都能查所有指标。Grafana 默认账号是 `admin/admin`，第一次登录就改；`/opt/grafana.env` 只放初始密码，权限 0600。官方镜像的默认运行用户是 Prometheus 的 `nobody`（UID 65534）和 Grafana 的 472，数据目录要按这两个 UID 授权；换镜像版本要重新确认。

Grafana 的 Prometheus 数据源填 `http://127.0.0.1:9090`。以上按 Linux 主机写；Docker Desktop 的 host 网络行为不同，先在目标机上用 `curl` 验证容器里能不能访问 `127.0.0.1:8080`，不要直接照抄。

## 还差的

- **最小组合没有接 Alertmanager**。规则能算、Grafana 能看图，但 `page` / `ticket` 还只是标签，没有真的变成电话或工单。要到「叫醒人」这一步，还得加 Alertmanager 路由，并把 `severity` 分到不同 receiver。
- **没有外部心跳服务**。`Watchdog` 只是一条一直 firing 的规则；如果 Prometheus 或 Alertmanager 整台挂了，这条规则也停了，没人知道。真正上线要接一个外部 dead-man's switch，或者第二台独立机器。
- **磁盘和证书告警只写在表里，没进这份规则文件**。它们分别依赖 `node_exporter` 和 `blackbox_exporter`（或 textfile collector）；没有这些指标，规则写了也不会响。
- **只按结构核对了 8 条规则**（两个 group 各 4 条）。YAML 与字段齐全不等于 PromQL 写对了，更不等于在真实 Paideia 流量上跑过；多窗口、延迟 SLO 的燃尽率、低流量最小请求量都还没有实测。
- **Docker host 网络没在 Docker Desktop 上验证**。上面的命令按 Linux 写；Windows/Mac 的 Docker Desktop 网络模式不同，容器里访问 `127.0.0.1:8080` 可能不是宿主机的应用。
