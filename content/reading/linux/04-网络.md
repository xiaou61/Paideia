## 先把结论摆出来

"连不上"有五个层次，**从下往上查，不要跳**：

```text
1. 本机网络（网卡、路由）      ip addr / ip route
2. 能不能到这个 IP            ping <ip>
3. 端口通不通                 nc -vz <ip> <port> / ss -lntp
4. 防火墙与安全组             iptables -L / ufw status
5. 应用层                     curl -v / 应用日志
```

跳层是最大的时间浪费：curl 报"连接被拒"却在查 DNS，"超时"却在查应用代码。

**两个症状要分清**：

| 症状 | 含义 |
| --- | --- |
| `Connection refused` | 到达了主机，但那个端口没人在听（或防火墙回了 RST） |
| `Connection timed out` | 包发出去了，没回应——中间被挡或路由不通 |

## 第一步：本机和路由

```text
$ ip addr
$ ip route
```

看有没有默认路由（`default via ...`）。没有默认路由 = 出不了这台机器。

```text
$ ping -c 2 <网关IP>
```

网关通不通，决定是"本机网络配置问题"还是"更远的问题"。

## 第二步：端口通不通

```text
$ nc -vz 10.0.0.5 3306
```

或者没有 nc 时用 `bash`：

```text
$ timeout 2 bash -c "cat < /dev/null > /dev/tcp/10.0.0.5/3306" && echo open || echo closed
```

在**目标机器**上看谁在听：

```text
$ ss -lntp
```

注意 `Local Address` 列：

- `127.0.0.1:8080` → **只监听本机**，外部连不上（这是"本地能访问、远程不行"的最常见原因）；
- `0.0.0.0:8080` → 所有网卡都监听；
- `[::]:8080` → IPv6 所有网卡。

**MySQL 的 `bind-address = 127.0.0.1`、Redis 的 `bind 127.0.0.1` 都是这一类的典型。**

## 第三步：防火墙

```text
$ iptables -L -n --line-numbers
$ ufw status verbose        # Ubuntu
$ firewall-cmd --list-all   # CentOS
```

要分清两种情况：

- **主机防火墙**（iptables/ufw/firewalld）：在机器上拦；
- **云安全组**：在云平台控制台拦，机器上看不到。

**"机器上防火墙全开，但外面还是不通"通常就是安全组。** 这一条在云环境里极常见，而且机器上没有任何痕迹。

## 第四步：DNS

如果只有**域名**不通、用 IP 正常：

```text
$ dig example.com +short
$ getent hosts example.com
```

`getent` 会走完整的解析链（包括 `/etc/hosts`、nsswitch 配置），比 `dig` 更接近应用实际行为。

**注意**：`ping` 用的是系统解析器，而 Java 应用可能用自己的缓存或配置。Java 的 `UnknownHostException` 有时和 shell 里能 `ping` 通并存。

## 第五步：应用层

```text
$ curl -v http://<ip>:<port>/health
```

`-v` 会把连接、TLS、请求、响应头全打出来。看它停在哪一步：

- `Trying <ip>...` 后卡住 → TCP 层不通；
- `Connected to` 之后卡住 → 应用不响应；
- 返回 4xx/5xx → 网络通了，是应用在拒绝。

## 一个具体的排查记录

```text
# 现象：从 A 机器连不上 B 的 3306
$ nc -vz 10.0.0.5 3306
nc: connect to 10.0.0.5 port 3306 (tcp) failed: Connection refused

# 说明：到达了主机，端口没人听
ssh 10.0.0.5 "ss -lntp | grep 3306"
LISTEN 0 151 127.0.0.1:3306 0.0.0.0:*

# 根因：MySQL 只监听回环
# 解法：改 bind-address（并确认安全组也放行）
```

**每次排查记录"症状 → 命令 → 结论"三段**，这是最快积累经验的方式。

## 常见误区

### 误区：ping 通就能连上端口

**你以为**：ICMP 通说明网络没问题。
**其实**：`ping` 只验证 ICMP 可达，端口可能被防火墙 DROP，应用可能没起来。ICMP 与 TCP 是不同的事。
**怎么验证**：`ping` 通但 `nc -vz host port` 不通——网络层通、传输层被挡。

### 误区：curl 超时就是服务挂了

**你以为**：超时说明目标没响应。
**其实**：超时可能来自 DNS 解析、TCP 握手被丢、或服务端处理过慢。要看 `curl -v` 停在哪一步、`curl -w` 的耗时拆分。
**怎么验证**：`curl -w "dns:%{time_namelookup} conn:%{time_connect} ttfb:%{time_starttransfer}\n"`。

### 误区：本地能访问就等于对外可用

**你以为**：我在服务器上 `curl localhost:8080` 通了，服务就是好的。
**其实**：本地回环通了只证明进程在跑，不证明绑定了对外网卡、也不证明防火墙放行。
**怎么验证**：`ss -lntp` 看绑定地址；从另一台机器连一次。
