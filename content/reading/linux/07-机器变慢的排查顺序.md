## 下午 2 点，订单接口 P99 从 200ms 涨到 3s

假设监控在下午 2 点报警：订单接口的 P99 从 200ms 涨到 3s，CPU 监控只有 30%。用户侧的表现是下单一直转圈，机器没挂，日志还在写。

先别加 CPU，也别急着重启。重启会丢掉 D 状态进程、连接队列、内存和内核日志的上下文；下一次复发时，你手里就没有现场了。

登录机器，先跑这一组，把「负载」和「阻塞」分开：

```bash
date; uptime; nproc; vmstat 1 5
```

工具不一定都在，完整的 `command -v` 检查在下一节；`vmstat` 不在就先看 `/proc/loadavg` 和 `/proc/stat`。

`uptime` 给出 1/5/15 分钟 load，`nproc` 给出核数。`vmstat` 的第一个数据行里，CPU/IO 速率是从开机以来的平均；`r`/`b` 等进程列虽是瞬时值，也建议整行跳过，从第二个数据行开始看。先把 load÷核数、第二个数据行的 `r`/`b`/`wa` 记下来。

如果 load÷核数 > 1，而 `us+sy` 不高，先别加 CPU。下一步去看 `iostat -x -y 1 5` 和 `pidstat -d 1 5`，确认是不是有一堆任务卡在 D 状态等磁盘。

现象与时间先记在下一节；这张表只填数字。

| 要记的 | 你的值 | 从哪来 |
| --- | --- | --- |
| load 1/5/15 |  | `uptime` |
| 核数 / load÷核数 |  | `nproc`，自己算 |
| `r` / `b` |  | `vmstat` 第二个数据行 |
| `us` / `sy` / `wa` / `st` |  | `top` 第二屏或 `vmstat` |
| `si` / `so` |  | `vmstat` |
| 磁盘 `r_await` / `w_await` / `aqu-sz` |  | `iostat -x -y` |
| 磁盘吞吐 / 设备上限 |  | `iostat`、云盘规格 |
| 网络重传 / 连接状态 |  | `ss -s`、`ss -tin` |
| 最可疑进程 |  | `pidstat`、`ps` |
| 内核日志关键字 |  | `dmesg`、`journalctl -k` |

我写这一篇时手上只有 Windows，没有 Linux 环境。下面的命令是标准形态，不是我在某台 Linux 上跑出来的输出；文中的「合成案例」数字是编的，只用来演示判断顺序。你照抄命令可以，但字段名、路径和阈值要按你的系统版本核对。

## 先把现象和时间钉住

先把四个问题写下来，再去翻命令：

| 问题 | 为什么要先问 |
| --- | --- |
| 几点开始 | 和发布、配置变更、备份、定时任务、流量高峰对齐 |
| 哪个接口 / 哪台机器 | 单接口、单实例、单可用区，还是全站 |
| 谁受影响 | 全部用户、某个租户、某个地区，还是只有内部调用 |
| 能不能复现 | 同一请求在另一台实例或测试环境是否也慢；不能复现就先留现场 |

如果只有一台实例慢，先怀疑这台机器的资源或进程；如果所有实例都慢，先怀疑下游、数据库、配置或流量。这个分流比一上来跑 `top` 更有用。

## 先跑一遍：八组命令，各看哪一列

顺序固定：

```text
load → CPU → 内存 → 磁盘 → 网络 → 进程 → 内核日志
```

不是每一步都要跑完，而是每一步都可能把后面的方向排除掉。先排除，再下钻。

先确认工具在不在，别假设 `iostat`、`pidstat`、`iotop`、`strace` 已经装好：

```bash
for c in top vmstat free iostat pidstat iotop sar strace timeout ss dmesg journalctl jcmd; do
  printf '%-8s %s\n' "$c" "$(command -v "$c" || echo missing)"
done
```

`top`/`vmstat`/`free` 来自 procps，`iostat`/`pidstat`/`sar` 来自 sysstat，`iotop`/`strace` 是单独包，`timeout` 来自 coreutils，`ss` 来自 iproute2，`journalctl` 来自 systemd，`jcmd` 来自 JDK。缺了先别在生产机上装包，除非你确认允许；用 `/proc` 的累计值顶一下，或者从同版本的预发机取。

下面是 procps 的写法；busybox 或其他实现先看 `top --help`、`vmstat --help`，选项名可能不同。

| 命令 | 看哪一列 / 哪一行 | 记下什么 |
| --- | --- | --- |
| `date; uptime; nproc` | load average 三个数、核数 | 开始时间、1/5/15 分钟 load、load÷核数 |
| `top -b -n2 -d1` | 第二个 `top -` 块里的 `%Cpu(s)` | us/sy/ni/wa/st/id；不要看 `-n1` 的第一屏 |
| `vmstat 1 5` | 跳过第一个数据行，看 `r`、`b`、`wa`、`si`、`so`、`cs` | 可运行、阻塞、换页、上下文切换 |
| `free -m` | `available`、`Swap used` | 可用内存和交换占用；隔一段时间再取一次 |
| `iostat -x -y 1 5` | `r_await`/`w_await`、`aqu-sz`、吞吐、`%util` | 读写延迟、队列、设备忙不忙；旧版字段名不同 |
| `df -h; df -i` | `Use%`、inode 使用率 | 空间或 inode 是否满 |
| `ss -s` | TCP 总数、`timewait`、`orphaned` | 连接堆积、短连接、孤儿连接 |
| `sudo dmesg -T \| tail -30` 或 `sudo journalctl -k` | OOM、I/O error、link down、SYN flood、hung task | 应用层看不到的证据 |

没有 sysstat 或工具缺失时，先用这些累计值顶着：

| 缺的工具 | 先用 | 怎么读 |
| --- | --- | --- |
| `iostat` | `/proc/diskstats` | 读/写完成次数和扇区数是累计值，隔 1 秒读两次相减 |
| `pidstat -d` | `/proc/<pid>/io` | `read_bytes`/`write_bytes` 是累计值，两次相减；先有 pid |
| `vmstat` / `top` 的 CPU | `/proc/stat` | 第一行 `cpu` 是累计 jiffies，两次相减算比例 |
| `uptime` | `/proc/loadavg` | 前三列就是 1/5/15 分钟 load |
| `free` | `/proc/meminfo` | 看 `MemAvailable`、`SwapTotal`、`SwapFree` |
| `sar` 的网卡吞吐 | `/proc/net/dev` | 字节/包/错误/丢包是累计值，两次相减 |
| `ss` | `/proc/net/tcp`、`/proc/net/tcp6` | 连接状态和队列；解析比 `ss` 麻烦 |

这张表的用法是先排除，再下钻：load 只说明有没有超额任务；`r`/`b` 和 CPU 分项说明超额发生在可运行还是阻塞；内存、磁盘、网络说明阻塞在等什么；进程和内核日志才落到具体对象。

## 第一刀：load 不是 CPU 使用率

`uptime` 的三个 load 数是约 1/5/15 分钟的指数衰减平均，不是三个精确窗口。Linux 的 load 统计可运行任务和不可中断睡眠（D 状态）任务；它不告诉你这些任务是在算还是在等。

所以 `load÷核数 > 1` 只说明「有超额任务」，不说明 CPU 不够。4 核 load 12，可能是 12 个任务在算，也可能是 12 个任务卡在 D 状态等磁盘，CPU 很闲。load 与 `vmstat` 的 `r+b` 不是严格一一对应，但足够用来判断「在算」还是「在等」。

用 `vmstat 1 5` 的第二个数据行拆开：

- `r` 大、`us+sy` 高：可运行任务在排队，CPU 是瓶颈；
- `b` 大、`wa` 高：任务阻塞在 IO，先看磁盘、NFS 或驱动；
- `r` 和 `b` 都不大、load 却高：load 是平均值，可能只是刚才的突发还没衰减完；看 1 分钟和 5 分钟的趋势，不要拿一个瞬时点下结论。

如果 `r` 大但 `us+sy` 不高，再看 `st`（VM 被偷走）和容器 `cpu.stat` 的 `nr_throttled`。

`load÷核数 > 1` 且 `us+sy` 不高时，先别加 CPU：先看 `iostat -x -y 1 5` 和 `pidstat -d 1 5`。

## 第二刀：CPU 分时，不要只看一个总数

`top -b -n1` 的第一屏 `%Cpu(s)` 是从开机以来的平均，不是当前。`-n1` 只采一次，你看到的是「这台机器开机以来大概什么样」。要看当前，用：

```bash
top -b -n2 -d1
```

输出里有两个以 `top -` 开头的块，只看第二个块的 `%Cpu(s)`。`vmstat 1 5` 同理：第一个数据行的速率列是从开机以来的平均，整行跳过最稳。

| 列 | 含义 | 高了先看什么 |
| --- | --- | --- |
| `us` | 用户态 | 应用线程、算法、GC |
| `sy` | 内核态 | 系统调用、上下文切换、网络协议栈、文件系统、驱动、内核锁；不要只归因于「系统调用多」 |
| `ni` | nice 过的用户态 | 低优先级任务是否在占 CPU |
| `wa` | 等磁盘 IO | `iostat`、`pidstat -d`；`wa` 是 CPU 等待，不是磁盘利用率 |
| `st` | 被宿主机偷走 | 虚拟机/超卖；看宿主机和邻居 |
| `id` | 空闲 | CPU 不是瓶颈 |

`hi`/`si` 是硬中断/软中断，网络收包多时 `si` 会高；它们和 `sy` 分开显示，别混在一起。

如果 `wa` 高，先别加 CPU，去看磁盘。如果 `sy` 高，不要只数系统调用：`vmstat` 的 `cs`（上下文切换/秒）和 `in`（中断/秒）也要看，再结合 `pidstat -u` 找进程。`cs` 高不一定是问题，可能是正常的调度；`in` 高要看网卡或磁盘中断。

`r` 持续大于核数，才说明可运行任务在排队；`r` 一两次高于核数不算持续压力。

## 第三刀：内存看 available，不看 free

`free -m` 里 `free` 是完全空闲的内存，`available` 才是内核估计「还能给新负载用多少」。`buff/cache` 不是一整块可回收池：里面有 tmpfs/共享内存这类不能当普通页缓存回收的页；系统里还有不可回收的 slab（`SUnreclaim`），也不该按「随时能回收」算。不要用 `free` 和 `buff/cache` 相加估算应用余量，直接看 `MemAvailable`。

老版本 `free` 没有 `available` 列，就看 `/proc/meminfo` 的 `MemAvailable`。容器里 `free` 的 `available` 可能显示的是宿主机的，不能直接当容器余量；后面容器一节单独说。

一条 `free -m` 看不出 Swap 是否在增长；Swap used 高本身也不等于正在换页。冷页被换出去后可能长期不动。要看换入/换出速率：

```bash
vmstat 1 5
grep -E 'pswp(in|out)' /proc/vmstat
sleep 10
grep -E 'pswp(in|out)' /proc/vmstat
```

`vmstat` 从第二个数据行起看 `si`/`so`（KB/s）；`/proc/vmstat` 的 `pswpin`/`pswpout` 是累计页数，两次读取相减。`si/so` 持续非零，或 `pswpout` 在两次读取之间明显增加，才说明内存压力已经在换页。只增加一次、后面不动，可能只是冷页被换出。

看进程：

```bash
ps aux --sort=-%mem | head -10
```

Java 进程分三层看：RSS、JVM 堆、非堆/native。

```bash
grep -E 'VmRSS|VmSwap' /proc/<pid>/status
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> VM.native_memory summary
```

`jcmd -l` 先确认 pid；`jcmd` 要和目标 JVM 同用户或具备 attach 权限。`VM.flags` 看实际生效的 `MaxHeapSize` 等参数；`GC.heap_info` 看堆的 used/committed（不同 GC 输出格式不同，G1 还会给 region 布局），堆上限从 `VM.flags` 里的 `MaxHeapSize` 看。

`VM.native_memory summary` 需要 JVM 启动时加 `-XX:NativeMemoryTracking=summary`，没加会提示未启用，不能靠事后开启补出来。NMT 有开销，生产开之前先确认。RSS 高但堆没满，可能是 Metaspace、线程栈、直接内存（Netty）、code cache、mmap 或 native 库。

## 第四刀：磁盘看延迟和队列，不只看 %util

先看版本：

```bash
iostat -V
```

较新的 sysstat 12.x 的 `iostat -x` 没有单列 `await`，读延迟和写延迟分成 `r_await`、`w_await`；老版本可能还有 `await` 和 `avgqu-sz`。用：

```bash
iostat -x -y 1 5
```

`-y` 让 iostat 跳过从开机以来的第一份报告；老版本没有 `-y` 就手动跳过第一份。

| 列 | 看什么 | 不要怎么用 |
| --- | --- | --- |
| `r_await` / `w_await` | 读/写请求的平均延迟（ms） | 不要拿 20ms/5ms 当通用阈值；和基线、设备类型、队列深度一起看 |
| `aqu-sz`（旧版 `avgqu-sz`） | 平均队列深度 | 队列高且延迟高才说明排队；只看队列高可能是并发高 |
| `rkB/s` / `wkB/s`、`r/s` / `w/s` | 吞吐和 IOPS | 要和云盘/设备上限比，不要只看绝对值 |
| `%util` | 设备忙的时间比例 | 接近 100 不等于饱和；NVMe/多队列可能不到 100 就饱和，也可能 100 仍有并行余量 |
| `rareq-sz` / `wareq-sz`（旧版可能只有 `avgrq-sz`） | 平均请求大小 | 小块随机 IO 和大块顺序 IO 不能直接比 |

设备上限从云盘规格、物理盘 datasheet 或厂商标称 IOPS/吞吐拿；`lsblk -d -o NAME,ROTA,SIZE` 只能粗分机械/非机械，不能当性能上限。

再看是哪个进程在读：

```bash
pidstat -d 1 5
# 或者
sudo iotop -o
```

`pidstat -d` 的第一次报告也可能从开机算起，跳过第一行；`iotop` 需要 root，容器里可能看不到宿主机上的 IO。

磁盘满或 inode 满也会让写入变慢或报错，顺手看 `df -h` 和 `df -i`。

一个能互相印证的组合是：load 高、`b` 大、`wa` 高、`iostat` 的 `w_await`/`aqu-sz` 高、`pidstat -d` 指向某个写进程。`wa` 高是线索，不是磁盘瓶颈的充分条件；磁盘饱和时 `wa` 也可能不高，尤其 CPU 很忙或 IO 走异步队列时。

## 第五刀：网络先看连接和重传

```bash
ss -s
ss -lntp
sar -n DEV 1 5
```

`ss -p` 要看别的用户的进程需要 root；`sar` 来自 sysstat，第一次报告也先别当现场，跳过第一行最稳。

- `ss -s`：TCP 总数、`estab`、`timewait`、`orphaned`。短连接多时 `TIME_WAIT` 会堆起来，可能正常，也可能要改连接复用；`orphaned` 持续增长说明有 socket 没人管。
- `ss -lntp`：监听端口和 backlog。LISTEN 状态的 `Recv-Q` 是已完成握手、应用还没 accept 的连接数；`Send-Q` 是 backlog 上限。`Recv-Q` 持续接近 `Send-Q`，说明应用 accept 不过来。
- `ss -tin`：每个连接的 `retrans`；`nstat -az TcpRetransSegs` 或 `/proc/net/snmp` 连读两次看增量。`ss -s` 不显示重传。
- `sar -n DEV 1 5`：看 `rxkB/s`、`txkB/s`；错误和丢包用 `sar -n EDEV 1 5` 看 `rxerr/s`、`txerr/s`、`rxdrop/s`、`txdrop/s`；增长再去查网卡、队列或上游。

`ss -tan state syn-recv` 数量大，可能是 SYN flood，也可能是后端或链路不可达；不要只看一个数字，结合 `dmesg` 的 SYN flooding 和上游日志。

本机网卡计数干净，只能说明本机收发没问题；DNS、负载均衡、TLS 握手、对端限流要在链路上看。网络放在最后，不是因为它不重要，而是因为它最容易被本机计数器误判。

## 第六刀：落到进程

```bash
ps -eo pid,ppid,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -15
```

`STAT` 不是只有一个字母，例如：

| 例子 | 拆开 | 含义 |
| --- | --- | --- |
| `R+` | R + + | 正在跑，前台进程组 |
| `Ssl` | S + s + l | 可中断睡眠，会话首领，多线程 |
| `D<` | D + < | 不可中断睡眠，高优先级（nice 为负） |
| `SN` | S + N | 可中断睡眠，低优先级（nice 为正） |

第一位：`R` 正在跑，`S` 可中断睡眠，`D` 不可中断睡眠，`Z` 僵尸，`T` 暂停，`I` 空闲内核线程。后面的 `s` 是会话首领，`l` 是多线程，`+` 是前台进程组，`<` 是高优先级，`N` 是低优先级，`L` 是锁在内存里。不同 `ps` 实现的标志可能不同，先按你机器上的 `man ps` 对。

`D` 不是「杀不掉」，而是「现在不处理信号」。`kill -9` 会把信号挂起，等 IO 返回或驱动恢复、任务重新进入可处理信号的路径时才生效；如果驱动永久卡死，它才会一直 D。D 不一定是磁盘，NFS、块设备、驱动都可能。先看它在等什么：

```bash
ps -o pid,stat,wchan:32,cmd -p <pid>
cat /proc/<pid>/wchan
sudo cat /proc/<pid>/stack
```

`wchan` 显示内核等待点；`/proc/<pid>/stack` 需要 root 和内核配置，可能只显示 `[<0>]` 或权限错误。`/proc/<pid>/status` 的 `State:` 也能确认。

`pidstat -u -r -d -p <pid> 1 5` 把 CPU、内存、IO 分开看；第一次报告也可能从开机算起，跳过第一行。

```bash
timeout -s INT 10 strace -c -p <pid>
```

`-c` 只在 strace 退出时打印汇总；不加 `timeout` 会一直挂着。`timeout -s INT` 在 10 秒后发 SIGINT，strace 收到后打印汇总再退出。strace 会让目标进程每次系统调用停一下，生产上可能把服务拖死；只在预发或低峰用，并确认有 ptrace 权限（同用户、Yama `ptrace_scope`、容器 `CAP_SYS_PTRACE`）。多线程进程要加 `-f` 才会跟线程，代价更大。

Java 线程对不上，是因为 `top -H -p <pid>` 显示十进制 TID，`jstack` 的 `nid` 是十六进制。先转换：

```bash
printf '0x%x\n' <tid>
jcmd <pid> Thread.print | grep -i -A 30 'nid=0x<hex>'
```

或者直接用 `jcmd <pid> Thread.print` 取线程栈；它仍然打印十六进制 `nid`，但省掉 `jstack` 的 attach 问题。先 `jcmd -l` 确认 pid。

## 第七刀：内核日志

```bash
sudo dmesg -T | tail -50
# 或者按时间线
sudo journalctl -k --since "today 14:00"
```

`dmesg` 可能被 `kernel.dmesg_restrict=1` 限制；非 root 会看到 `Operation not permitted`，用 `sudo` 或 `journalctl -k`。`dmesg -T` 的墙钟时间在挂起/恢复后可能不准，对时间线优先 `journalctl -k --since`。容器里 `dmesg`/`journalctl -k` 可能被限制或只看到宿主机；OOM 还要对照 cgroup 的 `memory.events` 和节点日志。

| 关键字 | 含义 |
| --- | --- |
| `Out of memory: Killed process` / `oom-kill` | 内核 OOM，进程被杀 |
| `I/O error` / `EXT4-fs error` / `XFS ...` | 磁盘或文件系统错误 |
| `nvme ... timeout` / `task ... blocked for more than 120 seconds` | 设备/驱动卡住，会看到 D 状态；hung task 默认 120 秒，可配置 |
| `TCP ... SYN flooding` | SYN flood 或连接异常 |
| `link down` / `NIC Link is Down` | 网卡链路断开 |

这些是应用层看不到的证据。

## 容器：宿主机视角不是容器限额

默认的 runc 容器不虚拟化 `/proc/meminfo`、`/proc/stat`、`/proc/loadavg`，除非你加了 lxcfs 之类的工具；所以容器里跑 `top`/`free`/`uptime`，看到的是宿主机，`nproc` 也可能只是亲和性允许的 CPU 数，不是 cgroup 配额。cgroup 文件才是容器的限额。先判断 v1 还是 v2：

```bash
stat -fc %T /sys/fs/cgroup
cat /proc/self/cgroup
```

`cgroup2fs` 对应 v2；`tmpfs` 对应 v1 的挂载点（hybrid 还要看挂载）。`/proc/self/cgroup` 里 `0::/...` 是 v2 的统一层级；出现 `:cpu:`、`:memory:` 这类行是 v1。

不要假设 `/sys/fs/cgroup` 根目录就是容器自己的 cgroup：

```text
v2: /sys/fs/cgroup/<cgroup path>/<file>
v1: /sys/fs/cgroup/<controller>/<cgroup path>/<file>
```

`<cgroup path>` 从 `/proc/self/cgroup` 取。cgroup v2 + cgroup namespace 的容器里，`/sys/fs/cgroup` 可能已经是容器根；v1 或没有 cgroup namespace 时，路径可能还要带 `/docker/<id>` 或 `/kubepods/...`。

v2：

| 文件（在 cgroup 目录下） | 看什么 |
| --- | --- |
| `cpu.max` | `quota period`；`max 100000` 表示不限 |
| `cpu.stat` | `nr_throttled`、`throttled_usec` 是否增长 |
| `memory.max` | 上限；`max` 表示不限 |
| `memory.current` | 当前用量（含 page cache） |
| `memory.stat` | `anon`、`file`、`slab_reclaimable`、`slab_unreclaimable` |
| `memory.events` | `oom`、`oom_kill` 是否增长 |
| `{cpu,io,memory}.pressure` | PSI 压力（内核启用时） |

v1：

| 文件（在 controller 的 cgroup 目录下） | 看什么 |
| --- | --- |
| `cpu.cfs_quota_us` | 配额；`-1` 表示不限 |
| `cpu.cfs_period_us` | 周期 |
| `cpu.stat` | `nr_throttled`、`throttled_time` |
| `memory.limit_in_bytes` | 上限；可能是一个极大的「无限制」值 |
| `memory.usage_in_bytes` | 当前用量（含 cache） |
| `memory.stat` | `total_cache`、`total_rss`、`total_slab_reclaimable`、`total_slab_unreclaimable` |
| `memory.oom_control` | `oom_kill`、`under_oom` |

例如 v2 的 `/proc/self/cgroup` 是 `0::/`，内存上限就是 `/sys/fs/cgroup/memory.max`；是 `0::/kubepods/<pod>/<container>`，就是 `/sys/fs/cgroup/kubepods/<pod>/<container>/memory.max`。v1 的 `/proc/self/cgroup` 是 `4:memory:/docker/<id>`，内存上限就是 `/sys/fs/cgroup/memory/docker/<id>/memory.limit_in_bytes`。

`memory.current` 接近 `memory.max` 不等于马上 OOM：page cache 可以回收，脏页还要先回写；先看 `memory.stat` 里 `file`/`anon` 各占多少，以及 `memory.events` 的 `oom`/`oom_kill` 是否增加。真正危险的是 `anon` 接近上限、回收不动、`oom_kill` 开始增长。

CPU 也一样：`cpu.max` 有配额时，`cpu.stat` 的 `nr_throttled` 增长说明容器被限流，即使宿主机很闲。`/proc/pressure/*` 是系统级；容器自己的压力看 cgroup v2 的 `*.pressure`（如果内核启用 PSI）。

## 合成案例：load 12，CPU 30%，b 大

下面这组数字是编的，只为说明判断顺序，不是某台机器的实测；也不贴原始 `iostat` 输出。

| 观察 | 合成值 | 说明 |
| --- | --- | --- |
| 核数 | 4 | 假设 |
| load 1/5/15 | 12 / 11 / 9 | 假设 |
| `top` 第二屏 `us/sy/wa` | 25% / 5% / 15% | CPU 不忙，但有等待 |
| `vmstat` 第二行 `r/b` | 2 / 9 | 可运行的少，阻塞的多 |
| `iostat -x -y` | `w_await` 高于基线，`aqu-sz` 持续高，`wkB/s` 接近设备上限 | 写盘排队 |
| `pidstat -d` | 日志采集进程写量最高 | 找到写盘来源 |
| `dmesg` | 没有 OOM，只有慢 IO 的痕迹 | 排除内存 |

结论：load 12 不是 12 个任务在算，而是约 9 个任务卡在 D 状态等磁盘；CPU 不是瓶颈。处理顺序是限制日志写入速率、把日志放到独立盘或独立卷、观察 `w_await`/`aqu-sz` 和 `b` 是否回落，而不是加 CPU。

如果只看到 load 高就去加 CPU，这个案例会被误判。
