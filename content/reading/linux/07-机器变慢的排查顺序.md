## 先把结论摆出来

"机器变慢"不是一个问题，而是四类问题共用的一个描述：**CPU、内存、磁盘 IO、网络**。排查顺序固定，目的是用最少的命令排除掉不相关的方向：

```text
现象与时间 → 负载 → CPU → 内存 → 磁盘 IO → 网络 → 进程 → 内核日志
```

先记录，再动手。**下面这些命令都不修改系统，先全部跑一遍存档**：

```text
date; uptime; nproc
top -b -n1 | head -20
free -m
vmstat 1 5
iostat -x 1 5
ss -s
df -h
dmesg -T | tail -30
```

事后回头对时间线时，这份记录比"我记得当时 top 很高"有用得多。

## 第一步：先看负载与核数

```text
$ uptime
 10:20:01 up 12 days,  3:41,  2 users,  load average: 12.35, 8.20, 4.10
$ nproc
4
```

**load average 要除以核数看**：4 核机器上 load 4 表示"刚好跑满"，load 12 表示"有三倍的活排队"。

三个数分别代表 1、5、15 分钟的平均值：

- 1 分钟高、15 分钟低 → 刚出现的突发；
- 三个都高 → 持续负载，不是瞬时抖动。

**关键**：Linux 的 load 统计的是**可运行 + 不可中断（D 状态）**的进程。所以 load 高但 CPU 不高，通常是在等 IO。

## 第二步：CPU 到底忙在哪

```text
$ top -b -n1 | head -5
%Cpu(s): 25.3 us,  5.1 sy,  0.0 ni, 60.2 id,  9.4 wa
```

| 列 | 含义 | 高说明 |
| --- | --- | --- |
| `us` | 用户态 | 应用在算 |
| `sy` | 内核态 | 系统调用多、上下文切换多 |
| `wa` | IO 等待 | CPU 空闲，在等磁盘 |
| `id` | 空闲 | — |

如果 `wa` 高，先别加 CPU，去看磁盘。如果 `sy` 高，看上下文切换：

```text
vmstat 1 5
```

关注 `cs`（每秒上下文切换）与 `r`（可运行队列长度）。`r` 长期大于核数说明 CPU 真的不够。

## 第三步：内存在哪

```text
$ free -m
               total        used        free      shared  buff/cache   available
Mem:           15884        9210        2100         512        4574        6100
Swap:           2047         512        1535
```

- `available` 才是"应用还能用多少"，`free` 小不代表内存不足（页缓存会占用）；
- `buff/cache` 可以回收；
- **`Swap` 的 used 在增长**是危险信号：内存压力已经大到开始换页，性能会断崖式下降。

看具体进程：

```text
ps aux --sort=-%mem | head -10
```

Java 应用还要分两层看：容器/进程的 RSS，以及 JVM 内部的堆与非堆。堆没满但 RSS 很高，可能是元空间、线程栈、直接内存（Netty）或 native 库。

## 第四步：磁盘是不是瓶颈

```text
iostat -x 1 5
```

关注：

- `%util`：设备忙的比例，接近 100 说明饱和；
- `await`：平均等待毫秒，机械盘 > 20ms、SSD > 5ms 就值得怀疑；
- `r/s`、`w/s`：每秒读写次数。

再看是哪个进程在读：

```text
pidstat -d 1 5
# 或者
iotop -o
```

**磁盘慢的典型表现**：load 高、CPU 不高、`wa` 高、应用日志里全是"查询超时"。

## 第五步：网络有没有问题

```text
ss -s                       # 连接数汇总
ss -lntp                    # 监听端口与对应进程
sar -n DEV 1 5              # 网卡吞吐
```

高并发下重点看：

- `TIME_WAIT` 数量是否异常（短连接太多）；
- `Recv-Q` / `Send-Q` 是否堆积；
- 是否有大量 `SYN-RECV`（可能是 SYN flood 或后端不可达）。

## 第六步：落到具体进程

```text
ps -eo pid,ppid,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -15
```

`STAT` 列很关键：

- `R`：正在跑；
- `S`：可中断睡眠（正常等待）；
- `D`：不可中断睡眠（通常在等 IO，**`kill -9` 也杀不掉**）；
- `Z`：僵尸（等父进程回收）。

对一个可疑进程继续下钻：

```text
pidstat -u -r -d -p <pid> 1 5
strace -p <pid> -c        # 统计系统调用（短时间采样）
```

Java 进程用 `jstack <pid>` 看线程栈，配合 `top -H -p <pid>` 找最忙的线程。

## 第七步：内核日志

```text
dmesg -T | tail -50
```

重点找：

- `Out of memory: Killed process`；
- `I/O error` / `EXT4-fs error`；
- `TCP ... SYN flooding`；
- 网卡 `link down`。

这些是"应用层看不到"的证据。

## 容器里的一个陷阱

在容器里跑 `top` / `free`，读到的往往是**宿主机**的数据，不是容器的限额。要确认容器自己的上限：

```text
cat /sys/fs/cgroup/cpu.max          # cgroup v2：配额/周期
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
cat /proc/pressure/cpu              # PSI：CPU 压力
cat /proc/pressure/io
```

如果 `memory.current` 接近 `memory.max`，容器会被内核限制甚至 OOM，但宿主机整体看起来很闲。

## 一个具体案例：load 12，CPU 只有 30%

4 核机器，应用响应变慢。按顺序：

1. `uptime` → load 12.35，远超 4；
2. `top` → `us 25%`、`wa 9%`，CPU 并不忙；
3. `vmstat 1 5` → `r` 队列 3，但 `b`（阻塞）队列 9；
4. `iostat -x` → 数据盘 `%util 98%`、`await 180ms`；
5. `pidstat -d` → 日志采集进程每秒写 200MB；
6. 结论：不是 CPU 问题，是日志写入把磁盘打满，导致大量进程进入 D 状态。

处理：限制日志采集速率 + 换独立磁盘，load 回落到 3 以下。

**如果只看到"load 高"就去加 CPU，这个案例会被误判。**

## 常见误区

### 误区：load 高就是 CPU 不够

**你以为**：load average 直接等于 CPU 使用率。
**其实**：load 统计可运行与不可中断进程；大量进程等磁盘 IO 时 load 也会很高，而 CPU 可能很闲。
**怎么验证**：`vmstat 1 5` 看 `r` 与 `b` 两列，再配合 `iostat` 的 `%util`、`await`。

### 误区：重启一下就好了

**你以为**：重启能清掉异常状态。
**其实**：重启会丢掉所有现场证据（内存快照、连接状态、D 状态进程），问题往往过一段时间复发，而且下次更难查。
**怎么验证**：重启前先按上面的命令存档；对比重启前后同一时刻的指标，才能判断是"缓存/连接堆积"还是"持续泄漏"。

### 误区：`free` 的 free 很小，说明内存不够

**你以为**：空闲内存应该一直很多。
**其实**：Linux 会把空闲内存拿去做页缓存，需要时随时回收；该看 `available`。
**怎么验证**：`free -m` 的 `available` 列；再 `cat /proc/meminfo | grep MemAvailable` 对照。

## 小结

排查顺序的价值在于**先排除，再下钻**：load 与核数决定"是不是真的忙"，CPU 的分项决定"忙在算还是在等"，`free` / `iostat` / `ss` 决定"等的是哪一类资源"，最后才落到具体进程与内核日志。容器场景额外记住 cgroup 限额，别把宿主机的数据当成容器的。
