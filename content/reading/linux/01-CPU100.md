## 先把结论摆出来

`top` 第一行那三个百分比，先分清再看进程：

| 指标 | 含义 | 高了说明什么 |
| --- | --- | --- |
| `us` | 用户态 | 你的代码在算，可能是死循环、算法太重 |
| `sy` | 内核态 | 系统调用频繁、上下文切换多、可能是锁竞争 |
| `wa` | IO 等待 | CPU 没在算，在等磁盘——这时 CPU 空转，加核没用 |

**同样是"CPU 100%"，这三种的排查方向完全不同。** 先看这三个数，再决定往下走。

## us 高：你的代码在忙

`top` 里找到占 CPU 最高的进程，拿到 PID：

```text
top -b -n1 | head -15
```

然后看这个进程里的哪个**线程**在烧：

```text
top -H -p <pid>
```

拿到线程 id（TID），转成十六进制，再和线程栈对：

```text
printf '%x\n' <tid>
jstack <pid> | grep -A 30 <十六进制tid>
```

这是一套固定的连招：**top → top -H → printf → jstack**。能回答"到底是哪个方法在转"。

> 前提是进程是 Java。如果是 Nginx、Python，用 `perf top -p <pid>` 或 `py-spy dump --pid <pid>`。

## sy 高：内核在忙

`sy` 高通常意味着两件事之一：

1. **系统调用太多**：大量小读写、频繁 `stat`、日志刷盘；
2. **上下文切换太多**：线程数远超核数，或锁竞争导致频繁阻塞/唤醒。

看切换次数：

```text
vmstat 1 5
```

`cs` 列是每秒上下文切换数。几千是正常，几万到几十万就要查原因。

```text
pidstat -w -p <pid> 1
```

看 `cswch/s`（自愿切换，通常是等 IO 或锁）与 `nvcswh/s`（非自愿，被强制让出 CPU——说明线程数超过了核数）。

**锁竞争的一个典型特征**：`sy` 高、`cs` 高，但应用吞吐上不去。因为大量 CPU 花在唤醒/阻塞线程上，而不是干活。

## wa 高：在等磁盘

`wa` 高的时候 CPU 其实是**空闲**的，只是被标记为"等待"。

```text
iostat -x 1 5
```

看 `%util`（设备忙的比例）和 `await`（平均等待毫秒）。`%util` 接近 100 且 `await` 很大，说明磁盘是瓶颈。

**这时加 CPU 没用**——瓶颈不在计算。

常见成因：

- 数据库全表扫描导致大量随机读；
- 日志同步刷盘（`fsync`）；
- 大文件拷贝或备份任务；
- swap 被用上了（内存不够的间接表现）。

## 一个具体例子

线上告警"CPU 100%"，按顺序走：

```text
$ top -b -n1 | head -5
Cpu(s): 92.3 us,  5.1 sy,  0.0 wa, ...

→ us 高，说明是代码在算

$ top -b -n1 | head -12
  PID USER   %CPU COMMAND
 1234 app    95.2 java

$ top -H -p 1234 | head -8
  PID USER   %CPU COMMAND
 1250 app    88.0 java

$ printf '%x\n' 1250
4e2

$ jstack 1234 | grep -A 20 0x4e2
"http-nio-8080-exec-3" ... RUNNABLE
  at com.example.OrderService.calculateTotal(OrderService.java:88)
```

一次定位到具体行号。**如果 `us` 高但 `jstack` 里所有线程都在 `WAITING`**，那可能是 GC 线程或 JIT 编译线程——这时该看 GC 日志。

## 常见误区

### 误区：CPU 100% 就是有死循环

**你以为**：跑满 CPU 一定是代码写错了。
**其实**：正常的计算密集任务（压缩、加密、大批量计算）也会跑满。要区分的是"该跑满"还是"不该跑满"——看同期的业务量。
**怎么验证**：对比 CPU 曲线与 QPS 曲线。CPU 涨、QPS 不涨才是异常。

### 误区：加 CPU 就能解决 CPU 高

**你以为**：CPU 是瓶颈就加核。
**其实**：如果 `wa` 高（等磁盘）或 `sy` 高（锁竞争），加核只会让竞争更激烈。
**怎么验证**：加核前后对比 QPS。没变化的说明瓶颈不在 CPU 数量。

### 误区：top 的 %CPU 是"占全部 CPU 的比例"

**你以为**：显示 100% 就是所有核都满了。
**其实**：默认模式下 `%CPU` 是**单核的百分比**，一个多线程进程可能显示 400%（4 核）。要看整机得看第一行的汇总或按 `1` 切换视图。
**怎么验证**：`top` 里按 `1` 展开每个核，对照进程的 `%CPU` 是否超过 100。
