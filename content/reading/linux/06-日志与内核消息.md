## 先把结论摆出来

Linux 上的日志分三层，**出问题时三层都要看**：

| 层 | 位置 | 看什么 |
| --- | --- | --- |
| 应用日志 | 你的程序自己写的文件 | 业务异常、堆栈 |
| systemd / 系统日志 | `journalctl` | 服务启动、退出、重启原因 |
| 内核日志 | `dmesg` / `/var/log/kern.log` | OOM Killer、磁盘错误、网卡异常 |

最常见的误判是：**只看应用日志**。应用"什么都没打就没了"，往往是被内核 OOM Killer 杀掉，或者被 systemd 因启动超时终止——这两类证据都不在应用日志里。

## journalctl：systemd 管的服务

查一个服务的完整历史：

```text
journalctl -u paideia --no-pager -n 200
```

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-u <unit>` | 只看某个服务 |
| `-f` | 实时跟踪（类似 `tail -f`） |
| `-b` | 只看本次启动 |
| `--list-boots` | 列出所有启动记录，`-b -1` 看上一次 |
| `--since "2026-10-26 10:00"` | 按时间过滤 |
| `-p err` | 只看 error 及以上 |
| `-o short-precise` | 带毫秒的时间戳 |

**一个常见坑**：默认情况下 journal 只保存在内存（`/run/log/journal`），重启就没了。要跨重启保留，得让 `/var/log/journal` 存在：

```text
sudo mkdir -p /var/log/journal
sudo systemctl restart systemd-journald
```

或者改 `/etc/systemd/journald.conf` 的 `Storage=persistent`。没做这一步，机器重启后再查"上次为什么挂"，`journalctl -b -1` 会告诉你没有记录。

## dmesg：内核说了什么

```text
dmesg -T | tail -50
```

`-T` 把"开机后的秒数"转成人类可读时间。**不加 `-T` 看到的是 `[12345.678]` 这种相对时间**，对不上应用日志的时间线。

### OOM Killer 的证据

进程被内核杀掉时，dmesg 里会有这样的记录：

```text
[Mon Oct 26 10:12:33 2026] Out of memory: Killed process 12345 (java)
total-vm:8388608kB, anon-rss:6291456kB, file-rss:0kB
```

看到 `Killed process` 就能确定不是应用自己退出的。接下来看是谁触发的：

```text
dmesg -T | grep -i -E 'oom|killed process|out of memory'
```

可能还会看到 `oom_reaper`、某个进程的 `oom_score_adj`。这能回答"为什么偏偏杀的是它"——分数高的进程优先被杀。

### 其他常见内核消息

- 磁盘：`I/O error`、`EXT4-fs error`、`read-only filesystem`；
- 网络：`TCP: request_sock_TCP: Possible SYN flooding`、网卡 `link down`；
- 文件系统：`No space left on device`（也可能出现在应用日志里）；
- 硬件：`MCE`、`EDAC`、内存校验错误。

`dmesg` 是**环形缓冲区**，容量有限（`dmesg -s` 可调）。高日志量下旧消息会被覆盖，所以发生故障后尽快抓一份：

```text
dmesg -T > /tmp/dmesg-$(date +%F-%H%M).log
```

## 日志把磁盘写满了

日志本身也会造成故障。典型链条：磁盘满 → 应用写日志失败 → 服务异常 → 重启 → 日志更多。

排查：

```text
df -h
du -sh /var/log/* | sort -h | tail -10
```

如果 `df` 显示满了但 `du` 加起来不大，看第 3 篇讲的"被删除但仍被打开的文件"：

```text
lsof +L1
```

清理要按类型来：

- **应用日志**：先确认 logrotate 配置，再考虑压缩/删除；直接 `rm` 正在写的文件不会释放空间（进程还开着 fd），要 `truncate -s 0` 或让进程重开；
- **journal**：`journalctl --vacuum-size=500M` 或 `--vacuum-time=7d`；
- **Docker 日志**：`/var/lib/docker/containers/*/*-json.log`，配置 `log-opts max-size/max-file`。

**不要**在没看清是什么文件之前 `rm -rf /var/log/*`：有些目录是服务运行必需的。

## 一个具体例子：服务每 10 分钟重启一次

现象：监控告警"服务不可用"，登录后发现进程在，但 uptime 只有几分钟。

第一步，看 systemd 怎么记录这次退出：

```text
$ journalctl -u paideia -n 30 --no-pager
Oct 26 10:00:01 server systemd[1]: paideia.service: Main process exited, code=killed, signal=9
Oct 26 10:00:01 server systemd[1]: paideia.service: Failed with result 'signal'.
Oct 26 10:00:01 server systemd[1]: paideia.service: Scheduled restart job.
```

`code=killed, signal=9` 说明不是应用自己退出的，是被 `SIGKILL` 杀的。

第二步，看内核为什么杀：

```text
$ dmesg -T | grep -i 'killed process'
[Sun Oct 26 10:00:01 2026] Out of memory: Killed process 4321 (java) ...
```

结论：JVM 堆设得比机器内存还大，加上其他进程，触发了 OOM Killer。修法是调小 `-Xmx` 或加内存，而不是"加个自动重启"。

## 常见误区

### 误区：应用日志里没有，就说明没发生

**你以为**：程序没打错误日志，所以不是它的问题。
**其实**：被内核杀掉、被 systemd 超时终止、容器被 OOM 杀掉，这些都发生在应用还来不及写日志之前。
**怎么验证**：`journalctl -u <unit>` 看 `signal` / `result` 字段；`dmesg -T | grep -i oom` 看内核记录。

### 误区：journalctl 默认会保留历史

**你以为**：重启后还能查上一次启动的日志。
**其实**：默认可能只存在内存里，重启即清空；`--list-boots` 会显示只有一条记录。
**怎么验证**：`journalctl --list-boots`；要保留就建 `/var/log/journal` 或设 `Storage=persistent`。

### 误区：`rm` 掉大日志文件就能腾出空间

**你以为**：文件删了，空间自然回来。
**其实**：如果进程还开着这个文件的 fd，inode 不会释放，`df` 仍然满。`lsof +L1` 能看到这类文件。
**怎么验证**：`rm` 后对比 `df -h`；空间没变就 `lsof +L1` 找持有者。

## 小结

排查"服务自己没了"的顺序是：**先 `journalctl -u` 看退出方式，再 `dmesg -T` 看内核是否动手，最后才回到应用日志找业务异常。** 日志本身也要设上限与轮转，否则它会从"排查工具"变成"故障原因"。
