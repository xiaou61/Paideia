## 每 10 分钟换一个 PID，应用日志却停在 started

（下面的终端回显是按 systemd 的输出格式写的示意，不是本机实测；这台开发机是 Windows，没有 Linux。你的 systemd 版本不同，字段可能略有差异。）

```text
$ systemctl status paideia --no-pager
● paideia.service - Paideia API
     Loaded: loaded (/etc/systemd/system/paideia.service; enabled; preset: enabled)
     Active: active (running) since Mon 2026-10-26 10:00:11 CST; 2min 13s ago
   Main PID: 5123 (java)
      Tasks: 42 (limit: 4915)
     Memory: 612.4M
        CPU: 8.219s
     CGroup: /system.slice/paideia.service
             └─5123 /usr/bin/java -Xmx2g -jar /opt/paideia/app.jar

$ systemctl show paideia -p NRestarts
NRestarts=7
```

```text
2026-10-26 10:00:11.412 INFO  [main] o.p.PaideiaApplication - started
```

十分钟前查，`Main PID` 还是 4987；再往前十分钟，是 4871。应用日志最后一行只有 `started`，没有异常、没有退出码。

`active (running)` 只说明「此刻有一个主进程活着」，不说明这十分钟里它死过没有。PID 和启动时间才是重启的痕迹。`NRestarts` 是较新 systemd 的属性；老版本没有就数 journal 里的 `Scheduled restart job`。

只看这几行，第一反应很容易是 OOM：进程没了、应用没留下异常，太像被内核杀的。但 `code=killed, signal=9` 只能证明主进程收到了 `SIGKILL`，不能证明是谁发的。systemd 的超时、人手 `kill -9`、容器 runtime、OOM Killer 都会留下同样的退出方式。

## 三个并列来源，不是一条因果链

这一篇默认 **systemd + journald**。Alpine/OpenRC、sysvinit、部分容器里没有 `journalctl`：这时用应用日志、`dmesg`（若有权限）、`/var/log/messages` 或 `/var/log/kern.log`，以及 `docker logs`/`kubectl logs` 这些运行时入口替代；下面带 `journalctl` 的命令不能照抄。

应用日志、journal、内核环形缓冲区是三个**并列**来源：

```sketch
{
  "title": "三个并列来源，不是一条因果链",
  "rows": [
    [
      { "id": "app", "title": "应用日志", "sub": "程序自己写的文件", "tone": "blue" }
    ],
    [
      { "id": "journal", "title": "journal", "sub": "systemd 收 stdout/stderr", "tone": "blue" }
    ],
    [
      { "id": "kernel", "title": "内核环形缓冲区", "sub": "dmesg；journalctl -k 是另一个视图", "tone": "amber" }
    ]
  ]
}
```

- 应用自己 `write()` 的文件不会自动流进 journal；只有 stdout/stderr 被 systemd 接走时，才进 journal。
- journal 收 systemd 服务的 stdout/stderr 和系统事件；`journalctl -k` 是它可选收录的内核消息视图。
- dmesg 是内核自己的环形缓冲区，不是 journal 的下游；`journalctl -k` 也不是 dmesg 的上级。

| 来源 | 工具 | 文件/位置（因发行版而异） | 能回答 |
| --- | --- | --- | --- |
| 应用日志 | `tail -f`、`less`、应用自己的查询接口 | 程序配置的路径（示例：`/var/log/paideia/app.log`） | 业务异常、最后处理到哪一步 |
| journal | `journalctl -u <unit>`、`journalctl -k`、`journalctl --user -u <unit>` | `/var/log/journal/`（持久化）或 `/run/log/journal/`（易失），二进制文件 | 服务启停、退出信号、stdout/stderr、systemd 超时 |
| 内核环形缓冲区 | `dmesg`；`journalctl -k` | 无固定文件；rsyslog 可能另存为 `/var/log/kern.log`（Debian/Ubuntu）或 `/var/log/messages`（RHEL/CentOS） | OOM、I/O 错误、网卡/文件系统错误 |

最容易犯的误判是只看第一列。被 OOM Killer 杀掉、被 systemd 超时终止、被容器 runtime 杀掉，证据都在另外两列；应用来不及写日志。

权限也要先确认：`journalctl` 要读系统日志，需要 root，或加入发行版给 journal 配置的组（组名可能是 `systemd-journal`，有些发行版用 `adm`）；不在组里可能只看得到自己的 user journal，或者直接没权限。`kernel.dmesg_restrict=1` 时，普通用户 `dmesg` 会得到 `Operation not permitted`。`lsof +L1` 看别人的进程要 root。`docker` 命令要 `docker` 组或 root，`docker logs` 也一样。下面命令按需加 `sudo`，不要假设自己有 root；只查自己的 user unit 用 `journalctl --user -u <unit>`。

## journalctl：先看退出方式，再看参数

先把时间窗挪到死亡前后，而不是只看最后 200 条：

```text
$ sudo journalctl -u paideia --since '2026-10-26 10:00:00' --no-pager
Oct 26 10:00:11 server systemd[1]: paideia.service: Killing process 4987 (java) with signal SIGKILL.
Oct 26 10:00:11 server systemd[1]: paideia.service: Main process exited, code=killed, signal=9
Oct 26 10:00:11 server systemd[1]: paideia.service: Failed with result 'signal'.
Oct 26 10:00:11 server systemd[1]: paideia.service: Scheduled restart job, restart counter is at 7.
Oct 26 10:00:11 server systemd[1]: Started Paideia API.
```

（示意输出。`Failed with result ...` 的值随触发原因和 systemd 版本变化，可能是 `signal`，也可能是 `timeout`；不要把这一行当成唯一判据。）

这五行只说明：主进程被 `SIGKILL`，systemd 记了一次失败，然后自动重启。它没说信号是谁发的。这条查询只截了五行；把 `--since` 再往前挪几十秒，或者把输出往上翻，才会看到 `Killing process` 之前 systemd 为什么进入 stop，或者 `start operation timed out` 这类启动超时记录。

`signal=9` 是 systemd 写进 message 的文字，不是 journal 的结构化字段；`Result` 和 `ExecMainStatus` 是 systemd 的 unit 属性，要用 `systemctl show` 读，不是从 journal 里拿。

查一个服务的完整历史，不要用 `-n 200` 冒充：`-n 200` 只是最后 200 条记录（一条多行堆栈也只算一条）。按时间窗查：

```text
sudo journalctl -u paideia --since '2026-10-26 09:00' --until '2026-10-26 10:30' --no-pager
```

确实要全部就不加 `-n`，但先 `sudo journalctl --disk-usage` 看它有多大。

| 参数 | 作用 |
| --- | --- |
| `-u <unit>` | 只看某个服务 |
| `-f` | 实时跟踪，类似 `tail -f` |
| `-b` | 只看本次启动；`-b -1` 看上一次（前提是上次的日志还在） |
| `--list-boots` | 列出可用的启动记录 |
| `--since` / `--until` | 按时间过滤，排障时优先用它把窗口缩小 |
| `-p err` | 只看 `err` 及以上（`err`、`crit`、`alert`、`emerg`），不是只等于 error |
| `-o short-precise` | 时间戳显示到微秒（6 位小数），不是毫秒；只改变显示 |
| `-k` | 只看内核消息（journald 收录的那一份） |
| `--disk-usage` | 看 journal 占用，不删东西 |

### 先判断 journal 会不会跨重启

先看它现在有没有历史，不要上来就 `mkdir`：

```text
$ sudo journalctl --list-boots
 0 8f3c... Mon 2026-10-26 09:58:11 CST—Mon 2026-10-26 10:02:24 CST

$ sudo journalctl --disk-usage
Archived and active journals take up 128.0M in the file system.
```

（示意输出；启动 ID 和时间不是本机值。）

只有一条 `0`，说明当前 journal 看不到上一次启动；可能是易失存储，也可能是新机器或归档被清过。先别下结论。

systemd 的默认 `Storage=auto` 不是「只存内存」：`/var/log/journal` 存在就持久化，不存在才写 `/run/log/journal`。有些发行版安装时已经建了这个目录，所以先看 `--list-boots`、`--disk-usage`，或：

```text
grep -E '^Storage=' /etc/systemd/journald.conf
```

没有这行就是默认 `auto`。要开启持久化：

```text
sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
```

不要只 `mkdir` 再 restart：目录的属主和权限要靠 tmpfiles 建，否则 journald 可能写不进去。也可以把 `/etc/systemd/journald.conf` 的 `Storage=` 改成 `persistent` 再 restart；如果那里写的是 `volatile` 或 `none`，建目录也不会持久化。

本次启动已经写在 `/run` 的日志，可以用 `sudo journalctl --flush` 刷到 `/var/log/journal`；不做也不影响以后的持久化。改完重启机器，`sudo journalctl --list-boots` 应该多出记录，`sudo journalctl -b -1` 才能读到上一次。

## 内核日志：dmesg 是环形缓冲区，不是 journal 的下游

```text
$ sudo dmesg -T | tail -50
[Mon Oct 26 10:00:11 2026] Out of memory: Killed process 4321 (java) total-vm:8388608kB, anon-rss:6291456kB, file-rss:0kB, shmem-rss:0kB
```

这一条在终端里会被折成两三行，但内核缓冲区里是**一条**记录；`total-vm` 等字段用逗号分隔。数值单位是 kB。

| 字段 | 含义 | 容易误读 |
| --- | --- | --- |
| `total-vm` | 虚拟地址空间总额 | 大不等于占用了同样多的物理内存 |
| `anon-rss` | 常驻的匿名页：堆、线程栈、匿名 mmap | JVM 堆主要落在这里，但它不等于 `-Xmx`，也不等于已提交堆 |
| `file-rss` | 常驻的文件页：可执行文件、jar、mmap 的文件 | 可回收，不代表进程私有内存 |
| `shmem-rss`（较新内核） | 共享内存/tmpfs 的常驻页 | 容器和 cgroup 里也可能计入 |

`Killed process` 说明内核 OOM Killer 选中了它，不是应用自己退出；但它仍然**不能**证明是 JVM 堆太大。堆外、线程栈、直接缓冲、其他进程把 cgroup 顶满，都可能让内核动手。

`oom_score_adj` 不是最终分数，它只是 -1000..1000 的调整值；最终比较的是 `/proc/<pid>/oom_score`（0..1000，受 adj 影响）。要看谁更可能被杀，读这两个文件，再看 cgroup v2 的 `memory.max` / `memory.current`，不要只盯 `oom_score_adj`。

`dmesg -T` 的时间是按当前时钟换算的：NTP 跳变、休眠、手改时间之后，它可能和应用日志对不上。要精确对齐，用 `journalctl -k --since '2026-10-26 10:00'`，或者同时记下 `date` 和原始的 `[12345.678]` 秒数。

`dmesg -s` 不是调大内核环形缓冲区的容量。它只是 dmesg 读取时用的用户态缓冲区大小；内核容量由启动参数 `log_buf_len` 或编译时的 `CONFIG_LOG_BUF_SHIFT` 决定。已经被覆盖的旧消息找不回来。要更大就改启动参数并重启；故障后尽快保存：

```text
sudo dmesg -T > /var/tmp/dmesg-$(date +%F-%H%M).log
```

`kernel.dmesg_restrict=1` 时普通用户读不了，先 `sudo dmesg`；`journalctl -k` 是另一个入口，但它依赖 journald 收录内核消息（`ReadKMsg=`），不是每个系统都开着。

内核日志的文件位置也随发行版变：Debian/Ubuntu + rsyslog 可能在 `/var/log/kern.log`，RHEL/CentOS 可能在 `/var/log/messages`；纯 systemd 系统直接用 `journalctl -k`。这些都不是「内核固定写在某处」。

## 日志把磁盘写满了：先定位，再按类型清理

日志本身也会变成故障原因：磁盘满 -> 应用写日志失败 -> 服务异常 -> 重启 -> 日志更多。先定位，不要先删。

### 先分清是空间还是 inode

```text
df -h
df -i
du -sh /var/log/* 2>/dev/null | sort -h | tail -10
```

`df -h` 有空间但 `df -i` 满了，也会报 `No space left on device`；这时删大文件没用，要找小文件多的目录。

### df 满了、du 却不大

这可能是有文件被删了但还被进程打开。先别重启进程，先看谁拿着 fd：

```text
sudo lsof -nP +L1
```

`+L1` 找 link count 小于 1 的已删除文件。示意输出：

```text
COMMAND  PID USER FD TYPE DEVICE SIZE/OFF NLINK NODE NAME
java    4321 app  1w REG  253,0 8.2G     0 123456 /var/log/paideia/app.log (deleted)
```

`df` 统计文件系统块，`du` 走目录项；路径没了，inode 还被 fd 持有，空间就不会释放。

### 应用日志：先让 logrotate 处理

不要上来 `rm`。先看有没有 logrotate 配置：

```text
ls /etc/logrotate.d/
logrotate -d /etc/logrotate.d/paideia
```

`logrotate -d` 只打印计划，不执行。`create` 模式是「改名 -> 让进程重开新文件」，进程要支持 `HUP`/`USR1`，或者配置里用 `copytruncate`；`copytruncate` 先复制再截断，复制和截断之间写入的几行可能丢，审计日志不要这么干。

已经 `rm` 了正在写的文件，`truncate <path>` 也打不开——路径没了。只能通过 `/proc/<pid>/fd/<n>` 找到 fd 再截断，或者重启进程让它重开。

`truncate -s 0` 不是无副作用：非 `O_APPEND` 写的进程，文件偏移还在，截断后下一次写会从旧偏移继续，留下巨大空洞，`ls -l` 很大、`du` 可能很小。`O_APPEND` 的进程每次写到末尾，截断后从 0 开始。先 truncate 再观察，不要同时 rm。

### journal：vacuum 会真删日志

```text
sudo journalctl --disk-usage
```

排障期间先别跑 `sudo journalctl --vacuum-size=500M` 或 `sudo journalctl --vacuum-time=7d`：它们会真的删除归档日志。先把需要的窗口导出：

```text
sudo journalctl -u paideia --since '2026-10-26 09:00' --until '2026-10-26 10:30' --no-pager > /var/tmp/paideia-journal.txt
```

导到另一块盘或至少 `/var/tmp`，不要只放 `/tmp`（可能在重启时被清掉）。确实要清，再 vacuum；`--vacuum-size` 只清归档文件，活动文件还在，占用可能不会立刻降到目标。长期上限用 `/etc/systemd/journald.conf` 的 `SystemMaxUse=`，改完 restart journald。

### Docker：先确认根目录和驱动

```text
docker info --format '{{.DockerRootDir}} {{.LoggingDriver}}'
```

`/var/lib/docker/containers/*/*-json.log` 只适用于 rootful Docker + 默认 `json-file` 驱动。rootless 的根目录在用户目录下；换成 `journald`、`local` 等驱动后，`*-json.log` 可能根本不存在；containerd 的日志路径和字段也不同。

要限流，在 `/etc/docker/daemon.json` 配 `log-opts` 的 `max-size` / `max-file`（rootful 默认路径），重启 Docker：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

已有容器在创建时已经定下日志配置，要重建才会套用新的 daemon 默认值；单容器可以用 `--log-opt`。如果驱动是 `journald`，去 `journalctl` 看，不是 json 文件。

### 不要 `rm -rf /var/log/*`

不要在没看清文件前 `rm -rf /var/log/*`：有些子目录是服务运行必需的，属主和权限也有讲究；删掉后服务下次写入会报目录不存在或权限错误。先用 `du` 定位到具体文件，再按上面的类型处理。

## 回到案例：从 signal=9 到定位

不要从 `signal=9` 直接跳到「OOM」或「JVM 堆太大」。把 journal 的时间窗往前挪，按顺序走：

```text
journal 里有 start operation timed out / Killing process ?
├─ 是 → systemd 动的手：查 unit 的 Type/TimeoutStartSec/TimeoutStopSec/RuntimeMaxSec，以及谁执行了 stop/restart
└─ 否 → dmesg 里有 Killed process / Out of memory ?
   ├─ 是 → 内存耗尽：再查 cgroup、堆、堆外
   └─ 否 → 人手 kill -9 / 容器 runtime / 旧消息已被环形缓冲区覆盖
```

先看 systemd 自己有没有写 `Killing process` 或 `start operation timed out`：

```text
sudo journalctl -u paideia --since '2026-10-26 09:59:00' --until '2026-10-26 10:00:20' --no-pager
```

上面的示意记录里有一行：

```text
Oct 26 10:00:11 server systemd[1]: paideia.service: Killing process 4987 (java) with signal SIGKILL.
```

`Killing process ... with signal SIGKILL` 是 systemd 自己写的：信号是它发的，不是内核 OOM。再往上翻，找它为什么进入 stop；这个示意里，unit 配了 `RuntimeMaxSec=10min` 加 `Restart=always`，应用又没在 `TimeoutStopSec` 内退出，所以每 10 分钟被 SIGKILL 一次。

这个示意里的关键配置是：

```ini
[Service]
Type=simple
Restart=always
RuntimeMaxSec=10min
TimeoutStopSec=10s
```

应用正常启动，所以 `status` 是 active；10 分钟后 systemd 发 `SIGTERM`，应用没在 10 秒内退出，systemd 发 `SIGKILL`，`Restart=always` 再拉起一个新 PID。`systemctl cat paideia` 能看到这些值；`systemctl show -p Result -p ExecMainStatus paideia` 读 systemd 记录的退出状态。注意：服务已经自动重启时，`Result` 可能显示当前这次成功，历史退出要看 journal 里的 `Failed with result`。

修法：去掉或调大 `RuntimeMaxSec`，或者让应用在收到 `SIGTERM` 后及时退出；`Restart=always` 只会把问题变成每 10 分钟一次的循环。

如果 journal 里没有 `Killing process`，也没有 `start operation timed out`，再看内核：

```text
sudo dmesg -T | grep -i -E 'killed process|out of memory|oom'
```

有 `Killed process` 才说明内核 OOM Killer 动手。没有，不要硬套；但 dmesg 是环形缓冲区，故障后拖太久，行可能已经被覆盖，没看到不等于没发生。

即使有 OOM 行，也只证明「内存耗尽」，还没证明是 JVM 堆。按这个顺序补证据：

1. `systemctl show -p Result -p ExecMainStatus paideia`。如果服务还在 failed 状态，`Result=signal`、`ExecMainStatus=9` 能把「被 SIGKILL」和 systemd 的记录对上；已经自动重启的话，这两个值可能已经重置，回 journal 看。
2. 进程还活着时，`jcmd <pid> VM.flags | grep -i maxheap` 看 `MaxHeapSize`，`jcmd <pid> GC.heap_info` 看堆的 used/committed。进程已经死了，`jcmd` attach 不上，别在马后炮里假装跑过。
3. `jcmd <pid> VM.native_memory summary` 看堆外，但只有启动时加了 `-XX:NativeMemoryTracking=summary` 才有；否则会提示未启用。metaspace、code cache、线程栈、direct buffer 都在这里分开。
4. `cat /proc/<pid>/smaps_rollup` 看 `Rss`、`Anonymous` 和堆的差距；这是进程级，不是 JVM 级。
5. cgroup 限额：cgroup v2 看 `memory.max`、`memory.current`、`memory.events` 里的 `oom_kill`；systemd 的 unit 可以先 `systemctl show paideia -p MemoryMax -p MemoryCurrent`（没设限额时可能为空）。容器看 `docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' <name>`；Kubernetes 看 `kubectl describe pod` 的 `OOMKilled` 和 `Exit Code 137`（137 = 128 + 9）。
6. `-XX:+HeapDumpOnOutOfMemoryError` 只在 JVM 自己抛 `OutOfMemoryError` 时写 heap dump；内核 OOM 的 SIGKILL 不给它这个机会。没有 heap dump 既不能证明是堆，也不能证明不是内存问题。

定位堆的办法不是猜 `-Xmx`，而是下一次启动前开 NMT/GC 日志，或者在还活着时抓 `jcmd`、`smaps_rollup`，把堆、堆外、cgroup 限额分开看。

两边都没有，剩下的来源是人手 `kill -9`、容器 runtime 的 stop/kill、配置管理或定时脚本。`history` 只能看到当前用户，不能当全局审计；容器看 `docker inspect`/`kubectl describe`，主机看审计日志（如果开了）。这类情况 journal 可能只有 `code=killed`，没有 `Killing process`，因为信号不是 systemd 发的。

如果 dmesg 已经被覆盖，也不能反证「没发生 OOM」；只能说明当前缓冲区没有证据。

## 还差的

- 这台开发机是 Windows，没有 Linux。上面所有 `systemctl`/`journalctl`/`dmesg` 回显都是按 systemd 文档和公开示例写的标准形态/示意，不是本机实测；具体字段、`Failed with result` 的取值、日志路径会随发行版和 systemd 版本变化。
- 案例里的 `RuntimeMaxSec=10min`、`TimeoutStopSec` 和 journal 文字是按 systemd 行为拼的示意；`Result` 在不同版本/触发原因下可能是 `signal` 或 `timeout`，没有在本机逐版本核对。
- 没有覆盖非 systemd 的日志栈（Alpine/OpenRC、sysvinit、runit、s6）和 Kubernetes 的日志采集链路；只给了替代入口，没有逐条命令。
- OOM 的堆/堆外定位只给了证据链，没有在真实 JVM 上复现；`jcmd` 的可用性取决于 JDK 版本和进程存活状态，NMT 需要预先开启。
- 没有验证 rootless Docker、containerd 镜像存储、`local`/`journald` 日志驱动下的具体路径；`/var/lib/docker/...` 只适用于 rootful + 默认 `json-file`。
- 没有讲日志脱敏、审计留存和集中式日志（journald 转发、Fluent Bit/Vector 等）；这些会改变「日志放在哪」和「能留多久」。
