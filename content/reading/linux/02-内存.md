## 先把结论摆出来

**看 `available`，不看 `free`。**

```text
$ free -m
              total  used  free  shared  buff/cache  available
Mem:          15886  9820   312    210      5754       5743
```

这行里 `free` 只有 312 MB，看着像要炸了——但 `available` 还有 5.7 GB，系统完全健康。

原因：Linux 会把暂时用不上的内存拿去做**页缓存**（`buff/cache`）。这部分随时可以回收给应用用。所以"空闲内存少"在 Linux 上是**正常且期望的**——内存闲着才是浪费。

## 每一列到底是什么意思

| 列 | 含义 |
| --- | --- |
| `total` | 物理内存总量 |
| `used` | 已用（不含可回收的 cache） |
| `free` | 完全没被碰过的 |
| `shared` | tmpfs 等共享内存 |
| `buff/cache` | 页缓存 + 块设备缓存，**可回收** |
| `available` | **还能给新应用多少**（free + 可回收部分） |

**判断内存够不够，只看 `available`。** 它小于总内存的 10% 才需要警惕。

## 页缓存是什么

你读一个文件，内核把内容存进内存；下次再读，直接从内存给。

这就是页缓存。它有几个特点：

- **不属于任何进程**，是内核管理的全局缓存；
- **满了会自动回收**，不需要你干预；
- **写文件默认是"写进页缓存就返回"**，真正的落盘由内核择机做。

第二条解释了"为什么 free 这么小但系统没事"；第三条解释了"为什么 `echo xxx > file` 成功了，断电却丢了"。

## OOM 是怎么发生的

真正的内存不足不是"free 小"，而是**匿名内存**（应用自己 `malloc` 的）超过了可用量，且页缓存也回收完了。

这时内核的 OOM Killer 会挑一个进程杀掉：

```text
dmesg -T | grep -i "out of memory"
```

会看到类似：

```text
Out of memory: Killed process 1234 (java) total-vm:8388608kB
```

**Java 应用被 OOM Killer 杀掉，日志里通常什么都没有**——因为它不是 Java 的 `OutOfMemoryError`，是内核直接 `SIGKILL`。这一点最容易误判：看应用日志一片空白，其实是被系统杀了。

## swap：用上了就是信号

```text
$ free -m
Swap:          2047  1820   227
```

swap 用了 1.8 GB，说明内存压力已经很大了。swap 在磁盘上，读写比内存慢几个数量级——**一旦应用被换出去，延迟会暴涨**。

排查时看谁在用 swap：

```text
for f in /proc/*/status; do
  awk '/VmSwap/ {if ($2 > 1000) print FILENAME, $2" kB"}' $f
done | sort -k2 -nr | head
```

**生产环境通常建议关掉 swap**（或调低 `vm.swappiness`），让 OOM 早点发生而不是让服务慢慢变卡。

## Java 应用的内存要看两层

`free` 是系统视角。Java 进程自己还有一层：

```text
jstat -gcutil <pid> 1000
```

看 `O`（老年代使用率）。如果老年代持续上涨、Full GC 后也降不下来，才是真的泄漏。

```text
jmap -histo:live <pid> | head -20
```

看哪类对象最多。数量异常增长的那个类就是嫌疑对象。

**注意**：`jmap -histo:live` 会触发一次 Full GC，生产上慎用（尤其是大堆）。

## 常见误区

### 误区：free 很小就是内存不足

**你以为**：`free` 接近 0 很危险。
**其实**：Linux 主动用空闲内存做页缓存，这是设计目标。看 `available` 才准确。
**怎么验证**：在一台空闲机器上 `cat` 一个大文件，再 `free -m`——free 会明显下降，但系统毫无压力。

### 误区：应用内存看 free 就够了

**你以为**：系统内存够，应用就不会 OOM。
**其实**：Java 有堆上限（`-Xmx`）。系统还有 10 GB 空闲，堆到上限照样 `OutOfMemoryError`。
**怎么验证**：`jstat -gcutil` 看老年代使用率，与 `free` 对照。

### 误区：加内存就能解决内存问题

**你以为**：不够就加。
**其实**：如果是泄漏，加多少都会被吃满，只是把崩溃时间推后。先分清是"容量不够"还是"泄漏"。
**怎么验证**：观察 Full GC 之后老年代是否回落到正常水平。回不去就是泄漏。
