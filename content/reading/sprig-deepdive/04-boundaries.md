## 先把结论摆出来

**模板的能力上限，应该等于"把数据排版成目标格式"，而不是"实现业务规则"。** 一旦你在模板里写条件分支处理业务语义，就已经走错了——Sprig 让这件事变得太容易，这才是它真正的风险。

## 一个判断清单

看到一个模板，用这四条问：

| 问题 | 是 → | 否 → |
| --- | --- | --- |
| 这段逻辑需要单元测试吗？ | 移到代码里 | 留在模板里可以 |
| 出错时需要明确的错误信息吗？ | 移到代码里（模板的错误信息很糟） | 模板里够用 |
| 它依赖外部状态（时间/环境/网络）吗？ | 移出去，作为参数传入 | 可以留在模板里 |
| 同一个规则会在别处复用吗？ | 移到代码里，模板只取值 | 模板里写一次就行 |

## 三个典型的越界

### 越界一：在模板里算业务数值

```go
# 反面教材
replicas: {{ if gt (int .Load) 80 }}
            {{ mul (div (int .Load) 20) 2 }}
          {{ else }}
            {{ max 2 (div (int .Load) 20) }}
          {{ end }}
```

这段"按负载算副本数"看起来还行，但：

- 它无法被单元测试（要渲染整个模板）
- 它无法被其它地方复用（同样的算法在 autoscaler 里要再写一遍）
- 它的错误信息是 `wrong type for value; expected int; got float64` 这种

**正确形态**：`replicas: {{ .Replicas }}`，算法在代码里、有测试、日志里能看到"为什么算成 4"。

### 越界二：用模板做数据校验

```go
# 反面教材
{{ if not (regexMatch "^[a-z][a-z0-9-]{2,30}$" .Name) }}
  {{ fail "name 不合法" }}
{{ end }}
```

`fail` 正是 Sprig 提供的函数，看起来恰到好处。问题是**校验规则现在有两份**：模板里一份、应用里一份（因为应用也要校验）。总有一天两边不一致，而模板那份是最后被发现的。

**正确形态**：应用校验完再传值；模板只负责排版。

### 越界三：用模板做"半个编程语言"

```go
{{- $result := dict -}}
{{- range $i, $item := .Items }}
  {{- if and (gt $item.Score 60) (not (hasKey $result $item.Group)) }}
    {{- $_ := set $result $item.Group $item -}}
  {{- end }}
{{- end }}
```

Sprig 提供了 `dict`、`set`、`list`、`append`、`merge`——足够在模板里实现数据结构。这已经不是"排版"了，是用一门没有类型检查、没有测试、错误信息极差的语言重写业务逻辑。

**正确形态**：`range .Groups`，分组在代码里做完。

## 那模板里适合放什么

- **排版**：循环、条件显示、格式化数字与日期
- **缺省值**：`default` 处理"可选项没填"
- **转义**：`b64enc`、`quote`、`indent`（这是 Sprig 最有价值的部分）
- **轻量字符串处理**：`trim`、`trunc`、`replace`

这些的共同点：**不需要测试就基本不会错，错了也能一眼看出来。**

## 常见误区

### 误区：模板里逻辑多写点，代码就能少改点

**你以为**：改模板比改代码风险小，所以逻辑尽量放模板。

**实际上**：模板**没有类型检查、没有单元测试、错误信息极差、改动的影响面是全量渲染产物**。它的风险比改一个纯函数高得多。

**所以**：模板适合"排版"，因为它出错时你会立刻看见（渲染出来就是不对）。而业务逻辑出错时，渲染结果是"看起来合理但是错的"——这是最难发现的一类 bug。

### 误区：学完 Sprig 就该多用它

**你以为**：这条线讲了 Sprig 的机制，那就是要学会用它的全部能力。

**实际上**：这条线真正想给的是**判断力**——看到任何模板函数库（Sprig、Jinja filters、Handlebars helpers）都知道它的机制与边界。

**所以**：四关下来最有用的不是"会用 100 个函数"，而是"知道什么时候不该用"。

## 这条线的收尾

回到第 1 关的那个机制：**FuncMap 是白名单**。

白名单越大，模板作者手边可用的工具越多，也越容易把模板写成程序。所以对一个模板引擎来说，"函数多不多"不是评价标准，**"边界清不清楚"才是**。

这也解释了为什么 Go 官方模板故意只给很少的内建函数：它希望你把逻辑写进代码。
