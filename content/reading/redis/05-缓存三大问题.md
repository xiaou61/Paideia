## 先把结论摆出来

三个词经常被混着说，但它们指的是**三种不同的失败**，解法也不一样：

| 问题 | 发生在哪 | 一句话 |
| --- | --- | --- |
| 穿透 | 查一个**根本不存在**的 key | 每次都绕过缓存打到库 |
| 击穿 | 一个**热点 key 正好过期** | 瞬时并发全砸向同一行数据 |
| 雪崩 | **大量 key 同时过期**或 Redis 挂了 | 整片流量压到数据库 |

判断方法很简单：**问"打到数据库的请求，查的是同一个 key 吗"**。是同一个 → 击穿；是很多个不同的不存在 key → 穿透；是很多个本来有值的 key 同时没了 → 雪崩。

## 穿透：查不存在的东西

典型场景：攻击者用不存在的 id 疯狂请求；或者业务上确实大量查询"查不到"的数据。

**为什么缓存救不了它**：缓存里本来就没有这个数据（因为它不存在），所以每次都会落到数据库，而数据库也查不到——但你付了每一次查询的成本。

三种解法，按代价从低到高：

1. **缓存空值**：查不到也写一个空标记，TTL 设短（比如 60 秒）。代价是"之后数据真的插入了，要等这个标记过期才能查到"，以及大量随机 key 会占内存；
2. **布隆过滤器**：把所有可能存在的 id 放进一个位图，查之前先问"这个 id 可能存在吗"。说不存在就直接返回。代价是有假阳性（说存在但实际没有），需要额外维护；
3. **参数校验**：id 必须是合法的、在你的取值范围内的。这一层最便宜，但只能挡住"明显非法"的请求。

**最实用的组合**：参数校验 + 缓存空值。布隆过滤器只在真的有大规模恶意流量时才值得上。

## 击穿：热点 key 过期的那一秒

场景：一个首页配置、一个爆款商品，QPS 很高，TTL 到期了。

那一瞬间，所有并发请求都发现"缓存没了"，然后一起去查数据库。**如果这个 key 的 QPS 是 5000，数据库立刻收到 5000 个相同查询。**

两种解法：

1. **互斥重建**：谁拿到锁谁去查库重建缓存，其他人短暂等待或返回旧值。这是最标准的做法；
2. **逻辑过期**：缓存里不设物理 TTL，而是存一个"逻辑过期时间"字段。读到过期的值就返回旧数据，同时异步触发一个线程去刷新。用户永远不等待，代价是短暂读到旧值。

**关键区别**：穿透是"查不到"，击穿是"有但刚好没了"，雪崩是"一大片同时没了"。

## 雪崩：大面积同时失效

两个成因：

1. **同一时刻批量写入的缓存，TTL 又设成同一个值** → 它们会在同一秒全部过期；
2. **Redis 本身挂了** → 所有缓存同时消失。

对应解法：

- **TTL 加随机抖动**。这是最便宜也最有效的一条：`ttl = 基础值 + random(0, 300秒)`，把过期时间打散；
- **多级缓存**：本地缓存（Caffeine）+ Redis。Redis 挂了本地还能挡一阵；
- **熔断降级**：数据库前面加限流，宁可返回"稍后再试"也不要让数据库被打挂。数据库一挂，整个系统就真的没了；
- **预热**：重启后先把热点数据灌进缓存，别让第一批用户去撞空缓存。

## 一个具体的判断流程

线上突然大量慢查询，怎么定位是哪一种？

```text
1. 看数据库慢日志里的 SQL：是不是同一个查询？
   - 是 → 击穿（或缓存没生效）
   - 否 → 继续
2. 这些查询的 key 在 Redis 里存在吗？
   - 都不存在 → 穿透（可能是攻击或脏参数）
   - 都存在但都过期了 → 雪崩
3. 看 Redis 是否重启过 / 内存是否达到 maxmemory
   - 是 → 雪崩的第二种成因
```

**先分清是哪一种，再选解法**——三者的解法互不通用，用错了会白干。

## 常见误区

### 误区：穿透、击穿、雪崩是一回事，都是"缓存失效"

**你以为**：都是缓存没命中，解法也差不多。
**其实**：三者触发条件不同：穿透是数据不存在、击穿是单点过期、雪崩是批量过期或 Redis 故障。解法完全不同——缓存空值对击穿没用，互斥重建对穿透也没用。
**怎么验证**：拿你的缓存代码，假设它失效了，问"打过来的请求是同一个 key 还是很多 key"——答案决定你该用哪套方案。

### 误区：加了缓存就高枕无忧

**你以为**：缓存命中率高，数据库就安全了。
**其实**：缓存的作用是"挡住绝大多数请求"，而不是"减少所有请求"。剩下的那部分（未命中、过期、故障）会**集中**打到数据库，冲击反而比没有缓存时更尖峰。
**怎么验证**：算一下缓存命中率 99%、QPS 1 万时，数据库还要扛多少——100 QPS 的尖峰集中在那几毫秒里。

### 误区：缓存和数据库双写，保证强一致

**你以为**：写的时候同时更新缓存和数据库，两边就一致了。
**其实**：两个写操作不是一个原子事务，中间任何一步失败都会造成不一致；并发下还可能出现"后写的旧值覆盖先写的新值"。业界主流做法是**先更新数据库，再删除缓存**，接受短暂不一致。
**怎么验证**：模拟两个并发写同一 key，观察缓存和库里的值是否可能不同。
