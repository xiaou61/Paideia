## 先把结论摆出来

**五种类型不是"五种存法"，是五种访问方式。选类型的标准只有一个：你最常做的那类操作，能不能用一条命令完成。**

| 类型 | 一句话 | 典型用途 |
| --- | --- | --- |
| string | 一个键对一个值，值可以是数字 | 缓存对象、计数器、限流 |
| hash | 一个键对一张小表 | 存对象的多个字段，单独改其中一个 |
| list | 一个两端都能进出的链表 | 时间线、最近 N 条、简单队列 |
| set | 不重复、无序的集合 | 去重、共同好友、抽奖 |
| zset | 带分数排序的集合 | 排行榜、延时队列、按时间范围取 |

一个判断方法：**如果为了完成一个操作要"取出来、在代码里改、再写回去"，说明类型选错了。** 三条命令的窗口期里，别的请求可能已经改过它。

## string：不只是字符串

string 是最基础的类型，值是二进制安全的字节串——所以能存文本、能存序列化后的 JSON、能存图片。单个值最大 512 MB。

它真正的特殊之处是**能当数字用**：

```bash
redis-cli SET stock:1001 50
redis-cli DECR stock:1001      # 49
redis-cli DECRBY stock:1001 10 # 39
redis-cli SETNX lock:1001 1    # 只在键不存在时写入
redis-cli SET lock:1001 1 NX PX 3000   # 不存在才写 + 3 秒后过期（一条命令）
```

`INCR` / `DECR` / `SETNX` / `SET NX PX` 都建立在"单条命令原子"上，所以可以直接拿来做计数器、库存扣减、锁。**换成先读后写就全废了。**

另一个冷门命令是 `SETRANGE key 0 "Hello"`：从指定偏移覆盖字符串。偏移很大时会用零字节补齐中间的空洞，所以它既能"预分配"，也能一次撑爆内存。

## hash：一张小表

hash 是"键 → 字段 → 值"的两级结构，适合存一个对象的多个属性，并且**只想改其中一两个**。

```bash
redis-cli HSET user:1001 name "张三" age 28 city "杭州"
redis-cli HGET user:1001 name       # "张三"
redis-cli HINCRBY user:1001 age 1   # 29
redis-cli HMGET user:1001 name city
redis-cli HDEL user:1001 city
```

对比一下：如果用一个 string 存整个 JSON，改 `age` 就得 `GET` → 反序列化 → 改 → 序列化 → `SET`。这中间别人改的字段会被你的旧副本覆盖掉。hash 的 `HSET` 只碰那一个字段。

hash 也有边界：**字段多了以后 `HGETALL` 会一次性返回全部**，这是第一篇说的大 key 问题。字段成千上万时用 `HSCAN` 分批，或者拆成多个 hash。

## list：两端进出，但别当正经队列用

list 是双向链表（小的时候底层是紧凑数组），两端插入删除都是 O(1)。

```bash
redis-cli RPUSH feed:1001 "post-1" "post-2" "post-3"
redis-cli LRANGE feed:1001 0 9      # 取最新 10 条
redis-cli LTRIM feed:1001 0 999     # 只保留前 1000 条，其余丢掉
redis-cli LPOP feed:1001
redis-cli BLPOP queue:mail 5        # 阻塞 5 秒等一个元素
```

`RPUSH` + `LTRIM` 是"最近 N 条"的标准写法：写入和裁剪各一条命令，集合大小永远是常数。

**用 list 当队列的坑在消费端**：

- `LPOP` 弹出后，如果消费者在处理时崩溃，这条消息就永久丢了——Redis 不会还给你；
- 想要"处理完再确认"，list 没有这个概念，得用 `RPOPLPUSH` 到一个"处理中"的 list，再自己搬回来；
- 一个 list 只能被一个消费者组用，多个消费者要靠 `BLPOP` 抢，但**没有确认、没有重试、没有死信**。

所以：**list 适合"最近 N 条"，不适合"必须处理一次的消息队列"。** 真要队列语义，Redis 5.0 之后用 Stream（`XADD` / `XREADGROUP` / `XACK`），它才有消费组和确认机制。

## set：去重与集合运算

set 无序、不重复，适合"这个元素在不在"和"两个集合怎么交并差"。

```bash
redis-cli SADD post:1001:likes 101 102 103
redis-cli SISMEMBER post:1001:likes 102   # 1，在
redis-cli SCARD post:1001:likes           # 3，点赞数
redis-cli SADD post:1002:likes 102 104
redis-cli SINTER post:1001:likes post:1002:likes   # 102，都点了赞
redis-cli SDIFF post:1001:likes post:1002:likes    # 101 103
redis-cli SRANDMEMBER post:1001:likes 1            # 随机抽一个，不删除
redis-cli SPOP post:1001:likes                     # 随机弹出一个，删除
```

`SISMEMBER` 是 O(1)——它靠一个哈希表实现，这也是 set 占内存比 list 多的原因（每个元素都要存哈希索引）。

**抽奖用 `SPOP` 还是 `SRANDMEMBER`**：前者抽中即移除（不重复中奖），后者不移除（可重复）。选错会让同一个人中两次。

## zset：带分数的集合

zset 的每个元素带一个分数（score），元素按分数排序。底层是**跳表 + 哈希表**：跳表负责按分数范围取数，哈希表负责按元素名 O(1) 查分数。

```bash
redis-cli ZADD rank 100 "alice" 250 "bob" 180 "carol"
redis-cli ZREVRANGE rank 0 2 WITHSCORES   # 从高到低取前三
redis-cli ZSCORE rank "bob"               # "250"
redis-cli ZINCRBY rank 30 "alice"         # 130，原子加 30
redis-cli ZRANK rank "carol"              # 从小到大排第几
redis-cli ZRANGEBYSCORE rank 150 300      # 分数在区间内的元素
```

三种用法值得记住：

1. **排行榜**：`ZINCRBY` 加分、`ZREVRANGE` 取前 N。整个过程不需要把全量数据取出来排序；
2. **按时间取范围**：把时间戳当分数，`ZRANGEBYSCORE` 取某个时间段；
3. **延时队列**：把"到期时间戳"当分数，消费者用 `ZRANGEBYSCORE key 0 <now>` 取到期任务，取到后删掉。

第 3 种有一个隐蔽问题：**取和删是两条命令**，两个消费者可能取到同一批任务。要么用 Lua 把"取+删"合成一次执行，要么接受重复执行、让业务幂等。

## 一个具体例子：同一份数据，三种存法

存一个用户的资料，改 `age` 这一件事，三种存法的代价完全不同：

| 存法 | 改 age 需要 | 问题 |
| --- | --- | --- |
| `SET user:1001 '{...整份JSON...}'` | GET → 改 → SET | 并发下会覆盖别人改的字段 |
| `HSET user:1001 age 29` | 一条命令 | 无 |
| 每个字段一个 key | `SET user:1001:age 29` | key 数量爆炸，取整份要多次往返 |

## 常见误区

### 误区：五种类型只是存法不同，随便挑一个能存就行

**你以为**：反正都能存字符串，用 string 最通用。
**其实**：类型决定了哪些操作能用一条命令完成。用 string 存集合，做"在不在"就要把整个集合取出来在应用里判断——既慢又存在竞态。
**怎么验证**：用 string 存 100 万个用户 ID 做去重，再看 `SMEMBERS` / `SISMEMBER` 的耗时对比。

### 误区：list 就是队列

**你以为**：`RPUSH` 进、`LPOP` 出，这就是队列。
**其实**：它只保证了"先进先出"这个顺序，没保证"每条被处理一次"。消费者崩溃、处理失败、需要重试、需要多消费者分组，list 全都没有。
**怎么验证**：写一个消费者，`LPOP` 之后 `kill -9`，再看那条消息还在不在。

### 误区：zset 的分数只能是整数

**你以为**：score 是整数，所以只能用来排名次。
**其实**：score 是双精度浮点数，可以放时间戳、权重、任何能比较大小的数。放时间戳就变成了按时间排序的索引。
**怎么验证**：`ZADD t 1750000000.5 "a"`，再 `ZRANGEBYSCORE t -inf +inf WITHSCORES` 看返回值。

## 小结

五种类型对应五种访问方式：string 做计数与整份读写，hash 做字段级更新，list 做"最近 N 条"，set 做去重与集合运算，zset 做排序与范围查询。判断标准是"核心操作能不能一条命令完成"。list 不是可靠队列，需要确认与重试就用 Stream。
