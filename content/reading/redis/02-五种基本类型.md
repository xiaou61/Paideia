## 同一个 key，先 listpack，后 skiplist

```text
127.0.0.1:6398> DEL demo:z
(integer) 1
127.0.0.1:6398> ZADD demo:z 1 alice 2 bob
(integer) 2
127.0.0.1:6398> TYPE demo:z
zset
127.0.0.1:6398> OBJECT ENCODING demo:z
"listpack"
```

再往里加到 129 个成员：

```bash
# bash / Git Bash；PowerShell 可用 3..129 | ForEach-Object { ... }
for i in $(seq 3 129); do
  redis-cli -p 6398 ZADD demo:z "$i" "m$i" > /dev/null
done
```

```text
127.0.0.1:6398> ZCARD demo:z
(integer) 129
127.0.0.1:6398> OBJECT ENCODING demo:z
"skiplist"
```

同一个 key，`TYPE` 两次都是 `zset`，`OBJECT ENCODING` 却从 `listpack` 变成了 `skiplist`。类型是逻辑接口，编码是物理实现；编码会随着元素数量、元素大小和配置变化，甚至同一个 key 在运行中切换。

129 不是巧合。这台 `redis-server 8.6.2`（MSYS/libc 构建）上：

```text
127.0.0.1:6398> CONFIG GET zset-max-listpack-entries
1) "zset-max-listpack-entries"
2) "128"
```

7.0 起 `ziplist` 已被 `listpack` 取代（官方版本变更；本机没见到 `ziplist`）。后面每种类型都带着自己的编码开关，先记住一条：**选类型看你要什么操作，编码由数据量和配置决定，不要背死某个结构。**

下面的实测都来自 `127.0.0.1:6398` 的临时实例，启动参数是 `--save "" --appendonly no`；测完用 `SHUTDOWN NOSAVE` 关掉。`DEBUG OBJECT` 默认可能被禁用，我这次额外加了 `--enable-debug-command yes`。

## 按操作选类型，不是按「能存什么」

| 类型 | 一条命令能完成的核心操作 | 常见用途 |
| --- | --- | --- |
| string | 原子加减、整值读写、按范围覆盖 | 计数、缓存、锁、限流 |
| hash | 改单个字段、取多个字段 | 对象属性、配置、用户资料 |
| list | 两端进出、按范围取、保留最近 N 条 | 时间线、最近列表、简单队列 |
| set | 去重、判断存在、交并差 | 标签、点赞去重、抽奖 |
| zset | 按分数排序、按分数范围取、排名 | 排行榜、延时队列、时间索引 |

判断方法还是这一条：**如果为了完成一个操作要「取出来、在代码里改、再写回去」，先怀疑类型选错了。** 三条命令的窗口里，别的请求可能已经改过它。例外当然有，比如整份文档本来就要一起改；那就别指望 Redis 帮你解决并发覆盖，得自己加版本号或锁。

## string：字节串，不是 C 字符串

先看值的编码：

```text
127.0.0.1:6398> SET s:int 100
OK
127.0.0.1:6398> OBJECT ENCODING s:int
"int"
127.0.0.1:6398> SET s:short hello
OK
127.0.0.1:6398> OBJECT ENCODING s:short
"embstr"
127.0.0.1:6398> SET s:long xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
OK
127.0.0.1:6398> OBJECT ENCODING s:long
"raw"
```

`int`、`embstr`、`raw` 是同一个 string 类型的三种值编码，不是三种类型。能写成 64 位整数的值会用 `int`；再大就按字符串存，比如 `SET s:bigint 12345678901234567890` 在这台机器上是 `embstr`。

string 的底层是 SDS（Simple Dynamic String，简单动态字符串），不是 C 字符串。差别不在名字：

- SDS 头里存长度，`STRLEN` 直接读头，不需要一路扫到 `\0`；标准实现是 O(1)，我没做规模计时；
- 因为按长度而不是 `\0` 判断结尾，它能存二进制。实测 `EVAL "return redis.call('SET', KEYS[1], string.char(97,0,98))" 1 bin` 之后，`STRLEN bin` 返回 `3`，`GET bin` 的字节是 `61 00 62`，中间的 `00` 没有被截断；
- 单个 value 上限是 512MB（官方文档；我没分配这么大的值去撞上限）。

C 字符串存 `a\0b` 会在 `\0` 处结束；SDS 不会。缓存序列化后的 JSON、图片、压缩包都靠这一点。

string 真正特殊的是能当数字用：

```text
127.0.0.1:6398> SET stock:1001 50
OK
127.0.0.1:6398> DECR stock:1001
(integer) 49
127.0.0.1:6398> DECRBY stock:1001 10
(integer) 39
127.0.0.1:6398> SETNX lock:1001 1
(integer) 1
127.0.0.1:6398> SETNX lock:1001 1
(integer) 0
127.0.0.1:6398> SET lock:1002 1 NX PX 3000
OK
```

`INCR` / `DECR` / `SETNX` / `SET NX PX` 都靠单条命令的原子性。换成先 `GET`、在应用里算、再 `SET`，两个请求就会丢一次更新。`SETRANGE key 0 "Hello"` 从指定偏移覆盖；偏移很大时中间用零字节补齐，所以它能预分配，也能一次撑大内存。

| 操作 | 时间复杂度 | 编码（小/大） | 选它 / 别选 |
| --- | --- | --- | --- |
| `SET` / `GET` | O(1) | `int` / `embstr` / `raw`，按值和长度分 | 缓存、标志位、整份读写 |
| `INCR` / `DECR` | O(1) | 数字用 `int`，超出范围转字符串 | 计数、库存；别用 GET→改→SET |
| `STRLEN` | O(1) | 读 SDS 头 | 取字节长度 |
| `MGET` | O(N) | 同上 | 一次取多个；N 大时拆批 |
| `SETRANGE` | O(M)，M 是写入长度 | 多为 `raw` | 覆盖/预分配；偏移大时中间补零，别拿来省内存 |

自己验证：`OBJECT ENCODING key` 看值编码，`STRLEN key` 看字节数，`MEMORY USAGE key` 看这个 key 的大致占用；`DEBUG OBJECT key` 还能看到 `encoding` 和 `serializedlength`。

## hash：字段级更新，省的是 key 和往返

```text
127.0.0.1:6398> HSET user:1001 name 张三 age 28 city 杭州
(integer) 3
127.0.0.1:6398> HGET user:1001 name
"张三"
127.0.0.1:6398> HINCRBY user:1001 age 1
(integer) 29
127.0.0.1:6398> HMGET user:1001 name city
1) "张三"
2) "杭州"
127.0.0.1:6398> HDEL user:1001 city
(integer) 1
```

小 hash 的编码是 `listpack`，不是「一个字段一个哈希节点」：

```text
127.0.0.1:6398> HSET h:small name 张三 age 28
(integer) 2
127.0.0.1:6398> OBJECT ENCODING h:small
"listpack"
```

字段多了或者单个值长了，才转 `hashtable`。默认值要看版本：Redis 7.x 是 128 个字段 / 64 字节；这台 8.6.2 的 `CONFIG GET` 读数是 512 个字段 / 64 字节：

```text
127.0.0.1:6398> CONFIG GET hash-max-listpack-entries
1) "hash-max-listpack-entries"
2) "512"
127.0.0.1:6398> CONFIG GET hash-max-listpack-value
1) "hash-max-listpack-value"
2) "64"
```

我把 `hash-max-listpack-entries` 临时设回 128，再塞 129 个字段，编码就变成 `hashtable`；默认 512 时，512 个字段还是 `listpack`，513 个才变。单个值也是同理：64 字节还是 `listpack`，65 字节转 `hashtable`。

hash 比「一个字段一个 key」省，省的是 key 头和多次往返。我拿 200 个短字段 `f1..f200` / `v1..v200` 做对照：

```text
HSET h:user200 f1 v1 ... f200 v200   # 实际是 200 条 HSET
MEMORY USAGE h:user200                         -> 2227
同一个对象存成紧凑 JSON string，MEMORY USAGE   -> 2630
200 个独立 key，逐个 MEMORY USAGE 相加          -> 7584
```

hash 是 `listpack`，JSON 是 `raw`，200 个 key 是 200 个独立对象。`MEMORY USAGE` 不含全局字典等开销，但方向很清楚：**hash 的占用约为 200 个 key 的 1/3.4；比整份 JSON 也略省，真正的好处是改一个字段只碰一个字段。**

字段多了以后，`HGETALL` 会一次返回全部。我建了 1000 个字段的 hash：

```bash
redis-cli -p 6398 HLEN h:1000                                  # (integer) 1000
redis-cli -p 6398 --raw HGETALL h:1000 | wc -l                # 2000
redis-cli -p 6398 --raw HSCAN h:1000 0 COUNT 10 | wc -l       # 23
```

`HGETALL` 是 1000 对字段/值，所以 2000 行；`HSCAN` 这一批只给了 11 对，23 行里包含 1 个游标。字段上千时用 `HSCAN` 分批，不要每次都把整张表塞进一个回复。

| 操作 | 时间复杂度 | 编码（小/大） | 选它 / 别选 |
| --- | --- | --- | --- |
| `HSET` / `HGET` / `HDEL` | O(1) 平均（`hashtable`）；`listpack` 下 O(N) 线性 | `listpack` → `hashtable` | 对象字段级更新 |
| `HMGET` | O(N) | 同上 | 一次取多个字段 |
| `HGETALL` | O(N) | 同上 | 小 hash；字段多时别一次取 |
| `HSCAN` | 每次 O(1) 摊还，整体 O(N) | 同上 | 大 hash 遍历 |
| `HINCRBY` | O(1) 平均 | 同上 | 字段计数 |

自己验证：`OBJECT ENCODING key`、`CONFIG GET hash-max-listpack-*`、`MEMORY USAGE key`；字段多时用 `HSCAN` 而不是 `HGETALL`。`DEBUG OBJECT key` 能看到 `encoding`，但不会告诉你每个字段多大。

## list：两端进出，但没有消费者组

```text
127.0.0.1:6398> RPUSH feed:1001 post-1 post-2 post-3
(integer) 3
127.0.0.1:6398> LRANGE feed:1001 0 9
1) "post-1"
2) "post-2"
3) "post-3"
127.0.0.1:6398> LTRIM feed:1001 0 999
OK
127.0.0.1:6398> LPOP feed:1001
"post-1"
127.0.0.1:6398> BLPOP queue:mail 5
(nil)
```

小 list 的编码是 `listpack`，不是「紧凑数组」；大了转 `quicklist`。`quicklist` 是双向链表，每个节点是一个 `listpack`。7.0 起 `ziplist` 被 `listpack` 取代（官方版本变更）。

这里有个容易背错的边界。129 个短元素在这台机器上仍然是 `listpack`：

```text
127.0.0.1:6398> LLEN l:short
(integer) 129
127.0.0.1:6398> OBJECT ENCODING l:short
"listpack"
```

因为 `list-max-listpack-size` 是 `-2`，按约 8KB 一个节点算，不是「到 128 个元素就换」。换成 129 个 100 字节的值：

```text
127.0.0.1:6398> OBJECT ENCODING l:big
"quicklist"
127.0.0.1:6398> DEBUG OBJECT l:big
Value at:0xa00134308 ... encoding:quicklist ... ql_nodes:2 ql_avg_node:64.50 ql_listpack_max:-2 ql_compressed:0 ql_uncompressed_size:13301
```

地址每次都会变，只看 `encoding`、`ql_nodes`、`ql_listpack_max` 这些字段。这台实例的配置是：

```text
127.0.0.1:6398> CONFIG GET list-max-listpack-size
1) "list-max-listpack-size"
2) "-2"
```

不要把 128 当固定值。

### list 不是可靠队列

`LPOP` / `BLPOP` 弹出即删除。消费者拿到消息后崩溃，这条消息不会自动回来；list 没有 ack、没有重试、没有死信。我在这台实例上验证了它不是「一个 list 只能被一个消费者组用」——list 根本没有消费者组这个概念：

```text
127.0.0.1:6398> XGROUP CREATE feed:1001 g 0
(error) WRONGTYPE Operation against a key holding the wrong kind of value
127.0.0.1:6398> XPENDING feed:1001 g
(error) WRONGTYPE Operation against a key holding the wrong kind of value
```

多个消费者只能靠 `BLPOP` / `BRPOP` 抢；抢到的那一个把元素拿走，其他消费者看不到，也没有「处理中」状态。可以用 `LMOVE` 把元素搬到另一个 processing list 模拟，但超时回收、重试、死信、消费者分组都得自己写。

消费者组是 Stream 的能力。同一个实例上，Stream 接受 `XGROUP CREATE`，`XACK` 也能正常返回：

```text
127.0.0.1:6398> XADD st 1-0 f v
"1-0"
127.0.0.1:6398> XGROUP CREATE st g 0
OK
127.0.0.1:6398> XACK st g 1-0
(integer) 1
```

所以：**list 适合「最近 N 条」和「两端进出」；需要确认、重试、死信，用 Stream（`XADD` / `XREADGROUP` / `XACK`），不要拿 list 硬凑。**

| 操作 | 时间复杂度 | 编码（小/大） | 选它 / 别选 |
| --- | --- | --- | --- |
| `RPUSH` / `LPUSH` | O(1) | `listpack` → `quicklist` | 最近 N 条、两端进出 |
| `LPOP` / `RPOP` | O(1) | 同上 | 简单队列；消费者崩溃会丢 |
| `LRANGE` | O(S+N)，S 是偏移 | 同上 | 范围读取；大范围慎用 |
| `LTRIM` | O(N) 删除元素 | 同上 | 保留最近 N |
| `BLPOP` / `BRPOP` | O(1) 等待，抢到即删 | 同上 | 多消费者抢；无 ack |
| `LINDEX` | O(N) | 同上 | 别用长 list 随机下标 |

自己验证：`OBJECT ENCODING key`、`DEBUG OBJECT key` 看 `ql_nodes`、`LLEN key` 看长度；队列语义用 `LPOP` 后马上 `LLEN`，再看能不能找到「处理中」列表。

## set：去重，但 SISMEMBER 不总是 O(1)

```text
127.0.0.1:6398> SADD post:1001:likes 101 102 103
(integer) 3
127.0.0.1:6398> SISMEMBER post:1001:likes 102
(integer) 1
127.0.0.1:6398> SCARD post:1001:likes
(integer) 3
127.0.0.1:6398> SADD post:1002:likes 102 104
(integer) 2
127.0.0.1:6398> SINTER post:1001:likes post:1002:likes
1) "102"
127.0.0.1:6398> SDIFF post:1001:likes post:1002:likes
1) "101"
2) "103"
```

set 至少有三档编码，`SISMEMBER` 的复杂度跟着编码走：

```text
127.0.0.1:6398> SADD set:int 1 2 3
(integer) 3
127.0.0.1:6398> OBJECT ENCODING set:int
"intset"
127.0.0.1:6398> SADD set:str apple banana cherry
(integer) 3
127.0.0.1:6398> OBJECT ENCODING set:str
"listpack"
127.0.0.1:6398> SADD set:str129 m1 ... m129   # 实际是 129 个成员
(integer) 129
127.0.0.1:6398> OBJECT ENCODING set:str129
"hashtable"
```

- 小整数集合是 `intset`：有序数组 + 二分，`SISMEMBER` 是 O(log N)；
- 7.2+ 的小规模非整数集合可以用 `listpack`：线性扫描，`SISMEMBER` 是 O(N)；
- 只有 `hashtable` 编码才是哈希索引，`SISMEMBER` 是 O(1) 平均。

这台 8.6.2 的配置是 `set-max-intset-entries 512`、`set-max-listpack-entries 128`、`set-max-listpack-value 64`；换版本先 `CONFIG GET` 看一眼。

「`SISMEMBER` 是 O(1)」这句话只对 `hashtable` 成立，不能当 set 的类型属性。

内存也一样。「set 一定比 list 费内存」不成立，编码决定：

```text
512 个整数：  set 1070 B（intset）   list 1455 B（listpack）
1000 个整数： set 37180 B（hashtable）list 2920 B（listpack）
100 个短字符串：set 537 B（listpack） list 538 B（listpack）
```

512 个整数时 set 反而少 385 字节；到 1000 个，set 转成 `hashtable`，才变成 list 的约 12.7 倍。100 个短字符串两者几乎一样。**不是「set 比 list 费」，是「hashtable 编码比 listpack 费」。**

| 操作 | 时间复杂度 | 编码（小/大） | 选它 / 别选 |
| --- | --- | --- | --- |
| `SADD` / `SREM` | O(1) 平均（`hashtable`）；`intset` / `listpack` 下 O(N) | `intset` / `listpack` → `hashtable` | 去重、标签 |
| `SISMEMBER` | O(1) 平均（`hashtable`）；O(log N)（`intset` 二分）；O(N)（`listpack` 线性） | 同上 | 存在性；大集合用 `hashtable` |
| `SCARD` | O(1) | 同上 | 基数 |
| `SINTER` / `SDIFF` | `SINTER` 最坏 O(N*M)；`SDIFF` O(N) | 同上 | 小集合交并差；大集合先算代价 |
| `SPOP` | O(1) 平均 | 同上 | 抽奖不重复；不是队列 |
| `SRANDMEMBER` | 不带 count O(1)，带 count O(N) | 同上 | 可重复抽 |

自己验证：`OBJECT ENCODING key`、`CONFIG GET set-max-intset-entries set-max-listpack-entries set-max-listpack-value`、`MEMORY USAGE key`。`SISMEMBER` 的复杂度不要凭感觉，先看编码。

## zset：分数是 double，小的时候也没有跳表

```text
127.0.0.1:6398> ZADD rank 100 alice 250 bob 180 carol
(integer) 3
127.0.0.1:6398> ZREVRANGE rank 0 2 WITHSCORES
1) "bob"
2) "250"
3) "carol"
4) "180"
5) "alice"
6) "100"
127.0.0.1:6398> ZSCORE rank bob
"250"
127.0.0.1:6398> ZINCRBY rank 30 alice
"130"
127.0.0.1:6398> ZRANK rank carol
(integer) 1
```

开头那个 `demo:z` 已经展示了 zset 的两档编码：128 个成员还是 `listpack`，129 个变 `skiplist`。小的时候没有跳表，也没有那个 member→score 的字典；大的时候才是 **skiplist + 一个 member→score 的字典（hashtable）**。`OBJECT ENCODING` 只显示 `skiplist`，字典是 zset 对象的一部分。

`zset-max-listpack-entries` 默认 128，`zset-max-listpack-value` 默认 64（这台实测）。成员长度到 64 字节还是 `listpack`，65 字节就转 `skiplist`。

score 是 double，不是整数。下面这个不是理论：

```text
127.0.0.1:6398> ZADD z:double 0.1 a
(integer) 1
127.0.0.1:6398> ZINCRBY z:double 0.2 a
"0.30000000000000004"
```

把时间戳当 score 可以做按时间范围取；但别拿 score 当金额或精确 ID，浮点会出现这种尾巴。`ZADD z:nan nan a` 也会直接报 `ERR value is not a valid float`。

延时队列的经典写法是把到期时间戳当 score，用 `ZRANGEBYSCORE key 0 <now>` 取到期任务。这里有一个真实的竞态：**取和删是两条命令**，两个消费者可能取到同一批任务。要么用 Lua 把「取 + 删」合成一次执行，要么接受重复执行、让业务幂等。`ZPOPMIN` 能原子弹出最低分的元素，但它不是按范围取，不能直接替代。

| 操作 | 时间复杂度 | 编码（小/大） | 选它 / 别选 |
| --- | --- | --- | --- |
| `ZADD` / `ZINCRBY` | O(log N)（`skiplist`）；O(N)（`listpack`） | `listpack` → `skiplist` + dict | 排行榜、按分数范围 |
| `ZSCORE` | O(1)（dict）；O(N)（`listpack`） | 同上 | 查单个分数 |
| `ZRANK` | O(log N)；O(N)（`listpack`） | 同上 | 排名 |
| `ZRANGEBYSCORE` | O(log N + M) | 同上 | 时间范围、到期任务 |
| `ZREVRANGE` | O(log N + M) | 同上 | 取前 N |
| `ZREM` | O(log N) | 同上 | 删除 |

自己验证：`OBJECT ENCODING key`、`CONFIG GET zset-max-listpack-*`、`DEBUG OBJECT key`；score 用 `ZSCORE` 看返回值，别用 `ZRANGE` 的输出猜。去重成本用 `MEMORY USAGE zset:100` 和 `MEMORY USAGE set:strs100` 对照。

只需要去重、不需要顺序时，set 更直接。100 个相同的短成员，`MEMORY USAGE` 在这台机器上是 zset 734 B、set 537 B，zset 多出约 37%——多存的就是分数和排序结构。

`EXPIRE` / `TTL`、过期删除和淘汰策略放到第 3 篇；这里先不把 `EXPIRE` 当可靠的定时任务。

## 同一份数据，三种存法

存一个用户资料，改 `age` 这一件事，三种存法的代价不同。下面 200 个短字段的数字是同一台实例上的对照，不是真实用户数据：

| 存法 | 改一个字段需要 | 200 个短字段的 `MEMORY USAGE` | 问题 |
| --- | --- | --- | --- |
| `SET user:json200 <整份 JSON>` | GET → 改 → SET | 2630 B | 并发下会覆盖别人改的字段 |
| `HSET h:user200 f1 29` | 一条 HSET | 2227 B | `HGETALL` 全取；字段多时用 `HSCAN` |
| 每个字段一个 key | `SET user:1001:age 29` | 7584 B（200 个 key 相加） | key 数量多，取整份要多次往返 |

我用两个「客户端」模拟了丢更新：两边都读到 `{"name":"张三","age":28,"city":"杭州"}`，A 把 age 改成 29 写回，B 用旧副本把 city 改成 上海 写回。最后：

```text
{"name":"张三","age":28,"city":"上海"}
```

A 的 age 被 B 的旧副本覆盖了。换成 hash，`HSET user:hash age 29` 和 `HSET user:hash city 上海` 各改各的字段，最后两个都在。这就是「字段级更新」的实际价值，不是 hash 一定比 JSON 省多少内存。

## 五个用错类型的例子

1. **用 string 存可变文档，改一个字段。** 就是上面的丢更新：两个客户端都拿旧 JSON 写回，后写的把先写的字段覆盖。要字段级并发更新，用 hash；要整份文档的并发控制，自己加版本号或 `WATCH`，别指望 `GET` + `SET` 这组操作变原子。
2. **用 list 当「必须处理一次」的队列。** `LPOP` 弹出即删除；消费者崩了消息就没了。`XGROUP CREATE` 对 list 直接报 `WRONGTYPE`，因为它没有消费者组。需要 ack/重试/死信，用 Stream。
3. **用 set 当「最近 N 条」。** set 没有顺序。我 `SADD news:set a b c` 后 `SPOP` 拿到 `b`，剩下 `a c`；它不会按加入时间给你最新的一条。最近 N 条用 list 的 `RPUSH` + `LTRIM`，或者用 zset 把时间戳当分数。
4. **用 hash 当超大对象，直接 `HGETALL`。** 1000 个字段一次返回 2000 行；字段越多，回复越大，单线程拼回复时别的命令只能等。字段多时用 `HSCAN` 分批，或者按业务拆成多个 hash。
5. **用 list 做去重/存在性判断。** `RPUSH seen:list a a b` 之后 `LLEN` 是 3；`SADD seen:set a a b` 之后 `SCARD` 是 2。list 不保证唯一，`LPOS` 还是 O(N)；去重用 set，存在性用 `SISMEMBER`。

## SCAN 是遍历，不是快照

在一台有 20,005 个 key 的临时实例上：

```text
127.0.0.1:6398> DBSIZE
(integer) 20005
127.0.0.1:6398> SCAN 0 COUNT 10
1) "5120"
2) 1) "scan:01862"
   2) "scan:13156"
   ... 共 11 个 key
```

`COUNT 10` 给了 11 个 key。`COUNT` 是提示，不是上限，也不保证每批一样多。`SCAN 0 COUNT 1000` 这一批给了 1000 个 key；遍历要拿着返回的游标继续，直到游标回到 `0`。

`SCAN` 的保证和「快照」不是一回事（官方语义）：

- 从开始到结束都在集合里的元素，完整遍历至少会返回一次；
- 遍历过程中可能重复返回同一个元素；
- 不保证一致快照：遍历时新增、删除、修改的元素，可能看到，也可能看不到。

「可能重复」我没有在 rehash 过程中构造出来，见「还差的」。但不要把它当 `SELECT` 那样的快照用。

`KEYS` 是另一回事：

```text
127.0.0.1:6398> KEYS 'scan:*'
... 20000 个 key
127.0.0.1:6398> INFO commandstats
cmdstat_keys:calls=1,usec=6318,usec_per_call=6318.00,rejected_calls=0,failed_calls=0
```

20,005 个 key 的一次 `KEYS 'scan:*'` 用了 6,318 微秒服务端时间；这段时间单线程 Redis 不处理别的命令。生产环境不要用 `KEYS`，用 `SCAN` / `HSCAN` / `SSCAN` / `ZSCAN`。PowerShell 下把 pattern 用单引号包住，`KEYS '*'` 可能先被 shell 展开；我上面的 `KEYS 'scan:*'` 是带引号跑的。

| 命令 | 复杂度 | 说明 |
| --- | --- | --- |
| `KEYS pattern` | O(N) | 遍历整个库并阻塞，生产禁用 |
| `SCAN cursor COUNT n` | 每次 O(1) 摊还，整体 O(N) | `COUNT` 是提示；可能重复；非快照 |
| `HSCAN` / `SSCAN` / `ZSCAN` | 同上 | 大 hash / set / zset 用这些 |

自己验证：`SCAN 0 COUNT 10` 看这一批给几个；`SCAN` 一直走到游标 0，统计是否漏 key；`INFO commandstats` 看 `KEYS` 的实际服务端耗时。只在临时实例上跑 `KEYS`，别在生产上试。

## 还差的

- 编码边界只在 Redis 8.6.2 上跑过。7.0 的 `ziplist`→`listpack`、7.2 的 set `listpack`、7.x 的 hash 默认 128，都是按版本说明写的，没在旧版本复测；你的实例先用 `CONFIG GET` 看实际值。
- `STRLEN` 的 O(1) 和 512MB 上限来自 SDS 实现/官方文档。我只验证了含 `\0` 的值能存、`STRLEN` 返回 3，没有分配 512MB 去撞上限，也没有做 10 字节 vs 10MB 的计时对比。
- `SCAN` 的「可能重复、不保证一致快照」是官方语义；我没有在 rehash 过程中构造出重复 key。`KEYS` 只测了 20,005 个 key / 6.3ms，没测百万级。
- Stream 只验证了 `XGROUP CREATE`、`XREADGROUP`、`XACK` 这条最小链路；PEL 超时认领、重试、死信没有写。
- `SINTER` / `ZRANGEBYSCORE` 的复杂度按文档，没有做规模计时。`MEMORY USAGE` 的数字受 key 名和 allocator 影响，换台机器会差几字节。
