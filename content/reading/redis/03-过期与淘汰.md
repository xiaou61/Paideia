## 先把结论摆出来

**`EXPIRE` 设了时间，键也不会到点就消失；内存满了之后，Redis 会主动删键——按什么规则删，由 `maxmemory-policy` 决定。**

三句话概括这一篇：

1. **过期是"懒删除 + 定期抽查"**，不是定时器。所以过期的键可能还占着内存；
2. **内存满了不是报错，是删东西**。默认策略会删掉"最近最少使用"的键，删到能塞进新数据为止；
3. **正因为会删，Redis 不能当唯一存储**。没有淘汰策略兜底的数据，随时可能消失。

## TTL 是怎么工作的

```bash
redis-cli SET session:abc token123 EX 60   # 写入时就带 60 秒过期
redis-cli TTL session:abc                  # 还剩几秒，-1 没有过期时间，-2 键不存在
redis-cli EXPIRE session:abc 120           # 改成 120 秒
redis-cli PERSIST session:abc              # 去掉过期时间，变永久
```

`TTL` 返回 `-1` 和 `-2` 是两件完全不同的事：`-1` 是"这个键在，但没有过期时间"，`-2` 是"这个键已经不在了"。排查"缓存为什么永远不失效"时，先看是不是 `-1`。

过期时间记的是**绝对时间戳**（毫秒），不是倒计时。所以主从复制、RDB 落盘时同步的是这个时间戳。

## 两种删除方式：惰性 + 定期

如果给每个键配一个定时器，一千万个键就是一千万个定时器，光管理它们就吃满 CPU。Redis 用的是两个更便宜的办法：

**惰性删除（lazy）**：只有当这个键被访问时，才检查它是否过期，过期就删掉再返回"不存在"。省 CPU，但没人访问的过期键会一直占内存。

**定期删除（active）**：每秒执行 10 次（`hz` 默认 10），每次随机抽 20 个带过期时间的键，删掉其中已过期的。如果这一轮里过期键占比超过 25%，就立刻再来一轮。

```bash
redis-cli CONFIG GET hz               # 每秒的定期任务次数
redis-cli INFO keyspace               # 每个库有多少键、多少带过期时间
redis-cli DBSIZE
```

第二条的 `expires` 字段很有用：`keys=1000,expires=998` 说明几乎所有键都有 TTL；`expires=0` 说明一个都没有——那内存迟早满。

**结果**：过期的键不会立刻消失。`DBSIZE` 里可能包含一批早该删掉的键，直到它们被访问或被抽查到。

## 内存满了：八种淘汰策略

先设一个上限，否则 Redis 会一直吃内存直到被系统 OOM 杀掉：

```bash
redis-cli CONFIG SET maxmemory 2gb
redis-cli CONFIG GET maxmemory-policy
```

`maxmemory-policy` 有八种，按"删不删、删谁"分成三组：

| 策略 | 行为 |
| --- | --- |
| `noeviction` | **不删，写入直接报错** `OOM command not allowed`。读操作还能用 |
| `allkeys-lru` | 从**所有键**里删最近最少使用的 |
| `allkeys-lfu` | 从所有键里删访问频率最低的 |
| `allkeys-random` | 从所有键里随机删 |
| `volatile-lru` | 只从**设了过期时间**的键里删最近最少用的 |
| `volatile-lfu` | 只从设了过期时间的键里删频率最低的 |
| `volatile-random` | 只从设了过期时间的键里随机删 |
| `volatile-ttl` | 只从设了过期时间的键里删**最快到期**的 |

两个词要先解释：

- **LRU**（Least Recently Used，最近最少使用）：看"最后一次访问距今多久"，久没用的先删；
- **LFU**（Least Frequently Used，最少使用频率）：看"被访问过多少次"，很少被访问的先删。

LRU 的经典问题：一个键几年前被访问过一次，之后一直没人碰，但按 LRU 它算"用过的"，反而比最近用过的键活得久。LFU 修掉这个：用得少就删，跟"多久以前"无关。

Redis 的 LRU 是**近似实现**：每个键记一个"最后访问时间"，淘汰时随机抽几个样本，删掉其中最久没用的。采样数由 `maxmemory-samples` 控制（默认 5）。

## volatile 系策略的陷阱

`volatile-*` 只删带 TTL 的键，听起来更安全——但它有一个致命情况：

**如果一个带 TTL 的键都没有，`volatile-*` 就退化成 `noeviction`，写入全部报错。**

更常见的是另一半：**你的业务数据没设 TTL，缓存设了 TTL**。内存满了，`volatile-lru` 会把缓存删光，然后开始报错——业务数据一个字节都没释放。

选择建议：

- **纯缓存场景**：`allkeys-lru` 或 `allkeys-lfu`。所有键都可以丢，谁冷删谁；
- **缓存 + 少量必须保留的数据**：给必须保留的键不设 TTL，其余全设 TTL，用 `volatile-lru`；
- **绝对不能丢数据**：`noeviction`，让写入报错，由应用决定怎么办——但要监控内存。

## 为什么不能拿 Redis 当唯一存储

把上面几条串起来看：

- 键会被淘汰。`allkeys-*` 不区分"缓存"和"数据"，内存一紧，数据也删；
- 主从是异步复制。主节点写完就返回成功，从节点可能还没收到；主节点这时宕机，这段数据就没了；
- 持久化有窗口。RDB 是定时快照，两次快照之间的写入会丢（第四篇细讲）；
- 运维动作会清库。误执行 `FLUSHALL`、换实例、集群扩容迁移失败。

这四条任意一条成立，"唯一存储"就站不住。Redis 的定位是**可重建的高速层**：数据丢了，能从数据库重建，只是慢一阵。

判断标准很简单：**这份数据丢了，你能不能从别的地方算回来？** 能，放 Redis 没问题；不能，Redis 只能是它的加速副本，原件必须在别处。

## 一个具体例子：会话为什么要设 TTL

```bash
redis-cli SET session:u1001 "logged-in" EX 1800
redis-cli TTL session:u1001          # 1800
redis-cli INFO keyspace              # db0:keys=1,expires=1,...
```

用户登录写一条，30 分钟后自动过期，等于"30 分钟不操作就登出"。

如果不设 TTL：用户登出时忘了删，这条记录就永久留着。一年后库里有几百万条死会话，内存一直不够——而它们全是垃圾。所以规则是：**凡是"会自然失效"的数据，写入时就带上 TTL**。

## 常见误区

### 误区：设了过期时间，到点就删

**你以为**：`EXPIRE` 就像闹钟，时间一到立刻删除。
**其实**：没有定时器。过期键要等"被访问"或"被定期抽查到"才删。所以内存占用和 `DBSIZE` 都可能高于"真正有效的数据量"。
**怎么验证**：`SET k v PX 100`，等 1 秒后 `DBSIZE` 看它还在，再 `GET k` 拿到 nil，此时 `DBSIZE` 才减一。

### 误区：淘汰策略会自动保护重要数据

**你以为**：Redis 知道哪些数据重要，会优先删缓存。
**其实**：`allkeys-*` 只看访问时间或频率，不看业务含义。一个很少被读但绝不能丢的配置项，照样会被删掉。
**怎么验证**：写一个几乎不访问但重要的键，把 `maxmemory` 调到很小，触发 `allkeys-lru`，再看它还在不在。

### 误区：内存满了 Redis 会崩

**你以为**：超过 `maxmemory` 就 OOM 退出。
**其实**：默认行为取决于策略。`noeviction` 是写入报错、读照常；`allkeys-*` 是删键腾地方。真正让 Redis 被系统杀掉的是**没设 `maxmemory`**，让它无限增长。
**怎么验证**：`CONFIG SET maxmemory 1mb` 后写一个大值，看返回的错误信息。

## 小结

过期是惰性删除加定期抽查，不是定时器。内存满了按 `maxmemory-policy` 淘汰：`allkeys-*` 删所有键，`volatile-*` 只删带 TTL 的（没有就退化成不淘汰）。键会被删、复制是异步、持久化有窗口——这三条决定了 Redis 只能是可重建的加速层。
