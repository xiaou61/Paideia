## 内存满了，先看到的是这一行

先看默认值。下面是我在一个 8.6.2 临时空实例上跑出来的；这个实例没开持久化。

```bash
redis-cli CONFIG GET maxmemory
redis-cli CONFIG GET maxmemory-policy
redis-cli SET oom:probe abc
redis-cli CONFIG SET maxmemory 700kb
redis-cli SET oom:probe2 abc
redis-cli GET oom:probe
```

```text
1) "maxmemory"
2) "0"
1) "maxmemory-policy"
2) "noeviction"
OK
OK
(error) OOM command not allowed when used memory > 'maxmemory'.
"abc"
```

`maxmemory` 是 `0`，在 64 位构建上表示不限制；`maxmemory-policy` 是 `noeviction`。把上限压到比当前 `used_memory` 低之后，写命令收到 OOM，读命令还能读到旧值。当时 `used_memory` 是 824714，`maxmemory` 是 716800，所以下一句 `SET` 直接撞线。`oom:probe` 是在压低上限之前写的，所以读得到；新写的 `oom:probe2` 被拒。

我原来以为内存满了 Redis 会删点东西腾地方。开源版默认不是这样：`noeviction` **不删，拒写**；只有显式配成 `allkeys-*` 或 `volatile-*`，才会进入淘汰逻辑。

64 位默认 `maxmemory=0`，32 位默认 3GB；这是官方文档的默认值。我手上只有 64 位实例，3GB 那半句没有实跑。

> 怎么自己验证：`CONFIG GET maxmemory`、`CONFIG GET maxmemory-policy`；把 `maxmemory` 调到低于 `INFO memory` 里的 `used_memory`，再执行一次会分配内存的 `SET`。

## TTL 的 -1 和 -2，不是一回事

同一个 `session:abc`，先写一次带过期的，再写一次不带过期的：

```bash
redis-cli SET session:abc token123 EX 60
redis-cli TTL session:abc
redis-cli SET session:abc token456
redis-cli TTL session:abc
redis-cli SET session:abc token789 EX 60
redis-cli SET session:abc token000 KEEPTTL
redis-cli TTL session:abc
redis-cli TTL missing
```

```text
OK
(integer) 60
OK
(integer) -1
OK
OK
(integer) 60
(integer) -2
```

`TTL` 返回 `-1` 是「键在，但没有过期时间」，`-2` 是「键不存在」。第一次 `SET` 带了 `EX 60`，第二次普通 `SET` 把值换了，也把 TTL 清掉了，所以变成 `-1`。这是最容易被忽略的一步：**普通 `SET` 成功覆盖时会丢弃旧 TTL**；要保留得用 `KEEPTTL`。

`SET ... EX 60` 是原子的：值和过期时间在一条命令里完成。拆成两条就有窗口：

```bash
redis-cli SET gap:key v
redis-cli EXPIRE gap:key abc
redis-cli TTL gap:key
```

```text
OK
(error) ERR value is not an integer or out of range
(integer) -1
```

第二条失败，或者根本没发出去，键已经写进去了，TTL 还是 `-1`。如果这是登录态，它就永久留下了。要避免这个窗口，写入时就带 `EX`/`PX`；要改已有键的 TTL，再用 `EXPIRE`。

几个容易混的命令，一句话分开：

| 写法 | 一次命令完成？ | TTL 结果 |
| --- | --- | --- |
| `SET k v EX 60` | 是 | 值和 60 秒过期一起写 |
| `SET k v` | 是 | 清掉旧 TTL |
| `SET k v KEEPTTL` | 是 | 保留旧 TTL |
| `SETEX k 60 v` / `PSETEX k 60000 v` | 是 | 等价于 `SET ... EX/PX`；官方已标废弃 |
| `GETSET k v` | 是 | 返回旧值，但会清掉 TTL；6.2 起废弃 |
| `PEXPIRE k 60000` | 是 | 毫秒单位改 TTL；`EXPIRE` 是秒 |

`SETEX` 和 `GETSET` 还能用，但新代码没必要再用：`SET ... EX` 和 `SET ... GET` 能覆盖同样的场景。`PEXPIRE` 不是「更快的 `EXPIRE`」，它只是把单位从秒换成毫秒；`PTTL` 配套看毫秒剩余。

`EXPIRE` 返回 `1` 表示设置成功，`0` 表示没设置（键不存在，或条件不满足）。`EXPIRE key 0` 会直接删键：

```bash
redis-cli SET tmp:key v
redis-cli EXPIRE tmp:key 0
redis-cli EXISTS tmp:key
```

```text
OK
(integer) 1
(integer) 0
```

`EXPIRE` 从 7.0 起支持四个条件：

| 选项 | 只在什么条件下设置 |
| --- | --- |
| `NX` | 键当前没有 TTL |
| `XX` | 键当前有 TTL |
| `GT` | 新 TTL 比当前更晚；没有 TTL 视为无限 |
| `LT` | 新 TTL 比当前更早；没有 TTL 视为无限 |

在一个已经有 100 秒 TTL 的键上跑：

```bash
redis-cli SET opt:key v
redis-cli EXPIRE opt:key 100 NX
redis-cli EXPIRE opt:key 200 NX
redis-cli EXPIRE opt:key 200 XX
redis-cli EXPIRE opt:key 300 GT
redis-cli EXPIRE opt:key 100 GT
redis-cli EXPIRE opt:key 100 LT
redis-cli TTL opt:key
```

```text
OK
(integer) 1
(integer) 0
(integer) 1
(integer) 1
(integer) 0
(integer) 1
(integer) 100
```

`NX` 第二次返回 `0`，因为 TTL 已经存在；`XX` 返回 `1`，因为 TTL 存在；`GT 300` 比当前 200 晚，返回 `1`；`GT 100` 比当前 300 早，返回 `0`；`LT 100` 比当前 300 早，返回 `1`。

键没有 TTL 时，`GT` 一定返回 `0`（新时间不可能比无限更晚），`LT` 会成功（新时间比无限早）：

```bash
redis-cli PERSIST opt:key
redis-cli EXPIRE opt:key 100 XX
redis-cli EXPIRE opt:key 100 GT
redis-cli EXPIRE opt:key 100 LT
redis-cli TTL opt:key
```

```text
(integer) 1
(integer) 0
(integer) 0
(integer) 1
(integer) 100
```

版本边界：`NX` 不能和 `XX`/`GT`/`LT` 同用，`GT` 和 `LT` 也不能同用；8.6.2 允许 `XX` 和 `GT`/`LT` 组合。跨版本别假设组合一定可用，先看 `EXPIRE` 文档。

> 怎么自己验证：`TTL`/`PTTL` 看剩余，`EXPIRE ... NX/XX/GT/LT` 看返回 `0` 还是 `1`，`PERSIST` 看能不能去掉 TTL。

## 过期键不是立刻消失：DBSIZE 会骗你

Redis 不用「每个键一个定时器」。它靠两件事：

- 惰性删除：键被访问时，先检查是否过期；过期就删掉，再返回不存在。
- 定期删除：`hz` 默认 10，也就是每秒 10 次；每次从带 TTL 的键里抽 20 个，删掉其中过期的。如果这一轮里过期键超过 25%，继续抽。

所以过期键可能还在字典里。`DBSIZE` 数的是字典里的键，不是「逻辑上还有效的键」；官方 FAQ 直接写了：过期键仍然会被计入 `INFO` 和 `DBSIZE`。

要稳定复现这个窗口，可以在一次性实例上关掉定期删除（默认 `DEBUG` 被禁用，需要配置 `enable-debug-command local` 并重启；生产不要开）：

```bash
redis-cli DEBUG SET-ACTIVE-EXPIRE 0
redis-cli FLUSHDB
redis-cli SET keep:long v PX 60000
redis-cli SET exp:probe v PX 100
# 等 400 毫秒
redis-cli DBSIZE
redis-cli INFO keyspace
redis-cli TTL exp:probe
redis-cli GET exp:probe
redis-cli DBSIZE
redis-cli MEMORY USAGE exp:probe
```

```text
OK
OK
OK
OK
(integer) 2
# Keyspace
db0:keys=2,expires=2,avg_ttl=0,subexpiry=0
(integer) -2
(nil)
(integer) 1
(nil)
```

在碰 `exp:probe` 之前，`DBSIZE` 是 `2`，`INFO keyspace` 也是 `keys=2,expires=2`。`expires=2` 是「两个键都有 TTL」，不是「两个键都还有效」；其中一个已经过期了。`TTL exp:probe` 返回 `-2`，`GET` 返回 `nil`，这次访问触发惰性删除，`DBSIZE` 才变成 `1`。`MEMORY USAGE exp:probe` 在删除后返回 `nil`。

`subexpiry` 是 7.4 起才有的字段，老版本没有；看 `keys=` 和 `expires=` 就够。

不要用「等 1 秒再 `DBSIZE`」判断过期有没有生效：定期删除可能已经把它清了，窗口不保证。要么用上面的测试开关复现，要么接受「可能还在、也可能已经没了」，用 `TTL` 判断逻辑上是否过期。

> 怎么自己验证：`CONFIG GET hz` 看频率，`INFO keyspace` 看 `keys=`/`expires=`，`TTL` 看逻辑过期，`DBSIZE` 看字典里还剩多少，`MEMORY USAGE key` 看单个键的实际占用。

## 八种策略：先决定删不删，再决定删谁

`maxmemory-policy` 有八种。先看候选键，再看选择方式：

| 策略 | 候选键 | 怎么选 |
| --- | --- | --- |
| `noeviction` | 不淘汰 | 写命令报 OOM，读命令可用 |
| `allkeys-lru` | 所有键 | 最近最少使用 |
| `allkeys-lfu` | 所有键 | 访问频率最低 |
| `allkeys-random` | 所有键 | 随机 |
| `volatile-lru` | 有 TTL 的键 | 最近最少使用 |
| `volatile-lfu` | 有 TTL 的键 | 访问频率最低 |
| `volatile-random` | 有 TTL 的键 | 随机 |
| `volatile-ttl` | 有 TTL 的键 | 最快到期 |

LRU 看「最后一次访问」：一个键几年前被访问过一次，之后一直没人碰，它的最后访问时间最旧，**LRU 会先淘汰它**。会让它靠「历史上被访问很多次」多活一阵的是 LFU，不是 LRU。

Redis 的 LRU 是近似实现：每个键记一个最近访问的时钟值，淘汰时随机抽 `maxmemory-samples` 个键（默认 5），删其中最久没用的。它不是精确的全局链表，所以别指望「严格按最后访问时间排序」。

LFU 是 4.0 起支持的策略：每个键有一个 8 位对数计数器，范围 0–255；`lfu-log-factor` 默认 10，控制计数的增长速度；`lfu-decay-time` 默认 1 分钟，计数会随时间下降。它也不是精确访问次数。

看两个键级命令：

```bash
redis-cli SET small hello
redis-cli OBJECT IDLETIME small
# 等 2 秒
redis-cli OBJECT IDLETIME small
redis-cli OBJECT FREQ small
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
redis-cli OBJECT FREQ small
# 连续 GET small 10 次
redis-cli OBJECT FREQ small
redis-cli OBJECT IDLETIME small
redis-cli CONFIG GET lfu-log-factor
redis-cli CONFIG GET lfu-decay-time
```

```text
OK
(integer) 0
(integer) 2
(error) ERR An LFU maxmemory policy is not selected, access frequency not tracked. Please note that when switching between policies at runtime LRU and LFU data will take some time to adjust.
OK
(integer) 0
(integer) 6
(error) ERR An LFU maxmemory policy is selected, idle time not tracked. Please note that when switching between policies at runtime LRU and LFU data will take some time to adjust.
1) "lfu-log-factor"
2) "10"
1) "lfu-decay-time"
2) "1"
```

`OBJECT IDLETIME` 在 LRU/noeviction 下可读；切到 LFU 会报错。`OBJECT FREQ` 只在 LFU 下可读；不在 LFU 下会报错。10 次 `GET` 后读到 `6`，不是 `10`——这个计数器是对数的、概率递增的，不是访问次数。

> 怎么自己验证：`CONFIG GET maxmemory-samples` 看采样数（默认 5）；`OBJECT IDLETIME`/`OBJECT FREQ` 看单键；`INFO stats` 的 `evicted_keys` 看累计淘汰数。

## 你想要什么，就配哪个策略

| 你想要 | 策略 | 要接受/检查什么 |
| --- | --- | --- |
| 所有键都可丢，冷数据先走 | `allkeys-lru` | 采样是近似的，热键也可能被误伤；看 `evicted_keys` |
| 所有键都可丢，低频先走 | `allkeys-lfu` | 4.0+；新键频率低；可调 `lfu-log-factor`/`lfu-decay-time` |
| 只删缓存，业务数据不能动 | `volatile-lru`/`volatile-lfu`/`volatile-random`/`volatile-ttl` | 只碰有 TTL 的键；TTL 键删光后写入会 OOM |
| 一条都不能丢，宁可拒写 | `noeviction` | 必须监控 `used_memory` 和 OOM 错误率 |
| 没有热点，想随机腾地方 | `allkeys-random` | 不保证保留热数据 |

`volatile-*` 最容易踩的坑不是「删错」，是「没得删」。它只从带 TTL 的键里选；如果一个带 TTL 的键都没有，它不会碰无 TTL 的键，行为退化成 `noeviction`。

我在 3MB 上限、`volatile-lru`、全部键都不带 TTL 的实例上逐条写 20KB 的值，写到第 119 条时报错：

```text
(error) OOM command not allowed when used memory > 'maxmemory'.
```

```bash
redis-cli INFO stats
redis-cli INFO keyspace
```

```text
evicted_keys:0
# Keyspace
db0:keys=118,expires=0,avg_ttl=0,subexpiry=0
```

`118` 不是固定阈值，取决于值大小和基线内存；关键是 `expires=0`、`evicted_keys:0`，写入还是 OOM。换成 `allkeys-lru`、同样写 150 条 20KB 的键，150 条全部成功，`evicted_keys` 是 32，`DBSIZE` 是 118。这说明它确实在删键腾地方。

`evicted_keys` 是累计值。比较前后要先 `CONFIG RESETSTAT`；我第一次没重置，看到 `volatile-lru` 也有 50 次淘汰，后来发现那是上一轮 `allkeys-lru` 留下的。

还有一个小坑：不要用一段 Lua 循环来测这个。我在这个 8.6.2 实例上用 `EVAL` 写 30 个 200KB 的键，结果全写进去了，`maxmemory` 看起来没拦住；同一个实例改成逐条 `SET` 才复现出 OOM。测淘汰和 OOM 时，用逐条客户端命令，别用脚本内的循环代替。

> 怎么自己验证：`CONFIG GET maxmemory-policy`、`INFO stats` 的 `evicted_keys`、`INFO keyspace` 的 `expires=`；比较前先 `CONFIG RESETSTAT`。

## used_memory 和 RSS 不是一回事

`INFO memory` 里有两个数经常被混着看：

- `used_memory`：Redis 分配器视角的逻辑用量，`maxmemory` 主要拿它来比；
- `used_memory_rss`：操作系统看到的常驻内存，包含分配器没还给 OS 的碎片。

我写了 30000 个约 1KB 的键，然后 `FLUSHDB`：

```bash
redis-cli EVAL "for i=1,30000 do redis.call('set','mem:'..i,string.rep('x',1000)) end return redis.call('dbsize')" 0
redis-cli INFO memory
redis-cli FLUSHDB
redis-cli INFO memory
```

```text
(integer) 30000
# 写入后
used_memory:33052648
used_memory_rss:33034466
mem_fragmentation_ratio:1.00
# FLUSHDB 后
used_memory:1020498
used_memory_rss:1002316
mem_fragmentation_ratio:1.00
mem_allocator:libc
```

这里用 Lua 只是造数据（`maxmemory=0`）；测 OOM 不要用这种脚本内循环。

这台机器的 `mem_allocator` 是 `libc`，RSS 跟着降了。**但这不能当成普遍保证**：官方文档明确说 `used_memory_rss` 包含碎片，删键不等于分配器马上把页还给 OS；jemalloc 构建可能把内存留在 arena 里。`MEMORY PURGE` 只在 jemalloc 下尝试归还脏页，其他分配器是 no-op；本机 `MEMORY PURGE` 返回 `OK`，但没有可验证的释放效果。jemalloc 上如果 PURGE 也不够，只能重启或滚动替换实例。

`maxmemory` 主要管的是 `used_memory` 这条逻辑量，不是 RSS。RSS 可能因为碎片高于 `used_memory`；容器按实际常驻内存算时，可能出现 `used_memory < maxmemory`、容器却先 OOM 的情况。

看单个键占多少，用 `MEMORY USAGE`；看编码，用 `OBJECT ENCODING`：

```bash
redis-cli SET small hello
redis-cli OBJECT ENCODING small
redis-cli MEMORY USAGE small
redis-cli SET big "$(printf 'x%.0s' {1..1000})"
redis-cli OBJECT ENCODING big
redis-cli MEMORY USAGE big
```

```text
OK
"embstr"
(integer) 41
OK
"raw"
(integer) 1036
```

同样是字符串，5 个字符的 `small` 是 `embstr`、41 字节；1000 个字符的 `big` 变成 `raw`、1036 字节。`MEMORY USAGE` 对集合类型默认只抽样 5 个嵌套值，结果是估算，不是精确总和；要看更准可以调 `SAMPLES`。

> 怎么自己验证：`INFO memory` 看 `used_memory`/`used_memory_rss`/`mem_fragmentation_ratio`/`mem_allocator`；`MEMORY USAGE key` 看单键；`OBJECT ENCODING key` 看编码；`MEMORY PURGE` 只在 jemalloc 上有意义。

## 为什么不能拿 Redis 当唯一存储

`noeviction` 只挡住「淘汰」这一种丢数据方式，挡不住另外三种：

| 丢失路径 | 怎么发生 |
| --- | --- |
| 淘汰 | 配了 `allkeys-*`，业务数据也可能被删；`volatile-*` 在 TTL 键删光后转为拒写 |
| 异步复制 | 主节点写完就返回，从节点还没收到；主节点这时宕机 |
| 持久化窗口 | RDB 两次快照之间；AOF 还没 fsync 的那一段 |
| 运维动作 | `FLUSHALL`、换实例、集群迁移失败 |

这四条里任意一条成立，Redis 就不能是唯一副本。判断标准很直接：**这份数据丢了，能不能从别的地方算回来？** 能，放 Redis 没问题；不能，Redis 只能是加速副本，原件必须在别处。

一个具体的会话写法：

```bash
redis-cli SET session:u1001 logged-in EX 1800
redis-cli TTL session:u1001
redis-cli INFO keyspace
```

```text
OK
(integer) 1800
# Keyspace
db0:keys=1,expires=1,...
```

`EX 1800` 是「这次写入后 30 分钟过期」，不是「30 分钟不操作才过期」。用户一直在操作，TTL 也不会自动续；要滑动过期，就在每次请求后 `EXPIRE session:u1001 1800`，或者更新值时重新 `SET ... EX 1800`。`KEEPTTL` 只保留原来的到期时间，不会续期。

## 还差的

- 本机没有可用于本文的常驻 Redis 服务，也没有 Docker；回显来自临时 8.6.2 空实例。以下没有实测：32 位默认 `maxmemory=3GB`、jemalloc 下的 RSS 行为和 `MEMORY PURGE` 实际释放量、主从/集群下的过期与淘汰。
