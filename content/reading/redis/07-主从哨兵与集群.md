## 主库回了 2000 个 OK，从库一条都没收到

下面这些数是我在自己机器上跑出来的：redis 8.6.2，两个临时实例，`127.0.0.1:6393` 当主，`127.0.0.1:6394` 当从，配置文件都放在临时目录里。业务侧只有一个东西——`order:1001` 这条订单。

先建复制。`REPLICAOF` 运行时就能改，不用重启：

```bash
redis-cli -p 6393 SET order:1001 paid
redis-cli -p 6394 REPLICAOF 127.0.0.1 6393
```

几秒后两边对得上（主库视角）：

```text
role:master
connected_slaves:1
slave0:ip=127.0.0.1,port=6394,state=online,offset=28,lag=1,io-thread=0
master_repl_offset:28
```

然后我干了一件真实环境里会发生的事：把从库指到一个没人监听的端口，让复制链路断掉。

```bash
redis-cli -p 6394 REPLICAOF 127.0.0.1 6392
```

```text
# 6394（从）
role:slave
master_host:127.0.0.1
master_port:6392
master_link_status:down
master_last_io_seconds_ago:-1
slave_repl_offset:85156

# 6393（主）
connected_slaves:0
master_repl_offset:85156
```

链路断着，主库照收 2000 条写（我用 `--pipe` 灌的，等价于下面这段循环）：

```bash
for i in $(seq 1 2000); do echo "SET order:r3:$i paid"; done | redis-cli -p 6393 --pipe
```

```text
errors: 0, replies: 2000          # 241 ms（含 redis-cli 启动）
connected_slaves:0
master_repl_offset:170049
```

`85156` 到 `170049`，涨了 84893 字节，2000 条写全部落进主库，一条报错都没有。另一边：

```text
slave_repl_offset:85156     # 从库的 offset 一动不动
master DBSIZE=4002  replica DBSIZE=2002
replica GET order:r3:1 = []          # 断链期间写的新 key，从库根本不知道
replica GET order:1001 = shipped     # 断链前的老值还在，读它不报错
```

我原来以为主库至少会喊一声，或者拒绝写。不会。`connected_slaves:0` 只是它自己 INFO 里的一行事实，写请求照样返回 `+OK`。它"知道"没副本，但它不因此改变行为——除非你显式把 `min-replicas-to-write` 打开。

这就是主从复制的第一个要害：**主库返回 OK 的时刻，只代表它自己写完了**。它挂掉时这批写还在不在，取决于副本收到没有，而主库从没等过副本。

## 先认字段：两台机器上的 INFO 不是同一套

排查主从问题，第一件事是分清楚你连的是哪台、以及你在读谁的数字。同一份 `INFO replication`，主库和从库给出的字段不一样：

```text
# 从库
role:slave
master_host:127.0.0.1
master_port:6393
master_link_status:up
master_sync_in_progress:0
slave_read_repl_offset:28
slave_repl_offset:28
slave_read_only:1
slave_priority:100

# 主库
role:master
connected_slaves:1
slave0:ip=127.0.0.1,port=6394,state=online,offset=28,lag=1,io-thread=0
master_repl_offset:28
```

注意 8.6.2 上角色值仍然是 `role:slave`，不是 `role:replica`——配置项改名叫 replica 了，INFO 的字段名没改名。照着新名字去 grep 会一条都找不到。

遇到问题时按这个顺序看：

| 现象 | 先看哪 | 怎么读 |
| --- | --- | --- |
| 应用大量报 `READONLY` | 你连的那台的 `role` | `role:slave` 就是连错了节点，不是复制坏了 |
| 从库数据比主库少 | 两边 `master_repl_offset` 与 `slave_repl_offset` | 主大从小且 `master_link_status:down` → 链路断了，差多少字节就是这两个数之差；两个数相等说明已经追上，DBSIZE 还不同就得去查过期、淘汰或者你连的根本是另一个实例 |
| 新加的从库一直是 down | 主库 `slave0` 的 `state` | `wait_bgsave` 表示 RDB 还在传或传不动，`online` 才算接上 |
| 主库 `lag` 一直涨 | `slave0` 的 `lag`、`connected_slaves` | `lag` 是「上次收到副本 ACK 到现在过了几秒」，涨起来说明从库在卡 |
| 不知道当前谁是主 | `role` | 切换之后 `role` 会变，IP 和机器名不可靠 |

`master_last_io_seconds_ago:-1` 这个 `-1` 是「没有最后一次 I/O 可算」——链路断着的时候它就是 -1，别当成 1 秒前刚通过。

## 全量同步只发生一次，之后靠 backlog 追

第一次接上时我从从库日志里看到的是这样：

```text
MASTER <-> REPLICA sync: Flushing old data
Loading RDB produced by version 8.6.2
Done loading RDB, keys loaded: 2, keys expired: 0.
MASTER <-> REPLICA sync: Finished with success
```

主库那一刻的计数是 `sync_full:1`、`sync_partial_err:1`——第一次 `PSYNC` 想走增量没成（新从库没有历史 offset），退回全量。之后我把链路断开几秒，再 `REPLICAOF 127.0.0.1 6393` 接回来：

```text
sync_full:1        # 没再增加
sync_partial_ok:1  # 这次走了增量
slave_repl_offset:170100   # 两边齐平
master DBSIZE=4002 replica DBSIZE=4002
```

为什么能增量？因为主库一直留着一份最近写命令的 backlog，从库重连时报上自己的 offset，落在 backlog 范围内就只补这一截。这份 backlog 的大小是 `repl-backlog-size`，8.6.2 实测默认 `1048576`（1 MB）。也就是说：**断线期间主库新写的量超过 1 MB，接回来就只能全量重传**。我断链那几秒只写了 84893 字节，刚好在 1 MB 里面。

全量同步的默认路径值得单独确认一遍：8.6.2 上 `repl-diskless-sync` 实测默认是 `yes`，主库 fork 一个子进程，把 RDB 直接写进复制连接的 socket，不落盘；从库这边 `repl-diskless-load` 默认 `disabled`，所以它还是先写本地文件再加载。fork 那一下的代价和第 04 课讲快照时是同一个东西。

在这台 cygwin 构建的 Windows 上，两个 key 的全量同步让我对着 `state=wait_bgsave` 等了约 6 秒。这个数字不要当基准——它反映的是这个构建的传输开销，不是 Linux 上的表现。

## WAIT 只回答「刚才有几个副本确认了」

想减小丢数据的窗口，第一反应是让主库等副本。Redis 给了 `WAIT`：

```bash
redis-cli -p 6393 SET order:1001 shipped
redis-cli -p 6393 WAIT 1 100
```

副本跟得上时返回 `1`（返回的是"确认了的副本数"）。链路断着的时候：

```text
WAIT=0    # 262 ms 后返回
```

那个 262 ms 里，120 ms 是 `redis-cli` 的启动开销（同一台机器上 `PING` 也是 121 ms），剩下 100 ms 是它**真的等满了超时**才返回 0。我把超时改大再试一遍：`WAIT 1 2000` 用了 2146 ms，`WAIT 0 2000` 立刻返回。所以它的行为是：

- 副本数不够时它不提前放弃，而是等满你给的毫秒数，然后返回已经确认的个数；
- 返回的是计数，不是错误。代码里不检查这个返回值，等于没等。

这也决定了它治不了什么：`WAIT` 只是把"刚才那一下有几个副本确认了"变成一个数字，主库收下这条写的事实没变，超时之后照样什么都不发生。所以任何"用 `WAIT` 实现强一致"的写法都要先回答一个问题：返回 0 的那次，你的代码打算怎么办？如果是不看返回值继续往下走，那这个 `WAIT` 只是让每次写多了 100 ms 延迟。

真要让主库在副本不够时拒写，是另一个开关：

```bash
redis-cli -p 6393 CONFIG SET min-replicas-to-write 1
redis-cli -p 6393 CONFIG SET min-replicas-max-lag 10
redis-cli -p 6393 SET order:1001 shipped
```

```text
(error) NOREPLICAS Not enough good replicas to write.
redis-cli -p 6393 GET order:1001   # 读照常，返回 shipped
```

写被拒了，读没被拒。这就是这个开关的代价：副本一断，应用侧所有写立刻失败，你把"丢数据风险"换成了"可用性风险"。

| 参数 | 8.6.2 实测默认 | 改它意味着什么 |
| --- | --- | --- |
| `replica-read-only` | `yes` | 改 `no` 允许从库写，主从立刻分叉 |
| `min-replicas-to-write` | `0` | 设 1：健康副本不足时主库拒写，报 `NOREPLICAS` |
| `min-replicas-max-lag` | `10` | 定义"健康副本"：ACK 超过 10 秒的不算 |
| `repl-backlog-size` | `1048576` | 断线期间超过 1 MB 新写，重连退化成全量 |
| `repl-timeout` | `60` | 主从之间多久没动静判定连接失效 |
| `repl-diskless-sync` | `yes` | 全量时子进程直接写 socket，不落盘 |
| `repl-diskless-load` | `disabled` | 从库仍先落盘再加载 RDB |

## 从库只会回这一句

从库上任何写命令，报错原文是同一句，改不了：

```text
(error) READONLY You can't write against a read only replica.
```

`SET` 是这句，`DEL` 也是这句。它不区分你写的是不是"从库本来也该有"的数据，也不看 key 存在不存在。

这句话在故障时特别值钱，因为它同时是症状和结论：**你连到了从库**。切换之后客户端拿着旧的主库地址重连，就会撞上它；配置里把 IP 写死、没走哨兵地址，也会撞上它。

想关掉只读（`replica-read-only no`）要清楚代价：从库一旦能被写，主从数据就分叉，切换时新主的数据可能比旧主旧、也可能多出旧主没有的 key；两边互相 `REPLICAOF` 成环时，还会把对方的写来回放大。

还有一种"看起来没坏"的状态：链路断着的时候，从库照样返回 `GET order:1001 = shipped`，读命令一条都不报错（`replica-serve-stale-data` 默认 `yes`）。所以"读得到"不等于"数据是新的"——这也是前面为什么要你从主库和从库各读一个 offset：只看得见一条链路的状态，看不见差了多少。

## 哨兵：标准形态，未实跑

下面这一段我没跑，写的是标准形态，数字来自官方文档和 `sentinel.conf` 的默认值——请按"要验就自己搭三个实例"来读。

哨兵本身是个独立进程，不存数据。它做三件事：

1. 定期 `PING` 主从，以及通过 `INFO` 发现新副本；
2. 判下线：单个哨兵认为主库没响应是**主观下线**（sdown）；凑够 `quorum` 个哨兵同意才升为**客观下线**（odown）；
3. 选一个哨兵当 leader 执行切换：把一个从库提升为主，再让其他从库和旧主改跟新主。

有个地方容易记混：`quorum` 只用于**判定客观下线**，不负责选 leader。选 leader 要靠多数派投票，所以哨兵数量才要是奇数、至少 3 个。两个哨兵的部署尤其尴尬：挂掉一个之后，多数派（2）永远凑不出来，投不出 leader；如果 `quorum` 还是按两个都同意来配，连客观下线都判不出来。

关键配置（`sentinel.conf` 默认值，未实跑）：`down-after-milliseconds 30000`（30 秒没响应算主观下线）、`failover-timeout 180000`、`parallel-syncs 1`。这三个值决定了"主库挂了到应用能写"这段窗口有多长——`parallel-syncs 1` 意味着新主一次只让一个从库同步，几个从库就要排队。

客户端要拿新主地址，靠的是问哨兵：

```bash
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
```

而不是自己缓存一个 IP。这一步没做对，哨兵切换得再快，你的应用也会一直撞 `READONLY`。

## 集群：16384 个槽，和 `{}` 到底怎么算

分片这部分我只跑了"算槽"这一件事——起了一个 `cluster-enabled yes` 的实例，没组集群。所以下面是真实槽号，但重定向和跨槽报错都是文档形态。

槽号是 `CRC16(key) % 16384`：对整串 key（有 `{}` 时只取 `{}` 里那截）算 CRC16(XMODEM)，再对 16384 取模。我顺手用 PowerShell 自己算了一遍做对照，和服务端的结果一致：

```text
CLUSTER KEYSLOT foo → 12182
CLUSTER KEYSLOT 1001 → 15391
CLUSTER KEYSLOT user:{1001}:profile → 15391
CLUSTER KEYSLOT user:{1001}:orders → 15391
CLUSTER KEYSLOT user:1002:orders → 6649
CLUSTER KEYSLOT {} → 15257
```

读法很清楚：带 `{}` 的两个 key 槽号都是 `15391`，等于 `CLUSTER KEYSLOT 1001`——花括号里的内容才是参与哈希的部分，`user:`、`:profile` 这些前后缀不参与。`{}` 是空 tag，不生效，所以它按整串 `{}` 算，而不是按空串算。

然后是我踩的一个坑：我第一遍直接在 Windows 上敲 `redis-cli -p 6395 CLUSTER KEYSLOT user:{1001}:profile`，得到的是 `2549`，两个本该同槽的 key 还给出了不同槽号。折腾了一阵才发现是这个 cygwin 版 `redis-cli` 在 argv 上把花括号吃掉了——同样的命令用 stdin 喂进去（`"CLUSTER KEYSLOT user:{1001}:profile" | redis-cli -p 6395`）才是 `15391`。**看到槽号对不上，先确认服务端真收到了那几个字符。**

未实跑的部分（按官方文档）：集群最少 3 个主节点分完 16384 个槽；客户端连错节点会收到 `MOVED <slot> <ip:port>`（槽永久归别人，更新路由表）或 `ASK <slot> <ip:port>`（槽正在迁移，这一次去新节点，别更新路由表）；`MGET`、事务、Lua 里的 key 必须同槽，否则报 `CROSSSLOT Keys in request don't hash to the same slot`。

槽是固定的 16384 个，扩容时是把槽搬走，不是把哈希函数改掉——所以 `{}` 这个技巧在扩容前后都成立，代价是同一组 `{}` 的数据只能落在一个节点上。

## 选型：按你现在卡在哪，而不是按功能多少

三种形态是叠加的，不是替代的：主从给副本，哨兵给自动切换，集群给分片。所以选型不该问"哪个更强"，该问"我现在卡在哪一层"。

| 你现在卡在哪 | 该动什么 | 代价 |
| --- | --- | --- |
| 读请求把主库 CPU 压满，内存还够 | 加从库，读走从节点 | 内存翻倍、多一份复制流量、读到的可能是旧值 |
| 内存够，但主库挂了要人半夜起来改配置 | 主从升级成 3 哨兵 | 多三个进程要维护；切换期间写会失败；最后一批写仍可能丢 |
| 单机内存到顶，key 数量还在涨 | Cluster | 多 key 操作要改代码；迁移、扩容、监控都多一层 |
| 写入量单机扛不住 | 只有 Cluster 能分摊；主从和哨兵都不提升写能力 | 写分散到多个主，跨槽事务没了 |
| 主库挂掉一条写都不能丢 | 上面三种都不够 | Redis 的复制是异步的，`WAIT` 只是缩小窗口，不是保证 |

最后一行值得单独说：如果这条写丢了业务就得出事，那问题不在"选哪种部署形态"，而在"这条数据该不该只存在 Redis 里"。

## 还差的

- **哨兵和集群没实跑。** 本文里 `quorum`、leader 选举、`down-after-milliseconds 30000`、`failover-timeout 180000`、`MOVED`/`ASK`、`CROSSSLOT` 全部来自官方文档与 `sentinel.conf` 默认值，没在真三节点上验过。切换到底占多少秒、切换期间客户端报什么，我给不出数字。
- **没验"backlog 不够就退化成全量"。** 我断的那 3 秒只写了 84893 字节，刚好在 1 MB 以内。要验这条得在断链期间灌超过 `repl-backlog-size` 的量，再看 `sync_full` 是不是涨 1。
- **旧主回来之后怎么被改回去，没测。** 文档说哨兵会对旧主发 `REPLICAOF` 让它跟新主，但脑裂窗口里旧主已经接了一批写，这批写在新主上不存在——这一步的实际数据结果我没有观测。
- **认证链路没测。** `masterauth`、`requirepass`、哨兵也带密码这三件事凑一起时，从库连着却一直是 `master_link_status:down`，我没验证具体表现。
- **客户端的重定向行为没测。** `MOVED`/`ASK` 在 Jedis、Lettuce、redis-py 里各是什么重试语义，本文只写了协议层。
