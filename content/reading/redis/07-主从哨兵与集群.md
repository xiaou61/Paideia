## 先把结论摆出来

Redis 的三种部署形态解决的是**不同的问题**：

```sketch

    { "from": "sentinel", "to": "cluster" }
  ]

```

| 形态 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| 主从（replication） | 读扩展、数据备份、故障时有个副本 | 不会自动切换，主挂了要人工处理 |
| 哨兵（sentinel） | 自动发现主挂了并完成切换 | 不提升写能力，数据量仍受单机内存限制 |
| 集群（cluster） | 分片，突破单机内存与写吞吐 | 多 key 操作受限，运维复杂度上一个台阶 |

**选型的顺序是**：先问数据量能不能放进一台机器，再问能不能接受几分钟的人工切换，最后才问写吞吐。

大多数业务系统停在"哨兵"就够了；真正需要 Cluster 的是数据量或写入量单机扛不住的场景。

## 主从：复制是怎么发生的

配一个从节点：

```text
# 从节点的 redis.conf
replicaof 10.0.0.11 6379
```

第一次连上时走**全量同步**：

1. 从节点发送 `PSYNC ? -1`；
2. 主节点执行 `BGSAVE` 生成 RDB，同时把期间的写命令记在缓冲区；
3. 把 RDB 发给从节点，从节点清空自己的数据并加载；
4. 再把缓冲区里的增量命令发过去。

之后的日常同步是**增量**：主节点把写命令传播给从节点，从节点按顺序执行。

两个关键事实：

- **复制是异步的**。主节点写完就返回客户端，不等待从节点确认。所以主挂掉时，最后一批写入可能还没到从节点——这部分数据会丢。
- **从节点默认只读**（`replica-read-only yes`）。想让它接受写入要显式关闭，但这会造成主从数据分叉，几乎不该做。

想减少丢数据，可以用 `WAIT`：

```text
SET order:1001 paid
WAIT 1 100     # 等至少 1 个副本确认，最多等 100ms
```

它只能降低概率，不能实现强一致——超时之后仍然返回，副本可能还是没收到。

## 哨兵：自动切换

哨兵是一个独立进程（通常部署 3 个），只做三件事：

1. **监控**：定期向主从发送 `PING`；
2. **判定下线**：单个哨兵认为主挂了是"主观下线"；达到 `quorum` 个哨兵都这么认为，才是"客观下线"；
3. **选举与切换**：哨兵之间选一个 leader，由它把一个从节点提升为主，并通知其他从节点改跟新主。

客户端不直接连主节点地址，而是先问哨兵：

```text
SENTINEL get-master-addr-by-name mymaster
```

拿到当前主节点地址后再连接。主从切换后，哨兵会返回新地址。

**哨兵的局限**：

- 切换期间有短暂不可写（通常几秒到几十秒）；
- 异步复制导致切换后可能丢最后一批写；
- 网络分区时可能出现"脑裂"：旧主还在接受写，新主已经选出。可以用 `min-replicas-to-write` 限制旧主在失去足够副本时拒绝写入。

## 集群：把数据切开

Cluster 把整个键空间分成 **16384 个槽（slot）**，每个主节点负责一部分：

```text
CRC16(key) % 16384 → 槽号 → 负责这个槽的节点
```

最少 3 主 3 从。客户端访问错节点时，会收到重定向：

- `MOVED 3999 10.0.0.12:6379`：这个槽永久归另一个节点，客户端应更新路由表；
- `ASK 3999 10.0.0.12:6379`：槽正在迁移，这一次去新节点问，但不要更新路由表。

**多 key 操作的限制**：`MGET`、`SUNION`、事务、Lua 脚本里的 key 必须落在同一个槽。跨槽会直接报错：

```text
CROSSSLOT Keys in request don't hash to the same slot
```

解决办法是 **hash tag**：用 `{}` 包住参与哈希的部分，让一组 key 落到同一个槽。

```text
user:{1001}:profile
user:{1001}:orders
```

两个 key 都按 `1001` 计算槽号，所以可以一起操作。代价是这一组数据只能落在一个节点上，热点会更集中。

**扩容**时把一部分槽迁到新节点，迁移过程中客户端会收到 `ASK` 重定向。整个过程可以在线完成，但要控制迁移速度，避免把网络打满。

## 怎么选：一张判断表

| 你的情况 | 推荐 |
| --- | --- |
| 数据量 < 单机内存的 50%，能接受人工切换 | 单机 + 定期备份 |
| 需要自动故障转移，数据量仍在一台机器内 | 主从 + 哨兵（3 哨兵） |
| 数据量或写入量超过单机，能接受多 key 限制 | Cluster（3 主 3 从起） |
| 只是读多、想扩展读 | 主从，读走从节点 |
| 想提升写吞吐 | 只能 Cluster；主从和哨兵都不增加写能力 |

**一个常见误解**：加从节点能提升写性能。不能。所有写都落在主节点，从节点只是复制。

## 一个具体现象：切换后报 READONLY

应用突然大量报错：

```text
READONLY You can't write against a read only replica.
```

说明客户端连到了从节点。原因通常是：

1. 哨兵完成了切换，但客户端缓存了旧的主节点地址；
2. 客户端配置的是直连主节点 IP，没有走哨兵；
3. 云厂商的代理层还没刷新路由。

排查顺序：先 `INFO replication` 看当前节点角色（`role:master` / `role:slave`），再确认客户端拿到地址的方式。

## 常见误区

### 误区：主从是强一致的

**你以为**：主节点返回成功，说明从节点也写好了。
**其实**：复制是异步的，主节点返回时从节点可能还没收到。主节点宕机切换后，这部分写入就消失了。
**怎么验证**：在主节点 `SET` 后立刻在从节点 `GET`，高并发下能观察到短暂读不到；`INFO replication` 里的 `master_repl_offset` 与从节点的 `slave_repl_offset` 也能看出差距。

### 误区：有了哨兵就不用管数据量

**你以为**：哨兵能自动切换，等于高可用也解决了容量问题。
**其实**：哨兵管理的仍是一主多从，所有数据在一台机器上。内存到顶时该淘汰还是淘汰，该扩容还是得换 Cluster。
**怎么验证**：看主节点的 `used_memory` 与 `maxmemory`；接近上限时观察 `evicted_keys` 是否增长。

### 误区：Cluster 可以像单机一样随便用多 key 命令

**你以为**：`MGET`、事务、Lua 在 Cluster 下行为不变。
**其实**：它们都要求 key 同槽，否则直接报 `CROSSSLOT`。改造现有代码时这是最常见的阻塞点。
**怎么验证**：在 Cluster 上执行 `MGET user:1:name user:2:name`，观察报错；再用 `{user}` hash tag 重试。

## 小结

主从解决"有副本"，哨兵解决"自动切换"，Cluster 解决"装不下 / 写不下"。三者是递进关系，不是替代关系。选型先看数据量与写吞吐，再看能接受多长的故障恢复时间；多 key 操作与跨槽限制是上 Cluster 之前必须盘点清楚的改造成本。
