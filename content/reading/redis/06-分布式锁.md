## 先把结论摆出来

用 Redis 做分布式锁，最小可用版本只有一条命令：

```text
SET lock:order-42 <唯一值> NX PX 30000
```

`NX` = 不存在才设置（抢锁），`PX 30000` = 30 秒后自动释放（防止持有者崩了锁永远不释放）。

但**"自动释放"正是所有麻烦的来源**：你怎么知道持有者是真的还活着，还是已经卡死但锁还没过期？又怎么保证释放时删的是自己的锁，而不是别人的？

这两件事都做不对，锁就会变成"偶尔失效"的定时炸弹。

## 为什么不能先 SETNX 再 EXPIRE

```text
# 错误写法
SETNX lock:order-42 1        # 抢到了
EXPIRE lock:order-42 30      # ← 如果进程在这里崩了，锁永久存在
```

两条命令不是原子的。中间崩溃 → 锁没有过期时间 → **永远锁死**，只能人工删。

正确做法是用一条 `SET ... NX PX`，Redis 保证这一条命令的原子性。

## 释放锁为什么必须先比对

```text
# 错误写法
DEL lock:order-42
```

假设 A 拿到了锁，但业务执行超过 30 秒，锁自动过期了。B 随后拿到了同一把锁。这时 A 执行完，`DEL` 删掉的是 **B 的锁**。

B 以为自己还持有锁，继续干活——现在两把"锁"同时生效，互斥被破坏。

正确做法是**先比对值再删，且比对和删除要原子**。用 Lua 脚本：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

那个"唯一值"通常是 UUID + 线程 id，保证每次加锁的值不同。

## 锁超时该设多久

这是最难的部分，没有标准答案。

设短了：业务还没跑完锁就过期，别的线程进来，互斥失效。
设长了：持有者崩了之后，其他人要白等这么久。

两种主流缓解：

1. **看门狗（watchdog）**：后台线程每隔一段时间（比如锁 TTL 的 1/3）检查业务是否还在跑，在跑就续期。Redisson 就是这个思路。代价是多一个线程、多一份复杂度，且**续期请求本身可能失败**；
2. **接受它可能失效，在业务层再做一层幂等**。很多场景下这才是根本解——锁只是减少并发，幂等才保证正确。

**核心认知**：分布式锁保证的是"大多数时候互斥"，不是"绝对互斥"。所有依赖锁来保证数据正确性的地方，都该问一句"如果锁失效了会怎样"。

## Redlock 的争议

Redis 作者提出 Redlock：向 N 个独立的 Redis 实例加锁，超过半数成功才算拿到。

批评者（包括 Martin Kleppmann）指出它依赖**时钟假设**：如果某个节点的时钟跳变、或者进程长时间 GC 停顿，锁可能在"实际仍被持有"时被判为过期。而分布式系统里时钟不可靠是基本前提。

**实践上的结论**：

- 单实例 Redis 锁在"锁失效的后果可接受"时够用；
- 真需要强一致的互斥（比如金融扣款），用数据库行锁、ZooKeeper、etcd 这类有共识协议的组件；
- **不要指望 Redis 锁给你线性一致性**。

## 一个完整的实现骨架

```text
加锁：
  token = uuid()
  ok = SET lock:<key> token NX PX 30000
  if !ok: 返回"稍后重试"

执行：
  try { 业务逻辑 }
  finally {
    // 原子比对并删除
    eval(lua, [lock:<key>], [token])
  }
```

要点：

- `token` 每次不同；
- 释放一定放在 `finally`，且只删自己的；
- 业务超时要有兜底（要么续期，要么业务层幂等）；
- 抢锁失败不要死循环重试，要有退避与超时。

## 常见误区

### 误区：有了分布式锁就不会有并发问题

**你以为**：加锁 = 线程安全。
**其实**：锁可能因超时、GC 停顿、网络分区而失效。锁的作用是降低冲突概率，不能替代幂等与唯一约束。
**怎么验证**：把锁 TTL 设成 1 秒，跑一个耗时 3 秒的业务，观察是否出现两个线程同时进入临界区。

### 误区：锁的 TTL 设长一点更安全

**你以为**：过期时间长，业务就不会中途丢锁。
**其实**：设得越长，持有者崩溃后别人等得越久，系统可用性越差。而且长 TTL 不解决"业务真的超过了这个时间"的问题。
**怎么验证**：统计业务执行时间的 P99，对比你的 TTL——如果 P99 接近 TTL，就必然有丢锁。

### 误区：用 DEL 释放锁就行，反正只有我会加锁

**你以为**：同一个 key 只有自己的业务在抢，删了就是自己的。
**其实**：锁过期后别人可能已经拿到，此时你的 DEL 删的是别人的锁。必须比对 token 并原子删除。
**怎么验证**：模拟 A 超时后 B 加锁、A 再释放，检查 B 的锁是否被删。
