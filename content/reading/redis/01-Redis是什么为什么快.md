## 先把结论摆出来

**Redis 是一个把数据放在内存里的键值数据库；它快，主要不是因为"单线程"，而是因为内存、IO 多路复用、以及不用加锁。**

三件事各管一段：

- **内存**：一次内存访问约 100 纳秒，一次机械硬盘随机读约 10 毫秒——差十万倍。数据不在磁盘上，就省掉了这一整段等待；
- **IO 多路复用**：一个线程用 `epoll` 同时盯着几千个连接，谁有数据来了就处理谁，不用为每个连接开一个线程；
- **无锁**：所有命令排成一队、一条一条执行，不存在两个线程同时改一份数据，所以不需要锁，也没有锁竞争和线程切换的开销。

"单线程"指的是**执行命令的那一条线程**。Redis 里还有别的线程（关闭大文件、AOF 刷盘、6.0 之后的网络读写），只是它们不碰你的数据。

## "单线程"到底单在哪

一条命令从到达到返回，路径是这样的：

```text
连接上的字节 → 解析成命令 → 查表/改数据结构 → 拼回复 → 写回连接
```

中间"查表/改数据结构"这一段，全局只有一条线程在做。所以：

- **任何时刻只有一个命令在跑**，天然串行，不会出现两个 `INCR` 读到同一个旧值；
- **一条命令慢了，后面所有连接一起等**。这是单线程唯一真正的代价。

所以"Redis 快"和"Redis 不能被一条慢命令拖住"是同一件事的两面。

## 内存：省掉的是等待，不是计算

把常见延迟摆在一起看，就知道瓶颈在哪：

| 操作 | 大致耗时 |
| --- | --- |
| 一次内存读 | 约 100 纳秒 |
| 一次 SSD 随机读 | 约 100 微秒 |
| 一次机械盘随机读 | 约 10 毫秒 |
| 同一机房一次网络往返 | 约 0.5 毫秒 |

Redis 的一条 `GET` 通常几十微秒就返回，其中大头是网络往返，不是"查找"本身。**它没有让计算变快，只是把"等磁盘"整段删掉了。**

代价也随之而来：内存贵，容量小。一台机器几百 GB 内存就到头了，所以才有第三篇要讲的淘汰策略。

## IO 多路复用：一个线程怎么盯几千个连接

如果每个连接配一个线程，一万个连接就是一万个线程，光切换就吃掉 CPU。

多路复用（multiplexing，就是"一路管多路"）换个思路：把一万个连接都注册给内核，然后问一句"哪些有数据了"。内核返回一个就绪列表，线程只处理列表里的连接。

```text
线程：有谁好了？
内核：第 3、17、2048 号连接可读
线程：好，我依次读它们
```

这条线程 99% 的时间在"等"，等的过程中不占 CPU。真正耗时的网络读写，Redis 6.0 之后可以交给 IO 线程并行做，但**命令还是排队执行**——因为并行执行就要加锁，那点收益抵不过复杂度。

## 无锁：串行带来的确定性

多线程改同一个哈希表，要么加锁，要么用无锁结构。两者都有代价：锁有竞争和切换，无锁结构难写难调。

单线程把这个问题直接消掉了：**没有并发，就没有并发问题**。

顺带得到一个很好用的性质：**单条命令是原子的**。`INCR` 不会读到中间值，`LPUSH` 不会插到一半被别的命令插队。这就是为什么计数器、限流、分布式锁都敢直接用 Redis 命令——它们的正确性依赖这一条。

注意范围：**原子的是"一条命令"，不是"一组命令"**。`MULTI/EXEC` 能保证一组命令不被插队，但它不保证"要么全成功要么全回滚"——中途出错，前面已执行的不会撤销。

## 单线程的边界在哪

任何"一次处理很多 key"的命令都会把整条线程占住。常见的几个：

| 危险命令 | 问题 | 换成 |
| --- | --- | --- |
| `KEYS *` | 遍历整个库，O(N) | `SCAN 0 COUNT 100` 分批 |
| `FLUSHALL` / `FLUSHDB` | 清空并释放所有内存 | 加 `ASYNC` 异步释放 |
| `DEL bigkey` | 释放大对象是同步的 | `UNLINK`（后台释放） |
| `HGETALL` 超大 hash | 一次返回几十万元素 | `HSCAN` 分批 |
| `SORT` / `ZRANGEBYSCORE` 大范围 | 排序或大范围取数 | 缩小范围，或把结果提前算好 |
| 长 Lua 脚本 | 脚本期间整条线程被独占 | 拆小，或改用别的方案 |

在 `redis-cli` 里可以自己验证一条命令有多慢：

```bash
redis-cli --latency          # 持续采样本机往返延迟
redis-cli INFO commandstats  # 每条命令的调用次数与平均耗时（微秒）
redis-cli DEBUG SLEEP 3      # 让服务端睡 3 秒——期间所有连接都卡住
```

最后一条最能说明问题：开两个终端，一个执行 `DEBUG SLEEP 3`，另一个立刻 `PING`，你会看到它也等了 3 秒才回。

## 一个具体例子：为什么 INCR 可以当计数器

```bash
redis-cli SET page:home 0
redis-cli INCR page:home     # 1
redis-cli INCRBY page:home 10 # 11
redis-cli GET page:home      # "11"
```

一千个客户端同时 `INCR`，最终结果一定是 1000，不会丢。原因不是"Redis 做了特殊处理"，而是**这些 INCR 本来就只能一个一个跑**。

如果换成"先 `GET` 再 `SET` 回去"，就退化成非原子操作，并发下会丢计数——这两者的区别，正是第五、六篇里锁与缓存一致性的起点。

## 常见误区

### 误区：单线程就是一个线程

**你以为**：Redis 进程里只跑着一条线程，所以 CPU 只用得上一个核。
**其实**：命令执行是单线程，但还有后台线程在做文件关闭、AOF 刷盘、6.0 之后的网络读写。你看到 `top` 里 CPU 超过 100%，正是这些线程。
**怎么验证**：`redis-cli INFO server | grep threads` 或 `ps -T -p <pid>`，能看到不止一条线程。

### 误区：既然是单线程，就不会有并发问题

```sketch

      { "id": "lost", "title": "结果是 11，不是 12", "sub": "要用 INCR 或事务", "tone": "amber" }

  ],
  "arrows": [
    { "from": "a", "to": "b" },
    { "from": "b", "to": "lost" }
  ]
}
```

**你以为**：只有一条线程，怎么用都不会出错。
**其实**：单条命令原子，不代表你的**业务逻辑**原子。先读后写、先判断后设置，跨了两条命令就存在竞态——两个客户端可能都判断通过，然后都去写。
**怎么验证**：两个 `redis-cli` 同时执行 `GET k`，看到都是旧值后各自 `SET k`，最终只剩后一个的值。

### 误区：加机器/加线程就能解决慢

**你以为**：QPS 上不去就是单线程的锅，换多线程版本就好。
**其实**：先看是不是有慢命令。`INFO commandstats` 里如果某条命令平均耗时是毫秒级，那它每次调用都在阻塞所有人，加机器只会让更多机器一起慢。
**怎么验证**：`redis-cli SLOWLOG GET 10` 看慢日志，先找出那条命令，再谈扩容。

## 小结

Redis 快靠三件事：数据在内存、一个线程用多路复用盯住所有连接、串行执行所以不用锁。单线程的代价是慢命令会阻塞全部请求，`KEYS`、大 `DEL`、大范围取数都要换成分批或异步版本。原子性的边界是单条命令。
