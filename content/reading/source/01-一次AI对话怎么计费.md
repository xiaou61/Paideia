## 这篇讲什么

一次「发送」在账单上要经过三次动作：**预留**、**结算**、**退款**。这篇跟着 `xiaou61/Paideia` 的真实代码走一遍，回答四个问题：

- 为什么不能等模型答完再扣钱？
- 结算为什么必须「只做一次」？
- 工具循环里，模型每转一圈都要付钱吗？
- 失败、超时、用户关页面时，已经占住的积分怎么回来？

## 先看整条路径

一次发消息只经过五个点：

1. `ConversationService.prepare()`：写用户消息、滑动续期，最后 `credits.reserve()` 预留。
2. `AssistantConversationController.runTurn()`：把这一轮丢到后台线程，调 `assistant.stream()`。
3. `AgentScopeConversation.stream()`：ReAct 循环，最多 4 轮，每轮都是一次真实的上游调用。
4. 成功：`conversations.complete()` 先落助手消息拿到 id，再 `credits.settle()` 按真实用量结算。
5. 失败：`onFailed()` 走**同一个** `settleOnce()`；拿不到用量就 `credits.refund()` 全额退回。

最值得注意的是第 4、5 步：成功和失败共用同一个结算出口，区别只是手上有没有 `usage`。

## 预留：为什么还没调模型就先扣一笔

结论先说：**预留不是收费，是为了在并发下不超扣。**

如果等模型答完再扣，两个请求会各自读到「余额够」，然后都扣，最后一个把余额扣成负数。预留把判断和执行压成一条 SQL，谁先扣到谁算数。

读这段要注意两件事：

- **`reserve()` 是 `prepare()` 里最后一个可能抛异常的动作**。历史、条目、记忆、学情这些读操作都排在它前面，因为它们都可能因为数据库异常失败；如果失败发生在预留之后，调用方连 `TurnPreparation` 都拿不到，也就没有任何地方会去退这笔钱。
- **`prepare()` 故意不加 `@Transactional`**。加了的话，预留抛 402 会把前面刚写入的用户消息一起回滚；界面早就把这句话画出来了，刷新就消失。用户确实说过那句话，扣费失败不该抹掉输入。

预留额不是报价，只是「先占住多少」。它由单次调用上限乘一个系数得到（代码默认是 `5000 × 0.2`）；真正扣多少要等结算。

`settle()` 只是入口，真正做多退少补的是私有方法 `settleAs`：它先算出 `actual`，再和 `reserved` 比，按上面注释里的三条规则改余额，最后写一行 `SETTLE`。

三个细节值得单独说：

- **实际费用会被截到单次上限**。价目表配错或上游异常放大用量时，这一步防止「一条消息吃掉全部余额」。
- **补扣补不动时不把余额扣成负数**。差额写进流水备注留痕，已经产生的回答不会被吞掉。
- **净额为 0 不写流水**。预留只动余额、不写流水，所以用户在明细里看到的是「一次调用一行」，而不是「预留一行、结算一行」。

代价是：如果进程崩在「预留后、结算前」，账本上没有 `RESERVE` 行可查。代码不靠流水自证，而是靠一条不变式发现异常——**余额 == 初始余额 + 流水求和**。等式不成立，就说明有一笔预留没结算。

## 为什么结算只能做一次

`settleOnce()` 的布尔闸不是防御性编程，而是针对一条真实路径：`onCompleted` 里先结算、再往 SSE 写 `done`；写事件时客户端可能已经断开，`send()` 会抛 `ClientGoneException`，异常落到外层 `catch`，于是同一次调用又走到结算。没有闸，这一轮就退两遍。

另一个出口是线程池拒收：任务根本没跑起来，预留到不了结算，`send()` 端点的 `catch` 会直接调 `settleOnce(..., null, null)` 全额退回，再把异常换成 429。也就是说，**预留的每个异常出口都有人负责**（进程直接崩掉除外，那就是上一节说的不变式要发现的情况）。

注意「失败不落库」只针对助手消息：失败轮次不写助手消息，也就不会进后续上下文；但钱那一步必须显式过账。

```code-tour
      "explain": "`total = add(total, toUsage(usage))` 把每一轮的输入、输出 token 相加。整条流结束后，`stream()` 里的 `listener.onUsage(turn.total)` 只调一次，控制器拿这个总和去结算。\n\n所以用户看到的是一条回答，账单上却是这一轮里所有模型调用的总和。工具轮不推正文，但它的 token 一分不少。"
    }
  ]
}
```

三条证据串起来看：

1. `maxIters(MAX_TOOL_ROUNDS)` 把循环卡在 4 轮，理由是防止模型绕着一个工具转圈把用户的钱烧光。
2. 超时预算是「每轮一份」再乘以轮数——注释写得很直白：4 次**串行上游调用**很容易超过单轮默认 60 秒。
3. 用量在 `ModelCallEndEvent` 上逐轮累加，最后把 `turn.total` 一次性交给控制器；控制器只结算一次，但结算的是所有轮次之和。

所以「只推最终轮的正文」是界面行为，不是计费行为。工具轮的旁白不推给用户，但它消耗的 token 照付。

## 失败时到底怎么退

把所有出口摊开看，规则其实只有一条：**有用量就按用量结算，没有用量就全额退回。**

| 情况 | 有 usage 吗 | 代码出口 | 钱怎么处理 |
| --- | --- | --- | --- |
| 上游报错、超时、客户端断开 | 可能已有 | `onFailed()` → `settleOnce()` → `settle()` | 按已产生的 token 扣，多退少补 |
| 上游报错且没返回用量 | 没有 | `onFailed()` → `settleOnce()` → `refund()` | 全额退回 |
| 线程池队列满，任务没跑起来 | 没有 | `send()` 端点的 `RejectedExecutionException` 分支 | 全额退回，返回 429 |
| 其它未捕获运行时异常 | 可能没有 | `runTurn()` 的 `catch` | 同上，没用量就全额退 |
| 实际费用超过预留且余额不够补 | 有 | `settleAs()` 的 `else` 分支 | 不扣成负数，差额写备注 |

最后一行值得记住：系统宁可少收，也不把账面做成负数，更不会因为补扣失败把已经生成的回答丢掉。审计页上「有用量但 0 扣减」或一条带差额备注的流水，就是这类情况的痕迹。

## 读源码时该问的三个问题

1. **这笔钱是在调用前动，还是调用后动？失败路径上有几个出口？** 顺着 `reserve()` 的返回值找：谁接住了它，`settle()` / `refund()` 各有哪些调用点，每个调用点是否都能拿到预留额。找不到出口的那条路径，就是会漏钱的路径。
2. **一次用户动作里发生了几次真实上游调用？** 看循环上限（`maxIters`）、每次调用的结束事件（`ModelCallEndEvent`）、以及用量是「最后一轮」还是「逐轮累加」。框架把重试和工具轮藏起来时，这一步最容易算少。
3. **这段结算代码能不能安全地执行两次？** 看有没有幂等闸、流水写的是净额还是每次动作一行、`ref_message_id` 能不能对上唯一一条消息。不能回答这个问题，就不要在失败路径上随手加一次「补偿」。
