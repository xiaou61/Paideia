## 面板是空的，而 `journalctl` 里有

`deploy/ops/alloy.service` 开头四行注释：

> Alloy（Paideia 日志采集，WORK-042）。读 journald 需要 `adm` 与 `systemd-journal` 组；install-ops.sh 负责加组，这里再用 SupplementaryGroups 兜一层（组不生效时 Alloy 会"启动成功但一条日志都没有"）。

同一件事在 `deploy/ops/install-ops.sh:55` 又写了一遍：

> Alloy 读 journald 必须在这两个组里；缺了不会报错，只是**一条日志都采不到**。

两个文件、两处注释，说的是同一种故障：**采集端读不到 journal 时不报错**。服务状态是 active，Grafana 的数据源是绿的，查询语法没错——结果就是空。

把这条链和 `journalctl` 并排放一起，就是这篇文章要走的线：

```text
# 标准形态，未实跑
$ journalctl -u paideia.service -n 3 --no-pager
Nov 19 10:02:41 paideia paideia[1187]: Started PaideiaApplication in 12.483 seconds
Nov 19 10:02:52 paideia paideia[1187]: Tomcat started on port 8080
Nov 19 10:03:10 paideia paideia[1187]: GET /api/knowledge/entries 200 34ms

$ curl -s 'http://127.0.0.1:3100/loki/api/v1/label/unit/values' | jq -c .data
["laya.service","rustfs.service"]
```

`unit` 这个标签是 `alloy-config.alloy:9-21` 那段 relabel 打上去的，值直接取自 journald 的 `_SYSTEMD_UNIT`。这份清单里有 laya 有 rustfs，没有 paideia——而 `journalctl` 里明明有它的日志。所以问题不在 Grafana，也不在「日志有没有写」，而在中间那一段没把它送过去。

> 写作环境是 Windows，没有 journald 也没有 systemd。本文所有 `journalctl`、`logrotate`、`curl` 的回显都标了「标准形态，未实跑」。能在这台机器上真跑的只有两件事：读仓库里的 unit、配置和注释，以及查 man page 对数字——那部分结论带出处。

## 一条日志要穿过四道门

应用 → journald → Alloy → Loki → Grafana。每一道都能让它消失，消失的方式各不相同，所以第一步不是「搜日志」，是先判断断在哪一道。

**第一道，journald 存不存。** systemd 的 `StandardOutput=` 默认就是 `journal`，所以 unit 没动过这一项时，`journalctl` 里没有东西，就该去查应用是不是只写了自己的文件、根本没往 stdout 打印。`content/courses/spring/20-打包与部署.md:172` 那句「日志走 journald（`journalctl -u paideia -f`），不做自建日志轮转」是这个仓库的约定，不是保证——`systemctl cat paideia.service` 看一眼 `StandardOutput=` / `StandardError=` 就知道这个约定有没有被执行。

**第二道，Alloy 读不读得到。** journalctl(1) 写明：`Members of the groups systemd-journal, adm, and wheel can read all journal files.` `alloy.service:14` 的 `SupplementaryGroups=adm systemd-journal` 和 `install-ops.sh` 里的 `usermod -aG adm,systemd-journal alloy` 都是在过这道门。验证不要靠猜，换个身份读一次就行：

```bash
# 标准形态，未实跑
$ sudo -u alloy journalctl -n 1 --no-pager
Nov 19 10:03:10 paideia paideia[1187]: GET /api/knowledge/entries 200 34ms
```

读到就是有权限；`Permission denied` 就是没有。另外 `usermod` 只改磁盘上的组表，已经在跑的进程还拿着旧的那份组，必须重启进程（`systemctl restart alloy`）才生效——这是「加了组还是采不到」的第二种成因。

**第三道，Alloy 采不采。** `alloy-config.alloy:9-21` 只采白名单：正则 `paideia\.service|laya\.service|rustfs\.service|mysql\.service|redis-server\.service` 配 `action = "keep"`，不在里面的 unit 被直接丢弃，不报错。按 relabel 的语义正则两端是锚定的，所以 `paideia\.service` 不会顺带匹配 `paideia-backup.service`。上线一个新服务就得把它加进这个正则，否则 Loki 里永远没有它。字段名那里还有一处容易照抄错：配置写的是 `__journal__systemd_unit`（连着两个下划线），它是 `__journal_` 前缀加小写字段名，对应 journal 的 `_SYSTEMD_UNIT`。

**第四道，Loki 留不留。** `loki-config.yaml:38-39` 是 `retention_period: 720h`（30 天），`:40-42` 的 `reject_old_samples: true` 配 `reject_old_samples_max_age: 168h`——时间戳超过 7 天的样本直接拒收，`:43` 的 `max_query_lookback: 720h` 卡住能查的时间跨度。「30 天前那次故障」的答案写在这几行里，不在 Grafana 的下拉框里。Grafana 自己还有一层：新建面板的默认时间范围是最近 6 小时，查不到先看右上角，比怀疑数据源快。

把四道门压成一张表，出问题时按症状查：

| 看到的现象 | 最可能断在哪 | 先跑什么 |
| --- | --- | --- |
| `journalctl -u x` 一条都没有 | 第一道：应用没往 stdout 写，或 unit 改了输出方向 | `systemctl cat x.service` 看 `StandardOutput=` / `StandardError=` |
| journalctl 有，Loki 里查不到 | 第二道：账号读不到 journal 文件 | `sudo -u alloy journalctl -n 1 --no-pager` |
| Loki 里有别的服务，就是没有这个 | 第三道：不在白名单正则里 | 对照 `alloy-config.alloy` 的 `keep` 正则，把 unit 加进去 |
| 昨天查得到，今天没了 | 第四道：保留期到了，或 journal 先被 vacuum 掉 | 先 `journalctl --since yesterday` 看 journal 里还在不在，再对 `retention_period` |
| 只有时间戳很旧的日志被丢 | 第四道：`reject_old_samples_max_age` | `timedatectl` 对时钟，看发送端有没有积压缓冲 |
| curl 有数据，面板空 | 第四道之后：查询面板本身 | 右上角时间范围，再核对 label 名有没有写错 |

## 还有一条路：文本副本

把 `syslog` 当成 journal 的备份是反的。journald.conf(5) 里是两条不同的路——journald 把消息转发到 `/run/systemd/journal/syslog`，由 syslog 守护进程去读（`ForwardToSyslog=`，默认只开了 wall 转发，也就是默认不转发）；或者 syslog 守护进程像 `journalctl` 一样直接读 journal 文件。man page 把这层对应关系写得很直白：这类守护进程该看的是 `Storage=`，不是 `ForwardToSyslog=`。

于是三件事跟着变：

- 「syslog 里有、journal 里没有」——前提是先开了转发，默认配置下这个现象本身就说明有人改过配置。
- 「journal 里有、文本文件里没有」——很正常。第二种路在 `Storage=none` 时根本不成立，而且文本文件还要再过一遍 logrotate。
- 发行版给的是哪套，只能查不能背：`grep -E '^ForwardToSyslog' /etc/systemd/journald.conf`，`grep -r imjournal /etc/rsyslog.conf /etc/rsyslog.d/`。

## 找一条消息：条件从窄到宽

排查顺序应该是「先证明这条日志进没进 journal」，而不是把所有过滤参数一次性堆上去——堆上去之后结果为空，你分不清是日志不存在，还是条件写错了。每个过滤参数都有自己的语义，写错一个就是完全不同的查询：

| 参数 | 实际做了什么 | 容易踩的地方 |
| --- | --- | --- |
| `-u x` | 展开成多路 OR：`_SYSTEMD_UNIT=`、关于该单元的 `UNIT=`/`_PID=1`、`OBJECT_SYSTEMD_UNIT=`、`COREDUMP_UNIT=` | 比手写 `_SYSTEMD_UNIT=x` 更宽；以为两者等价，会漏掉 coredump 那类记录 |
| `-k` | 加 `_TRANSPORT=kernel` 匹配，并隐含 `--boot=0` | 它不是 `dmesg` 的封装，只给本次开机的内核消息；`dmesg` 读的是内核环形缓冲区 |
| `-b -1` | 上一次开机 | 需要持久化，`--list-boots` 里没有负号行就匹配不到任何东西 |
| `-p err` | err(3) 及更严重（crit/alert/emerg） | 单值是阈值不是等号，`-p err` 也会给 crit 和 emerg |
| `--since 14:00` | 只写时间时默认理解为今天 14:00 | 要看昨天的同一时刻必须写日期 |
| `-n` | 默认 10 行 | 配 `-f` 时它只决定先回显多少行，随后才是实时追加 |
| `--no-pager` | 不交给 less | 脚本、管道里必须加，否则输出进分页器、等人按键 |
| `-o cat` | 只留消息正文 | hostname、pid、时间这些前缀全没了，按 pid 筛就得换 `-o json-pretty` |
| `-o json-pretty` | 每个字段单独展开 | 查 `_PID`、`_SYSTEMD_UNIT` 这类字段只能靠它 |

然后是一个具体场景：**日志里少了一段**。

先别怀疑级别。journald 的 `MaxLevelStore=` 默认是 `debug`，默认配置下 debug 也会被存下来，所以「级别太高被 journal 丢掉了」不是默认配置下的第一嫌疑。真正的第一嫌疑是速率限制：`RateLimitIntervalSec=` / `RateLimitBurst=` 默认是 30 秒 10000 条，按 cgroup 逐服务计算（journald.conf(5)，systemd 262）。某个服务刷得太快，超出那一段的消息被丢弃，journal 只补一条形如 `Suppressed <条数> messages from <cgroup>` 的汇总记录。丢掉的条目不回来。查它：

```bash
# 标准形态，未实跑
$ journalctl -t systemd-journald -g Suppressed --since today
```

要放宽只能在 unit 上用 `LogRateLimitBurst=` / `LogRateLimitIntervalSec=` 覆盖（systemd.exec(5)），或者改 `/etc/systemd/journald.conf` 的全局值。这是取舍：放宽等于让一个刷日志的进程把 journal 撑大，跟下面磁盘那节是同一笔账。

第二嫌疑是没落盘。`SyncIntervalSec=` 默认 5 分钟才同步一次，只有 crit 及以上级别会立即同步——所以刚写几分钟的日志遇上断电，丢的是那一小段，不是全部。

跨服务追一个请求，用 trace id 全文搜最省事：

```bash
# 标准形态，未实跑
$ journalctl --since '10 min ago' -o cat --no-pager | grep 'traceId=7f3a'
```

## 上次开机的那段日志

```text
# 标准形态，未实跑
$ ls -d /var/log/journal
/var/log/journal

$ journalctl --list-boots
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
 -1 3d1f0c7a9e4b4c1e8f2a5b6c7d8e9f01 Tue 2026-11-18 09:12:03 CST Wed 2026-11-18 23:48:11 CST
  0 9d2b1e4c6f8a4b2d0c3e5f7a9b1d2c34 Wed 2026-11-19 08:01:55 CST Wed 2026-11-19 10:03:10 CST
```

`--list-boots` 只有 `0` 那一行，就说明没有跨重启的记录，`-b -1` 没有任何开机可以匹配——不是命令写错了。判据是 `Storage=` 的四个取值：

| `Storage=` | 日志放在哪 | 重启后还在吗 |
| --- | --- | --- |
| `volatile` | `/run/log/journal`，只有内存 | 不在 |
| `persistent` | `/var/log/journal` | 在 |
| `auto` | 目录存在就按 `persistent`，不存在就按 `volatile` | 看目录在不在 |
| `none` | 不存，但转发仍然工作 | 不在 |

默认值不要背，会过期。systemd 262 的 journald.conf(5) 写的是编译期默认 `persistent`，而编译期默认是发行版能改的东西——`/etc/systemd/journald.conf` 就是改它的地方，被注释掉的旧行会留在文件里。真正的事实只有两条命令：`ls -d /var/log/journal` 看目录在不在，`journalctl --list-boots` 看开机记录有几行。

要开持久化：目录没建就先建好权限，再让它生效。

```bash
# 标准形态，未实跑
$ sudo mkdir -p /var/log/journal
$ sudo systemd-tmpfiles --create --prefix /var/log/journal
$ sudo journalctl --flush        # 把 /run 里已有的刷进去
```

**已经没存下来的补不回来**。日志和别的数据一样，排查时才想起要开持久化，那这一次就没有。

## 磁盘被写满

```text
# 标准形态，未实跑
$ journalctl --disk-usage
Archived and active journals take up 1.2G in the file system.
```

`--vacuum-size=500M` 跑完再查，数字没降是正常的：`--disk-usage` 把 active 和 archived 一起算，而 vacuum 只删 archived 文件，journalctl(1) 明说它对 `--disk-usage` 只有「间接影响」。要让当前文件也进删除范围，先 `--rotate` 把它归档，再 vacuum。

| 症状 | 该动哪个 | 代价 |
| --- | --- | --- |
| 用量缓慢涨，一年也到不了上限 | `SystemMaxUse=` | 到上限就删最旧的归档文件，历史会变短 |
| 磁盘本来就紧，别让日志吃满 | `SystemKeepFree=` | 与 `SystemMaxUse=` 取更小的那个，实际能用比这个上限更少 |
| 单个文件太大，删除粒度粗 | `SystemMaxFileSize=` | 默认是 `SystemMaxUse=` 的 1/8、封顶 128M，调小只是让删除更细 |
| 想按时间兜底 | `MaxRetentionSec=` | 默认是 0，也就是关着，不写就不生效 |
| 服务刷日志把别人挤掉 | `RateLimitBurst=` / `LogRateLimitBurst=` | 放宽后总量上去，等于把问题推给磁盘 |

以上默认值出自 journald.conf(5)（systemd 262）：`SystemMaxUse=` 与 `RuntimeMaxUse=` 默认是文件系统的 10%、封顶 4G；`SystemKeepFree=` / `RuntimeKeepFree=` 默认 15%、封顶 4G。

文件日志那半边是另一套工具。规则写在 `/etc/logrotate.d/` 下，由发行版的定时单元每天触发（systemd 的发行版是 `logrotate.timer`，走 cron 的发行版是 `/etc/cron.daily/logrotate`），所以写完规则不等于已经轮转过。

| 指令 | 实际动作 | 前提或代价 |
| --- | --- | --- |
| `rotate 7` | 留 7 份历史，第 8 份删掉 | 磁盘预算按「单文件大小 × 7」算，不是按一份算 |
| `compress` | 历史文件 gzip | 之后查历史要用 `zgrep`，`grep` 查不到 |
| `copytruncate` | 复制一份再截断原文件 | 复制与截断之间有时间片，这一小段的写入会丢；换来的是不用通知程序重开 |
| `create` + `postrotate` | 改名后发信号让程序重开 | 程序得支持（`SIGUSR1` / `SIGHUP`），否则新日志继续写旧 inode |
| `-d` | 只演练，逐条打印会怎么处理，不动文件 | 写完规则先跑这个，比等第二天发现没轮转便宜 |

最后一条和空间有关的老账：`rm` 一个正在被写的日志文件不释放空间，进程还开着那个 inode（第 14 关会再讲一次）。要清空用 `truncate -s 0`，要确认谁还占着用 `lsof +L1`。

## 还差的

1. **所有回显都没实跑。** 这台机器是 Windows，没有 journald、没有 logrotate、没有 Loki。上面每个 `# 标准形态，未实跑` 的块是按 man page 和仓库配置写的，跑出来格式对不对要在服务器上对一次；真遇到不一致，以你机器上的 `man journalctl` 为准。
2. **默认值不是你的发行版的值。** journald 那一串数字出自 systemd 262 的 man page。`systemctl --version` 报的版本低于它时，某些默认值可能不同（`Storage=` 的编译期默认就改过）；`journalctl --disk-usage` 和 `--list-boots` 才是你机器上的事实。
3. **`paideia.service` 本体没看到。** 它不在 `deploy/` 下，是服务器上由发布流程生成的，所以它的 `StandardOutput=` 和 `LogRateLimitBurst=` 我没有看到，第一道门在这篇文章里是推理不是观察。
4. **文件日志那一路没有轮转配置。** `deploy/ops/grafana.ini:10` 让 Grafana 往 `/var/log/grafana` 写文件，但仓库里没有任何 logrotate 规则（grep 过，`deploy/` 下一处都没有）。它会不会长满、要不要补一条规则，没有验过。
5. **Loki 的实际占用和保留期没量过。** `retention_period: 720h` 在这个数据量下够不够、磁盘实际用掉多少，都没测。`reject_old_samples_max_age: 168h` 一旦真触发，表现是发送端成功、Loki 里查不到——这个坑值得单独盯一次。
