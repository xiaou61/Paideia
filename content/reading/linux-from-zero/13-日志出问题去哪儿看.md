## 这一关在解决什么

"服务挂了，日志在哪？"——这个问题在 Linux 上有两个答案，取决于谁写的：

- **内核和系统服务**写的 → journald（`journalctl`）或 `/var/log` 下的文本文件；
- **你的应用**写的 → 你自己的日志文件，systemd 服务也可以让它进 journal。

这一关把 `/var/log` 的目录结构、`journalctl` 的六个过滤条件、以及"日志把磁盘写满"这件事讲清楚。

## 为什么日志分两套

因为历史原因叠了两层：

- **syslog 时代**：`rsyslog`/`syslog-ng` 收消息，按规则写到 `/var/log/syslog`、`/var/log/auth.log` 等纯文本文件。这套还在跑。
- **systemd 时代**：journald 用二进制格式收所有 stdout/stderr 与内核消息，存在 `/var/log/journal`（持久）或 `/run/log/journal`（内存，重启即失）。

现在的常态是**两套同时存在**：journald 收，rsyslog 再从 journal 读出来写成文本文件。所以同一条消息你既能在 `journalctl` 里看到，也能在 `/var/log/syslog` 里 grep 到。排查时用 `journalctl` 更结构化（有服务名、优先级、启动批次），归档与跨机器收集则常走文本文件。

## 讲解

### `/var/log` 里都放了什么

| 路径 | 内容 | 什么时候看 |
| --- | --- | --- |
| `/var/log/syslog`（Debian）或 `/var/log/messages`（RHEL） | 系统综合日志 | 万金油，先看这个 |
| `/var/log/auth.log` / `/var/log/secure` | 登录、sudo、SSH | 怀疑被爆破、查谁提权了 |
| `/var/log/kern.log` | 内核消息 | OOM Killer、磁盘错误、内核 panic |
| `/var/log/dpkg.log` / `/var/log/apt/history.log` | 装包卸载记录 | "谁昨天升级了这个包？" |
| `/var/log/nginx/access.log`、`error.log` | 应用自己的日志 | 按应用而异 |
| `/var/log/journal/` | journald 的二进制库 | 用 `journalctl` 读，**别直接 cat** |

`/var/log/journal` 里的文件是二进制，`cat` 只会吐乱码。所有读取都走 `journalctl`。

### `journalctl` 的六个过滤条件

```text
$ journalctl -u paideia                 # 按服务
$ journalctl -b                         # 本次开机以来
$ journalctl -b -1                      # 上一次开机（排查"重启前发生了什么"）
$ journalctl -p err                     # 只看 error 及以上
$ journalctl --since "1 hour ago"
$ journalctl --since "2026-10-29 14:00" --until "2026-10-29 15:00"
$ journalctl -f                         # 持续跟随（等价 tail -f）
$ journalctl -u paideia -n 200 --no-pager
```

优先级 `-p` 的取值（从高到低）：`emerg`、`alert`、`crit`、`err`、`warning`、`notice`、`info`、`debug`。写 `-p err` 表示"err 及更严重的"。

组合用法是排查的主力：

```text
# 上次重启前，paideia 服务的错误
$ journalctl -u paideia -b -1 -p err --no-pager

# 今天 14 点之后的所有内核错误
$ journalctl -k --since "14:00" -p err
```

`-k` 是"只看内核消息"，等价于 `dmesg` 但带时间戳与过滤能力。查 OOM Killer：

```text
$ journalctl -k | grep -i "killed process"
```

看到 `Out of memory: Killed process 9812 (java)` 就说明进程是被系统杀的，不是自己崩的——这是"服务莫名消失"最常见的真相。

### 看单条消息的完整信息

```text
$ journalctl -u paideia -o json-pretty -n 1
```

会给出 `_PID`、`_UID`、`_SYSTEMD_UNIT`、`_COMM`、`_EXE`、`_CMDLINE`、`PRIORITY` 等字段。做日志聚合或想确认"这条消息到底是哪个进程写的"时用这个输出。

### 别让日志把磁盘写满

两件事都会失控：**应用不轮转**、**journal 不清理**。

**应用日志用 logrotate。** 系统里所有 `*.log` 的轮转规则在 `/etc/logrotate.d/`，一个服务一个文件：

```text
# /etc/logrotate.d/paideia
/var/log/paideia/*.log {
    daily
    rotate 7
    missingok
    notifempty
    compress
    delaycompress
    copytruncate
    postrotate
        systemctl reload paideia > /dev/null 2>&1 || true
    endscript
}
```

每一行的意思：

| 指令 | 作用 |
| --- | --- |
| `daily` | 每天轮转一次（也可 `size 100M`、`hourly`） |
| `rotate 7` | 留 7 份，第 8 份删掉 |
| `missingok` | 文件不存在不报错 |
| `notifempty` | 空文件不轮转 |
| `compress` | 旧文件 gzip |
| `copytruncate` | 复制一份再把原文件截断（**不给程序发信号也能用**，代价是复制瞬间可能丢几行） |
| `postrotate` | 轮转后通知程序重开日志文件 |

`copytruncate` 和 `postrotate` 是两套方案：前者简单，适合不会重开日志文件的程序；后者更准（不丢行），但要求程序支持（Nginx/MySQL 收到 `SIGUSR1` 会重开）。**两个都写虽然不冲突，但没必要。**

手动验证规则有没有写对：

```text
$ sudo logrotate -d /etc/logrotate.d/paideia    # -d 只演练，不真动文件
$ sudo logrotate -f /etc/logrotate.d/paideia    # -f 立即执行一次
```

`-d` 的演练输出会逐条说明"这个文件会怎么处理"，写完规则先跑它。

**journal 用 `--vacuum`。**

```text
$ journalctl --disk-usage           # 当前占了多少
$ sudo journalctl --vacuum-size=500M   # 缩到 500M 以内
$ sudo journalctl --vacuum-time=14d     # 只留 14 天
```

想让它永久受限，改 `/etc/systemd/journald.conf`：

```ini
[Journal]
SystemMaxUse=1G
SystemMaxFileSize=100M
MaxRetentionSec=30day
Storage=persistent
```

`Storage=persistent` 才把日志写到 `/var/log/journal` 并跨重启保留；默认 `auto` 时，如果目录不存在就只放内存（`/run/log/journal`），**重启即无**——这也是"上次重启的日志呢？"这个问题的答案：没配持久化就没有。

### 追踪一个请求

应用日志一般带 trace id。跨多个服务的排查方式是全文搜这个 id：

```text
$ journalctl -u paideia --since "10 min ago" | grep -i "traceId=7f3a"
```

如果日志是自己的文件，`grep -n` 带行号后再用 `sed -n '起点,终点p'` 看上下文（第 07 关）。比"打开 vim 翻半天"快得多。

## 常见误区

### 误区：日志越多越好，全开着

**你以为**：debug 级别一直开着，出问题信息最全。
**其实**：debug 级别在高并发下能一天写几百 GB，把磁盘写满，然后所有服务一起挂——故障的根因就变成"日志把盘写满了"。正确做法是默认 info，需要时**临时**调 debug（改配置或调接口），复现完调回去。
**怎么验证**：`du -sh /var/log/*` 按服务看占用；`journalctl --disk-usage` 看 journal 大小。

### 误区：`/var/log/syslog` 里没有就是没发生

**你以为**：搜了 syslog 没找到，说明没这回事。
**其实**：不同发行版的默认文件不同（Debian 是 `syslog`，RHEL 是 `messages`），而且 journald 里可能有更全的内容（包括只进 journal 未写文件的）。另外**日志会轮转**——`syslog.1`、`syslog.2.gz` 里还有旧内容，`grep /var/log/syslog` 只看了当前那个。
**怎么验证**：`ls -l /var/log/syslog*` 看所有轮转文件；`zgrep 关键词 /var/log/syslog.*.gz` 搜压缩历史。

### 误区：日志文件删了就释放空间了

**你以为**：`rm /var/log/big.log` 空间立刻回来。
**其实**：如果进程还开着这个文件（日志写手一直在写），`rm` 只是删了目录项，**inode 仍被占用，空间不释放**（第 14 关会再遇到）。日志文件要用 `truncate -s 0` 或走 logrotate 的 `copytruncate`，别直接 `rm`。
**怎么验证**：`lsof +L1 | grep deleted` 能看到"已删除但仍被打开"的文件；`df -h` 的空间在重启相关进程后才回来。
