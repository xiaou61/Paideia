## 这一关在解决什么

为什么 `cmd > out.log 2>&1` 里的顺序不能反？为什么 `sudo echo x > /root/f` 还是没权限？为什么管道后面的命令收不到报错信息？

这三个问题的答案都在同一件事上：**每个进程有三根默认的水管，而 shell 负责在启动进程时把水管接到哪**。理解了这一点，`>`、`2>`、`|`、`tee`、`xargs` 就全是一个东西的不同接法。

## 为什么是"流"

Unix 的核心设计之一是：**程序不关心输出去哪，只往"标准输出"里写**。屏幕上显示、写进文件、喂给下一个程序，都是 shell 换了个接口，程序自己一行都不用改。

这就是"小工具组合出大功能"的物理基础：`grep` 不知道上游是 `cat` 还是 `curl`，它只读 stdin。

## 讲解

### 三根水管：0、1、2

每个进程启动时都拿到三个已经打开的"文件"：

| 编号 | 名字 | 默认接到 | 用途 |
| --- | --- | --- | --- |
| `0` | stdin 标准输入 | 键盘 | 程序读的东西 |
| `1` | stdout 标准输出 | 终端 | 程序正常的结果 |
| `2` | stderr 标准错误 | 终端 | 报错、警告、进度条 |

**默认都接在终端上**，所以你能同时看到结果和报错。重定向就是在启动进程时把某一根改接到文件或另一个进程。

`2>&1` 里的 `2` 和 `1` 就是这两个编号。叫"文件描述符"（file descriptor，fd）。

### 输出重定向：`>` 与 `>>`

```text
$ echo hello > a.txt        # 覆盖写（文件不存在就创建）
$ echo world >> a.txt       # 追加
$ cat a.txt
hello
world
```

`>` 在**命令执行之前**就把文件清空了。这一点有实际后果：

```text
$ sort big.txt > big.txt    # 本想把排序结果写回，结果是空文件
```

因为 shell 先打开 `big.txt` 并截断，`sort` 再读它时已经是空的了。想原地改要写临时文件再 `mv`：

```text
$ sort big.txt > big.tmp && mv big.tmp big.txt
```

### 错误重定向：`2>`、`&>`、`2>&1`

```text
$ ls /nope 2> err.log       # 只把错误写进文件，屏幕上看不到
$ ls /nope > out.log 2>&1   # 输出和错误都进 out.log
$ ls /nope &> out.log       # bash 简写，等价于上面那条
$ ls /nope > /dev/null 2>&1 # 全部丢掉
```

`/dev/null` 是内核提供的"黑洞"设备：写进去的东西直接丢弃，读它永远得到空。它有正经用途——把"不关心的噪音"扔掉，只留信号：

```text
$ find / -name "*.conf" 2>/dev/null       # 忽略权限报错，只看结果
```

**顺序为什么不能反**，这是本关最重要的一条：

```text
$ cmd > out.log 2>&1
```

从前往后读，shell 做两件事：

1. `> out.log`：把 fd **1** 指向 `out.log`。
2. `2>&1`：把 fd **2** 指向"**fd 1 现在指向的地方**"，也就是 `out.log`。

结果：两根都进文件。再看反过来的写法：

```text
$ cmd 2>&1 > out.log
```

1. `2>&1`：fd 2 指向"fd 1 现在指向的地方"——**此时 fd 1 还是终端**，所以错误仍去终端。
2. `> out.log`：fd 1 指向文件。

结果：错误在屏幕上，正常输出在文件里。**`2>&1` 复制的是"当时的"目标，不是"永远的"关系。**

### 输入重定向：`<`

```text
$ wc -l < access.log        # 把文件喂给 stdin
$ mysql -u root -p db < init.sql    # 批量执行 SQL
```

`<` 和"把文件名当参数传"不一样：`wc -l access.log` 会打印文件名和行数，`wc -l < access.log` 只知道从 stdin 收了一堆行，只打印行数。写脚本时 `<` 更干净。

### 管道：`|`

`|` 把左边命令的 **stdout** 接到右边命令的 **stdin**：

```text
$ cat access.log | grep " 500 " | wc -l
```

**只有 stdout 会过管道，stderr 仍然直接去终端。** 这就是"加了管道之后报错信息突然出现在屏幕上、没进文件"的原因。要把 stderr 也交给下一段，先合并：`cmd 2>&1 | grep foo`。

管道里的每个程序是**同时运行**的，不是一个跑完再跑下一个。`tail -f app.log | grep ERROR` 能实时过滤，就是这个原因。

一个判断技巧：管道右边的命令如果"不支持从 stdin 读"（比如 `ls`），它就无视输入直接干活。所以 `ls | grep log` 能过滤，是因为 `grep` 在读 stdin，`ls` 的输出正好是它要的。

### 保存一份同时看：`tee`

```text
$ ./deploy.sh 2>&1 | tee deploy.log
```

`tee` 把 stdin 同时写屏幕和文件——既想看着跑，又想留档时用。追加用 `tee -a deploy.log`。

### `xargs`：把"一批参数"喂给只吃参数的命令

有些命令不读 stdin（`rm`、`kill`、`chmod`），管道给它们喂数据没用。`xargs` 把 stdin 的每一行转成**命令行参数**：

```text
$ find /data -name "*.tmp" | xargs rm -f
$ find /data -name "*.log" | xargs -I{} mv {} /backup/{}
$ cat hosts.txt | xargs -n 1 ping -c 1
```

三个要点：

- `-n 1`：一次只传一个参数。
- `-I{}`：用占位符指定参数插在命令的哪个位置。
- **文件名里有空格时**要用 `-0`：`find ... -print0 | xargs -0 rm -f`。不加的话空格会把一个文件名拆成两个参数，删错东西。

### 一行接成脚本：`;`、`&&`、`||`

```text
$ a; b            # a 跑完不管成败都跑 b
$ a && b          # a 成功（退出码 0）才跑 b
$ a || b          # a 失败才跑 b
$ a && b || c     # 成功走 b，失败走 c
```

`&&` 在部署脚本里是核心：`cd /app && git pull && mvn package` 任何一步失败就停，不会在错的目录里继续干。

退出码用 `$?` 看（0 是成功，非 0 是失败）：

```text
$ ls /nope 2>/dev/null; echo $?
2
```

`2` 是 `ls` 的"文件不存在"，不是 shell 的错。每个程序自己定义非 0 的含义。

### heredoc：一段多行输入

```text
$ cat > app.env <<EOF
DB_HOST=127.0.0.1
DB_PORT=3306
EOF
```

`<<EOF` 表示"以下到我看到单独一行 `EOF` 为止，全作为 stdin"。要把 `$变量` 原样写进去（不要展开），把结束符加引号：

```text
$ cat > template.txt <<'EOF'
${DB_HOST}
EOF
```

带引号时 shell 不做任何替换——写配置文件模板时必须这样，否则 `$HOST` 会被你的 shell 先展开成空字符串（第 17 关还会遇到这个坑）。

## 常见误区

### 误区：`sudo echo 内容 > /etc/file` 能写进受保护的文件

**你以为**：前面有 `sudo`，整条命令就有权限了。
**其实**：**重定向是 shell 做的，不是 `echo` 做的**。shell 先以你自己的身份打开 `/etc/file`，这一步就被拒了，`sudo` 只作用于后面那个 `echo`——压根没轮到它。正确写法是把整条命令交给 root shell：

```text
$ echo "内容" | sudo tee /etc/file        # 推荐：tee 由 sudo 执行
$ sudo sh -c 'echo "内容" > /etc/file'
```

**怎么验证**：`sudo echo x > /root/t.txt` 报 `Permission denied`；`echo x | sudo tee /root/t.txt` 成功。

### 误区：`tail -f log | grep X > out.txt` 等价于 `tail -f log > out.txt | grep X`

**你以为**：位置换来换去没区别。
**其实**：第一种是把 `grep` 的结果写进文件（正确）；第二种是先让 `tail` 写进文件，再把文件的**空内容**（`>` 会先截断）喂给 `grep`，于是你永远看不到新行。重定向写在哪个命令后面，就作用于哪个命令。
**怎么验证**：两个写法各跑一次，看 `out.txt` 有没有内容增长。

### 误区：`cmd > f` 之后终端还能看到错误

**你以为**：`>` 只重定向正常输出，错误还会显示在屏幕上，挺方便。
**其实**：**确实如此，但经常不是你要的**——把它放进定时任务或 systemd 里跑时，屏幕不存在，错误就写进 journal 或“无处可去”。所以运维脚本一律写 `>> f 2>&1`，别指望 stderr 自动有个家。
**怎么验证**：`nohup ./job.sh > job.log 2>&1 &` 与 `nohup ./job.sh > job.log &` 各跑一次，人为制造一个错误，对比 `job.log` 里有没有那行。
