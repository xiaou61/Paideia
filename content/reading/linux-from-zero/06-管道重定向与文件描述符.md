## 判题说「通过」，可学员的报错一行都没显示

我在本机 Git Bash 里敲了这一行：

```text
# 本机实跑（Git Bash / MSYS，bash 5.2.26、gzip 1.13、coreutils 8.32）
$ dash -c "ls /nope &> out.log"
ls: cannot access '/nope': No such file or directory
$ echo $?
0
$ wc -c < out.log
0
```

报错打在屏幕上，退出码 **0**，`out.log` 是个 **0 字节空文件**。同一行换 bash：

```text
# 本机实跑
$ bash -c "ls /nope &> out.log"; echo $?
2
$ wc -c < out.log
53
```

我原来以为 `&>` 只是 `> out.log 2>&1` 的简写，哪个 shell 都认。实际是：**`&>` 是 bash 的方言，POSIX sh 里没有这两个字符组成的重定向符**。dash 把它拆成「`&`（放后台）」加「`> out.log`（对一条空命令重定向）」，于是你得到一条后台跑的命令、一个空文件、和一个骗你的 0。

这不是我编出来的场景，是这类代码里最贵的那种 bug：**脚本没报错，产物是空的，而判「成功」的依据恰好是退出码**。

反方向也一样贵。这个仓库里真跑的一段容器内脚本，`backend/paideia-sandbox/src/main/java/io/github/xiaou61/sandbox/internal/run/DockerCommand.java:111` 起：

```text
bash /tmp/in/run.sh > /tmp/.out 2> /tmp/.err
rc=$?
bash /tmp/in/judge.sh > /tmp/.jout 2> /tmp/.jerr
jrc=$?
find . -printf '%M %s %p\n' 2>/dev/null | sort > /tmp/.after
echo '###RC'
echo "$rc $jrc"
echo '###OUT'
head -c 8000 /tmp/.out
```

同一份代码的第 88–89 行写着为什么这里必须写 `bash` 而不是 `sh`：

> **用 bash 而不是 sh**：课程讲的是 bash（`[[ ]]`、`set -euo pipefail`），debian 的 `sh` 是 dash，照着课抄会失败——镜像行为必须与教材一致。

也就是说，上面那个 `&>` 的坑，这个仓库的解决方式不是「小心点」，是**显式指定解释器**。这篇就沿着这一段脚本讲：它一共动了四次文件描述符，每次都在决定「谁的输出算数」。

先约好标注方式，后面不再重复：

- 标 **本机实跑** 的 `text` 块，是我在 Windows 的 Git Bash（MSYS）里真敲的，有版本号。
- 标 **标准形态，未实跑** 的，是按官方文档和仓库代码写的。**我没有 Linux 机器，也没有 MySQL**，这些不是实测输出，别当证据用。

## 三根 fd，和一次在命令执行前就发生的截断

进程启动时已经开着三个文件：fd `0` 接键盘（stdin），fd `1` 接终端（stdout），fd `2` 也接终端（stderr）。编号就是文件描述符（file descriptor，fd），`2>&1` 里那两个数字说的就是它们。

`>` 做的不是「把输出改成写文件」，而是**在启动程序之前**，把 fd 1 这个表项指向一个刚打开的文件。打开时带截断（`O_TRUNC`），所以**程序还没开始运行，文件已经是 0 字节**。

```text
# 本机实跑
$ printf 'b\na\n' > t.txt
$ sort t.txt > t.txt
$ wc -c < t.txt
0
```

`sort` 想读的顺序早没了。这条纪律在备份脚本里是硬要求：`deploy/ops/paideia-backup.sh:24` 先写 `"$target.partial"`，第 60 行才 `mv` 成正式名。

这个文件开头第 7–8 行的注释写了理由，值得抄下来：

> 先写临时文件再 mv：dump 中途失败时不能留下一个「看起来完整」的 gzip——那会让「有备份」变成谎言，而发现它的时机恰好是你最需要它的时候。

`>>` 是同一个系统调用的另一个标志（追加），不截断。`> f` 在循环里用一次就会把上一次的写得全丢掉，这是最常见的「日志只剩最后一条」。

## 分开收：`>` 和 `2>` 是两根不同的管子

回到判题脚本第 111 行：

```text
bash /tmp/in/run.sh > /tmp/.out 2> /tmp/.err
```

两件事同时发生：fd 1 指向 `/tmp/.out`，fd 2 指向 `/tmp/.err`。**这里故意不用 `2>&1`**，因为前端要把「你的输出」和「你的报错」分成两栏显示；合并了就再也拆不开。第 122 行 `head -c 8000 /tmp/.err` 单独把报错截出来，就是这个道理。

第 113 行判题脚本同样分开：`>` 进 `.jout`、`2>` 进 `.jerr`。所以学员看到的是「判定脚本说了什么」和「判定脚本自己崩在哪」，而不是混在一起的一坨。

这两行里还藏着一个顺序问题：`rc=$?` 必须**紧贴**在 `bash` 那行之后。`$?` 只装「上一条命令」的退出码，中间插一条 `echo` 就没了。

## 顺序：`2>&1` 复制的是「当时」的目标

这是本篇最容易背错的一条。两种写法，一个字的差别，结果相反：

```text
# 本机实跑：/usr 存在、/nope 不存在，所以一条成功一条报错
$ ls /nope /usr > o1.txt 2>&1
$ head -1 o1.txt
ls: cannot access '/nope': No such file or directory
$ wc -l < o1.txt
8

$ ls /nope /usr 2>&1 > o2.txt
ls: cannot access '/nope': No such file or directory
$ head -1 o2.txt
/usr:
$ wc -l < o2.txt
7
```

第二种写法的报错跑到屏幕上、文件里只有 7 行正常输出。因为 shell 从左往右处理：

- `> o1.txt 2>&1`：先把 fd 1 指向文件，再让 fd 2 **指向 fd 1 此刻指向的东西**（文件）。
- `2>&1 > o2.txt`：fd 2 先指向 fd 1 此刻指向的东西（**还是终端**），然后 fd 1 才改指向文件。

`2>&1` 是一次性的复制，不是永久的「2 永远跟着 1」。所以顺序永远是把目的地先摆好，再复制。

一个反过来的用法是主动扔掉：`deploy/ops/install-ops.sh:53` 这行

```text
# 仓库原文（deploy/ops/install-ops.sh:53）
id "$account" >/dev/null 2>&1 || useradd --system --no-create-home --shell /usr/sbin/nologin "$account"
```

`>/dev/null` 在最前面，就是为了让紧接着的 `2>&1` 把 stderr 也扔进黑洞。写成 `2>&1 >/dev/null`，报错会留在屏幕上——很多幂等脚本「跑第二遍刷一屏红字」，就是这个顺序。

`/dev/null` 不是普通文件：写进去的东西被丢弃，读它立刻得到 EOF。它只解决「噪音去哪」，不解决「失败要不要管」——上面那行真正的判断在 `||` 后面。

## 管道只搬 stdout，而 `$?` 只看最后一段

`|` 连接的是左边命令的 fd 1 和右边命令的 fd 0。**stderr 不经过管道**，它还在原地。

`deploy/ops/paideia-backup.sh:49-54` 是这半篇最值钱的一段：

```text
# 仓库原文，变量已按第 11 行 set -euo pipefail 的前提理解
if ! mysqldump --defaults-extra-file="$DEFAULTS_FILE" \
        --single-transaction --quick --routines --triggers --events \
        --databases "$DATABASE" 2>"$error_log" | gzip -9 > "$temporary"; then
    message=$(head -c 500 "$error_log" 2>/dev/null | tail -1)
    fail "${message:-mysqldump 执行失败}"
fi
```

三处 fd 决策：`2>"$error_log"` 把 dump 的报错单独收起来（否则它会绕过管道直接进 journal，你事后翻不到）；stdout 交给 `gzip`；`> "$temporary"` 落到临时文件。后面 `head -c 500 | tail -1` 只取报错**最后一行**。

现在把第 11 行的 `pipefail` 拿掉，后果是什么？本机可以真跑出来：

```text
# 本机实跑：false 冒充「失败了的 mysqldump」
$ false | gzip -9 > a.gz
$ echo $?
0
$ wc -c < a.gz
20
$ gzip -t a.gz && echo 校验通过
校验通过
$ gzip -dc a.gz | wc -c
0
```

四行输出，每一行都在骗人：退出码 0、产物 20 字节、`gzip -t` 说这是合法 gzip、解开是 **0 字节**。

我原来以为脚本第 57 行的 `[ -s "$temporary" ]`（产物非空）能兜住这个。兜不住——**gzip 对空输入也会产出一个 20 字节的合法文件**，所以「非空」为真、「gzip 校验」也为真，`mv` 照样执行，状态文件照样写 `"success":true`。这个 20 字节是 gzip 的头部加尾部，不含任何数据。

补上 `pipefail` 就正常了：

```text
# 本机实跑
$ set -o pipefail
$ false | gzip -9 > b.gz
$ echo $?
1
```

`pipefail` 让整条管道的状态取**最右边那个非 0**，而不是只看最后一段（bash 默认只看最后一段：`false | true; echo $?` 是 0）。

但 `pipefail` 是 bash 的选项，不是 sh 的：

```text
# 本机实跑（dash 也在 Git Bash 里，顺手验证）
$ dash -c "set -o pipefail; false | true"
dash: 1: set: Illegal option -o pipefail
```

`set -e` 也有它的边界，而且正好被这段代码踩中：**`set -e` 在 `if`、`&&`、`||` 这些条件上下文里不触发**。所以第 49 行写在 `if !` 里，mysqldump 失败不会让脚本自动退出——必须像第 49–54 行那样自己 `if` 判、自己调 `fail`。同一条脚本第 57–58 行的 `[ -s "$temporary" ] || fail "..."` 也是这个形状：`||` 只在左边失败时走右边，是**显式**处理，不依赖 `set -e`。

顺带说个不该写死的数：`$?` 的具体值由程序自己定，不是 shell 定的。

```text
# 本机实跑（GNU coreutils 8.32）
$ ls /nope 2>/dev/null; echo $?
2
```

GNU 的 `ls` 用 2 表示「文件不存在」。别把 `[ $? -eq 2 ]` 写进脚本——BSD/macOS 的 `ls` 返回 1 是另一套约定（**标准形态，未实跑**，我手边没有那台机器）。判失败要看「非 0」，不要看具体数字。

## 想同时看和留档：`tee`，以及它不解决什么

`tee` 把 stdin 抄成两份，一份 stdout、一份文件，所以能从管道中间「截一份下来」：

```text
# 标准形态，未实跑
$ ./deploy.sh 2>&1 | tee deploy.log
```

`2>&1` 必须在 `|` 前面：要让 stderr 先进 stdout，才轮得到 `tee` 看到它。而且 `tee` 是管道最后一段，**整条管道的 `$?` 是 `tee` 的**——写日志成功、部署失败，也会是 0。前面那条 `pipefail` 同样适用。

bash 还留着每一段各自的退出码，在数组 `PIPESTATUS` 里：

```text
# 本机实跑（bash 专有，dash 没有这个数组）
$ false | true
$ echo "$? ${PIPESTATUS[0]}"
0 1
```

同一个管道：`$?` 是 0（`true` 的），`PIPESTATUS[0]` 是 1（`false` 的）。这个数组**只活到下一条命令为止**——先 `echo $?` 再读 `PIPESTATUS` 就晚了，那里面已经是 `echo` 自己的状态（我第一遍就是这么读错的，得到的是 0，和 `$?` 一样，看起来「没问题」）。

备份脚本没用 `tee`，不是没想到：它要的是「要么完整、要么没有」，而不是「过程留一份、成败另外判」。所以它选了「临时文件 + `gzip -t` 校验 + `mv`」，把「文件存不存在」变成可信信号。

## 反着走一遍：恢复

备份讲完得说恢复，因为恢复是把每条管道倒过来读：

```text
# 标准形态，未实跑（本机无 MySQL/mysqldump）
$ gzip -dc /opt/paideia-backup/paideia-20260101-031500.sql.gz | mysql paideia
```

方向对了之后，两个容易混的写法也该分清：「把文件当参数」和「把文件接到 stdin」。

```text
# 本机实跑
$ wc -l f.txt
2 f.txt
$ wc -l < f.txt
2
```

`<` 把文件接到 fd 0，程序根本不知道文件名，所以不会打印文件名。脚本里要一个能直接比较的「干净数字」时用 `<`（`n=$(wc -l < f.txt)`），需要「同时知道是哪个文件」时传参数。

`mysql -u root -p db < init.sql` 属于后一类：`mysql` 从 stdin 读 SQL，所以 `<` 和 `|` 都能喂它。这也是为什么上面那条 0 字节的空备份最贵：**它顺着管道流过去，mysql 读到 EOF，什么也没做，退出码是 0**——空备份不会报错，只会让你在真正需要它那天发现。（这一条是按 mysql 客户端行为推的，**标准形态，未实跑**。）

## 症状 → 先看哪

| 症状 | 先看哪 |
| --- | --- |
| 文件里有报错、终端也有一份 | 顺序是不是写成了 `2>&1 > f`，改成 `> f 2>&1` |
| 加了 `\| grep` 之后报错突然刷屏 | 管道只搬 fd 1；要一起过就 `2>&1 \|`，或像备份脚本那样单独 `2>文件` |
| `$?` 是 0，但命令确实失败了 | 失败的是不是管道里非最后一段；查 `pipefail` / `PIPESTATUS` |
| 脚本在 `if` 里失败却继续往下跑 | `set -e` 在条件上下文不触发，分支里要自己 `exit` |
| 部署机上一行 `&>` 变成空文件、退出码 0 | `/bin/sh` 可能不是 bash（Debian 是 dash）；改 shebang 或写 `> f 2>&1` |
| 文件被自己清空（如 `sort f > f`） | `>` 在 exec 前就截断；先写临时文件再 `mv` |
| 报错在屏幕上，但日志里找不到 | stderr 走了另一条路：journal、终端、或你写的 `2>文件` |

## 还差的

1. **没有真 Linux 机器**。这篇里标「标准形态，未实跑」的都得你自己验一遍：`mysqldump` 失败时的 stdout/stderr 具体形态、`gzip -dc | mysql` 恢复空文件时 mysql 的真实退出码、systemd 单元的 stderr 默认去处。我的 Git Bash 只是 MSYS 的 GNU 工具，不是 Linux 内核。
2. **dash 那条坑只验了一半**。`&>` 在 dash 里变空文件，我在本机 dash（MSYS 版）跑出来了；但「Debian 的 `/bin/sh` 指向 dash」是按 Debian 的发行约定写的，没在 Debian 上跑。按 RHEL 的约定 `/bin/sh` 指向 bash，那行 `&>` 就正常了——这一半我同样没跑，也没逐一核对各发行版现在的 `/bin/sh` 到底是哪个 shell。
3. **systemd 与 sysvinit 我只写了 systemd 那侧**。`paideia-backup.service` 没写 `StandardError`，默认进 journal（标准形态，未实跑）；老的 `/etc/init.d` 脚本里 stderr 去哪完全由脚本自己决定，我没有翻具体发行版的约定，所以不敢写成「都一样」。
4. **`head -c 8000` 那个截断值我没推敲过**。仓库注释说协议块整体约 32KB、要稳定落在输出上限内；但每段为什么是 8000/4000 而不是别的数，代码里没写推导，我也没有去改它。
5. **判题脚本里的 `grep -qx` 和 `diff` 各自在哪些实现上有差异，我没查全**。GNU 与 BSD 的 `grep`/`diff` 选项子集不完全一样，镜像钉的是 debian:12-slim（`images/shell/Dockerfile` 里按 digest 固定），所以至少这个镜像内是稳定的——镜像之外我没验过。
