## 这一关要做什么

前面十八关是零件，这一关把它们装成一台机器。目标很具体：**一台刚装的 Ubuntu 服务器，从零开始，把一个 Java 服务跑起来，做到重启后自动起来、崩了自动重启、日志能查、每天自动备份、外部只能访问需要的端口。**

每一步都给命令、给"这一步错了会怎样"、给验证方法。**没有验证的步骤等于没做**——这是本关最重要的一条纪律。

## 为什么按这个顺序

因为每一步都依赖前一步的状态，而且**顺序错了会留下难查的残留**：

- 先建用户再放文件（反过来文件属主是 root，服务读不到）；
- 先定目录再改权限（反过来要重新 `chown -R`）；
- 先能手动跑通再交给 systemd（反过来你在 `journalctl` 里查一个"本来就没跑通"的程序）；
- 先跑通再谈加固（反过来分不清是加固错了还是程序错了）。

## 讲解

### 第 0 步：确认你在哪台机器上

```text
$ hostnamectl
$ cat /etc/os-release | head -3
$ nproc && free -m | head -2 && df -h /
```

三条产出：发行版、核数与内存、磁盘余量。**先记下这些数字**，后面调限额（内存、`LimitNOFILE`）都从这里推。

### 第 1 步：专用账号与目录布局

```text
$ sudo useradd --system --no-create-home --shell /usr/sbin/nologin paideia
$ sudo mkdir -p /opt/paideia /etc/paideia /var/lib/paideia /var/log/paideia
$ sudo chown -R paideia:paideia /opt/paideia /var/lib/paideia /var/log/paideia
$ sudo chown root:paideia /etc/paideia
$ sudo chmod 750 /etc/paideia
```

四个目录各管一件事，这是 FHS 的实践版（第 02 关）：

| 目录 | 放什么 | 属主 |
| --- | --- | --- |
| `/opt/paideia` | jar、启动脚本 | `paideia` |
| `/etc/paideia` | 配置与密钥 | `root:paideia`，`750` |
| `/var/lib/paideia` | 运行数据 | `paideia` |
| `/var/log/paideia` | 日志 | `paideia` |

`/etc/paideia` 归 root 但组是 `paideia`：**服务能读，但它自己改不了配置**。这是有意的——被攻破的服务不应该能改自己的启动配置。

**验证**：

```text
$ sudo -u paideia test -w /var/lib/paideia && echo "可写 ok"
$ sudo -u paideia test -r /etc/paideia && echo "可读 ok"
$ id paideia
uid=998(paideia) gid=998(paideia) groups=998(paideia)
```

### 第 2 步：装运行时

```text
$ sudo apt update
$ sudo apt install -y openjdk-21-jre-headless
$ command -v java && java -version
```

生产环境装 **JRE 而不是 JDK**（`-headless` 更省），除非要在机器上编译。装完立刻 `command -v java` 记下绝对路径——unit 文件里要写它（第 12 关）。

如果要装 JDK 21 而仓库版本不对，装到 `/opt/jdk21` 并在 unit 里写 `/opt/jdk21/bin/java`，**不要去改系统的 `/usr/bin/java`**（第 11 关的多版本问题）。

### 第 3 步：上传产物

```text
$ rsync -avz --progress target/paideia.jar prod:/tmp/paideia.jar
$ sha256sum /tmp/paideia.jar        # 远端
$ sha256sum target/paideia.jar      # 本地
```

两个 `sha256sum` 必须一致。**这一步不是形式**：传输中断、磁盘写满、被中间人替换，三种情况都会得到一个"大小差不多但内容不同"的 jar，而它的症状是"启动报一个莫名其妙的类找不到"。

然后落位并给最小权限：

```text
$ sudo mv /tmp/paideia.jar /opt/paideia/paideia.jar
$ sudo chown paideia:paideia /opt/paideia/paideia.jar
$ sudo chmod 644 /opt/paideia/paideia.jar
```

### 第 4 步：配置与密钥

```text
$ sudo tee /etc/paideia/paideia.env > /dev/null <<'EOF'
SPRING_PROFILES_ACTIVE=prod
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=paideia
EOF
$ sudo chmod 600 /etc/paideia/paideia.env
```

口令不进这个文件的话最好，走别的渠道（例如只在 shell 里 `export` 后启动一次写入数据库）。**如果必须放**，`600` + `root:root`，然后在 unit 里用 `User=root` 读不了——所以要 `root:paideia` 且 `640`。两种都要在 unit 里写 `EnvironmentFile=`（第 12 关）。

**验证**：`sudo -u paideia cat /etc/paideia/paideia.env` 应该成功；`sudo -u nobody cat ...` 应该失败。

### 第 5 步：先手动跑通

```text
$ sudo -u paideia env $(cat /etc/paideia/paideia.env | xargs) \
    /usr/bin/java -jar /opt/paideia/paideia.jar
```

盯着它启动，看有没有报错，另开一个终端：

```text
$ ss -lntp 'sport = :8080'
$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/actuator/health
```

**必须先手动跑通。** 直接交给 systemd 时，失败信息散在 journal 里，还要区分"是程序的问题还是 unit 的问题"。这一步跑通了，后面出问题就一定是 unit/权限/环境的问题。

`Ctrl+C` 停掉（第 09 关：它发 SIGINT，程序优雅退出）。

### 第 6 步：写成服务

```ini
# /etc/systemd/system/paideia.service
[Unit]
Description=Paideia API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=paideia
Group=paideia
WorkingDirectory=/opt/paideia
EnvironmentFile=/etc/paideia/paideia.env
ExecStart=/usr/bin/java -Xms256m -Xmx768m -jar /opt/paideia/paideia.jar
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
LimitNOFILE=65535
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/paideia /var/log/paideia

[Install]
WantedBy=multi-user.target
```

```text
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now paideia
$ systemctl status paideia --no-pager
```

`-Xmx768m` 要按第 0 步的内存算：容器/机器内存减去系统与其他服务，留出余量。给太大，OOM Killer 会挑最大的进程杀（第 13 关）。

**验证**：

```text
$ systemctl is-active paideia && systemctl is-enabled paideia
$ ss -lntp 'sport = :8080'
$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/actuator/health
$ ps -o pid,user,rss,cmd -C java
```

`ps -o user` 那一列必须是 `paideia`。如果显示 `root`，说明 `User=` 没生效（写错段落、没 reload）。

**再测一次自愈**：

```text
$ sudo systemctl kill -s SIGKILL paideia
$ sleep 8 && systemctl is-active paideia
```

`Restart=on-failure` 让它 5 秒后自己起来；`systemctl status` 里的 `Active` 时间会变回几秒前，这就是证据。

### 第 7 步：日志

```text
$ journalctl -u paideia -n 100 --no-pager
$ sudo journalctl --disk-usage
```

要独立日志文件就在 unit 里改 `StandardOutput=append:/var/log/paideia/app.log`（或让应用自己写），然后配轮转（第 13 关）：

```text
# /etc/logrotate.d/paideia
/var/log/paideia/*.log {
    daily
    rotate 7
    missingok
    notifempty
    compress
    copytruncate
}
```

```text
$ sudo logrotate -d /etc/logrotate.d/paideia
```

### 第 8 步：备份，并且演练恢复

备份脚本（第 17 关的模板）：

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'
readonly SRC="/var/lib/paideia"
readonly DEST="/data/backup"
readonly KEEP=7

[[ -d "$SRC" ]] || { echo "源目录不存在: $SRC" >&2; exit 1; }
mkdir -p "$DEST"
stamp="$(date '+%Y%m%d-%H%M%S')"
tar -czf "$DEST/paideia-data-$stamp.tar.gz" -C "$(dirname "$SRC")" "$(basename "$SRC")"
ls -1t "$DEST"/paideia-data-*.tar.gz | tail -n +$((KEEP + 1)) | xargs -r rm -f
echo "ok: $DEST/paideia-data-$stamp.tar.gz"
```

挂到 timer（第 18 关）：

```ini
# /etc/systemd/system/paideia-backup.timer
[Unit]
Description=Paideia 每日备份

[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true
RandomizedDelaySec=300

[Install]
WantedBy=timers.target
```

**关键的一条：演练恢复。** 备份没恢复过 = 没有备份。

```text
$ mkdir -p /tmp/restore && tar -xzf /data/backup/paideia-data-xxx.tar.gz -C /tmp/restore
$ ls -l /tmp/restore/paideia/
```

只看 `tar -tzf` 列表是不够的——真正解出来的权限、属主、文件内容才说明它可用。演练一次能发现"打包时把符号链接打成了链接本身""属主丢了"这类问题。

### 第 9 步：对外开放的最小面

```text
$ sudo ufw default deny incoming
$ sudo ufw allow 22/tcp
$ sudo ufw allow 80,443/tcp
$ sudo ufw enable
$ sudo ufw status verbose
```

**8080 不要对公网开**——让 Nginx 反代，只暴露 80/443（第 15 关的理由：端口越少，攻击面越小）。云安全组也要同步收紧，那是第 0 层防火墙。

SSH 加固（第 16 关）：`PermitRootLogin no`、`PasswordAuthentication no`、`PubkeyAuthentication yes`。**改之前另开一个终端确认密钥能登。**

```text
$ sudo sshd -t && sudo systemctl reload ssh
```

重启一次，确认所有服务自动起来：

```text
$ sudo reboot
$ # 回来之后
$ systemctl is-active paideia
$ systemctl list-timers --all | grep paideia
$ sudo systemctl --failed
```

`systemctl --failed` 应该为空。**这一条是"无人值守"的最终验收。**

### 验收清单

| 检查 | 命令 | 期望 |
| --- | --- | --- |
| 服务在跑、以专用账号 | `ps -o user,cmd -C java` | `paideia` |
| 只监听需要的地址 | `ss -lntp` | 8080 绑回环或被反代 |
| 本机 HTTP 正常 | `curl -I 127.0.0.1:8080/actuator/health` | `200` |
| 外部只开必要端口 | 另一台机器 `nc -zv` | 只有 22/80/443 |
| 崩了会自愈 | `systemctl kill -9` 后等 8 秒 | `active` |
| 重启后自启 | `reboot` 后 | `active` + timer 有 `NEXT` |
| 日志可查、有轮转 | `journalctl -u` / `logrotate -d` | 有输出、无报错 |
| 备份可恢复 | 解包到 `/tmp` 检查 | 内容与属主正确 |
| 无失败单元 | `systemctl --failed` | 空 |
| 磁盘与 inode 有余量 | `df -h` / `df -i` | 都低于 80% |

十条全绿，这台机器才算"上线了"。缺任何一条都还是"能跑"。

## 常见误区

### 误区：服务能起来就算部署完成

**你以为**：`systemctl start` 成功、页面能打开，就完事了。
**其实**：起得来只是第一关。真正决定"明天早上它还活着"的是：`Restart=` 有没有配、`enable` 了没有、日志会不会撑爆磁盘、备份能不能恢复、端口有没有开太多。这些都不在"页面能打开"里体现。
**怎么验证**：按上面的验收清单逐条跑；尤其是 `reboot` 之后再看一次。

### 误区：先加固再跑通更安全

**你以为**：一开始就把权限收到最小、`ProtectSystem=strict` 全开，省得后面改。
**其实**：加固项会让"本来能跑"变成"跑不起来"（只读文件系统、私有 `/tmp`、限制目录），而这时你还没建立"它能正常跑"的基线，排查会同时在两个方向上怀疑。**顺序应该是：先跑通 → 再写 unit → 再加加固 → 每加一项验一次。**
**怎么验证**：`ProtectSystem=strict` 之后看 `journalctl -u` 有没有 `Read-only file system`；有就把需要写的目录补进 `ReadWritePaths`。

### 误区：`ufw allow 8080` 就够了

**你以为**：主机放行了端口，外面就能连。
**其实**：云上还有一层安全组（第 15 关），它在主机外面，主机上怎么看都正常。另外 8080 对公网开放本身就违反"最小暴露面"——正确做法是只开 80/443，用 Nginx 反代到 127.0.0.1:8080。
**怎么验证**：从内网另一台机器测（绕过安全组）与从公网测对比；`ss -lntp` 确认 8080 绑的是 `127.0.0.1` 而不是 `0.0.0.0`。
