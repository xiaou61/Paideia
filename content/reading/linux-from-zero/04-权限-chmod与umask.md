## 这一关在解决什么

"Permission denied" 是新手最常遇到、也最容易用 `chmod 777` 糊过去的报错。这一关讲清楚三件事：**那九个字母到底管什么、目录的权限和文件的权限为什么不是一回事、`umask` 决定了你新建文件的默认权限**。

学完你应该能回答：为什么有的文件自己有读权限但别人打不开？为什么 `/tmp` 里谁都能建文件、却删不了别人的？

## 为什么是"三组九个位"

因为每个文件都要同时回答三个问题：**文件的主人能干什么、同组的人能干什么、其他所有人能干什么**。三个身份 × 三个动作（读、写、执行）= 九个位。这是 1970 年代就定下来的模型，简单到能塞进一个整数，所以至今没换。

局限也很明显：它只能表达"一个属主 + 一个属组"。要更细的控制得用 ACL（`setfacl`），但 95% 的场景九个位够用。

## 讲解

### 九个位的读法

```text
$ ls -l run.sh backup.sh secrets.env
-rwxr-xr-x 1 lzf devs  512 Oct 20 10:00 run.sh
-rw-r--r-- 1 lzf devs 1024 Oct 20 10:00 backup.sh
-rw------- 1 lzf devs  256 Oct 20 10:00 secrets.env
```

第一列去掉代表类型的那一位，剩下九个字符分成三组：

| 组 | 对象 | `run.sh` 的这组 |
| --- | --- | --- |
| 第 1 组（第 2–4 位） | 属主（`lzf`） | `rwx` |
| 第 2 组（第 5–7 位） | 属组（`devs`） | `r-x` |
| 第 3 组（第 8–10 位） | 其他人 | `r-x` |

每个字母对应一个数字，**加起来就是这个组的权限**：

| 位 | 值 | 文件上的含义 | 目录上的含义 |
| --- | --- | --- | --- |
| `r` | 4 | 能读内容 | 能列出里面有哪些名字（`ls`） |
| `w` | 2 | 能改内容 | 能在里面创建、删除、改名 |
| `x` | 1 | 能执行（脚本、程序） | 能进入、能访问里面的已知路径（`cd`、读子文件） |

于是 `rwx` = 7，`rw-` = 6，`r-x` = 5，`r--` = 4，`---` = 0。`755` 就是 `rwxr-xr-x`。

### 目录的 x 是最容易被忽略的一位

**目录的 `x` 不是"能执行"，是"能穿过"**。这一位决定你能不能访问它下面的东西。

看这个组合：

```text
$ ls -ld /data /data/public
drwx------ 3 lzf devs 4096 /data
drwxr-xr-x 2 lzf devs 4096 /data/public
$ cat /data/public/readme.txt
cat: /data/public/readme.txt: Permission denied
```

`public` 目录本身是 `755`，里面的文件也是 `644`，但还是打不开。原因在 `/data` 是 `700`——**你没有 `/data` 的 `x`，就进不了 `/data`，也就到不了 `/data/public`**。权限检查是逐级进行的，路径上任何一级不通，整条路就不通。

反过来，`-wx` 的目录（`333`）能进、能在里面建文件，但 `ls` 看不到已有文件名——因为列名字要 `r`。这种"能进不能看"的组合在真实系统里很少见，但正好说明 `r` 和 `x` 是两件事。

### 删除一个文件，看的是目录的写权限

这是最反直觉的一条：**删文件不需要文件本身的写权限，需要的是它所在目录的 `w`**。

因为 `rm` 改的是目录里"名字 → inode"这张表，文件内容一个字节都没动。所以：

```text
$ ls -l /data/a.txt
-r--r--r-- 1 root root 100 /data/a.txt     # 文件本身对你只读
$ rm /data/a.txt
rm: cannot remove '/data/a.txt': Permission denied   # 因为 /data 你没有 w
```

只要你对 `/data` 有 `w`，即使 `a.txt` 是 `444` 也能删掉。**"只读文件"防的是改内容，不防删除。**

### `chmod`：两种写法

**数字写法**直接给三组的值：

```text
$ chmod 755 run.sh       # rwxr-xr-x
$ chmod 644 app.conf     # rw-r--r--
$ chmod 600 secrets.env  # 只有自己能读写
$ chmod 700 ~/.ssh       # 只有自己能进
```

**符号写法**在"只想改一组"时更好用：

```text
$ chmod +x run.sh        # 三组都加执行（等价 a+x）
$ chmod u+x run.sh       # 只给属主加执行
$ chmod go-w app.conf    # 组和其他去掉写
$ chmod u=rw,g=r,o= app.conf   # 显式设成 640
```

推荐组合：**新建的文件用数字（明确），微调用符号（清楚改了什么）**。`chmod 777` 永远不是答案——它意味着"任何能登录这台机器的人都能改这个文件"，而且如果它是脚本，还是**任何本地用户都能执行**。

### `chmod -R` 的经典事故

`chmod -R 777 /data` 会把 `/data` 下所有文件都变成可执行——包括 `.conf`、`.sql`、图片。系统不因此坏，但你会得到一堆"看起来能跑、其实是配置"的文件，以后很难判断。

更糟的是反向：`chmod -R 600 /some/dir` 会让**目录失去 `x`**，于是连你自己也进不去了。恢复要 `chmod -R u+rwX`（**大写 `X` 表示"只给目录和已有执行位的文件加执行"**）：

```text
$ chmod -R u+rwX /some/dir
```

大写 `X` 是唯一安全地对整棵树补执行位的写法，记它。

### `chown` 与 `chgrp`

```text
$ chown lzf app.conf              # 改属主
$ chown lzf:devs app.conf         # 同时改属组
$ chown -R www-data:www-data /srv/app    # 递归改
```

两条纪律：

- **只有 root 能把文件给别人。** 普通用户只能 `chown` 给自己的组（自己的文件）。
- **`sudo cp` 出来的文件属主是 root。** 这是"我用 sudo 备份了一下配置，后来改不回去了"的原因。备份系统文件要么用 `sudo cp -a`（保留属主）到 root 目录，要么先 `cp` 再 `chown`。

### `umask`：新建文件的默认权限

文件创建时不能直接指定权限，只能由 `umask` 决定上限：

| 对象 | 默认起点 | 减去 umask（022） | 结果 |
| --- | --- | --- | --- |
| 普通文件 | `666` | `666 - 022` | `644` |
| 目录 | `777` | `777 - 022` | `755` |

注意文件起点是 `666`：**新建文件默认不带执行位**，这是有意的设计——下载一个脚本不该直接能跑，要你显式 `chmod +x`。

```text
$ umask
0022
$ umask -S
u=rwx,g=rx,o=rx
```

按位算（不是减法，是"去掉 umask 里为 1 的位"）：`022` 表示"组和其他去掉写"。所以：

- `umask 022`：文件 `644`，目录 `755`。**默认值，多用户环境用这个。**
- `umask 027`：文件 `640`，目录 `750`。组内共享、外人完全进不来。
- `umask 077`：文件 `600`，目录 `700`。**放密钥、放数据库文件的目录应该用这个。**

要永久改，写进 `/etc/profile`（全局）或 `~/.bashrc`（自己）。临时改只在当前 shell 有效。

### 三个特殊位：`/tmp` 为什么人人能写又删不掉别人的

`/tmp` 的权限是这样的：

```text
$ ls -ld /tmp
drwxrwxrwt 12 root root 4096 /tmp
```

注意末尾那个 **`t`**。它叫 **sticky bit**（八进制 `1000`，`chmod 1777`）：

- 没有 `t` 的 `777` 目录：谁都能删里面任何文件（因为删看目录的 `w`）。
- 有 `t` 的 `777` 目录：**只有文件属主、目录属主和 root 能删**。

这就是 `/tmp`、`/var/tmp`、`/dev/shm` 都用 `1777` 的原因：大家都能建，但不能互相破坏。

另外两位你会在系统文件上看到，不必主动用：

| 位 | 八进制 | 显示 | 作用 | 典型例子 |
| --- | --- | --- | --- | --- |
| setuid | 4000 | `s` 在属主执行位 | 执行时以**文件属主**身份运行 | `/usr/bin/passwd`（普通用户改自己的密码，实际以 root 写 `/etc/shadow`） |
| setgid | 2000 | `s` 在属组执行位 | 执行时以属组身份运行；**在目录上表示新文件继承该组** | 共享目录 `2775` |

`passwd` 那一位是整个系统里最合理的 setuid 用法：密码文件只有 root 能写，但每个人都得能改自己的密码。**自己写程序时别用 setuid**，它极难写对。

### 一组够用的推荐权限

| 对象 | 权限 | 说明 |
| --- | --- | --- |
| 普通配置文件 | `644` | 大家可读，只有属主可改 |
| 含密钥/口令的配置 | `600` | 只有属主 |
| 可执行脚本、二进制 | `755` | 大家可执行 |
| 私有目录（`~/.ssh`） | `700` | 只有属主能进 |
| 共享写目录 | `1777`（如 `/tmp`） | 人人可写，互不删除 |
| 共享组目录 | `2775` | 同组协作，新文件继承组 |

## 常见误区

### 误区：`chmod 777` 能解决权限问题

**你以为**：报权限错误就 `chmod 777`，反正能跑了。
**其实**：`777` 意味着**这台机器上任何账号都能修改、替换这个文件**。如果它是被 root 执行的服务或脚本，任何本地用户都能把自己的代码塞进去等 root 执行——这是一条提权路径，不是"省事的开关"。正确做法是找到**哪一级**缺权限，只补这一级。
**怎么验证**：`ls -ld` 逐级看路径上每个目录；用 `namei -l /a/b/c` 一次性列出整条路径每一级的权限，缺在哪一目了然。

### 误区：文件有 `r` 就能读

**你以为**：`ls -l` 显示 `r--` 就说明能打开。
**其实**：读文件要同时满足"路径上每级目录有 `x`"和"文件本身有 `r`"。另外 SELinux/AppArmor 这类强制访问控制还会再拦一层，即使九位全开也可能被拒。
**怎么验证**：`namei -l /path/to/file` 看整条路径；`ls -Z file`（SELinux 系统）看安全标签。

### 误区：给目录 `w` 就能改里面的文件

**你以为**：`w` 是"可写"，对目录也意味着能改里面的东西。
**其实**：目录的 `w` 只允许**增删改名目录项**；改某个文件的内容要那**文件本身**有 `w`。所以 `drwx-wx-wx` 的目录里，你能建新文件、能删文件，但改不了已有文件的内容。
**怎么验证**：建个 `733` 目录，放一个 `644`、属主是别人的文件，试着 `echo >> 它`——被拒；再 `rm` 它——成功（如果目录属主是你）。
