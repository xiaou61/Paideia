## 这一关在解决什么

"服务起了，但外面连不上"——这是部署新服务时最常见的一句话。原因可能在三层：**服务只听在 127.0.0.1**、**防火墙挡了端口**、**云安全组挡了端口**。

这一关给你一套排查顺序和对应命令：从机器自己的角度看端口，从外部看连通性，并且分清"本机通"和"外面通"是两件事。

## 为什么"本机通"不代表"外面通"

一个 TCP 连接要经过好几道关，任何一道不通都不成：

```text
客户端 → DNS 解析 → 路由 → 云安全组 → 主机防火墙 → 内核的端口监听 → 应用
```

`curl 127.0.0.1:8080` 只验证了最后两环（内核监听 + 应用），前面四环一个都没测。所以**"本机能访问"是最弱的证据**，它只能排除应用本身的问题。

## 讲解

### 第一层：地址与路由

```text
$ ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             10.0.0.12/24 fe80::1/64
$ ip r
default via 10.0.0.1 dev eth0
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.12
```

`ip -br a`（`-br` 是 brief）比 `ip a` 好读。`ifconfig` 已经过时（net-tools 包默认不装），别再用它。

要确认三件事：**有没有地址**、**默认网关在不在**、**是不是有多张网卡**（云主机常有内网网卡和公网网卡，绑错网卡就没人能连）。

### 第二层：谁在监听端口

```text
$ ss -lntp
State   Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN  0      4096        0.0.0.0:8080       0.0.0.0:*     users:(("java",pid=9812,fd=42))
LISTEN  0      128         0.0.0.0:22         0.0.0.0:*     users:(("sshd",pid=812,fd=3))
LISTEN  0      100       127.0.0.1:3306       0.0.0.0:*     users:(("mysqld",pid=1204,fd=22))
```

四个参数的含义：`-l` 只看监听（LISTEN）、`-n` 不解析域名与服务名（快且准）、`-t` 只要 TCP（`-u` 是 UDP）、`-p` 显示进程（需要 root 才能看到别人的进程）。

**这一列是排查的核心**：

| Local Address | 谁能连 |
| --- | --- |
| `127.0.0.1:3306` | **只有本机**。外部连不上，这是有意的安全默认 |
| `0.0.0.0:8080` | 所有网卡的所有 IPv4 地址，外部可达 |
| `10.0.0.12:8080` | 只有那块网卡的地址 |
| `[::]:8080` | 所有 IPv6 地址（很多程序同时监听 v4/v6） |

"服务起了外部连不上"最常见的原因就是第一行那种：程序默认只听 `127.0.0.1`。MySQL、Redis、很多 Java 内嵌容器都是这个行为。改法在应用配置里（比如 Spring 的 `server.address`、MySQL 的 `bind-address`），不是在 Linux 这一层。

按端口过滤：

```text
$ ss -lntp 'sport = :8080'
$ ss -tnp state established          # 当前已建立的连接，看谁在连你
$ ss -s                              # 汇总：多少 TCP、多少 TIME_WAIT
```

`ss -s` 里的 `TIME_WAIT` 数量异常高，通常说明连接没被复用或有大量短连接（网络线里有一篇专门讲这个）。

### 第三层：从外部看

从**另一台机器**上测，而不是从本机：

```text
$ curl -v --connect-timeout 5 http://<公网IP>:8080/actuator/health
$ nc -zv <公网IP> 8080          # 只测端口通不通
$ timeout 5 bash -c '</dev/tcp/<IP>/8080' && echo open
```

结果分三种，含义完全不同：

| 现象 | 含义 | 下一步 |
| --- | --- | --- |
| `Connection refused` | 能到达主机，但**那个端口没人监听** | 回去看 `ss -lntp`，可能只听在回环 |
| 超时 / 无响应 | 包被**丢**了：防火墙、安全组、路由 | 查防火墙与云安全组 |
| 连上但没响应 | 端口通，应用没回 | 查应用日志 |

**"拒绝"和"丢包"的差别极有用**：拒绝说明网络路径通、只是没人接；超时说明路径上有人拦着。

### 第四层：防火墙

三套体系，看发行版：

```text
# Ubuntu（ufw 是 iptables/nftables 的前端）
$ sudo ufw status verbose
$ sudo ufw allow 8080/tcp

# RHEL/CentOS（firewalld）
$ sudo firewall-cmd --list-all
$ sudo firewall-cmd --add-port=8080/tcp --permanent && sudo firewall-cmd --reload

# 直接看内核规则（两套都适用）
$ sudo iptables -L -n -v
$ sudo nft list ruleset
```

一条判断技巧：`iptables -L -n -v` 里每条的**计数**会涨。测一次连接前后各看一次，计数涨了的那条规则就是参与决策的。

**云安全组是第 0 层防火墙**，在主机外面。它的特征是：**主机上的防火墙全关、`ss` 也显示在听，外面还是超时**。这种情况下任何 `iptables`/`ufw` 命令都不会有变化——要去云控制台放行端口。真实环境里很容易踩这个：看着像被 ufw 挡了，其实是云安全组只放行了某几个端口。

诊断方式是把两个变量分开：**从云内网的另一个实例测**（绕过安全组）与**从公网测**对比。内网通、公网不通 = 安全组。

### DNS 与主机名

```text
$ getent hosts example.com       # 按 NSS 顺序解析（和程序实际行为一致）
$ dig example.com +short
$ dig @8.8.8.8 example.com +short   # 换一个 DNS 服务器对比
```

`getent hosts` 值得优先用：它走系统的 name service switch，会读 `/etc/hosts`（`dig` 不读），也就是"程序实际会拿到哪个 IP"。排查"为什么程序连到了测试库"时，经常是 `/etc/hosts` 里有一行旧的。

`curl --resolve` 可以在不改 hosts 的情况下验证某个域名的后端：

```text
$ curl -I --resolve api.example.com:443:10.0.0.12 https://api.example.com/
```

### `curl` 的五个常用姿势

```text
$ curl -I https://example.com                  # 只要响应头
$ curl -v https://example.com                  # 看完整握手与请求头
$ curl -o file.zip https://example.com/f.zip   # 存文件
$ curl -L https://example.com                  # 跟随重定向
$ curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://example.com/health   # 只要状态码与耗时
$ curl --connect-timeout 3 -m 10 https://example.com    # 分别限制连接与总时长
```

最后一条在脚本里必须加：**没有超时的 curl 会一直挂着**，把调用它的脚本或定时任务卡死。

### `ping` 与 `traceroute` 的局限

`ping` 用的是 ICMP，**很多云厂商和防火墙默认丢掉 ICMP**。所以"ping 不通"不代表 TCP 不通——上面几种测法才是对的。`ping` 只能证明"ICMP 通"。

`traceroute`（或 `mtr`）看路径在哪一跳断：

```text
$ mtr -rw -c 10 example.com
```

中间跳显示 `* * *` 是正常的（那一跳不回 ICMP），要看的是**最后能否到达**。

## 常见误区

### 误区：`ping` 不通就是网络不通

**你以为**：`ping` 是连通性的标准测试。
**其实**：`ping` 用 ICMP，而很多防火墙与云安全组默认只放行 TCP，直接丢 ICMP。`ping` 失败时务必再用 `nc -zv` 或 `curl` 测 TCP 端口，很多"网络故障"其实是 ICMP 被禁。
**怎么验证**：同一目标 `ping` 失败但 `curl -I` 成功，就是这种情况。

### 误区：`netstat -tunlp` 才是正统

**你以为**：教程上都写 `netstat`。
**其实**：`netstat` 属于 net-tools，现代发行版默认不装（要 `apt install net-tools`），而且在高并发下比 `ss` 慢得多，因为 `netstat` 要遍历 `/proc` 的全部内容。`ss` 直接读内核的 socket 表。两者参数一一对应：`netstat -tunlp` ≈ `ss -lntp`。
**怎么验证**：`which netstat` 常常什么都没有；`ss -s` 立刻出汇总。

### 误区：改完防火墙规则就生效了

**你以为**：`ufw allow 8080` 或 `iptables -A` 之后就通了。
**其实**：`ufw` 的规则要 `ufw reload`（`ufw allow` 通常自带）；`firewall-cmd` 不带 `--permanent` 的规则**重启后消失**，带 `--permanent` 的不 `--reload` **现在不生效**；`iptables -A` 加的规则在机器重启或服务重载后清零（除非自己持久化）。所以"昨天放行了、今天又不行"经常是这两种情况。
**怎么验证**：改完立刻用另一台机器测；重启服务后再测一次；`sudo iptables-save | grep 端口` 看规则是否真的在表里。
