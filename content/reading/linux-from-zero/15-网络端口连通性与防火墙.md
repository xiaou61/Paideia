## 同一台机器、同一个端口，连了七次，得到四种结果

我在本机用 node 起了四个监听器，然后拿自己连自己，每次记下错误码和耗时：

```text
# Windows 11 + node v24.14.1，本机自连（LAN 地址 192.168.11.187 是 WLAN 那张网卡）
绑定地址                客户端连                  结果                      耗时
127.0.0.1:18080        127.0.0.1:18080          握手成功                  1.3 ms
127.0.0.1:18080        192.168.11.187:18080     ECONNREFUSED              2019 ms
0.0.0.0:18081          192.168.11.187:18081     握手成功                  0.5 ms
127.0.0.1:18082        127.0.0.1:18082          握手成功，之后没有数据      0.4 ms
::（未写 host）:18085   127.0.0.1:18085          握手成功                  0.4 ms
（没人监听）18084       127.0.0.1:18084          ECONNREFUSED              0.4 ms
192.0.2.1:80           192.0.2.1:80            3 s 上限到了还在等          3014.9 ms
```

第一行和第二行是同一段代码、同一个端口，唯一变量是**监听地址**：程序只听 `127.0.0.1`，从本机 LAN 地址打过去就变成 `ECONNREFUSED`；改成 `0.0.0.0` 立刻通。

我原来的判断是「连不上就是连不上，去看防火墙」。这张表把这件事拆成了四种，责任方完全不同：第四行连握手都成功了，只是应用一个字都不回；最后一行连 RST 都没有，3 秒过去还在等。

换成 `curl 8.0.1` 再看一遍，差别落在**报错原文和退出码**上（下面都是真跑的输出，`NUL` 是 Windows 的 `/dev/null`）：

```text
① 端口开着、应用答     $ curl -sSv --max-time 3 http://127.0.0.1:18080/health
                      < HTTP/1.1 200 OK
                      exit=0

② 没人监听            $ curl -sSv --max-time 3 http://127.0.0.1:18084/health
                      * connect to 127.0.0.1 port 18084 failed: Connection refused
                      * Failed to connect to 127.0.0.1 port 18084 after 2033 ms
                      exit=7

③ 握上手、应用不回     $ curl -sSv --max-time 3 http://127.0.0.1:18082/health
                      * Connected to 127.0.0.1 (127.0.0.1) port 18082 (#0)
                      * Operation timed out after 3015 milliseconds with 0 bytes received
                      exit=28

④ SYN 被丢            $ curl -sSv --connect-timeout 3 http://192.0.2.1/health
                      * Connection timed out after 3004 milliseconds
                      exit=28
```

③ 和 ④ 都是 `exit=28`、都要等满超时，区别只在 `-v` 有没有打出 `Connected to`。这一行是本文最有用的一个判据，后面「三种死的分辨」那张表就是围着它写的。

后面所有判断都拿一个真实端点来验：这台服务器上跑着 paideia 后端，`deploy/ops/prometheus.yml:3` 的注释写着「全部目标都在回环……公网仍只有 8081」，第 23 行抓的是 `127.0.0.1:8081/actuator/prometheus`。也就是说，公网上只开了 8081 一个口，而这个口上有的路径谁都能读、有的路径只有本机能读。

## 第一道门：绑定地址，`ss` 那一列只回答一件事

`ss` 的 `Local Address:Port` 那一列不是「端口号」，是「内核在哪个地址上接这个端口的连接」。下面是标准形态，未实跑（这台机器是 Windows，没有 `ss`）：

```text
# 标准形态，未实跑（Linux + iproute2）
$ ss -lntp
State  Recv-Q Send-Q Local Address:Port   Peer Address:Port Process
LISTEN 0      128            0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=812,fd=3))
LISTEN 0      4096                 *:8081           *:*    users:(("java",pid=9812,fd=42))
LISTEN 0      4096       127.0.0.1:3000        0.0.0.0:*    users:(("grafana",pid=2154,fd=9))
```

| Local Address 列 | 谁发起的连接能进来 | 下一步该看哪 |
| --- | --- | --- |
| `127.0.0.1:3000` | 只有本机进程 | 这不是故障。要给人看就得改应用的监听地址，或让它只被本机服务读 |
| `0.0.0.0:8080` / `*:8080` | 任何一张网卡上的任何 IPv4 地址 | 继续看防火墙与安全组，内核这一关已经过了 |
| `10.0.0.12:8080` | 只有那块网卡的对端能连 | 多网卡的机器上绑错网卡，就是「看着在听、别人连不上」 |
| `[::]:8080` | 所有 IPv6 地址，**并且默认也接 IPv4** | 别以为只开了 v6 就没事，见下一段 |

那个 `*:8080` 和 `0.0.0.0:8080` 是同一件事：iproute2 不同版本对通配地址的打印写法不一样，`[::]` 也出现在部分版本的输出里。**读法是「通配 = 所有地址」，不要盯着星号还是零去判断。**

关于 `[::]`，我原来以为「绑了 v6 通配就只服务 v6」。实际不是：内核参数 `net.ipv6.bindv6only` 的默认值是 `0`（`Documentation/networking/ip-sysctl.txt`），含义是绑在 `[::]` 上的 socket 同时接受 IPv4 映射过来的连接。上面实验里第五行就是这个：不写 host 起监听，内核给的地址是 `::`，从 `127.0.0.1` 连过去 0.4 ms 就握上手。要真的只服务 v6，程序得显式设 `IPV6_V6ONLY`——这是**内核默认行为**，不是所有程序都必须听话的规矩。

`-lntp` 四个字母各管一件事：`-l` 只看 LISTEN（不然会把已建立的连接一起打出来）、`-n` 不解析域名和服务名（快，而且不会把 8080 显示成 `http-alt` 让你认错）、`-t` 只 TCP（`-u` 是 UDP，两种协议各有各的端口表）、`-p` 带进程——**看别人的进程要 root**，普通用户跑出来那列是空的，不是没有进程。

`netstat` 那套参数换算时容易丢东西：`ss -ltunp` 才对应 `netstat -tunlp`（少了 `-u` 就看不见 UDP，而 DNS 的 53 恰恰是 UDP 为主）。`netstat` 也不再保证存在：先 `command -v netstat` 看一眼，没有就装 net-tools——`command not found` 不是环境坏了，是包没装。

回到 8081。这台机器上它是通配地址，同一台机器上的 Grafana 反过来是**显式**写的回环——两行配置放在一起看，就是「默认」和「明确决定」的差别：

```ini
# deploy/ops/grafana.ini:15-16
http_addr = 127.0.0.1
http_port = 3000
```

`deploy/ops/install-ops.sh:239` 那条自检也是照这个写的，注释是「监听端口（应全部是 127.0.0.1）」：

```bash
# 标准形态，未实跑
ss -ltn | grep -E ':(9090|9100|9104|9121|9115|3000|3100|3200|4317|4318|12345)\s'
```

8081 为什么不是回环？因为 `backend/paideia-app/src/main/resources/application.yml` 的 `server:` 段只写了 compression，**没有 `address`**。Spring Boot 在 `server.address` 为空时监听所有本地地址——「默认开在所有地址上」这个默认值，不是「默认安全」。想只绑回环，得自己写 `server.address: 127.0.0.1`。

## 拒绝、丢包、握上手不回：三种死的分辨

| 症状 | 先看哪 | 它在回答什么 |
| --- | --- | --- |
| 立刻 `ECONNREFUSED`，curl `exit=7` | `ss -lntp` 的 Local Address 列 | 包到了主机，这个端口没人接（或只听在别的地址上） |
| 等到超时才报，`curl -v` 里**没有** `Connected to` | 云安全组 → 本机防火墙 | 包在路径上被丢了，连 RST 都没回来 |
| 打出 `Connected to`，之后一个字都没有 | 应用日志、应用自己的放行规则 | 内核与握手都成了，是应用不肯答 |
| 拿到 4xx | 应用自己的鉴权 | 应用答得很正常，只是不给你读 |

两行「超时」必须分开：③ 和 ④ 的现象（都要等满你设的上限）一模一样，判据只有 `Connected to` 有没有打出来。没有它，说明 SYN 压根没被应答，别去看应用日志，那里什么都不会有。

`ECONNREFUSED` 的含义也要说准。它的默认解释是「主机内核回了 RST」，但 `iptables -j REJECT --reject-with tcp-reset` 会发出一个一模一样的 RST。所以它严格证明的是「路径上有人回了 RST」，**不严格证明「服务没起」**。反过来，拒绝确实比超时信息量大得多：超时说明你和主机之间有一层不让你说话。

再补一个坑，是我这次实验里撞出来的：**别拿 curl 报的毫秒数当网络耗时**。同一个没人监听的端口，curl 报 `after 2033 ms`，而 node 的 `net.connect` 在 5 ms 就拿到了 `ECONNREFUSED`；curl 自己记的 `%{time_connect}` 是 `0.000000`——那两秒根本不在握手上。

```text
# 真跑：还是那个没人监听的 18084，加 -w 把三个数拆开（PowerShell 里一行写完，`\` 不是续行符）
$ curl.exe -sS -o NUL --connect-timeout 3 -m 3 -w 'namelookup=%{time_namelookup} connect=%{time_connect} total=%{time_total}\n' http://127.0.0.1:18084/
namelookup=0.000024 connect=0.000000 total=2.025543
```

```text
$ node -e "const t=Date.now();net.connect({host:'127.0.0.1',port:18084}).on('error',e=>console.log(e.code, Date.now()-t, 'ms'))"
ECONNREFUSED 5 ms
```

所以判断链路快慢要看 curl 的 `-w`，不要看它错误信息里那句 `after N ms`。

## 8081 上还有第二道门：端口通，端点不一定给你读

这是这一篇我最想让你记住的事：**`ss` 显示在听，只证明内核接了这个端口**，它没法告诉你哪个路径会被应用放行。

`backend/paideia-security/src/main/java/io/github/xiaou61/security/SecurityConfiguration.java:151` 让 `/actuator/health` 对所有人开放（管理端健康徽标和两端 e2e 要用）；紧接着 `:156-157` 把 `/actuator/metrics/**` 和 `/actuator/prometheus` 交给 `LocalOnlyAuthorizationManager`。那个类只做一件事：

```java
// LocalOnlyAuthorizationManager.java:28
return new AuthorizationDecision(isLoopback(request.getRemoteAddr()));

// :31-39，认这四种写法
return remote.equals("127.0.0.1")
        || remote.equals("::1")
        || remote.equals("0:0:0:0:0:0:0:1")
        || remote.startsWith("127.");
```

于是同一个端口上会出现这种组合：TCP 连得上（通配地址 + 公网开着 8081）、`/actuator/health` 给你 200、`/actuator/prometheus` 被拒。**被拒不是「连不上」**，是应用回了你一个拒绝——具体是 401 还是 403 取决于请求带没带凭据、走哪个鉴权入口，我没在公网上打过，只按代码路径推，这一点写在最后。

这道门有一个明确的边界，仓库注释自己写出来了，`SecurityConfiguration.java:154-155`：

> 一旦本进程前面挂了反向代理，远端地址会变成 127.0.0.1，这条白名单即失效——那时必须改为独立回环管理端口。

原因也直白：`getRemoteAddr()` 拿到的是**直连的那个 TCP 对端**，反代之后对端永远是反代自己。它选 `remoteAddr` 而不是 `X-Forwarded-For`，正因为后者可伪造——`LocalOnlyAuthorizationManager.java:17` 的注释写着这个取舍。这是「按来源地址做访问控制」这类做法的通用代价：它能挡住「忘了关端口」，但挡不住「本机上已经有一个进程能连」和「前面多了一层自己人」。别把它当成认证。

## 防火墙与安全组，只在包被丢的时候轮到你

只有一种症状值得往下走：**超时，`curl -v` 里没有 `Connected to`**。绑定地址对了、进程在听、从外面打还是没反应，才轮到这两层。

下面全是标准形态，未实跑（这台机器没有 Linux，没有 ufw、firewalld、iptables）：

| 你在哪台机器上 | 命令 | 生效时机与它挡不住什么 |
| --- | --- | --- |
| Ubuntu/Debian | `ufw status verbose` | 看第一行是不是 `Status: active`。inactive 时规则照样列出来，但一条都不执行 |
| Ubuntu/Debian | `ufw allow 8080/tcp` | 立即生效（前提是上面那行 active）。它改的是 ufw 自己的规则表，不用 `ufw reload` |
| Ubuntu/Debian | `ufw reload` | 只在你手改了 `/etc/ufw/*.rules` 这种底层文件之后才需要 |
| RHEL/CentOS | `firewall-cmd --add-port=8080/tcp --permanent` | 只写进磁盘，**现在不生效**，要配 `--reload` |
| RHEL/CentOS | `firewall-cmd --add-port=8080/tcp` | 只进 runtime，`--reload` 或重启后消失 |
| 两者都适用 | `iptables -L -n -v` / `nft list ruleset` | 看内核里真正在执行的规则；`iptables -A` 加的规则重启就没了（除非自己持久化） |
| 机器外面 | 云控制台的安全组 | 主机上的规则全关、`ss` 也在听、外面仍然超时，就是它 |

「改完规则就通了」这句话，两个方向都可能错：`firewall-cmd` 不带 `--permanent` 是先通后不通（reload 就没了）；带 `--permanent` 不 reload 是先不通、下次重载才通。`ufw allow` 反过来是真的立即生效，`ufw reload` 是给手写 `/etc/ufw/before.rules` 那种场景用的——把 `ufw allow` 也套上一句 `reload`，只是没害处，不是必需。

`iptables -L -n -v` 的计数器很容易读错。规则链是**按顺序**匹配的，一个包命中终止动作（ACCEPT/DROP/REJECT）之后就结束了；因此**某行计数涨只说明包走到了这一行，不等于这一行是挡你的那条**。你要找的是「第一条命中、动作是 DROP/REJECT」的规则，而不是计数最大的那行。更省事的办法：从外面打一次，先用 `iptables -Z` 清零，再看计数涨在哪几行，同时 `journalctl -k` 里有没有 drop 记录，两头对上再下结论。

云安全组在主机外面，它和本机防火墙是两道独立的关卡，一台机器上只能看见一道。区分方法只有一个：**从云内网的另一台实例打**和**从公网打**，结果不一样就是安全组。顺带把 `ping` 这个坑说清：安全组的入方向是白名单语义——没单独放行的协议，包直接不进；ICMP 没放行就不通，所以「ping 不通」证明不了 TCP 不通，只能证明「ICMP 没被放行」。测端口就老老实实 `curl` 或 `nc -zv`，测的是你要用的那个 TCP 端口本身。

## 还差的

- **公网上 8081 那个被拒的状态码我没实测。** 我只从 `SecurityConfiguration` 的规则推出「非回环来源会被拒」，是 401（鉴权入口）还是 403（拒绝处理），得实际打一次才知道。想验就 `curl -i` 打自己的域名。
- **防火墙、安全组、`ss` 的命令回显全是标准形态。** 这台机器是 Windows 且没有 WSL，`ufw status verbose`、`firewall-cmd --list-all`、`iptables -L -n -v` 我一条都没跑过。`ufw allow` 立即生效、`--permanent` 要 reload 这些是按各自的行为语义写的，不是我看输出写的。
- **两个两秒延迟的成因没查清。** 从本机 LAN 地址拿 RST 要 2019 ms、curl 对一个关闭的回环端口要 2033 ms，而 node 的 `net.connect` 同端口 5 ms——我只知道结论「别拿耗时当判据」，机制没验。
- **`ss` 通配地址的打印形式我没核到版本分界。** `*:8080`、`0.0.0.0:8080`、`[::]:8080` 哪种出现在哪个 iproute2 版本，我只能说「都表示通配，读法一样」。
- **连接数多到什么程度才算 `TIME_WAIT` 有问题，我没给阈值。** 它取决于本地端口范围与每秒新建连接数，Linux 上 `TIME_WAIT` 是固定 60 秒、留在主动关闭的那一侧；光看 `ss -s` 的数量高下不了结论。
