## `cp -r app backup` 之后，backup 里多了一层 app

```text
$ cd ~/work
$ mkdir -p backup
$ cp -r app backup
$ ls backup
app
```

这是标准形态，不是这台 Windows 的输出。我的预期是 `backup` 变成 `app` 的副本，实际得到的是 `backup/app`：`backup` 已经存在，`cp` 把 `app` 这个目录**放进**了 `backup`。

这不是 `cp` 的 bug，是它的目标判定：目标已存在且是目录，源目录就作为子目录放进去；目标不存在，才把目标本身建成副本。把命令改成 `cp -r app backup2`（`backup2` 不存在），`backup2` 里直接就是 `app` 的内容。

源路径末尾的 `/` 还会再改一次语义，但只在目标已存在时看得出来：`cp -r app/ backup` 复制的是 `app` 的**内容**，不是 `app` 这一层目录。目标不存在时，`cp -r app backup/` 反而会报错，因为结尾斜杠要求目标已经是一个目录（GNU cp 的行为）。

所以我现在写复制命令先问三件事：目标是文件还是目录、存在没有、我要的是目录本身还是目录里的内容。三个答案不清楚，就先 `ls -ld` 看一眼。

## `ls -l` 那一行，先看类型和权限

```text
$ ls -l app/run.sh app/conf app/current
-rwxr-xr-x 1 lzf devs  412 Nov 18 21:04 app/run.sh
drwxr-xr-x 2 lzf devs 4096 Nov 18 20:58 app/conf
lrwxrwxrwx 1 lzf devs   28 Nov 18 20:59 app/current -> /srv/app/releases/2026-11-19
```

标准形态，数字是示意。七列：

| 列 | 例子 | 含义 |
| --- | --- | --- |
| 类型+权限 | `-rwxr-xr-x` | 第一位：`-` 普通文件、`d` 目录、`l` 软链接、`b` 块设备、`c` 字符设备、`s` socket、`p` 管道 |
| 链接数 | `1` | ext4/XFS 上目录常见是 2 + 直接子目录数；btrfs 等可能不是这个公式 |
| 属主 | `lzf` | 文件归谁 |
| 属组 | `devs` | 归哪个组 |
| 大小 | `412` | 普通文件是字节数；目录在 ext4 上常见 4096，是目录项占用的块，不是里面文件总和 |
| 修改时间 | `Nov 18 21:04` | 默认 mtime；GNU ls 对大约半年前的时间改显示年份 |
| 名字 | `app/current -> ...` | 软链接会带目标 |

`ls -l` 只给 mtime；要看 atime/ctime 用 `stat`，后面讲。

`ls` 的组合：

| 命令 | 用途 |
| --- | --- |
| `ls -lh` | 人类可读大小 |
| `ls -la` | 含隐藏文件 |
| `ls -lt` | 按 mtime 倒序 |
| `ls -lS` | 按大小倒序 |
| `ls -ld 目录` | 只看目录本身 |
| `ls -lR` | 递归，大目录别用 |

## 复制、移动、删除：同一条路径上的三个坑

### `cp`：默认覆盖，而且不建父目录

```text
$ cp app/conf/app.conf app/conf/app.conf.bak
$ cp app/conf/app.conf /etc/myapp/        # /etc/myapp 必须已存在
$ cp -a app /srv/app-copy                # 目标不存在；目录、权限、时间一起保留
```

- `cp` 默认覆盖已存在的目标文件，不问你。有的发行版给 root 配了 `cp -i` 别名；`type cp` 看当前 shell 实际用的是什么。脚本里不要依赖别名，显式写 `-i` 或 `-n`。
- 目标文件的父目录不存在时，`cp` 不会替你 `mkdir -p`；先建目录。
- 不带 `-a` 新建目标文件时，属主是当前用户；`sudo cp` 备份系统文件，新文件就是 root 的。目标已存在时，`cp` 写的是原来那个 inode，属主保持目标文件原来的属主——这两种情况别混。
- `cp -a` 保留权限、时间、软链接；属主要看权限，root 才能把文件仍归别人。普通用户跨文件系统用 `-a`，属主可能保不住。

### `mv`：同盘改名，跨盘复制再删

```text
$ mv app/conf/app.conf app/conf/app.conf.2026-11-19
$ mv app/logs/*.log /srv/app/logs/
$ mv -i app/conf/app.conf app/conf/app.conf.bak
```

同一个文件系统内，`mv` 只改目录项，文件内容不动；跨文件系统时，`mv` 是复制到目标、再删源。大目录跨盘 `mv` 的耗时按数据量增长，中断可能留下半个目标文件。用 `df /源路径 /目标路径` 看两边 `Filesystem` 是否相同。

### `rm`：没有回收站，尾斜杠在软链接上会变脸

```text
$ rm app/conf/app.conf.bak
$ rm -r app/conf/old/
$ rm -rf app/current
$ rm -rf app/current/
```

前三条删的是名字；最后一条不一样。`app/current` 是指向 `/srv/app/releases/2026-11-19` 的软链接：

- `rm -rf app/current` 删链接本身，目标目录不动。
- `rm -rf app/current/` 的尾斜杠让内核先把链接解析成目录，GNU rm 会递归清空目标目录的内容；链接和空的目标目录还在，命令还可能以 0 退出。`-f` 可能把中间的 `Not a directory` 报错也吞掉，看起来像成功。

这是 GNU coreutils 的行为；我没在这台 Windows 上跑过，别拿真实 release 目录试。普通目录末尾多一个 `/` 不会多删；危险的是「软链接 + 尾斜杠」这个组合。

另一个危险是空格：

```text
$ rm -rf app/current /home/lzf
```

shell 看到两个参数。GNU rm 默认有 `--preserve-root`，`rm -rf /` 会被拒绝，但 `/home/lzf` 不在保护范围。别把安全寄托在这个开关上。

批量删除的纪律：

1. 先 `ls -ld` 或 `find ... -maxdepth 1` 看匹配到哪些路径，再删。
2. 变量加引号，并用 `${DIR:?}` 挡住空值：`rm -rf "${DIR:?}/"`。
3. 文件名以 `-` 开头时用 `--`：`rm -- -weird.txt`。
4. 去掉 `-f` 不是演练；它只在某些情况下多问一句，真删还是真删。

## 软链接、硬链接：先看它到底指向哪

```text
$ ln -s /srv/app/releases/2026-11-19 app/current
$ ls -l app/current
lrwxrwxrwx 1 lzf devs 28 Nov 18 20:59 app/current -> /srv/app/releases/2026-11-19
$ readlink app/current
/srv/app/releases/2026-11-19
$ readlink -f app/current
/srv/app/releases/2026-11-19
```

- 软链接是一个独立文件，内容是目标路径字符串；目标删了它就断。可以跨文件系统、可以指向目录。
- 硬链接是同一个 inode 的第二个名字；删一个另一个还在；不能跨文件系统，Linux 上也不能给目录建硬链接。
- `readlink` 只打印链接里存的字符串；`readlink -f` 一路解析到底，脚本里判断真实目标用它。

相对路径的软链接要小心：`ln -s releases/2026-11-19 current` 里的 `releases/...` 是相对链接所在目录解析的，不是相对你当前所在目录。拿不准就写绝对路径，或者 `readlink -f` 验证。

## `find`：按名字、大小、时间找人

`find` 自己递归，不依赖 shell 通配符。找深层文件用它，不要用 `ls *`。

```text
$ find /srv/app -name "*.log"
$ find /srv/app -type f -size +100M
$ find /srv/app -mtime -1 -type f
$ find /srv/app -name "*.tmp" -delete
$ find /srv/app -name "*.log" -exec gzip {} \;
```

`-delete` 先去掉跑一遍，看清匹配到哪些文件再加回去。

`-name` 的模式要加引号：当前目录里正好有匹配时，shell 会先展开 `*.log`，`find` 收到的就不是模式了。

四个常用参数：

| 参数 | 含义 |
| --- | --- |
| `-name` / `-iname` | 名字匹配，`-iname` 忽略大小写 |
| `-type f` / `-type d` / `-type l` | 只要文件 / 目录 / 软链接 |
| `-size +100M` | 大于 100 MiB；`-size -1k` 小于；单位 `k`、`M`、`G` |
| `-mtime -1` | 1 天内改过；`+7` 是 7 天以前（按 24 小时整段算）；`-mmin -30` 按分钟 |

`-size` 不带加减号是「恰好这么多单位」，GNU find 按单位向上取整，所以 `-size 100M` 匹配的是 99MiB 以上到 100MiB 这一档，不是「大于 100M」。要大于就写 `+100M`。

`-exec ... \;` 对每个结果执行一次；`-exec ... +` 把一批结果一次传给命令，少起进程；管道给 `xargs` 也行，第 06 篇讲。

`find /` 会扫全盘。能限定目录就限定，能加 `-maxdepth` 就加：

```text
$ find /srv/app -maxdepth 2 -name "*.log"
```

## `stat`：mtime 之外还有两个时间

`ls -l` 只显示 mtime。GNU `stat` 的 `%x`、`%y`、`%z` 分别是 atime、mtime、ctime：

```text
$ stat -c '%n%n%x%n%y%n%z' app/conf/app.conf
app/conf/app.conf
<atime>
<mtime>
<ctime>
```

这里是字段顺序，不是本机输出。三个时间的含义：

| 时间 | 什么时候变 |
| --- | --- |
| `Access` (atime) | 文件被读；很多系统用 `relatime`，不是每次读都写盘 |
| `Modify` (mtime) | 文件内容被写 |
| `Change` (ctime) | inode 元信息变：内容、权限、属主、链接数都算 |

排查「这个文件是不是被人动过」要看 ctime，不是 mtime：`chmod` 只改 ctime，mtime 不动。反过来说，ctime 变了也不一定是内容变了。

## 跑一遍

下面要在 Linux 上跑；这台 Windows 没有 Linux，我没执行过。

```text
$ cd /tmp
$ rm -rf cp-demo
$ mkdir -p cp-demo/app/conf cp-demo/backup
$ printf 'port=8080\n' > cp-demo/app/conf/app.conf
$ cd cp-demo
$ cp -r app backup
$ ls backup
app
$ cp -r app backup2
$ ls backup2
conf
$ cp -r app/ backup
$ ls backup
app  conf
```

最后一条能看出源路径尾斜杠的差别：`backup` 已存在，`app/` 的内容被放进 `backup`，所以 `backup` 里同时有之前的 `app` 和新的 `conf`。这段是标准行为，不是本机输出。

## 还差的

- 这台机器没有 Linux 环境，上面所有终端输出都是标准形态，不是本机实测。`rm -rf 软链接/` 的行为按 GNU coreutils 的文档和公开测试写；BSD/macOS 的 `rm` 可能不同。
- `stat` 的 `%x/%y/%z` 是 GNU coreutils 的格式，macOS 的 `stat` 参数不一样。
- `find -size` 的边界我只按「单位向上取整」解释，没有逐字节验证 100MiB 上下各一字节的情况；`-mtime` 的 24 小时取整也没展开。
- 删除后的数据恢复、inode 和块分配只讲到能解释「为什么 rm 没有回收站」，没做恢复实验。
