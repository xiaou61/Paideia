## 这一关在解决什么

安全问题的起点只有一句话：**来自边界之外的数据，一律不可信**。

难点不在记住这句话，而在知道边界画在哪：哪些是"外面"，哪些校验做了也没用，还有一些调用看起来是内部，其实也能被伪造。这一关把一条请求从浏览器到数据库的路径拆开，标出每一段的可信度。

打个比方：边界就像公司前台。外面来的人都要登记，但前台放行不等于他能进财务室——真正的门禁在每一道门后面。真实机制也一样：网关只做粗过滤，业务校验必须落在应用层。

## 讲解

### 一条请求经过谁

```text
浏览器 → CDN/网关 → 应用 → 数据库 / 外部服务
   ↑ 不可信        ↑ 可校验     ↑ 受控
```

- **浏览器**：用户完全可控。改表单、改 JS、直接发请求，都不需要任何技巧。前端的校验是**体验**，不是安全。
- **网关**：能做限流、鉴权、IP 白名单，但它看到的是"请求"，不理解业务。它放过的请求不代表业务上合法。
- **应用**：唯一知道"这个用户能不能做这件事"的地方。**业务校验必须在这里。**
- **数据库/外部服务**：由应用控制，但仍然要防注入与 SSRF。

### 前端校验为什么不算安全

```js
if (amount <= 1000) {
  await fetch('/api/transfer', { method: 'POST', body: JSON.stringify({ amount }) })
}
```

攻击者不需要走你的页面：打开 DevTools、用 curl、改 JS 变量，都能直接发 `amount: 999999`。

**规则：前端校验为了少一次往返、早点给提示；服务端校验为了正确性与安全。两边都要有，但只有后者算数。**

### 隐藏字段与"前端传来的一切"

```html
<input type="hidden" name="price" value="99" />
<input type="hidden" name="userId" value="42" />
```

`price` 与 `userId` 都能被改成任意值。价格必须服务端按商品 id 查；用户身份必须从会话/令牌里取，不能信请求体。

同理不可信的还有：

- `X-Forwarded-For`、`Referer`、`User-Agent`（可伪造，除非在可信网关上覆写）；
- Cookie 里的角色/权限字段（除非签名）；
- 文件名与 MIME 类型（上传时都能伪造）。

### 校验要写在"最近的可信层"

一个常见错误：网关做了参数校验，应用就不再校验。网关的规则一旦被绕过（内网直连、规则漏配），应用就裸奔。

**每个入口自己校验自己的输入**，即使上游也校验过：

```java
@PostMapping("/transfer")
ApiResponse<TransferResult> transfer(@RequestBody TransferRequest body) {
    if (body.amount() == null || body.amount().signum() <= 0 || body.amount().compareTo(MAX) > 0) {
        throw new BizException(ErrorCode.INVALID_ARGUMENT, "金额不合法");
    }
    long userId = CurrentUser.userId();   // 身份来自令牌，不来自 body
    return service.transfer(userId, body.toAccountId(), body.amount());
}
```

校验三件套：**类型/范围、身份来源、资源归属**。缺一个，就有一类漏洞。

### 输出也是边界

不可信数据进入日志、HTML、SQL、命令行、文件路径、外部 HTTP 请求，每个去向都有对应的注入风险：

| 去向 | 风险 | 做法 |
| --- | --- | --- |
| HTML | XSS | 转义 / 安全 API |
| SQL | 注入 | 参数化 |
| shell | 命令注入 | 不拼命令，用参数数组 |
| 文件路径 | 路径穿越 | 白名单 + 规范化后校验前缀 |
| 外部 URL | SSRF | 协议与域名白名单，禁内网地址 |
| 日志 | 日志注入/泄漏 | 转义换行，脱敏 |

**"校验输入"不够，还要"按去向编码输出"**——同一个昵称，放进 HTML 要转义，放进 SQL 要参数化。两处规则不同。

### 报错信息也是信息泄漏

```text
错误：Unknown column 'password_hash' in 'field list'
错误：User not found
```

第一条泄露了表结构；第二条让攻击者能枚举哪些账号存在。对外统一成"用户名或密码错误"，细节只进内部日志。

## 常见误区

### 误区：参数在 URL 里才需要防，POST 体是安全的

**你以为**：POST 不好改。
**其实**：POST 只是 HTTP 方法，用 curl 一条命令就能改。所有参数位置（path、query、body、header、cookie）都不可信。
**怎么验证**：用 curl 改一个 POST 体里的金额，看服务端是否接受。

### 误区：内网调用可以信任

**你以为**：只有网关能访问应用，所以网关传来的头都可信。
**其实**：内网也可能被 SSRF、被攻破的机器、配置错误绕过。可信的是"你亲自签名的数据"，不是"来自某个地址的数据"。
**怎么验证**：直接连应用端口发一个带 `X-User-Id` 的请求，看是否被当成登录用户。

### 误区：校验了长度就防住了注入

**你以为**：`length <= 20` 就安全。
**其实**：`' OR 1=1 --` 只有 12 个字符。长度限制防的是资源耗尽，不是注入；注入要靠参数化与转义。
**怎么验证**：在本地测试库用 12 字符的 payload 试一次（只在自己环境）。
