## 这一关在解决什么

注入的本质是：**把数据当成了代码**。用户输入被拼进一段会被解释器执行的字符串里，输入里的引号、分号、反引号就变成了语法。

这一关讲三个最常见的注入面：SQL（含排序与模糊查询）、shell 命令、文件路径。每个都给"为什么错"与"怎么写"。

## 讲解

### SQL：参数化，不是转义

```java
// 错：用户输入进了 SQL 文本
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
```

输入 `' OR '1'='1` 之后，条件变成恒真，整表返回。更糟的是输入 `'; DROP TABLE users; --`。

```java
// 对：占位符
String sql = "SELECT * FROM users WHERE name = ?";
jdbcTemplate.queryForList(sql, name);
```

```js
// 对（node-mysql）
await db.query('SELECT * FROM users WHERE name = ?', [name]);
```

参数化让数据库把输入当**值**，而不是 SQL 片段。它不需要你手动转义引号，也不会因为编码差异失效。

**MyBatis 的 `#{}` 是参数化，`${}` 是字符串拼接**。`${}` 只该出现在列名/表名这类不能参数化的位置，且必须走白名单。

### 排序与列名：参数化不了的，用白名单

```xml
<!-- 错：用户可以传任意 ORDER BY 片段 -->
ORDER BY ${sort}
```

`ORDER BY` 后面不能放占位符，所以只能白名单：

```java
private static final Map<String, String> SORTS = Map.of(
    "created", "created_at",
    "amount", "amount DESC"
);

String column = SORTS.get(req.sort());
if (column == null) {
    throw new BizException(ErrorCode.INVALID_ARGUMENT, "排序字段不支持");
}
```

**白名单的键由前端传，值由代码定**——不要对输入做"过滤危险字符"，那是一场永远会输的军备竞赛。

### LIKE 与通配符

```sql
SELECT * FROM users WHERE name LIKE CONCAT('%', ?, '%');
```

参数化解决了注入，但 `%` 与 `_` 仍是通配符：用户搜 `%` 会匹配全部。需要按字面搜时转义：

```java
String escaped = keyword.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
```

### 命令注入：不要拼 shell

```java
// 错
Runtime.getRuntime().exec("convert " + filename + " out.png");
```

文件名里带 `; rm -rf /` 就会被执行。即使用 `ProcessBuilder`，如果把整串交给 shell（`sh -c`），一样会注入。

```java
// 对：参数数组，不经过 shell
new ProcessBuilder("convert", filename, "out.png").start();
```

更好的做法是**根本不让用户控制命令参数**：文件名由服务端生成 UUID，用户只传业务 id。

### 路径穿越

```java
File file = new File(uploadDir, userFileName);   // 用户传 ../../etc/passwd
```

修法三步：

1. 文件名不用用户给的，服务端生成（UUID + 固定扩展名）；
2. 必须用原文件名时，`Path.normalize()` 后校验 `startsWith(uploadDir)`；
3. 扩展名白名单，拒绝空字节与控制字符。

```java
Path base = Paths.get(uploadDir).toAbsolutePath().normalize();
Path target = base.resolve(name).normalize();
if (!target.startsWith(base)) {
    throw new BizException(ErrorCode.INVALID_ARGUMENT, "非法文件名");
}
```

### NoSQL 与模板注入

- MongoDB 查询里直接放 `req.body`，用户可传 `{"$ne": null}` 绕过条件；要显式取字段并限制类型；
- 模板引擎（Freemarker/Velocity）里用用户输入拼模板，可导致服务端模板注入（SSTI），甚至执行代码；模板只应由开发写，用户数据只作为变量传入。

## 常见误区

### 误区：把引号转义就安全了

**你以为**：`replace("'", "''")` 能防注入。
**其实**：编码、宽字符、数字型注入、`LIKE` 通配符都会绕过手写转义。转义规则与数据库、字符集、上下文都相关。
**怎么验证**：用参数化替代转义，代码更短，也不会漏。

### 误区：ORM 一定防注入

**你以为**：用了 JPA/MyBatis 就不会注入。
**其实**：ORM 的原生 SQL、`ORDER BY ${}`、`@Query` 里拼字符串同样会注入。防护来自"参数化"，不来自"用了 ORM"。
**怎么验证**：全局搜 `${`、`createNativeQuery(`、字符串拼接的 SQL。

### 误区：只让管理员能传排序参数就没事

**你以为**：管理员可信。
**其实**：管理员账号也可能被钓鱼、被 CSRF、被越权利用；而且"管理员"不该拥有执行任意 SQL 的能力。
**怎么验证**：白名单对所有角色一视同仁。

## 带走一句

**能参数化就参数化，不能参数化的（列名、排序、表名）一律白名单**——永远不要靠过滤字符来防注入。
