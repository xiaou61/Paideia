## 这一关在解决什么

现代应用的代码里，自己写的那部分可能不到 10%。其余来自依赖，而依赖会带着它们的依赖一起进你的进程——**你继承了它们的漏洞，也继承了它们的安装脚本**。

这一关讲四个能落地的动作：锁版本、审依赖、限制安装权限、控制构建链。

## 讲解

### 锁文件是底线

```text
package-lock.json / pnpm-lock.yaml / pom.xml（固定版本）
```

- 锁文件固定了**整棵依赖树**的版本，保证今天和明天装出来是同一套；
- 不提交锁文件，每次安装都可能拿到新版本，某次自动升级就可能引入漏洞或恶意包；
- CI 用 `npm ci` / `pnpm install --frozen-lockfile`，不要用会改写锁文件的命令。

### 审计：知道你在用什么

```bash
npm audit
pnpm audit
mvn dependency:tree
```

审计工具报告的是**已知漏洞**（CVE），它有三个局限：

1. 新漏洞有窗口期，审计通过不代表安全；
2. 传递依赖可能报一堆无关紧要的；
3. 有漏洞不代表可利用——要结合调用路径判断。

实践：高危（RCE、认证绕过）立即修；中低危排期；修不了的要记录原因与补偿措施（WAF、关闭入口）。

### 安装脚本：最容易被忽视的执行面

`npm install` 会执行包的 `postinstall` 脚本，**以你的用户权限运行**。一个恶意包可以在安装时读取环境变量、写文件、外联。

三个动作：

- 关掉不需要的安装脚本（pnpm 的 `onlyBuiltDependencies`、npm 的 `--ignore-scripts`）；
- 新依赖先看维护者、下载量、最近提交、仓库地址是否对得上；
- 名称拼写要核对：`cross-env` 与 `crossenv`、`lodash` 与 `lodassh`——typosquatting 专门钓手快的人。

### 版本范围不要"越宽越好"

```json
"dependencies": { "lib": "^1.2.3" }
```

`^` 允许自动升小版本，带来修复，也带来未经你验证的代码。对安全敏感的依赖，固定精确版本并定期手动升级，比"自动跟最新"更可控。

### 构建链也是供应链

- CI 里执行第三方脚本，等于给它仓库令牌与部署密钥；
- GitHub Actions 用 `uses: owner/action@<commit-sha>` 而不是 `@main`，防止上游被改；
- CI 令牌给最小权限（只读仓库、只推镜像），不要一个 token 通吃；
- 构建产物发布时附 SBOM（软件物料清单），出事后能快速定位影响范围。

### 一条实用流程

```text
新增依赖前：有没有标准库/现有依赖能做？→ 看仓库与维护者 → 看安装脚本
引入时：锁精确版本 → 记录用途 → 关掉不需要的脚本
定期：审计高危 → 升级 → 跑测试 → 记录
```

**能不引就不引**——每多一个依赖，就多一个需要信任的团队。

## 常见误区

### 误区：审计 0 漏洞就安全

**你以为**：`npm audit` 通过就没事。
**其实**：审计只覆盖已公开的 CVE；恶意包、0day、安装脚本行为都不在报告里。
**怎么验证**：看依赖的维护者与发布历史，比只看 audit 更有用。

### 误区：开发依赖不会进生产

**你以为**：`devDependencies` 无所谓。
**其实**：它们的安装脚本仍会在开发机与 CI 上执行，能读你的环境变量与 SSH 密钥；构建时也可能被打进产物。
**怎么验证**：在干净环境里装一次，观察网络请求与文件写入（只在自己环境）。

### 误区：自动升级最省心

**你以为**：`^` + 自动合并机器人，永远最新最安全。
**其实**：自动升级把小版本变更直接送进生产，缺少验证；供应链攻击也常利用"新版本"投毒。
**怎么验证**：看最近一次自动升级的 diff 与测试结果，是否真的有人看过。

## 带走一句

**锁文件、审计高危、限制安装脚本、收紧构建权限**——供应链安全不是"信任所有包"，而是"知道自己在信任谁"。
