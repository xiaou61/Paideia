## 这一关在解决什么

认证（authentication）回答"你是谁"，授权（authorization）回答"你能不能做这件事"。

大部分严重漏洞出在第二步：**登录校验做了，但没校验"这条数据是不是你的"**。这类漏洞叫 IDOR（不安全的直接对象引用）。利用成本低到只需要改一个数字。

打个比方：认证是进楼刷工牌，授权是这层楼你能不能进。刷开了大门，不代表每间办公室都对你开放。真实机制是：登录只证明“你是谁”，每次取数据还要校验“这条数据是不是你的”。

## 讲解

### 认证：会话与令牌

| | 服务端会话（Cookie + Session） | JWT |
| --- | --- | --- |
| 状态 | 服务端存会话 | 令牌自带声明 |
| 撤销 | 删会话即失效 | 到期前默认有效，需黑名单/短过期 |
| 扩展 | 需要共享存储 | 无状态，易水平扩展 |
| 风险 | 会话固定、CSRF | 令牌泄漏、算法混淆、过期太长 |

选择不是重点，**纪律**才是：

- 会话 id 登录后必须重新生成（防会话固定）；
- JWT 必须校验签名与 `alg`（拒绝 `none`），并检查 `exp`/`iss`/`aud`；
- 令牌不要放进 URL（会进日志、Referer）；
- 有效期短 + 刷新令牌轮换，比"一个长令牌用一年"安全得多。

### 授权：每次访问都要查归属

```java
// 错：只校验了登录
@GetMapping("/orders/{id}")
OrderView get(@PathVariable long id) {
    return orderService.find(id);
}
```

任何登录用户改一下 `id` 就能看别人的订单。正确做法是把"当前用户"作为查询条件的一部分：

```java
@GetMapping("/orders/{id}")
OrderView get(@PathVariable long id) {
    long userId = CurrentUser.userId();
    return orderService.findOwned(id, userId)
        .orElseThrow(() -> new BizException(ErrorCode.NOT_FOUND, "订单不存在"));
}
```

SQL 层面：

```sql
SELECT * FROM orders WHERE id = ? AND user_id = ?;
```

**把归属写进 WHERE，而不是查出来再在 Java 里比**。后者容易在某个分支忘记比较。而且会多一次"数据已经离开数据库"的暴露。

返回 404 而不是 403，可以避免"这个 id 存在"的信息泄漏。

### 水平越权与垂直越权

- **水平越权**：同角色之间互相访问（A 用户看 B 用户的订单）；
- **垂直越权**：低权限执行高权限操作（普通用户调管理接口）。

垂直越权常见于"只在菜单里隐藏了按钮"：

```jsx
{user.isAdmin && <button onClick={deleteUser}>删除</button>}
```

隐藏只是看不见，接口仍然能被直接调用。**每个管理端接口都要在服务端校验角色**，而且校验要写在控制器/服务层，不依赖前端路由。

### 401 与 403 不要混

- `401 Unauthorized`：没登录 / 令牌无效 → 去登录；
- `403 Forbidden`：登录了，但没权限 → 不要重新登录。

混用会让前端做错跳转（把"无权限"变成"登录失效"，用户反复登录）。

### 批量赋值（Mass Assignment）

```java
// 错：请求体直接映射到实体
User user = objectMapper.readValue(body, User.class);
userRepository.save(user);
```

攻击者传 `{"role":"ADMIN"}` 就把自己提权了。要用**明确的请求 DTO**，只接收允许修改的字段：

```java
record UpdateProfileRequest(String nickname, String avatarUrl) {}
```

### 密码与重置

- 存哈希，用 bcrypt/argon2，不要 MD5/SHA1；
- 重置令牌一次性、短有效期、绑定用户，且**不要明文存库**（存哈希）；
- 登录失败提示统一为"用户名或密码错误"，避免枚举账号；
- 登录、重置、验证码接口都要限流。

## 常见误区

### 误区：前端不显示入口，就不会被调用

**你以为**：按钮藏起来就安全了。
**其实**：接口地址可以从 JS 里找到，用 curl 直接调。权限判断必须在服务端。
**怎么验证**：用低权限令牌直接请求管理接口，看是否返回 200。

### 误区：查询出来再判断 owner 也一样

**你以为**：`if (order.userId != current) throw` 也行。
**其实**：逻辑上行，但每个读接口都要复制这段判断，漏一处就是一个洞。把条件写进 SQL 是"默认安全"。
**怎么验证**：搜一遍所有按 id 查询的接口，看有没有没带用户条件的。

### 误区：JWT 无状态所以不用管撤销

**你以为**：令牌到期自然失效。
**其实**：如果有效期是 7 天，被盗后 7 天内都有效。需要短有效期 + 刷新令牌 + 服务端可撤销的会话记录（或黑名单）。
**怎么验证**：登出后拿旧令牌再请求一次，看是否还能用。

## 带走一句

**认证解决"你是谁"，授权解决"这条数据是不是你的"**——后者要写进每一次查询，而不是靠页面隐藏。
