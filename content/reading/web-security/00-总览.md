## 这条线写给谁

写给**写业务代码、但不是安全岗**的人。

你不需要成为渗透测试工程师，但你需要知道：哪些输入绝对不能信、哪些写法一定会出事、上线前必须检查什么。这条线只讲与日常开发直接相关的部分，不讲密码学证明，也不教攻击工具。

## 为什么值得学

因为大部分安全事故不是"被高手攻破"，而是**一个本该做的检查漏了**：

- SQL 用字符串拼接，用户输入直接进了 `WHERE`；
- 前端把用户昵称 `innerHTML` 进页面；
- 删除接口只校验登录，不校验"这条数据是不是你的"；
- 密钥写进了前端构建变量，打包后谁都能看到。

这些问题都有确定的修法，而且成本很低。真正贵的，是出事之后的补救。

## 八关怎么排

分三段：

- **边界（01）**：先建立"谁不可信"的模型，后面每一关都是它的具体化。
- **四类攻击（02–05）**：注入（02）、XSS（03）、CSRF 与 Cookie（04）、认证与越权（05）。每一关的结构都是"攻击怎么发生 → 代码里长什么样 → 怎么修"。
- **工程底线（06–08）**：密钥与日志（06）、依赖与供应链（07）、上线前检查单（08）。

## 一个前提

需要能读 JavaScript / Java（或任意后端语言）与 HTTP 基础。示例以 Node/Spring 风格为主，但结论与语言无关。

**不要在没有授权的系统上做任何测试。** 这条线里的做法只用于你自己负责的代码与明确授权的环境。

## 常见误区

### 误区：安全是安全团队的事

**你以为**：业务开发只管功能，上线前有人扫一遍。
**其实**：扫描器只能发现已知模式；越权、口径错误、密钥泄漏这类问题，只有写代码的人知道"这里本该校验什么"。
**怎么验证**：看一次漏洞报告里的修复项，大部分都落在业务代码的几行里。

### 误区：用了框架就安全了

**你以为**：ORM 防注入、React 防 XSS。
**其实**：ORM 遇到字符串拼接的 `ORDER BY` 仍然会注入；React 的 `dangerouslySetInnerHTML` 是明确留的逃逸口。框架降低的是默认风险，不是取消判断。
**怎么验证**：搜一遍代码里的字符串拼接 SQL 与 `dangerouslySetInnerHTML`。
