> Robert C. Martin · 《代码整洁之道》第 4、5、7 章（2008）· 中译 韩磊，人民邮电出版社

## 先把结论摆出来

这一篇讲的三件事，有一个共同点：**它们都能让代码"看起来"更专业，同时让问题藏得更深。**

- 注释写得好，可能是名字取得差。
- 格式整齐，可能是逻辑被拉成了千层饼。
- 错误处理写全了，可能是把错误吞掉了。

## 一、注释：不是越多越好

书里有一句话很狠：**"注释是一种必要的恶。"**

不是说不要写注释，而是：**注释无法被编译检查，所以它一定会过期。** 代码改了、注释没改，读者信了注释，就出事了。

判断一条注释该不该留，只有一句话：

> **它能说出代码本身说不出来的东西吗？**

**该写的：**

- **为什么这么做**。代码写出"做了什么"，写不出"为什么不用更简单的做法"。这种动机一旦丢失，后来的人会把它改回去。
- **警告**。`// 这里必须保持顺序，先加锁再取数据，反过来在压测里会死锁`。
- **外部约束**。协议里的魔法值、第三方接口的怪癖。
- **法律与出处**。许可证头、算法来源。

**不该写的：**

- **复述代码**。`i++ // i 加一`。
- **过期日志**。`// 2023-05-12 张三修改：增加判断` —— 这在版本控制里，代码里只会误导。
- **被注释掉的代码**。它的下一世是"没人敢删的幽灵"。要留就留，删就删，不要半死不活。

最后一条在这本书里被反复强调：**注释掉的代码是所有代码里最贵的一种**——它需要被读、被维护、被犹豫，而且永远不工作。

## 二、格式：整齐不等于可读

书里的格式规则很具体：变量声明靠近使用处、相关的东西放近、空行分隔概念、一屏能读完一个函数。

但真正值得记的是**它反对的那种整齐**：

```text
// 看起来整齐，实际上读不下去
result = a.b()
    .c()
    .d()
    .e();
```

链式调用排得整整齐齐，可它藏了三层对象、可能四次 IO、可能每次都可能返回 null。

判断格式好坏的标准不是"对齐好看"，而是**读者的眼睛能不能顺着控制流走**。一个有五个嵌套 `if` 的函数，缩进再完美也很难读。

## 三、错误处理：不要返回特殊值

这一章的主张很硬：**用异常，不要用返回码。**

理由是返回码有一个天然的漏洞：**它可以被忽略。** 而语言不会提醒你。一个函数返回 `-1` 表示失败，调用方忘了检查，得到的就是"用户 id 是 -1"这种更远的 bug。

书里给的三条具体规则今天仍然成立：

**一、不给错误返回 null。**
返回 null 是把"没有"这件事推给每个调用方去处理，而总有人忘记判空。返回一个空集合、一个空对象，或者抛异常。

**二、不把 null 传给别人。**
在函数入口就校验，别把空值往里带。

**三、错误信息要说清"怎么办"。**
`operation failed` 是无用的。`连接池已满（上限 20），请检查是否有未关闭的连接` 才让人知道下一步做什么。

### 一条书里没强调、但现在更重要的

**区分"可重试"与"不可重试"**。网络的瞬时错误、限流，重试有意义；参数非法、权限不足，重试只是浪费。很多线上雪崩不是因为没处理错误，而是因为**对不该重试的错误重试了三次**。

第二条值得单独说：**`catch (e) { log.error(e); }` 是最常见的假整洁。** 它让编译通过、让日志里有一行、让代码看起来"处理了错误"——但调用方拿到的是 null，问题会在三层之后以另一个面目出现。

判断标准：**catch 里如果只是记录然后继续，那它等于把异常删了。**

## 边界在哪

- **不许返回 null 在有些语言里做不到**（比如 Java 的很多标准库）。这时正解是把判空集中在一处边界，而不是每条路径都写。
- **注释该不该留，取决于团队是否真的读代码**。一个三个月就扔掉的原型，写满"为什么"是浪费。
- **这一章的年代痕迹最重**：书里的异常与日志例子都假定同步阻塞调用。异步、响应式、协程的上下文里，错误传播是另一套问题。

## 带走一句

整洁的目标不是"看起来规范"，是**让错误无法被忽略**。一条注释、一次格式化、一个 try/catch，如果让问题更难被发现，那它就是脏的。
