> Robert C. Martin · 对《代码整洁之道》常见误用的复核（2008 至今）· 中译 韩磊，人民邮电出版社

## 先把结论摆出来

这本书的建议分三类，混在一起用是它被误用的根源：

| 类别 | 例子 | 该不该照做 |
| --- | --- | --- |
| **几乎总是对的** | 名字说出意图、一个函数只做一件事、不吞异常、不留注释掉的代码 | 照做 |
| **看情况** | 函数要小、参数要少、不用注释 | 看语言、团队、场景 |
| **当成硬指标就是错的** | 函数不超过四行、必须 TDD、每个函数只有一个 return | 不要当指标 |

书本身说得很清楚："这些是经验，不是规则。" 但一层层传下来，很多时候就变成了"代码检查不过就不合并"。

## 教条一：函数四行

书里说"函数应该小于二十行"，传到国内很多团队变成了"四行"。

**代价是什么**：一层一层抽下去，读到第十个函数才看到 `return a + b`。理解一个改动要打开八个文件，而且每个函数的名字都只是上一层的复述。

**正确的判据**：这个函数**作为一个整体**能不能被理解。一个三十行、无分支、从上往下读的解析逻辑，比五个四行的碎函数好读；一个十行但嵌了三层 `if` 的函数，才是真该拆的。

## 教条二：必须 TDD

书里的确把测试放在很高的位置，这套体系（Bob 大叔本人是 TDD 的强力倡导者）也影响了很多团队。

但"写代码必须先写测试"这件事，在这本书里是**方法论主张**，不是从它的成本账里推出来的结论。同一个成本账也能推出别的做法：

- 探索期的代码，先写测试等于给还没定型的设计上锁。
- UI 与集成层，测试的维护成本经常高于收益，这时更该投在端到端的关键路径上。
- 已经有强类型与静态检查的地方，一部分测试要证明的东西已经被编译器证明了。

**可以照做的是那条更弱的主张**：重要逻辑要有能跑的验证。至于先写后写、写多少层，取决于改动的风险与返工成本。

## 教条三：整洁与性能无关

书里几乎不谈性能。这造成一个很常见的冲突现场：**有人按"整洁"把热路径拆成十个小函数、加了三层抽象，然后压测掉了四成吞吐。**

书没有错——绝大多数业务代码里，可读性的收益远大于那点开销。但它没能回答"什么时候不该这么做"。

一条能用的分界线：

- **业务编排层**：按这本书写，越整洁越好。
- **热路径**（每次请求都走、数据量大、有明确延迟预算）：抽象要算成本，必要时接受"不够整洁"。

真正的风险不是慢，而是**为了整洁而做的抽象，让性能问题变得无法定位**——你在十个文件里找不到那一次多余的循环。

## 教条四：注释是失败

这句话有冲击力，但它被引用时经常丢掉后半句：**有些注释是必要的，因为它们说的是代码说不出的东西。**

书里自己列了很多该写的注释：为什么这么做、警告、外部约束、法律信息。

被误用之后的现场是这样：一个三行的 `if` 没写注释，因为"好代码不需要注释"，而那个 `if` 处理的是一个只在闰年最后一天出现的第三方 bug。三年后有人把它删了。

**判断标准**：这条注释能不能被一行更好的代码代替？能，就改代码；不能，就写注释。

## 教条五：这本书能提升团队代码质量

这条最需要冷静。

书里的建议是**个人习惯**。而代码质量是**团队结果**。一个人按这本书写得再漂亮，只要评审不查、风格不统一，整体还是乱的。

真正起作用的是机制：

- 静态检查与格式化（不靠人记规则）
- 评审时的具体问题（"这个变量名说的是什么"），而不是"不够整洁"
- 一份小而明确的团队约定，而不是一本书

指望一本书改变团队，和指望一篇健身文章改变体重是同一类问题。

## 边界在哪

- 这一篇不是在否定这本书。它的前两章（命名、函数）仍然是性价比最高的建议之一。
- "教条"这个词针对的是**把经验法则当硬指标**的用法，不是作者本人的表述。
- 书里的 Java 例子已经明显过时。同样的原则在 Rust、Go、TypeScript 里长得很不一样，照抄例子会走偏。

## 带走一句

把这本书当**提问清单**，不要当**考核标准**：这个名字说出意图了吗？这个函数在做几件事？异常被吞了吗？这三个问题好用；"函数超过四行"不好用。
