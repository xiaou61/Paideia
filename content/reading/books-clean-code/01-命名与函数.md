- **名字应该说出"它是什么、用来干什么"，而不是"它是什么类型"。**
- **函数应该只做一件事，而且它的名字要能准确说出那一件事。**

判断标准很粗暴，但很有效：**如果你读代码时需要停下来想"这个变量是干嘛的"，那次起名就失败了。**

## 命名：五条能立刻用上的规则

**一、说意图，不说类型。**
`list`、`data`、`info`、`temp`、`flag` —— 这些名字等于没起。`expiredOrders`、`retryBudget`、`userCancelledAt` 才是名字。

**二、能发音，才能讨论。**
`genymdhms`（生成时间，年月日时分秒）在脑子里读不出来，于是开会时没人会提它，于是它永远不会被改。

**三、可搜索。**
`7` 和 `e` 在代码里满屏都是。数字常量应该是有名字的，尤其当它代表一个业务含义（而不是循环上限）。

**四、不要编码。**
`strName`、`iCount`、`IUserService` —— 这些前缀是几十年前编译器需要的信息。今天的 IDE 一眼看得出类型，前缀只会让名字变长、让搜索变难。

**五、用业务语言，不用实现语言。**
把 `Map<String, List<Order>>` 叫 `ordersByCustomer`，比叫 `orderMap` 好。前者说的是它在业务上是什么，后者说的是它在内存里怎么存。

最后一条最容易被忽略，但它决定了**别人能不能在不读实现的情况下使用它**。

## 函数：小，而且只做一件事

"只做一件事"这句话太空，书里给了一个可操作的判据：

> **如果你能从这个函数里再抽出一个函数，而且那个函数的名字不是对原函数的复述，那这个函数就做了不止一件事。**

举个例子：

```text
handleOrder(order):
    if order.status == PAID:
        sendEmail(order.user, "paid")
        updateInventory(order)
        writeAuditLog(order)
```

`handleOrder` 做了四件事。抽出来的 `sendEmail` / `updateInventory` / `writeAuditLog` 都不是它的复述——所以它违反了这条规则。

### 参数越少越好

书里的排序是：0 个最好，1 个可以，2 个勉强，3 个就该想办法了，再往上就该包成对象。

原因不是洁癖：**参数是阅读者的记忆负担**。函数体的每一行，你都要记住五个参数分别是谁。

### 命令与查询要分开

一个函数要么**做事**（返回 void，有副作用），要么**回答**（返回数据，无副作用）。不要两样都做。

```text
// 不好：既判断又修改，调用方看不出它有副作用
if user.isActive():
    ...

// 好：分开
if user.isActive():
    ...

user.activate()
```

混合的后果很具体：**调用方会把一个会改状态的调用放进 `if` 条件里**，于是"判断"变成了"执行"，而且只在条件成立时执行——这种 bug 很难看出来。

## 两个常见误解

**误解一：小就是好，越小越好。**
书里说"函数应该小于二十行"，很多人读成"四行"。结果是三层函数调用来做一件简单的事，跳转到第十个文件才看到 `return a + b`。

真正的判据不是行数，是**这一屏能不能读懂这一件事**。一个三十行但线性、无分支的解析函数，比五个四行的碎函数更好读。

**误解二：抽函数是免费的。**
每次抽象都有成本：多一个名字、多一层跳转、多一个需要维护的边界。书里默认"抽出小函数"总是对的，这是它最需要打折扣的地方——**如果那个抽象没有减少理解总量，它就是在增加成本。**

## 边界在哪

- **命名规则是通用的，函数粒度是相对的**。前者换任何语言都成立，后者要看语言习惯——Go 的社区习惯和 Java 完全不同。
- **它默认你在写业务代码**。写一个密集的数据结构算法，把函数拆碎会明显拖慢理解。
- **它不讲性能**。抽函数在多数语言里零成本，但在热路径上、在需要手工内联的环境里不是。

## 带走一句

命名和函数是**唯一不依赖工具、不依赖流程、今天就能改**的两件事。改一个名字的成本是五分钟，收益是之后每个人每次读它省下的时间——这是全项目性价比最高的改动。
