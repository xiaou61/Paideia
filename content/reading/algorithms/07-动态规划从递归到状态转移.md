## 25 件 14 秒，30 件 20 秒没跑完

这是 0-1 背包的暴力递归。每件物品只有拿和不拿两种选择，递归函数的两个参数是「还剩前 i 件可选」和「当前容量」。

```python
import random, time

def build(n, W=200, seed=42):
    rng = random.Random(seed)
    weights = [rng.randint(5, 25) for _ in range(n)]
    values = [rng.randint(5, 30) for _ in range(n)]
    return weights, values, W

def knapsack(weights, values, W):
    calls = 0
    transitions = 0
    def f(i, cap):
        nonlocal calls, transitions
        calls += 1
        if i == 0 or cap == 0:
            return 0
        transitions += 1
        w, v = weights[i - 1], values[i - 1]
        best = f(i - 1, cap)                         # 不拿
        if w <= cap:
            transitions += 1
            best = max(best, f(i - 1, cap - w) + v)  # 拿
        return best
    answer = f(len(weights), W)
    return answer, calls, transitions

weights, values, W = build(25)
t = time.perf_counter()
answer, calls, transitions = knapsack(weights, values, W)
print(answer, calls, transitions, f'{time.perf_counter() - t:.3f}s')
```

```text
351 53446993 53446992 14.137s
```

同机多次运行从 `10.289s` 到 `18.570s`；其中三次是 `10.289s`、`16.433s`、`14.137s`，中位数 `14.137s`。用 `build(30)` 重新生成一组同分布数据后，再用 `subprocess.run(..., timeout=20)` 限时，`20.009s` 后被杀，没有结果。

同一套 `build` 生成的数据，另外三种写法的账：

| 规模 | 暴力递归 | 记忆化 | 二维递推 | 滚动数组 |
| --- | --- | --- | --- | --- |
| n=25 | 53,446,993 次调用 / 14.137 s | 3,190 个非 base 状态 / 2.008 ms | 5,025 个非 base 格 / 1.103 ms | 4,674 次更新 / 0.508 ms |
| n=30 | 超过 20.009 s 未完成 | 4,158 个非 base 状态 / 3.256 ms | 6,030 个非 base 格 / 1.312 ms | 5,607 次更新 / 0.628 ms |

n=25 的四个版本都返回 `351`；n=30 能跑完的三个版本都返回 `374`。快的那三版用 `timeit.repeat(number=1000, repeat=7)` 取最小平均；暴力是三次单跑的中位数。环境是 Windows 11、CPython 3.11.5，CPU 有负载时单次数字会飘。

我原来以为 n 从 25 加到 30 只是多 20% 的计算量，实际是 25 件 14 秒、30 件 20 秒还没结束。多出来的不是 5 件物品本身，是同一批 `(i, cap)` 被反复展开。

## 先数重复：同一对 (i, cap) 被算了 4 次

把规模缩小到 6 件物品、容量 10，保留同一套递归，在函数入口记调用次数和每个 `(i, cap)` 的出现次数：

```python
from collections import Counter

weights = [4, 4, 1, 3, 5, 4]
values  = [7, 5, 8, 6, 4, 9]
W = 10

calls = 0
seen = Counter()

def f(i, cap):
    global calls
    calls += 1
    if i == 0 or cap == 0:
        return 0
    seen[(i, cap)] += 1
    w, v = weights[i - 1], values[i - 1]
    best = f(i - 1, cap)
    if w <= cap:
        best = max(best, f(i - 1, cap - w) + v)
    return best

print(f(len(weights), W), calls, len(seen), max(seen.values()))
print(seen.most_common(4))
```

```text
24 79 32 4
[((1, 2), 4), ((1, 1), 4), ((1, 6), 3), ((1, 5), 3)]
```

79 次调用里只有 32 个不同的非 base 状态，`(1, 2)` 被算了 4 次。它从四条不同路径到达：

```text
f(6,10) → 不拿6 → 不拿5 → 拿4 → 拿3 → 拿2 → f(1,2)
f(6,10) → 不拿6 → 拿5 → 拿4 → 不拿3 → 不拿2 → f(1,2)
f(6,10) → 拿6 → 不拿5 → 不拿4 → 不拿3 → 拿2 → f(1,2)
f(6,10) → 拿6 → 不拿5 → 拿4 → 拿3 → 不拿2 → f(1,2)
```

四条路径的容量变化不同，但最后都落到「只剩第 1 件物品、容量 2」：第 1 件重 4，拿不了，答案都是 0。暴力递归把这个 0 算了四遍。

递归函数的参数只有 `i` 和 `cap`。同一对参数对应的子问题完全一样，跟你怎么走到这里无关。所以状态就是 `(i, cap)`。这就是「怎么想到状态」：先写暴力递归，参数是什么，状态就是什么；如果参数不够决定子问题，再补维度。

对 0-1 背包，状态写成 `dp[i][w]`，一句话读作：只考虑前 i 件物品、容量不超过 w 时的最大价值。

看第 i 件物品（下标 `i-1`）拿不拿：

- 不拿：`dp[i-1][w]`
- 拿：前提 `w >= wi`，`dp[i-1][w-wi] + vi`

两者取较大值。base case 是 `dp[0][w] = 0`（没有物品）和 `dp[i][0] = 0`（容量为零），答案是 `dp[n][W]`。

这套 base 适用于「容量不超过 w」。如果题目改成「恰好装满」，除了 `dp[0][0] = 0`，其余要设负无穷，不能全填 0。

状态、转移、base、遍历顺序、答案位置，这五件事定完，后面四种写法只是执行顺序不同。

## 版本 2：记忆化只算没算过的状态

版本 1 的问题不是递归，是重复。给 `(i, cap)` 加一个字典，第一次算完就存，下次直接取：

```python
weights = [4, 4, 1, 3, 5, 4]
values  = [7, 5, 8, 6, 4, 9]
W = 10

def knapsack_memo(weights, values, W):
    cache = {}
    transitions = 0
    def f(i, cap):
        nonlocal transitions
        if i == 0 or cap == 0:
            return 0
        key = (i, cap)
        if key in cache:
            return cache[key]
        w, v = weights[i - 1], values[i - 1]
        transitions += 1
        best = f(i - 1, cap)
        if w <= cap:
            transitions += 1
            best = max(best, f(i - 1, cap - w) + v)
        cache[key] = best
        return best
    answer = f(len(weights), W)
    return answer, len(cache), transitions

print(knapsack_memo(weights, values, W))
```

```text
(24, 32, 57)
```

小数据上答案仍是 24，但访问从 79 次调用降到 32 个状态，转移从 78 次降到 57 次。

换回 `build(25)` 的 25 件物品，同一函数返回 `(351, 3190, 6249)`，耗时 `2.008 ms`。缓存里只存非 base 状态；base 直接返回，没进字典。

跟版本 1 比，调用从 5,344 万次降到 3,190 个状态。但每个状态第一次访问都要算一次 tuple key 的哈希，递归深度最多 n 层。

## 记忆化和递推不是同一件事

很多人把「DP = 递归 + 记忆化」当成定义。这个说法只描述了其中一种写法。自顶向下记忆化和自底向上递推共用同一套状态与转移，但不是同一件事：

| 维度 | 记忆化（自顶向下） | 二维递推（自底向上） |
| --- | --- | --- |
| 起点 | 从 `(n,W)` 递归下去 | 从第 0 行开始填 |
| 状态 | 只碰从起点可达的 R 个 | 填满 `(n+1)(W+1)` 个 |
| 额外开销 | 递归栈（最多 n 层）、函数调用、tuple 哈希 | 数组寻址；可能填不可达状态 |
| 空间 | R 个缓存项 + 栈 | 整张表，可压到一行 |
| 方案回溯 | 要另存选择或重算 | 整张表在，直接比较前后行 |
| 适合 | 状态稀疏、依赖顺序不好定 | 状态稠密、要低常数、要回溯 |

在这组 n=25 数据上，记忆化只碰了 3,190 个状态，二维表写了 5,025 个非 base 格；记忆化少算 1,835 个状态，但耗时 `2.008 ms`，二维表 `1.103 ms`。少算的状态没有抵消递归调用和字典哈希的开销。

n=30 同样：4,158 对 6,030 个状态，`3.256 ms` 对 `1.312 ms`。

这不是说记忆化更差。它只是把开销换了个地方：状态稀疏时，少算的状态能赢回来；状态稠密时，递推的数组寻址更便宜。

状态稀疏的例子：所有重量都是 100 的倍数、`W=10000`，可达容量只有 101 个；记忆化在每个 i 上只碰这 101 个容量，二维表仍要填 10001 列。

递归栈也是成本。0-1 背包的递归深度最多 n 层；CPython 3.11 默认递归上限 1000，n=2000 时记忆化会先撞上限。要么调 `sys.setrecursionlimit`，要么改递推。

要打印方案时，二维表保留每一行，回溯时比较 `dp[i][w]` 和 `dp[i-1][w]` 就能知道第 i 件拿没拿；记忆化要另存每个状态的选择；滚动数组已经把旧行扔了。

## 版本 3：把递归倒过来填表

二维递推从第 0 行开始，按 i 从小到大、w 从 0 到 W 填：

```python
weights = [4, 4, 1, 3, 5, 4]
values  = [7, 5, 8, 6, 4, 9]
W = 10

def knapsack_table(weights, values, W):
    n = len(weights)
    dp = [[0] * (W + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        wi, vi = weights[i - 1], values[i - 1]
        for w in range(W + 1):
            dp[i][w] = dp[i - 1][w]
            if w >= wi:
                dp[i][w] = max(dp[i][w], dp[i - 1][w - wi] + vi)
    return dp[n][W]

print(knapsack_table(weights, values, W))
```

```text
24
```

小数据答案 24。换回 `build(25)`，答案 351；账是 5,025 个非 base 写入格、9,699 次转移、`1.103 ms`。

`dp[i][w]` 只读第 `i-1` 行，写的是第 `i` 行，所以行内 w 正序倒序都不影响正确性。这跟一维版必须倒序是两件事。

代价是即使某些容量不可达，也要填。n=25、W=200 是 5,025 个写入格；算上第 0 行是 5,226 个状态。n=2000、W=100000 就是约 2 亿格，光指针按 8 字节算就约 1.6GB，还没算 int 对象和行对象。

## 版本 4：只留上一行

第 i 行只依赖第 i-1 行，算完第 i 行后第 i-1 行不再需要，所以可以把两行合成一个数组：

```python
weights = [4, 4, 1, 3, 5, 4]
values  = [7, 5, 8, 6, 4, 9]
W = 10

def knapsack_rolling(weights, values, W):
    dp = [0] * (W + 1)
    for wi, vi in zip(weights, values):
        for w in range(W, wi - 1, -1):
            dp[w] = max(dp[w], dp[w - wi] + vi)
    return dp[W]

print(knapsack_rolling(weights, values, W))
```

```text
24
```

小数据答案 24。换回 `build(25)`，答案 351；数组只有 201 个元素，但一共被更新 4,674 次，`4,674` 次 max 比较，耗时 `0.508 ms`。时间仍是 O(nW)，空间降到 O(W)。

为什么能压：`dp[w]` 在更新前存的是上一行的值，更新后存的是当前行的值。只要转移只读第 `i-1` 行，就不需要保留更早的行。

为什么必须倒序：更新 `dp[w]` 时读 `dp[w-wi]`。如果 w 从小到大，`w-wi` 可能已经在本轮被更新过，读到的是第 i 行的值，不是第 i-1 行。倒序保证 `w-wi < w` 还没在本轮被碰过。

什么时候不能压：转移依赖前面任意多个状态，或者还要输出方案。LIS 的 `dp[i]` 要看所有 `j < i`，不能压成一个滚动变量；要打印方案，得保留每一行或另存父指针。爬楼梯只依赖前两个状态，两个变量就够；编辑距离依赖上、左、左上，压成一行时要先保存左上角。

## 压错空间：正序把 0-1 背包变成完全背包

把 A（重 2、值 3）和 B（重 3、值 4）放进容量 6 的背包，每件最多一次，最优是 A+B，价值 7。现在只改遍历方向：

```python
def knapsack_wrong(weights, values, W):
    dp = [0] * (W + 1)
    for wi, vi in zip(weights, values):
        for w in range(wi, W + 1):       # 正序：错
            dp[w] = max(dp[w], dp[w - wi] + vi)
    return dp[W]

def knapsack_right(weights, values, W):
    dp = [0] * (W + 1)
    for wi, vi in zip(weights, values):
        for w in range(W, wi - 1, -1):   # 倒序：对
            dp[w] = max(dp[w], dp[w - wi] + vi)
    return dp[W]

weights = [2, 3]
values = [3, 4]
W = 6
print(knapsack_wrong(weights, values, W))
print(knapsack_right(weights, values, W))
```

```text
9
7
```

正序输出 9，因为它把 A 拿了三次：重量 2×3=6，价值 3×3=9。倒序输出 7，才是 0-1 背包。

看数组更清楚：

```text
正序 dp: [0, 0, 3, 4, 6, 7, 9]
倒序 dp: [0, 0, 3, 4, 4, 7, 7]
```

正序处理 A 时，`dp[2]=3`；到 `w=4` 读 `dp[2]` 已经是本轮的值，于是 `dp[4]=6`；到 `w=6` 读 `dp[4]=6`，得到 9。倒序时 `dp[4]` 读到的 `dp[2]` 还是 0，A 只用一次。

这不是答案偏大一点，是题意变了：同一份代码算的是完全背包。这种错不会报错，只会多算。

## 复杂度：状态数 × 每个状态的转移代价

DP 的时间先数两个量：有多少个状态，每个状态要做多少次转移。

| 问题 | 状态数 | 每个状态的转移 | 时间 |
| --- | --- | --- | --- |
| 0-1 背包二维 | `(n+1)(W+1)` | 2 | O(nW) |
| LIS 朴素 | n | 最多 n | O(n²) |
| 编辑距离 | `(m+1)(n+1)` | 3 | O(mn) |

这里的 n 是物品件数，W 是背包容量（一个数值，不是物品件数），m 是第一个字符串的长度。`O(nW)` 不是 `O(n)`；W 翻倍，表大一倍。

记忆化是另一条账：R 个可达状态，每个状态最多 2 次转移，时间是 O(R)，空间是 O(R+n)，n 是递归栈深度。R 可能远小于 nW，也可能接近 nW；不要把它写成 O(n) 或无条件 O(nW)。

`O(nW)` 还是伪多项式：W 是数值，输入里只占 `log W` 位；W 翻倍，输入只多一位，时间却翻倍。W=10⁹ 时，nW 的表开不出来。

我一般先估状态数：超过 10⁷ 就先算内存，再决定要不要换算法或压缩。状态数本身就是很多题的天花板。

## 拿到新题，先过这三条

不是看到「最大」「最小」「方案数」就上 DP。先过三条，任何一条不过就换思路。

**最优子结构**：大问题的最优解能由子问题的最优解拼出来，而且拼接不会破坏子问题的约束。

反例是无权图的最长简单路径，边为 A-B、A-D、B-D、B-C、D-C。A 到 B 的最长简单路径是 A-D-C-B（3 条边），B 到 C 的最长简单路径是 B-A-D-C（3 条边）；拼起来是 A-D-C-B-A-D-C，A、D、C 重复，不是简单路径。A 到 C 的真实最长简单路径是 3 条边（A-B-D-C 或 A-D-B-C）。子问题的最优解不能直接拼，最优子结构不成立。

**重叠子问题**：同一个子问题在递归树里出现多次。

反例是归并排序。对 `[5,2,4,1]`，左半 `[5,2]`、右半 `[4,1]` 各自只出现一次，递归树没有重复节点。加 memo 不会命中，只会多出字典查找的开销。一次二分查找里也一样，每个 mid 只访问一次。

**无后效性**：状态一旦确定，未来只依赖这个状态，不依赖怎么走到这里。

反例是股票买卖只定义 `dp[i]` 为前 i 天的最大利润。到第 i+1 天要决定卖不卖，必须知道第 i 天结束时手里有没有股票；两个历史可能利润相同，但一个持股、一个空仓，未来不同。只记最大利润把这两种情况混在一起，状态不够。正确做法是加一维：`dp[i][0]` 空仓、`dp[i][1]` 持股。

三条都过了，再看状态规模。`n=2000, W=100000` 的二维表是约 2 亿格，光指针约 1.6GB；这时候不是「DP 对不对」，是「表开不开得出来」。先算状态数，再写转移。
