## 92 个解，打印出来是 92 张空棋盘

8 皇后：8×8 棋盘放 8 个皇后，任意两个不能同行、同列、同对角线。第一版写完是这样，剪枝已经写对了，问题只在存结果那一行：

```python
def solve(n):
    out = []
    board = [['.'] * n for _ in range(n)]
    col, d1, d2 = [False] * n, [False] * (2 * n), [False] * (2 * n)

    def dfs(row):
        if row == n:
            out.append(board)             # 存的是引用
            return
        for c in range(n):
            if col[c] or d1[row - c + n] or d2[row + c]:
                continue
            col[c] = d1[row - c + n] = d2[row + c] = True
            board[row][c] = 'Q'
            dfs(row + 1)
            board[row][c] = '.'           # 回退：把这一行的皇后擦掉
            col[c] = d1[row - c + n] = d2[row + c] = False

    dfs(0)
    return out

bad = solve(8)
print(len(bad), len({id(x) for x in bad}))
print(''.join(bad[0][0]))
```

```text
92 1
........
```

`92 1` 是关键：92 条结果，只有 1 个对象，内容去重后也只有 1 种。`board[row][c] = '.'` 这句回退擦的正是结果里存的同一块棋盘，所以 92 条最后都指向那张空盘。

我原来以为「解出来了就是解出来了」，实际是：回溯的分支一边在产出结果，一边在把状态擦回原样，两个动作共用同一个对象。把这一行换成拷贝，或者干脆不存棋盘、存每行的列号：

```python
out.append([r[:] for r in board])   # 92 条，92 种内容
out.append(tuple(cols))             # 8 个整数（dfs 里维护的每行列号）
```

```text
92 92
Q.......
....Q...
.......Q
.....Q..
..Q.....
......Q.
.Q......
...Q....
```

第一行是字典序上第一个解 `[0, 4, 7, 5, 2, 6, 1, 3]`。存棋盘的好处是能直接打印，代价是每条解 64 个字符、每层都要拷一次；存列号的代价是要多写一个画棋盘的函数。92 条解，两种存法的条数一样。

## 先数节点：16,777,216 → 109,601 → 2,057

回溯的骨架就是递归：每层做一个选择，往下递归，回来时撤销。省不省时间，全看「选到一半发现不可能」时你敢不敢提前返回。先给三档写法记同一笔账，目标都是「8 皇后有多少个解」。

第一档，最笨的：把 8 行的列号所有组合列出来（`itertools.product` 就是 8 层嵌套 for），每个组合最后整体验一次。

```python
import itertools, time

def brute(n):
    nodes = sols = 0
    for combo in itertools.product(range(n), repeat=n):
        nodes += 1
        ok = True
        for i in range(n):
            for j in range(i + 1, n):
                if combo[i] == combo[j] or abs(combo[i] - combo[j]) == j - i:
                    ok = False
                    break
            if not ok:
                break
        if ok:
            sols += 1
    return nodes, sols

for n in (7, 8):
    ts = []
    for _ in range(3):
        t = time.perf_counter()
        nodes, sols = brute(n)
        ts.append(time.perf_counter() - t)
    ts.sort()
    print(n, nodes, sols, f'{ts[1]:.2f}s')
```

```text
7 823543 40 0.37s
8 16777216 92 8.84s
```

这是其中一轮的输出。同一台机器上多跑几次：n=7 落在 0.33–0.51 s，n=8 落在 8.8–11.7 s。差 30% 来自别的进程在抢 CPU，节点数是精确的。

第二档和第三档共用一个函数，`with_diag` 决定要不要在「放下去之前」就查两条对角线：

```python
import time

def search(n, with_diag):
    nodes = leaves = valid = 0
    used = [False] * n
    d1 = [False] * (2 * n)
    d2 = [False] * (2 * n)
    cols = [0] * n

    def dfs(row):
        nonlocal nodes, leaves, valid
        nodes += 1
        if row == n:
            leaves += 1
            if with_diag or all(abs(cols[i] - cols[j]) != j - i
                                for i in range(n) for j in range(i + 1, n)):
                valid += 1
            return
        for c in range(n):
            if used[c]:
                continue
            if with_diag and (d1[row - c + n] or d2[row + c]):
                continue
            used[c] = True
            if with_diag:
                d1[row - c + n] = True
                d2[row + c] = True
            cols[row] = c
            dfs(row + 1)
            used[c] = False
            if with_diag:
                d1[row - c + n] = False
                d2[row + c] = False

    dfs(0)
    return nodes, leaves, valid

for flag in (False, True):
    ts = []
    for _ in range(3):
        t = time.perf_counter()
        r = search(8, flag)
        ts.append(time.perf_counter() - t)
    ts.sort()
    print(flag, r, f'{ts[1]*1000:.1f}ms')
```

```text
False (109601, 40320, 92) 75.2ms
True (2057, 92, 92) 1.0ms
```

口径：节点数 = 进入 `dfs` 的次数（含根），叶子 = 走到第 8 行的次数；`with_diag=False` 的「真合法」是在叶子上补验了一遍对角线，所以它那个 92 是验出来的，不是剪出来的。耗时是 3 次的中位数，同一份代码多跑几轮，`False` 落在 75–114 ms、`True` 落在 1.0–1.6 ms——节点数不会变，毫秒数会动，所以表里给区间。

| 版本 | 节点数 | 叶子数 | 其中真解 | n=8 耗时 |
| --- | --- | --- | --- | --- |
| 全枚举，最后验一次 | 16,777,216 | 16,777,216 | 92 | 8.8–11.7 s |
| 只保证列不重复 | 109,601 | 40,320 | 92 | 75–114 ms |
| 列 + 两条对角线 | 2,057 | 92 | 92 | 1.0–1.6 ms |

只保证列不重复，把节点从 1677 万砍到 10.9 万（153 倍），但 40,320 个叶子里只有 92 个是真解——438 个候选里挑 1 个。加上对角线之后节点变成 2,057，正好是上一档的 1/53（这个比值精确）；同轮耗时从 75.2 ms 降到 1.0 ms，也是约 1/75。

每把刀砍掉的是整棵子树，不是一个叶子：列不重复砍掉「同一列放两个」的所有走法；两条对角线各砍掉「同一条斜线上放两个」。所以看节点数比看叶子数有用——叶子只是最后一层，节点才是你真正执行的次数。

## 少一条对角线，92 变成 2,113

把两条对角线的判断写成同一件事（只查 `row - c`，不查 `row + c`），程序不报错，返回值还变多了：

```python
def search_one_diag(n):
    sols = 0
    col, d1 = [False] * n, [False] * (2 * n)

    def dfs(row):
        nonlocal sols
        if row == n:
            sols += 1
            return
        for c in range(n):
            if col[c] or d1[row - c + n]:
                continue
            col[c] = d1[row - c + n] = True
            dfs(row + 1)
            col[c] = d1[row - c + n] = False

    dfs(0)
    return sols

for n in (6, 7, 8):
    print(n, search_one_diag(n))
```

```text
6 83
7 405
8 2113
```

对照真值 4 / 40 / 92：8 皇后这里返回 2,113，多出 2,021 条，是 92 的 23 倍，每一条都能打印出一张有皇后互相攻击的棋盘。这跟「少检查一条规则」的直觉相反——错误方向是解变多，不是变少，而且不抛异常，只在结果条数上体现。

所以「剪枝」得跟「少枚举一点」分开：

- 少枚举：只保证列不重复，剩下的在叶子上验——这是把问题改小，正确性靠叶子上的检查兜着；
- 剪枝：在进入递归之前就证明「从这个状态往下，不可能再有合法解」，砍掉的整棵子树本来也是错的。

第二句要能写成一句话才允许落笔。只保证列不重复那句话写不出来：列不冲突不代表不斜着攻击。写不出来就先别剪。

| 症状 | 先看哪 | 这篇的对照数字 |
| --- | --- | --- |
| 条数对，内容全一样或全空 | `append` 前有没有拷贝 | 92 条、1 种内容 |
| 解比预期多，多出来的还互相攻击 | 剪枝覆盖了几种冲突 | 少一条对角线：2,113 对 92 |
| 解比预期少 | 撤销与加入是否一一对应 | 首列只取前半：46 对 92 |
| 只想要一个解，却等了很久 | 找到时有没有立即 return | 114 对 13 个节点 |
| `RecursionError` | 递归深度是不是等于 n | 默认上限 1000 |

## 同样 2,057 个节点，扫行慢一个数量级

冲突检查有两种写法：三个布尔数组 O(1) 查，或者每放一个就扫一遍前面已放的行。

```python
def by_scan(n):
    sols = 0
    cols = []

    def dfs(row):
        nonlocal sols
        if row == n:
            sols += 1
            return
        for c in range(n):
            if any(cols[r] == c or abs(cols[r] - c) == row - r for r in range(row)):
                continue
            cols.append(c)
            dfs(row + 1)
            cols.pop()

    dfs(0)
    return sols

import time
for n in (8, 9):
    ts = []
    for _ in range(3):
        t = time.perf_counter()
        sols = by_scan(n)
        ts.append(time.perf_counter() - t)
    ts.sort()
    print(n, sols, f'{ts[1]*1000:.2f}ms')
```

```text
8 92 12.15ms
9 352 61.82ms
```

两种写法访问的节点数完全一样（n=8 都是 2,057，n=9 都是 8,394，解也都是 92 和 352），耗时差一个数量级：

| 写法 | n=8 节点 | n=8 耗时 | n=9 节点 | n=9 耗时 |
| --- | --- | --- | --- | --- |
| 三个布尔数组 | 2,057 | 1.0–1.6 ms | 8,394 | 6.57 ms |
| 每次扫已放的行 | 2,057 | 12–19 ms | 8,394 | 62–78 ms |

倍数要在同一轮里量：把两种写法放进同一个脚本跑，得到 1.35 ms 对 16.14 ms（12.0 倍）、6.57 ms 对 73.53 ms（11.2 倍）。跨轮直接拿表里的两头相除会得到 8 倍或 16 倍，那不是写法变了，是两个绝对值都在飘。节点数是精确的，耗时只保证量级。

所以估时间要乘两个数：**节点数 × 每个节点做多少事**。剪枝管第一个数，数据结构管第二个数。只优化其中一个，另一个会把你省下的时间吃掉。

## 只要一个解时，顺序才有意义

找全部解时，把列从 0 试到 7 还是从 7 试到 0，节点数一样——树里每个前缀都会被走到，顺序只改变先走哪一枝：

```text
[0,1,2,3,4,5,6,7] -> 2057
[7,6,5,4,3,2,1,0] -> 2057
[3,4,2,5,1,6,0,7] -> 2057
```

但只要「找到一个就返回」，顺序立刻变成主要变量：

```python
def first_solution_nodes(n, order):
    nodes = 0
    col, d1, d2 = [False] * n, [False] * (2 * n), [False] * (2 * n)

    def dfs(row):
        nonlocal nodes
        nodes += 1
        if row == n:
            return True
        for c in order:
            if col[c] or d1[row - c + n] or d2[row + c]:
                continue
            col[c] = d1[row - c + n] = d2[row + c] = True
            if dfs(row + 1):
                return True
            col[c] = d1[row - c + n] = d2[row + c] = False
        return False

    dfs(0)
    return nodes

for order in ([0, 1, 2, 3, 4, 5, 6, 7],
              [3, 4, 2, 5, 1, 6, 0, 7],
              [1, 2, 3, 4, 5, 6, 7, 0]):
    print(order, first_solution_nodes(8, order))
```

```text
(0, 1, 2, 3, 4, 5, 6, 7) 114
(3, 4, 2, 5, 1, 6, 0, 7) 15
(1, 2, 3, 4, 5, 6, 7, 0) 13
```

114 到 13 是 8.8 倍，只改了循环里列的访问顺序。这两个顺序是我手挑的，不是通用启发式——真要找规律，得对一批 n 做统计，这一篇没做。能确定的只有机制：顺序不改变树的大小，只改变你「在第几个节点撞到第一个解」。

带上下界的剪枝也是同一个机制：先拿到一个不太差的解，用它当上界，后面超过上界的分支直接砍。8 皇后没有目标函数，这套用不上，所以这篇只给机制，不给例子。

## 92 个解只有 12 个本质解

把旋转、镜像算作同一种，8 皇后剩 12 种。这不是「92 ÷ 8 = 11.5，取整成 12」：

```text
n=8  92 个解  12 组  每组大小 [4, 8, 8, 8, 8, 8, 8, 8, 8, 8, 8, 8]
```

11 组各 8 个，1 组只有 4 个——那个解在 180° 旋转下和自己重合，轨道大小减半。所以 11×8 + 4 = 92。直接除会得到 11.5，四舍五入到 12 只是碰巧对。

只砍镜像（固定第一枚皇后只放在前四列）能得到 46 个解，正好一半；节点从 2,057 降到 1,029。但奇数 n 这条不成立：

```text
n=8  92 个解，首列在前半的 46 个（正好一半）
n=9  352 个解，首列在前半的 203 个（不是一半）
```

n=9 有一个中间列，落在中间列上的 54 个解在镜像下还是自己，配不成对。所以「对折再乘 2」只在偶数 n 上成立；奇数 n 要把中间列单独处理，否则要么漏解、要么算重。

这块最容易踩的是：剪掉一半之后忘了补回来。固定首列只取前半，结果只有 46 条；镜像补回来才是 92 条。少了一半不报错，只是数据不对。

## 规模表：n 每加 1，节点涨 4–6 倍

同一份 `search(n, with_diag=True)`，n 从 4 跑到 13：

| n | 节点数 | 解的数量 | 耗时（中位） |
| --- | --- | --- | --- |
| 4 | 17 | 2 | 0.01 ms |
| 5 | 54 | 10 | 0.03 ms |
| 6 | 153 | 4 | 0.10 ms |
| 7 | 552 | 40 | 0.39 ms |
| 8 | 2,057 | 92 | 1.57 ms |
| 9 | 8,394 | 352 | 6.73 ms |
| 10 | 35,539 | 724 | 29.21 ms |
| 11 | 166,926 | 2,680 | 144.44 ms |
| 12 | 856,189 | 14,200 | 772–777 ms |
| 13 | 4,674,890 | 73,712 | 4.32–4.59 s |

n 每加 1，节点涨 4.1–5.5 倍，耗时跟得差不多（n=13 是 n=12 的 5.5 倍节点、5.6 倍时间）。解的数量完全跟不上：n=13 有 7.3 万个解、467 万个节点，平均每个解要访问 63 个节点。所以「解不多」不等于「不用搜」——开销在中间层，不在结果上。

递归深度就是 n。CPython 3.11.5 里 `sys.getrecursionlimit()` 返回 1000（实测），这是 CPython 的实现值，不是语言规定；超过就抛：

```python
import sys
sys.setrecursionlimit(8)

def f(n):
    return f(n + 1)

try:
    f(0)
except RecursionError as e:
    print(type(e).__name__ + ':', e)
```

```text
RecursionError: maximum recursion depth exceeded
```

n=1000 的棋盘需要 1000 层递归，光这一条就顶到上限了；`sys.setrecursionlimit` 能把天花板抬高，但每层栈帧的内存还是你付。

## 还差的

- 只在这台机器上测了 CPython 3.11.5 / Windows 11，没测 PyPy，也没换 CPU 复测。耗时是 3 次中位数，别的进程抢 CPU 时能差 20%；节点数不受影响。
- n=1000 那一跑 300 秒没结束，所以「撞上递归上限那一刻」没有实测，只给默认上限 1000 和报错原文（用 `setrecursionlimit(8)` 复现）。改成显式栈之后的开销也没测。
- 带重复元素的组合去重（排序后是 `i > start` 还是 `i > 0`）没写进去：棋盘没有重复元素，这套判据在 8 皇后里没有可跑的例子。
- 分支限界只在「只要一个解」那节说了机制，没有实测。N 皇后没有目标函数，塞不进上界/下界的框架。
- 位运算剪枝（用整数位表示列和对角线）没写也没测。它能省掉数组下标访问，代价是可读性，值不值我没量。
