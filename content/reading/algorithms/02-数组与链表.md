## 我把 list 换成了手写链表，慢了 200 多倍

```text
[1] n=50000 保序插入 2000 次
    链: 走链找位置   1710.7 us/次  (平均 29728 个节点)
    list+bisect        6.27 us/次  (273x)
```

上面这行数字来自我自己练手项目里的一个组件：一张 5 万条的内存事件表，事件带时间戳，插进来要落到正确的顺序位置上，撤回时按位置删掉，界面按时间顺序整表扫一遍。第一版就是 `list` + `bisect.insort`。

后来我不甘心：「中间插入是 O(n)，链表是 O(1)」，这不是明摆着的优化空间么。于是手写了一个双向链表，插入时从头走到位置，接上两个指针。数据没换、插入次数没换（2000 条新事件），结果是这套链表慢了两个数量级。

条件写在这，免得你拿这组数字去别处用：CPython 3.11.5 / Windows 10 22H2 / AMD64，每组取 5 轮最快的一次，同一脚本连跑 5 次。链的耗时在 1711–2230 µs 之间摆，`list` 在 5.8–8.9 µs 之间，比值 205–343 倍。所以下面所有倍数我都给区间，不编小数。

插个必须交代的前提：这 5 万条是我自己造的数，不是生产数据。但「保序插入」这种形状本身很常见——按时间排序的事件流、排行榜、按分数插队的任务队列，都是它。

## O(1) 兑现的前提：手里得有那个节点

教科书说「链表中间插入 O(1)」，这句话没写错，但它省掉了一个从句。

插入分两步：**找到位置** 和 **把节点接进去**。接进去那一下，链表确实是 O(1)，只要手里已经攥着那个前驱节点：

```text
[2] n=50000 中间插入 2000 次
    链: 已持有节点   0.199–0.298 us/次
    list: 按下标     5.85–12.55 us/次
```

0.2 微秒——这就是教科书里那个 O(1) 的真身，比 `list` 快 20–60 倍。**但这组数字不可比**：`list` 那边没有「持有位置」这回事，每次都得按新的下标重新搬半张表；而链表这边我是一直贴着同一个 `mid` 节点插的。真要比较，得把「找位置」一起算进去。

问题就出在找位置上。

`list` 找位置能用 `bisect`：50000 个元素，16 次比较，比较在 C 层做；找到之后把后半段指针往后挪一格，也是 C 层的循环。CPython 3.11 分支的 `Objects/listobject.c` 里 `ins1()` 核心就三行：

```text
    items = self->ob_item;
    for (i = n; --i >= where; )
        items[i+1] = items[i];
```

一个 8 字节一个 8 字节地复制指针，顺序读、顺序写。

链表找位置只能从头走：它没有下标这个入口，跳不过去。我这一组平均每次要走 29,728 个节点，每一步是 Python 层的属性读取、比较、分支。按遍历时量到的 77 ns/节点（遍历那组还多做了求和，纯走链会便宜些）折算，29,728 步就是 2.3 ms 上下——和实测的 1.7–2.2 ms 对得上，说明这 200 倍里几乎全是「走链」这一项，跟插入动作本身没关系。

同一件事，一边是 16 次 C 层比较加一个 C 循环，一边是 3 万次解释器循环。O(同量级) 的记号看不见这个差，而它才是决定性的。

## list 的 O(n) 到底搬了多少字节

要把这个判断做对，得知道 `list` 的 O(n) 到底在动什么。答案很朴素：动的是指针，不是元素。

`sys.getsizeof` 能直接看到容量：

```text
追加后长度:  1    5    9   17   25   33   41   53
字节:       88  120  184  248  312  376  472  568
```

空 `list` 是 56 字节（对象头），之后每多一个槽位 8 字节。这串跳变点跟 CPython 源头 `list_resize()` 注释里写死的容量序列 `0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ...` 逐项对得上——注意这是 **CPython 3.11 的实现细节，不是语言保证**，PyPy 的 list 布局就不是这个数。

所以 `list` 的「搬 5 万个元素」其实是搬 5 万个指针的事，400 KB 数据，内存带宽层面并不贵；贵的是次数。

扩容同理。100 万次 `append`：

```text
append 1e6: 扩容 86 次, 复制指针 8,445,096 个, 最终容量 1,056,084
```

平均每追加一次复制 8.45 个指针；扩容 86 次，但其中只有 20 次落在「10 万到 100 万」这个区间，容量从 100,116 涨到 1,056,084，翻了 10.55 倍——反推每次扩容乘 1.125。几何增长的复制总量收敛在 `r/(r-1) ≈ 9` 倍 n，这就是「均摊 O(1)」的来源，也是那 8.45 的来历。

**代价是摊平的，尖峰不是**：86 次扩容里每一次都是当场的 O(n) 复制。你要是有 P99 尾延迟的指标，那一次就是那一次。

| 你调的东西 | 影响的量 | 我这次量到的 |
| --- | --- | --- |
| 预分配容量 | 中间那 86 次扩容是否发生 | 1e6 次追加 0.052–0.062 s；`[None]*1e6` 再按下标赋值 0.030–0.032 s |
| 元素个数 | 每次 `insert` 搬多少个指针 | 5 万元素中间插入 5.85–12.55 µs/次 |
| 从头部还是尾部插 | 搬全部还是一格不搬 | `insert(0)` 20.6–42.6 µs/次；`append` 只写一格 |
| 删掉多少 | 会不会真的把内存还回去 | 1e6 删到 60 万：`getsizeof` 仍是 8,000,056；删到 49 万才缩到 4,410,104 |

最后一行值得单独说：`list_resize()` 里有一句跳过条件，长度掉到当前容量一半以下才真去 `realloc`。所以「我删了 40 万个元素，内存怎么没降」不是 bug，是设计。

## 缓存这件事，我量到了什么、没量到什么

`list` 的指针数组是连续的，节点链不是。这句话在 C 和 Java 里可以直接量成缓存未命中率，在 CPython 里我只能量到它的影子。

同一句 `a[i]`，随机读 10 万次，只改 `n`：

```text
n=1,000      指针数组 0.008 MB   24–30 ns/次
n=1,000,000  指针数组 8.000 MB  183–238 ns/次
```

同一批下标，只改访问顺序（`sorted(idx)` 对 `random sample`，n=100 万）：

```text
按大小顺序 44–56 ns/次  /  乱序 288–325 ns/次  (5.7–7.4x)
```

代码一模一样、访问次数一模一样，只是工作集从 8 KB 涨到 8 MB、访问顺序从顺序变乱序，单次耗时涨了 5.7–7.4 倍。这部分是内存层次结构在起作用，跟算法复杂度没关系。至于缓存行是多少字节——x86-64 上一般是 64 字节，这是硬件规格，不是我量的。

但**别把这条当成「数组比链表快几倍」的论据**。遍历 5 万个元素求和：

```text
list 18.2–39.2 ns/元素   节点链 77.3–144.2 ns/节点   (2–4x)
```

只有 2–4 倍，因为 CPython 每走一步都要过一遍解释器，缓存的好处被摊薄了。上面那个 200 多倍的差距，主因是「Python 层循环 vs C 层循环」，缓存是第二层差异，两者别混着讲。

内存上也有一个反直觉的数：

```text
list(range(200000))  40.0 B/元素
200000 个 Node 链    96.1 B/元素
```

「链表按需分配所以省内存」在这里直接反了。节点本身 56 字节（三个槽的 `__slots__` 类），值（int 对象 28 字节）+ 列表里那个指向节点的指针再算进去，就是 96 字节。而 `list` 那边是 8 字节指针 + 28 字节 int。`getsizeof` 还有个坑：它只报指针数组，不看元素——`[0]*1000` 是 8056 字节，同样 1000 个元素的列表推导式是 8856 字节，差的那 800 字节是预留容量，不是元素变大。

## 症状 → 先看哪

| 症状 | 先看哪 | 我这次量到的 |
| --- | --- | --- |
| 循环里 `insert(0, x)` 或 `pop(0)` | 改 `append` + `reverse`，或换 `deque` | n=10 万头插 2000 次：20.6–42.6 µs/次 → `deque.appendleft` 0.35–0.65 µs/次 |
| 保序插入，数据量到万级，想换链表 | 别换，留在 `list` + `bisect.insort` | 5 万条：链 1711–2230 µs/次 对 `list` 5.8–8.9 µs/次 |
| 遍历过程中就地插入/删除，且手里已有节点 | 这才是链表真正兑现 O(1) 的地方 | 已持有节点插入 0.20–0.30 µs/次 |
| `append` 偶发卡顿，均值正常但 P99 难看 | 扩容；预分配 | 1e6 次追加触发 86 次扩容 |
| 内存吃紧，放了几十万个小对象 | 先算每元素字节，别假设链表省 | 40.0 B 对 96.1 B |
| 想用 `deque` 换掉 `list` 提速 | 看还要不要按下标取 | n=100 万随机取：`deque` 17.5 µs/次，`list` 0.051 µs/次 |

倒数第二行和最后一行是同一个决定的两面：`deque` 用环形分块结构换掉了头插的搬移，代价是按下标访问退化成走链。换句话说，**你只是把「走链」这件事从插入挪到了读取**——如果那段代码两种都要，就没有免费的解。

## 跑一遍

下面这段能直接粘贴运行，输出就是上面表格里那几行（数字会有小幅浮动）：

```python
import sys, time, random, bisect
random.seed(1)

# 1) 扩容：数 100 万次 append 触发了多少次 realloc
l, last, realloc, copied, prev_alloc = [], sys.getsizeof([]), 0, 0, 0
for i in range(1_000_000):
    l.append(i)
    s = sys.getsizeof(l)
    if s != last:
        alloc = (s - 56) // 8
        realloc += 1
        copied += prev_alloc
        prev_alloc, last = alloc, s
print(f"append 1e6: 扩容 {realloc} 次, 复制指针 {copied:,} 个, 最终容量 {prev_alloc:,}")

# 2) sys.getsizeof 的跳变点
l, last, pts = [], sys.getsizeof([]), []
for i in range(60):
    l.append(i)
    if sys.getsizeof(l) != last:
        last = sys.getsizeof(l)
        pts.append(f"{len(l)}->{last}")
print("sizeof:", " ".join(pts))

# 3) 保序插入：list+bisect vs 手写链表走链找位置
class Node:
    __slots__ = ("val", "prev", "nxt")
    def __init__(self, val, prev=None, nxt=None):
        self.val, self.prev, self.nxt = val, prev, nxt

N, M = 20_000, 400
vals = sorted(random.sample(range(10 * N), N))
new = [random.randrange(10 * N) for _ in range(M)]
head = Node(vals[0])
prev = head
for v in vals[1:]:
    prev.nxt = Node(v, prev)
    prev = prev.nxt

def chain():
    for v in new:
        p = head
        while p is not None and p.val <= v:
            p = p.nxt
        nd = Node(v, p.prev if p else None, p)
        if p is None:
            continue          # 只量走链的开销，尾部追加不参与
        if p.prev:
            p.prev.nxt = nd
        p.prev = nd

def lst():
    a = list(vals)
    for v in new:
        bisect.insort(a, v)

def best(fn, r=3):
    t = float("inf")
    for _ in range(r):
        s = time.perf_counter()
        fn()
        t = min(t, time.perf_counter() - s)
    return t

print(f"保序插入 n={N}: 链 {best(chain)/M*1e6:.0f} us/次, list+bisect {best(lst)/M*1e6:.2f} us/次")

# 4) 同一句 a[i]，工作集 8 KB vs 8 MB
for n in (1_000, 1_000_000):
    a = list(range(n))
    idx = [random.randrange(n) for _ in range(100_000)]
    def read():
        s = 0
        for i in idx:
            s += a[i]
        return s
    print(f"随机读 n={n:<9,} 指针数组 {n*8/1e6:.3f} MB: {best(read)/len(idx)*1e9:.0f} ns/次")
```

我那台机器上跑出来是：

```text
append 1e6: 扩容 86 次, 复制指针 8,445,096 个, 最终容量 1,056,084
sizeof: 1->88 5->120 9->184 17->248 25->312 33->376 41->472 53->568
保序插入 n=20000: 链 230 us/次, list+bisect 2.56 us/次
随机读 n=1,000     指针数组 0.008 MB: 26 ns/次
随机读 n=1,000,000 指针数组 8.000 MB: 232 ns/次
```

第 1、2 行是稳定的；第 3 行连跑三次是 223–264 µs 对 2.34–2.86 µs；第 4、5 行的绝对值摆动最大，同一脚本再跑一次「随机读 n=1000000」可能是 183 ns 也可能是 232 ns。差值 5.7–7.4 倍这个量级不变，但别拿单次数做小数点级别的比较。

## 动手

在你自己的代码里搜这两种写法，改一处，前后各量一次：

```bash
rg -n "insert\(0|pop\(0" --type py
```

把命中的那个循环换成 `append` + 最后 `reverse()`，或者改成 `deque.appendleft`（前提是那段代码后面不再按下标取）。量的时候不要只测一次：跑 3–5 轮取最快的一次，否则第一次运行的分配开销会被算进被测代码里。

改完再回头看一眼扩容：如果那个列表的大小基本是固定的，试试 `[None] * n` 预分配，然后用 `sys.getsizeof` 确认没有再跳变。

## 还差的

- 只量了 CPython 3.11.5 / Windows 10 / 单进程单线程。PyPy 的 list 和对象布局不一样，这些倍数搬不过去；JVM 上的 `ArrayList` 对 `LinkedList` 我也没在本机量，不给数字。
- 「缓存」那组只量到「工作集变大、顺序变乱之后变慢」这个现象，没有做步长扫描，也没有把解释器开销扣干净。所以 183–238 ns 里到底多少是缓存未命中、多少是解释器，我说不清。
- 没有测尾延迟。扩容那一次的 O(n) 复制在均值里被摊平了，但那一次尖峰可能正好是线上那次超时；要下结论得跑 P99。
- `96.1 B/元素` 这个数包含每个值自己的 int 对象（28 字节）。如果值是共享的小整数或者已经存在的对象引用，链路的内存优势会比这个数字好一些。
- 删除这件事只看了容量会不会缩，没看长期反复增删之后的碎片和分配器行为。
