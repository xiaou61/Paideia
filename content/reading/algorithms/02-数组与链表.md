教科书结论是"查得多用数组，改得多用链表"。**实际工程里数组（动态数组）赢得更多**，原因不在复杂度，而在**缓存**。

## 缓存局部性：被忽略的大头

CPU 读内存不是一次读一个字节，而是按缓存行（通常 64 字节）成块读。数组的元素挨在一起，遍历时一趟缓存行能覆盖十几个元素；链表节点散落在堆上，每跳一次都可能是一次缓存未命中。

后果很具体：**同样是 O(n) 遍历，数组常常比链表快几倍**。在大数据量下，这个常数差能盖过复杂度差。

这也是为什么 Java 的 `ArrayList`、Python 的 `list`、Rust 的 `Vec` 是默认选择，`LinkedList` 很少被推荐。

## 数组的两个真实代价

1. **中间插入/删除要搬元素**：O(n)。但注意——如果每次都在**尾部**操作，代价是均摊 O(1)。
2. **扩容要复制**：容量满了申请更大的块并复制。预分配能减少抖动。

**什么时候这些代价真的痛**：在十万级列表的头部反复插入。这时才考虑链表或双端队列（`ArrayDeque`）。

## 链表真正适合的场景

- **频繁在头部插入**（LRU 缓存里的访问记录）；
- **已有节点上做 O(1) 删除**（配合哈希表定位节点，如 LRU）；
- **不需要按下标访问**，只需要顺序遍历；
- 数据块很大且**不想整体搬家**（例如某些内存池实现）。

注意第一条：LRU 缓存是哈希表 + 双向链表的组合，单用链表并不能做到"查找 O(1)"。

## 选型速查

| 需求 | 选择 |
| --- | --- |
| 按下标随机读、遍历 | 数组 / ArrayList / list |
| 只在尾部增删 | 数组（均摊 O(1)） |
| 频繁头部增删 | 双端队列（ArrayDeque）优先于 LinkedList |
| 频繁中间插入且要按 key 找 | 哈希表 + 链表（LRU 那种） |
| 大量小对象、内存敏感 | 数组（对象头开销也是成本） |

**双端队列优先于链表**是一个很实用的结论：`ArrayDeque` 用环形数组实现，头尾操作都是均摊 O(1)，且缓存友好。

## 一个常见的性能 bug

```python
# 每次都在头部插入：每次搬动整个列表
result = []
for x in items:
    result.insert(0, x)
```

数据一万条时就是 5000 万次元素搬动。改成 `append` 再 `reverse()`，或者用 `deque.appendleft`，立刻正常。

同理，字符串在循环里 `+=` 也是"每次重建"，要用 `StringBuilder` / `"".join()`——本质相同：**避免在循环里做 O(n) 的搬移**。

## 常见误区

### 误区：链表插入删除一定比数组快

**你以为**：O(1) 对 O(n)，稳赢。
**其实**：找到插入位置本身可能要 O(n)，而且节点分散导致缓存不友好。只有在"已经持有节点引用"时，链表的 O(1) 才真正兑现。

### 误区：链表省内存

**你以为**：按需分配，肯定省。
**其实**：每个节点都有额外指针与分配器开销，小对象时链表反而更占内存。

### 误区：复杂度低就不用管常数

**你以为**：O(1) 一定快。
**其实**：哈希计算、随机内存访问、分支预测失败都会让"理论上 O(1)"的操作实际很慢。要量。

## 小结

数组赢在缓存连续与随机访问；链表只在"已持有节点、频繁头尾改"时占优。中间插入与扩容是数组的代价，能预分配或改尾部操作就绕开。双端队列通常优于链表。下一课：为什么哈希表能做到平均 O(1)。
