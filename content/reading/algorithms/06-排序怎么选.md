## 先把结论摆出来

**99% 的情况用语言内置排序**。`sorted()` / `Collections.sort()` / `Arrays.sort()` 是经过几十年优化的混合算法（Timsort、双轴快排），比手写的快排更稳、更快、边界更全。

你真正需要知道的是四件事：

1. 比较排序的下限是 **O(n log n)**，不可能更快；
2. 需要**稳定排序**还是不稳定；
3. 排序的**比较函数**写错会怎样；
4. 什么时候**不该排序**（用堆、用计数、用索引）。

## 为什么下限是 n log n

比较排序每次只回答"a 比 b 大吗"，最多区分两种情况。n 个元素有 n! 种排列，要把它们区分开至少需要 log₂(n!) ≈ n log n 次比较。这是信息论下限，不是算法不够聪明。

想突破只能换思路：**计数排序 / 桶排序 / 基数排序**。它们不比较元素，而是利用"值域有限"这个额外信息，可以做到 O(n + k)。代价是：数据必须是整数或能映射成有限区间，且值域不能太大。

## 三种主流算法各自的特点

| 算法 | 平均 | 最坏 | 稳定 | 额外空间 | 特点 |
| --- | --- | --- | --- | --- | --- |
| 快速排序 | O(n log n) | O(n²) | 否 | O(log n) | 快，最坏会退化 |
| 归并排序 | O(n log n) | O(n log n) | 是 | O(n) | 稳，可外部排序 |
| 堆排序 | O(n log n) | O(n log n) | 否 | O(1) | 空间省，常数大 |
| Timsort | O(n log n) | O(n log n) | 是 | O(n) | 利用已有顺序，实际最快 |

Python 的 `sorted` 和 Java 的对象排序（`Collections.sort`）都用 Timsort。Java 对基本类型数组用双轴快排（因为基本类型没有"相等对象"的概念，稳定性没意义）。

## 稳定性是什么意思，什么时候重要

**稳定**：相等元素的相对顺序保持不变。

```python
rows = [("a", 2), ("b", 1), ("c", 2)]
sorted(rows, key=lambda r: r[1])   # 结果里 a 一定在 c 前面
```

什么时候重要：**多字段排序**。先按时间排，再按分数排，稳定的排序能保留第一次的顺序作为第二关键字。不稳定的排序会打乱它。

Java 里 `Arrays.sort(int[])` 不稳定，`Collections.sort(List)` 稳定——这个差别在业务代码里踩过不少次。

## 比较函数写错的三种典型

1. **返回布尔而不是三态**：某些语言的比较器要求 -1/0/1，返回 `a > b` 会把"相等"也当成一种排序，导致结果不稳定或直接抛异常（Java 会报 "Comparison method violates its general contract"）。
2. **比较器不自洽**：`a < b` 和 `b < a` 同时为真（比如用了不满足传递性的规则），排序结果不可预测。
3. **比较时抛异常**：空值、类型不一致。要么先过滤，要么在比较器里显式处理 null。

**Java 的 "Comparison method violates its general contract" 几乎都是第 2 种**：比较器写得看起来对，但对某些输入不满足传递性。

## 什么时候不该排序

- **只要最大/最小的 K 个**：用堆，O(n log k)，比全排序 O(n log n) 省；
- **只要去重**：用哈希集合，不需要排序；
- **数据已经在数据库里**：让数据库用索引排序（`ORDER BY` 走索引时是免排序的），别拉回来再排；
- **值域很小**（比如年龄、分数段）：计数排序 O(n)。

## 一个实用建议

排序前先问：**这个顺序是给谁看的？**

- 给人看：通常要稳定、要可预测，用内置排序；
- 给程序用（比如后续做二分查找）：排序后要保证比较规则与查找规则一致；
- 给数据库用：加索引，而不是在应用层排。

## 常见误区

### 误区：手写快排比内置快

**你以为**：内置排序有很多通用分支，手写更针对场景。
**其实**：内置实现有大量工程优化（小数组插排、已排序检测、并行），手写几乎必然更慢，还容易在最坏情况退化。

### 误区：排序一定比不排序慢

**你以为**：能不排就不排。
**其实**：排一次序可以让后续多次二分查找从 O(n) 变 O(log n)。是否值得，看"查多少次"。

### 误区：大数据排序只能靠加内存

**你以为**：装不下就没法排。
**其实**：可以外部排序——分块排序写临时文件，再多路归并。数据库的 `ORDER BY` 超出内存时就是这么做的。

## 小结

内置排序几乎总是正确选择；比较排序下限 O(n log n)，要更快只能利用值域。稳定性在多关键字排序时重要。比较器必须自洽。只取 Top K 用堆，能交给数据库排就别在应用层排。这条线到此结束：结构决定上限，量级决定生死，常数决定体验。
