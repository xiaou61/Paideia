## 先把结论摆出来

哈希表用三步实现"按下标取"的近似：

1. 用哈希函数把 key 算成一个整数；
2. 对桶数量取模，得到桶的下标；
3. 在桶里找具体元素。

**平均 O(1)，最坏 O(n)。** 最坏情况来自所有 key 挤进同一个桶（哈希冲突），这时退化成链表查找。

日常使用几乎总是平均情况，但有三类场景会让它变坏：哈希函数差、分布刻意被攻击、扩容不及时。

## 冲突怎么处理

两种主流做法：

- **链地址法**：每个桶挂一条链表（或红黑树，Java 的 `HashMap` 在链过长时会树化）；
- **开放寻址法**：冲突了就按规则找下一个空位（Python 的 `dict` 用这种）。

两者都要面对同一个问题：**装得太满，查找会变慢**。所以有**负载因子**：元素数 / 桶数超过阈值（常见 0.75）就扩容并重新分布（rehash）。

**rehash 是 O(n) 的**，但按倍数扩容时摊还是 O(1)——和动态数组扩容同理。

## 为什么最坏能到 O(n)

如果所有 key 的哈希值都相同，它们会全部落在一个桶里，查找就变成遍历链表。

这在线下代码里很少见，但有安全含义：**哈希碰撞攻击**——攻击者构造大量同哈希的参数，让服务端每次查表都退化成线性，把 CPU 打满。很多语言的哈希函数因此加了随机种子（Python 的 `PYTHONHASHSEED`、Java 的 String 哈希是固定的但 JDK 8 起对长链做树化）。

## key 必须满足什么

无论哪种语言，用自定义对象当 key 都必须保证：

- **相等的对象，哈希值必须相等**；
- **放入后哈希值不能变**（所以可变对象不适合当 key）。

Java 里就是"重写 `equals` 必须同时重写 `hashCode`"。不这么做时，两个内容相同的对象算出的哈希不同，会被当成两个 key——`map.get` 拿不到刚放进去的值。

Python 里对应的是 `__eq__` 与 `__hash__`，同理。

## 哈希表不擅长什么

| 需求 | 哈希表的短板 |
| --- | --- |
| 按 key 排序遍历 | 无序，排序要额外 O(n log n) |
| 范围查询（10 < id < 20） | 做不到，得全扫 |
| 找"最小/最大" | 没有顺序信息 |
| 内存敏感 | 为了减少冲突要留空桶，空间利用率低于数组 |

**顺序与范围查询要用有序结构**（平衡树、跳表、数据库索引），不是哈希表。这也是数据库里 B+ 树仍然是主力的原因。

## 选型速查

| 需求 | 选择 |
| --- | --- |
| 按 key 快速查/去重/计数 | 哈希表（dict / HashMap / Set） |
| 需要有序遍历 | 有序字典 / TreeMap / 跳表 |
| 缓存且要淘汰 | 哈希表 + 双向链表（LRU） |
| 数据量很小（几十个） | 数组线性查找可能更快，别过度设计 |

最后一条值得记住：**小规模数据上，哈希表的常数开销可能比简单遍历还大**。

## 一个常见 bug：用可变对象当 key

```python
key = [1, 2]
table[key] = "x"     # 直接报错：列表不可哈希
```

Python 用列表当 key 会立刻报错，这是好事。Java 里如果用可变对象的字段参与 `hashCode`，放入后修改字段，就再也找不到这个 key 了——而且不会报错，只是"数据消失了"。

## 常见误区

### 误区：哈希表查询永远是 O(1)

**你以为**：不管多少数据都一样快。
**其实**：平均是 O(1)，最坏 O(n)；扩容那一次也是 O(n)。数据量、冲突率、负载因子都影响实际表现。

### 误区：任何对象都能当 key

**你以为**：能放进去就行。
**其实**：key 的哈希必须稳定。可变对象改字段后，等于把 key 从表里"弄丢"了。

### 误区：哈希表能替代排序

**你以为**：遍历时的顺序就是插入顺序。
**其实**：哈希表不保证顺序；需要顺序请用有序结构或显式排序。

## 小结

哈希表 = 哈希函数 + 取模 + 冲突处理，平均 O(1)、最坏 O(n)。key 的哈希必须稳定且与相等一致。它不擅长排序与范围查询。小数据量别过度设计。下一课：需要顺序时怎么办——树与堆。
