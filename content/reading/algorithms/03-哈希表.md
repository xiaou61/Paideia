## 一条记录，查不到；再数一次变成两条

`hits` 是一张「路径 → 命中次数」的表，键是我自己写的 `Path`：

```python
class Path:
    __slots__ = ('raw',)

    def __init__(self, raw):
        self.raw = raw

    def __hash__(self):
        return hash(self.raw)

    def __eq__(self, o):
        return isinstance(o, Path) and self.raw == o.raw

    def __repr__(self):
        return f'Path({self.raw!r})'
```

打日志的时候手滑，路径多了一个斜杠，正好改的是参与 `hash` 的那个字段：

```python
hits = {}
k = Path('/api/users')
hits[k] = 1

k.raw = '/api/users/'        # 改完才去查
```

```text
len = 1 | get -> None | in -> False
len = 2 | values -> [1, 2] | 条目背后只有 1 个对象 -> True
list -> [Path('/api/users/'), Path('/api/users/')]
```

第二行是紧接着又执行了一次 `hits[k] = 2` 之后。三件事同时成立，一件都没报错：

- 表里只有 1 条，`get` 说没有；
- 再数一次，`len` 变 2，可这两条背后是同一个对象（`id` 去重只剩一个）；
- 打印出来是两行一模一样的 `/api/users/`。

我原来的理解是「改字段只影响下一个环节的解析」。实际是：**这个对象在表里的位置，是由它的字段算出来的**，改字段等于把它从表里搬走，而表里那格还留着它。

## 起点是算出来的，所以改字段等于搬家

哈希表按下标取，靠的是三步：

1. `hash(key)` 得到一个整数；
2. `hash(key) & (槽数 - 1)`（槽数是 2 的幂）得到起始槽；
3. 从这个槽开始，按一条由 hash 决定的序列往后走：槽空 → 判为不存在；槽里那个 key 和要找的相等 → 命中；否则继续下一个。

第 3 步的比较用的是 key 对象本身：先看 `is`，再 `==`。CPython 的 dict 是开放寻址，存的 key 就是插入时那个对象，不拷贝。

于是上面那段代码坏在两处，而且是同一处修改造成的：

- **起点变了**：`hash('/api/users/')` 不等于 `hash('/api/users')`，探测从另一个槽开始，永远走不到原来那一格；
- **相等也不成立了**：存进表里的就是 `k` 这个对象，它的 `raw` 已经变成带斜杠的版本，就算探测碰上了，`k == Path('/api/users')` 也是 `False`。

`get(k)` 里传进去的就是 `k` 本身，`is` 是成立的，但仍然找不到——因为探测序列由 hash 决定，`is` 只是走到那一格之后的比较方式。

修法很土：**进表的东西就当它不会再变**。

```python
hits = {}
hits['/api/users'] += 1      # 直接用不可变的值当 key
```

真要用自定义类，就把参与 hash 的字段做成构造后不再改的（属性只读、或者干脆只存一个 `str`）。顺手说一个我自己踩过的：`__slots__` 只是限制「能挂哪些属性名」，它**不**提供只读——上面 `k.raw = ...` 在 `__slots__` 下照样能改。我一开始把它当成了不可变。

## 0.75 不是哈希表的常数：CPython 3.11.5 这里是 2/3

下面所有数字都是这台机器上跑出来的：Windows 11、CPython 3.11.5、单线程。换机器、换版本都会变，测量方法也一并给出，好复现。

`sys.getsizeof` 只算容器本身，不含 key 对象。空 dict 是 64 字节，插入第一个 key 才有槽位数组：

```python
import sys

d = {}
prev = sys.getsizeof(d)
jumps = []
for i in range(1, 60):
    d[i] = i
    if sys.getsizeof(d) != prev:
        prev = sys.getsizeof(d)
        jumps.append((i, prev))
print(jumps)
```

```text
[(1, 224), (6, 352), (11, 632), (22, 1168), (43, 2264)]
```

跳变点在第 1、6、11、22、43 个 key。反推一下：每次扩容槽数翻倍（8 → 16 → 32 → 64），跳变前的已用槽是 5、10、21、42，正好是容量的 2/3。CPython 3.11 的 dict 就是这么设计的：可用槽数上限是容量的 2/3，用完就重新分布一遍。

这是**实现值**，不是语言保证。Java 的 `HashMap` 把 0.75 写在 javadoc 里（「default load factor (.75)」），那是另一个实现的文档值。两个数字混着记，就会变成「哈希表扩容阈值是 0.75」这种既不对应 CPython、也不对应所有语言的说法。

规模上去以后，每条记录的成本大致稳定：10 万个整数键，dict 占 5,242,960 字节（约 5.0 MiB，52 字节/条），同规模的 `list` 只有 800,056 字节（8 字节/元素）。同样一份整数，换成哈希表是 6.5 倍内存。`sys.getsizeof` 不含 key 对象本身，键是字符串时还要另外算。

## 装满之后，一次查询要摸几个槽

「平均 O(1)」里的那个 O(1)，指的是**平均比较次数**，而它由装载因子决定。写个几十行的玩具表，能直接数出来：

```python
class Linear:                          # 线性探测，记录比较次数
    def __init__(self, cap):
        self.cap, self.slots, self.used = cap, [None] * cap, 0

    def put(self, k):
        if self.used == self.cap:
            raise RuntimeError('表满了：线性探测没有空槽可放')
        i = hash(k) % self.cap
        while self.slots[i] is not None:
            i = (i + 1) % self.cap
        self.slots[i] = k
        self.used += 1

    def probes(self, k):               # (比较次数, 是否命中)
        i = hash(k) % self.cap
        p = 1
        while True:
            s = self.slots[i]
            if s is None:
                return p, False
            if s == k:
                return p, True
            i = (i + 1) % self.cap
            p += 1
```

槽数 1024、键是 64 位随机整数，命中在全部已插入键上取平均，未命中在 2000 个不在表里的键上取平均；链地址版本就是每个槽挂一条 list，比较次数只数桶内的：

| 装载因子 | 线性探测·命中 | 线性探测·未命中 | 链地址·命中 | 链地址·未命中 |
| --- | --- | --- | --- | --- |
| 0.25 | 1.16 | 1.36 | 1.12 | 0.23 |
| 0.50 | 1.41 | 2.45 | 1.22 | 0.53 |
| 0.67 | 1.95 | 4.92 | 1.33 | 0.68 |
| 0.75 | 2.47 | 7.40 | 1.40 | 0.76 |
| 0.90 | 5.99 | 49.48 | 1.46 | 0.92 |

从 0.50 到 0.90，命中从 1.41 次比较涨到 5.99 次，未命中从 2.45 涨到 49.48——**查不到比查得到贵 8 倍**。原因在机制里：命中到目标就返回，未命中必须一直走到空槽，而线性探测的簇是连成片的，簇越长走得越远。

链地址那一列未命中低于 1，是因为空桶一次比较都不用，α=0.25 时四分之三的桶是空的。

线性探测还有一个硬前提：**找不到空槽就没法收尾**。15/16 装满时查一个不存在的键，玩具表走了 12 步才确认没有；再插一个直接抛 `RuntimeError`（真实实现当然是扩容，不会抛）。所以装载因子不是为了跑得快，是先保证正确。

我的读法是：2/3 到 0.75 这个区间压的是**未命中**成本。缓存场景真正的负载就是未命中——你只有先确认「没有」才知道要回源。这是我从这批数字得出的判断，不是这里证明了的事。

## hash 值跨进程就换了一套

同一份代码，两次运行：

```text
python x.py                  hash('/api/users') -> -5800826240340531625
python x.py                  hash('/api/users') ->  5842644047264239005
```

同一个字符串，两次进程算出两个数。因为 CPython 从 3.3 起 `str` 的 hash 默认带每进程随机种子（3.4 起换成带随机密钥的 SipHash，PEP 456），要用固定值得设 `PYTHONHASHSEED=0`：

```text
PYTHONHASHSEED=0             hash('/api/users') -> 5777356507557158931   （两次一样）
```

所以别把 `hash()` 的返回值存进磁盘、写进 Redis、放进 URL 或者日志里当 id：重启之后就全对不上了，而且不报错，只是「查不到」。要跨进程稳定的摘要，用 `hashlib`。

另一半是「相等」的方向，这两条别记反：

- **相等的对象，hash 必须相等**。反过来不成立：`hash(1) == hash(1.0) == hash(True) == 1`，所以 `{1: 'a', 1.0: 'b', True: 'c'}` 里只有 1 条；`hash(-1) == hash(-2) == -2`。
- hash 相等只说明进了同一个起点，是不是同一个 key 由 `__eq__` 再判。碰撞本来就会发生，它不算 bug；真正的 bug 是「相等的东西 hash 不等」——那才会导致「明明放进去了却查不到」。

## hash 全撞到一个槽：0.05 ms 变 158 ms

先说一个反直觉的实测。n = 20000，各查 10000 次命中：

```text
低 13 位全相同（hash & 8191 全为 0） ->     0.50 ms
普通整数键                          ->     0.40 ms
自定义类，__hash__ 恒返回 0         ->  6219.82 ms
```

「低比特全撞」几乎没有代价：0.50 与 0.40 ms 的差在噪声量级。因为探测在撞了之后会拿完整 hash 继续走，低比特相同只决定起点，决定不了整条路径。真正塌下去的是 **hash 值全都一样**——每次查询退化成扫全表。

用 `__hash__` 返回常数的类，把这一点量成曲线（每边各 n 次命中查询，两次运行里全碰撞那列落在 130–158 ms）：

| n | 普通整数键 | `__hash__` 恒 0 |
| --- | --- | --- |
| 500 | 0.01 ms | 9.80 ms |
| 1000 | 0.03 ms | 40.50 ms |
| 2000 | 0.05 ms | 157.96 ms |

n 翻倍，全碰撞那一列涨约 4 倍（9.8 → 40.5 → 158），也就是单次查询从 O(1) 变成 O(n)。这个类是我为了测量写的玩具，不是真实攻击。

安全含义要说得准确一点：需要同时满足两个条件——攻击者能预测 hash，且能构造出大量同 hash 的键。CPython 给 `str` 加随机种子去掉的是第一个条件，所以从外部构造同 hash 字符串这条路不好走了；但**你自己的 `__hash__` 它管不着**，`return 0` 或者用几个固定值兜底，等于把两个条件都送给对方。

## 顺序：保插入序，但那不是有序

`dict` 的遍历顺序是插入顺序，`sorted` 才是字典序：

```text
list({'b': 1, 'a': 2, 'c': 3}) -> ['b', 'a', 'c']
sorted(...)                    -> ['a', 'b', 'c']
```

两次运行、两种 `PYTHONHASHSEED` 下，第一行输出都不变。Python 3.7 起，插入序写进了语言规范（CPython 3.6 就已经这样，但那会儿还算实现细节）。

所以「哈希表不保证顺序」这句，对 CPython 的 `dict` 是错的——**保证的是插入序，不保证的是「有序」**。它对不上任何排序：插入顺序是数据进来的顺序，跟 key 的大小、路径的前缀都无关。

后果很具体：`hits` 这张表想输出「`/api/` 前缀下计数最高的 10 条」，得扫全表筛前缀、再排序，O(n log n)；想在「时间戳 10 点到 12 点」这个区间里取值，哈希表连门都没有，因为没有范围信息。这类需求要换结构：有序遍历用有序结构（第 4 课的树与堆），按值或按键排序用第 6 课的比较思路，数据库里则是 B+ 树索引的地盘。

## 一个排查表：症状 → 先看哪

按上面几节的现象倒查，比背复杂度有用：

| 症状 | 先看哪 |
| --- | --- |
| 放进去的数取不出来，不报错 | key 的字段在插入后有没有被改；`__hash__` 是否依赖可变字段 |
| 同一条逻辑记录出现两行，计数翻倍 | 相等性和 hash 覆盖的字段不一致（改了字段又插一次） |
| 重启 / 换进程后缓存命中率掉到 0 | 是不是把 `hash()` 当 id 存盘、写 Redis、进 URL |
| 单次查询从微秒涨到百微秒，CPU 打满 | 有没有 `__hash__` 返回常数；键集是不是被构造成同 hash |
| 要按前缀 / 范围 / 排序读，怎么调都别扭 | 选错结构了，不是哈希表调优问题 |
| 内存比数据大好几倍 | `sys.getsizeof(d) / len(d)` 是多少；本文实测 dict 52 字节/条、list 8 字节/元素 |

## 跑一遍

上面第一节和第三节的结论，一个脚本就能复现（Windows PowerShell 里 `python` 是 3.11.5）：

```python
class Path:
    __slots__ = ('raw',)

    def __init__(self, raw):
        self.raw = raw

    def __hash__(self):
        return hash(self.raw)

    def __eq__(self, o):
        return isinstance(o, Path) and self.raw == o.raw

    def __repr__(self):
        return f'Path({self.raw!r})'


hits = {}
k = Path('/api/users')
hits[k] = 1

k.raw = '/api/users/'

print('len =', len(hits), '| get ->', hits.get(k), '| in ->', k in hits)
hits[k] = 2
print('len =', len(hits), '| values ->', sorted(hits.values()),
      '| 条目背后只有 1 个对象 ->', len({id(x) for x in hits}) == 1)
print('list ->', list(hits))

import sys
d = {}
jumps = []
prev = sys.getsizeof(d)
for i in range(1, 60):
    d[i] = i
    if sys.getsizeof(d) != prev:
        prev = sys.getsizeof(d)
        jumps.append((i, prev))
print('扩容发生在第几个 key ->', jumps)
```

```text
len = 1 | get -> None | in -> False
len = 2 | values -> [1, 2] | 条目背后只有 1 个对象 -> True
list -> [Path('/api/users/'), Path('/api/users/')]
扩容发生在第几个 key -> [(1, 224), (6, 352), (11, 632), (22, 1168), (43, 2264)]
```

最后一行会随 CPython 版本变，`(1, 224)` 里的 224 也可能不同（32 位 Python 更小）。第一、二行的行为只要还是「拿字段算 hash」，哪个版本都一样。

## 动手

1. 把 `Path` 从 key 里换掉：直接用字符串，或者让 `raw` 变成没有 setter 的 property。重跑上一节，确认 `len` 停在 1、`get` 返回 1。这一步改的就是你项目里那类「归一化之后再进表」的位置——归一化必须在进表之前做完。
2. 量一下你手上最大的那个 dict：`len(d)`、`sys.getsizeof(d) / len(d)`。如果这个表是「路径 → 计数」这种几十个键的小表，`in` 用 dict 还是 list 其实差不多：本文实测 n=5 时 20 万次查询是 8.7 ms 对 6.5 ms，n=1000 时才拉开到 816 ms 对 11 ms。小表选 dict 的理由是语义（去重、计数），不是速度。
3. 在代码里搜一遍 `def __hash__`：返回常量的、依赖可变字段的，都是隐患。改成对不可变字段算 hash，然后别只跑新用例——把原来的单测跑一遍，看有没有用例恰好靠「两条同内容 key」通过。

## 还差的

- 只在 CPython 3.11.5 / Windows 11 上测过。PyPy、3.13、32 位构建都没跑；`sys.getsizeof` 的绝对值和跳变点、以及探测序列都跟实现绑，换环境要自己重测一遍。
- Java 一行没跑。文中 0.75 只引了 JDK 8 `HashMap` 的 javadoc；树化阈值（8 / 6 / 64）我见过源码常量但没在本机验证，所以这篇不写它。
- 没做真实碰撞攻击实验。全碰撞用的是 `__hash__` 返回 0 的玩具类；`str` 键在随机种子下能不能从外部批量构造同 hash，我没试，也不打算给方法。
- 没测并发。多线程同时读、同时写 dict 的时序和 GIL 下的切换开销都没量，这篇的结论只覆盖单线程。
- 探测次数只在玩具表上数得出来。CPython 的 dict 用的是带 perturb 的探测序列，我在外面看不到它走了几步，只能测耗时；二次探测、Robin Hood 这些变体也没实现对比。
- 键全是整数。字符串键的哈希代价、键长对内存的影响都没量——真实项目里键大概率是字符串。
