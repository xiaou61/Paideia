# 复杂度：只看量级就够用了

## 一次实测：同样是去重

需求很简单：一万条记录里去掉重复的 id，保留第一次出现的顺序。第一版这么写：

```python
seen = []
for x in data:
    if x in seen:       # 每次都要从头比一遍
        continue
    seen.append(x)
```

线上数据只有几千条时没人抱怨。某天批量导入了一份 16000 条的清单，这个函数卡了两秒多。换成 `set` 之后：

```python
seen = set()
for x in data:
    if x in seen:       # 哈希定位，和元素个数无关
        continue
    seen.add(x)
```

本机跑一遍（CPython 3.11.5，每组单次运行，只数循环本身，不含造数据）：

```text
n         list(ms)    set(ms)
1000          5.2        0.18
2000         18.4        0.42
4000         72.1        0.66
8000        224.1        1.15
16000       822.8        1.45
```

看第二列的变化率，比看绝对值有用：

| n 翻倍 | `list` 耗时变成 | `set` 耗时变成 |
| --- | --- | --- |
| 1000 → 2000 | 3.5 倍 | 2.3 倍 |
| 2000 → 4000 | 3.9 倍 | 1.6 倍 |
| 4000 → 8000 | 3.1 倍 | 1.7 倍 |
| 8000 → 16000 | 3.7 倍 | 1.3 倍 |

`list` 版本每次翻倍大约是 4 倍——**这就是平方**（n 变 2 倍，工作量变 4 倍）。`set` 版本翻倍大约是 1.3~2.3 倍，接近**线性**。

到 16000 条时两者差 500 多倍。**这个倍数不会随机器变快而变小**：换台三倍速的机器，两列同时除以三，差距还是 500 倍。

复杂度要回答的就是这件事：**n 变大时，耗时怎么涨。** 不是"跑多少秒"。

## 为什么差这么多

`x in seen` 对 `list` 是**从头逐个比**：list 有 n 个元素就要比 n 次，外面再套 n 次循环，总比较次数约 n²/2。

`x in seen` 对 `set` 是**算哈希再定位**：算一次哈希（和 n 无关），跳到一个桶，桶里再看一眼。平均情况和 n 无关，所以整体是线性的。

**同一份逻辑，只换了容器，量级从平方变成线性。** 这也是为什么实际救火时"换数据结构"比"换算法"出现得更频繁。

## 复杂度的写法

把操作次数写成 n 的函数，**只留增长最快的那一项，丢掉系数和低阶项**：

```text
3n² + 5n + 100   →   O(n²)
2n               →   O(n)
```

丢掉系数是有意的：`O(2n)` 和 `O(n)` 是同一类，因为机器快慢、语言开销都会带来常数差异，而这些在 n 足够大时被量级盖过。常用量级从好到坏：

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2^n)
```

业务代码里真正会咬人的只有三个地方：

1. **嵌套循环**：16000 条就要做上亿次比较，n=10 万时是 100 亿次；
2. **循环里查列表**：`if x in list` 是 O(n)，套在循环里就是平方——就是上面那个例子；
3. **循环里发请求或查库**：这是 N+1，瓶颈不是 CPU 而是网络往返。

## 数循环层数

看一段代码的复杂度，先数"随 n 变化的循环层数"，再看每层内部是不是常数操作。

```python
# O(n)：一层
for item in items:
    total += item

# O(n²)：嵌套。内层规模随外层变化时要更细看
result = []
for x in items:
    if x not in result:     # 每次扫一遍已收集的
        result.append(x)

# O(n)：换成 set，内层不再随 n 变
seen = set()
for x in items:
    if x in seen:
        continue
    seen.add(x)

# O(n)：两个循环并列是相加，不是相乘
for x in items: total += x
for x in items: print(x)
```

两个坑：

- **并列不嵌套是相加**，`O(n) + O(n)` 还是 `O(n)`；
- **内层不随 n 增长就不是 n²**。`for x in items: for bit in range(32)` 是 `O(32n)`，也就是 `O(n)`。

还有一类更隐蔽的：`for x in items: if x in list_of_fixed_10` 是 `O(10n)`，没问题；但 `if x in other_list`（另一个长度也是 n 的列表）就是平方，从名字上完全看不出来。

## 均摊：为什么 append 看起来是 O(1)

动态数组满了要扩容：申请更大空间、把旧元素逐个复制过去。这一次是 O(n)。如果每次都扩一点，总代价会变成平方；实际实现是按倍数扩（Python 的 list 约 1.125 倍增长，Java 的 ArrayList 是 1.5 倍），越往后扩容越少。

总复制量是 `n + n/2 + n/4 + … ≈ 2n`，摊到 n 次 append 上就是 O(1)。这叫**均摊**，它解释了两件事：

- 为什么 `append` 偶尔会卡一下（正好撞上扩容）；
- 为什么**预分配容量能减少抖动**：`new ArrayList<>(1000)`、`list.reserve(n)` 直接跳过中间那几次扩容。

注意均摊不是"每次都快"，是"总代价除以次数"。如果你有严格的尾延迟要求（比如 P99 延迟），那一次 O(n) 的扩容照样会打穿。

## 空间也算复杂度

- 一次性读进内存再处理：O(n) 空间，n 大就 OOM（这比慢更致命，慢还能等，OOM 直接挂）；
- 递归每层一个栈帧——Python 默认递归上限 1000，深递归会 `RecursionError`；
- 缓存不设上限：本质是"用空间换时间，但没有上限"，最后把内存换光。

**流式处理**（生成器、迭代器）就是把 O(n) 空间压成 O(1) 的手段：读一行处理一行，不保留全量。代价是不能回头、不能随机访问。

## 什么时候不该优化

上面那些数字只回答了"哪个方案在大 n 下更抗压"，没回答"该不该动它"。判断依据是**这段代码跑多少次**。

再补一组小 n 的实测（每组取 200 次里最快的一次，避开 GC 和调度噪声，单位微秒）：

```text
n       list(us)    set(us)
10           1.0        0.9
50           9.2        4.4
100         28.1        8.3
500        531.9       40.9
```

`n=10` 时两者几乎一样（1.0 对 0.9）。**小规模下常数决定胜负**：`set` 要算哈希、要分配桶，这些固定开销在 n 很小时正好抵掉了它省下的比较。所以"无脑换 set"在极小的集合上不是优化，甚至可能更慢（Python 里 `set` 的内存占用还明显大于小 list）。

| 场景 | 该怎么办 |
| --- | --- |
| 每个请求都跑的热路径 | 值得把平方降到线性，收益会乘以 QPS |
| 一天跑一次的批处理 | 16000 条 0.8 秒，能接受就先别动；先确认真的是它慢 |
| 循环里查数据库 | N+1 的锅在往返次数，不在复杂度，改批量查询 |
| 分页查库 | 复杂度不是问题，索引和 `LIMIT` 才是 |

最常被忽略的是第二行：**低频任务的量级优化收益很小**。一天跑一次的东西，从 O(n log n) 抠到 O(n) 换来的几十毫秒，永远赚不回你读那段代码的时间。

## 留个尾巴

上面所有数字都是单线程、无并发的纯 CPU 测量。真实服务里还有两个我没在这篇里量化的变量：GC（`set` 分配的桶对象会进入 GC 压力）和缓存局部性（`list` 顺序扫描对 CPU cache 友好，`set` 随机跳桶不友好）。真正的定论只能来自你在自己的场景里跑的那一次——复杂度只负责先筛掉"规模一大必死"的方案。
