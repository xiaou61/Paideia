## 先把结论摆出来

复杂度描述的是**输入变大时，耗时/空间怎么涨**，不是"跑多少秒"。

常用量级从好到坏：

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2^n)
```

业务代码里真正要警惕的只有三条：

1. **嵌套循环**：n² 在 n=10 万时就是 100 亿次操作，基本等于卡死；
2. **循环里查列表**：`if x in list` 是 O(n)，套在循环里就变 n²，换成 `set` 立刻变 O(n)；
3. **循环里发请求/查库**：这是"N+1 查询"，复杂度不是 CPU 问题，是网络往返问题。

## 怎么看一段代码的复杂度

**数循环的层数**，再看每层循环内部是不是常数操作。

```python
# O(n)
for item in items:
    total += item

# O(n²)
for a in items:
    for b in items:
        if a == b: ...

# O(n)
seen = set()
for a in items:
    if a in seen: ...     # set 查找平均 O(1)
    seen.add(a)
```

第三个例子是重点：**同一个需求，换个结构就从平方降到线性**。这也是"数据结构比算法更常救火"的原因。

注意：两个循环并列是 O(n) + O(n) = O(n)，不是 O(n²)；嵌套才是乘。

## 复杂度会忽略什么

大 O 丢掉常数和低阶项。这意味着：

- n=10 时，O(n²) 可能比 O(n) 更快（因为常数小）；
- 一个 O(n) 但每步都发网络请求的算法，实际比 O(n²) 的内存计算还慢。

**结论**：复杂度用来排除"规模一大必死"的方案，不能用来选常数级优劣。常数要靠实测。

## 均摊复杂度：为什么 append 看起来是 O(1)

动态数组满了要扩容：申请更大空间、把旧元素复制过去。单次是 O(n)，但扩容按倍数增长，摊到每次操作上是 O(1)。这叫**均摊**。

它解释了：偶尔一次卡顿（扩容），以及为什么**预分配容量**能减少抖动（`new ArrayList<>(1000)`、`list.reserve`）。

## 空间复杂度也不能忽略

- 把所有数据读进内存再处理：O(n) 空间，n 大时直接 OOM；
- 递归深度过深：每层一个栈帧，可能栈溢出；
- 缓存不设上限：本质是"用空间换时间但没有上限"。

**流式处理**（生成器/迭代器）就是把 O(n) 空间压成 O(1) 的手段——这是 Python 课里 `yield` 那一篇的实际用途。

## 三个真实场景的判断

| 场景 | 判断 |
| --- | --- |
| 去重一万条数据 | `set`，O(n)；用列表循环查是 O(n²) |
| 分页查数据库 | 复杂度不是问题，索引与 `LIMIT` 才是 |
| 每天跑一次的批处理 | n=10 万，O(n log n) 完全够；别为 O(n) 写复杂代码 |

**最后一条经常被忽略**：性能优化要看"跑多少次"。一天一次的任务，多花两秒没人感觉得到；每个请求都跑的热路径，才值得抠常数。

## 常见误区

### 误区：复杂度越低一定越快

**你以为**：O(log n) 完胜 O(n)。
**其实**：小规模下常数决定胜负；哈希表平均 O(1)，但哈希计算和冲突处理有实际成本。复杂度是筛子，不是判决书。

### 误区：两个循环就是 O(n²)

**你以为**：看到两层就平方。
**其实**：要看是否嵌套、内层是否随外层规模变化。并列循环是相加，不嵌套的固定次数循环仍是 O(n)。

### 误区：优化一定要改算法

**你以为**：想快就得换数据结构。
**其实**：多数"慢"来自 N+1 查询、没走索引、重复计算、序列化开销。先量再改，别一上来重写。

## 小结

复杂度看量级，重点防嵌套循环与循环里查列表。均摊解释动态数组。空间与递归深度也要算。优化的优先级由"跑多少次"决定：热路径值得抠，低频任务别折腾。下一课：最基础的一对权衡——数组与链表。
