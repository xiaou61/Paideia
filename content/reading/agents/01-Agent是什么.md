## 先把结论摆出来

一句话：**Agent 是"由模型自己决定下一步做什么"的程序**。

```sketch
{
  "title": "和普通程序的分界线：下一步谁定",
  "rows": [
    [
      { "id": "fixed", "title": "普通程序", "sub": "步骤写死在代码里", "tone": "gray" },
      { "id": "model", "title": "模型自己选下一步", "sub": "看当前结果决定", "tone": "blue" },
      { "id": "loop", "title": "循环到能回答为止", "sub": "中间可能查好几次", "tone": "green" }
    ]
  ],
  "arrows": [
    { "from": "fixed", "to": "model" },
    { "from": "model", "to": "loop" }
  ]
}
```

判据只有一条——**下一步调什么工具、要不要继续、什么时候停，是不是模型在运行时决定的**。是，就是 Agent；不是，就是一个用了模型的普通程序。

这条界线听起来很薄，但它改变的东西很多：测试怎么写、成本怎么估、出了事谁负责，全都跟着变。后面十几篇讲的，几乎都是这条界线带来的连锁反应。

## 对照一下就清楚了

同一个需求——"帮我把这个 Issue 的修复方案写出来"——两种做法。

**固定流程**（不是 Agent）：

```text
1. 用 API 拉 Issue 正文
2. 把正文塞进提示词，问模型"给出修复方案"
3. 把结果存库
```

第 2 步调用几次、什么时候调，是**你写死的**。模型只是其中一环，它的输入输出形状固定。

**Agent**：

```text
给模型：Issue 正文 + 可用工具（读仓库、搜代码、看历史提交）
模型决定：先搜一下相关代码 → 再读两个文件 → 发现要看的函数在另一个模块 → 再读 → 够了 → 输出方案
```

模型每一步都可能选不同的工具，也可能决定"信息不够，继续找"。**调用次数不确定**——这就是 Agent。

注意两者的差别不在"用不用模型"，而在**控制流归谁**。第一种里，控制流是你的 `if/else` 和 `for` 循环；第二种里，控制流是模型每一轮输出的那个"下一步"。

## 一个更细的判据：三次追问

拿不准的时候，问自己三个问题：

1. **同一份输入，跑两次，调用次数会一样吗？** 不一样，说明控制流在模型手里。
2. **模型能不能拒绝执行某一步？** 能（"信息不足，我需要先看配置"），说明它有决策权。
3. **你能在代码里预先画出完整流程图吗？** 画不出来，说明它真是 Agent。

三个都是"是"才叫 Agent。有一个是"否"，多半是固定流程套了个 Agent 的壳。

第三种情况很常见，而且不好：**代码里写着 `while (true)`，但实际每次都是固定的那三步**。这种"伪 Agent"付出了不确定性，没换到任何收益。

## 为什么这条界线值钱

因为固定流程写不动"不确定的探索"。

写代码修 bug 这件事，人也没法预先列出所有步骤：你得先看到代码才知道要查什么。固定流程只能在设计时把分支都想到，而 Agent 把"想到哪一步"交给模型在运行时判断。

一个具体对比。修一个"订单列表加载慢"的 bug：

```text
固定流程能写的：
  拉日志 → 提取慢 SQL → 输出建议

Agent 能做的：
  拉日志 → 发现是 selectByUser 慢
       → 去代码里搜 selectByUser 的定义
       → 发现它动态拼了 3 个条件，其中 1 个没走索引
       → 去看表结构，确认索引情况
       → 发现缺 (user_id, created_at)
       → 给出建议 + 迁移脚本
```

后者的第 2 到 5 步，在设计时根本写不出来——因为要看第 1 步的结果才知道下一步查什么。

所以 Agent 适合的活有个共同特征：**步骤数量与顺序事先说不准，但每一步做对了可以验证**。

反过来说，如果一件事的步骤你完全知道，**别用 Agent**。用一个 Agent 去做"先 A 再 B 再 C"的固定流程，你付出了不确定性（可能跑偏、可能多花十倍钱），换来的是零收益。

## 代价清单：这条界线不是白拿的

### 一、成本不可预估

固定流程调 1 次，Agent 可能调 8 次。而且输入 token 随轮次累积——第 5 轮要把前 4 轮的完整对话再发一遍。

算一笔账。假设系统提示词 + 工具描述 3000 token，每轮新增 1000 token：

```text
第 1 轮输入  4000
第 2 轮输入  6000
第 3 轮输入  8000
...
第 8 轮输入 18000
合计        ≈ 88000 token
```

而单次调用只要 4000。**差 22 倍**。

而且**同一个任务跑两次花的钱不一样**——因为轮次不同。所以做 Agent 必须设硬上限：最多几轮、最多几个工具调用、最多多少 token。没有上限的 Agent 等于一个不封顶的账单。

### 二、结果不可复现

温度调成 0 也只是"倾向更确定"，不等于幂等。同一个输入，模型可能这次搜 3 个文件、下次搜 2 个。

这直接影响测试怎么写：

```text
不能这样断言：output == "建议给 (user_id, created_at) 加联合索引"
可以这样断言：
  - 输出里包含 "user_id"
  - 输出里提到了"索引"
  - 如果调用了工具，必须调用过 search_code
```

**只能断言性质，不能断言字面**。这是 Agent 测试和普通单元测试最大的差别。

### 三、失败是静默的

固定流程挂了会抛异常。Agent 挂了往往**正常返回一段看起来很对的话**——它可能搜错了目录、读错了文件、然后基于错误信息给出一个自洽的答案。没有报错，没有异常栈。

一个真实形态：

```text
用户问：这个方法为什么慢
Agent 搜代码 → 搜到同名方法在另一个模块
Agent 读那个方法 → 分析得头头是道
结论：完全是另一个方法的分析
```

输出格式完美、逻辑通顺、结论错误。**错误伪装成成功**是 Agent 最危险的地方。

### 四、动作会真的发生

如果工具里包含"写文件""发消息""提交代码"，模型的一次误判就是一次真实副作用。

所以工具要按危险程度分级：只读的随便给，写入的要有确认或回滚。这条后面第 4 篇和第 13 篇还会展开。

## 一个能立刻用上的判断表

| 你的需求 | 用什么 | 为什么 |
| --- | --- | --- |
| 一段文本 → 一段文本（翻译、摘要、改写） | 直接调模型 | 步骤固定为零 |
| 步骤固定，只是中间用模型处理 | 固定流程 + 模型 | 控制流可控，好测好算钱 |
| 步骤不确定，但每步可验证 | Agent | 正是它的主场 |
| 不可逆的写操作 | Agent 建议，人来执行 | 把风险整个消掉 |

最后一行值得多说一句：**"让 AI 建议、让人执行"是成本最低的护栏**。它把不可逆操作的风险整个消掉了，而用户几乎感觉不到损失——因为大多数时候用户本来就要看一眼再点确定。

## 一个最小 Agent 长什么样

抛开所有框架，一个 Agent 的核心循环就这么点东西：

```python
messages = [
    {"role": "system", "content": 系统提示词},
    {"role": "user", "content": 用户任务},
]

for step in range(MAX_STEPS):          # 硬上限，必须有
    reply = call_model(messages, tools=工具清单)

    if reply.tool_calls:               # 模型想动手
        for call in reply.tool_calls:
            result = execute(call)     # 你的代码真的执行
            messages.append({          # 结果塞回消息
                "role": "tool",
                "tool_call_id": call.id,
                "content": result,
            })
        continue                       # 再来一轮

    return reply.content               # 模型不想动手了，收工
```

三十行不到。全部魔法都在这个循环里。

框架帮你做的是消息格式、并发、流式、重试、观测——**但循环本身就这么简单**，理解它之后再看任何框架都不会迷路。

关键的一行是 `messages.append(...)`。模型本身不记得上一轮调过什么，是你在每一轮把完整历史重新发给它。这一点想通了，后面「记忆与上下文」那一篇就没什么新东西了。

顺便说一个容易踩的坑：**`MAX_STEPS` 到了怎么办，必须提前定好**。两个选择——直接返回"信息不完整"的当前结果，或者再调一次模型让它基于现有信息收尾（这次不给工具）。后者体验好，但多一次调用，而且这条路径很容易漏测，因为它只在异常时走。

## 常见误区

### 误区：Agent 比普通调用"更高级"

**你以为**：能用 Agent 就该用，显得先进。
**其实**：Agent 是不确定性的来源。步骤确定的任务用 Agent，只会多花钱、多出错、更难测。
**怎么验证**：把你任务的实际步骤列出来。如果每次跑的顺序都一样，那它就是个固定流程。

### 误区：模型会记住上一轮说过什么

**你以为**：连续对话时模型自己攒着上下文。
**其实**：模型是无状态的。每一轮你都要把完整历史重新发过去，否则它什么都不知道。
**怎么验证**：只发最后一句用户消息、不带历史，看它还能不能接上上文——它接不上。

### 误区：Agent 跑出了看起来对的答案，就是成功

**你以为**：没有报错、格式正确、语气专业，说明做对了。
**其实**：它可能基于错误的检索结果给出自洽的结论。错误在这里不抛异常。
**怎么验证**：让它把用到的依据（哪几个文件、哪几条检索结果）一起输出，然后抽查依据本身对不对。

### 误区：把 `while (true)` 加上工具调用就叫 Agent

**你以为**：循环 + 工具 = Agent。
**其实**：如果每轮调用的工具和顺序都一样，你只是用模型做了一次参数解析，控制流还在你手里。
**怎么验证**：统计 20 次真实运行的工具调用序列。全一样，说明它不是 Agent，是固定流程。

## 小结

Agent 的判据只有一条：下一步由模型在运行时决定。它擅长步骤不确定但每步可验证的任务，代价是成本不可预估、结果不可复现、失败静默、动作会真的发生。核心就是一个"调模型 → 执行工具 → 把结果塞回消息 → 再调"的三十行循环。
