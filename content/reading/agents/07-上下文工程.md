## 5000 行日志，异常在最后 20 行

```text
PS> $log = 1..5000 | ForEach-Object {
>>   if ($_ -eq 4981) { '2026-11-19 10:00:00 ERROR order-service query timeout after 3000ms trace=7f3c' }
>>   else { '2026-11-19 10:00:{0:00} INFO order-service handled request id={1}' -f ($_ % 60), $_ }
>> }
PS> $log | Set-Content .\agent.log -Encoding UTF8
PS> (Get-Content .\agent.log).Count
5000
PS> Get-Content .\agent.log -TotalCount 200 | Select-String 'ERROR'
PS> Get-Content .\agent.log -Tail 20 | Select-String 'ERROR'
2026-11-19 10:00:00 ERROR order-service query timeout after 3000ms trace=7f3c
```

这是我本机造的玩具日志：5000 行，异常固定在第 4981 行。前 200 行那条命令没有输出，`-Tail 20` 那条才找到它。

Agent 那句「日志里没有异常」是示意——本机没有模型 API key，我没有调模型；但失败链路是完整的：工具只回了前 200 行，异常所在的后 20 行根本没进上下文。不是它不会看，是你只给了前 200 行。

这篇只处理一个问题：同一份 token 预算，怎么分、怎么压、什么时候按需取。05 篇讲的是记忆怎么存、怎么检索、怎么写回；这里不重复三层记忆、写入确认和检索排序。

## 预算里有五类内容，前两类是固定开销

一份请求大致长这样：

```json
{
  "model": "<model-id>",
  "messages": [
    { "role": "system", "content": "<系统/开发者指令>" },
    { "role": "user", "content": "<当前问题>" }
  ],
  "tools": [
    { "type": "function", "function": { "name": "get_log", "description": "<工具描述>" } }
  ]
}
```

`tools` 是请求的顶层字段，和 `messages` 平级，不在任何一条 message 里；但它序列化后仍是输入的一部分，会计入上下文和计费。别因为它不在 messages 里就当它免费。

| 类别 | 位置/形状 | 随什么变 | 先做什么 |
| --- | --- | --- | --- |
| 系统/开发者指令 | `messages` 里的 system，或顶层 `instructions` / `system` | 改配置才变 | 保证权威性，删掉互相冲突的规则 |
| 工具定义 | 顶层 `tools` | 工具数量、描述长度、参数 schema | 删未使用的工具，缩短描述 |
| 历史消息 | user / assistant 消息 | 轮次增加而增长 | 按 token 上限裁剪或摘要 |
| 检索/工具结果 | 文档块、tool 消息 | 单次可能极大 | 工具内限长，再选摘要/分页/句柄 |
| 当前问题 | 最后一条 user 消息 | 基本很小 | 必须保留，放在最后 |

前两类是固定开销：同一版配置下每轮都带。固定不等于小；工具多、描述长、schema 复杂时，`tools` 可能比当前问题大一个数量级。不要先入为主只删系统提示。

还要从同一个上限里给输出留位置。先看接口文档：上下文上限是否包含输出；如果包含，先给回复留 `max_output_tokens`，剩下的才是输入预算。

### 先数一遍，不要猜比例

我用 tiktoken `o200k_base` 对两份构造请求逐段 encode 后相加（不含消息包装的少量 token；换分词器数字会变）：

| 请求 | 系统提示 | 工具定义 | 普通对话历史 | 工具结果 | 当前问题 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 第 1 轮，无工具结果 | 72 | 181 | 0 | 0 | 12 | 265 |
| 后续请求，含两次工具结果 | 72 | 181 | 73 | 4,408 | 9 | 4,743 |

同一套系统提示和工具定义没变：固定开销始终是 253 token，占比从 95.5% 掉到 5.3%；后续请求的历史加工具结果占 94.5%，单请求是第 1 轮的 17.9 倍。

这不是线上统计。样本是我构造的：6 条普通对话消息、3 个工具定义、一次订单查询、一次 `EXPLAIN`、一份 200 行日志摘录。它只证明一件事：固定开销不一定是大头，把请求拉大的是历史和工具结果，具体落在哪一类要看任务。线上要按自己的请求日志数 p50 / p95，不要抄这张表的百分比。

同样这份玩具日志，5000 行全量是 109,007 token；前 100 行加后 100 行的摘录约 4.4k token。以 32k / 128k 窗口为例，前者直接超限，后者也被这份日志占掉八成以上。这是这份日志的形状，不是所有日志的形状。

### 一份可执行的分配顺序

1. 先扣输出预留。窗口上限减去 `max_output_tokens`，剩下的才是输入预算。
2. 量固定开销。系统提示和工具定义各占多少；删掉从没被调用过的工具，合并重复描述。
3. 放入当前问题和 pinned 约束。它们不能被后面的裁剪挤掉。
4. 保留最近 2–3 轮原文。再早的历史按 token 上限决定摘要还是丢弃。
5. 剩余预算给检索/工具结果。超了先压工具结果，再摘要旧历史；不要先动当前问题和 pinned 约束。

每一步的上限都按目标模型的上下文上限、任务的 p50 / p95 和成本预算反推；不存在一个通用的 token 数字。

## 5k vs 50k：这个实验要重新设计

老版说「同一任务分别用 5k 和 50k 上下文跑，比较准确率」，这证明不了「长度导致退化」。5k 和 50k 不只长度不同，内容、位置、信噪比也一起变了。准确率下降时，你不知道是长度、填充物还是相关信息被挤到中间造成的。

要测长度，保持相关信息、问题、输出格式完全一样，只增加中性填充：固定语料、固定随机种子、固定插入位置，做到 5k vs 50k。填充物不能是另一批相关文档，否则测的是内容差异。

要测位置，总长度固定在同一量级，只移动相关信息：开头、中间、结尾各一份，其他 token 完全一样。这样位置才是唯一变量。

每个条件先按 30 次起步；同一任务的多次采样要配对，别把 30 次采样当成 30 个独立任务。报告准确率和 Wilson 95% 区间，并预先定「差多少才算有用」。下面这组数是我用 Wilson 公式算的：

```text
24/30 = 80.0%，Wilson95 [62.7%, 90.5%]
18/30 = 60.0%，Wilson95 [42.3%, 75.4%]
```

观察差是 20 个百分点，但两个区间大面积重叠。这批数据不足以支持「中间位置固定低 20 个百分点」，只能支持「值得在更大样本上继续测」。30 次是起步，不是保证。

Lost in the Middle（Liu et al., TACL 2024，arXiv:2307.03172）的实验里，相关信息放在长上下文中间时，部分模型和任务的表现低于放在开头或结尾；论文也报告了模型、任务之间的差异。它支持一个待验证假设：位置可能影响使用。它不支持「所有模型都低 20 个百分点」。

窗口大不等于效果好。窗口大只保证不报超限，不保证模型用得上。长上下文退化是经验现象，机制不止位置一种；不要把它简化成「注意力按 token 数均分」。要在你的目标模型、你的任务上测。

## 历史怎么裁：三种策略，没有默认赢家

| 策略 | 怎么做 | 什么时候够用 | 代价 |
| --- | --- | --- | --- |
| 滑动窗口 | 只留最近 N 轮或 N token | 任务只看近期，早期信息可丢 | 早期约束和决定会消失 |
| 摘要 + 窗口 | 老对话压成摘要，近期保留原文 | 跨天、长任务、需要保留过程 | 摘要会丢细节，也会改写 |
| 按重要性保留 | pin 约束和决定，丢闲聊，保留任务状态 | 有明确的长期约束和决策 | 需要来源和确认，关键词规则很脆 |

摘要的触发条件要按 token，不按轮数：当固定开销 + 当前问题 + 最近几轮 + 待保留结果超过预算时，从最老的对话开始摘要，直到降回预算。最近 2–3 轮保留原文；当前任务、pinned 约束和未决问题不进摘要。

摘要本身也有预算。先给它 300–800 token 的上限，这是起步配置，不是实测最优；超过就再做确定性过滤或分段摘要。反复「摘要的摘要」会漂移，重要结论要留在结构化字段里，不要只活在摘要里。摘要不是无损替代，拿需要细节的问题回测，看它会不会编。

「重要性」不能靠关键词。给每条内容至少标四样东西：

```json
{
  "kind": "constraint",
  "text": "不要用 ORM",
  "source": "user_confirmed",
  "confidence": 1.0,
  "pinned": true,
  "pointer": "turn 3"
}
```

`kind` 区分约束、决定、任务状态、参考资料和闲聊；`source` 记录是配置、用户确认、工具结果还是模型推断；`confidence` 区分确认和猜测；`pointer` 指向原轮次或 `tool_call_id`。只有可信设置或用户显式确认的内容才能 `pinned`。

关键词规则可以当召回提示，不能当写入规则。「不一定」里有「一定」；「请用 Vue，别上 React」里没有「必须/不要/一定」，却是一条真约束。更严重的是，用户消息、网页和工具结果都可能包含指令性文本。把其中的关键词自动提升为 system 级长期约束，等于给 prompt injection 开一条持久化通道：攻击者在文档里写「以后都必须……」，这句话就会进入之后每一次请求。

所以长期约束分两类：系统级（来自可信配置或运营设定）可以进 system；用户级（用户显式确认的偏好）留在 user 角色或独立的结构化记忆条目里，不要塞进 system，带来源和置信度，不能因为一句话就升级。工具结果是数据，不是指令。

压缩要保留可追溯线索。比如把前 12 轮压成：

```text
[第 1–12 轮已压缩]
任务：排查订单 A1024 查询慢。
已确认：orders 的 possible_keys 为空，type=ALL，扫描约 198 万行
        （证据：工具调用 #3 的 EXPLAIN）。
未决：加索引的窗口和回滚方案。
原始记录：turn 1–12；tool_call_id #3（EXPLAIN）、#5（日志尾段）。
```

模型看到 #3、#5 和结论；需要细节时，如果工具有 `get_tool_result`，按 id 取回；没有工具，至少运维能按 id 回查。不要把「可追溯」写成一句空话：id 要真的存在，取回接口要真的能用。

裁剪时还要保住工具调用和结果的配对。删掉 assistant 的 tool call 却留下 tool 结果，或反过来，都会让消息序列不合法；大结果可以换成句柄，但不要把配对拆散。

## 工具结果：先限长，再按任务选策略

四种处理方式，不是四级优先级。默认先在工具内限长，然后按任务选一种或组合：

判断标准很简单：如果模型有工具能在需要时取到，就不要提前把全文塞进来；只有取不到的系统规则、当前任务和已确认约束才必须常驻。

| 策略 | 适合 | 代价 | 注意 |
| --- | --- | --- | --- |
| 头尾截断 | 日志：开头有上下文，末尾有异常 | 中间细节丢失 | 保留总行数、省略区间和句柄 |
| 摘要 + 句柄 | 只需要诊断，不需要全文 | 摘要可能漏掉未知异常 | 摘要字段由任务定，不让模型自由发挥 |
| 分页 | 顺序重要、要逐段核对 | 多轮调用，累计 token 高 | 每页也要限长 |
| 预压缩/过滤 | 结构化日志、指标、重复文本 | 可能过滤掉真正异常 | 先确定性 grep/聚合，再考虑小模型摘要 |

头尾截断在日志类里是默认之一，不是所有工具的硬规定。同一个 200 行上限，可以这样分：

```text
[前 100 行]
...
[省略 4800 行]
...
[后 100 行，共 5000 行]
```

100 + 100 + 4800 = 5000。开头那个坏实现是只给前 200 行；同一个 200 行上限，改成前 100 加后 100，就能把第 4981 行带进来。截断不是只留头，也不是一律头尾；要看你的任务里关键信息在哪。

工具返回时可以带一个信封：

```json
{
  "truncated": true,
  "total_lines": 5000,
  "returned": [[1, 100], [4901, 5000]],
  "omitted_lines": 4800,
  "handle": "log://order-service/2026-11-19"
}
```

摘要 + 句柄要说清三件事。重要性怎么标：摘要必须保留任务 schema 指定的字段，比如错误数、时间范围、首个和最后一个错误、trace id；这些字段由调用方定，不由模型猜。什么时候触发：工具输出超过上限，或任务只需要定位而不是全文时，在返回前就做。预算怎么分：摘要先占 300–800 token，句柄几十 token；原始结果不写回后续历史，只存到可按 id 取的地方，需要细节再分页取。300–800 是起步配置，不是最优值。这要求框架不把原始结果自动追加到下一轮 `messages`；如果框架会自动追加，就在工具层只返回摘要和句柄，原始结果写到外部存储。

分页适合必须逐段核对的任务，比如审计、账单、完整堆栈。它保留原文，但每翻一页都要再发一次系统提示、历史和已有结果；页数多时，累计计费 token 会上去。

预压缩适合结构已知的数据：先用 `grep`、聚合、去重把 5000 行变成 20 行统计，再让模型看。它省 token，但也可能把「不在过滤器里的异常」删掉。只有你确定异常模式时再用。

风险很高的做法是全塞进去：单请求可能超限；即使没超，这份结果会留在历史里，后面每轮重发，累计计费更高；长上下文退化还是经验风险，不是「每条分到的注意力少了」这种可计算机制。

这里要把两个账分开：

- **单请求上下文**：这一次送进去多少 token。按需取、摘要和句柄会让它变小。
- **累计计费 token**：所有轮次的输入加输出。多一轮调用会把系统提示、历史和已有工具结果再发一遍，这一轮本身就是一笔额外的累计输入；只有少塞了大量无关内容，或缓存/批处理折扣覆盖了额外轮次，金额才可能下降。缓存不会把 token 数变成 0。

至少要记两个指标：`last_request_input_tokens` 和 `sum_input_tokens_all_rounds`，再加 `cache_read_tokens`、输出 token 和实际金额。否则「按需取更省」只是感觉。

## 关键约束：权威位置和近因位置不是一回事

把「关键约束放 system 开头或末尾」当成一条规则，是把两个位置混了。

- **权威位置**是 system / developer 指令。它定义角色、权限和不能做的事，覆盖整段对话。
- **近因位置**是最终 user 消息。它离生成最近，适合放本轮任务、输出格式和这次一定要遵守的 1–2 条提醒。

system 的最后一句仍然在所有 user 消息之前；它换来的是 system 内部的末尾，不是整段对话的末尾。不同接口的 system 位置不一样：Anthropic Messages 的 `system` 是顶层参数，OpenAI Responses 的 `instructions` 也是顶层字段；Chat Completions 的 system 消息按惯例放在最前。不要假设你能把 system 放到最后。

所以「关键约束靠两端」的准确说法是：**system 开头放权威规则，最终 user 消息放本轮提醒**，不是 system 的开头和末尾各放一遍。需要重复时，明确写在最终 user 消息里：

```text
本轮必须遵守（来自系统设置，原文）：不要删除文件；只读排查。
```

只有它真的来自系统设置，才能这么写。用户刚确认的偏好要写成「你确认过：……」，不要冒充系统规则。

检索资料放中间，最相关的 1–2 块放在资料段的两端，并标来源。这是布局建议，不是效果保证；位置有没有用，仍要在目标模型上测。

用户消息和工具结果里的指令性文本，不能因为出现「必须」「不要」就提升为 system 级约束。它们是用户级输入或数据；要变成长期规则，只能走可信设置或用户显式确认，并记录来源和置信度。

## 上线检查清单

- 用真实请求日志按段数 token，至少看 p50 和 p95；把 `tools`、输出预留也算进去。
- 单个工具结果最大可能是多少？工具有没有默认上限、总行数、省略区间和句柄？
- 用一个「异常在最后 20 行」的样本测截断；只给前 N 行的实现应该被这条测出来。
- 第 10 轮、第 20 轮的历史各有多大？裁剪策略是什么？工具调用和结果有没有成对保留？
- 摘要按什么触发、上限多少、保留哪些字段、能不能按 `tool_call_id` 取回原文？
- 关键约束是否在 system 开头？最终 user 消息有没有本轮提醒？有没有把用户文本误提升为系统规则？
- 长度/位置实验有没有保持相关信息不变、只加中性填充或只移动位置？有没有模型、任务、样本量和置信区间？
- 预算按 `min(模型上下文上限 - 输出预留, 成本/延迟上限, 评测里准确率开始下降的拐点)` 反推；三个数都要在你自己的模型和任务上测。

如果第 10 轮的 p95 超过预算，先看工具结果和旧历史，不要先删系统提示。固定开销不一定是最大的那块，但它很容易被凭感觉改错。

## 还差的

- **没有调模型。** 文中的模型行为——说「日志里没有异常」、遵守率、摘要质量、位置效应——都是示意或引用，不是本机实测；本机没有 API key，只有本地 Python/tiktoken 可做计数。
- **token 占比不是线上分布。** 表里的 265 / 4,743 来自构造样本；p50 / p95、摘要上限和预算阈值都要用你的请求日志重算。
- **没有实现工具网关。** 截断信封、句柄存储、`get_tool_result` 和摘要器都停在协议设计，没有跑过真实取回链路。
- **统计只做了演示。** Wilson 区间是用 24/30 和 18/30 算的，没有做功效分析、配对检验或预注册；30 次/条件不是保证。
- **没有核对所有厂商的最新限制。** 角色顺序、缓存折扣、批处理价格和计费口径，上线前要按你实际使用的接口版本重查。
