## 先把结论摆出来

上下文工程听起来玄，其实就是一句话：**在有限的窗口里，决定放哪些内容、按什么顺序放。**

它比"提示词工程"大一圈——提示词只是其中一部分，历史、检索结果、工具描述、工具返回全都在抢同一块空间。

窗口再大也是有限的，而且**塞得越多，模型对每一条的注意力越少**。这是所有取舍的根源。

## 四类内容在抢同一块空间

```text
[系统提示词]      ← 固定成本，每次都带
[工具描述]        ← 工具越多越贵
[历史消息]        ← 随轮次线性增长
[检索/工具结果]   ← 单次可能很大
[当前问题]        ← 最小
```

真实的 Agent 里，**历史消息和工具结果通常是最大头**，不是系统提示词。

一个实测比例：某排查类 Agent 的第 5 轮请求，各部分占比大致是

```text
系统提示词    8%
工具描述      6%
历史消息     52%
工具结果     32%
当前问题      2%
```

所以优化上下文要先看历史和工具结果这两块，而不是反复精简提示词——**改错地方等于没改**。

## 三条取舍原则

### 原则一：离当前一步越近，越该靠两端

模型对长上下文中部的注意力会下降——这叫"丢了中间"（lost in the middle）。

实践含义：

- 关键约束（"不得删除文件"）放在**系统提示词开头**或**末尾**，别埋在中间；
- 当前问题和最相关的检索结果放在**最后**；
- 大段的参考资料放中间，反正它本来就是被"查阅"的。

一个可测的验证方法：把同一条约束分别放在提示词的第 3 行、第 50 行、最后一行，各跑 50 次任务，统计遵守率。中间那份通常低 20 个百分点以上。

### 原则二：宁可按需取，不要一次全塞

一次塞 20 条检索结果，不如让模型先看 3 条，不够再查。

后者多一轮调用，但总 token 往往更少，且准确率更高——因为它不会在 20 条里被噪声带偏。

判断标准：**如果模型有工具能自己取，就别提前塞**。

这也是"给工具"和"塞内容"的分界线：能被按需获取的信息，塞进去就是浪费；无法按需获取的（比如系统规则），才必须塞。

### 原则三：压缩要保留可追溯性

摘要会丢信息。所以压缩历史时，要保留"可以回去查"的线索：

```text
（前 12 轮：排查订单查询慢，已确认缺联合索引，
  详见工具调用 #3、#5 的原始结果）
```

这样模型知道"如果需要细节，可以去查 #3"——如果它有工具的话。没有工具就至少保留关键结论。

## 历史怎么裁

**滑动窗口**：只留最近 N 轮。简单，但早期信息彻底丢失。

**摘要 + 窗口**：老对话压成一段，近期保持原文。多数产品用这个。

**按重要性保留**：给每轮打个标记，用户明确说过的约束（"别用 XX 框架"）永久保留，闲聊丢弃。

第三种最好但要有机制。一个轻量做法：**用户消息里出现"必须/不要/一定"这类词时，单独抽出来放进一个"长期约束"区块**，不参与裁剪。

```text
## 长期约束（不随对话裁剪）
- 不要用 ORM
- 回答控制在 300 字内
```

这个区块每次都带，成本固定（几百 token），但它保证了最关键的信息不会因为窗口滑动而消失。

## 工具结果特别大怎么办

一次工具调用返回了 5000 行日志——这是上下文最容易爆的地方。

四个处理方式，按优先级：

1. **在工具里就截断**：返回前 200 行 + "共 5000 行，已截断"。截断逻辑放在工具里，不要指望模型自己忽略；
2. **返回摘要 + 句柄**：返回统计信息（错误数、时间范围）和一个 id，需要细节时再调工具取；
3. **分页**：工具支持 `offset`，模型自己翻；
4. **压缩后再给**：用小模型先摘要一遍。最贵，最后考虑。

**最坏的做法是全塞进去**：既贵，又因为太长导致模型看不到关键那几行。

第一条的实现要点：截断时**保留头尾**往往比只保留头更有用。日志的异常通常出现在末尾，而上下文信息在开头。

```text
[前 100 行]
...
[省略 4800 行]
...
[后 100 行]
```

## 一个可用的检查清单

上线前问自己五个问题：

- 系统提示词里有没有一条规则可以删掉而不影响效果？
- 工具描述加起来占了多少 token？有没有工具从没被调用过？
- 历史在第 10 轮时有多大？有没有上限？
- 单个工具结果最大可能是多少？有没有截断？
- 关键约束是不是埋在中间？

第三和第四条通常能发现最大的浪费。一个经验值：**如果第 10 轮的请求超过 30k token，而任务本身不需要那么多信息，说明裁剪策略有问题**。

## 常见误区

### 误区：窗口够大就不用做上下文管理

**你以为**：200k 窗口，随便塞。
**其实**：成本按 token 线性涨，延迟随长度增加，且中部注意力下降。窗口大只意味着"不会报错"，不意味着"效果不变差"。
**怎么验证**：同一任务分别用 5k 和 50k 的上下文跑，比较准确率与耗时。

### 误区：优化上下文就是精简系统提示词

**你以为**：提示词短了就省了。
**其实**：系统提示词是固定成本，历史和工具返回才是变量大头。省错地方等于没省。
**怎么验证**：统计一次真实请求里各部分的 token 占比——历史通常是提示词的几倍。

### 误区：摘要能无损替代原文

**你以为**：压成一段话就等价了。
**其实**：摘要由模型生成，会丢细节也可能记错，且不可追溯。
**怎么验证**：让模型基于摘要回答需要细节的问题，看它是否会编。

### 误区：截断就是保留前面一部分

**你以为**：取前 N 行就行。
**其实**：日志的关键信息常在末尾（异常、最终状态），只留头会丢掉最有用的部分。
**怎么验证**：对比"只留头"和"留头尾"两种截断，看模型定位问题的成功率。

## 小结

上下文工程就是"窗口有限，放什么进去"。四类内容抢同一块空间，历史和工具返回通常是大头。三条原则：关键信息靠两端、按需取而非全塞、压缩保留可追溯线索。工具结果必须在工具内部截断，且保留头尾。
