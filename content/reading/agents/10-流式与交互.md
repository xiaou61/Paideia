## 先把结论摆出来

Agent 的响应时间是**几十秒到几分钟**，而用户的耐心只有几秒。

```sketch

  "rows": [

      { "id": "wait", "title": "等全部算完", "sub": "几十秒白屏", "tone": "amber" },
      { "id": "stream", "title": "边算边流", "sub": "第一个字很快就到", "tone": "blue" },

    ]

  "arrows": [
    { "from": "wait", "to": "stream" },
    { "from": "stream", "to": "state" }
  ]
}
```

不解决这件事，功能做得再好也没人用——**用户看不到进度就会以为卡死了**，然后刷新、重发、放弃。

流式不是"锦上添花的体验优化"，是 Agent 类功能的**可用性前提**。

## 时间花在哪

一个 5 轮工具调用的任务，时间大致这样分配：

```text
模型思考（首 token 前）  1–3 秒 × 5 轮 = 5–15 秒
工具执行                0.1–10 秒 × 5 轮
输出生成                2–10 秒
```

两件事由此而来：

1. **首 token 慢**是主要体感来源——第一轮就要等好几秒才有动静；
2. **中间的工具调用**是纯等待，用户看不到任何东西。

第二条比第一条更严重。首 token 慢至少最后会出字，而工具执行期间如果没有任何提示，界面就是彻底静止的——用户会认为程序挂了。

## 三个层次的反馈

### 一、文本流式

模型输出时逐字推送。这是最基础的，所有 SDK 都支持。

实现要点：服务端用 SSE 或 chunked 推送，客户端增量渲染。

**注意别把"每来一个 token 就重渲染整段 Markdown"**——那会卡，而且 Markdown 在流式过程中是"半成品"（代码块还没闭合、列表还没结束），渲染会闪烁。

### 二、步骤可见

比流式文本更有用的是**告诉用户在做什么**：

```text
正在检索相关文档…
已找到 3 篇，正在阅读…
正在生成回答…
```

这一层的信息量比文本流大得多，因为它解释了"为什么还没出结果"。

代价是模型每轮的意图要先解析出来再推给前端。多数框架把工具调用当作结构化事件流的一部分，能直接转发。

一个细节：**步骤文案要用用户能懂的话**。"调用 search_code" 不如 "正在检索相关文档"。技术细节可以放在可展开的地方，不要放在主界面上。

### 三、可中断

用户看到"正在检索"时，如果能点"停"，体验就完整了。

中断要处理三件事：

- **取消上游请求**（别让它继续烧 token）；
- **保留已有输出**（别把已经显示的内容清掉）；
- **状态一致**（服务端记的会话状态要和界面对上）。

第三件最容易漏。取消后如果服务端还把这一轮记进历史，下次对话就会出现"用户没说过的话"。

## 一个常见的架构错误

**把整个 Agent 循环塞进一个 HTTP 请求，最后一次性返回。**

问题不只是慢：

- 中间任何一步超过网关超时，整个请求就断了，而模型可能还在跑；
- 用户没有任何进度感知；
- 长连接占着资源，并发能力差。

正确做法是**流式返回**，并且让前端能区分"文本增量"和"步骤事件"两类消息。消息类型要在协议里定清楚，别靠猜。

一个可用的消息设计：

```text
event: step       data: {"kind":"tool_start","name":"检索文档"}
event: step       data: {"kind":"tool_done","count":3}
event: delta      data: {"text":"根据检索到的"}
event: delta      data: {"text":"资料…"}
event: done       data: {"usage":{"input":8200,"output":340}}
```

分开的好处：前端可以把 `step` 显示在进度区、把 `delta` 显示在正文区，各管各的。

## 流式 Markdown 的坑

如果回答里有 Markdown（代码块、表格、列表），流式渲染会遇到：

- 代码块还没闭合时，渲染器会把后面的内容当成代码；
- 表格只到一半时，列数不对；
- 数学公式 `$` 只出现一个时，后面的内容被当成公式。

三种应对：

1. **只在完整块上渲染**：遇到未闭合的代码块，先当纯文本显示，闭合后再渲染；
2. **用支持"流式容错"的渲染库**：有些库专门处理半成品状态；
3. **降级**：流式过程中全部按纯文本显示，结束后再整体渲染一次。

第三种最简单，体验也够用——**用户在意的是"有没有在动"，不是"代码高亮什么时候出现"**。

## 思考过程要不要给用户看

如果模型有思考内容（reasoning），三个选择：

- **不展示**：最省事，但用户不知道它在想什么；
- **展示但默认折叠**：多数产品的选择。想看的人点开，不想看的人不受干扰；
- **直接展示**：只适合开发者工具。

不管选哪个，**思考内容不要进历史消息**。它占 token、对后续轮次没有帮助，而且某些上游会拒绝带思考内容的历史请求。

这一条在实践里踩过：把带思考的历史发给上游，返回 400。而错误信息往往很模糊，容易误判成别的问题。

## 常见误区

### 误区：先把功能做对，体验后面再优化

**你以为**：慢一点没关系，先能用。
**其实**：几十秒无反馈的功能，用户根本走不到"能用"那一步。
**怎么验证**：让一个没参与开发的人试一次，观察他在第几秒开始点刷新。

### 误区：流式就是把最终结果切片发出去

**你以为**：把完整回答分成小块推送就是流式。
**其实**：真正的流式要在**生成过程中**转发，且要包含工具调用这类非文本事件。
**怎么验证**：看首字节时间——如果等于完整生成时间，那就不是真流式。

### 误区：思考过程放历史里没关系

**你以为**：反正模型能忽略。
**其实**：它占 token、对后续无帮助，且某些上游会拒绝带思考内容的历史请求。
**怎么验证**：把带思考内容的历史发一次，看上游是否报错或效果变差。

### 误区：取消就是把前端请求 abort 掉

**你以为**：前端断开就完事了。
**其实**：上游可能还在跑、服务端可能还在写历史，前端断开只解决了三件事里的一件。
**怎么验证**：取消后查服务端日志，看上游请求是否还在、这一轮是否仍被记进历史。

## 小结

Agent 慢是常态，流式是可用性前提。三层反馈：文本流式、步骤可见、可中断。中断要同时处理上游取消、保留输出、服务端状态一致。流式 Markdown 有半成品问题，先当纯文本是最省事的解。思考内容默认折叠，且不进历史。
