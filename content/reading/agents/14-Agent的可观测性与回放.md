## 先把结论摆出来

Agent 出问题时，最没用的一句话是"模型不行"。有用的问题是：**哪一步、花了多少、卡了多久、为什么失败。**

```sketch
{
  "title": "出问题时要能回答这四问",
  "rows": [
    [
      { "id": "where", "title": "哪一步", "sub": "第几轮、哪个工具", "tone": "gray" },
      { "id": "cost", "title": "花了多少", "sub": "token 与耗时", "tone": "blue" },
      { "id": "stuck", "title": "卡了多久", "sub": "哪一次调用时间长", "tone": "blue" },
      { "id": "why", "title": "为什么失败", "sub": "报错原文与入参", "tone": "green" }
    ]
  ],
  "arrows": []
}
```

可观测性不是"多打日志"，而是把一次任务拆成可查询的结构：

1. **trace 与 span**：一次任务是一条 trace，每次模型调用、工具调用、检索、校验、重试是一个 span；
2. **工具记录**：调了什么、参数是什么、返回多大、耗时多少、错误类型是什么；
3. **token 与成本**：每个 span 的输入、输出、缓存命中，按任务和用户汇总；
4. **延迟拆解**：排队、首 token、生成、工具执行、重试各占多少；
5. **失败分类**：模型、工具、超时、权限、编排、输入，分别计数；
6. **脱敏与回放**：能查清问题，但不泄露数据；能固定现场，而不是再赌一次；
7. **采样与告警**：线上持续采样，异常能主动发现，失败样本能进评测集。

一个前提要先说清楚：**回放不是"再跑一遍"。** 模型有随机性，外部系统会变，时间、权限、数据都可能不同。真正的回放是**用记录下来的输入和工具结果重建现场**，副作用工具用桩或沙箱，绝不在生产环境重放写操作。

## trace 与 span：一次任务是一棵树

先统一两个词。

- **trace（追踪）**：一次用户任务的全过程，从收到请求到返回最终答案。它有一个 `trace_id`，贯穿所有日志。
- **span（跨度）**：trace 里的一个操作。模型调用、工具调用、检索、参数校验、重试、护栏检查，各是一个 span。span 有父子关系，能拼成一棵树。

一棵典型的树：

```text
trace task-8f3a  (总 33.7s, $0.104)
├─ span plan            model   1.8s   1.2k in / 300 out
├─ span search_logs     tool   18.4s   返回 48,000 字符 ≈ 12k token
├─ span summarize       model   6.1s  16.5k in / 600 out
├─ span get_order       tool    0.3s   403 permission denied
├─ span get_order retry tool    0.4s   403 again
├─ span final           model   3.2s   9.0k in / 400 out
├─ span validate        guard   0.01s  fail: missing refund_eligible
└─ span final retry     model   3.5s   9.2k in / 420 out
```

没有这棵树，你只能看到"任务失败"或"总耗时 33 秒"；有了它，你能直接说"18.4 秒花在 `search_logs`，47% 的成本花在 `summarize`，最后还因为一个必填字段重试了一次"。

每个 span 至少要有这些属性：

| 属性 | 用途 |
| --- | --- |
| `trace_id` / `span_id` / `parent_span_id` | 串起整条链路，定位父子关系 |
| `task_id` / `user_id_hash` | 按任务、按用户聚合；用户 ID 要哈希或脱敏 |
| `span_type` | model / tool / retrieval / guard / internal |
| `name` / `version` | 模型名与版本、工具名与版本、提示词版本 |
| `start_time` / `duration_ms` | 延迟拆解和瀑布图 |
| `status` / `error_type` / `error_code` | 成功、失败、超时、限流、权限 |
| `input_tokens` / `output_tokens` / `cached_tokens` | 成本和缓存分析 |
| `cost` / `currency` | 按 span 记账，避免只看到总数 |
| `round_index` / `retry_count` | 判断绕圈和重试 |
| `attributes` | 工具参数摘要、结果大小、检索文档 ID 等 |

如果团队已经在用 OpenTelemetry，可以参考它的 GenAI 语义约定来命名模型和工具相关的属性；没有的话，自己定一套稳定的字段名也行。**关键是字段名稳定、类型稳定、能跨服务关联**，而不是追某个标准。

一个常见错误是只在应用日志里打一行"调用模型失败"，没有 `trace_id`，也没有 span 层级。这样即使日志量很大，也回答不了"失败发生在第几轮、前一步是什么、当时上下文里有什么"。

## 工具调用记录：记什么、别记什么

Agent 和普通 API 最大的区别是它会调工具，而工具记录是最容易记错的部分。

| 字段 | 记什么 | 注意 |
| --- | --- | --- |
| 工具名与版本 | `lookup_order@v3` | 工具改了行为要能区分 |
| 参数 | 结构、类型、关键 id；敏感值脱敏 | 不要记录完整密钥、密码、身份证号 |
| 参数哈希 | `args_hash` | 用于关联同一次调用，不泄露原文 |
| 结果摘要 | 行数、字节数、状态码、前几条的脱敏摘要 | 不要把完整结果塞进 trace |
| 结果指针 | 对象存储地址或内部 ID | 需要时再去受控存储取 |
| 耗时 | 工具执行时间、排队时间 | 区分工具慢和模型慢 |
| 重试 | 第几次、为什么重试 | 403 重试通常是错的 |
| 错误 | `error_type`、上游错误码、是否可重试 | 不要只写"失败" |
| 权限决策 | 允许/拒绝、依据 | 越权排查的关键 |
| 幂等键 | 写操作的 `idempotency_key` | 回放和重试都靠它防重复副作用 |

**不要把完整工具结果写进 trace。** 原因有三个：结果可能包含用户隐私或密钥；结果可能很大，存储成本高；结果里可能藏着注入文本，进入日志系统后又是新的风险。正确做法是"摘要进 trace，原文进受控存储，用指针关联"。

但摘要也不能太省。只写 `result: "ok"` 等于没记；至少要有"返回了多少行/多少字节、耗时多少、是否被截断"。排查"为什么模型答错了"时，你往往需要知道"工具到底返回了什么"，这时再通过指针去取原文，而不是让所有人都能在日志平台里搜到。

工具错误要分类，不要一个 `FAILED` 打天下：

```text
TIMEOUT          超时
RATE_LIMITED     429
AUTH_FAILED      401/403
INVALID_ARGS     422/参数校验失败
UPSTREAM_5XX     上游服务错误
EMPTY_RESULT     成功但空结果
MALFORMED        返回格式不对
PERMISSION_DENIED 策略拒绝
```

不同类别的处理方式完全不同：超时和 5xx 可以重试；401/403 重试没有意义；422 要改参数；空结果要让模型知道"确实没有"，而不是让它编一个。

## token 与成本：按 span 记账

只记"这个任务花了多少 token"不够。要能回答"哪一轮、哪个工具之后、哪次重试最贵"。

每个模型 span 至少记录：

```text
input_tokens        总输入
cached_input_tokens 缓存命中部分
output_tokens       输出
reasoning_tokens    推理模型的思考 token（如果有）
cost                按当时价格算出的成本
price_version       价格表版本
```

成本公式：

```text
span 成本 =
  (input_tokens - cached_input_tokens) × 输入单价
  + cached_input_tokens × 缓存单价
  + output_tokens × 输出单价
```

任务成本是各 span 之和，再加上工具、检索、存储等外部成本。**成本要能按任务、用户、功能、模型版本四个维度聚合**，否则账单涨了只能看到总数。

一个容易忽略的点：**重试也是成本。** 一次校验失败后的重试，会重新发送整个上下文，可能比第一次还贵。如果只记录成功那一次的 token，就会低估真实成本。按 span 记账时，把失败和重试的 span 也保留下来，并在任务汇总里标明"其中重试成本多少"。

预算告警也应该建在 span 上：单任务成本超过阈值、单用户日成本超过阈值、某个工具的调用成本突然上升。只设全局月度预算，等发现时已经晚了。

## 延迟拆解：卡在哪一步

总时长是一个数，但它由很多段组成：

```text
总时长 =
  排队时间
  + 每轮模型时间（TTFT + 生成时间）
  + 工具执行时间
  + 检索时间
  + 校验与重试时间
  + 序列化与网络开销
```

串行执行时，这些时间相加；并行工具调用时，同一层的工具取最大值，不是相加。做延迟优化前，先画瀑布图，确认哪一段最长。

几个常见误判：

- **"模型太慢"**：其实模型只占 40%，剩下 60% 是工具。上面的例子里，模型总时间 14.6 秒，工具总时间 19.1 秒，`search_logs` 一个就占了 18.4 秒。
- **"总时长 30 秒，用户等不了"**：先看 TTFT。如果首 token 2 秒、后面 28 秒是生成，流式可以让用户早看到内容；如果 TTFT 15 秒，流式也救不了。
- **"平均延迟 8 秒，还行"**：看 p95。平均值会被大量快请求拉低，尾部可能已经 40 秒。
- **"重试一次不贵"**：一次重试可能增加 3 到 5 秒，而且把整个上下文再发一遍。重试率高的任务，延迟和成本都会明显变差。

延迟记录要区分 `ttft_ms` 和 `total_ms`，并按 span 记录 `duration_ms`。没有 TTFT，你无法判断"慢"是排队/预填充慢，还是生成慢。

## 失败分类：模型、工具、超时、权限

"任务失败"不是一个可行动的结论。至少要分成下面几类，并分别计数。

| 类别 | 典型信号 | 通常的责任方 | 处理 |
| --- | --- | --- | --- |
| 模型/输出 | schema 不合法、字段缺失、拒绝回答、空回答、选错工具 | 提示词/模型 | 带错误重试、改提示词、换模型、补评测 |
| 工具 | 4xx/5xx、返回格式错、空结果、结果过大 | 工具 owner | 修工具、加超时、截断、降级 |
| 超时 | deadline exceeded、排队过久、p95 突增 | 基础设施/编排 | 超时预算、并行、取消、扩容 |
| 权限 | 401/403、归属校验失败、策略拒绝 | 安全/产品 | 不重试、修权限、人工确认 |
| 编排 | 超过最大轮次、上下文溢出、重复调用 | 应用 | 停止条件、去重、摘要压缩 |
| 输入 | 信息缺失、歧义、注入、超长 | 产品/交互 | 追问、校验、限制长度、护栏 |

分类要打在**失败发生的那个 span 上**，而不是只打在任务上。一个任务失败，可能是 `get_order` 403 导致后面全错；如果你只记"任务失败：模型输出错误"，就会把排查方向带偏。

重试策略要跟错误类型绑定：

```text
可重试：TIMEOUT、RATE_LIMITED、UPSTREAM_5XX
不重试：AUTH_FAILED、PERMISSION_DENIED、INVALID_ARGS、注入拦截
谨慎重试：EMPTY_RESULT（可能确实没有数据）
```

一个真实的反例：某次 `get_order` 返回 403，通用重试策略又试了两次，每次 0.3 到 0.4 秒，最后任务仍然失败，还多花了 token 和延迟。更糟的是，如果工具是写操作，盲目重试可能造成重复副作用。**403 不是"再试一次就会好"的错误。**

## 脱敏：能查清和不能泄漏的平衡

可观测性最大的矛盾是：**排查需要细节，合规要求少存。**

原则是"**结构保留，值脱敏**"。比如工具参数：

```json
{
  "order_id": "ord_8f3a****",
  "email": "u***@example.com",
  "phone": "138****5678",
  "card_last4": "****"
}
```

你仍然能看出参数类型对不对、有没有传错字段，但看不到完整敏感值。

具体做法：

1. **在源头脱敏**：日志/trace SDK 在采集时就过滤，不要先写原文再事后清洗；
2. **按字段白名单**：只允许已知安全的字段进入 span 属性，其他字段一律哈希或丢弃；
3. **敏感原文分离存储**：需要排查时，把完整请求/响应存到加密、受控、有审计的对象存储，trace 里只放指针；
4. **用户 ID 哈希**：用带盐哈希，既能按用户聚合，又不直接暴露身份；
5. **保留期限**：trace 默认保留 7 到 30 天，敏感原文更短；支持按用户删除；
6. **访问控制**：不是所有工程师都能看完整 prompt；调试模式要审批、要记录谁看过。

提示词本身也可能含敏感信息：系统提示词里可能有内部规则、工具清单、业务逻辑，用户消息里可能有隐私。**默认不要记录完整 prompt**；需要时记录哈希、长度、模板版本，或者只在受控调试模式下开启。

脱敏过度的反面是"什么都查不到"：把参数全打成 `***`，你就无法判断是参数错了还是工具错了。好的脱敏保留形状和类型，只隐藏值。

## 回放：固定现场，而不是再赌一次

回放的价值是回答"如果当时换一个提示词/模型/参数，会发生什么"，以及"这次失败到底卡在哪一步"。

回放要记录的东西：

```text
完整的消息序列（system / user / assistant / tool）
每次工具调用的参数与结果（或结果指针）
模型名与版本、温度、top_p、max_tokens、seed（如果支持）
提示词版本、工具版本、检索索引版本
检索到的文档 ID 或快照
时间、随机数、feature flag、用户权限
```

三种回放模式，用途不同：

| 模式 | 做法 | 适合 | 风险 |
| --- | --- | --- | --- |
| 重建 | 用记录下来的模型输出和工具结果，重放编排逻辑 | 排查代码、提示词、分支问题 | 不能发现"换个模型会怎样" |
| 重跑 | 用记录下来的输入重新调用模型 | 对比提示词/模型/参数 | 结果不完全可复现，要看分布 |
| 沙箱重放 | 工具用桩返回记录结果，写操作全部拦截 | 安全地测试整条链路 | 桩数据可能与真实系统漂移 |

**回放写操作工具是红线。** 退款、发消息、删数据这类工具，在回放时必须替换成桩，或者用只读的沙箱环境。不要因为"只是再跑一次"就把真实副作用放出去。

回放的排查方法是**找第一个分歧点**：

1. 从 trace 根节点往下走，对比每一步的输入、模型输出、工具结果；
2. 找到第一处与预期/线上不同的地方；
3. 看那一层的输入里是不是少了字段、多了无关内容、工具返回变了、权限变了；
4. 只针对这一层做实验，不要一上来就改整个提示词。

回放不能保证 100% 复现。模型可能已经升级、温度采样有随机性、外部 API 返回变了、时间影响了业务逻辑。所以：

- 需要确定性时，用"重建"模式，固定模型输出和工具结果；
- 需要比较效果时，用"重跑"模式，跑多次看通过率，而不是只看一次；
- 记录模型版本，供应商弃用旧模型后，回放结果要标注"模型已变"。

## 从 trace 到评测集与回归

线上 trace 是评测集最好的来源。流程可以固定成：

```text
发现失败 trace
  → 脱敏、最小化输入
  → 写清期望行为（必须调用什么、不能调用什么、输出要有什么）
  → 加入评测集
  → 每次改提示词/模型/工具都跑
  → 通过率、成本、延迟不倒退才放行
```

一条来自 trace 的评测用例至少包含：

- 输入（脱敏后的用户输入、必要的上下文）；
- 期望的工具序列（例如必须先 `lookup_order`，不能调用 `refund`）；
- 期望的输出约束（schema、必含字段、禁止内容）；
- 来源 `trace_id`，便于回溯；
- 失败类型标签，便于按类别统计。

回归判据要用**性质断言**，不要用"输出必须等于某段文字"。比如：

```text
- 输出是合法 JSON，且 category 在枚举内
- 调用了 lookup_order，且 order_id 与输入一致
- 没有调用任何写操作工具
- 回答中包含「预计送达时间」，且不包含「保证退款」
- 单任务成本 < 0.05 元，p95 延迟 < 15 秒
```

每次发版前跑评测集，看四个数：通过率、每成功任务成本、p95 延迟、最差失败类别。**通过率不降、成本不涨、延迟不退化**，才算过关。更严格的话，按失败类别设阈值：格式错可以容忍少量，越权和数据泄露必须为零。

## 线上采样与告警

全量记录成本高，采样是必须的，但要"按需采样"：

- **错误和慢请求全采**：失败、超时、p95 以上的 trace 一律保留；
- **成功请求按比例采**：5% 到 10% 就够看趋势，新版本上线初期可以提高；
- **按用户/租户分层**：大客户、异常用户单独采样，避免小样本偏差；
- **尾部采样**：先收全量 span，任务结束后根据结果决定保留哪些，比请求开始就随机采样更准。

告警要围绕"能行动"的指标，不要什么都报：

| 告警 | 触发条件示例 | 先看什么 |
| --- | --- | --- |
| 任务失败率 | 5 分钟内失败率 > 10% | 失败分类 Pareto，最大类别 |
| 工具错误率 | 某工具 5xx/超时 > 5% | 工具上游状态、最近发布 |
| p95 延迟 | 连续 10 分钟 > 阈值 | 瀑布图，最大 span |
| 单任务成本 | 日均成本比基线高 30% | 按 span/模型/工具拆 |
| 最大轮次命中率 | 超过 5% 的任务触顶 | 提示词停止条件、工具返回 |
| schema 失败率 | 校验失败 > 3% | 模型/提示词/输出预算 |
| 注入/越权 | 出现即告警 | 安全事件流程 |

告警必须能点进 trace。只告诉你"失败率升高"而没有样本，等于把排查工作推给下一个人。

缓解动作也要提前写进 runbook：回滚提示词/模型、禁用某个工具、调高超时、降级到小模型、切人工。**先止血，再定位**，不要在现场一边查一边改。

## 一个具体例子

用户问："我的订单 12345 还没到，能退吗？"

Agent 跑了 5 轮工具循环，最终回答"查不到订单，请确认订单号，已转人工"。任务成功，但耗时 33.7 秒，成本 $0.104。按 1000 次/天算，一天 $104，一个月约 $3,100。

trace 拆开是这样（价格假设：输入 $3/百万，缓存 $0.30/百万，输出 $12/百万）：

| span | 类型 | 耗时 | 输入 | 缓存 | 输出 | 成本 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| plan | model | 1.8s | 1,200 | 0 | 300 | $0.0072 | ok |
| search_logs | tool | 18.4s | - | - | - | $0 | ok，返回 48,000 字符 |
| summarize | model | 6.1s | 16,500 | 3,000 | 600 | $0.0486 | ok |
| get_order | tool | 0.3s | - | - | - | $0 | 403 |
| get_order retry | tool | 0.4s | - | - | - | $0 | 403 again |
| final | model | 3.2s | 9,000 | 3,000 | 400 | $0.0237 | ok |
| validate | guard | 0.01s | - | - | - | $0 | 缺 `refund_eligible` |
| final retry | model | 3.5s | 9,200 | 3,000 | 420 | $0.0245 | ok |
| **合计** | | **33.7s** | **35,900** | **9,000** | **1,720** | **$0.104** | |

三个结论直接从这个表里出来：

**第一，卡在工具，不在模型。** `search_logs` 18.4 秒，占总时长 54.6%；所有模型调用加起来 14.6 秒，占 43.3%。用户感觉"模型慢"，其实是一个日志搜索工具在慢。

**第二，钱花在一个过大的工具结果上。** `search_logs` 返回 48,000 字符，约 12k token，直接进入 `summarize` 的输入。`summarize` 一次花了 $0.0486，占任务成本 46.7%。如果只截取最近 200 行、约 2k token，这一段的输入从 16.5k 降到 6.5k，成本约 $0.0186，单任务省 $0.03；1000 次/天就是 $30/天。

**第三，有一次不该发生的重试。** `get_order` 返回 403（权限不足），通用重试策略又试了一次。403 重试不会变好，只多花 0.4 秒；更危险的是，如果这是写操作，可能造成重复副作用。重试策略要按错误类型区分。

还有一次校验失败：最终 JSON 要求 `refund_eligible`，但模型没给，触发 `final retry`，多花 3.5 秒和 $0.0245，占成本 23.6%。这个字段在"查不到订单"时本来就不适用，schema 应该允许 `null`，或者由代码先算出默认值，而不是让模型猜。

修复后：

```text
search_logs 加时间范围和 limit，返回从 48k 字符降到 2k token，耗时 18.4s → 4.0s
工具结果在进入模型前截断，summarize 输入 16.5k → 6.5k
403 不再重试，去掉 0.4s 和一次无效调用
refund_eligible 允许 null，去掉 final retry
```

新 trace：

```text
总耗时：1.8 + 4.0 + 6.1 + 0.3 + 3.2 + 0.01 ≈ 15.4s
总成本：0.0072 + 0.0186 + 0.0237 ≈ $0.050
```

同一个任务，33.7 秒降到 15.4 秒，$0.104 降到 $0.050，评测集通过率保持 94%。这不是"换了个更强的模型"，而是**把 trace 里最大的两段砍掉了**。

## 常见误区

### 误区：有日志就叫可观测

**你以为**：应用日志里记了请求和错误，出问题查日志就行。
**其实**：没有 `trace_id`、没有 span 层级、没有结构和字段约定，日志只能告诉你"失败了"，不能告诉你"第几轮、哪个工具、花了多少"。
**怎么验证**：拿一条真实的失败任务，只打开现有日志，试着回答"第几轮失败、当时工具返回了什么、重试了几次"。答不上来就是不可观测。

### 误区：回放就是再跑一遍

**你以为**：把同样的输入再发给模型，就能重现问题。
**其实**：模型有随机性、外部系统会变、时间和权限也会影响结果；重跑写操作还可能造成真实副作用。回放要固定记录，区分"重建"和"重跑"。
**怎么验证**：同一条 trace 重跑 5 次，比较工具序列和最终答案；如果每次都不一样，说明你需要记录输入和工具结果，而不是只靠重跑。

### 误区：记录越全越好

**你以为**：把完整 prompt、完整工具结果都存下来，排查最方便。
**其实**：里面可能有用户隐私、密钥、注入文本；存储成本和访问风险都会上升。正确做法是"结构保留、值脱敏、原文受控存储"。
**怎么验证**：检查 trace 存储里有没有明文邮箱、手机号、token；再试着执行一次"按用户删除数据"，看能不能删干净。

### 误区：只看总耗时和总成本

**你以为**：知道任务花了 30 秒、0.1 元就够了。
**其实**：平均值会掩盖尾部，总数会掩盖结构。一次任务 55% 的时间可能花在一个工具上，47% 的成本可能花在一个过大的工具结果上。
**怎么验证**：画一次 trace 的瀑布图和成本表，看最大贡献的 span；再看 p95，而不是只看平均。

### 误区：采样只采失败

**你以为**：成功请求没必要留，浪费存储。
**其实**：没有成功样本作基线，你无法判断失败率、延迟和成本是否异常；也无法比较"新版本是不是真的更好"。
**怎么验证**：对比采样成功样本和全量成功样本的通过率/延迟，看采样是否引入偏差。

## 小结

Agent 的可观测性不是多打日志，而是把一次任务拆成 trace 和 span：模型、工具、检索、校验、重试各一段，每段记录耗时、token、成本、状态和错误类型。工具记录要保留参数结构、结果大小、错误分类和幂等键，但不泄露完整敏感内容。成本按 span 记账，延迟看 TTFT、总时长和 p95，失败按模型/工具/超时/权限/编排/输入分类。回放要用记录下来的输入和工具结果重建现场，写操作用桩或沙箱，绝不在生产重放。线上按需采样、告警能点进 trace、失败样本进评测集，形成闭环。

这条线到这里结束。十四篇讲的其实是同一件事：**Agent 的难点不在模型，在工程**——工具怎么给、上下文放什么、走几步、钱怎么花、错了怎么发现、坏了怎么兜住。可观测性是最后一块拼图：它不阻止问题发生，但能让每一次问题都变成下一次的评测用例。
