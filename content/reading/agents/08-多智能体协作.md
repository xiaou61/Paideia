## 先把结论摆出来

**大多数情况下不该拆成多智能体。**

一个 Agent 加更多工具、更好的提示词，能解决八成的"看起来需要多角色"的问题。多智能体带来的是：调用次数翻倍、信息在传递中损耗、错误更难定位、成本更难预估。

它值得用的场景很窄，但确实存在。先学会判断边界，再决定拆不拆。

## 为什么单 Agent 常常就够了

一个常见的误解是"审查代码需要一个审查员 Agent、写代码需要一个程序员 Agent"。

实际上，**同一个模型换个系统提示词就能扮演不同角色**。你不必为此开多个进程、传多份上下文。一次对话里让它"先写、再以审查者视角检查一遍"，效果接近两个 Agent，成本低得多。

"多角色"和"多 Agent"是两件事：

- **多角色**：一个 Agent，提示词里分阶段切换视角。便宜、信息无损；
- **多 Agent**：多个独立的调用链，各自有上下文，靠消息传递协作。贵、有信息损耗。

先问自己：真的需要**独立的上下文**吗？如果两个角色需要看到的信息几乎一样，那就用多角色。

一个具体例子。写一段代码再自审：

```text
多角色（一次对话）：
  你：写一个分页查询
  模型：[写出代码]
  你：现在以严格审查者的视角，找出这段代码的问题
  模型：[指出索引、边界、N+1 等问题]

多 Agent（两个调用链）：
  写手 Agent：[写代码] → 传给审查 Agent
  审查 Agent：[看代码] → 指出问题
```

差别在于第二个方案里，审查 Agent 看不到"为什么这么写"的推理过程。而那个推理过程往往正是审查最需要的信息——**信息在传递中被丢掉了**。

## 拆的真正理由只有三个

### 一、上下文必须隔离

两个角色要看的资料会互相干扰。典型例子：一个 Agent 负责"找所有可疑点"，另一个负责"判断哪个真的有问题"。

第一个需要看大量噪声（宁可多报），第二个需要干净输入（只看候选）。放在一起，前者的噪声会污染后者的判断。

判断标准：**两个角色的"理想上下文"重叠度低于 50% 吗？** 低于，就值得拆。

### 二、需要并行

三个独立的子任务，同时跑能省时间。这时拆是为了**并发**，不是为了"角色分工"。

注意：并行只在子任务真的独立时才有意义。有依赖的步骤并行会得到错误结果。

一个判据：如果子任务 B 需要 A 的输出来决定做什么，就不能并行。

### 三、需要不同的工具权限

一个能读生产库、一个只能读测试库。这在权限上是硬隔离，不能靠提示词约束——**提示词不是权限边界**（第 13 篇会展开）。

这一条最硬：当你的需求是"这个 Agent 绝对不能碰 X"，而工具清单是共享的，那只能拆。

## 三种协作拓扑

**主管-工人（supervisor-worker）**

一个主管拆分任务、分派给工人、汇总结果。最常用，因为控制流清晰。代价是主管是单点，它的判断错了全局就错。

```text
主管：把"审查这个 PR"拆成三块
  ├── 工人 A：检查空指针与边界
  ├── 工人 B：检查 SQL 注入与权限
  └── 工人 C：检查性能问题
主管：汇总三份报告，去重，按严重度排序
```

**流水线（pipeline）**

A 的输出是 B 的输入，串行。简单可预测，但没有回退能力——上游错了下游只会放大。

**对等讨论（debate）**

多个 Agent 各自给答案，再互相批评或投票。适合"没有标准答案、需要多视角"的判断类任务。成本最高（N 倍调用 + 讨论轮次）。

实践中九成场景用第一种就够。第三种在学术上好看，真实产品里很少值得那个成本。

## 信息怎么在 Agent 之间传

这是多智能体最容易出问题的地方。

**反例：传完整对话历史**

把 A 的全部历史原样给 B。结果是 B 的上下文被 A 的试错过程塞满，注意力被稀释。

更糟的是 A 的错误也会传下去——它试过的错误方向会成为 B 的"背景知识"。

**正例：传结构化结论**

A 只输出 B 需要的东西：

```json
{
  "findings": [
    {"file": "OrderMapper.xml", "line": 42, "issue": "缺索引", "severity": "high"}
  ],
  "confidence": "high",
  "checked": ["OrderMapper.xml", "OrderService.java"]
}
```

三个原则：

- **只传下游需要的**，不传过程；
- **用结构化格式**，让下游能可靠解析；
- **传置信度或依据**，让下游知道该不该信。

第三个原则经常被漏。下游 Agent 如果不知道上游的结论有多可靠，就只能一律当真——那么一个低置信度的猜测会被当成事实继续传递。

## 成本会怎么变

一个 N 步的任务：

- 单 Agent：N 次调用，上下文累积；
- 主管 + 3 工人：1 次拆分 + 3 次执行 + 1 次汇总 = 5 次，而且每次都要带各自系统提示词。

**大致是 2–3 倍成本**，复杂拓扑更高。所以拆之前要能说清"拆了之后解决了什么单 Agent 解决不了的问题"。

算得再细一点。假设单 Agent 跑一个任务是 8 轮、总共 40k token：

```text
单 Agent            40k
主管-工人（3 工人）  拆分 8k + 3×12k + 汇总 10k = 54k   ← 约 1.35 倍
对等讨论（3 方 2 轮）3×12k + 讨论 2×20k = 76k          ← 约 1.9 倍
```

实际倍率取决于子任务大小。**子任务越小，拆分开销占比越高**——拆五个很小的任务，光主管的拆分和汇总就超过一半成本。

## 调试会难很多

单 Agent 出错，你看一条调用链。

多 Agent 出错，可能是：

1. 主管拆分错了；
2. 工人理解错了；
3. 信息传递丢了；
4. 汇总漏了。

**四种原因，表现都一样：结果不对。**

所以拆之前先想清楚：出问题时我能不能定位到具体环节？做不到就先别拆。

一个必要的基础设施：**每个 Agent 的输入输出都要能单独回看**。没有这个，多智能体的调试基本靠猜。

## 常见误区

### 误区：多 Agent 更像真实团队，所以更强

**你以为**：模拟人类分工，效果更好。
**其实**：人类分工是因为个体能力有限且并行需要沟通；模型没有这个约束，拆开只会增加信息损耗。
**怎么验证**：同一个任务，单 Agent 与主管-工人拓扑各跑一批，比较成功率与总成本。

### 误区：用提示词可以限制 Agent 的权限

**你以为**：告诉它"不要碰生产库"就安全了。
**其实**：提示词不是权限边界。真正的隔离要靠给不同 Agent 不同的工具清单或不同的凭据。
**怎么验证**：故意在提示词里留漏洞（比如让用户输入影响判断），看它是否会越界。

### 误区：拆了之后每个 Agent 都更专注，所以总成本更低

**你以为**：分工让每次调用都更短。
**其实**：每次调用都要带自己的系统提示词和工具描述，加上拆分与汇总的额外调用，总体通常是 2–3 倍。
**怎么验证**：记录单 Agent 与多 Agent 跑同一批任务的总 token 数。

### 误区：子任务拆得越细越好

**你以为**：拆成 5 个小 Agent，各司其职。
**其实**：子任务越小，拆分与汇总的开销占比越高，可能一半成本花在"协调"上。
**怎么验证**：算一下主管的拆分 + 汇总 token 占总量的比例。超过 40% 说明拆太细了。

## 小结

多智能体在多数场景是过度设计。真正的理由只有三个：上下文需要隔离、需要并行、需要工具权限硬隔离。九成场景用主管-工人拓扑就够。信息传递只传下游需要的结构化结论，别传过程。成本通常翻 2–3 倍，调试难度更高——拆之前先能说清它解决了什么单 Agent 解决不了的问题。
