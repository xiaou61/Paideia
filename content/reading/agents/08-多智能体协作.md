三个工人一起审一个 12 文件的 PR，同一个 `OrderService.java:118` 的 N+1 被报了三遍。本机 Redis 8.6.2（临时实例 `127.0.0.1:6399`，`save ""` + `appendonly no`）跑 5 轮，每轮都是这样：

```text
run1: 认领 36 次 / 12 个文件; 被重复认领的文件 12 个; 多出来的执行 24 次; 墙钟 0.44s
```

认领当时是这么写的：

```python
def claim(path, worker):
    if r.get(f'claim:{path}'):        # 有人占了吗
        return False
    r.set(f'claim:{path}', worker)    # 没有，我占了
    return True
```

`GET` 和 `SET` 之间隔着一整个网络往返。三个工人几乎同时读到「没人占」，各自写了一次自己的名字；最后一次写入的看起来赢了，但三个都已经开始读文件、跑 `explain`、写结论。36 次认领 = 12 个文件 × 3 个工人，一次都没漏。

换成一条原子命令，同样 5 轮，每轮都是：

```python
def claim(path, worker):
    return r.set(f'claim:{path}', worker, nx=True, ex=300) is not None
```

```text
run1: 认领 12 次 / 12 个文件; 被重复认领的文件 0 个; 多出来的执行 0 次; 墙钟 0.13s
```

这里得交代一句：我把 `GET` 与 `SET` 之间的窗口人为放大到 5ms（约一次同机房往返），所以是 100% 复现。真实窗口窄得多，复现是概率性的——放大窗口只是让它必然发生，坏掉的形状没变。

但 `SET NX` 修掉的是「抢占不原子」，不是「只执行一次」。把 TTL 设成 1 秒，让第一个工人干 1.2 秒的活：

```text
t=0.00s  w1 认领: OK
t=0.00s  该认领 TTL: 1s
t=1.20s  w1 还在跑；w2 认领同一文件: OK
t=1.20s  当前持有者: w2
```

TTL 到点时持有者失去保护，第二个工人合法接手，第一个工人的副作用还在进行。要挡住重复副作用，得让认领序号（fencing token）跟着每一次写操作一起下去，由被写入的那一侧拒绝旧序号；或者让工具本身幂等、可去重。

这篇文章只用这一个场景：PR #214、12 个文件、3 个工人、`OrderService.java:118`。下面的数字全部来自本机实测（Python 3.11.5 + tiktoken 0.13.0 的 `o200k_base`、Redis 8.6.2）；模型与供应商侧的行为按官方文档写，会明确标「未实跑」。

## 一、请求数从 13 涨到 17，累计 token 掉了一半

我原来以为「每多一个 Agent 就多一条独立调用链，成本与延迟都翻倍」。按这个假设数了一遍，两个方向都不对。

口径先说清楚：12 个文件的玩具样本（构造的 Java / XML / TS，与真实 Spring 项目文件同量级），合计 6,268 token；系统提示 85 token、工具定义 39 token、任务说明 109 token；只累计**输入** token，输出不计。

```text
单 Agent 串行：13 次请求（12 次读文件 + 1 次输出清单），累计输入 42,263 token
  各轮请求：233 / 539 / 1,177 / 1,718 / 2,453 / 2,758 / 3,202 / 3,840 / 4,187 / 5,019 / 5,247 / 5,480 / 6,410
主管+3 工人（结构化交接）：17 次请求，累计输入 17,455 token
  主管·分派: 211
  工人1·4 文件: 5,585（最重一轮 2,346）
  工人2·4 文件: 4,849（最重一轮 1,869）
  工人3·4 文件: 6,122（最重一轮 2,366）
  主管·汇总: 688，其中交接文本 461 token
差值：17,455 - 42,263 = -24,808（-58.7%）
```

请求数 13 → 17，多了 4 次，不是翻倍。总工作量没变（还是 12 次读文件 + 一次出结论），拆开只是把它切成三条并行的小链，再各加一次「输出结论」，主管两次。

累计 token 少了 58.7%，机制是第七篇讲过的那个前缀重发。单 Agent 那条链，每读一个文件都把全文追加进历史，下一次请求再整段重发：第 13 次请求单次就是 6,410 token。拆开以后，工人 1 最重的一轮只有 2,346 token——它只背自己那 4 个文件。

至于「延迟翻倍」：三条链并行跑，墙钟取决于最慢的那条（工人 3，6,122 token 的累计工作量）。前提是真并行。要是主管同步等工人 1 回来再派工人 2，延迟确实是加法——那是调度写坏了，不是拆开的必然代价。

还有一个方向得说清楚：这一节不是「拆开更便宜」的证明。它证明的是**成本由每条链的轨迹长度决定**，不由「拆不拆」决定。

## 二、把共享上下文加进去，方向就反过来了

上一节的分法有个不真实的地方：三个工人各读 4 个互不相交的文件。真实的 PR 里 `OrderMapper.xml`、`OrderDTO.java`、那个索引迁移脚本是每个人都要看的。让每个工人先读同样 3 个共享文件（合计 1,457 token），再读自己的人份：

| 装配方式 | 累计输入 | 相对不拆 |
| --- | --- | --- |
| 不拆：1 个 Agent 串行 | 42,394 | — |
| 3 工人，每人先读 3 共享 + 最多 3 自己的 | 33,408 | −21.2% |
| 5 工人，每人先读 3 共享 + 最多 2 自己的 | 38,622 | −8.9% |
| 9 工人，每人先读 3 共享 + 最多 1 自己的 | 49,915 | **+17.8%** |

工人越多，共享部分被复印的次数越多，省下的历史长度抵不过复印费。到 9 个工人时，累计输入比不拆还高 17.8%——这就是「拆开更贵」的真实版本，它不是规律，是参数算出来的。

同样 12 个文件，换切法（每人不共享，只按文件切）：

| 切法 | 请求数 | 累计输入 | 相对不拆 |
| --- | --- | --- | --- |
| 不拆：1 个 Agent 串行 12 文件 | 13 | 42,263 | — |
| 2 工人 × 6 文件 | 16 | 24,238 | −42.6% |
| 3 工人 × 4 文件 | 17 | 17,455 | −58.7% |
| 4 工人 × 3 文件 | 18 | 14,592 | −65.5% |
| 6 工人 × 2 文件 | 20 | 12,510 | −70.4% |
| 12 工人 × 1 文件 | 26 | 10,370 | −75.5% |

这张表也不能读成「工人越多越好」。12 个工人 × 1 文件这一行，每个工人只读一个文件、只回一条结构化结论，等于把并行度拉到最大、把每个 Agent 的判断责任压到最小——真实任务里没有这种切法，而且它完全没算输出 token（12 份结论 + 主管汇总，输出份数随工人数线性增长）和协调成本。

那为什么 Anthropic 报的是多智能体更贵？他们 2025-06-13 的工程博客给的口径是：普通 agent 的 token 用量约为 chat 的 4×，多智能体系统约为 chat 的 15×（对单 agent 就是 15÷4 ≈ 3.75×，这个除法是我做的，他们没写）。差异不在「拆」，在轨迹：他们的 subagent 要各自做十几次以上的检索，我这里的工人只读 4 个本地文件、没有搜索循环。同一篇博客里也写了 token 用量单独解释了 BrowseComp 上 80% 的方差——用量本身就是主变量。

所以他们那句「需要所有 agent 共享同一上下文、或 agent 之间依赖很多的领域，目前不适合多智能体」，和我上面那张表里 +17.8% 那一行是同一件事：共享上下文一多，拆开的账就翻回去了。

## 三、交接：一份 JSON 和一条 traceback

工人回传的是被包在围栏里的一段文本，后面还带一句「以上是 w2 的结论」。主管直接 `json.loads` 拿到的是：

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

解析器看到的前 12 个字符里根本没有 `{`：先是围栏开头那三个反引号，再是 `json`，再换行，然后才是 `{"wo`。找第一个 `{` 到最后一个 `}` 再解析能过，但这条修法很脆：正文里出现花括号、回了两个 JSON、或者输出被截断，都会再炸一次。协议层面该做的是「只回一段可解析的 JSON」，或者干脆走工具调用的结构化参数。

更贵的错在合并那一步。两个工人对同一行给出不同严重度，我按「文件 + 行号去重，严重度取更高者」合并，结果是：

```text
OrderService.java:118  high   疑似 N+1  依据=（空）
最终清单里留下 severity=high 的那条；w1 带依据的 medium 被顶掉了。
```

有依据的判断被没依据的「更严重」换掉了。改成 `evidence` 必填、缺依据降级为待核实、冲突两条都留：

```text
OrderService.java:118 保留 2 条：
  worker=w1  severity=medium  依据=循环内调用 findById，explain 显示 1+N 次索引查找
  worker=w2  severity=unverified  依据=（空）
```

这里有两处我一开始就写反了，值得单独说。

**先是「信息在传递中被丢掉了」——不是传输丢包。** 工人的隐藏推理不在它返回给调用方的 assistant 文本里（各家接口不同：有的完全不返回，有的只在特定模式返回且不能当普通消息转发）。主管压根没见过那段推理，不是见过了又弄丢。所以修法也不是加校验和或者重传，而是要求工人把判断依据写进输出契约——上面那个 `evidence` 字段就是干这个的。


**再是「传置信度或依据，让下游知道该不该信」——依据能传，置信度不行。** 模型自报的置信度没有校准保证（这一条按各家接口文档与评测惯例写，未实跑：本机没有 API key，我不会编一个校准数字）。把 0.8 当成概率 0.8 用，等于把「说得像」当成「算得准」，而上面那条空依据的 high 正是「说得像」的典型产物。

还有一个方向相反的说法也得纠正：单 Agent 自审不是「信息无损」。它保留了全部推理，所以它审自己刚写的推理时会锚定在那条推理上——围栏那个错、还有「取更高严重度」这个错，都是写的人自己看不出来的。多 Agent 在这里的优势不是信息更多，是推理被强制丢掉、只剩可核验的产物。代价就是本节开头那条 traceback：丢掉推理的同一瞬间，也丢掉了「他为什么这么判断」。

Anthropic 在同一篇博客的附录里给的做法是这个方向：让 subagent 把产物写进文件系统，只回传轻量引用，以减少「传话游戏」的失真。

## 四、同一个现象，会在四个地方坏

| 现象 | 先看哪一层 | 判据 |
| --- | --- | --- |
| 同一处问题被报了 2–3 遍 | 认领与去重 | 认领计数 > 文件数；报告里同一个 `file:line` 出现多次 |
| 清单里有结论、没有依据 | 交接契约 | 随机抽一条，只看交接文本能不能答出「依据是什么」 |
| 累计 token 比不拆还高 | 上下文装配 | 共享文件 token × 工人数，与单 Agent 累计相比 |
| 墙钟比不拆还慢 | 调度 | 存在「B 的输入里有 A 的输出」却被拆到两个工人 |

这四行是分开的层：第一行在并发控制里，第二行在协议里，第三行在装配里，第四行在调度里。现象都是「多智能体不好用」，改的位置完全不同——把第四行的问题当成第一行去调（比如给更多工人、加更多重试），只会让日志更长。

## 五、什么时候值得拆

三条判据，每条都能先算一算再决定。

**一、上下文能不能切干净。** 先算共享部分：共享 token × 工人数，和单 Agent 的累计比。我第二节那张表里，共享只要 1,457 token，9 个工人就让累计反超 17.8%。共享部分越大，拆开越像「把同一段话复印 N 份」。

**二、能不能真并行。** 问一句「B 的输入里有没有 A 的输出」。没有才并行；有就只能串行，拆开只多两次交接。Anthropic 那篇也把同步执行列为瓶颈。

**三、要的是独立视角，还是硬边界。** 想要「别自己审自己」，多 Agent 有效，代价是推理不再传递。想要权限隔离，多智能体本身给不了——边界必须在执行层（工具白名单、凭据范围），提示词不是权限边界，第 13 篇展开。

再加一条不是判据、但要先想清楚的：愿不愿意付调试成本。一个会话里能读完的 traceback，拆开以后是 4 条互相对不上的日志。

三种拓扑放在一起看（「请求」那一列是机制推算，流水线与对等讨论**未实跑**）：

| 拓扑 | 一次任务里的请求 | 最典型的失败 | 比主管-工人差在哪 |
| --- | --- | --- | --- |
| 主管-工人 | 2 + Σ(每个工人的读次数 + 1) | 工人之间冲突没人裁；边界文件重复执行 | —（作为基线） |
| 流水线 | 与步骤数同阶，逐段串行 | 上游格式错到下游才炸 | 没有并行收益，错一次要重跑整段 |
| 对等讨论 | N 份答案 + k 轮互看，输入随 N·k 增长 | 互相说服，收敛到一个错的共识 | 请求最多，而且没有裁决者 |

## 还差的

- **没有调模型。** 全文没有一次真实模型调用（本机没有 API key）。工人的实际输出、真实 JSON 合规率、多 Agent 的判断质量、置信度是否校准，都是未实跑。真跑的只有：token 计数、Redis 认领、JSON 解析失败、合并规则。
- **样本是构造的。** 12 个文件 6,268 token 的玩具代码，不是线上分布；真实项目单文件上千 token 很常见，交叉点会整体右移。而且只算了输入，输出没算——拆开后结论份数随工人数增加，这部分没进表。
- **没有缓存与批处理口径。** 真实账单里前缀缓存会改变累计成本，拆开后每条链要各自预热缓存，我的表是「无缓存」下的相对值，不是账单。
- **重复窗口是人为放大的。** 5ms 是我插的模拟往返；线上复现是概率性的，我没在真实网络里测过重复率。fencing token 那一行标了未实测，我没有实现它。
- **供应商细节没核到代码级。** 4×/15× 是 2025-06-13 那篇博客的口径（3.75× 是我做的除法），不是账单；「隐藏推理不在 assistant 文本里」按各家接口文档写，具体行为要按你用的 SDK 版本重查。
