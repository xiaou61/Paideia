## 12 个请求同时进来，桶放过去 10 个

客服组 12 个人共用一个 key，我在模型调用前面放了个令牌桶。我以为「12 个人一起点，就是慢慢排队」，第一次跑出来是这样：

```python
import time


class TokenBucket:
    def __init__(self, rate, capacity, now=time.monotonic):
        self.rate = float(rate)          # 每秒补多少
        self.capacity = float(capacity)  # 突发上限
        self.tokens = float(capacity)    # 一开始是满的
        self.last = now()
        self._now = now

    def allow(self, cost=1.0):
        t = self._now()
        self.tokens = min(self.capacity, self.tokens + (t - self.last) * self.rate)
        self.last = t
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False


b = TokenBucket(rate=5, capacity=10)
passed = [b.allow() for _ in range(12)]
print("12 个并发请求通过:", sum(passed), "拒绝:", passed.count(False))
print("桶里剩下的 token:", round(b.tokens, 3))
print("被拒的那个要等:", round((1 - b.tokens) / b.rate, 3), "秒")
```

```text
$ python bucket.py
12 个并发请求通过: 10 拒绝: 2
桶里剩下的 token: 0.0
被拒的那个要等: 0.2 秒
```

我猜的是「每秒 5 个」，所以第 6 个人就该等。实际一次放过去 10 个，因为桶一开始是满的：`capacity` 是这一瞬间能放过的上限，`rate` 只决定「扣完之后多久补一个」。名字里其实写着——capacity 是桶有多大，rate 是每秒补多少——我还是把它当成了「每秒最多 5 个」的计数器。计数器没有存量，桶有。

对 Agent，这个差别直接换算成上游压力。这 10 个请求各自是一个 8 轮任务，输入 token 从 4k 涨到 18k，合计 880k 输入 token，会在任务跑完之前陆续压向上游。而桶在这 10 个请求上的计数是 **10**——它数的是请求，不是 token。按各厂商文档，模型 API 的限流分请求数（RPM）和 token 数（TPM）两条，字段名各家不同；只按请求数放行，等于 TPM 那一维完全没人管。

## 时间被拨一下，桶就开始冤枉人

实现里那行 `self.last = now`，`now` 从哪来，决定它遇到时钟调整时会不会冤枉人。我用两个可控时钟各跑一遍：先按 1 个/秒补、容量 5 的桶抽干，然后让墙钟往回跳 3 秒，再真实过去 2 秒，看 10 个请求能过几个。

```python
class Clock:
    def __init__(self):
        self.wall = 1000.0   # time.time 口径：会被拨
        self.mono = 1000.0   # time.monotonic 口径：只随真实流逝涨

    def jump(self, d):
        self.wall += d       # 只拨墙钟

    def tick(self, d):
        self.wall += d
        self.mono += d
```

把第一节那版里的 `now=time.monotonic` 分别换成 `clock.wall` 和 `clock.mono`，就是下面这两组输出。

```text
$ python clock.py
time.time  回拨 3 秒             通过 0 个，tokens=-1.000
monotonic 回拨 3 秒             通过 2 个，tokens=0.000

time.time  前跳 3600 秒          通过 5 个，tokens=0.000
monotonic 前跳 3600 秒          通过 2 个，tokens=0.000
```

`(t - self.last) * rate` 在回拨时是负的，token 直接被扣成负数：回拨 3 秒、真实过了 2 秒，账上是 -1，10 个请求全拒，还得再等 1 秒才恢复。原来那 2 秒本该补 2 个 token，被那 3 秒的负数吃掉了。往前跳 3600 秒更干脆——桶瞬间补满到 capacity，额外放过去 5 个，这 5 个在真实时间里一个都不该有。

两处都改：
- 用 `time.monotonic()`，它不随墙钟跳变。
- 见到负的流逝就按 0 算，宁可少补一次也不欠债。

但别把 monotonic 当万能：它的零点没有定义，文档只说保证不回退，所以只能在同一台机器的同一进程内比较。额度要是存在 Redis 里跨实例共享，这个 `last` 就不能是本地单调钟——那得用服务器侧的时间和原子操作。

## 单线程也会超发：await 就是那个窗口

上面那版 `allow` 里，检查 `self.tokens >= cost` 和 `self.tokens -= cost` 是两行。我一直以为中间被打断是多线程或多进程才会有的事，CPython 有 GIL 兜着。跑完这个才知道错在哪：

（这条线前面都是同步代码，这里第一次出现 `async def`。只用一条性质就够：函数跑到 `await` 时会把执行权交出去，等别人跑完再从原地接着跑。没写过的话照抄这段就能跑。）

```python
import asyncio


class Bucket:
    def __init__(self):
        self.tokens = 1          # 每秒补 0 个：一桶只该放 1 个
        self.passed = 0

    async def allow(self):
        if self.tokens >= 1:          # 读
            await asyncio.sleep(0)    # 中间任何一次 await 都会放开事件循环
            self.tokens -= 1          # 写
            self.passed += 1
            return True
        return False
```

```text
$ python race2.py
CPython 3.11.5, win32
asyncio 8 个协程抢 1 个 token：通过 8 个
并发期间 tokens 变成: -7
把检查+扣减收成一步（无 await）：通过 1 个
8 线程、检查与扣减之间 sleep(0)：5 次实验通过数 = [1, 1, 1, 2, 1]
8 线程、检查与扣减之间 sleep(0.001)：5 次实验通过数 = [8, 8, 8, 8, 8]
```

asyncio 是单线程，但 8 个协程都在 `await` 处让出去，醒来时谁手里的 `tokens` 都是过期的 1，于是 8 个全过、token 变成 -7。这不是偶发，是确定性的：那个 `await` 就是一个必然打开的窗口。

线程那两行说明另一半：GIL 只是解释器级的互斥，不是事务。`sleep(0)` 只把窗口撑开了一点点，5 次里 4 次还只放 1 个；把停顿换成 1 毫秒，5 次全放 8 个。所以「我这边没测出超发」不构成「没有这个 bug」——窗口宽度取决于你两次操作之间有没有 IO，而不是有没有多线程。

两条修法，方向不同：
- **同进程**：把检查与扣减收进一个同步函数（`try_take`），`await` 只出现在取到 token 之后。asyncio 里一个不 await 的同步函数不会被别的协程插进来。
- **跨实例**：状态在 Redis 里，读-改-写就必须在一次服务端操作里完成（Lua 脚本把 check 和 decr 合成一步）。这是设计，不是我这篇实测过的东西——但窗口是一样的，而且更宽：一次网络往返就是几毫秒。

## 固定窗口在整分钟放双倍

额度写「每分钟 100 次」，有两种实现，差别只在边界上。我让它们各接同一串请求：59.9 秒时打 100 个，60.1 秒再打 100 个。

```python
class FixedWindow:
    def __init__(self):
        self.win = None
        self.count = 0

    def allow(self, now):
        w = int(now // 60)
        if w != self.win:        # 跨窗口就清零
            self.win, self.count = w, 0
        if self.count < 100:
            self.count += 1
            return True
        return False


class SlidingLog:
    def __init__(self):
        self.hits = []

    def allow(self, now):
        self.hits = [t for t in self.hits if now - t < 60]   # 只看过去 60 秒
        if len(self.hits) < 100:
            self.hits.append(now)
            return True
        return False
```

```text
$ python window.py
固定窗口           59.9s 放行 100 个 / 60.1s 放行 100 个，共 200
滑动窗口（记时间戳）     59.9s 放行 100 个 / 60.1s 放行   0 个，共 100
```

固定窗口的额度是 100，但任意一个 60 秒的区间里能看到 200 个。要它不是问题，得让「多放的那份」在整天的量级里可以忽略——所以一天的额度用固定窗口我照样用，一分钟的额度不行：多放的那一份正好是 100%。

滑动窗口记时间戳精确，代价是每个 key 存一份时间戳列表，100 次/分钟就是 100 个浮点数。额度大、key 多时换成按秒分桶的计数，误差有界，实现简单得多。

到这里，限流器本身的坑差不多齐了。真出问题时按症状分：

| 症状 | 先看哪 | 为什么 |
| --- | --- | --- |
| 某个整分钟、整点请求量翻倍 | 窗口是固定的还是滑动的 | 59.9 秒 100 个、60.1 秒又 100 个，任意 60 秒里能看到 200 |
| 桶在某个时刻全拒，几分钟后自己好了 | 时间源是不是墙钟 | 回拨 3 秒就把 token 扣成 -1，得等真实时间还债 |
| 偶发超发，压测时更明显 | 检查与扣减之间有没有 await、状态是不是跨实例 | 8 个协程同时读到 tokens=1，最后变成 -7 |
| 上游请求数是用户请求数的 9 倍以上 | 重试是不是叠了三层 | 见下一节，3 层各 3 次共 27 个请求 |
| 账单涨了、请求数没涨 | 轮次和每轮上下文长度 | 8 轮 88k 输入 token，16 轮 304k |

## 退避重试，一次任务打出去 27 个请求

限流器修好了，被拒的请求开始走退避重试，这才是我漏得最厉害的一处。我先写了个只包一层重试的调用，然后照真实代码的结构又搭了一层：SDK 自己会重试，我的 Agent 步骤包了一层重试，任务调度又包了一层。

```text
$ python retry.py
只包一层重试（最多 3 次尝试）：上游请求 3 次，等待 [0.32, 0.025]
SDK / 步骤 / 任务 三层各重试到 3 次尝试：上游请求 27 次
各次重试的退避上限: [0.5, 1.0, 2.0, 4.0, 8.0]
full jitter 期望等待合计 ≈ 7.75 秒，最坏 15.5 秒
不封顶（cap 去掉）第 6 次的退避上限: 16.0 秒
```

每层 r 次重试、L 层叠起来，放大倍数是 `(r+1)^L`。3 层各 2 次重试就是 27 个请求；写预算时按「客户端重试 3 次」算，少算 9 倍。

算法本身没什么神秘，`min(cap, base * 2 ** attempt)` 再加抖动。几处容易写错的：

- **抖动区间**。`sleep = random.uniform(0, min(cap, base * 2**attempt))` 是 full jitter，期望值是一半上限；上面那串上限对应期望 7.75 秒、最坏 15.5 秒。写成 `base * 2**attempt + random.uniform(0, 1)` 只是加了最多 1 秒的偏移，退避基数一大，这点偏移就淹在同一个峰值里，一群客户端还是会踩在同一个点回来。
- **上限必须有**。去掉 cap，第 6 次的退避上限是 16 秒，第 10 次 256 秒——比任务超时还长，重试已经没意义了。
- **429 优先听对方的**。429 由 RFC 6585 §4 定义，`Retry-After` 的语义在 RFC 9110 §10.2.3（值可以是秒数，也可以是 HTTP 日期）。这个头盖过你自己算的退避：对方说 5 秒后再说，你 0.3 秒后打回去只会再吃一个 429。
- **重试的前提是幂等**。Agent 的一轮里可能有副作用（写库、发消息、调用计费工具），整任务重试会把这些重做一遍。所以我把重试放在「单次模型请求」这一层，探索性的工具调用不整任务重试，宁可把失败明确抛给用户。

## 8 轮任务 88k 输入 token，是单次的 22 倍

现在算那 10 个并发请求到底吃了多少。按一个具体配置：系统提示词 + 工具描述 3k token，首轮提问 1k，之后每轮新增助手输出 1k + 工具结果 1k。

```text
$ python cost.py
8 轮：每轮输入 [4000, 6000, 8000, 10000, 12000, 14000, 16000, 18000]
总输入 88000，单次调用 4000，倍数 22.0x
其中系统提示词被重复发送 8 次 = 24000 token，占 27%
第 1 轮的工具结果此后被重发 7 次

 4 轮：总输入   28000，是单次的 7.0 倍
 8 轮：总输入   88000，是单次的 22.0 倍
16 轮：总输入  304000，是单次的 76.0 倍
```

关键是第 1 轮的工具结果会被重发 7 次、系统提示词被发 8 次。轮次翻一倍（8→16），总量不是翻倍而是 88k→304k，3.45 倍。

两个立刻能用的推论：

- **别拿 88k 乘单价往下推**。这 88k 里有 24k 是同一段前缀，前缀缓存命中后按缓存读价计费，比例各家文档不同、会变。这篇不抄具体价格——抄下来三个月后就错，而且错得很像真的。真要估账，用自己的响应里返回的 usage 字段累加，比按单价乘 token 靠谱。
- **截断要在工具内部做**。一次工具返回 5000 行 CSV，等于往上下文里塞 20 万 token。用 tiktoken 0.13.0 实测（cl100k_base / o200k_base 两种编码）：

```text
$ python tokens.py
   20 行 /    1302 字符 -> cl100k_base=830  o200k_base=790
  200 行 /   12642 字符 -> cl100k_base=8210  o200k_base=7810
 5000 行 /  315042 字符 -> cl100k_base=205010  o200k_base=195010
```

20 行 830 token，5000 行 205,010 token，差 247 倍；两个编码之间也差 5%。所以「按字符数除以 4」这种估法只能用来判断量级，真要报数就调接口数，别猜。

## 预扣与结算：第二次结算影响 0 行

有额度的产品还要处理「先扣后结」。核心不是折扣算法，是那笔预扣只能被结算一次。用 sqlite 3.42.0 验证语义：

```sql
UPDATE quota SET state='SETTLED', charged=?
 WHERE id='task-1' AND state='RESERVED';
```

```text
$ python settle.py
第一次结算 rowcount = 1
重试时又结算一次 rowcount = 0
结算后再想退款 rowcount = 0
表里最终状态 = ('SETTLED', 100)
```

状态机就四个转移：`RESERVED → SETTLED`、`RESERVED → REFUNDED`、两个终态不再变。把状态判断写进 `WHERE`，重试、超时、双写都只会成功一次——这是单行条件更新的语义，不是压测结果。换成先 `SELECT` 判一下再 `UPDATE`，中间那段就是第 3 节那个窗口。

顺序上还有一条，方向别弄反：**余额检查必须在发出任何上游请求之前**。先发后扣，余额耗尽的用户还能继续消耗；一个任务要跑十几秒到几十秒，那段被透支的时间就是那么长。

## 参数各自决定什么

| 参数 | 它决定什么 | 设错的症状 |
| --- | --- | --- |
| capacity | 一瞬间能放过多少（突发上限） | 12 人同时点全进去，然后集体等 |
| rate | 长期平均吞吐 | 任务要 20 秒，rate 设小了队列只涨不落 |
| 窗口长度 | 额度滚动的粒度 | 1 分钟固定窗口在整分放双倍 |
| 退避 base / cap | 失败后多久打回来 | 去掉 cap，第 6 次退避 16 秒 |
| 重试层数 L | 请求放大 `(r+1)^L` | 三层各 3 次 = 27 个请求 |
| 单任务轮次上限 | token 总量 | 8→16 轮，22 倍变 76 倍 |

三层预算（单任务 / 单用户 / 全局）要同时设，因为漏洞各不相同：只限轮次不限 token，一轮塞进超大工具结果照样爆；只限 token 不限轮次，卡在小循环里一直转；只限单用户不限全局，一个客户端 bug 的重试风暴就能打满。

## 跑一遍

把上面几处修法收进一个能用的版本：单调钟、负增量兜底、检查与扣减之间不 await、线程互斥。

```python
import threading
import time


class RateLimiter:
    def __init__(self, rate_per_sec, capacity):
        self.rate = float(rate_per_sec)
        self.capacity = float(capacity)
        self.tokens = float(capacity)
        self.last = time.monotonic()
        self.lock = threading.Lock()
        self.passed = 0
        self.rejected = 0

    def try_take(self, cost=1.0):
        with self.lock:
            now = time.monotonic()
            delta = now - self.last
            if delta < 0:
                delta = 0.0
            self.last = now
            self.tokens = min(self.capacity, self.tokens + delta * self.rate)
            if self.tokens >= cost:
                self.tokens -= cost
                self.passed += 1
                return True
            self.rejected += 1
            return False

    async def allow(self, cost=1.0):
        # await 之前就把 token 扣掉，返回后只剩发请求
        return self.try_take(cost)


if __name__ == "__main__":
    lim = RateLimiter(rate_per_sec=5, capacity=10)
    [lim.try_take() for _ in range(12)]
    print("放行", lim.passed, "拒绝", lim.rejected, "桶里剩", round(lim.tokens, 3))

    lim2 = RateLimiter(rate_per_sec=1000, capacity=1)
    out, bar = [], threading.Barrier(8)

    def w():
        bar.wait()
        out.append(lim2.try_take())

    ts = [threading.Thread(target=w) for _ in range(8)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    print("8 线程抢 capacity=1 的桶：放行", sum(out), "个")
```

```text
$ python final.py
放行 10 拒绝 2 桶里剩 0.0
8 线程抢 capacity=1 的桶：放行 1 个
```

`async def allow` 里只调一个同步函数，超发在这条路径上就没了。要是哪天有人往 `try_take` 里加了一句 `await`，那 8 个协程会立刻变回 8 个。

## 动手

1. 把 `capacity` 改成 3 再跑一遍，12 个请求应该只过 3 个；再把 `rate` 改成 0.5，第 4 个请求要等 1/rate = 2 秒，跑出来对一对。
2. 在自己项目的 async 代码里搜 `await`，找「先读状态、await 一下、再写状态」的形状——限流、配额、去重、锁，都在这个形状上出过事。
3. 数一下自家链路有几层重试：SDK、HTTP 客户端、业务包装、任务调度。算出 `(r+1)^L`，然后拿网关的请求数与业务请求数对一遍，看差几倍。

## 还差的

- **跨实例的限流没做**。额度放 Redis 的方案我只写了「用 Lua 把 check 和 decr 合成一步」，没压测，也没测网络往返对精度的影响。多副本部署时这台机器上的桶只能管住自己。
- **只做了拒绝，没做排队**。真实客服场景里 429 之后应该进队列、按优先级放行，而不是让用户手点重试。队列的公平性和饥饿问题这篇一个字没碰。
- **账没接到真实账单**。88k 是算式，不是我抓的响应 usage；缓存命中率、批处理折扣、图片/音频计价都没算进去。真要报数，得从响应里累加 usage。
- **没有压测数据**。所有数字来自单机脚本，真实 QPS 下锁竞争、Redis 往返、GC 停顿都会改变形状。我给出的 27 个请求是结构推演，不是线上抓包。
- **时钟只测了单进程**。跨主机偏移 200 毫秒时，滚动窗口会多放还是少放，取决于宁严还是宁松，我没做这个取舍，也没写对应的保护。
