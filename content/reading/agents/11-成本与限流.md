## 先把结论摆出来

Agent 的成本结构和普通 API 调用完全不同：**它按"轮次 × 上下文长度"增长，是乘法不是加法。**

第 5 轮的输入包含前 4 轮的全部内容。所以一个 8 轮的任务，输入 token 大致是单次的十几倍到几十倍。**用"单次调用成本 × 调用次数"估算，会低估一个数量级。**

## 先把账算对

一个具体例子：

```text
系统提示词 + 工具描述：3k token
每轮新增内容（工具结果）：1k token

第 1 轮输入：3k + 1k = 4k
第 2 轮输入：4k + 1k + 1k = 6k
第 3 轮输入：8k
...
第 8 轮输入：18k

总输入 ≈ 4+6+8+...+18 = 88k
```

而如果只调一次，输入是 4k。**差了 22 倍。**

这就是为什么"感觉单价很便宜"的模型，做成 Agent 之后账单会失控。

再放大到业务量：一天 1000 次这样的任务，就是 8800 万输入 token。按每百万 token 几块钱算，一天几十到几百块——**而且这是成功路径的成本，失败重试的还没算**。

## 三层预算

必须同时设，缺一层就有漏洞。

### 一、单次任务

```text
最多 8 轮工具调用
最多 60k 输入 token
超时 120 秒
```

三个都要设。只设轮次不设 token，一轮塞进超大工具结果照样爆；只设 token 不设轮次，可能卡在很小的循环里一直转。

超限时的行为要明确：返回已有结果并说明不完整，还是直接报错。前者体验好，但要确保**用户能看出"这是不完整的"**。

### 二、单用户

按天或按小时限制总量。防的是单个用户反复触发（无论是有意刷还是写了个循环脚本）。

限流的粒度建议是"每天 N 次任务"而不是"每分钟 N 次"——前者更符合真实使用，后者对正常用户太苛刻。

### 三、全局

所有用户加起来的上限。防的是整体被打爆（比如某个客户端 bug 导致重试风暴）。

全局上限触发时，宁可让部分请求失败并明确告知，也不要让服务整体不可用。

## 预扣与结算

如果要做配额（比如积分），有个关键设计：**先预扣、再结算**。

```text
1. 请求开始前：按最坏情况预扣（比如预估上限）
2. 实际跑完：按真实用量结算，多退少补
3. 余额不足：一个上游请求都不要发
```

第 3 条最重要：**余额检查必须在发请求之前**。如果先发再扣，用户可以在余额耗尽后继续消耗——这在多轮 Agent 里尤其明显，因为一轮任务可能跑十几秒。

预扣和结算之间要保证"只结算一次"。重试、超时、并发都可能让结算逻辑跑两遍，结果是用户被扣两次钱。

一个实现要点：**用状态机而不是布尔标志**。

```text
RESERVED → SETTLED   （正常）
RESERVED → REFUNDED  （失败退款）
SETTLED / REFUNDED   （终态，不可再变更）
```

条件更新（`UPDATE ... WHERE state = 'RESERVED'`）保证并发下只有一个请求能推进状态。

## 省钱的四个真办法

按性价比排序。

**一、减少轮次**

最有效。绕圈是 Agent 最大的浪费来源，而绕圈往往是提示词没写清停止条件导致的。加一句"信息足够就停止检索"，可能省掉 30% 的调用。

**二、截断工具结果**

一次工具返回 5000 行，塞进去就是几万 token，而模型真正需要的可能只有其中 20 行。截断要在工具内部做。

**三、少塞历史**

滑动窗口 + 摘要。第 20 轮还把第 1 轮原样带着，纯属浪费。

**四、用小模型做简单步骤**

工具选择、意图判断这类任务，小模型往往够用。把"重活"留给大模型，简单判断用小模型，能显著降本。

注意顺序：**先做前三条，再考虑第四条**。前三条不花钱，第四条要改架构。

## 记账要记到什么粒度

只记"这次花了多少 token"不够。要能回答：

- 哪个用户、哪次任务花的？
- 花在哪几轮、哪个工具之后？
- 有没有触顶（轮次上限、token 上限）？
- 上游返回的错误和重试有没有产生额外消耗？

**没有这些，成本异常时你只能看到总数涨了，找不到原因。**

至少记录：任务 id、用户 id、每轮的输入/输出 token、工具名、是否触顶。

一个实用的排查方法：按"平均轮次"做分组统计。如果某一天的平均轮次从 4.2 跳到 6.8，说明有东西在让模型多绕圈——可能是提示词改了、工具坏了、或者上游返回变慢了。

## 常见误区

### 误区：单价便宜的模型做 Agent 也便宜

**你以为**：单 token 价格低，总账就低。
**其实**：Agent 的 token 总量是乘出来的。便宜的模型可能多绕几轮，总账反而更高。
**怎么验证**：同一批任务用两个模型跑，比较总 token 数 × 各自单价。

### 误区：设了轮次上限就够了

**你以为**：限制 8 轮，成本就可控。
**其实**：一轮里塞进一个超大工具结果，照样能爆。token 上限必须单独设。
**怎么验证**：构造一个返回超长内容的工具，看单轮能吃掉多少 token。

### 误区：限流会影响正常用户体验，所以先不做

**你以为**：上线初期用户少，不需要限流。
**其实**：打爆系统的往往不是用户量，而是一个客户端 bug 引发的重试风暴。
**怎么验证**：看日志里有没有短时间内大量相同请求——有就是征兆。

### 误区：记账只要记总 token 数

**你以为**：知道花了多少就够了。
**其实**：总数涨了但不知道为什么涨，等于没有信息。要能按用户、轮次、工具拆开看。
**怎么验证**：现在能不能回答"昨天哪一轮最贵"？答不上来就是记粒度不够。

## 小结

Agent 成本按"轮次 × 上下文长度"增长，是乘法。三层预算必须同时设：单次任务（轮次 + token + 超时）、单用户、全局。配额要预扣后结算，且余额检查必须在发请求前，结算只能做一次（用状态机保证）。省钱先做零成本的三件事：减轮次、截断工具结果、少塞历史。
