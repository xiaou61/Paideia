## 我在第一个分片上就 parse 了

练手项目里有个只有一个工具的循环：`read_file`。它在 OpenAI 兼容那家上游上跑了几天，参数一次没解析错过。换 Anthropic Messages 试同一条调用，工具参数一次都没解析成功过。

我第一版写的是「来一片就 parse 一片」：

```js
const fragments = ['{"path"', ': "content/reading/agents/09-', '框架选型.md"', '}'];
for (const f of fragments) {
  try { JSON.parse(f) } catch (e) { console.log(`${JSON.stringify(f)} -> ${e.name}: ${e.message}`) }
}
```

跑出来（本机 Node v24.14.1，片段是把一次 `read_file` 的 arguments 按流式事件切开的样子）：

```text
  "{\"path\"" -> SyntaxError: Expected ':' after property name in JSON at position 7 (line 1 column 8)
  ": \"content/reading/agents/09-" -> SyntaxError: Unexpected token ':', ": "content"... is not valid JSON
  "框架选型.md\"" -> SyntaxError: Unexpected token '框', "框架选型.md"" is not valid JSON
  "}" -> SyntaxError: Unexpected token '}', "}" is not valid JSON
```

四片全挂。`JSON.parse(fragments.join(''))` 才对，得到一个对象。

第 04 课讲过 `arguments` 是 JSON 字符串、Anthropic 的 `input` 已经是对象——那是**非流式**响应里的样子。流式下两边都变成一段一段到达，而且分组键不同：OpenAI 在 `choices[0].delta.tool_calls[]` 里按 `index` 归并，Anthropic 是 `content_block_start` 给出 `id`/`name`、后续 `input_json_delta.partial_json` 追加（流式细节放到第 10 课，这里只需要知道「片段要归组」）。

我当时以为撞的是 schema 问题——参数类型不对、校验器不够严。实际是位置问题：**拼接属于上游适配，不属于循环。** 循环只该在拿到完整的 `{ id, name, input }` 之后才执行工具。

## 循环那个 while 很短，它旁边的东西很长

这一点可以直接数。

- **pi**：`runLoop` 在 `agent-loop.ts` 的 `:172`–`:330`，按行号差约 160 行；同一个文件整个约一千行。出处是内容线《03 · agentLoop：一次请求走完七步》与《10 · 对照 DSH》，版本 `v1.5.0`（`f9a2636`，2026-11-09 核对）。
- **DSH**：我在 `F:\tmp-dsh-review`（根 `package.json` 是 `0.2.2-rc.5`，`HEAD` `2e39e704`）里数了 `packages/core/agent-loop/src` 下六个文件，合计 **2155 行**（`index.ts` 844、`agent.ts` 751、`inbox.ts` 232、`runtime-context.ts` 181、`assistant-stream.ts` 141、`constants.ts` 6）；同一个包的 `tests/loop.spec.ts` 一个文件 **1979 行**。
- **llm 那一层**：`packages/llm/llm/src` 里 `retry-policy.ts` 201、`assembler.ts` 208、`message.ts` 319、`adapter-failure.ts` 109——合计 837 行；再加 `llm-deepseek/src/translate.ts` 的 180 行。这些一行都不在循环里。

所以「自己写一个循环几百行」这句话是对的，但它算的是错的分母。你要交付的不是那 160 行，是它旁边那几千行：拼接、重试、消息转换、失败分类、记录，以及证明这些没坏的测试。

那么「该不该上框架」就可以换成一个更具体的问题：**你现在卡住的那个 bug，落在这张表的哪一行？**

| 你卡在哪 | 该动的是哪一层 | 为什么不是循环 |
| --- | --- | --- |
| 换一家上游，工具参数解析不了 | 上游适配层（分片归组 + 回填形状） | 循环只负责「拿到调用意图就执行」 |
| 同一条历史 A 家能发、B 家 400 | 消息转换闸门 | 会话层可以宽，发给模型的消息必须窄；pi 把这道转换单独做成 `convertToLlm`（《03》《10》） |
| 同一轮里重复调了两次 `read_file` | 循环的结束条件 | 这是你的判断逻辑，换框架也不会消失 |
| 想在执行前插人工确认 | 工具钩子 | 拦截也得算一次执行、回一条错误结果，否则模型以为工具不存在 |
| 升级框架后工具结果字段变了 | 绑定深度 | 说明你直接吃的是框架的内部结构，不是它承诺的接口 |

表里前三行都不该靠换框架解决；第四、第五行才是选型真正在谈的东西。

## 四层，判据是「第二家上游来了，你要改哪里」

同一个 `read_file` 场景，四类东西的差别不在功能多少，在你被迫改的位置。

- **模型 SDK**：只封装认证、请求、流式解析。第二家上游来了，你得写第二套分片归组——就是第一屏那四行报错的来源。
- **循环封装**：注册工具，循环归它管。第二家来了，你改它给的 adapter；改得动改不动，取决于它有没有留这个口子。本文的默认假设就是这一格——下面说的「框架」都指它。
- **图/流程编排**：把 agent 拆成节点和边，带持久化。第二家来了，节点不用改，但要确认它的 checkpoint 里存的是它自己的消息结构还是你的——存的是它的，你就换不掉它。
- **平台/低代码**：改配置。第二家来了，看平台有没有这个 provider；没有就只能等。

顺着这四层往上，改动点从「我自己的一个函数」变成「别人的一份配置」。省掉的是重复代码，交出去的是排错时的栈。

## 接之前，三个能当场查的

不用读源码通读，用同一件事去试：让 `read_file` 读一个不存在的路径，然后看会话里多出了什么。

| 查什么 | 怎么查 | 什么结果算危险 |
| --- | --- | --- |
| 工具失败怎么进历史 | 故意让工具失败一次，把会话里的那条消息原样打出来 | 历史里什么都没有，或者只有一条 `failed` 而无原因。pi 的做法是把拦截和失败都变成一条错误结果、照常广播（《05 · 工具执行》，`:738-757`、`:488`），模型才有依据改 |
| 能不能只用子集 | 只 import 它的循环，不碰记忆和编排，跑通一次 | import 一个函数把整个 runtime 拉进来——你为了 160 行循环背了几千行 |
| 依赖树的形状 | `npm ls --all`（pnpm 用 `pnpm why <包名>`）看深度和直接依赖数 | 深度由你自己对照基线判断，本文不给阈值：我的建议是把「现在」和「接完之后」的启动时间各记一次 |
| 它在改什么 | 看最近三个 minor 有没有动工具调用的类型 | 改得多不等于不成熟。pi 的 api 层本身就有十几种请求形态，`extensions/types.ts` 到 main 已改三十多行（《07》《10》）——是这块协议本身还在动 |

第四条要解释一下：**「框架不稳定」和「它包的协议在动」是两件事。** 前者换个人写也一样，后者你自研也要跟着改。判断方法是看它改的是抽象（端口、事件名）还是字段名——改字段名是协议跟上了，改端口才是你要付迁移成本。

## 薄端口：一个接口，四个方法

折中方案是给自己的循环定一层很窄的接口，底层先用框架实现：

```java
// 示意签名，类型换成你自己的 DTO；没编译，它要表达的是职责边界
interface AgentPort {
    List<ToolCall> call(List<LlmMessage> history, List<ToolSpec> tools); // 发一次请求
    String execute(String toolName, String argsJson);                    // 执行一次工具，失败也走这里
    void record(String traceJson);                                       // 一行一条，回放要用（第 14 课）
    List<LlmMessage> toLlm(List<Object> sessionMessages);                // 会话宽，模型窄
}
```

第四个方法是我第一版漏掉的，也是第一屏那四行报错的位置：只要差异（分片怎么拼、错误怎么回填）留在循环里，第二家上游就会把它咬穿。把它关进实现里，换上游才是「再加一个实现」，不是「改一遍循环」。

代价要说清：这层抽象必须薄。方法数一只手数得完只是粗略指标，更准的信号是**端口里开始出现「记忆」「规划」「重试策略」这类名词**——那时候你已经在维护一套自己的框架，比直接用别人的更贵，因为只有你在维护它。

## 跑一遍

把整段脚本存成 `probe.mjs`，`node probe.mjs` 就能跑，不需要装任何包。它把两家的分片各自归组、拼成同一份 `{ id, name, input }`：

```js
const fragments = ['{"path"', ': "content/reading/agents/09-', '框架选型.md"', '}'];

const openaiChunks = [
  { choices: [{ delta: { tool_calls: [{ index: 0, id: 'call_1', function: { name: 'read_file', arguments: '' } }] } }] },
  { choices: [{ delta: { tool_calls: [{ index: 0, function: { arguments: fragments[0] } }] } }] },
  { choices: [{ delta: { tool_calls: [{ index: 0, function: { arguments: fragments[1] } }] } }] },
  { choices: [{ delta: { tool_calls: [{ index: 0, function: { arguments: fragments.slice(2).join('') } }] } }] },
];

const anthropicEvents = [
  { type: 'content_block_start', index: 0, content_block: { type: 'tool_use', id: 'toolu_01', name: 'read_file', input: {} } },
  { type: 'content_block_delta', index: 0, delta: { type: 'input_json_delta', partial_json: fragments[0] } },
  { type: 'content_block_delta', index: 0, delta: { type: 'input_json_delta', partial_json: fragments[1] } },
  { type: 'content_block_delta', index: 0, delta: { type: 'input_json_delta', partial_json: fragments.slice(2).join('') } },
];

function collect(pairs) {
  const slots = new Map();
  for (const [index, id, name, piece] of pairs) {
    const s = slots.get(index) ?? { id, name: '', args: '' };
    if (name) s.name = name;
    s.args += piece;
    slots.set(index, s);
  }
  return [...slots.values()].map((s) => ({ id: s.id, name: s.name, input: JSON.parse(s.args) }));
}

const fromOpenAI = openaiChunks.flatMap((c) =>
  (c.choices[0].delta.tool_calls ?? []).map((tc) => [tc.index, tc.id, tc.function.name, tc.function.arguments ?? '']));
const fromAnthropic = anthropicEvents.flatMap((e) =>
  e.type === 'content_block_start'
    ? [[e.index, e.content_block.id, e.content_block.name, '']]
    : e.type === 'content_block_delta'
      ? [[e.index, undefined, '', e.delta.partial_json]]
      : []);

console.log(JSON.stringify(collect(fromOpenAI)));
console.log(JSON.stringify(collect(fromAnthropic)));
```

真实输出（Node v24.14.1，逐字）：

```text
[{"id":"call_1","name":"read_file","input":{"path":"content/reading/agents/09-框架选型.md"}}]
[{"id":"toolu_01","name":"read_file","input":{"path":"content/reading/agents/09-框架选型.md"}}]
```

两家的 envelope 完全不一样——一边是 `tool_calls[].function.arguments` 的字符串增量，一边是 content block 加 `partial_json` 增量——归一之后结构一样。上面这三十几行就是「不该待在循环里」的代码。这层东西在 pi 里叫 api 层：`packages/ai/src/providers/` 有 51 个 provider、`src/api/` 有十几种请求形态，一个 provider 指向一种 api 实现（《07 · pi-ai：五十一家的适配矩阵》，`v1.5.0`）。

还有一个我这段脚本故意没处理的情况：模型输出撞上 token 上限被截断时，`arguments` 可能是半截 JSON，`JSON.parse` 会抛。pi 的处理是这一批工具一个都不执行、每个都回一条错误结果（`failToolCallsFromTruncatedMessage`，《05》）。你的版本至少要有一个出口，别让异常顺着循环抛出去。

## 动手

1. 让 `read_file` 读一个不存在的路径，把你框架在历史里留下的那条消息原样打出来。打不出来，说明失败没进历史——这是要补的第一件事，比换框架优先。
2. 数一下你现在这层端口（或你的循环入口函数）有几个公开方法，再问一句：第二家上游来了，我要碰几处？答案超过一处，差异就还在循环里。
3. 只 import 它的循环模块跑一次最小调用，记两个数：直接依赖数、进程冷启动时间。这两个数是你后面判断「值不值」的唯一依据，别人的评价都不算。

## 还差的

- **没有真连过两家 API。** 本机没有网络也没有 key，`probe.mjs` 里的分片形状是按第 04 课记录的协议结构、加上各家流式增量字段手写的，不是抓包录音。真实上游的字段名、分组键、结束标记以你的日志为准。
- **没有实跑过任何框架。** 文中对 pi 与 DSH 的描述来自内容线那两批文章和我在 `F:\tmp-dsh-review` 上的行数统计；「只 import 循环能不能跑通」「让工具失败后历史里留了什么」这两条是给读者的做法，我自己没在框架上验证。
- **没有测过升级破坏面。** 说「看它改抽象还是改字段」是判据，不是我做过迁移的结论。真要验证，得拿一个旧版本对着新版本跑同一批会话。
- **图编排那一层只给了判据。** 断点续跑、checkpoint 里存什么、换掉引擎要付多少，我都没有实验记录，所以没写「适合什么规模」这类话。
- **低代码平台一句都没展开。** 那条判断来自读别人的迁移记录，不是我自己的操作，读者别把它当成结论用。
