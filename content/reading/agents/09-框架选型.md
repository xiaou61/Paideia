## 先把结论摆出来

所有 Agent 框架替你做的都是同一件事：**把"调模型 → 解析工具调用 → 执行 → 把结果塞回去"这个循环包起来**，再加上消息格式、重试、流式、观测这些外围。

理解这一点之后，选型就变成了两个问题：

1. 我需不需要为这些外围功能引入一个依赖？
2. 我能不能接受它的抽象方式成为我的架构？

**先手写一个 200 行的循环，再决定要不要框架**——这是最省事的判断方法。写完你就知道框架到底帮了你什么，也知道它的抽象有没有碍事。

## 框架的四个层次

不同框架的定位差很远，混着比较没有意义。

**一、模型 SDK**

只封装 API 调用（认证、重试、流式解析）。这是最小的一层，几乎不限制你。

**二、循环封装**

把工具调用循环、消息历史管理包好，你只需要注册工具。省掉重复代码，但控制流基本被它接管。

**三、图/流程编排**

把 Agent 描述成节点和边（有向图），支持分支、并行、状态持久化。适合流程复杂、需要断点续跑的场景，代价是学习曲线陡，简单任务会被写得很绕。

**四、平台/低代码**

可视化拖拽，不用写代码。上手快，但一旦超出模板能力，绕不过去。

越往下，省的事越多，绑定也越深。**选型时要问的是"我三个月后会不会想拆掉它"，而不是"它功能多不多"。**

## 一个能立刻用的判断表

| 你的情况 | 建议 |
| --- | --- |
| 只有一个固定流程，模型只负责其中几步 | 直接用模型 SDK，别上框架 |
| 单 Agent + 十来个工具 | 循环封装类框架能省事 |
| 流程有分支、要中断恢复、要人工审批节点 | 图编排类更合适 |
| 非工程团队做原型 | 低代码平台 |

大部分产品落在前两行。**第二行自己写循环也就几百行**，这是很多团队最终的选择。

## 框架真正的价值在哪

不是"少写代码"，而是这几件容易写错的事：

**流式解析**

边收边解析增量，还要处理工具调用的分片到达。这个如果自己写，很容易写出"最后一个 chunk 丢失"这类 bug。

**重试与退避**

限流、超时、上游 5xx 的差异处理。哪些该重试、重试几次、退避多久，都有讲究。

**消息格式转换**

不同上游对 tool call 的格式要求不一样——有的要求工具结果逐条发、有的不接受思考内容进历史、有的对空字符串报错。这些差异会不断咬你。

**可观测**

记录每轮的工具、参数、结果、耗时。

第四条尤其重要。**你最终一定会需要完整的调用记录**，因为 Agent 的失败是静默的。如果框架没提供，你自己补的工作量可能比写循环还大。

## 框架的代价

**抽象泄漏**

上游的怪癖（某种格式限制、某个字段不能空）会穿透框架，你得绕过它的抽象去修。这类问题在升级框架时反复出现。

典型表现：框架提供了 `callModel(messages)`，但你需要传一个框架不支持的参数，于是要么等它加，要么 hack 进去。

**版本不稳定**

这个领域迭代极快，一年内主版本可能换两三次。绑定越深，升级越痛。

**调试变难**

出错时你要同时理解自己的代码和框架的行为。手写循环时，栈就是你写的那些函数。

**依赖体积**

一个框架可能带来几十个传递依赖。如果是 Java 后端，这直接影响启动时间与安全面。

## 怎么判断一个框架是否靠谱

四个检查项，都能在半小时内做完。

**一、看它怎么处理工具调用失败**

文档里有没有写"工具报错时消息怎么构造"？没有的话，你上线后一定会踩。

这一项最能反映成熟度。工具失败是 Agent 的日常，不处理它的框架说明作者没在生产里跑过。

**二、看它能不能只用一个子集**

能不能只用它的循环、不用它的记忆和编排？能，说明分层清楚。

**三、看它的 issue 区**

搜"tool call"和"streaming"，看有没有长期未修的核心问题。

**四、看它的依赖树**

拉下来看引入了多少东西。

## 一种折中做法

**薄端口 + 可替换实现**：自己定义一层很窄的接口（发消息、调工具、记日志），底层先用框架实现，将来能换成手写或另一个框架。

```java
// 端口只有三个方法，不含"记忆""规划"这类概念
interface AgentPort {
    ModelReply call(List<Message> messages, List<ToolSpec> tools);
    ToolResult execute(ToolCall call);
    void record(RunTrace trace);
}
```

代价是多写一层抽象。收益是**不被单一框架锁死**——这在迭代这么快的领域很值。

但要注意：这层抽象要真的很薄。一旦它开始包含"记忆管理""规划策略"这类概念，它就变成了你自己的框架，维护成本立刻上来。

判断标准：**端口里的方法数能不能用一只手数完**。超过五个，多半已经在造框架了。

## 常见误区

### 误区：框架功能越多，开发越快

**你以为**：一套框架把记忆、编排、工具全包了，最省事。
**其实**：用不到的模块是负债——它们带来依赖、版本升级压力和调试干扰。
**怎么验证**：看你的依赖树里，实际用到的模块占多少比例。

### 误区：自己写循环太原始，不够工程化

**你以为**：手写说明水平不够。
**其实**：核心循环只有几百行，很多成熟团队最终都收敛到手写，因为可控、可调、好排查。
**怎么验证**：读一遍你正在用的框架的循环实现——它也就是那几百行，只是多了重试和日志。

### 误区：低代码平台能一直用下去

**你以为**：先拖拽出原型，后面再迁移。
**其实**：超出模板能力的需求会在平台里越绕越死，而迁移时业务逻辑全在可视化配置里，几乎没法带走。
**怎么验证**：拿一个稍微复杂的需求去试（比如工具返回需要自定义截断），看要绕多少弯。

### 误区：薄端口这层抽象没有成本

**你以为**：多写个接口而已。
**其实**：抽象一旦变厚（开始含记忆、规划、会话状态），你就得自己维护一套框架，比直接用别人的更贵。
**怎么验证**：数一下你的端口接口方法数。超过五个就要警惕。

## 小结

框架都在包同一个循环，差别在包的层次与绑定深度。选型先问"我需不需要它"，而不是"它功能全不全"。判断成熟度看它怎么处理工具调用失败。折中方案是薄端口，但抽象必须保持足够薄，否则就变成自研框架。
