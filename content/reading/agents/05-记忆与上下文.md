## 第 18 轮，它说「您正在使用 Redis」

我拿一个给商家用的玩具客服 Agent 练手：它能查订单，也能回答缓存配置，还会从每轮对话里抽「用户信息」。第 1 轮用户说：

> 我可能会用 Redis 做缓存，还没定。

抽取器跑出来是这样（一个玩具规则，不是模型调用）：

```python
import json, re

utterance = "我可能会用 Redis 做缓存，还没定。"
# 玩具规则：句子里出现「用 X」就抽成「用户使用 X」
m = re.search(r"用\s*([A-Za-z]+)", utterance)
record = {
    "type": "fact",
    "text": f"用户使用 {m.group(1)}",
    "confidence": 0.92,
    "source": {"turn": 1, "quote": utterance},
}
print(json.dumps(record, ensure_ascii=False, indent=2))
```

```json
{
  "type": "fact",
  "text": "用户使用 Redis",
  "confidence": 0.92,
  "source": {
    "turn": 1,
    "quote": "我可能会用 Redis 做缓存，还没定。"
  }
}
```

第 18 轮用户问「缓存穿透怎么处理」，复现时系统把这条记录拼进 system：

```text
已知用户信息：
- 用户使用 Redis（置信度 0.92，来源：第 1 轮）
```

Agent 答：

```text
您正在使用 Redis，可以在缓存层前面加布隆过滤器……
```

这条回复是我按这份请求手写的（本机没有模型 API key，没调模型）；但失败链路是完整的：存了、检索到了、拼进去了，三个环节都没坏，坏在第 1 轮那次抽取，它把「可能会用」写成了「使用」，还给了 0.92。

我原来以为记忆系统的问题是「存不下」。这条记录让我改了口：先要解决的是「存进来的东西是谁说的、是什么类型、有多确定」。

这篇沿着这条线走：一次请求里到底有什么、「忘了」分几类、三种记忆形态怎么配合、历史重发到底多贵、检索和上下文布局各自要做什么。

## 记得 = 这次请求里又拼了一遍

标题里的「模型没有记忆」，说的是模型推理本身；不是说所有 API 产品都无状态。先把两个东西分开：模型推理，和 API 产品。

模型推理没有跨请求状态。一次调用只根据这次送进去的 token 算下一个 token；你换一个请求，它不会自动想起上一个。服务端的 KV cache、prompt cache 是性能优化，不会把上一次的内容变成这一次的语义记忆。

但 API 产品可以有状态。按 2026-11 的 OpenAI 文档，Responses API 默认 `store: true`，响应在服务端保存 30 天（除非你的组织策略或请求里关掉）；下一轮可以只发 `previous_response_id`，服务端把上一轮的输入输出接上。Conversations 是更长的会话对象，里面的条目不受这个 30 天 TTL（过期时间）限制，直到你删除。两个值得注意的点：`previous_response_id` 不携带上一轮的顶层 `instructions`，系统提示要每轮重发；即使这样接，链上先前各次响应的所有输入 token，仍然按输入 token 计费。

所以「API 无状态」只对「每次自己带全历史」的接口成立，比如 Chat Completions 和 Anthropic Messages；不能推广到所有 API 产品。更准确的说法是：模型不替你记；API 产品可以替你存，但存下来的东西仍然要占 token、要算钱，也不等于模型真的理解了它。

不管走哪条路，你送进去的都不是一根字符串，而是结构化的 item 列表。Chat Completions 的 `messages` 是数组，`content` 可以是字符串，也可以是分段的内容块（OpenAI 的 content parts、Anthropic 的 content blocks）；Responses API 的 `input` 是 items 数组，`instructions` 是顶层字段。下面是一个 Chat Completions 形状的请求，注意 `tools` 和 `messages` 平级：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是售后客服。只回答订单与缓存配置问题；不确定时先问。已知用户信息：用户使用 Redis（置信度 0.92）。"
    },
    { "role": "user", "content": "我可能会用 Redis 做缓存，还没定。" },
    { "role": "assistant", "content": "好，定了告诉我。" },
    { "role": "user", "content": "缓存穿透怎么处理？" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_order",
        "description": "按订单号查订单状态",
        "parameters": {
          "type": "object",
          "properties": { "order_id": { "type": "string" } },
          "required": ["order_id"]
        }
      }
    }
  ]
}
```

这条请求里同时有第 1 轮原话和一条「用户使用 Redis」。模型看到的不是数据库，而是这份组装后的请求；system 里的记忆块，角色上比历史原话更权威，模型如果跟了前者，不是因为笨，是因为前者在请求里被当成了设定。

「把所有历史拼成一个字符串」只描述了最老的一层封装。今天拼的是数组和块，不是字符串；但「没拼进去就看不到」这条没变。

## 「忘了」有四种，修法完全不同

把请求日志、记忆表、检索结果摆在一起，「忘了」至少分四类。开头那条不在四类里：它不是忘记，是记错。

| 类型 | 现象 | 实际发生了什么 | 先查什么 |
| --- | --- | --- | --- |
| 0. 记错 | 第 18 轮把「可能用」答成「正在用」 | 存进去的事实被改写，或抽取时丢了限定词 | 记忆行的 `source.quote`、`confidence`、抽取规则 |
| 1. 没进上下文 | 问「我叫什么」答不上 | 没存 / 没检索到 / 超窗口 | 请求日志里有没有这条；记忆表有没有；检索分数 |
| 2. 进了但被截断或摘要丢细节 | 知道用户在排查订单，但说不出具体报错 | 裁剪或摘要把细节丢了 | 实际发送的 `messages`，不是数据库里的原文 |
| 3. 进了但模型没用上 | 约束明明在上下文里，回答还是违背 | 可能是位置、指令冲突或注意力分配 | 关键约束在哪一段；有没有相反指令 |
| 4. 取错会话 | 答的是别人的订单 | `conversation_id` 或 `user_id` 串了 | 请求里的 `conversation_id`、`tenant_id`、`user_id` |

我原来以为「忘了」等于「窗口不够大」。排完这张表发现，窗口只占第 1 类里的一种；第 2 类是你自己裁掉的，第 3 类是模型没用上，第 4 类是取错了人。把这四类都叫「记忆不好」，排查时会一直扩窗口，修不到点上。

第 1 类先看请求日志：数据库里有、请求里没有，是组装或检索的问题；请求里有、模型还是答错，往第 3 类查。

第 2 类要对比「数据库原文」和「实际发送的 messages」。摘要写成「用户在用 Redis」，原文却是「可能会用」，这是摘要改写，不是窗口丢了。

第 3 类的一种典型情况是指令冲突：system 里写「用户使用 Redis」，摘要里写「缓存方案未定」，模型跟了更权威的那条。它不是没看到，是看到了但用错了。

第 4 类在日志里看起来像「记错」，实际是越权：`conversation_id` 从客户端传、查询漏了 `tenant_id`，都会把别人的记忆拼进来。

## 三种记忆形态，对应三个不同的问题

这三种都是记忆，不是只有第三种才算。把它们分开，是因为它们解决的不是同一个问题。

**最近 N 轮原文 = working memory。** 零改写，细节全；代价是每轮重发，成本线性涨。第 18 轮把第 1 轮挤出窗口，就是这一层在起作用。滑动窗口只决定 working memory 的边界，不是记忆系统的全部。

**摘要 = 压缩后的 episodic memory。** 把第 1–12 轮压成一段，长度可控，适合跨天恢复和长任务。代价是细节会丢，而且摘要本身是模型写的，会改写。

第 12 轮的摘要要写成「用户可能用 Redis，未定；已确认 MySQL 8.0」，不能写成「用户使用 Redis」。摘要里丢了限定词，后面就会把猜测当事实。摘要还要留原文指针，比如 `source_turns: 1-12`；需要细节时能回去查。只有不存原文的实现，才是真的不可追溯。

关键事实不该只活在摘要里；能落到结构化字段的，单独存一份。

旧会话不必每轮重放；需要细节时按 `conversation_id` + turn 范围取回原文，取回后再拼进当前请求。这样「三个月前的第 3 轮」不是每轮都带着，而是要用的时候才翻出来。

**结构化事实 = semantic memory。** 把稳定的事实、偏好、计划抽成字段，带类型、来源、置信度、有效期。

它的优势不是「不会错」——开头那条就是它错的例子；优势是「不会被下一次复述改写」。原文可以改，字段可以改，改哪条有记录；摘要做不到这一点。

它也不是唯一的「记忆系统」。三层是配合关系：历史负责过程和细节，摘要负责把长过程压短，事实负责跨会话稳定复用。

存什么、存哪、什么时候取、取多少、怎么过期，可以用这张表定：

| 存什么 | 存哪 | 什么时候取 | 取多少 | 怎么过期 |
| --- | --- | --- | --- | --- |
| 最近 N 轮原文（working memory） | 会话表或 Redis，按 `conversation_id` 分区 | 每轮都取 | 剩余预算内，按轮次倒序 | 滑出窗口就不再取；原文仍留在归档表 |
| 旧会话摘要（episodic） | 会话表，一段或几段 | 超过 N 轮、跨天恢复、切换任务 | 1–2 段，几百 token | 新摘要覆盖旧摘要，保留原文指针 |
| 稳定事实 / 偏好（semantic） | 结构化表，带类型、来源、置信度 | 写入时确认；读取时按 query 检索 | 先取 3–5 条，再看预算 | TTL、用户删除、被新事实 `superseded` |
| 外部资料（RAG，不是记忆） | 文档索引 | 每次请求 | 先取 3–5 块，再看预算 | 按文档版本重建索引 |

这张表里的数量是预算起点，不是实测最优值。每一行都在花预算，也都多一处会挂的东西；先问这一层是不是现在就需要。

## 跑一遍：20 轮全量重发是多少 token

假设每轮新增 500 token，20 轮都把历史全带上。第 n 轮的输入是 500n：第 20 轮整轮 10,000，其中历史 9,500、本轮新增 500。累计不是 9,500，也不是 9,500 乘 20。

```python
PER_TURN = 500
TURNS = 20
CONVERSATIONS = 1000

inputs = [PER_TURN * n for n in range(1, TURNS + 1)]
total = sum(inputs)
last = inputs[-1]
last_history = last - PER_TURN

print(f"每轮新增: {PER_TURN} token")
print(f"第 {TURNS} 轮请求输入: {last:,} token（历史 {last_history:,} + 本轮 {PER_TURN}）")
print(f"{TURNS} 轮累计输入: {total:,} token")
print(f"累计 / 第 {TURNS} 轮历史: {total / last_history:.2f}x")
print(f"{CONVERSATIONS} 段对话的输入: {total * CONVERSATIONS:,} token")
```

```text
每轮新增: 500 token
第 20 轮请求输入: 10,000 token（历史 9,500 + 本轮 500）
20 轮累计输入: 105,000 token
累计 / 第 20 轮历史: 11.05x
1000 段对话的输入: 105,000,000 token
```

公式：

```text
Σ(n=1..T) c·n = c·T(T+1)/2
c=500, T=20 → 500×20×21/2 = 105,000
```

105,000 是第 20 轮历史部分 9,500 的 11.05 倍。1000 段这样的 20 轮对话，光这部分输入（绝大部分是历史）就是 1.05 亿 token；原文只算第 20 轮单次再乘 1000，会得到 950 万，差了一个数量级。

这还只是对话本身，不含 system、检索资料、工具结果和输出。`previous_response_id` 能让请求体变小，因为不用重传；但按文档，链上先前输入 token 仍按输入计费。缓存命中可能打折，不会把 token 数变成 0。

别用字数估 token。本机 Python 3.11.5 + tiktoken `o200k_base` 量了一下：「我可能会用 Redis 做缓存，还没定。」20 个字符 11 token；「用户使用 Redis」10 个字符 3 token。500 这个假设要用你自己的对话量。

## 检索：别让「问过」变成「会用」

存了 500 条记忆，不可能每轮全塞。要检索。检索的第一件事不是算相似度，是先确定这条记忆是什么类型、从哪来、能不能用。

一个具体的反例：记忆里有「用户问过 Redis 持久化」和「用户精通 Redis 持久化」。两句话的主题都是 Redis 持久化；向量相似度算的是主题接近程度，分不出「问过」和「精通」的谓词差别。相似度只能告诉你「在说同一个话题」，不能告诉你「这句话成立不成立」。如果 top-k 里同时有这两条，「问过」那条就可能被当成「会用」的证据。

所以记忆记录至少要带四样东西：类型（事实 / 偏好 / 计划 / 事件）、来源（哪轮原话）、置信度（用户确认 vs 模型抽取）、时间（何时生效 / 失效）。

一条记忆记录至少要长这样（字段齐全，值对不对是另一回事）：

```json
{
  "id": "mem_1042",
  "tenant_id": "t_01",
  "user_id": "u_88",
  "conversation_id": "c_88",
  "scope": "private",
  "type": "fact",
  "subject": "用户",
  "predicate": "使用",
  "object": "Redis",
  "confidence": 0.92,
  "source": {
    "turn": 1,
    "quote": "我可能会用 Redis 做缓存，还没定。"
  },
  "valid_from": "2026-11-19T10:00:00+08:00",
  "valid_to": null,
  "status": "active",
  "superseded_by": null
}
```

`type` 区分事实、偏好、计划和事件；`source` 让你能回到原话；`confidence` 区分用户确认和模型抽取；`status` 和 `superseded_by` 让新事实能覆盖旧事实；`tenant_id` / `user_id` / `scope` 是权限边界，不是可选的标签。

排序可以用加权分：

```text
score = w_r * recency + w_i * importance + w_s * similarity
```

`recency` 用指数衰减或 `1/(1+age)`；`importance` 给用户确认的事实、明确偏好、当前任务更高的权重；`similarity` 用关键词或向量。权重没有通用值，要在你自己的评测集上定；没有评测集，就先固定一组，记录每次改动的影响。

排序解决的是先看哪条，不解决这条是不是真的；真假要靠来源和确认。

关键词和向量可以各取一个排名列表，再用 RRF 合并（Reciprocal Rank Fusion，Cormack et al., 2009）：`score = Σ 1/(60 + rank_i)`。这样不用把两种分数硬归一化到同一个尺度。

同一 `subject + predicate` 出现新值时，不要追加一条就完事。给旧记录 `status = superseded`、`superseded_by = new_id`、`valid_to = ...`；读取时只取 `status = active`，需要历史时再按 id 查。

回到这条主线：第 1 轮「可能用 Redis」和第 9 轮「Redis 只是本地缓存候选，数据库定了 MySQL 8.0」不是二选一；真正要改的是 Redis 那条的 `type` 和 `confidence`：它是 `plan`，不是 `fact`。如果后面用户明确说「不用 Redis 了」，再把旧记录标成 `superseded`。

同一 `subject + predicate + object` 的重复记录合并，更新 `last_seen` 和 `evidence_count`。但「模型又复述了一遍」不算新证据；靠重复提高置信度，会把一句猜测越洗越真。

记忆表每行都要有 `tenant_id`、`user_id`、`scope`（private / conversation / team）。检索时先按这些字段过滤，再算相似度；不要把权限过滤放在 top-k 之后。`conversation_id` 从服务端会话取，不要直接信客户端传的值。团队共享记忆要显式标 `scope=team` 并单独授权，不要用「相似度高」绕过权限。

## 上下文怎么摆：开头、结尾、中间

组装请求时，位置不是随便排的。一个实用的布局：

```text
[开头] 系统约束：角色、权限、不能做什么、必须引用来源
[中间] 检索资料：每块标 source_id 和标题，最相关的 1–2 块放在这段的头尾
[结尾] 当前问题 + 输出格式 + 这次一定要遵守的 1–2 条约束
```

为什么不是把「最近的对话」放两头？因为「近」是时间，「位置」是注意力。Lost in the Middle（Liu et al., TACL 2024，arXiv:2307.03172）测的是：同一段相关信息放在长上下文开头或结尾，比放在正中间更容易被用上。它说的是相关信息的位置，不是消息的新旧。第 1 轮的原话很重要，不代表它该放开头；它该不该出现，取决于它和当前问题相关不相关。

系统约束放开头，是因为它要覆盖整段；当前问题和输出格式放结尾，是因为模型从结尾接着生成；检索资料放中间，但把最相关的块放在资料段的两端，并标来源。这样既不把整段资料塞到系统提示后面，也不把关键约束埋进中间。

工具呢？原生 function calling 的 `tools` 是请求的顶层字段，和 `messages` 平级，不在任何一条 message 里。API 会把它和 messages 一起组装给模型；你能控制的是工具数量、描述精度、是否按需暴露。只有文本 ReAct 才需要把工具说明写进提示词，这时才轮到「放前面还是后面」。

原文说「工具描述放前面」，把两件事混了：原生 tools 不在 messages 里，文本 ReAct 才需要排版。

还有一个值得注意的点：系统提示里的记忆块，角色上比历史原话更权威。第 18 轮那条错误事实写成「已知用户信息：用户使用 Redis」，它就比第 1 轮那句「我可能会用」更像一条已经确认的结论。模型如果跟了 system 那条，不是因为笨，是因为前者在请求里被当成了设定，而不是待核对的原话。

## 写入口：模型提议，用户确认

最容易被低估的做法是全自动提取、不做确认。它跑起来很顺，前几轮看起来都对；错的那条不会立刻报错，而是在第 18 轮以一个很自信的句子出现。

更稳的形态是：模型提议、用户确认。它说「我记一下：你可能在用 Redis，还没定，对吗？」，用户点一下才落库。确认之后还要有更新、删除、过期：用户说「不用 Redis 了」，旧事实要标成 `superseded`，不是再存一条「用户不用 Redis」和旧的同时生效。

记忆列表要让用户看得见：存了什么、从哪句话来的、什么时候过期、怎么删。做不到这四点，用户无法纠正你，你也无法解释第 18 轮为什么那么答。

如果一定要自动提取，至少把 `type` 和 `confidence` 写对：「可能用」是 `plan`，置信度低；「已确认」才是 `fact`，置信度高。不要让抽取器把情态动词吃掉。

## 检查一下

## 还差的

这一版没做的，具体是四件事：

- **没有真实 embedding 对比。** 本机没有模型 API key，向量召回那段的阈值、权重、召回率都没有实测数字；文里给的是过滤顺序和打分公式，不是调好的参数。
- **没有实现记忆服务。** 表结构、`superseded`、权限过滤都停在设计层，没有迁移、接口和后台页面。
- **没有压测长对话。** 成本算的是 token，不是首 token 延迟和总时长；这两件事随模型、并发、缓存策略变。
- **没有复现多用户串号。** `conversation_id` 取错人的场景需要多账号并发操作，本文只给了排查入口，没有做故障注入。

记忆的难点不在存，在存什么、什么时候取、取多少；这篇只把这几件事拆开，真正的参数还得在你的数据上定。
