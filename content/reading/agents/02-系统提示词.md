## 先把结论摆出来

Agent 的行为，**八成由系统提示词决定**，剩下两成由工具设计决定。模型本身没有那么大的差异。

同一个模型，系统提示词写好写坏，任务成功率能差一倍。而换一个更强的模型，往往只提升十几个百分点。

所以调 Agent 的第一步永远是**改提示词**，不是换模型。这不是省钱的建议，是效果的建议。

## 系统提示词到底在管什么

它管四件事，缺一件就会出问题：

**一、角色与边界**
它是谁、负责什么、不负责什么。

```text
你是代码审查助手，只评论正确性与可读性，不评论风格偏好。
```

后半句比前半句有用。前半句告诉它往哪走，后半句告诉它别往哪走——而后者决定了输出里会不会混进一堆"建议改用 XX 命名风格"。

**二、工具使用规则**
什么时候用哪个工具、什么时候不该用。

```text
查代码用 search_code，不要用 read_file 遍历目录。
一次只搜一个关键词，不要传整句话。
```

**三、输出格式**
要结构化还是自然语言、要多长、必须包含哪些字段。

**四、停止条件**
什么时候算做完。

```text
信息足够给出结论时就停止检索，不要追求完美覆盖。
```

第四条最常被漏掉，而它直接决定了成本。没有停止条件的 Agent 会一直"再多查一点"，因为模型天然倾向"更全面"——在没有人告诉它"够了"的时候。

## 写提示词的三条硬规则

### 规则一：写"不要什么"比写"要什么"更有效

"请给出准确的答案"几乎没有约束力。"答案里不得出现你没从工具结果中读到的类名"——这条能挡住一整类幻觉。

原因是**否定约束可检验**。模型输出后，你和它自己都能检查"有没有出现未读到的类名"，而"准不准确"没法当场判定。

对比一下两种写法的可执行性：

```text
弱：请确保分析准确
强：每个结论后面标注依据（文件名 + 行号），没有依据的结论不要写
```

第二种不只是"更严格"，它是**可验证的**——你甚至能写个脚本检查输出里有没有行号。

### 规则二：规则要能落到具体动作

```text
反例：请谨慎处理用户数据
正例：涉及删除或修改的操作，先输出你打算改什么、等用户确认后再调用工具
```

前者是态度，后者是流程。模型只能执行流程。

判断标准很简单：**这条规则能不能被翻译成"第几步做什么"**。翻译不出来，它就不是规则，是愿望。

### 规则三：矛盾的规则会互相抵消

```text
请尽可能详细地回答
回答要简洁，控制在三句话内
```

两条都在，模型会随机满足其中一条。更糟的是，它可能这次满足第一条、下次满足第二条——你看到的是"行为不稳定"，实际是提示词在打架。

写完通读一遍，把所有互相冲突的要求删掉——**宁可少一条，不要留矛盾**。

常见的隐形矛盾还有：

- "不确定时要说不知道" vs "要给出明确结论"
- "主动提问澄清" vs "不要反问用户，直接给答案"
- "覆盖所有边界情况" vs "控制在 300 字以内"

## 长提示词的结构

系统提示词写到几百行后，模型对中间部分的遵守率会下降（和长上下文是同一个问题）。有效的结构：

```text
# 角色            ← 两三句
# 工作流程        ← 编号步骤，最重要
# 工具使用        ← 每个工具一句边界
# 输出格式        ← 模板或 schema
# 禁止事项        ← 短句列表，放最后
```

三个要点：

- **流程放前面**，它是主体；
- **禁止事项放最后**，末尾位置模型记得最牢；
- **每节用小标题**，模型对结构化的内容遵守率更高。

"末尾记得最牢"不是玄学，是长上下文里"首尾优于中间"的直接应用——同一批内容，放在最后一条的遵守率明显高于埋在中段。

## 一个真实的骨架

```markdown
# 角色
你是排查线上问题的助手。你的结论必须能被工程师直接执行。

# 工作流程
1. 先读用户给的报错信息，提取关键标识（错误码、接口名、时间点）
2. 用 search_code 找相关代码，最多 3 次
3. 找到可疑点后，用 read_file 读完整方法
4. 给出结论：现象 → 根因 → 建议改动

# 工具使用
- search_code：找类名/方法名/错误信息。不要用它搜业务描述。
- read_file：读具体文件。一次最多读一个。
- 工具报错时，把错误如实告诉用户，不要自己猜。

# 输出格式
## 现象
## 根因
## 建议
（每节不超过 5 行）

# 禁止事项
- 不要修改任何文件
- 不要输出你没从工具结果里读到的类名
- 信息不足时直接说缺什么，不要编
```

这个骨架里，**流程是最值钱的部分**。它把"该怎么查"这件事从模型自由发挥变成了固定路径，同时又保留了"查到什么算什么"的灵活性。

## 提示词版本化

提示词是代码，要进版本控制、要有版本号、要和评测结果绑定。

不这么做的后果很具体：三个月后你发现效果变差了，想回滚到"上次好的时候"——但没人记得上次是哪一版。**没有版本号，就没有回滚能力。**

最小做法：

- 提示词放**文件**里（不是硬编码在 Java 字符串里）；
- 提交时带 git 提交号；
- 评测记录里记这个号。

做到这三步，你就能回答"这次效果变好是因为提示词还是因为换了模型"——这是所有优化的前提。

## 少样本示例怎么用

给两三个输入输出示例，能显著提升格式遵循率。但要注意：

- **示例要覆盖边界**，不能全是顺利路径。三个示例里至少一个是"信息不足时该怎么答"；
- **示例会挤占上下文**，三四个就够，多了反而让模型只会照抄；
- **示例要和规则一致**。规则说"简洁"，示例却写了五百字，模型会跟示例走。

最后一条比看起来严重。模型对示例的模仿优先于对规则的遵守——所以示例实际上是"最硬的规则"。写示例时按最严格的标准来。

## 常见误区

### 误区：换更强的模型比改提示词划算

**你以为**：效果不好就换个更贵的模型。
**其实**：提示词的问题换模型解决不了。同一个提示词换模型通常只提升十几个百分点，而修好提示词能翻倍。
**怎么验证**：固定评测集，先只改提示词跑一遍，再只换模型跑一遍，对比提升幅度。

### 误区：提示词越长越周全

**你以为**：把所有情况都写进去，模型就不会错。
**其实**：超过几百行后，中间部分的遵守率明显下降，而且规则之间更容易互相冲突。
**怎么验证**：把同一套规则分别写成 50 行和 300 行，跑同一批任务比较遵守率。

### 误区：示例越多，格式越稳

**你以为**：多给几个例子总没坏处。
**其实**：示例占上下文，且会挤掉真正的任务信息；示例与规则不一致时，模型跟示例走。
**怎么验证**：把示例从 2 个加到 8 个，看格式正确率是否继续上升——通常会持平或下降。

### 误区：提示词是"写一次就完"的配置

**你以为**：上线前写一版，之后不用动。
**其实**：它是行为的主要来源，会随需求不断调整，且每次调整都可能让别处变差——所以才需要评测集和版本号。
**怎么验证**：看你的提示词文件有多少次提交。少于三次，说明它还没被真正调过。

## 小结

Agent 的行为八成由系统提示词决定。它要管角色、工具规则、输出格式、停止条件四件事。三条硬规则：写可检验的否定约束、规则落到具体动作、不留矛盾。长提示词按"流程在前、禁止事项在后"结构，并且必须进版本控制。示例比规则更硬，写的时候按最严格的标准来。
