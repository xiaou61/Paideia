## 先把结论摆出来

模型**本身不能做任何事**。它只会输出文本。所谓"调用工具"，全过程是这样的：

```sketch
{
  "title": "模型只出文本，干活的是宿主",
  "rows": [
    [
      { "id": "model", "title": "模型输出", "sub": "一段「要调哪个工具」的 JSON", "tone": "gray" },
      { "id": "host", "title": "宿主解析并执行", "sub": "真正调用函数或 HTTP", "tone": "blue" },
      { "id": "back", "title": "结果塞回上下文", "sub": "模型再决定下一步", "tone": "green" }
    ]
  ],
  "arrows": [
    { "from": "model", "to": "host" },
    { "from": "host", "to": "back" }
  ]
}
```

1. 你在请求里附上一份**工具清单**（名字、用途、参数结构）；
2. 模型输出一段结构化文本，表示"我想调 `search_code`，参数是 `{"q": "OrderMapper"}`"；
3. **你的代码**解析这段文本、真的去执行、把结果拼成一条新消息；
4. 再发给模型。

模型从头到尾没碰过任何系统。它只是"说要调什么"，执行权一直在你手里。

想通这一点，工具的所有问题都变成了提示词问题和参数校验问题。

## 一次工具调用，前后到底发生了什么

把中间过程拆开看，一次请求里其实有三样东西在变：

```text
请求 1：
  tools:   [search_code, read_file]        ← 工具清单，每次都要带
  messages:[system, user]

响应 1：
  { tool_calls: [{ id: "call_1",
                   name: "search_code",
                   arguments: '{"q":"OrderMapper"}' }] }

你做的事：
  解析 arguments → 校验 → 真的执行 → 拿到结果

请求 2：
  tools:   [search_code, read_file]        ← 还是同一份，重复发送
  messages:[system, user, assistant(tool_calls), tool(call_1, 结果)]
```

两个容易忽略的成本：

- **工具清单每次都重发**。5 个工具、每个 200 token，就是 1000 token，每一轮都付；
- **工具结果进历史后一直留着**。第 5 轮的时候，第 1 轮那个 3000 行的搜索结果还在上下文里。

这两点是后面讲成本时的主要来源。

## 工具描述就是提示词

新手最容易犯的错：把工具描述当成给同事看的接口注释，写得很简短。

```text
// 反例
search_code: 搜索代码
```

模型要靠这段文字判断"这个场景该不该用它"。写得含糊，它就会选错工具或者干脆不选。对比：

```text
// 正例
search_code: 在代码库里按关键词搜索。适合找类名、方法名、错误信息。
  不适合查业务逻辑的说明（那用 read_file 读具体文件）。
  一次只搜一个关键词，不要传整句话。
```

三个要点：**做什么**、**什么时候不该用**、**参数有什么坑**。

第二点最常被漏掉，而它恰恰是减少误用的关键。原因是模型在工具选择时做的是"排除法"——它看到 10 个工具，需要判断哪些不适用。你告诉它"什么时候不该用"，等于直接给了排除依据。

一个具体的对比实验：给两个相似工具 `search_code`（搜代码）和 `search_docs`（搜文档），只写"做什么"时，模型会经常用错；补上"查代码里的实现用 search_code，查设计文档用 search_docs"，错误率明显下降。

工具描述里的每一个字都在花 token（每次请求都要带上），但它属于"值得花"的那类成本。

## 参数结构要严格

模型给参数是"生成"出来的，不是"填表"出来的。它可能给错类型、漏字段、编一个不存在的枚举值。

所以每个工具在真正执行前必须做三件事：

- **类型校验**：要整数给了字符串，拒绝；
- **范围校验**：`limit` 上限 100，给了 5000，截断或拒绝；
- **权限校验**：这个用户能不能查这条记录，跟模型说什么无关。

第三种情况最容易出事，看个例子：

```text
工具：get_document(documentId)
模型传：{"documentId": 12345}

错误实现：SELECT * FROM documents WHERE id = 12345
正确实现：SELECT * FROM documents WHERE id = 12345 AND owner_id = 当前用户
```

第一种实现里，模型（或被诱导的模型）传一个别人的 id 就能读到别人的数据。**这不是模型的问题，是工具没做归属校验。**

第三条是安全底线。**模型给出的参数是不可信输入**，和用户直接提交的表单没有区别。区别只在于：用户输入是明显的攻击面，模型参数容易被当成"自己人"。

## 工具一多就会坏

单看每个工具都合理，放到一起就开始互相干扰。经验上：

- **5 个以内**：基本稳定；
- **10 个左右**：开始出现选错工具；
- **20 个以上**：明显退化，参数格式错误率上升。

原因不难理解：所有工具描述都在同一个上下文里竞争注意力，工具越多，每个工具分到的"注意力"越少；而且相似的工具描述会互相混淆。

还有一个更隐蔽的成本：**工具越多，每次请求越贵**。20 个工具、每个 200 token，光是清单就 4000 token，每一轮都付。8 轮的 Agent 光工具清单就烧掉 32000 token。

三种应对，按代价从小到大：

1. **砍**：能合并的合并，能删的删。大多数产品真正需要的工具不到 8 个。
2. **分组**：先让模型选大类，再给那一类的工具。多一次调用，但选择空间小很多。
3. **按需加载**：给模型一个"查工具"的工具，它需要时自己去检索。适合工具很多但每次只用几个的场景（企业内部 API 网关就是这样）。

第三种是个很有意思的模式——**用一个工具来管理其他工具**。代价是模型得先意识到"可能有我不知道的工具"，这本身要靠提示词引导。

## MCP 在解决什么

上面这些是"工具怎么接"的问题。MCP（Model Context Protocol）解决的是另一个问题：**同一个工具，怎么让不同的客户端都能用**。

在没有 MCP 之前，你给一个客户端写一套工具、给 IDE 写一套、给自己的 Agent 再写一套，三份代码三套格式。

MCP 定义了一套标准的"工具清单 + 调用"协议，服务端实现一次，任何支持 MCP 的客户端都能连上。

它带来的实际变化：

- **工具从"写在应用里"变成"跑在进程外"**——可以是本地进程，也可以是远程 HTTP 服务；
- **能力可以组合**：一个客户端同时连几个 MCP server，工具清单合并；
- **权限边界更清楚**：server 是独立进程，能单独限制它能访问什么。

一个典型的结构：

```text
你的 Agent
  ├── MCP server: 文件系统（只能读 /data/docs）
  ├── MCP server: 数据库（只读账号）
  └── MCP server: 内部 API（带独立 token）
```

三个 server 各有自己的权限，Agent 不需要知道它们怎么实现，只要知道有哪些工具。

要注意的是：**MCP 不解决工具选错、参数给错、上下文膨胀**——那些还是你自己的问题。它只统一了"怎么发现工具、怎么调用"这一层。工具数量爆炸的问题在 MCP 下依然存在，甚至更严重，因为接一个 server 就多一堆工具。

## 危险分级

按副作用给工具分三档，处理方式完全不同：

| 档位 | 例子 | 处理 |
| --- | --- | --- |
| 只读 | 查文档、搜代码、读配置 | 随便给，出错成本低 |
| 可逆写 | 建草稿、写临时文件 | 给，但要能回滚 |
| 不可逆 | 删数据、发消息、转账、提交代码 | 要人确认，或干脆不给模型 |

第三档的正确做法不是"加一句提示词让它小心"，而是**从工具清单里拿掉**，改成"模型只能建议、人来执行"。

这条在真实事故里反复验证过：模型不会被"请谨慎操作"这句话拦住，它会被"这个工具不存在"拦住。

## 常见误区

### 误区：工具描述越短越省

**你以为**：描述短能省 token。
**其实**：省下的那点 token，会以选错工具、参数错误、多轮重试的形式花回来。
**怎么验证**：把某个工具的"什么时候不该用"补上一句，跑一批同样的任务，看误用率是否下降。

### 误区：接了 MCP 就等于工具体系做好了

**你以为**：协议统一了，工具这块就解决了。
**其实**：MCP 只统一发现与调用。选错工具、参数越界、工具太多导致退化，全都还在。
**怎么验证**：接一个工具很多的 server，看模型的工具选择准确率——通常会掉。

### 误区：模型给的参数可以信任

**你以为**：参数是模型按 schema 生成的，应该没问题。
**其实**：它是生成的不是填表的，可能越界、可能编造 id。这跟用户提交的表单一样是不可信输入。
**怎么验证**：给一个"按 id 查文档"的工具，让它查一条不属于当前用户的记录——不做归属校验就会返回。

### 误区：工具越多，能力越强

**你以为**：多给几个工具，总有用得上的。
**其实**：超过十个后准确率下降，而且每轮都在为清单付 token。工具是负债不是资产。
**怎么验证**：记录每个工具的实际调用次数。一个月没被调用过的，删掉试试。

## 小结

模型不会动手，它只会说要调什么；执行权、校验权、权限判断全在你的代码里。工具描述就是提示词，要写清"什么时候不该用"。工具超过十个开始退化，砍、分组、按需加载是三种解法。MCP 统一了工具的发现与调用，但不解决选择和数量问题。不可逆操作的正确护栏是"不给这个工具"。
