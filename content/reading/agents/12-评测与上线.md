## 一条全部 `status=ok` 的失败 trace

```text
trace refund-eval-001  （手写复现，不是线上 trace）
用户：我上周买的课程，订单号 A1024，超过 7 天了还能退吗？

├─ span search_docs   tool   41ms  status=ok  results=0
├─ span plan          model  1.1s  status=ok  「没检索到，但退款问题可以直接答」
├─ span get_order     tool   33ms  status=ok  refundable=null
├─ span final         model  2.3s  status=ok  「课程支持购买后 30 天内无理由退款……」
└─ span validate      guard   2ms  status=ok  「答案非空」
```

用户看到的是一段完整、礼貌、带步骤的回答。trace 里没有红色，validator 也过了。真正的问题在 `search_docs` 的 `results=0`：它把「没有资料」当成了正常的 `ok`，模型随后用先验补了一个不存在的退款政策。

这是我在本机手写的一条复现，不是线上事故。它要说明的失败模式是：**失败可以伪装成成功**。

我原来以为「工具没报错」等于「工具调用成功」。实际要分开：HTTP 200、空结果、结果不相关是三件事。空结果应该标成 `EMPTY_RESULT`，进入「不能据此断言」的分支，而不是继续生成一个听起来很像真的答案。

## 先把四个词拆开

中文里「可用性」有时指 usability；下面说的是 availability。四个词各管一件事，混在一起就会用一个指标替另一个指标签字。

| 词 | 问的问题 | 一个可执行指标 | 它不能证明 |
| --- | --- | --- | --- |
| 可用性 availability | 请求能不能得到响应 | 非 5xx、非连接失败的响应 / 总请求 | 任务是否答对 |
| 可靠性 reliability | 任务有没有按约定完成 | 通过判据的任务 / 总任务 | 单步工具是否选对 |
| 成本 cost | 每个成功任务花多少 | 总成本 / 成功任务数 | 单次调用单价低 |
| 可观测性 observability | 失败能不能定位 | 失败可定位率：有完整 trace 的失败样本 / 抽样失败样本 | 日志条数多 |

可用性高、可靠性低是常见状态：服务每个请求都返回 200，但 Agent 给出的答案是编的。成本也要按成功任务算，失败重试的钱同样要摊进去；只看单次调用单价，会把「便宜但老失败」的模型算成省钱。

## 三种好，三张不同的成绩单

| 层 | 测什么 | 怎么测 | 会漏什么 | 成本 |
| --- | --- | --- | --- | --- |
| 离线固定集 | 这次改动有没有引入回归 | 固定输入、判据和环境，改前改后跑同一套 | 真实流量漂移、长尾意图、线上工具和索引的差异 | 低，本地或 CI 可跑 |
| 灰度 / AB | 上线后有没有变好 | 随机分流，主指标加护栏指标，按样本量停手 | 长期效果、稀有事件、不同租户的差异 | 中，要流量和统计 |
| 人工 + judge | 主观质量有没有变差 | 抽样人工按 rubric 评；judge 先校准再批量跑 | 覆盖率低、judge 偏差、标注者不一致 | 高，人力和调用都要钱 |

离线固定集回答「有没有回归」；灰度 / AB 回答「上线后有没有变好」；人工 + judge 回答「主观质量有没有变差」。把这三件事压成一句「只有一个办法」，就会漏掉另外两个问题。

## 20 条能抓什么，抓不到什么

20 到 50 条可以起步，但先知道它能抓多大的变化。基线 80%、样本量 20 时，比例的标准误是：

```text
sqrt(0.8 × 0.2 / 20) = 0.0894
```

也就是约 8.9 个百分点。95% Wilson 区间约为 58.4%–91.9%。16/20 掉到 15/20 只是 5 个百分点，落在这个噪声里；把 78% 到 82% 的 4 个百分点变化当成「变好了」，同样分不出来。

| 样本量（基线 80%） | 标准误 | 95% Wilson 区间 |
| --- | --- | --- |
| 20 | 8.9pp | 58.4%–91.9% |
| 50 | 5.7pp | 67.0%–88.8% |
| 100 | 4.0pp | 71.1%–86.7% |
| 500 | 1.8pp | 76.3%–83.3% |

如果要在同一批题上判断 4 个百分点的变化（比较每道题从错到对和从对到错的对子），按 McNemar 检验、10% 不一致对、80% 功效、α=0.05 做规划，大约需要 491 条；判断 2 个百分点大约要 1,962 条。两组独立样本的粗略规划更贵：78% 对 82%，每组约 1,566 条。这些是规划估算，真实样本量要用试点的不一致率重算。

所以 20 条适合冒烟和抓大回归：16/20 掉到 10/20、且 6 道题同向翻错，这种崩坏看得出来；16/20 到 15/20 看不出来，也不该拿它对外宣布 4 个百分点的提升。评测集要覆盖含糊输入、超长输入、诱导输入、工具空结果或报错，每类至少一条，按风险加权；不要四类各写两条就宣称覆盖了真实分布。

## 一条填好的评测 case

| 项 | 内容 |
| --- | --- |
| 输入 | `我上周买的课程，订单号 A1024，超过 7 天了还能退吗？` |
| 固定环境 | `search_docs` 返回 `results=[]`，索引版本 `docs-2026-11-18`；`get_order` 返回 `paid_at=2026-11-11, refundable=null`；两个工具都是 mock，fixture 固定 |
| 期望行为 | 先调用 `search_docs`，query 含「退款」；再调用 `get_order`，参数是 `A1024`；检索为空时，最终答案必须说「当前资料无法确认超过 7 天能否退款」，并给人工复核入口 |
| 判据 | trace 中两个工具都出现；最终答案含「无法确认」或「人工」之一；不得出现「30 天内无理由退款」「随时可退」；`search_docs` 的空结果标成 `EMPTY_RESULT` |
| 来源 | 手写复现，不是线上样本 |

这条 case 的判据是 trace 断言加文本性质断言，不是整串匹配。它能抓住开头那条 trace：工具都调了，但答案编了政策，`forbidden_ok` 会是 false。

## 判分：整串相等只适合标量

结构化不等于整串相等。JSON 的 key 顺序、空格、换行一改，字符串比较就不等了。正确做法是先解析，再按 schema 和字段比较：

```python
import json

def same_fields(actual_text, expected, fields):
    actual = json.loads(actual_text)
    return all(actual.get(key) == expected.get(key) for key in fields)

def score(case, trace, answer):
    calls = [span["tool"] for span in trace if span["type"] == "tool"]
    return {
        "tools_ok": all(name in calls for name in case["must_call"]),
        "forbidden_ok": not any(p in answer for p in case["must_not_contain"]),
        "behavior_ok": any(p in answer for p in case["must_contain_any"]),
    }

print("json_fields=", same_fields('{"b": 2, "a": 1}', {"a": 1, "b": 2}, ["a", "b"]))

case = {
    "must_call": ["search_docs", "get_order"],
    "must_contain_any": ["无法确认", "人工"],
    "must_not_contain": ["30 天内无理由退款", "随时可退"],
}
trace = [
    {"type": "tool", "tool": "search_docs"},
    {"type": "tool", "tool": "get_order"},
]
answer = "可以的。课程支持购买后 30 天内无理由退款，超过 7 天也可以申请。"
result = score(case, trace, answer)
print("case_pass=", all(result.values()), result)
```

```text
json_fields= True
case_pass= False {'tools_ok': True, 'forbidden_ok': False, 'behavior_ok': False}
```

这段只用了 Python 标准库，没有调用模型。它证明这条判据能抓住这条失败，不证明判据覆盖了所有失败。

三种判据的边界要分清：

- **精确匹配**只适合归一化后的标量、枚举、ID。JSON 要解析后按字段或 schema 比较，数字要有容差，枚举要校验取值；不要拿整串相等比 JSON。
- **性质断言**便宜、可解释，但只覆盖你写出来的性质。长度区间单独当奖励会被 Goodhart：模型学会写长就能得分；长度要和内容判据一起用，并监控长度分布。
- **轨迹性质**和文本性质不是一回事。「必须调用过 read_file」只有 trace 记录了工具调用才判得了，从最终答案里推断不出来。
- **judge** 未校准不能做硬门禁；校准后可以。固定 rubric、低温度降低采样方差、多采样、与人标算一致率、持续看漂移；位置和长度偏差要随机顺序盲评，交换 A/B 再判一次。门禁要绑定 judge 的模型快照和 prompt 版本，换版本就重新校准。

## 记录：模型别名不是模型快照

一次跑完的数字，如果只记「模型名 + 版本」，下次还是没法比。同一个别名可能在不同时间指向不同快照；同一个模型也可能走不同 provider 路由。记录至少要能回答：这次到底是哪个模型、哪个 judge、哪个工具、哪个索引、哪套编排。

```text
run_id: <时间>-<序号>
candidate: <provider>/<model>@<snapshot>
provider_route: <route>
prompt: <prompt-version> / <commit>
judge: <provider>/<judge-model>@<snapshot>; prompt=<judge-prompt-version>; rubric=<rubric-version>
tools: search_docs@<version> (mock, fixture=<fixture-version>, mcp=<server-version>); get_order@<version> (real sandbox, mcp=<server-version>)
retrieval_index: <index-version>
sampling: temperature=<...> top_p=<...> seed=<...> max_tokens=<...>
harness: <agent-framework>@<version>
evalset: <path>@<commit>
price_table: <version>
```

其中「工具是 mock 还是真实」「MCP server 版本」「检索索引版本」「provider 路由」「harness 版本」最容易被漏。漏掉任何一项，你看到的「通过率从 78% 涨到 82%」都可能是环境变了，而不是改动有效。

## 成本：4k 的两种含义

成本不能按「单次调用 × 次数」估。每个模型调用的输入都包含之前的历史，所以要逐次求和：

```text
cost/task = Σ(input_tokens_i × input_price + output_tokens_i × output_price)
tasks/day = DAU × 使用率 × 人均任务数
```

先用开头那条 trace 把算术走一遍。系统提示词和工具描述假设为 2,400 token；用户 query 22、`search_docs` 调用 22、空结果 20、`get_order` 调用 15、订单结果 27、最终答案 32，都是用 `tiktoken 0.13.0` 的 `o200k_base` 量出来的。这是 tokenizer 估算，换成别的 encoding 或模型，数会变，也不等于供应商的实际计费 token。

| 轮次 | 输入构成 | 输入 token | 输出 token |
| --- | --- | --- | --- |
| 1 | 2,400 + 22 | 2,422 | 22 |
| 2 | 2,422 + 22 + 20 | 2,464 | 15 |
| 3 | 2,464 + 15 + 27 | 2,506 | 32 |
| 合计 | 三次调用的历史都重新发送 | 7,392 | 69 |

按输入 $3/百万 token、输出 $15/百万 token 的假设价：

```text
7,392 × 3 / 1,000,000 + 69 × 15 / 1,000,000
= 0.022176 + 0.001035
= 0.023211
```

约 $0.0232/任务。2,400 是假设值，不是量出来的；这个数只证明公式和累计方式，不能证明线上成本。

现在看「最多 8 轮、每轮 4k token，最坏 32k 输入」这句话。4k 可能指两种完全不同的东西：

| 4k 的含义 | 8 轮计费输入 | 计算 |
| --- | --- | --- |
| 每次调用的总输入上限 | 最多 32k | 8 × 4k，这是上限，不是「新增 32k」 |
| 每轮新增 4k，历史累积 | 144k | 4 + 8 + … + 32 = 4 × (1 + … + 8) |
| 固定 3k，每轮新增 1k | 52k | 3 + 4 + … + 10 |

如果每轮新增 4k，而每次调用的总输入上限也是 4k，第二轮就装不下历史；这两个约束不能同时按字面成立。写预算时要明确是「每次调用的输入上限」还是「每轮新增的 token」，否则算出来的数会差几倍。

按输入 $3/百万、输出 $15/百万，每轮输出 300 token：

| 8 轮计费输入 | 输入成本 | 输出成本（2.4k） | 合计 |
| --- | --- | --- | --- |
| 32k | $0.096 | $0.036 | $0.132 |
| 52k | $0.156 | $0.036 | $0.192 |
| 144k | $0.432 | $0.036 | $0.468 |

价格是假设，换成你的报价只需要替换两个单价。把业务量代进去：10,000 DAU × 12% 使用率 × 2.5 任务/人 = 3,000 任务/天。52k 场景是 $576/天、$17,280/30 天；144k 场景是 $1,404/天、$42,120/30 天。把 DAU 当任务数会怎样：10,000 × $0.192 = $1,920/天，是 3,000 任务估算的 3.33 倍。

上面的公式算一次任务；运营口径还要再除以成功率：`cost/success = cost/task / success_rate`。失败、重试、超时都产生 token；只记成功那一次，会低估真实账单。

## 容量：按 p95/p99，不按平均

容量规划看尾部，不看平均值：

```text
所需 TPM ≈ 峰值任务速率（任务/分钟）× p99 每任务输入 token × (1 + 重试率)
```

下面是一组手写示例，不是线上数据：p50=6k、p95=20k、p99=40k，峰值 30 任务/分钟，重试率 10%。

| 取值 | 计算 | 所需输入 TPM |
| --- | --- | --- |
| p50 | 30 × 6k × 1.1 | 198k |
| p95 | 30 × 20k × 1.1 | 660k |
| p99 | 30 × 40k × 1.1 | 1.32M |

p99 是 p50 的 6.7 倍。按平均值采购，尾峰会排队或收到 429；平均值只适合做月度预算，不适合做容量下限。

## 灰度：比例、样本、停止规则

灰度不是「先给一小部分用户，跑一周」。要写清楚五件事：cohort、最小样本、主指标、护栏指标、停止规则。下面是一组可直接改的起点，不是线上结果：

```text
cohort: 5% 符合条件流量，按 tenant_id 哈希分流；内部账号和高风险租户不进实验
主指标: 任务成功率（固定判据 + 人工抽样复核）
护栏: P0 安全/越权事件、每次成功任务成本、p95 延迟、工具错误率、放弃率
最小样本: 300 个完成任务/组，只够抓约 10pp 的变化；要按 5pp 停手，每组约 1,248
停止: 任一 P0 事件立即 kill switch；护栏越过阈值，或主指标低 10pp 且区间支持，回滚
时间: 达到样本量或 7 天，先到者为准；7 天没到样本量不放量
```

300/组这个数来自 70% 到 80% 的两组比例规划，约 290 条/组，取整到 300。如果只有 5% 流量，300/组可能要跑不止一周；这时要么延长，要么提高 cohort，不能为了「跑满一周」就放量。

追问率可以看，但不能直接推「提示词理解有偏差」。先把定义写清楚：同一会话 10 分钟内再次提问的任务 / 完成任务数。高追问可能来自答案不完整、用户想继续探索、界面没给下一步、任务本身需要多轮；先看追问内容分类，再决定改提示词、改答案结构还是改交互。

## 四道护栏，按优先级

| 优先级 | 护栏 | 最低实现 | 触发后 |
| --- | --- | --- | --- |
| P0 | 租户隔离与权限 | 数据层按 `tenant_id` / `owner_id` 过滤；检索索引按租户分区；跨租户默认拒绝 | 拒绝、告警、kill switch |
| P0 | 不可逆动作人工确认 | 删除、退款、发消息绑定具体参数；确认一次只放行一次 | 拦截、转人工 |
| P1 | 预算、轮次、超时加 rate limit | 单任务 token、轮次、超时；单用户和租户日限额；全局限流；429 带 retry-after | 返回不完整结果或拒绝、降级 |
| P1 | 失败可见加 kill switch / rollback | `trace_id`、span、工具结果、错误分类；一键切回上一版 prompt / model / tool；告警能点进 trace | 回滚、关闭工具、转人工 |

顺序不是随便排的：越权和数据泄漏不可逆，先挡住；成本和超时可以在边界内止损；可观测性是发现前两类问题的前提。

`kill switch` 要能单独关闭整个 Agent、某个工具、某个租户、某个模型路由，不能只有一个「全站下线」。`rollback` 要能回到上一版 prompt、模型和工具配置，且不依赖数据迁移。`rate limit` 至少分用户、租户、全局三层。租户隔离要同时覆盖数据查询、检索索引、配额和 trace，不能只在前端做过滤。

## 还差的

- 我没有真实线上流量：开头的 trace、p95/p99 分布、灰度样本都是手写示例，没有在真实用户上验证过这些阈值。
- 我没有模型 API key：judge 与人标的一致率、位置偏差、长度偏差没有在本机跑过；文中给的是校准方法，不是校准结果。
- 工具和检索都是 mock：mock 与真实 MCP server、真实索引的差异没有量化，工具版本漂移也没有测。
- 成本价格是假设：缓存、重试、失败调用和工具费没有完整纳入，真实账单要按供应商价格表重算。
- `kill switch`、`rollback`、租户隔离只给了设计：没有在部署环境做演练，回滚耗时和数据一致性未验证。
