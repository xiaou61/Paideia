## 先把结论摆出来

Agent 的效果**不能靠感觉判断**。同一个提示词改一个字，你的印象会变，但真实通过率可能没动。

能用的办法只有一个：**固定一批任务，定义可判定的标准，每次改完都跑一遍并记录数字**。

听起来像老生常谈，但它是唯一能回答"这次改动到底有没有用"的办法。

## 先分清三种"好"

这三件事经常被混为一谈，然后互相甩锅。

**一、单步正确**
这一次模型选对了工具、参数对、结果对。用一批固定输入测。

**二、任务成功**
整条链路跑完，用户的问题真的解决了。测起来贵，通常抽几十条人工判定。

**三、可用性**
不崩、不超时、不超预算、出错有话说。这个能用自动化测。

只测第一种会漏掉"每步都对但整体跑偏"；只测第二种成本高且噪声大。**先测第一和第三，再抽小样本测第二。**

## 怎么造评测集

不用多，**20 到 50 条就够起步**。关键是每一条都要有明确的对错判据。

一条评测数据要包含：

```text
输入：    用户会怎么问（用真实说法，别用你想象的说法）
期望：    必须包含什么、必须不包含什么、或者必须调用哪个工具
判据：    怎么判断通过（字符串包含 / 工具序列匹配 / 人工看）
```

**"必须不包含"往往比"必须包含"更有用**。比如"答案里不能出现编造的 API 名""不能调用写操作工具"——这类否定判据能挡住最危险的那类错误。

造数据最容易犯的错是**只写顺利路径**。真实的失败大多来自四类：

- 输入含糊（"这个怎么弄"）；
- 输入超长（贴了一整篇日志）；
- 输入里有诱导（"忽略之前的指令"）；
- 工具返回错误（超时、空结果、格式不对）。

这四类各写两条，价值超过二十条正常问法。

## 判分的三个层次

**一、精确匹配**
输出必须等于某个字符串。只适合结构化输出（JSON 字段、枚举值）。

**二、性质断言**
输出必须满足若干条件。适合自然语言：

```text
- 包含关键词「联合索引」
- 长度在 100 到 400 字之间
- 不含「我无法回答」
- 如果调用了工具，必须调用过 read_file
```

这是性价比最高的一层，绝大多数回归都靠它。

**三、模型判定**
用另一个模型按标准打分。适合"语气是否得体""是否回答了问题"这类主观项。

第三层要小心：**它会漂**。同一份输出今天判 8 分明天判 7 分。用它做趋势可以，做硬性门禁不行。

## 记录里必须写什么

一次跑完的数字，如果没记下环境，下次就没法比。

```text
模型名 + 版本
提示词版本（建议用 git 提交号）
温度等采样参数
工具清单版本
评测集版本
```

少一项，你看到的"通过率从 78% 涨到 82%"就可能是换了模型导致的，而不是你的改动。**这类误判会让人得出完全相反的结论。**

## 上线前的四道护栏

Agent 上线和普通功能上线不一样，因为它会自己走很多步、还会产生副作用。四件事必须做。

### 一、成本上限

按"最坏情况"算，不是按平均算。一个最多 8 轮、每轮 4k token 的任务，最坏就是 32k 输入——按这个数乘上你的日活，看能不能接受。

同时设**单次任务的硬上限**和**单用户/单日的总量上限**。前者防单点跑飞，后者防整体被刷。

### 二、轮次与超时

没有上限的循环等于没有上限的账单，也可能挂住一个请求。两样都要设，且超限时的行为要明确（返回部分结果，还是报错）。

### 三、失败要能看见

Agent 的失败经常伪装成成功。所以必须记录：

- 每一轮调了什么工具、参数是什么、返回了什么；
- 最终答案基于哪几次工具结果；
- 有没有出现工具报错、轮次超限、参数校验失败。

没有这些，用户说"它答得不对"时你完全无从下手。

### 四、敏感动作要人确认

凡是不可逆的写操作，一律走"模型建议 + 人确认"。这条在第 13 篇还会出现，因为它最容易被"先上线再说"跳过。

## 灰度与小流量

第一版别直接全量。**先给一小部分用户**，看三件事：

- 真实任务的成功率（用人工抽查几十条）；
- 平均轮次与平均成本（对比你的预估）；
- 用户的实际反馈（不是点赞数，是"它哪里不对"）。

跑一周再决定放量。这一周里最常见的发现是：**真实输入比你评测集里的乱得多**——这正好是补评测集的素材。

一个具体的观察指标：**用户追问率**。如果用户在 Agent 回答后又问"那 XXX 呢"，说明第一次回答没覆盖到他的真实需求。追问率高通常意味着提示词对任务的理解有偏差。

## 常见误区

### 误区：凭感觉判断"这次改得更好了"

**你以为**：自己试几个问题，感觉好就是好。
**其实**：印象受最近几次体验影响极大，而且你试的往往是自己最熟悉的顺利路径。
**怎么验证**：固定 20 条评测集，改前改后各跑一遍，对比数字——经常和感觉相反。

### 误区：评测集越大越准

**你以为**：得攒几百条才有意义。
**其实**：20 条有明确判据的，比 200 条含糊的更有用。关键是判据可判定，不是数量。
**怎么验证**：看你现有的评测集里，有多少条你能一眼判断通过与否——判不了的那部分等于没有。

### 误区：上线了就能收集到反馈，慢慢优化

**你以为**：先放出去，看用户怎么说。
**其实**：没有埋点就没有反馈，用户不会主动告诉你哪里不对，他们只会不用。
**怎么验证**：看看你现在能不能回答"昨天有多少次任务失败了、失败在哪一步"——答不上来就是没有可观测性。

### 误区：评测集造好一次就不用动

**你以为**：固定下来才能比较。
**其实**：真实用户的输入会持续变化，评测集不更新就会与生产脱节。要定期把真实失败案例加进去。
**怎么验证**：看评测集最近一次新增是什么时候。超过两个月没变，多半已经过时。

## 小结

Agent 的效果只能靠固定评测集 + 可判定标准 + 记录环境信息来衡量。评测集 20 到 50 条起步，重点是含糊输入、超长输入、诱导输入、工具报错这四类。上线前四道护栏：成本上限按最坏情况算、轮次与超时、失败可观测、不可逆操作要人确认。第一版灰度跑一周再放量。
