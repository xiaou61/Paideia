## 退款 7 个工作日，现行文档写的是 1–3 个

用户问「退款多久到账」。知识库里有《退款时效 v3》（现行）和《退款时效 v2》（已下线，索引没删）。下面这条轨迹是按 RAG 链路字段构造的**示意**，不是本机实测——本机没有嵌入模型 API key，检索分数和模型回答都无法真跑。

```text
问题：退款多久到账

关键词召回（前 4）：
  1. refund-v2.md#退款时效        18.42  已下线
  2. faq/refund-old.md#到账时间   15.10  已下线
  3. shipping.md#退款             11.87  在用
  4. account.md#退款申请          10.21  在用

refund-v3.md#到账时间：第 27 名；本次只取前 20 进重排
重排后取前 3（k=3）：上面第 1–3 块
实际进入提示词的资料：3 块

这条样本的 recall@3 = 0，recall@20 = 0
```

```text
模型回答（示意）：
退款会在 7 个工作日内原路退回。
```

这条示意里，v3 的标题路径没进索引，正文里的「到账时间」又被分词器当成了一个整串；v2 的「退款时效」逐词命中，所以排到了前面。

我一开始把这类失败记成「模型不听资料」。把轨迹摊开后发现，v3 排在第 27 名，连候选都没进；模型看到的只有 v2 和一条转述 v2 的旧 FAQ。换更强的生成模型，答案还是 7 个工作日——它没机会看到 1–3 个工作日那条。

先查的不是模型，是这条样本的 `recall@k`：正确块有没有进入最终送给模型的上下文。没进去，换模型只是换一个更会复述旧资料的人。

## 开卷考试，但没人检查你翻的是不是旧版

RAG 像开卷考试：先翻到相关那几页，再照着答题。区别是考场上老师会发最新教材，RAG 的索引里可能同时躺着 v2 和 v3；检索把 v2 排第一，模型就会用 v2 答。

它解决「模型没读过你的私有资料」，不解决「模型爱编」。**检索错了会制造更可信的幻觉**：模型拿着看似权威的旧文档，用流畅的语气复述，读者很难分辨。

也别把话说满：检索是最常见的瓶颈，不是唯一上限。检索全对，生成仍可能忽略资料、误读限定语、漏引，或引一条不支持结论的资料。

四段是切分、索引、检索、生成。只有最终生成由生成式 LLM 完成；索引里的 `embed()` 是嵌入模型，重排也常是另一个模型——同样有成本、延迟、限流和版本故障点。

## 切分：按结构切，长度上限按 token 计

切分决定「一块」有多大。太大，检索结果混进无关内容；太小，一句话被切成两半。

**一、按结构切，不按字数切。** Markdown 按标题、代码按函数、HTML 按段落；只有单个结构单元超过上限才硬切。上限按 token 计，不按字数：同样 800 个汉字，不同 tokenizer 下 token 数不同，拿「800 字」当阈值，换模型后就会失准。一个 800 字的函数说明，token 数在上限内就整块保留；超过上限（比如 800 token）才按段落切。

**二、带标题路径。** 「缺索引 | 1.2s」单独看没有主语；前面拼上「[订单模块 > 性能问题 > 慢查询]」，用户问「订单慢查询」时才有词可命中。每次索引只是多存一行标题。

**三、相邻块留 10%–20% 重叠。** 避免关键句正好落在切口上。比如「因为缺少联合索引」在 A 末尾、「导致全表扫描」在 B 开头；不重叠时两块都不完整。重叠太多会让同一段被反复召回，挤占名额。

切分时就把 `doc_id`、`version`、`status`、`heading_path`、`acl` 写进每块。否则后面没法按版本下线，也没法按权限过滤。

## 索引：embed() 也是模型，旧文档要能删

索引为每块建倒排索引（关键词）和向量（语义）。

`embed()` 不是免费的本地函数。它可能是远程 API，也可能是本地模型；有 token 成本、网络延迟、限流和版本变化。索引任务要能重试、断点续跑，失败要记清是哪一块。

嵌入模型换版后要重建旧向量，不要假设新旧可混用；索引记录里存 `embedding_model` 和 `dim`。新旧向量混在一个库里，检索结果会时准时偏，很难从日志上看出来。

文档下线不是删源文件就完事：索引里要按 `doc_id` / `version` 删除或标 `status=offline`，查询默认过滤。开头那条 v2 就是索引没清理。

索引时要把权限过滤需要的字段写进元数据：

```text
chunk_id: refund-v3#2
doc_id: refund-policy
version: v3
status: active
heading_path: 售后 > 退款 > 到账时间
acl: tenant=t_01, visibility=internal, groups=[support]
```

查询时按当前用户权限过滤，别把一份 ACL 烤死在索引里当最终真相。不要等检索出结果再从业务库补权限；补不全就会漏，补得晚，片段可能已经进了日志、缓存或提示词。

## 检索：三种做法，先定义什么叫「不够」

| 做法 | 强项 | 代价与弱项 | 什么时候选 |
| --- | --- | --- | --- |
| 关键词（BM25 一类） | 订单号、错误码等精确匹配；结果可解释 | 仍要分词器和倒排索引；中文要分词；换个说法就漏 | 资料以精确标识符为主；预算只够一套索引 |
| 向量 | 同义表达能召回 | 要嵌入模型和向量存储；相似不等于有用；精确标识符弱 | 用户说法和文档用词差异大；能承担嵌入成本 |
| 混合 | 两路互补 | 多一套索引、多一次查询、多一个故障点 | 评测集显示两路各有盲区；融合后 `recall@k` 确实提升 |

关键词不依赖嵌入模型和向量库，但仍要分词器：SQLite FTS5 的默认 tokenizer 没有中文词典，不按词切，别假设它认识「退款」和「时效」是两个词（本机 SQLite 3.42.0 实测：`退款` 匹配不到 `退款时效`，只匹配空格分开的 `退款 时效`）。向量也不是万能：「退款已提交」和「退款已到账」语义很近，状态不同，向量相似度不一定能区分；`A1024` 和 `A1025` 这类标识符也可能很接近。纯向量和关键词谁召回高，取决于语料和问题分布，不能一概而论。

选择还要看资料质量、预算和是否需要拒答：资料版本混乱、噪声多，先修数据；预算只够一套索引，先关键词；需要拒答，单独设计——分数不能假设跨查询可比，固定阈值容易误拒或漏拒。先收集「资料里确实没有」的问题，单独定策略，或者用重排分数加判断器再人工抽检。

「先关键词，不够再向量」的「不够」要能操作：先准备 50–100 条真实问题做开发集，标正确块的 `doc_id` 和 `version`；算 `recall@k`（k 取实际送给模型的块数）；低于目标（比如 0.9）就看失败样本，是词不匹配、分词错，还是正确块没进索引。只有词不匹配才加向量；没索引或分词错，加向量也救不了。20 条只够 smoke test，后面会算。

### 混合检索：RRF 遇到缺失和并列怎么办

RRF 只看名次：`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60。这样不用把 BM25 分数和余弦相似度硬归一化。

k=60 时：A 关键词第 1、向量第 8 → 1/61+1/68=0.031099；B 关键词第 5、向量第 2 → 1/65+1/62=0.031514；C 只在关键词第 2 → 1/62=0.016129；D 两路都第 3 → 1/63+1/63=0.031746。B 比 A 高，因为两路都靠前；C 只有一路，分数天然低一截。

缺失的一路有两种处理，选一种写进代码：跳过（只在出现它的列表累加，实现简单，但单路命中不额外扣分）；补虚拟名次（按 `k+len(list)+1` 补一项，明确惩罚单路命中）。不要混用。并列时先按最好单路名次、再按 `doc_id` 字典序；这是实现选择，关键是固定。融合前同一路去重；两路都召回同一块时各加一次，这是 RRF 的本意。

RRF 的盲点是不看原始分数：精确命中和弱匹配都排第 1 时贡献一样大。订单号、错误码这类查询，加精确匹配直达规则或加权 RRF。

### 重排：检索宁多勿漏，重排宁准勿多

检索召回比如 20–50 条，重排挑一个更小的 top-k，常见起点 3–5 条。重排常用 cross-encoder 或另一个模型，输入（问题，块）对，比向量点积贵，但能看到交互；也可以是规则（标题命中、版本加权）。

两个阶段要求不同：检索「宁多勿漏」，重排「宁准勿多」。用同一个粗排器做精选，等于让粗筛决定最终上下文。重排的性价比常高于换生成模型——前提是正确块已在候选里、只是名次靠后；根本没召回，重排也救不了。

块数不是定理，3–5 块只是起点，要在评测集上调。取块用 `slice`，不要手写下标；`top` 为空要有出口；`embed`、`rerank` 可能是异步的，接口要统一。

```ts
const k = 4
const hits = await retrieve(q, { tenantId, userId })
const allowed = await acl.filter(hits, { tenantId, userId })
const top = (await rerank(q, allowed)).slice(0, k)

if (top.length === 0) {
  return { answer: '资料中未提及', citations: [] }
}
```

同步实现就去掉 `await`，但不要在一个地方当前提、另一个地方当同步函数调。

## 生成：引用不是装饰，要能被程序检查

三种给法，选择看条件：

**直接拼。** 资料和问题一起给，不要求引用。适合资料少、问题单一、答案不需要逐条核对的内部草稿；模型容易把资料和参数知识混着说。

**带编号、要求引用。** 每块标 `[n]`，每个结论后标依据编号。适合需要核对、拒答、审计的场景；代价是输出变长，模型可能漏引、错引。

**先判断相关性再答。** 让模型先列出哪些资料相关，再回答。适合资料质量参差、噪声多的场景；多一次判断，成本和延迟更高。

选哪种看三件事：资料是否干净、答案是否必须可追溯、预算是否允许两次生成。需要审计或拒答选第二种；资料里混着大量无关块选第三种；内部草稿、资料少，第一种就够。

```text
资料：
[1] {块 1，带 doc_id / version / heading_path}
[2] {块 2}

问题：{问题}

要求：
- 每个事实性结论后标 [n]，n 只能来自上面资料。
- 资料没有的信息，写「资料中未提及」，不要补。
- 引用要能支持该结论；不要用 [1] 支持一个 [1] 里没有的说法。
```

拼提示词时按实际块数遍历，不要写死下标：

```ts
let prompt = '资料：\n'
let n = 1
for (const c of top.slice(0, k)) {
  prompt += `[${n++}] ${c.text}\n`
}
```

模板本身不保证不幻觉。模型可以漏引、错引，也可以引一条真实但不支持结论的资料。用户看到没有 `[n]`，也不一定知道那段是模型自己说的。

生成后至少跑两道程序检查：引用存在性（每个 `[n]` 都能在 `top` 里找到，没有悬空编号）；引用支持结论（把「引用句 + 被引块」交给 NLI 或带 rubric 的 judge，不支持就重生成、降级成「资料中未提及」，或转人工）。

更便宜的存在性查法：要求模型附一句原文摘录，程序检查它是不是被引块的字面子串；它能抓编造引用，抓不住「摘录真实、结论过度」，所以还要支持性检查。

这两道都不是 100%：judge 会错，NLI 对长句和否定不擅长。高风险场景加人工抽检，把样本和失败率写进评测报告。引用展示要带 `doc_id`、`version`、`status`；引用了已下线文档要提示。

## 什么时候不该用 RAG

**资料能全塞进去，而且问题需要看全量。** 几千字说明、20 页规范，每次都要总结全文，直接放提示词更简单；检索会丢信息。边界不是固定数字，按模型窗口、请求预算和问题类型算。

**问题是开放推理，资料里没有可引用的答案。** RAG 提供事实，不提供推理能力；多步推理仍可能错。需要计算、规划、代码执行的，交给工具或程序。

**资料没有权威版本，或者权限边界不清。** 垃圾进垃圾出；检索还会让错误看起来有依据。多租户产品做不到按用户过滤，别上 RAG——它会把检索变成越权读取通道。先把版本、责任人、下线流程和 ACL 建起来。

## 跑一遍：20 条召回率能说明什么

拿 20 条真实问题，人工标正确块，跑 `recall@5`。假设 14 条命中，70%。先算 Wilson 区间。

```python
from math import sqrt

def wilson(k, n, z=1.96):
    p = k / n
    den = 1 + z*z/n
    center = (p + z*z/(2*n)) / den
    half = z/den * sqrt(p*(1-p)/n + z*z/(4*n*n))
    return p, center - half, center + half

for k, n in [(14, 20), (70, 100), (140, 200)]:
    p, lo, hi = wilson(k, n)
    print(f'{k}/{n}: {p:.1%}, 95% CI {lo:.1%}–{hi:.1%}')
```

本机 Python 3.11.5 的输出：

```text
14/20: 70.0%, 95% CI 48.1%–85.5%
70/100: 70.0%, 95% CI 60.4%–78.1%
140/200: 70.0%, 95% CI 63.3%–75.9%
```

同一个 70%，20 条的区间 48.1%–85.5%，分不清 50%、70%、85%；100 条收窄到 60.4%–78.1%，200 条到 63.3%–75.9%。20 条只能做 smoke test：能看出链路是不是完全断了，不能支撑「低于 70% 就换模型」。要写进报告，至少用上百条量级并报区间。

要比较两个方案，先算样本量。比如双侧 95%、80% 功效、分清 50% 与 70%，每组约 93 条（两比例检验）；实际还要留标注错误和分层样本的余量。

两个坑：模型可能靠参数知识答对，答对率不能代替 `recall@k`；标「正确块」要写 `doc_id` 和 `version`，否则会把召回了 v2 算成命中。
