# ReAct 与规划：想一步、做一步

## 我的 Agent 把同一个文件读了三次

我给自己写了一个查慢接口的小 Agent，问它"订单列表为什么慢"。第一轮它去查慢查询日志，拿到这条：

```text
# Time: 2026-11-19T10:41:23.512345+08:00
# User@Host: app[app] @ 10.0.0.7 []  Id: 8123
# Query_time: 2.418311  Lock_time: 0.000102  Rows_sent: 1  Rows_examined: 1002341
SET timestamp=1763517683;
SELECT id, status, created FROM orders WHERE user_id = 8821 AND created >= '2026-11-01';
```

第二轮它去读 `OrderMapper.java`，第三轮去读 `OrderService.java`，第四轮**又去读了一遍 `OrderMapper.java`**——因为前面几轮的工具结果把它挤到了上下文的后半段，它"忘了"自己看过。

这就是 ReAct 在真实项目里的样子：它能干成事，但它绕圈、忘记、过早下结论，跟你我一样。

ReAct 的意思是 **Reason + Act**：让模型在同一个循环里交替"想一步"和"做一步"，而不是先想完全部再一口气执行。它想解决的是一个很具体的问题——**模型先写完整计划，第一步拿到的事实和计划不符时，它不会回头改计划**。

## 为什么"先想清楚再动手"会翻车

假设还是那个问题：订单列表为什么慢。

**先规划后执行**版本，模型会先输出一份 5 步计划：查日志 → 查监控 → 看代码 → 查索引 → 给结论。然后逐步执行。

问题在第一步之后才显形：**写计划时它还没看过日志**。第 3 步"看代码"要看哪个文件，取决于第 1 步日志里出现的表名和方法名——这个信息在写计划的那一刻不存在，所以计划里只能写"看相关代码"，执行时就是瞎猜。

第二个问题更麻烦：**已写下的计划会锁定后续行为**。计划第 4 步是"查索引"，那么即使第 3 步已经发现根本不是索引问题（比如是循环里逐条查库），它仍然倾向于走完第 4 步——计划在那儿，它不想承认前面白写了。

这个现象我自己反复遇到过，但要说清楚：**我没有做过对照实验证明它必然发生**。它更像是把"锚定 + 沉没成本"这两个人类倾向套在模型上的一种合理解释，而我在实际 trace 里确实见过模型为一条已被证伪的计划继续寻找证据。

**边做边看**版本是这样走的：

```text
查慢日志        → 发现是 OrderMapper.selectByUser，2.4 秒，扫了 100 万行
去看这个方法    → 它在一个循环里被逐个调用（典型 N+1）
去看调用处      → OrderService.listByUser 里 for 循环里逐条查
结论            → 不是索引问题，是循环查询
```

每一步都基于上一步的真实结果。第 3 步完全推翻了"可能是索引"的初始假设——但因为它从没把假设写进计划，推翻的成本是零。

差别不在模型聪明不聪明，在**信息什么时候进入上下文**：ReAct 让事实在它被需要的那一刻才进来。

## 循环长什么样

```text
Thought:     先看慢日志，确认哪个方法慢
Action:      read_slow_log(最近一小时)
Observation: Query_time 2.418311 / Rows_examined 1002341
             SELECT ... FROM orders WHERE user_id = 8821 AND created >= '2026-11-01'

Thought:     一百万行对一行，先看这个 SQL 有没有索引可用
Action:      explain_sql(...)
Observation: type=ref, key=idx_orders_user_created, rows=1
             （索引是对的，扫一百万行的不是这句）

Thought:     那可能是被调了太多次，去看调用链
Action:      search_code("selectByUser")
Observation: OrderService.java:88  for (Long id : ids) { mapper.selectByUser(id); }
             （1000 个用户 = 1000 次查询）

Thought:     找到了。是 N+1，不是索引
Answer:      ...
```

这里有个细节值得注意：**这条 trace 里真正的答案是第 2 轮才排除掉的**。「扫了 100 万行」在第一眼看起来就是索引问题，但 `EXPLAIN` 显示 `rows=1`、走了 `idx_orders_user_created`——索引没问题，问题是被调了一千次。

先规划后执行的版本会把"查索引"当成第 4 步的重要一环，然后在这里得出"索引正常，可能是数据库负载"这种含糊结论就收工了。

## Observation 必须是代码生成的

这是整个 ReAct 里唯一不能靠提示词保证的东西。

如果工具报错，而你给模型的 Observation 是"执行成功，结果为空"，它会基于假事实继续推理，一路错到底——而且输出看起来完全自洽。

三种反馈，模型的反应完全不同：

| 你告诉模型的 | 模型的反应 |
| --- | --- |
| 执行成功，结果为空 | 认为确实没有，可能下结论"不存在" |
| 连接超时 | 认为查不到，倾向重试或换路径 |
| 参数错误：缺少字段 user_id | 修正参数重试 |

只有第二、三种有用。第一种是**假信息**，它会把错误固化进结论。

具体做法：解析模型输出时**只接受结构化的工具调用**，任何出现在文本里的 `Observation:` 都不认。模型只能通过真的调一次工具来获得观察。这一条必须写在代码里，写在系统提示词里没用——要求模型"不要编造观察"，它照样会编。

## "规划"在 Agent 里指三种不同的东西

混在一起讲就乱。

**一、隐式规划**（ReAct 就是这种）
每步想一句，没有显式计划列表。灵活，但会绕路——它会反复看同一个文件，就是本文开头那次。

**二、显式计划**
先让模型输出任务列表，逐项执行并打勾。好处是进度可见、不会丢项，用户能看到"还剩几步"；坏处是计划本身可能错，需要"重新规划"机制，而这个机制在实际实现里经常被漏掉，于是一个错计划被硬执行到底。

**三、固定工作流**
步骤写死在代码里，模型只负责每一步内部的处理。**这不算 Agent**（见第 1 篇的判据），但真实产品里用得最多：可测、可控、便宜。

工程里最常见的是混合：外层固定流程，内层某一步交给 ReAct。比如"必须先出大纲、再逐节写"——外层写死，每节内部怎么写让模型自由发挥。

## 五种翻车方式

### 一、绕圈

反复调同一个工具、拿同样的结果。原因是历史里塞了太多内容，早期的观察被稀释（就是我开头遇到的）。

**对策**：在上下文里显式维护"已查过什么"（比如已读文件列表，每轮附在提示词末尾），或者在轮次上限上硬截断。

### 二、过早收手

查了一条信息就下结论。典型表现：只看了调用方没看实现，就断言"这个方法有问题"。

**对策**：系统提示词里写清"结论必须基于哪些证据"，或者加一步自查——让它核对结论是否被 Observation 支持。

### 三、幻觉观察

不调工具，直接编一个 Observation（尤其在它觉得自己知道答案时）。

**对策**：Observation 的生成权完全收归代码（上面那节）。这是架构保证，不是提示词技巧。

### 四、工具选择漂移

工具一多（十几个），开始选错工具或用错参数格式。

**对策**：工具描述写"什么时候该用它"而不只是"它是什么"；工具数量控制在一屏内；必要时分组，先让模型选组再选工具。

### 五、沉没成本

查了 6 轮没找到，不肯说"没找到"，而是编一个看起来合理的结论。

**对策**：在系统提示词里明确允许失败——"如果查了 N 次仍无法确定，就直接说明查不到什么、可能的原因有哪些"。给它一条体面的退路。

## 轮次上限

```text
最多 8 轮工具调用，超出就强制收尾
```

没有上限的循环等于给了一个不封顶的账单和一个可能不结束的请求。

上限到了怎么办？两个选择：

- **直接返回已有信息** + 一句"信息可能不完整"；
- **再调一次模型**让它基于现有信息收尾（这次不许调工具）。

第二种体验更好，代价是多一次调用。要注意：**这个收尾调用只在异常路径触发**，很容易漏测，也就很容易在生产上变成一次超长延迟。

数值怎么定？我没有一套能直接抄的公式。我自己的做法是按任务类型分档（查一个事实 2~3 轮、"为什么慢"这类诊断 8~10 轮、需要改代码的 15 轮左右），然后**记录被截断的比例**：如果某类任务有 20% 以上撞到上限，说明上限偏低或者任务该拆；如果几乎从不撞上限，说明这个上限只是账单保险，没有在改善质量。

这里要纠正一个流传很广的说法：**限制轮次通常能降低成本，但它不保证提升准确率**。降下来的是绕圈的那些调用（省钱），代价是可能有任务被提前截断（可能变差）。"限制轮次同时提升准确率和成本"这句话把方向说反了。

## 留个尾巴

我这套实现里有个还没解决的问题：**绕圈检测只做了"同一工具+同一参数"这一种**。模型读 `OrderMapper.java` 三次可以被抓住，但它换个说法（先 `read_file`、再 `grep` 同一条字符串）就绕过了。真正的去重需要按"信息增益"判断，而我目前没找到便宜的办法——按文件路径判重会误杀（同一个文件换个行区间确实是新信息），按内容哈希判重又抓不到"换个角度查同一件事"。这篇里先把它记成已知缺口。
