## 先把结论摆出来

前面几篇讲的是"git 怎么工作"，这篇讲**日常怎么用得顺手**。四个工具各解决一类问题：

| 工具 | 解决的问题 | 一句话 |
| --- | --- | --- |
| `stash` | 手头改动还没完成，但必须切去处理别的事 | 把工作区与暂存区暂存成一个提交 |
| `cherry-pick` | 只想把某个提交搬到当前分支 | 复制一个提交，不是移动 |
| `tag` | 标记"这是 v1.2.0 发布点" | 给提交起一个不会移动的名字 |
| `bisect` | 不知道哪个提交引入了 bug | 二分查找，log2(n) 次定位 |

四个都不是"高级功能"，而是每天都会遇到的场景。用的前提仍然是前面那套认知：**提交是快照，分支是指针**。

## stash：把没做完的活先收起来

场景：你在 `feature/pay` 上改到一半，线上突然要热修，必须切到 `main`。直接切会带着未提交的改动，可能冲突或误提交。

```text
git stash push -u -m "支付重构进行到一半"
```

- `-u`（`--include-untracked`）把新建但没 add 的文件也收进去，否则它们会留在工作区；
- `-m` 给这条 stash 一个说明，`git stash list` 时能认出来。

常用命令：

```text
git stash list                 # 看有哪些
git stash show -p stash@{0}    # 看这一条具体改了什么
git stash pop stash@{0}        # 恢复并从列表删除
git stash apply stash@{0}      # 恢复但保留列表项（更安全）
git stash drop stash@{0}       # 丢弃
```

`pop` 与 `apply` 的区别只在"要不要保留副本"。**不确定会不会冲突时用 `apply`**，冲突处理坏了还能再来一次。

stash 的本质也是一个提交（挂在 `refs/stash` 下），所以它同样能被 reflog 找到。但它**不是长期存储**：没有说明、越堆越多之后，没人知道哪条是哪条。

**一个容易踩的坑**：`git stash pop` 遇到冲突时，stash 不会自动删除，工作区处于冲突状态。解决冲突后要手动 `git stash drop`，否则下次 `pop` 会重复应用。

## cherry-pick：只把某一个提交搬过来

场景：`main` 上有个 hotfix 提交，`release/1.2` 也需要同一份修复。

```text
git switch release/1.2
git cherry-pick 4c5b3a2
```

它会读取那个提交的改动，在当前分支上**新建一个提交**。注意：

- **哈希会变**：父提交不同，内容哈希就不同；
- 原来的提交仍然留在原分支，不会消失；
- 冲突处理方式与 merge 一样：解决后 `git add`，再 `git cherry-pick --continue`。

适合用的地方：

- hotfix 从 `main` 回合到发布分支；
- 把误提交到错误分支的一次改动搬到正确分支；
- 从别人的分支挑一个独立的小提交。

不适合的地方：

- 一次搬十几个提交——这时候应该 merge 或 rebase；
- 提交之间有依赖关系——单独挑一个可能编译不过。

`git cherry-pick A..B` 可以搬一段连续提交，但顺序与边界要自己确认清楚。

## tag：给发布点起名字

提交哈希没法记，`v1.2.0` 可以。

```text
git tag -a v1.2.0 -m "订单超时取消上线"
git push origin v1.2.0
```

两种 tag：

| 类型 | 命令 | 存什么 |
| --- | --- | --- |
| 轻量 tag | `git tag v1.2.0` | 只是一个指向提交的引用 |
| 附注 tag | `git tag -a v1.2.0 -m "..."` | 一个独立对象，带作者、时间、说明，可签名 |

**发布一律用附注 tag**：它能被 `git describe` 识别，也能签名（`-s`），事后能查是谁、什么时候打的。

**默认 `git push` 不会推 tag**。要么显式 `git push origin <tag>`，要么 `git push --tags`（会推所有本地 tag，容易把测试 tag 也推上去，慎用）。

删除远端 tag 要两步：

```text
git tag -d v1.2.0
git push origin :refs/tags/v1.2.0
```

## bisect：二分找出"哪个提交弄坏了"

场景：上周还好好的，现在有个 bug，中间有 200 个提交，不知道是哪一个引入的。

`git bisect` 做二分查找：你只需要回答"这个提交是好是坏"，它每次砍掉一半。

```text
git bisect start
git bisect bad                 # 当前版本是坏的
git bisect good v1.1.0         # 这个版本是好的
```

之后 git 会检出中间的某个提交，你跑一下验证，然后：

```text
git bisect good    # 这个提交没问题
git bisect bad     # 这个提交有问题
```

大约 8 次就能在 200 个提交里定位到第一个坏提交。

如果你有一个能自动判断的测试脚本，可以全自动：

```text
git bisect run ./scripts/check.sh
```

脚本退出码 0 表示 good，1–127（除 125）表示 bad，125 表示"这个提交测不了，跳过"。

结束时一定要：

```text
git bisect reset
```

否则会停在某个中间提交上，看起来像"代码突然变旧了"。

**bisect 的价值不在命令，而在"可复现的判定标准"**：你得有一个能稳定回答"好还是坏"的脚本或步骤，否则二分无从谈起。

## 一个组合场景

线上报了一个 bug，你怀疑是最近合并的一批提交引入的：

1. `git bisect` 定位到具体提交 `4c5b3a2`；
2. `git show 4c5b3a2` 看它改了什么；
3. 如果修复很小，在当前分支 `git revert 4c5b3a2` 先止血；
4. 再在 `main` 上正常修复，用 `cherry-pick` 回合到发布分支；
5. 发版后 `git tag -a v1.2.1` 标记。

这套动作比"从头读 200 个提交"快得多，也比"猜一个地方改改试试"可靠。

## 常见误区

### 误区：stash 可以当长期分支用

**你以为**：不想开分支，改动先 stash 着，过几天再回来。
**其实**：stash 没有父提交语义、没有分支名、列表里只有一句说明；时间一长就分不清哪条对应哪个任务，而且 `pop` 的顺序很容易搞混。
**怎么验证**：`git stash list` 看一周后的列表——如果已经分不清，就说明该开分支了。

### 误区：`git push` 会把 tag 一起推上去

**你以为**：提交都推了，tag 自然也在。
**其实**：tag 是独立引用，默认不随 `push` 上传。别人 clone 下来看不到你的 tag。
**怎么验证**：推完后在另一台机器 `git tag -l`；为空就说明只推了分支。

### 误区：bisect 必须手动一次次跑

**你以为**：200 个提交要人工验 8 次，太麻烦。
**其实**：只要有一个退出码可靠的检查脚本，`git bisect run` 可以全自动跑完并直接告诉你第一个坏提交。
**怎么验证**：先手动跑 `./scripts/check.sh; echo $?`，确认它在好版本返回 0、坏版本返回非 0，再交给 `bisect run`。

## 小结

`stash` 管"先收起来"，`cherry-pick` 管"只搬一个"，`tag` 管"标记发布点"，`bisect` 管"定位是哪一个提交弄坏的"。四个工具都不改变前面几篇的模型：它们仍然只是在移动指针、复制快照或给提交起名字。真正的门槛不是命令，而是**你有没有一个稳定的判断标准**。
