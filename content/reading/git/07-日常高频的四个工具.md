## 我先 stash 了，然后切不过去

```text
PS> git -C $repo switch main
error: The following untracked working tree files would be overwritten by checkout:
	scratch.txt
Please move or remove them before you switch branches.
Aborting
```

这是我在 `$env:TEMP` 下新建的空仓库里跑出来的。仓库里只有一个玩具模块 `discount.py`（加一个 `notes.md`），分支有 `main`、`feature/coupon`、`release/1.2`；`scratch.txt` 是我在 `feature/coupon` 上随手写的试算，从头到尾没 `git add` 过。

在这条命令之前，我刚执行过 `git stash push`，`status` 看上去也「干净」了。往回倒两条命令就明白它干净在哪：

```text
PS> git -C $repo status --short
 M discount.py
?? scratch.txt

PS> git -C $repo stash push -m 优惠券做到一半
Saved working directory and index state On feature/coupon: 优惠券做到一半

PS> git -C $repo status --short
?? scratch.txt

PS> git -C $repo stash show --stat stash@{0}
 discount.py | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
```

stash 收走的是 `discount.py`，`scratch.txt` 原地没动。`status` 之所以看起来干净，是因为剩下那一行 `??` 既不在 stash 里，也不在任何提交里——它只是被我扫过去没看见。等 `main` 上有人提交了同名的 `scratch.txt`，它就成了上面那个 checkout 错误。

环境：Windows、PowerShell 7、Git 2.45.1.windows.1（`git --version`）。这些临时仓库我都设了 `core.autocrlf false`，否则每条命令后面都会跟一句 `LF will be replaced by CRLF` 的警告，把真正的输出挤到看不见。命令统一写成 `git -C $repo ...`，`$repo` 指当次实验的目录；哈希是各次运行现出的，换个目录就对不上，别照抄。

05 那篇末尾留过一句「默认 stash 不收未跟踪文件，切分支时这些文件会留在原地，可能挡住 checkout」。我当时觉得自己读懂了，直到它真把我挡在 `switch` 这一步。

## 加 `-u` 收进去了，`stash show` 还是少一行

换成 `-u` 再收一次：

```text
PS> git -C $repo stash push -u -m 优惠券做到一半
Saved working directory and index state On feature/coupon: 优惠券做到一半

PS> git -C $repo status --short

PS> git -C $repo stash list
stash@{0}: On feature/coupon: 优惠券做到一半

PS> git -C $repo stash show --stat stash@{0}
 discount.py | 4 +++-
 notes.md    | 1 +
 2 files changed, 4 insertions(+), 1 deletion(-)

PS> git -C $repo stash show -u --stat stash@{0}
 discount.py | 4 +++-
 notes.md    | 1 +
 scratch.txt | 1 +
 3 files changed, 5 insertions(+), 1 deletion(-)
```

同一条 stash、同一次收，两条命令少一个文件。这不代表 `-u` 没生效——`status` 已经空了，`scratch.txt` 就在这条 stash 里，只是 `stash show` 默认只比对 tracked 那部分，要 `-u` 才把未跟踪的也算进来。

这个差异的根子在 stash 的存储方式上。旧版这篇里我写过一句「stash 没有父提交语义」，那是错的：stash 本身就是挂在 `refs/stash` 下的一个提交，`cat-file` 能一层层拆开。

```text
PS> git -C $repo show-ref
ab575c4d0c8f8f2b1c9e2a6a4b1f0d9c7e3a5b21 refs/heads/main
4e5e6a45b750be3a091337eaba1e355f2e7ff311 refs/stash

PS> git -C $repo cat-file -p refs/stash
tree 3f25e9d6c1a24b7e8f0d5c3a9b6e2f4d1c8a7b30
parent ab575c4d0c8f8f2b1c9e2a6a4b1f0d9c7e3a5b21
parent d4a1ad2f7c1e9b3a5d8f2c6e0b4a9d7c3f1e8b56
author demo <demo@example.com> 1795088734 +0800
committer demo <demo@example.com> 1795088734 +0800

On main: 优惠券做到一半
```

普通 stash 是两个父提交：第一个是当时的 `HEAD`，第二个是那一刻暂存区的快照（它本身也是一个提交），工作区的内容放在 stash 自己的树里。带 `-u` 收的会多出第三个父提交，未跟踪文件单独压在那一层：

```text
PS> git -C $repo cat-file -p refs/stash | Select-Object -First 4
tree 29a174f21bac402aa113602bb7c57f2c1f100d4b
parent 9c076cd7440285454fd73e9e71ddd3f17103b09a
parent b7db421574f16660cec16da4ddae3a6561856a30
parent ecd719a4dc36f79170397036e97997cd37f9cddc

PS> git -C $repo show --stat --format='%s' 'refs/stash^3'
untracked files on main: 9c076cd base
 u.txt | 1 +
 1 file changed, 1 insertion(+)
```

知道这个结构以后，`stash show` 少一行就不再是谜：它默认只比对相对第一个父提交的 tracked 改动，未跟踪那份在第三个父提交里，得 `-u` 才被带进来。也顺便解释了另一件事——为什么 `drop` 之后还能靠一个哈希把它捞回来（后面单独跑一遍），以及为什么它**不是长期存储**：一条 stash 只有一句 `-m` 说明和几个父提交，攒上十几条以后，光看 `stash list` 根本分不清哪条对应哪个任务。

## `pop` 撞上冲突：条目不会自动消失

真正麻烦的不是收，是放回去的时候撞车。场景换成热修：`feature/coupon` 改到一半的改动已经 stash 起来，`main` 上有人提交了负价热修，我把它 cherry-pick 到 `feature/coupon`，再 pop：

```text
PS> git -C $repo stash pop stash@{0}
Auto-merging discount.py
CONFLICT (content): Merge conflict in discount.py
...
The stash entry is kept in case you need it again.

PS> git -C $repo status --short
UU discount.py

PS> git -C $repo stash list
stash@{0}: On feature/coupon: 优惠券做到一半
```

`UU` 是两边都改过、需要人裁决。文件里留下的是标准的冲突标记：

```text
<<<<<<< Updated upstream
def price(cents):
    return max(cents, 0)
=======
def price(cents, coupon=0):
    return cents - coupon
>>>>>>> Stashed changes
```

注意最后那句 `The stash entry is kept in case you need it again.`——它明说了条目还在。这一步最容易犯的错是解完冲突就跑，忘了列表里那条还在；下次再 `pop` 一次，同一处冲突会叠第二遍。

我这次特意把它搞坏，好看看重来的成本：

```text
PS> git -C $repo reset --hard HEAD
HEAD is now at 876bdb4 clamp negative price

PS> git -C $repo stash apply stash@{0}
...（同样报 CONFLICT，同样三块标记）
```

`reset --hard` 把工作区清回提取前的样子，stash 条目毫发无损，`apply` 能从零再走一遍。这就是「不确定会不会冲突时选 `apply`」的实际含义：`pop` = `apply` + `drop`，而冲突时那个 `drop` 没有发生；`apply` 干脆不带 `drop`，失败随时可以重来。

确认解完、`git add` 也做了以后，手动收尾：

```text
PS> git -C $repo stash drop stash@{0}
Dropped stash@{0} (525e0d02248ff70a572fddc2277f4accf43ef973)
```

括号里那串哈希是这条 stash 提交自己的 id——不是随手打的一句提示，它是这条 stash 在对象库里的真名。

## cherry-pick：搬的是改动，不是提交

上面那个热修是怎么从 `main` 挪到发布分支的？两条线已经分叉：

```text
PS> git -C $repo log --oneline --graph --all
* 3d31a15 clamp negative price
| * f7bf4a7 release notes for 1.2
|/
* 69d6916 add price function

PS> git -C $repo switch release/1.2
PS> git -C $repo cherry-pick 3d31a15
[release/1.2 cb00f8d] clamp negative price
 Date: Thu Nov 19 19:44:10 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)
```

同一个提交的改动，在新分支上变成了新提交 `cb00f8d`，原标题、原时间都保留着。哈希为什么变？原提交的父提交是 `69d6916`，新提交的父提交换成了 `release/1.2` 当时的顶端 `f7bf4a7`——01 讲过提交哈希里包含父提交。

但这句话不能当保证写。我在另一个仓库里碰到过反例：

```text
PS> git -C $repo cherry-pick main
[feature/coupon 876bdb4] clamp negative price
 Date: Thu Nov 19 19:40:12 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`876bdb4` 和 `main` 上那个热修**同一个哈希**，没变。原因很简单：那次 `feature/coupon` 正停在 `a819768`，而热修的父提交也是 `a819768`；接回父提交不变的位置、树又一样，算出来的对象自然一模一样。所以准确的写法是条件句——**父提交或内容不同时，哈希才会变；两者都相同时，哈希可以原样不变**。搬过去以后原提交仍在原分支，这点倒是不变的。

冲突处理和 merge 同一套：解完 `git add`，再 `git cherry-pick --continue`。想搬一段连续提交用 `git cherry-pick A..B`，注意这个区间**不含 A**，边界得自己数清楚。

## tag：`describe` 默认只认附注 tag

发布点打 tag 的命令本身没什么可讲的，坑都在「别人看不看得见」和「`describe` 认不认」上。先看两种 tag 的类型差异：

```text
PS> git -C $repo tag -a v1.2.1 -m 订单负价修复
PS> git -C $repo tag v1.2.1-lw

PS> git -C $repo cat-file -t v1.2.1
tag

PS> git -C $repo cat-file -t v1.2.1-lw
commit
```

附注 tag 是独立对象（`tag`），轻量 tag 只是给提交多起一个名字（`commit`）。这个差别在 `describe` 上立刻显形。我先把附注 tag 删掉，只留轻量的：

```text
PS> git -C $repo tag -d v1.2.1
Deleted tag 'v1.2.1' (was 398769e)

PS> git -C $repo describe
fatal: No annotated tags can describe 'd85f31d194510f09a9e4e0d416c8a58985df2393'.
However, there were unannotated tags: try --tags.

PS> git -C $repo describe --tags
v1.2.1-lw
```

`git describe` 默认只拿附注 tag 当锚点，轻量的要用 `--tags` 才认。所以「发布一律用附注 tag」的真正理由不是好看——是默认工具链只认它。至于轻量 tag 为什么还会存在：临时标记、本地指路，用不着作者和说明。

另一个坑在推送上。推完分支，看对端到底有什么：

```text
PS> git -C $repo push -u origin main
 * [new branch]      main -> main

PS> git -C $repo ls-remote origin
3d31a150b205a1d0e2aa4a29bdad620c66edde78	refs/heads/main

PS> git -C $repo push origin v1.2.1
 * [new tag]         v1.2.1 -> v1.2.1

PS> git -C $repo ls-remote origin
3d31a150b205a1d0e2aa4a29bdad620c66edde78	refs/heads/main
53508b964de465f3797e29e2272d5fb4d722049f	refs/tags/v1.2.1
cb00f8d3c7b50bd25ad80821f2a19fc481c32327	refs/tags/v1.2.1^{}
```

第一次 `ls-remote` 只有一条 `refs/heads/main`——tag 一个都没跟着上去，`git push` 默认不推 tag。推完之后多出两条：`refs/tags/v1.2.1` 是那个附注对象（`53508b9`），`refs/tags/v1.2.1^{}` 是它剥开后指向的提交（`cb00f8d`）。`--tags` 会把本地所有 tag 一起推，包括上面那个轻量 `v1.2.1-lw`：

```text
PS> git -C $repo push origin --tags
 * [new tag]         v1.2.1-lw -> v1.2.1-lw
```

后果是别人 clone 下来时，本地 tag 列表完全取决于你推了什么。只推了分支的仓库，clone 出来是这样：

```text
PS> git -C $repo-clone tag -l

PS> git -C $repo-clone describe --tags
fatal: No names found, cannot describe anything.
```

`tag -l` 空输出、`describe` 直接找不到任何名字——不是 tag 坏了，是它从来没上传过。

删 tag 要分两步，因为本地删引用不会通知远端：

```text
PS> git -C $repo tag -d v1.2.1
Deleted tag 'v1.2.1' (was 53508b9)

PS> git -C $repo push origin :refs/tags/v1.2.1
 - [deleted]         v1.2.1
```

## bisect：三次运行定位一个坏提交

发布之后过了几天，测试报 `check.py` 红了。仓库里 8 个提交，我完全不知道是哪一个弄坏的。先确认判定标准能跑：

```text
PS> python check.py
Traceback (most recent call last):
  File "...\check.py", line 4, in <module>
    assert discount.price(199, 50) == 100, discount.price(199, 50)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError: 99
```

期望 `100`，实际 `99`——一分钱被截断。`check.py` 里的断言不随提交变化，这是 `bisect run` 的前提：判定脚本必须和被测代码分开，脚本一变，二分就没有意义了。

```text
PS> git -C $repo bisect start
PS> git -C $repo bisect bad d8104e8
PS> git -C $repo bisect good 3c583ca
Bisecting: 3 revisions left to test after this (roughly 2 steps)
[c43f53ece2bd8880f50efb45b74070a7663015ce] add notes

PS> git -C $repo bisect run python check.py
running 'python' 'check.py'
ok
Bisecting: 1 revision left to test after this (roughly 1 step)
[408d5862dd92ff0d6b9206cb4ea481751aec2311] inline the percent math
running 'python' 'check.py'
Traceback (most recent call last):
  File "...\check.py", line 4, in <module>
    assert discount.price(199, 50) == 100, discount.price(199, 50)
AssertionError: 99
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[cf0afe6e72dc2bfcd12d1d81a7d9a4c8e51de6b8] docstring for price
running 'python' 'check.py'
ok
408d5862dd92ff0d6b9206cb4ea481751aec2311 is the first bad commit
commit 408d5862dd92ff0d6b9206cb4ea481751aec2311
    inline the percent math
 discount.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit
```

8 个提交只跑了 3 次判定：`3 → 1 → 0`，每次砍一半。换成 200 个提交，次数是 `ceil(log2 200) = 8`（`2^7 = 128 < 200 ≤ 256 = 2^8`），不是「大约 8 次」这种估法。

退出码的三档写在 git 2.45 自己的文档里（`git-bisect`，`Bisect run` 一节）：0 表示 good/old；1 到 127（含端点、**除 125**）表示 bad/new；125 表示这个提交测不了、跳过；其他任何退出码直接中止 bisect。真正要防的是这条规则的副作用：脚本自己崩了（未捕获异常）也会退出 1，而 1 落在 bad 区间里，于是「这个提交是坏的」里混进了「这次没跑起来」。所以判定脚本要把「判定为坏」和「环境不对」分开——坏用 1，跑不起来用 125（跳过）或 128 以上（中止），别让它落进 1–127。

最后一定要收尾：

```text
PS> git -C $repo bisect reset
Previous HEAD position was cf0afe6 docstring for price
Switched to branch 'main'
```

漏了这条，`HEAD` 会停在某个中间提交上，打开文件像是代码突然变旧了——06 里那些「怎么回到原来的地方」的招数，有一半是被这件事逼出来的。

## blame 和 bisect 的分工

同样这 8 个提交，`blame` 给出的是另一个答案：

```text
PS> git -C $repo blame -L 1,6 discount.py
0c8db768 (demo 2026-11-19 19:43:09 +0800 1) def price(amount, percent):
cf0afe6e (demo 2026-11-19 19:43:08 +0800 2)     """按百分比打折后的价格，单位分。"""
c612dcb3 (demo 2026-11-19 19:43:07 +0800 3)     if not 0 <= percent <= 100:
c612dcb3 (demo 2026-11-19 19:43:07 +0800 4)         raise ValueError('percent out of range')
0c8db768 (demo 2026-11-19 19:43:09 +0800 5)     return int(amount * (100 - percent) / 100)
4caaa60c (demo 2026-11-19 19:43:07 +0800 6)
```

出错的是第 5 行，`blame` 把它记在 `0c8db76`（`rename cents to amount`）名下，而 bisect 认定引入点是 `408d586`（`inline the percent math`）。两个都对，只是回答的问题不同：`blame` 回答「这一行最后是谁动的」，`0c8db76` 只把 `cents` 改名成 `amount`，行内容被重写了一遍，归属就翻到了它头上；bisect 回答「行为从哪个提交开始变坏」，跟行归属无关。

所以顺序是：`blame` 用来找人（这行谁碰过），`bisect` 用来找因（哪个提交让行为变了）。反过来用会得出很自信的错误结论——比如拿着 `0c8db76` 去问「你为什么把取整改成截断」，而那次改动根本没碰取整。

## `drop` 之后还能捞回来

`stash drop` 打印的那个哈希不是装饰。第三节那条是 `525e0d0`；为了把后面的输出截全，我另起一个干净仓库把 drop 重做了一遍：

```text
PS> git -C $repo stash drop stash@{0}
Dropped refs/stash@{0} (4e5e6a45b750be3a091337eaba1e355f2e7ff311)

PS> git -C $repo show --stat 4e5e6a4
commit 4e5e6a45b750be3a091337eaba1e355f2e7ff311
Merge: ab575c4 d4a1ad2
 discount.py | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)

PS> git -C $repo stash apply 4e5e6a4
 M discount.py
```

`drop` 只是把 `refs/stash` 这个引用挪走，提交对象本身还在库里，用哈希直接 `apply` 就回来了；记不住哈希就让 `fsck` 去找：

```text
PS> git -C $repo fsck --lost-found
dangling commit 4e5e6a45b750be3a091337eaba1e355f2e7ff311
```

`dangling commit` 就是「没有任何引用指向、但对象还在」的提交。这条后路有期限：这些对象迟早会被 `gc` 清掉，`reflog` 也有自己的保留期（06 讲过默认值和怎么改）。我这次是几分钟内就回头捞的，所以从没撞上过期——真过了几个月再来找，`fsck` 未必还给你这行。

## 症状 → 先跑哪条

| 症状 | 先跑 | 别先做 |
| --- | --- | --- |
| `switch` 报 `untracked working tree files would be overwritten` | `git status --short`，看清哪些 `??` 没进 stash，再决定 `stash push -u` 还是移走 | 先 rebase 或 merge——同一个错会换个说法再报一遍 |
| `stash pop` 打了 `CONFLICT`，`stash list` 里还有条目 | 解冲突 → `git add` → `git stash drop` | 直接再 `pop` 一次，同一处冲突会叠第二遍 |
| 只想把某个修复搬到发布分支 | `git show --stat <sha>` 看范围，再 `cherry-pick` | 用 merge 会把整条线带过去，发布分支多出一堆无关提交 |
| `git describe` 报 `No names found` 或 `No annotated tags` | `git tag -l` 看本地，`git ls-remote --tags origin` 看远端 | 先怀疑 tag 打错了——先分清是没推上去，还是只有轻量 tag、要加 `--tags` |
| 某个测试突然变红，不知道哪个提交 | 先手动跑判定脚本确认退出码，再 `git bisect run` | 用 `git log -p` 逐个读，慢且容易看漏 |
| `blame` 指向的提交看着不像元凶 | 用 `bisect` 复核引入点 | 顺着 `blame` 去找人问罪——它只记「最后改这一行」 |

最后两行的分工不是「哪个更准」，而是回答的问题不同；前面 blame 那一节的 8 个提交就是现成的对照。

## 还差的

- `git stash push -- <path>` 只收指定路径的写法我没实测。按文档它只收匹配的改动，但和 `-u` 组合时的边界（路径外的未跟踪文件怎么处理）我没跑过。
- cherry-pick 的冲突收尾（解冲突 → `git add` → `--continue`）这次没实测，只实测了 `stash pop` 的冲突。两边机制相似不等于一样，比如 `cherry-pick` 冲突时 `CHERRY_PICK_HEAD` 这个状态文件的存在感，我只有文档印象。
- `git bisect skip` 和退出码 125 的实际跳过行为没跑出来。我这 8 个提交每一个都能判定，所以只引了文档，没有自己观察到「跳过之后 git 怎么选下一个」。
- 需要编译或联网的 `bisect run` 没试。这次是单文件 python 脚本、判定成本接近零；真实项目里脚本要编译几十秒，`bisect run` 的收益和中断恢复的成本完全是另一个量级。
- submodule 或多 worktree 下 stash 的作用域没试。`refs/stash` 是每个仓库一份，多个 worktree 共享同一个 `refs/stash`，谁 pop 谁先得——这条我只在文档里读到，没建环境验证。
