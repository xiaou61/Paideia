## 先把结论摆出来

**一次提交存的是整个项目在这一刻的完整快照，不是"改了什么"。**

每个提交包含四样东西：

- 一棵**目录树**（tree）：这一刻所有文件与目录的结构，每个文件指向一份内容对象；
- 一个**父提交**的哈希（第一次提交没有父）；
- **作者、时间、提交信息**；
- 自己的哈希（由以上内容算出）。

差异（diff）是事后拿两份快照比出来的，从来没有被存下来。

这个认知能直接解释三件事：为什么切到很老的提交能立刻看到完整代码、为什么"改了十个文件只提交一个"是一次完整提交、为什么同样的改动在不同分支上会产生不同的提交哈希。

## 内容对象、树、提交：三层

git 把所有东西存成三种对象，都用内容算出的 SHA-1 当文件名：

| 对象 | 存什么 | 类比 |
| --- | --- | --- |
| blob | 一个文件的**内容** | 一页纸 |
| tree | 一层目录：名字 → blob 或子 tree | 一个文件夹的目录页 |
| commit | 一棵根 tree + 父提交 + 元信息 | 一张快照的封面 |

关键在第二层：**tree 里只有"名字 → 内容哈希"的映射，没有内容本身**。所以两个提交里同名同内容的文件，指向的是同一个 blob，磁盘上只有一份。

这就是"快照不占额外空间"的原因：**只有真正变了的文件才会产生新 blob**。

## 为什么每个提交都能独立还原

因为每个提交的 tree 是**完整的**——它列出这一刻项目的每一个文件和子目录。

想象一本书的每一页都印着完整目录。翻到第 50 页，你不需要读前 49 页就知道这一刻全书有哪些章节。

`git checkout <commit>` 做的事就是：把那个提交的 tree 整个展开到工作区。所以它永远不需要"先回退到某个中间状态"，一步到位。

## 提交哈希是怎么算出来的

哈希的输入包括：根 tree 的哈希、父提交的哈希、作者与时间、提交信息。

这带来两个后果：

1. **改提交信息 = 换一个新提交**（哈希变了，旧提交还在）；
2. **同样的改动在不同父提交上 = 不同的哈希**。所以把一次提交 cherry-pick 到别的分支，会得到一个内容相同但哈希不同的新提交。

**哈希不是"内容指纹"那么简单，它把历史也编了进去。** 这是理解 rebase 为什么"改写历史"的钥匙。

## 工作区、暂存区、仓库：三个位置

| 位置 | 是什么 | 命令 |
| --- | --- | --- |
| 工作区 | 你能看见、能编辑的文件 | 编辑器改的就是它 |
| 暂存区（index） | 下一次提交的**候选快照** | `git add` 往里放 |
| 仓库 | 已经提交的对象库 | `git commit` 把暂存区定格 |

暂存区不是"待提交的差异列表"，而是**一棵预备好的 tree**。`git add` 做的是"把这个文件此刻的内容写成一个 blob，并更新暂存区里的 tree"。

所以 `git add` 之后又改了文件，工作区和暂存区就不一致了——`git status` 会同时显示"已暂存"和"未暂存"两组改动。

## 一个具体例子

假设你改了 `a.txt` 和 `b.txt`，但只 `git add a.txt`：

```text
$ git status
Changes to be committed:
        modified:   a.txt
Changes not staged for commit:
        modified:   b.txt
```

此时 `git commit` 提交的**只有 a.txt 的新内容**，b.txt 保持原样。这不是"部分提交一个文件"，而是"这次快照里的 a.txt 用新版、b.txt 用旧版"——**仍然是一次完整的项目快照**。

## 常见误区

### 误区：提交保存的是 diff，所以历史很长会很慢

**你以为**：一万个提交就是一万份补丁，读历史要一路回放。
**其实**：每个提交都能直接拿到完整 tree，读某个文件的历史是沿着该文件的 blob 链走，不需要回放整个项目。
**怎么验证**：`git log --oneline | wc -l` 看提交数，再 `git show <很老的commit>:某个文件` —— 秒出，没有回放过程。

### 误区：`git add` 是"标记这个文件要提交"

**你以为**：add 只是打个勾，真正的内容在 commit 时才读。
**其实**：`git add` 当场就把文件内容写成 blob 并更新暂存区的 tree。之后你再改文件，暂存区里还是 add 那一刻的版本。
**怎么验证**：`git add a.txt` → 再改 a.txt → `git diff --cached` 看到的是旧版，`git diff` 看到的是新版。

### 误区：哈希一样就一定是同一个提交

**你以为**：哈希是内容指纹，内容相同哈希就相同。
**其实**：哈希把**父提交**和**提交时间**也编进去了。同样的改动、同样的信息，在不同父提交或不同时间下会得到不同哈希。
**怎么验证**：把一次提交 cherry-pick 到另一个分支，`git log` 里能看到两条内容一样、哈希不同的提交。

## 小结

一次提交 = 完整快照 + 父指针 + 元信息。文件内容按哈希去重，所以快照不贵；tree 完整，所以任意提交都能一步还原。暂存区是一棵预备好的 tree，不是差异清单。
