本机 Git 2.45.1.windows.1，PowerShell 7.6.3。临时仓库里先提交 `a.txt`、`b.txt` 的 `v1`，再把两个文件都改成 `v2`，只把 `a.txt` 放进暂存区：

```text
PS> git init -q
PS> git config user.name 'Paideia Example'
PS> git config user.email 'example@paideia.local'
PS> Set-Content a.txt 'v1'
PS> Set-Content b.txt 'v1'
PS> git add a.txt b.txt
PS> git commit -q -m 'base: a/b v1'
PS> git rev-list --count HEAD
1
PS> Set-Content a.txt 'v2'
PS> Set-Content b.txt 'v2'
PS> git add a.txt
PS> git status
On branch master
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   a.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   b.txt
```

`git status` 这里是完整输出，`Changes to be committed` 和两条 `(use ...)` 提示行都在，没有删节。

提交：

```text
PS> git commit -q -m 'a: v2'
PS> git rev-list --count HEAD
2
PS> git show --stat --oneline HEAD
be2b2b5 a: v2
 a.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
PS> git show HEAD:b.txt
v1
PS> Get-Content b.txt
v2
```

`git show --stat` 只列 `a.txt`，`git show HEAD:b.txt` 却是 `v1`，磁盘上的 `b.txt` 已经是 `v2`。b.txt 的改动没有丢，但它不在这一次提交里。那 commit 到底存了什么？

顺带说一句数提交：`git rev-list --count HEAD` 在这个临时仓库第一次提交后是 `1`，第二次提交后是 `2`。原文用的 `git log --oneline | wc -l` 在 PowerShell 7.6 里会报 `The term 'wc' is not recognized as a name of a cmdlet, function, script file, or executable program.`；`wc` 在 Git Bash 里有，PowerShell 里没有。

## 打开提交对象

```text
PS> git cat-file -p HEAD
tree 6195b032ba2cfb692660e29e86558294340c693b
parent 326684d95cbb949a2038701cfbd442da59628c22
author Paideia Example <example@paideia.local> 1795062542 +0800
committer Paideia Example <example@paideia.local> 1795062542 +0800

a: v2
PS> git rev-parse HEAD
be2b2b5a4aaab5e4f5047d7e2a500ac726631ade
```

`git cat-file -p` 打出来的是 commit 对象的全部内容。这个提交有五个字段：`tree`、`parent`、`author`、`committer`、`message`。第一次提交没有 `parent` 行，因为前面没有提交；这次有，因为前面还有一个 `base: a/b v1`。

这里没有一行叫 `hash`。`be2b2b5...` 是对象名，不是提交内容。对象名是 SHA-1 对「类型 + 空格 + 字节数 + NUL + 内容」的摘要；如果把对象名写回内容，算之前就要先知道结果，循环。这个仓库是默认的 SHA-1 格式；SHA-256 仓库的算法不同、对象名更长，但「名字在内容外面」这件事不变。

原文说「每个提交包含自己的哈希」，把对象名和对象内容混成了一件事。`git cat-file -p HEAD` 的输出就是反证。

`author` 是写这次改动的人和时间，`committer` 是把它放进当前历史的人和时间。直接 `git commit` 时两行由同一次操作写入；rebase 会保留 author、更新 committer。时间戳是 Unix 秒，比较时直接看数字。

## 一棵 tree 指向每个文件的内容

```text
PS> git ls-tree HEAD~1
100644 blob 626799f0f85326a8c1fc522db584e86cdfccd51f	a.txt
100644 blob 626799f0f85326a8c1fc522db584e86cdfccd51f	b.txt
PS> git ls-tree HEAD
100644 blob 8c1384d825dbbe41309b7dc18ee7991a9085c46e	a.txt
100644 blob 626799f0f85326a8c1fc522db584e86cdfccd51f	b.txt
```

`HEAD~1` 里 `a.txt` 和 `b.txt` 都指向 `626799f`；`HEAD` 里 `a.txt` 换成 `8c1384d`，`b.txt` 还是 `626799f`。`b.txt` 在 HEAD 的 tree 里仍然指向 `v1` 的 blob，所以 `git show HEAD:b.txt` 读到 `v1`。工作区的 `v2` 没有进这棵树。

```text
PS> git cat-file -t 626799f
blob
PS> git cat-file -p 626799f
v1
PS> git cat-file -p 8c1384d
v2
```

三层对象各自管什么：

| 对象 | 存什么 | 这次提交里的例子 |
| --- | --- | --- |
| blob | 文件内容的字节 | `626799f` 是 `v1`，`8c1384d` 是 `v2` |
| tree | 文件名、mode、类型、对象名 | HEAD 的根 tree `6195b03...` |
| commit | 根 tree、parent、author、committer、message | `be2b2b5...` |

tree 的每一行只有 `mode type hash name`，没有文件正文；正文在 blob 里。一个 commit 指向一棵完整的根 tree，所以 `git show --stat` 只列 `a.txt` 并不代表 commit 里只有一个文件——那只是拿 HEAD 和 parent 两棵树算出来的摘要。

工作区干净、对象都在本地时，`git switch --detach <old-commit>` 直接展开那棵 tree，不需要从当前提交回放补丁。

## 对象不止三种

核心三层是 blob、tree、commit。对象库里还有第四种：annotated tag。

```text
PS> git tag -a demo-tag -m 'release demo'
PS> git cat-file -t demo-tag
tag
PS> git cat-file -p demo-tag
object be2b2b5a4aaab5e4f5047d7e2a500ac726631ade
type commit
tag demo-tag
tagger Paideia Example <example@paideia.local> 1795062617 +0800

release demo
```

`git cat-file -t` 返回 `tag`，不是 `commit`。轻量 tag（`git tag demo-tag`）只写一条 ref，不产生 tag 对象；`-a` 才会产生。日常说「三种对象」是在说核心模型，但 `git cat-file` 能看到第四种，别把它写成不存在。

## 快照不重复存内容，但提交本身要占空间

`b.txt` 的 blob 没变，`HEAD~1` 和 `HEAD` 两棵 tree 都指向 `626799f`，所以 `v1` 的内容只存了一份。`a.txt` 变了，才有新 blob `8c1384d`。

但不要说「快照不占额外空间」。每个提交至少多一个 commit 对象；这次 HEAD 的 commit 对象内容有 232 字节：

```text
PS> git cat-file -s HEAD
232
PS> git cat-file -s 'HEAD^{tree}'
66
```

根 tree 的内容是 66 字节。目录结构变了还会多 tree 对象；只有未变文件的内容会复用 blob。准确说法是「不会为未变的文件重复存内容」。

## commit 里没有 diff，packfile 里可能有 delta

提交对象里没有 diff 字段，这是对的。`git show` 和 `git diff` 都是拿两棵树或两端的快照比出来的。

但不要把这句话扩展成「仓库从来没有存过差异」。我拿一个 5000 行的 `big.txt` 改了 12 次，`git gc` 后看到：

```text
PS> git gc
PS> $idx = (Get-ChildItem .git/objects/pack/*.idx).FullName
PS> git verify-pack -v $idx | Select-String '^ea8cfbe|^ad3310b'

ea8cfbe53be60ddfe97c1e3c398e776f2e50ca37 blob   278893 12892 1921
ad3310b099f67ed07bfcc6da1bb21a3abb55cc1c blob   55 65 14813 1 ea8cfbe53be60ddfe97c1e3c398e776f2e50ca37
```

第二行末尾的 `1 ea8cfbe...` 就是 `depth 1` 和 `base <blob>`：`ad3310b` 这个 blob 实际有 278859 字节，但 pack 里只存了 55 字节的 delta（压缩后 65 字节），base 是 `ea8cfbe`。`git verify-pack -v` 末尾的 `chain length = 1: 2 objects` 也能看到链长。

这是 packfile 的存储格式，不是 commit 对象里的 diff。`git show` 仍然按两棵树算 patch。准确说法是：commit 对象不含 diff；packfile 可能用 delta 压缩对象。对象很小或改动很大时，`git gc` 不一定产生 delta；这里只证明它会发生。

## 暂存区是一棵预备好的 tree

现在把 `b.txt` 也 `add` 进去，然后不改 index，只改工作区：

```text
PS> git add b.txt
PS> Set-Content b.txt 'v3'
PS> git diff --cached
diff --git a/b.txt b/b.txt
index 626799f..8c1384d 100644
--- a/b.txt
+++ b/b.txt
@@ -1 +1 @@
-v1
+v2
PS> git diff
diff --git a/b.txt b/b.txt
index 8c1384d..29ef827 100644
--- a/b.txt
+++ b/b.txt
@@ -1 +1 @@
-v2
+v3
```

`git diff --cached` 比的是 HEAD 的 tree 和 index 的 tree：`-v1 +v2`。`git diff` 比的是 index 和 working tree：`-v2 +v3`。所以「`--cached` 看旧版」这种说法会让人对错行：它不是固定看旧版，而是看「已提交 vs 已暂存」；工作区那份它不看。

暂存区不是「待提交的差异列表」，而是一份预备好的目录内容；`git write-tree` 会把它写成一棵 tree 对象。`git add b.txt` 把 index 里 `b.txt` 的条目指向 `v2` 的 blob `8c1384d`——它和 `a.txt` 的 `v2` 是同一个 blob，因为内容一样。之后你把工作区改成 `v3`，index 仍然是 `v2`。

```text
PS> git status
On branch master
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   b.txt

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   b.txt
```

同一个文件同时在两组里出现，不是 `git status` 坏了：一组是 index 里的 `v2`，另一组是工作区的 `v3`。这时 `git commit` 只会提交 index 里的 `v2`，工作区的 `v3` 留在外面。开头只 `add a.txt` 时也是同一件事。

## 同样的 patch，不一定是同样的哈希

原文的标题「哈希一样就一定是同一个提交」基本为真（忽略碰撞）。真正会错的是反过来：同样的改动、同样的 patch，不一定得到同样的哈希。

```text
rebase 前：
PS> git cat-file -p ab10210
tree af2d782e99207b27f03963b2f8f3d830d4fd7dbe
parent 435516f1036cbc047838bf49b4f2bcaa0e338b6f
author Paideia Example <example@paideia.local> 1795062476 +0800
committer Paideia Example <example@paideia.local> 1795062476 +0800

feature: add same patch

rebase 后：
PS> git cat-file -p 4aeb547
tree f60243c08d39f065cd8e87a4320b64720424f337
parent 87ebbaf8b68b5cfedd03dac15f7a87127a3a02c7
author Paideia Example <example@paideia.local> 1795062476 +0800
committer Paideia Example <example@paideia.local> 1795062479 +0800

feature: add same patch
```

两次 `git show --format= --patch` 的 patch 都是 `feature.txt` 新增一行 `same patch`。patch 一样，哈希从 `ab10210` 变成 `4aeb547`。author 时间没变，committer 时间从 `1795062476` 变成 `1795062479`；parent 也从 `435516f` 变成 `87ebbaf`；tree 变了是因为新 base 多了 `main.txt`。

所以 commit 的「内容」不只是 patch：根 tree、parent、author、committer、message 都进哈希。原文漏了 committer 这一行；rebase 保留 author、更新 committer，patch 一样哈希也会变。cherry-pick 同理：把同一个 patch 接到另一个父提交上，commit 内容变了，哈希就是新的。

## 还差的

- 没测 SHA-256 仓库：`git init --object-format=sha256` 后对象名长度和部分工具行为会变；这篇只覆盖默认 SHA-1。
- 没测 `git commit --amend` 与 `git rebase --committer-date-is-author-date` 的组合；这篇只证明了默认 rebase 会改 committer 时间。
- 没展开 packfile 的 delta 选择策略：多大的 blob 会 delta、`window`/`depth` 怎么调，本文只给了一个 5000 行文件的观察。
- 没覆盖浅克隆/部分克隆：对象不在本地时，`git show HEAD:b.txt` 可能触发 promisor fetch；这篇没验证。
