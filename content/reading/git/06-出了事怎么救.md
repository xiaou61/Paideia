## 先把结论摆出来

**只要你曾经提交过，绝大多数"丢了"的东西都还在，入口是 `git reflog`。**

reflog 是本地仓库对 `HEAD` 和分支指针移动的记录。每次 `commit`、`reset`、`rebase`、`checkout`、`merge`，它都会记一行"从哪到哪"。默认保留 90 天。

真正救不回来的只有一类：**从来没被提交、也没进过暂存区的改动**。它们从未变成 git 对象，`reset --hard` 或 `checkout -- .` 之后没有任何地方存着。

所以出事后的第一原则不是"赶紧修"，而是：**先停手，先看清，再动。**

## 先做这三件事，别急着敲命令

```text
git status          # 现在在哪个分支、工作区与暂存区各有什么
git log --oneline -5 # 当前分支最近几个提交
git reflog -20      # HEAD 最近怎么移动的
```

`reflog` 的输出像这样，**左边是当时 `HEAD` 指向的提交**：

```text
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
9f8e7d6 HEAD@{1}: commit: 补上订单超时取消
4c5b3a2 HEAD@{2}: commit: 抽出金额计算
...
```

`HEAD@{1}` 就是"你 `reset` 之前待的地方"。拿到哈希，就能把东西捞回来。

## 场景一：`reset --hard` 把提交弄没了

假设你本来想撤销最近三次提交，结果连想保留的那次也一起撤了：

```text
$ git reset --hard HEAD~3
```

别慌，三个提交还在对象库里：

```text
$ git reflog
9f8e7d6 HEAD@{3}: commit: 补上订单超时取消

$ git branch rescue 9f8e7d6
```

现在 `rescue` 分支指向那次提交，内容全回来了。确认无误后再决定是合并回主分支，还是只挑其中某个文件：

```text
git checkout rescue -- src/order/TimeoutJob.java
```

**关键点**：`reset --hard` 移动的是分支指针，不会立刻删除对象。真正删除对象的是 `git gc` / `git prune`，而它们要等 reflog 过期之后才会动手。

## 场景二：误删了一个分支

```text
$ git branch -D feature/pay
Deleted branch feature/pay (was 7c1d2e3).
```

输出里那个 `was 7c1d2e3` 就是最后一次提交。直接：

```text
git branch feature/pay 7c1d2e3
```

如果连输出都没留，`git reflog` 里也能找到该分支最后的提交（reflog 也记录分支移动）。

## 场景三：rebase / amend 之后发现改坏了

`rebase` 和 `commit --amend` 都会创建新提交、把旧提交丢在一边。旧提交仍然在 reflog 里：

```text
$ git reflog
e4f5a6b HEAD@{0}: rebase (finish): returning to refs/heads/main
...
e4f5a6b HEAD@{5}: rebase (start): checkout origin/main
7c1d2e3 HEAD@{6}: commit: 原来的提交
```

想整体退回 rebase 之前：

```text
git reset --hard HEAD@{6}
```

还有一个快捷入口：`ORIG_HEAD` 记录着上一次危险操作之前的 `HEAD`。

```text
git reset --hard ORIG_HEAD
```

它只保留"上一次"，多次操作之后还是得看 reflog。

## 场景四：没提交的改动被 `reset --hard` 了

这是**唯一救不回来**的情况。因为：

- 没 `git add` 的内容只存在于工作区，git 没存过；
- `git add` 过但没 commit 的内容在暂存区（本质是一个 blob），`reset --hard` 会把暂存区一起重置。

少数情况下还能从这些地方找：

1. **IDE 的 Local History**（IntelliJ 默认有，右键文件 → Local History）；
2. 编辑器的撤销栈或自动保存；
3. `git fsck --lost-found` 能捞出"悬空 blob"——但只有曾经 `git add` 过的文件才会以 blob 形式存在，而且没有文件名，只能按内容认。

**预防比补救便宜**：动手前先 `git stash`，或者 `git diff > /tmp/backup.patch`。一条命令的事。

## 场景五：错误提交已经 push 了

分两种情况：

| 情况 | 做法 | 风险 |
| --- | --- | --- |
| 只有你在用这个分支 | `git reset --hard <好的提交>` + `git push --force-with-lease` | 别人基于旧提交的工作会断 |
| 共享分支（main / develop） | `git revert <错误提交>`，产生一个反向提交 | 历史保留，所有人都能安全 pull |

**共享分支永远用 `revert`**。`revert` 不删除历史，只是新增一次"抵消"的提交。代价是历史里会留下两条记录，但这正是审计需要的。

如果已经 `force push` 覆盖了别人的提交，让被覆盖的人用他自己的 `reflog` 找回，再重新合并——不要试图在服务器上"修复历史"。

## 场景六：想找回某个文件的旧版本

不需要 reset 整个分支：

```text
git log --oneline -- src/order/PriceService.java   # 这个文件的修改历史
git show 4c5b3a2:src/order/PriceService.java       # 那一刻的完整内容
git restore --source=4c5b3a2 -- src/order/PriceService.java  # 直接恢复到工作区
```

`git restore --source` 只改文件，不动分支、不动其他文件，是找回单个文件最安全的方式。

## 一张"我做了什么 / 该用什么"的表

| 你做了什么 | 想恢复什么 | 用什么 |
| --- | --- | --- |
| `reset --hard` 掉了已提交内容 | 提交 | `git reflog` → `git branch rescue <hash>` |
| 删了分支 | 整个分支 | `git branch <名字> <was 后面的哈希>` |
| `rebase` / `amend` 改坏 | 整个分支 | `git reset --hard ORIG_HEAD` 或 reflog |
| 只想找回一个文件 | 文件 | `git restore --source=<commit> -- <path>` |
| 改错了共享分支 | 抵消某次提交 | `git revert <commit>` |
| 没提交的改动被清掉 | 工作区内容 | 基本救不回来；找 IDE Local History |
| 忘了某个提交在哪 | 定位 | `git log --all --oneline --grep="关键词"` / `git branch -a --contains <hash>` |

## 常见误区

### 误区：reflog 在服务器上也有一份

**你以为**：本地删了、清了，还能去远端找 reflog。
**其实**：reflog 是**本地仓库**的记录，不会随 `push` 上传。换一台机器 clone 下来，只有提交历史，没有你本地的 reflog。
**怎么验证**：在另一台机器或新建目录 clone 后跑 `git reflog`——只有 clone 那一刻的一行。

### 误区：`git gc` 会马上删掉"丢失"的提交

**你以为**：只要执行过 gc，旧提交就彻底没了。
**其实**：可达性判断会先看 reflog；reflog 未过期的提交仍被视为可达。默认 90 天后才可能被清理。
**怎么验证**：`git config --get gc.reflogExpire` 看保留期；`git reflog expire --dry-run --all` 预览会被清理的条目（别随手真跑）。

### 误区：`git fsck --lost-found` 能恢复被 reset 的工作区改动

**你以为**：任何丢失内容都能靠 fsck 捞回来。
**其实**：fsck 只能找到已经进入对象库、但没有任何引用的对象（悬空 blob/commit）。从没 `git add` 过的内容不在对象库里，fsck 看不到。
**怎么验证**：改一个文件但**不 add**，然后 `reset --hard`，再 `git fsck --lost-found`——找不到这次改动。

## 小结

出事后的顺序固定：`git status` → `git log` → `git reflog`，先确认"东西还在不在"，再决定用 `branch`、`reset` 还是 `restore` 去接。已提交的内容几乎都能救；没提交的内容只能靠 `stash` 和 IDE 历史预防。共享分支只 `revert`，不改写历史。

下一篇讲日常真正高频的几个工具：`stash`、`cherry-pick`、`tag` 和 `bisect`——它们解决的是"怎么把工作拆开、搬走和定位"。
