## `reset --hard` 之后，`git status` 干净得吓人

我在 `$env:TEMP` 建了一个四提交的订单服务仓库，最后两次提交是 `cancel timed-out orders` 和 `document retry policy`。`notes.md` 里是：

```text
PS> git log --oneline --decorate
96b74d0 (HEAD -> main) document retry policy
953e545 cancel timed-out orders
aec23eb extract price calculation
2902769 initial import

PS> Get-Content notes.md
retry=3
timeout=10
```

我在文件末尾加了一行 `timeout=30`，没有 `git add`：

```text
PS> git status --short
 M notes.md
PS> Get-Content notes.md
retry=3
timeout=10
timeout=30
```

然后想撤掉最近两次提交，命令敲成了 `HEAD~2`：

```text
PS> git reset --hard HEAD~2
HEAD is now at aec23eb extract price calculation
```

结果不是「回到两次提交前，改动还在」，而是：

```text
PS> git status
On branch main
nothing to commit, working tree clean

PS> git log --oneline --decorate
aec23eb (HEAD -> main) extract price calculation
2902769 initial import

PS> Get-Content notes.md
retry=3
timeout=10
```

`status` 越干净越吓人：它只说明工作区等于当前 `HEAD`，不说明刚才那份 `timeout=30` 还在。

我先跑了 `git fsck --lost-found`，以为能把两份东西都捞回来：

```text
PS> git fsck --lost-found
dangling commit 96b74d09a4108901f672f47ca2d4f89d8b373dd1
```

只出来一个 dangling commit，没有 `notes.md` 的 blob。那一刻我才把两类损失分开：

- 提交 `96b74d0` 和它的父提交 `953e545` 已经进了对象库，只是 `main` 不再指向它们；`reflog` 也还记着 `HEAD` 怎么走到这里。
- `timeout=30` 从没 `git add`，没变成 blob，也没有文件名；任何 git 命令都找不到它。`git status` clean 只是把「工作区被覆盖」这件事说得很好听。

环境是 Windows、PowerShell 7、Git 2.45.1.windows.1（`git --version` 的输出）；下面的哈希和临时路径都来自这次练习，换一个仓库就会变。

## 先停手：三行命令，别先 gc

事故后顺序固定：

```text
git status
git log --oneline -5
git reflog -20
```

`status` 告诉你现在在哪、工作区与暂存区各有什么；`log` 告诉你当前分支还看得见什么；`reflog` 告诉你 `HEAD` 刚才怎么动的。三条都只读，先跑没有代价。

这时候最不该做的四件事：

1. `git gc`、`git prune`、`git reflog expire`：它们会把「只剩 reflog 还指着」的对象变成真的不可达；
2. 再来一次 `git reset --hard` 或 `git clean -fd`：先覆盖工作区，后面想找也少一份副本；
3. 直接 `git push --force`：你还没确认丢了什么，先把远端也改成一样的；
4. 关掉编辑器或重启：未保存的缓冲区、IDE 的 Local History 可能比 git 更早一步救你。

## reflog 是本地日志，不是远端备份

`git reflog` 的第一行就是答案：

```text
PS> git reflog
aec23eb HEAD@{0}: reset: moving to HEAD~2
96b74d0 HEAD@{1}: commit: document retry policy
953e545 HEAD@{2}: commit: cancel timed-out orders
aec23eb HEAD@{3}: commit: extract price calculation
2902769 HEAD@{4}: commit (initial): initial import
```

`HEAD@{1}` 不是「上一个提交」的固定编号，它的意思是「`HEAD` 上一次移动之前在哪」。你刚 `checkout`、`commit`、`rebase` 过，它指的东西就完全不同。所以先看右边的动作说明，再取哈希。

先建一个救援分支，不直接动 `main`：

```text
PS> git branch rescue 96b74d0
PS> git log --oneline --decorate --graph --all
* 96b74d0 (rescue) document retry policy
* 953e545 cancel timed-out orders
* aec23eb (HEAD -> main) extract price calculation
* 2902769 initial import
```

`rescue` 一旦指向 `96b74d0`，整条父链就重新可达，`953e545` 也一起回来。确认文件内容后，再决定合并、挑提交还是把 `main` 移过去。先建分支的好处是：你还没有改 `main`，随时可以反悔。

`reflog` 记的是本仓库里 `HEAD` 和分支引用的移动，文件在 `.git/logs/` 下。`push` 不会把它上传；新建 clone 只有 clone 那一行。所以「远端有仓库」不等于「远端有你的 reflog」。

默认保留期也不是一个数字。本机查：

```text
PS> git config --get gc.reflogExpire
PS> $LASTEXITCODE
1
PS> git config --get gc.reflogExpireUnreachable
PS> $LASTEXITCODE
1
```

两条都没输出、退出码 1：这台机器没有显式配置。Git 官方 [`git-config`](https://git-scm.com/docs/git-config#Documentation/git-config.txt-gcreflogExpire) 文档给的默认值是：可达的 reflog 条目 90 天，不可达的条目 30 天。在默认配置下，`reset` 掉的那类提交先受 30 天这一档影响；但这是默认值，不是保证。别人机器、CI、托管平台都可以改，`git gc --prune=now` 更不会等你。

## 什么时候真的救不回来

`reset --hard` 只是把引用移走；`reflog` 还在时，对象也在。把 reflog 清掉再 gc，才是真的删。下面这段只在临时仓库跑，不要在还有东西要找的仓库里执行：

```text
PS> git cat-file -t b6280ad
commit

PS> git reflog expire --expire=now --all
PS> git gc --prune=now

PS> git cat-file -t b6280ad
fatal: git cat-file: could not get object info

PS> git reflog
PS> git fsck --lost-found
```

最后两条都没有输出。对象已经被 prune 掉，`reflog` 和 `fsck` 都接不回来了；只能从别的 clone、备份或 IDE 历史里找。

把不可逆的边界压成三句话：

1. `reflog` 过期加上 `gc` prune 之后，本地对象没了；
2. 已 push 的历史改写，不会追回别人 clone、fork 或缓存里的副本；
3. `filter-repo` 只改你当前这份仓库，别人的本地仓库不会自动跟着变。

## 删掉的分支：先看 `was` 后面的哈希

在同一个仓库里给 `feature/pay` 加一个提交，然后删掉：

```text
PS> git log --oneline -2
289fffd add payment adapter
aec23eb extract price calculation

PS> git branch -D feature/pay
Deleted branch feature/pay (was 289fffd).
```

`was 289fffd` 就是分支最后指向的提交。直接重建：

```text
PS> git branch feature/pay 289fffd
PS> git branch -vv
  feature/pay 289fffd add payment adapter
* main        aec23eb extract price calculation
  rescue      96b74d0 document retry policy
```

如果那行 `was` 没留下，先别 gc，跑：

```text
PS> git fsck --lost-found
dangling commit 289fffd41caba7ccd1d8cc88d90ca1688c721d52
```

`fsck` 找到的是没有引用指向的 commit；同一棵提交链可能只报最上面那个。`git reflog` 也可能还留着当时的 `commit` 行，但分支自己的 reflog 已经随分支删掉了，不能把它当成必然。两条都找不到、对象又被 gc 清掉时，这个分支就只能从别人的 clone 或备份里找。

## amend 和 rebase：`ORIG_HEAD` 只保上一次

`git commit --amend` 不是改原提交，而是造一个新提交，把分支指针移过去。旧提交还在，只是 `reflog` 里。一次实测：

```text
PS> git log --oneline -1
0dab116 set runtime mode

PS> git commit --amend -m 'set runtime mode'
[config cff817c] set runtime mode
 Date: Thu Nov 19 12:05:21 2026 +0800
 1 file changed, 1 insertion(+)
 create mode 100644 config.txt

PS> git reflog -3
cff817c HEAD@{0}: commit (amend): set runtime mode
0dab116 HEAD@{1}: commit: set runtime mode
cd1ec85 HEAD@{2}: checkout: moving from main to config

PS> git show HEAD@{1}:config.txt
mode=fast

PS> git reset --hard HEAD@{1}
HEAD is now at 0dab116 set runtime mode
```

`HEAD@{1}` 是 amend 前的旧提交；回退后 `config.txt` 又变成 `mode=fast`。如果你已经又做了别的事，`HEAD@{n}` 的 `n` 会变，按 `reflog` 里的动作说明找。

rebase 的冲突现场长这样（另起一个临时仓库，`main` 和 `topic` 改同一行）：

```text
PS> git rebase main
Auto-merging settings.txt
CONFLICT (content): Merge conflict in settings.txt
Rebasing (1/1)
error: could not apply 7b8da1c... topic changes mode
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
hint: Disable this message with "git config advice.mergeConflict false"
Could not apply 7b8da1c... topic changes mode
```

`git status --short` 是 `UU settings.txt`，文件里是冲突标记。此时 rebase 还没结束，`git rebase --abort` 会回到开始前：

```text
PS> git status --short
UU settings.txt

PS> git rebase --abort
PS> git status
On branch topic
nothing to commit, working tree clean

PS> git log --oneline --decorate --graph --all
* ffb2919 (main) main changes mode
| * 7b8da1c (HEAD -> topic) topic changes mode
|/
* 5db8ce7 base settings
```

真正会出事的是第二种：冲突解错，还 `git add` + `git rebase --continue` 完成了。rebase 结束后再跑 `--abort` 已经没有进行中的 rebase；这时看 `ORIG_HEAD` 或 reflog：

```text
PS> git reflog -5
9a721f0 HEAD@{0}: rebase (finish): returning to refs/heads/topic
9a721f0 HEAD@{1}: rebase (continue): topic changes mode
ffb2919 HEAD@{2}: rebase (start): checkout main
7b8da1c HEAD@{3}: rebase (abort): returning to refs/heads/topic
ffb2919 HEAD@{4}: rebase (start): checkout main

PS> git rev-parse --short ORIG_HEAD
7b8da1c
PS> git show ORIG_HEAD:settings.txt
mode=topic

PS> git reset --hard ORIG_HEAD
HEAD is now at 7b8da1c topic changes mode
```

`ORIG_HEAD` 只保留「上一次危险操作之前」的位置；我执行完这次 `reset` 再查，它已经变成 `9a721f0`（恢复前的错误结果），不是刚才的 `7b8da1c`。所以先把目标哈希抄下来，或者用 reflog 里最后一次 `rebase (start)` 之前的那行（这里是 `HEAD@{3}`）。

## 共享分支：能 revert 就别 force push

如果是普通提交，`git revert` 是最便宜的止损：它新增一个反向提交，不改历史。

```text
PS> git revert --no-edit HEAD
[main 6b9a94c] Revert "wrong price"
 Date: Thu Nov 19 12:06:18 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)

PS> git log --oneline -3
6b9a94c Revert "wrong price"
6262ae4 wrong price
7bc9032 add price

PS> Get-Content price.txt
unit_price=99.00
```

私有分支确实要改写时，至少用 `git push --force-with-lease`；它会在远端有你没 fetch 的提交时拒绝。共享分支仍然先 `revert`，因为别人不需要重建本地历史。

## 没进对象库的改动：先分清 ` M` 和 `M `

`git status --short` 左边两位很关键：` M` 是工作区改了、没暂存；`M ` 是暂存了、没提交。两者在 `reset --hard` 后的命运不同。

工作区-only 的改动就是开头那份 `timeout=30`：没对象、没文件名，`fsck` 也看不到。IDE 的 Local History、编辑器撤销栈、系统备份是仅剩的入口。

`M ` 则已经 `git add`，git 为内容建了 blob。`reset --hard` 后 blob 变成悬空对象，`git fsck --lost-found` 能捞：

```text
PS> git status --short
M  notes.md
PS> git reset --hard HEAD
HEAD is now at 25935a6 initial notes
PS> git fsck --lost-found
dangling blob 29f2fdd4a3a737d8f10a27e9ee83aab081b55b29

PS> git cat-file -p 29f2fdd4a3a737d8f10a27e9ee83aab081b55b29
retry=3
timeout=30
```

`--lost-found` 还会把 blob 复制到 `.git/lost-found/other/`：

```text
PS> Get-ChildItem .git\lost-found\other | Select-Object -ExpandProperty Name
29f2fdd4a3a737d8f10a27e9ee83aab081b55b29
```

但 blob 没有文件名，内容相同的文件还会共用一个 blob；只能按内容认，不能指望 `fsck` 告诉你它原来叫 `notes.md`。真丢了工作区-only 的改动，先翻 IDE 的 Local History，再考虑文件系统恢复工具；不要先 gc。

## `.env` 已经提交：本地能撤，推送后只能减损

`git add .` 把 `.env` 一起塞进提交，输出很直白：

```text
PS> git add .
PS> git status --short
A  .env
A  app.txt

PS> git commit -m 'add app config'
[main 0f29c7f] add app config
 2 files changed, 3 insertions(+)
 create mode 100644 .env
 create mode 100644 app.txt

PS> git show HEAD:.env
API_KEY=demo-secret-123
DB_PASSWORD=not-a-real-password
```

还没 push 时，最省事的撤回是软重置，把提交拆回暂存区，再把 `.env` 拿出来：

```text
PS> git reset --soft HEAD~1
PS> git restore --staged .env
PS> git status --short
A  app.txt
?? .env
```

然后把 `.env` 写进 `.gitignore`，只提交 `app.txt` 和 `.gitignore`：

```text
PS> git add .gitignore app.txt
PS> git commit -m 'add app config'
[main daa75a1] add app config
 2 files changed, 2 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 app.txt

PS> git log --oneline
daa75a1 add app config
16864cf initial import

PS> git check-ignore -v .env
.gitignore:1:.env	.env
```

到这里，本地当前历史干净了；但旧提交 `0f29c7f` 仍在 reflog 和对象库里，直到过期和 gc。这不等于密钥没泄露：只要别人已经 fetch 过、看过 diff，或者 CI 日志抓过，内容就已经出去了。

已经 push 的，先别把「删文件」当成「撤回」：

```text
PS> git rm --cached .env
rm '.env'
PS> git commit -m 'stop tracking .env'
[main f610f59] stop tracking .env
 1 file changed, 2 deletions(-)
 delete mode 100644 .env
PS> git push
To ../origin.git
   e4fa87f..f610f59  main -> main

PS> git log --oneline --all -- .env
f610f59 stop tracking .env
e4fa87f add app config

PS> git show HEAD~1:.env
API_KEY=demo-secret-123
DB_PASSWORD=not-a-real-password
```

`git rm --cached` 只让下一次提交不再包含它；旧提交还在。`git log --all -- .env` 仍能列出那次提交，`git show HEAD~1:.env` 仍能把密钥原样打出来。

要把远端历史也改掉，得在**新 clone** 上跑 `git filter-repo`。它默认会移除 `origin` 远程。我在副本上跑了 `git filter-repo --path .env --invert-paths`，重写后的历史是：

```text
PS> git log --oneline --decorate
0924cc8 (HEAD -> main) add app config
fff171e initial import

PS> git show HEAD:.env
fatal: path '.env' does not exist in 'HEAD'
```

然后重新加 remote，再 force push：

```text
PS> git push --force origin main
To ../origin.git
 + f610f59...0924cc8 main -> main (forced update)
```

这只是把远端当前分支挪走。另一个在重写前 clone 的仓库里，旧对象还在：

```text
PS> git show HEAD~1:.env
API_KEY=demo-secret-123
DB_PASSWORD=not-a-real-password

PS> git status --short --branch
## main...origin/main [ahead 2, behind 1]
```

只要别人不主动清理或重建，他的本地仍能读到旧密钥；这就是「已 push 的历史不可逆」的实际含义。正确顺序是：先轮换密钥，再改历史；改完通知所有协作者重新 clone 或按约定重置，不要让他们直接 `git pull`。

我建的这个裸仓库 `origin.git` 下没有 `logs` 目录：

```text
PS> Test-Path ..\origin.git\logs
False
PS> git --git-dir=../origin.git reflog show main
PS> $LASTEXITCODE
0
```

服务端 reflog 空输出、退出码 0。托管平台可能保留服务端日志，也可能不保留；恢复时不要把「服务端有 reflog」当前提。

## 只想找回一个文件：不要 reset 整个分支

`git restore --source` 只改工作区里的一个路径，不动分支：

```text
PS> git log --oneline -- notes.md
e87c1ff tune retry
bb29716 initial notes

PS> git show HEAD:notes.md
retry=5
timeout=30

PS> git show HEAD~1:notes.md
retry=3
timeout=10

PS> git restore --source=HEAD~1 -- notes.md
PS> git status --short
 M notes.md

PS> Get-Content notes.md
retry=3
timeout=10

PS> git log --oneline -1
e87c1ff tune retry
```

`git restore` 把旧内容放回工作区，分支和 `HEAD` 没动；确认后再提交，或者只挑需要的行。若文件已经删除，`git restore --source=<commit> -- <path>` 同样能把文件恢复出来，前提是那个路径在目标提交里存在。

## 一张表：先看症状，再选命令

| 症状 | 先跑 | 能救回 | 救不回 |
| --- | --- | --- | --- |
| `reset --hard` 后 `status` clean、`log` 少提交 | `git reflog` | 已提交的提交和文件 | 从没 add 的工作区改动 |
| `git branch -D` 删了分支 | 看 `was` 哈希；`git fsck --lost-found` | 分支 tip 和祖先 | 已被 gc 清掉的对象 |
| `amend` 或 rebase 后改坏 | `git reflog`、`ORIG_HEAD` | rebase 或 amend 前的提交 | 已 push 且别人已 fetch 的旧历史 |
| 误提交 `.env`，还没 push | `git reset --soft HEAD~1` 加 `git restore --staged .env` | 本地当前历史 | 已经被别人看到的密钥 |
| `.env` 已 push | 先轮换密钥；`git filter-repo` 加 force push | 远端当前分支 | 别人的 clone、fork、缓存、日志 |
| 想找单个文件旧版 | `git log -- <path>` 加 `git restore --source` | 文件内容 | 没进对象库的内容 |

## 还差的

这篇只覆盖了普通文件仓库里的本地恢复。下面这些没实测，也没给出可靠步骤：

- **submodule**：子模块的提交、`.gitmodules` 和父仓库指针是三层状态，`reflog` 只能告诉你父仓库指针怎么动，子模块自己的对象库要单独看。
- **Git LFS**：LFS 指针在 git 里，真实大文件在 `.git/lfs/objects` 或远端 LFS 存储；`filter-repo` 改历史后，LFS 对象不会跟着自动迁移，清理密钥或大文件要同时处理两边。
- **多人同时 force push**：`--force-with-lease` 能挡住「远端在你 fetch 后又变了」，但挡不住两个人几乎同时改写；谁先谁后、谁的 reflog 还有效，需要团队约定。
- **托管平台的服务端保留**：我测的裸仓库没有 reflog，托管平台可能有审计日志或保留策略；这不是你能控制的副本，不能拿它当恢复方案。
- **文件系统级恢复**：工作区-only 的改动被覆盖后，git 层没有入口；IDE Local History、系统快照、文件恢复工具是另一套东西，这篇没展开。
