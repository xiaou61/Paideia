## 同一段历史，rebase 后换了一组哈希

Git 2.45.1.windows.1，PowerShell 7.6.3，临时仓库。main 和 feature 从 c2 分叉，feature 里还有一次把 side 合进来的合并提交：

```text
$ git log --graph --oneline --all
*   455ec00 Merge branch 'side' into feature
|\
| * 4df0cea s1 侧栏样式
* | fc84c6c f2 空状态
* | 94d7526 f1 列表
|/
| * 424501b c3 修导航
|/
* c997862 c2 主页文案
* 5e89c16 c1 初始化
```

`feature` 指向 `455ec00`。把它接到 main 的最新提交上：

```text
$ git switch feature
$ git rebase -q main
```

`-q` 只关掉进度行；命令没有输出，退出码 0。历史变成一条直线：

```text
$ git log --graph --oneline
* cc87338 s1 侧栏样式
* 6ac50b6 f2 空状态
* 9347a44 f1 列表
* 424501b c3 修导航
* c997862 c2 主页文案
* 5e89c16 c1 初始化
```

再把新的 feature 推回远端：

```text
$ git push origin feature
To ../story-final-origin.git
 ! [rejected]        feature -> feature (non-fast-forward)
error: failed to push some refs to '../story-final-origin.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
```

我原来以为推送的是同一个分支名，远端就会接受。实际 Git 检查的是新 tip 能不能从旧 tip 快进过去：rebase 生成的 `9347a44` 父提交是 `c3`，不是旧 tip `455ec00`，所以远端直接拒绝。这里的 `git pull` 只是 Git 的通用提示；先判断这个分支是不是共享的，再决定下一步。

## merge 不一定新建合并提交

先看能快进的情况。main 在 `c2`，topic 从 `c2` 往前走了 `f1`，此时把 topic 合进 main：

```text
$ git merge topic
Updating 432cdbb..4fa85df
Fast-forward
 topic.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 topic.txt

$ git rev-list --parents -n 1 HEAD
4fa85dfd0756c2b3178006791ed17f39fd51361d 432cdbb56f219acdefe63c86a993ac00da03d275
```

`rev-list --parents` 只输出了两个哈希：当前提交，加上一个父提交。没有合并提交，main 的指针只是从 `432cdbb` 挪到了 `4fa85df`。这就是 fast-forward。

只有两边都往前走了，merge 才需要把两条线接起来。下面是分叉后的合并：

```text
$ git merge feature --no-edit
Merge made by the 'ort' strategy.
 feature.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 feature.txt

$ git rev-list --parents -n 1 HEAD
62fb3afdf010a50d69b1fc9e0532fa8ab7efe800 b2e855ccdde701bcb0b3639a8f3832a2e4175d93 df307a81a6f2f1ba1160eb4ca915df2cbd9be761
```

这次有三个哈希：合并提交，加两个父提交 `c3` 和 `f1`。只有这种分叉合并，才会新建一个双父的合并提交；`--no-ff` 的作用就是在本可快进时也强制生成这样一个提交。

所以看到 `Fast-forward` 时，不要去找合并提交，它不存在。这个区别直接决定 `git log --graph` 里有没有那条分叉线。

## rebase 换的是基底，旧提交不会立刻消失

rebase 把 feature 上还没进入 main 的提交取出来，按顺序重新接到 main 的最新提交后面。父提交变了，提交对象的哈希也就全变了。

我原以为旧提交只能靠 `git reflog` 找。实际 `ORIG_HEAD` 就直接指向 rebase 前的 tip：

```text
$ git log --oneline -1 ORIG_HEAD
455ec00 Merge branch 'side' into feature
```

`ORIG_HEAD` 是这次 rebase 留下的救援线索，能直接拿来回退或建分支。但它不是备份：下一次 rebase、merge、reset 都可能覆盖它。`reflog` 也不是永久保存，它受 `gc.reflogExpire` 控制，过了保留期会被清理。不要把这两个东西当成远端仓库的替代品。

另一个容易漏掉的点：默认 rebase 会丢掉合并提交。上面那个 feature 里本来有 `Merge branch 'side' into feature`，rebase 后：

```text
$ git rev-list --count --merges HEAD
0
```

原来在 side 上的 `s1` 也被重放成了普通提交。要保留 feature 内部的合并结构，得显式加参数：

```text
$ git branch structure 455ec00
$ git switch structure
$ git rebase -q --rebase-merges main

$ git log --graph --oneline
*   8e80ecc Merge branch 'side' into feature
|\
| * 79b13dd s1 侧栏样式
* | b56e365 f2 空状态
* | 8057293 f1 列表
|/
* 424501b c3 修导航
* c997862 c2 主页文案
* 5e89c16 c1 初始化

$ git rev-list --count --merges HEAD
1
```

`--rebase-merges` 重建的是合并结构，不是原来的提交对象；`8e80ecc` 仍然是新哈希。它也不会自动保留你当时对合并冲突做的每一个手工决定，复杂合并仍要用 `rerere` 或人工复核。

## 冲突：merge 停一次，rebase 可能停很多次

两边改了同一文件的同一区域，merge 把冲突集中到合并提交里解决一次：

```text
$ git merge feature
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.
```

rebase 的工作单位是单个提交，所以它会在每个撞上冲突的提交处停下。我在临时仓库里让 feature 的两个提交依次改同一行，rebase 停了两次：

```text
$ git rebase main
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Rebasing (1/2)
error: could not apply 7fc0a7f... f1 改这一行

$ git rebase --continue
[detached HEAD c9a46ad] f1 改这一行
 1 file changed, 1 insertion(+), 1 deletion(-)
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Rebasing (2/2)
error: could not apply e42d330... f2 再改这一行
```

这不是说每次 rebase 都一定解两次；冲突次数取决于提交触到哪些区域。但工作量的形状不同：merge 在一个合并提交里对照两边，rebase 按提交逐个重放，前面的解决结果会改变后面的上下文。五个提交改同一块代码，可能就要停五次。

## 什么时候选哪个

| 场景 | 选 | 代价 |
| --- | --- | --- |
| 共享功能分支合入主干 | `git merge`，或平台上的 merge | 多一个双父合并提交，保留分叉 |
| 自己的功能分支落后主干，想接到最新继续 | `git rebase main` | 哈希全变，可能多次停冲突 |
| 评审前整理自己的提交 | `git rebase -i` | 改写哈希，只对独占分支做 |
| 已推送、别人可能基于它工作 | 不要 rebase，改用 merge 或先协调 | 否则别人的旧提交会和新历史分叉 |
| 要保留 feature 内部的合并结构 | `git rebase --rebase-merges main` | 结构保留，哈希仍然全变 |

这里没有哪条路更「高级」：merge 保留分叉，rebase 换基底重写哈希。选哪个看这条分支是否共享、你要不要保留分叉，以及你能不能承受再次解决冲突。

「本地没推」也不等于可以随便 rebase。只在自己独占、确认没人基于它工作的分支上做。别人可能从你机器上拉过，另一个 worktree 也可能正基于它工作；这些都不会因为「没 push」而自动消失。

## rebase -i 不能不带基准直接压

「用 `git rebase -i` 先把提交压成一次再 rebase」这句话，在本地分支没有 upstream 时根本跑不起来：

```text
$ git rebase -i
There is no tracking information for the current branch.
Please specify which branch you want to rebase against.
See git-rebase(1) for details.

    git rebase '<branch>'

If you wish to set tracking information for this branch you can do so with:

    git branch --set-upstream-to=<remote>/<branch> feature
```

正确写法是先给一个基准，或者在一次交互里直接指定 main：

```text
git rebase -i <分叉点>
# 在打开的 todo 里把后几个 pick 改成 squash，保存退出
git rebase main
```

或者直接：

```text
git rebase -i main
```

第二种写法在 todo 里把要合并的提交改成 `squash` 或 `fixup`，一次完成压缩和换基底。`<分叉点>` 是占位符，换成那个分支从 main 分出去时的提交哈希或分支名。

压缩能减少停下来的次数，但不等于减少冲突工作量。原来三个提交可能各撞一次，压成一个后可能一次性撞一个更大的冲突；你省掉的是重复的 `--continue`，不是冲突本身。

## rebase 之后为什么必须 force push

上面那次 `git push` 被拒，是因为本地 feature 的哈希已经不属于远端旧 feature 的后代。你如果确定要发布这组新哈希，并且这条分支由你独占，普通 push 没有用，只能用 force 类操作。

优先用：

```text
git push --force-with-lease origin feature
```

不要用 `git push --force`。后者无条件覆盖远端，连「远端现在是什么」都不问。`--force-with-lease` 至少会检查一个预期值，不匹配就拒绝。

但这条规则只适用于「这是我独占的分支，我确认要替换远端旧历史」。如果分支已经共享，先考虑 merge、revert 或和对方协调，而不是 force push。

如果你只是把提交推到了错误分支，那又是另一件事，force push 不是修复手段。先把提交推到正确的分支，再和仓库所有者确认错误分支是删除还是回退；不要用覆盖别人提交的方式「纠正」自己的手误。

也不要拿两人共用的仓库做「rebase 再 force push，让对方 pull 看看」的实验。要观察后果，用两个一次性临时克隆和一个一次性裸仓库。真实共享分支上，对方如果本地已经有一笔提交，默认 `git pull` 会尝试把旧提交和新历史合并，留下分叉或冲突；这不是一句「大家 pull 一下」就能抹平的。

## --force-with-lease 防的是还没 fetch 到的提交

这是最容易误会的地方：`--force-with-lease` 默认拿本地记录的 `refs/remotes/origin/<branch>` 当预期值，而 `git fetch` 会先把这个引用更新到远端最新。于是同一个命令，fetch 前后结果相反。

先看没 fetch 的情况。远端已经被 Alice 推到了 `f51fda6`，Bob 本地的 `origin/main` 还停在 `4486ae1`：

```text
$ git push --force-with-lease origin main
To ../lease-origin.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '../lease-origin.git'
```

Git 拒绝了，因为远端实际值不是 Bob 以为的 `4486ae1`。接下来 Bob 执行 fetch：

```text
$ git fetch origin
From ../lease-origin
   4486ae1..f51fda6  main       -> origin/main

$ git status --short --branch
## main...origin/main [ahead 1, behind 1]

$ git push --force-with-lease origin main
To ../lease-origin.git
 + f51fda6...d7ed64f main -> main (forced update)
```

这次通过了，Alice 的 `f51fda6` 也从远端分支上消失：

```text
$ git log --oneline --graph --decorate -3 origin/main
* d7ed64f (HEAD -> main, origin/main, origin/HEAD) Bob 的修改
* 4486ae1 base
```

所以 fetch 不会改远端，也不会改你的工作区，但它会把 lease 的预期值更新成你刚看到的东西。`--force-with-lease` 防的是「远端在你上次查看之后又变了」；它不防「你已经看见了别人的提交，然后决定覆盖它」。

需要把预期值钉死时，可以显式写出来：

```text
git push --force-with-lease=main:<预期远端哈希> origin main
```

远端不是这个哈希就拒绝，是就覆盖。这个参数校验的是你的预期，不是提交的安全性。也正因为如此，fetch 之后看到别人的提交，正确动作是先判断该不该保留它，而不是顺手 force。

## 还差的

- 这篇只说了 `--rebase-merges` 能保留合并结构，没有展开 `rerere` 怎么复用同一冲突的解决结果；复杂分支仍可能反复解。
- 没覆盖 `git rebase --onto` 和 `--update-refs`：「把一段提交搬到另一个基底」和「一次 rebase 更新多个本地分支」都不在例子里。
- 没验证 GitHub、GitLab 的受保护分支、merge queue 和 squash merge 对本地 rebase、force push 的服务端限制；客户端 lease 通过，服务端仍可能拒绝。
- 没讲 `git pull --rebase`、`pull.rebase` 配置和团队约定的差异；本文只覆盖手动 rebase 之后怎么推。
