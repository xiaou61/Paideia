## 先把结论摆出来

**合并（merge）保留真实历史，变基（rebase）伪造一条干净的历史。**

两者都在解决同一个问题：你在分支上干活时，主干也前进了，怎么把两边接上。

- **merge**：新建一个"合并提交"，有两个父提交。历史是分叉再汇合，真实但看着乱；
- **rebase**：把你的提交**一个个重放到主干最新提交之后**，产生一批新提交（哈希全变）。历史是一条直线，干净但改写了事实。

一条实用规则：**已经推送到共享分支的提交不要 rebase**，本地没推的随便 rebase。

## 问题是怎么产生的

```text
main:    c1 ── c2 ── c3
                 ↘
feature:          f1 ── f2
```

feature 从 c2 分出，之后 main 又前进到 c3。现在要把 feature 合进 main。

## merge 做了什么

```text
main:    c1 ── c2 ── c3 ────── M
                 ↘           ↗
feature:          f1 ── f2 ──┘
```

`M` 是一个**合并提交**，有两个父（c3 和 f2）。它的 tree 是两边内容的合并结果。

特点：

- **不改变任何已有提交**，哈希全部保留；
- 历史保留了"什么时候从哪儿分的叉"，能看出真实的并行开发；
- 冲突在 `M` 这一处集中解决一次。

代价：分支多了之后，`git log --graph` 会变成一团麻。

## rebase 做了什么

```text
main:    c1 ── c2 ── c3 ── f1' ── f2'
```

rebase 把你的每个提交**重新应用**到 c3 上，产生 f1' 和 f2'。

注意那是**新提交**：内容可能一样，但父提交变了，所以哈希全变。原来的 f1/f2 变成孤儿（靠 reflog 还能找到）。

特点：

- 历史是一条直线，`git log` 好读；
- **改写历史**：所有提交哈希都变了；
- 冲突可能**每个提交都要解一次**（不是一次性）。

代价：如果别人已经基于 f1/f2 干活，rebase 后他们的历史就断了。

## 冲突为什么会出现

两边改了同一个文件的同一区域，git 无法自动判断该留哪份。

merge 时冲突集中在合并提交里解决一次。rebase 时每个被重放的提交都可能撞上冲突——因为它是在新的基底上重新应用，前面的改动可能已经改变了上下文。

**这是 rebase 最主要的体验代价**：五个提交可能要解五次冲突。

（可以用 `git rebase -i` 先把提交压成一次再 rebase，减少冲突次数。）

## 什么时候选哪个

| 场景 | 选 |
| --- | --- |
| 把功能分支合进主干，分支已共享 | merge |
| 本地分支落后于主干，想接上最新代码再继续 | rebase |
| 提交历史乱（"fix typo" 一堆），想整理后提交评审 | rebase -i |
| 已经推到远端、别人可能拉过的分支 | **不要 rebase** |
| 想保留"这条功能是什么时候并行开发的" | merge |

一句话：**rebase 是"整理自己的历史"，merge 是"记录两条历史汇合"**。

## 推错分支为什么必须 force push

rebase 之后本地历史变了（哈希全变），远端还是旧的。直接 `git push` 会被拒绝（非快进）。

这时才需要 `git push --force-with-lease`。

**为什么用 `--force-with-lease` 而不是 `--force`**：前者会先检查远端是否还是你上次看到的那个提交，如果别人已经推了新东西，它会拒绝而不是覆盖掉别人的工作。

`--force` 会无条件覆盖——这是团队协作里最容易造成数据丢失的操作。

## 一个具体例子

```text
$ git switch feature
$ git rebase main
Successfully rebased and updated refs/heads/feature.

$ git log --oneline --graph -4
* f2' 第二个功能
* f1' 第一个功能
* c3  主干上的最新提交
* c2  更早的主干提交
```

`f1'` 和 `f2'` 是新的哈希。原 `f1`/`f2` 已经不在任何分支上，只能通过 `git reflog` 找到。

## 常见误区

### 误区：rebase 更"高级"，所以应该总用 rebase

**你以为**：直线历史更专业，merge 是新手做法。
**其实**：两者表达不同的东西。merge 记录"两条线并行过、在此汇合"，rebase 表达"这些改动是接着最新代码做的"。已经共享的分支 rebase 会破坏别人的历史。
**怎么验证**：在一个两人协作的仓库里对已推的分支 rebase 再 force push，让另一个人 `git pull`——他会看到历史分叉。

### 误区：merge 会产生多余提交，所以它更"脏"

**你以为**：合并提交是噪音。
**其实**：合并提交记录了一个真实事件——两条开发线在这一刻汇合。删掉它就丢失了"谁在什么时候并行做了什么"。
**怎么验证**：`git log --graph --all` 看一个有合并提交的仓库，能还原出并行开发的时序。

### 误区：rebase 冲突一次就够

**你以为**：rebase 和 merge 一样，冲突只解一次。
**其实**：rebase 逐个重放提交，每个都可能撞冲突。五个提交可能要解五次。
**怎么验证**：在一个有多个提交的分支上 rebase 到改过同一文件的 main，观察 `git rebase --continue` 被调用几次。

## 小结

merge 加一个双父提交、保留历史、冲突解一次；rebase 重放提交、得到直线、哈希全变、可能多次冲突。已共享的分支不 rebase。force push 只用 `--force-with-lease`。
