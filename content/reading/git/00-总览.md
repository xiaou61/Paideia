## 这条线是干什么的

大多数人用 git 的方式是背命令：`add`、`commit`、`push`，出事就搜"git 怎么撤销"。这套方法在顺利时能用，一旦冲突、丢提交、推错分支，就只能试命令，试错成本高。

这条线反过来：**先讲清 git 到底在存什么**，再讲命令。你一旦知道"一次提交是一份完整快照 + 指向父提交的指针"，`reset`、`rebase`、`cherry-pick` 这些命令就不再是魔法，而是对同一份数据的几种移动方式。

## 五篇的走法

1. **一次提交里存了什么**：快照不是差异，分支不是文件夹——两个认知换掉，后面全通；
2. **分支就是一个指针**：为什么建分支几乎免费，`HEAD` 到底指什么；
3. **合并与变基**：两者都在"接上别人的工作"，代价完全不同；
4. **撤销**：`reset` / `revert` / `restore` 各管什么，什么时候会真丢东西；
5. **协作时的几条硬规则**：什么绝不 force push，冲突该怎么解。

## 一个前提

这条线假设你已经会 `git add` / `git commit` / `git push`，并且至少遇到过一次冲突。不涉及 git 内部对象格式（blob/tree 的字节布局），也不需要你会写 hooks。

**读的时候对照自己的仓库**：找一次你曾经"搞砸了"的提交，读完第四篇回去看，你会知道当时该用哪条命令。

## 常见误区

### 误区：提交存的是"改了什么"

**你以为**：每个提交记录的是相对上一次的增删行。
**其实**：每个提交存的是**整个项目在这一刻的完整快照**（未变的文件复用上一份的对象，所以体积不会翻倍）。差异是事后算出来的，不是存下来的。
**怎么验证**：`git show --stat <commit>` 看到的是"这次涉及哪些文件"，`git diff A B` 才是算出来的差异；`git checkout <commit> -- .` 能把整个工作区还原到那一刻。

### 误区：分支是项目的副本，所以很贵

**你以为**：建分支就是把代码复制一份，多了会占空间。
**其实**：分支只是一个指向某个提交的**指针**，创建它只写一个 41 字节的文件。贵的是提交里的文件对象，而那些对象所有分支共享。
**怎么验证**：在一个大仓库里 `git branch test-x` 然后 `cat .git/refs/heads/test-x`——里面只有一个提交哈希。

### 误区：出事了先 `git reset --hard`

**你以为**：`--hard` 是最干净的"回到之前"。
**其实**：它同时丢掉工作区改动、暂存区改动和当前分支的移动记录。未提交的改动**没有进对象库，`reset --hard` 之后就真的没了**（reflog 也救不回来）。
**怎么验证**：`git reset --hard` 前先 `git stash`，或者先 `git diff` 看一眼再决定。
