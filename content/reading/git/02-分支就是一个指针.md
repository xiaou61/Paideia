本机 Git 2.45.1.windows.1，PowerShell 7.6.3。下面 `PS>` 是提示符，复制时从它后面开始。临时仓库里 `main`、`topic`、`experiment` 各有一个提交，我在 `main` 上敲：

下面的 `$repo`、`$det3`、`$rw`、`$del`、`$del2`、`$sha` 都是 `$env:TEMP` 下的路径，文末「跑一遍」会把它们建出来；只想看某一段，就把它们换成你的临时目录。

```text
PS> git -C $repo log --oneline --no-decorate -1
c5af50b main: shared=main
PS> git -C $repo status -sb
## main
PS> git -C $repo branch
  experiment
* main
  topic
```

`git log` 只给了一个提交，`git status` 说在 `main`，`git branch` 却列出三个分支。另外两个分支的提交不在 `git log` 的输出里。`git log` 默认从 HEAD 指向的提交往回走，不负责列分支；`git branch` 列的是 ref。把这两个命令混在一起看，才会觉得「我明明在一个提交上，怎么又有三个分支」。

`git branch -vv` 把每个分支的 tip 和提交标题放在一起：

```text
PS> git -C $repo branch -vv
  experiment cbc2de4 experiment: add file
* main       c5af50b main: shared=main
  topic      51ba722 topic: shared=topic
```

`*` 是 HEAD 所在的分支；方括号里是 upstream，没设置就没有。我这三条记录是三个不同的提交 ID。`git log --all` 才能把三条线都画出来：

```text
PS> git -C $repo log --all --oneline --decorate --graph
* cbc2de4 (experiment) experiment: add file
* c5af50b (HEAD -> main) main: shared=main
| * 51ba722 (topic) topic: shared=topic
|/  
* c51bae2 base: shared/base
```

所以问题不是「我在哪个提交」，而是「分支这个名字，到底指向什么」。

## 分支是一条 ref，不是 `.git/refs/heads/` 下的文件

Git 里的 ref 是「名字 → 对象 ID」的引用。分支是 `refs/heads/` 命名空间下的 ref。先看 HEAD 和三条分支：

```text
PS> git -C $repo symbolic-ref HEAD
refs/heads/main
PS> git -C $repo show-ref --heads
cbc2de4dc0acc04d3c3d4e282e4b4554d0a596a5 refs/heads/experiment
c5af50b80227165c591e7ebb9030e4fe98fa8c83 refs/heads/main
51ba7229a213fde062b43d889fae0bb399df8a6a refs/heads/topic
```

`HEAD` 现在是一条 symbolic ref，内容是 `ref: refs/heads/main`；`refs/heads/main` 再指向提交 `c5af50b...`。打开 loose ref 看到的是一行完整 ID：

```text
PS> Get-Content (Join-Path $repo '.git\refs\heads\main')
c5af50b80227165c591e7ebb9030e4fe98fa8c83
PS> (Get-Content (Join-Path $repo '.git\refs\heads\main') -Raw).Trim().Length
40
```

40 不是 Git 的固定宽度，是 SHA-1 对象 ID 的十六进制字符数。`git rev-parse --show-object-format` 返回 `sha1`，这个仓库就是 SHA-1。换一个 SHA-256 仓库：

```text
PS> git -C $sha init -q --object-format=sha256 -b main
PS> git -C $sha rev-parse --show-object-format
sha256
PS> (git -C $sha rev-parse HEAD).Length
64
PS> (Get-Content (Join-Path $sha '.git\refs\heads\main') -Raw).Trim().Length
64
```

同一个 ref 存的是 64 个十六进制字符。把分支定义成「写了 40 位哈希的文件」，在 SHA-256 仓库里第一句就错。

更直接的反例是 packed-refs。`git pack-refs --all` 之后，loose 文件消失，分支没有消失：

```text
PS> Test-Path (Join-Path $repo '.git\refs\heads\main')
True
PS> git -C $repo pack-refs --all
PS> Test-Path (Join-Path $repo '.git\refs\heads\main')
False
PS> Get-Content (Join-Path $repo '.git\packed-refs')
# pack-refs with: peeled fully-peeled sorted 
cbc2de4dc0acc04d3c3d4e282e4b4554d0a596a5 refs/heads/experiment
c5af50b80227165c591e7ebb9030e4fe98fa8c83 refs/heads/main
51ba7229a213fde062b43d889fae0bb399df8a6a refs/heads/topic
PS> git -C $repo rev-parse main
c5af50b80227165c591e7ebb9030e4fe98fa8c83
PS> git -C $repo branch
  experiment
* main
  topic
```

`.git/refs/heads/main` 不在了，`git branch` 仍然列出 main，`rev-parse main` 仍然给出哈希。分支是那条 ref；loose 文件、packed-refs 只是它的存储位置。`git pack-refs --all` 是 Git 自带的命令，所以「分支一定在 `.git/refs/heads/` 下」不能当定义用；它取决于当前存储方式。

结论：**分支是 `refs/heads/` 下的一条 ref，名字映射到一个提交 ID。** 存成 loose 文件还是 packed-refs，是存储层的事，不是分支的定义。

## HEAD 的两种形态

attached HEAD 指向分支。`.git/HEAD` 里存的是另一条 ref 的名字：

```text
PS> Get-Content (Join-Path $repo '.git\HEAD')
ref: refs/heads/main
PS> git -C $repo symbolic-ref HEAD
refs/heads/main
PS> git -C $repo rev-parse --abbrev-ref HEAD
main
```

detached HEAD 直接指向提交，`.git/HEAD` 里就是一个对象 ID：

```text
PS> git -C $det3 switch --detach HEAD~1
HEAD is now at c51bae2 base: shared/base
PS> Get-Content (Join-Path $det3 '.git\HEAD')
c51bae2bb42cbfb943506042d8f10143c9a2a395
PS> git -C $det3 symbolic-ref HEAD
fatal: ref HEAD is not a symbolic ref
PS> $LASTEXITCODE
128
PS> git -C $det3 rev-parse --abbrev-ref HEAD
HEAD
PS> git -C $det3 status -sb
## HEAD (no branch)
PS> git -C $det3 branch
* (HEAD detached at c51bae2)
  main
```

`symbolic-ref` 失败不是 HEAD 坏了，是 HEAD 里直接存了提交 ID，不再是 `ref: ...`。`rev-parse --abbrev-ref HEAD` 在 attached 时给分支名，在 detached 时给 `HEAD`；`status` 的 `(no branch)` 是同一个事实。`git switch --detach` 是 `git checkout <提交>` 的新写法。

`git checkout origin/main` 和 `git switch main` 的区别，在远程跟踪 ref 上最明显：

```text
PS> git -C $rw checkout origin/main
Note: switching to 'origin/main'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>

Or undo this operation with:

  git switch -

Turn off this advice by setting config variable advice.detachedHead to false

HEAD is now at c5af50b main: shared=main
PS> git -C $rw status -sb
## HEAD (no branch)
PS> git -C $rw switch main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.
PS> git -C $rw status -sb
## main...origin/main
```

`origin/main` 是 `refs/remotes/origin/main`，不是本地分支；checkout 一个 commit-ish 就 detached。`switch main` 看到本地 main 不在时，从 `origin/main` 建本地分支并设置跟踪：

```text
PS> git -C $rw switch -c other
Switched to a new branch 'other'
PS> git -C $rw branch -D main
Deleted branch main (was c5af50b).
PS> git -C $rw branch
* other
PS> git -C $rw switch main
branch 'main' set up to track 'origin/main'.
Switched to a new branch 'main'
PS> git -C $rw status -sb
## main...origin/main
PS> git -C $rw branch -vv
* main  c5af50b [origin/main] main: shared=main
  other c5af50b main: shared=main
```

`git checkout -b` 和 `git switch -c` 在这个用法上等价，都是「新建分支并切过去」：

```text
PS> git -C $rw switch -c sw-eq
Switched to a new branch 'sw-eq'
PS> git -C $rw checkout -b co-eq
Switched to a new branch 'co-eq'
PS> git -C $rw rev-parse sw-eq co-eq
c5af50b80227165c591e7ebb9030e4fe98fa8c83
c5af50b80227165c591e7ebb9030e4fe98fa8c83
```

## 在 detached HEAD 上提交，切走之后

在 detached HEAD 上提交，提交会落在 HEAD 上，不会自动挂到任何分支：

```text
PS> Set-Content (Join-Path $det3 'detached.txt') -Value 'work'
PS> git -C $det3 add detached.txt
PS> git -C $det3 commit -m 'detached: only on reflog'
[detached HEAD d95a418] detached: only on reflog
 1 file changed, 1 insertion(+)
 create mode 100644 detached.txt
PS> git -C $det3 switch main
Your branch is up to date with 'origin/main'.
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  d95a418 detached: only on reflog

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> d95a418

Switched to branch 'main'
PS> git -C $det3 reflog -3
c5af50b HEAD@{0}: checkout: moving from d95a418bc168fe29f3f5759cd120e2c8b16d1892 to main
d95a418 HEAD@{1}: commit: detached: only on reflog
c51bae2 HEAD@{2}: checkout: moving from main to HEAD~1
PS> git -C $det3 switch -c rescue d95a418
Switched to a new branch 'rescue'
PS> git -C $det3 log --oneline -1 rescue
d95a418 detached: only on reflog
```

`d95a418` 不在任何分支上；`git reflog` 里还留着 `commit: detached: only on reflog` 这一条，所以能按哈希救回来。`git switch -c rescue <哈希>` 会新建分支并切过去；`git branch rescue <哈希>` 只新建 ref，不切换。救不回来的条件是这条 reflog 记录已经过期、没有别的 ref 指向它，并且 `gc` 已经清掉对象；默认窗口见下一节。

## 切分支动的是 HEAD、index、worktree 三层

先在 `main` 上看 index 里的 `shared.txt`：

```text
PS> git -C $repo branch --show-current
main
PS> git -C $repo ls-files -s shared.txt
100644 ba2906d0666cf726c7eaadd2cd3db615dedfdf3a 0	shared.txt
PS> git -C $repo cat-file -p ba2906d
main
```

改 `base.txt` 但不提交。`topic` 上这个文件的内容和 `main` 相同：

```text
PS> Set-Content (Join-Path $repo 'base.txt') -Value 'dirty-base'
PS> git -C $repo status --short
 M base.txt
PS> git -C $repo switch topic
M	base.txt
Switched to branch 'topic'
PS> Get-Content (Join-Path $repo 'shared.txt')
topic
PS> git -C $repo ls-files -s shared.txt
100644 0f62d67e76ce1255a098942495a846df0f8a2c11 0	shared.txt
PS> git -C $repo cat-file -p 0f62d67
topic
PS> git -C $repo status --short
 M base.txt
```

`shared.txt` 从 `main` 变成 `topic`，index 里的 blob 从 `ba2906d` 变成 `0f62d67`，HEAD 从 `refs/heads/main` 变成 `refs/heads/topic`；`base.txt` 的本地改动跟着过来，因为两个分支的 `base.txt` 是同一个 blob。`M base.txt` 那行是 checkout 在提醒「这个本地修改被带过去了」，不是它新改了文件。

暂存了再切也一样，只要目标分支不碰同一个文件。先回到 `main` 并清掉刚才的改动：

```text
PS> git -C $repo restore base.txt
PS> git -C $repo switch main
Switched to branch 'main'
PS> Set-Content (Join-Path $repo 'base.txt') -Value 'staged-base'
PS> git -C $repo add base.txt
PS> git -C $repo status --short
M  base.txt
PS> git -C $repo switch topic
M	base.txt
Switched to branch 'topic'
PS> git -C $repo status --short
M  base.txt
PS> git -C $repo diff --cached --stat
 base.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

目标分支改了同一个文件，Git 会拒绝切换。未暂存和已暂存都是这条报错：

```text
PS> git -C $repo restore --staged --worktree base.txt
PS> git -C $repo switch main
Switched to branch 'main'
PS> Set-Content (Join-Path $repo 'shared.txt') -Value 'dirty-main'
PS> git -C $repo status --short
 M shared.txt
PS> git -C $repo switch topic
error: Your local changes to the following files would be overwritten by checkout:
	shared.txt
Please commit your changes or stash them before you switch branches.
Aborting
PS> $LASTEXITCODE
1
PS> git -C $repo branch --show-current
main
```

把 `shared.txt` 先 `git add` 再切，报错还是这三行，退出码还是 1。未跟踪文件也一样：目标分支没有同路径时跟着走，有同路径时被拦：

```text
PS> git -C $repo restore --staged --worktree shared.txt
PS> Set-Content (Join-Path $repo 'untracked-new.txt') -Value 'new'
PS> git -C $repo status --short
?? untracked-new.txt
PS> git -C $repo switch topic
Switched to branch 'topic'
PS> git -C $repo status --short
?? untracked-new.txt
PS> git -C $repo switch main
Switched to branch 'main'
PS> Remove-Item (Join-Path $repo 'untracked-new.txt')
PS> Set-Content (Join-Path $repo 'topic.txt') -Value 'untracked collision'
PS> git -C $repo switch topic
error: The following untracked working tree files would be overwritten by checkout:
	topic.txt
Please move or remove them before you switch branches.
Aborting
```

所以「切分支只换指针，工作区不动」是错的。干净切换时，被跟踪文件的内容会变成目标提交里的版本；dirty 改动只有在目标分支不碰同一路径时才跟着走，碰了就拒绝切换：

| 本地改动 | 目标分支改同一路径 | 结果 |
| --- | --- | --- |
| 未暂存 | 否 | 带着走 |
| 已暂存 | 否 | 带着走，仍是 staged |
| 未暂存 | 是 | 拒绝，退出码 1 |
| 已暂存 | 是 | 拒绝，退出码 1 |
| 未跟踪文件 | 目标有同名文件 | 拒绝 |

## 删分支：`-d` 拒绝，`-D` 才强制

`-d` 不是「删除并顺便检查一下」，它先做合并检查。没有 upstream 时对照当前 HEAD；走不到就拒绝：

```text
PS> git -C $del branch -d doomed
error: the branch 'doomed' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D doomed'
hint: Disable this message with "git config advice.forceDeleteBranch false"
PS> $LASTEXITCODE
1
```

没有 upstream、tip 就在当前 HEAD 历史里的分支，用 `-d` 可以删：

```text
PS> git -C $repo branch merged-temp main
PS> git -C $repo branch -d merged-temp
Deleted branch merged-temp (was c5af50b).
```

`-D` 跳过合并检查，强制删 ref：

```text
PS> git -C $del branch -D doomed
Deleted branch doomed (was 979c303).
PS> git -C $del cat-file -t 979c303
commit
PS> git -C $del log --oneline -1 979c303
979c303 doomed: unmerged
PS> git -C $del fsck --unreachable --no-reflogs | Select-String '979c303'
unreachable commit 979c303eac00675628d35722322f5b5ba6562640
```

这时旧 tip 已经不在任何 ref 下；如果没有 tag、别的分支或远端 ref 指向它，它就是不可达对象。`cat-file` 和 `log` 还能按哈希读到那个提交；`fsck --unreachable --no-reflogs` 才把它标成 unreachable，因为 `--no-reflogs` 让 fsck 不把 reflog 当引用。删 ref 不会立刻删对象；只要还有别的分支、tag、远端 ref 或 reflog 指向它，它就在。已合并的分支更不会丢，tip 本来就在接收它的分支历史里。

reflog 里还有记录时，按哈希把分支建回来：

```text
PS> git -C $del2 reflog | Select-String '320fb2f'
320fb2f HEAD@{1}: commit: doomed2: unmerged
PS> git -C $del2 branch rescue2 320fb2f
PS> git -C $del2 log --oneline -1 rescue2
320fb2f doomed2: unmerged
```

天数要分两种。指向「不在当前分支历史里」的提交的 reflog 记录，默认保留 30 天（`gc.reflogExpireUnreachable`）；当前分支可达历史的 reflog 记录，默认保留 90 天（`gc.reflogExpire`）。这两项在这台机器上都没有显式配置：

```text
PS> git -C $del config --get gc.reflogExpire
PS> git -C $del config --get gc.reflogExpireUnreachable
PS> $LASTEXITCODE
1
```

上面的空输出和退出码 1 表示没设置；30/90 天是 `git-config` 文档写的默认值，不是我从空配置里读出来的。30 天是保护期，不是定时器：记录过期后，下一次 `gc` 才可能清掉对象。把过期时间手动调到 `now` 再跑 `gc`，能立刻看到它消失：

```text
PS> git -C $del reflog expire --expire=now --expire-unreachable=now --all
PS> git -C $del gc --prune=now
PS> git -C $del cat-file -t 979c303
fatal: git cat-file: could not get object info
```

删本地分支也不会删远端分支。把本地 `main` 删掉后，远端的 `refs/heads/main` 还在：

```text
PS> git -C $rw ls-remote --heads origin main
c5af50b80227165c591e7ebb9030e4fe98fa8c83	refs/heads/main
```

要删远端 ref 是另一条命令（`git push origin --delete`），本文没跑。删分支这件事，删掉的是 `refs/heads/<name>` 这条引用（分支自己的 reflog 文件也会一起消失）；提交对象还在对象库里。提交本身能不能找回来，取决于还有没有别的引用或 reflog 记录。

## 跑一遍

下面的脚本在 `$env:TEMP` 下建仓库，所有命令都用 `git -C`，不切当前目录。命令里的提交和 blob 短哈希（`c5af50b`、`c51bae2`、`ba2906d`、`d95a418`、`979c303`、`320fb2f` 等）都是我这次跑出来的值；你复现时用 `git rev-parse`、`git ls-files -s` 或 `git reflog` 里的实际值替换。

```text
$repo = Join-Path $env:TEMP ('git02-demo-' + (Get-Date -Format 'HHmmss'))
New-Item -ItemType Directory -Path $repo | Out-Null
git -C $repo init -q -b main
git -C $repo config user.name 'Paideia Example'
git -C $repo config user.email 'example@paideia.local'
Set-Content -LiteralPath (Join-Path $repo 'shared.txt') -Value 'base'
Set-Content -LiteralPath (Join-Path $repo 'base.txt') -Value 'base'
git -C $repo add .
git -C $repo commit -q -m 'base: shared/base'
Set-Content -LiteralPath (Join-Path $repo 'shared.txt') -Value 'main'
Set-Content -LiteralPath (Join-Path $repo 'main.txt') -Value 'main'
git -C $repo add .
git -C $repo commit -q -m 'main: shared=main'
git -C $repo switch -q -c topic HEAD~1
Set-Content -LiteralPath (Join-Path $repo 'shared.txt') -Value 'topic'
Set-Content -LiteralPath (Join-Path $repo 'topic.txt') -Value 'topic'
git -C $repo add .
git -C $repo commit -q -m 'topic: shared=topic'
git -C $repo switch -q main
git -C $repo switch -q -c experiment
Set-Content -LiteralPath (Join-Path $repo 'experiment.txt') -Value 'experiment'
git -C $repo add .
git -C $repo commit -q -m 'experiment: add file'
git -C $repo switch -q main
$det3 = "${repo}-detach"
git clone -q $repo $det3
$rw = "${repo}-remote"
git clone -q $repo $rw
$del = "${repo}-del"
git clone -q $repo $del
git -C $del switch -q -c doomed
Set-Content -LiteralPath (Join-Path $del 'doomed.txt') -Value 'doomed'
git -C $del add .
git -C $del commit -q -m 'doomed: unmerged'
git -C $del switch -q main
$del2 = "${repo}-del2"
git clone -q $repo $del2
git -C $del2 switch -q -c doomed2
Set-Content -LiteralPath (Join-Path $del2 'doomed2.txt') -Value 'doomed2'
git -C $del2 add .
git -C $del2 commit -q -m 'doomed2: unmerged'
git -C $del2 switch -q main
git -C $del2 branch -D doomed2
$sha = "${repo}-sha256"
New-Item -ItemType Directory -Path $sha | Out-Null
git -C $sha init -q --object-format=sha256 -b main
git -C $sha config user.name 'Paideia Example'
git -C $sha config user.email 'example@paideia.local'
Set-Content -LiteralPath (Join-Path $sha 'a.txt') -Value 'hello'
git -C $sha add .
git -C $sha commit -q -m 'sha256 repo'
```

`$repo` 是主仓库，`$det3`、`$rw`、`$del`、`$del2` 是它的临时克隆，`$sha` 是一个独立的 SHA-256 仓库。跑完 `git -C $repo branch` 应看到 `experiment`、`main`、`topic`；`git -C $repo log --all --oneline --graph` 应看到两条分叉。

## 还差的

- 没测 reftable 后端和 linked worktree 里的 ref 存储；本文只验证了 loose ref 与 packed-refs。
- 没等 30/90 天自然过期；只做了 `reflog expire ... now` 加 `gc --prune=now` 的立即清理，默认天数按 `git-config` 文档。
- 没验证 `git switch -m` 的三方合并、`--discard-changes` 等选项；dirty 冲突时只覆盖了拒绝切换这条路径。
- 没在 SHA-256 仓库里跑 clone、remote、merge；只验证了 init、commit 和 ref 长度。
- 没测 Windows 大小写不敏感和文件锁对切换、删除的影响。
