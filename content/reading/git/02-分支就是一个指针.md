## 先把结论摆出来

**分支不是文件夹，也不是副本，只是一个写着提交哈希的文件。**

`.git/refs/heads/main` 里存的是一行 40 位哈希。`git branch feature` 做的事就是新建一个文件，写入当前提交的哈希——所以它几乎不花时间、不占空间。

`HEAD` 是另一个指针，它指向"你现在在哪个分支上"。

这个认知能解释：为什么建分支是免费的、为什么切分支瞬间完成、为什么"分支删了提交还在"、为什么 detached HEAD 会让人慌。

## 三个指针的层次

```text
HEAD → refs/heads/main → 提交 c3
                          ↓ 父
                        提交 c2 → c1
```

- **HEAD**：你在哪儿。通常是"指向某个分支"（`HEAD → refs/heads/main`）；
- **分支**：指向某个提交；
- **提交**：指向它的父提交。

`git commit` 做的事只有两步：新建一个提交对象（父 = 当前提交），然后**把当前分支指针往前挪一格**。

所以提交不是"往分支里加东西"，而是"分支指针移动"。这也是为什么分支指针永远指向最新提交。

## 为什么切分支是瞬间的

`git checkout feature` 做两件事：

1. 把 HEAD 指向 `refs/heads/feature`；
2. 把工作区文件更新成 feature 指向的那个提交的 tree。

第二步需要改文件，所以如果工作区有未提交改动，可能冲突、可能被拒绝——这是"切分支失败"的唯一真实原因，不是 git 慢。

如果两个分支指向**同一个提交**，第 2 步无事可做，切换是零成本的。

## 建分支为什么免费

因为分支只是一个文件，写的是已有提交的哈希。

```text
$ git branch new-feature
$ cat .git/refs/heads/new-feature
a1b2c3d4e5f6...（和 main 一样）
```

新建分支后，两个分支指向同一个提交。**在你往新分支提交之前，仓库里没有多出任何文件内容。** 第一次提交才会产生新的 tree/blob。

对比 SVN 那种"目录复制"式的分支，这是 git 最核心的设计差异。

## 删分支为什么不会丢东西

`git branch -d feature` 只删那个指针文件。提交对象还在对象库里。

只要还有别的东西指向那些提交，它们就不会消失。指向它们的可能是：

- 另一个分支（比如 `main` 已经合并了 feature）；
- 一个 tag；
- **reflog**（HEAD 的移动历史，默认保留 90 天）。

所以"分支删错了"通常能靠 `git reflog` 找回来——找到哈希再 `git branch 恢复名 <哈希>`。

真正会丢的情况是：那些提交**没有任何引用指向，且 reflog 也过期了**。这时 `git gc` 才会清掉它们。

## detached HEAD 是什么

`git checkout <某个提交哈希>` 会让 HEAD **直接指向提交**，而不是指向分支：

```text
HEAD → 提交 c2   （没有分支名）
```

这叫 detached HEAD（游离头）。此时你看到的代码是对的，但**在这里提交，新提交不属于任何分支**——一旦你切走，就只能靠哈希或 reflog 找回。

什么时候会自然进入这个状态：

- `git checkout <tag>`；
- `git checkout <远程分支名>`（没有建本地分支时）；
- rebase 过程中（临时状态）。

**想在这里干活就先建分支**：`git switch -c 新分支名`。

## 一个具体例子

```text
$ git log --oneline -3
c3 修复登录超时
c2 加上重试
c1 初始化

$ git branch experiment        # 建分支，指向 c3
$ git switch experiment        # HEAD → experiment
$ echo "试试" >> note.txt
$ git add note.txt && git commit -m "实验"
[experiment d4] 实验            # 新提交 d4，父是 c3

$ git switch main              # 回到 main，仍是 c3
$ git log --oneline -1
c3 修复登录超时
```

`main` 一点没动，`experiment` 多了一个提交。两条线共享 c1–c3 的全部对象。

## 常见误区

### 误区：切分支会把当前分支的改动带过去

**你以为**：切到别的分支，刚才没提交的改动会跟过去或丢掉。
**其实**：未提交的改动在**工作区**，不属于任何分支。切分支时 git 会尽量保留它们（能干净切换就带过去）；如果目标分支上同一文件内容不同，git 会拒绝切换而不是悄悄丢。
**怎么验证**：改一个文件不提交，`git switch 另一个分支`，再看 `git status`——改动还在。

### 误区：分支多会拖慢 git

**你以为**：几十个分支会让操作变慢。
**其实**：每个分支只是一个几十字节的文件。慢的是对象数量和历史深度，跟分支数量几乎无关。
**怎么验证**：`git branch | wc -l` 和 `time git status` 对比——分支数不影响 `status` 耗时。

### 误区：删了分支就等于删了代码

**你以为**：`git branch -d` 会把那些提交一起删掉。
**其实**：只删指针。提交还在对象库里，能通过 reflog、tag 或其他分支找回；只有完全无引用且 reflog 过期后才会被 gc 清掉。
**怎么验证**：删掉一个分支后 `git reflog` 还能看到它的提交哈希，`git branch 恢复 <哈希>` 就能救回来。

## 小结

分支是一个写着提交哈希的文件，HEAD 指向分支。提交只是"新建对象 + 移动指针"，所以建分支免费、切分支瞬间。detached HEAD 是 HEAD 直接指向提交，在那里干活前先建分支。
