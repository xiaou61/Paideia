## 先把结论摆出来

三个命令管三件不同的事，**混用它们是最常见的自伤**：

| 命令 | 干什么 | 已推送的历史能用吗 |
| --- | --- | --- |
| `git restore` | 把**工作区文件**还原成某个版本 | 无关，它不碰历史 |
| `git reset` | 把**分支指针**挪到另一个提交 | 不能（会让别人的历史分叉） |
| `git revert` | **新建一个提交**抵消某次提交的改动 | 能，这是唯一安全的做法 |

判断标准只有一条：**要不要改动已经推送出去的历史**。要改 → 只有 revert；不改 → 按想撤的东西选 restore 或 reset。

## 先分清要撤的是什么

问自己：我要撤的是哪一层？

1. **工作区里没提交的改动** → `git restore`
2. **已经 commit 但还没 push** → `git reset`
3. **已经 push 出去了** → `git revert`

走错层次是最常见的错误：用 `reset --hard` 想撤工作区改动，结果把提交也丢了。

## restore：只碰文件

```text
$ git restore a.txt            # 把 a.txt 还原成暂存区的版本
$ git restore --staged a.txt   # 把 a.txt 从暂存区撤出（内容不动）
$ git restore --source=HEAD~2 a.txt   # 还原成两个提交之前的版本
```

`restore` 从不移动分支、从不删提交，它只覆盖文件。**它丢掉的是工作区里未提交的改动**——那部分没进对象库，覆盖后找不回来。

所以养成习惯：覆盖前先 `git diff` 看一眼。

## reset：移动分支指针

`reset` 有三种模式，区别只在"要不要顺手改暂存区和工作区"：

| 模式 | 分支指针 | 暂存区 | 工作区 |
| --- | --- | --- | --- |
| `--soft` | 移动 | 不动 | 不动 |
| `--mixed`（默认） | 移动 | 重置 | 不动 |
| `--hard` | 移动 | 重置 | **重置** |

```text
$ git reset --soft HEAD~1    # 撤掉最后一次提交，改动还在暂存区
$ git reset HEAD~1           # 撤掉提交，改动回到工作区（未暂存）
$ git reset --hard HEAD~1    # 撤掉提交，改动一并丢掉
```

**`--soft` 是最安全的**：它只把分支指针往回挪，改动原封不动留在暂存区，你可以重新组织后提交。常用于"提交信息写错了"或"想拆成两个提交"。

**`--hard` 是最危险的**：工作区未提交的改动会直接消失，reflog 也救不回来（reflog 记的是提交，不记工作区）。

## revert：新建一个反向提交

```text
$ git revert <commit>
```

它做的事是：算出那个提交的改动，然后**新建一个提交把改动反向应用一遍**。

历史变成：

```text
A ── B ── C ── D
                ↘
                 B'（撤销 B 的改动）
```

原来的 B 还在历史里，只是被抵消了。**这是唯一可以安全用在已推送分支上的撤销方式**——因为它在末尾追加，不改写已有提交，别人拉取不会冲突。

代价：历史里会留着"犯错 + 撤销"两条记录。对共享分支来说这是**正确**的，因为历史应该记录真实发生过什么。

## 已经 push 了但又必须抹掉怎么办

严格说：不该抹。用 revert。

如果真的必须改写（比如提交了密钥），做法是：本地 `reset` 或 `rebase` 改历史 → `--force-with-lease` 推上去 → **通知所有协作者**重新拉取，因为他们的本地历史已经分叉。

这条路的成本很高，而且要假设"所有人都会照做"。密钥泄露的场景下这个成本是值得的，但普通的功能撤销不值得。

## 一个具体例子

```text
$ git log --oneline -3
d4 加了个有 bug 的校验
d3 改配置
d2 初始化

# 还没 push：直接撤掉
$ git reset --soft HEAD~1
$ git log --oneline -1
d3 改配置              # 改动还在暂存区，可以改了再提交

# 已经 push：新建反向提交
$ git revert d4
[main e5] Revert "加了个有 bug 的校验"
$ git log --oneline -2
e5 Revert "加了个有 bug 的校验"
d4 加了个有 bug 的校验
```

## 常见误区

### 误区：出事了先 reset --hard 再说

**你以为**：`--hard` 最干净，回到已知状态最保险。
**其实**：它同时丢掉工作区未提交的改动。那部分没有对象引用，reflog 也救不回来。
**怎么验证**：改一个文件不提交，`git reset --hard`，再 `git status`——改动没了，且 `git fsck --lost-found` 也找不回未暂存的内容。

### 误区：revert 会把提交删掉

```sketch
{
  "title": "revert 是加一笔，不是抹掉",
  "rows": [
    [
      { "id": "a", "title": "提交 A", "sub": "已经推给别人了", "tone": "gray" },
      { "id": "r", "title": "revert A", "sub": "新增一个反向提交", "tone": "blue" },
      { "id": "keep", "title": "历史里两条都在", "sub": "别人不用改自己的历史", "tone": "green" }
    ]
  ],
  "arrows": [
    { "from": "a", "to": "r" },
    { "from": "r", "to": "keep" }
  ]
}
```

**你以为**：revert 等于"撤销提交"，历史里就没了。
**其实**：它**新增**一个提交，原提交仍在历史里。想真正抹掉只能用 reset/rebase + force push。
**怎么验证**：`git revert <c>` 之后 `git log --oneline` 里两个提交都在，且 revert 那个的提交信息自带 `Revert "..."`。

### 误区：force push 只在本地生效

**你以为**：推错了推回来就好，反正是自己的分支。
**其实**：force push 会覆盖远端引用。别人基于旧提交的工作会变成孤儿，他们的下一次 pull 会出问题。用 `--force-with-lease` 至少能防止覆盖别人刚推的东西。
**怎么验证**：`git push --force` 前先 `git fetch`，比较 `origin/分支` 与自己记的哈希是否一致。

## 小结

撤工作区用 `restore`，撤未推送的提交用 `reset`（优先 `--soft`），撤已推送的用 `revert`。`--hard` 会真丢东西。force push 只在必须改写历史时用，且只用 `--force-with-lease`。
