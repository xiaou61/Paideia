## `MM` 不是「改了两处」，是两层

我在 `$env:TEMP` 建了个仓库：`a.txt` 先 `git add` 了一版，随后又改了一版但没再 add。`git status --short` 的输出是：

```text
PS> git status --short
MM a.txt
PS> git log --oneline -2
2043562 把 a.txt 改成第二版
4c4757e 初始化 a.txt
PS> git branch -vv
* main 2043562 [origin/main] 把 a.txt 改成第二版
```

最后一条提交和 `origin/main` 同哈希，已经 push。`MM` 的第一列是暂存区，第二列是工作区；两列各有一版改动。分开看：

```text
PS> git diff --staged
diff --git a/a.txt b/a.txt
index 5f7c520..715e495 100644
--- a/a.txt
+++ b/a.txt
@@ -1 +1 @@
-第二版
+第三版（已暂存）
PS> git diff
diff --git a/a.txt b/a.txt
index 715e495..21de535 100644
--- a/a.txt
+++ b/a.txt
@@ -1 +1 @@
-第三版（已暂存）
+第四版（工作区）
```

我原来以为 `MM` 是「改了两处」，其实它是两层。撤销的第一步不是选命令，是回答：**我要撤的改动在哪一层？**

环境是 Windows、PowerShell 7.6.3、Git 2.45.1.windows.1；下面的哈希和输出都来自这个临时仓库，换一个仓库就会变。

## 四个层次，四条命令

| 命令 | 改什么 | 碰不碰历史 |
| --- | --- | --- |
| `git restore` | 把某个版本的文件复制到工作区或暂存区 | 不碰 |
| `git reset` | 带目标时移动分支指针，按模式重置暂存区/工作区；`git reset HEAD <file>` 只重置该路径的暂存区 | 改写本地历史；已推送不要用 |
| `git revert` | 新建一个反向提交，追加在末尾 | 不改写，只追加 |

判断顺序只有四层：

1. 工作区有、暂存区没有 → `git restore <file>`
2. 暂存区有、还没 commit → `git restore --staged <file>`，或 `git reset HEAD <file>`
3. 已经 commit、还没 push → `git reset --soft` / `--mixed` / `--hard`
4. 已经 push → `git revert <commit>`

不是问「要不要改写已推送历史」——revert 根本不改写历史，它是在末尾加一笔。要问的是：**要撤销的内容有没有已经推送出去**。没推送，reset 改本地历史；已推送，revert 追加反向提交。已推送的历史默认不改写；要撤就 revert 加一笔。

## `restore` 改工作区，也改暂存区

接着上面的 `MM` 状态，只跑 `git restore a.txt`：

```text
PS> git restore a.txt
PS> git status --short
M  a.txt
```

它把工作区拉回暂存区那一版；暂存区里的「第三版」还在。再跑 `git restore --staged a.txt`：

```text
PS> git restore --staged a.txt
PS> git status --short
 M a.txt
PS> git diff --staged
```

`git diff --staged` 没有输出，因为 index 已经回到 HEAD；工作区仍是「第三版」。再 `git restore a.txt`，`git status --short` 才没有输出。

所以 `restore` 不是「只碰文件」：`--staged` 改的就是 index。`--source=HEAD~1` 也不是「把旧版本提交上去」，它默认只写工作区：

```text
PS> git restore --source=HEAD~1 a.txt
PS> git status --short
 M a.txt
PS> git commit -m '只想提交旧版本'
On branch restore-demo
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   a.txt

no changes added to commit (use "git add" and/or "git commit -a")
```

`commit` 只读 index；工作区改了不等于暂存区改了。要把旧版本提交进去，先 `git add a.txt`。要同时改 index 和工作区，用 `git restore --source=HEAD~1 --staged --worktree a.txt`：

```text
PS> git restore --source=HEAD~1 --staged --worktree a.txt
PS> git status --short
M  a.txt
```

这时暂存区里已经是旧版本，下一次 `git commit` 会提交它。

`restore` 也救不了未跟踪文件：

```text
PS> git restore new.txt
error: pathspec 'new.txt' did not match any file(s) known to git
```

`new.txt` 不在 index，也不在 HEAD，Git 没有「还原成哪个版本」可谈。删掉它用 `Remove-Item`，或者先 `git clean -n` 看清楚再 `git clean -f`。

## `reset`：带目标才移动分支

三种模式的区别只在「顺手改不改暂存区和工作区」：

| 模式 | 分支指针 | 暂存区 | 工作区 |
| --- | --- | --- | --- |
| `--soft` | 移动 | 不动 | 不动 |
| `--mixed`（默认） | 移动 | 重置 | 不动 |
| `--hard` | 移动 | 重置 | 重置 |

先看**不带目标**的 `git reset --hard`。我改了一个已跟踪文件，又放了一个未跟踪文件：

```text
PS> git log --oneline -1
6072885 加了个校验，这次写对了
PS> git status --short
 M a.txt
?? untracked.txt
PS> git reset --hard
HEAD is now at 6072885 加了个校验，这次写对了
PS> git log --oneline -1
6072885 加了个校验，这次写对了
PS> git status --short
?? untracked.txt
PS> git clean -n
Would remove untracked.txt
```

分支没移动，提交没少，`untracked.txt` 还在。`--hard` 只把已跟踪文件的工作区/暂存区重置到 HEAD；未跟踪文件要 `git clean` 才删。

带目标才会移动分支：

```text
PS> git log --oneline -2
4f588fe 临时提交
6072885 加了个校验，这次写对了
PS> git reset --hard HEAD~1
HEAD is now at 6072885 加了个校验，这次写对了
PS> git reflog -3
6072885 HEAD@{0}: reset: moving to HEAD~1
4f588fe HEAD@{1}: commit: 临时提交
6072885 HEAD@{2}: reset: moving to HEAD
```

`4f588fe` 从 `main` 上消失了，但还在 reflog 里。reflog 记提交，不记工作区；同一次 `--hard` 覆盖掉的未提交改动，reflog 里没有。

另一个只动暂存区的写法是 `git reset HEAD a.txt`：

```text
PS> git status --short
M  a.txt
PS> git reset HEAD a.txt
Unstaged changes after reset:
M	a.txt
PS> git status --short
 M a.txt
PS> git log --oneline -1
6072885 加了个校验，这次写对了
```

`git reset HEAD a.txt` 只把 `a.txt` 的暂存区拉回 HEAD，没有目标提交，所以分支没有移动。默认的 `git reset HEAD~1` 则是 `--mixed`：

```text
PS> git reset HEAD~1
Unstaged changes after reset:
M	a.txt
PS> git status --short
 M a.txt
```

分支回退一个提交，改动留在工作区、没暂存。`--soft` 则把改动留在暂存区；这就是下面场景 A 的起点。

## 场景 A：还没 push，soft reset 后重新提交

我在 `main` 上提交了 `b77c073`，还没 push。现在要撤掉这次提交，但保留改动：

```text
PS> git log --oneline -3
b77c073 加了个有 bug 的校验
2043562 把 a.txt 改成第二版
4c4757e 初始化 a.txt
PS> git reset --soft HEAD~1
PS> git status --short
M  a.txt
PS> git log --oneline -2
2043562 把 a.txt 改成第二版
4c4757e 初始化 a.txt
PS> git revert b77c073
error: your local changes would be overwritten by revert.
hint: commit your changes or stash them to proceed.
fatal: revert failed
```

`b77c073` 已经不在 `main` 上；soft reset 把它的改动留在暂存区。revert 会先检查工作区/暂存区，发现有内容会被这次反向改动覆盖，就停下来。这不是「revert 坏了」，是把两个场景混在一起了。

没 push 时，soft reset 后重新提交就够：

```text
PS> git commit -m '加了个校验，这次写对了'
[main 6072885] 加了个校验，这次写对了
 1 file changed, 2 insertions(+), 1 deletion(-)
PS> git log --oneline -3
6072885 加了个校验，这次写对了
2043562 把 a.txt 改成第二版
4c4757e 初始化 a.txt
```

要拆成两个提交，就在 `M  a.txt` 这步用 `git reset`（默认 `--mixed`）把改动放回工作区，再分次 `git add` / `git commit`。

## 场景 B：已经 push，不 reset，直接 revert

这次 `6f5483c` 已经 push 到 `main`（下面是当时那次 push 的输出）：

```text
PS> git push
To ../origin.git
   6072885..6f5483c  main -> main
PS> git log --oneline -3
6f5483c 加了个有 bug 的校验
6072885 加了个校验，这次写对了
2043562 把 a.txt 改成第二版
```

不要 `reset`。直接 revert：

```text
PS> git revert --no-edit 6f5483c
[main 937577b] Revert "加了个有 bug 的校验"
 Date: Thu Nov 19 12:26:43 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)
PS> git log --oneline -4
937577b Revert "加了个有 bug 的校验"
6f5483c 加了个有 bug 的校验
6072885 加了个校验，这次写对了
2043562 把 a.txt 改成第二版
```

这里加 `--no-edit`，否则 Git 会打开编辑器让你改 revert 的提交信息。历史是直的：

```text
A ── B ── 6f5483c ── 937577b
```

`937577b` 的直接父提交是 `6f5483c`，不是斜出去的旁支。原来的 `6f5483c` 还在，revert 只是加了一笔反向改动。公开分支上撤一个已推送的提交，用这条路。

### 合并提交要 `-m`

`revert` 遇到合并提交会停下：

```text
PS> git revert --no-edit 8aebb93
error: commit 8aebb93819bf300164f79f9e2be5d25b757e4691 is a merge but no -m option was given.
fatal: revert failed
```

要告诉 Git 哪一条是主线。合并时我在 `merge-main` 上，`-m 1` 保留第一父（`merge-main`），撤销另一侧：

```text
PS> git revert -m 1 --no-edit 8aebb93
[merge-main 06a5934] Revert "合并 feature"
 Date: Thu Nov 19 12:27:29 2026 +0800
 1 file changed, 1 deletion(-)
 delete mode 100644 feature.txt
```

`-m 2` 会以另一个父提交为主线；选错会把你想保留的那一侧撤掉。

## revert 是普通提交，冲突照来

revert 不是「远端帮我抹掉」，它生成一个普通提交。同一行后来又被改过，revert 就冲突：

```text
PS> git revert --no-edit bd97b59
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
error: could not revert bd97b59... 把校验改成 A
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run
hint: "git revert --continue".
hint: You can instead skip this commit with "git revert --skip".
hint: To abort and get back to the state before "git revert",
hint: run "git revert --abort".
hint: Disable this message with "git config advice.mergeConflict false"
PS> git status --short
UU a.txt
```

别人拉取也一样。另一个克隆里，协作者本地改了同一行；远端先合入 `f72e793`，随后 `dbacce6` revert 了它：

```text
# 另一个克隆，默认 merge 配置
PS> git pull --no-edit
Auto-merging a.txt
CONFLICT (content): Merge conflict in a.txt
Automatic merge failed; fix conflicts and then commit the result.
```

这里省略了 `From` 那一行。revert 提交和普通提交没有区别，冲突不会因为「它是撤销提交」而消失。解完冲突 `git add a.txt`，再 `git revert --continue`；不想解就 `git revert --abort`。

## force push 改的是远端，不是本地

旧说法「force push 只在本地生效」正好反了：它改的是远端引用，本地只是发起方。更麻烦的是 `--force-with-lease` 不是「我 fetch 过就安全」。

A、B 两个克隆。A 先 push 了 `7fa955a`；B 本地有 `bdc8207`，先 fetch：

```text
PS> git branch -vv
* main bdc8207 [origin/main: ahead 1] B 的提交
PS> git fetch
   4877ac7..7fa955a  main       -> origin/main
PS> git branch -vv
* main bdc8207 [origin/main: ahead 1, behind 1] B 的提交
```

这里省略了 `From` 行。B 已经看到远端是 `7fa955a`，但没看 `HEAD..origin/main` 里是什么，直接改写自己的提交（push 的 `To` 行省略）：

```text
PS> git commit --amend -m 'B 的提交（改写）'
[main 8c4151d] B 的提交（改写）
 Date: Thu Nov 19 12:28:25 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)
PS> git push --force-with-lease
 + 7fa955a...8c4151d main -> main (forced update)
```

`7fa955a` 被覆盖。lease 比较的是「远端当前值」和「你本地的 remote-tracking ref」；`git fetch` 刚把后者更新成 `7fa955a`，所以它认为一切正常。它防的是「你还没 fetch 到的更新」，不防「你 fetch 到了但没看」。

要挡住「远端在你确认之后又变了」，锁旧值。换一个还没 fetch 到这次覆盖的克隆 A，它以为远端还是 `7fa955a`：

```text
PS> git push --force-with-lease=main:7fa955a
 ! [rejected]        main -> main (stale info)
```

远端已经是 `8c4151d`，和 `7fa955a` 对不上，所以拒绝；Git 还会打印一行 `error: failed to push some refs to ...`。注意：如果 A 就是要覆盖 `7fa955a`，锁 `7fa955a` 仍会放行；lease 只保证「远端没在你锁定的值之后又变」，不替你做「该不该覆盖」的判断。先看 `git log --oneline HEAD..origin/main` 里有没有别人的提交，确认后再用 `--force-with-lease=<branch>:<expected-oid>` 锁住你确认过的那个值。

## 密钥泄露：先轮换，再改历史

顺序不能反。第一步不是 Git，是吊销/轮换：假设密钥已经泄露，去服务端 revoke 旧密钥、发新密钥、更新部署环境。Git 历史改得再干净，没轮换的旧密钥仍然能用。第二步才是改历史。

下面的演示用 `git-filter-repo`（不是 Git 自带；`git filter-repo --version` 能跑再照做）。它会打印解析和重写进度，这里只留前后历史：

```text
PS> git log --oneline
99a2b94 写 README
f5a11b9 加配置（含密钥）
PS> git filter-repo --path secret.txt --invert-paths --force
PS> git log --oneline
cd72f66 写 README
```

`filter-repo` 会把 `origin` 删掉；我重新 `git remote add origin <远端地址>` 后才 push。强制推上去（`To` 行省略）：

```text
PS> git push --force origin main
 + 99a2b94...cd72f66 main -> main (forced update)
```

然后通知协作者。不能直接 `git pull`；先 `git fetch`（`From` 行省略），我的测试克隆是默认 merge 配置，pull 直接拒绝：

```text
PS> git fetch
 + 99a2b94...cd72f66 main       -> origin/main  (forced update)
PS> git pull --no-edit
fatal: refusing to merge unrelated histories
```

也不能无脑 `git rebase origin/main`。我试了，它把旧历史里的密钥提交重放回来了。下面两段 rebase 输出都省略了 `Rebasing (n/m)` 进度行：

```text
PS> git rebase origin/main
warning: skipped previously applied commit 99a2b94
hint: use --reapply-cherry-picks to include skipped commits
hint: Disable this message with "git config advice.skippedCherryPicks false"
Successfully rebased and updated refs/heads/main.
PS> git log --oneline -3
e27f61d 协作者本地改 README
b61f11f 加配置（含密钥）
cd72f66 写 README
```

正确做法是只搬自己的提交。`99a2b94` 是改写前的远端 tip，`f574e44` 是协作者自己的本地提交；`git rebase --onto origin/main 99a2b94 main` 只重放 `99a2b94..main` 里的提交：

```text
PS> git reset --hard f574e44
HEAD is now at f574e44 协作者本地改 README
PS> git rebase --onto origin/main 99a2b94 main
Successfully rebased and updated refs/heads/main.
PS> git log --oneline -3
c920e97 协作者本地改 README
cd72f66 写 README
```

也可以 `git switch -c fix origin/main` 后 `git cherry-pick f574e44`，效果是只把自己的提交放到新历史上。无论哪种，改完都要确认 `git log --all --oneline -- secret.txt` 为空。

改历史 + force push 不能保证旧密钥从别人的本地、fork、CI 缓存里消失；轮换才是止血。force push 只是让远端分支不再指向旧提交，旧对象还可能留到 gc。

## 还差的

- `git rebase -i` 的拆提交/压缩提交没讲；场景 A 只演示了 soft reset 后重新提交，多个提交怎么重排是另一套操作。
- `git revert` 一次撤多个提交没讲：`git revert --no-commit A..B` 的顺序、以及 revert 一个 revert 怎么处理，这篇都没展开。
- `git restore --source=<commit> --staged --worktree` 只验证了 `HEAD~1` 这一个组合；从任意分支/标签取文件、以及路径不存在时怎么报错，没逐项跑。
- 受保护分支（branch protection）会拒绝 force push（除非管理员显式放行）；团队要求走 PR 时怎么清理密钥，这篇没给流程。
- `git filter-repo` 之后旧对象什么时候被 gc、fork 和 PR 引用为什么还会留着密钥，这篇只验证了主仓库的历史。
