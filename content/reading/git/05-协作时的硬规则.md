## 先看这条 fatal

远端多了一个提交，我本地也多了一个提交。Git 2.45.1.windows.1，临时仓库，`pull.rebase` 未配置（系统级和全局配置都隔离掉）：

```text
$ git pull
From ../origin
   1b63e94..96d3eef  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

$ git status --short --branch
## main...origin/main [ahead 1, behind 1]
```

我原来以为「没配 `pull.rebase` 就是 merge」。实际从 Git 2.33.1 起（2.33.1 本身按发布说明，本机 2.45.1 实测），这种两边都前进的状态下 `git pull` 直接失败，退出码 128；fetch 已经成功，但本地分支没有被合并，也没有被 rebase。

这条 fatal 不是每台机器都能复现。我的 Git for Windows 在系统级配置里已经写了 `pull.rebase=false`：

```text
$ git config --show-origin --get pull.rebase
file:C:/Program Files/Git/etc/gitconfig	false
```

所以上面那个临时仓库才把 `GIT_CONFIG_NOSYSTEM` 设为 1、把全局配置指向空文件。你先在自己机器上查这一条，别假设「默认」是什么。

下面每个代码块都来自 `$env:TEMP` 里的独立临时仓库；哈希只用于对照，不会和你的仓库一致。

## pull 的三种结局

### 快进：只移动分支指针

main 在 `c1`，远端又推进到 `c2`，本地没有新提交：

```text
$ git pull
From ../origin
   20bfc5e..301aa6a  main       -> origin/main
Updating 20bfc5e..301aa6a
Fast-forward
 remote.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 remote.txt

$ git rev-list --parents -n 1 HEAD
301aa6a8ac8fab069765d2b41e91ee9d2557a4e1 20bfc5eead227b8ba3339f4244c05151eb0159fb
```

`rev-list --parents` 只有两个哈希：当前提交和它的一个父提交。没有合并提交。即使 `pull.rebase=true`，能快进时输出仍然是 `Fast-forward`（我另跑了一次同样的场景）。

### 需要选择：fatal，不是自动 merge

就是开头那条。两边都前进时，未配置 `pull.rebase` 的 `git pull` 不会「可能 merge」；它直接退出，要求你先选。选了之后才有两种历史。

先把配置设成 merge：

```text
$ git config pull.rebase false
$ git pull
From ../origin
   20bfc5e..301aa6a  main       -> origin/main
Merge made by the 'ort' strategy.
 remote.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 remote.txt

$ git rev-list --parents -n 1 HEAD
6dbe3705a427e81588273f8960f87761dae56757 045a61d345a93921bb5febb13222ce1f1eb9059a 301aa6a8ac8fab069765d2b41e91ee9d2557a4e1
```

三个哈希：合并提交加两个父提交。`git log --graph` 会保留那条分叉。

改成 rebase：

```text
$ git config pull.rebase true
$ git pull
From ../origin
   20bfc5e..301aa6a  main       -> origin/main
Rebasing (1/1)
Successfully rebased and updated refs/heads/main.

$ git log --graph --oneline --decorate -4
* 6db7ffb (HEAD -> main) r1 本地提交
* 301aa6a (origin/main, origin/HEAD) c2 远端提交
* 20bfc5e c1 初始化
```

本地提交 `r1` 换了哈希，历史变成一条直线。`Rebasing (1/1)` 和 `Successfully...` 之间还有一行空白进度条，我省掉了。

### 拒绝：`pull.ff only` 会把选择权留给你

```text
$ git config pull.ff only
$ git pull
From ../origin
   301aa6a..cb04958  main       -> origin/main
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint:     git merge --no-ff
hint:
hint: or:
hint:
hint:     git rebase
hint:
hint: Disable this message with "git config advice.diverging false"
fatal: Not possible to fast-forward, aborting.
```

本地分支没动，`git status` 仍显示 `[ahead 1, behind 1]`。这时你可以明确地 `git merge origin/main` 或 `git rebase origin/main`，而不是让 `pull` 替你选。

三条实践建议：

1. 团队统一显式配置 `pull.rebase`：要合并提交就 `git config --global pull.rebase false`，要直线历史就 `true`。先 `git config --show-origin --get pull.rebase` 看有没有系统级默认值。
2. 不想让 `pull` 自动造合并提交，就 `git config --global pull.ff only`；分叉时它直接拒绝，你再用 `git merge` 或 `git rebase` 明确处理。
3. 单次命令覆盖：`git pull --no-rebase`、`git pull --rebase`、`git pull --ff-only`。不要把「我这台机器默认怎样」当成团队约定。

## merge 与 rebase：收尾命令不是一套

03 那篇讲了两条路的形状；这里只记冲突后的收尾，因为这两套命令混用会直接报错。

### merge：`git add` + `git commit`（或 `git merge --continue`）

```text
$ git merge topic
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU app.txt

$ cat app.txt
line1
<<<<<<< HEAD
main side
=======
topic side
>>>>>>> topic
line3

$ git add app.txt
$ git commit --no-edit
[main bd000b7] Merge branch 'topic'
```

`git merge --continue` 等价于在 add 之后继续这次 merge；我也跑了一遍：

```text
$ git merge --continue
[main 100bd7c] Merge branch 'topic'
```

但 merge 冲突里敲 rebase 的收尾命令会直接失败：

```text
$ git rebase --continue
fatal: no rebase in progress
```

所以 merge 的收尾是 `git add` + `git commit`（或 `git merge --continue`），不是 `git rebase --continue`。

### rebase：`git add` + `git rebase --continue`

```text
$ git rebase main
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Rebasing (1/1)
error: could not apply f52fae3... t1 topic 改这一行
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
hint: Disable this message with "git config advice.mergeConflict false"
Could not apply f52fae3... t1 topic 改这一行

$ cat app.txt
line1
<<<<<<< HEAD
main side
=======
topic side
>>>>>>> f52fae3 (t1 topic 改这一行)
line3
```

rebase 时右侧不是分支名，而是「提交哈希 + 提交标题」；因为现在在 detached HEAD 上重放。收尾命令也不同：

```text
$ git merge --continue
fatal: There is no merge in progress (MERGE_HEAD missing).

$ git add app.txt
$ git rebase --continue
[detached HEAD 18a045f] t1 topic 改这一行
 1 file changed, 1 insertion(+), 1 deletion(-)
Successfully rebased and updated refs/heads/topic.
```

rebase 的收尾就是 `git add` + `git rebase --continue`；`git commit` 是 merge 那一套，别拿来代替。

历史后果也不同：

- merge 分叉时会产生双父提交，`git log --graph` 能看到两条线；冲突在合并提交里解一次。
- rebase 把每个本地提交按顺序重放到新基底上，哈希全变，历史成直线；冲突可能按提交停多次。

## 什么时候才轮到 `--force-with-lease`

普通 `git push` 被拒，不是马上 `--force`。先看括号里的原因：

- `fetch first`：远端有你本地没有的对象。先 `git fetch`，再决定 merge/rebase。
- `non-fast-forward`：你已经 fetch 过，但本地历史与远端分叉。先整合，别覆盖。
- `stale info`：只出现在 force-with-lease；远端当前值和你的 lease 预期值不一致。

这三行来自不同的临时仓库，括号就是 Git 给你的分类：

```text
 ! [rejected]        main -> main (fetch first)
 ! [rejected]        main -> main (non-fast-forward)
 ! [rejected]        main -> main (stale info)
```

下面这个临时仓库里，Bob 先推了 `b1`，Alice 随后用 `git push --force` 把远端改写成 `a1`。Bob 本地还记着 `b1`，但没 fetch：

```text
$ git push --force-with-lease origin main
To ../origin.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '../origin.git'
```

lease 拒绝，因为远端不是 Bob 记的 `b1`。Bob 执行 fetch：

```text
$ git fetch origin
From ../origin
 + c275ec1...cf33f26 main       -> origin/main  (forced update)

$ git status --short --branch
## main...origin/main [ahead 2, behind 1]

$ git log --oneline --graph --decorate -3 origin/main
* cf33f26 (origin/main, origin/HEAD) Alice 改写 b1
* aeaddde base
```

fetch 只更新远端跟踪引用，不改 Bob 的本地分支；但 lease 的预期值已经变成 `cf33f26`。再推：

```text
$ git push --force-with-lease origin main
To ../origin.git
 + cf33f26...1ae9487 main -> main (forced update)
```

这次通过了，Alice 的 `cf33f26` 从远端分支上消失：

```text
$ git log --oneline --graph --decorate -3 origin/main
* 1ae9487 (HEAD -> main, origin/main, origin/HEAD) Bob 的修改 b2
* c275ec1 Bob 的修改 b1
* aeaddde base
```

这就是边界：默认 lease 只比较「远端引用是否还是 `refs/remotes/origin/main` 里记的值」。fetch 会把这个值更新到远端最新；你已经看到 Alice 的提交，但没审，默认 lease 仍然放行。它防的是「远端在你上次查看之后又变了」，不防「你已经看见了，然后决定覆盖」。

要把预期值钉死，显式写 `<ref>:<expected-oid>`。下面 Alice 把期望值钉在 `b2`（`1ae9487`），Bob 又把它改写成 `b3`（`1464726`）：

```text
$ git push --force-with-lease=main:1ae948775097864c4c0ac4c4411fb41eafbb8f8d origin main
To ../origin.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '../origin.git'
```

remote 不是 `b2`，拒绝。如果 Alice fetch 了 `b3`，默认 lease 又会接受新值；她再推就覆盖 Bob 的 `b3`：

```text
$ git fetch origin
From ../origin
 + 1ae9487...1464726 main       -> origin/main  (forced update)

$ git push --force-with-lease origin main
To ../origin.git
 + 1464726...e907859 main -> main (forced update)
```

所以它不能拦「同时改写历史」的另一方。两边都在改写时，lease 不判断谁的内容更重要，只比一个哈希：对方先推、你没 fetch，你得到 `stale info`；你 fetch 完，lease 就接受对方的新值，再推就覆盖对方。

它适用的场景很窄：

- 这条分支由你独占，刚 rebase/amend 过，确认没人基于旧提交工作；
- 你确实要把敏感信息或大文件从历史里移除，且已经和协作者约好重写时间。

共享分支上的错误，优先 `git revert`，不是 reset + force。

### 已经推上去的错：先想 revert

```text
$ git revert --no-edit HEAD
[main f1ce803] Revert "c2 要撤的提交"
 Date: Thu Nov 19 14:27:09 2026 +0800
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git reset --hard HEAD~1
HEAD is now at 7bc6ef8 c2 要撤的提交
```

`revert` 多一个反向提交，历史可以继续快进推送；`reset --hard` 把当前分支指针往回拨，已经推过的分支再推会被非快进拒绝，要过就得走 force 类操作，别人基于旧提交的工作会断。共享分支上，我优先 revert。

### 删除文件不等于从历史删除

临时仓库里加入一个 5MB 的 `big.bin`，下一提交删掉：

```text
$ git log --oneline --all -- big.bin
5cb8dbd 删除 5MB 文件
a68b7fe 加入 5MB 文件

$ git cat-file -e HEAD:big.bin
fatal: path 'big.bin' does not exist in 'HEAD'

$ git clone big clone
$ git -C clone cat-file -s a68b7fe:big.bin
5242880
```

`HEAD` 里没有这个路径了，但新 clone 仍能按旧提交 `a68b7fe` 取出 5MB 的 blob。删文件只是让最新树不再引用它，历史对象还在。要把历史里的副本也去掉，按文档要用 `git filter-repo` 重写（先做镜像/备份，重写后协作者重新 clone，再协调 force push）；我没在本机跑这段重写，标记为按文档。凭据泄露还要先轮换，因为别人可能已经拉走了旧历史。

## 冲突标记与 stash 的两个细节

### 冲突标记不止一种

默认 merge 冲突的标记就是前面那三行：`<<<<<<< HEAD`、`=======`、`>>>>>>> <branch>`。打开 `merge.conflictStyle=diff3` 后，同一个冲突会多出 merge base：

```text
$ git config merge.conflictStyle diff3
$ git merge topic
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.

$ cat app.txt
line1
<<<<<<< HEAD
main side
||||||| bf3b02a
base
=======
topic side
>>>>>>> topic
line3
```

`||||||| bf3b02a` 里的 `bf3b02a` 是 merge base 的缩略哈希；`<base>` 指的就是这一段，不是固定字符串。rebase 冲突的右侧则是 `>>>>>>> f52fae3 (t1 topic 改这一行)`，带提交哈希和标题，前面已经看到。

删除、重命名、二进制冲突不一定有文本标记，先看 `git status --short` 的两字母状态。

```text
$ git merge del
CONFLICT (modify/delete): doc.txt deleted in del and modified in HEAD.  Version HEAD of doc.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UD doc.txt
```

文件内容就是 HEAD 版本，没有 `<<<<<<<`，要用 `git add` 或 `git rm` 明确选保留还是删除。

```text
$ git merge b
CONFLICT (rename/rename): old.txt renamed to a.txt in HEAD and to b.txt in b.
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
AU a.txt
UA b.txt
DD old.txt
```

两个目标文件都在，旧的没了；没有文本标记，按状态决定保留哪个名字。

```text
$ git merge topic
warning: Cannot merge binary files: pic.bin (HEAD vs. topic)
Auto-merging pic.bin
CONFLICT (content): Merge conflict in pic.bin
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU pic.bin
```

文件内容保持 HEAD 版本（实测首字节 `00 09 03 04 05`），没有标记。注意：Git 是否把文件当二进制是它自己判定的。我第一次用不含 NUL 的 `01 02 03 04 05`，它仍按文本合并，塞进了 `<<<<<<<` 标记；只有含 NUL 的那次才走了 binary 分支。别按扩展名猜。

### stash 默认不收未跟踪文件

```text
$ git status --short --ignored
 M readme.txt
?? untracked.txt
!! debug.log

$ git stash
Saved working directory and index state WIP on main: 226daf1 base

$ git status --short --ignored
?? untracked.txt
!! debug.log
```

默认 `git stash` 只收 tracked 文件的改动；`untracked.txt` 和 ignored 的 `debug.log` 都留在工作区。加 `-u`：

```text
$ git stash -u
Saved working directory and index state WIP on main: 226daf1 base

$ git status --short --ignored
!! debug.log
```

未跟踪文件收进去了，ignored 还在。再加 `-a`：

```text
$ git stash -a
Saved working directory and index state WIP on main: 226daf1 base

$ git status --short --ignored
```

这次没有输出，ignored 文件也收进去了。`git stash` 不是备份：默认模式下它不会带走未跟踪文件，切分支时这些文件会留在原地，可能挡住 checkout。

## 两条仍然成立的日常检查

- 提交前 `git diff --cached`：`commit` 提交的是暂存区，不是工作区。`git add .` 很容易把 `.env.local`、日志、别人的在飞改动卷进来。
- 一个提交只做一件事：混着格式和逻辑，冲突范围更大；要 revert 其中一个功能时也只能整笔撤或手工挑。
- 提交信息写「为什么」，不要写「改了点东西」；三个月后 `git log` 是排查的第一手资料。

## 一张表

| 我要做什么 | 该用哪条命令 | 失败时先看什么 |
| --- | --- | --- |
| 只同步，不允许本地分叉 | `git pull --ff-only` | `fatal: Not possible to fast-forward`：远端有新提交且本地也前进过（分叉），先决定 merge/rebase |
| 接远端，保留分叉历史 | `git pull --no-rebase` 或 `git merge origin/<branch>` | `CONFLICT` 后看 `git status --short`；`UU` 两边都改、`AA` 两边都加、`UD/DU` 一边改一边删 |
| 接远端，把自己的提交接到最新之后 | `git pull --rebase` 或 `git rebase origin/<branch>` | `CONFLICT` 后 `git add` + `git rebase --continue`，不要用 `git commit` 收尾 |
| 普通 `git push` 被拒 | `git push` | 括号里 `fetch first` 先 fetch；`non-fast-forward` 先整合；别直接 force |
| 推送自己刚 rebase/amend 的独占分支 | `git push --force-with-lease=<branch>:<expected-oid>` | `stale info` 说明远端不是你钉的值；先 fetch、审提交、再决定 |
| 撤销已经共享的提交 | `git revert <commit>` | 冲突按 merge 收尾：`git add` + `git commit` 或 `git merge --continue` |
| 临时收起未提交改动 | `git stash -u`（含未跟踪）或 `git stash -a`（含忽略） | `git status --short --ignored` 看还剩什么；默认 stash 不收未跟踪 |
| 提交前确认内容 | `git diff --cached` | 看是否混入 `.env.local`、日志、别人的在飞改动 |

## 还差的

- 这篇文章以 Git 2.45.1.windows.1 + 隔离配置为基线；2.33.1 之前的行为，以及各平台 system config 到底预置了什么，我没有逐版本验证。
- `git filter-repo` 的历史重写流程按文档写，没有在本机跑；BFG 和 `filter-branch` 也没测。
- 没覆盖 `git pull --rebase=merges`、`rebase.autoStash` 这类组合；自动 stash 在冲突时的行为我没实测。
- 没验证 GitHub/GitLab 的受保护分支、merge queue、squash merge 对 force push 和 rebase 的服务端限制；客户端 lease 通过，服务端仍可能拒绝。
- stash 只测了默认、`-u`、`-a` 对文件范围的影响，没测 `--index`、pathspec 和 stash 冲突。
