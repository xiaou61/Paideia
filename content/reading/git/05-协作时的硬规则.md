## 先把结论摆出来

团队协作里九成的 git 事故来自四条可以背下来的规则：

1. **共享分支绝不 force push**（除非先通知所有人）；
2. **提交前看 `git diff --cached`**，确认暂存了什么；
3. **冲突在本地解，不在远端解**；
4. **一个提交只做一件事**——这是让冲突变少、让 revert 可行的前提。

前三条是防止伤害别人，第四条是防止伤害未来的自己。

## 规则一：共享分支不 force push

`--force` 会无条件把远端引用改成你本地的样子。别人基于旧提交的工作瞬间失去依据。

如果真的必须改写（rebase 后推送、清理敏感信息），做法是：

```text
git push --force-with-lease
```

它会先确认远端引用是否还是你上次 fetch 到的那个。如果别人已经推了新东西，它会**拒绝**而不是覆盖。

即使如此，也要在团队里说一声——别人需要 `git fetch` 后重建本地分支，不能直接 `git pull`（历史已分叉）。

## 规则二：提交前看暂存区

`git add` 之后，**暂存区才是真正要提交的内容**，不是工作区。

```text
$ git diff --cached
```

这条命令显示"这次提交会包含什么"。它挡住的典型事故：

- `git add .` 把不该提交的本地配置文件、日志、临时文件一起带上；
- 把调试用的 `console.log`、`print` 提交上去；
- **把凭据提交上去**（公开仓库里这是不可逆的）。

还有一个更隐蔽的：**多个会话/多个人共用一个工作区时，`git add .` 会把别人的在飞改动卷进你的提交**。所以要么用 `git add <具体文件>`，要么提交前一定看一眼 `--cached`。

## 规则三：冲突在本地解

远端永远不该出现冲突。冲突应当在本地 `pull` / `merge` / `rebase` 时解决，然后提交一个干净的结果再推。

如果 push 被拒绝，正确顺序是：

```text
git fetch
git rebase origin/分支     # 或 git merge origin/分支
# 解冲突、git add、git rebase --continue
git push
```

错误做法是 `git push --force` 把别人的提交顶掉。

## 规则四：一个提交只做一件事

这不只是风格问题，它直接决定两件事：

1. **冲突范围**：一个提交同时改了格式和逻辑，别人改同一文件时冲突会更难判断；
2. **能不能 revert**：混着三个功能的提交，想撤掉其中一个就只能手工挑。

具体做法：提交前 `git diff --cached` 过一遍，发现是两件事就分两次 `git add` + `commit`。

## pull 的默认行为是个坑

`git pull` = `fetch` + 合并。合并策略取决于配置：

- 默认可能是 **merge**（产生合并提交）；
- 也可能配成 **rebase**（直线历史）；
- 新版 git 在"两边都前进过"时会**拒绝并提示你配置**。

团队里应该显式定下来：

```text
git config --global pull.rebase true    # 或者 false，二选一
```

不定的话，不同人机器上行为不同，历史形态就不一致。

## 一个具体的踩坑现场

```text
$ git add .
$ git commit -m "改了点东西"
$ git push
```

问题在哪：

- `git add .` 可能带上了 `.env.local`、`target/`、别人正在改的文件；
- 提交信息"改了点东西"让 `git log` 三个月后完全无法使用；
- 如果推上去的是凭据，**删文件不能补救**，因为历史里还有。

正确做法：

```text
$ git status                  # 看有哪些改动
$ git add src/Login.java      # 只加自己这次要提交的文件
$ git diff --cached           # 确认暂存内容
$ git commit -m "fix(auth): 登录超时后不再重复刷新令牌"
$ git push
```

## 常见误区

### 误区：提交信息随便写，反正能改

**你以为**：提交信息无关紧要，代码能看懂就行。
**其实**：`git log` 是排查"这行为什么这样"的第一手资料。写了"改了点东西"的提交，三个月后连作者自己也不知道当时在修什么。
**怎么验证**：翻自己三个月前的提交，看能不能只靠信息说出改了什么。

### 误区：反正有 reflog，丢不了

**你以为**：所有操作都能回滚。
**其实**：reflog 只记**引用移动**（提交、切换、reset），不记工作区未提交的改动。`reset --hard` 或 `restore` 覆盖掉的未提交内容真的没了。
**怎么验证**：改文件不提交 → `git reset --hard` → `git reflog` 里找不到那段内容。

### 误区：冲突是 git 的问题，工具不好用

**你以为**：冲突频繁说明 git 难用。
**其实**：冲突来自"两个人改了同一处"，是真实的协作矛盾。git 只是把它显式摆出来。冲突少靠的是提交粒度小、分支生命周期短。
**怎么验证**：对比长命分支（几周）与短命分支（一两天）的冲突频率。

## 小结

四条规则：不 force push 共享分支、提交前看 `--cached`、冲突本地解、一个提交一件事。`pull.rebase` 显式配置。提交信息写清"为什么"。
