## 这一关在解决什么

你在地址栏敲下一个网址，到看见页面，中间发生了一长串事。这一关把这条链路拆开：**哪一步在等网络、哪一步在等你的 CSS 和 JS、哪一步是浏览器在算像素**。

拆开之后你会得到三个能立刻用上的判断：

- 页面"白屏很久"到底是网络慢，还是渲染被阻塞；
- 为什么 `<script>` 放的位置会影响首屏；
- 为什么"接口很快但页面还是很卡"完全可能。

## 讲解

### 第一步：把名字变成地址

浏览器先要找到服务器。`https://example.com/a` 里的 `example.com` 对人友好，对网络不友好——它得先查 DNS，拿到 IP。

这一步的耗时通常几十毫秒，但**首次访问**（没有缓存）可能几百毫秒。它发生在任何 HTTP 请求之前，所以"我的接口日志里没有这次请求"有可能是请求根本没到服务器。

### 第二步：建立连接，发一个 HTTP 请求

拿到 IP 后建立 TCP 连接；`https` 还要多做一次 TLS 握手（协商密钥、验证证书）。之后才发出真正的 HTTP 请求：

```text
GET /a HTTP/1.1
Host: example.com
Accept: text/html
```

服务器返回状态行、响应头、响应体。**响应体通常就是一份 HTML 文本**——注意，浏览器此刻拿到的还不是"页面"，只是文本。

### 第三步：解析 HTML，边下边建 DOM

浏览器不会等整个 HTML 下载完才开始。它一边收一边解析，把标签变成一棵 **DOM 树**：

```text
html
├── head
│   ├── title
│   └── link rel=stylesheet
└── body
    ├── h1
    └── p
```

这解释了两件事：

1. **HTML 是流式的**：服务器可以先把头部发出来，浏览器先解析头部、开始下载 CSS。
2. **解析会被同步脚本打断**：遇到没有 `defer`/`async` 的 `<script>`，浏览器必须停下来，先把脚本下载并执行完，因为脚本可能 `document.write` 改掉后面的结构。这就是"JS 阻塞解析"。

### 第四步：CSS 也要变成一棵树

`<link rel="stylesheet">` 指向的 CSS 被下载、解析成 **CSSOM**。它和 DOM 一起决定"每个节点长什么样"。

关键点：**CSS 阻塞渲染**。浏览器必须等 CSSOM 建好才敢画第一帧，否则会先画一个没有样式的页面再跳变（FOUC）。所以首屏的 CSS 越早到越好，放在 `<head>` 里是有原因的。

### 第五步：DOM + CSSOM → 布局 → 绘制 → 合成

有了两棵树，浏览器：

1. **计算样式**：每个节点最终命中哪些规则（层叠、优先级、继承）；
2. **布局（layout/reflow）**：算出每个盒子的位置与大小；
3. **绘制（paint）**：把文字、背景、边框画到图层上；
4. **合成（composite）**：把图层按顺序拼成屏幕上的像素。

你改一个属性，触发的步骤不同，代价也差一个数量级：

| 你改的 | 触发 | 代价 |
| --- | --- | --- |
| `width`、`margin`、`font-size` | 布局 → 绘制 → 合成 | 最贵 |
| `background-color`、`box-shadow` | 绘制 → 合成 | 中等 |
| `transform`、`opacity` | 只合成 | 最便宜 |

"用 `transform` 做动画"不是玄学，是因为它跳过了布局与绘制。

### 三个等待点，对应三类问题

```text
网络（DNS/TCP/TLS/HTTP） → 解析（HTML/CSS/JS） → 渲染（布局/绘制/合成）
```

- 首屏慢、Network 面板里首字节很久：问题在**网络或服务端**；
- 首字节很快，但页面一直白：可能是**同步脚本或阻塞的 CSS**；
- 页面出来了但滚动卡：**渲染/绘制**的问题（动画属性、布局抖动、图层过多）。

DevTools 的 Performance 面板就是按这三段给你时间线的。看不懂之前，先记住这三段。

## 常见误区

### 误区：HTML 下载完，页面就该出来了

**你以为**：`Network` 里 HTML 请求 200 了，页面空白就是"代码有问题"。
**其实**：HTML 只是原料。之后还要下载 CSS、执行脚本、等接口数据、再渲染。React 这类应用甚至要等 JS 执行完才第一次画东西——所以"HTML 到了但页面空白"是正常的中间态。
**怎么验证**：Performance 面板录一次加载，看 Main 线程什么时候开始有渲染活动；或者禁用缓存再刷新，对照 Network 瀑布图。

### 误区：`<script>` 放哪都一样

**你以为**：脚本放 `<head>` 更"整齐"。
**其实**：普通 `<script>` 会阻塞 HTML 解析，放在 `<head>` 意味着后面的 DOM 还没建，脚本里 `document.querySelector` 很可能拿到 `null`。放在 `</body>` 前，或者加 `defer`，才是常规做法。
**怎么验证**：把一段 `document.querySelector('h1')` 的脚本分别放 `<head>` 与 `</body>` 前，看控制台一个报 null、一个有结果。`defer` 的脚本会在解析完成后按顺序执行，也不会阻塞解析。

### 误区：接口快，页面就一定快

**你以为**：`fetch` 花了 50ms，用户就该 50ms 后看到内容。
**其实**：拿到数据只是开始。你还要改 DOM、浏览器要重新布局与绘制。如果一次插入几千行、或者每插一行都读一次 `offsetHeight`，主线程会被占满，用户看到的是卡顿而不是"数据很快"。
**怎么验证**：Performance 面板里看 Long Task；一次渲染超过 50ms 就会让交互感觉发黏。
