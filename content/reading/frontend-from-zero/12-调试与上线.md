## 这一关在解决什么

本地一切正常、部署上去白屏——这是前端最典型的一类事故。它通常不是"代码坏了"，而是三件事之一：

1. 构建时和运行时的差别（环境变量、路径、API 地址）；
2. 服务器没配单页应用的回退规则；
3. 缓存让浏览器拿到了旧入口文件。

这一关先教怎么用 DevTools 定位，再讲构建与部署时最容易漏的配置。

打个比方：本地能跑、线上白屏，就像菜谱没错，但换了个厨房、换了口锅。真实机制是构建时替换环境变量、服务器决定 MIME、缓存与路由回退，这三处一变，表现就变。

## 讲解

### 五个面板，各管一段

| 面板 | 什么时候看 | 关键信息 |
| --- | --- | --- |
| Console | 有报错、变量不对 | 异常栈、网络错误、`console.log` |
| Network | 首屏慢、接口不对 | 状态码、请求头、响应体、瀑布时间线 |
| Elements | 样式没生效 | 命中的规则、被谁覆盖、盒模型 |
| Performance | 卡顿 | Main 线程长任务、布局/绘制耗时 |
| Application | 登录态、缓存 | localStorage、Cookie、Service Worker、缓存存储 |

排查顺序建议：**先 Console 看有没有红字，再 Network 看请求是否成功，最后才进代码**。跳过前两步直接读代码，经常是在修一个不存在的问题。

### 一个白屏的标准排查流程

1. Console 有没有 `Uncaught`？有就先修它（常见：`Cannot read properties of undefined`）。
2. Network 里入口 HTML 是 200 吗？JS/CSS 是 200 还是 404？
3. 如果 JS 全是 404：检查部署路径与 `base` 配置——资源引用的是 `/assets/...`，而站点部署在 `/app/` 下，就会全 404。
4. 如果 JS 200 但没执行：看是不是 MIME 类型不对（服务器把 `.js` 当 `text/plain` 返回，模块脚本会被拒绝执行）。
5. 如果路由刷新 404：服务器没配 SPA 回退，`/settings` 这类前端路由需要回退到 `index.html`。

### 构建到底做了什么

```text
pnpm build        # 产出 dist/
```

典型产物：

```text
dist/
├── index.html
└── assets/
    ├── index-a1b2c3.js
    └── index-d4e5f6.css
```

文件名里的哈希来自**内容**：内容变了哈希才变。这样才能让浏览器长期缓存 `assets/*`（一年），而 `index.html` 必须每次回源校验。否则用户会一直拿到指向旧哈希的旧入口。

常见部署规则：

```text
/assets/*      Cache-Control: public, max-age=31536000, immutable
/index.html    Cache-Control: no-cache
```

这条规则写反（给 index.html 长缓存）就是"发版后部分用户还是旧页面"的根因。

### 环境变量在构建时就被替换

大多数前端构建工具（Vite、CRA）把 `import.meta.env.VITE_API_BASE` 在**构建时**替换成字面量。所以：

- 构建机上的变量决定产物，运行时改服务器环境变量没用；
- 不要把密钥放进 `VITE_*`——它会原样打进 JS，任何人打开 DevTools 都能看到；
- 同一份产物要部署到多个环境，应该用运行时配置（部署时生成的 `config.js`）或在网关层做反向代理。

### 路由回退

单页应用的路由是浏览器端的。用户直接访问 `/settings` 时，服务器上并没有这个文件，必须回退：

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

没有这一条，用户刷新非首页就是 404。本地开发服务器默认帮你做了，所以本地永远复现不了。

### 发布前的最小检查

- [ ] `pnpm build` 本地能过（不是只过 dev）；
- [ ] 产物用静态服务器跑一遍（`npx serve dist`），而不是继续用 dev server；
- [ ] 直接访问一个非首页路由并刷新；
- [ ] 断网/慢网下看加载态与失败态；
- [ ] Console 无报错，Network 无 404。

这五条能挡住绝大多数"上线才发现"的问题。

## 常见误区

### 误区：本地能跑，线上也应该能跑

**你以为**：同一份代码，环境不重要。
**其实**：构建会替换环境变量、压缩代码、拆分 chunk；服务器会决定 MIME、缓存与回退规则。这三处任何一处不同，表现就不同。
**怎么验证**：本地 `pnpm build && npx serve dist`，再走一遍主流程——这一步比再跑十次 dev server 有用。

### 误区：缓存清了就没事了

**你以为**：用户报"页面没更新"，让他 Ctrl+F5 就行。
**其实**：如果 `index.html` 被设了长缓存，普通刷新也不会回源；正确做法是修缓存头，而不是教用户清缓存。
**怎么验证**：Network 面板看 `index.html` 的响应头与 `from disk cache` 标记。

### 误区：把 API 地址写死在前端最省事

**你以为**：`fetch('http://1.2.3.4:8080/api')` 直接能用。
**其实**：写死地址会让跨域、HTTPS 混合内容、换环境全部变成问题；而且地址会进 Git 历史。常规做法是同源相对路径 `/api`，由网关或反向代理转发到后端。
**怎么验证**：部署到 HTTPS 后请求 HTTP 接口，Console 会报 Mixed Content 并被浏览器拦截。

## 带走一句

**先看 Console 与 Network，再怀疑代码；构建产物用静态服务器验一遍，缓存头与路由回退是上线必查项**——白屏九成出在这三处。
