## 这一关在解决什么

到了 React 里，最常见的三类 bug 是：

1. `setState` 之后立刻读，拿到旧值；
2. 组件莫名其妙重渲染很多次，或者该更新时没更新；
3. `useEffect` 依赖写错，请求发两遍、定时器泄漏、无限循环。

这一关把"什么时候渲染、什么时候不渲染、副作用该放哪"讲清楚。

打个比方：状态像一次拍照的快照，你手里这张照片不会因为下次再拍就变。真实机制是每次渲染里的 `state` 都是当次固定值，`setState` 只是请求下一次重新渲染。

## 讲解

### 状态是快照

```jsx
const [count, setCount] = useState(0)

function handleClick() {
  setCount(count + 1)
  console.log(count) // 还是旧值
  setCount(count + 1) // 两次都基于同一个旧值，结果只加 1
}
```

`setState` 是**请求一次重新渲染**，不是立刻改变当前这份渲染里的变量。当前这次渲染看到的 `count` 是一个快照，永远不会变。

要基于上一次的值更新，用函数式写法：

```jsx
setCount((prev) => prev + 1)
setCount((prev) => prev + 1) // 现在加了 2
```

### 什么时候重新渲染

- `setState` 被调用，且新值与旧值**不同**（`Object.is` 比较）时，组件重新渲染；
- 父组件重新渲染时，子组件默认也重新渲染，除非用 `memo` 包住且 props 没变。

注意第一点：直接改对象再 `set` 同一个引用，**不会**触发渲染：

```jsx
user.name = 'B'
setUser(user)        // 引用没变，React 认为没变

setUser({ ...user, name: 'B' }) // 新对象，渲染
```

这就是"不可变更新"的由来——不是为了优雅，是为了让"变了没有"这个判断成立。

### 派生值不要存进 state

```jsx
// 不必要
const [total, setTotal] = useState(0)
useEffect(() => { setTotal(items.reduce((sum, i) => sum + i.price, 0)) }, [items])

// 直接算
const total = items.reduce((sum, i) => sum + i.price, 0)
```

凡是能由现有 state/props 算出来的，就在渲染时算。存两份就要同步两份，同步就会漏——这是上一关"单一数据源"的延续。

### useEffect：与外部世界同步

`useEffect` 的用途只有一个：**让组件和 React 之外的东西保持同步**（请求、订阅、定时器、直接操作 DOM）。它不负责"在渲染后做点事"的通用逻辑。

```jsx
useEffect(() => {
  const controller = new AbortController()
  setStatus('loading')
  fetch(`/api/tasks`, { signal: controller.signal })
    .then((res) => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      return res.json()
    })
    .then((data) => { setTasks(data); setStatus('ready') })
    .catch((error) => {
      if (error.name !== 'AbortError') { setError(error.message); setStatus('error') }
    })
  return () => controller.abort() // 清理：卸载或依赖变化时先取消
}, [])
```

三个要点：

1. **空依赖 = 只在挂载时跑一次**；
2. **返回的函数是清理**，卸载或依赖变化时执行——取消请求、清定时器、退订都在这里；
3. 开发模式下 React 会故意跑两次（严格模式）来暴露"清理不干净"的问题，**重复请求很可能不是 bug，而是你的清理写得不对**。

### 依赖数组不是"想不想再跑"

它是"这个 effect 用到了哪些外部值"。漏写会拿到旧值（闭包），多写会不必要地重跑。把 effect 里读到的所有 props/state 都写进去，通常就是对的。

如果发现加全依赖后无限循环，一般是因为 effect 里 `set` 了一个依赖项里的值——那说明这个值不该是 state，应该算出来。

### 请求的三种写法，选一种

- **组件里 `useEffect` + 四态**：简单页面够用，缺点是缓存、去重、重试都要自己写；
- **数据请求库**（TanStack Query 等）：自带缓存、失效、重试、加载态，中大型项目更省；
- **框架级数据加载**（路由 loader、Server Components）：首屏更快，但依赖框架。

三种没有高下，关键是**不要每个组件各写一套 `useEffect` 请求**。那会同时发出重复请求，且卸载后还在 `setState`。

## 常见误区

### 误区：`setState` 之后可以立刻读到新值

**你以为**：`setCount(1); console.log(count)` 输出 1。
**其实**：当前渲染里的 `count` 是快照；新值要等下一次渲染才出现在变量里。需要基于旧值计算就用函数式更新。
**怎么验证**：在 `setCount` 后面打日志，再在渲染函数里打日志，看两次执行的顺序。

### 误区：`useEffect(() => {...}, [])` 里的值是实时的

**你以为**：effect 每次执行都能拿到最新的 props。
**其实**：空依赖的 effect 只在挂载时执行一次，闭包里是当时的快照。后续 props 变化它看不到——典型的"定时器里一直是旧值"。
**怎么验证**：在 effect 里每秒钟打印一个 prop，改变 prop 后看输出是否变化。

### 误区：所有逻辑都可以塞进 `useEffect`

**你以为**：渲染后统一处理，逻辑集中。
**其实**：能从 state 算出来的（总数、过滤后的列表、是否为空）应该在渲染时算；只有与外部系统交互才需要 effect。滥用 effect 会让数据流变成"改 A → effect 改 B → effect 又改 C"，很难追踪。
**怎么验证**：数一下页面上有几个 effect 在 `setState`——超过两三个就值得重构。

## 带走一句

**状态是快照、派生值现算、副作用只用来和外部同步**——这三条能消掉 React 里大部分"更新了但没变"和"怎么又跑了一遍"。
