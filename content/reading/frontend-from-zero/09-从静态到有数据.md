## 这一关在解决什么

前面八关是零件，这一关把它们装成一台能用的机器：**一个从接口取数据、能加载、能失败、能空、能操作、能重试的列表页**。不引入框架，全部用原生 DOM 手写。

写完之后你会得到一个清晰的对照：React 到底替你省掉了哪几步。

打个比方：这一关像照着图纸组装一台机器，前面的零件（DOM、事件、异步）都在这一关装到一起。真实机制是：页面只有一个状态变量，渲染函数只按状态画界面。

## 讲解

### 目标

一个任务列表：

- 打开时显示"加载中"；
- 成功：渲染列表，每项有删除按钮；
- 空：显示"还没有任务"；
- 失败：显示原因与"重试"；
- 删除后列表与计数同步更新。

### 页面骨架

```html
<main class="page">
  <h1>任务</h1>
  <p id="count" class="muted"></p>
  <ul id="list" class="list"></ul>
  <p id="state" class="muted" hidden></p>
  <button id="retry" type="button" hidden>重试</button>
</main>
```

关键点：**状态区域与列表区域是两个节点**，不要用"清空整个 main 再重建"来切状态。那会把重试按钮自己的事件监听也一起清掉（除非用委托）。

### 状态只有四种

```js
let tasks = []
let status = 'loading' // loading | ready | error
let errorMessage = ''
```

真实项目里通常合并成一个对象，避免"状态与数据对不上"（比如 `loading` 为 false 但列表还是空）。

### 渲染函数：只负责把状态画出来

```js
const listEl = document.querySelector('#list')
const stateEl = document.querySelector('#state')
const countEl = document.querySelector('#count')
const retryEl = document.querySelector('#retry')

function render() {
  const loading = status === 'loading'
  const failed = status === 'error'
  const empty = status === 'ready' && tasks.length === 0

  retryEl.hidden = !failed
  stateEl.hidden = !(loading || failed || empty)
  stateEl.textContent = loading ? '加载中…' : failed ? errorMessage : empty ? '还没有任务，先加一条。' : ''

  countEl.textContent = status === 'ready' ? `共 ${tasks.length} 条` : ''
  listEl.replaceChildren(
    ...tasks.map((task) => {
      const li = document.createElement('li')
      li.dataset.id = String(task.id)
      li.className = 'row'

      const text = document.createElement('span')
      text.textContent = task.title // 用户输入，绝不 innerHTML

      const remove = document.createElement('button')
      remove.type = 'button'
      remove.dataset.action = 'remove'
      remove.textContent = '删除'

      li.append(text, remove)
      return li
    }),
  )
}
```

三个细节：

1. `textContent` 而不是 `innerHTML`：标题来自用户，拼 HTML 就是 XSS；
2. `replaceChildren` 一次替换，比循环 `append` 少触发多次布局；
3. 渲染函数**不发起请求、不绑监听**，只读状态写 DOM——这一点是后面理解 React 的关键。

### 加载数据

```js
async function load() {
  status = 'loading'
  render()
  try {
    const res = await fetch('/api/tasks')
    if (!res.ok) throw new Error(`服务器返回 ${res.status}`)
    tasks = await res.json()
    status = 'ready'
  } catch (error) {
    status = 'error'
    errorMessage = error.name === 'AbortError' ? '请求已取消' : `加载失败：${error.message}`
  }
  render()
}
```

`AbortError` 单独判断：用户切页导致的取消不该显示成"加载失败"。

### 操作：删除走事件委托

```js
listEl.addEventListener('click', async (event) => {
  const button = event.target.closest('[data-action="remove"]')
  if (!button) return
  const id = button.closest('[data-id]').dataset.id
  button.disabled = true
  try {
    const res = await fetch(`/api/tasks/${id}`, { method: 'DELETE' })
    if (!res.ok) throw new Error(`删除失败（${res.status}）`)
    tasks = tasks.filter((task) => String(task.id) !== id)
    render()
  } catch (error) {
    button.disabled = false
    stateEl.hidden = false
    stateEl.textContent = error.message
  }
})

retryEl.addEventListener('click', load)
load()
```

删除是**本地状态与服务器同时变**的操作。先请求、成功后再改本地数组。这比"先删 UI 再请求、失败再撤"简单且不会出现"看起来删了其实没删"。

### 四条纪律，框架也会要求你

1. **单一数据源**：列表只从 `tasks` 渲染，不在 DOM 上另存一份；
2. **状态变化后重新渲染**：所有修改都走 `render()`，不手改某一个节点；
3. **渲染是纯的**：不请求、不绑事件、不读全局可变状态；
4. **用户输入永远当文本**：`textContent`、`setAttribute`，不拼 HTML。

这四条手写时靠自觉，框架里是强制的——这就是为什么同样的逻辑换成 React 后更难写错。

## 常见误区

### 误区：局部更新比整段重渲染快

**你以为**：只改一行 DOM 更省。
**其实**：手写局部更新最容易漏——删了一行忘了改计数、改了标题忘了改排序。整段重渲染只要几十个节点，代价可以忽略；一致性比微优化重要。
**怎么验证**：Performance 面板对比两种写法，几十行列表的差异在 1ms 级别。

### 误区：先把 UI 改了，请求失败再改回来

**你以为**：这样响应更快。
**其实**：失败回滚要处理"回滚时数据又被别人改了"的情况，复杂度高；而且用户看到的中间态是假的。删除、提交这类操作，**等服务端确认再改**更稳。
**怎么验证**：断网后点删除，看页面是否出现"删了又回来"的闪烁。

### 误区：`render()` 里调用 `load()` 很方便

**你以为**：渲染时顺便拉数据，少写一处调用。
**其实**：渲染会因为各种原因被调用（重试、状态变化），把请求放进去会重复发、造成循环。**渲染只读状态**，副作用放在事件或初始化里。
**怎么验证**：在 `render` 里打日志，数一次操作触发了几次请求。
