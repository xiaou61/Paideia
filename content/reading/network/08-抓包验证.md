## 这一篇只做一件事

前面七篇讲的都是别人告诉你的规则。这一篇把它们全部用一次：**你在自己的机器上抓一次真实的访问，按时间线把每一步对上号。**

做完之后，你对"一次请求经过了几步"这件事就不再是背下来的，而是亲眼数过的。

## 准备：三样工具

只用一个工具也能做完，但三样各有各的用处：

| 工具 | 能看什么 | 不需要装东西？ |
| --- | --- | --- |
| `curl -w` | 每一段花了多久（DNS、连接、TLS、首字节） | 是 |
| `dig` / `nslookup` | 解析结果、TTL、走的哪个解析器 | 是（多数系统自带） |
| `tcpdump` / Wireshark | 每一个包、每个标志位、每次重传 | `tcpdump` 可能需要装 |

**建议顺序**：先用 `curl` 拿到时间账，再用 `tcpdump` 对一下包。`curl` 告诉你"慢了 200 ms"，`tcpdump` 告诉你"慢在哪一个包上"。

## 第一步：把时间打成四段

```text
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' -o /dev/null -s https://example.com/
```

输出是五个累加时间，全是**从开始请求算起**的秒数，不是各段独立耗时。所以要看差值：

| 差值 | 对应什么 | 对应哪一篇 |
| --- | --- | --- |
| `dns` | 域名解析 | 03 |
| `connect - dns` | TCP 三次握手 | 04 |
| `tls - connect` | TLS 握手 | 01 |
| `first - tls` | 发请求到收到首字节（含服务端处理） | 06 |
| `total - first` | 下载正文 | 07 |

### 关键动作：跑两遍

第一遍是冷启动，第二遍连接已经建立。**两遍的数字差别，就是"连接复用"省下的东西。**

如果第二遍的 `dns` 还是很大，说明有东西没缓存住；如果 `tls` 还是很大，说明连接没被复用（可能是 `curl` 每次都是新进程，天然不复用——这是 `curl` 的特性，不是服务端的问题）。

想把复用也测出来，用同一次 `curl` 发两个请求：

```text
curl -w 'reuse=%{num_connects} connect=%{time_connect} total=%{time_total}\n' -o /dev/null -s https://example.com/ https://example.com/
```

`num_connects` 是"这次一共新建立了几条连接"。第二个请求如果复用了，这个数会小于请求数。

## 第二步：验证解析

```text
dig example.com A +noall +answer
```

你会看到类似：

```text
example.com.  3600  IN  A  93.184.216.34
```

三个信息：地址、记录类型、**TTL（那个 3600）**。

再过十秒查一次，TTL 会减少——这是缓存在倒计时。如果是每次都 3600 不变，说明每次都在问权威服务器，缓存没生效。

想确认走的是哪个解析器：

```text
dig example.com | grep -A2 "SERVER"
```

如果返回值和你 `hosts` 里写的不一样，先看 `hosts`。这类问题排查起来很快，但如果不看，往下查半小时也找不到。

## 第三步：抓包看握手

这一步需要能抓本机流量的权限。用 `tcpdump` 抓 TCP 握手（把地址换成你要测的）：

```text
tcpdump -n -i any 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0)' -c 20
```

参数解释：

- `-n`：不把地址和端口解析成名字（避免抓包时又触发 DNS，干扰观察）；
- `-i any`：所有网卡；
- 过滤条件只留 SYN / FIN / RST，把数据包滤掉；
- `-c 20`：抓 20 个就停。

然后另开一个窗口发一次请求。你会看到：

```text
.54321 > 443: Flags [S]      ← 客户端 SYN
443 > .54321: Flags [S.]     ← 服务端 SYN+ACK
.54321 > 443: Flags [.]      ← 客户端 ACK（第三次握手完成）
...
.54321 > 443: Flags [F.]     ← 主动关闭方发 FIN
443 > .54321: Flags [F.]     ← 对方回 ACK 再发 FIN
.54321 > 443: Flags [.]      ← 最后的 ACK，随后进入 TIME_WAIT
```

对照前两篇：三个 SYN/ACK 就是三次握手；两个 FIN 就是四次挥手（中间两个 ACK 被合并显示，所以看起来字段更少）；最后那条连接会在 `ss -tan` 里显示为 `TIME_WAIT` 六十秒。

## 第四步：对着抓包看四个数字

现在把 `curl` 的时间账和抓包的时间戳对起来：

1. 第一个 SYN 的时间戳 ≈ `curl` 的 `dns` 之后（解析完成后才开始连接）；
2. 第三个包（ACK）的时间戳 - 第一个 SYN 的时间戳 ≈ `connect - dns`，这就是握手的实际耗时；
3. 如果走 TLS，握手包在 TCP 之后还有一组，对应 `tls - connect`；
4. 第一个应用层数据包到对方第一个响应包之间 ≈ `first - tls`，这一段包含服务端处理。

如果某一段和预期严重不符，比如握手花了 300 ms 但 `ping` 只有 5 ms，那问题就在中间设备上（防火墙丢包、或者在排队），不在两端。

## 第五步：故意制造一次失败

前面的验证都是"成功路径"。真正考验理解的是失败路径：

### 试一个没开的端口

```text
curl -v --connect-timeout 3 http://example.com:9
```

端口 9 一般没有服务。你会看到 `Connection refused`。回到第 04 篇的表格——这证明包到了对方，对方回了 RST。

### 试一个不可达的地址

```text
curl -v --connect-timeout 3 http://10.255.255.1
```

这个地址在你的局域网里大概率不存在。你会看到 **超时**（不是 refused）。两者对比，就是"包到了"与"包没回来"的区别。

**这两个实验值得亲手做一次**，因为以后再遇到用户的模糊描述（"打不开""连不上"），你能用一句话把范围切开。

### 看 TIME_WAIT 的产生

发完请求后立刻看：

```text
ss -tan | grep -c TIME-WAIT
```

然后再发几次，再看。数字会增加——因为你（客户端）主动关闭了这些连接。等一分多钟再看，数字回落。这就是 2MSL 到期释放。

## 把整条链路画出来

做完上面五步，你应该能自己画出这样一张图，而且每个数字都是量出来的：

```text
时间 →
│
├─ [DNS]        解析：本机缓存/递归解析器/根/顶级域/权威
├─ [TCP]        SYN → SYN+ACK → ACK          1 个往返
├─ [TLS]        ClientHello → ... → Finished  1 个往返（TLS 1.3）
├─ [HTTP]       GET → 首字节                   1 个往返
├─ [下载]       正文传输（受带宽影响）
└─ [关闭]       FIN/ACK → FIN/ACK → TIME_WAIT 2MSL
```

这张图画出来之后，看到"某某网站慢"这类描述，脑子里会自动跳出六个可以逐段量化的位置。

## 常见误区

### 误区：curl 跑得快就说明服务端快

**你以为**：命令行测出来 20 ms，用户也应该 20 ms。
**其实**：你的机器可能同机房、可能连接已复用、可能 DNS 与 TLS 会话都命中缓存。用户的冷启动路径完全不同。
**怎么验证**：跑两遍对比冷热差异；再用不同网络环境（移动网络、跨地域）测一次。

### 误区：抓包里没看到 HTTP 就是没发请求

**你以为**：抓不到请求说明客户端没发。
**其实**：HTTPS 的正文是加密的，`tcpdump` 只能看到 TLS 记录，看不到 HTTP 内容。要看明文需要解密（导入会话密钥）或改用服务端日志。
**怎么验证**：抓包里能看到 TLS 握手与应用数据量，说明确实在通信，只是内容加密。

### 误区：TIME_WAIT 数字一直涨就是有 bug

**你以为**：这个计数不该增加。
**其实**：只要是客户端主动关闭短连接，它就会涨，这是协议的正常行为。要看的不是绝对值，而是有没有逼近端口上限。
**怎么验证**：对比 `net.ipv4.ip_local_port_range` 的范围与你当前的 TIME_WAIT 数量。

## 小结

这一篇把前七篇合成一次实测：用 `curl -w` 拿时间账、用 `dig` 验证解析与 TTL、用 `tcpdump` 看握手与挥手、再故意制造两种失败对比报错文本。做完之后，"一次请求经过几层、慢在哪一段"就从记忆变成了可测量的东西。

下一篇往上一层：HTTPS 与 TLS，看看加密到底发生在哪一层，以及证书报错该怎么查。读之前可以先挑一个你正在用的真实服务，把冷启动与热启动各量一遍，差值就是连接复用给你省下的时间。
