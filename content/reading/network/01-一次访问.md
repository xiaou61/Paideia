## 先看一段我自己跑出来的数字

这台机器上，对同一个网址连打三次 `curl -w`：

```text
$ curl -s -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer}\n' https://example.com
dns=0.060302 connect=0.261894 tls=0.918312 first_byte=1.079550

$ ...（立刻再跑一次）
dns=0.012466 connect=0.226935 tls=0.410919 first_byte=0.567887

$ ...（第三次）
dns=0.015054 connect=0.191415 tls=0.374807 first_byte=0.580216
```

三条命令访问的是同一个网址、同一份内容，但耗时差了将近一倍。而且第二次和第三次稳定在 0.57 秒左右，不再是 1.08 秒。

第一次多出来的那一段，我把它归到"这台机器还没热"：DNS 要真去查（60ms 对 12ms），TLS 那一跳 918ms 对 410ms。至于具体省掉的是哪一步——证书链拉取、路由预热，还是别的——我没有抓包确认，只能记成现象。

真正有用的是**后面两次的结构**：这台机器到 example.com 的往返（RTT）大约 180ms，而每一段耗时都刚好接近一个 180ms：

| 查这段差值 | 得到 | 大概几个往返 |
| --- | --- | --- |
| `dns` | 0.012 | 本机到解析器一次 |
| `connect - dns` | 0.215 | TCP 握手，1 个 |
| `tls - connect` | 0.184 | TLS 1.3 握手，1 个 |
| `first_byte - tls` | 0.189 | 发请求到首字节，1 个 |

四段，四跳，每跳一个往返。这就是本文要讲的东西：**首字节之前的等待是往返次数的加法，不是带宽的乘法。**

## 为什么是"往返"而不是"时间"

往返的意思是：你发出去，必须等对方回话，才轮到你说下一句。链路上就算空着，这一来一回也省不掉。

所以延迟高的时候，一条 10 KB 的小响应照样慢——它卡在等回话上，不在搬运量上。带宽决定"一次能搬多少"，往返决定"要等几轮"。这两个是完全不同的量。

## 第一段：把名字换成 IP

浏览器不会一上来就问网络，它按顺序找：

1. 浏览器进程自己的缓存；
2. 操作系统解析缓存、`hosts` 文件；
3. 配置里的递归解析器（运营商给的，或 8.8.8.8 / 223.5.5.5 这类公共 DNS）。

前两步命中就结束，零往返。都没命中，才真正出网。

递归解析器的缓存也空着时，它要逐级问：

- 问**根服务器**：`.com` 谁管 → 得到顶级域服务器地址；
- 问**顶级域服务器**：`example.com` 谁管 → 得到该域名的**权威服务器**地址；
- 问**权威服务器**：这个域名解析成什么 IP → 得到答案。

三次一问一答，加上你的机器到解析器的一次，**最坏情况四个往返**。日常很少走满：解析器缓存命中就只剩你到它的那一次。

顺带解释一个现象：改了域名解析，有人立刻生效、有人几小时后才生效。差别在各自链路上缓存的 TTL 还没到期，跟"网络快慢"无关。

## 第二段：建连接

TCP 用三次握手：

```text
客户端                        服务端
  |  ---- SYN, seq=x  -------->  |
  |  <--- SYN+ACK, seq=y, ack=x+1 |
  |  ---- ACK, ack=y+1 -------->  |
```

前两步构成一个往返——客户端必须等到 `SYN+ACK` 才知道对方收到了自己的 `SYN`。第三步可以顺手捎带业务数据。

**为什么不能只握手两次？** 常见的说法是"两次只证明了单向"，说反了一半。收到 `SYN+ACK` 之后，客户端已经能确认：服务端能收（我的 SYN 到了）、也能发（我收到了它的包）。缺的是反向——**服务端此刻还不知道自己那个 `SYN+ACK` 有没有到达客户端**。

这个"不知道"会带来实际问题：如果客户端没收到、超时重发，或者网络上飘着一个上一次连接留下的旧包，服务端就需要一个明确的信号来区分"这是新的连接请求"还是"这是老连接的残渣"。第三次 `ACK` 携带的对序号 `y+1` 的确认，就是那个信号：双方对彼此的初始序号达成一致之后，落在序号窗口之外的包才能被安全丢掉。

## 第三段：协商加密

HTTPS 是在传输层之上再叠一层 TLS，**注意这个"叠"字，它是 HTTP/2 及以前的前提**。

- **TLS 1.3** 首次握手 1 个往返。客户端在第一个包里就把密钥交换参数发出去，服务端算完直接回，一来一回就够。
- **TLS 1.2** 要 2 个往返。它得先协商用哪套算法，再交换密钥。
- 之前连过的话可以恢复会话：TLS 1.3 允许 **0-RTT**，第一个包里就带上应用数据。代价是这类早期数据有重放风险——攻击者可以把截下来的 0-RTT 数据重放一次，所以只该用在幂等的 `GET` 上，不要用在"下单""转账"这种请求上。

这一段解释了一件事：为什么"复用已有连接"的收益比"优化服务端计算"大得多。复用省掉的是两个完整往返（TCP+TLS），而那通常是几百毫秒；服务端省下的几十毫秒 CPU，在这个尺度上几乎看不见。

## 一个必须补的例外：HTTP/3 不是这个模型

上面"TCP 握手 + TLS 握手"两段的结构，在 HTTP/3 上不成立。

HTTP/3 跑在 **QUIC** 上，QUIC 是建在 UDP 之上的传输协议，**它自己就把传输握手和加密握手合并成了一次**，TLS 1.3 是内嵌在 QUIC 里的，不是叠在它上面的独立一层。

结果：

| | 冷启动建连 | 会话恢复 |
| --- | --- | --- |
| HTTP/1.1、HTTP/2（TCP + TLS 1.3） | 2 个往返 | 1 个（TCP）+ 0 个（TLS 恢复） |
| HTTP/3（QUIC） | **1 个往返** | **0 个往返**（0-RTT） |

这也是为什么在丢包严重、延迟高的链路上，HTTP/3 比 HTTP/2 快得更明显——它把两段合成一段，而且不用等 TCP 那种"一个包丢了后面全队等"的重传。

## 第四段：发请求，等响应

HTTP 请求就是一串字节：

```text
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

```

请求行 + 首部 + 一个空行；有正文时再接正文。服务端处理完，回状态行 + 首部 + 正文。这一来一回又是 1 个往返——**但注意，这 1 个往返里已经包含了服务端的处理时间**，实测时它减去 TLS 那一段，会同时体现"网络往返"和"服务端算多久"。

冷启动的总账（TLS 1.3 / HTTP/2）：

| 阶段 | 往返 |
| --- | --- |
| DNS（解析器缓存全空，最坏） | 最多 4 |
| TCP 握手 | 1 |
| TLS 1.3 握手 | 1 |
| 请求到首字节 | 1 |

按我上面测到的 180ms 算：最坏情况 7 × 180 ≈ 1.26 秒，全在等待上，一个字节的业务数据都还没开始传。同城 RTT 若是 5ms，同样 7 个往返只有 35ms——**决定这个总量的是 RTT，不是带宽**。CDN 之所以立竿见影，就是因为它同时压缩了 DNS 之后的每一跳 RTT。

## 服务端那一段，浏览器看不见

请求到达机房后，不一定直接进应用进程：

- 可能先到 CDN 或负载均衡，由它终止 TLS；
- 可能经过反向代理，做路由、限流、压缩；
- 最后才到应用服务器，应用再去查缓存或数据库。

这一段对客户端是不透明的，表现在你这边只有一件事：**首字节回来得慢**。所以判断"前端慢还是后端慢"要看 TTFB，别看总耗时——总耗时里还包含下载正文和渲染。

反过来，TTFB 慢也不能直接判给后端代码：里面还有代理排队、TLS 终止、以及服务端到上游的那一跳。要对半切，得在服务端内部再打一个"从收到请求到开始写响应"的时间，和前端的 TTFB 相减。

## 页面出现之后，这笔账再算一遍

HTML 回来只是开始。浏览器解析时发现 CSS、JS、图片，每个**不同域名**的资源都可能把上面四段重走一遍。域名不同、协议不同、连接池不共享时，这些往返是叠加的。

所以优化的顺序是：

1. **减少需要新连接的资源数量**——合并、内联关键 CSS、砍掉阻塞脚本；
2. **复用连接**——keep-alive、HTTP/2 多路复用、HTTP/3；
3. **缩短每段往返**——CDN、就近接入；
4. 最后才是压体积。

反过来先压体积，能省的只是"最后一跳之后的搬运时间"，前面那些往返一个都省不掉。

## 自己量一遍

```bash
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' -o /dev/null -s https://example.com
```

看差值，不要看累计值：

- `dns`：本机到解析器
- `connect - dns`：TCP 握手
- `tls - connect`：TLS 握手
- `first_byte - tls`：服务端处理 + 一个往返
- `total - first_byte`：正文传输

哪一段异常，就去查那一层。多跑几次再下结论——第一次通常包含缓存未命中和路径预热，单次结果说明不了问题。

## 一句话

首字节之前的等待，是**往返次数的加法**：DNS 最坏 4、TCP 1、TLS 1（HTTP/3 上这两段合成 1）、请求 1。带宽只影响"跳完之后搬多快"，改不了这几次等待——所以优化要砍往返，不是砍体积。
