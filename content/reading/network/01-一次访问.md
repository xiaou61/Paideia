## 先把结论摆出来

在浏览器地址栏敲下域名、按下回车，到页面第一个字节出现，最少要经过四段彼此独立的等待：

1. 把名字换成 IP 地址；
2. 建立一条到服务器的可靠连接；
3. 协商加密（如果走 HTTPS）；
4. 发出请求并等第一个字节回来。

每一段都是一次或多次**往返**（round trip，缩写 RTT）。往返的意思是：你发出去，必须等对方回话，你才能继续。它和带宽没有关系——链路上哪怕空着，这一来一回的时间也省不掉。

记住这个数：**完全冷启动时，首字节之前大约 6 到 7 个往返；连接被复用时可以降到 1 到 3 个。** 后面每一节都在解释这几个数是怎么来的。

## 第一段：把名字换成地址

人记名字，机器认地址。这一步由 DNS 完成。

浏览器不会一上来就问网络。它按这个顺序找：

1. 自己进程内的缓存；
2. 操作系统的解析缓存，以及 hosts 文件这类本地配置；
3. 配置里的**递归解析器**（可能是运营商给的，也可能是公共 DNS）。

前两步命中就结束，一个往返都不用花。没命中才真正上网查。递归解析器如果也没有缓存，就要挨个问：

- 问**根服务器**："`.com` 谁管？" 得到顶级域服务器的地址；
- 问**顶级域服务器**："`example.com` 谁管？" 得到这个域名自己的**权威服务器**地址；
- 问**权威服务器**："这个域名对应的 IP 是多少？" 得到最终答案。

三次一问一答，就是三个往返，再加上你的机器到解析器的那一次。**所以冷启动时，光解析域名就可能花掉四个往返。** 答案会按记录上的 TTL 缓存起来，TTL 内再访问就直接命中，这一段归零。

顺带解释一个常见现象：改了域名解析，有人立刻生效、有人几小时后才生效。差别不在"网络快慢"，而在各自链路上缓存的 TTL 还没到期。

## 第二段：建立连接

拿到 IP 之后，TCP 要用三次握手确认双方都能收发：

1. 客户端发 `SYN`，带上自己的初始序号；
2. 服务端回 `SYN + ACK`，带上自己的初始序号、并确认客户端的；
3. 客户端回 `ACK`。

前两步占掉**一个往返**。第三步可以顺手带上业务数据，但在此之前不能发——因为连接还没被双方确认。

为什么不是两次？两次只能证明"客户端能发、服务端能收"，证明不了反向。第三次 ACK 让服务端确认"我发的包你能收到"，同时也让客户端确认"我的初始序号你收到了"。少这一次，历史上出现过的旧连接残留包就可能被当成新连接的数据，造成错乱。

## 第三段：协商加密

HTTPS 在 TCP 之上再加一层 TLS。

- **TLS 1.3 首次握手占一个往返**；
- TLS 1.2 要两个；
- 之前连过的会话可以恢复，TLS 1.3 允许 0-RTT 直接带数据，代价是这类早期数据有重放风险，所以只适合幂等请求。

这一段常被忽略，但它解释了一件事：为什么"复用已有连接"的收益远大于"优化服务端计算"。省掉的是整个往返，而不只是几十毫秒的 CPU。

## 第四段：发请求，等响应

HTTP 请求本身就是一串字节：

```
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

```

请求行 + 首部 + 一个空行；有正文时再跟正文。服务端处理完，回状态行 + 首部 + 正文。

首次请求到首字节，又是一个往返。到这里，冷启动的总账大致是：

| 阶段 | 往返 |
| --- | --- |
| DNS（无缓存，含到解析器） | 最多 4 |
| TCP 握手 | 1 |
| TLS 1.3 握手 | 1 |
| HTTP 请求到首字节 | 1 |

同城链路 5 ms 往返，冷启动约 35 ms；跨洲 150 ms，就是 1 秒左右。**这也是为什么 CDN 把静态资源放到离用户近的地方，效果那么直接：它同时缩短了 DNS 之后的每一段往返。**

## 服务端那一段，浏览器看不见

请求到达机房后，通常不会直接进应用进程：

- 可能先到 CDN 或负载均衡，由它终止 TLS；
- 可能经过反向代理，做路由、限流、压缩；
- 最后才到应用服务器，应用再去查缓存或数据库。

这一段对客户端是**不透明**的：表现在你这边，只是"首字节回来得慢"。所以判断"前端慢还是后端慢"，看首字节时间（TTFB）而不是总耗时——总耗时里还包含下载正文和渲染。

## 页面出现之后，同样的账再算一遍

HTML 回来只是开始。浏览器解析时发现 CSS、JS、图片，每一个不同域名的资源都可能重新走一遍上面的流程。域名不同、协议不同、连接池不共享时，这些往返是**叠加**的。

所以真正的优化顺序是：

1. 减少需要新连接的资源数量（合并、内联关键资源）；
2. 复用连接（keep-alive、HTTP/2 多路复用、HTTP/3）；
3. 缩短每段往返（CDN、就近接入）；
4. 最后才是压缩体积。

反过来做——先压缩体积——往往只能省下带宽，省不掉等待。

## 自己量一遍

`curl` 能把这几段时间分别打出来：

```text
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' -o /dev/null -s https://example.com
```

看四个差值：`connect - dns` 是 TCP 握手，`appconnect - connect` 是 TLS，`first_byte - appconnect` 是服务端处理加一个往返。哪一段异常，就去查那一层。

## 常见误区

### 误区：往返次数只影响"第一次"，之后都很快

**你以为**：连上以后就不用再等了。
**其实**：每个请求仍然要等一个往返才能拿到首字节。请求越多、串行依赖越多，累加越明显。
**怎么验证**：连续发 10 个串行请求，观察总耗时是否约等于 10 个往返。

### 误区：带宽够大就不会慢

**你以为**：升级带宽能解决所有慢的问题。
**其实**：带宽决定"一次能搬多少"，往返决定"每次要等多久"。小响应在长链路上就是慢，与带宽无关。
**怎么验证**：在 200 ms 延迟下传输一个 10 KB 的响应，看耗时是否接近一个往返而不是接近零。

### 误区：TTFB 慢一定是后端代码慢

**你以为**：首字节慢就是接口逻辑重。
**其实**：TTFB 里还包含服务端链路上的往返、代理排队、以及 TLS 终止的开销。
**怎么验证**：在服务端内部另打一个从收到请求到开始写响应的耗时，与 TTFB 相减。

## 小结

一次访问可以拆成四段等待：解析、连接、加密、请求。冷启动 6 到 7 个往返，复用连接后降到 1 到 3 个。下一篇把这条链路按层拆开，讲清每一层各自解决什么问题，以及为什么分层能让排查变简单。
