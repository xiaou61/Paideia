## 一段字节，四块内容

一个 HTTP 请求在网络里就是一串纯文本（HTTP/1.x），分四块：

```sketch
{
  "title": "一个 HTTP 报文就是四块文本",
  "rows": [
    [
      { "id": "line", "title": "起始行", "sub": "方法 路径 版本", "tone": "gray" },
      { "id": "head", "title": "头部", "sub": "一行一个键值对", "tone": "blue" },
      { "id": "blank", "title": "一个空行", "sub": "告诉对方头部结束", "tone": "violet" },
      { "id": "body", "title": "正文", "sub": "可以有，也可以没有", "tone": "green" }
    ]
  ],
  "arrows": []
}
```

```text
GET /api/user?id=7 HTTP/1.1        ← 请求行
Host: example.com                   ← 首部
Accept: application/json
                                    ← 空行（这一行必须存在）
                                    ← 正文（GET 通常没有）
```

响应同理：

```text
HTTP/1.1 200 OK                     ← 状态行
Content-Type: application/json      
Content-Length: 27
                                    
{"id":7,"name":"张三"}
```

就这些。没有魔数、没有二进制结构，**你可以用 telnet 手工敲一个请求出来**。理解这一点，后面所有"响应慢""乱码""跨域"的问题都能落到具体是哪一块出了岔子。

## 请求行：方法、目标、版本

**方法**表示"想干什么"：

| 方法 | 语义 | 幂等 |
| --- | --- | --- |
| `GET` | 取资源 | 是 |
| `POST` | 提交，通常会产生新资源 | 否 |
| `PUT` | 整体替换 | 是 |
| `PATCH` | 部分修改 | 通常不保证 |
| `DELETE` | 删除 | 是 |
| `HEAD` | 只要首部，不要正文 | 是 |
| `OPTIONS` | 问支持哪些方法（跨域预检用） | 是 |

"幂等"的实际含义是：**重复调用结果一样**。为什么重要？因为网络会重试——网关超时重发、用户刷新、客户端自动重试。`GET` 重发一百次也不会改数据；`POST` 重发一次可能就多下了一单。

注意 `HEAD` 常被忽略但很有用：它返回的首部和 `GET` 一样，只是不带正文。想知道一个文件有多大、有没有变、是什么类型，不需要把它整个下下来。

**目标**部分在 HTTP/1.1 的请求行里通常只有路径和查询串（`/api/user?id=7`），主机名放在 `Host` 首部里。HTTP/1.0 时代是完整 URL，这个差别常让人看抓包时困惑。

**版本号**决定了很多行为差异：1.0 默认不支持持久连接、1.1 默认支持、2 改成了二进制帧。看清版本再谈"为什么每次都要新建连接"。

## 首部：元数据，不是内容

首部分四类，分类清楚了就不容易记混：

### 1. 描述正文

| 首部 | 作用 |
| --- | --- |
| `Content-Type` | 正文是什么格式。`application/json; charset=utf-8` |
| `Content-Length` | 正文字节数 |
| `Content-Encoding` | 正文是否压缩过。`gzip`、`br` |
| `Transfer-Encoding: chunked` | 正文长度不定，分块传（此时不能有 `Content-Length`） |

`Content-Type` 和 `Content-Encoding` 是**两回事**，经常被混：前者说"这是 JSON"，后者说"这些字节被 gzip 压过"。少了后者，客户端会把压缩后的字节当 JSON 解析，得到乱码。

**`charset` 不是可选的**。不带 charset 时，浏览器对 `text/*` 有自己的猜测规则，中文很容易变成乱码。这也是为什么老接口偶发乱码、换个浏览器就正常。

### 2. 协商与缓存

| 首部 | 作用 |
| --- | --- |
| `Cache-Control` | 缓存能活多久、能不能存。`max-age=3600`、`no-store` |
| `ETag` / `If-None-Match` | 内容指纹。客户端带上它，服务端可以直接回 304 |
| `Last-Modified` / `If-Modified-Since` | 按时间判断有没有变 |
| `Vary` | 缓存时还要看哪个首部（比如 `Accept-Encoding`） |

304 相比 200 省的是**正文**，不是往返。如果目的是省往返，用它没用。

### 3. 认证与会话

| 首部 | 作用 |
| --- | --- |
| `Authorization: Bearer xxx` | 令牌 |
| `Cookie` / `Set-Cookie` | 浏览器会话 |
| `WWW-Authenticate` | 服务端要求认证时告诉客户端用哪种方式 |

这条链路有个经典坑：**登录接口返回的 `Set-Cookie` 如果带了 `Secure`，而你在 http 下访问，浏览器就直接不存了**，后续请求全都没有凭证。表现是"登录成功但马上又变成未登录"。

### 4. 跨域与安全

| 首部 | 作用 |
| --- | --- |
| `Origin` | 请求来自哪个源 |
| `Access-Control-Allow-Origin` | 服务端允许哪个源读响应 |
| `Access-Control-Allow-Credentials` | 是否允许带 Cookie |
| `Content-Security-Policy` | 限制页面能加载什么 |
| `Strict-Transport-Security` | 强制后续走 HTTPS |

跨域这件事值得多说一句：**请求其实发出去了、服务端也处理了**，是浏览器不让页面读到响应。所以"跨域报错"不等于"请求失败"——副作用可能已经发生。写"删除"这类操作时这尤其危险。

## 状态码：五组，各自含义

| 组 | 含义 | 常见 |
| --- | --- | --- |
| 1xx | 还在处理 | `100 Continue`、`101 Switching Protocols` |
| 2xx | 成功 | `200 OK`、`201 Created`、`204 No Content` |
| 3xx | 需要额外动作 | `301` 永久重定向、`302` 临时、`304` 没变、`307`/`308` 保方法重定向 |
| 4xx | 客户端的问题 | `400` 参数错、`401` 未认证、`403` 无权限、`404` 不存在、`429` 限流 |
| 5xx | 服务端的问题 | `500` 内部错误、`502` 上游返回无效、`503` 不可用、`504` 上游超时 |

几个容易搞混的：

- **`401` 与 `403`**：401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能"。前者应该引导登录，后者不该。
- **`301` 与 `302`**：301 会被浏览器永久缓存，改回来很麻烦（要清缓存）。不确定时用 302。
- **`307` 与 `302`**：都临时，但 307 保证重定向后**方法不变**。用 302 时，浏览器历史上会把 POST 改成 GET——如果你在做表单提交，这会丢数据。
- **`502` 与 `504`**：502 是上游回了不合法的东西，504 是上游超时没回。前者多数是上游崩了，后者多数是上游慢了。

## 正文：为什么要区分"长度确定"和"分块"

如果响应有 `Content-Length`，客户端就知道要读多少字节，读满就结束。

但有些响应是**边生成边发**的：服务端不知道总长度，比如导出大文件、或者流式输出。这时用 `Transfer-Encoding: chunked`：每块前面写着这一块多长，最后用一个 0 长度的块表示结束。

这条规则有个必要的原因：**TCP 是字节流，没有消息边界**。一个 HTTP 响应发完，连接可能还开着等下一条请求。如果客户端不知道正文到哪里结束，它就无法判断下一条响应从哪里开始。所以"长度确定"这件事是必须的——要么给总长度，要么给分块，要么直接关连接（HTTP/1.0 的老办法）。

## 自己敲一个请求

最简单的验证方式，是绕过所有框架直接说协议：

```text
curl -i https://example.com/
```

`-i` 会把响应首部一起打出来。你能看到状态行、每一个首部、空行、然后是正文。再配合 `-v` 能看到请求侧的报文。

如果想看"服务端到底允不允许某方法"，发一个预检：

```text
curl -i -X OPTIONS -H "Origin: http://localhost" -H "Access-Control-Request-Method: POST" https://example.com/api
```

看返回的 `Access-Control-Allow-*` 首部，就知道跨域配置是否到位。

## 常见误区

### 误区：跨域请求失败了，说明服务端没收到

**你以为**：浏览器报 CORS 错误，所以请求没发出去。
**其实**：请求发出去了、服务端也处理了，只是浏览器不让页面读响应。副作用（比如删数据）已经发生。
**怎么验证**：在服务端加日志，或用 `curl` 直接发同一个请求（`curl` 不受同源策略限制）。

### 误区：接口慢就是后端代码慢

**你以为**：响应慢等于接口逻辑重。
**其实**：可能慢在首部之外——大正文下载、gzip 解压、甚至客户端渲染。用 `curl -w` 把首字节和总时长分开看。
**怎么验证**：对比 `time_starttransfer`（首字节）与 `time_total`（含正文下载）。

### 误区：用 301 做跳转无所谓，反正浏览器会跟

**你以为**：301 和 302 差不多。
**其实**：301 会被浏览器和中间缓存长期记住，改回来用户可能还跳到旧地址。
**怎么验证**：配一次 301，再改配置，用另一个浏览器或清缓存对比行为差异。

## 小结

HTTP/1.x 报文是四块纯文本：起始行、首部、空行、正文。首部分描述正文、协商缓存、认证、跨域四类。状态码按 1–5 分组，401/403、302/307、502/504 三对最容易混。正文长度必须能被客户端确定，否则无法划分消息边界。
