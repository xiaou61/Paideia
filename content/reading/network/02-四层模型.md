## 先记住一张表

网络分层不是学术分类，是**排查工具**。它的用处只有一句话：**出了问题，先定位在哪一层，再问是什么原因。**

| 层 | 它只回答一个问题 | 地址是什么 | 你平常在哪里碰到 |
| --- | --- | --- | --- |
| 应用层 | 双方用什么"语言"说话 | 域名、URL、路径 | HTTP、DNS、WebSocket |
| 传输层 | 数据要送到这台机器的**哪个程序** | 端口 | TCP、UDP、QUIC |
| 网络层 | 数据怎么从一台主机到**另一台主机** | IP 地址 | ping、路由、网关 |
| 网络接口层 | 数据怎么在**本地这一段线路**上发出去 | MAC 地址 | 网卡、ARP、Wi-Fi |

每一层只认得自己那一层的地址，别的层的东西对它来说都是"一段要搬运的字节"。这个设计叫**封装**。

## 封装：信封套信封

寄一份文件可以这么想：

1. 你在纸上写内容——**应用层数据**；
2. 装进信封，写上收件人所在的公司和部门——**传输层加上端口**；
3. 再套一个大信封，写上收件人的公司地址——**网络层加上 IP**；
4. 最后贴上这张纸怎么送到当地邮局的运输标签——**链路层加上 MAC**。

收件方拆的顺序反过来：看运输标签、看地址、看部门、最后才看到内容。每拆一层，就有一层的信息被用掉、被丢掉，不会再传给上一层。

这就是为什么抓包时你能看到完整的四层结构：抓包工具在链路层就把整份数据截下来了，所以四层的头都在。

## 每层各自管什么、不管什么

### 应用层：只管"说什么"，不管"怎么送到"

HTTP 规定请求长什么样、状态码是什么意思、首部有哪些字段。它**不关心**这条消息是走光纤还是走 Wi-Fi，也不关心中途有没有丢包——那是下面三层的事。

所以你能用同一个 HTTP 跑在 TCP 上、也能跑在 QUIC 上，甚至能拿纸笔抄下来人工传递。协议本身不依赖运输方式。

DNS 也在这一层。它的工作是"名字换成地址"，但它自己也是一个应用层协议，跑在 UDP 或 TCP 之上——**查地址这件事本身也要用网络**，这听起来循环，实际上靠的是你配置里的解析器地址（那个是直接给的 IP）。

### 传输层：只管"送到哪个程序"

一台机器上同时跑着浏览器、聊天软件、数据库。IP 地址只能把包送到这台机器，**送不到具体的程序**。端口就是用来区分程序的：一个 16 位的数字，0 到 65535。

传输层还负责一些"可靠性"的事，但取决于用哪个协议：

| | TCP | UDP |
| --- | --- | --- |
| 连接 | 先握手，有状态 | 无连接，发了就走 |
| 可靠 | 丢包重传、按序交付 | 不保证，可能丢、可能乱序 |
| 用途 | 网页、数据库、SSH | DNS 查询、音视频、游戏、QUIC 底层 |

TCP 为了"可靠"，付出的代价是：要握手、要记状态、丢包了要等重传。UDP 什么都不保证，代价是要可靠性就得自己在应用层做——QUIC 就是这么干的。

### 网络层：只管"从这台主机到那台主机"

IP 地址是逻辑地址，由网络分配，可以变。路由器看的是 IP 头里的目的地址，查表决定下一跳往哪发。

网络层**不保证送达**，也不保证顺序。它的哲学是"尽力而为"（best effort）：能送就送，送不到就丢，丢了由上面那层自己看着办。这样路由器才能做得简单快速——它不需要为每个包保留状态，也不需要等确认。

网络层还有一件容易被忽略的事：**分片**。链路层一般最多一次搬 1500 字节（这个上限叫 MTU），IP 包太大就要切成几块，到对面再拼回来。切开的每一块单独路由，丢一块整包就废了。

### 网络接口层：只管"这一段线路上怎么发"

这一层管的是相邻两个设备之间：你的机器到路由器、路由器到路由器。地址是 MAC 地址，硬件出厂就定了。

以太网、Wi-Fi、手机网络都在这一层。它们的具体格式完全不同，但对上面三层来说都是"能发一串字节的通道"。

ARP 也在这一层附近工作：知道对方的 IP，问"这个 IP 的 MAC 是多少"，然后在本地广播。所以同网段的通信其实**不看 IP**，看的是 MAC。

## 分层带来的两个直接好处

### 好处一：可以单独替换

光纤换成 Wi-Fi，IP 层不用改；IPv4 换成 IPv6，HTTP 不用改；TCP 换成 QUIC，HTTP 的语义不变。每一层只跟自己上下相邻的层打交道。

### 好处二：排查有明确的切分点

出问题时按层往下或往上查，每一层都有自己的工具：

| 层 | 工具 | 你能确认的事 |
| --- | --- | --- |
| 应用层 | `curl -v`、浏览器开发者工具 | 请求发出去了吗？状态码是什么？ |
| 传输层 | `ss -tan`、`telnet host port` | 端口通不通？连接处于什么状态？ |
| 网络层 | `ping`、`traceroute` | 目标主机可达吗？在哪一跳断的？ |
| 链路层 | `arp -a`、`ip link` | 本地这一段通不通？ |

排查顺序通常是**从下往上**：先确认能到达目标主机（ping），再确认能连上端口（telnet 或 curl 只连不请求），最后才看应用层返回什么。

反过来——直接看应用层报错信息——经常会被误导。比如"连接超时"这四个字，可能是 DNS 解析慢、可能是 TCP 握手包被防火墙丢、也可能是服务端 accept 队列满了，报错文本一样。

## 一个具体例子：同一句话，四层各看什么

假设你请求 `https://example.com/api/user`，超时了。

- **应用层**：域名拼错了？路径错了？服务端返回 5xx？
- **传输层**：443 端口通吗？`telnet example.com 443` 能不能连上？
- **网络层**：`ping example.com` 通吗？`traceroute` 走到哪一跳没了？
- **链路层**：本机网卡起来了？ARP 表里有网关的 MAC？

四层都过一遍，通常三分钟内能确定范围。只盯着"超时"这个现象本身，可能查一小时。

## 常见误区

### 误区：分层是"数据一层层变多"，只有发的时候才加

**你以为**：四层是四份数据依次叠起来，总大小翻四倍。
**其实**：每层只加一个很薄的头（IP 头 20 字节、TCP 头 20 字节），主要内容还是原来那份。加的是"寄件信息"，不是复制内容。
**怎么验证**：`curl -v` 看响应头里的 `Content-Length`，再用抓包工具看整个 IP 包大小，差的就是各层头加上 TLS 的开销。

### 误区：ping 通了就说明服务没问题

**你以为**：`ping` 通就是网络好的证明。
**其实**：`ping` 只证明网络层可达，也就是对方的机器在、路由通。端口没开、进程没起、应用报错，`ping` 全都看不出来。
**怎么验证**：找一个没开 80 端口的机器，`ping` 会通，`curl` 会拒绝连接——两者都是"网络正常"。

### 误区：抓包抓到的是"网络层的东西"

**你以为**：Wireshark 里看到的就是 IP 包。
**其实**：抓包是在网卡上抓的，链路层的帧也在，所以你既能看到 MAC，也能看到 HTTP 明文。选中某一层只是工具在帮你过滤和解析。
**怎么验证**：抓一次 HTTP 请求，展开以太网帧 → IP → TCP → HTTP 四层，逐层看那些头。

## 小结

四层各解决一个问题：应用层定语言、传输层定程序、网络层定主机、链路层定线路。每一层只认自己的地址，别的都当载荷。分层最实用的地方不是理论，是排查时能一处一处缩小范围。
