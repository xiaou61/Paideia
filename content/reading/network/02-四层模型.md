## 三个结果，先判断哪一层可以排除

屏幕上只剩一行：

```text
ERR_CONNECTION_TIMED_OUT
```

接着跑三条：

```text
> ping example.com
Pinging example.com [172.66.147.243] with 32 bytes of data:
Reply from 172.66.147.243: bytes=32 time=171ms TTL=48
Reply from 172.66.147.243: bytes=32 time=152ms TTL=48
Reply from 172.66.147.243: bytes=32 time=162ms TTL=48
Reply from 172.66.147.243: bytes=32 time=136ms TTL=48

Ping statistics for 172.66.147.243:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
Approximate round trip times in milli-seconds:
    Minimum = 136ms, Maximum = 171ms, Average = 155ms

> curl.exe -v https://example.com
*   Trying 172.66.147.243:443...
（停在这里，没有 Connected，也没有 TLS 握手）

> Test-NetConnection example.com -Port 443
ComputerName     : example.com
RemoteAddress    : 172.66.147.243
RemotePort       : 443
TcpTestSucceeded : False
```

`ping` 这段是我本机的真实输出；`curl` 和 `Test-NetConnection` 的失败形态是现场还原，后面会用三个可复现的地址分别跑。最后一条只留了关键字段，是 Windows PowerShell 5.1 的形态；PowerShell 7.6 在这里打印的是 `Connected : False` 的表格，字段名不同，结论一样。域名解析出的 IP、往返时间都会随网络变。

先把这三个结果翻译一下：

- `ping` 有 4 个回包，说明域名已经解析成了 `172.66.147.243`，而且 ICMP 到这个地址有去有回。应用层的 DNS、网络层的「到这台主机」先划掉。
- `curl` 停在 `Trying ...:443`，没有出现 `Connected`：TCP 连接没建起来，传输层的 443 这一关没过。
- `Test-NetConnection` 的 `False` 和上一条一致：不是 HTTP 返回了错误，而是根本没走到 HTTP。

剩下的可能是 443 没有进程在听、防火墙把 SYN 丢了、中间设备拦了 443，或者服务端 accept 队列满了。**这三条命令只能证明 ICMP 这条路通，不能证明服务没问题。**

网络分层不是学术分类，是排查工具：先把已经排除的层划掉，再决定下一条命令查哪一层。

| 层 | 主要职责 | 这一层的地址/标识 | 常见协议与工具 |
| --- | --- | --- | --- |
| 应用层 | 双方用什么语言说话：请求、响应、状态码、记录类型 | 域名、URL、路径、方法 | HTTP、DNS、WebSocket、SMTP；`curl.exe -v`、`nslookup` |
| 传输层 | 把字节送到哪个进程；可靠性、顺序、拥塞控制由具体协议决定 | 端口（16 位） | TCP、UDP、QUIC；`Test-NetConnection -Port`、`netstat -ano` |
| 网络层 | 从一台主机到另一台主机，按目的 IP 选路 | IP 地址 | IP、ICMP、路由；`ping`、`tracert` |
| 网络接口层 | 在相邻设备之间搬帧，管本地这一段 | MAC/链路层地址（随技术而异） | 以太网、Wi-Fi、PPP、ARP；`arp -a` |

四层模型给每层一个主要职责；它不规定每层只能有一个机制。可靠性归传输层的 TCP/QUIC，分片归网络层的 IP，ARP 是网络层和链路层之间的解析辅助——这些都是某一层主要职责之外的附带机制，不需要另开一层。这一层在不同教材里也叫链路层；OSI 七层把它的数据链路和物理部分拆开。

## 信封套信封，但 MAC 只是下一站

寄一份文件可以这么想：

1. 你在纸上写内容——**应用层数据**；
2. 装进信封，写上部门和房间号——**传输层加端口**，决定哪个程序收；
3. 再套一个大信封，写最终地址——**网络层加 IP**，决定哪台主机收；
4. 交给快递员时，外面再贴一张「到下一个中转站」的标签——**链路层加 MAC**，只决定下一跳交给谁。

第四步最容易讲错。MAC 不是「收件人的终点标签」，它是「下一站的标签」。你的机器要把包发给网关时，帧的目的 MAC 是网关的 MAC；IP 头里的目的地址仍然是最终服务器。到了网关，网关拆掉这张标签，按 IP 再查下一跳，重新贴一张新的 MAC 标签。每一跳都换 MAC，IP 目的地不变（NAT 会改 IP/端口，第 10 篇再说）。

发出去时，包大概长这样：

```text
[以太网头 | IP 头 | TCP 头 | HTTP 数据 | 以太网尾]
```

抓包工具在网卡上抓的就是这一整帧，所以你能在同一份捕获里看到四层。到了收件方，拆的顺序反过来：链路层看 MAC，网络层看 IP，传输层看端口，应用层读 HTTP。**每层拆掉的是自己那一层的信封，里面的信还在**；端口和 IP 不是「用完就丢」，而是被对应层读走之后，剩下的载荷继续往上交。

路由器上只有链路层的帧头/帧尾会被换掉，IP 头继续往前（TTL 减一，必要时分片）。所以「端到端由 IP 负责、逐跳由 MAC 负责」要分开看：IP 选的是最终目的地，MAC 选的是下一跳。

顺带纠正一个常见的验证方法：不要拿 `Content-Length` 去减总包大小，说差值是各层头加 TLS。`Content-Length` 只描述响应正文长度；分块传输时根本没有这个头。我在本机跑：

```text
> curl.exe -sS -o NUL -w "size_request=%{size_request} size_header=%{size_header} size_download=%{size_download}`n" https://example.com/
size_request=74 size_header=344 size_download=577
```

同一份响应头里是 `Transfer-Encoding: chunked`，没有 `Content-Length`。要算各层头，得看抓包里的帧长度，不是看这个字段。

## 四层各自的主要职责

### 应用层：双方说什么

HTTP 规定请求行、首部、状态码、正文的格式。它不关心底层是光纤、Wi-Fi 还是丢包的链路；同一套 HTTP 语义可以跑在 TCP 上，也可以跑在 QUIC 上。HTTP/1.1 和 HTTP/2 跑 TCP（HTTP/2 也有 h2c 明文变体，但浏览器走的是 TLS over TCP），HTTP/3 跑 QUIC（QUIC 自己跑在 UDP 上）。所以「网页 = TCP」只对前两个成立，HTTP/3 是例外。

DNS 也在这一层。它的任务是把名字换成地址，但自己也是一个协议：主查询默认走 UDP 53，响应太大或做区域传送时走 TCP 53；DoH 是把 DNS 查询包在 HTTPS 里，DoT 是包在 TLS 里，底层又回到 TCP（DoH 也可以走 HTTP/3）。所以「DNS = UDP」只描述了默认的那条路径。

传统 TLS 跑在 TCP 之上，给 HTTP/1.1、HTTP/2 提供加密；HTTP/3 的 TLS 1.3 握手在 QUIC 里完成，不再单独跑一层 TLS。抓 HTTPS（HTTP/1.1、HTTP/2）时你看到的是 TLS 记录，不是 HTTP 明文。TLS 的细节在第 09 篇。

### 传输层：送到哪个程序

一台机器上同时跑浏览器、聊天软件、数据库。IP 只能把包送到这台机器，送不到具体进程；端口就是进程的门牌号，16 位，0–65535。

端口之上，可靠性不是「传输层」这个层名自带的，而是协议给的：

| | TCP | UDP | QUIC |
| --- | --- | --- | --- |
| 连接 | 三次握手，维护状态 | 无连接 | 握手，TLS 1.3 内嵌 |
| 可靠/有序 | 丢包重传、按序交付 | 不保证；可能丢、可能乱序 | 按流可靠、有序 |
| 拥塞控制 | 有 | 没有 | 有 |
| 典型用途 | HTTP/1.1、HTTP/2、数据库（MySQL/PostgreSQL）、SSH | DNS 主查询、音视频、游戏、QUIC 的底层 | HTTP/3 |

TCP 的「可靠」只到字节流：它保证发出去的字节按序到达（或连接报错），不保证对方应用处理成功，也不保留你写入的消息边界。

UDP 不是「什么都不保证」。它有端口，能把数据交给正确的进程；有长度和校验和（IPv4 里校验和可选，IPv6 里必选），能发现一部分损坏。它不提供的是连接、重传、排序和拥塞控制——这些要么由应用自己补，要么换 TCP/QUIC。

QUIC 值得单独说一句：它跑在 UDP 之上，但它是**传输层协议**，不是应用层协议。可靠性、按流排序、拥塞控制、TLS 1.3 都在 QUIC 里实现，只是实现位置在用户态而不是内核。HTTP/3 才是使用 QUIC 的应用层协议。把 QUIC 说成「在应用层做可靠性」的例子，会把层号讲反。

### 网络层：从这台主机到那台主机

IP 是逻辑地址，由网络分配，可以变。路由器看 IP 头里的目的地址，查路由表决定下一跳。它不保证送达，也不保证顺序；拥塞时排队、满了就丢，可靠性交给 TCP/QUIC 或应用自己。`ping` 用的 ICMP 也在这层，但它是辅助协议：ICMP 有回包，不代表 TCP 端口开着。

网络层的主要职责是选路和转发。分片是它的附带机制：

- IPv4 头最小 20 字节，带选项最多 60 字节；IPv6 固定头 40 字节，扩展头另算。
- 以太网标准 MTU 是 1500 字节；PPPoE 是 1492（1500 减 8 字节 PPPoE 头），VPN/隧道更低，局域网巨帧可以到 9000。路径上最小的那个 MTU 才作数。
- IPv4 路由器在 DF=0 时可以分片；IPv6 路由器不分片，由源端做路径 MTU 发现（PMTUD）。如果 ICMPv6 的「Packet Too Big」被防火墙挡住，就会出现「小包能通、大包卡死」的 PMTUD 黑洞。

### 网络接口层：本地这一段怎么发

这一层管相邻两个设备之间：你的机器到路由器、路由器到下一台路由器。它把网络层交下来的包封装成帧，在本地链路上发出去，接收方按帧头里的链路层地址决定要不要收。

链路层地址不永远是「MAC，出厂就定」：

- 以太网和 Wi-Fi 常用 48 位 MAC；Wi-Fi 默认可能对每个网络随机化 MAC，虚拟网卡也可以改 MAC。
- PPP 是点对点链路，没有 MAC 这个概念，靠协议字段和会话标识。
- 蜂窝网络没有以太网 MAC，链路由蜂窝协议自己的标识（如 RNTI/TMSI）区分。
- 隧道用 VXLAN VNI、GRE key 之类的隧道标识；IPv6 不用 ARP，用邻居发现（NDP）。

所以更准确的说法是：**链路层地址随技术而异，也不永远等于出厂值。** 它只在本地这一段有意义，出了这个广播域就要换。

ARP 是 IPv4 的地址解析辅助：知道下一跳的 IP，问「这个 IP 的 MAC 是多少」，本地广播，拿到回复后写进 ARP 表。它横跨网络层和链路层，不是第五层。

主机怎么决定问谁？先拿目的 IP 和自己的子网掩码比：

- 同网段：ARP 问目的 IP 本身的 MAC，帧直接发给它。
- 不同网段：ARP 问默认网关的 MAC，帧的目的 MAC 是网关，IP 头的目的地址仍是最终服务器。

所以「同网段的通信不看 IP，看 MAC」是错的。选路和「发给谁」仍由 IP 决定；ARP 只负责把「下一跳 IP」翻译成「下一跳 MAC」，帧按这个 MAC 交付。跨网段时，网关会拆掉旧帧头，按 IP 查下一跳，再写新帧头。

## 同一句话，四层各看什么

「连不上」不是一个错误，它至少是四种不同的失败。下面四条都是我在本机跑出来的，命令可以直接粘到 Windows PowerShell 7.6；你的 IP、时间和 PID 会不同。

### 1. `Could not resolve host`：DNS 没给出 IP

```text
> curl.exe -sS -v --connect-timeout 5 https://paideia-does-not-exist.invalid
* Could not resolve host: paideia-does-not-exist.invalid
* Closing connection 0
curl: (6) Could not resolve host: paideia-does-not-exist.invalid
```

这里连 IP 都没拿到，TCP 的 SYN 根本没发出去。先查域名拼写、hosts、解析器；`nslookup paideia-does-not-exist.invalid 1.1.1.1` 在我这里能问到：

```text
*** one.one.one.one can't find paideia-does-not-exist.invalid: Non-existent domain
Server:  one.one.one.one
Address:  1.1.1.1
```

如果你的网络不许直连外部解析器，把 `1.1.1.1` 换成你本机配置的 DNS。这一步是应用层的 DNS，不是传输层。`Resolving timed out` 也在这里：解析器没在超时内回话，TCP 同样没开始。

### 2. `Connection refused`：传输层收到了 RST

```text
> curl.exe -sS -v --connect-timeout 4 http://127.0.0.1:9/
*   Trying 127.0.0.1:9...
* connect to 127.0.0.1 port 9 failed: Connection refused
* Failed to connect to 127.0.0.1 port 9 after 2024 ms: Couldn't connect to server
* Closing connection 0
curl: (7) Failed to connect to 127.0.0.1 port 9 after 2024 ms: Couldn't connect to server
```

`127.0.0.1` 是通的，但 9 端口没有进程监听，主机回了一个 RST。网络层到了、传输层明确拒绝，应用层的 HTTP 没开始。服务端如果防火墙是 REJECT，也可能是这个；如果是 DROP，就会变成下面的超时。

### 3. `Timeout was reached`：SYN 没等到回包

```text
> curl.exe -sS -v --connect-timeout 4 https://203.0.113.1
*   Trying 203.0.113.1:443...
* ipv4 connect timeout after 4000ms, move on!
* Failed to connect to 203.0.113.1 port 443 after 4006 ms: Timeout was reached
* Closing connection 0
curl: (28) Failed to connect to 203.0.113.1 port 443 after 4006 ms: Timeout was reached
```

`203.0.113.1` 是文档保留地址，正常网络里不会有人回。这里 SYN 发出去了，没等到 SYN-ACK；可能是路径不通、防火墙 DROP、目标端口被过滤，也可能是服务端 accept 队列满了直接丢。**光看这条错误分不出是哪一种**，所以才要 `ping`、`tracert`、或者换一台机器再测。`ping` 通也不能排除 443 被单独 DROP——ICMP 和 TCP 443 是两条不同的规则。

### 4. `404 Not Found`：四层都通了，应用层说没有这个路径

```text
> curl.exe -sS -D - -o NUL https://example.com/definitely-not-here | Select-Object -First 1
HTTP/1.1 404 Not Found
```

能收到状态行，说明 DNS、TCP、TLS、HTTP 都走通了。404 不是「网络连不上」，是服务器收到了请求但找不到这个路径；5xx 则是服务器（或它前面的网关）收到了请求但处理失败。到这一步再回去查 ping 或端口，方向就错了。

把四种失败放在一起：

| 你看到的 | 已经证明 | 还没证明 |
| --- | --- | --- |
| `Could not resolve host` | DNS 没给出 IP，TCP 没开始 | 域名、hosts、解析器；网络层以后都没走到 |
| `Connection refused` | IP 到了，TCP 收到 RST | 端口没监听或被 REJECT；应用层没开始 |
| `Timeout was reached` | SYN 发了，没等到 SYN-ACK | 路径、防火墙 DROP、端口过滤、服务端丢包，单看错误分不出 |
| `404` / `5xx` | DNS、TCP、TLS、HTTP 都到了应用层 | 路径/路由/业务逻辑；不是网络层「连不上」 |

这就是分层作为排查工具的样子：不是给协议分类，而是给失败点分边界。`Could not resolve host`、`Connection refused`、`Connection timed out` 分别落在 DNS、TCP 拒绝、TCP 无响应三个不同的位置；`5xx` 更在后面，是应用收到请求之后的事。对同一次请求，前三种结果不会同时成立；`5xx` 已经是另一个阶段。

**`ping` 通了，不等于服务没问题。** `ping` 用的是 ICMP，只证明 ICMP 有回包；它不证明 443 在听，也不证明防火墙没把 TCP 443 DROP。端口没开但主机回 RST 时，你看到的是 `Connection refused`；防火墙 DROP 时，你看到的是 `Connection timed out`。两种都不叫「服务正常」。

排查顺序从下往上：先确认能到主机（`ping`/`tracert`），再确认端口（`Test-NetConnection -Port`），最后看应用层返回（`curl -v`/浏览器）。如果每一步都马上返回，几分钟能缩小范围；如果遇到 DROP，`Test-NetConnection` 要等它自己的超时才回 `TimedOut`（我这次跑 `203.0.113.1:443` 用了约 23 秒），`curl` 则取决于你给的 `--connect-timeout`。**时间取决于超时设置，不是固定的三分钟。**

## 工具表：正常输出和异常输出

| 层 | Windows 命令 | 正常输出 | 异常输出 |
| --- | --- | --- | --- |
| 应用层（HTTP） | `curl.exe -v https://example.com` | `Connected to ...`，随后 `HTTP/1.1 200 OK` | `Could not resolve host`、`Connection refused`、`Timeout was reached`、`404`、`5xx` |
| 应用层（DNS） | `nslookup example.com` | `Name: example.com`，下面列出 `Addresses` | `can't find ...: Non-existent domain`；解析器不响应时是 `DNS request timed out`（标准形态） |
| 传输层 | `Test-NetConnection example.com -Port 443` | PowerShell 5.1：`TcpTestSucceeded : True`；7.6：`Connected : True`；`-InformationLevel Quiet`：`True` | `False`、`TimedOut`、`ConnectionRefused` |
| 传输层 | `netstat -ano` | `LISTENING`、`ESTABLISHED` | 该监听的端口没有 `LISTENING`；`CLOSE_WAIT` 长期不消失；`TIME_WAIT` 数量异常高（见第 05 篇） |
| 网络层 | `ping example.com` | `Reply from ...` | `Request timed out.`（标准形态）、`Destination host unreachable.` |
| 网络层 | `tracert -d example.com` | 每一跳有 IP 和时间 | 某一跳 `* * * Request timed out.`；可能只是那台路由器不回 ICMP |
| 链路层 | `arp -a` | `<IP>  <MAC>  dynamic` | `No ARP Entries Found.`，或网关的 MAC 不对 |

`curl` 是跨层工具：它既能报 DNS/连接错误，也能给出 HTTP 状态码；放在应用层，是因为最后一步看的是 HTTP 响应。

三件事在 Windows 上要换写法：

- Linux 的 `ss -tan` 换成 `netstat -ano`；`traceroute` 换成 `tracert`。
- `telnet` 在 Windows 上默认没装；而且它连上后也会发协议字节，不是「只连不请求」的纯端口探测。
- `curl` 也不是纯端口探测：它连上后会继续发 HTTP 请求。要只测端口，用 `Test-NetConnection -Port`；要看应用层，才用 `curl -v`。`curl -v` 里的 `Connected` 只说明 TCP 建好了；TLS 握手和 HTTP 请求还在后面。

`Test-NetConnection` 的输出随 PowerShell 版本变：Windows PowerShell 5.1 打的是 `TcpTestSucceeded : True/False`；我这里的 PowerShell 7.6 打的是 `Connected : True/False` 和 `Status : Success/TimedOut/ConnectionRefused` 的表格。脚本里只要布尔值，加 `-InformationLevel Quiet`，它只回 `True`/`False`。我实测：

```text
> Test-NetConnection example.com -Port 443 -InformationLevel Quiet
True
> Test-NetConnection 127.0.0.1 -Port 9 -InformationLevel Quiet
False
> Test-NetConnection 203.0.113.1 -Port 443 -InformationLevel Quiet
False
```

`203.0.113.1` 那条要等约 23 秒才回 `False`，因为它在等 TCP 超时。

`netstat -ano` 的最后几列是本地地址、远端地址、状态和 PID（`-a` 显示所有连接，`-n` 不做反向解析，`-o` 显示 PID）。Windows 打的是 `LISTENING` / `ESTABLISHED` / `TIME_WAIT`；Linux 的 `ss` 常简写成 `LISTEN` / `ESTAB`，名字不同，状态含义一样。我本地起了一个监听器，连上再关掉，三个状态都出现了：

```text
  TCP    127.0.0.1:45680        0.0.0.0:0              LISTENING       70940
  TCP    127.0.0.1:45680        127.0.0.1:59381        ESTABLISHED     70940
  TCP    127.0.0.1:59381        127.0.0.1:45680        ESTABLISHED     70940
--- after close ---
  TCP    127.0.0.1:59381        127.0.0.1:45680        TIME_WAIT       0
```

- `LISTENING`：进程绑定了端口，等 SYN；此时还没有连接。
- `ESTABLISHED`：三次握手完成，双方可以发数据；一行是一条连接，服务端和客户端各有一行。
- `TIME_WAIT`：主动关闭的一方在等旧包过期，端口暂时不能复用。它不是「连接没关掉」，而是关闭流程的正常最后一步；堆积很多时才是问题（第 05 篇）。

## 动手：抓一次，确认四层头都在

装 Wireshark，选正在用的网卡，过滤 `http`，然后跑：

```text
curl.exe -sS -o NUL http://example.com/
```

在捕获里选中任意一个 HTTP 包，展开 `Ethernet II` → `Internet Protocol Version 4` → `Transmission Control Protocol` → `Hypertext Transfer Protocol`，四个头都在。抓包工具是在网卡上抓的整帧，所以它既能看到 MAC，也能看到 IP、端口和 HTTP 请求行；选中某一层只是工具在过滤/解析，不是它只抓了那一层。

抓 HTTPS 不一样：你看到的是 TLS 记录，HTTP 明文被加密了；除非你有会话密钥，否则展不开 HTTP。**这一步我没在本机抓包**，上面是 Wireshark 的标准展开路径；`curl` 命令本身可以先跑，抓包结果取决于你选的网卡和过滤器。

## 还差的
