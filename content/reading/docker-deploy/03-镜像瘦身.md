## 场景

`Dockerfile` 长这样，镜像 900MB：

```dockerfile
FROM debian:12
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN apt-get install -y vim
COPY target/app.jar app.jar
CMD ["java", "-jar", "app.jar"]
```

三个问题：

1. 每个 `RUN` 是一层，`apt-get update` 的索引留在了**前面那层**，后面清理也删不掉；
2. 没有 `--no-install-recommends`，会装一堆推荐包；
3. `apt-get update` 与 `install` 分开，可能用到过期的索引。

打个比方：镜像的层像千层饼，你在最上面一层抹掉一块，下面那层还是原样。真实机制是：每个 `RUN` 生成一个只读层，后层的删除只遮住文件，不减小镜像总大小。

## 先想清楚

Docker 的层是只读叠加的：你在第 5 层删掉文件，文件仍然存在于第 2 层，镜像总大小不变。所以清理必须**与安装写在同一个 `RUN` 里**：

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl git \
 && rm -rf /var/lib/apt/lists/*
```

一行（一个 `RUN`）完成"更新索引 → 装包 → 删索引"。这样索引从未留在镜像层里。

`--no-install-recommends` 只装你点名要的包，不装 Debian 推荐的附加包。

## 常见误区

### 误区：另起一个 `RUN rm -rf` 能减小镜像

**你以为**：删了就是小了。
**其实**：删除只发生在最后一层，前面层的文件仍在。`docker history` 看到的总大小不会变。
**怎么验证**：加一行独立的 `RUN rm -rf /var/lib/apt/lists/*`，对比 `docker images` 的大小。

### 误区：`apt-get update` 单独一层更清晰

**你以为**：分层清楚，缓存好复用。
**其实**：索引会过期；隔几天构建时 `install` 用的还是旧索引，可能 404。而且清理必须同层。
**怎么验证**：把 update 与 install 拆开，过几天再构建，看是否出现包找不到。

### 误区：装 `vim`/`curl` 方便排查

**你以为**：容器里没有工具，出事没法查。
**其实**：生产镜像里每多一个工具就多一点攻击面与体积。排查用 `docker exec` 进临时调试容器，或者用 distroless + 单独的工具镜像。
**怎么验证**：`docker run --rm 镜像 sh -c 'command -v vim'`，为空说明没带。

## 带走一句

**安装与清理必须在同一个 RUN 里**——层是只读的，删不掉前面的东西。
