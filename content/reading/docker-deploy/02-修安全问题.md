## 场景

线上要发一个镜像，`Dockerfile` 是这样的：

```dockerfile
FROM openjdk:latest
ENV DB_PASSWORD=demo123
WORKDIR /app
COPY target/app.jar app.jar
RUN apt-get update && apt-get upgrade -y && apt-get install -y curl
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

它"能跑"，但四处有问题。你的任务是把它们修掉，同时保持应用仍能启动。

打个比方：安全整改像给房子换固定型号的门锁、把备用钥匙从门框上拿走、不给住户管理员权限。真实机制是：这四条分别对应构建可复现、密钥不泄漏、进程不越权、结果不漂移。

## 先想清楚

四个问题各自的风险：

| 问题 | 风险 |
| --- | --- |
| `openjdk:latest` | 基础镜像随时变，构建不可复现；`latest` 也可能被投毒 |
| `ENV DB_PASSWORD=...` | 密钥进入镜像层，`docker history`/导出镜像都能看到 |
| 没有 `USER` | 进程以 root 运行，逃逸后权限最大 |
| `apt-get upgrade -y` | 在镜像里升级全部包，结果不可复现，还可能破坏基础镜像 |

修法：

- 基础镜像固定版本，最好用 JRE：`eclipse-temurin:21-jre`；
- 密钥不进镜像：运行时用环境变量/密钥服务注入；
- 加 `USER 1000`，需要 curl 之类工具时再决定是否保留；
- 去掉 `upgrade`，只装需要的包。

## 常见误区

### 误区：`ENV` 里放密钥只是"明文一点"

**你以为**：反正是内部镜像。
**其实**：镜像层是永久的，`docker history` 能看到，推到仓库后所有有拉取权限的人都能拿到。删除变量也不会删掉历史层。
**怎么验证**：`docker history --no-trunc 镜像 | grep DB_PASSWORD`。

### 误区：容器里用 root 方便

**你以为**：装包、写文件都省事。
**其实**：容器逃逸、应用被 RCE 时，root 的爆炸半径最大；而且很多基础镜像的非 root 用户是现成的，成本很低。
**怎么验证**：`docker run --rm 镜像 id`，看是 `uid=0` 还是 1000。

### 误区：`apt-get upgrade` 能让镜像更安全

**你以为**：升级到最新补丁总是好的。
**其实**：它让构建结果依赖"当天仓库里有什么"，同一份 Dockerfile 明天构建可能得到不同镜像；还可能把基础镜像的兼容性改坏。要补丁就换基础镜像的 tag。
**怎么验证**：同一份 Dockerfile 隔几天构建，对比 `docker history` 的层哈希。

## 带走一句

**固定基础镜像、密钥不进层、非 root、不 upgrade**——这四条是镜像安全的最低线。
