> Martin Kleppmann · 《数据密集型应用系统设计》第 3 章 Storage and Retrieval（2017）· 中译 中国电力出版社
>
> 数字出处说明：书上「顺序写 200 MB/s、随机写每秒几百次」是 2017 年**机械硬盘**的量级。下面我先把自己这台机器测到的结果摆出来，再说清它改变了什么、没改变什么。

## 我以为顺序写会快几十倍，测出来是 1.01 倍

这一章的经典说法是：顺序写比随机写快，而且差距很大——所以 B 树（就地改页）吃亏，LSM 树（只追加）占便宜。

我拿自己的机器测了一遍，用 4 KB 块、每写一次 `fsync`，一次追加写、一次在 1 GB 文件里随机偏移覆写，各 2000 次：

```text
A 追加写 4KB x 2000（每次 fsync）: 1.093s -> 1830 次/秒, 0.547 ms/次
B 随机写 4KB x 2000（每次 fsync）: 1.108s -> 1805 次/秒, 0.554 ms/次
   随机/追加 耗时比 = 1.01x

C 顺序覆写 1MB x 200（每次 fsync）: 0.444s -> 450.9 MB/s, 2.218 ms/次
```

1.01 倍。几乎没差别。

先说清这个测试是什么：块大小 4 KB、每次写完强制落盘、跑在**插在 USB 上的外置 SSD**（`Fanxiang PS2000`）上，Python 直接读写文件，不是数据库。所以它只能说明一件事——**在这台机器的这个盘上，4 KB 粒度的写,顺序还是随机，主机侧看不出区别**。

至于为什么没差别，我的推测是：每次 `fsync` 的固定开销（约 0.55 ms）把寻道那一项彻底盖住了；而在 SSD 上本来就没有磁头要移动。这个推测我没有拆开验证（要看设备内部的 FTL 行为，主机侧看不到）。

那书上说的差距哪去了？没消失，只是**换了个位置**：从"磁头寻道"变成了"设备内部擦除块的写放大"，从主机侧看不见了。

## 三种思路，不是两种

上一版我写过"存数据只有两种思路"，这个说法不准确。实际有三类：

| 思路 | 怎么找一条记录 | 代表 |
| --- | --- | --- |
| B 树 | 按 key 排好的多层页，从根往下走 | InnoDB、PostgreSQL、SQLite |
| LSM 树 | 内存表 + 多层只读文件，从新到旧找 | RocksDB、Cassandra、HBase、LevelDB |
| 哈希索引 | 内存里一张 `key → 文件偏移` 的哈希表 | Bitcask、MySQL `MEMORY` 引擎 |

哈希索引这一族常被漏掉，但它的取舍和 B 树恰好相反：**点查快得离谱**（哈希查一次内存就有偏移），**但范围查询完全做不了**（哈希无序，`BETWEEN`、`ORDER BY` 全废），而且所有 key 的偏移必须放得进内存。Bitcask 就是"只追加 + 内存哈希表指向旧值偏移"——本质上是 LSM 的极简祖先。

InnoDB 里也有个用哈希的地方：自适应哈希索引（AHI），它为热点页自动建哈希来加速等值查找，`SHOW ENGINE INNODB STATUS` 里能看命中率。它是运行时自己加的，不是你能选的主索引类型。

## 页多大

这一点原稿写错了，值得单独纠正，因为它决定"改一个字节要写多少"：

| 系统 | 页大小 | 可配吗 |
| --- | --- | --- |
| 操作系统（x86） | 4 KB | 一般不动 |
| InnoDB | **16 KB** | `innodb_page_size`，建库时定，8/16/32/64 KB |
| PostgreSQL | **8 KB** | 编译期 `BLCKSZ` |

InnoDB 那 16 KB 不是操作系统页——它自己按 16 KB 组织 B 树节点，绕开操作系统页。所以"通常 4 KB"是把三个层次的东西混成一个了。

这个数字直接影响写放大：**你改一行里 16 个字节，InnoDB 也要重写整个 16 KB 的页**（连同 WAL 里的记录）。这是"就地更新"这件事的固有成本，跟磁盘是机械还是 SSD 无关。

## B 树：把随机写藏进页里

B 树按 key 排好、切成固定大小的页、页之间用指针连成树。

- 查找：从根往下，通常三到四层就到叶子，`O(log n)` 次页读。
- 写入：找到目标页，改它，写回去。一次逻辑写 = 一次随机页写 + 一条 WAL。

读的优点是**稳定**：每个 key 在唯一确定的位置，读的页数可预测。

这里还有一处容易被含糊过去的区别，值得记一下：

- **MySQL/InnoDB**：主键是**聚簇索引**——表本身就是一棵 B 树，行数据存在主键的叶子页里。所以"按主键范围扫"是顺序读，走二级索引则要"先在二级索引拿主键、再回主键树取行"（回表）。
- **PostgreSQL**：表是**堆表**（heap，物理上不按任何 key 排），索引是独立的 B 树，叶子项存指向堆里位置的 `ctid`。所以即便走索引扫，数据页本身仍是乱序访问的——除非你用 `CLUSTER` 重排过、或者索引覆盖了所有需要的列（index-only scan）走 visibility map。

"PostgreSQL 用 B 树"这句话没错，但不说清是"堆表 + B 树索引"，就会得出"PG 的读也是顺序的"这种错结论。

## LSM 树：把随机写变成顺序写

LSM 的思路是"先不写进去"：

1. 写入先进内存里的有序表（memtable）；
2. 攒到阈值，整体刷成磁盘上一个**只读文件**（SSTable）——纯顺序追加；
3. 后台把多个小文件**合并**成大的，顺手丢掉被覆盖的旧值。

代价全在后台：

- **读放大**：一个 key 可能存在 memtable、也可能在 L0/L1/L2 任一层文件里，读的时候从新到旧逐层找。所以 LSM 通常配 Bloom filter 来跳过不可能含该 key 的文件。
- **写放大**：合并本身就是反复读写整份数据——一条记录在它的一生里可能被 compaction 重写十几遍。
- **空间放大**：旧版本要等合并才消失，中间态占着磁盘。

## 一张表说清取舍

| | B 树 | LSM 树 |
| --- | --- | --- |
| 单次写 | 改一个页（InnoDB 是 16 KB）+ WAL | 追加到 memtable + WAL，攒批刷盘 |
| 单次读 | 三到四层页，稳定 | 可能翻多个文件，受合并状态影响 |
| 空间放大 | 小（就地更新，但有页内碎片） | 大（旧值要等合并才消失） |
| 写放大 | 页级（改 16 字节写 16 KB） | 合并级（一条记录被重写多次） |
| 读延迟稳定性 | 好 | 差（合并时会抖） |
| 最怕什么 | 随机写密集 + 页分裂 | 大量更新同一批 key |

最后一行是全章最值钱的判断：**LSM 不怕写多，怕"反复写同一批 key"**。写多只是让 memtable 刷得更勤；反复改同一批 key 则让合并永远追不上——刚合并完，上层又落下来一堆同一批 key 的新版本，磁盘里堆满注定被丢掉的旧值。

这也是为什么"用 LSM 存计数器"这种设计很危险，除非用分片计数（每个分片独立累加，读时求和）。

## 什么时候选哪个

- **读多、要求延迟稳定、数据量中等**：B 树更省心。关系库的默认选择基本都是它。
- **写吞吐是第一优先级、能容忍读抖动**：LSM。典型是日志、时序、事件流、消息堆积。
- **两者都想要**：现实里没有这种好事。工程上能做的是**把两类负载拆到两个系统里**——热数据放 B 树、冷数据沉到 LSM，中间靠异步同步。

判断顺序我建议这样走：先问"我的瓶颈是写吞吐还是读延迟稳定性"，再问"我的 key 更新是分散的还是集中在一小批上"，最后才看具体产品。跳过前两问直接选数据库，通常是在赌。

## SSD 改变了什么，没改变什么

**改变了**：机械硬盘上"随机读慢几十倍"的惩罚基本消失。这削弱了一个传统的选型理由——"B 树随机读多，所以写多的场景要上 LSM"。在现代 SSD 上，读多几次页，代价比 2017 年小得多。这也部分解释了为什么这些年新系统里 B 树方案重新变得常见（比如各种基于 B 树的 KV 存储）。

**没改变**：

- **写放大依然存在**，只是从主机侧移到设备侧——SSD 的擦除单位是块（常见几百 KB 到几 MB），改写小块会触发内部搬移，还消耗寿命。主机侧测不出来，但账单和寿命是真的。
- **页级写放大依然存在**：InnoDB 改 16 字节写 16 KB，这件事跟介质无关。它在 SSD 上表现为"设备收到 16 KB 而不是 16 字节"，在机械盘上表现为"要转过去写一个扇区"。
- **合并的 CPU 与 IO 开销依然存在**，它跟介质无关，只跟数据量和更新模式有关。

## 边界在哪

- 这一章讲**单机**存储引擎。分片、复制在第 5、6 章。
- 不讲查询优化器——那是"怎么选数据"，这里是"怎么放数据"。
- 不涉及具体产品的参数。同样是 LSM，参数调错了照样慢；同样是 B 树，`innodb_page_size` 选错了也难受。

## 我还没搞清楚的

测出来 4 KB 随机写和追加写几乎一样快，这个结果我信，但它能推广到多大块、多少并发，我不知道——我只测了单线程、4 KB、每写一次 `fsync`。如果你要拿它下"SSD 上不需要 LSM"的结论，那是过度外推：企业盘、多路并发、写放大在设备内部的真实表现，都得另测。这也是我把结论只写在"主机侧看不见区别"这个范围内的原因。

## 带走一句

看到"我们换了个更快的数据库"，先问三个问题：**你的瓶颈是写吞吐还是读延迟稳定性？你的 key 更新是分散还是集中在一小批上？你的写放大在主机侧还是在设备侧？** 答不上来，换引擎只是把问题换个地方发生。
