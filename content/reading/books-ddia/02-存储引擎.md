## 先把结论摆出来

数据库真正存数据的内核只有两种思路：

- **B 树**：把数据按 key 排好，**就地更新**。改一条记录就是改那一页上的几个字节。
- **LSM 树**：把写入先攒进内存，攒够了**追加写**成一个大文件，后台再合并。

两种思路没有优劣，它们在不同维度上赢。这也是为什么 MySQL/InnoDB、PostgreSQL 用 B 树，而 Cassandra、RocksDB、HBase 用 LSM——不是谁落后，是取舍不同。

## 为什么会有两种

底层的物理事实只有一个：**顺序写比随机写快，而且差距很大**。

- 机械硬盘上，顺序写能到 200 MB/s，随机写每秒只有几百次（每次都要等磁头移动）。
- SSD 上差距小很多，但随机写仍然更贵：SSD 的写是"先擦除一个块再写"，随机写会造成更多的写放大。

B 树和 LSM 就是对这个事实的两种应对方式。

### B 树：把随机写藏进页里

B 树把数据切成固定大小的**页**（通常 4 KB），按 key 排序，页与页之间用指针连成树。

- 查找：从根往下走，读三到四页就找到，这是 `O(log n)` 次随机读。
- 写入：找到目标页，**改它，再写回去**。所以一次写是一次随机写。

它的优点是**读得稳**：每个 key 都在唯一确定的位置，读一次就能拿到。缺点是写放大：改一个字节也要写一整页。

### LSM 树：把随机写变成顺序写

LSM 的思路是"先不写进去"。写入先进内存里的一个有序表（memtable），攒到一定大小就整体刷成磁盘上的一个**只读文件**（SSTable）——这是纯顺序写。

代价是读的时候可能有多个文件，得从新到旧挨个找。所以后台要做**合并**：把几个小文件合成一个大文件，顺便丢掉被覆盖的旧值。

它的优点是**写得快**：所有写都是追加，没有随机写。缺点是**读放大**和**写放大**都转移到了后台：查一个 key 可能要翻好几个文件；合并本身又要反复读写整份数据。

## 一张表说清取舍

| | B 树 | LSM 树 |
| --- | --- | --- |
| 单次写 | 随机写一整页 | 顺序追加 |
| 单次读 | 三到四页，稳定 | 可能翻多个文件，受合并状态影响 |
| 空间放大 | 小（就地更新） | 大（旧值要等合并才消失） |
| 写吞吐 | 受随机 IO 限制 | 高 |
| 读延迟的稳定性 | 好 | 差（合并时会抖） |
| 最怕什么 | 随机写密集 | 大量更新同一批 key |

注意最后一行：**LSM 不怕写多，怕"反复写同一批 key"**——那会让合并永远追不上，磁盘里堆满要被丢掉的旧版本。

## 什么时候选哪个

- **读多、要求延迟稳定、数据量中等**：B 树更省心。这也是大多数关系库的默认选择。
- **写吞吐是第一优先级、能容忍读抖动**：LSM。典型场景是日志、时序数据、事件流。
- **两者都想要**：现实里没有。你能做的是**把两类负载拆到两个系统里**——热数据用 B 树，冷数据落到 LSM。

## SSD 改变了什么

这是 2017 年之后最值得补的一条。

SSD 把随机读的性能拉近到了顺序读的同一个量级，所以"B 树读得慢"这个理由弱了很多。但**随机写仍然更贵**，因为 SSD 的擦除粒度是块而不是字节，随机写会造成写放大，还消耗寿命。

所以：**LSM 在写密集场景下的优势仍然成立，但幅度缩小了**。这也解释了为什么新出的存储系统里，B 树方案重新变得常见。

## 边界在哪

- 这一章讲的是**单机**存储引擎。分片、复制是后面章节的事。
- 它不讨论查询优化器。那是"怎么选数据"，这里是"怎么放数据"。
- 它对具体产品的配置一言未发。同样是 LSM，参数调错了照样慢。

## 带走一句

看到"我们换了个更快的数据库"，先问：**你的瓶颈是随机写还是随机读**。写多的换成 B 树会更慢，读多的换成 LSM 一定会抖。
