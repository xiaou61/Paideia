执行顺序是这样的：

1. 线程数 < `corePoolSize` → 新建线程执行；
2. 否则**先入队**；
3. 队列满了才扩到 `maxPoolSize`；
4. 还是满 → 走拒绝策略。

关键在第 2 步：**队列先于扩容**。所以给一个无界队列（`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`），`maxPoolSize` 永远用不上，任务无限堆积直到 OOM。

**这就是"线程池把内存吃光"的全部原因。**

打个比方：线程池像一家餐厅——先开后厨（核心线程），坐满就把客人安排在门口等位（队列），等位区也塞不下才加桌子（扩容）。真实机制是：`ThreadPoolExecutor` 的调度顺序是先把任务放进队列，队列满了才扩到 `maxPoolSize`，所以给了无界队列就永远走不到扩容那一步。

## 七个参数里真正要定的两个

| 参数 | 怎么定 |
| --- | --- |
| `corePoolSize` | 按**任务类型**定：CPU 密集 ≈ 核数；IO 密集可以更大（等 IO 时线程闲着） |
| `queue` | **必须有界**，容量按"能容忍的积压"反推 |
| `maxPoolSize` | 有界队列下才有意义；等于"突发时最多开几个" |
| `keepAlive` | 空闲多久回收非核心线程 |
| 拒绝策略 | 见下 |

其余三个（线程工厂、时间单位、是否核心线程超时）很少是事故原因。但**线程工厂一定要给线程起名字**——排查时 `jstack` 里全是 `pool-1-thread-N` 等于没有信息。

## 拒绝策略怎么选

| 策略 | 行为 | 什么时候用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 大多数业务：让调用方知道失败了 |
| `CallerRunsPolicy` | 提交任务的线程自己跑 | 想限流：让上游被拖慢 |
| `DiscardPolicy` | 静默丢弃 | **几乎不要用**，丢任务不留痕 |
| `DiscardOldestPolicy` | 丢最老的 | 只适合"新数据比旧数据重要"的采集场景 |

**默认的 Abort 通常是对的**：拒绝会让上游报错，报错了你能看见；静默丢弃不会。

## 队列满了意味着什么

要分清两种"满"：

- **短时突发**：队列有界、偶尔满、被拒绝几次——正常，说明限流生效了；
- **持续积压**：队列长期在高水位、持续拒绝——说明**处理能力不够**，加线程只能缓解一时，因为瓶颈可能在数据库或下游。

判断方法：看队列的 `queue.size()` 与活跃线程数的时间序列。活跃线程长期打满 + 队列单调上涨 = 能力问题，不是参数问题。

## 一个具体的配置例子

```text
new ThreadPoolExecutor(
    8,                                  // core：8 核机器上的 CPU 密集任务
    16,                                 // max：突发时最多 16 个
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),      // 有界：最多积压 200 个
    r -> { Thread t = new Thread(r, "order-import"); return t; },
    new ThreadPoolExecutor.AbortPolicy()
);
```

8 核 + 200 队列 + 16 上限：**最坏情况下内存里最多 216 个任务**，这是可控的。换成 `LinkedBlockingQueue`（无界），最坏情况是"直到内存耗尽"。

## 常见误区

### 误区：maxPoolSize 是硬上限，设小就安全

**你以为**：把最大线程数设小，内存就不会爆。
**其实**：无界队列下 `maxPoolSize` 根本用不到，任务全堆在队列里，吃的是堆内存而不是线程栈。
**怎么验证**：用 `LinkedBlockingQueue` 提交远超处理能力的任务，观察 `maxPoolSize` 与 `queue.size()`。

### 误区：线程数越多吞吐越高

**你以为**：加线程就能加吞吐。
**其实**：线程超过瓶颈资源（CPU 核数、数据库连接数）后只会增加切换与竞争。线程数应当由**瓶颈**决定，不是由"想快一点"决定。
**怎么验证**：固定任务量，逐步加线程，画出吞吐曲线——它会先升后降。

### 误区：线程池用完自己会释放，不用管

**你以为**：不 shutdown 也没事。
**其实**：非守护线程会阻止 JVM 退出。`Executors.newFixedThreadPool` 创建的是非守护线程，忘了 `shutdown` 的应用会"停了但进程还在"。
**怎么验证**：起一个只有线程池的应用，主线程结束后看进程是否退出。
