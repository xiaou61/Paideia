## 先把结论摆出来

**`java.util.concurrent` 里的容器不是"加了锁的集合"，每一个都有自己的一致性契约。用之前先问清楚：它保证哪一级原子性，读到的数据有多新。**

```sketch
{
  "title": "并发容器各有各的契约",
  "rows": [
    [
      { "id": "chm", "title": "CHM", "sub": "单键原子，整体不强一致", "tone": "blue" },
      { "id": "cow", "title": "CopyOnWrite", "sub": "读不加锁，写复制整份", "tone": "violet" },
      { "id": "bq", "title": "阻塞队列", "sub": "满了阻塞，空了也阻塞", "tone": "green" }
    ]
  ],
  "arrows": []
}
```

三句话概括：

1. `ConcurrentHashMap` 保证**单个方法**的原子性，`size()` 只是估计值，复合操作仍然要用 `putIfAbsent` / `compute` / `merge`；
2. `CopyOnWriteArrayList` 适合**读多、写极少、列表很小**的场景，写一次复制整个数组；
3. `BlockingQueue` 是生产者-消费者的标准件，但**默认无界的实现会把内存吃光**，线程池的队列尤其如此。

自己用 `synchronized` + `ArrayList` / `HashMap` 拼一个"线程安全容器"，通常会同时输掉正确性、吞吐和可维护性。这不是因为锁不能用，而是因为容器内部的可见性、扩容、迭代、内存回收，每一处都有坑。

## 为什么不自己造

先看一个常见的"我自己包一层"：

```java
class SafeList<T> {
    private final List<T> inner = new ArrayList<>();

    synchronized void add(T value) { inner.add(value); }

    synchronized T get(int index) { return inner.get(index); }

    synchronized int size() { return inner.size(); }

    synchronized List<T> snapshot() { return new ArrayList<>(inner); }
}
```

这段代码本身没错，但它把**所有读也串行化了**。十个线程读、一个线程偶尔写，读线程仍然要排队。换成 `CopyOnWriteArrayList`，读完全无锁；换成 `ConcurrentHashMap`，读也不会被写挡住。

更麻烦的是复合操作。下面这段看起来"都加锁了"，实际上每次调用只锁一个方法：

```java
if (list.size() > 0) {
    list.remove(0);   // size 和 remove 之间，别人可能已经删空了
}
```

要正确，得把判断和删除放进同一个锁里，或者用容器提供的原子方法。**"每个方法都线程安全"不等于"方法组合起来线程安全"**，这是并发容器最核心的认知。

JDK 已经把这些模式实现好了，而且针对硬件做了优化（CAS、分段、无锁读、伪共享填充）。自己写很难同时做到正确和快。

## ConcurrentHashMap：从分段锁到 CAS + synchronized

`ConcurrentHashMap` 在 JDK 7 和 JDK 8 的实现差别很大，面试和排查都常问。

| 维度 | JDK 7 | JDK 8+ |
| --- | --- | --- |
| 结构 | `Segment[]`，每个 Segment 是一个小 HashMap | `Node[]`，每个桶挂链表或红黑树 |
| 锁 | Segment 继承 `ReentrantLock` | 空桶用 CAS，冲突桶 `synchronized` 首节点 |
| 并发度 | 由 `concurrencyLevel` 决定，默认 16 | 锁粒度到桶，冲突少时几乎无锁 |
| 扩容 | 每个 Segment 独立扩容 | 多线程协助扩容（`ForwardingNode`） |
| 计数 | 加锁统计所有 Segment | `baseCount` + `CounterCell[]`，类似 `LongAdder` |
| 树化 | 无 | 链表长度到 8 且表长到 64 时转红黑树 |

JDK 7 的分段锁把锁分成 16 份，最多 16 个线程同时写。这个设计在低并发下够用，但并发度是**静态的**：写热点集中在一个 Segment 时，其他 Segment 空着也帮不上忙。

JDK 8 改成了"每个桶一把锁"：

- 桶为空时，用 CAS 直接放入新节点，不加锁；
- 桶不为空时，只 `synchronized` 这个桶的首节点；
- 链表过长时转红黑树，把最坏查找从 O(n) 降到 O(log n)；
- 扩容时用 `ForwardingNode` 标记已迁移的桶，其他线程可以帮忙搬数据。

所以现代 `ConcurrentHashMap` 的并发度不再是一个固定数字，而是"桶的数量"。桶越多，冲突越少，写并行度越高。

### `size()` 为什么只是估计值

JDK 8 的计数不是一个 `AtomicLong`，而是一组分散的计数单元：

```text
baseCount + CounterCell[0] + CounterCell[1] + ...
```

写线程优先 CAS 更新 `baseCount`；冲突时落到自己的 `CounterCell`，减少争用。`size()` 调用 `sumCount()` 把这些值加起来。

问题在于：**加的过程中，别的线程还在改。** 你加到一半，某个 Cell 又变了，最后得到的数既不是开始时的快照，也不是结束时的快照。

```java
map.size();          // int，超过 Integer.MAX_VALUE 会饱和
map.mappingCount();  // long，推荐用它
```

`mappingCount()` 返回 `long`，避免大表溢出，但**同样是估计值**。Javadoc 写得很清楚：返回值是估计值，并发更新时可能不准确。

所以：

- 不要用 `size()` 做限流、分页、判断"是否为空"的业务逻辑；
- 监控里可以用它看趋势，但别把它当精确值报警；
- 需要精确计数时，自己用 `LongAdder` 或数据库计数，别指望并发容器。

`isEmpty()` 也是弱一致的：它返回 true 只代表"那一刻看起来空"，不代表之后没有线程插入。

### 单个操作原子，复合操作不原子

`ConcurrentHashMap` 的 `put`、`get`、`remove` 都是线程安全的，但下面这些写法仍然有竞态：

```java
// 错：先查后放
if (!map.containsKey(key)) {
    map.put(key, load(key));
}

// 对：原子地"没有才放"
map.putIfAbsent(key, load(key));
```

注意 `putIfAbsent` 仍然会执行 `load(key)`（参数先求值），只是"放入"这一步是原子的。如果加载很贵，应该用 `computeIfAbsent`：

```java
User user = map.computeIfAbsent(id, key -> load(key));
```

`computeIfAbsent` 在桶级别加锁，保证同一个 key 只计算一次。但它有几个坑：

- **映射函数里不要做慢操作**。它持有桶锁，同一个桶的其他更新会被挡住；如果函数里调用远程接口，可能把整个桶拖住几秒。
- **不要在映射函数里修改这个 map**。规范明确禁止递归更新，JDK 可能抛 `IllegalStateException`，也可能死锁。
- **映射函数返回 null 时不会建立映射**，而且不会存入 null。
- **异常会原样抛出**，不会留下半个映射。

其他常用的原子方法：

| 方法 | 语义 |
| --- | --- |
| `putIfAbsent(k, v)` | 不存在才放，返回旧值或 null |
| `remove(k, v)` | 只有当前值等于 v 才删除 |
| `replace(k, old, new)` | 只有当前值等于 old 才替换 |
| `replace(k, v)` | 存在才替换 |
| `computeIfAbsent(k, fn)` | 不存在时计算并放入 |
| `computeIfPresent(k, fn)` | 存在时计算并替换 |
| `compute(k, fn)` | 无论是否存在都计算，返回 null 则删除 |
| `merge(k, v, fn)` | 不存在放 v，存在则用 fn 合并 |

这些方法把"读-判断-写"合成一个原子步骤，是 `ConcurrentHashMap` 正确的使用方式。**只要你的逻辑跨了两次方法调用，就要怀疑它是不是复合操作。**

### 迭代器是弱一致的

`ConcurrentHashMap` 的迭代器不会抛 `ConcurrentModificationException`，因为它基于某个时刻的桶数组视图，遍历时能看到一部分并发修改，也可能看不到另一部分。

```java
for (Map.Entry<String, User> entry : map.entrySet()) {
    // 遍历期间 map 可以被其他线程修改，不报错
}
```

这叫**弱一致（weakly consistent）**：不保证看到遍历开始后的所有修改，但保证不重复、不抛异常、能走完。它适合"扫一遍做统计/清理"，不适合"遍历时依赖某个精确快照"。

需要精确快照时，自己复制一份：

```java
List<Entry<String, User>> snapshot = new ArrayList<>(map.entrySet());
```

但复制本身也不是原子的，只是复制之后你拿到的是一个不再变化的列表。

### 不允许 null

`ConcurrentHashMap` 的 key 和 value 都不能为 null。原因很实际：`get(key)` 返回 null 时，无法区分"没有这个 key"和"这个 key 的值就是 null"。单线程的 `HashMap` 可以用 `containsKey` 区分，但并发下 `containsKey` 和 `get` 之间状态可能变化，干脆禁止 null 更安全。

所以缓存里想表达"查过了，没有"，不要存 null，可以存一个哨兵对象：

```java
private static final User MISSING = new User("__missing__", null);
```

### 其他并发 Map

| 类 | 特点 | 适用 |
| --- | --- | --- |
| `ConcurrentHashMap` | 哈希、无序、桶级锁 | 通用缓存、索引 |
| `ConcurrentSkipListMap` | 跳表、按 key 有序、O(log n) | 需要排序/范围查询 |
| `Collections.synchronizedMap` | 整表一把锁 | 低并发、需要包装已有 Map |
| `Hashtable` | 整表一把锁、不允许 null | 遗留代码，不建议新用 |

`Collections.synchronizedMap` 的迭代仍然需要你手动 `synchronized (map)`，否则会抛 `ConcurrentModificationException`。它只是把每个方法包了一层锁，没有解决复合操作和迭代问题。

## CopyOnWriteArrayList：读多写少的极端取舍

`CopyOnWriteArrayList` 的策略非常直接：**每次修改都复制一个新数组，读操作永远读旧数组。**

```java
private final List<Listener> listeners = new CopyOnWriteArrayList<>();

void register(Listener listener) {
    listeners.add(listener);   // 复制数组、追加、替换引用
}

void fire(Event event) {
    for (Listener listener : listeners) {   // 读的是某个快照，不加锁
        listener.onEvent(event);
    }
}
```

写操作的开销是 O(n) 复制，读操作几乎零开销。迭代器拿到的是创建那一刻的数组快照，遍历期间即使有人 `add` / `remove`，也不会抛 `ConcurrentModificationException`，也不会看到新元素。

适合的场景：

- 监听器/回调列表：注册和注销很少，触发很频繁；
- 配置项列表：启动时加载，运行时偶尔刷新；
- 白名单/黑名单：读多写少，列表规模小；
- 事件总线订阅者：遍历时不能被并发修改打断。

不适合的场景：

- 列表很大（几千、几万元素）：每次写都复制整个数组，内存和 GC 压力都大；
- 写很频繁：复制次数多，吞吐会明显下降；
- 需要"写完立刻被正在遍历的线程看到"：旧迭代器看不到新元素；
- 元素本身可变：COW 只保证数组结构安全，元素对象的字段仍然需要自己同步。

`CopyOnWriteArrayList` 的 `addIfAbsent` 是原子的（内部加锁并检查），适合去重注册；但它是 O(n) 的，列表大时很慢。`remove` 也是复制新数组，遍历时删除不会影响当前迭代器。

一个容易忽略的坑：**遍历时某个监听器抛异常，后面的监听器就不会被调用。** 容器不负责隔离异常，你要自己包一层：

```java
void fire(Event event) {
    for (Listener listener : listeners) {
        try {
            listener.onEvent(event);
        } catch (Throwable error) {
            log.error("listener failed: {}", listener, error);
        }
    }
}
```

`CopyOnWriteArraySet` 基于同一个机制，适合小规模、读多写少的集合。它的 `add` 会遍历检查重复，写开销比 `CopyOnWriteArrayList` 更大，别用在频繁写入的场景。

## BlockingQueue：生产者-消费者的标准件

`BlockingQueue` 在普通队列上加了两个能力：**队列满时阻塞写入，队列空时阻塞读取。** 这一个能力就让生产者-消费者从"自己写 wait/notify"变成"调两个方法"。

### 四组方法，先分清语义

| 操作 | 抛异常 | 返回特殊值 | 阻塞 | 超时 |
| --- | --- | --- | --- | --- |
| 插入 | `add(e)` | `offer(e)` | `put(e)` | `offer(e, time, unit)` |
| 取出 | `remove()` | `poll()` | `take()` | `poll(time, unit)` |
| 查看 | `element()` | `peek()` | 无 | 无 |

- `add` 在队列满时抛 `IllegalStateException`；
- `offer` 在队列满时返回 `false`，不阻塞；
- `put` 在队列满时一直等，直到有空位或被中断；
- `take` 在队列空时一直等，直到有元素或被中断；
- `poll(timeout)` 等不到就返回 null，适合"消费者要定期检查退出标志"的场景。

**没有超时的 `put` / `take` 是阻塞队列最常见的故障源。** 生产者 `put` 在一个没人消费的队列上，线程永远挂着；消费者 `take` 在一个没人生产的队列上，也一样。如果你不能保证另一端一定活着，就用带超时的版本。

### 四种核心实现

| 实现 | 是否有界 | 数据结构 | 锁 | 典型用途 |
| --- | --- | --- | --- | --- |
| `ArrayBlockingQueue` | 有界，必须指定容量 | 数组 + 头尾指针 | 一把锁 + 两个条件 | 固定容量、可预测内存 |
| `LinkedBlockingQueue` | 可选，默认 `Integer.MAX_VALUE` | 链表 | 两把锁（put/take） | 吞吐较高，但默认无界很危险 |
| `PriorityBlockingQueue` | 无界 | 二叉堆 | 一把锁 | 按优先级处理任务 |
| `SynchronousQueue` | 容量 0 | 栈/队列 | CAS | 直接交接，`newCachedThreadPool` 用它 |

补充三个常用的：

- `DelayQueue`：无界，元素实现 `Delayed`，只有到期才能 `take`，适合定时任务、缓存过期；
- `LinkedTransferQueue`：`transfer()` 会等消费者真正接手，适合"必须确认被处理"的交接；
- `LinkedBlockingDeque`：双端队列，适合工作窃取。

`ArrayBlockingQueue` 的容量在构造时固定，内存一次性分配，最可预测。它只有一把锁，生产和消费不能完全并行，但实现简单、行为稳定。

`LinkedBlockingQueue` 用两把锁，生产者和消费者可以同时操作头尾，吞吐通常更高。代价是默认容量 `Integer.MAX_VALUE`——**不传容量就是无界队列**，这是线程池 OOM 的头号原因。

`PriorityBlockingQueue` 按优先级出队，不是 FIFO。它无界，插入不会阻塞（除非 OOM）；元素必须实现 `Comparable` 或提供 `Comparator`；相同优先级的顺序不保证稳定。低优先级任务在高优先级持续到来时可能**永远排不上**，这就是优先级队列的饥饿问题。

`SynchronousQueue` 没有容量，每个 `put` 必须等到一个 `take`，反之亦然。它适合"生产者直接把任务交给消费者"的交接场景。`Executors.newCachedThreadPool` 用它配合无上限线程数：来一个任务，没有空闲线程就新建一个。任务提交速率高于处理速率时，线程数会一直涨。

### 一个标准的生产者-消费者

```java
class ImportService {
    private final BlockingQueue<ImportTask> queue = new ArrayBlockingQueue<>(1000);
    private final ExecutorService workers = Executors.newFixedThreadPool(4);
    private volatile boolean running = true;

    void start() {
        for (int i = 0; i < 4; i++) {
            workers.execute(this::consume);
        }
    }

    void submit(ImportTask task) throws InterruptedException {
        queue.put(task);   // 队列满时阻塞，形成背压
    }

    private void consume() {
        while (running || !queue.isEmpty()) {
            try {
                ImportTask task = queue.poll(1, TimeUnit.SECONDS);
                if (task == null) {
                    continue;
                }
                try {
                    handle(task);
                } catch (Throwable error) {
                    log.error("import task failed: {}", task, error);
                }
            } catch (InterruptedException error) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }

    void stop() throws InterruptedException {
        running = false;
        workers.shutdown();
        workers.awaitTermination(30, TimeUnit.SECONDS);
    }
}
```

这段代码有几个刻意的选择：

- **有界队列** `1000`：队列满时 `put` 阻塞，把压力传回上游，而不是无限堆积；
- **`poll(1s)` 而不是 `take()`**：消费者能定期检查 `running`，停机时不会被永久挂住；
- **每个任务单独 `try/catch`**：一个任务失败不会杀死消费者线程；
- **`InterruptedException` 恢复中断标志**：让上层知道线程被中断了，而不是吞掉。

停机还有另一种常见做法：**毒丸（poison pill）**。往队列里放一个特殊任务，消费者读到它就退出：

```java
private static final ImportTask POISON = new ImportTask(null);

void stop() throws InterruptedException {
    for (int i = 0; i < 4; i++) {
        queue.put(POISON);   // 每个消费者一个
    }
}
```

毒丸的坑：消费者数量必须和毒丸数量一致；队列满时 `put` 毒丸也会阻塞；如果有消费者已经异常退出，毒丸可能没人取。相比之下，`shutdown()` + 中断更不容易出错。

### 异常丢失：最安静的一种故障

消费者里如果不捕获异常，线程会退出，队列里的任务还在，但没人处理了。更隐蔽的是线程池的 `submit`：

```java
executor.submit(() -> {
    throw new RuntimeException("boom");   // 不会打印，也不会让线程池报错
});
```

`submit` 把任务包进 `FutureTask`，异常被捕获并存进 `Future`。如果你不调用 `Future.get()`，这个异常就永远不会出现。日志里没有、监控里没有，只有任务没执行。

对比 `execute`：

```java
executor.execute(() -> {
    throw new RuntimeException("boom");   // 会走线程的 UncaughtExceptionHandler，默认打印栈
});
```

`execute` 的异常会由工作线程抛出，默认打印到 stderr；`submit` 的异常被 `Future` 吃掉。两种都不是"自动可靠"：`execute` 的日志可能被容器吞掉，`submit` 需要你主动 `get`。

可靠的做法是**在任务体内部统一捕获并记录**：

```java
executor.submit(() -> {
    try {
        doWork();
    } catch (Throwable error) {
        log.error("task failed", error);
        throw error;   // 需要让 Future 也知道失败时再抛
    }
});
```

或者在 `ThreadPoolExecutor` 里重写 `afterExecute`，统一处理 `Throwable`。`ScheduledExecutorService` 更严格：周期任务只要抛一次异常，后续执行就会停止，必须自己包 `try/catch`。

## 线程池的队列怎么选

线程池的队列不是随便填的，它直接决定了"任务堆积在哪里"和"内存会不会爆"。

| 工厂方法 | 队列 | 风险 |
| --- | --- | --- |
| `newFixedThreadPool(n)` | `LinkedBlockingQueue`（无界） | 任务无限堆积，可能 OOM |
| `newSingleThreadExecutor()` | `LinkedBlockingQueue`（无界） | 同上 |
| `newCachedThreadPool()` | `SynchronousQueue` | 线程数无上限，可能线程爆炸 |
| `newScheduledThreadPool(n)` | `DelayedWorkQueue`（无界） | 定时任务堆积 |
| `newWorkStealingPool()` | `ForkJoinPool` 内部队列 | 适合分治任务，不适合阻塞 IO |

`Executors` 的工厂方法是为了"开箱即用"，不是为了"生产安全"。真正上线建议直接 `new ThreadPoolExecutor(...)`，把队列、线程工厂、拒绝策略都写清楚。

一个可控的配置：

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                                      // core：按 CPU 密集任务估算
    16,                                     // max：突发上限
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),          // 有界：最多积压 500 个
    new ThreadFactory() {
        private final AtomicInteger seq = new AtomicInteger();
        public Thread newThread(Runnable task) {
            return new Thread(task, "order-import-" + seq.incrementAndGet());
        }
    },
    new ThreadPoolExecutor.AbortPolicy()    // 满了就抛，让上游看见
);
```

队列容量怎么定？看两个数：

- **能容忍的延迟**：队列长度 / 处理速率 ≈ 最坏等待时间。500 个任务、每秒处理 50 个，最坏等 10 秒；如果接口超时是 3 秒，这个队列就太长了。
- **能容忍的内存**：队列长度 × 单个任务的平均内存。任务里带大对象时，500 个可能就几百 MB。

队列太长，故障时表现为"请求都超时了，但服务还在慢慢处理"；队列太短，突发时大量拒绝。**队列是缓冲，不是仓库。** 它应该吸收短时抖动，而不是掩盖长期能力不足。

优先级任务用 `PriorityBlockingQueue` 时要小心：它是无界的，且低优先级任务可能饿死。更好的做法是分多个队列/线程池，按优先级隔离资源，而不是在一个池里靠优先级抢。

## 一个具体例子

某服务用固定线程池处理订单导入：

```java
ExecutorService pool = Executors.newFixedThreadPool(8);

void importOrders(List<Order> orders) {
    for (Order order : orders) {
        pool.submit(() -> {
            importOne(order);   // 里面可能抛异常
        });
    }
}
```

上线后两个症状同时出现：

1. 内存缓慢上涨，Full GC 后也降不回原来的水位；
2. 部分订单永远没导入，但日志里没有任何错误。

第一个问题的根因是 `newFixedThreadPool` 用的是无界 `LinkedBlockingQueue`。上游导入速度是每秒几千条，下游处理只有每秒几百条，任务在队列里越堆越多。每个任务闭包都持有 `Order` 对象，队列就成了一个只进不出的集合，直到 OOM。

第二个问题的根因是 `submit` 吞异常。`importOne` 抛出的异常被存进 `Future`，没人 `get`，所以既没有日志也没有告警；工作线程继续处理下一个任务，看起来"一切正常"。

修复分三步：

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(2000),
    new ThreadFactory() {
        private final AtomicInteger seq = new AtomicInteger();
        public Thread newThread(Runnable task) {
            return new Thread(task, "order-import-" + seq.incrementAndGet());
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy()
);

void importOrders(List<Order> orders) {
    for (Order order : orders) {
        pool.execute(() -> {           // execute：未捕获异常会走 UncaughtExceptionHandler
            try {
                importOne(order);
            } catch (Throwable error) {
                log.error("import failed, orderId={}", order.id(), error);
                throw error;           // 保留失败信号，交给上层统计
            }
        });
    }
}
```

- 队列改成有界 `2000`，满了用 `CallerRunsPolicy` 让提交线程自己跑，天然限流；
- 线程起了名字，`jstack` 里能直接看出是导入线程；
- 用 `execute` 并在任务内记录异常，失败不再静默。

如果导入是批量接口，更好的做法是一次提交一批，而不是每个订单一个任务。任务粒度太细，队列和线程调度的开销会超过业务本身。

## 常见误区

### 误区：用了 ConcurrentHashMap 就整个逻辑线程安全

**你以为**：容器是线程安全的，围绕它写的代码也安全。
**其实**：容器只保证**单个方法**的原子性。`if (!map.containsKey(k)) map.put(k, v)` 仍然是先查后放，两个线程可能都通过检查。要用 `putIfAbsent` / `computeIfAbsent` / `merge` 把复合操作交给容器。
**怎么验证**：并发执行上面这段，统计是否出现重复放入或覆盖；把写法换成 `putIfAbsent` 再跑一遍对比。

### 误区：CopyOnWriteArrayList 读快，所以哪里都能用

**你以为**：读多写少的场景一律 COW。
**其实**：COW 的写是复制整个数组，列表大或写频繁时，内存分配和 GC 开销会远超收益；而且旧迭代器看不到新元素，依赖"写后立刻可见"的逻辑会出错。
**怎么验证**：往一个十万元素的 COW 列表里循环 `add`，观察耗时和 GC；再和 `ArrayList` + 锁对比。写多读少时 COW 明显更慢。

### 误区：BlockingQueue 的 put/take 很安全，阻塞一下没关系

**你以为**：阻塞只是等一等，不会出问题。
**其实**：没有超时的 `put` / `take` 可能永久阻塞。生产者在一个没人消费的队列上 `put`，消费者在一个没人生产的队列上 `take`，线程会一直挂着；停机时也无法优雅退出。线程池里阻塞的 worker 还会占住名额，导致其他任务排队。
**怎么验证**：起一个只有生产者、没有消费者的队列，调用 `put` 直到满，然后 `jstack` 看线程停在 `ArrayBlockingQueue.put` 上；再用 `poll(timeout)` 对比退出行为。

### 误区：`size()` 可以用来做限流和分页

**你以为**：`ConcurrentHashMap.size()` 返回当前元素个数，和单线程一样准。
**其实**：它是 `baseCount` 加多个 `CounterCell` 的和，求和过程中其他线程还在更新，所以只是估计值；并发高时可能偏差很大。
**怎么验证**：多个线程持续插入，同时另一个线程反复读 `size()`，观察它是否单调、是否和实际插入数一致。需要精确计数时用 `LongAdder` 或数据库。

### 误区：Executors 的工厂方法可以直接上生产

**你以为**：`newFixedThreadPool` / `newCachedThreadPool` 是官方推荐，默认配置够用。
**其实**：`newFixedThreadPool` 和 `newSingleThreadExecutor` 用无界队列，可能 OOM；`newCachedThreadPool` 用 `SynchronousQueue` 且最大线程数是 `Integer.MAX_VALUE`，可能线程爆炸。生产环境应显式构造 `ThreadPoolExecutor`，给出有界队列、线程命名和拒绝策略。
**怎么验证**：用 `newFixedThreadPool` 提交远超处理能力的任务，观察队列大小和堆增长；用 `newCachedThreadPool` 提交大量阻塞任务，观察线程数。

## 小结

并发容器的价值不在于"帮你加锁"，而在于**把正确的一致性契约封装好**：

- `ConcurrentHashMap`：单操作原子、`size()` 弱一致、复合操作要用原子方法、迭代器弱一致、不允许 null；
- `CopyOnWriteArrayList`：读无锁、写复制、迭代器快照，只适合读多写少的小列表；
- `BlockingQueue`：用 `put` / `take` 做背压，但要有界、要能中断、要处理异常；
- 线程池：队列决定堆积位置，工厂方法的默认队列大多不适合生产。

选型时先问三个问题：**我需要多强的原子性？读到的数据可以多旧？队列满了以后谁来承担压力？** 答完这三个问题，容器基本就定了。
