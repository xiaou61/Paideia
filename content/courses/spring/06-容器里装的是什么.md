# 06 · 容器里装的是什么

## 启动日志里那行 `Pre-instantiating singletons`，默认看不到

第 5 课的容器是「`register` 只写单子，`getBean` 才造对象」。拿这个模型去看真实的 Spring 应用，最想确认的一件事很朴素：**启动跑完的那一刻，到底有几个对象已经存在了。**

我先去日志里找证据。我记得有一行 `Pre-instantiating singletons in ... BeanFactory`，按理说它能告诉我「提前造了哪些单例」。默认日志里没有这一行；把 `org.springframework` 开到 `INFO`、再开到 `DEBUG`，还是没有。它得开到 `TRACE`（Spring Boot 3.5.6 / Spring Framework 6.2.11 / JDK 25，本机真跑）：

```text
TRACE 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Pre-instantiating singletons in org.springframework.beans.factory.support.DefaultListableBeanFactory@1e44b638: defining beans [org.springframework.context.annotation.internalConfigurationAnnotationProcessor,...,app,auditLog,reportGenerator,archivedReport,probe,runner,...]; root of factory hierarchy
```

中间的清单我截了（原文是一行几百个名字，中间没有换行）。这里有个细节先记住：`archivedReport` **就在这份名单里**，可它是整个启动过程中**最后一个**被创建的——第三节的 `DEBUG` 行会证明这一点。所以这句话打的是「我准备遍历这份名单」，不是「这些对象已经造好了」。我第一版把这句话当成「实例已就绪」的证据，方向是反的。

换个能直接量的办法：`BeanFactoryPostProcessor`（BFPP）。它的执行时机正好卡在「定义都登记完、业务单例还没开始造」之间，容器自己的两张表都能读。下面这段是本机那个探针，类名叫 `lab06.a1.App`：

```java
@Bean
ReportGenerator reportGenerator() {
    return new ReportGenerator("reportGenerator");
}

@Bean
@Lazy
ReportGenerator archivedReport() {
    return new ReportGenerator("archivedReport");
}

@Bean
static BeanFactoryPostProcessor probe() {
    return beanFactory -> {
        DefaultListableBeanFactory factory = (DefaultListableBeanFactory) beanFactory;
        var byMethod = factory.getBeanDefinition("reportGenerator");
        var byScan = factory.getBeanDefinition("auditLog");
        var single = factory.getBeanDefinition("archivedReport");
        System.out.println("[BFPP] 定义数=" + factory.getBeanDefinitionNames().length
                + " 单例数=" + factory.getSingletonCount()
                + " ReportGenerator 构造次数=" + ReportGenerator.created.get()
                + " 按类型可查到的名字数=" + factory.getBeanNamesForType(Object.class).length);
        System.out.println("[BFPP] reportGenerator: class=" + byMethod.getBeanClassName()
                + " factoryBean=" + byMethod.getFactoryBeanName()
                + " factoryMethod=" + byMethod.getFactoryMethodName()
                + " lazyInit=" + byMethod.isLazyInit());
        System.out.println("[BFPP] auditLog: class=" + byScan.getBeanClassName()
                + " scope=[" + byScan.getScope() + "]"
                + " lazyInit=" + byScan.isLazyInit()
                + " initMethod=" + byScan.getInitMethodName());
        System.out.println("[BFPP] archivedReport(单点 @Lazy)=" + single.isLazyInit());
        System.out.println("[BFPP] 按 ReportGenerator 查到="
                + String.join(",", factory.getBeanNamesForType(ReportGenerator.class)));
        System.out.println("[BFPP] 已有单例=" + String.join(",", factory.getSingletonNames()));
    };
}

@Bean
ApplicationRunner runner(ConfigurableApplicationContext context) {
    return args -> {
        DefaultListableBeanFactory factory = (DefaultListableBeanFactory) context.getBeanFactory();
        System.out.println("[Runner] 启动末尾 定义数=" + factory.getBeanDefinitionCount()
                + " 单例数=" + factory.getSingletonCount()
                + " ReportGenerator 构造次数=" + ReportGenerator.created.get());
        context.getBean("archivedReport");
        System.out.println("[Runner] 取过 archivedReport 后 构造次数=" + ReportGenerator.created.get());
    };
}
```

`ReportGenerator.created` 是个 static `AtomicInteger`，每构造一次加一并打印；`AuditLog` 是个普通的 `@Component`。`probe()` 写成 `static`，否则为了拿到这个 BFPP，得先把它的配置类实例化，探针的时机就往后挪了。

未开全局懒加载的本机输出：

```text
[BFPP] 定义数=56 单例数=21 ReportGenerator 构造次数=0 按类型可查到的名字数=68
[BFPP] reportGenerator: class=null factoryBean=app factoryMethod=reportGenerator lazyInit=false
[BFPP] auditLog: class=lab06.a1.AuditLog scope=[singleton] lazyInit=false initMethod=null
[BFPP] archivedReport(单点 @Lazy)=true
[BFPP] 按 ReportGenerator 查到=reportGenerator,archivedReport
[BFPP] 已有单例=org.springframework.boot.context.ContextIdApplicationContextInitializer$ContextId,autoConfigurationReport,springApplicationArguments,springBootBanner,springBootLoggingSystem,springBootLoggerGroups,springBootLoggingLifecycle,environment,systemProperties,systemEnvironment,applicationStartup,org.springframework.boot.autoconfigure.internalCachingMetadataReaderFactory,org.springframework.context.annotation.internalConfigurationAnnotationProcessor,org.springframework.context.annotation.ConfigurationClassPostProcessor.importRegistry,propertySourcesPlaceholderConfigurer,org.springframework.boot.sql.init.dependency.DatabaseInitializationDependencyConfigurer$DependsOnDatabaseInitializationPostProcessor,org.springframework.context.event.internalEventListenerProcessor,probe,forceAutoProxyCreatorToUseClassProxying,bootstrapExecutorAliasPostProcessor,org.springframework.context.event.internalEventListenerFactory

[ctor] ReportGenerator(reportGenerator) 第 1 次构造
[Runner] 启动末尾 定义数=57 单例数=70 ReportGenerator 构造次数=1
[ctor] ReportGenerator(archivedReport) 第 2 次构造
[Runner] 取过 archivedReport 后 构造次数=2
```

我原来的印象是「扫描结束只有定义、零实例」。实测是 21 个。这 21 个一个业务对象都没有：`environment`、`systemProperties`、几个 `internalXxxProcessor`、`lifecycleProcessor` 之类，全是容器自己要用的人（`ReportGenerator 构造次数=0` 就是证据）。

还有一行值得盯：`getBeanNamesForType(ReportGenerator.class)` 在这个时刻已经能查到 `reportGenerator,archivedReport` 两个名字，而这两条定义里**都没有类名**（`class=null`，只记了 `factoryBean=app` + `factoryMethod=reportGenerator`），构造次数也还是 0。也就是说：按类型查询不需要先造对象，它去读 `@Bean` 方法的返回类型就够了。这一点决定了下面第四节「按类型查」到底是什么机制。

## 定义是一张单子，实例是另一张表

同一个时刻，从 BFPP 里分头读两边的账：

| 你调用 | 拿到什么 |
| --- | --- |
| `getBeanDefinitionNames().length` | `56` |
| `getSingletonCount()` | `21`（全是上面那串容器基础设施） |
| `getBeanDefinition("reportGenerator").getBeanClassName()` | `null`，只有 `factoryBean=app`、`factoryMethod=reportGenerator` |
| `getBeanDefinition("auditLog").getBeanClassName()` | `lab06.a1.AuditLog`（扫描来的定义，这一层就有类） |
| `getBeanDefinition("archivedReport").isLazyInit()` | `true`（单点标了 `@Lazy`） |
| 启动末尾的 `getSingletonCount()` | `70` |

同一个容器在两端的差别是 21 → 70，而定义只从 56 走到 57。**定义的增长是「登记」的节奏，实例的增长是「有人要」的节奏，两者不是一个东西。**「单例」这个词说的是「这个名字最多只有一个实例」，不是「启动时就该有一个」。

`scope=[singleton]` 是默认作用域，这里先当常量看，第 8 课再展开其它作用域。

## 懒加载改的是定义上的一个标记

同一份代码加一个启动参数 `--spring.main.lazy-initialization=true`，先把 BFPP 那几行摊开对比：

```text
[BFPP] 定义数=56 单例数=21 ReportGenerator 构造次数=0 按类型可查到的名字数=68
[BFPP] reportGenerator: class=null factoryBean=app factoryMethod=reportGenerator lazyInit=true
[BFPP] auditLog: class=lab06.a1.AuditLog scope=[singleton] lazyInit=true initMethod=null
[BFPP] archivedReport(单点 @Lazy)=true
[Runner] 启动末尾 定义数=57 单例数=43 ReportGenerator 构造次数=0
[ctor] ReportGenerator(archivedReport) 第 1 次构造
[Runner] 取过 archivedReport 后 构造次数=1
```

定义还是那些定义（56、57），作用域没变，变的是**每条定义的 `lazyInit` 从 `false` 变 `true`**——连扫描来的 `auditLog` 也被改成了 `true`。结果是启动末尾单例从 70 掉到 43，业务对象的构造次数从 1 掉到 0。所以这个开关不是一个「跳过某些创建」的分支，它是把标记刷到定义上，然后让「预实例化」这一步按标记筛。

筛的过程能从 `DEBUG` 日志里逐条看到。下面这次是**没开全局开关**、只给 `archivedReport` 单点标了 `@Lazy`：

```text
DEBUG 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Creating shared instance of singleton bean 'app'
DEBUG 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Creating shared instance of singleton bean 'auditLog'
DEBUG 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Creating shared instance of singleton bean 'reportGenerator'
DEBUG 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Creating shared instance of singleton bean 'runner'
...
DEBUG 171208 --- [           main] o.s.b.f.s.DefaultListableBeanFactory     : Creating shared instance of singleton bean 'archivedReport'
```

时间戳和进程号我删了，其余逐字（`--logging.level.org.springframework.beans.factory.support=DEBUG`）。`archivedReport` 那一行排在整串名单的最后，因为它是 `runner` 里那句 `context.getBean("archivedReport")` 触发的，不是启动扫出来的。

代价也很具体。给一个标了懒加载的 `@Component` 在构造器里加一句 `throw new IllegalStateException("boom")`，全局懒加载下启动是成功的，第一次 `getBean` 才炸：

```text
started, BoomReport 构造次数=0
getBean 失败: org.springframework.beans.factory.BeanCreationException
根因: java.lang.IllegalStateException: boom
```

第一条一行是启动期打印的，说明容器认为一切正常；错误从「启动失败、日志里一屏 `APPLICATION FAILED TO START`」变成「运行时第一个摸到它的人拿到 500」。开关的默认值是 `false`（BFPP 里读到的 `lazyInit=false` 就是这个默认值的投影），它有没有被打开、以及打开之后你接受不接受这个代价，是两件事。

## 名字才是主键，按类型是每次算出来的

我第一版在正文里写过一句「容器还有一张『类型 → 名字』的索引，在扫描阶段建立，来源是类自己、它实现的接口、父类的接口」。查下来这句话是错的：6.2.11 里 `DefaultListableBeanFactory` 的 `getBeanNamesForType` 走 `doGetBeanNamesForType`，实现是遍历 `beanDefinitionNames` 逐个 `isTypeMatch`——没有那张反查表，匹配用的是「可赋值」（父类、接口都算），不是「声明了哪些接口」。

拿一个 `AnnotationConfigApplicationContext` 验证这三点：`csvSink` 的类是 `CsvSinkBean extends AbstractSink implements ReportSink`，`pdfSink` 的类是 `PdfSinkBean implements ReportSink`：

```text
按 Object 取到的名字数=15
按 ReportSink 取到的名字=csvSink,pdfSink
按 AbstractSink(父类) 取到的名字=csvSink
getBean(Object.class) 失败: org.springframework.beans.factory.NoUniqueBeanDefinitionException
No qualifying bean of type 'java.lang.Object' available: expected single matching bean but found 15: org.springframework.context.annotation.internalConfigurationAnnotationProcessor,...,csvSink,pdfSink,environment,systemProperties,systemEnvironment,applicationStartup,...,messageSource,applicationEventMulticaster
```

中间的候选我截了两处。三件事分别是：父类能匹配子类；接口能匹配实现类；按 `Object` 取会命中一大片，因为「可赋值给 `Object`」几乎对所有定义成立。所以按 `Object` 取失败不是特例，是「按类型取要求候选唯一」这条规则遇到一位过于宽泛的类型时的必然结果。

同样的规则也会在你没打算按类型取的时候咬人。

## 症状出来时先看哪

下面四行都是本机真跑出来的报错开头（Spring Boot 3.5.6，`APPLICATION FAILED TO START` 的 `Description` 段或异常首行）：

| 症状 | 先看哪 |
| --- | --- |
| `Parameter 0 of constructor in lab06.a3.ReportJob required a single bean, but 2 were found:` | 同一个接口有两个实现，注入点按类型取，候选不唯一。要么给其中一个 `@Primary`，要么在注入点写 `@Qualifier`，要么把消费方改成接收多个（`List<T>` / `Map<String, T>`） |
| `No qualifying bean of type 'java.lang.Object' available: expected single matching bean but found 15` | 别按 `Object` 这种过宽的类型取。候选数是算出来的，不是有人登记的 |
| `ConflictingBeanDefinitionException: Annotation-specified bean name 'userService' for bean class [lab06.a6.invoice.UserService] conflicts with existing, non-compatible bean definition of same name and class [lab06.a6.audit.UserService]` | 默认 bean 名是「类名首字母小写」，不同包的两个 `UserService` 会撞在同一条定义名上。给至少一个显式命名（`@Service("invoiceUserService")`），或者只扫其中一个包 |
| 启动成功，第一次调用才抛 `BeanCreationException` | 有人把创建推后了：全局 `lazy-initialization`、或那个 Bean 上标了 `@Lazy`。翻回上一节的 BFPP 输出看 `lazyInit` |

第三行值得单独说一句：它发生在**扫描阶段**，堆栈里根本没有实例化的事（`ComponentScanAnnotationParser.parse` → `ClassPathBeanDefinitionScanner.checkCandidate`）。这也是一处「两层」的旁证——名字冲突在写定义的时候就爆了。

## `ApplicationContext` 不是一个包着 `BeanFactory` 的壳

第一版还有一句「`BeanFactory` 是 `ApplicationContext` 内部的一个字段」，也不准确。`javap` 看 6.2.11：

```text
public interface org.springframework.context.ApplicationContext extends org.springframework.core.env.EnvironmentCapable,org.springframework.beans.factory.ListableBeanFactory,org.springframework.beans.factory.HierarchicalBeanFactory,org.springframework.context.MessageSource,org.springframework.context.ApplicationEventPublisher,org.springframework.core.io.support.ResourcePatternResolver
```

`ApplicationContext` 自己就 `extends ListableBeanFactory`，所以它「是一个」`BeanFactory`，可以直接 `getBean`。`AbstractApplicationContext` 里没有那个字段，只有一个抽象方法 `public abstract ConfigurableListableBeanFactory getBeanFactory()`；真正持有它的是 `GenericApplicationContext`：

```text
private final org.springframework.beans.factory.support.DefaultListableBeanFactory beanFactory;
```

两者的真实差别不在类型关系，而在谁会去触发「按定义造单例」。同一段程序里先手搓一个裸 `DefaultListableBeanFactory`，再起一个 `AnnotationConfigApplicationContext`：

```text
裸 BeanFactory 注册后: 定义数=1 单例数=0 构造次数=0
[ctor] ReportGenerator 第 1 次构造
裸 BeanFactory getBean 后: 单例数=1 构造次数=1
[ctor] ReportGenerator 第 2 次构造
ApplicationContext refresh 后(还没 getBean): 定义数=7 单例数=15 构造次数=2
```

裸的 `DefaultListableBeanFactory` 注册完什么都不造，`getBean` 才造。`AnnotationConfigApplicationContext` 在构造器里就跑完了 `refresh()`，还没 `getBean`，`@Bean` 方法已经执行过（构造次数 2），单例表已经 15 个。触发点在 `refresh()` 末尾：`AbstractApplicationContext` 的字节码里能看到它调 `ConfigurableListableBeanFactory.preInstantiateSingletons()`——也就是第一节那句 `TRACE` 打的地方。

所以「用 `ApplicationContext` 时错误暴露得更早」的说法要落到具体机制上：不是它多包了一层，而是它的 `refresh()` 里有一段主动按名单造单例的代码，而裸 `BeanFactory` 要等你逐个 `getBean`。

## 跑一遍

下面不是 Spring，是一个把本文三条规则压小的玩具容器：定义与实例分两张表；标了懒的定义不在 `refresh` 里造；按类型取要求候选唯一，并且父类能匹配子类。

<!-- run -->
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class Main {

    // 第一层：只有「怎么造」，没有对象
    static final class Definition {
        final String name;
        final Class<?> type;
        final boolean lazy;

        Definition(String name, Class<?> type, boolean lazy) {
            this.name = name;
            this.type = type;
            this.lazy = lazy;
        }
    }

    static class ReportGenerator {
        ReportGenerator() {
            this("reportGenerator");
        }

        ReportGenerator(String label) {
            System.out.println("构造 " + label);
        }
    }

    static final class ArchivedReport extends ReportGenerator {
        ArchivedReport() {
            super("archivedReport");
        }
    }

    static final class AuditLog {
        AuditLog() {
            System.out.println("构造 auditLog");
        }
    }

    static final class Container {
        private final Map<String, Definition> definitions = new LinkedHashMap<>();
        private final Map<String, Object> singletons = new LinkedHashMap<>();

        void register(String name, Class<?> type, boolean lazy) {
            definitions.put(name, new Definition(name, type, lazy));
        }

        // 第二层：refresh 只造没标懒的那些
        void refresh() {
            for (Definition definition : definitions.values()) {
                if (!definition.lazy) {
                    create(definition);
                }
            }
        }

        Object get(String name) {
            Definition definition = definitions.get(name);
            if (definition == null) {
                throw new IllegalStateException("没有这个定义: " + name);
            }
            return create(definition);
        }

        // 按类型取：遍历定义逐个匹配，候选必须唯一
        Object get(Class<?> type) {
            List<String> candidates = new ArrayList<>();
            for (Definition definition : definitions.values()) {
                if (type.isAssignableFrom(definition.type)) {
                    candidates.add(definition.name);
                }
            }
            if (candidates.size() != 1) {
                throw new IllegalStateException("候选 " + candidates.size() + " 个: " + candidates);
            }
            return get(candidates.get(0));
        }

        private Object create(Definition definition) {
            Object existing = singletons.get(definition.name);
            if (existing != null) {
                return existing;
            }
            try {
                Object made = definition.type.getDeclaredConstructor().newInstance();
                singletons.put(definition.name, made);
                return made;
            } catch (ReflectiveOperationException error) {
                throw new IllegalStateException("创建失败: " + definition.name, error);
            }
        }

        int definitionCount() {
            return definitions.size();
        }

        int singletonCount() {
            return singletons.size();
        }
    }

    public static void main(String[] args) {
        Container container = new Container();
        container.register("reportGenerator", ReportGenerator.class, false);
        container.register("archivedReport", ArchivedReport.class, true);
        container.register("auditLog", AuditLog.class, false);
        System.out.println("注册 " + container.definitionCount() + " 个定义，实例 "
                + container.singletonCount() + " 个");

        container.refresh();
        System.out.println("refresh 后实例 " + container.singletonCount() + " 个（archivedReport 还没造）");

        try {
            container.get(ReportGenerator.class);
        } catch (IllegalStateException error) {
            System.out.println("按类型取 ReportGenerator: " + error.getMessage());
        }

        container.get("archivedReport");
        System.out.println("按名字要过 archivedReport，实例 " + container.singletonCount() + " 个");

        System.out.println("按类型取 AuditLog: " + container.get(AuditLog.class).getClass().getSimpleName()
                + "，实例 " + container.singletonCount() + " 个");
    }
}
```
```text
注册 3 个定义，实例 0 个
构造 reportGenerator
构造 auditLog
refresh 后实例 2 个（archivedReport 还没造）
按类型取 ReportGenerator: 候选 2 个: [reportGenerator, archivedReport]
构造 archivedReport
按名字要过 archivedReport，实例 3 个
按类型取 AuditLog: AuditLog，实例 3 个
```

第一行是「定义 3、实例 0」；`refresh` 之后是 2，因为第三条规定只造两条；第四行是按类型取撞上两个候选（子类 `ArchivedReport` 也算 `ReportGenerator`），抛的不是「找不到」，是「不唯一」；最后两行说明按名字和按类型取到的是同一个实例。

## 动手

把下面这几行排成一次完整的、只标了单点 `@Lazy` 的启动时序：从扫描到那个对象被造出来。

```code-challenge
  ],
  "answer": [3, 1, 4, 0, 2, 5],
  "explain": "懒加载不改「怎么造」，只改「谁触发第一次造」：预实例化跳过标了 lazy 的定义，所以启动完成时它只有定义没有实例；第一次按名字要，才走构造并进单例表，之后就是普通单例。注意第 2 步和第 4 步的顺序：名单里一直有它，被跳过的是「造」这一步。"
}
```

**提示**：把「定义」「实例」两张表分开想，顺序就不会错。
