# 06 · 容器里装的是什么

## 这一课你要会

- 分清「描述一个对象怎么造」与「造出来的对象」这两层；
- 说清 `BeanDefinition` 与 `BeanFactory` 各自负责什么；
- 解释延迟初始化为什么可能、以及它带来的代价；
- 知道启动日志里 `BeanFactory` 与 `ApplicationContext` 的差别。

## 为什么

第 5 课的容器把"登记"和"实例"揉在一张表里：`register` 一调用，对象就已经造出来了。这够用来理解 IoC，但解释不了三件事：

1. 为什么有的对象**要到第一次用才创建**（`@Lazy`）；
2. 为什么**原型作用域**每次都要新的，容器却不会每次都重新读注解；
3. 为什么启动日志里有一句 "Pre-instantiating singletons in ... BeanFactory"——它到底在干什么。

答案只有一个：**容器里存了两层东西，而第 5 课只写了一层。**

## 讲解

### 第一层：描述。第二层：实例

| 层 | 里面有什么 | 什么时候产生 |
| --- | --- | --- |
| 定义（`BeanDefinition`） | 类名、作用域、是否懒加载、构造参数、初始化方法、是否 primary | 扫描阶段，一个类一条 |
| 实例 | 真正的对象 | 实例化阶段，按作用域决定造几个 |

分开的好处很直接：**定义可以在不造对象的前提下被查询、修改、排序**。启动时的"扫描 → 条件判断 → 覆盖/让位"全都只动定义，一个对象都还没造。

### 手写一遍

注意 `register` 只写定义，`getBean` 才造对象：

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {

    // 第一层：怎么说清"这个对象怎么造"
    static final class BeanDefinition {
        final String name;
        final Class<?> type;

        BeanDefinition(String name, Class<?> type) {
            this.name = name;
            this.type = type;
        }
    }

    // 第二层：按定义造实例，并且记住造过哪些
    static final class BeanFactory {
        private final Map<String, BeanDefinition> definitions = new LinkedHashMap<>();
        private final Map<String, Object> instances = new LinkedHashMap<>();

        void register(String name, Class<?> type) {
            definitions.put(name, new BeanDefinition(name, type));
        }

        Object getBean(String name) {
            return instances.computeIfAbsent(name, key -> {
                BeanDefinition definition = definitions.get(key);
                try {
                    return definition.type.getDeclaredConstructor().newInstance();
                } catch (ReflectiveOperationException error) {
                    throw new IllegalStateException("创建失败: " + key, error);
                }
            });
        }

        int definitionCount() {
            return definitions.size();
        }

        int instanceCount() {
            return instances.size();
        }
    }

    static final class Greeter {
        static int created;

        Greeter() {
            created++;
        }

        String hello() {
            return "hello";
        }
    }

    public static void main(String[] args) {
        BeanFactory factory = new BeanFactory();
        factory.register("greeter", Greeter.class);
        factory.register("unused", String.class);
        System.out.println("注册了 " + factory.definitionCount() + " 个定义，已创建 "
                + factory.instanceCount() + " 个实例");

        System.out.println(factory.getBean("greeter").getClass().getSimpleName());
        System.out.println(factory.getBean("greeter") == factory.getBean("greeter"));
        System.out.println("Greeter 被创建了 " + Greeter.created + " 次");
        System.out.println("实例数 " + factory.instanceCount());
    }
}
```
```text
注册了 2 个定义，已创建 0 个实例
Greeter
true
Greeter 被创建了 1 次
实例数 1
```

关键在倒数两行：`getBean` 被调用了三次，对象只被创建了一次。这就是"单例 + 定义与实例分离"的全部效果。

### 名字是键，类型也是

上表用的是 `name` 作键。真实容器还有一张"类型 → 名字"的索引，所以 `getBean(Repo.class)` 也能用。这个索引在扫描阶段建立，来源是三样东西：

- 这个类自己（`ClassName.class`）；
- 它实现的所有接口；
- 它父类的所有接口。

所以一个 `class DefaultRepo implements Repo` 被登记后，`Repo`、`DefaultRepo`、甚至 `Object` 都能查到它（`Object` 会因为候选太多而报"不唯一"）。这不是特性，是索引的自然结果——**理解它就能解释"为什么按 Object 取 Bean 会失败"**。

### 延迟初始化：把实例化推到第一次使用

```yaml
spring:
  main:
    lazy-initialization: true
```

打开之后，启动时不造任何单例，第一次 `getBean` 才造。代价很明确：

- **启动变快**，因为省掉了实例化；
- **错误被推迟**：某个 Bean 的构造器会抛异常，现在要等第一个请求打进来才知道；
- **第一个请求变慢**，那一次要现场造对象。

所以生产环境一般**不开**全局懒加载。单点用 `@Lazy` 是另一回事——它常用于"两个对象互相依赖，但其中一个只在特定路径用"的场景。

### `BeanFactory` 与 `ApplicationContext`

启动日志里这两个名字经常一起出现：

| | `BeanFactory` | `ApplicationContext` |
| --- | --- | --- |
| 能力 | 只有容器本身：定义、实例、`getBean` | 容器 + 事件、国际化、资源加载、环境配置 |
| 关系 | 是 `ApplicationContext` 内部的一个字段 | 把它包了一层，再加能力 |

`ApplicationContext` 在启动时会**主动把所有单例造完**（日志里那句 "Pre-instantiating singletons" 就是它），而裸的 `BeanFactory` 不会。这就是"用 `ApplicationContext` 启动时错误暴露得更早"的原因。

## 常见误区

### 误区：容器启动完，所有对象就都造好了

**你以为**：启动日志打完，所有 Bean 都已存在。
**其实**：只有**单例**默认被提前造；原型作用域的每次都要新造，`@Lazy` 的等到第一次使用。所以"启动成功"不等于"所有 Bean 都能正常构造"。
**怎么验证**：给一个 `@Lazy` 的 Bean 构造器里加 `throw new IllegalStateException("boom")`，启动照样成功，第一次用到才炸。

### 误区：`getBean(Object.class)` 能拿到"随便一个"

**你以为**：`Object` 是所有类的父类，按它应该能取到东西。
**其实**：按类型取要求**候选唯一**。`Object` 匹配所有单例，候选不唯一，容器直接报 `NoUniqueBeanDefinitionException`。同理，两个类都实现了同一个接口、又都没标 `@Primary`，按那个接口注入也会报这个错。
**怎么验证**：加第二个 `Repo` 实现，不标 `@Primary`，启动会失败并列出两个候选的 bean 名字。

### 误区：Bean 名字随便取

**你以为**：名字只是给人看的。
**其实**：名字是容器的主键之一。默认名字是"类名首字母小写"（`DefaultRepo` → `defaultRepo`），两个不同包下的同名类会撞在一起，报 `ConflictingBeanDefinitionException`。本项目里给 Bean 显式命名是一个廉价的好习惯。
**怎么验证**：在两个包里各建一个 `UserService`，都标 `@Service`，启动看报错。

## 小结

容器里有两层：定义（怎么说造）与实例（造出来的）。分开之后才有懒加载、条件装配、原型作用域。`ApplicationContext` 包了 `BeanFactory` 并主动提前造完单例，所以它报错更早。名字与类型都是键，按类型取要求候选唯一。
