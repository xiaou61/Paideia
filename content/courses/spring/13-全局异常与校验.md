# 13 · 全局异常与参数校验

## 这一课你要会

- 用 `@RestControllerAdvice` + `@ExceptionHandler` 把异常统一映射成状态码；
- 说清"没有兜底分支"会造出什么样的 bug；
- 用 `@Valid` 把参数校验从业务方法里挪出去；
- 知道 `BindingResult` 与全局异常处理器的取舍。

## 为什么

第 4 课讲过：状态码要真实。但一个人不可能在每个 Controller 方法里都写一遍 `try/catch` 再逐个映射。

更糟的是，漏写一个分支的后果不是"少了一个错误提示"，而是**整个响应变成 500**。曾经真实出现过的一次：业务码算出来是 `40200`（余额不足），HTTP 却是 500——因为异常映射漏了 `default`，前端拿到的是"服务器错误"，于是给用户显示"请稍后再试"，而实际该显示"积分不足，去充值"。

所以这件事值得一处收口。

## 讲解

### 一张映射表加一个兜底

全局异常处理的本质是：**给异常类型登记状态码，查不到的一律 500**。查表用"从具体到宽泛"的第一个匹配。

```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {

    static class ValidationException extends RuntimeException {
        ValidationException(String message) {
            super(message);
        }
    }

    static class NotFoundException extends RuntimeException {
        NotFoundException(String message) {
            super(message);
        }
    }

    static class ConflictException extends RuntimeException {
        ConflictException(String message) {
            super(message);
        }
    }

    static class InsufficientBalanceException extends RuntimeException {
        InsufficientBalanceException(String message) {
            super(message);
        }
    }

    static final class ErrorHandler {
        private final Map<Class<?>, Integer> mapping = new LinkedHashMap<>();

        ErrorHandler() {
            mapping.put(ValidationException.class, 400);
            mapping.put(NotFoundException.class, 404);
            mapping.put(ConflictException.class, 409);
            mapping.put(InsufficientBalanceException.class, 402);
        }

        String handle(RuntimeException error) {
            for (Map.Entry<Class<?>, Integer> entry : mapping.entrySet()) {
                if (entry.getKey().isInstance(error)) {
                    return entry.getValue() + " " + error.getMessage();
                }
            }
            // 兜底必须存在：没有它，未登记的异常会把整个响应变成 500 且不带任何说明
            return 500 + " 服务器内部错误";
        }
    }

    static void call(ErrorHandler handler, Runnable action) {
        try {
            action.run();
            System.out.println("200 ok");
        } catch (RuntimeException error) {
            System.out.println(handler.handle(error));
        }
    }

    public static void main(String[] args) {
        ErrorHandler handler = new ErrorHandler();
        call(handler, () -> {
        });
        call(handler, () -> {
            throw new ValidationException("标题不能为空");
        });
        call(handler, () -> {
            throw new NotFoundException("书籍不存在");
        });
        call(handler, () -> {
            throw new ConflictException("同名书籍已存在");
        });
        call(handler, () -> {
            throw new InsufficientBalanceException("积分不足");
        });
        call(handler, () -> {
            throw new ArithmeticException("/ by zero");
        });
    }
}
```
```text
200 ok
400 标题不能为空
404 书籍不存在
409 同名书籍已存在
402 积分不足
500 服务器内部错误
```

注意最后一行：一个**从没登记过**的异常（`ArithmeticException`）落到了兜底。它返回 500，而不是把异常原样抛给容器——原样抛出去时，客户端可能拿到一页 HTML 错误页，前端 `JSON.parse` 直接崩。

**兜底分支的价值不在"好看"，在"格式一致"**。

### Spring 里怎么写

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ValidationException.class)
    public ResponseEntity<ApiError> onValidation(ValidationException error) {
        return ResponseEntity.badRequest().body(new ApiError("VALIDATION_FAILED", error.getMessage()));
    }

    @ExceptionHandler(ConflictException.class)
    public ResponseEntity<ApiError> onConflict(ConflictException error) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(new ApiError("CONFLICT", error.getMessage()));
    }

    @ExceptionHandler(Exception.class)                 // 兜底：最后匹配
    public ResponseEntity<ApiError> onOther(Exception error) {
        String traceId = UUID.randomUUID().toString();
        log.error("unhandled exception, traceId={}", traceId, error);   // 完整堆栈只进日志
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ApiError("INTERNAL", traceId));               // 响应里只给可搜索的 id
    }
}
```

两件事要记住：

- **匹配规则是"最具体的赢"**，不是声明顺序。所以 `Exception.class` 的兜底不会抢走更具体的处理。
- **响应体里不要放堆栈**。给一个 `traceId`，日志里用同一个 id；用户报障时凭 id 就能定位。

### 参数校验：从"每个方法都写 if"到"声明式"

不用校验框架时：

```java
@PostMapping("/books")
public Book create(@RequestBody BookRequest request) {
    if (request.title() == null || request.title().isBlank()) {
        throw new ValidationException("标题不能为空");
    }
    if (request.title().length() > 120) {
        throw new ValidationException("标题不能超过 120 字");
    }
    if (request.isbn() != null && !request.isbn().matches("\\d{13}")) {
        throw new ValidationException("ISBN 必须是 13 位数字");
    }
    ...
}
```

三条规则占了六行，而且每加一个字段就多一段。用注解声明：

```java
public record BookRequest(
        @NotBlank(message = "标题不能为空")
        @Size(max = 120, message = "标题不能超过 120 字")
        String title,

        @Pattern(regexp = "\\d{13}", message = "ISBN 必须是 13 位数字")
        String isbn) {
}

@PostMapping("/books")
public Book create(@Valid @RequestBody BookRequest request) {
    return service.create(request);          // 到这里，参数一定合法
}
```

`@Valid` 触发校验，失败时抛 `MethodArgumentNotValidException`，默认就是 **400**。要自定义响应体，在全局处理器里加一个分支：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ApiError> onInvalid(MethodArgumentNotValidException error) {
    String detail = error.getBindingResult().getFieldErrors().stream()
            .map(field -> field.getField() + ": " + field.getDefaultMessage())
            .collect(Collectors.joining("; "));
    return ResponseEntity.badRequest().body(new ApiError("VALIDATION_FAILED", detail));
}
```

### `BindingResult` 还是全局处理器

```java
@PostMapping("/books")
public ResponseEntity<?> create(@Valid @RequestBody BookRequest request, BindingResult result) {
    if (result.hasErrors()) {
        return ResponseEntity.badRequest().body(...);   // 自己处理，不抛异常
    }
    ...
}
```

两种风格的差别：

| | 抛异常 + 全局处理器 | 方法签名带 `BindingResult` |
| --- | --- | --- |
| 统一性 | 所有接口一种格式 | 每个方法都要自己拼响应 |
| 可控性 | 只能整体改 | 可以按接口定制 |
| 污染 | 无 | 每个方法多一个参数 |

**默认用全局处理器**。`BindingResult` 只在"这个接口的校验失败要返回业务数据"时才值得用。

### 分组校验：新建和修改的规则不同

```java
public interface OnCreate { }
public interface OnUpdate { }

public record BookRequest(
        @Null(groups = OnCreate.class, message = "新建时不能指定 id")
        @NotNull(groups = OnUpdate.class, message = "修改时必须给 id")
        Long id,

        @NotBlank(groups = {OnCreate.class, OnUpdate.class}, message = "标题不能为空")
        String title) {
}
```

```java
@PostMapping("/books")
public Book create(@Validated(OnCreate.class) @RequestBody BookRequest request) { }

@PutMapping("/books")
public Book update(@Validated(OnUpdate.class) @RequestBody BookRequest request) { }
```

`@Valid` 不支持分组，要用 `@Validated`。这个区别很小的细节，是"为什么我的分组校验不生效"的常见原因。

### 校验和业务规则的分界

- **校验**：这个值本身合不合法（非空、长度、格式、范围）。不需要查询任何数据。
- **业务规则**：这个值在这个上下文里能不能用（这本书是不是已经存在、余额够不够）。需要查询。

分界的判据很简单：**校验失败时不用碰数据库，业务规则失败时必须碰过**。


所以 `@Size(max = 120)` 是校验，`existsByTitle` 是业务规则（抛 `ConflictException`，映射成 409）。两者不要混在一处——混了之后，单元测试要造数据才能查一个长度限制。

## 常见误区

### 误区：把异常转换成响应是 Controller 的事

**你以为**：每个接口自己 catch 自己处理最灵活。
**其实**：一个业务异常会被十几个接口抛出，每个都 catch 一遍就要维护十几份映射。一处漏了就变成 500。收口到一个 `@RestControllerAdvice`，加异常类型只改一处。
**怎么验证**：`rg "catch \(" 在你自己的 controller 包里，数量应该是 0（除了确实要吞掉的那些）。

### 误区：`@Valid` 会校验所有层

**你以为**：在 Controller 上加了 `@Valid`，Service 里接收的对象也一定是合法的。
**其实**：校验只在**被 `@Valid` 标注的那个入口**发生。直接调 Service 的定时任务、内部工具不会经过它。所以 Service 里该有的关键校验还得有——这不是重复，这是"两个入口各自保证"。
**怎么验证**：给 Service 写一个单测，直接传一个空标题，看它是否还抛异常。

### 误区：校验消息随便写，反正用户不看

**你以为**：`message = "参数错误"` 就够了。
**其实**：校验消息是**唯一能告诉用户怎么改的东西**。"标题不能为空" vs "参数错误"，后者会让用户只能猜。而且它是随手就能写好的，成本几乎为零。
**怎么验证**：打开一个表单，故意留空提交，看提示能不能让你知道该填什么。

## 小结

异常收口到一处：一张类型到状态码的表 + 一个必有的兜底。兜底保证格式一致，代价是会静默吞掉忘了登记的异常，所以新增业务异常时要同步登记。参数校验用 `@Valid`，分组用 `@Validated`。校验与业务规则的分界是"失败时要不要查库"。

横切这一章结束。下一章换回 HTTP：返回值怎么变成 JSON，一次请求到底穿过多少层，配置的优先级又是怎么排的。
