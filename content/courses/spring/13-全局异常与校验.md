# 13 · 全局异常与参数校验

## 该 400 的请求回了 500

JDK 25.0.4 + Spring Boot 4.1.1（Spring Framework 7.0.9）的最小 demo，服务在 8080。下面这条命令是原样跑的：

```text
$ curl -i -X POST localhost:8080/books -H 'Content-Type: application/json' -d '{"title":""}'
（curl 进度表略）
HTTP/1.1 500
Content-Type: application/json
Transfer-Encoding: chunked
Date: Thu, 19 Nov 2026 05:04:07 GMT
Connection: close

{"code":"INTERNAL","message":"MethodArgumentNotValidException"}
```

日志里不是“校验没生效”，而是校验抛出的异常被兜底接住了：

```text
ERROR ... demo.BlanketExceptionHandler : blanket handler caught org.springframework.web.bind.MethodArgumentNotValidException
org.springframework.web.bind.MethodArgumentNotValidException: Validation failed for argument [0] ...
```

我第一反应是 `@NotBlank` 没起作用。实际正相反：校验跑了，`MethodArgumentNotValidException` 也抛了；真正的问题是 `@ExceptionHandler(Exception.class)` 把它接住，写死返回 500。

同一个 demo，只切换有没有这个兜底，结果是这样：

| 请求 | 只有 `Exception.class` 兜底 | 去掉兜底 |
| --- | --- | --- |
| `POST /books`，`title` 为空 | 500 `MethodArgumentNotValidException` | 400 |
| `POST /books`，坏 JSON | 500 `HttpMessageNotReadableException` | 400 |
| `GET /nope` | 500 `NoResourceFoundException` | 404 |
| `POST /books/1` | 500 `HttpRequestMethodNotSupportedException` | 405 |

```sketch
{
  "title": "一次校验失败实际走的链路",
  "rows": [
    [
      { "id": "req", "title": "POST /books", "sub": "title 为空", "tone": "gray" },
      { "id": "valid", "title": "@Valid", "sub": "抛 MethodArgumentNotValidException", "tone": "blue" },
      { "id": "specific", "title": "具体 handler", "sub": "400 VALIDATION_FAILED", "tone": "green" },
      { "id": "broad", "title": "Exception 兜底", "sub": "先接住就是 500", "tone": "amber" }
    ]
  ],
  "arrows": [
    { "from": "req", "to": "valid" },
    { "from": "valid", "to": "specific" },
    { "from": "valid", "to": "broad" }
  ]
}
```

这不是说兜底总在具体 handler 之前执行；两条分支是互斥的。只有没有具体映射时，异常才落到 amber 那条。

所以“失败时抛 `MethodArgumentNotValidException`，默认就是 400”这句话，只在没有具体 handler、只有 `Exception.class` 兜底时才会被改写；有具体 handler 时，Spring 仍选最具体的那个。

但把兜底删掉也不是终点：400 会回来，响应体却变成 Boot 默认的 `/error` 结构，不再是项目自己的 `ApiError`。正确做法是让兜底先认异常自带的状态码，只把真正未知的异常映射成 500。

## 40200 / HTTP 500 那次，缺的不是 default

我在练手项目里复现过一个小版本：业务层算出业务码 40200（余额不足；这是另一个项目的数字业务码，下面的 demo 用字符串 code），HTTP 却是 500。上一版讲义把原因写成“异常映射漏了 default”。这个因果是错的。

漏 `default` 的结果是异常落到容器默认处理，仍然是 500；补一个返回 500 的 `default` 也不会变成 402。真正缺的是 `InsufficientBalanceException` 的具体映射。兜底不会抢走具体映射，它抢走的是**没有具体映射**的异常。

这也是全局异常处理最危险的地方：兜底能保证格式一致，但会把“你忘了登记”这件事静默变成一个 500。每加一个业务异常类型，都要同时确认它有映射；否则至少要在兜底里把异常类型打进日志，别让它连痕迹都没有。

## 先手写一遍：查表不是按插入顺序

先用一个小模型把选择顺序跑出来。它只做三件事：框架异常先保留状态码；应用异常按继承深度找最具体的；都找不到才 500。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {

    interface ErrorResponseLike {
        int status();
        String code();
    }

    static class ValidationFailure extends RuntimeException implements ErrorResponseLike {
        ValidationFailure(String message) {
            super(message);
        }
        public int status() {
            return 400;
        }
        public String code() {
            return "VALIDATION_FAILED";
        }
    }

    static class NoRoute extends RuntimeException implements ErrorResponseLike {
        NoRoute(String message) {
            super(message);
        }
        public int status() {
            return 404;
        }
        public String code() {
            return "HTTP_404";
        }
    }

    static class MethodNotAllowed extends RuntimeException implements ErrorResponseLike {
        MethodNotAllowed(String message) {
            super(message);
        }
        public int status() {
            return 405;
        }
        public String code() {
            return "HTTP_405";
        }
    }

    static class BusinessException extends RuntimeException {
        BusinessException(String message) {
            super(message);
        }
    }

    static class NotFoundException extends BusinessException {
        NotFoundException(String message) {
            super(message);
        }
    }

    static class ConflictException extends BusinessException {
        ConflictException(String message) {
            super(message);
        }
    }

    static class InsufficientBalanceException extends BusinessException {
        InsufficientBalanceException(String message) {
            super(message);
        }
    }

    static final class Rule {
        final int status;
        final String code;

        Rule(int status, String code) {
            this.status = status;
            this.code = code;
        }
    }

    static final class Result {
        final int status;
        final String code;
        final Class<?> matched;

        Result(int status, String code, Class<?> matched) {
            this.status = status;
            this.code = code;
            this.matched = matched;
        }

        String render() {
            String suffix = matched == null ? "" : " (" + matched.getSimpleName() + ")";
            return status + " " + code + suffix;
        }
    }

    static final class Handler {
        // 故意先放父类：如果按插入顺序查，BusinessException 会先吃掉所有子类
        private final Map<Class<?>, Rule> mapping = new LinkedHashMap<>();

        Handler() {
            mapping.put(BusinessException.class, new Rule(422, "BUSINESS_RULE"));
            mapping.put(NotFoundException.class, new Rule(404, "NOT_FOUND"));
            mapping.put(ConflictException.class, new Rule(409, "CONFLICT"));
            mapping.put(InsufficientBalanceException.class, new Rule(402, "INSUFFICIENT_BALANCE"));
        }

        Result handle(RuntimeException error) {
            // 框架异常自带状态码，先保留；这一步就是修掉“4xx 变 500”的地方
            if (error instanceof ErrorResponseLike framework) {
                return new Result(framework.status(), framework.code(), error.getClass());
            }

            Class<?> best = null;
            int bestDepth = -1;
            for (Class<?> candidate : mapping.keySet()) {
                if (candidate.isInstance(error)) {
                    int depth = depth(candidate);
                    if (depth > bestDepth) {
                        best = candidate;
                        bestDepth = depth;
                    }
                }
            }
            if (best == null) {
                return new Result(500, "INTERNAL", null);
            }
            Rule rule = mapping.get(best);
            return new Result(rule.status, rule.code, best);
        }

        static int depth(Class<?> type) {
            int depth = 0;
            for (Class<?> cursor = type; cursor != null; cursor = cursor.getSuperclass()) {
                depth++;
            }
            return depth;
        }
    }

    static void call(Handler handler, String label, RuntimeException error) {
        System.out.println(label + " -> " + handler.handle(error).render());
    }

    public static void main(String[] args) {
        Handler handler = new Handler();
        call(handler, "POST /books {}", new ValidationFailure("title 为空"));
        call(handler, "GET /nope", new NoRoute("没有这个路径"));
        call(handler, "POST /books/1", new MethodNotAllowed("只支持 GET"));
        call(handler, "GET /books/999", new NotFoundException("书籍不存在"));
        call(handler, "POST /books（重名）", new ConflictException("同名书籍已存在"));
        call(handler, "POST /books/1/purchase", new InsufficientBalanceException("积分不足"));
        call(handler, "GET /boom", new IllegalStateException("数据库连接池耗尽"));
    }
}
```
```text
POST /books {} -> 400 VALIDATION_FAILED (ValidationFailure)
GET /nope -> 404 HTTP_404 (NoRoute)
POST /books/1 -> 405 HTTP_405 (MethodNotAllowed)
GET /books/999 -> 404 NOT_FOUND (NotFoundException)
POST /books（重名） -> 409 CONFLICT (ConflictException)
POST /books/1/purchase -> 402 INSUFFICIENT_BALANCE (InsufficientBalanceException)
GET /boom -> 500 INTERNAL
```

`BusinessException` 是故意先放进去的，`InsufficientBalanceException` 后放。如果按 `LinkedHashMap` 的插入顺序遍历，`InsufficientBalanceException` 会先命中 `BusinessException`，输出 422；上面输出是 402，因为代码按继承深度排序，**最具体的赢**。

这不是 Spring 源码，只是一个能跑的模型。真实的异常解析器还会考虑 Controller 局部 `@ExceptionHandler`、多个 advice 的 `@Order`、以及异常自身的 `ErrorResponse`；但“框架异常先保状态码、应用异常找最具体类型”这两步，和模型是一致的。

模型里的 `ErrorResponseLike` 对应 Spring 的 `ErrorResponse`；把它写成接口，只是为了让这段代码不依赖 Spring。

## 在 Spring 里把状态码保住

### 先把 validation starter 加上

01 课的 pom 只有 `spring-boot-starter-web`。Boot 3.5/4 的 web starter 不带 validation，`@NotBlank`、`@Size`、`@Pattern` 都不在 classpath 上。加在 `<dependencies>` 里：

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

不加它，`@NotBlank` 连编译都过不了。我在一个只有 web starter 的临时工程里编译，报的是：

```text
[ERROR] ... 程序包jakarta.validation.constraints不存在
[ERROR] ... 找不到符号
  符号:   类 NotBlank
```

加上 starter 后，依赖树里是 API 加实现：

```text
+- org.springframework.boot:spring-boot-starter-validation:jar:4.1.1:compile
|  \- org.hibernate.validator:hibernate-validator:jar:9.1.3.Final:compile
|     \- jakarta.validation:jakarta.validation-api:jar:3.1.1:compile
```

只引 `jakarta.validation-api` 不引实现，注解能编译，但 `@Valid` 没有 Validator 可调，等于纯注释。starter 把实现也带进来，这才是它和只加 API 的区别。

请求体用普通类，不用 record（Java 线第 35 课才讲 record）：

```java
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

public class BookRequest {

    @NotBlank(message = "标题不能为空")
    @Size(max = 120, message = "标题不能超过 120 字")
    private String title;

    @Pattern(regexp = "\\d{13}", message = "ISBN 必须是 13 位数字")
    private String isbn;

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getIsbn() { return isbn; }
    public void setIsbn(String isbn) { this.isbn = isbn; }
}
```

```java
@PostMapping("/books")
public Book create(@Valid @RequestBody BookRequest request) {
    return service.create(request);
}
```

`@Valid` 触发校验，失败时抛 `MethodArgumentNotValidException`。要自定义响应体，就在 advice 里加一个具体分支。

### `ApiError` 和 Logger

原稿用了 `new ApiError(...)` 和 `ApiError.of(error)`，但整篇没有定义 `ApiError`，`ApiError.of(error)` 这个静态方法也不存在；Logger 也没有声明。最小版本就是一个普通类加两个 getter：

```java
public class ApiError {

    private final String code;
    private final String message;

    public ApiError(String code, String message) {
        this.code = code;
        this.message = message;
    }

    public String getCode() { return code; }
    public String getMessage() { return message; }
}
```

处理器里要有这一行，否则 `log.error` 编译不过：

```java
private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);
```

`Book`、`BookService` 沿用第 04 课的书籍例子：`Book` 只有 id/title/isbn 三个字段，`BookService` 用内存 Map 代替数据库。`NotFoundException`、`ConflictException`、`InsufficientBalanceException` 都是只有 `String message` 构造器的 `RuntimeException` 子类；`InsufficientBalanceException` 就是本文要补映射的那个。下面只贴与异常、校验有关的代码。

### 处理器：具体映射 + 先认 `ErrorResponse`

先看具体映射。`MethodArgumentNotValidException`、`NotFoundException`、`ConflictException`、`InsufficientBalanceException` 各有一条：

```java
import java.util.Set;
import java.util.UUID;
import java.util.stream.Collectors;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.web.ErrorResponse;
import org.springframework.web.HttpRequestMethodNotSupportedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.server.ResponseStatusException;
```

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> onInvalid(MethodArgumentNotValidException error) {
        String detail = error.getBindingResult().getFieldErrors().stream()
                .map(field -> field.getField() + ": " + field.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ResponseEntity.badRequest()
                .body(new ApiError("VALIDATION_FAILED", detail));
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<ApiError> onUnreadable(HttpMessageNotReadableException error) {
        return ResponseEntity.badRequest()
                .body(new ApiError("BAD_JSON", "请求体不是合法 JSON"));
    }

    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<ApiError> onNotFound(NotFoundException error) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError("NOT_FOUND", error.getMessage()));
    }

    @ExceptionHandler(ConflictException.class)
    public ResponseEntity<ApiError> onConflict(ConflictException error) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError("CONFLICT", error.getMessage()));
    }

    @ExceptionHandler(InsufficientBalanceException.class)
    public ResponseEntity<ApiError> onBalance(InsufficientBalanceException error) {
        return ResponseEntity.status(HttpStatus.PAYMENT_REQUIRED)
                .body(new ApiError("INSUFFICIENT_BALANCE", error.getMessage()));
    }
```

兜底接在同一个类里。关键在 `ErrorResponse` 分支：它带着框架已经算好的状态码，先把这个状态码拿出来，不要直接 500：

```java
    @ExceptionHandler(DuplicateKeyException.class)
    public ResponseEntity<ApiError> onDuplicate(DuplicateKeyException error) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError("CONFLICT", "同名书籍已存在"));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> onOther(Exception error) {
        if (error instanceof HttpRequestMethodNotSupportedException methodError) {
            ResponseEntity.BodyBuilder builder = ResponseEntity.status(HttpStatus.METHOD_NOT_ALLOWED);
            Set<HttpMethod> supported = methodError.getSupportedHttpMethods();
            if (supported != null) {
                builder.allow(supported.toArray(new HttpMethod[0]));
            }
            return builder.body(new ApiError("HTTP_405", methodError.getMessage()));
        }
        if (error instanceof ResponseStatusException response) {
            String reason = response.getReason() == null
                    ? response.getStatusCode().toString()
                    : response.getReason();
            return ResponseEntity.status(response.getStatusCode())
                    .body(new ApiError("HTTP_" + response.getStatusCode().value(), reason));
        }
        if (error instanceof ErrorResponse response) {
            HttpStatusCode status = response.getStatusCode();
            String detail = response.getBody().getDetail();
            return ResponseEntity.status(status)
                    .body(new ApiError("HTTP_" + status.value(), detail == null ? status.toString() : detail));
        }
        String traceId = UUID.randomUUID().toString();
        log.error("unhandled exception traceId={}", traceId, error);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ApiError("INTERNAL", "服务器内部错误"));
    }
}
```

`HttpRequestMethodNotSupportedException` 那个分支不是装饰。方案②自己拼 `ResponseEntity` 时，框架原本附在 405 上的 `Allow: GET` 不会自动带过来；下面的 405 输出里能同时看到 `Allow` 和 JSON，是因为这里手动补了。

`DuplicateKeyException` 来自 `spring-tx`；用 JdbcTemplate/MyBatis 时它本来就在。JPA 可能把唯一键冲突包成 `DataIntegrityViolationException`，按你的持久层确认实际类型。

### 跑出来的状态码

下面每个响应都省略了 `Date`、`Transfer-Encoding`、`Content-Length` 三个头，状态码、`Content-Type` 和 body 是原文。

```text
$ curl -i localhost:8080/books/1
HTTP/1.1 200
Content-Type: application/json

{"id":1,"title":"深入理解 Java 虚拟机","isbn":"9787111544937"}

$ curl -i -X POST localhost:8080/books -H 'Content-Type: application/json' -d '{"title":""}'
HTTP/1.1 400
Content-Type: application/json

{"code":"VALIDATION_FAILED","message":"title: 标题不能为空"}

$ curl -i -X POST localhost:8080/books -H 'Content-Type: application/json' -d '{"title":'
HTTP/1.1 400
Content-Type: application/json

{"code":"BAD_JSON","message":"请求体不是合法 JSON"}

$ curl -i localhost:8080/nope
HTTP/1.1 404
Content-Type: application/json

{"code":"HTTP_404","message":"No static resource nope."}

$ curl -i -X POST localhost:8080/books/1
HTTP/1.1 405
Allow: GET
Content-Type: application/json

{"code":"HTTP_405","message":"Request method 'POST' is not supported"}

$ curl -i -X POST localhost:8080/books/1/purchase?points=100
HTTP/1.1 402
Content-Type: application/json

{"code":"INSUFFICIENT_BALANCE","message":"积分不足，还差 50"}

$ curl -i localhost:8080/books/boom
HTTP/1.1 500
Content-Type: application/json

{"code":"INTERNAL","message":"服务器内部错误"}
```

这组里最重要的是 400、404、405 三条：同一个兜底，改之前全是 500，改之后保留了框架原来的状态码。409 的输出在下面的并发小节里。

检查有没有重复的异常映射：在项目根目录跑 `rg -n "@ExceptionHandler|catch \(" src/main/java`。Windows 上把 `src/main/java` 换成 `src\main\java` 也行，`rg` 两种都认。重点不是 catch 数量为 0，而是同一个异常类型是不是在多处各写了一套状态码；重复映射迟早会分叉。

## 两条正确路线，选一条

**路线①：继承 `ResponseEntityExceptionHandler`。** 框架异常由父类维护，400、404、405 以及一部分头信息不用你逐条写。代价是父类默认返回 `ProblemDetail`，要和上面的 `ApiError` 统一，还得覆写 `handleExceptionInternal` 或对应的方法。

**路线②：兜底里先判断 `ErrorResponse` / `ResponseStatusException`。** 就是上面的写法。一个方法统一 `ApiError`，但要自己保状态码，还要记得补 405 的 `Allow`；如果 Spring 以后新增一个不实现 `ErrorResponse` 的框架异常，它仍可能被兜底成 500。

本文选②，因为 demo 的错误体已经统一成 `ApiError`，少一层 body 转换。你若更想让框架维护那张异常表，选①；但“继承之后 body 就自动变成你的 `ApiError`”是错的，覆写那一步不能省。

## `BindingResult`：什么时候让方法自己处理

普通创建接口的坏请求体应该是 400。但有一类接口，校验失败本身就是业务结果，比如批量导入、预检报告：

`ImportResult` 是演示用的普通类，只有 `accepted`、`reason`、`book` 三个字段和对应 getter。

```java
@PostMapping("/books/import")
public ImportResult importOne(@Valid @RequestBody BookRequest request, BindingResult result) {
    if (result.hasErrors()) {
        String reason = result.getFieldErrors().stream()
                .map(error -> error.getField() + ": " + error.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return new ImportResult(false, reason, null);
    }
    return new ImportResult(true, null, service.create(request));
}
```

同一个坏请求体，两个接口的结果不同：

```text
$ curl -i -X POST localhost:8080/books -H 'Content-Type: application/json' -d '{"title":""}'
HTTP/1.1 400
{"code":"VALIDATION_FAILED","message":"title: 标题不能为空"}

$ curl -i -X POST localhost:8080/books/import -H 'Content-Type: application/json' -d '{"title":""}'
HTTP/1.1 200
{"accepted":false,"reason":"title: 标题不能为空","book":null}
```

区别不是校验强度，而是失败是不是这个接口的业务数据。导入接口要把“第几行为什么没收”返回给调用方，所以它继续走 200；普通创建接口没有这种数据可返回，用 400 更诚实。

| | 抛异常 + 全局处理器 | 方法签名带 `BindingResult` |
| --- | --- | --- |
| 状态码 | handler 决定；本文统一 400 | 方法自己决定，可以继续 200 |
| 响应体 | 统一错误结构 | 可以是业务数据，如导入报告 |
| 局部化 | `basePackages` / `@Order` / Controller 内 handler | 天然只影响这个方法 |
| 代价 | 异常路径不进入方法体 | 每个方法多一个参数，容易忘记检查 |

上一版说“全局处理器只能整体改”，不准确。`@RestControllerAdvice(basePackages = "com.example.admin")` 只覆盖某个包；多个 advice 可以用 `@Order` 排序（数值小的先）；Controller 里自己写 `@ExceptionHandler`，对这个 Controller 优先。所谓“全局”，只是默认范围大，不是没有局部化手段。

## 分组校验：同一个请求体，新建通过，修改失败

新建和修改的规则不同，但请求体可以共用一个类。用两个空接口做 group：

这段的 import 是 `jakarta.validation.constraints.Null/NotNull/NotBlank`。

```java
public interface OnCreate { }
public interface OnUpdate { }

public class BookMutationRequest {

    @Null(groups = OnCreate.class, message = "新建时不能指定 id")
    @NotNull(groups = OnUpdate.class, message = "修改时必须给 id")
    private Long id;

    @NotBlank(groups = {OnCreate.class, OnUpdate.class}, message = "标题不能为空")
    private String title;

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
}
```

Controller 用 `@Validated` 指定 group：

```java
@PostMapping("/books/shelf")
public Book create(@Validated(OnCreate.class) @RequestBody BookMutationRequest request) {
    BookRequest normal = new BookRequest();
    normal.setTitle(request.getTitle());   // 其余字段按你的 DTO 映射补
    return service.create(normal);
}

@PutMapping("/books/shelf")
public Book update(@Validated(OnUpdate.class) @RequestBody BookMutationRequest request) {
    return service.find(request.getId());
}
```

两个请求体一模一样，差别只在 HTTP 方法和 group，结果完全不同：

```text
$ curl -i -X POST localhost:8080/books/shelf -H 'Content-Type: application/json' -d '{"title":"球状闪电"}'
HTTP/1.1 201
{"id":3,"title":"球状闪电","isbn":null}

$ curl -i -X PUT localhost:8080/books/shelf -H 'Content-Type: application/json' -d '{"title":"球状闪电"}'
HTTP/1.1 400
{"code":"VALIDATION_FAILED","message":"id: 修改时必须给 id"}
```

新建通过，是因为 `OnCreate` 只要求 `id` 为 null；修改失败，是因为 `OnUpdate` 要求 `id` 非 null。`@Valid` 不支持分组，`@Validated` 才带 group。

`id` 是 3，因为 demo 启动时预置了两本书（id 1、2）；你自己的库从 1 开始。

还有一个容易踩的点：约束一旦声明了 `groups`，就不在 Default 组里。这个类只配 `@Validated` 用；如果你又拿 `@Valid` 调它，一条约束都不会跑。

## 校验通过不等于业务合法

`@Valid` 通过时，只能说“到这里，声明的格式校验通过”。它证明不了：

- 这本书是不是已经存在（`existsByTitle` 要查库）；
- 用户余额够不够（要查账户）；
- 这个用户有没有权限改这本书（要查授权）。

而且 `@Valid` 只在校验入口发生。Controller 参数上的 `@Valid` 不会跟着 Service 走；定时任务、内部工具直接调 Service 时，根本不经过它。所以 Service 里的关键不变量还要自己守，这不是重复，是两个入口各自保证。

分界的判据还是那一句：**校验失败时不用碰数据库，业务规则失败时必须碰过**。`@Size(max = 120)` 是校验；`existsByTitle` 是业务规则。

## `existsByTitle` 只是提示，唯一索引才是约束

先查再插有一个 TOCTOU：两个并发请求都查到“不存在”，然后都去插入。`existsByTitle` 只改善常见情况的提示，不构成约束。

```java
public Book create(BookRequest request) {
    if (repository.existsByTitle(request.getTitle())) {
        throw new ConflictException("同名书籍已存在");   // 友好提示，不是并发保证
    }
    return repository.insert(request);                    // 这里可能撞唯一索引
}
```

真正的约束在数据库：

```sql
ALTER TABLE book ADD CONSTRAINT uk_book_title UNIQUE (title);
```

如果表里已经有重复的 `title`，这条 `ALTER TABLE` 会直接失败；先把重复数据清理或合并，再加索引。

插入时撞到唯一键，Spring 的 JdbcTemplate/MyBatis 会把 MySQL 唯一键冲突翻译成 `DuplicateKeyException`。把它映射成 409：

```java
@ExceptionHandler(DuplicateKeyException.class)
public ResponseEntity<ApiError> onDuplicate(DuplicateKeyException error) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ApiError("CONFLICT", "同名书籍已存在"));
}
```

先创建同名的第一条，再发一次：

```text
$ curl -i -X POST localhost:8080/books -H 'Content-Type: application/json' -d '{"title":"三体","isbn":"9787536692930"}'
HTTP/1.1 409
Content-Type: application/json

{"code":"CONFLICT","message":"同名书籍已存在"}
```

这条 409 走的是预检查分支；我也单独打了一枪 `DuplicateKeyException` 分支，返回同一个 409。但没有做并发压测，竞态窗口是按代码推出来的，不是压出来的。

## 402 是业务约定，不是 HTTP 语义的必然

`InsufficientBalanceException` 映射成 402 `Payment Required`（demo 里余额固定 50，`points=100` 一定不够）：

```text
$ curl -i -X POST localhost:8080/books/1/purchase?points=100
HTTP/1.1 402
Content-Type: application/json

{"code":"INSUFFICIENT_BALANCE","message":"积分不足，还差 50"}
```

402 的官方短语是 Payment Required。积分不足不是支付失败，但前端要做的动作是“去充值”，所以我在这个练手项目里用了它。换 409（当前状态冲突）或 422（格式对但语义不合法）也讲得通；代价是前端要么多读一个业务码，要么把 402 的特殊分支并进 409/422。选哪个都行，写进 API 契约并全项目统一，别一个接口 402、另一个接口 409。

## traceId 只进日志，不进响应体

500 的响应只有通用文案，没有堆栈，也没有 traceId：

```text
HTTP/1.1 500
Content-Type: application/json

{"code":"INTERNAL","message":"服务器内部错误"}
```

同一时刻的日志里才有 traceId 和异常：

```text
ERROR ... demo.GlobalExceptionHandler : unhandled exception traceId=95948ee6-4be9-42d2-a5d7-8c81cfbdd0d0
java.lang.IllegalStateException: 数据库连接池耗尽
	at demo.BookController.boom(BookController.java:79)
```

`traceId` 只进日志，不进响应体。响应里放它，等于把内部关联 id 交给客户端；而客户端真正需要的是“服务器错了”，不是“错在哪个内部调用”。用户报障时用发生时间 + URL 查日志；如果确实要一个用户可报的 id，那应该是单独的 request id，并且同样不能带内部异常信息。

500 的 `message` 也不要放 `error.getMessage()`。它可能包含 SQL、文件路径、内部主机名；这些只该在日志里。

## 客户端拿到 JSON 还是 HTML，由 `Accept` 决定

“客户端可能拿到 HTML”这句话太粗。实际是内容协商：同一个没有处理器的 404，`Accept` 不同，结果不同。

```text
$ curl -i localhost:8080/nope -H 'Accept: application/json'
HTTP/1.1 404
Content-Type: application/json

{"timestamp":"2026-11-19T04:59:43.775Z","status":404,"error":"Not Found","path":"/nope"}

$ curl -i localhost:8080/nope -H 'Accept: text/html'
HTTP/1.1 404
Content-Type: text/html;charset=UTF-8

<html><body><h1>Whitelabel Error Page</h1>...
```

浏览器地址栏默认更偏好 `text/html`，所以更容易看到后者；API 客户端发 `Accept: application/json`，才稳定拿 JSON。不是“客户端一定拿到 HTML”，是 `Accept` 决定谁赢。

即使你写了返回 `ApiError` 的 advice，`Accept: text/html` 时也可能落到容器的 HTML 错误页——我实测就是这样。如果你要求 API 永远 JSON，最稳的是让客户端固定 `Accept: application/json`；也可以在响应上显式设 `Content-Type`，但那是在覆盖内容协商，本文没有单独验证那条路径。

## 还差的

- 没做并发压测：`existsByTitle` 的 TOCTOU 是代码层分析，`DuplicateKeyException` 分支是手工触发的；没有用两个并发请求真撞唯一索引。
- 没跑路线①：正文只给了 `ResponseEntityExceptionHandler` 的取舍，没有把它的默认 `ProblemDetail` 覆写成 `ApiError`；如果你选①，`handleExceptionInternal` 那一步要自己补。
- 没接真实数据库：demo 用内存 Map 和手工抛 `DuplicateKeyException` 模拟唯一索引；MySQL/JPA 实际可能包成 `DataIntegrityViolationException`，要按持久层确认。
- 没做全链路 trace：`traceId` 只在单机日志里生成，没有接 Micrometer Tracing、网关或日志平台；多实例下不能靠它串请求。
- 没验证 3.5.x：实测是 Temurin 25.0.4 + Spring Boot 4.1.1 / Spring Framework 7.0.9；`HttpStatus.UNPROCESSABLE_CONTENT` 等常量在 3.5.x 上可能不同，照抄前先对齐版本。
