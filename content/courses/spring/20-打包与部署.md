# 20 · 打包与部署

## 这一课你要会

- 说清 `java -jar app.jar` 为什么能跑（`MANIFEST` 里写了什么）；
- 知道 Boot 的 jar 里那几层目录各是什么，以及为什么不能拆开拷；
- 看懂六条最常见的启动失败报错，知道各自该查哪里；
- 把服务装成一个能被重启、能看日志的常驻进程。

## 为什么

开发时用 IDE 点绿三角就能跑，部署时换一种方式——很多问题只在这一步暴露：`ClassNotFoundException`、`no main manifest attribute`、端口被占、连不上库、迁移冲突。

这些报错的共同点是：**它们都在启动的最初几秒内发生**，而且信息量极大。能读懂它们，部署就从"试运气"变成"看日志"。

## 讲解

### `java -jar` 到底执行了什么

```bash
java -jar app.jar
```

JVM 打开 jar，读 `META-INF/MANIFEST.MF` 里的 `Main-Class`，调用那个类的 `main`。Spring Boot 的 `Main-Class` 不是你写的启动类，而是：

```text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.demo.DemoApplication
```

`JarLauncher` 是那个"先建好 classpath、再调你的 main"的入口。它存在的理由：Boot 的 jar 里嵌套了 jar（依赖都在 `BOOT-INF/lib/` 下），标准 JVM 的 `-cp` 不能直接加载嵌套 jar 里的类。`JarLauncher` 自己实现了嵌套 jar 的类加载。

jar 的目录结构：

```text
BOOT-INF/
├── classes/          ← 你的编译产物
└── lib/              ← 所有依赖 jar（嵌套）
META-INF/
└── MANIFEST.MF
org/springframework/boot/loader/   ← 启动器
```

两个实践推论：

- **不要手工往 jar 里塞文件**。重打包时用 `jar cfm` 会把嵌套的依赖 jar 再压一遍，Boot 的启动器解不开，应用直接起不来。
- **不要把 `BOOT-INF/lib` 拆出来用 `-cp` 跑**。嵌套 jar 的类加载逻辑就在启动器里，绕开它等于自己实现一遍。

### 启动就是一串检查，第一个失败的立刻中止

`SpringApplication.run` 的顺序大致是：

```text
读配置（application.yml + profile + 环境变量 + 命令行）
  → 建 ApplicationContext
  → 扫描并注册 BeanDefinition
  → 处理条件（自动配置生效/让位）
  → 实例化单例（这里暴露依赖问题）
  → 启动内嵌 Web 服务器（这里暴露端口问题）
  → 跑 Flyway 迁移（如果配了）
  → 发布 ApplicationReadyEvent（此时才算"起来了"）
```

下面这段代码把这条链打印出来。它不启动任何东西，但它就是排查启动失败的心智模型：

<!-- run -->
```java
public class Main {

    static int failures;

    static void check(String step, boolean ok, String hint) {
        if (ok) {
            System.out.println("✓ " + step);
        } else {
            failures++;
            System.out.println("✗ " + step + "  → " + hint);
        }
    }

    public static void main(String[] args) {
        check("读取配置（application.yml）", true, "");
        check("数据源 URL 已配置", false,
                "检查 spring.datasource.url，占位符没被注入时就是这个错");
        check("按类型注入唯一", false,
                "两个同类型 Bean 都没有 @Primary，改用 @Qualifier 或加 @Primary");
        check("端口 8081 可绑定", true, "");
        check("迁移脚本无冲突", true, "");

        if (failures > 0) {
            System.out.println("启动中止：" + failures + " 项检查失败");
        }
    }
}
```
```text
✓ 读取配置（application.yml）
✗ 数据源 URL 已配置  → 检查 spring.datasource.url，占位符没被注入时就是这个错
✗ 按类型注入唯一  → 两个同类型 Bean 都没有 @Primary，改用 @Qualifier 或加 @Primary
✓ 端口 8081 可绑定
✓ 迁移脚本无冲突
启动中止：2 项检查失败
```

关键是最后一行：**所有检查都跑完了才中止吗？** 不是——真实框架在第一个失败处就抛异常。上面这段把全部检查跑完，是为了让你看到"可能同时有几处问题"，但线上你通常只会看到第一条。

### 六条最常见的启动失败

| 报错关键片段 | 真实原因 | 先查哪里 |
| --- | --- | --- |
| `Web server failed to start. Port 8081 was already in use` | 端口被占（旧进程没停、别的应用占了） | `netstat -ano \| rg 8081` 找 PID，按 PID 杀 |
| `Failed to configure a DataSource: 'url' attribute is not specified` | 数据源配置没读到 | 有没有引驱动、`spring.datasource.url` 在哪个 profile 里 |
| `No qualifying bean of type 'X' available` | 依赖没被注册（扫描不到、条件不成立、忘了加注解） | 启动类包位置、`@Mapper`/`@Service` 在不在、`--debug` 看条件 |
| `NoUniqueBeanDefinitionException: expected single matching bean but found 2` | 两个同类型 Bean | `@Primary` 或 `@Qualifier` |
| `Found more than one migration with version 25` | 迁移版本号重复（并行开发撞号） | 迁移目录里是否有两个同版本文件 |
| `Access denied for user 'x'@'y'` / `Communications link failure` | 凭据错 / 网络或 max-lifetime 问题 | 口令、账号的 host 限制、`wait_timeout` |

第一条有个本项目真实踩过的坑：**用 `pkill -f '<模式>'` 杀进程时，模式串会匹配到执行它的那条 shell 自己**，于是你把会话自己杀了、旧进程还在。正确做法是按 PID 杀。

### 装成常驻进程

```ini
[Unit]
Description=paideia
After=network.target mysql.service

[Service]
User=ubuntu
ExecStart=/opt/jdk25/bin/java -jar /opt/paideia-app/app.jar \
          --spring.config.additional-location=file:/opt/paideia-app/
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

四个要点：

- **`--spring.config.additional-location` 让 jar 外的配置生效**。服务器上的 `application.yml`（含口令）就放在那个目录，**永远不进仓库**。
- **`Restart=always`** 保证崩溃后自动起来。但要注意：如果配置错了导致启动失败，它会每 5 秒重启一次，日志刷得飞快——此时应该先 `systemctl stop` 再排查。
- **日志走 journald**（`journalctl -u paideia -f`），不做自建日志轮转。自建轮转的文件名与大小策略是另一套要维护的东西。
- **`After=mysql.service`** 只保证"在 mysql 之后"，不保证"mysql 已就绪"。真正需要时就绪检查要自己加（比如启动时重试连库）。

### 部署前的最小自检

```bash
java -jar app.jar --help                            # 能起来吗（读配置阶段）
java -jar app.jar --spring.profiles.active=prod     # 换成生产的 profile 再起一次
```

以及三条与本项目相关的：

- **改了配置记得重启**：`@Value` 与 `@ConfigurationProperties` 都不会热更新。
- **jar 里只能有一个版本的迁移文件**：`mvn clean package` 之后 `unzip -l app.jar | rg 迁移名` 确认。不 clean 时旧文件会残留在 `target/classes`。
- **从主树构建**：在合并前的工作树里构建，可能缺对方刚合进来的文件，表现为"应用的迁移历史与本地不一致"。

### 什么算"部署成功"

不是"命令返回 0"。是这三条同时成立：

```sketch
{
  "title": "部署成功要三条同时成立",
  "rows": [
    [
      { "id": "proc", "title": "进程在跑", "sub": "不是每 5 秒重启一次", "tone": "blue" },
      { "id": "health", "title": "健康检查 200", "sub": "/actuator/health", "tone": "green" },
      { "id": "log", "title": "日志里有 Started", "sub": "并且没有 ERROR", "tone": "green" }
    ]
  ],
  "arrows": []
}
```

1. 进程在跑（`systemctl status`），且**没有每 5 秒重启一次**；
2. 健康检查返回 200（本项目是 `/actuator/health`，它是公开的；`/api/v1/health` 需要登录）；
3. 日志里没有 `ERROR`，并且能看到 `Started ... in X seconds`。

第二条特别容易搞错：拿一个需要登录的接口做健康检查，你会一直看到 401，然后误判成"服务没起来"。

## 常见误区

### 误区：`systemctl status` 显示 active 就是好了

**你以为**：进程在跑就是部署成功。
**其实**：`Restart=always` 会让配置错误的应用"看起来在跑"——它每 5 秒重启一次，`status` 短暂显示 active。真正的判据是"没有反复重启 + 健康检查 200 + 日志里有 `Started`"。
**怎么验证**：`systemctl status` 看 `Restart` 计数，或者 `journalctl -u paideia | rg "Started|Stopping"` 数一下频率。

### 误区：改了配置不用重启

**你以为**：配置是每次用的，改了自动生效。
**其实**：`@Value` 与 `@ConfigurationProperties` 都在启动时绑定一次。改文件必须重启，除非引入配置中心与 `@RefreshScope`（本项目不用）。
**怎么验证**：改一个日志级别，不重启，看输出是否变化。

### 误区：日志文件自己轮转更可控

**你以为**：写到文件再配 `logback-spring.xml` 轮转更好管。
**其实**：多一套轮转就要多一套清理与磁盘告警。交给 journald（`journalctl`）自带轮转与按时间检索，`-u paideia -f` 跟日志比 `tail -f` 好用。
**怎么验证**：`journalctl -u <服务> --since "10 min ago"`，看能不能只取这十分钟。

## 小结

`java -jar` 执行的是 Boot 的启动器，它负责嵌套 jar 的类加载。启动是一串检查，第一个失败的就中止，六条报错各自指向一个明确的位置。部署成功有三个同时成立的条件，`active` 不算。配置改了要重启，日志交给 journald。
