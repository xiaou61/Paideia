# 16 · 配置从哪来

## 发版后还在读旧库：两个来源在竞争

我在自己的部署机上遇到过一次：发版后，日志里查出来的数据全是上周的。第一反应是「代码没发上去」，于是又发了一遍，还是一样。

服务器上的环境里躺着这一行：

```text
$ systemctl show paideia-app -p Environment --value
SPRING_DATASOURCE_URL=jdbc:mysql://db.internal.example:3306/paideia_old
```

我改的是 `application-local.yml` 里的 url。这条输出能证明环境里有旧地址，但不能直接证明「文件被它盖住」——还得先看 active profile：如果服务器跑的是 `prod`，`application-local.yml` 根本不会加载，改它当然没用。查 profile：

```text
$ systemctl show paideia-app -p Environment --value | tr ' ' '\n' | grep SPRING_PROFILES_ACTIVE
SPRING_PROFILES_ACTIVE=prod
```

同一个 key 被两个来源同时设置时，先打印「谁赢了」：

```text
$ APP_NAME=from-env java -jar app.jar --spring.main.web-application-type=none
PROBE app.name=from-env origin=systemEnvironment
```

这篇的 Java 输出都在 Temurin 25.0.4 + Spring Boot 4.1.1 上重跑；01 课的 pom 还是 Boot 3.5.6 + Java 21。3.5.x 的 PropertySource 名字和错误文本可能是 `applicationConfig: [classpath:/application.yml]` 一类，不保证逐字相同，照抄前先在你自己的版本上打印一次。

我原来把环境变量排在 Java 系统属性前面，反了：`-D` 赢。下面把顺序排清楚。探针工程不想起 Web 容器，所以命令里加了 `--spring.main.web-application-type=none`；你的应用不需要这一项。

> 上面是 Linux 写法。PowerShell 里要先设 `$env:APP_NAME='from-env'`，并且 `-Dapp.name=from-sys` 要加引号；不加引号会被 PowerShell 拆开，报 `ClassNotFoundException: /name=from-sys`。

## 优先级：从高到低

Boot 4.1.1 实测出来的顺序：

| 顺序 | 来源 | 这次看到的 PropertySource 名 |
| --- | --- | --- |
| 1 | 命令行参数 `--app.name=...` | `commandLineArgs` |
| 2 | `SPRING_APPLICATION_JSON` | `spring.application.json` |
| 3 | Java 系统属性 `-Dapp.name=...` | `systemProperties` |
| 4 | 操作系统环境变量 `APP_NAME=...` | `systemEnvironment` |
| 5 | `application-{profile}.yml` / `.properties` | `Config resource ... application-local.yml ...` |
| 6 | `application.yml` / `.properties` | `Config resource ... application.yml ...` |

读法是「越靠近这次启动现场，优先级越高」：命令行只在这一次启动有效，`SPRING_APPLICATION_JSON` 也是临时塞进去的，系统属性和环境变量跟着进程走，文件则跟着部署包走。文件最低，所以它适合放「每个环境都一样的默认值」，不是「配置的最终真相」。

表里只列这次会互相打架的六档。Boot 还有测试注解、`SpringApplication.setDefaultProperties` 等更低的档；它们也在 `Environment` 里，但不是这篇的重点。

`SPRING_APPLICATION_JSON` 虽然也是通过环境变量传的，但 Boot 会把它解析成一个单独的 `spring.application.json` PropertySource，位置在系统属性之上；不要把它当普通环境变量排在第四档。

把四个来源依次叠上去，输出是：

```text
$ APP_NAME=from-env java -jar app.jar ...
PROBE app.name=from-env origin=systemEnvironment

$ APP_NAME=from-env java '-Dapp.name=from-sys' -jar app.jar ...
PROBE app.name=from-sys origin=systemProperties

$ APP_NAME=from-env SPRING_APPLICATION_JSON='{"app":{"name":"from-json"}}' \
    java '-Dapp.name=from-sys' -jar app.jar ...
PROBE app.name=from-json origin=spring.application.json

$ APP_NAME=from-env SPRING_APPLICATION_JSON='{"app":{"name":"from-json"}}' \
    java '-Dapp.name=from-sys' -jar app.jar ... --app.name=from-cli
PROBE app.name=from-cli origin=commandLineArgs
```

这组只盯 `app.name`：每叠一个来源，赢家就往上换一档。

profile 专属文件高于基础文件，实测：

```text
$ java -jar app.jar --spring.profiles.active=local
PROBE app.name=from-local origin=Config resource 'class path resource [application-local.yml]' ...
```

`spring.config.additional-location` 指定的是文件位置，不是新的优先级档位：它让 jar 外的那份 `application.yml` 盖住 jar 内的同名文件（实测来源是 `Config resource 'file [.../external/application.yml]' ...`），但它仍然低于命令行、JSON、系统属性和环境变量。

### 字段默认值不是第七层

```java
private String name = "paideia";
```

这个 `"paideia"` 不在 `env.getPropertySources()` 里。`env.getProperty("app.unset")` 是 `null`，`origin("app.unset")` 是 `none`；它只是 Java 对象字段的初始值。`@Value("${app.name:paideia}")` 的 `:paideia` 也是占位符默认值，同样不是 PropertySource。别把这两件事当成「文件下面还有一层代码配置」。

真正最低的 `SpringApplication.setDefaultProperties` 会进 `Environment`，那是另一回事，本课不展开。

## 先补两个依赖，别照 01 的 pom 直接抄

01 的 pom 只有 `spring-boot-starter-web`。这一课新加两个 dependency，加到 `<dependencies>` 里：

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

父工程版本沿用 01 的 `3.5.6` 就行，不要为了这两个依赖把版本改成 `4.1.1`；本篇的输出是在 4.1.1 上重跑的，依赖坐标相同，行为差异按开头那段处理。`spring-boot-maven-plugin` 01 已经有了，这一课没有新插件。

没有 validation starter，`@NotBlank` 不是「不生效」，是编译就过不了：

```text
[ERROR] ... package jakarta.validation.constraints does not exist
[ERROR] ... cannot find symbol
  symbol:   class NotBlank
```

没有 actuator starter，`/actuator/env` 这个端点根本不存在。只加 `spring-boot-starter-web` 的探针工程里：

```text
$ curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/actuator/env
404
$ curl -s localhost:8080/ping
pong
```

`@Valid` 也不是开关：它负责触发校验，校验器本身要由 validation starter 带进来。两个依赖都不在 01 的 pom 里，照抄 01 建工程再写这一篇的代码，报错是必然的。

## 按 key 解析，不是整份文件合并

不同 key 可以来自不同来源。Spring 的 `Environment` 对每个属性 key 独立解析：从高到低找第一个有这个 key 的 PropertySource；高优先级来源只覆盖同名 key，不同 key 各留各的。

实测同时保留两个来源：

```text
$ APP_TIMEOUT=PT9S java -jar app.jar ...
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT9S, names=[x, y], mapping={a=b}]
```

基础文件里 `app.timeout` 是 `PT3S`；`APP_TIMEOUT=PT9S` 只换掉了这个 key，`app.name` 仍是 `from-file`。两个 key 各来自各的来源。再把 `APP_NAMES=p,q` 叠上去，列表是整个换掉：

```text
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT9S, names=[p, q], mapping={a=b}]
```

不是 `[x, y, p, q]`。

下面这个小模型只做两件事：按从低到高的顺序应用来源；给每个 key 记住最后是谁写的。它不模拟字段绑定，字段绑定看下一节。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {

    static final class Config {
        private final Map<String, String> values = new LinkedHashMap<>();
        private final Map<String, String> origins = new LinkedHashMap<>();

        Config put(String source, String key, String value) {
            values.put(key, value);
            origins.put(key, source);
            return this;
        }

        String get(String key, String fallback) {
            return values.getOrDefault(key, fallback);
        }

        String origin(String key) {
            return origins.getOrDefault(key, "代码默认值");
        }
    }

    public static void main(String[] args) {
        Config config = new Config()
                .put("application.yml", "app.name", "paideia")
                .put("application.yml", "app.server-port", "8080")
                .put("环境变量", "app.debug", "true")
                .put("环境变量", "app.name", "from-env")
                .put("命令行", "app.name", "from-cli");

        System.out.println("app.name = " + config.get("app.name", "unnamed")
                + "（来自 " + config.origin("app.name") + "）");
        System.out.println("app.debug = " + config.get("app.debug", "false")
                + "（来自 " + config.origin("app.debug") + "）");
        System.out.println("app.server-port = " + config.get("app.server-port", "8080")
                + "（来自 " + config.origin("app.server-port") + "）");
    }
}
```
```text
app.name = from-cli（来自 命令行）
app.debug = true（来自 环境变量）
app.server-port = 8080（来自 application.yml）
```

`app.name` 被命令行盖掉，`app.debug` 来自环境变量，`app.server-port` 留在文件里。**排查配置问题的第一步永远是找「谁赢了」，而不是改文件。**

## 宽松绑定：`app.server.port` 不是 `serverPort`

上一版这张表写错了：把 `app.server.port` 和 `app.server-port` 当成同一个 key。它们不是。

`@ConfigurationProperties(prefix = "app")` 里的 `String serverPort`，能绑上的是 `app.server-port`、`app.serverPort`、`APP_SERVER_PORT`；`app.server.port` 是另一个 key，只会成为 `app.server.port`，不会变成 `serverPort`。

| 来源写法 | 能绑到 `serverPort` 吗 | 说明 |
| --- | --- | --- |
| `app.server-port`（yml） | 能 | 文件里的 kebab 写法 |
| `app.serverPort`（yml） | 能 | 文件里的 camel 写法 |
| `APP_SERVER_PORT`（环境变量） | 能 | 环境变量源同时解析出 `app.server.port` 与 `app.server-port` |
| `--app.server-port=...` | 能 | 命令行 key 精确，绑定器再做字段映射 |
| `--app.serverPort=...` | 能 | 命令行只放 camel key，绑定器按字段名找到；`Environment.getProperty("app.server-port")` 仍是 null |
| `--app.server.port=...` | 不能 | 这是另一个 key，不会折成 `serverPort` |

拿一个只有 `app.name` 的配置文件做隔离，分别从三种来源塞 `serverPort`：

```text
$ java -jar app.jar --spring.config.name=dotlab-name --app.server.port=from-cli-dot
PROBE app.server.port=from-cli-dot origin=commandLineArgs
PROBE app.server-port=null origin=none
PROPS AppProps[name=from-dotlab, serverPort=null, timeout=PT5S, names=[a, b], mapping={}]

$ java -jar app.jar --spring.config.name=dotlab-name --app.serverPort=from-cli-camel
PROPS AppProps[name=from-dotlab, serverPort=from-cli-camel, timeout=PT5S, names=[a, b], mapping={}]

$ APP_SERVER_PORT=from-env-port java -jar app.jar --spring.config.name=dotlab-name
PROBE app.server.port=from-env-port origin=systemEnvironment
PROBE app.server-port=from-env-port origin=systemEnvironment
PROPS AppProps[name=from-dotlab, serverPort=from-env-port, timeout=PT5S, names=[a, b], mapping={}]
```

第一组最关键：`--app.server.port` 确实进了 `Environment`（`app.server.port=from-cli-dot`），但 `serverPort` 还是 `null`。它不是「写法不同」，它是另一个 key。

`@Value` 不做字段级宽松绑定，它把 `${...}` 里的名字原样交给 `Environment`。所以：

- 文件里写 `app.server-port`，`@Value("${app.serverPort}")` 取不到，走默认值；没有默认值就启动失败。
- 但环境变量源自己有一套名字映射，`APP_SERVER_PORT` 能被 `@Value("${app.server_port}")` 取到。

实测输出：

```text
VALUE ... serverPortCamel=[] serverPortUnderscore=[from-env-port]
```

`serverPortCamel` 是 `@Value("${app.serverPort:}")`，空；`serverPortUnderscore` 是 `@Value("${app.server_port:}")`，在 `APP_SERVER_PORT=from-env-port` 下拿到了值。

## `@Value` 还是 `@ConfigurationProperties`

`@Value` 不是「只支持字符串」。它支持标量、逗号分隔的 `List`、以及 Boot 的 `Duration`；简单 `Map` 注入确实失败，嵌套结构也不适合。

```java
@Component
class AppSettings {
    @Value("${app.name:}")
    private String name;

    @Value("${app.names:a,b}")
    private List<String> names;

    @Value("${app.timeout:PT5S}")
    private Duration timeout;
}
```

`names: x,y`（逗号串）时实测：

```text
VALUE ... names=[x, y] timeout=PT3S
```

但 YAML 的列表写法只适合 `@ConfigurationProperties`。同一个 `@Value("${app.names:a,b}")`，配置写成：

```yaml
app:
  names: [x, y]
```

会静默拿默认值：

```text
VALUE ... names=[a, b] timeout=PT3S
PROPS AppProps[name=from-inline, ..., names=[x, y], ...]
```

`app.names` 在环境里是 `app.names[0]`、`app.names[1]`，不是一个逗号串；`@Value` 找不到 `app.names` 这个 key，就用了 `:a,b`。这不是报错，是最难查的那种「看起来有值」。

`Map` 这样写会失败：

```java
@Value("${app.mapping:a=b}")
private Map<String, String> mapping;
```

```text
Failed to convert value of type 'java.lang.String' to required type 'java.util.Map';
Cannot convert value of type 'java.lang.String' to required type 'java.util.Map':
no matching editors or conversion strategy found
```

成组配置用 `@ConfigurationProperties`。下面这个类只保留 `mapping` 一个字段，够跑通 Map：

```java
import java.util.LinkedHashMap;
import java.util.Map;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "app")
public class MapProps {
    private Map<String, String> mapping = new LinkedHashMap<>();

    public Map<String, String> getMapping() { return mapping; }
    public void setMapping(Map<String, String> mapping) { this.mapping = mapping; }
}
```

启动类上加 `@EnableConfigurationProperties(MapProps.class)`，配置写：

```yaml
app:
  mapping:
    a: b
```

启动时打印 `System.out.println("mapping=" + props.getMapping());`，输出：

```text
mapping={a=b}
```

把同一串压成平铺的 `app.mapping: a=b`，`@ConfigurationProperties` 也不会「聪明地」拆开：

```text
Failed to bind properties under 'app.mapping' to java.util.Map<java.lang.String, java.lang.String>:
Reason: org.springframework.core.convert.ConverterNotFoundException: No converter found capable of converting
from type [java.lang.String] to type [java.util.Map<java.lang.String, java.lang.String>]
```

下面是本篇真正用的 `AppProperties`，普通 JavaBean，字段配 getter/setter：

```java
@Validated
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    @NotBlank(message = "不能为空")
    private String name;
    private String serverPort;
    private Duration timeout = Duration.ofSeconds(5);
    private List<String> names = List.of("a", "b");
    private Map<String, String> mapping = new LinkedHashMap<>();

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getServerPort() { return serverPort; }
    public void setServerPort(String serverPort) { this.serverPort = serverPort; }
    public Duration getTimeout() { return timeout; }
    public void setTimeout(Duration timeout) { this.timeout = timeout; }
    public List<String> getNames() { return names; }
    public void setNames(List<String> names) { this.names = names; }
    public Map<String, String> getMapping() { return mapping; }
    public void setMapping(Map<String, String> mapping) { this.mapping = mapping; }
}
```

注册它二选一：

```java
@SpringBootApplication
@EnableConfigurationProperties(AppProperties.class)
public class Application { ... }
```

或：

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class Application { ... }
```

只写 `@ConfigurationProperties`、别处又注入它，启动会报：

```text
No qualifying bean of type 'com.example.configlab.AppProperties' available
```

旁注：record 也能绑，但 record 是 Java 课第 35 课的内容，现在看不懂可以跳过。record 只标这个注解不会自己变成 Bean，注册方式还是上面两种。给 record 加 `@Component` 也不是办法。实测会报（日志里是一行，这里按句子拆开）：

```text
ComponentProps is annotated with @ConstructorBinding but it is defined as a regular bean
which caused dependency injection to fail.
Action: Update your configuration so that ComponentProps is defined via
@ConfigurationPropertiesScan or @EnableConfigurationProperties.
```

可变 JavaBean 才适合 `@Component` 那条路；record 用 `@EnableConfigurationProperties` 或 `@ConfigurationPropertiesScan`。

未知 key 默认忽略。命令行加 `--app.serverprot=typo-value`，应用正常启动，`serverPort` 仍是文件里的值：

```text
Started ConfigLabApplication ...
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT3S, names=[x, y], mapping={a=b}]
```

要让未知 key 启动失败，显式写：

```java
@ConfigurationProperties(prefix = "app", ignoreUnknownFields = false)
```

```text
Property: app.serverprot
Value: "typo-value"
Reason: The elements [app.serverprot] were left unbound.
```

这里的 `ignoreUnknownFields = false` 才是抓未知 key 的开关。校验注解抓不到它：`@NotBlank` 只看已经绑定的 `name` 字段，`app.serverprot` 根本没进对象。默认忽略、要严格才打开。

校验则加 `@Validated` 和 JSR-303：

```java
@Validated
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    @NotBlank(message = "不能为空")
    private String name;
}
```

不给 `app.name` 时：

```text
Property: app.name
Value: "null"
Reason: 不能为空
```

如果只写 `@NotBlank`、不写 `message`，输出会跟着 JVM 的 locale 走：英文 JVM 实测是 `must not be blank`，中文 JVM 是 `不能为空`。日志里要稳定看到中文，就写 `message = "不能为空"`；不写就得知道这是 locale 资源，不是固定字符串。

| 维度 | `@Value` | `@ConfigurationProperties` |
| --- | --- | --- |
| 宽松绑定 | 不做字段名映射；文件 `app.server-port` 取不到 `${app.serverPort}`。环境变量源自己的映射仍生效：`APP_SERVER_PORT` 能取 `${app.server_port}` | 绑定器做字段映射：`app.server-port`、`app.serverPort`、`APP_SERVER_PORT` 能绑到 `serverPort`；`app.server.port` 不能 |
| 结构 | 标量、逗号分隔 `List`、`Duration` 可以；简单 `Map` 注入失败，嵌套对象不适合 | 嵌套对象、`List`、`Map`、`Duration` 都可以 |
| 校验 | 手写判断；`@Validated` 不作用于 `@Value` 字段 | `@Validated` + JSR-303；只校验已绑定字段，未知 key 要靠 `ignoreUnknownFields = false` |
| 拼错/未知 key | 不给默认值就启动失败（占位符解析失败）；给了默认值就静默 | 默认忽略，字段保持默认值（引用类型是 `null`）；`ignoreUnknownFields = false` 才报 `left unbound` |
| 热更新 | 启动时解析一次；默认不刷新 | 启动时绑定一次；默认不刷新。`@RefreshScope` 在 Spring Cloud Context，不在本课 pom；要配置中心才谈得上，本课不覆盖 |

`@RefreshScope` 不是 Boot 自带。它来自 `org.springframework.cloud.context.config.annotation`；本课 pom 没加 Spring Cloud，写上去直接编译失败：

```text
程序包org.springframework.cloud.context.config.annotation不存在
找不到符号
  符号: 类 RefreshScope
```

所以这篇不把它当 Boot 能力，也不贴示例。

## Profile：先看激活了谁

可以拆成三个文件，也可以塞进一个 YAML 用 `---` 分段；不是必须分开。唯一硬要求：按 profile 生效的那一段必须写 `spring.config.activate.on-profile`。

`application.yml`：

```yaml
app:
  name: paideia
```

`application-local.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/paideia
    username: paideia
```

`application-prod.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://db.internal.example:3306/paideia
```

选哪个：

```text
java -jar app.jar --spring.profiles.active=local
```

或 `SPRING_PROFILES_ACTIVE=prod`。

如果你确实想在一个文件里放多段，给按 profile 区分的那几段写激活条件：

```yaml
# application.yml
app:
  name: paideia

---
spring:
  config:
    activate:
      on-profile: local
  datasource:
    url: jdbc:mysql://localhost:3306/paideia
```

没有 `on-profile` 的多个文档会一起被加载，后一个文档的 key 盖住前一个。实测把 `app.name=from-doc1` 和 `app.name=from-doc2` 放在同一个文件的 `---` 两边，输出是：

```text
PROBE app.name=from-doc2 origin=Config resource '...multidoc.yml...' (document #1)
```

`document #1` 是第二个文档（从 0 开始数）。`---` 没有生成 `application-prod.yml`，它只是把两段放进同一个文件。

给第二段加上 `on-profile: local` 后，不激活 local 时读到的是 `from-base-doc`（`document #0`），激活后才是 `from-local-doc`（`document #1`）。所以「多文档」和「分文件」都能用，别把「必须分文件」当成规则。

不写 profile 时的默认值必须是生产安全的：不连测试库、不开调试端点。种子数据只在专用测试 profile 或测试启动时注入，口令从环境变量读，不写进仓库。生产 profile 不加载测试种子，测试 profile 才加载。

## 敏感配置放哪

| 方式 | 进仓库吗 | 适用 |
| --- | --- | --- |
| 写进 `application.yml` | 会 | 不行，公开仓库里绝不能有口令 |
| 写进 `application-local.yml` 并 `.gitignore` | 不会 | 本地开发 |
| 环境变量 | 不会 | 部署 |
| 服务器上独立文件（`additional-location` 引入） | 不会 | 部署 |

服务器文件放 `/opt/paideia-app/application.yml`，权限 `600`，属主是运行应用的用户；仓库里只提交 `.env.example` 这类占位示例。引用密钥时只写环境变量名，不写值。`.gitignore` 只对未跟踪文件生效；如果密钥已经进过提交，加忽略规则不等于从历史里消失，要轮换凭据并清理历史。

## 改了不生效，先找「谁赢了」

1. **先看 active profile。** 如果跑的是 `prod`，`application-local.yml` 不会加载；这时改 local 文件当然没用。启动日志里有一行 `The following 1 profile is active: "prod"`，或看 `SPRING_PROFILES_ACTIVE`。
2. **再看 PropertySource 顺序。** 不要先改文件，先打印每个 key 的来源；同名 key 被更高优先级盖住时，改低优先级文件不会有用。
3. **再看 key 名和绑定方式。** `app.server.port` 与 `serverPort` 不是一回事；`@Value` 与 `@ConfigurationProperties` 的宽松绑定能力也不同。
4. **最后看有没有重启。** 两者都是启动时绑定一次，改文件不重启不会生效。

下面这个 `ApplicationRunner` 把 PropertySource 名字和几个 key 的来源打出来。只打名字含 `application` 的源，跳过 `configurationProperties` 适配层和 `applicationInfo`：

```java
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.PropertySource;
import org.springframework.stereotype.Component;

@Component
class ConfigProbe implements ApplicationRunner {

    private final ConfigurableEnvironment env;

    ConfigProbe(ConfigurableEnvironment env) {
        this.env = env;
    }

    @Override
    public void run(ApplicationArguments args) {
        int total = 0;
        for (PropertySource<?> source : env.getPropertySources()) {
            total++;
            String name = source.getName();
            if (name.contains("application") && !name.equals("applicationInfo")) {
                System.out.println("SOURCE " + name);
            }
        }
        System.out.println("TOTAL_SOURCES=" + total);
        System.out.println("PROBE app.name=" + env.getProperty("app.name")
                + " origin=" + origin("app.name"));
    }

    private String origin(String key) {
        for (PropertySource<?> source : env.getPropertySources()) {
            if (!source.getName().equals("configurationProperties")
                    && source.containsProperty(key)) {
                return source.getName();
            }
        }
        return "none";
    }
}
```

Web 应用实测输出：

```text
SOURCE Config resource 'class path resource [application.yml]' via location 'optional:classpath:/'
TOTAL_SOURCES=11
PROBE app.name=from-file origin=Config resource 'class path resource [application.yml]' via location 'optional:classpath:/'
```

真实输出不止这几行。未过滤时还有 `servletConfigInitParams`、`servletContextInitParams`、`Management Server`、`systemProperties`、`systemEnvironment` 等；这篇的 web 探针是 11 个源，加别的 starter 还会更多。未过滤时，`commandLineArgs` 排在 `systemProperties` 前面，`systemEnvironment` 排在 `application.yml` 前面；`configurationProperties` 是适配层，`server.ports` 只放端口。别把 11 当成固定值，也别把 `applicationInfo` 当成配置文件。

`--debug` 给的不是这个。它输出的是 `CONDITIONS EVALUATION REPORT`：

```text
CONDITIONS EVALUATION REPORT
Positive matches:
   PropertyPlaceholderAutoConfiguration#propertySourcesPlaceholderConfigurer matched:
        - @ConditionalOnMissingBean ...
```

这里没有每个属性的最终值，也没有 PropertySource 列表。别把它当 `/actuator/env` 用。

`/actuator/env` 能看到键和来源；值是否显示还取决于 `management.endpoint.env.show-values` 和脱敏规则。它默认只暴露 `health`，要显式加：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,env
  endpoint:
    env:
      show-values: always
```

只加 `include: health,env`、不加 `show-values` 时，值默认是 `******`（我把 `show-values` 显式设成 `never` 复现过）：

```text
"app.name":{"origin":"class path resource [application.yml] ...","value":"******"}
```

默认看不到值不代表这个端点安全，键和来源本身就够敏感。一旦打开，配置键、来源、可能的值都会暴露，不要公网无鉴权开放。只在本机或内网临时开，查完关掉；或者用上面的探针在启动日志里打印。

## 三件我原来以为对的事

**一、配置文件是「配置的真相」。** 它在外部来源里是最低一档。既然低，就该只放默认值；每个环境要变的东西留给环境变量、系统属性、`SPRING_APPLICATION_JSON` 或命令行。`additional-location` 引入的服务器文件能盖住 jar 内的文件，但它仍然盖不过前面四档。

**二、`@Value` 和 `@ConfigurationProperties` 只是写法不同。** 差别在能力：宽松绑定、嵌套结构、校验，这三样 `@Value` 都没有；但 `@Value` 也不是「只支持字符串」——逗号分隔的 `List` 和 `Duration` 它能转，简单 `Map` 才是不行的。选错的代价是「配置悄悄是默认值」，或者启动时才发现没绑上。

**三、改完配置下次请求就生效。** 绑定发生在启动时。`@Value` 和 `@ConfigurationProperties` 都不会因为文件改了而自动刷新；`@RefreshScope` 或配置中心是另外的机制。日志级别有 Actuator 的 `/actuator/loggers` 这类运行时接口，那是另一套机制，不代表你的 `app.*` 会跟着变。

## 还差的

- 没讲配置中心（Nacos / Apollo / Spring Cloud Config）和动态刷新；`@RefreshScope` 在 Spring Cloud Context，不在本课 pom，也没有可运行例子。
- 没讲 `spring.config.import`、配置树（config tree）、Kubernetes ConfigMap/Secret 的挂载方式；这些会把「文件从哪来」再扩展一层。
- 没做加密配置（Jasypt、KMS、Vault）；这篇只说了敏感值不要进仓库，没说怎么在服务器上加密落盘。
- 实测只覆盖 Temurin 25.0.4 + Spring Boot 4.1.1。你如果跟的是 01 的 3.5.6，先确认启动日志里的 PropertySource 顺序和依赖坐标，再照抄本文命令；3.5.x 的名字和错误文本没有在这台机器上重跑。
- `/actuator/env` 只给了暴露开关和安全警告，没有做鉴权、脱敏和审计；生产环境要另配。
