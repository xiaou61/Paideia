# 16 · 配置从哪来

## 发版后还在读旧库：两个来源在竞争

一次发版之后，日志里查出来的数据全是上周的。第一反应是「代码没发上去」，于是又发了一遍，还是一样。

服务器上的环境里躺着这一行：

```text
$ systemctl show <unit> -p Environment --value
SPRING_DATASOURCE_URL=jdbc:mysql://db.internal.example:3306/paideia_old
```

我改的是 `application-local.yml` 里的 url。这条输出能证明环境里有旧地址，但不能直接证明「文件被它盖住」——还得先看 active profile：如果服务器跑的是 `prod`，`application-local.yml` 根本不会加载，改它当然没用。查 profile：

```text
$ systemctl show <unit> -p Environment --value | tr ' ' '\n' | grep SPRING_PROFILES_ACTIVE
SPRING_PROFILES_ACTIVE=prod
```

同一个 key 被两个来源同时设置时，结果是这样的（Temurin 25.0.4 + Spring Boot 4.1.1，探针工程）：

```text
$ APP_NAME=from-env java -jar app.jar --spring.main.web-application-type=none
PROBE app.name=from-env origin=systemEnvironment

$ APP_NAME=from-env java '-Dapp.name=from-sys' -jar app.jar --spring.main.web-application-type=none
PROBE app.name=from-sys origin=systemProperties
```

我原来把环境变量排在 Java 系统属性前面，反了：`-D` 赢。下面把整条顺序排清楚，再给一段能打印 PropertySource 的探针。探针工程不想起 Web 容器，所以命令里加了 `--spring.main.web-application-type=none`；你的应用不需要这一项。

> 上面是 Linux 写法。PowerShell 里要先设 `$env:APP_NAME='from-env'`，并且 `-Dapp.name=from-sys` 要加引号；不加引号会被 PowerShell 拆开，报 `ClassNotFoundException: /name=from-sys`。

## 优先级：从高到低

Boot 4.1.1 实测出来的顺序：

1. 命令行参数：`--app.name=from-cli`
2. `SPRING_APPLICATION_JSON`：整段 JSON 塞进环境变量
3. Java 系统属性：`-Dapp.name=from-sys`
4. 操作系统环境变量：`APP_NAME=from-env`
5. `application-{profile}.yml` / `.properties`
6. `application.yml` / `.properties`
7. 代码里的默认值：`private String name = "paideia";`

读法是「越靠近这次启动现场，优先级越高」：命令行只在这一次启动有效，`SPRING_APPLICATION_JSON` 也是临时塞进去的，系统属性和环境变量跟着进程走，文件则跟着部署包走。文件最低，所以它适合放「每个环境都一样的默认值」，不是「配置的最终真相」。

`SPRING_APPLICATION_JSON` 虽然也是通过环境变量传的，但 Boot 会把它解析成一个单独的 `spring.application.json` PropertySource，位置在系统属性之上；不要把它当普通环境变量排在第四档。

把四个来源依次叠上去，输出是：

```text
$ APP_NAME=from-env java -jar app.jar ...
PROBE app.name=from-env origin=systemEnvironment

$ APP_NAME=from-env java '-Dapp.name=from-sys' -jar app.jar ...
PROBE app.name=from-sys origin=systemProperties

$ APP_NAME=from-env SPRING_APPLICATION_JSON='{"app":{"name":"from-json"}}' \
    java '-Dapp.name=from-sys' -jar app.jar ...
PROBE app.name=from-json origin=spring.application.json

$ APP_NAME=from-env SPRING_APPLICATION_JSON='{"app":{"name":"from-json"}}' \
    java '-Dapp.name=from-sys' -jar app.jar ... --app.name=from-cli
PROBE app.name=from-cli origin=commandLineArgs
```

这组只盯 `app.name`：每叠一个来源，赢家就往上换一档。

profile 专属文件高于基础文件，实测：

```text
$ java -jar app.jar --spring.profiles.active=local
PROBE app.name=from-local origin=Config resource 'class path resource [application-local.yml]' ...
```

`spring.config.additional-location` 指定的是文件位置，不是新的优先级档位：它让 jar 外的那份 `application.yml` 盖住 jar 内的同名文件（实测来源是 `Config resource 'file [.../external/application.yml]'`），但它仍然低于命令行、JSON、系统属性和环境变量。

## 按 key 解析，不是整份文件合并

上一版我把这件事说成了整份配置的覆盖关系，漏掉了另一半：不同 key 可以来自不同来源。

Spring 的 `Environment` 对每个属性 key 独立解析：从高到低找第一个有这个 key 的 PropertySource；高优先级来源只覆盖同名 key，不同 key 可以来自不同来源。列表按整份替换，不会逐项追加。

实测同时保留两个来源：

```text
$ APP_TIMEOUT=PT9S java -jar app.jar ...
PROBE app.name=from-file origin=Config resource '...application.yml...'
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT9S, names=[x, y]]
```

基础文件里 `app.timeout` 是 `PT3S`；`APP_TIMEOUT=PT9S` 只换掉了这个 key，`app.name` 仍是 `from-file`。两个 key 各来自各的来源。再把 `APP_NAMES=p,q` 叠上去，列表是整个换掉：

```text
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT9S, names=[p, q]]
VALUE names=[p, q] timeout=PT9S
```

不是 `[x, y, p, q]`。

下面这个小模型只做两件事：按从低到高的顺序应用来源；给每个 key 记住最后是谁写的。它不模拟字段绑定，字段绑定看下一节。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Locale;
import java.util.Map;

public class Main {

    static final class Config {
        private final Map<String, String> values = new LinkedHashMap<>();
        private final Map<String, String> origins = new LinkedHashMap<>();

        // 同名 key 才覆盖；不同 key 各留各的
        Config apply(String source, Map<String, String> entries) {
            for (Map.Entry<String, String> entry : entries.entrySet()) {
                values.put(entry.getKey(), entry.getValue());
                origins.put(entry.getKey(), source);
            }
            return this;
        }

        String get(String key, String fallback) {
            return values.getOrDefault(key, fallback);
        }

        String originOf(String key) {
            return origins.getOrDefault(key, "代码默认值");
        }
    }

    static Map<String, String> map(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i], pairs[i + 1]);
        }
        return result;
    }

    // 这个模型里的环境变量名转换：APP_DEBUG -> app.debug
    static Map<String, String> env(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i].toLowerCase(Locale.ROOT).replace('_', '.'), pairs[i + 1]);
        }
        return result;
    }

    // 命令行：--app.name=from-cli
    static Map<String, String> args(String... raw) {
        Map<String, String> result = new LinkedHashMap<>();
        for (String item : raw) {
            int at = item.indexOf('=');
            result.put(item.substring(2, at), item.substring(at + 1));
        }
        return result;
    }

    public static void main(String[] args) {
        Config config = new Config()
                .apply("application.yml", map("app.name", "paideia", "app.server-port", "8080"))
                .apply("环境变量", env("APP_NAME", "from-env", "APP_DEBUG", "true"))
                .apply("命令行", args("--app.name=from-cli"));

        System.out.println("app.name = " + config.get("app.name", "unnamed")
                + "（来自 " + config.originOf("app.name") + "）");
        System.out.println("app.debug = " + config.get("app.debug", "false")
                + "（来自 " + config.originOf("app.debug") + "）");
        System.out.println("app.server-port = " + config.get("app.server-port", "8080")
                + "（来自 " + config.originOf("app.server-port") + "）");
    }
}
```
```text
app.name = from-cli（来自 命令行）
app.debug = true（来自 环境变量）
app.server-port = 8080（来自 application.yml）
```

`app.name` 被命令行盖掉，`app.debug` 来自环境变量，`app.server-port` 留在文件里。**排查配置问题的第一步永远是找「谁赢了」，而不是改文件。**

## 宽松绑定：`app.server.port` 不是 `serverPort`

上一版这张表写错了：把 `app.server.port` 和 `app.server-port` 当成同一个 key。它们不是。

`@ConfigurationProperties(prefix = "app")` 里的 `String serverPort`，能绑上的是 `app.server-port`、`app.serverPort`、`APP_SERVER_PORT`；`app.server.port` 是另一个 key，只会成为 `app.server.port`，不会变成 `serverPort`。

| 来源写法 | 能绑到 `serverPort` 吗 | 说明 |
| --- | --- | --- |
| `app.server-port`（yml） | 能 | 文件里的 kebab 写法 |
| `app.serverPort`（yml） | 能 | 文件里的 camel 写法 |
| `APP_SERVER_PORT`（环境变量） | 能 | 环境变量源同时解析出 `app.server.port` 与 `app.server-port` |
| `--app.server-port=...` | 能 | 命令行 key 精确，绑定器再做字段映射 |
| `--app.serverPort=...` | 能 | 同上 |
| `--app.server.port=...` | 不能 | 这是另一个 key，不会折成 `serverPort` |

拿一个只有 `app.name` 的配置文件做隔离，分别从三种来源塞 `serverPort`：

```text
$ java -jar app.jar --spring.config.name=dotlab --app.server.port=from-cli-dot
PROBE app.server.port=from-cli-dot origin=commandLineArgs
PROBE app.server-port=null origin=none
PROPS AppProps[name=from-dotlab, serverPort=null, timeout=PT3S, names=[x, y]]

$ java -jar app.jar --spring.config.name=dotlab --app.serverPort=from-cli-camel
PROPS AppProps[name=from-dotlab, serverPort=from-cli-camel, timeout=PT3S, names=[x, y]]

$ APP_SERVER_PORT=from-env-port java -jar app.jar --spring.config.name=dotlab
PROBE app.server.port=from-env-port origin=systemEnvironment
PROBE app.server-port=from-env-port origin=systemEnvironment
PROPS AppProps[name=from-dotlab, serverPort=from-env-port, timeout=PT3S, names=[x, y]]
```

第一组最关键：`--app.server.port` 确实进了 `Environment`（`app.server.port=from-cli-dot`），但 `serverPort` 还是 `null`。它不是「写法不同」，它是另一个 key。

`@Value` 不做字段级宽松绑定，它把 `${...}` 里的名字原样交给 `Environment`。所以：

- 文件里写 `app.server-port`，`@Value("${app.serverPort}")` 取不到，走默认值；没有默认值就启动失败。
- 但环境变量源自己有一套名字映射，`APP_SERVER_PORT` 能被 `@Value("${app.server_port}")` 取到。

实测输出：

```text
VALUE name=[from-file] serverPortCamel=[] serverPortUnderscore=[9000]
```

`serverPortCamel` 是 `@Value("${app.serverPort:}")`，空；`serverPortUnderscore` 是 `@Value("${app.server_port:}")`，在 `APP_SERVER_PORT=9000` 下拿到了 9000。

## `@Value` 还是 `@ConfigurationProperties`

`@Value` 的否定不能写得太绝对。它支持标量、逗号分隔的 `List`、以及 Boot 的 `Duration`；简单 `Map` 注入确实失败，嵌套结构也不适合。

```java
@Component
class AppSettings {
    @Value("${app.name:}")
    private String name;

    @Value("${app.names:a,b}")
    private List<String> names;

    @Value("${app.timeout:PT5S}")
    private Duration timeout;
}
```

实测：

```text
VALUE names=[x, y] timeout=PT3S
```

`Map` 这样写会失败：

```java
@Value("${app.mapping:a=b}")
private Map<String, String> mapping;
```

```text
Failed to convert value of type 'java.lang.String' to required type 'java.util.Map';
no matching editors or conversion strategy found
```

成组配置用 `@ConfigurationProperties`：

```java
@ConfigurationProperties(prefix = "app")
public record AppProperties(
        String name,
        String serverPort,
        Duration timeout,
        List<String> names) {
}
```

record 只标这个注解不会自己变成 Bean。要让它被注册，二选一：

```java
@SpringBootApplication
@EnableConfigurationProperties(AppProperties.class)
public class Application { ... }
```

或：

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class Application { ... }
```

只写 `@ConfigurationProperties`、别处又注入它，启动会报：

```text
No qualifying bean of type 'com.example.configlab.AppProperties' available
```

给 record 加 `@Component` 也不是办法。实测会报（日志里是一行，这里按句子拆开）：

```text
ComponentProps is annotated with @ConstructorBinding but it is defined as a regular bean
which caused dependency injection to fail.
Action: Update your configuration so that ComponentProps is defined via
@ConfigurationPropertiesScan or @EnableConfigurationProperties.
```

可变 JavaBean 才适合 `@Component` 那条路；record 用前两种注册方式。

| 维度 | `@Value` | `@ConfigurationProperties` |
| --- | --- | --- |
| 宽松绑定 | 不做字段名映射；文件 `app.server-port` 取不到 `${app.serverPort}`。环境变量源自己的映射仍生效：`APP_SERVER_PORT` 能取 `${app.server_port}` | 绑定器做字段映射：`app.server-port`、`app.serverPort`、`APP_SERVER_PORT` 能绑到 `serverPort`；`app.server.port` 不能 |
| 结构 | 标量、逗号分隔 `List`、`Duration` 可以；简单 `Map` 注入失败，嵌套对象不适合 | 嵌套对象、`List`、`Map`、`Duration` 都可以 |
| 校验 | 手写判断；`@Validated` 不作用于 `@Value` 字段 | `@Validated` + JSR-303；未知 key 默认忽略，要启动失败加 `ignoreUnknownFields = false` 或校验注解 |
| 拼错/未知 key | 不给默认值就启动失败（占位符解析失败）；给了默认值就静默 | 默认忽略，字段保持默认值（引用类型是 `null`）；`ignoreUnknownFields = false` 才报 `left unbound` |
| 热更新 | 启动时解析一次；默认不刷新，要刷新得把 bean 放进 `@RefreshScope`，由 refresh 事件触发重建 | 启动时绑定一次；默认不刷新，配置中心的 refresh 可以触发重新绑定，或同样走 `@RefreshScope` |

`@ConfigurationProperties` 默认忽略未知 key。在命令行加 `--app.serverprot=typo-value`，应用正常启动，`serverPort` 仍是文件里的值：

```text
Started ConfigLabApplication ...
PROPS AppProps[name=from-file, serverPort=from-file-kebab, timeout=PT3S, names=[x, y]]
```

要让未知 key 启动失败，显式写：

```java
@ConfigurationProperties(prefix = "app", ignoreUnknownFields = false)
```

```text
Property: app.serverprot
Value: "typo-value"
Reason: The elements [app.serverprot] were left unbound.
```

校验则加 `@Validated` 和 JSR-303：

```java
@Validated
@ConfigurationProperties(prefix = "app")
public record AppProperties(@NotBlank String name) { }
```

不给 `app.name` 时：

```text
Property: app.name
Value: "null"
Reason: 不能为空
```

## Profile：先看激活了谁

三个文件要分开写，不要塞进一个 YAML 里。`---` 只是 YAML 文档分隔符，不是文件名。

`application.yml`：

```yaml
app:
  name: paideia
```

`application-local.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/paideia
    username: paideia
```

`application-prod.yml`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://db.internal.example:3306/paideia
```

选哪个：

```text
java -jar app.jar --spring.profiles.active=local
```

或 `SPRING_PROFILES_ACTIVE=prod`。

如果你确实想在一个文件里放多段，给按 profile 区分的那几段写激活条件：

```yaml
# application.yml
app:
  name: paideia

---
spring:
  config:
    activate:
      on-profile: local
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/paideia
```

没有 `on-profile` 的多个文档会一起被加载，后一个文档的 key 盖住前一个。实测把 `app.name=from-doc1` 和 `app.name=from-doc2` 放在同一个文件的 `---` 两边，输出是：

```text
PROBE app.name=from-doc2 origin=Config resource '...multidoc.yml...' (document #1)
```

`document #1` 是第二个文档（从 0 开始数）。`---` 没有生成 `application-prod.yml`，它只是把两段放进同一个文件。

不写 profile 时的默认值必须是生产安全的：不连测试库、不开调试端点。种子数据只在专用测试 profile 或测试启动时注入，口令从环境变量读，不写进仓库。生产 profile 不加载，测试 profile 才加载。

## 敏感配置放哪

| 方式 | 进仓库吗 | 适用 |
| --- | --- | --- |
| 写进 `application.yml` | 会 | 不行，公开仓库里绝不能有口令 |
| 写进 `application-local.yml` 并 `.gitignore` | 不会 | 本地开发 |
| 环境变量 | 不会 | 部署 |
| 服务器上独立文件（`additional-location` 引入） | 不会 | 部署 |

服务器文件放 `/opt/paideia-app/application.yml`，权限 `600`，属主是运行应用的用户；仓库里只提交 `.env.example` 这类占位示例。引用密钥时只写环境变量名，不写值。`.gitignore` 只对未跟踪文件生效；如果密钥已经进过提交，加忽略规则不等于从历史里消失，要轮换凭据并清理历史。

## 改了不生效，先找「谁赢了」

1. **先看 active profile。** 如果跑的是 `prod`，`application-local.yml` 不会加载；这时改 local 文件当然没用。启动日志里有一行 `The following 1 profile is active: "prod"`，或看 `SPRING_PROFILES_ACTIVE`。
2. **再看 PropertySource 顺序。** 不要先改文件，先打印每个 key 的来源；同名 key 被更高优先级盖住时，改低优先级文件不会有用。
3. **再看 key 名和绑定方式。** `app.server.port` 与 `serverPort` 不是一回事；`@Value` 与 `@ConfigurationProperties` 的宽松绑定能力也不同。
4. **最后看有没有重启。** 两者都是启动时绑定一次，改文件不重启不会生效。

下面这个 `ApplicationRunner` 把 PropertySource 名字和几个 key 的来源打出来。`configurationProperties` 是 Boot 加的适配层，跳过它才能看到真正提供值的源：

```java
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.PropertySource;
import org.springframework.stereotype.Component;

@Component
class ConfigProbe implements ApplicationRunner {

    private final ConfigurableEnvironment env;

    ConfigProbe(ConfigurableEnvironment env) {
        this.env = env;
    }

    @Override
    public void run(ApplicationArguments args) {
        for (PropertySource<?> source : env.getPropertySources()) {
            System.out.println("SOURCE " + source.getName());
        }
        System.out.println("app.name=" + env.getProperty("app.name")
                + " origin=" + origin("app.name"));
        System.out.println("app.server-port=" + env.getProperty("app.server-port")
                + " origin=" + origin("app.server-port"));
    }

    private String origin(String key) {
        for (PropertySource<?> source : env.getPropertySources()) {
            if (!source.getName().equals("configurationProperties")
                    && source.containsProperty(key)) {
                return source.getName();
            }
        }
        return "none";
    }
}
```

实测输出（只截了前几行）：

```text
SOURCE configurationProperties
SOURCE commandLineArgs
SOURCE systemProperties
SOURCE systemEnvironment
SOURCE random
SOURCE Config resource 'class path resource [application.yml]' via location 'optional:classpath:/'
SOURCE applicationInfo
app.name=from-file origin=Config resource 'class path resource [application.yml]' via location 'optional:classpath:/'
```

注意 `SOURCE` 的顺序基本就是优先级顺序：`configurationProperties` 是适配层，`random` 只提供 `random.*`；`app.name` 的第一个真实来源是 `application.yml`。

`--debug` 给的不是这个。它输出的是 `CONDITIONS EVALUATION REPORT`：

```text
CONDITIONS EVALUATION REPORT
Positive matches:
   PropertyPlaceholderAutoConfiguration#propertySourcesPlaceholderConfigurer matched:
...
```

这里没有每个属性的最终值，也没有 PropertySource 列表。别把它当 `/actuator/env` 用。

`/actuator/env` 能看到键和来源；值是否显示还取决于 `management.endpoint.env.show-values` 和脱敏规则。它默认不暴露，要显式加：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,env
```

有的版本还要求 `management.endpoint.env.show-values` 才显示值；默认看不到值不代表这个端点安全，键和来源本身就够敏感。一旦打开，配置键、来源、可能的值都会暴露，不要公网无鉴权开放。只在本机或内网临时开，查完关掉；或者用上面的探针在启动日志里打印。

## 动手

下面这段配置在服务器上改了环境变量 `SERVER_PORT=9000`，但应用还是监听 8080。找出最该确认/改的那一处：

```code-challenge
{
  "id": "spring-16-bug",
```

## 三件我原来以为对的事

**一、配置文件是「配置的真相」。** 它在外部来源里是最低一档。既然低，就该只放默认值；每个环境要变的东西留给环境变量、系统属性、`SPRING_APPLICATION_JSON` 或命令行。`additional-location` 引入的服务器文件能盖住 jar 内的文件，但它仍然盖不过前面四档。

**二、`@Value` 和 `@ConfigurationProperties` 只是写法不同。** 差别在能力：宽松绑定、嵌套结构、校验，这三样 `@Value` 都没有；但 `@Value` 也不是「只支持字符串」——逗号分隔的 `List` 和 `Duration` 它能转，简单 `Map` 才是不行的。选错的代价是「配置悄悄是默认值」，或者启动时才发现没绑上。

**三、改完配置下次请求就生效。** 绑定发生在启动时。`@Value` 和 `@ConfigurationProperties` 都不会因为文件改了而自动刷新；`@RefreshScope` 或配置中心是另外的机制。日志级别这种看起来「应该能热改」的东西，不加额外机制也一样要重启。

## 还差的

- 没讲配置中心（Nacos / Apollo / Spring Cloud Config）和动态刷新；`@RefreshScope` 只在这篇里提了一句，没有可运行例子。
- 没讲 `spring.config.import`、配置树（config tree）、Kubernetes ConfigMap/Secret 的挂载方式；这些会把「文件从哪来」再扩展一层。
- 没做加密配置（Jasypt、KMS、Vault）；这篇只说了敏感值不要进仓库，没说怎么在服务器上加密落盘。
- 实测只覆盖 Temurin 25.0.4 + Spring Boot 4.1.1。你如果跟的是 3.5.x 那条线，先确认启动日志里的 PropertySource 顺序和依赖坐标，再照抄本文命令；本文没有把 3.5.6 的输出混进来。
- `/actuator/env` 只给了暴露开关和安全警告，没有做鉴权、脱敏和审计；生产环境要另配。
