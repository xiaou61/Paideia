# 16 · 配置从哪来

## 这一课你要会

- 排出配置来源的优先级，并说清"为什么改了环境变量没生效"；
- 说清 `@Value` 与 `@ConfigurationProperties` 的取舍；
- 用 Profile 把"本地 / 测试 / 生产"隔开，而不是靠注释；
- 知道宽松绑定（relaxed binding）把 `APP_SERVER_PORT` 变成了 `app.server.port`。

## 为什么

配置出问题的表现特别"不像配置问题"：端口没变、连接的是错误的库、某个开关没打开。

原因几乎总是同一个：**你以为改的那个来源，优先级低于另一个**。比如你在 `application.yml` 里改了端口，但环境变量里还留着一个旧的 `SERVER_PORT`——环境变量优先，于是你改十次文件都没用。

## 讲解

### 优先级（从高到低，常用的几档）

```text
1. 命令行参数            --server.port=9000
2. 环境变量              SERVER_PORT=9000
```

读法是：**越"临时、越靠近启动现场"的越高**。命令行最高，因为它一定是你这次手动敲的；文件最低（在"外部来源"里），因为它会被部署环境覆盖——这正是你想要的：镜像里带一份默认配置，部署时用环境变量改。

注意还有几个不常用但更"外部"的来源，比如 `spring.config.additional-location` 指定的目录、`SPRING_APPLICATION_JSON` 环境变量里的整段 JSON。本项目部署时用 `--spring.config.additional-location=file:/opt/paideia-app/` 把服务器上的配置目录加进搜索路径，那份文件比 jar 里的优先级高。

### 手写一遍覆盖过程

关键只有一句：**按优先级从低到高依次应用，后应用的覆盖先应用的**。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Locale;
import java.util.Map;

public class Main {

    static final class Config {
        private final Map<String, String> values = new LinkedHashMap<>();
        private final Map<String, String> origins = new LinkedHashMap<>();

        // 后应用的覆盖先应用的
        Config apply(String source, Map<String, String> entries) {
            for (Map.Entry<String, String> entry : entries.entrySet()) {
                values.put(entry.getKey(), entry.getValue());
                origins.put(entry.getKey(), source);
            }
            return this;
        }

        String get(String key, String fallback) {
            return values.getOrDefault(key, fallback);
        }

        String originOf(String key) {
            return origins.getOrDefault(key, "代码默认值");
        }
    }

    static Map<String, String> map(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i], pairs[i + 1]);
        }
        return result;
    }

    // 宽松绑定：APP_SERVER_PORT → app.server.port
    static Map<String, String> env(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i].toLowerCase(Locale.ROOT).replace('_', '.'), pairs[i + 1]);
        }
        return result;
    }

    // 命令行：--app.debug=true
    static Map<String, String> args(String... raw) {
        Map<String, String> result = new LinkedHashMap<>();
        for (String item : raw) {
            int at = item.indexOf('=');
            result.put(item.substring(2, at), item.substring(at + 1));
        }
        return result;
    }

    public static void main(String[] args) {
        Config config = new Config()
                .apply("application.yml", map("app.server.port", "8080", "app.name", "paideia"))
                .apply("环境变量", env("APP_SERVER_PORT", "9000"))
                .apply("命令行", args("--app.debug=true"));

        System.out.println("app.server.port = " + config.get("app.server.port", "8080")
                + "（来自 " + config.originOf("app.server.port") + "）");
        System.out.println("app.debug = " + config.get("app.debug", "false")
                + "（来自 " + config.originOf("app.debug") + "）");
        System.out.println("app.name = " + config.get("app.name", "unnamed")
                + "（来自 " + config.originOf("app.name") + "）");
    }
}
```
```text
app.server.port = 9000（来自 环境变量）
app.debug = true（来自 命令行）
app.name = paideia（来自 application.yml）
```

三个值各自来自不同层，这就是覆盖过程的全貌：没有"合并"，只有"后来的盖住前面的"。

### 宽松绑定：三种写法是一个键

```sketch
{
  "title": "三种写法，绑到同一个配置项上",
  "rows": [
    [
      { "id": "dot", "title": "app.server.port", "sub": "yml / properties", "tone": "gray" },
      { "id": "env", "title": "APP_SERVER_PORT", "sub": "环境变量", "tone": "blue" },
      { "id": "dash", "title": "app.server-port", "sub": "连字符写法", "tone": "violet" }
    ]
  ],
  "arrows": []
}
```

Spring Boot 认这几种写法为同一个配置项：

| 写法 | 出现在哪 |
| --- | --- |
| `app.server.port` | yml / properties |
| `app.server-port` | yml |
| `APP_SERVER_PORT` | 环境变量 |
| `app.serverPort` | yml |
| `--app.server.port=9000` | 命令行 |

原因是环境变量不允许用点号，所以框架把下划线统一转成点、并忽略大小写。**这条规则在排查"环境变量没生效"时非常有用**：先确认变量名转出来的属性名与你要的完全一致（`APP_SERVER_PORT` → `app.server.port`，注意中间那个多出来的点）。

### `@Value` 还是 `@ConfigurationProperties`

```java
// 一、逐项注入
@Value("${app.server.port}")
private int port;

@Value("${app.name}")
private String name;
```

```java
// 二、成组绑定
@ConfigurationProperties(prefix = "app")
public record AppProperties(String name, int serverPort) { }
```

| | `@Value` | `@ConfigurationProperties` |
| --- | --- | --- |
| 适合 | 一个零散的开关 | 一组有结构的配置 |
| 类型转换 | 简单类型 | 嵌套对象、`List`、`Map`、`Duration` |
| 校验 | 不方便 | 配 `@Validated` + JSR-303 注解 |
| 热更新 | 不刷新 | 不刷新（除非配合 `@RefreshScope`） |
| 拼写错误 | 启动时才发现（除非给了默认值） | 启动时绑定失败，报得很清楚 |

**本项目用 `@ConfigurationProperties`**：一处前缀、一个 record、字段自带类型，比散落十几个 `@Value` 好查。

还有一条容易踩的：`@Value` 里的类**必须在构造器之前被填好**，所以 `@Value` 字段在每个方法里都会重新解析表达式，性能差且不支持复杂结构。这只是它不适合成组配置的补充理由。

### Profile：把环境隔开

```yaml
# application.yml —— 公共部分
app:
  name: paideia

---
# application-local.yml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/paideia
    username: paideia

---
# application-prod.yml
spring:
  datasource:
    url: jdbc:mysql://...
```

启动时选：

```bash
java -jar app.jar --spring.profiles.active=local
```

或者用环境变量 `SPRING_PROFILES_ACTIVE=prod`。

**默认 profile 应该是"生产安全"的那个**：不写 profile 时不该连上测试库、不该打开调试端点。本项目的原则更严格——**任何 profile 都不加载测试种子数据**，只有端到端测试显式加一个专用 profile。原因是种子账号的口令是公开写在仓库里的。

### 敏感配置放哪

| 方式 | 是否进仓库 | 适用 |
| --- | --- | --- |
| 写进 `application.yml` | 会 | **不行**，公开仓库里绝不能有口令 |
| 写进 `application-local.yml` 并 `.gitignore` | 不会 | 本地开发 |
| 环境变量 | 不会 | 部署 |
| 服务器上的独立配置文件（被 additional-location 引入） | 不会 | 部署 |

本项目的做法是后三种：本地用被忽略的 `application-local.yml`，服务器上用 `/opt/paideia-app/application.yml`，仓库里只提交占位示例。

### 配置改了不生效的三个原因

1. **优先级**：被更高层的来源盖住了（最常见）；
2. **属性名不对**：`app.serverPort` 与 `app.server.port` 是两个不同的键，绑定失败的字段是 `null` 而不是报错（用 `@ConfigurationProperties` 时通常会报，用 `@Value` 时常给默认值就静默了）；
3. **没重启**：`@Value` 与 `@ConfigurationProperties` 都不会自动刷新。热更新需要额外的机制（`@RefreshScope` 或配置中心），本项目不用。

## 常见误区

### 误区：`application.yml` 里改了就是最终值

**你以为**：文件是"配置的唯一真相"。
**其实**：文件是**最低**的那一层（在外部来源里）。部署时环境变量与命令行都会盖住它。所以文件里应该写"默认值"，把必须变的留给环境。
**怎么验证**：启动时加 `--debug` 或访问 `/actuator/env`（若已启用），能看到每个属性最终值与它的来源。

### 误区：`@Value` 与 `@ConfigurationProperties` 只是写法不同

**你以为**：随便选一个。
**其实**：`@Value` 不支持嵌套、集合、`Map`，也不参与"绑定失败的集中报错"；拼错时如果给了默认值，它会安静地用默认值跑下去。成组配置用 `@ConfigurationProperties` 是唯一能"启动时报错"的选择。
**怎么验证**：故意把属性名写错一个字母，看启动是否报错。

### 误区：配置改了会自动生效

**你以为**：改完文件，下次请求就用新值。
**其实**：`@Value` 与 `@ConfigurationProperties` 都是启动时绑定一次，之后不再读。改文件必须重启（`@RefreshScope` 是另一套机制，本项目不用）。
**怎么验证**：改一个日志级别的配置，不重启，看输出是否变化。

## 小结

配置有优先级，越靠近启动现场越高：命令行 > 环境变量 > `application-{profile}.yml` > `application.yml` > 代码默认值。宽松绑定让 `APP_SERVER_PORT` 与 `app.server.port` 是同一个键。成组配置用 `@ConfigurationProperties`，敏感值走环境变量或服务器上的独立文件，永远不进仓库。
