# 16 · 配置从哪来

## 代码是新的，连的却是旧库

一次发版之后，日志里查出来的数据全是上周的。第一反应是"代码没发上去"，于是又发了一遍，还是一样。

真正的原因在这条链上：

```text
$ systemctl show paideia -p Environment --value
SPRING_DATASOURCE_URL=jdbc:mysql://10.0.0.9:3306/paideia_old
```

我改的是 `application-local.yml` 里的 url，但服务器上这个环境变量还在，**环境变量的优先级高于配置文件**，所以我改十次文件都没用。

配置的坑几乎都是同一个形状：**你以为改的那个来源，优先级低于另一个**。这篇把来源排清楚，再讲怎么在出问题时三分钟定位到"哪个来源赢了"。

## 优先级：越靠近启动现场越高

```text
1. 命令行参数                --server.port=9000
2. 环境变量                  SERVER_PORT=9000
3. Java 系统属性             -Dserver.port=9000
4. SPRING_APPLICATION_JSON   （整段 JSON 塞环境变量）
5. application-{profile}.yml / .properties
6. application.yml / .properties
7. 代码里的默认值            private int port = 8080;
```

读法是：**越"临时、越靠近这次启动现场"的越高**。文件最低，因为它要被部署环境覆盖——这正是你想要的：镜像里带一份默认配置，部署时用环境变量或命令行改。

还有一档更"外部"的：`spring.config.additional-location` 指定的目录，优先级高于 jar 内的配置文件。本项目部署时用：

```text
java -jar app.jar --spring.config.additional-location=file:/opt/paideia-app/
```

于是服务器上那份 `application.yml` 盖住了 jar 里的同名文件——改配置不用重新打包。

## 手写一遍覆盖过程

关键只有一句：**按优先级从低到高依次应用，后应用的覆盖先应用的**。没有"合并"，只有"盖住"。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Locale;
import java.util.Map;

public class Main {

    static final class Config {
        private final Map<String, String> values = new LinkedHashMap<>();
        private final Map<String, String> origins = new LinkedHashMap<>();

        // 后应用的覆盖先应用的
        Config apply(String source, Map<String, String> entries) {
            for (Map.Entry<String, String> entry : entries.entrySet()) {
                values.put(entry.getKey(), entry.getValue());
                origins.put(entry.getKey(), source);
            }
            return this;
        }

        String get(String key, String fallback) {
            return values.getOrDefault(key, fallback);
        }

        String originOf(String key) {
            return origins.getOrDefault(key, "代码默认值");
        }
    }

    static Map<String, String> map(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i], pairs[i + 1]);
        }
        return result;
    }

    // 宽松绑定：APP_SERVER_PORT → app.server.port
    static Map<String, String> env(String... pairs) {
        Map<String, String> result = new LinkedHashMap<>();
        for (int i = 0; i < pairs.length; i += 2) {
            result.put(pairs[i].toLowerCase(Locale.ROOT).replace('_', '.'), pairs[i + 1]);
        }
        return result;
    }

    // 命令行：--app.debug=true
    static Map<String, String> args(String... raw) {
        Map<String, String> result = new LinkedHashMap<>();
        for (String item : raw) {
            int at = item.indexOf('=');
            result.put(item.substring(2, at), item.substring(at + 1));
        }
        return result;
    }

    public static void main(String[] args) {
        Config config = new Config()
                .apply("application.yml", map("app.server.port", "8080", "app.name", "paideia"))
                .apply("环境变量", env("APP_SERVER_PORT", "9000"))
                .apply("命令行", args("--app.debug=true"));

        System.out.println("app.server.port = " + config.get("app.server.port", "8080")
                + "（来自 " + config.originOf("app.server.port") + "）");
        System.out.println("app.debug = " + config.get("app.debug", "false")
                + "（来自 " + config.originOf("app.debug") + "）");
        System.out.println("app.name = " + config.get("app.name", "unnamed")
                + "（来自 " + config.originOf("app.name") + "）");
    }
}
```
```text
app.server.port = 9000（来自 环境变量）
app.debug = true（来自 命令行）
app.name = paideia（来自 application.yml）
```

三个值来自三个不同的层。**排查配置问题的第一步永远是找"谁赢了"，而不是改文件。**

## 宽松绑定：几种写法是一个键

| 写法 | 出现在哪 |
| --- | --- |
| `app.server.port` | yml / properties |
| `app.server-port` | yml（推荐写法） |
| `app.serverPort` | yml |
| `APP_SERVER_PORT` | 环境变量 |
| `--app.server.port=9000` | 命令行 |

环境变量名不允许用点号，所以框架把下划线当点、并忽略大小写。**排查"环境变量没生效"时，先把变量名按规则转成属性名，逐字比对**：`APP_SERVER_PORT` 转出来是 `app.server.port`，中间那个点是三个词拼出来的，少一个就对不上。

这里有个关键差别，很多人第一次踩：

- `@ConfigurationProperties(prefix = "app")` 的 `serverPort` 字段，上面五种写法**都能绑上**（宽松绑定）；
- `@Value("${app.serverPort}")` **只在属性名逐字匹配时生效**。yml 里写的是 `app.server-port`，它取不到，值就是报错或默认值。

也就是说：**宽松绑定是 `@ConfigurationProperties` 的能力，不是 `@Value` 的**。同一份 yml，换成 `@Value` 就可能一半失效。

## `@Value` 还是 `@ConfigurationProperties`

```java
// 一、逐项注入
@Value("${app.server.port}")
private int port;
```

```java
// 二、成组绑定
@ConfigurationProperties(prefix = "app")
public record AppProperties(String name, int serverPort) { }
```

| | `@Value` | `@ConfigurationProperties` |
| --- | --- | --- |
| 适合 | 一个零散开关 | 一组有结构的配置 |
| 宽松绑定 | 不支持 | 支持 |
| 嵌套 / `List` / `Map` / `Duration` | 不支持 | 支持 |
| 校验 | 手写判断 | `@Validated` + JSR-303 注解 |
| 拼错属性名 | 给了默认值就静默用默认值 | 启动时绑定失败，报得清楚 |
| 热更新 | 不刷新 | 不刷新（除非 `@RefreshScope` 或配置中心） |

`@Value` 的表达式是**注入时解析一次**，之后字段值就固定了；不是什么"每次调用都重新解析"。它真正的短板是上表中间那三行：不宽松、不结构化、错了不吭声。

**本项目一律用 `@ConfigurationProperties`**：一个前缀、一个 record、字段自带类型，比散落十几个 `@Value` 好查，而且拼错会在启动时炸出来。

## Profile：把环境隔开

```yaml
# application.yml —— 公共部分
app:
  name: paideia

---
# application-local.yml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/paideia
    username: paideia

---
# application-prod.yml
spring:
  datasource:
    url: jdbc:mysql://10.0.0.9:3306/paideia
```

选哪个：

```text
java -jar app.jar --spring.profiles.active=local
```

或环境变量 `SPRING_PROFILES_ACTIVE=prod`。

**不写 profile 时的默认值必须是"生产安全"的**：不该连测试库、不该开调试端点。本项目更严格一点——**任何 profile 都不加载测试种子数据**，只有端到端测试显式加一个专用 profile。原因是种子账号的口令是公开写在仓库里的。

## 敏感配置放哪

| 方式 | 进仓库吗 | 适用 |
| --- | --- | --- |
| 写进 `application.yml` | 会 | **不行**，公开仓库里绝不能有口令 |
| 写进 `application-local.yml` 并 `.gitignore` | 不会 | 本地开发 |
| 环境变量 | 不会 | 部署 |
| 服务器上独立文件（`additional-location` 引入） | 不会 | 部署 |

本项目后三种都用：本地用被忽略的 `application-local.yml`，服务器上用 `/opt/paideia-app/application.yml`，仓库里只提交占位示例。

## 改了不生效，按这个顺序查

1. **有没有更高优先级的来源。** 这是绝大多数情况。查法：启动时加 `--debug`，或者启用 `/actuator/env`——它把每个属性的最终值和**提供它的 PropertySource** 都列出来，第一个就是赢家。
2. **属性名对不对。** `@Value` 不容错；`@ConfigurationProperties` 用宽松绑定，但要保证拼写能被规则转过去（`serverPort` 对应 `server-port`，写成 `serverport` 就绑不上）。
3. **有没有重启。** `@Value` 与 `@ConfigurationProperties` 都是启动时绑定一次，改文件不重启不会生效。`additional-location` 那份文件也一样，它只在启动时读。

## 三件我原来以为对的事

**一、配置文件是"配置的真相"。** 它在外部来源里是最低一档。既然是低的，就该只放默认值，凡是每个环境要变的东西都留给环境变量或命令行。

**二、`@Value` 和 `@ConfigurationProperties` 只是写法不同。** 差别在能力：宽松绑定、嵌套结构、拼错时报错，这三样 `@Value` 都没有。选错的代价是"配置悄悄是默认值"。

**三、改完配置下次请求就生效。** 绑定发生在启动时。日志级别这种看起来"应该能热改"的东西，不加额外机制也一样要重启。

## 这一课之后

优先级：命令行 > 环境变量 > 系统属性 > profile 文件 > `application.yml` > 代码默认值。后应用的覆盖先应用的，没有合并。

宽松绑定是 `@ConfigurationProperties` 的能力，`@Value` 没有。成组配置用 `@ConfigurationProperties`，敏感值走环境变量或服务器独立文件，永远不进仓库。改了不生效先查"谁赢了"，`--debug` 与 `/actuator/env` 直接告诉你答案。
