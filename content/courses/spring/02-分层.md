# 02 · 分层：Controller / Service / Repository

## 这一课你要会

- 说清三层各管什么，以及一条业务规则该写在哪一层；
- 识别"把业务写进 Controller"和"把 SQL 写进 Controller"这两种最常见的位置错误；
- 知道为什么"转账"这种操作必须在 Service 层一次做完；
- 写出一个 Controller 只做协议转换的三层结构。

## 为什么

分层不是为了好看。它解决的是一个具体问题：**同一条业务规则会被几个入口用到**。

比如"转账不能超过余额"。今天它由一个 HTTP 接口触发；明天要加一个定时任务批量结算，后天要加一个管理端补单。如果这条规则写在 Controller 的 `transfer` 方法里，后两个入口就必须复制一遍——复制就要漂移，漂移就会有一条路径能透支。

分层把"协议"和"规则"分开：Controller 认识 HTTP，Service 不认识 HTTP；Service 只认识"从 A 转 30 元给 B"。

## 讲解

### 三层各自的职责

| 层 | 认识什么 | 不认识什么 | 该写什么 |
| --- | --- | --- | --- |
| Controller | HTTP：路径、参数、状态码 | 业务规则 | 参数取出、调用 Service、结果转成响应 |
| Service | 业务规则与事务边界 | HTTP、SQL 字符串 | 校验规则、编排多个数据访问、决定事务范围 |
| Repository | 表与列、SQL | 业务规则 | 增删改查、映射结果 |

判据很简单：**把 Controller 整个删掉，Service 还能不能跑？** 能，说明分层是对的。

### 一条规则写错层会发生什么

假设"不能转给自己"这条规则被写进了 Controller：

```text
POST /transfer  →  Controller: if (from == to) return 400
                →  Service: 真正转账
定时任务        →  Service: 真正转账        ← 这里没有那条校验
```

定时任务绕过了 Controller，于是"转给自己"在批量结算里成了合法操作——余额没变，但流水多了一条，对账时就说不清了。

### 手写一遍三层

下面这段代码把三层都写出来，重点看：**Controller 里没有任何业务判断，Service 里没有任何 HTTP 概念**。

<!-- run -->
```java
import java.util.HashMap;
import java.util.Map;

public class Main {

    // Repository：只管存取，不认识"转账"这回事
    static final class AccountRepo {
        private final Map<String, Long> balances = new HashMap<>();

        AccountRepo() {
            balances.put("A", 100L);
            balances.put("B", 0L);
        }

        Long find(String owner) {
            return balances.get(owner);
        }

        void update(String owner, long value) {
            balances.put(owner, value);
        }
    }

    // Service：只有业务规则，看不到任何 HTTP 概念
    static final class TransferService {
        private final AccountRepo repo;

        TransferService(AccountRepo repo) {
            this.repo = repo;
        }

        String transfer(String from, String to, long amount) {
            if (from.equals(to)) {
                return "不能转给自己";
            }
            if (amount <= 0) {
                return "金额必须为正";
            }
            Long source = repo.find(from);
            if (source == null) {
                return "账号不存在: " + from;
            }
            if (source < amount) {
                return "余额不足";
            }
            repo.update(from, source - amount);
            repo.update(to, repo.find(to) + amount);
            return "ok";
        }
    }

    // Controller：只做协议转换，一行业务判断都没有
    static final class TransferController {
        private final TransferService service;

        TransferController(TransferService service) {
            this.service = service;
        }

        String handle(String query) {
            String[] parts = query.split("&");
            String from = parts[0].split("=")[1];
            String to = parts[1].split("=")[1];
            long amount = Long.parseLong(parts[2].split("=")[1]);
            String result = service.transfer(from, to, amount);
            return (result.equals("ok") ? "200 " : "400 ") + result;
        }
    }

    public static void main(String[] args) {
        AccountRepo repo = new AccountRepo();
        TransferController controller = new TransferController(new TransferService(repo));
        System.out.println(controller.handle("from=A&to=B&amount=30"));
        System.out.println(controller.handle("from=A&to=A&amount=10"));
        System.out.println(controller.handle("from=A&to=B&amount=999"));
        System.out.println("A=" + repo.find("A") + " B=" + repo.find("B"));
    }
}
```
```text
200 ok
400 不能转给自己
400 余额不足
A=70 B=30
```

注意最后一行：两次失败的调用**没有改动任何余额**。这不是运气——`source < amount` 的判断在 `update` 之前，且整个方法没有中途返回过。

### 换成 Spring 的写法

```java
@RestController
@RequestMapping("/api/transfer")
public class TransferController {

    private final TransferService service;

    // 构造器注入：依赖来自外面，Controller 自己 new（第 5 课讲为什么）
    public TransferController(TransferService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<String> transfer(@RequestBody TransferRequest request) {
        String result = service.transfer(request.from(), request.to(), request.amount());
        return result.equals("ok")
                ? ResponseEntity.ok(result)
                : ResponseEntity.badRequest().body(result);
    }
}
```

```java
@Service
public class TransferService {

    private final AccountRepository repository;

    public TransferService(AccountRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public String transfer(String from, String to, long amount) {
        // 规则与上面手写版一字不差
    }
}
```

```java
@Repository
public interface AccountRepository {
    @Select("SELECT balance FROM accounts WHERE owner = #{owner}")
    Long find(@Param("owner") String owner);

    @Update("UPDATE accounts SET balance = #{value} WHERE owner = #{owner}")
    int update(@Param("owner") String owner, @Param("value") long value);
}
```

三个注解的分工就是三个层的标记：`@RestController` 注册进路由表、`@Service` 注册成普通对象、`@Repository` 注册成数据访问对象（严格说它只是标记 + 异常转换，真正干活的是 MyBatis 的代理）。

### 事务边界为什么在 Service

`@Transactional` 加在 Service 的方法上，意味着"这一整个方法在一个事务里"。如果加在 Controller 上，事务范围就包含了参数解析与响应序列化——那两段失败时你并不想回滚业务数据。

如果加在 Repository 的单条 SQL 上，那"先扣款、再加款"就是两个独立事务，中间失败会凭空少一笔钱。**范围必须覆盖"要么都成、要么都不成"的那个整体**，那个整体通常在 Service 的一个方法里。

## 常见误区

### 误区：层越多越专业

**你以为**：再加一层 `Manager`、`Facade`、`Converter` 会更清晰。
**其实**：每一层都要有人跨过去读一遍才能改一个功能。本项目只要三层：Controller（协议）、Service（规则）、Mapper（数据）。**只有当一层能独立回答一个问题时才值得存在**——"它负责什么、别人绕不过它"。
**怎么验证**：随便挑项目里的一个类，问"删掉它，逻辑应该搬到哪？"答不上来，说明这层没在负责任何东西。

### 误区：Repository 只是换个名字的 DAO，无所谓

**你以为**：把 SQL 写在 Service 里也一样能跑。
**其实**：本项目有一条硬规则——**所有 SQL 只写在 mapper 中，不在 Java 代码里拼接**。原因不是洁癖：SQL 字符串出现在业务代码里，就没法被统一审查注入风险（`${}` 与 `#{}` 的差别，第 18 课细讲），也没法做统一的慢查询统计。
**怎么验证**：在 Service 里 `rg "SELECT "` 一遍自己项目的业务包，数量应该是 0。

### 误区：Controller 里判断一下参数格式没什么损失

**你以为**：`if (amount < 0) return 400` 写在 Controller 最省事。
**其实**：格式校验（能不能解析成数字）确实归 Controller，但**取值范围属于业务**。"金额必须为正"这条在批量结算里同样成立，所以它在 Service。两件事看起来一样，归属不同。
**怎么验证**：给同一个 Service 方法写一个不走 HTTP 的单元测试，看那条校验还在不在。

## 小结

三层靠"认识什么"分工：Controller 认识 HTTP、Service 认识业务规则、Repository 认识表。业务规则下沉到 Service 的唯一判据是"是否会被第二个入口用到"。事务边界要覆盖业务的整体，所以它在 Service 的一个方法上。
