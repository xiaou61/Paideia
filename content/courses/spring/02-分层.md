# 02 · 分层：Controller / Service / Repository

## 从一句报错开始

上一课的 `HelloController` 能返回字符串了。接着我想把转账逻辑搬进 Spring，照着手写版把三层各写成一个类，然后启动，得到这个：

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in com.example.demo.web.TransferController required a
bean of type 'com.example.demo.repo.AccountRepository' that could not be found.
```

`AccountRepository` 明明写了，还标了 `@Repository`，为什么"找不到"？

因为 **`@Repository` 标在接口上什么都不会发生**。它是个标记注解，Spring 不会凭它给一个没有实现类的接口造对象。真正负责"造对象"的是 MyBatis 的 mapper 代理，而要让 MyBatis 认出这个接口，注解得是 `@Mapper`（或启动类上 `@MapperScan`）。

这个错误值得作为分层的开场，因为它一次说明了三件事：三层不是三个注解、注解不等于实现、以及"分层"最终要落到**谁持有谁**上。

## 为什么分层

分层不是为了好看。它解决一个具体问题：**同一条业务规则会被几个入口用到**。

"转账不能超过余额"今天由一个 HTTP 接口触发；明天要加定时任务批量结算，后天要加管理端补单。如果这条规则写在 Controller 的 `transfer` 方法里，后两个入口就得复制一遍——复制就会漂移，漂移就会有某条路径能透支。

分层把"协议"和"规则"分开：Controller 认识 HTTP，Service 不认识 HTTP；Service 只认识"从 A 转 30 元给 B"。

| 层 | 认识什么 | 不认识什么 | 该写什么 |
| --- | --- | --- | --- |
| Controller | HTTP：路径、参数、状态码 | 业务规则 | 取出参数、调用 Service、把结果转成响应 |
| Service | 业务规则与事务边界 | HTTP、SQL 字符串 | 校验规则、编排多次数据访问、决定事务范围 |
| Repository | 表与列、SQL | 业务规则 | 增删改查、映射结果 |

判据只有一句：**把 Controller 整个删掉，Service 还能不能跑？** 能，分层就是对的。

## 一条规则写错层，会怎样

```text
POST /transfer  →  Controller: if (from == to) return 400
                →  Service: 真正转账
定时任务        →  Service: 真正转账        ← 这条路上没有那个 if
```

定时任务绕过 Controller，"转给自己"在批量结算里就成了合法操作：余额没变，流水多一条，对账时说不清。

这种 bug 有个讨厌的性质——**两个入口都测过，都没问题**。只有把两个入口放在一起看，才会发现规则只写在其中一个门口。

## 手写一遍三层

下面这段代码把三层都写出来，重点看两处：Controller 里没有任何业务判断，Service 里没有任何 HTTP 概念。

<!-- run -->
```java
import java.util.HashMap;
import java.util.Map;

public class Main {

    // Repository：只管存取，不认识"转账"这回事
    static final class AccountRepo {
        private final Map<String, Long> balances = new HashMap<>();

        AccountRepo() {
            balances.put("A", 100L);
            balances.put("B", 0L);
        }

        Long find(String owner) {
            return balances.get(owner);
        }

        void update(String owner, long value) {
            balances.put(owner, value);
        }
    }

    // Service：只有业务规则，看不到任何 HTTP 概念
    static final class TransferService {
        private final AccountRepo repo;

        TransferService(AccountRepo repo) {
            this.repo = repo;
        }

        String transfer(String from, String to, long amount) {
            if (from.equals(to)) {
                return "不能转给自己";
            }
            if (amount <= 0) {
                return "金额必须为正";
            }
            Long source = repo.find(from);
            if (source == null) {
                return "账号不存在: " + from;
            }
            Long target = repo.find(to);
            if (target == null) {
                return "账号不存在: " + to;
            }
            if (source < amount) {
                return "余额不足";
            }
            repo.update(from, source - amount);
            repo.update(to, target + amount);
            return "ok";
        }
    }

    // Controller：只做协议转换，一行业务判断都没有
    static final class TransferController {
        private final TransferService service;

        TransferController(TransferService service) {
            this.service = service;
        }

        String handle(String query) {
            String[] parts = query.split("&");
            String from = parts[0].split("=")[1];
            String to = parts[1].split("=")[1];
            long amount = Long.parseLong(parts[2].split("=")[1]);
            String result = service.transfer(from, to, amount);
            return (result.equals("ok") ? "200 " : "400 ") + result;
        }
    }

    public static void main(String[] args) {
        AccountRepo repo = new AccountRepo();
        TransferController controller = new TransferController(new TransferService(repo));
        System.out.println(controller.handle("from=A&to=B&amount=30"));
        System.out.println(controller.handle("from=A&to=A&amount=10"));
        System.out.println(controller.handle("from=A&to=B&amount=999"));
        System.out.println(controller.handle("from=A&to=Z&amount=10"));
        System.out.println("A=" + repo.find("A") + " B=" + repo.find("B"));
    }
}
```
```text
200 ok
400 不能转给自己
400 余额不足
400 账号不存在: Z
A=70 B=30
```

最后一行是重点：三次失败的调用没有改动任何余额。

但这**不是**因为"有校验所以安全"，而是因为这三次失败都发生在任何 `update` 之前。我第一版写的时候漏了"转入账户存在"这个检查，代码是 `repo.update(to, repo.find(to) + amount)`——`find("Z")` 返回 `null`，自动拆箱抛 `NullPointerException`。

那时的状态是：**A 的钱已经扣了，B 没加，然后抛异常**。余额凭空少了 30。

这就是手写版和真实系统的距离：它没有任何"要么都成、要么都不成"的保证。下一节补上。

## 事务边界为什么在 Service

`@Transactional` 加在 Service 方法上，意思是"这一整个方法在一个事务里"。三个位置各有下场：

| 加在哪 | 事务范围 | 后果 |
| --- | --- | --- |
| Controller | 包含参数解析与响应序列化 | 序列化失败也回滚业务数据，你可能不想 |
| Repository 单条 SQL | 一条 SQL | "先扣款、再加款"是两个独立事务，中途失败就少一笔钱 |
| Service 方法 | 扣款 + 加款一起 | 上面那个 NPE 会自动回滚 |

范围必须盖住"要么都成、要么都不成"的那个整体，那个整体通常就是一个 Service 方法。

### 一个更要命的坑：事务也可能悄悄不生效

`@Transactional` 靠代理实现（第 4 课手写那套）。所以下面这种写法**事务根本没开**，而且不报错：

```java
@Service
public class TransferService {

    public String transfer(String from, String to, long amount) {
        validate(from, to, amount);
        doTransfer(from, to, amount);   // 自调用，不经过代理
        return "ok";
    }

    @Transactional
    public void doTransfer(String from, String to, long amount) {
        // 这里抛异常，不会回滚
    }
}
```

`transfer()` 里调 `doTransfer()` 用的是 `this`，不是代理对象，注解被完全绕过。同理，`private` 方法上的 `@Transactional`、`final` 方法上的 `@Transactional`，都是这么静默失效的。

验法很简单：在方法里查一下自己是不是代理。

```java
System.out.println(this.getClass().getName());
// com.example.demo.service.TransferService          ← 事务不会生效
// com.example.demo.service.TransferService$$SpringCGLIB$$0   ← 生效
```

我在自己的项目里就吃过这个：日志显示扣款成功、加款抛了异常，两边余额不一致，翻代码半小时才想起自调用。后来第一件事就是打印这行。

## 换成 Spring 的写法

三个类分别对应三层，每个都有一个我第一版写错的地方，注释里标出来了。

```java
// 请求体：手写版从 query 串取参，这里换成 JSON。
// 没有它，编译就过不去——我第一次直接从 query 版的参数列表搬过来，忘了定义。
public record TransferRequest(String from, String to, long amount) {
```

```java
@RestController
@RequestMapping("/api/transfer")
public class TransferController {

    private final TransferService service;

    // 构造器注入：依赖从外面来，Controller 自己不 new（第 5 课讲为什么）
    public TransferController(TransferService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<String> transfer(@RequestBody TransferRequest request) {
        String result = service.transfer(request.from(), request.to(), request.amount());
        return result.equals("ok")
                ? ResponseEntity.ok(result)
                : ResponseEntity.badRequest().body(result);
    }
}
```

```java
@Service
public class TransferService {

    private final AccountRepository repository;

    public TransferService(AccountRepository repository) {
        this.repository = repository;
    }

    // 规则与手写版一字不差
    public String transfer(String from, String to, long amount) {
        if (from.equals(to)) {
            return "不能转给自己";
        }
        if (amount <= 0) {
            return "金额必须为正";
        }
        Long source = repository.find(from);
        if (source == null) {
            return "账号不存在: " + from;
        }
        Long target = repository.find(to);
        if (target == null) {
            return "账号不存在: " + to;
        }
        if (source < amount) {
            return "余额不足";
        }
        // 两行 update 必须在同一个事务里——注意这里没有自调用，
        // 所以把 @Transactional 加在外层方法上（不是拆出一个 private 方法）
        repository.updateBalance(from, source - amount);
        repository.updateBalance(to, target + amount);
        return "ok";
    }
}
```

```java
// 这里是 @Mapper，不是 @Repository。
// 少了它，启动就是开头那句 required a bean of type ... could not be found。
@Mapper
public interface AccountRepository {

    @Select("SELECT balance FROM accounts WHERE owner = #{owner}")
    Long find(@Param("owner") String owner);

    @Update("UPDATE accounts SET balance = #{value} WHERE owner = #{owner}")
    int updateBalance(@Param("owner") String owner, @Param("value") long value);
}
```

注解的分工，以及它到底做了什么：

| 注解 | 它到底做了什么 |
| --- | --- |
| `@RestController` | 把类登记进 MVC 的路由注册表，并把返回值交给消息转换器 |
| `@Service` | 只是 `@Component` 的语义别名，被组件扫描注册成普通对象 |
| `@Repository` | `@Component` + 把持久层异常翻译成 Spring 的统一异常 |
| `@Mapper` | MyBatis 的标记，它为接口生成实现类并注册成 Bean |

注意最后两行的区别：**`@Repository` 不会替你实现接口，`@Mapper` 会。** 两个都标上也不算错（很多人这么干，异常转换与代理生成各拿一半），但只标 `@Repository` 是启动不了的。

在 `@Transactional` 上还得补一句：它要生效，方法必须是从**代理对象**外部调进来的。上面把两行 `update` 直接写在 `transfer` 里、注解加在 `transfer` 上，就是为了避开自调用。

## 三件我原本以为对、其实不对的事

**一、`@Repository` 标在接口上就能注入。** 不行。它不造实现。MyBatis 的接口要 `@Mapper`，Spring Data JPA 的接口靠 `@EnableJpaRepositories` 扫描，都不是 `@Repository` 的功劳。

**二、把校验写在 Controller 里，Service 也就安全了。** 只对走 HTTP 的入口安全。定时任务、消息消费者、别的 Service 互相调用，全都绕过 Controller。

**三、`@Transactional` 加上就一定生效。** 自调用、`private`、`final` 三种情况都静默失效，不报错、不回滚。打印 `this.getClass().getName()` 看有没有 `$$` 是最快的验证方式。

## 这一课之后

三层按"认识什么"分工：Controller 认识 HTTP、Service 认识业务规则、Repository 认识表。业务规则下沉到 Service 的判据是"会不会被第二个入口用到"。事务边界要覆盖业务的整体，所以它在 Service 的一个方法上——而且要小心代理边界。

下一课：参数从路径、查询串、请求体三个地方来，Spring 靠什么判断该从哪儿取，以及取错了会返回哪个状态码。
