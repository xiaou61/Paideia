# 12 · 事务就是切面

## 扣了 30，对方余额没动

下面这段输出，是我在本地 H2 上按一个真实故障形态重放的玩具项目（不是某家公司的线上日志，账号和金额都是造出来的）：

```text
debit account=1 amount=30 tx=Main$TransferService.transfer
credit account=2 amount=30 tx=Main$TransferService.transfer
caught: account 2 frozen
transfer returned normally
balance account=1 70
balance account=2 100
```

`debit` 扣了 30，`credit` 也被调用了，但两行的事务名一模一样。`credit()` 上写的是 `REQUIRES_NEW`，它却没有自己的事务。最后 A 少了 30，B 一分没多。

`Main$` 只是临时工程里的嵌套类前缀，下面几段输出同理。

关键代码只有这几行（省略了构造器和 `AccountRepository` 的实现）：

```java
@Service
public class TransferService {

    @Transactional
    public void transfer(long from, long to, int amount) {
        accounts.debit(from, amount);
        try {
            this.credit(to, amount);
        } catch (RuntimeException e) {
            log.warn("credit failed: {}", e.getMessage());
        }
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void credit(long to, int amount) {
        if (accounts.frozen(to)) {
            throw new IllegalStateException("account 2 frozen");
        }
        accounts.credit(to, amount);
    }
}
```

`credit()` 在冻结检查处抛了异常，所以 B 没有写入；`transfer()` 捕获后正常返回，外层事务提交了 A 的扣款。

先别往下翻。四种常见失效里，这是哪一种？

| 候选 | 现象 |
| --- | --- |
| 自调用 | `this.credit()` 没经过代理 |
| private / final | 代理覆盖不到方法 |
| 类不归 Spring 管 | `new TransferService()` 没有代理 |
| 异常没触发回滚 | 被 catch 吞掉，或抛了 checked 异常，默认不回滚 |

我一开始怀疑是 `REQUIRES_NEW` 的传播行为配错，翻了半天 `Propagation` 枚举；实际是调用根本没经过代理，传播行为没轮到。而且 `catch` 把异常吞了，属于第四组的另一种表现。下面先把代理讲清楚，再回来算这笔账。

## 注解不在方法体里，在代理上

`@Transactional` 不是编译器插进方法体的代码，它是 Spring AOP 的一段环绕通知。调用方拿到的是代理，代理在调用目标方法前后做三件事：

```text
调用方 → 代理 → 拦截器
  1. 从连接池拿连接，setAutoCommit(false)
  2. 调用目标方法（这次调用里的 SQL 走同一条连接）
  3. 正常返回 commit；抛出该回滚的异常 rollback；最后把连接还回池
```

所以先别问「注解写对没」，先问「这次调用有没有经过代理」。

我在一个临时 Boot 4.1.1 工程（Spring Framework 7.0.9）里，给一个没有接口的 `WalletService` 加 `@Transactional`，从容器里取出来打印：

```text
bean class = Main$WalletService$$SpringCGLIB$$0
isAopProxy = true
isCglibProxy = true
public active = true
this inside public method = Main$WalletService
```

前四行说明容器给你的是 CGLIB 子类，事务拦截器在；最后一行说明方法体里的 `this` 仍是原始对象，不是代理。

最便宜的自检分两处看：

```java
// 1. 在调用方/注入点：看手里的引用是不是代理
System.out.println(service.getClass().getName());   // ...$$SpringCGLIB$$0

// 2. 在事务方法内部：看这次调用到底有没有活动事务
System.out.println(TransactionSynchronizationManager.isActualTransactionActive());
```

注意：`System.out.println(this.getClass().getName())` 如果写在事务方法体里，打印出来是 `WalletService`，不是 `...$$SpringCGLIB$$0`。这不是事务失效，而是 `this` 本身就是原始对象——代理调用的是目标对象上的方法。用这一行判断「有没有代理」会误判；要看代理，得在调用方打印注入进来的引用，或者用 `AopUtils.isAopProxy(service)`。

`@Transactional` 打在类上和打在方法上，作用范围不一样：

| 写法 | 作用范围 | 注意 |
| --- | --- | --- |
| 类上 | 代理能拦到的所有方法 | `private`、`final` 方法仍然不生效 |
| 方法上 | 只覆盖这个方法 | 方法级设置覆盖类级设置 |

类上的注解不会让 `private` 或 `final` 方法突然变得可代理；注解的位置不改变 CGLIB 能不能覆盖方法。

## 四种失效，先过同一道门

把代理这一层拆开，常见的失效可以分成两组：调用有没有经过代理，异常有没有穿出去。

### 代理这一层

| 写法 | 实际发生 | 原因 | 怎么修 / 怎么确认 |
| --- | --- | --- | --- |
| `this.inner()` | 内层不经过代理；外层有事务时它只是加入外层，不会新建事务，也不会创建保存点 | `this` 是原始对象 | 拆到另一个 bean；注入自身（`ObjectProvider`）；把事务放到外层 |
| `private` 方法 | 不生效 | CGLIB 不能覆盖 private | 改成 protected / 包级私有 / public，并确保从代理调用 |
| `final` 方法 | 不生效；public final 方法启动时 `CglibAopProxy` 会打 WARN | CGLIB 不能覆盖 final | 去掉 final；或接口 + JDK 代理 |
| `final` 类 | CGLIB 下启动失败：无法生成子类 | 不能继承 | 去掉 final；或接口 + JDK 代理 |
| `new Service()` | 没有代理，注解完全不参与 | 对象不归 Spring 管 | 从容器注入或 `getBean` |

这里要改掉一个旧说法：**不是 public 才生效**。Spring 6.0 起，类代理（CGLIB）下 protected 和包级私有方法也能开事务；我这次在 Boot 4.1.1 / Spring Framework 7.0.9 上跑出来：

```text
protected active = true
package active = true
final active = false
private active = false
```

类上的 `@Transactional` 我也跑了同一组：`class protected/package=true`，`class final/private=false`。所以失效清单应该写 **private、final 方法、final 类、自调用**，不要再把 protected / 包级私有算进去。

前提是容器真的用了类代理。如果退到 JDK 接口代理，接口里没有的方法不在代理上，protected / 包级私有也拦不到。Spring Boot 默认 `spring.aop.proxy-target-class=true`，所以常见情况是 CGLIB；但你如果把它关掉，或者注入的是接口类型，行为会变。

`final` 方法也不是每次都静默。我这次看到了这条启动日志：

```text
WARN ... CglibAopProxy -- Public final method [public final void Main$WalletService.finalProbe()] cannot get proxied via CGLIB, consider removing the final marker or using interface-based JDK proxies.
```

别把 WARN 当噪音。protected / 包级私有的 final 方法未必有人提醒你，所以不能靠日志兜底。

### 异常这一层

| 写法 | 实际发生 | 原因 | 怎么修 |
| --- | --- | --- | --- |
| 方法内 `catch` 吞掉 | 正常提交，已写的数据留在库里 | 拦截器看到正常返回 | 别 catch；或 catch 后 `throw`；或 `setRollbackOnly()` |
| 抛 checked 异常 | 默认提交 | 默认只回滚 `RuntimeException` 与 `Error` | `rollbackFor = Exception.class` |
| 事务里开新线程 | 新线程不在当前事务 | 连接绑定在 `ThreadLocal` 上 | 别在事务里开线程；用事务同步或消息 |

Spring 的默认回滚规则是 `RuntimeException` 和 `Error`，不是只有 `RuntimeException`。我在 Boot 4.1.1 上实测：`IllegalStateException` 和 `AssertionError` 都把插入回滚到 0 行；`IOException` 不回滚，留下 1 行：

```text
runtime rows = 0
error rows = 0
checked rows = 1
checked rollback rows = 0
```

最后一行是加了 `rollbackFor = Exception.class` 之后的 `IOException`。`rollbackFor = Exception.class` 补的是 checked 异常，`Error` 仍按默认回滚（`AssertionError` 实测也是 0 行）。

如果必须在方法内 catch，catch 后调用 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`；但这样外层提交时会抛 `UnexpectedRollbackException`，调用方要接住。更简单的是让异常穿出去。

## 回到那笔转账

日志里两行事务名一样，说明 `this.credit()` 没经过代理；`REQUIRES_NEW` 没机会执行，`credit` 只是加入了 `transfer` 的事务。`credit` 在冻结检查处抛 `IllegalStateException`，`transfer` 的 `catch (RuntimeException)` 把它吞掉，外层看到正常返回，于是提交了扣款。

修法不是把 `catch` 改成 `RuntimeException | Error` 就完事——异常还是被吞。只把 `credit` 挪到另一个 bean、`catch` 还在，`REQUIRES_NEW` 会开新事务，但异常仍被吞，外层照样提交扣款；所以两处都要改。要么让 `credit` 加入外层事务，并让异常穿出去：

```java
@Service
public class TransferService {

    private final AccountRepository accounts;
    private final CreditService creditService; // 另一个 bean

    @Transactional
    public void transfer(long from, long to, int amount) {
        accounts.debit(from, amount);
        creditService.credit(to, amount); // 不再 this，也不再 catch
    }
}
```

我按这个改法跑同一组数据：

```text
fixed debit tx=Main$FixedTransferService.transfer
fixed credit tx=Main$FixedTransferService.transfer
fixed caught: account 2 frozen
fixed balance account=1 100
fixed balance account=2 100
```

两行事务名仍然一样，但这次是因为 `credit` 加入了外层事务，而不是因为自调用。异常穿出后，A 的扣款也回滚了。

如果 `credit` 必须独立提交（比如记审计日志），用 `REQUIRES_NEW` 就要接受它可能成功、外层可能回滚；业务上要么用 outbox / 补偿 / 幂等拆成可重试的步骤，要么把两件事放到一个事务里。不能既想让它独立提交，又想用一个 `@Transactional` 保证两件事一起回滚。

## 传播行为与保存点

| 传播 | 外层有事务时 | 外层没事务时 | 连接 |
| --- | --- | --- | --- |
| `REQUIRED`（默认） | 加入外层，成为同一个事务 | 新建一个 | 同一条 |
| `REQUIRES_NEW` | 挂起外层，自己开一个新的 | 新建一个 | **第二条** |
| `NESTED` | 在外层里开一个保存点 | 新建一个 | 同一条 |
| `SUPPORTS` | 加入外层 | 非事务执行 | 同一条或无 |

`MANDATORY`、`NEVER`、`NOT_SUPPORTED` 是另外三种：`MANDATORY` 要求外层必须有事务，否则抛 `IllegalTransactionStateException`；`NEVER` 要求外层没有事务，否则抛异常；`NOT_SUPPORTED` 挂起外层、以非事务方式执行。

`REQUIRES_NEW` 是最容易踩的一个：它要**两条连接**。我把 Hikari 的 `maximumPoolSize` 设成 1、`connectionTimeout` 设成 1000ms，外层事务里调用另一个 bean 的 `REQUIRES_NEW`：

```text
outer connection held
pool exception = CannotCreateTransactionException / SQLTransientConnectionException
pool message = HikariPool-1 - Connection is not available, request timed out after 1001ms (total=1, active=1, idle=0, waiting=0)
```

外层那条连接还没还，内层要第二条，池里没有，只能等超时。这个例子把池设成 1 是为了让等待可见；真实池更大，但同样的等待会出现在并发高、池小、事务长的时候；它发生在事务内部，表现为接口整体变慢。连接池至少要给并发数留出余量，或者别在长事务里调用 `REQUIRES_NEW`。

`NESTED` 用的是保存点，不额外占连接。我把同样的池设成 1，外层插 1、内层 NESTED 插 2 后抛异常、外层 catch 住再插 3，最后表里是 1 和 3：

```text
nested inner caught: nested rollback
nested rows = [{ID=1}, {ID=3}]
```

这说明 `NESTED` 的回滚只回到保存点，外层还能继续；它和 `REQUIRES_NEW` 的区别是「同一个事务里的回滚点」对「另起一个事务」。前提是数据库和驱动支持 JDBC savepoint；JTA 事务管理器不支持 `NESTED`。另外，`NESTED` 也必须经过代理；`this.inner()` 连保存点都不会创建。

## 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 备注 |
| --- | --- | --- | --- | --- |
| `READ_UNCOMMITTED` | 可能 | 可能 | 可能 | 很少用 |
| `READ_COMMITTED` | 不会 | 可能 | 可能 | PostgreSQL / Oracle / SQL Server 默认 |
| `REPEATABLE_READ` | 不会 | 不会 | 标准说可能 | MySQL InnoDB 默认 |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 可能因冲突回滚，应用要能重试 |

这些是 SQL 标准下的允许行为，不是所有数据库都按同一方式实现。MySQL InnoDB 在可重复读下用 next-key lock 处理当前读的幻读；快照读和锁定读的行为不同，别把表里的「不会」当成所有读法的保证。

`@Transactional(isolation = Isolation.REPEATABLE_READ)` 只是把连接设成对应级别，具体支持程度看驱动；`Isolation.DEFAULT` 用数据库默认值，不要把它当成某个固定级别。

`@Transactional(readOnly = true)` 是给驱动和 ORM 的提示，不是权限。不同数据库对它的处理不同，别拿它当防误写；真正的防误写要靠代码审查和测试。

事务里也尽量别做网络调用、发消息或开新线程：连接被占着等网络，消息可能在外层回滚后变成幽灵，新线程拿不到当前线程绑定的连接。消息这类副作用，常见做法是用 outbox 表隔开。

## 两个 schema 不等于两个事务

最后纠正一个很容易传错的结论：「两个库就是两个连接」。

同一个数据库实例上的两个 schema，共用一个 `DataSource` 时，可以是同一条连接、同一个事务。我在 H2 里建了 `bank_a.entries` 和 `bank_b.entries`，在一个 `@Transactional` 方法里各插一行再抛异常：

```text
schema connections same = true
cross caught: rollback both schemas
bank_a rows = 0
bank_b rows = 0
```

两条 insert 走的是同一个 `Connection`，一次回滚两边都没了。只有跨不同数据源或不同实例，一个 `DataSourceTransactionManager` 才管不到另一边；那需要 XA / 2PC，或者 outbox / 补偿 / 幂等这一套。2PC 也不是免费的：协调者、超时、启发式回滚都要处理。

## 跑一遍

下面把代理和异常规则缩成一个纯 Java 模板，不需要 Spring，也不需要数据库。它不做 SQL，只用一个 `List` 模拟「已写入的行」；重点是看哪几次快照被恢复。

<!-- run -->
```java
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;

public class Main {

    static final class Store {
        private final List<String> rows = new ArrayList<>();

        List<String> rows() {
            return rows;
        }

        void add(String value) {
            rows.add(value);
        }

        List<String> snapshot() {
            return new ArrayList<>(rows);
        }

        void restore(List<String> snapshot) {
            rows.clear();
            rows.addAll(snapshot);
        }

        void clear() {
            rows.clear();
        }
    }

    interface Action {
        void run() throws Exception;
    }

    static final class TxTemplate {
        private final Store store;
        int runs;

        TxTemplate(Store store) {
            this.store = store;
        }

        void run(Action action) throws Exception {
            runs++;
            List<String> snapshot = store.snapshot();
            try {
                action.run();
            } catch (RuntimeException | Error error) {
                store.restore(snapshot);
                throw error;
            } catch (Exception error) {
                // 受检异常默认不回滚：不恢复快照
                throw error;
            }
        }
    }

    static final class AccountService {
        private final Store store;

        AccountService(Store store) {
            this.store = store;
        }

        void ok() {
            store.add("A-30");
            store.add("B+30");
        }

        void runtimeFail() {
            store.add("A-30");
            throw new IllegalStateException("余额不足");
        }

        void errorFail() {
            store.add("A-30");
            throw new AssertionError("断言失败");
        }

        void checkedFail() throws IOException {
            store.add("A-30");
            throw new IOException("磁盘已满");
        }

        void catchInside() {
            store.add("A-30");
            try {
                throw new IllegalStateException("被吞掉");
            } catch (IllegalStateException ignored) {
            }
            store.add("B+30");
        }

        void selfCall() {
            store.add("A-30");
            store.add("B+30");
        }
    }

    static final class AccountServiceProxy {
        private final AccountService target;
        private final TxTemplate tx;

        AccountServiceProxy(AccountService target, TxTemplate tx) {
            this.target = target;
            this.tx = tx;
        }

        void ok() throws Exception {
            tx.run(target::ok);
        }

        void runtimeFail() throws Exception {
            tx.run(target::runtimeFail);
        }

        void errorFail() throws Exception {
            tx.run(target::errorFail);
        }

        void checkedFail() throws Exception {
            tx.run(target::checkedFail);
        }

        void catchInside() throws Exception {
            tx.run(target::catchInside);
        }

        void selfCall() {
            target.selfCall();
        }
    }

    static void show(String name, TxTemplate tx, Store store, Action action) {
        try {
            action.run();
            System.out.println(name + " → 保存 " + store.rows().size() + " 条，事务开了 " + tx.runs + " 次");
        } catch (Exception | Error error) {
            System.out.println(name + " → 保存 " + store.rows().size() + " 条，事务开了 " + tx.runs
                    + " 次（抛出：" + error.getMessage() + "）");
        }
        store.clear();
        tx.runs = 0;
    }

    public static void main(String[] args) {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        AccountServiceProxy service = new AccountServiceProxy(new AccountService(store), tx);

        show("ok", tx, store, service::ok);
        show("runtimeFail", tx, store, service::runtimeFail);
        show("errorFail", tx, store, service::errorFail);
        show("checkedFail", tx, store, service::checkedFail);
        show("catchInside", tx, store, service::catchInside);
        show("selfCall", tx, store, service::selfCall);
    }
}
```
```text
ok → 保存 2 条，事务开了 1 次
runtimeFail → 保存 0 条，事务开了 1 次（抛出：余额不足）
errorFail → 保存 0 条，事务开了 1 次（抛出：断言失败）
checkedFail → 保存 1 条，事务开了 1 次（抛出：磁盘已满）
catchInside → 保存 2 条，事务开了 1 次
selfCall → 保存 2 条，事务开了 0 次
```

六行对应六个事实：

- `ok`：正常提交，2 条；
- `runtimeFail`：`RuntimeException` 被模板捕获，快照恢复，0 条；
- `errorFail`：`Error` 也被捕获（`RuntimeException | Error`），0 条——只写 `catch (RuntimeException)` 的话这里会留下 1 条；
- `checkedFail`：受检异常默认不回滚，留下 1 条；
- `catchInside`：异常没穿出模板，2 条都提交；
- `selfCall`：直接调目标，事务开 0 次，2 条照写。

`TxTemplate` 的 `catch (Exception)` 分支故意不恢复快照，模拟 Spring 默认对 checked 异常不回滚。

## 还差的

- **只在 H2 内存库上验证。** MySQL / PostgreSQL 的保存点行为、隔离级别默认值、`readOnly` 的处理没复测。
- **同实例跨 schema 验证了，跨两个物理数据源的 XA / 2PC 没搭。** 那部分只按文档写，没有两套库可跑。
- **`REQUIRES_NEW` 的连接池耗尽只用 Hikari `maximumPoolSize=1` 复现。** 没有做并发压测，也没算生产池大小。
- **没有在 Boot 3.x 逐版复测。** protected / 包级私有的结论按 Spring 6.0+ 的类代理行为，实测环境是 Boot 4.1.1 / Spring Framework 7.0.9。
- **`@Transactional` 与 `@Async`、消息监听、响应式事务的组合没覆盖。** 这些场景的线程和事务边界与本文不同，不能直接照搬。
