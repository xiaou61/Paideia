# 12 · 事务就是切面

## 这一课你要会

- 说清 `@Transactional` 生效的三个条件，以及不满足时会怎样；
- 复现四种失效：自调用、非 public、异常被吞、受检异常；
- 知道 `rollbackFor = Exception.class` 什么时候必须写；
- 分清 `REQUIRED` / `REQUIRES_NEW` / `NESTED` 三种传播行为。

## 为什么

`@Transactional` 是 Spring 里最容易"看起来生效"的注解：加上了，代码能跑，测试也过——直到某天线上出现"扣了钱没到账"。

它和 `@Async`、`@Cacheable` 一样，本质都是**第 10 课那个代理上的一段逻辑**。所以它的失效原因不是四个，而是**一个**：那段逻辑没有机会执行，或者执行了但没有按你以为的条件判断。

## 讲解

### 它到底做了什么

```text
进入带 @Transactional 的方法前：从连接池拿一个连接，setAutoCommit(false)
方法正常返回：commit
方法抛出「该回滚的异常」：rollback
无论哪种：连接还回池
```

就这么三步。所谓"事务"不是一个神秘的东西，就是**同一个连接上的一组语句一起提交或一起撤销**。

这也解释了两条常见的困惑：

- **为什么事务只在同一个数据库上有效**：它是连接级别的，两个库就是两个连接，没有跨库事务（除非两阶段提交，那是另一个话题）。
- **为什么事务方法里做的事如果走了另一个线程，就不在事务里**：`ThreadLocal` 里绑的连接是当前线程的，新线程拿不到。

### 手写一遍

下面这段代码把"三步"显式写出来，包括异常条件：

<!-- run -->
```java
import java.util.ArrayList;
import java.util.List;

public class Main {

    static final class Store {
        private final List<String> saved = new ArrayList<>();

        List<String> saved() {
            return saved;
        }

        void add(String value) {
            saved.add(value);
        }

        List<String> snapshot() {
            return new ArrayList<>(saved);
        }

        void restore(List<String> snapshot) {
            saved.clear();
            saved.addAll(snapshot);
        }

        void clear() {
            saved.clear();
        }
    }

    static final class TxTemplate {
        private final Store store;
        int runs;

        TxTemplate(Store store) {
            this.store = store;
        }

        // 与 Spring 默认一致：只有 RuntimeException 触发回滚
        void run(Runnable action) {
            runs++;
            List<String> snapshot = store.snapshot();
            try {
                action.run();
            } catch (RuntimeException error) {
                store.restore(snapshot);
                throw error;
            }
        }
    }

    static final class AccountService {
        private final Store store;

        AccountService(Store store) {
            this.store = store;
        }

        void okBody() {
            store.add("A-30");
            store.add("B+30");
        }

        void failBody() {
            store.add("A-30");
            throw new IllegalStateException("余额不足");
        }

        void catchInsideBody() {
            store.add("A-30");
            try {
                throw new IllegalStateException("被吞掉");
            } catch (IllegalStateException ignored) {
                // 异常没有传出事务边界
            }
            store.add("B+30");
        }
    }

    // 代理：只有经过它才开事务（真实 Spring 里这一层是运行时生成的）
    static final class AccountServiceProxy {
        private final AccountService target;
        private final TxTemplate tx;

        AccountServiceProxy(AccountService target, TxTemplate tx) {
            this.target = target;
            this.tx = tx;
        }

        void ok() {
            tx.run(target::okBody);
        }

        void fail() {
            tx.run(target::failBody);
        }

        void catchInside() {
            tx.run(target::catchInsideBody);
        }

        // 自调用：直接调目标，等价于同类里写 this.okBody()
        void selfCall() {
            target.okBody();
        }
    }

    public static void main(String[] args) {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        AccountServiceProxy service = new AccountServiceProxy(new AccountService(store), tx);

        service.ok();
        System.out.println("ok → 保存 " + store.saved().size() + " 条，事务开了 " + tx.runs + " 次");
        store.clear();
        tx.runs = 0;

        try {
            service.fail();
        } catch (IllegalStateException error) {
            System.out.println("fail → 保存 " + store.saved().size() + " 条，事务开了 " + tx.runs
                    + " 次（抛出：" + error.getMessage() + "）");
        }
        store.clear();
        tx.runs = 0;

        service.catchInside();
        System.out.println("catchInside → 保存 " + store.saved().size() + " 条，事务开了 " + tx.runs + " 次");
        store.clear();
        tx.runs = 0;

        service.selfCall();
        System.out.println("selfCall → 保存 " + store.saved().size() + " 条，事务开了 " + tx.runs + " 次");
    }
}
```
```text
ok → 保存 2 条，事务开了 1 次
fail → 保存 0 条，事务开了 1 次（抛出：余额不足）
catchInside → 保存 2 条，事务开了 1 次
selfCall → 保存 2 条，事务开了 0 次
```

四行对应四个事实：

- **正常路径**：两条都进去了，事务开了一次；
- **异常传出边界**：第一条被写入过，然后被快照还原——`保存 0 条`。这是"原子性"的全部内容；
- **异常被内部 catch**：异常没穿出 `TxTemplate.run`，所以它认为一切正常，**照常提交**。数据留在库里，业务其实是错的；
- **自调用**：数据写进去了（保存 2 条），但 `事务开了 0 次`——它**根本没有事务**。这一行比"回滚没生效"更隐蔽，因为正常路径下它看起来完全正确。

### 四种失效与各自的修法

```sketch
{
  "title": "四种失效，其实两种根因",
  "rows": [
    [
      { "id": "self", "title": "自调用 / private", "sub": "这一跳没经过代理", "tone": "amber" },
      { "id": "swallow", "title": "异常被吞", "sub": "切面看不到失败", "tone": "amber" },
      { "id": "fix", "title": "让调用过代理、让异常穿出去", "sub": "其它修法都是变体", "tone": "green" }
    ]
  ],
  "arrows": []
}
```

| 失效 | 现象 | 为什么 | 怎么修 |
| --- | --- | --- | --- |
| 自调用 | 内层方法的事务/回滚不生效 | `this.inner()` 不经过代理 | 拆成两个类；或注入自己（`ObjectProvider`）；或把事务放到外层 |
| 方法不是 public | 完全不生效 | 代理覆盖不到 | 改成 public；或者把逻辑挪到 public 方法里 |
| 异常被吞 | 数据已写入，没回滚 | 异常没穿出边界 | 别 catch，或 catch 后 `throw`；必要时 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 受检异常 | 抛了 checked 异常却没回滚 | **默认只回滚 `RuntimeException` 与 `Error`** | `@Transactional(rollbackFor = Exception.class)` |

第四条值得单独记：Spring 的这个默认值是**故意的**，因为受检异常在 Java 里表示"可预期的业务分支"，框架不认为它该撤销一切。但实际项目里几乎总是希望你回滚——所以本项目约定：**重要的写操作一律写 `rollbackFor = Exception.class`**，不要依赖默认。

### 三种传播行为

| 传播 | 外层有事务时 | 外层没事务时 | 用途 |
| --- | --- | --- | --- |
| `REQUIRED`（默认） | 加入外层，成为同一个事务 | 新建一个 | 绝大多数业务方法 |
| `REQUIRES_NEW` | **挂起外层**，自己开一个新的 | 新建一个 | 记审计日志（外层回滚了日志也要留） |
| `NESTED` | 在外层里开一个保存点 | 新建一个 | 部分失败不影响整体（依赖数据库支持保存点） |

`REQUIRES_NEW` 是最容易踩的一个：它要**两个数据库连接**。连接池小于并发数时，一个请求会占两个连接——高并发下会出现"连接池耗尽"的等待，而这个等待发生在事务里面，表现为莫名其妙的全站变慢。

`NESTED` 与 `REQUIRES_NEW` 的区别用一句话说清：`NESTED` 是"同一个事务里的一个回滚点"，`REQUIRES_NEW` 是"另起一个事务，互不影响"。

### 只读事务

```java
@Transactional(readOnly = true)
public List<Book> list() { ... }
```

它的作用不是"性能更好"这么笼统：它告诉驱动与连接池"这次不会写"，一些驱动会据此跳过写缓冲；在部分数据库上还能让只读副本路由生效。本项目用它标记所有纯查询的 Service 方法，成本一行。

**注意**：`readOnly = true` 不阻止你写——它是个提示，不是权限。真写了，有些数据库照写不误，有些会报错，行为不统一。

### 事务里不要做的事

- **不要做网络调用**：一个 HTTP 请求在事务里，意味着数据库连接被占着等网络。超时设得不合理时，连接池会在几秒内被抽干。
- **不要发消息**：消息发出去了、事务回滚了——消息就成了幽灵。这是 outbox 表存在的原因（本项目有这条规则）。
- **不要在事务里开新线程**：新线程拿不到当前连接，它的写操作在事务外。

## 常见误区

### 误区：加了 `@Transactional` 就一定有事务

**你以为**：注解在就生效。
**其实**：三个前提缺一不可——方法是 public、调用经过了代理、类不是 final。任一条不满足，注解完全不生效，而且**没有任何报错**。
**怎么验证**：在事务方法里打一行 `TransactionSynchronizationManager.isActualTransactionActive()`，`false` 就是根本没开。

### 误区：事务范围越大越安全

**你以为**：一个请求从头到尾包在事务里，出问题全能回滚。
**其实**：范围越大，连接被占的时间越长，锁持有越久，回滚代价越高，中间夹着的网络调用还会被卷进事务。事务范围应该刚好覆盖"要么都成、要么都不成"的那几步。
**怎么验证**：看一个事务方法里有没有 HTTP 调用 / 消息发送 / 循环处理大批数据。有的话，多半该拆。

### 误区：`readOnly = true` 能防止误写

**你以为**：只读事务是权限。
**其实**：它是个提示。不同数据库与驱动对它的处理不一致，有的直接忽略。真正的防误写要靠代码审查与测试。
**怎么验证**：在一个 `readOnly = true` 的方法里插一条数据，看是否成功（MySQL 上通常成功）。

## 小结

`@Transactional` 是代理上的三段逻辑：拿连接、提交、回滚。四种失效是同一个原因的不同表现——边界没被经过，或异常没穿出去。受检异常默认不回滚，重要写操作一律写 `rollbackFor = Exception.class`。传播行为里 `REQUIRES_NEW` 要额外一个连接，高并发下会咬人。
