# 04 · 返回值与状态码

## 这一课你要会

- 200 / 201 / 204 / 400 / 404 / 409 / 500 各是什么语义；
- `@ResponseStatus`、`ResponseEntity`、直接返回对象三种写法的差别与选择；
- 为什么"全都返回 200，再在响应体里写 code"是个坏主意，以及什么时候它还能接受；
- 一个 Controller 方法返回 `String` 时，到底返回的是页面还是 JSON。

## 为什么

状态码是 HTTP 给**中间所有环节**看的：浏览器缓存、代理、负载均衡、重试库、监控告警。你把它一律写成 200，这些环节就全都瞎了——重试库不会重试本该重试的 503，监控看不出错误率，浏览器把错误响应当成正常内容缓存起来。

业务码是给你的前端看的，用来区分"用户不存在"和"余额不足"。两者解决的不是同一个问题，**可以并存，不能用前者替代后者**。

## 讲解

### 常用状态码的语义

| 码 | 含义 | 什么时候用 |
| --- | --- | --- |
| 200 | 成功且有内容 | 查询、更新成功 |
| 201 | 已创建 | `POST` 创建了新资源，通常配 `Location` 头 |
| 204 | 成功但无内容 | 删除成功、`PUT` 幂等覆盖后无返回 |
| 400 | 请求本身不合法 | 参数类型错、必填缺失、JSON 解析失败 |
| 401 | 没认证 | 没带令牌或令牌过期 |
| 403 | 认证了但没权限 | 普通用户访问管理端接口 |
| 404 | 资源不存在 | 路径没匹配，或 id 查不到 |
| 409 | 状态冲突 | 唯一键重复、乐观锁版本不匹配 |
| 500 | 服务端自己的错 | 未捕获异常 |

最容易混的两对：**401 与 403**（你谁？／你不能），**400 与 422**（格式错／格式对但语义错）。本项目统一用 400，不去区分 422——多一个码就多一处前端分支，收益很小。

### 三种返回方式

```java
// 一、直接返回对象：状态码永远是 200，用注解改
@GetMapping("/books/{id}")
public Book find(@PathVariable long id) {
    return service.find(id);                    // 200 + JSON
}

@PostMapping("/books")
@ResponseStatus(HttpStatus.CREATED)             // 固定成 201
public Book create(@RequestBody Book book) {
    return service.create(book);
}
```

```java
// 二、ResponseEntity：状态码可以按分支决定
@PostMapping("/books")
public ResponseEntity<Book> create(@RequestBody Book book) {
    if (book.title() == null || book.title().isBlank()) {
        return ResponseEntity.badRequest().build();
    }
    Book saved = service.create(book);
    return ResponseEntity.created(URI.create("/books/" + saved.id())).body(saved);
}
```

```java
// 三、业务失败抛异常，由全局处理器转成状态码（第 13 课细讲）
@PostMapping("/books")
public Book create(@RequestBody Book book) {
    return service.create(book);                // 失败时抛，统一在 @RestControllerAdvice 里映射
}
```

选择顺序：**只有一个状态码用第一种；按分支决定用第二种；失败路径多、要统一格式用第三种**。一个项目里三种混用是正常的，但同一类接口要统一——否则前端要为每个接口记一套规则。

### 手写一遍状态码映射

下面这段代码把"业务结果 → 状态码"这一步显式写出来。框架做的也是这件事，只是它读的是注解与异常：

<!-- run -->
```java
public class Main {

    static final class Api<T> {
        final int status;
        final String message;
        final T data;

        Api(int status, String message, T data) {
            this.status = status;
            this.message = message;
            this.data = data;
        }

        String render() {
            return status + " " + message + " | " + data;
        }
    }

    static <T> Api<T> ok(T data) {
        return new Api<>(200, "ok", data);
    }

    static <T> Api<T> created(T data) {
        return new Api<>(201, "created", data);
    }

    static Api<Void> noContent() {
        return new Api<>(204, "no content", null);
    }

    static <T> Api<T> badRequest(String message) {
        return new Api<>(400, message, null);
    }

    static <T> Api<T> conflict(String message) {
        return new Api<>(409, message, null);
    }

    public static void main(String[] args) {
        System.out.println(ok("book-7").render());
        System.out.println(created("book-7").render());
        System.out.println(noContent().render());
        System.out.println(badRequest("标题不能为空").render());
        System.out.println(conflict("同名书籍已存在").render());
    }
}
```
```text
200 ok | book-7
201 created | book-7
204 no content | null
400 标题不能为空 | null
409 同名书籍已存在 | null
```

一句要点：**状态码是"这次请求的结果类别"，不是"业务处理到第几步"**。创建成功是 201，不是"200 + body.step=2"。

### 反模式：全部 200 + body.code

```json
HTTP/1.1 200 OK

{"code": 40100, "message": "未登录"}
```

这种设计的代价：

- 浏览器与代理把"未登录"当正常内容缓存；
- 监控看不到错误率，因为它只统计 5xx；
- 重试库不会重试，因为它只对 5xx / 408 / 429 重试；
- 网关的限流与熔断拿不到信号。

它的好处是"前端只写一个分支"，但这个好处可以用一个统一的拦截器拿到，不需要牺牲协议的语义。

本项目有一条硬规则：**业务码可以与 HTTP 状态码并存，但 HTTP 状态码必须是真实的**。曾经真实踩过的坑是：业务码 40200 是对的，但 HTTP 返回了 500——因为异常映射漏了一个 `default` 分支，前端拿到了"服务器错误"而不是"余额不足"。这类问题只在真跑时看得见。

### 返回 `String` 时到底是页面还是 JSON

这是新手最容易困惑的一处：

```java
@Controller
public class PageController {
    @GetMapping("/hello")
    public String hello() {
        return "hello";          // 视图名 → 去找 hello.html 模板
    }
}

@RestController
public class ApiController {
    @GetMapping("/hello")
    public String hello() {
        return "hello";          // 响应体就是 hello 这两个字
    }
}
```

差别只在 `@Controller` 与 `@RestController`。`@RestController` = `@Controller` + `@ResponseBody`，后者表示"把返回值直接写进响应体，不要去找模板"。这就是为什么 API 类必须用 `@RestController`——用错会得到一个 500 和一条 `Circular view path` 报错。

## 常见误区

### 误区：删除成功就该返回 200 和一个 `{"success":true}`

**你以为**：总得给人一个"成功了"的凭据。
**其实**：204 的含义就是"成功了，没有内容"，`{"success":true}` 没有增加任何信息，只增加了字节。真要回执，返回 200 + 被删对象的信息（比如归档记录 id）更有用。
**怎么验证**：看一个 REST API 的删除接口，状态码与 body 是否在说同一件事——重复表达说明有一个是多余的。

### 误区：`@ResponseStatus` 能按条件改状态码

**你以为**：`@ResponseStatus(CREATED)` 加上去，方法里可以按情况返回别的码。
**其实**：它是**固定值**，方法不管返回什么都用这个码。要按分支决定，必须用 `ResponseEntity`，或者抛异常交给全局处理器。
**怎么验证**：在一个标了 `@ResponseStatus(HttpStatus.CREATED)` 的方法里 `return null` 和 `throw`，观察状态码分别是多少。

### 误区：错误信息越详细越好，方便排查

**你以为**：500 的响应体里把异常堆栈返回去最省事。
**其实**：堆栈里有类名、SQL、文件路径，等于把内部结构交出去。正确做法是**响应里给一个可搜索的短标识（如 traceId），完整堆栈只进日志**，两条用同一个 id 串起来。
**怎么验证**：搜一下线上响应体里有没有 `Exception`、`at com.` 这类字样。有就是泄漏。

## 小结

状态码描述"这次请求的结果类别"，业务码描述"业务上的哪种失败"，两者并存但不互相替代。三种返回方式按场景选：单码用 `@ResponseStatus`、按分支用 `ResponseEntity`、失败路径多用全局异常处理器。返回 `String` 是页面还是文本，只看类上是 `@Controller` 还是 `@RestController`。

到这里第一章结束：你已经有能力让一个接口被访问到、把逻辑放在正确的层、从正确的位置取参数、用正确的状态码回答。下一章开始拆容器——对象到底是谁 new 的。
