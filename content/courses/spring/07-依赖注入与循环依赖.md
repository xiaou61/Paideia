# 07 · 依赖注入与循环依赖

## 两个 `@Service` 互相要对方，启动直接失败

`A` 的构造器要 `B`，`B` 的构造器要 `A`：

```java
// A.java
@Service
public class A {
    private final B b;

    public A(B b) {
        this.b = b;
    }
}
```

```java
// B.java
@Service
public class B {
    private final A a;

    public B(A a) {
        this.a = a;
    }
}
```

Spring Boot 3.5.6 / Spring Framework 6.2.11，JDK 25，启动：

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

The dependencies of some of the beans in the application context form a cycle:

┌─────┐
|  a defined in file [.../A.class]
↑     ↓
|  b defined in file [.../B.class]
└─────┘

Action:

Relying upon circular references is discouraged and they are prohibited by default. Update your application to remove the dependency cycle between beans. As a last resort, it may be possible to break the cycle automatically by setting spring.main.allow-circular-references to true.
```

路径我用 `...` 省了，其余逐字来自本机输出。

我原来以为这只是构造器注入的毛病：换成字段注入，Spring 会先把两个对象 `new` 出来，再互相塞字段，环就解了。这个印象来自 Boot 2.6 之前。2.6 起 `spring.main.allow-circular-references` 默认是 `false`，同样的字段环**也起不来**，根因同样是 `BeanCurrentlyInCreationException`：

```text
The dependencies of some of the beans in the application context form a cycle:

┌─────┐
|  a (field private lab.fieldcycle.B lab.fieldcycle.A.b)
↑     ↓
|  b (field private lab.fieldcycle.A lab.fieldcycle.B.a)
└─────┘
```

所以先把结论说死：**字段注入不是循环依赖的解法，只是把「构造器阶段就失败」换成了「填充阶段才失败」；开关不开，两者都失败。**

## 三种注入，差别在「对象什么时候算完整」

```java
// 构造器注入
@Service
public class TransferService {
    private final AccountRepository repository;

    public TransferService(AccountRepository repository) {
        this.repository = repository;
    }
}
```

```java
// setter 注入
@Service
public class TransferService {
    private AccountRepository repository;

    @Autowired
    public void setRepository(AccountRepository repository) {
        this.repository = repository;
    }
}
```

```java
// 字段注入
@Service
public class TransferService {
    @Autowired
    private AccountRepository repository;
}
```

| | 依赖能否 `final` | 必需 Bean 缺失 | 可选依赖缺失（`required=false`） | 测试里能否直接 `new` |
| --- | --- | --- | --- | --- |
| 构造器 | 能 | 启动失败 | 用 `Optional<T>` / `ObjectProvider<T>` 表达 | 能，`new TransferService(repo)` |
| setter | 不能 | 启动失败 | 启动成功，字段保持 `null`，第一次调用 NPE | 能，但要记得调 setter |
| 字段 | 不能 | 启动失败 | 启动成功，字段保持 `null`，第一次调用 NPE | 难：字段私有且没有入口 |

三种「必需依赖缺失」的报错，本机分别是：

```text
Parameter 0 of constructor in lab.missingctor.A required a bean of type 'lab.missingctor.Repo' that could not be found.
Field repo in lab.missingfield.A required a bean of type 'lab.missingfield.Repo' that could not be found.
Parameter 0 of method setRepo in lab.missingsetter.A required a bean of type 'lab.missingsetter.Repo' that could not be found.
```

三行都是 `APPLICATION FAILED TO START`，不是第一次调用才炸。**能把必需依赖的失败拖到运行期的是 `required=false`；绕过容器自己 `new` 也一样。** `Optional<T>` / `ObjectProvider<T>` 则是把「可能没有」写进类型，空值处理在调用点。

所以「构造器注入在编译期暴露缺依赖」这句话要拆开看：只有你手写 `new TransferService()` 时，少传一个参数才编译不过；对象交给容器装配时，缺 Bean 仍然是启动期失败。构造器注入真正的收益是另外两条：

- 构造器返回时对象已经完整，没有「先存在、后补依赖」的窗口；
- 依赖可以是 `final`，类也可以直接 `new` 出来做单测，不必起容器。

单构造器还可以不写 `@Autowired`——Spring 4.3 以后只有一个构造器时会自动选它。把 `@Service` 移到 `@Configuration` 的 `@Bean` 方法上，这个类就是普通 Java 类。

## 循环依赖：不是「互相引用」，是「创建顺序成环」

运行期两个 Service 互相调方法，不一定是循环依赖。循环依赖说的是创建关系：

```text
A 的构造需要 B
B 的构造需要 A
```

构造器注入要求参数就位才能调用构造器。要造 A，先要有 B；要造 B，先要有 A；谁都没有第一个。Spring 容器本身允许字段/setter 注入先把对象 `new` 出来（此时字段是 `null`），再填依赖，所以存在一个两阶段的窗口；但 Boot 2.6 起默认关掉了提前暴露，这个窗口默认不会打开。`BeanCurrentlyInCreationException` 的意思是：这个 Bean 已经在 creation 集合里，第二次要它时它还没造完。它只说明容器发现你又绕回来了，不说明字段注入能处理。

## 打开开关之后：半成品真的会伤人

字段注入的 A、B，在 B 里加一个探针：

```java
@Service
public class A {
    @Autowired
    B b;
}
```

```java
@Service
@DependsOn("a")
public class B {
    @Autowired
    A a;

    @PostConstruct
    void probe() {
        System.out.println("B postConstruct: a=" + (a == null ? "null" : "set")
                + ", a.b=" + (a == null || a.b == null ? "null" : "set"));
    }
}
```

`@DependsOn("a")` 只是为了固定创建顺序，让 A 先被创建；没有它，谁先创建取决于扫描顺序，探针可能换到另一边。

启动时加上 `--spring.main.allow-circular-references=true`，本机输出：

```text
B postConstruct: a=set, a.b=null
after start: a.b==b true
after start: b.a==a true
after start: a.b.a==a true
```

第一行就是重点。B 的 `@PostConstruct` 里，`a` 不是 `null`——提前引用生效了；但 `a.b` 还是 `null`，因为 A 只完成了实例化，它的字段注入还没轮到 `b`。**半成品窗口不是「没人看见就没事」：初始化逻辑就在窗口里。** 在 `@PostConstruct` 里读协作者状态、注册回调、校验配置、预热缓存，看到的都可能是这个半成品。

开关只让容器不报错，不会让对象变完整。

## 四种处理方式，先看代价

| 处理方式 | 能不能启动 | 要求 | 代价 | 什么时候用 |
| --- | --- | --- | --- | --- |
| 拆环 | 能 | 找到职责边界：抽第三个 Bean、改成单向依赖、或改用事件 | 要动代码，可能改接口 | 默认首选 |
| 构造器参数加 `@Lazy` | 能，前提是代理能生成 | 注入点声明成非 final 类或接口；A 的构造期不调用代理 | CGLIB/JDK 代理；目标 Bean 仍可能启动时预实例化；把环藏起来 | 环确实无害、短期拆不掉 |
| 构造器参数改成 `ObjectProvider<T>` | 能 | 调用处显式 `getObject()` | 每个使用点都要处理 provider；不生成代理 | 需要延迟、可选或原型实例 |
| `spring.main.allow-circular-references=true` | 只有 setter/字段的单例环能；构造器环、prototype 环仍失败 | 全局配置，重启 | 半成品会被初始化逻辑看见；依赖三级缓存维持引用一致；掩盖设计问题 | 遗留系统过渡，不作为新代码方案 |

### 拆环：首选

常见两种拆法：一是把两边都需要的逻辑抽成 C，让 A→C、B→C；二是把其中一条调用改成事件或回调接口，让 B 不再在构造时持有 A。前者改类型关系，后者改时序关系，两者都比「让容器容忍环」更接近问题本身。

### `@Lazy`：给一个代理，不是把环拆掉

```java
@Service
public class A {
    private final B b;

    public A(@Lazy B b) {
        this.b = b;
    }
}
```

B 不是 final 类时，默认配置下也能启动。A 构造时拿到的是 B 的代理，第一次调用代理上的方法时才去解析真正的 B。本机把代理类打出来：

```text
a.b class: lab.lazyparam.B$$SpringCGLIB$$0
a.b.a==a: true
```

注入点声明成类时，代理由 CGLIB 生成；类不能是 `final`，否则启动阶段就失败：

```text
Caused by: org.springframework.aop.framework.AopConfigException: Could not generate CGLIB subclass of class lab.lazyfinal.FinalB: Common causes of this problem include using a final class or a non-visible class
Caused by: java.lang.IllegalArgumentException: Cannot subclass final class lab.lazyfinal.FinalB
```

这里有两个容易说错的点。

第一，`@Lazy` 只把 **A 构造时对 B 的解析** 推后，不等于把 B 的创建推后。B 如果是普通的非懒加载单例，容器启动末尾仍会预实例化它。我在 B 的构造器里 `throw new IllegalStateException("boom")`，启动照样失败：`Failed to instantiate [lab.lazyfail.B]: Constructor threw exception`。如果 B 本身也是懒加载（类上再标 `@Lazy`，或全局懒加载），才会出现「启动成功，第一次调用才炸」：本机先打印 `started`，调用 `a.b().hello()` 时才抛 `BeanCreationException`，根因是 `IllegalStateException: boom`。

第二，它没有拆环，只是把环的一侧换成了代理。代理、延迟解析、以及「设计问题被藏起来」都是代价；`final` 类只是其中最硬的一条限制。

### `ObjectProvider`：显式地晚点拿

```java
@Service
public class A {
    private final ObjectProvider<B> provider;

    public A(ObjectProvider<B> provider) {
        this.provider = provider;
    }

    void use() {
        B b = provider.getObject();
        b.hello();
    }
}
```

本机拿到的 provider 和对象：

```text
provider class: org.springframework.beans.factory.support.DefaultListableBeanFactory$DependencyObjectProvider
getObject class: lab.providerparam.B
provider.a()==a: true
```

它不生成代理，`getObject()` 是显式的一次解析。单例每次拿到同一个，原型每次拿新的。代价是每个使用点都要自己处理 provider；好处是「这里会晚点拿」在代码里看得见，不靠注解魔法。

和 `@Lazy` 一样，它解决的是 A 构造时不等 B，不是把 B 的创建挪到第一次调用。B 是普通单例时，启动时仍会被预实例化。两者都不如拆环：它们只改变解析时机，没有改变 A 和 B 的职责关系。

### 开开关：只对 setter/字段的单例环有效

```yaml
spring:
  main:
    allow-circular-references: true
```

构造器环即使开了开关也起不来。本机的 `Action` 换成了另一句：

```text
Despite circular references being allowed, the dependency cycle between beans could not be broken. Update your application to remove the dependency cycle.
```

原因是提前暴露发生在「实例化之后、填充字段之前」；构造器注入在实例化之前就要参数，没有对象可暴露。

prototype 环也不行。两个 prototype Bean 用字段互相依赖，`getBean` 时的根因仍然是 `BeanCurrentlyInCreationException`，消息里是：

```text
Requested bean is currently in creation: Is there an unresolvable circular reference or an asynchronous initialization dependency?
```

提前暴露只对单例生效：源码里的条件是 `mbd.isSingleton() && this.allowCircularReferences && isSingletonCurrentlyInCreation(beanName)`。prototype 不进单例缓存，也就没有「先给一个早期引用」这条路。

## 三级缓存到底解决什么

先纠正一个说法：**三级缓存不是字段注入的默认兜底。** Boot 2.6 起默认禁止循环引用，这个 Bean 的早期引用工厂根本不会登记，三级缓存没有机会参与；只有你显式开了开关，才轮到它。

Framework 自己的 `AbstractAutowireCapableBeanFactory.allowCircularReferences` 字段默认是 `true`；Boot 2.6 起在启动时把它设成 `false`。所以不是 Spring 容器不会解环，是 Boot 默认不让它解。

三个 Map 在 Spring Framework 6.2.11 和 7.0.10 里都还在。6.2.11 用反射看，7.0.10 用 `javap` 看，字段名和类型一致：

```text
private final java.util.Map<java.lang.String, java.lang.Object> singletonObjects;
private final java.util.Map<java.lang.String, org.springframework.beans.factory.ObjectFactory<?>> singletonFactories;
private final java.util.Map<java.lang.String, java.lang.Object> earlySingletonObjects;
```

它们的分工：

- `singletonObjects`：完整的单例，最终成品；
- `earlySingletonObjects`：提前暴露出去的早期引用，避免同一个 Bean 被提前解析多次；
- `singletonFactories`：一个能生成早期引用的 `ObjectFactory`。有 AOP 时，代理可能在这里提前生成。

它解决的是两个问题：一是「别人现在就要 A，但 A 还没填充完」，先给一个早期引用；二是「提前给出去的引用，必须和最终放进 `singletonObjects` 的是同一个」，否则注入的是代理、调用的是另一个对象。它不解决构造器环，也不解决 prototype 环——那两个场景连「实例化之后」都到不了，或者根本不进单例缓存。

## 跑一遍：把开关的行为压成一个容器

下面不是 Spring，是一个玩具容器。它只复刻本文用到的两条规则：构造器注入永远不提前暴露；字段注入只有开关打开才提前暴露。

<!-- run -->
```java
import java.lang.reflect.Constructor;
import java.lang.reflect.Field;
import java.util.HashMap;
import java.util.LinkedHashSet;
import java.util.Map;
import java.util.Set;

public class Main {

    interface Init {
        void postConstruct();
    }

    static final class CtorA {
        final CtorB b;

        CtorA(CtorB b) {
            this.b = b;
        }
    }

    static final class CtorB {
        final CtorA a;

        CtorB(CtorA a) {
            this.a = a;
        }
    }

    static class FieldA implements Init {
        FieldB b;

        public void postConstruct() {
            System.out.println("A.postConstruct: b=" + (b == null ? "null" : "set"));
        }
    }

    static class FieldB implements Init {
        FieldA a;

        public void postConstruct() {
            System.out.println("B.postConstruct: a=" + (a == null ? "null" : "set")
                    + ", a.b=" + (a == null || a.b == null ? "null" : "set"));
        }
    }

    static final class Container {
        private final boolean allowCircular;
        private final Map<Class<?>, Object> singletons = new HashMap<>();
        private final Set<Class<?>> creating = new LinkedHashSet<>();

        Container(boolean allowCircular) {
            this.allowCircular = allowCircular;
        }

        Object get(Class<?> type) {
            Object existing = singletons.get(type);
            if (existing != null) {
                return existing;
            }
            if (!creating.add(type)) {
                throw new IllegalStateException("循环依赖: " + trail() + " -> " + type.getSimpleName());
            }
            try {
                Constructor<?> constructor = type.getDeclaredConstructors()[0];
                constructor.setAccessible(true);
                if (constructor.getParameterCount() > 0) {
                    return construct(type, constructor);
                }
                Object made = constructor.newInstance();
                if (allowCircular) {
                    singletons.put(type, made);
                }
                for (Field field : type.getDeclaredFields()) {
                    field.setAccessible(true);
                    field.set(made, get(field.getType()));
                }
                if (!allowCircular) {
                    singletons.put(type, made);
                }
                if (made instanceof Init init) {
                    init.postConstruct();
                }
                return made;
            } catch (ReflectiveOperationException error) {
                throw new IllegalStateException(error);
            } finally {
                creating.remove(type);
            }
        }

        private Object construct(Class<?> type, Constructor<?> constructor) throws ReflectiveOperationException {
            Class<?>[] parameters = constructor.getParameterTypes();
            Object[] arguments = new Object[parameters.length];
            for (int i = 0; i < parameters.length; i++) {
                arguments[i] = get(parameters[i]);
            }
            Object made = constructor.newInstance(arguments);
            singletons.put(type, made);
            if (made instanceof Init init) {
                init.postConstruct();
            }
            return made;
        }

        private String trail() {
            StringBuilder builder = new StringBuilder();
            for (Class<?> type : creating) {
                if (builder.length() > 0) {
                    builder.append(" -> ");
                }
                builder.append(type.getSimpleName());
            }
            return builder.toString();
        }

        FieldA fieldA() {
            return (FieldA) get(FieldA.class);
        }
    }

    public static void main(String[] args) {
        try {
            new Container(false).get(CtorA.class);
            System.out.println("构造器环 + 默认: 启动成功");
        } catch (IllegalStateException error) {
            System.out.println("构造器环 + 默认: " + error.getMessage());
        }

        try {
            new Container(true).get(CtorA.class);
            System.out.println("构造器环 + 开关: 启动成功");
        } catch (IllegalStateException error) {
            System.out.println("构造器环 + 开关: " + error.getMessage());
        }

        try {
            new Container(false).fieldA();
            System.out.println("字段环 + 默认: 启动成功");
        } catch (IllegalStateException error) {
            System.out.println("字段环 + 默认: " + error.getMessage());
        }

        Container open = new Container(true);
        FieldA a = open.fieldA();
        System.out.println("字段环 + 开关: 启动成功");
        System.out.println("启动后 a.b.a == a: " + (a.b.a == a));
    }
}
```
```text
构造器环 + 默认: 循环依赖: CtorA -> CtorB -> CtorA
构造器环 + 开关: 循环依赖: CtorA -> CtorB -> CtorA
字段环 + 默认: 循环依赖: FieldA -> FieldB -> FieldA
B.postConstruct: a=set, a.b=null
A.postConstruct: b=set
字段环 + 开关: 启动成功
启动后 a.b.a == a: true
```

前两行说明构造器环不靠开关解决；第三行说明字段环默认也不行；最后四行说明开了开关之后能启动，但 B 的初始化逻辑确实看到了 A 的 `null` 字段。
