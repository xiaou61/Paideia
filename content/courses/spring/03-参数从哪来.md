# 03 · 参数从哪来

## 一个 415，一个 200

同一个请求，参数换成另一个注解就好了：

```text
curl -X POST localhost:8080/form -d 'name=小林'
  → 415 Unsupported Media Type   （接口写的是 @RequestBody User user）

curl -X POST localhost:8080/form -d 'name=小林'
  → 200 FORM[小林]                （接口改成 @RequestParam String name）
```

`curl -d` 发出去的是 `Content-Type: application/x-www-form-urlencoded`，`name=小林` 在**表单请求体**里。`@RequestBody` 想按 JSON 解析它，解析不了，415；`@RequestParam` 读的是「请求参数」，表单体里的键值对也算请求参数，于是拿到了。

这件事说明一件事：注解的区别不在名字，也不完全在「请求的哪一段」——`@RequestParam` 能读两段。分不清就会写出最难查的一类 bug：参数是 `null`，或者干脆 415，而代码看着没错。

## 四类参数，实际是三段半

```text
POST /users/42/books?page=2&size=10 HTTP/1.1     ← 路径(/users/42/books) 查询串(?page=2&size=10)
Host: example.com                                 ← 请求头
Content-Type: application/json

{"title":"SpEL"}                                  ← 请求体
```

| 注解 | 从哪取 | 典型用法 |
| --- | --- | --- |
| `@PathVariable` | 路径里 `{}` 占的位置 | `/users/{id}` → `GET /users/42` |
| `@RequestParam` | **请求参数**：查询串、`application/x-www-form-urlencoded` 表单体、multipart 字段 | `?page=2&size=10`，或 `<form>` 提交 |
| `@RequestBody` | 整个请求体，交给 `HttpMessageConverter` 读 | JSON / XML |
| `@RequestHeader` | 请求头 | `Authorization`、`X-Trace-Id` |

`@RequestParam` 那一行是这一课最值得记的一条：它读的不是「问号后面」，是 Servlet 概念里的 request parameter。表单 POST 用 `@RequestParam` 是完全正常的写法，不用改成 `@RequestBody`。

一个请求里能同时用三种：

```java
@GetMapping("/users/{id}/books")
public List<Book> books(
        @PathVariable("id") long userId,
        @RequestParam(name = "page", defaultValue = "1") int page,
        @RequestParam(name = "size", defaultValue = "20") int size,
        @RequestHeader(name = "X-Trace-Id", required = false) String traceId) {
    return service.books(userId, page, size);
}
```

## 参数名不写会怎样

`@RequestParam` 不写名字时，Spring 用**编译后的参数名**。`javac` 默认会把参数名擦成 `arg0`、`arg1`——所以必须加 `-parameters`（Spring Boot 的父工程已经替你加了）。自己手写 Maven 项目时漏了这个配置，表现是：

```text
java.lang.IllegalArgumentException: Name for argument of type [java.lang.String]
not specified, and parameter name information not available via reflection.
```

看到它就去查编译器的 `-parameters`，别怀疑注解写错了。反过来，注解里写死名字（`@RequestParam("page")`）就不依赖这个配置——这也是我在项目里一律写死名字的原因。

## 必填、可选、默认值

```java
@RequestParam("page") int page                                // 必填，缺了 400
@RequestParam(name = "page", required = false) Integer page    // 可选，缺了是 null
@RequestParam(name = "page", defaultValue = "1") int page      // 缺了或空着，都是 1
```

三个写法在「缺参数」时的行为是 400、`null`、默认值。但有两个细节，原稿里我写错了，这里更正：

**一，`defaultValue` 在参数缺失或为空时都生效。** 实测 `GET /default-int-empty?page=` 返回 `200 page=1`，不是把空字符串硬转成 `int` 然后 400。空串走默认值这件事，做分页、做筛选的时候很实用——前端把没填的输入框拼进 URL，就会得到 `?page=`。

**二，`required = false` + 基本类型不会在启动时报错。** 实测应用正常启动，出问题在请求阶段：

```text
GET /optional-int            → 500   （null 拆箱成 int，炸在方法调用里）
GET /optional-int?page=      → 400
GET /optional-int?page=abc   → 400
```

`required = false` 只表示「可以不传」，它不会给基本类型补一个 0。要么给 `defaultValue`，要么把类型改成 `Integer`。这类错误不是启动期能抓到的，只有真请求一次才暴露——所以别依赖「启动成功」当作参数定义正确的证据。

## 手写一遍取参数

三件事：把 `/users/{id}` 与真实路径对上、把 `?a=1&b=2` 切开放进 Map、把取到的字符串转成数字并处理失败。

<!-- run -->
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class Main {

    // 1. 路径变量：把 /users/{id}/books/{bookId} 与 /users/42/books/7 对上
    static Map<String, String> pathVars(String pattern, String path) {
        String[] p = pattern.split("/");
        String[] q = path.split("/");
        if (p.length != q.length) {
            return null;
        }
        Map<String, String> vars = new LinkedHashMap<>();
        for (int i = 0; i < p.length; i++) {
            if (p[i].startsWith("{") && p[i].endsWith("}")) {
                vars.put(p[i].substring(1, p[i].length() - 1), q[i]);
            } else if (!p[i].equals(q[i])) {
                return null;
            }
        }
        return vars;
    }

    // 2. 查询串：page=2&size=10 → {page=2, size=10}
    static Map<String, String> query(String raw) {
        Map<String, String> map = new LinkedHashMap<>();
        if (raw == null || raw.isEmpty()) {
            return map;
        }
        for (String pair : raw.split("&")) {
            int at = pair.indexOf('=');
            map.put(pair.substring(0, at), pair.substring(at + 1));
        }
        return map;
    }

    // 3. 类型转换：取不到或转不动，是两种不同的错
    static int toInt(String value) {
        try {
            return Integer.parseInt(value);
        } catch (NumberFormatException error) {
            throw new IllegalArgumentException("不是整数: " + value);
        }
    }

    public static void main(String[] args) {
        System.out.println(pathVars("/users/{id}/books/{bookId}", "/users/42/books/7"));
        System.out.println(pathVars("/users/{id}", "/users/42/extra"));
        System.out.println(query("page=2&size=10"));
        System.out.println(query(""));
        try {
            toInt("abc");
        } catch (IllegalArgumentException error) {
            System.out.println("400 " + error.getMessage());
        }
    }
}
```
```text
{id=42, bookId=7}
null
{page=2, size=10}
{}
400 不是整数: abc
```

对着输出说三件事：

- **段数不一样直接 `null`** —— 对应「路径压根匹配不上」，也就是 404。注意这在 Spring 里根本不会执行到你的方法：路由层就 404 了。
- **空查询串返回空 Map，不是 `null`** —— 对应 `@RequestParam(required = false)` 拿到 `null` 值。这两者手感完全不同：Map 空着还能 `containsKey`，`null` 只能判空。
- **转换失败抛异常** —— 对应 Spring 抛 `MethodArgumentTypeMismatchException`，默认翻成 **400**。

这个 `query()` 只是个玩具，别把它当成「注解底下就是这么干的」。它只认 `a=b`：客户端发一个合法的 `?flag`（没有等号），`indexOf('=')` 返回 `-1`，`substring(0, -1)` 直接抛 `StringIndexOutOfBoundsException`。它也没做 URL 解码（`?q=%E4%B8%AD` 会原样给你 `%E4%B8%AD`）、没处理重复键（`?a=1&a=2` 后一个覆盖前一个）。真实的 `@RequestParam` 这三件都做了——差别就在这儿。

## GET 到底能不能带请求体

「GET 永远用 `@PathVariable` 和 `@RequestParam`」这个说法太绝对。Spring 并不拦你：

```text
GET /get-body
Content-Type: application/json
{"a":1}
→ 200 BODY[{a=1}]
```

`@RequestBody` 在 GET 上也能读到东西。但**别这么写**：HTTP 规范对 GET 的请求体没有定义，代理、缓存、网关可以合法地把它丢掉，现象是本地好、上线空。真要传复杂查询条件，用 `POST /search`，或者把条件压进查询串。

还有一点更麻烦：缺参数时的错误码不是统一的 `null`。缺必填的 `@RequestParam` 是 400；路径不匹配是 404；JSON 解析失败是 400；`Content-Type` 不对是 415；只有可选参数、包装类型、请求体里缺失的字段，才常常表现为 `null`。**先看状态码，能省掉一半排查。**

## 415 是怎么来的

`@RequestBody` 有一个前提：请求要带能被识别的 `Content-Type`。少了或不对：

```text
org.springframework.web.HttpMediaTypeNotSupportedException: Content-Type 'application/x-www-form-urlencoded;charset=UTF-8' is not supported
```

这不是参数没传对，是它不知道该用哪个转换器把字节变成对象。用 `curl` 调试时最容易踩：

```bash
curl -X POST http://localhost:8080/api/users \
     -H "Content-Type: application/json" \
     -d '{"name":"小林"}'
```

`-d` 默认带的是 `application/x-www-form-urlencoded`，必须显式 `-H` 覆盖。反过来说，如果你的接口本来就想收表单，用 `@RequestParam` 就行，不用跟 415 较劲。

## 还差的

- **空值行为我只在 Boot 4.1.1 上验过。** Boot 3.x 的几个小版本上 `?page=` 是否同样走 `defaultValue`，我没有逐版复测。
- **multipart 只用 `@RequestParam` 取过普通字段，没试文件。** 文件上传那一套（`MultipartFile`、大小限制、临时目录）这课没覆盖。
- **查询串的编码细节没讲透。** 中文、`+` 与空格的差异、重复键的取值规则，我只知道现象，没系统验过。
- **`MethodArgumentTypeMismatchException` 的自定义错误响应没做。** 默认 400 的响应体对前端不友好，改法在错误处理那一课。
