# 15 · 一次请求的完整旅程

## 这一课你要会

- 说清一次请求从进入容器到写出响应，依次经过哪几层；
- 分清 Filter、Interceptor、AOP、`@ControllerAdvice` 四者的位置与能拿到什么；
- 判断一段横切逻辑该挂在哪一层；
- 知道"404 时为什么全局异常处理器没被调用"。

## 为什么

你已经会写接口、会加事务、会统一异常。剩下的问题是：**这段逻辑该挂在哪**。

挂错位置的代价常常不是报错，而是"某些路径漏了"：权限切在 Controller 上，定时任务就绕过了；日志写在 Interceptor 里，404 就记不上；在 `@ControllerAdvice` 里兜底一个错误页，路径根本不存在时它根本不执行。

把这条链看清楚，这些坑全是显然的。

## 讲解

### 完整顺序

```text
socket
  → Filter 链（Servlet 规范层）
      → DispatcherServlet
          → HandlerMapping：按路径找处理方法
          → HandlerInterceptor.preHandle
          → ArgumentResolver：把请求绑定到方法参数
          → 业务方法执行（这里可能进入 @Transactional 代理）
          → returnValueHandler + HttpMessageConverter
          → HandlerInterceptor.postHandle
          → HandlerInterceptor.afterCompletion（无论成败）
  → Filter 链回程
  → socket
```

下面这段代码把这条链打印出来。手写版没有真正的 Servlet，但顺序与职责是一致的：

<!-- run -->
```java
public class Main {

    interface Filter {
        void doFilter(Runnable next);
    }

    static void log(String line) {
        System.out.println(line);
    }

    public static void main(String[] args) {
        Filter auth = next -> {
            log("1 filter.auth：鉴权，最外层");
            next.run();
        };
        Filter trace = next -> {
            log("2 filter.trace：分配 traceId");
            next.run();
        };
        Filter encoding = next -> {
            log("3 filter.encoding：设置字符集");
            next.run();
        };

        Runnable dispatcher = () -> {
            log("4 DispatcherServlet：按路径查 HandlerMapping");
            log("5 interceptor.preHandle：登录态检查");
            log("6 argumentResolver：把请求绑定到方法参数");
            log("7 业务方法执行");
            log("8 returnValueHandler：判断返回值该当视图名还是对象");
            log("9 messageConverter：对象 → JSON");
            log("10 interceptor.afterCompletion：无论成败都执行");
        };

        auth.doFilter(() -> trace.doFilter(() -> encoding.doFilter(dispatcher)));
    }
}
```
```text
1 filter.auth：鉴权，最外层
2 filter.trace：分配 traceId
3 filter.encoding：设置字符集
4 DispatcherServlet：按路径查 HandlerMapping
5 interceptor.preHandle：登录态检查
6 argumentResolver：把请求绑定到方法参数
7 业务方法执行
8 returnValueHandler：判断返回值该当视图名还是对象
9 messageConverter：对象 → JSON
10 interceptor.afterCompletion：无论成败都执行
```

### 四层横切的对照

| | Filter | Interceptor | `@ControllerAdvice` | AOP |
| --- | --- | --- | --- | --- |
| 在哪 | DispatcherServlet **之前** | DispatcherServlet **之内** | 异常抛出之后 | 方法调用外层 |
| 拿得到控制器信息吗 | 不能（还不知道要调谁） | 能（知道哪个 handler） | 能（能读异常） | 能（知道方法签名） |
| 能改请求/响应吗 | 能（原始 request/response） | 有限 | 不能（只能改响应体） | 不能 |
| 路径不存在时会执行吗 | **会** | 不会 | 不会（没有异常可拦） | 不会 |
| 典型用途 | CORS、traceId、鉴权、压缩、错误页兜底 | 登录态、权限注解、耗时统计 | 异常转状态码 | 事务、缓存、重试 |

这张表里最值得记的是第 4 行：**只有 Filter 会在"路径根本不存在"时执行**。所以：

- 想给 404 也返回统一的 JSON 错误体，只能靠 Filter（或容器的错误页配置）；
- 想在 404 时记一条访问日志，也只能靠 Filter。

### 为什么全局异常处理器管不到 404

404 的产生过程是：`DispatcherServlet` 找不到 handler → 直接写 404，**没有任何异常抛出**（准确说它会抛 `NoHandlerFoundException` 只有当 `throwExceptionIfNoHandlerFound=true` 时；默认是直接走错误页）。既然没有异常，`@ExceptionHandler` 自然不会被调用。

同理，请求体在进入方法之前就解析失败（`HttpMessageNotReadableException`）时，**处理方法根本没被执行**，但异常确实被抛出了，所以 `@ControllerAdvice` 能兜住——两者要分清。

### 各类逻辑该挂哪

| 逻辑 | 挂哪 | 理由 |
| --- | --- | --- |
| CORS、压缩、traceId | Filter | 要在最外层，且 404 也要有 |
| 登录态解析（JWT → 用户） | Filter | 后面的所有环节都要用 |
| 接口级权限（`@PreAuthorize`） | Interceptor 或 AOP | 需要知道"要调哪个方法" |
| 事务 | AOP（Service 层） | 范围要覆盖业务整体 |
| 异常转状态码 | `@ControllerAdvice` | 一处收口 |
| 接口耗时统计 | Interceptor 或 AOP | 两者都能，AOP 粒度更细 |
| 慢 SQL 统计 | AOP 或数据源代理 | 要包住 SQL 执行 |

本项目里登录态解析就在 Filter：JWT 在请求头里，解析出来的身份要给后面的每一层用，而且**未登录的请求连 Controller 都不该进**。

### 一个请求里的两个"事务边界"

注意上面那张链里第 7 步的括号说明：**业务方法执行时可能进入事务代理**。也就是说，一次请求里其实有两条独立的"包裹链"：

```text
Filter 链（HTTP 层）          ← 关心 request/response
  AOP 代理链（对象层）        ← 关心方法调用、事务、缓存
```

它们互不知道对方存在。这解释了为什么"事务回滚了但响应还是 200"——事务在对象层回滚，HTTP 层完全不知道；响应状态码由你自己决定。

## 常见误区

### 误区：Filter 和 Interceptor 差不多，随便用哪个

**你以为**：都是"拦截请求"，功能重叠。
**其实**：它们的能力边界由位置决定。Filter 拿不到"要调哪个方法"，做不了方法级权限；Interceptor 拿不到"原始 request 的全部能力"，且在 404 时不执行。选错层的表现是"某些路径漏了"。
**怎么验证**：用一种拦截手段打一条日志，然后请求一个不存在的路径，看日志出不出来。

### 误区：`@ControllerAdvice` 能兜住所有异常

**你以为**：它是全局的，所有异常都归它。
**其实**：它只兜"已经进到 DispatcherServlet 处理流程里、并且被抛出来"的异常。Filter 里抛的、`Filter` 在 DispatcherServlet 之前抛的、容器启动时的异常，它都管不到。
**怎么验证**：在一个 Filter 里 `throw new RuntimeException()`，看 `@ExceptionHandler` 有没有反应。

### 误区：一次请求只有一个"入口"，所以横切挂哪都一样

**你以为**：所有逻辑都从 Controller 进来。
**其实**：定时任务、消息消费者、`CommandLineRunner`、管理端工具都不经过 HTTP。所以业务层的横切（事务、权限、审计）必须挂在 Service，而不是 Controller 或 Filter。
**怎么验证**：`rg "@Scheduled"` 找到所有定时任务，看它们的业务方法有没有被 HTTP 层的横切覆盖。

## 小结

一次请求依次经过 Filter 链、DispatcherServlet、HandlerMapping、Interceptor、参数绑定、业务方法、返回值与消息转换。四层横切的能力由位置决定：Filter 最外层、404 也执行；Interceptor 知道 handler；Advice 只兜抛出来的异常；AOP 包在方法外面。事务在对象层，HTTP 层不知道它回滚了。
