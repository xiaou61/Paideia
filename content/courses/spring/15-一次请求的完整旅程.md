# 15 · 一次请求的完整旅程

## `/nope` 的 404，先撞上了 `@ControllerAdvice`

下面是我在临时工程里请求 `GET /nope` 的日志（Temurin 25.0.4、Spring Boot 4.1.1、Spring Framework 7.0.9、Tomcat 11.0.24；时间、PID、线程名和 handler 属性做了省略；日志里的 18080 是临时工程端口，下面 curl 统一写成 8080，换成你的端口即可）。

```text
INFO  ... demo.ProbeFilter : FILTER default enter uri=/nope dispatcher=REQUEST asyncStarted=false
INFO  ... demo.Interceptor.A : A preHandle uri=/nope handler=ResourceHttpRequestHandler dispatcher=REQUEST asyncStarted=false
INFO  ... demo.Interceptor.B : B preHandle uri=/nope handler=ResourceHttpRequestHandler dispatcher=REQUEST asyncStarted=false
WARN  ... demo.ProbeAdvice : NoResourceFoundException: No static resource nope for request '/nope'.
INFO  ... demo.Interceptor.B : B afterCompletion uri=/nope status=404 dispatcher=REQUEST asyncStarted=false ex=null
INFO  ... demo.Interceptor.A : A afterCompletion uri=/nope status=404 dispatcher=REQUEST asyncStarted=false ex=null
INFO  ... demo.ProbeFilter : FILTER default exit uri=/nope dispatcher=REQUEST asyncStarted=false status=404
```

我之前也以为「404 没有 handler，所以不会进 `@ControllerAdvice`，拦截器也不会跑」。这组日志正好相反：`preHandle` 跑了，advice 接住了，`afterCompletion` 还跑了两个。`postHandle` 没出现，因为资源处理器是在 `preHandle` 之后抛的异常，`postHandle` 被跳过。

`curl -i` 看到的响应（省略了 `Date`、`Transfer-Encoding` 这类每次都变的头）：

```text
$ curl -i localhost:8080/nope
HTTP/1.1 404
X-Advice: no-resource
Content-Type: application/json

{"where":"advice","detail":"No static resource nope for request '/nope'."}
```

Boot 3.2 起，默认的 `/**` 静态资源映射会把没有匹配到 Controller 的路径先交给 `ResourceHttpRequestHandler`。它找不到 `static/nope`，抛 `NoResourceFoundException`。这是一个正常的异常，所以会走 DispatcherServlet 的异常解析链，`@ExceptionHandler` 能接住。**404 不是「没有 handler」，而是「handler 没找到资源」。**

只有一种情况才真的没有这个异常：连 `/**` 的资源映射都没有，DispatcherServlet 找不到任何 handler mapping。用 `--spring.web.resources.add-mappings=false` 启动同一个工程，再请求 `/nope`：

```text
WARN  ... o.s.web.servlet.PageNotFound : No mapping for GET /nope
WARN  ... o.s.web.servlet.PageNotFound : No endpoint GET /nope.
```

这次原请求没有进拦截器，也没有 `NoResourceFoundException`；容器通过 `sendError(404)` 转到 `/error`，由 `BasicErrorController` 写默认 JSON：

```text
$ curl -i localhost:8080/nope
HTTP/1.1 404
Content-Type: application/json

{"timestamp":"2026-11-19T05:32:33.797Z","status":404,"error":"Not Found","path":"/nope"}
```

日志里 `/error` 那次 dispatch 仍可能跑拦截器，但那是另一次 dispatch，不是原请求。这个区别在后面讲 `/error` 时还会用到。

## 三层各自能看见什么

把这次请求按位置拆开：

| 位置 | 能看见 | 看不见 |
| --- | --- | --- |
| Filter | 原始 request、response、路径、头、参数；能包 Wrapper；能 catch 整条 `chain.doFilter` 抛出的异常 | 不知道最终会调哪个 Controller 方法；被 advice 消化的异常也不会再抛到它这里 |
| DispatcherServlet 内部 | HandlerMapping 找到的 handler、HandlerAdapter、拦截器、advice、MVC 异常 | Filter 在进入 DispatcherServlet 之前抛出的异常；容器自己的错误页 |
| Controller 方法体 | 方法参数、返回值、业务异常 | 404 的资源查找、Filter 短路、`/error` 的兜底 |

这里说的 Controller 层，是 handler 方法体本身，不是整个 DispatcherServlet。404 时 Controller 方法根本没有被调用，所以它什么都看不见。

## 链条里还有 HandlerAdapter

把 `/hello`、`/nope` 和 `/unhandled` 的日志对起来，正常链路是这样：

```text
Filter 链
  → DispatcherServlet
      → HandlerMapping：找到 handler 和它的拦截器链
      → HandlerAdapter：选中能调用这个 handler 的适配器
      → HandlerInterceptor.preHandle
      → HandlerAdapter 内部：参数解析器 → 方法调用 → 返回值处理器/HttpMessageConverter
      → HandlerInterceptor.postHandle
      → HandlerInterceptor.afterCompletion
  → Filter 链回程
```

`HandlerMapping` 只负责「找到 handler」，真正调用方法、解析参数、处理返回值的是 `HandlerAdapter`。处理 `@Controller` 方法的是 `RequestMappingHandlerAdapter`；处理 `ResourceHttpRequestHandler` 的是另一个适配器。`preHandle` 在参数解析之前，不是在参数解析之后；参数解析是 HandlerAdapter 进入方法调用时才做的。

这个顺序不是从图上猜的。下面是我在 `/unhandled` 故意抛 `IllegalArgumentException` 后，堆栈里露出来的四行：

```text
at ...RequestMappingHandlerAdapter.invokeHandlerMethod(RequestMappingHandlerAdapter.java:934)
at ...RequestMappingHandlerAdapter.handleInternal(RequestMappingHandlerAdapter.java:853)
at ...AbstractHandlerMethodAdapter.handle(AbstractHandlerMethodAdapter.java:86)
at ...DispatcherServlet.doDispatch(DispatcherServlet.java:963)
```

如果没有 HandlerAdapter，这四行不会出现在异常栈里。想自己验证，就在一个没有 advice 映射的接口里抛异常，然后看 `ERROR ... Servlet.service()` 后面的堆栈；不要只看「handler 名字对了」就以为链路完整。

## 四层的位置

- **Filter**：在 DispatcherServlet 外面，拿到的是原始 request/response。它不知道最终要调哪个方法，但能看到所有路径，包括 404 和 Filter 自己抛出的异常。
- **Interceptor**：在 DispatcherServlet 里面，HandlerMapping 之后、HandlerAdapter 调用前后。它知道 handler，能做方法级判断；但它不是最外层。
- **`@ControllerAdvice`**：在 DispatcherServlet 的异常解析阶段。它只处理已经进入 DispatcherServlet、并被抛出来的异常；它不是正常请求的必经层。
- **AOP**：在对象层，包住方法调用。它和 HTTP 层是两条链；事务、缓存、重试挂在这里，不挂在 Filter 或 Interceptor 里。

动作能力拆成一张表：

| 层 | 读请求参数 | 改响应头 | 改状态码 | 替换/包装 request、response | 替换响应 body | 中止请求 |
| --- | --- | --- | --- | --- | --- | --- |
| Filter | 能 | 能，提交前 | 能，提交前 | 能，`HttpServletRequestWrapper` / `HttpServletResponseWrapper` | 能，包 response 后改写已写内容 | 能，不调 `chain.doFilter` |
| Interceptor | 能，同一个 request | 能，提交前；`preHandle` 最稳 | 能，提交前；`preHandle` 最稳 | 不能，拿到的是同一对象 | 不能直接替换返回值；可以自己写 response 后中止 | 能，`preHandle` 返回 false |
| `@ControllerAdvice` | 能，从 request 或异常里读 | 能，`ResponseEntity` 或 `HttpServletResponse` | 能，`ResponseEntity.status` | 不能，拿到的是同一对象 | 能，返回新的 body | 不能中止，只能把异常变成响应 |
| AOP | 能读方法参数 | 不直接 | 不直接 | 不能 | 能改方法返回值，不等于改 HTTP body | 能抛异常或不 `proceed`，仍走异常链 |

能看见什么、典型用途：

| 层 | 能看到异常吗 | 能拿到 handler 方法吗 | 典型用途 |
| --- | --- | --- | --- |
| Filter | 能，捕 `chain.doFilter` 抛出的；被 advice 消化的看不到 | 不能 | traceId、鉴权、CORS、压缩、错误页 |
| Interceptor | 能，`afterCompletion` 的 `ex` 参数；被 advice 处理后常是 `null`；`preHandle` 返回 false 或抛异常时不回调 | 能，handler 是 `HandlerMethod` 时；404 时是 `ResourceHttpRequestHandler` | 登录态、权限注解、耗时、handler 相关日志 |
| `@ControllerAdvice` | 能，只限进入 DispatcherServlet 的异常；Filter 抛的看不到 | 间接，从 request attribute 取；正常是 `HandlerMethod`，404 是资源处理器 | 异常转状态码/响应体 |
| AOP | 能，异常穿过代理时；自调用绕过 | 拿到被代理方法签名，不是 MVC 的 handler | 事务、缓存、重试、指标 |

`postHandle` 能不能改响应，取决于响应有没有提交。我这次 31 字节的 `/interceptor-write` 在 `postHandle` 里把状态改成 203、加上 `X-Interceptor-Post` 都生效：

```text
$ curl -i localhost:8080/interceptor-write
HTTP/1.1 203
X-Interceptor-Pre: yes
X-Interceptor-Post: yes
Content-Type: application/json

{"status":"set by interceptor"}
```

20KB 的 `/big` 就不行：`postHandle` 执行时 body 已经提交，状态仍是 `preHandle` 设的 202，`X-Interceptor-Post` 没出现。所以「拦截器不能改响应」是错的，「随时都能改」也不对。判断标准只有一条：**提交前能改，提交后改不动**。

还有一个我猜错的点：`@ExceptionHandler` 方法里直接写 `HandlerMethod` 参数，7.0.9 会报 `Could not resolve parameter [2] ... No suitable resolver`。要拿当前 handler，从 `request.getAttribute(HandlerMapping.BEST_MATCHING_HANDLER_ATTRIBUTE)` 取；正常 Controller 是 `HandlerMethod`，404 时是 `ResourceHttpRequestHandler`。别把它声明成 advice 方法的参数。

## `afterCompletion` 的三个前提

`afterCompletion` 不是「一定执行」。要同时满足：

1. 这个拦截器的 `preHandle` 已经返回 `true`；
2. 请求没有在它自己的 `preHandle` 返回 `false` 或抛异常时被截断；返回 false 的那个和排在它后面的不回调，已经返回 true 的前面的仍会回调；
3. 如果是异步请求，要等 async dispatch 结束后的那次调用；初始 dispatch 不会给你 `afterCompletion`。

把三次请求的日志压成一行看：

```text
B 返回 false：A preHandle → B preHandle → A afterCompletion；B afterCompletion 没有
B 抛异常：A preHandle → B preHandle → advice 418 → A afterCompletion；B afterCompletion 没有
A 第一个就抛：A preHandle → advice 418；A、B 的 afterCompletion 都没有
```

`afterCompletion` 的 `ex` 参数也不能当「原始异常」用：被 advice 处理掉的 `/boom`，A/B 拿到 `ex=null`；没有 advice 处理的 `/unhandled`，A/B 才拿到 `IllegalArgumentException`。要记录业务失败，优先在 advice 或 Filter 里记；`afterCompletion` 适合做资源清理和耗时收尾，不适合当唯一的错误日志点。

把几种情况写成一个能跑的小模型（不是 Spring 源码，只演示回调条件）：

<!-- run -->
```java
import java.util.ArrayList;
import java.util.List;

public class Main {

    enum Pre { OK, FALSE, THROW }

    static void run(String label, Pre a, Pre b) {
        List<String> events = new ArrayList<>();
        events.add("pre A");
        if (a == Pre.FALSE) {
            events.add("A returns false");
            print(label, events);
            return;
        }
        if (a == Pre.THROW) {
            events.add("A throws");
            print(label, events);
            return;
        }
        events.add("pre B");
        if (b == Pre.FALSE) {
            events.add("B returns false");
            events.add("after A");
            print(label, events);
            return;
        }
        if (b == Pre.THROW) {
            events.add("B throws");
            events.add("after A");
            print(label, events);
            return;
        }
        events.add("controller");
        events.add("post B");
        events.add("post A");
        events.add("after B");
        events.add("after A");
        print(label, events);
    }

    static void print(String label, List<String> events) {
        System.out.println(label + ": " + String.join(" -> ", events));
    }

    public static void main(String[] args) {
        run("A false", Pre.FALSE, Pre.OK);
        run("A throw", Pre.THROW, Pre.OK);
        run("B false", Pre.OK, Pre.FALSE);
        run("B throw", Pre.OK, Pre.THROW);
        run("both true", Pre.OK, Pre.OK);
    }
}
```
```text
A false: pre A -> A returns false
A throw: pre A -> A throws
B false: pre A -> pre B -> B returns false -> after A
B throw: pre A -> pre B -> B throws -> after A
both true: pre A -> pre B -> controller -> post B -> post A -> after B -> after A
```

## Filter 抛的异常，advice 看不到

同一个工程里，让 Filter 在 `chain.doFilter` 之前抛 `IllegalStateException("filter boom")`：

```text
INFO  ... demo.ProbeFilter : FILTER default enter uri=/filter-boom dispatcher=REQUEST asyncStarted=false
ERROR ... o.a.c.c.C.[.[.[/].[dispatcherServlet] : Servlet.service() for servlet [dispatcherServlet] in context with path [] threw exception
java.lang.IllegalStateException: filter boom
```

没有 `ProbeAdvice` 的日志。响应是 Boot 默认的错误体：

```text
$ curl -i localhost:8080/filter-boom
HTTP/1.1 500
Content-Type: application/json

{"timestamp":"2026-11-19T05:31:30.987Z","status":500,"error":"Internal Server Error","path":"/filter-boom"}
```

Filter 在 DispatcherServlet 前面，异常没有进入 `processHandlerException`。`HandlerExceptionResolver` 也是 DispatcherServlet 内部的 SPI，不能拿来兜 Filter 异常——这点容易和 `@ControllerAdvice` 混在一起。能兜 Filter 异常的是：

- Filter 自己 `try/catch`，然后写状态码和 JSON；
- 让容器走 `/error`，再自定义 `ErrorAttributes` 或 `BasicErrorController`。

这次 `/error` 那次 dispatch 里，拦截器 A/B 又跑了一遍；Filter 默认跳过 ERROR dispatch。不要在拦截器里假设 `/error` 还是原始请求，也不要在 Filter 里假设 advice 一定在。

## advice 没接住时，谁写 500

`/filter-boom` 的 500 不是 advice 写的。链路是：Filter 抛异常 → 容器捕获 → ERROR dispatch 到 `/error` → `BasicErrorController` 调用 `ErrorAttributes` 生成模型 → 写响应。`DefaultErrorAttributes` 同时实现了 `ErrorAttributes` 和 `HandlerExceptionResolver`，前者负责整理字段，后者负责在 MVC 内部存异常。

默认响应里只有 `timestamp`、`status`、`error`、`path`，没有异常消息、类名和堆栈。Boot 4.1.1 的开关是 `spring.web.error.include-*`；旧资料里常见的 `server.error.*`，在 4.1.1 上不生效：

| 属性 | 默认 | 控制什么 |
| --- | --- | --- |
| `spring.web.error.include-message` | `never` | `message` |
| `spring.web.error.include-exception` | `false` | `exception` 类名 |
| `spring.web.error.include-binding-errors` | `never` | `errors` |
| `spring.web.error.include-stacktrace` | `never` | `trace` |
| `spring.web.error.include-path` | `always` | `path` |

我先把旧前缀写成 `always` 试了一次：

```text
java -jar app.jar --server.error.include-message=always
$ curl -i localhost:8080/filter-boom
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/filter-boom"}
```

响应没变。换成新前缀才有 `message`、`exception`、`trace`：

```text
java -jar app.jar --spring.web.error.include-message=always --spring.web.error.include-exception=true --spring.web.error.include-stacktrace=always
$ curl -i localhost:8080/filter-boom
{"timestamp":"...","status":500,"error":"Internal Server Error","exception":"java.lang.IllegalStateException","trace":"java.lang.IllegalStateException: filter boom ...","message":"filter boom","path":"/filter-boom"}
```

顺序要记清楚：**advice 先处理；advice 返回了响应，`/error` 就不会参与。** 只有 advice 没接住、异常继续往外走（或容器 `sendError`）时，才会发生 ERROR dispatch 到 `/error`。`/nope` 在关掉静态资源映射后就是后一条路：没有 handler mapping，没有 `NoResourceFoundException`，advice 不执行，最后由 `/error` 写 404。

## Callable 之后，请求线程先走了

`Callable`、`DeferredResult`、`WebAsyncTask` 都会让 Servlet 进入 async 模式。下面是 `/async-callable` 的日志（省略了部分重复行）：

```text
INFO ... demo.ProbeFilter : FILTER default enter uri=/async-callable dispatcher=REQUEST asyncStarted=false
INFO ... demo.AsyncAwareFilter : FILTER async-aware enter uri=/async-callable dispatcher=REQUEST asyncStarted=false
INFO ... demo.Interceptor.A : A preHandle uri=/async-callable handler=HandlerMethod dispatcher=REQUEST asyncStarted=false
INFO ... demo.Interceptor.B : B preHandle uri=/async-callable handler=HandlerMethod dispatcher=REQUEST asyncStarted=false
INFO ... demo.ProbeController : CONTROLLER async-callable thread=http-nio-18080-exec-2
INFO ... demo.ProbeController : CALLABLE body thread=task-1
INFO ... demo.AsyncAwareFilter : FILTER async-aware exit uri=/async-callable dispatcher=REQUEST asyncStarted=true
INFO ... demo.ProbeFilter : FILTER default exit uri=/async-callable dispatcher=REQUEST asyncStarted=true status=200
INFO ... demo.AsyncAwareFilter : FILTER async-aware enter uri=/async-callable dispatcher=ASYNC asyncStarted=false
INFO ... demo.Interceptor.A : A preHandle uri=/async-callable handler=HandlerMethod dispatcher=ASYNC asyncStarted=false
INFO ... demo.Interceptor.B : B preHandle uri=/async-callable handler=HandlerMethod dispatcher=ASYNC asyncStarted=false
INFO ... demo.Interceptor.B : B postHandle uri=/async-callable status=200 dispatcher=ASYNC asyncStarted=false
INFO ... demo.Interceptor.A : A afterCompletion uri=/async-callable status=200 dispatcher=ASYNC asyncStarted=false ex=null
INFO ... demo.AsyncAwareFilter : FILTER async-aware exit uri=/async-callable dispatcher=ASYNC asyncStarted=false
```

几个关键点：

- `Callable` 在 `task-1` 上跑，Tomcat 请求线程在 `FILTER default exit` 那行就回去了；`DeferredResult` 的 worker 线程名字是 `deferred-worker`，同样不在请求线程上。
- `OncePerRequestFilter` 默认 `shouldNotFilterAsyncDispatch()` 返回 `true`，所以 `ProbeFilter` 在 ASYNC dispatch 没有再进；我把 `AsyncAwareFilter` 的该方法改成 `false`，才看到第二次 enter/exit。
- 拦截器的 `preHandle` 在 REQUEST 和 ASYNC 各跑一次；`postHandle`、`afterCompletion` 只在 ASYNC 那次、async 结果回来之后跑。`afterCompletion` 的「延后」不是框架慢了，是请求生命周期还没结束。
- 异步异常仍在同一套 advice 机制里。`/async-error` 在 `task-1` 抛 `IllegalStateException`，ASYNC dispatch 上 advice 接住，返回 418，`afterCompletion` 也在 ASYNC 那次才出现。
- 这带来一个实际坑：如果你在 Filter 的 `finally` 里关闭异步任务还要用的资源，默认 Filter 在初始 dispatch 结束时就会执行 `finally`，那时 async 还没完成。要么把清理放到 async 完成之后，要么关掉 `shouldNotFilterAsyncDispatch()` 并自己判断 `DispatcherType`。

`WebAsyncTask` 我没有单独跑；它和 `Callable` 走同一套 Servlet async dispatch，但超时和错误回调的细节要按你实际用的返回类型再验。

## 事务回滚不等于 HTTP 500

事务是 AOP 层的事，不是 HTTP 层的事。一个 Service 方法回滚，只说明事务被标记为 rollback；它不会自动给 response 写 500。比如：

```java
@Transactional
public void create() {
    throw new IllegalStateException("rollback");
}
```

Controller 如果把这个异常 catch 住，返回一个正常对象：

```java
@PostMapping("/orders")
public Map<String, String> create() {
    try {
        service.create();
    } catch (IllegalStateException error) {
        return Map.of("status", "caught");
    }
}
```

按这套代码，`curl -i` 应该看到 200，而不是 500；我没有接数据库复跑，验证时要自己看状态码。事务回滚和 HTTP 状态码是两条链：对象层回滚，HTTP 层完全不知道；只有异常继续往外抛，才可能被 advice 或 `/error` 变成 500。验证方法就是准备两个接口，一个 catch、一个不 catch，分别 `curl -i` 看状态码。
