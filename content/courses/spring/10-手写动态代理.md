# 10 · 手写动态代理

## 这一课你要会

- 用 `java.lang.reflect.Proxy` 给一个接口生成代理，并在方法调用前后插入行为；
- 解释"同类内部调用不经过代理"为什么是必然的，而不是框架的 bug；
- 说清 JDK 动态代理只能代理接口，这个限制从哪来；
- 知道 Spring 的 AOP、事务、`@Async`、`@Cacheable` 全都建立在这一层上。

## 为什么

前面九课讲的是"对象怎么被造出来"。这一课讲的是"造出来之后，怎么在它外面再套一层"。

这一层套上之后，`@Transactional`、`@Async`、`@Cacheable`、`@PreAuthorize`、`@Retryable` 才有地方生效——**它们全都是"方法被调用时插一段逻辑"**。而"插逻辑"的唯一手段，是在调用方与目标之间放一个中间人。

中间人就是代理。理解了它，Spring 里最常被问的那句"为什么加了注解没生效"就有了统一答案：**因为那次调用没有经过代理**。

## 讲解

### 代理要做的事只有一个

```text
调用方 → 代理.方法() → [前置] → 目标.方法() → [后置] → 调用方
```

代理必须与目标**实现同一个接口**，否则调用方没法把它当目标用——就是 Java 的赋值兼容。

### 手写一遍

`Proxy.newProxyInstance` 只需要三样东西：类加载器、要实现的接口列表、以及一个"方法被调用时该干什么"的处理器。

<!-- run -->
```java
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

public class Main {

    interface Greeting {
        String hello(String name);

        String twice(String name);
    }

    static class GreetingImpl implements Greeting {
        public String hello(String name) {
            return "hello, " + name;
        }

        public String twice(String name) {
            return hello(name) + hello(name);
        }
    }

    static Greeting timed(Greeting target, List<String> log) {
        return (Greeting) Proxy.newProxyInstance(
                Greeting.class.getClassLoader(),
                new Class<?>[]{Greeting.class},
                (proxy, method, args) -> {
                    log.add("before:" + method.getName());
                    Object result = method.invoke(target, args);
                    log.add("after:" + method.getName());
                    return result;
                });
    }

    public static void main(String[] args) {
        List<String> log = new ArrayList<>();
        Greeting proxy = timed(new GreetingImpl(), log);

        System.out.println(proxy.hello("a"));
        System.out.println(log);

        log.clear();
        System.out.println(proxy.twice("x"));
        System.out.println(log);
    }
}
```
```text
hello, a
[before:hello, after:hello]
hello, xhello, x
[before:twice, after:twice]
```

最后一行是全课的重点，请仔细看：`twice` 内部调用了两次 `hello`，但日志里**只有 `twice` 自己的前后置，没有两次 `hello`**。

原因是：`proxy.twice("x")` 进入代理后，处理器调的是 `target.twice("x")`——`target` 是那个**原始对象**。它在方法体里写 `hello(name)`，等价于 `this.hello(name)`，`this` 是原始对象自己，不是代理。所以那两次调用根本没经过代理。

这不是我手写版的缺陷，这就是 Spring 的 `@Transactional` 在同类内部调用时失效的**全部原因**。

### JDK 动态代理只能代理接口

`Proxy.newProxyInstance` 的返回值**只能赋给接口类型**。原因在原理上：

- 代理类是在运行时**生成的一个新类**，它 `implements` 你给的那一组接口；
- Java 不支持多继承，所以它没法 `extends` 你的目标类；
- 不继承目标类，就没法把目标的方法"覆盖"掉——而"覆盖"是插入逻辑的唯一手段。

所以对没有接口的类，JDK 代理无能为力。这就是 CGLIB 存在的原因：**CGLIB 直接生成目标类的子类**，覆盖它的方法。代价是：

| | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 前提 | 目标必须实现接口 | 目标不能是 `final` 类 |
| 不能代理 | 没有接口的类 | `final` 类、`final` 方法、`private` 方法 |
| 生成方式 | 实现同一接口 | 继承目标类 |

**Spring Boot 从 2.x 起默认用 CGLIB**（`spring.aop.proxy-target-class=true`），所以"我的类没实现接口却能被事务包住"是正常的。但这也意味着：`final` 方法和 `private` 方法永远不会被代理——这条限制无法绕过。

### 三个失效场景，同一个原因

| 你写的 | 实际发生 | 原因 |
| --- | --- | --- |
| 同类内部 `this.other()` | 直接调用，不经代理 | `this` 是原始对象 |
| 方法标了 `private` | 代理覆盖不到 | 子类不能覆盖私有方法 |
| 类是 `final` / 方法是 `final` | 代理生成失败或该分支不拦截 | 不能继承/覆盖 |

三个场景在代码里长得完全不一样，原因却是同一句：**那段逻辑没有机会被插入**。

### Spring 里怎么写

```java
@Aspect
@Component
public class TimingAspect {

    @Around("execution(* com.example.service..*(..))")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        String name = joinPoint.getSignature().getName();
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            System.out.println(name + " 耗时 " + (System.nanoTime() - start) / 1_000_000 + " ms");
        }
    }
}
```

`joinPoint.proceed()` 就是上面手写版里的 `method.invoke(target, args)`。`@Around` 能做的所有事（改返回值、吞异常、重试），手写版的处理器都能做——它就是在那个位置写代码。

### 怎么确认自己拿到的是代理

一句最便宜的自检：

```java
System.out.println(this.getClass().getName());
```

看到 `$$EnhancerBySpringCGLIB$$` 或 `$Proxy` 前缀，说明有代理；看到你自己的类名，说明没有——那这次方法调用里所有基于注解的行为都不会生效。

## 常见误区

### 误区：自调用失效是 Spring 的 bug

**你以为**：框架应该能识别出"这次调用也需要事务"。
**其实**：代理是"套在对象外面"的一层。对象内部的方法调用根本不经过外面那层，框架没有任何机会插入逻辑——除非它改写字节码（那就不叫代理了）。这是代理模式的固有代价。
**怎么验证**：在第 12 课的事务实验里，把 `@Transactional` 从外层方法挪到被自调用的内层方法，观察事务是否还开。

### 误区：用了 CGLIB 就没有限制了

**你以为**：CGLIB 能代理普通类，所以什么方法都能拦。
**其实**：CGLIB 是子类代理，`final` 类不能继承、`final` 方法不能覆盖、`private` 方法不可见。这三条在字节码层面是硬限制。Spring 会在启动时给出提示（`Cannot proxy ...`），但办法只有改代码。
**怎么验证**：给一个 `@Service` 加 `final`，看启动是否报代理失败。

### 误区：代理对象的字段就是目标的字段

**你以为**：拿到代理后读它的字段能拿到目标的状态。
**其实**：CGLIB 代理是**子类实例**，JDK 代理是完全不同的类（字段根本没有）。多数情况下访问器方法会转发到目标，但直接读字段（包括反射）读到的是代理自己的那份，通常是 null。
**怎么验证**：在 `@Service` 里用 `this.getClass().getDeclaredFields()`，对比经过代理与不经过代理的结果。

## 小结

代理就是在调用方与目标之间放一个中间人，唯一手段是"实现同一接口"或"继承目标类"。自调用、`private`、`final` 三个失效场景是同一个原因：逻辑没有机会被插入。Spring 默认用 CGLIB，所以没实现接口的类也能被事务包住，但 `final` 与 `private` 永远不行。
