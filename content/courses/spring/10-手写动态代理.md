# 10 · 手写动态代理

## 一行业务异常，变成了一行 null

给自己的库存服务手写了一层代理，想统一记日志。上线后报错日志长这样：

```text
java.lang.reflect.UndeclaredThrowableException
	at com.example.Main$GreetingImpl$$... 
Caused by: java.lang.reflect.InvocationTargetException
Caused by: java.lang.IllegalStateException: 库存不足
```

真正的业务异常 `库存不足` 被埋在第三层，第一行的 `getMessage()` 还是 `null`——监控告警上配的「消息包含 库存不足」永远不会触发。

原因是这一行：

```java
return method.invoke(target, args);     // 反射调用的异常会被包一层
```

`Method.invoke` 从不直接抛出目标方法自己的异常，它统一包成 `InvocationTargetException`。而 `InvocationTargetException` 是**受检异常**，代理接口上又没声明它，于是 JDK 再包一层 `UndeclaredThrowableException`。

这篇从这条链往回走，把动态代理的手写、边界、以及"为什么 `@Transactional` 会失效"讲完。

## 代理做的事只有一个

```text
调用方 → 代理.方法() → [前置] → 目标.方法() → [后置] → 调用方
```

代理必须与目标**实现同一个接口**，否则调用方没法把它当目标用——这就是 Java 的赋值兼容。

`@Transactional`、`@Async`、`@Cacheable`、`@PreAuthorize`、`@Retryable` 全都建立在"方法被调用时插一段逻辑"这件事上，而插入的唯一手段就是中间人。

## 手写一遍

`Proxy.newProxyInstance` 只要三样：类加载器、要实现的接口列表、一个"方法被调用时干什么"的处理器。

<!-- run -->
```java
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

public class Main {

    interface Greeting {
        String hello(String name);

        String twice(String name);
    }

    static class GreetingImpl implements Greeting {
        public String hello(String name) {
            return "hello, " + name;
        }

        public String twice(String name) {
            return hello(name) + hello(name);
        }
    }

    static Greeting timed(Greeting target, List<String> log) {
        return (Greeting) Proxy.newProxyInstance(
                Greeting.class.getClassLoader(),
                new Class<?>[]{Greeting.class},
                (proxy, method, args) -> {
                    log.add("before:" + method.getName());
                    Object result = method.invoke(target, args);
                    log.add("after:" + method.getName());
                    return result;
                });
    }

    public static void main(String[] args) {
        List<String> log = new ArrayList<>();
        Greeting proxy = timed(new GreetingImpl(), log);

        System.out.println(proxy.hello("a"));
        System.out.println(log);

        log.clear();
        System.out.println(proxy.twice("x"));
        System.out.println(log);
    }
}
```
```text
hello, a
[before:hello, after:hello]
hello, xhello, x
[before:twice, after:twice]
```

最后两行是这课的重点：`twice` 内部调了两次 `hello`，日志里**只有 `twice` 自己的前后置，没有那两次 `hello`**。

原因：`proxy.twice("x")` 进代理后，处理器调的是 `target.twice("x")`，`target` 是**原始对象**。它在方法体里写 `hello(name)` 等价于 `this.hello(name)`，`this` 是原始对象自己，不是代理。那两次调用根本没经过代理。

这不是手写版的缺陷——这就是 Spring 的 `@Transactional` 在同类内部调用时失效的全部原因。

## 反射会把异常包一层

回到开头那个问题。修法是**把包拆掉**：

```java
try {
    return method.invoke(target, args);
} catch (InvocationTargetException e) {
    throw e.getCause();          // 把目标方法自己的异常还原出来
}
```

同一段代码，改前改后调用方看到的：

```text
改前  类型: java.lang.reflect.UndeclaredThrowableException   消息: null
改后  类型: java.lang.IllegalStateException                  消息: 库存不足
```

这件事在 Spring 里由框架替你做，所以平时感觉不到。但只要你手写代理（或自己写 `@Around` 切面里调 `proceed()` 之外的东西），这层包装就会出现，而且它会**改变事务回滚的判定**——Spring 判断是否回滚看的是异常类型，包了一层之后 `rollbackFor` 里写的类型全都对不上。

顺带一句：`@Around` 里的 `joinPoint.proceed()` 已经处理过这层包装，直接抛出去就是原始异常。

## `Object` 的三个方法也会被拦

处理器收到的不只是你接口里声明的方法。`toString()`、`equals()`、`hashCode()` 也会走它：

```text
1) 调 g.toString()
  [拦截] toString
  Main$GreetingImpl@5cad8086
```

（`@5cad8086` 这个数是原始对象的 `hashCode`，每次运行不同。）

三个后果：

- 日志里打印代理对象会**触发一次拦截**，别在有副作用的处理器里做这件事（比如统计"调用次数"，`toString` 会把它抬高）；
- 处理器要转发 `equals`/`hashCode` 到 `target`，否则两个"同一个目标"的代理彼此不相等；
- 如果处理器对 `Object` 方法也做业务逻辑（比如开事务），`hashCode()` 被调用时也会开事务。

## JDK 动态代理只能代理接口

`Proxy.newProxyInstance` 的返回值**只能赋给接口类型**。原理：

- 代理类是运行时**生成的新类**，它 `implements` 你给的那组接口；
- Java 不支持多继承，它没法 `extends` 你的目标类；
- 不继承，就没法"覆盖"目标的方法——而覆盖是插入逻辑的唯一手段。

所以对没有接口的类，JDK 代理无能为力。CGLIB 走的是另一条路：**生成目标类的子类**，覆盖它的方法。

| | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 前提 | 目标必须实现接口 | 目标不能是 `final` 类 |
| 不能代理 | 没有接口的类 | `final` 类、`final` 方法、`private` 方法 |
| 生成方式 | 实现同一接口 | 继承目标类 |
| 生成物 | `jdk.proxy2.$Proxy12` 之类 | `Xxx$$SpringCGLIB$$0` |

**Spring Boot 从 2.x 起默认用 CGLIB**（`spring.aop.proxy-target-class`，默认 `true`），所以"类没实现接口也能被事务包住"是正常的。代价是 `final` 与 `private` 永远拦不到。

## 三个失效场景，同一个原因

| 你写的 | 实际发生 | 原因 |
| --- | --- | --- |
| 同类内部 `this.other()` | 直接调用，不经代理 | `this` 是原始对象 |
| 方法标了 `private` | 代理覆盖不到 | 子类不能覆盖私有方法 |
| 类是 `final` / 方法是 `final` | 代理生成失败或该分支不拦 | 不能继承/覆盖 |

三种写法看起来毫无关系，原因只有一句：**那段逻辑没机会被插入**。

## Spring 里怎么写

```java
@Aspect
@Component
public class TimingAspect {

    @Around("execution(* com.example.service..*(..))")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        String name = joinPoint.getSignature().getName();
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            System.out.println(name + " 耗时 " + (System.nanoTime() - start) / 1_000_000 + " ms");
        }
    }
}
```

`joinPoint.proceed()` 就是手写版里的 `method.invoke(target, args)`，只不过异常包装由它处理掉了。`@Around` 能做的所有事（改返回值、吞异常、重试），手写版的处理器都能做——它就是在同一个位置写代码。

## 怎么确认自己拿到的是代理

一句最便宜的自检：

```java
System.out.println(this.getClass().getName());
```

看到 `$$SpringCGLIB$$` 或 `$Proxy`，说明有代理；看到自己的类名，说明这次调用里所有基于注解的行为都不会生效。

更彻底的一条是从外面看：

```java
System.out.println(AopUtils.isAopProxy(bean));
```

## 三件我原来以为对的事

**一、`@Transactional` 失效是框架的 bug。** 代理是套在对象外面的一层，对象内部的方法调用不经过外面那层，框架没有任何插入机会——除非它改写字节码（那就不是代理了）。这是模式的固有代价，不是实现缺陷。

**二、用了 CGLIB 就没有限制了。** `final` 类不能继承、`final` 方法不能覆盖、`private` 方法不可见，这三条在字节码层面是死限制。Spring 启动时会提示代理失败，但办法只有改代码。

**三、代理对象的字段就是目标对象的字段。** CGLIB 代理是**子类实例**，字段是它自己的（通常是 null）；JDK 代理根本没有那些字段。所以别用反射从代理上读状态——要读就读返回值，或者把状态放到单独的对象里。

## 这一课之后

代理就是调用方与目标之间的中间人：实现同一接口（JDK）或继承目标类（CGLIB）。自调用、`private`、`final` 三个失效场景是同一个原因——逻辑没机会被插入。手写时记得拆掉 `InvocationTargetException`，否则异常类型会变、事务回滚判断会错；`toString`/`equals`/`hashCode` 也会走一遍处理器。
