# 08 · 作用域与生命周期

## 两次请求，builder 还是同一个

`ReportBuilder` 是原型，`ReportService` 是单例，构造器把 builder 注入进去。下面两个类各放一个文件：

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import java.util.ArrayList;
import java.util.List;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;

@Component
@Scope("prototype")
public class ReportBuilder implements DisposableBean {
    private static int nextId = 1;
    private final int id = nextId++;
    private final List<String> owners = new ArrayList<>();

    ReportBuilder() {
        System.out.println("ReportBuilder ctor #" + id);
    }

    @PostConstruct
    void init() {
        System.out.println("@PostConstruct #" + id);
    }

    ReportBuilder add(String owner) {
        owners.add(owner);
        return this;
    }

    String build() {
        return "builder#" + id + " owners=" + owners;
    }

    int id() {
        return id;
    }

    @PreDestroy
    void preDestroy() {
        System.out.println("@PreDestroy #" + id);
    }

    @Override
    public void destroy() {
        System.out.println("destroy() #" + id);
    }
}

@Service
public class ReportService {
    private final ReportBuilder builder;

    public ReportService(ReportBuilder builder) {
        this.builder = builder;
        System.out.println("ReportService ctor, builder#" + builder.id());
    }

    public String report(String owner) {
        return builder.add(owner).build();
    }
}
```

在 Temurin 25.0.4 + Spring Boot 3.5.6 的临时工程里，用 `AnnotationConfigApplicationContext` 启动，连着调两次 `report()`：

```text
ReportBuilder ctor #1
@PostConstruct #1
ReportService ctor, builder#1
builder#1 owners=[alice]
builder#1 owners=[alice, bob]
```

第二次没有新建 builder，`owners` 还把 alice 留在里面。我原来的判断是「`@Scope("prototype")` 写在类上，谁注入谁就每次拿新的」；实际是**注入只发生一次**：单例 `ReportService` 启动时解析一次依赖，之后一直握着同一个原型对象。Boot 4.1.1 上这段输出一样。

容器关闭时也没有出现 `@PreDestroy` 或 `destroy()` 行。这不是输出被截断，原型 bean 的销毁回调本来就不会被容器调用；下一节把两张表摆出来，再回头解释这两件事。

## 六个作用域：谁创建、活多久、谁收尾

| 作用域 | 谁创建、放在哪 | 活多久 | 容器会调销毁回调吗 | 前提 |
| --- | --- | --- | --- | --- |
| `singleton` | Spring 容器创建，放单例池 | 容器启动到关闭 | 会；正常关闭时 | 无 |
| `prototype` | Spring 每次向容器要时创建，容器不保存 | 调用方持有期间 | **不会** | 无 |
| `request` | Spring 创建，放当前 request 属性 | 一次 HTTP 请求 | 会；请求结束时 | `WebApplicationContext` |
| `session` | Spring 创建，放 `HttpSession` | 一个会话 | 会；会话失效或过期时 | `WebApplicationContext` |
| `application` | Spring 创建，放 `ServletContext` | 一个 Web 应用 | 会；Web 应用关闭时 | `ServletContext` |
| `websocket` | Spring 创建，放 WebSocket/SIMP 会话 | 一个 WebSocket 会话 | 会；会话关闭时 | WebSocket 消息配置 |

`singleton` 的「单例」只在一个容器、一个 bean 定义内成立。它不是 GoF 单例，也不是 JVM 单例：`new AnnotationConfigApplicationContext(...)` 两次就是两个实例；同一个类用两个 `@Bean` 方法注册两次，也是两个 bean。

`singleton` 默认在容器启动时创建；加 `@Lazy` 后第一次被要时才创建，但活到容器关闭这一点不变。

`prototype` 的「每次」指每次向容器要，不是每次方法调用，也不是每次注入。`ObjectProvider.getObject()`、`ApplicationContext.getBean()`、`@Lookup` 都算向容器要；构造器注入只解析一次。

`application` 的销毁挂在 `ServletContext` 关闭上。Spring Framework 7.0.9 的 `ServletContextScope` Javadoc 明确写了一句：这个时点可能早于、也可能晚于包含它的 Spring 容器关闭。所以别把 `application` 的 `@PreDestroy` 当成「Spring 容器关了我才收尾」。

`websocket` 需要 WebSocket 消息配置（比如 `@EnableWebSocketMessageBroker`）。Spring 7 / Boot 4.1.1 提供了 `@WebSocketScope` 组合注解；Boot 3.5.6 里用 `@Scope("websocket")`，底层的 scope 名是同一个。

## 生命周期：不是「或」，是「然后」

一个 bean 的正常链路：

```text
构造器
  → 依赖注入（构造器参数 / 字段 / setter）
  → @PostConstruct
  → InitializingBean.afterPropertiesSet()
  → 使用
  → @PreDestroy
  → DisposableBean.destroy()
```

`@PostConstruct` / `@PreDestroy` 的包名是 `jakarta.annotation`，不是 `javax.annotation`。Boot 3.5.6 和 4.1.1 都用 Jakarta EE 9+ 的命名空间；我在这两个版本的临时工程里把 import 换成 `javax.annotation`，编译直接报：

```text
[ERROR] ...Main.java:[1,24] 程序包javax.annotation不存在
[ERROR] ...Main.java:[2,24] 程序包javax.annotation不存在
```

准确的 import 是：

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
```

两个接口都实现时，两个回调都会跑；顺序固定：

```java
@Component
public class LifecycleProbe implements InitializingBean, DisposableBean {
    @Autowired
    private Dependency dependency;

    public LifecycleProbe() {
        System.out.println("1 ctor: dependency=" + (dependency == null ? "null" : "set"));
    }

    @PostConstruct
    void postConstruct() {
        System.out.println("3 @PostConstruct: dependency=" + (dependency == null ? "null" : "set"));
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("4 afterPropertiesSet: dependency=" + (dependency == null ? "null" : "set"));
    }

    String use() {
        return "5 use: dependency=" + (dependency == null ? "null" : "set");
    }

    @PreDestroy
    void preDestroy() {
        System.out.println("6 @PreDestroy");
    }

    @Override
    public void destroy() {
        System.out.println("7 destroy()");
    }
}
```

`Dependency` 是一个只打印 `0 Dependency ctor` 的 `@Component`；主类拿到 probe 后调了一次 `use()`，所以输出里有第 5 行。

实测输出（Boot 3.5.6 和 4.1.1 一致）：

```text
0 Dependency ctor
1 ctor: dependency=null
3 @PostConstruct: dependency=set
4 afterPropertiesSet: dependency=set
5 use: dependency=set
6 @PreDestroy
7 destroy()
```

这里有两个常被写错的点：

- 不是「`@PostConstruct` 或 `afterPropertiesSet` 二选一」。两个都实现，就是两个都执行，`@PostConstruct` 在前。
- `afterCreate()` 不是 Spring 的回调。`InitializingBean` 的方法名是 `afterPropertiesSet()`；`DisposableBean` 的方法名是 `destroy()`。自己写 `afterCreate()`，Spring 不会替你调用。

### 每个时刻能看到什么

| 时刻 | 构造器参数 | `@Autowired` 字段 | 这时能做什么 |
| --- | --- | --- | --- |
| 构造器 | 已赋值 | 还是 `null` | 只能用构造器参数；不要读字段注入的依赖 |
| 字段/setter 注入后 | 已赋值 | 已赋值 | 依赖齐了，但 `@PostConstruct` 还没跑 |
| `@PostConstruct` | 已赋值 | 已赋值 | 第一个「注入完成」的钩子；适合校验依赖、初始化派生状态 |
| `afterPropertiesSet` | 已赋值 | 已赋值 | `@PostConstruct` 已经跑完；适合框架级初始化 |
| 使用期 | 已赋值 | 已赋值 | 完全初始化；AOP 代理也已包好 |
| `@PreDestroy` | 已赋值 | 已赋值 | bean 还能用；别的 bean 可能已经在销毁，别依赖它们的资源 |
| `destroy()` | 已赋值 | 已赋值 | `@PreDestroy` 已经跑完；还是同一个对象，字段还在 |

同一 bean 内，`@PreDestroy` 一定在 `destroy()` 前。不同单例之间，当前实现按创建的反序销毁；我让 B 构造器依赖 A，在 3.5.6 和 4.1.1 上实测都是 `ctor A → ctor B → destroy B → destroy A`。这能让依赖者先死，但它是当前实现，不是你可以拿来写业务顺序的契约。

## 跑一遍

把 prototype 的计数抽成一个不依赖 Spring 的小程序，方便你确认「容器不保存原型，所以关容器时没有东西可销毁」：

<!-- run -->
```java
public class Main {
    static int initCount;
    static int destroyCount;

    static final class Prototype {
        Prototype() {
            initCount++;
        }

        void destroy() {
            destroyCount++;
        }
    }

    static final class Container {
        Prototype getPrototype() {
            return new Prototype();
        }

        void close() {
            // 容器不持有 prototype，这里没有可销毁的对象
        }
    }

    public static void main(String[] args) {
        Container container = new Container();
        Prototype first = container.getPrototype();
        Prototype second = container.getPrototype();
        System.out.println("same instance: " + (first == second));
        container.close();
        System.out.println("init=" + initCount + ", destroy=" + destroyCount);
    }
}
```
```text
same instance: false
init=2, destroy=0
```

这段只用 JDK，证明的是这个玩具容器的计数；真正的 Spring 输出在前面，版本是 3.5.6 / 4.1.1。它对应的是下面第二个坑：`getPrototype()` 每次 new，但 `close()` 不会碰它们。

## 三个真正会咬人的坑

### 坑一：prototype 注入进 singleton，原型退化成单例

开头已经看到结果：`ReportService` 是单例，构造器只跑一次，`ReportBuilder` 也只解析一次。`builder#1 owners=[alice, bob]` 就是状态被复用的证据。

修法不是把 `ReportService` 也改成 prototype，而是把「什么时候要」推迟到方法调用：

```java
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.stereotype.Service;

@Service
public class ReportService {
    private final ObjectProvider<ReportBuilder> builders;

    public ReportService(ObjectProvider<ReportBuilder> builders) {
        this.builders = builders;
    }

    public String report(String owner) {
        return builders.getObject().add(owner).build();
    }
}
```

注入到单例里的是一个 provider，不是 prototype 实例；`getObject()` 每次向容器要一个新的 prototype。实测两次输出变成：

```text
ReportBuilder ctor #1
@PostConstruct #1
builder#1 owners=[alice]
ReportBuilder ctor #2
@PostConstruct #2
builder#2 owners=[bob]
init=2, destroyed=0
```

注意最后一行：状态不串了，但 `destroyed` 还是 0。`ObjectProvider` 解决的是「拿新实例」，不解决「谁负责关」。这就是下一个坑。

### 坑二：prototype 的 `@PreDestroy` 不会执行

直接向容器要两次 prototype，容器关闭后再看计数。`Prototype` 就是开头 `ReportBuilder` 的缩小版：构造器、`@PostConstruct`、`@PreDestroy`、`destroy()` 各加一次计数，其他不变。

```java
@Configuration
class Config {
    @Bean
    @Scope("prototype")
    Prototype prototype() {
        return new Prototype();
    }
}
```

实测：

```text
ctor #1
@PostConstruct #1
ctor #2
@PostConstruct #2
same instance: false
init=2, @PreDestroy=0, destroy()=0
```

`init=2` 说明两个实例都完成了初始化；`@PreDestroy=0` 和 `destroy()=0` 说明容器关闭时一个都没收尾。Spring 只负责创建和装配 prototype，交给你之后不再保留引用，所以它没有对象可销毁。这是契约，不是漏调。

清理责任在调用方：能 `try-with-resources` 就让 prototype 实现 `AutoCloseable`；不能就用 `try/finally` 显式 `close()`。如果这个 prototype 被单例长期持有，单例的 `@PreDestroy` 要负责关它——但这时它实际上已经是一个单例资源，应该重新考虑作用域。

### 坑三：request/session 只在 Web 上下文里有

在普通的 `AnnotationConfigApplicationContext` 里注册一个 `@Scope("request")` 的 bean，首次 `getBean` 就报：

```java
var context = new AnnotationConfigApplicationContext(Config.class);
context.getBean(RequestBean.class);
```
```text
java.lang.IllegalStateException
No Scope registered for scope name 'request'
```

`session` 同理；`application` 要 `ServletContext`；`websocket` 要 WebSocket 消息配置。不是加个注解就自动有请求。

更常见的是「在 Web 应用里，把没有代理的 request bean 注入 singleton」，启动时直接失败：

```text
Scope 'request' is not active for the current thread;
consider defining a scoped proxy for this bean if you intend to refer to it from a singleton
```

因为 singleton 在启动时创建，那时还没有请求。下一节讲怎么让 singleton 拿到「当前请求」的对象。

Boot 3.5.6 用 `spring-boot-starter-web`；Boot 4.1.1 的对应 starter 是 `spring-boot-starter-webmvc`。只加 `spring-boot-starter` 不够：非 Web 的 `ApplicationContext` 没有注册 request/session scope。

## 让 singleton 拿到「当前请求」：scoped proxy

singleton 在启动时创建，request bean 要等请求才有；直接把 request bean 注入 singleton，容器会在启动时试图创建它，于是报上面的 `Scope 'request' is not active`。解法是让 singleton 注入一个**代理**，代理本身是单例，每次方法调用再按当前请求找真实对象：

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.context.annotation.Scope;
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;
import org.springframework.web.context.WebApplicationContext;

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST,
       proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestBean {
    private static int nextId = 1;
    private final int id = nextId++;

    @PostConstruct
    void init() {
        System.out.println("@PostConstruct request#" + id);
    }

    @PreDestroy
    void destroy() {
        System.out.println("@PreDestroy request#" + id);
    }

    int id() {
        return id;
    }
}
```

`@RequestScope` 是它的组合注解，默认 `proxyMode = TARGET_CLASS`；我在 Boot 3.5.6 / 4.1.1 对应的 `spring-web` 6.2.11 / 7.0.9 字节码里确认过默认值。它在 `org.springframework.web.context.annotation.RequestScope`，把上面两行注解换成 `@RequestScope` 即可，字段和回调不用动。

在 Boot 3.5.6（`spring-boot-starter-web`）和 4.1.1（`spring-boot-starter-webmvc`）上各起一个临时 Web 应用，singleton 注入上面的 `RequestBean`，连打两次 `GET /who`，输出一致：

```text
@PostConstruct request#1
@PreDestroy request#1
GET /who -> request#1
@PostConstruct request#2
@PreDestroy request#2
GET /who -> request#2
destroyed before close=2
destroyed after close=2
```

`@PreDestroy` 行出现在 `GET` 行之前，是因为服务端在请求结束时先收尾，客户端随后才打印收到的响应；不代表 handler 还没执行。两次请求拿到 `request#1` 和 `request#2`；`@PreDestroy` 在请求结束时执行，容器关闭时没有再执行一遍（`destroyed` 前后都是 2）。这也说明「`@PreDestroy` 只在容器关闭时调用」并不准确：request scope 在请求结束就销毁，不等容器关闭。

**什么时候必须用**：长命对象（singleton）直接构造器注入短命对象（request/session）时，代理是最直接的解法。代理让 singleton 持有的是代理，不是真实 request bean。不想加代理，也可以注入 `ObjectFactory<RequestBean>` 或 `ApplicationContext`，在请求线程里手动取；代理只是把「每次按当前请求取」声明式化。

**代价**：

- `TARGET_CLASS` 用 CGLIB 生成子类。`final` 类直接起不来；我在 Boot 4.1.1 上把 `RequestBean` 改成 `final`，启动报 `Cannot subclass final class ...RequestBean`。
- `final` 方法不会被代理拦截，调用会落到代理对象自身，而不是当前请求的真实对象；所以别在 scoped bean 的对外方法上加 `final`。
- 每次方法调用多一次作用域查找和一层间接调用。只在边界用，不要给所有 bean 都加代理。
- 在请求之外调用代理（比如启动阶段、没有请求的线程），仍然会报 `Scope 'request' is not active`。代理不是「把 request 变成全局」。

`ScopedProxyMode.INTERFACES` 用 JDK 动态代理，只代理接口方法；类没有接口时只能用 `TARGET_CLASS`。`@RequestScope` 默认 `TARGET_CLASS`，所以类能被 CGLIB 子类化是前提。

## 还差的

- 没在 `kill -9` 或断电下验证销毁回调。这是 JVM 进程被杀、代码没机会执行的边界，不是本文能补的实验。
- 没跑 `session` 的过期销毁：需要真实容器加会话超时；表里的结论来自 `ServletRequestAttributes.registerSessionDestructionCallback` 把回调挂成 `HttpSessionBindingListener` 这条源码路径。
- 没跑 `application` / `websocket` 的完整关闭流程：`application` 按 `ServletContextScope` 的 Javadoc，`websocket` 按 `SimpSessionScope` 和 `WebSocketMessageBrokerConfigurationSupport` 的源码说明；这两项没有端到端输出。
- `@WebSocketScope` 只在 Spring 7.0.9 源码里确认了 `@since 7.0` 和默认 `TARGET_CLASS`；没有在 Boot 4.1.1 或 3.5.6 上跑 WebSocket 会话。
