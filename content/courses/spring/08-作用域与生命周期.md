# 08 · 作用域与生命周期

## 这一课你要会

- 说清单例、原型、请求、会话四种作用域各在什么时候造一个对象；
- 用 `@PostConstruct` / `@PreDestroy`（或两个接口）挂初始化和销毁逻辑；
- 知道销毁回调是**逆序**的，以及为什么必须是逆序；
- 判断"单例里放了可变状态"会不会出问题。

## 为什么

单例是默认，也是最容易被误用的默认。

一个对象被整个应用共享，意味着它的每个可变字段都是**所有请求共享的**。放一个 `currentUser` 进去，第一个请求刚设置好，第二个请求就把它覆盖了——这类 bug 极难复现，因为它依赖并发时序。

作用域就是回答这个问题：**这个对象该活多久、该被几个请求共用**。生命周期回调则回答另一个问题：**它活着的这一段里，什么时候该做准备、什么时候该收尾**。

| 作用域 | 什么时候造 | 谁拿到的是一样东西 | 典型用途 |
| --- | --- | --- | --- |
| `singleton` | 启动时造一次（默认） | 全应用共享一个 | 无状态的 Service、配置、连接池 |
| `prototype` | 每次 `getBean` 都新造 | 谁要谁一个新的 | 有状态的临时对象、Builder |
| `request` | 每个 HTTP 请求造一个 | 同一个请求内共享 | 当前请求上下文（用户、traceId） |
| `session` | 每个会话造一个 | 同一个用户会话内共享 | 购物车（本项目不用，服务端无状态） |

判据只有一句：**这个对象里有可变状态吗？有就往下走一档。**

### 生命周期回调的顺序

一个 Bean 从生到死：

```text
构造器
  → 依赖注入（构造器参数已在构造器里完成；字段/setter 注入在这一步）
  → @PostConstruct（或 InitializingBean.afterPropertiesSet）
  → 使用
  → @PreDestroy（或 DisposableBean.destroy）
```

两个注意点：

- **`@PostConstruct` 在注入之后**。用它读依赖是安全的；在构造器里读字段注入的依赖则可能还是 null（这又是构造器注入的一个好处）。
- **`@PreDestroy` 只在容器正常关闭时被调用**。`kill -9`、断电、容器被强杀——都不会调用。所以它只能用来"尽量收尾"（关连接、刷缓冲），不能用来做"必须发生"的业务（比如落库）。

### 手写一遍作用域与销毁顺序

<!-- run -->
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class Main {

    interface InitializingBean {
        void afterCreate();
    }

    interface DisposableBean {
        void destroy();
    }

    static final List<String> events = new ArrayList<>();

    static class ServiceA implements InitializingBean, DisposableBean {
        public void afterCreate() {
            events.add("create-a");
        }

        public void destroy() {
            events.add("destroy-a");
        }
    }

    static class ServiceB implements InitializingBean, DisposableBean {
        public void afterCreate() {
            events.add("create-b");
        }

        public void destroy() {
            events.add("destroy-b");
        }
    }

    static class Task {
    }

    static final class Container {
        private final Map<Class<?>, Object> singletons = new LinkedHashMap<>();
        private final List<Class<?>> creationOrder = new ArrayList<>();
        private final List<Class<?>> prototypes = new ArrayList<>();

        void singleton(Class<?>... types) {
            for (Class<?> type : types) {
                singletons.put(type, instantiate(type));
                creationOrder.add(type);
            }
        }

        void prototype(Class<?>... types) {
            for (Class<?> type : types) {
                prototypes.add(type);
            }
        }

        private Object instantiate(Class<?> type) {
            try {
                Object made = type.getDeclaredConstructor().newInstance();
                if (made instanceof InitializingBean bean) {
                    bean.afterCreate();
                }
                return made;
            } catch (ReflectiveOperationException error) {
                throw new IllegalStateException(error);
            }
        }

        Object get(Class<?> type) {
            Object singleton = singletons.get(type);
            if (singleton != null) {
                return singleton;
            }
            if (prototypes.contains(type)) {
                return instantiate(type);
            }
            throw new IllegalStateException("没有注册: " + type.getSimpleName());
        }

        void close() {
            for (int i = creationOrder.size() - 1; i >= 0; i--) {
                Object instance = singletons.get(creationOrder.get(i));
                if (instance instanceof DisposableBean bean) {
                    bean.destroy();
                }
            }
        }
    }

    public static void main(String[] args) {
        Container container = new Container();
        container.singleton(ServiceA.class, ServiceB.class);
        container.prototype(Task.class);

        System.out.println("单例两次同一个: " + (container.get(ServiceA.class) == container.get(ServiceA.class)));
        System.out.println("原型两次不同: " + (container.get(Task.class) == container.get(Task.class)));

        container.close();
        System.out.println(events);
    }
}
```
```text
单例两次同一个: true
原型两次不同: false
[create-a, create-b, destroy-b, destroy-a]
```

最后一行是全课重点：**销毁是创建的逆序**。

### 为什么销毁必须逆序

考虑依赖关系：`ServiceB` 依赖 `ServiceA`。关闭时如果先销毁 `ServiceB`，它还有可能在使用 `ServiceA`；反过来先销毁 `ServiceA`，`ServiceB` 就可能在收尾时访问一个已经关掉的对象（连接池已关闭、`ExecutorService` 已 shutdown）。

逆序销毁保证了"被依赖者活得更久"。这条规则在所有资源管理体系里都一样——栈、`try-with-resources`、`useEffect` 的清理函数。

### 单例的可变状态为什么会咬人

```java
@Service
public class CurrentUserHolder {
    private String userId;                 // 危险：共享的可变字段

    public void set(String userId) {
        this.userId = userId;
    }

    public String get() {
        return userId;
    }
}
```

这是**用一个单例存"当前请求的身份"**。它在单线程测试里永远是对的，在并发下会随机串号。正确的替代是：

- 把身份作为方法参数一路传下去（最省事，最明确）；
- 或者用 `request` 作用域的 Bean（每个请求一个实例）；
- 或者用 `ThreadLocal`（本项目避免，线程池复用线程时容易泄漏）。

判断标准很朴素：**这个字段的值会不会因请求而不同？** 会，就不该是单例的字段。

### 原型注入进单例的陷阱

```java
@Component
@Scope("prototype")
public class ReportBuilder { }

@Service
public class ReportService {
    private final ReportBuilder builder;      // 只有启动时注入了一次

    public ReportService(ReportBuilder builder) {
        this.builder = builder;
    }
}
```

`ReportService` 是单例，它的构造器只跑一次，所以 `builder` 也只有那一个原型实例——**原型在这里退化成了单例**。

要每次都拿新的，得用 `ObjectProvider<ReportBuilder>`：

```java
public ReportService(ObjectProvider<ReportBuilder> builders) {
    this.builders = builders;
}

public Report build() {
    ReportBuilder builder = builders.getObject();   // 每次都是新的
    ...
}
```

`ObjectProvider` 的含义就是"我要的时候再给你找"，这也是它解决懒加载与可选依赖的原因。

## 常见误区

### 误区：`@PostConstruct` 和构造器差不多，放哪都行

**你以为**：都是初始化，写在构造器里更直接。
**其实**：构造器执行时，字段注入与 setter 注入**还没发生**。在构造器里读注入的依赖会拿到 `null`（构造器注入的依赖除外，它在参数里）。`@PostConstruct` 才是"所有注入都完成"的第一个时机。
**怎么验证**：在构造器里和 `@PostConstruct` 里各打一次依赖，对比是否有一边是 null。

### 误区：`session` 作用域省事，放购物车正好

**你以为**：会话作用域天然隔离用户。
**其实**：它要求服务端记住会话。本项目是**无状态**部署（JWT + 无 Sticky Session），多个实例之间不共享会话内存，用 `session` 作用域会让用户在换实例后"购物车变空"。要用就必须引入共享存储（Redis），那是另一个成本。
**怎么验证**：在集群里部署两个实例，同一会话连打两次，看数据是否一致。

### 误区：单例一定比原型省资源，所以都该是单例

**你以为**：越少对象越好。
**其实**：原型的作用是**隔离状态**。为了省几个对象把一个有状态的构建器做成单例，换来的是并发 bug。对象本身很轻，"状态被共享"才是贵的那个东西。

## 小结

作用域回答"活多久、被谁共享"，判据是"有没有可变状态"。生命周期回调里，`@PostConstruct` 在注入之后、`@PreDestroy` 只在正常关闭时执行，销毁必须逆序。单例里放请求相关的可变状态是最高频的并发 bug 来源；原型注入进单例会退化成单例，要用 `ObjectProvider`。
