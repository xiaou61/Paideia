# 19 · 切片测试

## 同一个 Controller，两个注解，7.05 秒和 6.57 秒

Temurin 25.0.4 + Maven 3.9.0 + Spring Boot 4.1.1（Spring Framework 7.0.9），Windows，`%TEMP%` 下 6 个主类的最小工程。两个测试类各含一个完全相同的「找不到返回 404」用例，一条 Maven 命令、`reuseForks=false` 让它们各起一个 JVM：

```text
$ mvn -B -Dtest=FullOnlyTest,SliceOnlyTest -DforkCount=1 -DreuseForks=false test
...
Started FullOnlyTest in 7.048 seconds
Tests run: 1, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 8.475 s
...
Started SliceOnlyTest in 6.571 seconds
Tests run: 1, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 8.159 s
...
Total time: 30.460 s
```

`FullOnlyTest` 是 `@SpringBootTest`（默认 `MOCK`），`SliceOnlyTest` 是 `@WebMvcTest(BookController.class)`。上下文启动只快了 7%，整个测试类只快 3.7%，不是十倍。日志里两次 `Started` 的 PID 是 108568 和 81808，确实是两个 JVM。

我原来也以为切掉数据库和 Service 会立竿见影。实际两个上下文都在 6–7 秒；同一个 JVM 的第二个上下文只要 0.35–0.55 秒，说明大头是每个 JVM 的第一次加载，不是注解本身。

差别不在注解，在**全量上下文里到底装了什么**。本项目 `paideia-app` 2026-10-21 的实测：31 个 `@SpringBootTest` 类产生 14 个上下文，每个 2–22 秒，累计约 79 秒；同一轮全量里，纯单测 317 条约 20 秒，集成测试 226 条约 220 秒。全量上下文连 MySQL、跑迁移、装全部 Bean；Controller 切片把 DB、迁移、远程客户端绕开，mapper 切片只装 DB 和 MyBatis，差距才出来。

所以这篇不卖「切片一定快十倍」。先看你的全量上下文里有什么，再决定切哪一层。

## 慢的不是 Tomcat，是整个 ApplicationContext

先把这个最常见的归因改准。下面两个探针都在 Boot 4.1.1 上跑：

```java
@SpringBootTest
class MockEnvironmentProbeTest {

    @Autowired
    private ServletContext servletContext;

    @Autowired
    private Environment environment;

    @Test
    void probe() {
        System.out.println(servletContext.getClass().getName());
        System.out.println(environment.getProperty("local.server.port"));
    }
}
```

输出：

```text
org.springframework.boot.test.mock.web.SpringBootMockServletContext
null
```

换成 `@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)`，同一个探针：

```text
org.apache.catalina.core.ApplicationContextFacade
23104
```

日志里还会多一行 `Tomcat started on port 23104 (http)`。端口每次不同，重点是它是真的。

`@SpringBootTest` 默认 `webEnvironment = MOCK`。它建的是 mock servlet 环境，不启动 Tomcat，也不监听端口。只有 `RANDOM_PORT` / `DEFINED_PORT` 才真起容器。所以「`@SpringBootTest` 慢是因为起 Tomcat」这句话是错的；慢的原因是加载整个 `ApplicationContext`：组件扫描、自动配置、数据源、迁移、缓存预热、远程客户端初始化。Tomcat 只是 `RANDOM_PORT` / `DEFINED_PORT` 时额外加的那一段。

如果全量上下文里只有几个 Bean，它热起来也不慢；慢的是你装进去的东西。

## 纯单测：连 Spring 都不需要

还是 `BookService`。它的依赖从构造器进来，所以它可以是一个普通 Java 对象：

<!-- run -->
```java
public class Main {

    record Book(long id, String title) {
    }

    interface BookRepository {
        Book find(long id);
    }

    static class BookService {
        private final BookRepository repository;

        BookService(BookRepository repository) {
            this.repository = repository;
        }

        Book find(long id) {
            return repository.find(id);
        }
    }

    public static void main(String[] args) {
        BookService service = new BookService(
                id -> id == 1 ? new Book(1, "深入理解 Java 虚拟机") : null);

        System.out.println(service.find(1).title());
        System.out.println(service.find(2));
    }
}
```
```text
深入理解 Java 虚拟机
null
```

这段没有 JUnit，但「给定输入、观察输出」就是单测的内核。写成 JUnit 5：

```java
class BookServiceTest {

    @Test
    void 找不到时返回 null() {
        BookService service = new BookService(
                id -> id == 1 ? new Book(1, "深入理解 Java 虚拟机") : null);

        assertThat(service.find(1).title()).isEqualTo("深入理解 Java 虚拟机");
        assertThat(service.find(2)).isNull();
    }
}
```

没有 `@SpringBootTest`，没有 Mockito，没有容器。判断标准很直接：**如果一个类的依赖都能作为构造参数传进来，它就不需要容器**。这也是第 7 课推荐构造器注入的理由之一：它直接决定了这类测试能不能写。

## 一张表看清五种测试装了什么

| 注解 | 加载什么 | 不加载什么 | 什么时候用 |
| --- | --- | --- | --- |
| 无注解（纯单测） | 只有你 `new` 出来的对象 | Spring 容器、数据源、Web 层 | 业务计算、分支、边界 |
| `@WebMvcTest(X.class)` | MVC 自动配置 + 指定 Controller、`@ControllerAdvice`、`Filter`、`HandlerInterceptor`、`Converter` 等 Web 组件 | `@Service`、`@Repository`、普通 `@Component`、数据源 | Controller 的协议契约 |
| `@MybatisTest` | MyBatis + 一个 DataSource；默认把 DataSource 换成内嵌库 | Controller、Service、完整应用配置；普通配置下也不连你的 MySQL | mapper 的 SQL 与映射（要真库得额外配置） |
| `@SpringBootTest`（默认 MOCK） | 整个 `@SpringBootApplication` 上下文 | 真实 servlet 容器与端口 | 跨层装配、整条链路 |
| `@SpringBootTest(RANDOM_PORT)` | 整个上下文 + 真实内嵌容器 | 没有可省的；它装全量并起容器 | 需要真实 HTTP/端口、过滤器、序列化全链路 |

这张表只回答装载范围，不回答速度。速度看你省掉了多少真实工作，不看你用了哪个注解。

## @WebMvcTest 只装 Web 层

Controller 的依赖是 `BookService`，而 `@WebMvcTest` 不扫描 `@Service`，所以必须补替身：

```java
@WebMvcTest(BookController.class)
class BookControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private BookService service;

    @Test
    void 找不到时返回 404() throws Exception {
        given(service.find(9L)).willReturn(null);

        mockMvc.perform(get("/api/books/9"))
                .andExpect(status().isNotFound());
    }
}
```

`MockMvc` 不发真实网络请求：它把请求交给 DispatcherServlet 的同一套分发逻辑，但不监听端口。所以断言快，也不占端口。

怎么确认它真的只装了 Web 层？在测试里注入 `ApplicationContext`，打印两类 Bean 的数量：

```java
System.out.println(context.getBeanNamesForType(BookRepository.class).length);
System.out.println(context.getBeanNamesForType(BookController.class).length);
```

我这里是 `0` 和 `1`：Controller 在，Repository 不在。Service 是我用 `@MockitoBean` 补的替身，不是扫描出来的。

**包名和依赖在 Boot 3.5.6 与 4.1.1 之间变了。** Boot 3.5.6 用：

```java
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
```

`spring-boot-starter-test` 已经带 `spring-boot-test-autoconfigure`，不用额外加依赖。

Boot 4.1.1 改成：

```java
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
```

并且 `spring-boot-starter-test` 不再带 `@WebMvcTest`（它搬到了 `spring-boot-webmvc-test`），要加这个测试依赖：

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-webmvc-test</artifactId>
  <scope>test</scope>
</dependency>
```

我第一版照抄旧包名，编译报的就是 `package org.springframework.boot.test.autoconfigure.web.servlet does not exist`。这不是「注解没了」，是包名和测试依赖都换了。

## Controller 只断言协议层

在 `@WebMvcTest` 里断言业务结果，是很容易写出来、但没什么价值的一种测试：

```java
given(service.find(1L)).willReturn(new Book(1L, "深入理解 Java 虚拟机"));

mockMvc.perform(get("/api/books/1"))
        .andExpect(jsonPath("$.title").value("深入理解 Java 虚拟机"));
```

`service` 是替身，返回值是你自己给的。上面这条断言真正验证的是「你给 mock 的返回值有没有被序列化出来」，不是「业务算得对不对」。业务正确性应该由 `BookServiceTest` 那种纯单测保证。

Controller 该断言的是协议层：

```java
given(service.find(1L)).willReturn(new Book(1L, "深入理解 Java 虚拟机"));

mockMvc.perform(get("/api/books/1"))
        .andExpect(status().isOk())
        .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
        .andExpect(jsonPath("$.id").value(1))
        .andExpect(jsonPath("$.title").isString());

verify(service).find(1L);
```

状态码、Content-Type、字段形状、参数有没有正确传给 Service，这些才是 Controller 的职责。序列化格式（字段名、日期格式、null 是否省略）也算协议层契约，可以在切片里断言；业务计算不要在这里重复测。

## @MybatisTest 默认连的不是 MySQL

`@MybatisTest` 不是 Spring Boot 自带的，来自 `mybatis-spring-boot-starter-test`。本项目 01 课的 pom 里没有这个依赖，照抄会直接编译失败：

```text
package org.mybatis.spring.boot.test.autoconfigure does not exist
```

Boot 4.1 要加：

```xml
<dependency>
  <groupId>org.mybatis.spring.boot</groupId>
  <artifactId>mybatis-spring-boot-starter-test</artifactId>
  <version>4.1.0</version>
  <scope>test</scope>
</dependency>
```

Boot 3.5.6 用 3.0.x（3.0.5 是当前该线版本），4.1.0 对应 Boot 4.1。版本不要和主 starter 差太远。我只在 4.1.0 上跑了这套。

更关键的是默认行为：**即使 `application.properties` 里写着 MySQL，它也会把 DataSource 换成内嵌库。** 我的日志：

```text
Replacing 'dataSource' DataSource bean with embedded version
Starting embedded database: url='jdbc:h2:mem:...;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=false'
PROBE product=H2
```

这里有个细节要纠正：很多文章写「默认 `replace = ANY`」。Boot 3.5.6 和 4.1.x 的 `@AutoConfigureTestDatabase.replace()` 默认值其实是 `NON_TEST`，不是 `ANY`。但对普通 MySQL 配置，`NON_TEST` 仍然判定为可替换，结果一样：默认不会连你配置的 MySQL。别背默认值，记行为。

要连真实 MySQL，`@MybatisTest` 本身没有 `replace()` 属性。写 `@MybatisTest(replace = NONE)` 会编译失败：

```text
cannot find symbol
  symbol:   method replace()
  location: @interface org.mybatis.spring.boot.test.autoconfigure.MybatisTest
```

正确写法是外挂 `@AutoConfigureTestDatabase`：

```java
@MybatisTest
@AutoConfigureTestDatabase(replace = Replace.NONE)
class BookMapperTest {

    @Autowired
    private BookMapper mapper;

    @Test
    void 能查到造出来的书() {
        assertThat(mapper.titleOf(1)).isEqualTo("深入理解 Java 虚拟机");
    }
}
```

Boot 4.1 的 `Replace` 在 `org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase`；Boot 3.5.6 在 `org.springframework.boot.test.autoconfigure.jdbc`。包名不对，照样编译失败。

我一这么改，连接就从 H2 变成了配置里的 MySQL：本机 3306 上确实有 MySQL，故意写错口令时报 `Access denied for user ...`，说明请求已经打到 MySQL，而不是内嵌库。

本项目的规则是 mapper 验证走真实 MySQL（`scripts/test-db.sh`），所以默认替换成 H2 的 `@MybatisTest` 不能用。要么外挂 `@AutoConfigureTestDatabase(replace = Replace.NONE)` 并自己保证库和 schema，要么直接用 `@SpringBootTest` 走项目已有的测试库。我更倾向后者：`@MybatisTest` 只装 DataSource + MyBatis，不负责你项目的完整迁移/种子编排，和线上 schema 差得远。

另外 `@MybatisTest` 默认带 `@Transactional`，测试方法结束回滚。这对真实 MySQL 也一样，但 DDL 不在事务里，别拿它测迁移。

## context cache 按什么复用

Spring TestContext 把 `MergedContextConfiguration` 当缓存 key。这个 key 包含：

- 配置类、XML locations、组件扫描入口；
- active profiles；
- 属性源：`@TestPropertySource`、`@SpringBootTest(properties = ...)`；
- context customizers：`@DynamicPropertySource`、`@MockitoBean` / `@MockitoSpyBean` 的 override 集合；
- 测试自动配置：`@AutoConfigureMockMvc`、`@AutoConfigureTestDatabase`；
- `@SpringBootTest` 的 `webEnvironment`；
- 父上下文、context initializers。

它不包括测试类名，也不包括方法名。两个类只要这些配置相同，就复用同一个上下文；任何一项不同，就新建。

我做了 4 个 `@WebMvcTest` 类来验证：

- A、B 注解完全一样；
- C 多 mock 一个 `AuditInterceptor`；
- D 多一个 `@TestPropertySource(properties = "cache.probe=second")`。

开启缓存日志：

```text
logging.level.org.springframework.test.context.cache=DEBUG
```

跑完 4 个类，最后的统计：

```text
Spring test ApplicationContext cache statistics: [DefaultContextCache@..., size = 3, maxSize = 32, contextUsageCount = 1, parentContextCount = 0, hitCount = 50, missCount = 3, failureCount = 0]
```

4 个类只有 3 个上下文：A/B 共用一个（B 没有新的 `Started ... in` 行），C 因为 mock 组合不同新建，D 因为属性源不同新建。`missCount = 3`，正好对应三次新建。

这组实验说明的是 override 集合会进 cache key。`@MockitoBean` 的真实作用是替代已移除的 `@MockBean`，**不是**让不同 mock 组合复用；`@MockBean` 也一样，旧注解同样通过 `MockitoContextCustomizer` 参与缓存 key。不同 mock 组合从来就是不同上下文，换注解不会改变这件事。

什么时候会新建上下文：

- `@MockitoBean` / `@MockitoSpyBean` 的集合变了；
- `@TestPropertySource`、`properties`、`@ActiveProfiles` 变了；
- `webEnvironment` 从 MOCK 换成 RANDOM_PORT；
- 加了或去掉 `@AutoConfigureMockMvc`、`@AutoConfigureTestDatabase`；
- 换了一个嵌套 `@TestConfiguration` 或 `@SpringBootTest(classes = ...)`；
- `@DirtiesContext` 主动关闭并移除当前上下文。

当前实现里缓存上限是 32（日志里的 `maxSize`），满了按 LRU 淘汰。

为什么测试之间能复用：同一个 JVM、同一个 Spring TestContext cache。Maven Surefire 默认 `reuseForks=true`，类之间可以复用；你单跑一个 `mvn`，或者把 `reuseForks` 设成 `false`，就是新 JVM，缓存从零开始。这也解释了开头那对冷启动数字：两个类各起一个 JVM，都在付第一次加载 Spring 的钱。

怎么自己验证：加上那行 DEBUG，先跑 A/B，看 `missCount` 不再增加、B 没有新的 `Started` 行；再给 C 多写一个 `@MockitoBean`，看 `missCount` 加一。

## @MockBean 在 Boot 4 里没了

Boot 3.5.6 的 `@MockBean` 还在，但 class 文件上写着 `@Deprecated(since = "3.4.0", forRemoval = true)`；Boot 4.1.1 的 `spring-boot-test` jar 里已经没有 `MockBean.class`。新代码用 Spring Framework 6.2（Boot 3.4+）提供的：

```java
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.context.bean.override.mockito.MockitoSpyBean;
```

换注解不是缓存优化。`@MockBean` 和 `@MockitoBean` 都是 context customizer，override 集合都进 cache key；不同 mock 组合照样各建上下文。新注解的收益是替代已移除的 API，不是减少上下文数量。

看到旧教程写 `@MockBean`：在 3.5.6 上还能编译，但注解已标记 deprecated（IDE/编译器可能提示）；在 4.x 上直接编译失败。别照抄。

验证方式：拿 3.5.6 的 `spring-boot-test` jar 跑 `jar tf` 能看到 `MockBean.class`，`javap -v` 里是 `forRemoval=true`；换成 4.1.1 的 jar，同一个 `jar tf` 没有这个类。

## 测试金字塔与运行策略

```text
        少量 端到端（真浏览器）
      一些 集成（@SpringBootTest + 真库）
    较多 切片（@WebMvcTest / @MybatisTest）
  最多 纯单测（无容器）
```

这个仓库 2026-10-21 的实测：纯单测 317 条约 20 秒；集成 226 条约 220 秒；31 个 `@SpringBootTest` 类只产生 14 个上下文，每个 2–22 秒。所以内环先跑纯单测和受影响的切片；外环按端、按文件跑 e2e；全量只在交接、改跨模块契约或 schema、发版前跑。

任何碰数据库的验证走 `scripts/test-db.sh`，不要直接 `mvn test` 或共用测试库。共用库上的绿可能是别人导入的数据刚好满足了你的断言，红可能是别人正在删表。测试通过的前提是它控制了自己的输入。

不要把 `@SpringBootTest` 当默认。它是最后一道，不是第一道。

## 还差的

- 没在真实的 `paideia-app` 上逐个测 `@WebMvcTest`。文中的切片耗时来自 6 个主类的最小工程，真实项目还受 Bean 数量、数据库和远程客户端影响。
- `@MybatisTest` 只用 H2 和一个故意配错的 MySQL 连接验证了替换行为；没在 MySQL 8 + 本项目完整迁移和种子数据下跑 mapper 切片。
- 没覆盖 `@DataJpaTest`、`@JsonTest`、`@RestClientTest`、WebFlux，也没测并行测试和 `@DirtiesContext` 对缓存的具体影响。
- 耗时是 Windows + JDK 25 + Maven 3.9 的本机数字；Linux CI 的冷启动和文件系统不同，不能直接当 SLA。
