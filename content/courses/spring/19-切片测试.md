# 19 · 切片测试

## 这一课你要会

- 说清"切片测试"切的是什么，以及它为什么比 `@SpringBootTest` 快一个数量级；
- 分清 `@WebMvcTest`、`@MybatisTest`、`@SpringBootTest` 各自装了哪些东西；
- 知道 Boot 4 里 `@MockBean` / `@SpyBean` 已被移除，替换成 `@MockitoBean` / `@MockitoSpyBean`；
- 判断一个测试该不该起容器。

## 为什么

一个 `@SpringBootTest` 会启动整个容器：扫描所有 Bean、连数据库、跑迁移、起 Tomcat。一次几百毫秒到几秒。100 个测试就是几分钟。

更糟的是它**测得太宽**：一个纯计算方法的测试也顺带验证了数据库连得上——于是数据库一抖，这个测试就红了，而它本来和数据库毫无关系。

切片测试的思路是：**只装这一层需要的东西**。测 Controller 就只装 MVC 基础设施和这一个 Controller，Service 用替身；测 mapper 就只装数据源和 mapper，Controller 不装。

## 讲解

### 先看一个根本不需要容器的测试

因为第 7 课用了构造器注入，这个 Service 是一个**普通 Java 对象**：

<!-- run -->
```java
public class Main {

    static final class Book {
        final long id;
        final String title;

        Book(long id, String title) {
            this.id = id;
            this.title = title;
        }
    }

    interface BookRepo {
        Book find(long id);
    }

    static final class BookService {
        private final BookRepo repo;

        BookService(BookRepo repo) {
            this.repo = repo;
        }

        String titleOf(long id) {
            Book book = repo.find(id);
            return book == null ? "not found" : book.title;
        }
    }

    public static void main(String[] args) {
        // 替身：不连库、不起容器，一个 lambda 就是全部实现
        BookRepo fake = id -> id == 1 ? new Book(1, "深入理解 Java 虚拟机") : null;

        BookService service = new BookService(fake);
        System.out.println(service.titleOf(1));
        System.out.println(service.titleOf(2));
    }
}
```
```text
深入理解 Java 虚拟机
not found
```

这段代码没有任何测试框架，但它就是"一个测试"：给定输入，观察输出。**这就是单测能跑在毫秒级的原因**——它没有启动任何东西。

判断标准：**如果一个类的依赖都能作为构造参数传进来，它就不需要容器**。这也是第 7 课推荐构造器注入的最强理由——它直接决定了这类测试能不能写。

| 注解 | 装什么 | 不装什么 | 单个测试耗时量级 |
| --- | --- | --- | --- |
| 无注解（纯单测） | 什么都没有 | 全部 | 毫秒 |
| `@WebMvcTest(X.class)` | MVC 基础设施 + 指定 Controller | Service、mapper、数据源 | 几百毫秒 |
| `@MybatisTest` | 数据源 + mapper | Controller、Service、Web 层 | 几百毫秒（要连库） |
| `@SpringBootTest` | 全部 | 无 | 秒级 |

`@WebMvcTest` 里 Service 没装，所以必须用替身填上：

```java
@WebMvcTest(BookController.class)
class BookControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean                      // Boot 4：原来的 @MockBean 已移除
    private BookService service;

    @Test
    void 找不到时返回404() throws Exception {
        given(service.find(9L)).willReturn(null);

        mockMvc.perform(get("/api/books/9"))
                .andExpect(status().isNotFound());
    }
}
```

`MockMvc` 不发真实网络请求：它把请求交给 DispatcherServlet 的同一套分发逻辑，但**不监听端口**。所以断言快、也不占端口——并发跑多个测试模块时不会打架。

### 为什么 Boot 4 换掉了 `@MockBean`

`@MockBean` 在 Boot 3.4 被标记为废弃，Boot 4 移除。替代品是 Spring Framework 6.2 提供的 `@MockitoBean` / `@MockitoSpyBean`，来自 `org.springframework.test.context.bean.override.mockito` 包。

差别不只是改名：新注解把"替换哪个 Bean"做成了**上下文缓存的显式部分**。旧的 `@MockBean` 会导致"每个不同的 mock 组合都要新建一个上下文"，测试类一多就积累出几十个应用上下文，内存与时间都被吃掉。新注解复用已有的上下文。

所以看到旧教程写 `@MockBean` 时要知道：**在你的 Boot 4 项目里它不存在了**，编译直接失败。

### 三个容易写坏的测试

**一、在 `@WebMvcTest` 里断言业务结果。**

```java
mockMvc.perform(post("/api/transfer").content(json))
       .andExpect(jsonPath("$.balance").value(70));   // 依赖真实 Service
```

但 Service 是替身，它返回什么完全由你决定。这个断言实际在测"你的 mock 配置对不对"，而不是"业务对不对"。**Controller 的测试只该断言协议层**：状态码、响应结构、参数是否被正确传给 Service。

**二、在 `@MybatisTest` 里依赖库里的既有数据。**

```java
@Test
void 能查到第一本书() {
    assertThat(mapper.findAll()).isNotEmpty();      // 依赖库里有数据
}
```

在独占的空库上跑，这条必红。本项目对此有一整套纪律：测试库必须由 `scripts/test-db.sh` 每次分配一个独占库，测试自己在 `@BeforeEach` 里造数据。

**三、用 `@SpringBootTest` 测一个纯计算。**

```java
@SpringBootTest
class PriceCalculatorTest { }
```

它不需要任何 Bean，却要起整个容器。改成纯单测，从几秒降到毫秒。

### 测试金字塔与运行策略

```text
        少量 端到端（Playwright，真浏览器）
      一些 集成（@SpringBootTest，真库）
    大量 切片（@WebMvcTest / @MybatisTest）
  最多的 纯单测（无容器）
```

本项目的实践约定：

- **内环**只跑受影响的用例；
- **后端不跑全量**，切片提交跑"除集成模块外的全部单测" + "几条结构守卫"；
- **端到端**先选文件、`--grep` 或 `--last-failed`，不要默认全量；
- **任何碰数据库的验证都走 `scripts/test-db.sh`**，它每次分配独占库——直接连共用测试库会让并发会话互相删数据，造出"单类绿、全量红"的假故障。

最后一条值得展开：**假绿和假红一样危险**。共用库上的绿可能是别人导入的数据刚好满足了你的断言；共用库上的红可能是别人正在删表。所以"测试通过"这件事的前提是"这个测试真的控制了自己的输入"。

## 常见误区

### 误区：测试越多越好，全用 `@SpringBootTest` 最省心

**你以为**：一个注解搞定所有，不用想装什么。
**其实**：它慢、测得太宽、失败时定位困难（一个红灯可能是任何一层）。而且每个不同的 `@MockitoBean` 组合都会缓存一个上下文，几十个测试类就是几十个上下文常驻内存。
**怎么验证**：看一次全量测试的耗时分布，集成测试通常占 70% 以上。

### 误区：切片测试就不用连数据库

**你以为**：切片 = 全用替身。
**其实**：`@MybatisTest` 恰恰要连真库——它测的就是 SQL 与映射。**本项目明确禁止用 H2 替代 MySQL**，因为方言、函数、`ON DUPLICATE KEY UPDATE` 这些行为完全不同，H2 上绿了生产照样炸。
**怎么验证**：搜一下项目里有没有 H2 依赖。有就说明有人走了这条捷径。

### 误区：测试通过就说明功能对

**你以为**：绿灯等于正确。
**其实**：测试只能证明"你想到的那些情况是对的"。共用库上跑出来的绿还可能是别人的数据刚好满足了你的断言。
**怎么验证**：把一条测试在空库上单跑一次。红的话，说明它依赖了环境而不是自己的输入。

## 小结

切片测试 = 只装这一层需要的对象，缺的用替身补上。`@WebMvcTest` 装 MVC + 一个 Controller，`@MybatisTest` 装数据源 + mapper，`@SpringBootTest` 装全部。Boot 4 用 `@MockitoBean`，`@MockBean` 已不存在。测试要有价值，前提是它控制自己的输入。

最后一课：打出来的 jar 为什么起不来——六条最常见的报错各自在说什么。
