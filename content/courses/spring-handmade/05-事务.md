# 05 · 事务：快照、回滚与自调用

## 这一课你要会

- 用"快照 + 还原"实现回滚，并知道真实事务用的是数据库的 undo 日志；
- 说清为什么"异常被吞掉"就不回滚；
- 说清为什么"自调用"根本没有事务；
- 把四条断言（提交 / 回滚 / 吞异常 / 自调用）与真实 Spring 的行为一一对上。

## 为什么

这是最后一关，也是把前四关连起来的一关：容器把 `TxTemplate` 注入进 `AccountService`（第 1、2 关），事务边界是一条"模板"（第 3 关的思路：一张表 + 一个入口），而"自调用没有事务"正是第 4 关代理结论的直接推论。

四条断言里有一条特别值得看：**`catchInside()` 会保存 2 条**。这不是 bug，这就是 `@Transactional` 最常被误解的那个行为——回滚的判据是"异常有没有穿出事务边界"，不是"有没有发生过异常"。

## 讲解

### 你要交的东西

`Store` 与 `TxTemplate` 的骨架已经给出，你要补三个方法：`TxTemplate.run`、`AccountService` 的四个方法。

| 符号 | 语义 |
| --- | --- |
| `void run(Runnable action)` | `runs++`；拍快照；执行；抛 `RuntimeException` 时还原快照并继续往外抛 |
| `void ok()` | 包在 `tx.run` 里保存两条 |
| `void fail()` | 包在 `tx.run` 里保存一条，然后抛 `IllegalStateException` |
| `void catchInside()` | 包在 `tx.run` 里保存两条，中间抛出的异常在**内部**吞掉 |
| `void selfCall()` | **不经过** `tx.run`，直接保存两条 |

最后一条是这一关的考点：`selfCall()` 必须**不**包在事务里。如果你出于"保持一致"也把它包起来，第六条断言会红——而那个红是对的。

真实事务不用快照（把整个库复制一份太贵），用的是数据库的 undo/redo 日志：每条语句的反向操作都记着，回滚时逆序执行。但**语义完全一样**：把状态恢复到进入之前。

```java
    }
```


### 为什么"吞掉异常"就不回滚

`run` 里唯一的判断是 `catch (RuntimeException error)`。如果异常在 `action` 内部就被 catch 了，那么 `run` 看到的是"正常返回"——它凭什么回滚？

真实 Spring 完全一样：`@Transactional` 的实现是 `try { proceed(); } catch (...) { rollback(); }`。你吞掉异常，切面就认为成功。

### 为什么"自调用"根本没有事务

`selfCall()` 里直接保存两条，没有经过 `tx.run`——所以 `runs` 保持 0。

真实场景里它看起来是"标了 `@Transactional` 的方法被自己调用"，而代理没有介入（第 4 关）。本关把它简化成"直接不包模板"，是为了让你在断言里看见这个事实：**`runs` 是 0，不是 1**。

```java
import java.util.ArrayList;
import java.util.List;

public class Main {

    public static void main(String[] args) {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        AccountService service = new AccountService(store, tx);
        service.ok();
        System.out.println("保存了 " + store.saved().size() + " 条，事务开了 " + tx.runs() + " 次");
    }
}

class Store {

    private final List<String> saved = new ArrayList<>();

    List<String> saved() {
        return saved;
    }

    void add(String value) {
        saved.add(value);
    }

    List<String> snapshot() {
        return new ArrayList<>(saved);
    }

    void restore(List<String> snapshot) {
        saved.clear();
        saved.addAll(snapshot);
    }
}

class TxTemplate {

    private final Store store;
    private int runs;

    TxTemplate(Store store) {
        this.store = store;
    }

    void run(Runnable action) {
        runs++;
        List<String> snapshot = store.snapshot();
        try {
            action.run();
        } catch (RuntimeException error) {
            store.restore(snapshot);
            throw error;
        }
    }

    int runs() {
        return runs;
    }
}

class AccountService {

    private final Store store;
    private final TxTemplate tx;

    AccountService(Store store, TxTemplate tx) {
        this.store = store;
        this.tx = tx;
    }

    private void okBody() {
        store.add("A-30");
        store.add("B+30");
    }

    void ok() {
        tx.run(this::okBody);
    }

    void fail() {
        tx.run(() -> {
            store.add("A-30");
            throw new IllegalStateException("余额不足");
        });
    }

    void catchInside() {
        tx.run(() -> {
            store.add("A-30");
            try {
                throw new IllegalStateException("被吞掉");
            } catch (IllegalStateException ignored) {
                // 异常没有穿出事务边界
            }
            store.add("B+30");
        });
    }

    void selfCall() {
        okBody();
    }
}
```

</details>

### 四个容易卡住的地方

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 回滚断言红（残留 1 条） | 还原了快照但顺序反了，或先 `clear` 后忘记 `addAll` | 先 `clear` 再 `addAll(snapshot)` |
| 异常断言红 | `catch` 里把异常吞了没往外抛 | 还原后 `throw error;` |
| 自调用断言红（runs 是 1） | 把 `selfCall` 也包进了 `tx.run` | 它必须不包——这正是考点 |
| 正常路径 runs 是 0 | `runs++` 写在了 `action.run()` 之后，异常时没执行到 | 进方法第一行就 `runs++` |

## 常见误区

### 误区：加了 `@Transactional` 就一定回滚

**你以为**：注解是"保证"。
**其实**：它只是"在异常穿出边界时回滚"。三个前提：方法 public、调用经过代理、异常类型在回滚范围内（默认只算 `RuntimeException` 与 `Error`）。本关的 `catchInside` 与 `selfCall` 就是前两个前提不成立的演示。
**怎么验证**：把 `run` 的 `catch` 改成 `catch (Exception)`，看受检异常是否也能回滚。

### 误区：事务范围越大越安全

**你以为**：一个请求从头到尾包起来最保险。
**其实**：范围越大，连接被占越久、锁持有越久、回滚越贵。范围应刚好覆盖"要么都成、要么都不成"的那几步。本关的 `ok()` 只包了两条写操作，这就是合适的粒度。
**怎么验证**：在一个事务方法里加一次网络调用，想想这次请求平均占着连接多久。

### 误区：快照实现就是真实事务

**你以为**：本关学会了就等于会写事务管理器。
**其实**：本关只复现了**语义**（原子性）。真实事务还有隔离级别、锁、并发可见性、持久性，那些由数据库承担，应用层只是发 `BEGIN` / `COMMIT` / `ROLLBACK`。本关的价值是"知道边界在哪"，不是"会写数据库"。
**怎么验证**：想想两个并发事务同时扣同一个余额会发生什么——本关的快照实现完全没处理这种情况。

## 小结

事务是"快照 → 执行 → 异常时还原"。回滚的判据是异常有没有穿出边界，所以吞掉异常就不回滚；自调用不经过边界，所以根本没有事务。四条断言把这四件事变成可执行的事实。

五关到此结束。回头看：容器、作用域、路由、代理、事务——这五样凑起来，就是 Spring 里你会天天用到的那一半。剩下的细节（自动配置、切片测试、配置优先级）在 **Spring 从零开始** 的对应课时里。
