# 05 · 事务：快照、回滚与自调用

## 一笔转账，账上留了一行不该在的记录

对账时看到 `A-30` 与 `B+30` 两行都在账上，可当天的业务日志写着「对方账户已冻结，入账失败」。我第一个念头是「异常被外层 `catch` 吞了，所以回滚没触发」。把这笔业务改写成能独立跑的类，本机跑出来是这样：

<!-- run -->
```java
import java.util.ArrayList;
import java.util.List;

public class Main {

    public static void main(String[] args) {
        selfCall();
        throughOtherObject();
        escape();
    }

    static void selfCall() {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        new AccountService(store, tx).transferSelfCall();
        System.out.println("自调用：账上 " + store.saved() + "，事务 " + tx.runs() + " 次");
    }

    static void throughOtherObject() {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        new AccountService(store, tx).transferThroughOtherObject();
        System.out.println("走另一个对象：账上 " + store.saved() + "，事务 " + tx.runs() + " 次");
    }

    static void escape() {
        Store store = new Store();
        TxTemplate tx = new TxTemplate(store);
        try {
            new AccountService(store, tx).transferEscape();
        } catch (IllegalStateException error) {
            System.out.println("异常穿出边界：" + error.getMessage());
        }
        System.out.println("异常穿出边界：账上 " + store.saved() + "，事务 " + tx.runs() + " 次");
    }
}

class Store {

    private final List<String> saved = new ArrayList<>();

    List<String> saved() {
        return saved;
    }

    void add(String value) {
        saved.add(value);
    }

    List<String> snapshot() {
        return new ArrayList<>(saved);
    }

    void restore(List<String> snapshot) {
        saved.clear();
        saved.addAll(snapshot);
    }
}

class TxTemplate {

    private final Store store;
    private int runs;

    TxTemplate(Store store) {
        this.store = store;
    }

    void run(Runnable action) {
        runs++;
        List<String> snapshot = store.snapshot();
        try {
            action.run();
        } catch (RuntimeException error) {
            store.restore(snapshot);
            throw error;
        }
    }

    int runs() {
        return runs;
    }
}

class AccountService {

    private final Store store;
    private final TxTemplate tx;

    AccountService(Store store, TxTemplate tx) {
        this.store = store;
        this.tx = tx;
    }

    void transferSelfCall() {
        tx.run(() -> {
            store.add("A-30");
            try {
                bookIn();
            } catch (IllegalStateException error) {
                System.out.println("入账失败，外层记一笔日志：" + error.getMessage());
            }
        });
    }

    void transferThroughOtherObject() {
        tx.run(() -> {
            store.add("A-30");
            try {
                new LedgerBook(store, tx).bookIn();
            } catch (IllegalStateException error) {
                System.out.println("入账失败，外层记一笔日志：" + error.getMessage());
            }
        });
    }

    void transferEscape() {
        tx.run(() -> {
            store.add("A-30");
            bookIn();
        });
    }

    void bookIn() {
        store.add("B+30");
        throw new IllegalStateException("对方账户已冻结");
    }
}

class LedgerBook {

    private final Store store;
    private final TxTemplate tx;

    LedgerBook(Store store, TxTemplate tx) {
        this.store = store;
        this.tx = tx;
    }

    void bookIn() {
        tx.run(() -> {
            store.add("B+30");
            throw new IllegalStateException("对方账户已冻结");
        });
    }
}
```

```text
入账失败，外层记一笔日志：对方账户已冻结
自调用：账上 [A-30, B+30]，事务 1 次
入账失败，外层记一笔日志：对方账户已冻结
走另一个对象：账上 [A-30]，事务 2 次
异常穿出边界：对方账户已冻结
异常穿出边界：账上 []，事务 1 次
```

第二行才是病根：**事务 1 次**。`bookIn()` 头上是挂着事务边界的，可调用它的是 `this`，那一跳没经过模板，所以它一次事务都没开——不是「回滚没生效」，是「根本没有事务可回滚」。`B+30` 写进去之后没有谁负责擦掉，外层又决定把异常吞掉，这一行就留下了。

三组结果只差两个开关：**这一跳有没有进边界**、**异常有没有穿出边界**。下面几节分开说这两个开关，以及它们在真实 Spring 里各对应哪条规则。

## 边界只有一条：拍快照、执行、还原

第 4 关的结论是「代理只拦从外面进来的调用」。事务边界就挂在那条前后置通知上：进去之前记下状态，异常穿出就还原，正常返回就放行。手写出来只有十几行，就是上面程序里的 `TxTemplate`：

```java
class TxTemplate {

    private final Store store;
    private int runs;

    TxTemplate(Store store) {
        this.store = store;
    }

    void run(Runnable action) {
        runs++;
        List<String> snapshot = store.snapshot();
        try {
            action.run();
        } catch (RuntimeException error) {
            store.restore(snapshot);
            throw error;
        }
    }

    int runs() {
        return runs;
    }
}
```

四个位置都不能挪：

- **`runs++` 放在第一行。** 挪到 `action.run()` 后面，正常路径照样过，异常路径根本执行不到，计数器就少一次。
- **快照在 `try` 之前拍。** 拍进 `try` 里，抛出异常之前那句话已经改过状态，你拍到的是脏状态。
- **`restore` 之后必须 `throw error`。** 只还原不重抛，调用方会以为成功——`catchInside()` 就是这种形状，本关唯一一条「看着像 bug、其实是考点」的断言。
- **`catch` 的类型决定谁能触发回滚。** 这里写 `RuntimeException`，因为这恰好是框架的默认规则，下一节说细的。

`runs` 数的是「进出了几次边界」，不是「开了几个数据库事务」。这个区别在真实 Spring 里很要紧：默认传播行为 `REQUIRED` 下，内层方法加入的是外层那一个物理事务，进两次边界不等于两个事务。

上面那三次调用按「进没进边界」「吞没吞异常」两个开关排开，就是这样：

| 调用 | runs | 账上 | 为什么 |
| --- | --- | --- | --- |
| `this.bookIn()` | 1 | `[A-30, B+30]` | 那一跳没进模板，`B+30` 没人擦；外层吞掉异常就提交了 |
| `new LedgerBook(store, tx).bookIn()` | 2 | `[A-30]` | 内层有自己的快照，先把自己那次写入还原，外层再提交剩下的 |
| 不吞，直接抛出边界 | 1 | `[]` | 异常穿出最外层，快照把两次写入全部抹掉 |

第一行是这次对账的现场。第二行只改了一处调用——把 `this.bookIn()` 换成另一个对象上的 `bookIn()`，让那一跳真经过模板，`B+30` 就被内层擦掉了，`A-30` 按外层的意思提交。第三行是不吞异常：异常一路穿出最外层，账上空的，整笔转账当作没发生。

**第二行这个结果只在我们的玩具里成立。** `TxTemplate.run` 每次调用都独立拍一张快照，所以内层能单独还原——这是 savepoint（`PROPAGATION_NESTED`）的模型。真实 Spring 默认的 `REQUIRED` 不是这个形状：内层没有自己的回滚点，它只是把加入的那个事务标成 rollback-only。拿玩具的语义去推 `REQUIRED`，会推错，这正是下一节第 2 条。

## 真实 Spring 里，同一条边界有三处和手写的不一样

### 1. 回滚判据是「类型规则 + 是否穿出」，不是「有没有发生异常」

`@Transactional` 的 javadoc 原话是 roll back on `RuntimeException` and `Error` but not on checked exceptions：默认只对运行时异常和 `Error` 回滚，受检异常就算穿出边界，也照样提交。要改，逐方法用 `rollbackFor`；或者从 Spring 6.2 起在配置上全局改，`@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)`。

所以「吞掉异常就不回滚」这句要写准：**异常没穿出这条边界，这条边界就不回滚，边界内的写入照常提交**。这才是 `catchInside()` 存下两条的原因，不是什么「框架看不见被吃掉的异常」那种拟人说法。

### 2. 两层 REQUIRED 里，内层失败会让外层提交不了

内层方法走代理、传播行为是默认的 `REQUIRED` 时，它加入的是外层那一个物理事务。内层切面在异常穿出时做的是「把这个事务标成 rollback-only」，而不是自己回滚一段。外层就算 `catch` 住、正常返回，提交那一刻发现标志位，抛 `UnexpectedRollbackException`，数据不落。参考手册对这个设计的解释是：调用方不该被误导成「提交成功了」。

两个推论：

- 「加了注解、在外面 `catch` 住就当这步成功」是错的。要么让内层真开一个独立事务（`REQUIRES_NEW`），要么别吞。
- 我们的玩具在这里会给出不同答案（内层自己还原了），因为它模拟 savepoint，不是 `REQUIRED`。

### 3. 没有快照，只有 undo；redo 不负责回滚

MySQL 8.4 手册对 undo log record 的定义是：contains information about how to undo the latest change by a transaction to a clustered index record——记的是「怎么撤销某一行上的某次改动」，粒度是行，不是语句；另一件事是一致性读需要旧版本时，也从 undo 里取。

redo log 是另一套东西：记页的物理改动，用于崩溃恢复与持久性。回滚不走它。

这个设计差别决定成本落在哪：undo 让「回滚多贵」取决于这次改了多少行；我们的快照让「回滚多贵」取决于状态有多大。`Store` 里放几十个字符串时看不出区别，换成几十万行的表，两边就不是一个量级了——真实实现不复制整份状态，理由是成本该跟你改了多少成正比，而不是跟表多大成正比。

四条症状，四条排查入口：

| 症状 | 先看哪 |
| --- | --- |
| 报错的那一步留下了写入，业务却判定它失败 | 这一跳进没进边界：`runs` 涨了没有；`this.x()` 不涨 |
| 抛了异常，数据还在 | 异常穿出边界了吗：被 `catch` 了？是受检异常？配了 `noRollbackFor`？ |
| 一路顺利，提交时抛 `UnexpectedRollbackException` | 内层事务把标志位设成了 rollback-only：查内层那次失败是不是被外层吞了 |
| 注解写全了，`runs` 一直是 0 | 调用是不是从类外进来的，方法能不能被代理覆盖 |

## 两条和版本绑定的说法

**「必须 public」要拆开看。** 文档的说法是 `@Transactional` 通常用在 public 方法上；但从 Spring 6.0 起，基于类的代理（CGLIB，Spring Boot 默认用它）也支持 protected 与包可见方法。基于接口的代理则要求方法 public，并且声明在接口上。一直拦不到的是 private、static、final——代理没有覆盖它们的入口。

**「自调用没有事务」与版本无关。** 调用不经过代理就没有通知，没有通知就没有边界。文档给的唯一另一条路是 AspectJ 模式（`AdviceMode.ASPECTJ`），它织进字节码，所以能拦自调用；默认的代理模式不能。

两条合起来解释一个常见现场：注解齐全、`runs` 却一直是 0。先查调用是不是从类外来的，再查方法有没有被覆盖。

## 动手

## 还差的

- **没在真 Spring 上跑。** `UnexpectedRollbackException` 的抛出时机、默认回滚范围、6.0 的方法可见性，这三条是读 Spring Framework 的 javadoc 与参考手册得来的；本机只有 JDK，没有能跑的 Spring 工程，所以只验证了文档怎么说，没验证异常类什么时候真抛出来。
- **没碰并发。** 两个线程同时扣同一笔余额会怎样，这篇的快照实现完全没处理；隔离级别、锁等待、死锁，一个都没测。
- **没跑传播行为。** `REQUIRES_NEW` 真开第二个物理事务要多占一个连接，`NESTED` 靠 savepoint，两者的实际开销、以及连接池打满时的表现，都没测。
- **没量 undo 的成本。** 只引了手册对 undo 记录的描述，没在真库上测过一次大批量改动回滚要多久、undo 表空间涨多少。
- **版本边界。** 本机是 JDK 25.0.4（Temurin，Windows），课程门禁的沙箱基线是 Java 21。这段代码只用了 lambda 和集合，21 上应该一样，但没在 21 上跑过这一篇。
