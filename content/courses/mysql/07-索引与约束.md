# 07 · 主键、索引与唯一约束

## 这一课你要会

- 说清主键、唯一索引、普通索引三者各自约束什么；
- 知道索引加速的是"找行"，不是"取行"；
- 用 `EXPLAIN` 判断一句查询到底用没用上索引。

## 为什么

数据量小的时候，有没有索引几乎没差别——几千行全表扫一遍也就几毫秒。等数据涨到百万行，同一个查询从 5 毫秒变成 2 秒，这时候再补索引已经要停服了。

索引的正确时机是**建表的时候**：你知道哪些列会被用来查，就先把索引建上。

## 讲解

### 三个东西，三种约束

| 名字 | 约束 | 数量 | 能重复吗 |
| --- | --- | --- | --- |
| 主键（`PRIMARY KEY`） | 唯一 + 非空 | 每表一个 | 不能 |
| 唯一索引（`UNIQUE`） | 唯一，允许一个 `NULL` | 可以多个 | 不能 |
| 普通索引（`INDEX`） | 无约束，只为加速 | 可以多个 | 能 |

**主键是"这一行的身份"**，唯一索引是"这一列不许重复但可以空着"，普通索引只是"让查询快点"。

实践上一般这样做：

- 主键用 `id BIGINT AUTO_INCREMENT`，业务字段不做主键；
- 邮箱、手机号、订单号这类**天然唯一**的字段建唯一索引；
- 用在外键列与高频查询条件上的列建普通索引。

为什么不用业务字段当主键？因为业务字段会变（用户改邮箱）、可能很长（索引占空间）、可能不确定是否真唯一。用一个与业务无关的自增数字做主键，稳定性最好。

### 索引加速的是什么

先纠正一个直觉：索引**不会让"取一行数据"变快**——从磁盘读一行本来就是一样的成本。

索引加速的是**定位**：没有索引，要找 `email = 'b@x'` 得把每一行都读出来比对（全表扫描）；有索引，数据库在 B+ 树里查几次就能直接找到那一行的位置。

所以：

- **返回行数占全表比例很小**时，索引效果显著；
- **返回行数占全表比例很大**时（比如 `WHERE status = 'paid'` 而 90% 都是 paid），索引反而不如全表扫描——因为要随机读的位置太多，还不如顺序扫一遍。优化器会自己判断，这也是为什么有时候你建了索引它就是不用。

### 唯一索引的真实价值：拦住重复

比加速更重要的是**在数据库层拦住重复数据**。应用层做"先查一下有没有、没有再插"是有竞态的：两个请求同时查到"没有"，然后都插进去。

```sql
CREATE UNIQUE INDEX uk_users_email ON users (email);
```

有了这条约束，第二个 `INSERT` 会直接报 1062 错误，应用捕获即可。**把唯一性交给数据库，是并发下唯一可靠的做法。**

唯一索引对 `NULL` 的处理值得注意：**多个 `NULL` 是允许的**。因为 `NULL` 不等于 `NULL`，唯一约束只在"值相等"时触发。所以 `email UNIQUE` 上可以有很多行 email 为 `NULL` 的记录。如果要求"必须填且不重复"，得同时加 `NOT NULL`。

### 复合索引与最左前缀

一个索引可以包含多列：

```sql
CREATE INDEX idx_city_age ON users (city, age);
```

它按 **(city, age)** 这个组合排序，所以：

| 查询条件 | 能用上索引吗 |
| --- | --- |
| `WHERE city = '北京'` | 能（用到第一列） |
| `WHERE city = '北京' AND age = 20` | 能（两列都用） |
| `WHERE age = 20` | **不能**（跳过了第一列） |

这叫**最左前缀原则**：复合索引像一本先按城市、再按年龄排的电话簿。你只知道年龄、不知道城市，就没法用这本目录。

由此推出一条设计规则：**把选择性高（重复少）的列放在前面**。反过来说，如果两列都会单独被查，就该建两个索引，而不是一个复合索引。

### 什么时候索引会失效

这是实践里最有用的一节。以下几种写法会让索引用不上：

| 写法 | 为什么失效 | 怎么改 |
| --- | --- | --- |
| `WHERE YEAR(created_at) = 2026` | 函数包住了列 | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| `WHERE email LIKE '%@x.com'` | 以通配符开头 | 改成前缀匹配，或用全文索引 |
| `WHERE age + 1 = 21` | 运算包住了列 | `WHERE age = 20` |
| `WHERE code = 123`（code 是字符串） | 隐式类型转换 | `WHERE code = '123'` |
| `WHERE name = '张三' COLLATE ...` | 排序规则不一致 | 保持列与参数同一排序规则 |

**核心规律：只要列被"加工"过（函数、运算、类型转换），索引就用不上。** 因为索引里存的是原始值，加工后的值它不认识。

```sql
CREATE TABLE users (

  email VARCHAR(50),

CREATE INDEX idx_users_city_age ON users (city, age);

EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city = '北京' AND age = 20;
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE age = 20;
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city LIKE '北%';
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city LIKE '%京';
```
```text
found=1
EXPLAIN=-> Index lookup on users using idx_users_city_age (city='北京', age=20)  (cost=0.35 rows=1)

EXPLAIN=-> Filter: (users.age = 20)  (cost=0.55 rows=1)
    -> Table scan on users  (cost=0.55 rows=3)

EXPLAIN=-> Index range scan on users using idx_users_city_age, with index condition: (users.city like '北%')  (cost=1.16 rows=2)

EXPLAIN=-> Filter: (users.city like '%京')  (cost=0.55 rows=1)
    -> Table scan on users  (cost=0.55 rows=3)
```

四段 `EXPLAIN` 正好演示了四种情况：

1. **`Index lookup`**：两列都被索引用上，直接定位到那一行。
2. **`Table scan`**：只查 `age`，跳过了复合索引的第一列 `city`，索引作废。
3. **`Index range scan`**：`LIKE '北%'` 是前缀匹配，索引能用，范围扫描。
4. **`Table scan`**：`LIKE '%京'` 以通配符开头，索引用不上。

**看 `EXPLAIN` 的诀窍：找 `Index` 这个词有没有出现，以及它后面跟的索引名对不对。** 出现 `Table scan` 就是全表扫。

### 唯一索引拦住重复

```sql
INSERT INTO users (email, city, age) VALUES ('a@x','广州',25);
```

这条会失败，报 `Duplicate entry 'a@x' for key 'users.uk_users_email'`。应用层捕获这个错误，就能可靠地保证邮箱不重复——不需要先查再插。

## 常见误区

### 误区：索引越多越快

**你以为**：每个列都建上索引总没坏处。
**其实**：每个索引都要在写入时维护。插入、更新、删除都会变慢，占用的磁盘也更多。而且优化器要在多个索引之间选，索引太多反而可能选错。
**怎么验证**：对同一张表在加索引前后跑批量插入，对比耗时。

### 误区：建了索引查询就一定用它

**你以为**：`CREATE INDEX` 之后优化器会用。
**其实**：返回行数占比过高、索引列被函数包住、类型不匹配、复合索引违反最左前缀——任何一种都会让它用不上。
**怎么验证**：`EXPLAIN` 看 `key` 是不是那个索引名，`type` 是不是 `ALL`。

### 误区：唯一性靠"先查再插"就够了

**你以为**：应用里 `SELECT` 一下没有重复再 `INSERT` 就行。
**其实**：两个请求并发时，都会查到"没有"，然后都插进去。只有数据库的唯一索引能真正拦住。
**怎么验证**：并发发起两个相同邮箱的插入，看是否两个都成功。

## 小结

主键是行的身份（唯一且非空），唯一索引拦重复（允许多个 `NULL`），普通索引只为加速。索引加速的是定位而不是取行。复合索引遵守最左前缀，列被函数包住就失效。唯一性必须由数据库约束保证，应用层的"先查再插"在并发下不可靠。
