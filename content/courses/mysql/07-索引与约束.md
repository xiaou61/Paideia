# 07 · 主键、索引与唯一约束

## 同一张表，两句只差一个条件的 SQL

先看结果，再讲道理。一张三行的 `users`，上面建了一个复合索引 `(city, age)`：

```sql
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city = '北京' AND age = 20;
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE age = 20;
```

```text
-> Index lookup on users using idx_users_city_age (city='北京', age=20)  (cost=0.35 rows=1)
-> Filter: (users.age = 20)  (cost=0.55 rows=1)
    -> Table scan on users  (cost=0.55 rows=3)
```

第一句直接"在索引里定位到那一行"，第二句退化成"从头扫一遍"。区别只在：第一句给了 `city`，第二句没给。

**索引不是"给这一列加速"的开关，它对"什么形状的查询能用"有严格要求。** 这一课讲的就是这些形状。

## 主键、唯一索引、普通索引：约束强度不同

| 名字 | 约束 | 每表能有几个 | 值能重复吗 | `NULL` 怎么办 |
| --- | --- | --- | --- | --- |
| 主键（`PRIMARY KEY`） | 唯一 + 非空 | 一个 | 不能 | 不允许 `NULL` |
| 唯一索引（`UNIQUE`） | 唯一 | 多个 | 不能 | **允许多个 `NULL`** |
| 普通索引（`INDEX`） | 无约束，只加速 | 多个 | 能 | 随便 |

唯一索引那格值得单独说：**多个 `NULL` 是允许的**。因为唯一性检查是"值相等才拦"，而 `NULL = NULL` 在 SQL 里结果是 `UNKNOWN`，不算相等，所以它不触发冲突。

这个行为很实用：`email UNIQUE` 允许你放很多"还没填邮箱"的行（`NULL`），却不允许两个相同的邮箱。反过来说，**如果你要的是"必须有值且不重复"，得同时写 `NOT NULL`**——只写 `UNIQUE` 会留下一个"可以无限多个空值"的口子。

实践上一般这样分工：

- 主键用 `id BIGINT AUTO_INCREMENT`，业务字段不当主键；
- 邮箱、手机号、订单号这类天然唯一的字段建唯一索引；
- 高频查询条件和关联列建普通索引。

为什么不用业务字段当主键？它会变（用户改邮箱）、可能很长（占索引空间）、也未必真唯一。一个与业务无关的自增数字最稳。

## 索引加速的是定位，不是"取行"

从磁盘读一行的成本，有没有索引都一样。索引改变的是**找到那一行需要读多少东西**：

- 没有索引：`WHERE email = 'b@x'` 要把每一行读出来比对（全表扫描）；
- 有索引：在 B+ 树里走几层，直接拿到那一行的位置。

所以判断"该不该建索引"的关键是**返回行数占全表的比例**：

- 比例很小（比如按唯一邮箱查 1 行），索引几乎一定赢；
- 比例很大（比如 `WHERE status = 'paid'` 而九成行都是 paid），走索引要随机读一大堆页，反而不如顺序扫一遍。优化器会自己算这个账——这就是为什么你建了索引它却不用。

## 复合索引：列序决定谁能用

```sql
CREATE INDEX idx_city_age ON users (city, age);
```

它按 `(city, age)` 排序，等价于一本先按城市分组、组内再按年龄排的电话簿：

| 查询条件 | 能用上吗 | 为什么 |
| --- | --- | --- |
| `WHERE city = '北京'` | 能 | 用第一列定位到一段 |
| `WHERE city = '北京' AND age = 20` | 能 | 两列一起定位 |
| `WHERE city = '北京' AND age > 20` | 能 | 第一列等值 + 第二列范围 |
| `WHERE age = 20` | **不能** | 只看第二列，找不到起点 |

这就是**最左前缀原则**：复合索引必须从第一列开始、连续地提供条件，才能走索引。中间跳一列（`WHERE city = ... AND note = ...` 跳过 `age`）也一样废掉后面的列。

所以"复合索引的列序怎么定"要按查询来定，不是按"哪列更唯一"来定：

1. **等值条件多的列放前面**——它们先把范围收窄；
2. **范围条件（`>`、`BETWEEN`、`LIKE 'x%'`）放在等值列之后**——一旦进范围，后面的列就没法再精确定位了；
3. 如果两列**各自**都会单独出现在 `WHERE` 里，那就建两个索引，别指望一个复合索引覆盖两种查法。

（"选择性高的列放前面"这句话在单开索引时有意义——唯一性高的索引过滤效果最好；但把它当成复合索引列序的唯一规则，就会写出 `(city, age)` 这种和它自己矛盾的索引。）

## 唯一索引真正的价值：拦住重复

比加速更重要的用途是**在数据库层拦住重复数据**。

应用层那种"先 `SELECT` 查有没有，没有再 `INSERT`"在并发下不可靠：两个请求同时查到"没有"，然后都插进去，两张同样的邮箱。

```sql
CREATE UNIQUE INDEX uk_users_email ON users (email);
```

有了它，第二个 `INSERT` 会直接报 1062：

```text
ERROR 1062 (23000): Duplicate entry 'a@x' for key 'users.uk_users_email'
```

应用捕获这个错误，就能**可靠地**保证不重复——不需要先查。**把唯一性交给数据库，是并发下唯一可靠的做法。**

## 索引什么时候失效

| 写法 | 为什么用不上 | 怎么改 |
| --- | --- | --- |
| `WHERE YEAR(created_at) = 2026` | 函数包住了列 | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| `WHERE email LIKE '%@x.com'` | 以通配符开头，没有前缀可定位 | 改成前缀匹配（`LIKE 'x%'`），或上全文索引 |
| `WHERE age + 1 = 21` | 运算包住了列 | `WHERE age = 20` |
| `WHERE code = 123`（`code` 是字符串列） | 隐式类型转换把列变成了数值 | `WHERE code = '123'` |
| `WHERE id = '123'`（`id` 是整型） | 这个**能**用（转换发生在常量一侧），但也别依赖 | 参数类型与列一致 |

**核心规律：只要列被"加工"过（函数、运算、类型转换），索引就用不上**——B+ 树里存的是原始值，加工后的值它不认识。

注意表里最后一行：隐式转换的方向很关键。常量被转成列的类型时，索引照用；把**列**转成常量类型（`code` 是字符串却拿数字比）才会失效。

## 看 EXPLAIN 要看什么

`EXPLAIN FORMAT=TREE` 的输出读起来最直观：出现 `Index lookup` / `Index range scan` 就是走索引了，出现 `Table scan` 就是全表扫。

传统的表格格式多两列更有用：

```sql
EXPLAIN SELECT * FROM users WHERE age = 20;
```

```text
+----+-------------+-------+------------+------+---------------+------+---------+------+------+----------+-------------+
| id | select_type | table | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra       |
+----+-------------+-------+------------+------+---------------+------+---------+------+------+----------+-------------+
|  1 | SIMPLE      | users | NULL       | ALL  | NULL          | NULL | NULL    | NULL |    3 |   100.00 | Using where |
+----+-------------+-------+------------+------+---------------+------+---------+------+------+----------+-------------+
```

- `type = ALL`：全表扫描；
- `key = NULL`：一个索引都没用上；
- `possible_keys` 有值但 `key` 是 `NULL`：**索引存在，优化器主动放弃了它**——多半是它算出"扫表更便宜"。

最后这条要记牢：`possible_keys` 和 `key` 是两回事。前者回答"能用哪些"，后者回答"实际用了哪个"。

## 索引不是越多越好

每个索引都是一份额外的有序副本：写入时要维护它，占磁盘，优化器还要在多个索引之间挑（挑错了就是"该用没用"）。

所以索引该建在**真正会被查**的列上；没人查的列、区分度极低的列（比如"性别"），建了只是给写入加负担。

顺带修一个流传很广的说法："给大表补索引要停服"。**不用。** InnoDB 支持在线加二级索引：

```sql
ALTER TABLE orders ADD INDEX idx_created (created), ALGORITHM=INPLACE, LOCK=NONE;
```

`LOCK=NONE` 表示不阻塞读写。但这条要看清适用条件——**加/删二级索引可以在线做，改主键、改列类型、加 `NOT NULL` 列这类操作仍然会重建表**，那些才是真正要挑维护窗口的。

```sql
CREATE TABLE users (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(50),
  city  VARCHAR(20),
  age   INT,
  note  VARCHAR(20)
);
INSERT INTO users (email, city, age, note) VALUES
  ('a@x','北京',20,'n1'), ('b@x','上海',30,'n2'), ('c@x','北京',40,'n3');

CREATE UNIQUE INDEX uk_users_email ON users (email);
CREATE INDEX idx_users_city_age ON users (city, age);

SELECT COUNT(*) AS found FROM users WHERE email = 'b@x';

EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city = '北京' AND age = 20;
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE age = 20;
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city LIKE '北%';
EXPLAIN FORMAT=TREE SELECT * FROM users WHERE city LIKE '%京';
```
```text
found=1
EXPLAIN=-> Index lookup on users using idx_users_city_age (city='北京', age=20)  (cost=0.35 rows=1)

EXPLAIN=-> Filter: (users.age = 20)  (cost=0.55 rows=1)
    -> Table scan on users  (cost=0.55 rows=3)

EXPLAIN=-> Index range scan on users using idx_users_city_age, with index condition: (users.city like '北%')  (cost=1.16 rows=2)

EXPLAIN=-> Filter: (users.city like '%京')  (cost=0.55 rows=1)
    -> Table scan on users  (cost=0.55 rows=3)
```

四段正好对应四种情况：

1. `Index lookup`：两列一起对上，直接定位；
2. `Table scan`：只给 `age`，跳过第一列 `city`，复合索引作废；
3. `Index range scan`：`LIKE '北%'` 有前缀，能走范围扫描；
4. `Table scan`：`LIKE '%京'` 没有前缀，只能扫。

## 一句话

主键 = 唯一且非空的行身份；唯一索引 = 拦重复（允许多个 `NULL`，要禁止空值就加 `NOT NULL`）；普通索引 = 只为加速。索引加速的是**定位**，而它能不能被用上，取决于查询的形状：最左前缀、列不能被加工、返回比例不能太大。判断只有一条路——**看 `EXPLAIN` 的 `key` 和 `type`，别猜**。
