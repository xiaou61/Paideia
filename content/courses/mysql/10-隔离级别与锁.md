# 10 · 隔离级别与锁

## 这一课你要会

- 说清脏读、不可重复读、幻读各是什么现象；
- 知道 MySQL 默认的隔离级别，以及它用什么办法消除幻读；
- 判断什么时候需要 `FOR UPDATE`，什么时候不需要。

## 为什么

上一关讲的事务只解决了"自己不出错"。这一关讲的是**两个事务同时操作同一批数据**时会发生什么。

这是线上最难查的一类问题：本地单线程永远复现不出来，测试环境并发低也复现不出来，只有生产上量之后偶发一次，而且日志里看不出明显异常。

## 讲解

### 四种隔离级别，四个问题

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 |
| `READ COMMITTED` | 不会 | 可能 | 可能 |
| `REPEATABLE READ`（MySQL 默认） | 不会 | 不会 | InnoDB 用间隙锁基本消除 |
| `SERIALIZABLE` | 不会 | 不会 | 不会 |

三个问题的定义，都要用"同一个事务里读两次"来描述：

**脏读**：事务 A 读到了事务 B **还没提交**的改动。B 后来回滚了，A 读到的就是个从未真实存在过的值。

**不可重复读**：事务 A 第一次读 `v = 10`，事务 B 把它改成 11 并提交，A 再读发现变成 11。**同一行、同一个事务内，读两次结果不同。**

**幻读**：事务 A 第一次查 `WHERE city = '北京'` 得到 2 行，B 插入了一条北京记录并提交，A 再查变成 3 行。**行数变了，像凭空多出来一行。**

注意后两个的区别：不可重复读是"同一行变了"，幻读是"多了/少了行"。

### 为什么 REPEATABLE READ 下第二次读到的还是旧值

InnoDB 的实现方式是**快照读**（MVCC）：事务开始时（或第一次读时）拍一张快照，之后的普通 `SELECT` 都从快照读，看到的是那一时刻的数据。

所以：

```sql
BEGIN;
SELECT v FROM t WHERE id = 1;   -- 10
-- 另一个会话把 v 改成 11 并提交
SELECT v FROM t WHERE id = 1;   -- 还是 10（快照）
COMMIT;
```

这是**特性**不是 bug。它保证了"事务内两次读到的一样"。

但它带来一个常见困惑：**自己改过之后，读到的就是新值了**——因为快照读会看到自己未提交的改动。所以现象是"我能看到自己改的，看不到别人改的"。

### 快照读与当前读

这是理解 MySQL 锁的**关键分界线**：

| 类型 | 写法 | 读什么 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | 事务开始时的快照，**不加锁** |
| 当前读 | `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、所有 `UPDATE`/`DELETE` | 最新已提交的值，**加锁** |

由此推出几条很实用的结论：

1. **普通 `SELECT` 不加锁**，所以它不会阻塞别人，也不会被别人阻塞。它只是"看到旧值"。
2. **`UPDATE` 一定是当前读并加锁**。这也是为什么"先 `SELECT` 检查再 `UPDATE`"不可靠——中间这段时间没有锁保护。
3. 要"读出来就锁住，防止别人改"，必须写 `SELECT ... FOR UPDATE`。

### 什么时候需要 `FOR UPDATE`

典型场景：**读一个值、根据它做判断、然后更新它**，这三步必须原子。

```sql
-- 错：两步之间没有锁
SELECT qty FROM stock WHERE id = 1;      -- 读到 1
-- 此时另一个事务也读到 1，也卖了一台
UPDATE stock SET qty = 1 WHERE id = 1;   -- 覆盖

-- 对：一条语句搞定
UPDATE stock SET qty = qty - 1 WHERE id = 1 AND qty > 0;
```

更简单的做法是**根本不用先读**，把判断写进 `WHERE`（上一关讲过）。这是首选。

只有"判断逻辑复杂到写不进 `WHERE`"时，才用 `FOR UPDATE` 把行锁住再在应用里算：

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- 锁住这一行
-- 应用里算：够不够？够就更新
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

`FOR UPDATE` 的代价：**其他事务对这行的写（以及 `FOR UPDATE` 读）会阻塞**，直到你提交或回滚。阻塞太久会报 `Lock wait timeout exceeded`。所以它必须配短事务。

### 间隙锁：InnoDB 消除幻读的办法

如果只锁"已经存在的行"，那 B 可以插入一条新行，A 再查就有幻影了。InnoDB 在 `REPEATABLE READ` 下除了锁行，还锁**行之间的间隙**（gap lock），让别的事务**插不进来**。

这就是为什么 `REPEATABLE READ` 下幻读基本被消除。代价是间隙锁会阻塞插入，在写多读少的场景里容易造成死锁。

### 死锁：两个事务各等对方

经典场景：A 锁了行 1 想锁行 2，B 锁了行 2 想锁行 1，两边互相等。

InnoDB 会**主动检测**并杀掉其中一个（报 `Deadlock found when trying to get lock`），而不是无限等下去。所以死锁不是"数据库挂了"，是"你的事务顺序有问题"。

**减少死锁的两条做法**：

1. **按固定顺序访问多行**（比如总是按 id 升序更新），避免交叉等待；
2. **让事务尽可能短**，缩小持有锁的时间窗。

## 跑一遍

<!-- run -->
```sql
CREATE TABLE t (id INT PRIMARY KEY, v INT);
INSERT INTO t VALUES (1, 10), (2, 20);

SELECT @@transaction_isolation AS mysql_default_iso;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT @@transaction_isolation AS session_iso;

BEGIN;
SELECT v AS plain_read FROM t WHERE id = 1;
SELECT v AS current_read FROM t WHERE id = 1 FOR UPDATE;
UPDATE t SET v = v + 1 WHERE id = 1;
SELECT v AS after_own_update FROM t WHERE id = 1;
COMMIT;

SELECT v AS final_value FROM t WHERE id = 1;
```
```text
mysql_default_iso=REPEATABLE-READ
session_iso=READ-COMMITTED
plain_read=10
current_read=10
after_own_update=11
final_value=11
```

四处：

1. `mysql_default_iso=REPEATABLE-READ`：MySQL 的默认级别是 RR，不是 SQL 标准常说的 RC。
2. `session_iso=READ-COMMITTED`：隔离级别可以按会话改，不改全局。
3. `plain_read` 与 `current_read` 都是 10，但后者拿到了行锁。
4. `after_own_update=11`：**自己改完立刻能看到**——快照读也会看到本事务的未提交改动。

### 行锁阻塞是什么样

单会话演示不了阻塞，这里给实测结果。两个会话同时操作同一行：

```text
会话 A：BEGIN; UPDATE t SET v = 99 WHERE id = 1;   -- 不提交
会话 B：UPDATE t SET v = 1 WHERE id = 1;            -- 阻塞
       → Lock wait timeout exceeded; try restarting transaction
会话 A：ROLLBACK;
会话 B：再执行 → 成功，影响 1 行
```

B 的第二个请求在 A 提交/回滚前会一直等，等到 `innodb_lock_wait_timeout`（默认 50 秒）后报错。这就是"事务太长会把别人卡死"的具体形态。

## 常见误区

### 误区：`REPEATABLE READ` 下读不到别人提交的新数据就是 bug

**你以为**：数据明明改了，为什么还读到旧的。
**其实**：快照读按事务开始时的版本读，这是隔离性的定义。要读最新值用 `FOR UPDATE`（或提交后重新开事务）。
**怎么验证**：两个会话，A 开事务后 B 更新并提交，A 再读仍是旧值；`COMMIT` 后重开事务读到新值。

### 误区：`SELECT` 加了事务就能防止并发修改

**你以为**：`BEGIN` 之后查一遍就锁住了。
**其实**：普通 `SELECT` 不加任何锁。要锁住必须显式 `FOR UPDATE`，或者干脆用条件更新。
**怎么验证**：A 事务里 `SELECT` 一行后不提交，B 直接 `UPDATE` 同一行——B 不会被阻塞。

### 误区：死锁说明数据库有问题

**你以为**：出现死锁要去找数据库的毛病。
**其实**：死锁是两个事务的访问顺序互相冲突。InnoDB 会检测并杀掉一个，报错是正常行为。
**怎么验证**：让两个会话按相反顺序更新同一批行，观察其中一个立即报 `Deadlock found`。

## 小结

隔离级别决定并发读到什么：脏读、不可重复读、幻读依次被消除，MySQL 默认 RR 用 MVCC 快照加间隙锁。普通 `SELECT` 是快照读不加锁，`FOR UPDATE` 是当前读并加锁。能写进 `WHERE` 的判断就别用 `FOR UPDATE`。死锁来自访问顺序不一致，靠固定顺序与短事务避免。
