# 10 · 隔离级别与锁

## 两个事务都读到 1，最后只卖掉一台

库存只剩一台。两个请求几乎同时进来，代码都是「先查、够了再扣」：

```text
会话 A                                   会话 B
BEGIN;
SELECT qty FROM stock WHERE id = 1;
→ 1
                                          BEGIN;
                                          SELECT qty FROM stock WHERE id = 1;
                                          → 1
UPDATE stock SET qty = 0 WHERE id = 1;
COMMIT;
                                          UPDATE stock SET qty = 0 WHERE id = 1;
                                          COMMIT;
```

最后库存是 0，**卖出了两台**。两个事务从数据库的角度都是「读到了 1，然后写了 0」，没有任何一条语句报错——数字对不上是几天后对账才发现的。

这不是隔离级别没设对。`REPEATABLE READ` 保证的是「**同一个事务里读两次结果一样**」，它管不到「你读了之后自己算一遍再写回去」这段逻辑。两个事务各自读自己的快照、各自算、各自覆盖，谁都没违反规则。

所以这一课要说的不是「调高隔离级别就安全了」，而是三件事：

1. 四种隔离级别各挡什么、不挡什么；
2. **快照读**与**当前读**的区别——这是理解 MySQL 锁的分界线；
3. 什么时候必须 `FOR UPDATE`，以及它的代价。

## 四种隔离级别，挡的是「读」的异常

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 |
| `READ COMMITTED` | 不会 | 可能 | 可能 |
| `REPEATABLE READ`（InnoDB 默认） | 不会 | 不会 | 快照读不会；加锁读靠 next-key 锁 |
| `SERIALIZABLE` | 不会 | 不会 | 不会 |

三个现象都要用「同一个事务里读两次」描述：

- **脏读**：A 读到了 B **还没提交**的值。B 后来回滚，A 读到的那个值从未真实存在过。
- **不可重复读**：A 第一次读 `v = 10`，B 改成 11 并提交，A 再读变成 11。**同一行，同一事务，两次不同。**
- **幻读**：A 查 `WHERE city = '北京'` 得 2 行，B 插了一条并提交，A 再查得 3 行。**行数变了。**

后两者的区别就一句：不可重复读是「同一行的值变了」，幻读是「多了或少了几行」。

MySQL 默认是 `REPEATABLE READ`，而 SQL 标准里很多数据库的默认是 `READ COMMITTED`（Oracle、PostgreSQL）。**从 PG 迁过来时不注意这个差异，「同一事务读两次」的结果会不一样。**

## 为什么 RR 下第二次读到的还是旧值

InnoDB 用 MVCC：事务第一次读时确定一个快照，之后的普通 `SELECT` 都从快照读。

```sql
BEGIN;
SELECT v FROM t WHERE id = 1;   -- 10
-- 另一个会话把 v 改成 11 并提交
SELECT v FROM t WHERE id = 1;   -- 还是 10
COMMIT;
```

这是特性不是 bug，它保证了事务内两次读一致。

但它有个必须记住的推论：**自己改过的值，自己立刻能看到**。快照读会合并本事务的未提交改动，所以现象是「看得到自己改的，看不到别人改的」。日志里出现「读出来的值和我刚写的不一样」时，先想是不是这两个方向搞混了。

## 快照读与当前读：MySQL 锁的分界线

| 类型 | 写法 | 读什么 | 加锁 |
| --- | --- | --- | --- |
| 快照读 | 普通 `SELECT` | 事务开始时的快照 | **不加锁** |
| 当前读 | `SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`UPDATE`、`DELETE` | 最新已提交的值 | **加锁** |

由此三条结论：

1. **普通 `SELECT` 不加锁**，它不阻塞别人，也不被别人阻塞，只是看到旧值。
2. **`UPDATE` / `DELETE` 一定是当前读并加锁**——这就是为什么「先查再改」不安全：查那一步没有锁，改那一步才上锁，中间是空的。
3. 要「读出来就锁住」，只能显式 `SELECT ... FOR UPDATE`。

`LOCK IN SHARE MODE` 在 MySQL 8.0.1 之后叫 `FOR SHARE`，老写法仍能用。共享锁允许多个人同时读，但谁都写不了；`FOR UPDATE` 是排他锁，连别人来读锁都会被挡住。

## 什么时候真的需要 FOR UPDATE

首选永远是**把判断写进 `WHERE`**，一条语句完成读改：

```sql
UPDATE stock SET qty = qty - 1 WHERE id = 1 AND qty > 0;
-- 影响行数 0 就是没抢到货，不需要先 SELECT
```

只有「判断逻辑复杂到写不进 `WHERE`」时才用 `FOR UPDATE`：

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- 读到最新值并锁住
-- 应用里算：够不够？够就更新
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

它的代价很具体：**其他事务对这一行的写（以及 `FOR UPDATE` 读）会一直等**，等到 `innodb_lock_wait_timeout`（默认 50 秒）后报错：

```text
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

线上看到这个错，八成不是「数据库慢」，而是有人在一个事务里做了 HTTP 调用、发了消息、或者循环里逐行 `FOR UPDATE` 却不提交。所以 `FOR UPDATE` 必须配短事务。

## 间隙锁：RR 挡幻读的办法

只锁「已经存在的行」挡不住插入。所以 InnoDB 在 `REPEATABLE READ` 下还会锁**行之间的间隙**，让别的事务插不进来——这就是 next-key 锁（记录锁 + 间隙锁）。

几个容易踩的细节：

- **`READ COMMITTED` 下没有间隙锁**（除了外键约束和唯一性检查）。把隔离级别调成 RC 能减少锁冲突，代价是幻读重新出现。
- 间隙锁只对**索引范围**生效。走不到索引的 `UPDATE ... WHERE name = 'x'` 会扫全表，锁的范围大到接近锁表。
- **唯一索引等值命中已存在的行时只剩记录锁**，不会锁间隙；命中不存在的行才需要间隙锁来防别人插。这也解释了一个现象：同样的 SQL，主键查有值时不阻塞插入，查空值时却会。

## 死锁：两个事务各等对方

A 锁了行 1 想锁行 2，B 锁了行 2 想锁行 1，互相等。InnoDB 会主动检测并杀掉代价小的那个：

```text
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

看到这个错不要第一反应「数据库有问题」。它说明**你的两个（或多个）事务访问顺序不一致**。排查用：

```sql
SHOW ENGINE INNODB STATUS\G
-- 找 LATEST DETECTED DEADLOCK 那一段，里面有两个事务各自的 SQL 和持锁/等锁信息
```

两条减少死锁的做法：

1. **按固定顺序访问多行**——批量扣库存时先 `ORDER BY id` 再逐行更新，让所有事务的加锁顺序一致；
2. **事务尽量短**——把网络调用、文件读写挪到事务外面。

第二条比第一条更常被忽略：一个事务里夹了一次 3 秒的外部调用，锁的持有时间就从毫秒变成秒，并发一上来必然互相等。

## 跑一遍

<!-- run -->
```sql
CREATE TABLE t (id INT PRIMARY KEY, v INT);
INSERT INTO t VALUES (1, 10), (2, 20);

SELECT @@transaction_isolation AS mysql_default_iso;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT @@transaction_isolation AS session_iso;

BEGIN;
SELECT v AS plain_read FROM t WHERE id = 1;
SELECT v AS current_read FROM t WHERE id = 1 FOR UPDATE;
UPDATE t SET v = v + 1 WHERE id = 1;
SELECT v AS after_own_update FROM t WHERE id = 1;
COMMIT;

SELECT v AS final_value FROM t WHERE id = 1;
```
```text
mysql_default_iso=REPEATABLE-READ
session_iso=READ-COMMITTED
plain_read=10
current_read=10
after_own_update=11
final_value=11
```

四处对照：

1. `mysql_default_iso=REPEATABLE-READ`：默认是 RR，不是标准常说的 RC。
2. `session_iso=READ-COMMITTED`：隔离级别可以按会话改，只影响当前连接；要改全局用 `SET GLOBAL`，且只对**之后建立**的连接生效。
3. `plain_read` 与 `current_read` 都是 10（此时没人改过），但后者拿到了行锁。
4. `after_own_update=11`：自己改完立刻能看到，快照读并不屏蔽自己的改动。

### 阻塞长什么样（两会话补记）

单会话演示不了阻塞，下面是两个会话同时操作同一行的实际形态：

```text
会话 A：BEGIN; UPDATE t SET v = 99 WHERE id = 1;   -- 不提交
会话 B：UPDATE t SET v = 1 WHERE id = 1;            -- 阻塞
       → ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
会话 A：ROLLBACK;
会话 B：再执行 → Query OK, 1 row affected
```

B 会一直等，等到 `innodb_lock_wait_timeout`（默认 50 秒）才报错。这就是「事务太长会把别人卡死」的具体形态。

## 还差的

- **间隙锁的具体加锁范围没实测**。哪种查询锁哪段区间、`INSERT ... ON DUPLICATE KEY UPDATE` 在边界上的行为，我只按文档和别人的结论写，没有自己造数据逐条验证。
- **RC 与 RR 在真实业务上的性能差异没量过**。只知道 RC 锁更少，具体能快多少说不出数字。
- **`SERIALIZABLE` 一次都没在生产用过**。它的并发代价有多大，我只有理论印象。
