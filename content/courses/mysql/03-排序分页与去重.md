# 03 · 排序、分页与去重

## 同一条 SQL，两次结果顺序不一样

造一张五行记录全部并列的表，加一个 `salary` 索引：

```sql
CREATE TABLE t_sort (id INT PRIMARY KEY, name VARCHAR(10), salary INT,
                     KEY idx_salary (salary));
INSERT INTO t_sort VALUES (1,'a',9000),(2,'b',9000),(3,'c',9000),
                          (4,'d',9000),(5,'e',9000);
```

然后同一条查询，只改索引提示：

```sql
SELECT name FROM t_sort FORCE  INDEX (idx_salary) ORDER BY salary DESC;
SELECT name FROM t_sort IGNORE INDEX (idx_salary) ORDER BY salary DESC;
```

在一台 MySQL 8.0.46 上的实测输出：

```text
e
d
c
b
a

a
b
c
d
e
```

同一条 SQL、同一个库、同样的数据，顺序反了。这不是 bug，是标准行为：**排序键完全相等时，它们的相对顺序没有被定义**，数据库选了哪条执行路径就按哪条路径给。

第一次读到这个结果时我的反应是「那分页怎么办」。答案是会出事，而且出得很安静。

## 翻页会重复、会漏行

```sql
-- 第 1 页
SELECT name FROM t_sort ORDER BY salary DESC LIMIT 2 OFFSET 0;
-- 第 2 页
SELECT name FROM t_sort ORDER BY salary DESC LIMIT 2 OFFSET 2;
```

第 1 页拿到 `a, b`，第 2 页若换了计划拿到 `b, c`，用户看到 b 出现两次、e 一次都没有。**没有报错，条数也对，只是内容错了。**

修法：让排序成为全序。排序键末尾补一个唯一键。

```sql
ORDER BY salary DESC, id
```

`id` 唯一，所以任意两行的次序都有确定答案，两次查询必然一致。

两个必须说清的边界：

- **排序键本身就唯一时不用补**（`ORDER BY id` 已经是全序）；没有主键时用唯一键或唯一组合也行。
- **补了唯一键不等于并发安全**。两次翻页之间如果有人插入/删除/改了排序键，窗口整体移动，照样重复或漏行。那要靠游标分页（下一节）或一致性快照，补主键解决不了。

## OFFSET 不是「跳着读」

```sql
LIMIT 10 OFFSET 100000   -- 跳过 10 万行，取 10 行
LIMIT 100000, 10         -- 等价写法
```

`OFFSET 100000` 的语义是「产生前 100000 行并丢弃」。有覆盖索引时可能只扫索引项、不必回表读整行，但**扫的量级照样是 offset 那么多**。翻得越深越慢，根因在这里。

连续翻页（下拉加载、下一页）用游标：

```sql
-- 上一页最后一行是 salary=9000, id=2
SELECT id, name, salary FROM employees
WHERE (salary, id) < (9000, 2)      -- 行值比较，两列必须同向
ORDER BY salary DESC, id DESC
LIMIT 10;
```

两个容易踩的点：

1. **方向必须与 `ORDER BY` 一致**。升序排就得写 `>` 配 `ASC`；`ORDER BY salary DESC` 配 `WHERE (salary,id) > (...)`，翻出来的还是同一段。
2. **行值比较只支持同向**。别写 `ORDER BY salary DESC, id ASC` 再配 `(salary, id) < (...)` —— 那是两个方向拼在一起，结果不是你要的第二页。要混向就拆成 `salary < 9000 OR (salary = 9000 AND id > 2)`。

游标分页的代价是**不能跳页**。它适合滚动加载，不适合「跳到第 100 页」的页码导航。这是产品形态决定的，不是技术优劣。

## 一句流行但会给你错行的写法

网上常见这个「深分页优化」：

```sql
-- 按 id 排序时勉强成立
SELECT * FROM employees
WHERE id >= (SELECT id FROM employees ORDER BY id LIMIT 100000, 1)
LIMIT 10;
```

它不是关联子查询，是个标量子查询；而且只有**按 `id` 排序**时才成立。我按薪资排序实测过：

```sql
-- 想取按 salary DESC, id 排序的第 2 页（每页 2 条）
-- 正确结果应该是 赵六 12000、王五 9000
SELECT * FROM employees
WHERE id >= (SELECT id FROM employees ORDER BY salary DESC, id LIMIT 2, 1)
ORDER BY salary DESC, id LIMIT 2;
```

拿到的却是 `孙八 NULL` 一行。原因很直白：子查询取到的是 offset 处的那个 `id`（此处是 4），`WHERE id >= 4` 就把 id 1/2/3 的行全排除了——而它们里才有薪资最高的几个人。**排序键和过滤键不是同一列，这个改写直接把结果改错。**

它也没绕开成本：子查询本身仍要扫掉 offset 那么多行。

要支持随意跳页，正确方向是「先只取主键，再回表」：

```sql
SELECT e.* FROM employees e
JOIN (SELECT id FROM employees ORDER BY salary DESC, id LIMIT 100000, 10) x
  ON x.id = e.id
ORDER BY e.salary DESC, e.id;
```

子查询只碰索引（覆盖索引，不回表），回表只发生在最终这 10 行。**但它仍然有 offset 成本**——只是把成本从「读 10 万行整行」降到「读 10 万个索引项」。真正的解还是游标，或者干脆不给用户跳那么深。

## 顺手记两件事

**`NULL` 在排序里当最小值**：升序排最前，降序排最后。想固定位置，用表达式做第一排序键：

```sql
ORDER BY salary IS NULL, salary DESC   -- IS NULL 得到 0/1，有值的先出
```

接口返回「薪资最低的 N 个人」时，一堆没填薪资的会挤在最前面——这不是排序错，是 `NULL` 的语义。

**`DISTINCT` 作用于 SELECT 列表的整体组合**，不是「整行」，也不是「第一列」：

```sql
SELECT DISTINCT dept FROM employees;          -- 按 dept 这一列去重
SELECT DISTINCT dept, salary FROM employees;  -- 按 (dept, salary) 组合去重
```

同一个部门不同薪资各留一行，所以它不是「每个部门取一条」。每组取一条是 `GROUP BY` 的事（下一关）。

`DISTINCT` 需要排序或哈希去重，数据量大时明显比不去重慢——这是它的真实代价，不是白拿的。

-- q2 多列排序：先部门，同部门内按薪资降序
SELECT name, dept, salary FROM employees ORDER BY dept, salary DESC, id;
-- q3 第 1 页
SELECT name, salary FROM employees ORDER BY salary DESC, id LIMIT 2;
-- q4 第 2 页
SELECT name, salary FROM employees ORDER BY salary DESC, id LIMIT 2 OFFSET 2;
-- q5 单列去重
SELECT DISTINCT dept FROM employees ORDER BY dept;
-- q6 去重计数 vs 总行数

`列=值 | 列=值` 是这个课程统一的输出格式，不是 MySQL 客户端的样子（客户端给的是表格）。六段结果按 `q1` 到 `q6` 的顺序排下来。

观察四处：

1. 降序时 `NULL` 排在最后，因为 `NULL` 被当成最小值。
2. 王五和钱七都是 9000，靠 `id` 才定下了固定顺序——去掉 `id` 就回到开头那个「顺序会变」的状态。
3. `q3` 与 `q4` 拼起来正好是 `q1` 的前四行，不重不漏；这就是全序排序买来的东西。
4. `COUNT(DISTINCT dept)` 是 3，总行数是 6——去重计数和总计数是两个数。

## 还差的

- **并发翻页没有真正解**。补唯一键只解决「同一份数据两次查顺序不同」，翻页之间有人插入记录，窗口整体移动的问题还在，要么用游标（且排序键不变），要么用一致性快照读。
- **跳页方案只做过小数据量对比**。deferred join 在千万级上的实际收益、以及优化器会不会把它改写成别的计划，我没有实测。
- **`DISTINCT` 的哈希去重代价没量化**。只知道「数据量大时慢」，慢多少、在什么行数上开始明显，我说不出数字。
