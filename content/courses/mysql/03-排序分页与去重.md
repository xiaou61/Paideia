# 03 · 排序、分页与去重

## 这一课你要会

- 用 `ORDER BY` 排序，知道多列排序是从左到右逐级生效的；
- 写对分页，知道为什么翻到后面会越来越慢；
- 说清 `DISTINCT` 作用在"整行"还是"单列"。

## 为什么

排序和分页看起来最简单，实际是**线上最容易出现数据重复、丢失、错乱**的地方。

一个真实案例：翻页时某条数据在第一页出现、翻到第二页又出现一次。不是 bug 重了，是排序不稳定——两次查询里相等的那几行顺序变了。这一关讲清为什么会这样、怎么修。

## 讲解

### `ORDER BY`：默认升序

```sql
ORDER BY salary DESC     -- 从大到小
ORDER BY salary ASC      -- 从小到大（默认）
```

`NULL` 在 MySQL 的排序里被当作**最小值**：升序时排最前，降序时排最后。这和很多人的直觉相反，接口里返回"薪资最低的"时可能拿到一堆没填薪资的。

想控制 `NULL` 的位置，用 `IS NULL` 作为第一排序键：

```sql
ORDER BY salary IS NULL, salary DESC
```

`salary IS NULL` 的结果是 0 或 1，先按它排就把有值的放前面了。

### 多列排序：从左到右逐级生效

```sql
ORDER BY dept, salary DESC
```

意思是：先按部门排，**同一个部门内部**再按薪资降序。不是"两个条件都满足"，而是"第一列相同时才看第二列"。

### 排序不稳定：为什么必须加主键

关键事实：**如果排序键有重复值，MySQL 不保证这些行的相对顺序，也不保证两次查询顺序一致。**

上面的例子里王五和钱七都是 9000。这次它们按这个顺序，下次可能反过来——取决于数据库用了索引还是全表扫描、有没有走并行。

后果在分页时最明显：

```sql
-- 第 1 页
ORDER BY salary DESC LIMIT 2 OFFSET 0
-- 第 2 页
ORDER BY salary DESC LIMIT 2 OFFSET 2
```

如果 9000 那两行的相对顺序在两次查询之间变了，第 2 页就会把它们中的一个再返回一次，而另一条被跳过。

**修法：排序键末尾永远补上主键。**

```sql
ORDER BY salary DESC, id
```

主键唯一，所以整个排序是全序的，两次查询结果必然一致。**分页查询必须这么写**，否则翻页错乱只是早晚的事。

### `LIMIT` 与 `OFFSET`

```sql
LIMIT 10 OFFSET 20   -- 跳过 20 行，取 10 行
LIMIT 20, 10         -- 等价写法
```

深分页的问题：`OFFSET 100000` 不是"直接跳到第 10 万行"，而是**先读出前 10 万行再扔掉**。翻到后面越来越慢，就是这个原因。

几种改法：

| 场景 | 做法 |
| --- | --- |
| 有递增主键、翻页是连续的 | 游标分页：`WHERE id > 上一页最后一条的 id ORDER BY id LIMIT 10` |
| 需要跳页（用户点第 100 页） | 关联子查询先定位主键：`WHERE id >= (SELECT id ... LIMIT 100000, 1)` |
| 总数也要显示 | 单独一次 `COUNT(*)`，别在主查询里算 |

**游标分页的代价是不能跳页**，只能一页页往下。所以它适合"滚动加载"，不适合"页码导航"。这是产品形态决定的，不是技术优劣。

### `DISTINCT`：作用于整行

```sql
SELECT DISTINCT dept FROM employees;     -- 去重这一列
SELECT DISTINCT dept, salary FROM ...;   -- 去重(部门, 薪资)这个组合
```

第二种经常被误解成"按部门去重、顺便带出薪资"——不是，它是按**两列的组合**去重，同一个部门不同薪资会各留一行。

如果真想要"每个部门留一条"，那属于分组问题，用 `GROUP BY`（下一关）。

`DISTINCT` 的另一个代价：它需要排序或哈希去重，数据量大时明显比不加慢。

## 常见误区

### 误区：同样的查询两次结果顺序一定一样

**你以为**：数据库是确定的，怎么会变。
**其实**：排序键有重复时，MySQL 不保证相等行的相对顺序，执行计划一变顺序就可能变。
**怎么验证**：造几行排序键相同的记录，反复执行同一条查询，观察顺序是否变化。

### 误区：`LIMIT 10 OFFSET 100000` 是跳着读的

**你以为**：数据库直接定位到第 10 万行。
**其实**：它要读出前 10 万行再丢弃，越往后越慢。这是深分页慢的根因。
**怎么验证**：对比 `OFFSET 0` 与 `OFFSET 100000` 的耗时，差值应随时移量线性增长。

### 误区：`DISTINCT` 能用来"每个分组取一条"

**你以为**：`SELECT DISTINCT dept, name` 能得到每个部门一个名字。
**其实**：它按 (dept, name) 组合去重，部门里有多少人还是多少行。要每组一条得用 `GROUP BY` 加聚合。
**怎么验证**：对一个有多人的部门执行该查询，看返回行数是否等于人数。

## 小结

`ORDER BY` 默认升序，`NULL` 被当最小值。多列排序从左到右逐级生效。**分页查询的排序末尾必须补主键**，否则会重复或漏行。`OFFSET` 越大越慢，连续翻页用游标分页。`DISTINCT` 作用在整行。
