# 08 · 范式与表设计

## 客户搬家了

客户 ann 从北京搬到上海。运营在后台改了客户资料，页面显示正确。第二天报表出来：同一个 ann 同时出现在"北京"和"上海"两个分组里，两个城市的订单数分别少了一些。

原因很朴素：订单表里除了 `customer_id`，还存了一份 `customer_city`。ann 有 3 张订单，就存了 3 份"北京"。改资料只改了客户表里的那一份，订单表里 3 行还是旧值。

这件事**不会报错**。它只会让报表慢慢变得不可信，然后花一周去对数。

范式就是用来防这类问题的判断依据：**这条信息该不该存在这张表里**。它不保证设计好，但能挡住绝大多数明显错误。

## 一句话：同一事实只存一份

范式把这句话拆成三级更严格的要求。三级都围绕一个词——**依赖**：非主键列是不是只由主键决定。

### 第一范式：每格只放一个值

| id | customer | products |
| --- | --- | --- |
| 1 | ann | 键盘, 鼠标 |

`products` 这一格塞了两个商品。要查"买过键盘的订单"，只能：

```sql
SELECT * FROM bad_orders WHERE products LIKE '%键盘%';
```

两个后果：**慢**（前面是 `%`，索引完全用不上，只能全表扫），**会错**（买"键盘膜"的也命中）。

正解是一行一个商品（订单明细表）。

### 第二范式：非主键列依赖**整个**主键

假设明细表用 `(order_id, product_id)` 做联合主键，同时把商品名也放进来：

| order_id | product_id | product_name | qty |
| --- | --- | --- | --- |
| 1 | 10 | 键盘 | 2 |
| 2 | 10 | 键盘 | 1 |

`product_name` 只由 `product_id` 决定，和 `order_id` 无关——它只依赖主键的一半。这叫部分依赖。商品改名时要改所有出现它的明细行，漏一行就有两个名字。

正解：商品名放商品表，明细表只存 `product_id`。

### 第三范式：非主键列之间不能互相决定

上一节那个 ann 的例子，表长这样：

| id | customer_id | customer_city | amount |
| --- | --- | --- | --- |
| 1 | 7 | 北京 | 199.00 |
| 2 | 7 | 北京 | 89.50 |
| 3 | 7 | 北京 | 1099.00 |

`customer_city` 由 `customer_id` 决定，而 `customer_id` 是普通列（不是主键）——于是城市是**通过** `customer_id` 传递依赖主键的。这就是 3NF 要拆的东西。

这里要小心一个常见的写错的例子：**说"城市依赖客户名"是错的**。客户名不唯一（两个 ann 很正常），所以"客户名 → 城市"根本不成立。判断传递依赖，要看的是那个真正唯一的标识（`customer_id`）。

正解：城市放客户表，订单只存 `customer_id`。

### 一条能用的经验

> 如果同一个值在表里出现了不止一次，问一句：**它为什么会重复？**

是"同一件事实被存了多份"（ann 的城市），就拆出去。
是"不同时间的两个事实"（下单时的价格 vs 现在的价格），就该留着——这是快照，不是冗余，下一节细说。

## 确实该故意冗余的地方

范式保证改数据时只需改一处，代价是查询要连接。有两种情况值得故意反着来：

| 场景 | 做法 | 理由 |
| --- | --- | --- |
| 下单时的商品名称与价格 | 订单明细里冗余存一份当时的名称与价格 | 商品后来改名或涨价，历史订单必须显示当时的值 |
| 高频统计的汇总值 | 单独建汇总表，由定时任务或事件更新 | 每次都去 `SUM` 百万行不现实 |

**判断标准：这份重复是"同一事实的副本"，还是"不同时间的两个事实"。** 前者该拆，后者该留。

订单价格是最好用的例子：`order_items.price` 和 `products.price` 看起来是同名字段，但它们是两个不同的事实——一个是成交价，一个是当前挂牌价。把它们当"冗余"删掉，等于让历史订单随涨价一起变。

## 拆表不是免费的

上一节那句"改表要停机"其实说重了，得说清代价到底在哪：

- **加列、加二级索引**：InnoDB 支持在线 DDL，`ALTER TABLE ... ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE` 不阻塞读写；
- **改列类型、改主键、加 `NOT NULL` 列（无默认值）**：通常是重建表，期间写入受限；
- **拆表本身**：不是 DDL 难，是**代码和存量数据**难——所有查询、所有写入、历史数据回填、上下游对接方，都要跟着改。

所以拆表的正确时机是**设计阶段**，不是"发现冗余了再拆"。这也是为什么这一课放在建表那一关（07）之后、并发之前：范式是设计动作，不是重构动作。

## 外键：建还是不建

MySQL 支持 `FOREIGN KEY`，但要不要用是**逐个关系判断**，不是一个团队级口号。

这个仓库（Paideia）的实际做法可以从迁移文件里读出来（`backend/paideia-app/src/main/resources/db/migration/`）：**有明确父子生命周期、删父必须删子**的关系都建了外键，并且用 `ON DELETE CASCADE`：

```sql
-- V1__create_account_tables.sql
CONSTRAINT fk_refresh_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE

-- V3__create_knowledge_tables.sql
CONSTRAINT fk_knowledge_entries_category FOREIGN KEY (category_id)
  REFERENCES knowledge_categories (id)
```

而"只是引用一下"的关系（比如某张表里记了个 `created_by`）就没有外键，只留列 + 索引。判断标准是三条：

- **父子生命周期是否一致**？删父必须删子 → 建，并且用 `CASCADE`；删父时子必须留 → 别用 `CASCADE`，用 `RESTRICT` 或应用层处理；
- **会不会分库分表**？跨库外键无法维护，这种关系只能靠应用保证；
- **写入量大不大**？外键检查是每行写入的额外开销，高频写入表上要称一下。

不建外键的代价是**一致性完全由应用与测试保证**，所以还有一条硬要求：**外键列必须建索引**。没有索引时，删除父行要全表扫子表来找引用，连接查询也会全表扫。

三种违反各演示一次，再演示修复后的样子。

```sql
-- 违反 1NF：一格塞两个商品
CREATE TABLE bad_orders (
  id            INT PRIMARY KEY AUTO_INCREMENT,
  customer_name VARCHAR(20),
  customer_city VARCHAR(20),
  products      VARCHAR(60)
);
INSERT INTO bad_orders (customer_name, customer_city, products)
VALUES ('ann', '北京', '键盘, 鼠标'),
       ('ann', '北京', '显示器');

-- LIKE 会误命中「键盘膜」
INSERT INTO bad_orders (customer_name, customer_city, products)
VALUES ('bob', '上海', '键盘膜');
SELECT id, customer_name, products FROM bad_orders WHERE products LIKE '%键盘%' ORDER BY id;

-- 违反 3NF：同一客户的同一事实存了三份
SELECT customer_name, customer_city, COUNT(*) AS rows_with_city
  FROM bad_orders GROUP BY customer_name, customer_city
  ORDER BY customer_name;

-- 违反 2NF：明细表里塞了只依赖 product_id 的商品名
CREATE TABLE bad_items (
  order_id     INT NOT NULL,
  product_id   INT NOT NULL,
  product_name VARCHAR(20) NOT NULL,
  qty          INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO bad_items VALUES (1, 10, '键盘', 2), (2, 10, '键盘', 1);
SELECT product_name, COUNT(*) AS rows_named FROM bad_items GROUP BY product_name;

-- 修复：客户 / 订单 / 明细 三张表，商品名留在商品表
CREATE TABLE customers (
  id   INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(20) NOT NULL,
  city VARCHAR(20) NOT NULL
);
CREATE TABLE orders (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,
  created     DATETIME NOT NULL,
  KEY idx_orders_customer (customer_id)
);
CREATE TABLE order_items (
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  product    VARCHAR(20) NOT NULL,
  price      DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO customers (name, city) VALUES ('ann', '北京'), ('bob', '上海');
INSERT INTO orders (customer_id, created) VALUES (1, '2026-10-20 10:00:00'), (1, '2026-10-21 15:00:00');
INSERT INTO order_items VALUES (1, 10, '键盘', 199.00), (1, 11, '鼠标', 89.50), (2, 10, '键盘', 189.00);

SELECT c.name, c.city, COUNT(DISTINCT o.id) AS orders_cnt, SUM(i.price) AS amount
  FROM customers c
  LEFT JOIN orders o ON o.customer_id = c.id
  LEFT JOIN order_items i ON i.order_id = o.id
  GROUP BY c.id, c.name, c.city
  ORDER BY c.id;
```
```text
LIKE '%键盘%'
id=1 | customer_name=ann | products=键盘, 鼠标
id=2 | customer_name=bob | products=键盘膜

customer_name=ann | customer_city=北京 | rows_with_city=2
customer_name=bob | customer_city=上海 | rows_with_city=1

product_name=键盘 | rows_named=2

name=ann | city=北京 | orders_cnt=2 | amount=487.50
name=bob | city=上海 | orders_cnt=0 | amount=NULL
```

逐段看：

1. `LIKE '%键盘%'` 把 `键盘膜` 也捞出来了——1NF 的直接代价；
2. ann 的"北京"在表里存了 2 份，这就是 3NF 说的传递依赖。她搬家时要改 2 行，漏 1 行报表就出现两个城市；
3. `键盘` 在明细表里出现 2 次，改个名字要改 2 行——2NF 的部分依赖；
4. 拆开之后：ann 的订单数用 `COUNT(DISTINCT o.id)` 才对（直接 `COUNT(*)` 会把一单数成两单，因为明细一行一条）。

看第 4 条你会注意到一个细节：**`bob` 出现在结果里，但订单数是 0、金额是 `NULL`**。因为他没有订单，而最后那句用的是 `LEFT JOIN`。如果写成 `JOIN`，bob 整行会消失。这不是范式问题，是**语义选择**：要"只统计有订单的客户"就用 `JOIN`，要"所有客户都列出"就用 `LEFT JOIN` 配 `COALESCE(SUM(i.price), 0)`。范式解决重复，语义得你自己定。

## 一个实用的设计流程

拿到需求按四步走：

1. **列名词**：需求里的名词逐个列出来（用户、订单、商品、地址……），每个名词通常对应一张表；
2. **定关系**：一对多用外键列（`orders.customer_id`）；多对多用中间表（`order_items`）；
3. **查重复**：按三条范式过一遍，把"另一张表里已经有的信息"删掉；
4. **标快照**：必须保留历史值的列（价格、名称、地址）明确标成"故意的冗余"，并在注释里写清它是快照。

## 一句话

三条范式分别是：每格一个值、非主键列依赖整个主键、非主键列之间不互相决定。判断一个重复该不该留，只看它是不是"同一时刻的副本"——同一事实的副本要拆，不同时间的两个事实（成交价、下单时地址）必须留。拆表的代价在设计阶段付最便宜；外键按"父子生命周期是否一致"逐个决定，不建外键时关联列必须有索引。
