# 08 · 范式与表设计

## 这一课你要会

- 说清第一、二、三范式各自禁止什么；
- 判断什么时候**故意**不遵守范式；
- 看到一张宽表能说出它会在什么时候出问题。

## 为什么

表设计错了，代价不是"改一下"，而是：改表要停机、改代码要连带改十几个地方、历史数据要回填、而且旧数据里已经有不一致。

范式的价值在于给你一套**判断依据**：这个字段该不该放这张表里。它不保证设计好，但能挡住绝大多数明显错误。

## 讲解

### 范式讲的是"有没有冗余"

一句话：**每一条信息只存一份。** 范式就是把这句话拆成三级更严格的要求。

### 第一范式（1NF）：每格只放一个值

**禁止：一个单元格里塞多个值。**

反面例子：

| id | customer | products |
| --- | --- | --- |
| 1 | ann | 键盘, 鼠标 |

`products` 这一格塞了两个商品。后果：要查"买过键盘的订单"就得 `LIKE '%键盘%'`，既慢又容易误匹配（买"键盘膜"的也算）。要加第三个商品还得改数据格式。

正解：一张订单明细表，一个商品一行。

### 第二范式（2NF）：非主键列必须依赖**整个**主键

**禁止：只依赖联合主键的一部分。**

假设订单明细表用 `(order_id, product_id)` 做主键，然后把 `product_name` 也放进来：

| order_id | product_id | product_name | qty |
| --- | --- | --- | --- |
| 1 | 10 | 键盘 | 2 |
| 2 | 10 | 键盘 | 1 |

`product_name` 只依赖 `product_id`，不依赖 `order_id`。这就是部分依赖。后果：同一个商品名要存很多次，改名时要改所有行，漏改一行就出现两个名字。

正解：商品名放商品表，明细表只存 `product_id`。

### 第三范式（3NF）：非主键列之间不能互相依赖

**禁止：A 决定 B，B 又决定 C（C 通过 B 传递依赖主键）。**

反面例子：

| id | customer_name | customer_city |
| --- | --- | --- |
| 1 | ann | 北京 |
| 2 | ann | 北京 |

`customer_city` 依赖 `customer_name`，而 `customer_name` 依赖主键——这叫传递依赖。

后果很实际：ann 搬家到上海，你得更新**所有 ann 的订单行**。漏更新一条，同一个客户就有了两个城市。而且这件事**不会报错**。

正解：客户单独一张表，订单只存 `customer_id`。

### 三范式合起来的一条经验

> **如果同一个值在表里出现了不止一次，问一句：它为什么会重复？**
>
> 如果它是"同一件事实"被重复存了，就该拆出去。

### 什么时候该故意不遵守

范式是为了改数据的一致性，代价是查询要连接。有两种情况值得故意反着来：

| 场景 | 做法 | 理由 |
| --- | --- | --- |
| 下单时的商品名称与价格 | 订单明细里**冗余存一份当时的名称与价格** | 商品后来改名或涨价，历史订单必须显示当时的值。这里的冗余不是错误，是**快照** |
| 高频统计的汇总值 | 单独建汇总表，或用触发器/定时任务更新 | 每次查询都去 `SUM` 百万行行不通 |

**判断标准：这份冗余是"同一事实的副本"，还是"不同时间的两个事实"。** 前者该拆，后者该留。

订单里的商品价格就是典型：它和商品表里的当前价格是**两个不同的事实**（下单时 vs 现在）。所以必须冗余。

### 一个实用的设计流程

拿到需求，按这四步走：

1. **列名词**：把需求里出现的名词都列出来（用户、订单、商品、地址……），每个名词通常对应一张表；
2. **确定关系**：一对多（用户 → 订单）用外键列；多对多（订单 ↔ 商品）要中间表；
3. **检查冗余**：按上面三条范式过一遍，把"另一张表里已经有的信息"删掉；
4. **标出快照字段**：那些必须保留历史值的列（价格、名称、地址），明确它们是故意的冗余。

### 外键要不要建

MySQL 支持外键约束（`FOREIGN KEY`），但生产上**很多团队不用**，原因：

- 写入时外键检查有开销；
- 分库分表后跨库外键无法维护；
- 删父行时行为（`CASCADE` / `RESTRICT`）容易误伤。

本项目（Paideia）的约定是：**关联关系靠列 + 索引表达，不建外键约束，一致性由应用与测试保证。**

不用外键不等于可以不管：**外键列一定要建索引**，否则连接查询会全表扫。

```sql
CREATE TABLE bad_orders (

  customer_name VARCHAR(20),

  product2      VARCHAR(20),
  price1        DECIMAL(10,2),
  price2        DECIMAL(10,2)
);
INSERT INTO bad_orders (customer_name, customer_city, product1, product2, price1, price2)
VALUES ('ann', '北京', '键盘', '鼠标', 199.00, 89.50);

-- 同一客户的两张订单，城市被存了两遍
INSERT INTO bad_orders (customer_name, customer_city, product1, price1)
VALUES ('ann', '北京', '显示器', 1099.00);

SELECT customer_name, customer_city, COUNT(*) AS order_rows
  FROM bad_orders GROUP BY customer_name, customer_city;

-- 正解：客户、订单、明细三张表
CREATE TABLE customers (
  id   INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(20) NOT NULL,
  city VARCHAR(20) NOT NULL
);
CREATE TABLE orders (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,
  created     DATETIME NOT NULL
);
CREATE TABLE order_items (
  id       INT PRIMARY KEY AUTO_INCREMENT,
  order_id INT NOT NULL,
  product  VARCHAR(20) NOT NULL,
  price    DECIMAL(10,2) NOT NULL,
  KEY idx_items_order (order_id)
);
INSERT INTO customers (name, city) VALUES ('ann', '北京');
INSERT INTO orders (customer_id, created) VALUES (1, '2026-10-21 10:00:00');
INSERT INTO order_items (order_id, product, price) VALUES (1, '键盘', 199.00), (1, '鼠标', 89.50);

SELECT c.name, c.city, COUNT(i.id) AS item_count
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items i ON i.order_id = o.id
  GROUP BY c.id, c.name, c.city;
```
```text
customer_name=ann | customer_city=北京 | order_rows=2
name=ann | city=北京 | item_count=2
```

看两个数：

- 第一段 `order_rows=2`：ann 的城市被存了两遍。她搬家时你要更新两行，漏一行就出现两个城市。
- 第二段 `item_count=2`：拆开之后，一个订单的多个商品各占一行，加第三个商品不需要改表结构。

**拆开之后查询变长了**（要连三张表），这是范式的代价。换来的是"改一次就够"。

## 常见误区

### 误区：范式越高越好，一律按三范式做

**你以为**：拆得越细越规范。
**其实**：拆得越细连接越多，查询越慢，代码也越绕。快照字段与汇总表就是必须故意的冗余。
**怎么验证**：把一张订单表按三范式拆开，对比"查一个订单全部信息"的 SQL 复杂度与耗时。

### 误区：不用外键就可以不管关联关系

**你以为**：既然不建外键，关联列就随便放。
**其实**：不建外键只是放弃数据库层的强制检查。关联列仍必须建索引，否则每次连接都要全表扫。
**怎么验证**：对关联列有无索引两种情况分别 `EXPLAIN` 一句连接查询，看是否出现 `Table scan`。

### 误区：一个字段存逗号分隔的列表很方便

**你以为**：省了一张表，读取时拆开就行。
**其实**：查询、统计、更新单个元素、排序全都要靠字符串处理；索引完全用不上；长度还有上限。
**怎么验证**：尝试写"查包含某个 id 的记录"的查询，对比用中间表的写法。

## 小结

三条范式分别是：每格一个值、非主键列依赖整个主键、非主键列之间不能互相依赖。判断冗余该不该留：是"同一事实的副本"就拆，是"不同时间的两个事实"（快照）就留。关联列即使不建外键也必须建索引。
