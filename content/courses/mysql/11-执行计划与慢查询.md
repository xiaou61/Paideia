# 11 · 执行计划与慢查询

## 从一条慢查询日志说起

线上"慢"最难受的地方是它不是一个可以讨论的描述——你手里只有一句"用户说列表页卡"。

真正能往下走的起点是慢查询日志。打开之后，超过阈值的语句会连耗时、扫描行数一起记下来：

```text
# Time: 2026-11-19T10:41:23.512345+08:00
# User@Host: app[app] @ 10.0.0.7 []  Id: 8123
# Query_time: 2.418311  Lock_time: 0.000102  Rows_sent: 1  Rows_examined: 1002341
SET timestamp=1763517683;
SELECT id, customer_id, created FROM orders WHERE DATE(created) = '2026-10-21';
```

这两行已经说清了三件事：

- `Query_time 2.4 秒`——慢的事实；
- `Rows_examined 1002341` 对 `Rows_sent 1`——扫了一百万行，只返回一行；
- 语句里 `DATE(created)`——列被函数包住了。

后面这一条几乎就是答案。这一课讲的是：**怎么把"慢"变成这种可指认的东西，以及怎么看懂数据库给出的执行计划。**

## EXPLAIN：不执行，只看打算怎么拿数据

```sql
EXPLAIN SELECT id, customer_id, created FROM orders WHERE uid = 1;
```

它不真正跑查询，只打印**执行计划**——数据库打算用哪个索引、按什么顺序、扫多少行。

常看的几列：

| 列 | 意思 | 关注点 |
| --- | --- | --- |
| `type` | 访问方式 | `ALL` 全表扫，最差；`index` 全索引扫，也不理想 |
| `possible_keys` | 理论上能用哪些索引 | 有值但 `key` 为 `NULL`，说明优化器一个都没选 |
| `key` | 实际用了哪个 | `NULL` 就是没走索引 |
| `key_len` | 索引用了多少字节 | 复合索引下能看出用了几列 |
| `rows` | **预估**要扫多少行 | 越大越慢，但只是估算 |
| `Extra` | 附加信息 | `Using filesort`、`Using temporary`、`Using index` 都要会读 |

`type` 从好到差：

```text
system > const > eq_ref > ref > range > index > ALL
```

看到 `ALL` 基本就是"这张表被完整扫了一遍"。

MySQL 8 还有树形输出，更好读：

```sql
EXPLAIN FORMAT=TREE SELECT id FROM orders WHERE uid = 1;
```

```text
-> Filter: (orders.uid = 1)  (cost=0.75 rows=1)
    -> Table scan on orders  (cost=0.75 rows=5)
```

```text
-> Index lookup on orders using idx_orders_uid (uid=1)  (cost=0.70 rows=2)
```

**诀窍：先找两个词。** 出现 `Table scan` 是扫全表；出现 `Index lookup` / `Index range scan` 是走了索引。

## `rows` 是估算，别当账本

`rows` 来自优化器的统计信息（采样得到），不是真实扫描行数。数据分布倾斜、统计信息过期时，它能差一个数量级。

要看真实数字：

```sql
EXPLAIN ANALYZE SELECT id FROM orders WHERE uid = 1;
```

`EXPLAIN ANALYZE` 会**真的执行**这句查询（MySQL 8.0.18+），逐节点打出实际耗时与实际行数。代价就是它真跑了——所以别在生产上对 `UPDATE`/`DELETE` 用它。

## 索引"没用上"有三种完全不同的原因

这一节是整门课最实用的部分。**把它们混成一句"列被加工过就失效"会把后面的判断全带偏**——因为另外两种原因下，你改写法也没用。

### 一、列被加工过

B+ 树里存的是列的原始值，索引按原值有序。你拿函数或运算的结果去比，它没法在这个有序结构里定位。

| 写法 | 为什么不行 | 怎么改 |
| --- | --- | --- |
| `WHERE YEAR(created) = 2026` | 函数包住列 | `WHERE created >= '2026-01-01' AND created < '2027-01-01'` |
| `WHERE DATE(created) = '2026-10-21'` | 同上 | `>= '2026-10-21' AND < '2026-10-22'` |
| `WHERE amount * 2 > 100` | 运算包住列 | `WHERE amount > 50` |
| `WHERE code = 123`（`code` 是 `VARCHAR`） | 列被转成数字再比 | `WHERE code = '123'` |

最后一行要看清方向：**失效的原因是"列"被转换，不是"类型不一致"这个现象本身。**

反例：`phone` 是 `BIGINT`，你传字符串 `WHERE phone = '13800138000'`——这里转换发生在**常量一侧**（字符串转数字），列还是原值，索引照用。所以"参数类型必须和列完全一致"这句话太绝对；准确的判断是：**谁被转换了**。列被转换才失效，常量被转换只是多一次隐式转换的开销（以及 `VARCHAR` 列上可能出现的精度/前导零问题）。

### 二、索引结构不允许

复合索引按 `(city, age)` 排序时，只给 `age` 就找不到起点——这是最左前缀，上一课讲过。

`LIKE` 也是同一类：`LIKE '数据%'` 有前缀能定位，`LIKE '%线'` 没有。它不属于"列被加工"，属于"这个结构没法从中间开始找"。

### 三、优化器主动放弃

这种情况最容易被误判成"写法有问题"：

- 返回行数占全表比例很高（`WHERE status = 'paid'` 而九成行都是 paid），走索引要随机读一大堆页，不如顺序扫；
- 统计信息过期，优化器估错了行数；
- 表太小——扫 20 行本来就不值得走索引。

**判断方法：看 `possible_keys` 和 `key`。** `possible_keys` 有值、`key` 是 `NULL`，说明索引**存在但被放弃**，这时候再改写法是白费力气，要看的是数据分布和统计信息（必要时 `ANALYZE TABLE`）。

## 慢查询日志：先找到该看哪一句

`EXPLAIN` 解决的是"我知道这句慢"。但很多情况下你根本不知道是哪一句。

```sql
-- 开日志（全局，影响之后建立的新连接）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;      -- 超过 1 秒记录
SET GLOBAL log_output = 'FILE';
```

一个必须知道的细节：**`long_query_time` 是会话级参数，`SET GLOBAL` 只对之后建立的新连接生效。** 你在当前连接里改完，然后用同一个连接跑 SQL，发现日志里什么都没记——不是没生效，是你这个连接还在用旧阈值。

当前连接立刻生效要这样：

```sql
SET SESSION long_query_time = 1;
```

想永久生效用 `SET PERSIST long_query_time = 1;`（写入 `mysqld-auto.cnf`，重启后仍在）。

日志会越攒越大，而且同一句 SQL 反复出现。排查顺序不是"打开日志往下翻"，而是**先聚合**：

```bash
mysqldumpslow -s t -t 20 /var/log/mysql/slow.log
```

`-s t` 按总耗时排序，`-t 20` 取前 20 条。找"总耗时高"而不是"单次最高"——一条每秒执行一次的 100 ms 查询，一天消耗 2.4 小时；一条每天一次 5 秒的语句，一天只消耗 5 秒。

<!-- run -->
```sql
CREATE TABLE orders (
  id      INT PRIMARY KEY AUTO_INCREMENT,
  uid     INT NOT NULL,
  amount  DECIMAL(10,2) NOT NULL,
  created DATETIME NOT NULL
);
INSERT INTO orders (uid, amount, created) VALUES
  (1, 100.00, '2026-10-01 10:00:00'),
  (1, 250.00, '2026-10-02 11:00:00'),
  (2,  80.00, '2026-10-03 12:00:00'),
  (2, 300.00, '2026-10-04 13:00:00'),
  (3,  50.00, '2026-10-05 14:00:00');

SELECT COUNT(*) AS orders_total FROM orders;

EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE uid = 1;

CREATE INDEX idx_orders_uid ON orders (uid);

EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE uid = 1;
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE amount * 2 > 100;
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE created >= '2026-10-03';
```
```text
orders_total=5
EXPLAIN=-> Filter: (orders.uid = 1)  (cost=0.75 rows=1)
    -> Table scan on orders  (cost=0.75 rows=5)

EXPLAIN=-> Index lookup on orders using idx_orders_uid (uid=1)  (cost=0.70 rows=2)

EXPLAIN=-> Filter: ((orders.amount * 2) > 100)  (cost=0.75 rows=5)
    -> Table scan on orders  (cost=0.75 rows=5)

EXPLAIN=-> Filter: (orders.created >= TIMESTAMP'2026-10-03 00:00:00')  (cost=0.75 rows=2)
    -> Table scan on orders  (cost=0.75 rows=5)
```

四段对照着看：

1. 建索引前 `Table scan`——全表 5 行都读，这就是 `type=ALL`；
2. 建 `uid` 索引后 `Index lookup using idx_orders_uid`——走上索引了；
3. `amount * 2 > 100`——列被运算包住，只能扫；
4. `created >= '2026-10-03'`——条件本身完全正确，**但 `created` 上没建索引**，所以还是扫。

第 4 条是最容易误判的一种：**条件写对了，不等于索引存在。** 判断依据永远是 `EXPLAIN` 的 `key`，不是"我写的是范围条件"。

## 一句话

`EXPLAIN` 把"慢"变成可指认的数字：`type` 看访问方式、`key` 看有没有走索引、`rows` 只是估算。索引没用上有三种原因——**列被加工**、**索引结构不允许最左前缀或前缀通配符**、**优化器主动放弃**；只有前两种能靠改写法解决。找起点永远是慢查询日志，按总耗时聚合，不是按单次最慢。
