# 11 · 执行计划与慢查询

## 这一课你要会

- 用 `EXPLAIN` 看出一句查询是走索引还是全表扫；
- 读懂 `type` 与 `key` 两列，知道哪个值代表"最差"；
- 说出五种常见的索引失效写法，并改成能走索引的写法。

## 为什么

"这条查询慢"不是一个可以拿来讨论的描述。慢可能是：没走索引、走了但选错了索引、数据量本身大、锁等待、网络慢、或者代码在循环里查了一千次。

`EXPLAIN` 的作用是把"慢"变成**可指认的一件事**：这句查询扫了多少行、用了哪个索引、拿到之后还要额外过滤吗。

## 讲解

### 怎么用

```sql
EXPLAIN SELECT * FROM orders WHERE uid = 1;
```

它不真正执行查询，只打印**执行计划**：数据库打算怎么拿到这些行。

最常看的是这几列：

| 列 | 意思 | 关注点 |
| --- | --- | --- |
| `type` | 访问方式 | `ALL` 是全表扫，最差；`index` 是全索引扫；`ref`/`range`/`eq_ref` 是好的 |
| `possible_keys` | 理论上能用哪些索引 | 有值但 `key` 是 `NULL`，说明优化器全都没选 |
| `key` | 实际用了哪个索引 | 是 `NULL` 就是没走索引 |
| `key_len` | 索引用了多少字节 | 复合索引时能看出用了几列 |
| `rows` | 预估要扫多少行 | 越大越慢 |
| `Extra` | 附加信息 | `Using filesort`、`Using temporary` 要留意 |

`type` 的好坏顺序（从好到差）：

```text
system > const > eq_ref > ref > range > index > ALL
```

看到 `ALL` 基本就等于"这张表被完整扫了一遍"。

### `FORMAT=TREE`：更好读的版本

MySQL 8 支持树形输出，读起来更直观：

```sql
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE uid = 1;
```

输出类似：

```text
-> Filter: (orders.uid = 1)  (cost=0.75 rows=1)
    -> Table scan on orders  (cost=0.75 rows=5)
```

`Table scan` 就是全表扫。建了索引之后：

```text
-> Index lookup on orders using idx_orders_uid (uid=1)  (cost=0.70 rows=2)
```

`Index lookup` + 索引名，就是走索引了。

**诀窍：只看两个词。** 出现 `Table scan` 就是扫全表；出现 `Index lookup` / `Index range scan` 就是用了索引。

### 五种索引失效的写法

这一节是整门课最实用的一段。规律只有一句：**列被加工过，索引就用不上。**

**一、函数包住列**

```sql
-- 失效
WHERE YEAR(created) = 2026
-- 改成范围
WHERE created >= '2026-01-01' AND created < '2027-01-01'
```

**二、运算包住列**

```sql
-- 失效
WHERE amount * 2 > 100
-- 改成把运算移到右边
WHERE amount > 50
```

**三、以通配符开头的 LIKE**

```sql
-- 失效
WHERE name LIKE '%线'
-- 能走索引（前缀匹配）
WHERE name LIKE '数据%'
```

**四、隐式类型转换**

```sql
-- code 是 VARCHAR，传了数字：失效
WHERE code = 123
-- 传字符串：可用
WHERE code = '123'
```

反过来也有问题：`phone` 是 `BIGINT` 而参数是字符串，同样会转换。**参数类型与列类型必须一致。**

**五、复合索引违反最左前缀**

上一关讲过：`(city, age)` 索引上用 `WHERE age = 20` 用不上。

### 关于 `rows` 的误读

`rows` 是**预估**值，不是真实扫描行数。优化器的统计信息来自采样，可能不准；数据分布倾斜时偏差会很大。

所以判断"有没有问题"主要看 `type` 和 `key`，`rows` 只用来做粗判断。要看真实数字用：

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE uid = 1;
```

它会**真的执行**这句查询，打出每一段的实际耗时与实际行数。代价是查询确实跑了——所以别在生产上对 `DELETE`/`UPDATE` 用它。

### 慢查询日志：找到该看哪一句

`EXPLAIN` 解决的是"我知道这句慢"。但通常你不知道是哪句慢。这就要开慢查询日志：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;      -- 超过 1 秒记录
```

日志里会记下执行超过阈值的语句、耗时、扫描行数。**排查顺序：先看日志找出最频繁且最慢的几条，再逐个 `EXPLAIN`。**

## 跑一遍

<!-- run -->
```sql
CREATE TABLE orders (
  id      INT PRIMARY KEY AUTO_INCREMENT,
  uid     INT NOT NULL,
  amount  DECIMAL(10,2) NOT NULL,
  created DATETIME NOT NULL
);
INSERT INTO orders (uid, amount, created) VALUES
  (1, 100.00, '2026-10-01 10:00:00'),
  (1, 250.00, '2026-10-02 11:00:00'),
  (2,  80.00, '2026-10-03 12:00:00'),
  (2, 300.00, '2026-10-04 13:00:00'),
  (3,  50.00, '2026-10-05 14:00:00');

SELECT COUNT(*) AS orders_total FROM orders;

EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE uid = 1;

CREATE INDEX idx_orders_uid ON orders (uid);

EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE uid = 1;
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE amount * 2 > 100;
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE created >= '2026-10-03';
```
```text
orders_total=5
EXPLAIN=-> Filter: (orders.uid = 1)  (cost=0.75 rows=1)
    -> Table scan on orders  (cost=0.75 rows=5)

EXPLAIN=-> Index lookup on orders using idx_orders_uid (uid=1)  (cost=0.70 rows=2)

EXPLAIN=-> Filter: ((orders.amount * 2) > 100)  (cost=0.75 rows=5)
    -> Table scan on orders  (cost=0.75 rows=5)

EXPLAIN=-> Filter: (orders.created >= TIMESTAMP'2026-10-03 00:00:00')  (cost=0.75 rows=2)
    -> Table scan on orders  (cost=0.75 rows=5)
```

对照着看四段：

1. 建索引前：`Table scan`，全表 5 行都读。这就是 `type=ALL` 的样子。
2. 建 `uid` 索引后：`Index lookup on ... using idx_orders_uid`，走索引了。
3. `amount * 2 > 100`：列被运算包住，只能 `Table scan`。
4. `created >= '2026-10-03'`：范围条件本身能走索引，但 `created` 这一列**没建索引**，所以还是全表扫。条件写对了不等于索引存在。

`orders_total=5` 是表里的总行数，用来对照 `rows` 那一列的量级。

## 常见误区

### 误区：`possible_keys` 有值就说明用了索引

**你以为**：这一列不为空，就是走索引了。
**其实**：它只表示"理论上可用"。真正用了哪个要看 `key`，`key` 为 `NULL` 就是没用。
**怎么验证**：找一条 `possible_keys` 有值而 `key` 为 `NULL` 的查询，看 `type` 是不是 `ALL`。

### 误区：加了索引、查询还是慢，说明索引没用

**你以为**：索引建了没效果就是白建。
**其实**：可能是索引失效的写法（函数、运算、通配符开头、类型不匹配、最左前缀），也可能是返回行数占比太高，优化器主动放弃了索引。
**怎么验证**：`EXPLAIN` 对比改写法前后的 `key` 与 `type`。

### 误区：优化就该先看最慢的那条

**你以为**：耗时最大的那条最该优化。
**其实**：一条每秒跑 100 次的 100 ms 查询，比一天一次 5 秒的语句影响大得多。看"总耗时 = 单次耗时 × 次数"。
**怎么验证**：慢查询日志里按"总耗时"而不是"单次最长"排序。

## 小结

`EXPLAIN` 把"慢"变成可测量的数字：`type` 看访问方式、`key` 看是否走索引、`rows` 是预估扫描量。判断诀窍是找 `Table scan` 还是 `Index lookup`。索引失效的根因统一是"列被加工过"。先开慢查询日志找出该看哪句，再逐个 `EXPLAIN`，按总收益排序优化。
