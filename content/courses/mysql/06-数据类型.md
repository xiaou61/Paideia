# 06 · 数据类型怎么选

## 这一课你要会

- 说清为什么金额必须用 `DECIMAL`，`FLOAT`/`DOUBLE` 错在哪；
- 分清 `VARCHAR` 与 `CHAR`，知道长度按字符算不按字节算；
- 知道时间类型该选哪一个，以及时区信息到底存在哪。

## 为什么

类型是表结构里**最贵**的决定。改一张有数据的表，加个列还算容易，改类型往往要锁表、改代码、回填数据、还要担心精度。

而且类型选错造成的错误通常是**静默**的：金额差一分钱、时间差八小时、字符串比较漏了空格——都不报错，只在某个业务节点上暴露。

## 讲解

### 金额：`DECIMAL`，没有第二个选项

浮点数用二进制表示，而大多数十进制小数在二进制里是**无限循环**的。就像十进制写不出 1/3，二进制也写不出 0.1。

后果：

```text
0.1 + 0.2 = 0.30000000000000004
```

用 `DOUBLE` 存金额，累加多次之后误差会放大；用 `=` 比较两个金额几乎永远不成立。实测一下就很清楚：

| 类型 | `SUM(amount)`（存 0.1 与 0.2） |
| --- | --- |
| `DOUBLE` | `0.30000000000000004` |
| `DECIMAL(10,2)` | `0.30` |

`DECIMAL(10,2)` 的意思是：**总共 10 位数字，其中 2 位小数**，所以整数部分最多 8 位，范围到 99,999,999.99。它按十进制精确存储，加减乘都是精确的。

选位数时的规则：

- 金额：`DECIMAL(10,2)` 够大多数业务（到千万级）；货币种类多可以到 `(18,4)`。
- **不要用 `DECIMAL(10,2)` 存汇率**：汇率常要 4–6 位小数，2 位会把 0.0091 存成 0.01。
- `DOUBLE` 留给科学计算、统计指标这类"不需要精确到分"的场景。

### 字符串：`VARCHAR` 还是 `CHAR`

| 类型 | 特点 | 用在 |
| --- | --- | --- |
| `VARCHAR(n)` | 变长，只占实际长度 + 1–2 字节长度信息 | 姓名、标题、邮箱——绝大多数情况 |
| `CHAR(n)` | 定长，不足补空格，取出去掉尾部空格 | 固定长度的代码：国家代码、性别标志 |
| `TEXT` | 变长，最大 64KB，不能有默认值，索引要指定前缀长度 | 长正文 |
| `LONGTEXT` | 最大 4GB | 极长内容 |

**`n` 是字符数，不是字节数。** `VARCHAR(20)` 在 `utf8mb4` 下能存 20 个汉字，但最多占 80 字节。所以"`VARCHAR(20)` 只能存 20 字节"的说法是错的。

`CHAR` 的补空格行为要小心：存 `'ab'` 到 `CHAR(5)` 会变成 `'ab   '`，取值时 MySQL 会把尾部空格去掉。所以它不影响相等比较，但会影响长度计算。

### 一个实际的坑：尾部空格与比较

`VARCHAR` 的比较规则取决于排序规则（collation）。`utf8mb4_0900_ai_ci` 是 NO PAD——**尾部空格参与比较**，`'ab'` 与 `'ab '` 不相等。

而 `CHAR` 会忽略尾部空格。所以用 `CHAR` 存的编码和用 `VARCHAR` 存的同一个值，在某些比较下表现不同。

**实践建议**：入库存之前先 `TRIM`，别让空格进入数据。

### 时间类型：三个选择

| 类型 | 存什么 | 范围 |
| --- | --- | --- |
| `DATE` | 只有日期 | 1000-01-01 到 9999-12-31 |
| `DATETIME` | 日期时间，**不带时区**，存进去什么就是什么 | 同上 |
| `TIMESTAMP` | 日期时间，**按 UTC 存储**，读取时按会话时区转换 | 1970 到 2038 |

关键区别是**时区**：

- `DATETIME` 不做任何转换。应用传 `2026-10-21 10:00:00`，读出来还是这个字面值。跨时区部署时，这个"10 点"是哪里的 10 点没人说得清。
- `TIMESTAMP` 存 UTC，读取时按 `time_zone` 会话变量转成本地时间。同一行数据在不同时区的会话里读出来不一样，但**指向同一个时间点**。

选哪个？看约定。本项目（Paideia）的做法是**应用层统一用 UTC，`DATETIME` 存 UTC，连接串强制 `connectionTimeZone=UTC`**。这样不依赖服务器时区、也不受 2038 限制。

无论选哪个，两条纪律：

1. **写入和读取走同一个时区约定**，别一半本地一半 UTC；
2. **永远别用字符串存时间**（`VARCHAR` 存 `'2026-10-21'`），比较会按字典序、排序会错、函数用不了。

### 枚举与状态：用 `TINYINT` 还是 `VARCHAR`

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| `TINYINT` + 代码里定常量 | 省空间、快 | 可读性差，加值时容易撞号 |
| `VARCHAR(20)` 存字符串 | 可读、加值不用改结构 | 占空间、要防拼写错误 |
| `ENUM` | 数据库层校验 | 加值要改表结构，历史上踩坑多 |

**推荐 `VARCHAR(20)` 存状态字符串**（`paid` / `refund`），除非这张表有千万级行且状态列被高频过滤。理由是：可读性带来的排查效率，比省那几个字节省的价值大得多。

### 布尔值

MySQL 没有真正的布尔类型：`BOOL` / `BOOLEAN` 都是 `TINYINT(1)` 的别名。存 0 和 1。

实践上直接用 `TINYINT(1) NOT NULL DEFAULT 0`，命名上带 `is_` / `has_` 前缀（`is_deleted`、`has_paid`）。

## 跑一遍

<!-- run -->
```sql
CREATE TABLE money_float (id INT PRIMARY KEY, amount DOUBLE);
CREATE TABLE money_decimal (id INT PRIMARY KEY, amount DECIMAL(10,2));
INSERT INTO money_float VALUES (1, 0.1), (2, 0.2);
INSERT INTO money_decimal VALUES (1, 0.1), (2, 0.2);

SELECT SUM(amount) AS float_sum FROM money_float;
SELECT SUM(amount) AS decimal_sum FROM money_decimal;
SELECT SUM(amount) = 0.3 AS float_equals FROM money_float;

CREATE TABLE texts (id INT PRIMARY KEY, code VARCHAR(10), ch VARCHAR(10), created DATETIME);
INSERT INTO texts VALUES (1, ' ab ', '中文', '2026-10-21 10:00:00');
SELECT LENGTH(code) AS code_bytes, CHAR_LENGTH(code) AS code_chars,
       CHAR_LENGTH(ch) AS ch_chars FROM texts;
SELECT code = 'ab' AS equal_raw, TRIM(code) = 'ab' AS equal_trimmed FROM texts;
SELECT created, DATE(created) AS day_only,
       DATE_ADD(created, INTERVAL 1 HOUR) AS plus_hour FROM texts;
```
```text
float_sum=0.30000000000000004
decimal_sum=0.30
float_equals=0
code_bytes=4 | code_chars=4 | ch_chars=2
equal_raw=0 | equal_trimmed=1
created=2026-10-21 10:00:00 | day_only=2026-10-21 | plus_hour=2026-10-21 11:00:00
```

四处对照：

1. `float_sum` 是 `0.30000000000000004`，`decimal_sum` 是精确的 `0.30`。
2. `float_equals=0`：用 `DOUBLE` 存的金额，求和结果**不等于** 0.3。这就是金额必须用 `DECIMAL` 的实证。
3. `code_bytes=4`、`code_chars=4`、`ch_chars=2`：`LENGTH` 数字节，`CHAR_LENGTH` 数字符。两个汉字是 2 个字符、6 个字节。
4. `equal_raw=0`：`' ab '` 带前导空格，不等于 `'ab'`。`TRIM` 之后才相等。

## 常见误区

### 误区：`FLOAT`/`DOUBLE` 只是精度低一点，不影响业务

**你以为**：差那点小数无所谓。
**其实**：误差会累加，而且用 `=` 比较时几乎永远不成立。对账差一分钱、超时判定错一秒，都是这么来的。
**怎么验证**：用 `DOUBLE` 存 0.1 与 0.2 求和再与 0.3 比较，实测返回 0。

### 误区：`VARCHAR(20)` 是 20 个字节

**你以为**：中文字符一个占 3 字节，只能存 6 个。
**其实**：`n` 是字符数，不是字节数。字符占多少字节由字符集和具体字符决定。
**怎么验证**：用 `VARCHAR(20)` 存 20 个汉字，再 `CHAR_LENGTH` 与 `LENGTH` 分别看。

### 误区：时间用字符串存更方便

**你以为**：`VARCHAR` 存 `'2026-10-21 10:00:00'` 也能比大小。
**其实**：字符串比较是字典序，格式稍一变化（少补零、换分隔符）就错；时间函数、区间查询、索引全都用不上。
**怎么验证**：用字符串存 `'2026-9-1'` 与 `'2026-10-1'`，比较大小，看是否符合时间顺序。

## 小结

金额用 `DECIMAL`，浮点存不准。`VARCHAR(n)` 的 `n` 是字符数。`CHAR` 补空格、`VARCHAR` 不补。时间用 `DATETIME`（统一 UTC）或 `TIMESTAMP`（自动转换），不要用字符串。状态优先用 `VARCHAR` 存可读字符串。布尔用 `TINYINT(1)`。
