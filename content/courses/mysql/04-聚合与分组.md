# 04 · 聚合与分组

7 行订单，`COUNT(*)` 数出 7，`COUNT(amount)` 数出 6，`ROUND(AVG(amount),2)` 是 141.75。第三个数字不是 850.50 ÷ 7。先把这 7 行跑出来，再看为什么。

## 跑一遍

下面这一整段会建 `orders`、插入 7 行，再按顺序跑 5 条查询。输出里的 `列=值 | 列=值` 是课程统一格式，不是 MySQL 客户端的样子。5 条查询一共 7 行输出。

<!-- run -->
```sql
CREATE TABLE orders (
  id     INT PRIMARY KEY AUTO_INCREMENT,
  uid    INT NOT NULL,
  amount DECIMAL(10,2),
  status VARCHAR(10) NOT NULL
);
INSERT INTO orders (uid, amount, status) VALUES
  (1, 100.00, 'paid'), (1, 250.00, 'paid'), (2, 80.00, 'paid'),
  (2, 300.00, 'refund'), (3, 50.00, 'paid'), (3, 70.50, 'paid'),
  (4, NULL, 'paid');

SELECT COUNT(*) AS rows_all, COUNT(amount) AS rows_with_amount FROM orders;
SELECT SUM(amount) AS total, ROUND(AVG(amount),2) AS avg_all FROM orders;
SELECT SUM(amount) AS empty_sum FROM orders WHERE uid = 999;
SELECT status, COUNT(*) AS n, SUM(amount) AS total
  FROM orders GROUP BY status ORDER BY status;
SELECT uid, SUM(amount) AS total
  FROM orders WHERE status = 'paid' GROUP BY uid HAVING SUM(amount) > 100 ORDER BY uid;
```
```text
rows_all=7 | rows_with_amount=6
total=850.50 | avg_all=141.75
empty_sum=NULL
status=paid | n=6 | total=550.50
status=refund | n=1 | total=300.00
uid=1 | total=350.00
uid=3 | total=120.50
```

按出现顺序，5 条查询与输出行的对应关系是：

| # | 查询在做什么 | 输出 |
| --- | --- | --- |
| 1 | `COUNT(*)` 与 `COUNT(amount)` | `rows_all=7`、`rows_with_amount=6` |
| 2 | `SUM(amount)` 与 `AVG(amount)` | `total=850.50`、`avg_all=141.75` |
| 3 | 空集合上的 `SUM` | `empty_sum=NULL` |
| 4 | 按 `status` 分组 | `paid`：`n=6`、`total=550.50`；`refund`：`n=1`、`total=300.00` |
| 5 | 先筛 `paid`，再按 `uid` 分组，最后 `HAVING SUM > 100` | uid=1 350.00、uid=3 120.50 |

对着结果看四组数：

1. `rows_all=7` 而 `rows_with_amount=6`：uid=4 那条金额是 `NULL`，被 `COUNT(amount)` 跳过了；`COUNT(*)` 仍然把它算作一行。所以 `status=paid` 的 `n=6` 里有它，`total=550.50` 里没有它。
2. `avg_all=141.75` = 850.50 ÷ **6**，不是 ÷ 7。分母不含 `NULL` 那一行。
3. `empty_sum=NULL`：空集合上 `SUM` 不返回 0。
4. 最后的 `HAVING SUM(amount) > 100` 只留下 uid=1 和 uid=3。uid=2 的已支付只有 80，被筛掉；uid=4 的 `SUM(amount)` 是 `NULL`，`NULL > 100` 是 UNKNOWN，也被筛掉。

## COUNT(*) 和 COUNT(amount)：7 和 6 不是一回事

把 `COUNT` 说成「会把 NULL 排除在外」是不准确的。准确的说法是：**`COUNT(*)` 数行，`COUNT(列)` 数该列的非空值**。7 行就是 7；`amount` 有 1 行是 NULL，所以 `COUNT(amount)` 是 6。表里只有 `COUNT(*)` 写「算所有行」，其余几个都跳过 NULL；关键差别是 `COUNT(*)` 数的是行，不是某一列的值。

| 函数 | 作用 | 对 `NULL` 的处理 |
| --- | --- | --- |
| `COUNT(*)` | 行数 | 算所有行 |
| `COUNT(col)` | 该列非空的行数 | **跳过 `NULL`** |
| `SUM(col)` | 求和 | 跳过 `NULL` |
| `AVG(col)` | 平均 | **跳过 `NULL`（分母也不含它）** |
| `MIN` / `MAX` | 最小 / 最大 | 跳过 `NULL` |

`AVG` 的分母是**非空值的个数**。所以 850.50 ÷ 6 = 141.75；没填金额的人既不加进分子，也不加进分母。如果业务上「没填金额」要按 0 算，写 `AVG(COALESCE(amount, 0))`（`COALESCE(x, 0)` 就是 x 为 NULL 时取 0），分母会变成 7；这两个口径回答的是不同问题，先把业务语义定下来再写 SQL。

空集合上的 `SUM` 返回 `NULL`，不是 0。第 3 条查询 `SELECT SUM(amount) FROM orders WHERE uid = 999` 得到 `empty_sum=NULL`。`COALESCE` 取第一个非 NULL 参数，所以 `COALESCE(SUM(amount), 0)` 就把这个 NULL 变成 0。空集上 `COUNT` 返回 0，`SUM` 返回 `NULL`，这两个空值语义不一样。

## 前端拿到 NULL：不是 NaN

接口把 `NULL` 原样返回，前端会怎样？先把 JS 的实际行为摆出来：

- `null + 1` 得到 `1`；
- `null * 2` 得到 `0`；
- `Number(null)` 得到 `0`；
- `undefined + 1`、`Number(undefined)`、`Number('abc')` 才是 `NaN`。

所以「前端拿 `null` 去做加法就是 `NaN`」是反的。真正危险的是 `null` 被静默当成 0：总金额看起来合理，实际少了一笔。Python 里 `None + 1` 直接抛 `TypeError`，不会给你一个看似合理的数。

接口返回 `NULL` 时，先决定业务语义：没填金额算 0，还是这笔不算？如果算 0，用 `COALESCE(SUM(amount), 0)`；如果「无数据」，保留 `NULL` 并让前端显式处理。别让它悄悄变成 0，也别把「无数据」和「金额是 0」混成同一个值。

## GROUP BY：按值分组，NULL 自成一组

```sql
SELECT status, COUNT(*) AS n
FROM orders
GROUP BY status
```

意思：把 `status` 相同的行归成一组，每组算一个 `COUNT(*)`，输出每组一行。跑一遍里 `paid` 是 6 行、`refund` 是 1 行。

如果分组列有 `NULL`，`NULL` 会单独成一组；它不会并到空串，也不会被丢掉。`COUNT(*)` 会数这一组，`COUNT(列)` 在该组里仍然跳过 `NULL`。这一课的 `orders` 里 `status` 是 `NOT NULL`，所以看不到这个现象；换成可空列分组时，记得它单独占一行。

`SELECT` 里的非聚合列要出现在 `GROUP BY` 里。MySQL 8 默认开启 `ONLY_FULL_GROUP_BY`，写漏了会报错；例外是按主键/唯一键分组时，函数依赖的列可以省略。比如 `orders.id` 是主键，`SELECT id, uid, COUNT(*) FROM orders GROUP BY id` 能跑，因为 `uid` 由 `id` 唯一决定。对初学者仍建议写全，别依赖这个判断。**也别为了让它跑通把 `ONLY_FULL_GROUP_BY` 关掉**：关掉等于让数据库随便挑一个值，错误会藏起来。

## WHERE 与 HAVING：分组前和分组后

SQL 的逻辑执行顺序是：

```text
FROM → WHERE → GROUP BY → 聚合 → HAVING → SELECT → ORDER BY → LIMIT
```

由此推出两条规则：

- **`WHERE` 在分组之前**：它过滤的是「行」，所以不能引用聚合结果。`WHERE SUM(amount) > 100` 直接报错。
- **`HAVING` 在分组之后**：它过滤的是「组」，可以用聚合结果。`HAVING SUM(amount) > 100` 合法。

需求是「统计每个用户已支付订单的总额，只要超过 100 的」。正确写法：

```sql
SELECT uid, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY uid
HAVING SUM(amount) > 100;
```

结果是 uid=1 的 350.00 和 uid=3 的 120.50。uid=2 的已支付只有 80，被 `HAVING` 筛掉；uid=4 的 `SUM(amount)` 是 `NULL`，`NULL > 100` 是 UNKNOWN，也不在结果里。

错误写法是把逐行条件放进 `HAVING`：

```sql
SELECT uid, SUM(amount) AS total
FROM orders
GROUP BY uid
HAVING status = 'paid';
```

MySQL 8 报的是：

```text
ERROR 1054 (42S22): Unknown column 'status' in 'having clause'
```

不是 1055。`status` 既不在 `GROUP BY` 里，也不是聚合结果，MySQL 在 `HAVING` 阶段找不到它。即使在某些宽松设置下让它跑，逻辑也不对：它会在每个 uid 组里挑一个 `status` 来判断，组里混了 `paid` / `refund` 时含义就变了。

**实践原则：能放 `WHERE` 的就不要放 `HAVING`。** `WHERE` 先执行，能提前把行减少，后面的分组少干活；放在 `HAVING` 里等于先全部分组、再筛掉大部分。但别把聚合条件硬挪到 `WHERE`——那里根本不能写 `SUM`。

## 还差的

- **`ONLY_FULL_GROUP_BY` 的函数依赖只举了主键例子**。联合唯一键、视图、派生表里的判断没实测；这一课只到「按主键分组可以省略依赖列」。
- **`COUNT(DISTINCT)`、窗口函数、`WITH ROLLUP` 没展开**。本课只到单列/多列分组的基础，连接后的重复计数留到第 05 课。
- **`GROUP BY` 的执行成本没量化**。只知道早过滤能少干活，少多少没测；临时表还是哈希聚合也没看执行计划。
- **前端只给了 JS 和 Python 两条语言事实**。你项目里的 JSON 序列化框架把 `NULL` 变成什么，没覆盖。
