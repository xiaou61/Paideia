# 04 · 聚合与分组

## 这一课你要会

- 用 `COUNT` / `SUM` / `AVG` / `MIN` / `MAX` 把多行压成一个数；
- 分清 `COUNT(*)` 与 `COUNT(列)`；
- 说清 `WHERE` 和 `HAVING` 各在哪一步生效，什么时候必须用后者。

## 为什么

业务上绝大多数问题都是"统计"：这个月卖了多少、每个用户下过几单、哪个部门平均薪资最高。

聚合看起来只是换个函数，但它有两个藏得很深的坑：**`COUNT` 会把 `NULL` 排除在外**，以及**`WHERE` 在分组之前运行**。这两条都会让数字看起来合理、实际错得很干净。

## 讲解

### 五个聚合函数

| 函数 | 作用 | 对 `NULL` 的处理 |
| --- | --- | --- |
| `COUNT(*)` | 行数 | 算所有行 |
| `COUNT(col)` | 该列非空的行数 | **跳过 `NULL`** |
| `SUM(col)` | 求和 | 跳过 `NULL` |
| `AVG(col)` | 平均 | **跳过 `NULL`（分母也不含它）** |
| `MIN` / `MAX` | 最小 / 最大 | 跳过 `NULL` |

关键差别只有一处：`COUNT(*)` 数行，`COUNT(col)` 数非空值。

如果一张表有 6 行、其中 1 行的 `salary` 是 `NULL`：

- `COUNT(*)` = 6
- `COUNT(salary)` = 5
- `AVG(salary)` = 5 个数之和 ÷ **5**（不是 6）

最后这条最容易被忽略：`AVG` 的分母是**非空值的个数**。所以"平均薪资"里，没填薪资的人既不加进分子也不加进分母，等于被无视了。业务上如果"没填薪资"应该算 0，那得显式写 `AVG(COALESCE(salary, 0))`。

### `SUM` 全空时返回 `NULL` 不是 0

一个空集合（或被 `WHERE` 过滤空了）上 `SUM` 的结果是 `NULL`。所以 `SELECT SUM(amount) FROM orders WHERE uid = 999` 返回 `NULL`。

接口里直接返回这个值，前端拿到 `null` 去做加法，结果就是 `NaN`。**要么用 `COALESCE(SUM(amount), 0)`，要么在代码里兜住。**

### `GROUP BY`：按某列的值分组

```sql
SELECT status, COUNT(*) AS n
FROM orders
GROUP BY status
```

意思：把 `status` 相同的行归成一组，每组算一个 `COUNT(*)`，输出每组一行。

**规则**：`SELECT` 里出现的非聚合列，必须出现在 `GROUP BY` 里。上例中 `status` 在 `SELECT` 里，就必须在 `GROUP BY` 里。

MySQL 8.0 默认开启了 `ONLY_FULL_GROUP_BY`，写错会直接报错——这是好事，比旧版本悄悄返回一个不确定的值强。**别为了让它跑通把这个模式关掉**，那等于把错误藏起来。

### `WHERE` 与 `HAVING`：两步，顺序不能换

这是本关的核心。SQL 的执行顺序是：

```text
FROM → WHERE → GROUP BY → 聚合 → HAVING → SELECT → ORDER BY → LIMIT
```

由此推出两条规则：

- **`WHERE` 在分组之前**：它过滤的是"行"，所以**不能引用聚合结果**。`WHERE SUM(amount) > 100` 直接报错。
- **`HAVING` 在分组之后**：它过滤的是"组"，可以用聚合结果。`HAVING SUM(amount) > 100` 合法。

**实践原则：能放 `WHERE` 的不要放 `HAVING`。** 因为 `WHERE` 先执行，能提前把行减少，后面的分组就少干活。放在 `HAVING` 里等于先全部分组、再筛掉大部分。

### 一个常见错误：把逐行条件写成聚合条件

需求是"统计每个用户已支付订单的总额，只要超过 100 的"。

```sql
-- 对：按状态过滤行，再分组，最后筛组
SELECT uid, SUM(amount) AS total
FROM orders
WHERE status = 'paid'
GROUP BY uid
HAVING SUM(amount) > 100;

-- 错：把状态条件放进 HAVING
SELECT uid, SUM(amount) AS total
FROM orders
GROUP BY uid
HAVING status = 'paid';   -- 报错：status 不在 GROUP BY 里，也不是聚合
```

第二种即使在某些宽松设置下能跑，逻辑也是错的：它在"已经按 uid 分好组"之后去判断组里随便哪一行的 `status`，含义完全变了。

## 跑一遍

<!-- run -->
```sql
CREATE TABLE orders (
  id     INT PRIMARY KEY AUTO_INCREMENT,
  uid    INT NOT NULL,
  amount DECIMAL(10,2),
  status VARCHAR(10) NOT NULL
);
INSERT INTO orders (uid, amount, status) VALUES
  (1, 100.00, 'paid'), (1, 250.00, 'paid'), (2, 80.00, 'paid'),
  (2, 300.00, 'refund'), (3, 50.00, 'paid'), (3, 70.50, 'paid'),
  (4, NULL, 'paid');

SELECT COUNT(*) AS rows_all, COUNT(amount) AS rows_with_amount FROM orders;
SELECT SUM(amount) AS total, ROUND(AVG(amount),2) AS avg_all FROM orders;
SELECT SUM(amount) AS empty_sum FROM orders WHERE uid = 999;
SELECT status, COUNT(*) AS n, SUM(amount) AS total
  FROM orders GROUP BY status ORDER BY status;
SELECT uid, SUM(amount) AS total
  FROM orders WHERE status = 'paid' GROUP BY uid HAVING SUM(amount) > 100 ORDER BY uid;
```
```text
rows_all=7 | rows_with_amount=6
total=850.50 | avg_all=141.75
empty_sum=NULL
status=paid | n=6 | total=550.50
status=refund | n=1 | total=300.00
uid=1 | total=350.00
uid=3 | total=120.50
```

对着结果看三个数：

- `rows_all=7` 而 `rows_with_amount=6`：uid=4 那条金额是 `NULL`，被 `COUNT(amount)` 跳过了。
- `avg_all=141.75` = 850.50 ÷ **6**，不是 ÷ 7。分母不含 `NULL` 那一行。
- `empty_sum=NULL`：空集合上 `SUM` 不返回 0。
- 最后的 `HAVING SUM(amount) > 100` 只留下 uid=1 和 uid=3；uid=2 的已支付只有 80，被筛掉。

## 常见误区

### 误区：`COUNT(*)` 和 `COUNT(列)` 结果总是相同

**你以为**：都在数行数。
**其实**：`COUNT(列)` 跳过该列的 `NULL`。有 `NULL` 时两个数不同。
**怎么验证**：插一行该列为 `NULL` 的记录，对比两个计数。

### 误区：`SUM` 没有行时返回 0

**你以为**：0 行求和就是 0。
**其实**：SQL 里空集合的 `SUM` 是 `NULL`。代码里拿去运算会变成 `null` 或 `NaN`。
**怎么验证**：用一个必定不匹配的条件查询 `SUM`，看返回值。

### 误区：`GROUP BY` 之后还能随便 `SELECT` 其他列

**你以为**：想加什么列就加什么列。
**其实**：非聚合列必须出现在 `GROUP BY` 里，否则在 `ONLY_FULL_GROUP_BY` 下直接报错；关掉这个模式则返回一个不确定的代表值。
**怎么验证**：故意在 `SELECT` 里加一个没分组的列，看 MySQL 8 的报错。

## 小结

`COUNT(*)` 数行、`COUNT(列)` 数非空，`AVG` 的分母也不含 `NULL`，空集合上 `SUM` 返回 `NULL`。`GROUP BY` 按列分组，非聚合列必须出现在里面。`WHERE` 在分组前、`HAVING` 在分组后，能提前过滤就别放在 `HAVING`。
