# 05 · 多表连接

## 这一课你要会

- 分清 `INNER JOIN` 与 `LEFT JOIN` 各自保留哪些行；
- 说清 `ON` 与 `WHERE` 的条件为什么不能随便换位置；
- 知道"连接之后行数变多"是怎么来的，以及怎么避免统计翻倍。

## 为什么

真实的数据从不放在一张表里。用户存在一张表、订单存在另一张，靠 `uid` 关联。要把"每个用户花了多少钱"算出来，就必须连接。

连接是 SQL 里**最容易算错数**的地方。它不报错，甚至结果看着很合理——只是某个用户少算了一笔，或者某笔订单被重复计入两次。这类错误上线后往往要等财务报表对不上才发现。

## 讲解

### 两种最基本的连接

| 类型 | 保留谁 | 用在哪 |
| --- | --- | --- |
| `INNER JOIN` | 两边都匹配上的行 | 只关心有订单的用户 |
| `LEFT JOIN` | 左表全部 + 右表匹配的 | 关心所有用户，包括没下单的 |

右边那个"左表全部"是关键：**没有匹配时，右表的列填 `NULL`，左表的行仍然保留。**

所以"列出所有用户及其订单数"必须用 `LEFT JOIN`。用 `INNER JOIN` 会把没下单的用户整个丢掉——这不是 bug，是 `INNER` 的定义。

### `ON` 与 `WHERE`：位置不同，含义不同

这是本关最重要的一节。看两句话：

```sql
-- A：把条件写在 ON 里
SELECT u.name, o.id
FROM users u LEFT JOIN orders o ON o.uid = u.id AND o.amount > 100;

-- B：把条件写在 WHERE 里
SELECT u.name, o.id
FROM users u LEFT JOIN orders o ON o.uid = u.id
WHERE o.amount > 100;
```

**它们的结果不一样。**

- A：先按要求匹配（只匹配金额 > 100 的订单），然后**左表所有行都保留**。没匹配上的用户右列是 `NULL`，但用户还在。
- B：先做完整个左连接（所有用户都保留），然后 `WHERE o.amount > 100` 把右列是 `NULL` 的行筛掉了——因为 `NULL > 100` 是"未知"。**结果退化成内连接，没下单的用户消失了。**

一句话记住：**`LEFT JOIN` 的右表条件写在 `ON` 里是"过滤匹配"，写在 `WHERE` 里是"过滤结果"。**

左表的条件则相反：写在 `WHERE` 里和写在 `ON` 里（对 INNER JOIN）效果一样，但对 `LEFT JOIN` 写在 `ON` 里不会过滤左表——所以左表条件一律写 `WHERE`。

### 一对多：为什么行数会翻倍

`users` 有一个用户 3 条订单。连接后，这个用户出现 **3 行**——每行配一条订单。

这带来一个经典错误：

```sql
-- 错：每个用户的行数不再是 1
SELECT u.name, o.amount
FROM users u JOIN orders o ON o.uid = u.id;

-- 想统计总金额：SUM 是对的（每笔订单各出现一次）
SELECT u.name, SUM(o.amount) FROM users u JOIN orders o ON o.uid = u.id GROUP BY u.id;

-- 但如果同时要另一张一对多的表，就会交叉相乘
SELECT u.name, COUNT(o.id), COUNT(p.id)
FROM users u
JOIN orders o ON o.uid = u.id
JOIN payments p ON p.uid = u.id   -- 两张都是"多"，行数变成 订单数 × 支付数
GROUP BY u.id;
```

第三种情况叫**笛卡尔积爆炸**：3 条订单和 2 条支付会组合出 6 行，两个 `COUNT` 都变成 6。

**修法二选一**：

1. 分别聚合后再连接（子查询各算各的）；
2. 用 `COUNT(DISTINCT o.id)` / `COUNT(DISTINCT p.id)` 去重计数。

第一种更稳，第二种更快但要记得每处都加 `DISTINCT`。

### `LEFT JOIN` 之后统计，`COUNT` 要数右表的主键

```sql
SELECT u.name, COUNT(o.id) AS n
FROM users u LEFT JOIN orders o ON o.uid = u.id
GROUP BY u.id, u.name;
```

用 `COUNT(o.id)` 而不是 `COUNT(*)`：没订单的用户连接后右列全是 `NULL`，`COUNT(o.id)` 跳过 `NULL` 得到 0，而 `COUNT(*)` 会数到 1。

**这是个高频错误**——"有 0 个订单"被统计成"有 1 个"。

### 找"没有关联记录"的行

三种写法，都能用：

```sql
-- 1. LEFT JOIN + IS NULL
SELECT u.name FROM users u
LEFT JOIN orders o ON o.uid = u.id
WHERE o.id IS NULL;

-- 2. NOT EXISTS（通常最快，也最不容易写错）
SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.uid = u.id);

-- 3. NOT IN（有 NULL 陷阱，慎用）
SELECT u.name FROM users u
WHERE u.id NOT IN (SELECT uid FROM orders);
```

第 3 种在子查询返回 `NULL` 时会**一行都查不到**——因为 `x NOT IN (1, NULL)` 里有"未知"。这一点在第 02 关讲过，这里再强调一次，因为它最常见的实际踩坑场景就是这里。

```sql
  LEFT JOIN orders o ON o.uid = u.id AND o.amount > 90

  LEFT JOIN orders o ON o.uid = u.id
  WHERE o.amount > 90 ORDER BY u.id;

SELECT u.name FROM users u
  WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.uid = u.id) ORDER BY u.id;
```

四处对照着看：

1. `inner_rows=4` 而 `left_rows=6`：多出来的两行是 cid 和 dan——他们有 0 条订单，用 `INNER` 会被直接丢掉。
2. 第三段里 cid 和 dan 的订单数是 **0**，不是 1——因为用的是 `COUNT(o.id)`。
3. 第四段（条件在 `ON`）保留了所有用户：ann 只匹配到金额 > 90 的那一条（100），其余用户右列是 `NULL`，但她们本人还在。
4. 第五段（条件在 `WHERE`）只剩 ann 那一条——**其他用户全没了**，因为 `NULL > 90` 不成立。这就是 `ON` 与 `WHERE` 的区别。

## 常见误区

### 误区：`LEFT JOIN` 和 `INNER JOIN` 只差一点，随便用

**你以为**：反正大部分数据都有匹配。
**其实**：差的就是"没有子记录的那批行"，而这批行往往是业务上最关心的（没下单的用户、没付款的订单）。
**怎么验证**：对同一张表分别跑两种连接，对比行数差值，再去查那些"被丢掉"的行是谁。

### 误区：`ON` 里的条件和 `WHERE` 里的条件是等价的

**你以为**：都是过滤，写哪儿都一样。
**其实**：`LEFT JOIN` 时不等价。右表条件写 `WHERE` 会让未匹配行消失（退化为内连接），写 `ON` 则只影响匹配内容。
**怎么验证**：用同一条查询把条件在 `ON` 与 `WHERE` 之间挪一次，对比行数。

### 误区：连接多张表就是把它们加起来

**你以为**：三张表连接就是三张表的数据合并。
**其实**：是多对多的组合。两张"多"的表连进来，行数会相乘，聚合结果非要用 `DISTINCT` 修正。
**怎么验证**：连接前分别 `COUNT(*)` 两张表，连接后再 `COUNT(*)` 一次，看是不是乘积。

## 小结

`INNER` 只留匹配，`LEFT` 保留左表全部。`LEFT JOIN` 里右表条件写 `ON` 是过滤匹配、写 `WHERE` 会退化成内连接。一对多连接会让行数翻倍，多个一对多连在一起会相乘。统计"没有子记录的行"用 `NOT EXISTS` 最稳。
