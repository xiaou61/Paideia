# 05 · 多表连接

## 同一条查询，条件挪个位置，四行变一行

四张用户、四条订单：ann 下了三单（100、50、30），bob 一单 70，cid 和 dan 没有订单。

我想列「每个用户花了多少钱」，顺手加了金额门槛，第一种写法的条件是跟在连接后面的：

```sql
SELECT u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON o.uid = u.id AND o.amount > 90
ORDER BY u.id, o.id;
```

```text
name=ann | order_id=10
name=bob | order_id=NULL
name=cid | order_id=NULL
name=dan | order_id=NULL
```

四个人都在。第二种写法我只是把条件从句尾挪到了 `WHERE`：

```sql
SELECT u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON o.uid = u.id
WHERE o.amount > 90
ORDER BY u.id, o.id;
```

```text
name=ann | order_id=10
```

只剩一行。**两条 SQL 都没有报错，都是「列用户和订单」，结果一个四个用户一个只有一个。**

我第一次遇到这个的时候花了半小时才相信是条件位置的问题——因为 `WHERE` 里的条件在直觉上只是「再筛一下」，怎么会把 left join 的左表筛掉。

答案是 `o.amount` 在没匹配的行上是 `NULL`，而 `NULL > 90` 是 UNKNOWN，`WHERE` 只保留结果为真的行。于是所有空匹配行被静默丢弃，`LEFT JOIN` 退化成了 `INNER JOIN`。

一句话：**`LEFT JOIN` 里右表的条件写在 `ON` 里是「过滤匹配」，写在 `WHERE` 里是「过滤结果」**——后者会顺手把没有子记录的那批行删掉，而它们往往正是你要找的。

## 两种连接，差的就是那批行

| 类型 | 保留谁 | 典型用途 |
| --- | --- | --- |
| `INNER JOIN` | 两边都匹配上的行 | 只要下过单的用户 |
| `LEFT JOIN` | 左表全部 + 右表匹配的行（无匹配则右列为 `NULL`） | 所有用户，包括没下单的 |

同一份数据：

```sql
SELECT COUNT(*) AS inner_rows FROM users u JOIN orders o ON o.uid = u.id;      -- 4
SELECT COUNT(*) AS left_rows  FROM users u LEFT JOIN orders o ON o.uid = u.id; -- 6
```

差的 2 行就是 cid 和 dan。做「活跃用户占比」这类指标时用错连接，分母会凭空少两个——**不报错，只是数字变了**。

左表自己的条件则相反：写在 `WHERE` 里能过滤左表；写在 `ON` 里对 `LEFT JOIN` 不起过滤作用（左表照样全留）。所以左表条件一律写 `WHERE`。

## 统计时的两个经典坑

**坑一：`COUNT(*)` 把「没有」数成「1」。**

```sql
SELECT u.name, COUNT(o.id) AS order_cnt, COALESCE(SUM(o.amount),0) AS total
FROM users u LEFT JOIN orders o ON o.uid = u.id
GROUP BY u.id, u.name ORDER BY u.id;
```

```text
name=ann | order_cnt=3 | total=180.00
name=bob | order_cnt=1 | total=70.00
name=cid | order_cnt=0 | total=0.00
name=dan | order_cnt=0 | total=0.00
```

没订单的用户连接后是**一行**右列全 `NULL` 的记录。`COUNT(o.id)` 跳过 `NULL` 得 0；`COUNT(*)` 数的是行，得 1。写成 `COUNT(*)` 的报表里，每个注册用户都至少「有 1 单」。

`SUM` 同理：空匹配的 `SUM` 是 `NULL` 不是 0，所以要 `COALESCE`。

**坑二：两张一对多的表一起连，行数相乘。**

```sql
-- 错的写法：3 条订单 × 2 条支付 = 6 行，两个 COUNT 都变成 6
SELECT u.name, COUNT(o.id), COUNT(p.id)
FROM users u
JOIN orders o   ON o.uid = u.id
JOIN payments p ON p.uid = u.id
GROUP BY u.id;
```

每行订单都会和每条支付配对。用户只有 3 单 2 笔支付，连接结果是 6 行——**这不是数据库的 bug，是笛卡尔积的定义**。

两种修法：

1. 分别聚合再连接（子查询各算各的）——更稳，行数不会骗你；
2. `COUNT(DISTINCT o.id)` / `COUNT(DISTINCT p.id)`——更快，但每一处聚合都得记得加，漏一个就错。

## 找「没有子记录」的行

```sql
-- 1. LEFT JOIN + IS NULL
SELECT u.name FROM users u
LEFT JOIN orders o ON o.uid = u.id
WHERE o.id IS NULL;

-- 2. NOT EXISTS
SELECT u.name FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.uid = u.id);

-- 3. NOT IN —— 有 NULL 陷阱
SELECT u.name FROM users u
WHERE u.id NOT IN (SELECT uid FROM orders);
```

第 3 种最危险。子查询里只要出现一个 `NULL`，结果就是**一行都没有**——因为 `x NOT IN (1, 2, NULL)` 等价于 `x != 1 AND x != 2 AND x != NULL`，最后一项是 UNKNOWN，整个 `AND` 链永远不为真。

我倾向用 `NOT EXISTS`：它不依赖列是否可空，语义也直接（「不存在这样的订单」），不会被 NULL 咬。至于哪种更快，取决于索引和数据分布，**我没在同一份数据上做过三方对比**，别把它当结论。

```sql
  name VARCHAR(20) NOT NULL,

);

  id     INT PRIMARY KEY,

);
INSERT INTO users VALUES (1,'ann','北京'), (2,'bob','上海'), (3,'cid','北京'), (4,'dan',NULL);
INSERT INTO orders VALUES (10,1,100), (11,1,50), (12,2,70), (13,1,30);

SELECT COUNT(*) AS inner_rows FROM users u JOIN orders o ON o.uid = u.id;
SELECT COUNT(*) AS left_rows FROM users u LEFT JOIN orders o ON o.uid = u.id;

SELECT u.name, COUNT(o.id) AS order_cnt, COALESCE(SUM(o.amount),0) AS total
  FROM users u LEFT JOIN orders o ON o.uid = u.id
  GROUP BY u.id, u.name ORDER BY u.id;

SELECT u.name, o.id AS order_id FROM users u
  LEFT JOIN orders o ON o.uid = u.id AND o.amount > 90
  ORDER BY u.id, o.id;

SELECT u.name, o.id AS order_id FROM users u
  LEFT JOIN orders o ON o.uid = u.id
  WHERE o.amount > 90 ORDER BY u.id;

SELECT u.name FROM users u
  WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.uid = u.id) ORDER BY u.id;
```
```text
inner_rows=4
left_rows=6
name=ann | order_cnt=3 | total=180.00
name=bob | order_cnt=1 | total=70.00
name=cid | order_cnt=0 | total=0.00
name=dan | order_cnt=0 | total=0.00
name=ann | order_id=10
name=bob | order_id=NULL
name=cid | order_id=NULL
name=dan | order_id=NULL
name=ann | order_id=10
name=cid
name=dan
```

对照着看：

1. `inner_rows=4` 对 `left_rows=6`：多出来的两行是 cid 和 dan，`INNER` 会把他们整个丢掉。
2. 第三段里 cid 和 dan 是 **0** 不是 1——因为用的是 `COUNT(o.id)`。
3. 第四段（条件在 `ON`）保留了四个人，ann 只匹配到金额 > 90 的那一条（100），其他人右列 `NULL` 但人还在。
4. 第五段（条件在 `WHERE`）只剩 ann——其他用户被 `NULL > 90` 静默筛掉。
5. 最后一段 `NOT EXISTS` 正好找回被丢掉的那两个用户。

## 还差的

- **`NOT EXISTS` / `NOT IN` / `LEFT JOIN + IS NULL` 三者的性能我没实测**。只说「我倾向 NOT EXISTS」，不给谁更快的结论。
- **连接顺序对执行计划的影响没验证**。三张表以上时优化器怎么选驱动表、`STRAIGHT_JOIN` 在什么情况下才有必要，我只有文档印象。
- **`COUNT(DISTINCT)` 在大数据量下的代价没量过**。只知道它要额外去重，具体慢多少说不出数字。
