# 13 · 综合案例：设计一个博客库

## 这一课你要会

- 把"用户写文章、给文章打标签、读者评论"拆成五张表，并说清一对多与多对多分别落在哪；
- 给每张表选主键、外键、唯一键和索引，知道它们各自拦住什么错误；
- 写出最新文章、每篇评论数、按标签筛选、翻页这四类查询；
- 看出应用层循环查库的 N+1，并改成一次查询；
- 判断哪些字段值得冗余，以及冗余之后怎么保证它不漂。

## 为什么

前面十二关是分开练的：连接、聚合、索引、事务各一篇。真实工作不会按知识点出题，它先给你一段需求，让你决定表怎么拆。

博客库是最好的练手对象。它小到能画在纸上，却同时包含一对多、多对多、状态、计数、筛选和分页——几乎把关系型数据库的常见结构都占全了。设计对了，后面的查询都很短；设计错了，每个页面都在补窟窿。

这一关不教新语法，只练一件事：**从需求推到表，再从表推回查询。**

## 讲解

### 先写需求，再画表

先把要做的事写成五句话，不要一上来就想字段：

1. 用户用邮箱注册，邮箱不能重复；
2. 用户可以写文章，文章有草稿和已发布两种状态；
3. 文章可以打多个标签，一个标签下也可以有多篇文章；
4. 读者可以评论文章；
5. 首页按发布时间倒序列出已发布文章，并显示每篇的评论数；点进标签可以筛选文章。

接着问四个关系问题，答案直接决定表结构：

| 问题 | 答案 | 结论 |
| --- | --- | --- |
| 一个用户能有几篇文章？ | 多篇 | 一对多 |
| 一篇文章能有几个作者？ | 一个 | 作者 id 放在文章表里 |
| 一篇文章能有几个标签？ | 多个 | 多对多 |
| 一条评论属于几篇文章？ | 一篇 | 评论表里放文章 id |

### 五张表与它们的关系

| 表 | 存什么 | 关键字段 | 关系 |
| --- | --- | --- | --- |
| `users` | 作者与读者 | `id`、`email` | 被 posts / comments 引用 |
| `posts` | 文章 | `author_id`、`status`、`created_at` | 多对一指向 users |
| `comments` | 评论 | `post_id`、`user_id` | 多对一指向 posts 与 users |
| `tags` | 标签字典 | `id`、`name` | 被 post_tags 引用 |
| `post_tags` | 文章与标签的对应 | `(post_id, tag_id)` | 多对多的中间表 |

这里没有 `tag_name` 这样一列直接塞进 `posts`。原因在第 08 关讲过：一篇文章有多个标签，塞进一列就只能存成 `"mysql,数据库"`，而这串文本既不能建索引，也不能保证标签名唯一，想查"所有 mysql 标签的文章"只能 `LIKE '%mysql%'`——数据量一上来就全表扫描，还会把 `mysqld` 这种名字误匹配进来。

**多对多的标准解法就是中间表**：每一行表示"这篇文章有这个标签"，两列合起来做主键，天然防止同一篇文章重复打同一个标签。

### 键怎么选：四种键各管一件事

| 键 | 放在哪 | 拦住什么 | 代价 |
| --- | --- | --- | --- |
| 主键 | 每张表一个，`INT AUTO_INCREMENT` | 一行没有身份、被重复引用 | 自增值会跳号，不要拿它当业务编号 |
| 唯一键 | `users.email`、`tags.name` | 两个用户抢同一个邮箱、标签重复创建 | 插入重复会报 1062，应用要接住 |
| 外键 | `posts.author_id` 等 | 文章指向一个不存在的用户 | 写入多一次检查；删父行会被拦住 |
| 普通索引 | `posts(status, created_at)` 等 | 查询扫全表 | 占空间、拖慢写入 |

几个容易选错的地方：

**主键不要用邮箱。** 邮箱会变、长度大，而且它天然唯一这件事应该交给唯一键表达。主键只负责"这一行是谁"，用与业务无关的自增整数最省事。

**唯一键不是查询优化。** 它的第一职责是让数据库替你拦住重复。两个请求同时注册同一个邮箱，靠"先 SELECT 再 INSERT"是拦不住的——两个 SELECT 都会说"没有"，然后都插入。正确做法是直接 INSERT，让唯一索引报 1062，应用捕获后返回"邮箱已存在"。

**外键要不要用，是一个取舍。** 开发和中小规模系统里，外键能在最早的时间拦住脏数据；超大规模、分库分表或需要频繁批量导入时，外键的检查和 DDL 成本会变成负担，很多团队改成"逻辑外键 + 定期对账"。这一关先用真外键，把关系写清楚。

**索引按查询建，不按字段建。** `posts` 最常用的条件是"已发布、按时间倒序"，所以建联合索引 `(status, created_at)`；`comments` 总是按文章取，所以建 `(post_id, created_at)`；`post_tags` 的主键 `(post_id, tag_id)` 已经能支撑"按文章取标签"，再补一个 `(tag_id, post_id)` 支撑"按标签取文章"。

### 一对多与多对多，写法差在哪

一对多：**外键放在"多"的那一边**。一个用户有多篇文章，所以 `author_id` 在 `posts` 上。反过来把 `post_id` 列表塞进 `users` 就错了——用户表会变成一列不断变长的字符串。

多对多：**关系本身是一张表**。`post_tags` 只有两列，没有自增 id。它的主键 `(post_id, tag_id)` 同时完成两件事：唯一约束（同一篇文章不能重复打同一个标签）和索引（按文章查标签）。

如果以后要给"打标签"这个动作加信息——谁打的、什么时候打的——中间表就再加列，它本来就是一个可以长大的实体。

### 四条必须写对的查询

**一、首页：最新已发布文章 + 评论数。**

```sql
SELECT p.id, p.title, COUNT(c.id) AS comment_count
  FROM posts p
  LEFT JOIN comments c ON c.post_id = p.id
  WHERE p.status = 'published'
  GROUP BY p.id, p.title
  ORDER BY p.created_at DESC, p.id DESC;
```

两个细节：

- 用 `LEFT JOIN`，否则零评论的文章会整个消失；
- 用 `COUNT(c.id)` 而不是 `COUNT(*)`，否则零评论的文章会被数成 1（第 05 关的坑）；
- `ORDER BY` 带上 `id` 做第二排序键。只按 `created_at` 排，同一秒发布的两篇文章在两次请求里可能换位置，翻页时就会重复或漏掉。

**二、每篇评论数（含 0）。** 就是上面这条查询。不要为每篇文章单独发一次 `SELECT COUNT(*)`——那是下一节要说的 N+1。

**三、按标签筛选。**

```sql
SELECT p.id, p.title
  FROM posts p
  JOIN post_tags pt ON pt.post_id = p.id
  JOIN tags t ON t.id = pt.tag_id
  WHERE t.name = 'mysql' AND p.status = 'published'
  ORDER BY p.created_at DESC, p.id DESC;
```

过滤条件在 `tags.name` 上，走 `tags` 的唯一索引先找到标签 id，再用 `post_tags` 的 `(tag_id, post_id)` 索引找到文章，最后回表取标题。这条链路能走通，靠的正是中间表那个反向索引。

**四、翻页。** 小数据量用 `LIMIT ... OFFSET ...` 没问题：

```sql
SELECT id, title FROM posts
 WHERE status = 'published'
 ORDER BY created_at DESC, id DESC
 LIMIT 20 OFFSET 40;
```

但 `OFFSET 100000` 不是"直接跳到第 10 万行"，而是**先数过前 10 万行再丢掉**。深翻页要改成游标：

```sql
SELECT id, title FROM posts
 WHERE status = 'published'
   AND (created_at, id) < ('2026-10-01 09:00:00', 1)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

把上一页最后一行的 `(created_at, id)` 带回来，查询从索引上直接定位，代价与页深无关。代价是不能随机跳到第 500 页——产品上通常用"加载更多"代替页码。

### N+1：一次请求发了一百次查询

新手最容易写出的代码长这样：

```text
posts = query("SELECT id, title FROM posts WHERE status='published' ORDER BY created_at DESC LIMIT 20")
for p in posts:
    p.comment_count = query("SELECT COUNT(*) FROM comments WHERE post_id = ?", p.id)
```

20 篇文章就是 1 + 20 = 21 次数据库往返。页面看着能跑，数据库连接却被这种小查询占满，接口延迟随文章数线性上涨。这就是 N+1。

修法有两种，按场景选：

1. **一次聚合**：上面的 `LEFT JOIN + GROUP BY`，一条查询拿回全部计数；
2. **一次批量取回，应用层分组**：评论本身要展示时，先 `WHERE post_id IN (?, ?, ...)` 一次取回，再按 `post_id` 分组。

同理，给 20 篇文章取标签不要在循环里查，先取文章 id 列表，再 `WHERE post_id IN (...)` 一次查完。

### 事务：哪些写必须绑在一起

博客库有三处写入必须是一个事务：

| 动作 | 一个事务里做什么 | 不这么做会怎样 |
| --- | --- | --- |
| 发文章 | 插 `posts`，再按标签名查/建 `tags`，最后插 `post_tags` | 文章发出去了，标签只写了一半 |
| 发评论 | 插 `comments`，同时 `UPDATE posts SET comment_count = comment_count + 1` | 评论有了，列表上的数字不动 |
| 删文章 | 先删 `comments`、`post_tags`，再删 `posts` | 外键报错，或者留下孤儿行 |

发文章时还有一个并发细节：两个作者同时第一次使用标签 `mysql`，都查不到，都去 `INSERT`，其中一个必然撞唯一键。与其先查再插，不如直接：

```sql
INSERT INTO tags (name) VALUES ('mysql')
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id);
```

它要么插入，要么在冲突时把已有 id 放进 `LAST_INSERT_ID()`，应用拿到的永远是有效 id。这是"让数据库处理竞争"的典型写法。

状态流转也要防并发。发布文章不要写 `UPDATE posts SET status='published' WHERE id=?`，而要把当前状态写进条件：

```sql
UPDATE posts SET status = 'published'
 WHERE id = ? AND status = 'draft';
```

影响行数为 0 说明已经被发布过（或文章不存在），应用据此决定是提示"已发布"还是继续。这样两个并发的发布请求只有一个会成功，不会重复发通知、重复记日志。

### 什么时候该反范式

`comment_count` 是这一关唯一建议冗余的字段。理由是首页每次都要显示它，而实时 `COUNT` 需要扫评论表；文章多、评论多时，这个开销会压在最热的页面上。

但冗余不是白拿的：

- 写评论时必须**在同一个事务里**更新计数；
- 删评论、删文章时也要同步减；
- 任何漏掉的路径都会让计数永久偏大或偏小；
- 所以要有一个定期对账任务，用真实 `COUNT` 修正它。

判断一个字段该不该冗余，用三个问题：

1. 它是不是被高频读取？
2. 它能不能从源数据重新算出来？
3. 我能不能接受它短时间不准，并有一套对账？

三个都是"是"，才值得冗余。像"文章作者名"就不该冗余：用户改名后，所有历史文章都应该显示新名字，而连接 `users` 只是走一次主键索引，很便宜。

## 常见误区

### 误区：标签用逗号分隔存一列就够了

**你以为**：一篇文章的标签不多，存成 `"mysql,数据库"` 最简单，省一张表。
**其实**：这串文本没法建普通索引，按标签筛选只能 `LIKE '%mysql%'` 全表扫描；标签名重复无法约束，改名要更新所有文章；想统计"每个标签多少篇文章"还得在应用层拆字符串。多对多的标准解法是中间表，多一张表的成本远低于这些债。
**怎么验证**：在 `posts` 上对标签列建索引，然后 `EXPLAIN SELECT * FROM posts WHERE tags LIKE '%mysql%'`，看 `type` 是不是 `ALL`；再对比中间表版本的 `ref` 访问。

### 误区：评论数实时 COUNT 一下就行，不用冗余

**你以为**：`COUNT(*)` 很快，列表页每篇查一次没关系。
**其实**：一页 20 篇就是 20 次查询，文章和评论越多越慢，这就是 N+1；把 20 次合成一次 `LEFT JOIN + GROUP BY` 通常够用，只有列表极热、评论极多时才需要把计数冗余到 `posts` 上。
**怎么验证**：打开慢查询日志或 `performance_schema`，数一次首页请求实际发了几条 SQL；再对比合并成一条后的耗时。

### 误区：反范式就是多加一个字段，写完就行

**你以为**：`comment_count` 加上去，首页快了，事情就完了。
**其实**：冗余字段是一份必须手动维护的副本。新增评论、删除评论、删除文章、后台批量导入，每条路径都要在同一个事务里改它；漏一条就会永久偏差。还必须有一个用真实 `COUNT` 对账的任务。
**怎么验证**：随便删一条评论，再对比 `posts.comment_count` 与 `SELECT COUNT(*) FROM comments WHERE post_id=?`，看两者是否还相等。

## 小结

博客库的五张表是这样落下来的：一对多的外键放在"多"的一边（`posts.author_id`、`comments.post_id`），多对多用中间表（`post_tags`），主键只负责身份，唯一键负责拦重复，索引按真实查询建。

四条查询各有陷阱：列表要 `LEFT JOIN` + `COUNT(c.id)`，排序要加唯一列做第二键，深翻页要用游标而不是大 `OFFSET`，循环里查库是 N+1。写入侧，发文章、发评论、删文章都必须是一个事务；标签并发用唯一键加 `ON DUPLICATE KEY` 解决。冗余只留给"高频读、可重算、能对账"的字段。

下一关换一个方向：不设计新表，专门收集那些**不报错但结果不对**的 SQL，以及怎么一步步把它们揪出来。
