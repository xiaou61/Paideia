# 13 · 综合案例：设计一个博客库

## 我的首页把「0 条评论」显示成了「1 条」

需求是这样的五句话：

1. 用户用邮箱注册，邮箱不能重复；
2. 用户可以写文章，文章有草稿和已发布两种状态；
3. 文章可以打多个标签，一个标签下也可以有多篇文章；
4. 读者可以评论文章；
5. 首页按发布时间倒序列出已发布文章，并显示每篇的评论数。

前四句是表结构，第五句是查询。表我画得挺快，查询第一版也写出来了：

```sql
SELECT p.id, p.title, COUNT(*) AS comment_count
  FROM posts p
  LEFT JOIN comments c ON c.post_id = p.id
  WHERE p.status = 'published'
  GROUP BY p.id, p.title, p.created_at;
```

跑起来看着没问题——直到我看见那篇零评论的文章显示 `comment_count=1`。

原因不难：`LEFT JOIN` 在没有匹配时仍然产出一行（右表列全是 NULL），而 `COUNT(*)` 数的是**行**，那行 NULL 也算一行。改成 `COUNT(c.id)`——它只数非 NULL——才得到 0。

这一处错在开发环境里很不容易被发现，因为**测试数据里每篇文章都有评论时，两种写法结果完全一样**。这一关后面所有内容都围绕这个主题：**设计对了，错的地方才看得见**。

## 从需求推到表

先写需求再画字段。需求里的四个关系问题，答案直接决定表结构：

| 问题 | 答案 | 结论 |
| --- | --- | --- |
| 一个用户能有几篇文章？ | 多篇 | 一对多，`author_id` 放 `posts` |
| 一篇文章能有几个作者？ | 一个 | 不用中间表 |
| 一篇文章能有几个标签？ | 多个 | 多对多，要中间表 |
| 一条评论属于几篇文章？ | 一篇 | `post_id` 放 `comments` |

于是五张表：

| 表 | 存什么 | 关键字段 | 关系 |
| --- | --- | --- | --- |
| `users` | 作者与读者 | `id`、`email` | 被 posts / comments 引用 |
| `posts` | 文章 | `author_id`、`status`、`created_at` | 多对一指向 users |
| `comments` | 评论 | `post_id`、`user_id` | 多对一指向 posts 与 users |
| `tags` | 标签字典 | `id`、`name` | 被 post_tags 引用 |
| `post_tags` | 文章与标签的对应 | `(post_id, tag_id)` | 多对多的中间表 |

`posts` 里没有 `tag_names` 这样一列。塞进去就只能存成 `"mysql,数据库"`：这串文本没法建索引，按标签查只能 `LIKE '%mysql%'` 全表扫，还会把 `mysqld`、`mysql-cluster` 全误命中；标签重名也没法约束；想统计"每个标签多少篇文章"还得在应用层拆字符串。

**多对多的标准解法就是中间表**——每一行表示"这篇文章有这个标签"，两列合起来做主键，天然防止同一篇文章重复打同一个标签。

## 四种键各管一件事

| 键 | 放在哪 | 拦住什么 | 代价 |
| --- | --- | --- | --- |
| 主键 | 每张表一个，`INT AUTO_INCREMENT` | 一行没有身份、被重复引用 | 自增值会跳号，不要拿它当业务编号 |
| 唯一键 | `users.email`、`tags.name` | 两个用户抢同一个邮箱、标签重复创建 | 插入重复会报 1062，应用要接住 |
| 外键 | `posts.author_id` 等 | 文章指向一个不存在的用户 | 写入多一次检查；删父行会被拦住 |
| 普通索引 | `posts(status, created_at)` 等 | 查询扫全表 | 占空间、拖慢写入 |

**主键不要用邮箱**：邮箱会变、长度大，它"天然唯一"这件事应该交给唯一键表达。主键只负责"这一行是谁"。

**唯一键不是查询优化**，它的第一职责是让数据库替你拦住重复。两个请求同时注册同一个邮箱，"先 SELECT 再 INSERT"是拦不住的：两个 SELECT 都会说"没有"，然后都插入。正确做法是直接 INSERT，让唯一索引报 1062，应用捕获后返回"邮箱已存在"。

**外键要不要用，是个取舍，不是一个主义**。开发和中小规模系统里，外键能在最早的时间拦住脏数据；超大规模、分库分表或需要频繁批量导入时，外键的检查与 DDL 成本会变成负担，很多团队改成"逻辑外键 + 定期对账"。这一关先用真外键把关系写清楚。

**索引按查询建，不按字段建**。`posts` 最常用的条件是"已发布、按时间倒序"，所以建联合索引 `(status, created_at)`；`comments` 总是按文章取，所以建 `(post_id, created_at)`；`post_tags` 的主键 `(post_id, tag_id)` 已能支撑"按文章取标签"，再补一个 `(tag_id, post_id)` 支撑"按标签取文章"。

## 四条必须写对的查询

**一、首页：最新已发布文章 + 评论数。**

```sql
SELECT p.id, p.title, COUNT(c.id) AS comment_count
  FROM posts p
  LEFT JOIN comments c ON c.post_id = p.id
  WHERE p.status = 'published'
  GROUP BY p.id, p.title, p.created_at
  ORDER BY p.created_at DESC, p.id DESC;
```

三个细节，都是踩过的：

- `LEFT JOIN` 不能换：换成 `INNER JOIN`，零评论的文章会整行消失（产品上表现为"这篇文章发失败了"）；
- `COUNT(c.id)` 不能换成 `COUNT(*)`：就是我开头那个 bug；
- `ORDER BY` 必须带第二排序键 `id`。`created_at` 不唯一，同一秒发布的两篇文章在两次请求里顺序可能不同，翻页时就会重复或漏行。

**二、按标签筛选。**

```sql
SELECT p.id, p.title
  FROM posts p
  JOIN post_tags pt ON pt.post_id = p.id
  JOIN tags t ON t.id = pt.tag_id
  WHERE t.name = 'mysql' AND p.status = 'published'
  ORDER BY p.created_at DESC, p.id DESC;
```

过滤条件在 `tags.name` 上：先走 `tags` 的唯一索引找到标签 id，再用 `post_tags` 的 `(tag_id, post_id)` 索引找到文章 id，最后回表取标题。这条链路能走通，靠的正是中间表那个**反向索引**——如果只有主键 `(post_id, tag_id)`，按标签查文章就只能全表扫 `post_tags`。

**三、翻页（小数据量）。**

```sql
SELECT id, title FROM posts
 WHERE status = 'published'
 ORDER BY created_at DESC, id DESC
 LIMIT 20 OFFSET 40;
```

`OFFSET` 不是"直接跳到第 40 行"，而是**先数过前 40 行再丢掉**。所以 `OFFSET 100000` 会先把 10 万行取出来扔掉——深翻页要改成游标：

```sql
SELECT id, title FROM posts
 WHERE status = 'published'
   AND (created_at, id) < ('2026-10-01 09:00:00', 1)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

把上一页最后一行的 `(created_at, id)` 带回来，从索引上直接定位，代价与页深无关。代价是不能随机跳到第 500 页——产品上通常用"加载更多"代替页码。这里的行值比较方向必须与 `ORDER BY` 一致（都是 `DESC` 配 `<`），方向写反会重复或跳过整页。

**四、N+1：一次请求发了一百次查询。**

新手最容易写出的代码长这样：

```text
posts = query("SELECT id, title FROM posts WHERE status='published' ORDER BY created_at DESC, id DESC LIMIT 20")
for p in posts:
    p.comment_count = query("SELECT COUNT(*) FROM comments WHERE post_id = ?", p.id)
```

20 篇文章就是 1 + 20 = 21 次数据库往返。页面看着能跑，连接池却被这种小查询占满，接口延迟随文章数线性上涨。

修法两种，按场景选：

1. **一次聚合**：上面那条 `LEFT JOIN + GROUP BY`，一条查询拿回全部计数；
2. **一次批量取回，应用层分组**：评论本身要展示时，先 `WHERE post_id IN (?, ?, ...)` 一次取回，再按 `post_id` 分组。

标签同理，不要在循环里查。

## 三处写入必须是一个事务

| 动作 | 一个事务里做什么 | 不这么做会怎样 |
| --- | --- | --- |
| 发文章 | 插 `posts`，按标签名查/建 `tags`，插 `post_tags` | 文章发出去了，标签只写了一半 |
| 发评论 | 插 `comments`，同时 `UPDATE posts SET comment_count = comment_count + 1` | 评论有了，列表上的数字不动 |
| 删文章 | 先删 `comments`、`post_tags`，再删 `posts` | 外键报错，或者留下孤儿行 |

发文章还有一个并发细节：两个作者同时第一次使用标签 `mysql`，都查不到，都去 `INSERT`，其中一个必然撞唯一键。与其先查再插，不如直接：

```sql
INSERT INTO tags (name) VALUES ('mysql')
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id);
```

它要么插入，要么在冲突时把已有 id 放进 `LAST_INSERT_ID()`，应用拿到的永远是有效 id。这是"把竞争交给数据库"的典型写法——你先查再插，中间那段空隙就是竞争窗口。

状态流转也一样。发布文章不要写 `UPDATE posts SET status='published' WHERE id=?`，而要把当前状态写进条件：

```sql
UPDATE posts SET status = 'published'
 WHERE id = ? AND status = 'draft';
```

影响行数为 0 说明已经被发布过（或文章不存在）。这样两个并发的发布请求只有一个会成功，不会重复发通知、重复记日志。

## 什么时候该冗余

`comment_count` 是这一关唯一建议冗余的字段。理由：首页每次都要显示它，实时 `COUNT` 需要扫评论表；文章多、评论多时，这个开销压在最热的页面上。

但冗余不是白拿的：

- 写评论时必须**在同一个事务里**更新计数；
- 删评论、删文章时也要同步减；
- 任何漏掉的路径都会让计数永久偏大或偏小；
- 所以要有一个用真实 `COUNT` 修正它的对账任务。

判断一个字段该不该冗余，问三个问题：**它是不是被高频读取？能不能从源数据重算？我能不能接受它短时间不准、并有对账兜底？** 三个都是"是"，才值得。

像"文章作者名"就不该冗余：用户改名后所有历史文章都该显示新名字，而连接 `users` 只是走一次主键索引，很便宜。

## 这一版明确没做的

- **全文检索**：标题和正文的搜索这一关没做。`LIKE '%关键词%'` 全表扫，MySQL 的 `FULLTEXT` 分词对中文不友好，真要做通常是外挂 Elasticsearch 或上 PG 的 `tsvector`。这是博客库绕不过去的一块，但塞进这一关会让它变成四不像。
- **层级评论**：现在评论是平的。要支持"回复某条评论"，`comments` 得加 `parent_id` 自引用，然后用递归 CTE（MySQL 8 的 `WITH RECURSIVE`）取整棵树——那是另一个话题。
- **权限**：谁能删谁的评论，这一关完全没管。这属于应用层，不是表结构能解决的。
- **文章改名的历史**：`posts.title` 改了就没了旧值。要留历史得另建版本表，代价是每次读取都要选版本。

下一关换方向：不设计新表，专门收集那些**不报错但结果不对**的 SQL，以及怎么一步步把它们揪出来。

**延伸阅读**：[MySQL 8.0 参考手册 · 优化 SELECT 语句](https://dev.mysql.com/doc/refman/8.0/en/select-optimization.html)（把这一关的索引选择与官方的访问类型对照一遍）。
