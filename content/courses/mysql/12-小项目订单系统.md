# 12 · 小项目：订单系统

## 这一课你要会

- 把需求拆成四张表，并说清每张表为什么存在；
- 用一条事务完成"扣库存 + 建订单明细"，并处理库存不足；
- 写出"每个客户贡献多少营收""每个商品卖了多少"这类统计查询。

## 为什么

前面十一关都是单个知识点。真实工作是它们混在一起：设计表、写事务、写统计、还要保证在并发下不出错。

这一关是一个最小但完整的订单系统。跑通它，你就有了一个能对照的样板。

## 讲解

### 需求

三个动作：

1. 下单：选商品、指定数量，扣库存并生成订单；
2. 查订单：看某笔订单买了什么、总价多少；
3. 统计：每个客户花了多少钱、每个商品卖了多少。

### 拆成四张表

| 表 | 存什么 | 为什么单独存在 |
| --- | --- | --- |
| `customers` | 客户姓名、城市 | 客户信息只存一份，改名/搬家只改一处 |
| `products` | 商品名、当前价格、库存 | 库存必须独立成行才能原子扣减 |
| `orders` | 客户、下单时间 | 一个订单可以有多件商品 |
| `order_items` | 订单号、商品、**下单时单价**、数量 | 多对多关系需要中间表；单价必须存快照 |

两个设计决定值得展开：

**一、`order_items.unit_price` 是故意的冗余。** 商品表里的 `price` 是"现在卖多少"，订单里的 `unit_price` 是"当时卖多少"。商品涨价后，历史订单必须显示原价。这不是违反范式，是两个不同的事实（第 08 关讲过）。

**二、库存放在 `products` 上，不单独建库存表。** 因为扣库存要与商品行同锁同事务。单独一张表也能做，但会多一次连接和额外的锁，除非有"多仓"这种真实需求。

### 下单必须是一个事务

四步：检查库存 → 扣减 → 建订单 → 建明细。

关键在于**第一步和第二步要合成一条语句**：

```sql
UPDATE products SET qty = qty - 2 WHERE id = 1 AND qty >= 2;
```

影响行数为 1 说明扣成功，为 0 说明库存不足。**如果先 `SELECT` 查库存再 `UPDATE`，两个并发请求会同时查到"够"，然后都扣。**（第 09、10 关讲过）

应用层的写法大致是：

```text
BEGIN
  UPDATE products ... WHERE id=? AND qty>=?      → 0 行就 ROLLBACK，返回库存不足
  INSERT INTO orders (...)
  INSERT INTO order_items (...)
COMMIT
```

### 统计查询要注意的事

**每个客户的营收**：要连三张表，并且用 `COUNT(DISTINCT o.id)` 数订单数——因为一个订单有多条明细，直接 `COUNT(o.id)` 会把一个订单数成多单。

**每个商品卖了多少**：`SUM(i.qty)` 而不是 `SUM(i.qty * i.unit_price)`——后者是营收，前者是件数。这两个词在中文里差别很小，在报表上差别很大。

**金额一律 `DECIMAL`**：总价用 `SUM(unit_price * qty)` 累加，全程不碰浮点（第 06 关）。

### 建表与数据

```sql
CREATE TABLE customers (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(20) NOT NULL,
  city  VARCHAR(20) NOT NULL
);
CREATE TABLE products (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(30) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  qty   INT NOT NULL
);
CREATE TABLE orders (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,
  created     DATETIME NOT NULL,
  KEY idx_orders_customer (customer_id)
);
CREATE TABLE order_items (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  qty        INT NOT NULL,
  KEY idx_items_order (order_id)
);

INSERT INTO customers (name, city) VALUES ('ann','北京'), ('bob','上海'), ('cid','北京');
INSERT INTO products (name, price, qty) VALUES ('键盘',199.00,10), ('鼠标',89.50,5), ('显示器',1099.00,2);
INSERT INTO orders (customer_id, created) VALUES
  (1, '2026-10-20 10:00:00'), (2, '2026-10-21 09:00:00'), (1, '2026-10-21 15:00:00');
INSERT INTO order_items (order_id, product_id, unit_price, qty) VALUES
  (1, 1, 199.00, 2), (1, 2, 89.50, 1),
  (2, 3, 1099.00, 1),
  (3, 2, 89.50, 3);

SELECT o.id AS order_id, c.name AS customer, SUM(i.unit_price * i.qty) AS total
  FROM orders o
  JOIN customers c ON c.id = o.customer_id
  JOIN order_items i ON i.order_id = o.id
  GROUP BY o.id, c.name
  ORDER BY o.id;
```
```text
order_id=1 | customer=ann | total=487.50
order_id=2 | customer=bob | total=1099.00
order_id=3 | customer=ann | total=268.50
```

三笔订单的总价都是 `DECIMAL` 精确算出来的：`199.00 × 2 + 89.50 × 1 = 487.50`。

```sql
INSERT INTO orders (customer_id, created) VALUES
  (1, '2026-10-20 10:00:00'), (2, '2026-10-21 09:00:00'), (1, '2026-10-21 15:00:00');
INSERT INTO order_items (order_id, product_id, unit_price, qty) VALUES
  (1, 1, 199.00, 2), (1, 2, 89.50, 1),
  (2, 3, 1099.00, 1),
  (3, 2, 89.50, 3);

SELECT c.name AS customer,
       SUM(i.unit_price * i.qty) AS revenue,
       COUNT(DISTINCT o.id) AS order_count
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items i ON i.order_id = o.id
  GROUP BY c.id, c.name
  ORDER BY revenue DESC;

SELECT p.name AS product, SUM(i.qty) AS sold_qty
  FROM order_items i
  JOIN products p ON p.id = i.product_id
  GROUP BY p.id, p.name
  ORDER BY sold_qty DESC;
```
```text
customer=bob | revenue=1099.00 | order_count=1
customer=ann | revenue=756.00 | order_count=2
product=鼠标 | sold_qty=4
product=键盘 | sold_qty=2
product=显示器 | sold_qty=1
```

对照两个地方：

- **`COUNT(DISTINCT o.id)`**：ann 有两笔订单，但她的订单明细有 3 条。不写 `DISTINCT` 会把订单数算成 3。
- **ann 的 756.00** = 487.50 + 268.50。金额跨两笔订单累加，没有浮点误差。

### 下单：一个事务

<!-- run -->
```sql
CREATE TABLE products (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(30) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  qty   INT NOT NULL
);
CREATE TABLE order_items (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  qty        INT NOT NULL,
  KEY idx_items_order (order_id)
);
INSERT INTO products (name, price, qty) VALUES ('键盘', 199.00, 10);

START TRANSACTION;
UPDATE products SET qty = qty - 2 WHERE id = 1 AND qty >= 2;
SELECT ROW_COUNT() AS stock_taken;
INSERT INTO order_items (order_id, product_id, unit_price, qty) VALUES (1, 1, 199.00, 2);
COMMIT;
SELECT name, qty AS stock_after_order FROM products WHERE id = 1;

START TRANSACTION;
UPDATE products SET qty = qty - 100 WHERE id = 1 AND qty >= 100;
SELECT ROW_COUNT() AS stock_taken_when_short;
ROLLBACK;
SELECT name, qty AS stock_after_rollback FROM products WHERE id = 1;
```
```text
stock_taken=1
name=键盘 | stock_after_order=8
stock_taken_when_short=0
name=键盘 | stock_after_rollback=8
```

第二段是关键：要 100 台但只有 8 台，`UPDATE` 影响 0 行。**应用代码看到这个 0 就该 `ROLLBACK` 并告诉用户"库存不足"**——而不是继续插订单。

## 常见误区

### 误区：订单总价可以直接取 `products.price` 算

**你以为**：报表里的营收应该按商品现在的价格算。
**其实**：应该按下单时的 `unit_price`。用当前价格会让历史营收随涨价而"变大"，对账永远对不上。
**怎么验证**：改一次商品价格，再看历史订单总额是否变化。

### 误区：库存扣减可以用"查一下再改"

**你以为**：先 `SELECT qty` 判断够不够，再 `UPDATE`。
**其实**：两个请求之间没有锁保护，并发时会同时判断为"够"。必须把条件写进 `UPDATE` 的 `WHERE`，并检查影响行数。
**怎么验证**：两个会话同时执行"读—判断—写"的流程，观察库存变成负数或被覆盖。

### 误区：订单和明细分两个事务写更安全

**你以为**：分开写，失败一个还能留下另一个。
**其实**：只有订单没有明细，或只有明细没有订单，都是脏数据。它们必须同一个事务。
**怎么验证**：在第二次写入前人为抛错，看回滚后是否两张表都没有残留。

## 小结

订单系统的最小骨架是四张表：客户、商品、订单、订单明细。明细里冗余存下单时单价——这是快照，不是设计错误。下单靠"条件更新 + 检查影响行数"防超卖，整个下单过程一个事务。统计时注意连接后的行数放大，订单数用 `DISTINCT`。

到这里十二关结束。回看一遍你应该能做到：读懂并写对查询、按类型和范式设计表、判断索引有没有用上、说清并发下会发生什么、用一个事务把多步操作串起来。
