# 12 · 小项目：订单系统

## ann 明明只下了两单，报表说三单

运营来对账：报表上 ann 有三笔订单，后台列表只有两笔。

数据没错、SQL 也没报错，错在这一句：

```sql
SELECT c.name, COUNT(o.id) AS order_count
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items i ON i.order_id = o.id
 GROUP BY c.id;
```

`orders` 到 `order_items` 是一对多。ann 的两笔订单一共 3 条明细，一 JOIN **同一个订单就出现 3 次**，`COUNT(o.id)` 数的是明细行数，不是订单数。改成 `COUNT(DISTINCT o.id)` 才是 2。

这个 bug 特别值得记：**连接放大行数**这件事不会报错、不会变慢，只是数字悄悄错了。而且它只在"有多条明细"的数据上才现形——我的测试数据里每单只有一件商品时，两种写法结果完全一样。

这一课把订单系统的四张表、下单事务和三类统计一次做完，中间把这类"不报错但错"的坑逐个标出来。

## 需求

三个动作：

1. **下单**：选商品、指定数量，扣库存并生成订单；
2. **查订单**：看某笔订单买了什么、总价多少；
3. **统计**：每个客户花了多少钱、每个商品卖了多少。

## 拆成四张表

| 表 | 存什么 | 为什么单独存在 |
| --- | --- | --- |
| `customers` | 客户姓名、城市 | 客户信息只存一份，改名/搬家只改一处 |
| `products` | 商品名、当前价格、库存 | 库存必须独立成行才能原子扣减 |
| `orders` | 客户、下单时间 | 一个订单可以有多件商品 |
| `order_items` | 订单号、商品、**下单时单价**、数量 | 多对多关系的中间表；单价必须存快照 |

四个设计决定，每个都有代价：

**一、`order_items.unit_price` 是故意的冗余。** `products.price` 是"现在卖多少"，`order_items.unit_price` 是"当时卖多少"。商品涨价后历史订单必须显示原价，所以这是**两个不同的事实**，不是违反范式。代价：改价时要意识到"历史订单不跟着变"，对账口径要写清楚。

**二、库存放在 `products` 上，不单独建库存表。** 扣库存要与商品行同锁同事务，同一行最省事。等真的出现"多仓"需求再拆表。

**三、`order_items` 要加唯一键。**

```sql
UNIQUE KEY uk_order_product (order_id, product_id)
```

业务上"一张订单里同一个商品只应该有一行"。没有这条约束，重试、并发、代码 bug 都会插出两行同样的商品，而**报表会把它们当成两件商品各算一次**，导致销量翻倍。这类数据在写入时拦得住，事后就只能人工合并。

**四、索引按查询建，不是按"感觉该有"建。**

```sql
KEY idx_orders_customer (customer_id)              -- 查某客户订单
KEY idx_orders_customer_created (customer_id, created)   -- 查某客户最近的订单
KEY idx_items_order (order_id)                    -- 按订单取明细
KEY idx_items_product (product_id, qty)           -- 按商品统计销量（覆盖索引）
```

最后一条值得注意：商品销量统计是 `GROUP BY product_id` + `SUM(qty)`，`(product_id, qty)` 这个联合索引能让查询**只读索引不读行**（覆盖索引）——`EXPLAIN` 里 `Extra` 会显示 `Using index`。

## 下单必须是一个事务

四步：扣库存 → 建订单 → 建明细 → 提交，任一步失败整笔回滚。

关键在第一步：**判断和扣减必须合成一条语句**。

```sql
UPDATE products SET qty = qty - 2 WHERE id = 1 AND qty >= 2;
```

影响行数 1 = 扣成功，0 = 库存不足。**如果先 `SELECT qty` 判断再 `UPDATE`，两个并发请求会同时判断"够"，然后都扣**——中间没有锁（第 09 课讲过这件事）。

```text
BEGIN
  UPDATE products SET qty = qty - ? WHERE id = ? AND qty >= ?   → 0 行就 ROLLBACK，返回库存不足
  INSERT INTO orders (...)                                       → 取回自增 id
  INSERT INTO order_items (...)
COMMIT
```

多商品下单时还有一件事：**扣减顺序要固定**。

```sql
-- 两笔订单都要扣 1 号与 2 号商品
-- 事务 A：先扣 1，再扣 2
-- 事务 B：先扣 2，再扣 1      ← 顺序相反
```

A 拿到 1 号行锁、等 2 号；B 拿到 2 号行锁、等 1 号——**死锁**。InnoDB 会检测到并回滚其中一个，报：

```text
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

正确做法是按 `product_id` 排序后再逐个扣减，让所有事务的加锁顺序一致。死锁不是"偶发故障"，是**可以被代码结构消除的**；消除不掉的那部分才需要应用层重试。

## 三类统计各有各的坑

**每个客户的营收**：连三张表，订单数用 `COUNT(DISTINCT o.id)`——就是开头那个 bug。

**每个商品卖了多少**：`SUM(i.qty)` 是件数，`SUM(i.qty * i.unit_price)` 是营收。中文里"卖了多少"两种意思都通，报表上差一个数量级。

**金额全程 `DECIMAL`**：`SUM(unit_price * qty)` 累加不碰浮点。`DECIMAL` 与 `DECIMAL` 运算的结果仍是 `DECIMAL`，不会中途变成 `DOUBLE`。

```sql
  (1, '2026-10-20 10:00:00'), (2, '2026-10-21 09:00:00'), (1, '2026-10-21 15:00:00');

  (1, 1, 199.00, 2), (1, 2, 89.50, 1),
  (2, 3, 1099.00, 1),
  (3, 2, 89.50, 3);

SELECT o.id AS order_id, c.name AS customer, SUM(i.unit_price * i.qty) AS total
  FROM orders o
  JOIN customers c ON c.id = o.customer_id
  JOIN order_items i ON i.order_id = o.id
  GROUP BY o.id, c.name
  ORDER BY o.id;
```
```text

order_id=2 | customer=bob | total=1099.00
order_id=3 | customer=ann | total=268.50
```

`199.00 × 2 + 89.50 × 1 = 487.50`——整数分算出来，没有 `0.000000001` 那种尾巴。

### 统计：客户营收与商品销量

<!-- run -->
```sql
CREATE TABLE customers (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(20) NOT NULL,
  city  VARCHAR(20) NOT NULL
);
CREATE TABLE orders (
  id          INT PRIMARY KEY AUTO_INCREMENT,
  customer_id INT NOT NULL,
  created     DATETIME NOT NULL,
  KEY idx_orders_customer (customer_id)
);
CREATE TABLE order_items (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  qty        INT NOT NULL,
  KEY idx_items_order (order_id)
);
CREATE TABLE products (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(30) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  qty   INT NOT NULL
);

INSERT INTO customers (name, city) VALUES ('ann','北京'), ('bob','上海'), ('cid','北京');
INSERT INTO products (name, price, qty) VALUES ('键盘',199.00,10), ('鼠标',89.50,5), ('显示器',1099.00,2);
INSERT INTO orders (customer_id, created) VALUES
  (1, '2026-10-20 10:00:00'), (2, '2026-10-21 09:00:00'), (1, '2026-10-21 15:00:00');
INSERT INTO order_items (order_id, product_id, unit_price, qty) VALUES
  (1, 1, 199.00, 2), (1, 2, 89.50, 1),
  (2, 3, 1099.00, 1),
  (3, 2, 89.50, 3);

SELECT c.name AS customer,
       SUM(i.unit_price * i.qty) AS revenue,
       COUNT(DISTINCT o.id) AS order_count
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items i ON i.order_id = o.id
  GROUP BY c.id, c.name
  ORDER BY revenue DESC;

SELECT p.name AS product, SUM(i.qty) AS sold_qty
  FROM order_items i
  JOIN products p ON p.id = i.product_id
  GROUP BY p.id, p.name
  ORDER BY sold_qty DESC;
```
```text
customer=bob | revenue=1099.00 | order_count=1
customer=ann | revenue=756.00 | order_count=2
product=鼠标 | sold_qty=4
product=键盘 | sold_qty=2
product=显示器 | sold_qty=1
```

对照三处：

- **`COUNT(DISTINCT o.id)`**：ann 有 2 笔订单、3 条明细。不写 `DISTINCT` 会数成 3——就是开头那个 bug。
- **ann 的 756.00** = 487.50 + 268.50，跨两笔订单累加没有浮点误差。
- **`cid` 不在结果里**：他从没下过单，而 `JOIN` 把没有匹配的行丢了。要让他出现在报表里、营收显示 0，得用 `LEFT JOIN` 并把 `SUM` 包成 `COALESCE(SUM(...), 0)`——这是报表最常见的"人怎么少了一个"。

### 下单：一个事务

<!-- run -->
```sql
CREATE TABLE products (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  name  VARCHAR(30) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  qty   INT NOT NULL
);
CREATE TABLE order_items (
  id         INT PRIMARY KEY AUTO_INCREMENT,
  order_id   INT NOT NULL,
  product_id INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  qty        INT NOT NULL,
  KEY idx_items_order (order_id)
);
INSERT INTO products (name, price, qty) VALUES ('键盘', 199.00, 10);

START TRANSACTION;
UPDATE products SET qty = qty - 2 WHERE id = 1 AND qty >= 2;
SELECT ROW_COUNT() AS stock_taken;
INSERT INTO order_items (order_id, product_id, unit_price, qty) VALUES (1, 1, 199.00, 2);
COMMIT;
SELECT name, qty AS stock_after_order FROM products WHERE id = 1;

START TRANSACTION;
UPDATE products SET qty = qty - 100 WHERE id = 1 AND qty >= 100;
SELECT ROW_COUNT() AS stock_taken_when_short;
ROLLBACK;
SELECT name, qty AS stock_after_rollback FROM products WHERE id = 1;
```
```text
stock_taken=1
name=键盘 | stock_after_order=8
stock_taken_when_short=0
name=键盘 | stock_after_rollback=8
```

第二段是关键：要 100 台但只有 8 台，`UPDATE` 影响 0 行。**应用代码看到 0 就该 `ROLLBACK` 并返回"库存不足"**，而不是继续插订单。

## 三件我原来以为对的事

**一、`JOIN` 只是把表拼起来，不影响计数。** 一对多连接会让行数放大，`COUNT`、`SUM`、`AVG` 全部跟着偏。凡是要对"父表"计数，先想清楚连接后一个父行会变成几行。

**二、库存不足靠 `SELECT` 判断就够了。** 判断与扣减之间有窗口，并发下两边都会判断"够"。必须把条件写进 `UPDATE ... WHERE`，再看影响行数。

**三、死锁是数据库的锅。** 大部分死锁来自加锁顺序不一致，而这由代码决定。多资源操作按固定顺序（这里是 `product_id` 升序）加锁，能把死锁从"偶发"变成"不发生"。

## 这一课之后

订单系统的最小骨架是四张表：客户、商品、订单、订单明细。明细冗余存下单时单价——那是快照；唯一键防重复明细；索引按查询建。下单靠"条件更新 + 检查影响行数"防超卖，整笔一个事务，多商品按固定顺序加锁防死锁。统计要小心连接放大，订单数用 `DISTINCT`。

到这里 MySQL 这条线结束。回看一遍应该能做到：读懂并写对查询、按类型和范式设计表、判断索引有没有用上、说清并发下会发生什么、用一个事务把多步操作串起来。

**延伸阅读**：[MySQL 8.0 参考手册 · InnoDB 事务隔离](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)（把本项目里的并发结论与官方定义对照一遍）。
