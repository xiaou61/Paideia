# 15 · 测试与构建

## 这一课你要会

- 说清一个 JUnit 测试文件长什么样，`@Test` 与断言各做什么；
- 知道 Maven 的 `pom.xml` 管什么，以及 `mvn test` 与 `mvn package` 的区别；
- 写出一个"能红也能绿"的断言，而不是打印出来看一眼。

## 为什么

Java 项目几乎没有"没有测试"的。不是规矩大，而是 **Java 的编译期检查再严，也查不出"算错了"**。测试是唯一能证明逻辑对的手段。

构建工具同理：手写 `javac` + 手工找 jar 包在第三个依赖时就会崩。Maven 把"依赖、编译、测试、打包"四件事固定下来。

## 讲解

### 一个测试的样子

```text
import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class CalculatorTest {

    @Test
    void addsTwoNumbers() {
        assertEquals(5, Calculator.add(2, 3));
    }
}
```

三件事：

- **`@Test` 标记一个方法**，JUnit 会反射调用它；
- **断言判断对错**，失败会抛 `AssertionFailedError` 并给出期望/实际；
- **测试方法名描述行为**，不是 `test1`。

常用断言：`assertEquals`、`assertTrue`、`assertNull`、`assertThrows`。`assertThrows` 用来验"确实抛了这个异常"——**没有它，抛异常就等于测试失败**，区分不了。

### 为什么不用 `System.out.println` 验证

打印出来看一眼，是手工检查。改动之后要靠人记得回头看。**断言让机器替你盯**，而且能在 CI 里自动跑。

### Maven 的最小知识

`pom.xml` 至少要写：坐标（groupId / artifactId / version）、Java 版本、依赖、插件。

```text
mvn test        # 编译 + 跑测试
mvn package     # 再打成 jar
mvn verify      # 再跑集成测试/校验
```

`src/main/java` 放生产代码，`src/test/java` 放测试。**这个目录结构是 Maven 约定，不是可选的**——放错地方就编译不到。

依赖作用域：`compile`（默认，随产物）、`test`（只测试用，不进最终包）、`provided`（容器提供）。

### 测试该测什么

- **纯逻辑**：算法、校验、格式化——最值得测，也最好测；
- **边界**：空输入、零、负数、超长、重复调用；
- **不该测**：getter/setter 这类没有逻辑的东西。

**不要追求覆盖率数字**。测到"关键分支都走过"比"行覆盖 90% 但全是空断言"有用得多。

### 跑一遍

下面这个例子把"断言"和"手写检查"放在一起，让你看清差别。

<!-- run -->
```java
public class Main {

    static int add(int a, int b) {
        return a + b;
    }

    static int divide(int a, int b) {
        if (b == 0) {
            throw new IllegalArgumentException("除数不能为 0");
        }
        return a / b;
    }

    static void assertEquals(int expected, int actual, String label) {
        if (expected != actual) {
            throw new AssertionError(label + "：期望 " + expected + "，实际 " + actual);
        }
        System.out.println("通过：" + label);
    }

    static void assertThrows(Class<? extends Throwable> type, Runnable action, String label) {
        try {
            action.run();
        } catch (Throwable error) {
            if (type.isInstance(error)) {
                System.out.println("通过：" + label);
                return;
            }
            throw new AssertionError(label + "：抛了 " + error.getClass().getSimpleName());
        }
        throw new AssertionError(label + "：没有抛异常");
    }

    public static void main(String[] args) {
        assertEquals(5, add(2, 3), "2 + 3");
        assertEquals(-1, add(2, -3), "负数相加");
        assertEquals(2, divide(7, 3), "整数除法");

        assertThrows(IllegalArgumentException.class, () -> divide(1, 0), "除数为 0 时拒绝");

        try {
            assertEquals(4, add(2, 3), "故意写错的断言");
        } catch (AssertionError error) {
            System.out.println("断言失败：" + error.getMessage());
        }
    }
}
```
```text
通过：2 + 3
通过：负数相加
通过：整数除法
通过：除数为 0 时拒绝
断言失败：故意写错的断言：期望 4，实际 5
```

最后一段是重点：**断言失败会告诉你期望与实际**。真实项目里这就是 JUnit 做的事，只是它由框架汇总成报告。

## 常见误区

### 误区：打印出来看一眼也算测试

**你以为**：输出对了就算通过。
**其实**：那是手工检查。改动之后要靠人记得回头看；断言让机器盯。
**怎么验证**：故意改坏一个逻辑，看有没有东西自动报错。

### 误区：测试要覆盖每一行才能证明质量

**你以为**：覆盖率越高越好。
**其实**：覆盖率只说明"走过"，不说明"断言对不对"。边界和分支比行数重要。

### 误区：抛异常就等于测试失败

**你以为**：只要程序抛了异常就说明测试错了。
**其实**：有些方法**应该**抛异常。验它用 `assertThrows`，那才是正确行为。

## 小结

`@Test` + 断言，名字描述行为。`assertThrows` 验异常。Maven 按约定分主代码与测试代码，`mvn test` 跑测试。覆盖率不是目标，分支与边界才是。
