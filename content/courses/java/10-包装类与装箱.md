# 10 · 包装类与自动装箱

## 同一个 1000，`==` 说不是，`equals` 说是

```java
public class Main {
    public static void main(String[] args) {
        Integer a = 1000, b = 1000;
        System.out.println("a == b      : " + (a == b));
        System.out.println("a.equals(b) : " + a.equals(b));

        Integer total = null;
        System.out.println(total + 1);
    }
}
```

本机 JDK 25，`javac --release 21 -g Main.java`，`java Main`：

```text
a == b      : false
a.equals(b) : true
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because "total" is null
	at Main.main(Main.java:8)
```

`-g` 只是让 NPE 消息里出现变量名 `total`；不加也能复现，在我这台机器上消息里会显示 `<local3>`。

我原以为 `a == b` 会是 `true`，毕竟两边都是 1000。实际不是：两个 `Integer` 变量都做了装箱，装出来是两个不同对象。`==` 比的是引用，`equals` 才比 `int` 值。

第二段更直接。`Integer` 参与 `+` 时先拆回 `int`，`total` 是 `null`，没有 `intValue()` 可调，程序在这里结束。缓存那个坑不报错，只给你一个容易误读的 `false`；拆箱这个坑会直接抛 NPE。两者不是一类。NPE 是运行期异常，异常机制在第 13 课讲；这里只需要认出它。

## 装箱和拆箱，编译器替你插了什么

八种基本类型各有一个包装类：`int` → `Integer`、`char` → `Character`，其余是首字母大写（`byte` → `Byte`、`short` → `Short`、`long` → `Long`、`float` → `Float`、`double` → `Double`、`boolean` → `Boolean`）。

```java
Integer boxed = 42;    // Integer.valueOf(42)
int unboxed = boxed;   // boxed.intValue()
```

`Integer boxed = 42` 是装箱转换，编译器生成 `Integer.valueOf(42)`；`int unboxed = boxed` 是拆箱转换，生成 `boxed.intValue()`。装箱可能返回缓存对象，也可能新建对象；拆箱遇到 `null` 就是 NPE。

包装类最常见的用途有两类：

- 泛型不能写 `List<int>`，要写 `List<Integer>`；往集合里放 `1` 会装箱，取出来赋给 `int` 会拆箱。
- 需要表达「没有值」：`Integer score = null`，`int` 做不到。

局部变量、方法参数、返回值，只要确定有值，就用 `int`。循环里反复装箱会产生对象；命中缓存的那些除外，但不要靠猜。

`Integer` 没有无参构造器。把 `new Integer()` 单独编译：

```java
public class Main {
    public static void main(String[] args) {
        Integer x = new Integer();
    }
}
```

得到：

```text
Main.java:3: error: no suitable constructor found for Integer(no arguments)
        Integer x = new Integer();
                    ^
    constructor Integer.Integer(int) is not applicable
      (actual and formal argument lists differ in length)
    constructor Integer.Integer(String) is not applicable
      (actual and formal argument lists differ in length)
1 error
```

能写的两个构造器 `Integer(int)` 和 `Integer(String)` 都标了 deprecated for removal。把 `new Integer(100)` 放进 `main` 编译：

```java
public class Main {
    public static void main(String[] args) {
        Integer old = new Integer(100);
        Integer cached = Integer.valueOf(100);
        System.out.println("new Integer(100) == valueOf(100) : " + (old == cached));
        System.out.println("new Integer(100).equals(valueOf(100)) : " + old.equals(cached));
    }
}
```

会看到：

```text
Main.java:3: warning: [removal] Integer(int) in Integer has been deprecated and marked for removal
        Integer old = new Integer(100);
                      ^
1 warning
```

运行输出：

```text
new Integer(100) == valueOf(100) : false
new Integer(100).equals(valueOf(100)) : true
```

自动装箱只走 `valueOf`/装箱转换，不要写 `new Integer`。`new` 出来的对象和缓存里的对象不是同一个，`==` 立刻变成 `false`，而 `equals` 仍然是 `true`。

## 缓存范围：JLS 保证的只有一小段

`valueOf` 可能直接返回缓存里的对象，这个缓存不是 `Integer` 独有：

| 包装类 | JLS 5.1.7 保证的同一性范围 |
| --- | --- |
| `Boolean` | `true`、`false` 两个常量 |
| `Byte` | 全部 256 个值（-128..127） |
| `Short`、`Integer`、`Long` | -128..127 |
| `Character` | `\u0000`..`\u007f`（0..127） |
| `Float`、`Double` | 没有缓存保证 |

`Integer` 的默认 HotSpot 缓存上界是 127；`Long`、`Short` 的缓存也是 -128..127，`Character` 到 127，`Byte` 的 256 个值全在缓存里，`Boolean` 只有两个常量。`Float`/`Double` 在规范里没有同一性保证，别拿 `==` 比。

边界可以真跑出来：

```java
public class Main {
    public static void main(String[] args) {
        Integer a = 127, b = 127;
        Integer c = 128, d = 128;
        System.out.println("127 == 127 : " + (a == b));
        System.out.println("128 == 128 : " + (c == d));
        System.out.println("128 equals : " + c.equals(d));
    }
}
```

```text
127 == 127 : true
128 == 128 : false
128 equals : true
```

同一个 128，`==` 说不同，`equals` 说相同。`127` 之所以是 `true`，是因为它落在 JLS 保证的 `-128..127` 里，两次装箱拿到同一个缓存对象。

`200` 不在这个范围，默认 HotSpot 下是 `false`，但别把 `false` 当成语言保证：

```java
public class Main {
    public static void main(String[] args) {
        Integer a = 200, b = 200;
        System.out.println("200 == 200   : " + (a == b));
        Integer c = 1000, d = 1000;
        System.out.println("1000 == 1000 : " + (c == d));
    }
}
```

默认 `java Main`：

```text
200 == 200   : false
1000 == 1000 : false
```

同一个程序加 `-XX:AutoBoxCacheMax=2000` 再跑：

```text
200 == 200   : true
1000 == 1000 : true
```

JLS 只保证 `-128..127`；实现可以缓存更多，HotSpot 允许用这个参数把上界调大。`200` 的答案因此不是「语言规定 false」，而是「默认 HotSpot 是 false，换实现或换参数就可能变」。结论只有一条：**包装类一律用 `equals`，不要用 `==`**。

如果 `==` 一边是 `int`，包装类会被拆箱，比的是数值；两边都是包装类时，比的才是引用。`Integer a = 1000; a == 1000` 是 `true`（`a` 不为 null 时），`a == b` 才是 `false`。这也是 `==` 容易让人误判的地方。

`equals` 也不是跨类型数值比较：

```text
Integer.valueOf(1).equals(Long.valueOf(1)) : false
```

`Integer.equals` 先看对方是不是 `Integer`，不是就直接 `false`。`Objects.equals(Integer.valueOf(1), Long.valueOf(1))` 同样是 `false`。要跨类型比数值，先统一拆成 `long` 再比。

## 条件表达式：类型先统一，但只算被选中的分支

```java
Integer maybe = null;
Integer result = true ? 0 : maybe;
System.out.println(result);
```

```text
0
```

这里没有 NPE。条件表达式的两个分支，一个是 `int` 字面量 `0`，一个是 `Integer`，类型会统一成 `int`；但**只有被选中的分支会被求值**。`true` 选中 `0`，`maybe` 根本没有参与计算，也就没有拆箱。

把条件改成 `false`，选中的就是 `maybe`：

```java
Integer maybe = null;
Integer result = false ? 0 : maybe;
```

这时才拆箱 `null`，抛 `NullPointerException`。**求值时机和类型统一是两件事**：类型统一决定了「如果选中 `Integer` 分支，要按 `int` 用」；求值规则决定了「没选中的分支不碰」。

安全的写法是先判空，让条件表达式只在 `maybe` 非 null 时走它：

```java
Integer maybe = null;
int safe = maybe == null ? 0 : maybe;
System.out.println(safe);
```

```text
0
```

或者两个分支都用 `Integer`：

```java
Integer safe = maybe == null ? Integer.valueOf(0) : maybe;
```

`Integer total = null; if (total > 0)` 和 `if (total == 0)` 都会拆箱，都是 NPE；只有 `total == null` 是引用比较，不会拆箱。

`Integer.compare(a, b)` 的参数是 `int`，传 `Integer` 会拆箱；任一参数为 `null` 都 NPE。它不处理 null，必须先判空。`a.compareTo(b)` 也一样：`a` 为 null 直接 NPE，`b` 为 null 也会在内部取 `value` 时 NPE。

如果只是判两个包装类是否相等，`Objects.equals(a, b)` 是 null 安全的：`Objects.equals(null, null)` 为 `true`，`Objects.equals(null, 1)` 为 `false`。它内部调用 `equals`，所以 `Integer.valueOf(1)` 和 `Long.valueOf(1)` 仍然是 `false`。

## 两个 `Integer` 相加，结果还是走 `valueOf`

```java
Integer one = 1, two = 2;
Integer three = one + two;
System.out.println("1 + 2 == valueOf(3) : " + (three == Integer.valueOf(3)));

Integer thousand = 1000;
Integer plusOne = thousand + 1;
System.out.println("1000 + 1 == valueOf(1001) : " + (plusOne == Integer.valueOf(1001)));
```

```text
1 + 2 == valueOf(3) : true
1000 + 1 == valueOf(1001) : false
```

`a + b`（两个 `Integer`）的执行顺序是：两个都拆箱成 `int`，相加，再把结果装箱。最后这一步走的是 `Integer.valueOf(int)`，不是 `new Integer`。所以小结果 `3` 命中缓存，`three` 和 `Integer.valueOf(3)` 是同一个对象；`1001` 超出默认缓存，`plusOne` 和 `Integer.valueOf(1001)` 不是同一个对象。

`==` 仍然不可靠，但理由不是「结果一定是新对象」——而是「结果可能命中缓存，也可能不命中，取决于值和实现」。两个操作数任意一个是 `null`，拆箱那一步就 NPE，加法根本不会发生。

## `parseInt` 与 `valueOf`：看你要的是 `int` 还是 `Integer`

```java
int a = Integer.parseInt("42");        // int
Integer b = Integer.valueOf("42");     // Integer
Integer c = Integer.parseInt("42");    // 仍然会装箱
```

`parseInt` 返回 `int`，`valueOf` 返回 `Integer`。所以：

- 目标类型是 `int`：用 `parseInt`，不产生包装对象。
- 目标类型是 `Integer`：用 `valueOf`，需要缓存时它会走缓存。

`Integer c = Integer.parseInt("42")` 这行仍然是装箱：`parseInt` 先得到 `int`，赋值给 `Integer` 时编译器再插一次 `Integer.valueOf`。`c == Integer.valueOf(42)` 是 `true`，不是因为 `parseInt` 返回了 `Integer`，而是因为赋值时又装箱，`42` 命中了缓存。

「能用 `parseInt` 就用它，省一次装箱」只在目标类型是 `int` 时成立；目标类型是 `Integer` 时，省不掉。

`parseInt` 和 `valueOf(String)` 遇到不能解析的字符串都会抛 `NumberFormatException`，不是返回 `null`。

## 包装类当 `HashMap` 的 key

```java
Map<Integer, String> byId = new HashMap<>();
byId.put(1, "a");
System.out.println(byId.get(1));   // a
```

`HashMap` 用 `hashCode` 和 `equals` 找 key。`Integer` 实现了这两个方法，所以 `put(1, ...)` 和 `get(1)` 能对上：两次 `1` 都装箱成缓存里的同一个 `Integer`，`equals` 也为真。

但 `Integer` 和 `Long` 不是同一种 key：

```java
Map<Object, String> keys = new HashMap<>();
keys.put(1, "Integer 1");
System.out.println(keys.get(1L));   // null
```

`Integer.valueOf(1).equals(Long.valueOf(1))` 是 `false`，所以 `get(1L)` 找不到 `1`。`HashMap` 的 key 语义、`equals`/`hashCode` 的契约在第 11 课细讲——下一课就是 `equals 与 hashCode 必须成对`。异常在第 13 课，Optional 在第 18 课。这里只需要记住：包装类做 key 可以，但类型要一致。

## 还差的

- 只讲了包装类的装箱、缓存和拆箱，没有讲 `BigDecimal` 的精度、舍入，以及它的 `equals` 与 `compareTo` 不一致的问题；那是另一套数值语义。
- 没有讲 `Integer` 的进制转换（`parseInt(String, radix)`、`toHexString`）、位运算和 `Number` 基类的 `xxxValue()` 溢出行为；`long` 转 `int` 会截断，这篇没展开。
- 没有讲 `Optional` 在 API 边界上的取舍；它解决的是「返回值可能没有」，不是「包装类可能为 null」的通用替代品，第 18 课再讲。
- 没有讲 `HashMap` 的哈希冲突与扩容；第 11 课讲 `equals`/`hashCode`，第 12 课讲集合选型。
- 缓存数字来自本机 JDK 25 / HotSpot；没有在其他 JVM 厂商和 Java 21 运行时上逐项复测。`-XX:AutoBoxCacheMax` 是 HotSpot 参数，换 JVM 不一定有。
