# 16 · 小项目与并发入门

## 4000 笔只数出 3937 笔

记账本要从 CSV 导入 4000 条流水，四个线程一起数。最直观的写法是共享一个 `int`：

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    static class Counter {
        int value = 0;
        void increment() { value++; }
    }

    static int runOnce() throws Exception {
        Counter counter = new Counter();
        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int i = 0; i < 4000; i++) {
            pool.execute(counter::increment);
        }
        pool.shutdown();
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
            pool.shutdownNow();
            throw new IllegalStateException("线程池没有在 10 秒内结束");
        }
        return counter.value;
    }

    public static void main(String[] args) throws Exception {
        for (int round = 1; round <= 10; round++) {
            System.out.println("第 " + round + " 轮：" + runOnce());
        }
    }
}
```

JDK 25.0.4，4 个线程，4000 个任务，10 轮：

```text
第 1 轮：3964
第 2 轮：3981
第 3 轮：3944
第 4 轮：3959
第 5 轮：3937
第 6 轮：3944
第 7 轮：3963
第 8 轮：3977
第 9 轮：3950
第 10 轮：3952
```

我原来以为 4000 个任务都交给了线程池，`awaitTermination` 也返回了 true，结果就该是 4000。实际 10 轮没有一轮是 4000，最低 3937。你跑出来的数字不会和我一样，但 10 轮都不到 4000，原因就是这个。

`value++` 不是一条原子指令。它至少是读 `value`、加 1、写回 `value` 三步。两个线程都读到 3999，各自算 4000，最后都写 4000，其中一个加号就没了。

怎么自己验证：同一段代码跑 10 轮，别只看一轮；把 4000 改成 40000，少算会更明显，但某一轮刚好 40000 也不能说明没问题——竞态不是每次都出现。

## volatile 只保证看得见，不保证加得对

最容易被当成修法的是给 `value` 加 `volatile`：

```java
static class Counter {
    volatile int value = 0;
    void increment() {
        value++;
    }
}
```

同样 4000 个任务、4 个线程，跑 5 轮：

```text
第 1 轮：3966
第 2 轮：3977
第 3 轮：3960
第 4 轮：3994
第 5 轮：3968
```

还是少。把每个线程改成各 5 万次，另一台机器上记录到 199306、199678；我在 i5-12500H 上复跑是 131501、152561。两台机器的数字差很多，但都少于 200000。

`volatile` 保证的是：对同一个变量，写操作 happens-before 后续的读操作；它还禁止一部分指令重排。它不保证 `value++` 的三步是一个整体。两个线程仍然可以同时读到旧值。

`volatile` 适合一个线程写、其他线程只读的开关，比如 `volatile boolean running`。它不适合计数器，也不适合先判断再修改的复合操作。

怎么自己验证：把 `volatile` 加到上面的 `Counter`，跑 5 轮；再把循环加到 5 万，数字会更接近 200000，但不会稳定等于 200000。

## 四种修法，先选不共享

先问一句：这个计数一定要共享吗？如果每个线程能算自己的局部和，最后合并，连原子类都不用。

| 写法 | 结果 | 什么时候用 |
| --- | --- | --- |
| 裸 `int total` | 错，丢更新 | 只在单线程里用 |
| `volatile int total` | 不够，`total++` 仍丢 | 一个线程写、其他线程只读的开关或状态标志 |
| `AtomicInteger` | 够，无锁 CAS | 多个线程自增同一个计数 |
| `synchronized` | 够，有锁 | 一次要改多个字段，或要维护复合不变式 |

`AtomicInteger` 是计数器最直接的修法：

```java
static final class AtomicCounter {
    private final AtomicInteger value = new AtomicInteger();

    void increment() {
        value.incrementAndGet();
    }

    int value() {
        return value.get();
    }
}
```

`incrementAndGet()` 把读、加、写合成一个原子操作。不要写成 `value.set(value.get() + 1)`，那只是把 `value++` 拆得更明显。

`synchronized` 是另一种：

```java
static final class LockedCounter {
    private final Object lock = new Object();
    private int value;

    void increment() {
        synchronized (lock) {
            value++;
        }
    }

    int value() {
        synchronized (lock) {
            return value;
        }
    }
}
```

两个方法锁的必须是同一个 `lock`。`synchronized (new Object())` 每次新建锁对象，等于没锁；一个方法锁 `this`，另一个锁 `lock`，也等于没锁。锁还负责可见性：读和写都要进同一个锁，读方法不能裸奔。

怎么自己验证：`AtomicInteger` 和 `synchronized` 各跑 10 轮，应该每轮都是 4000。把 `synchronized` 的锁对象换掉再跑，可能少；但竞态不保证每次出现，所以不能拿一次 4000 当证明。

## 小项目：记账本拆四层

并发代码最后要落在一个能维护的小项目里。记账本拆四层：数据、逻辑、存储、入口。

```text
ledger/
  Entry.java            数据：一条只读的账
  LedgerService.java    逻辑：合计、筛选，不碰文件
  LedgerRepository.java 存储：唯一读写 ledger.csv 的地方
  Main.java             入口：解析参数、串起来、打印
```

判断拆得对不对，用一句话：我想测「合计」这条规则，需要造文件吗？不需要，说明逻辑没有漏到存储层。

数据层用不可变对象：

```java
record Entry(String note, int cents) {
}
```

`record` 是第 35 课的内容，这里先照抄。它把 `note` 和 `cents` 变成 final 组件，引用不能再换。但它只做到浅不可变：

```java
record R(int[] a) {}

int[] a = {1, 2};
R r = new R(a);
r.a()[0] = 99;
System.out.println(Arrays.toString(r.a()));
```

```text
[99, 2]
```

`r.a()` 还是原来那个数组，数组内容能改。要深不可变，构造时 `Arrays.copyOf`，访问器也返回拷贝；列表用 `List.copyOf`。`List.copyOf` 只锁住列表结构，元素本身还得不可变。这些第 35 课展开。

`record Entry(String note, int cents)` 现在够用，因为 `String` 和 `int` 本身不可变。换成 `List<String>` 或数组，就要在构造器里做防御性拷贝，否则「不可变」只是引用不可变。

逻辑层只依赖传入的列表：

```java
static int totalCents(List<Entry> entries) {
    return entries.stream().mapToInt(Entry::cents).sum();
}
```

它不读文件、不打印、不碰数据库。测试直接 `totalCents(List.of(new Entry("早餐", 650)))`，不用造 CSV。

存储层是唯一碰文件的地方：`LedgerRepository` 里放一个 `Path`，`load()` 和 `save()` 都在这个类。以后换数据库，只改它。入口 `Main` 最薄：解析参数、调用逻辑和存储、打印结果。

## start() 是开新线程，run() 只是普通调用

```java
Thread worker = new Thread(() -> System.out.println("干活"));
worker.run();    // 仍在 main
worker.start();  // 新线程
worker.join();
```

`run()` 是普通方法调用，当前线程执行，线程对象的状态仍是 `NEW`；`start()` 才让 JVM 创建新线程，再由新线程调用 `run()`。同一个线程对象第二次 `start()` 会抛 `IllegalThreadStateException`。

```text
before run: NEW
run in main
after run: NEW
run in Thread-0
after start+join: TERMINATED
second start: java.lang.IllegalThreadStateException
```

怎么自己验证：在 `run()` 里打印 `Thread.currentThread().getName()`；直接调用看到 `main`，`start()` 后看到另一个名字。或者看 `getState()`：`run()` 之后还是 `NEW`，`start()` 加 `join()` 之后才是 `TERMINATED`。

## join() 只同步它等的那条线程

```java
static int value = 0;

Thread worker = new Thread(() -> value = 42);
worker.start();
worker.join();
System.out.println(value); // 42
```

`join()` 返回后，当前线程能看到被 join 线程结束前的写入。这是 Java 内存模型里的 happens-before，不是「等它结束」这么一句就完了。

但它只对调用 `join()` 的线程生效。线程 A 写了一个对象，主线程 `join(A)` 能看到；如果线程 B 已经在跑，并且它读的时候没有 `volatile`、锁或并发容器，B 仍可能看到旧值。

更隐蔽的是安全发布：

```java
final class Holder {
    int value;
    Holder(int value) {
        this.value = value;
    }
}

static Holder holder; // 没有 volatile

// 写线程
holder = new Holder(42);

// 读线程
if (holder != null) {
    System.out.println(holder.value); // 可能是 0
}
```

读线程可能看到 `holder` 非空，但 `value` 还是 0；也可能一直看到 null。原因是构造对象和把引用赋给 `holder` 之间没有同步，读线程可能先看到引用，后看到字段的默认值。x86 上跑很多次可能都不出现，不能靠跑一遍证明。

「只有一个线程写」也不够。只要还有别的线程在读，而且读的时候没有 `volatile`、没有同一个锁、也不是安全发布后的不可变对象，就可能读到旧值或未安全发布的对象。

要跨线程共享可变状态，选一条：`volatile`（一个变量、写少读多、不要复合操作）、`synchronized`（同一个锁保护读写）、`final` 加正确构造（只保护 final 字段，构造期间 `this` 不能逃逸）、`ConcurrentHashMap` / `BlockingQueue`（并发容器负责发布）、`AtomicReference`（引用替换有 volatile 语义），或者干脆用不可变对象。

`AtomicReference` 只保护引用替换，不保护对象内部字段；放进去的对象仍然要不可变，或者不再修改。

怎么自己验证：写线程构造对象并发布，读线程循环读；这类测试可能一万次都不失败。更可靠的是用 JCStress 这类专门压并发的工具，或者直接检查发布路径有没有上面这些同步手段。

## 线程池：submit 的异常不会自己冒出来

并发任务有一种很坑的失败方式：不报错。

```java
ExecutorService pool = Executors.newFixedThreadPool(1);
Future<?> future = pool.submit(() -> {
    throw new IllegalStateException("boom-submit");
});
pool.shutdown();
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    pool.shutdownNow();
}
System.out.println("submit 后主线程正常结束");
```

```text
submit 后主线程正常结束
```

任务抛了 `IllegalStateException`，控制台什么都没有。`submit` 返回 `Future`，`FutureTask` 把异常存起来；没人调用 `get()`，就没人处理。线上看不到报错时，先查这里。

`get()` 会抛 `ExecutionException`，原始异常在 `getCause()`：

```java
try {
    future.get();
} catch (ExecutionException e) {
    System.out.println("get cause=" + e.getCause());
}
```

```text
get cause=java.lang.IllegalStateException: boom-submit
```

`get()` 还会阻塞到任务结束；批量任务里不要在主线程一个个等，除非你就是要这个顺序。

不想用 `Future`，就用 `execute` 加线程工厂里的 `UncaughtExceptionHandler`：

```java
ThreadFactory factory = task -> {
    Thread thread = new Thread(task, "ledger-worker");
    thread.setUncaughtExceptionHandler((t, e) ->
        System.out.println("uncaught on " + t.getName() + ": " + e));
    return thread;
};

ExecutorService pool = Executors.newFixedThreadPool(1, factory);
pool.execute(() -> {
    throw new IllegalStateException("boom-execute");
});
pool.shutdown();
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
    pool.shutdownNow();
}
```

```text
uncaught on ledger-worker: java.lang.IllegalStateException: boom-execute
```

`execute` 的异常会交给线程的未捕获异常处理器；`submit` 不会，因为 `FutureTask` 先接住了。

`shutdown()` 只是不再接受新任务，不会阻塞等待。`awaitTermination` 才有返回值：`true` 表示在超时前终止，`false` 表示还没完。上面检查了返回值；不检查就可能主线程先走，后台任务还在跑。

怎么自己验证：把 `future.get()` 注释掉跑一次，看不到异常；加回来再跑，能看到 `ExecutionException` 和 cause。把 `awaitTermination` 的返回值打印出来，给一个睡 2 秒的任务、只等 100 毫秒，会看到 `false`。

## 跑一遍

把上面的数据层、逻辑层和原子计数拼成一个能直接跑的程序。存储层为了不依赖文件，下面用内存里的 `List` 代替；真实项目里把 `load()`/`save()` 放进 `LedgerRepository`。

<!-- run -->
```java
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {

    record Entry(String note, int cents) {
    }

    static final class LedgerService {
        static int totalCents(List<Entry> entries) {
            return entries.stream().mapToInt(Entry::cents).sum();
        }
    }

    static final class AtomicCounter {
        private final AtomicInteger value = new AtomicInteger();

        void increment() {
            value.incrementAndGet();
        }

        int value() {
            return value.get();
        }
    }

    public static void main(String[] args) throws Exception {
        var entries = List.of(
                new Entry("早餐", 650),
                new Entry("地铁", 300));
        System.out.println("账目合计（分）：" + LedgerService.totalCents(entries));

        AtomicCounter counter = new AtomicCounter();
        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int i = 0; i < 4000; i++) {
            pool.execute(counter::increment);
        }
        pool.shutdown();
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
            pool.shutdownNow();
            throw new IllegalStateException("线程池没有在 10 秒内结束");
        }
        System.out.println("原子计数：" + counter.value());
    }
}
```
```text
账目合计（分）：950
原子计数：4000
```

这段里 `LedgerService.totalCents` 是纯函数，`AtomicCounter` 是共享计数。4 个线程各跑各的任务，最后 `awaitTermination` 检查是否真的结束。

怎么自己验证：把 `AtomicCounter` 换回裸 `int`，输出可能少几个；把 `awaitTermination` 的返回值忽略掉，程序可能提前打印；把 `pool.shutdown()` 和 `awaitTermination` 都删掉，主线程结束后 JVM 不会退出，因为线程池里的非守护线程还活着。

## 还差的

- 没讲死锁：两个锁的获取顺序、`jstack` 里怎么看 BLOCKED、`tryLock` 超时后怎么退。这篇只到最小修法。
- 没讲线程池参数：核心线程数、最大线程数、队列长度、拒绝策略，以及 Java 21 的虚拟线程和结构化并发。`Executors.newFixedThreadPool` 只是入门。
- 没讲 `CompletableFuture` 的组合、超时和异常传播；多任务有依赖时，`Future.get()` 会写得很别扭。
- 没讲 `record` 的深不可变和防御性拷贝细节，第 35 课展开；这篇只到「浅不可变」这一句。
- 没讲怎么写出可重复的并发测试；JCStress 之类的工具只在验证段落提了名字，没有展开。
