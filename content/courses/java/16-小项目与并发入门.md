# 16 · 小项目与并发入门

## 这一课你要会

- 把一个程序拆成"数据 / 逻辑 / 入口"三层，并说清每层不该做什么；
- 用 `Thread` 或 `ExecutorService` 起并发任务，看到共享可变状态出问题；
- 知道为什么 `i++` 在多线程下会少算，以及最小修法。

## 为什么

前十一课都是单个类。真实项目要分层，否则改一个需求要动整块代码。

并发放在最后一课，是因为它**必须建立在"知道什么被共享"之上**。而"什么被共享"正是前十一课反复在讲的东西：static、引用传递、可变对象。

## 讲解

### 分三层

```text
todo/
  Task.java      数据：一个不可变记录
  TaskService.java  逻辑：纯函数，不碰 I/O
  TaskRepository.java  存储：只管读写文件
  Main.java      入口：解析参数、串起来、打印
```

- **`Task` 用 `record`**：不可变，天然线程安全；
- **`TaskService` 只依赖传入的列表**，不读文件、不打印——所以能直接测；
- **`TaskRepository` 是唯一碰文件的地方**，换成数据库只改它；
- **`Main` 最薄**。

### 起一个线程

```text
Thread worker = new Thread(() -> System.out.println("子线程"));
worker.start();
worker.join();   // 等它结束
```

`start()` 才真正启动；`run()` 只是普通方法调用，仍在当前线程。

现代写法用 `ExecutorService` 管线程池，别自己 `new Thread` 起几百个：

```text
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
    pool.submit(() -> ...);
}
```

### 共享可变状态为什么会出错

```text
class Counter {
    int value = 0;              // 共享
    void increment() { value++; }   // 不是原子操作
}
```

`value++` 实际是三步：读、加、写。两个线程交错时可能都读到 0，各自加 1 写回 1——**两次自增只加了一次**。

修法从轻到重：

1. **不共享**（最好）：每个线程算自己的，最后合并；
2. **不可变**：共享只读数据，不共享可变状态；
3. **同步**：`synchronized` 或 `AtomicInteger`（必要才用，会降低并行度）。

### 结论：先想"要不要共享"

并发的问题不是"锁用得不够"，而是"本来就不该共享的东西被共享了"。写并发代码前先问：**这个变量谁写？** 只有一个线程写，就基本安全。

### 跑一遍

这段会真的起多线程，并演示不加保护时的丢计数。

<!-- run -->
```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {

    record Task(String title, boolean done) {
        Task complete() {
            return new Task(title, true);
        }
    }

    static long unfinished(java.util.List<Task> tasks) {
        return tasks.stream().filter(task -> !task.done()).count();
    }

    static class SafeCounter {
        final AtomicInteger value = new AtomicInteger();

        void increment() {
            value.incrementAndGet();
        }
    }

    public static void main(String[] args) throws Exception {
        var tasks = java.util.List.of(
                new Task("写测试", true),
                new Task("写文档", false),
                new Task("发布", false));
        System.out.println("未完成：" + unfinished(tasks));
        System.out.println(tasks.get(0).complete());

        SafeCounter safe = new SafeCounter();

        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int i = 0; i < 4000; i++) {
            pool.submit(safe::increment);
        }
        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);

        System.out.println("原子计数：" + safe.value.get());
    }
}
```
```text
未完成：2
Task[title=写测试, done=true]
原子计数：4000
```

**这个例子里没有把"不加保护的 int 计数"放进去**，因为它的输出**每次都不一样**：本机线程少、竞争不激烈时常常也是 4000，看起来完全正确。这正是并发 bug 最难的地方——**它不是必然复现**。

想自己看一眼：把 `int value = 0` 与 `value++` 直接写进上面那个类，循环次数加到十万级，多跑几次。多数时候仍然是对的，偶尔少几个——**偶发的那一次才是真相**。所以结论不靠"跑出来对不对"，而是靠"`value++` 不是原子操作"这一条事实。

## 常见误区

### 误区：加个 `synchronized` 就万事大吉

**你以为**：所有并发问题都能靠锁解决。
**其实**：锁会带来死锁、性能下降，而且忘了锁同一个对象等于没加。**先减少共享**。

### 误区：并发 bug 一定会复现

**你以为**：测一遍没问题就没问题。
**其实**：竞态往往只在特定时序出现。它的"没复现"不代表正确。

### 误区：可变数据只要不写就行

**你以为**：多线程读同一个对象没问题。
**其实**：如果一个线程在读、另一个在写，读到的是**中间状态**。只读的前提是"确实没人写"。

## 小结

三层：不可变数据、纯逻辑、只碰 I/O 的存储。线程用 `ExecutorService`，不是裸 `new Thread`。`i++` 不是原子的。并发第一问："这个变量谁写？"
