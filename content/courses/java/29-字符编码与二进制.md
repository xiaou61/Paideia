# 29 · 字符编码与二进制

## 控制台打出「中A?」，内存里的 String 还是 4 个单元

```java
public class Main {
    public static void main(String[] args) {
        String nick = "中A👍";
        System.out.println("stdout.encoding=" + System.getProperty("stdout.encoding"));
        System.out.println("length=" + nick.length());
        System.out.println("console=" + nick);
    }
}
```

本机 JDK 25（Temurin 25.0.4+7，Windows，`native.encoding=GBK`），`javac --release 21 -encoding UTF-8 Main.java` 之后 `java Main`：

```text
stdout.encoding=GBK
length=4
console=中A?
```

把 stdout 重定向到文件，`console=` 后面那四个字节是 `D6 D0 41 3F`：`D6 D0` 是 GBK 的「中」，`41` 是 A，`3F` 是问号。

我一开始以为是终端字体缺字。不是。`length=4` 摆在那里，说明字符串本身一个单元都没少；丢东西的是 **`System.out` 把字符编成字节那一步**——它按 `stdout.encoding=GBK` 编，GBK 里没有 U+1F44D，编码器只能替换成 `?`。加一个参数，重定向出来的同一行就变成 `E4 B8 AD 41 F0 9F 91 8D`：

```text
java -Dstdout.encoding=UTF-8 Main
```

这台机器上 `file.encoding` 和 `stdout.encoding` 是两个独立属性：前者决定 `Charset.defaultCharset()`，JDK 18 起默认 UTF-8（JEP 400）；后者管控制台和重定向输出，默认跟 `native.encoding` 走，也就是这里的 GBK。「JVM 默认编码是 UTF-8」和「屏幕上打出问号」可以同时成立，我原来把这两件事当成一件。

## 三把尺子：8 个字节、4 个代码单元、3 个码点

<!-- run -->
```java
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public class Main {
    public static void main(String[] args) {
        String s = "中A👍";
        byte[] utf8 = s.getBytes(StandardCharsets.UTF_8);
        System.out.println("utf8=" + HexFormat.of().formatHex(utf8) + " (" + utf8.length + " bytes)");
        System.out.println("length=" + s.length());
        System.out.println("codePoints=" + s.codePointCount(0, s.length()));
    }
}
```
```text
utf8=e4b8ad41f09f918d (8 bytes)
length=4
codePoints=3
```

三个数都对，因为量的不是同一样东西：

| 你想问的 | 该用哪个 | `中A👍` 的结果 |
| 占多少存储或带宽 | `getBytes(UTF_8).length` | 8 字节 |
| 字符串里有多少个 `char` | `length()` | 4 |
| 人眼看到几个字符 | `codePointCount` | 3 |

`length()` 数的是 UTF-16 代码单元，`String.length()` 的 javadoc 原文就是「number of Unicode code units」，不是某个实现的巧合；`char` 是 16 位无符号整数，也只等于一个代码单元。BMP（U+FFFF 以内）的字符一个 `char` 就够，`👍`（U+1F44D）要两个 `char` 拼成代理对，所以是 4 而不是 3。

代码单元还能被直接切开：

```java
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public class Main {
    public static void main(String[] args) {
        String half = "👍".substring(0, 1);
        System.out.println(half.length());
        System.out.println(HexFormat.of().formatHex(half.getBytes(StandardCharsets.UTF_8)));
    }
}
```
```text
1
3f
```

`3f` 又是问号，而且这里没有经过任何解码：`substring(0, 1)` 只拿走了一个代理，落单的高位代理照样被编码器替换。我以前把代理对当成「只影响数长度」的问题，实际上 `substring`、`split`、按字数截断这类操作都会把字符切坏。

## 首字节的高位就写明了「我占几个字节」

UTF-8 不是「一个汉字三个字节」，是四种长度，看首字节的高位就知道属于哪组：

| 首字节的位 | 占几个字节 | 码点范围 |
| `0xxxxxxx` | 1 | U+0000–U+007F |
| `110xxxxx` | 2 | U+0080–U+07FF |
| `1110xxxx` | 3 | U+0800–U+FFFF |
| `11110xxx` | 4 | U+10000–U+10FFFF |

上面那串 `e4 b8 ad` 里，`E4` = `1110 0100`，所以是三字节组；后面 `B8` = `1011 1000`、`AD` = `1010 1101` 都以 `10` 开头，是纯负载。把三段低位拼起来：`0100` + `111000` + `101101` = `0x4E2D`，正是「中」。`F0` = `1111 0000` 开头的那组是四字节，所以 `👍` 占 4 个字节、在 Java 里占 2 个 `char`。

「汉字 3 字节」只对 U+4E00–U+9FFF 这一块成立。U+20BB7（𠮷）落在四字节区：`length()` 是 2，`codePointCount` 是 1，UTF-8 是 `f0a0aeb7`。

## 同样 8 个字节，三种解码器，只有两种还能救

把上面那 8 个字节分别交给两种单字节字符集，再把 GBK 的字节当成 UTF-8 读一次：

```java
import java.nio.charset.Charset;
import java.nio.charset.StandardCharsets;
import java.util.Arrays;

public class Main {
    static String cps(String s) {
        StringBuilder b = new StringBuilder();
        s.codePoints().forEach(cp -> b.append(String.format("%04X ", cp)));
        return "[" + b.toString().trim() + "]";
    }

    public static void main(String[] args) {
        byte[] utf8 = "中A👍".getBytes(StandardCharsets.UTF_8);
        Charset win1252 = Charset.forName("windows-1252");

        System.out.println(cps(new String(utf8, StandardCharsets.ISO_8859_1)));
        System.out.println(cps(new String(utf8, win1252)));
        System.out.println(cps(new String("中A".getBytes(Charset.forName("GBK")), StandardCharsets.UTF_8)));

        byte[] backLatin1 = new String(utf8, StandardCharsets.ISO_8859_1).getBytes(StandardCharsets.ISO_8859_1);
        byte[] back1252 = new String(utf8, win1252).getBytes(win1252);
        System.out.println(Arrays.equals(backLatin1, utf8));
        System.out.println(Arrays.equals(back1252, utf8));
    }
}
```
```text
[00E4 00B8 00AD 0041 00F0 009F 0091 008D]
[00E4 00B8 00AD 0041 00F0 0178 2018 FFFD]
[FFFD FFFD 0041]
true
false
```

三行都不是原文，但能否救回来完全不同，关键看有没有 `FFFD`。

ISO-8859-1 把 0x00–0xFF 一对一映射到 U+0000–U+00FF，8 个字节变成 8 个字符，一个都没丢，用同一张表编回去字节一模一样。cp1252 不是：它有五个位置（0x81、0x8D、0x8F、0x90、0x9D）没有定义，`0x8D` 解出来直接是 U+FFFD，再编码变成 `3F`。

所以 `�`（U+FFFD）是可逆性的墓碑：它一出现，原始字节就已经被替换掉，后面换什么编码都救不回来。第三行更干脆，GBK 的两个字节 `D6 D0` 在 UTF-8 里不合法，解码器给出两个 U+FFFD。

## 「ä¸­æ–‡」不是 ISO-8859-1 造出来的

「中文」的 UTF-8 是 `e4 b8 ad e6 96 87`。用 cp1252 解开，得到 6 个码点：

```text
[00E4 00B8 00AD 00E6 2013 2021]
```

`2013`（–）和 `2021`（‡）在 ISO-8859-1 里根本不存在——那两个位置是 0x96、0x87，属于 C1 控制符，屏幕上连字形都没有。所以在 Windows 上看到 `ä¸­æ–‡`，说明解码用的是 **windows-1252**（Windows 英文版所谓的 ANSI），不是 ISO-8859-1。这个区别决定怎么反推：

```java
import java.nio.charset.Charset;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public class Main {
    public static void main(String[] args) {
        String bad = "ä¸­æ–‡";
        System.out.println(HexFormat.of().formatHex(bad.getBytes(Charset.forName("windows-1252"))));
        System.out.println(HexFormat.of().formatHex(bad.getBytes(StandardCharsets.ISO_8859_1)));
    }
}
```
```text
e4b8ade69687
e4b8ade63f3f
```

第一行和「中文」的 UTF-8 对上，说明 `ä¸­æ–‡` 确实是 cp1252 解出来的；第二行拿 ISO-8859-1 去反推，会把两个字符换成 `?`，第二次就真的没救了。我在这上面错过一次：第一反应是「UTF-8 被当 Latin-1 读了」，照着修，越修越坏。

## 写出去那一步也会丢

前面讲的是「字节 → 字符」。反方向一样会丢，因为目标字符集可能压根没有这个字：

| 编到 | `👍` 的字节 | 解回来的值 |
| UTF-8 | `f09f918d` | `👍` |
| GB18030 | `9439d131` | `👍` |
| GBK | `3f` | `?` |
| US-ASCII | `3f` | `?` |

所以「乱码只有两个方向」这个说法不完整：读的时候解码器选错会丢，写的时候编码器选错也会丢，而且写下去那一刻丢了就没有「换个编码再打开」这条路。GBK 存不下 emoji，GB18030 存得下（四个字节）；Windows 工具里那个笼统叫「ANSI」的选项，实际落到哪个字符集要自己去确认，能力差一截。

## 症状 → 先看哪

| 屏幕上 | 先看哪一步 | 还能救吗 |
| `?` | 写出这一端的编码器：`stdout.encoding`、`getBytes(GBK)`、`US-ASCII` | 不能，字节已经是 `3F` |
| `�`（U+FFFD） | 读入这一端的解码器：字节不合它的规则 | 不能，原字节已被替换 |
| `ä¸­æ–‡` 这种拉丁字母夹怪符号 | 解码器用错了字符集，多半是 cp1252 | 能：先用 cp1252 编回字节，再按 UTF-8 解 |
| 中文变成 `涓瑼` | 写的是 UTF-8，读的按 GBK 走 | 能：`涓瑼`.getBytes(GBK) 回到 `e4 b8 ad 41` |
| 半个 emoji、末尾一个 `?` | 字符串在代码单元层面被切过 | 不能，切的时候已经换成 `?` |

前四行都来自这篇跑出来的数；第五行就是上面那个 `3f`。

## Base64：只换字形，不换信息

```java
import java.nio.charset.StandardCharsets;
import java.util.Arrays;
import java.util.Base64;

public class Main {
    public static void main(String[] args) {
        byte[] utf8 = "中A👍".getBytes(StandardCharsets.UTF_8);   // 8 字节
        String b64 = Base64.getEncoder().encodeToString(utf8);
        System.out.println(b64 + " " + b64.length());
        System.out.println(Arrays.equals(Base64.getDecoder().decode(b64), utf8));
    }
}
```
```text
5LitQfCfkY0= 12
true
```

8 个字节变成 12 个字符。Base64 每 3 字节出 4 个字符，不足 3 字节的尾巴补 `=`，所以 8 字节是 `ceil(8/3) * 4 = 12`，比原文长 50%；字符串很长时这个比值收敛到 4/3。它干的事只是把 0–255 压进可打印字符里，`+/` 换成 `-_` 就是 URL-safe 版（同一组字节 `+/8=` → `-_8=`），换汤不换药。

它不是加密。`Base64.getDecoder().decode` 一行就解回来，不需要密钥；要保密得用加密算法。

## 还差的

- 没验 HTTP 和数据库这一层：`Content-Type: text/plain; charset=...`、JDBC 的 `characterEncoding`、MySQL 的 `utf8mb4` 排序规则一个都没碰。线上乱码更多出在这里，不在 `new String`。
- 没验 UTF-16 / UTF-32 与 BOM。`new String(bytes, StandardCharsets.UTF_16)` 按 BOM 猜字节序、没有 BOM 时按大端，这条是按 javadoc 写的，本机没跑。
- `CharsetDecoder` 只走到 `onMalformedInput(REPORT)` 抛 `MalformedInputException`；`onUnmappableCharacter` 和缓冲区不够（`CoderResult.OVERFLOW`）没试。
- 屏幕那一节只在本机 Windows（`native.encoding=GBK`）测过。Linux 容器里 `stdout.encoding` 跟 locale 走，我没有在那种环境下跑过；现象对不上时先查这里。
- 没做「猜编码」：`juniversalchardet` 这类库能不能把上面几种乱码认对，没试。
