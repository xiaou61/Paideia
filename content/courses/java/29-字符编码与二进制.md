# 29 · 字符编码与二进制

## 这一课你要会

- 分清 `char`、码点（code point）和 `byte` 三件事；
- 用 UTF-8 显式编码/解码，不依赖平台默认值；
- 看到乱码时判断是"编码错了"还是"解码错了"；
- 知道一个 emoji 为什么可能占两个 `char`。

## 为什么

"读出文件是问号"、"接口收到的中文变成 `ä¸­æ–‡`"——这类问题几乎每个后端都遇到过。它们不是"Java 的 bug"，而是**同一串字节被用错了编码解释**。

理解这一课，你就能在两分钟内判断问题出在哪一层，而不是到处加 `-Dfile.encoding=UTF-8` 碰运气。

## 讲解

### 三层概念，别混

| 概念 | Java 里的类型 | 含义 |
| --- | --- | --- |
| 字符（码点） | `int`（码点值） | 一个"人看到的字符"，如 `中` = U+4E2D |
| `char` | `char`（2 字节） | UTF-16 的一个**代码单元** |
| 字节 | `byte` | 存储/传输时的实际单位，UTF-8 下 `中` 是 3 个字节 |

一个汉字在 Java 的 `char` 里是 1 个单元，但存成 UTF-8 是 3 个字节；一个 emoji（如 👍）在 `char` 里占 **2 个**单元，`String.length()` 返回 2，可它只是一个码点。要数字符个数，用 `codePointCount`。

### 编码就是"字符 → 字节"，解码是反过来

```text
"中文A"  --UTF-8 编码-->  [E4 B8 AD] [E6 96 87] [41]
"中文A"  --GBK 编码---->  [D6 D0] [CE C4] [41]
```

同一串字符，不同编码得到的字节完全不同。反过来，拿到字节时必须知道它当初用哪种编码写的，否则解出来就是乱码。

**乱码只有两种方向**：

- 用 A 编码、用 B 解码 → 得到一堆看不懂的字符（`ä¸­æ–‡`）；
- 解码时遇到非法字节 → 变成 `�`（替换字符）或直接抛 `MalformedInputException`。

### 显式指定编码

<!-- run -->
```java
import java.nio.charset.StandardCharsets;
import java.util.Arrays;

public class Main {
    public static void main(String[] args) {
        String text = "中文A";
        byte[] utf8 = text.getBytes(StandardCharsets.UTF_8);

        System.out.println(Arrays.toString(utf8));
        System.out.println(utf8.length);
        System.out.println(new String(utf8, StandardCharsets.UTF_8).equals(text));

        String emoji = "👍";
        System.out.println(emoji.length() + "/" + emoji.codePointCount(0, emoji.length()));
    }
}
```
```text
[-28, -72, -83, -26, -106, -121, 65]
7
true
2/1
```

`byte` 是有符号的（-128~127），所以 UTF-8 的 `E4` 打印成 `-28`，不是错误。`中`（3 字节）+ `文`（3 字节）+ `A`（1 字节）= 7。

三个必须显式写编码的位置：

- `new String(bytes, StandardCharsets.UTF_8)` —— 不要用单参构造器；
- `Files.readString(path, StandardCharsets.UTF_8)` —— 不要用默认重载；
- `new OutputStreamWriter(out, StandardCharsets.UTF_8)` —— 写文件/响应时同理。

JDK 18 起，标准库的默认字符集已经是 UTF-8，看起来"不写也行"。但你的数据可能来自老系统、Windows 上的第三方工具、或者一个显式用 GBK 的接口——**边界上显式写，才不会随环境漂移**。

### 什么时候会用到 Base64

Base64 不是加密，它把任意字节变成可打印字符，常用于：把图片塞进 JSON、HTTP 基本认证、URL 安全的签名参数。

```text
String encoded = Base64.getEncoder().encodeToString(bytes);
byte[] decoded = Base64.getDecoder().decode(encoded);
```

它会让体积增大约 1/3。只在"传输通道只能放文本"时用，不要把 Base64 当加密。

## 常见误区

### 误区：一个 `char` 就是一个字符

**你以为**：`String.length()` 就是"有几个字"。
**其实**：它数的是 UTF-16 代码单元。emoji、部分生僻字占两个单元。要数真正的字符用 `codePointCount`。

### 误区：乱码是"Java 的编码坏了"

**你以为**：加个启动参数就好了。
**其实**：乱码是写入与读取用了不同编码。加参数只改了某一端的默认值，可能让别的地方又坏。正确做法是在**读写这个数据的那一处**显式指定编码。

### 误区：Base64 是一种加密

**你以为**：编码后别人看不懂，就安全了。
**其实**：任何人都能一行解回来。Base64 只解决"通道只能传文本"，不做保密；保密要用加密算法。

## 小结

字符是码点，`char` 是 UTF-16 单元，`byte` 是存储单位。UTF-8 下常用汉字 3 字节，emoji 可能占两个 `char`。编码和解码必须成对，边界处显式写 `StandardCharsets.UTF_8`。乱码只有两种方向：编码错或解码错。Base64 不是加密。
