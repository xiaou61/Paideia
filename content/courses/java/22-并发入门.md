# 22 · 并发入门：线程、线程池与共享状态

## 这一课你要会

- 用 `Runnable` 提交任务，知道为什么**不要自己 `new Thread()`**；
- 分清"多线程更快"与"多线程更慢"的分界；
- 认出**共享可变状态**这个万恶之源，以及三种处理方式；
- 用 `synchronized` 与 `AtomicInteger` 保护计数，知道各自的适用场景。

## 为什么

Java 是最常被要求写并发的语言之一：Web 请求天然并发、后台任务要并行、批量处理要提速。

并发难不在于 API——`new Thread` 谁都会写。难在于**竞态条件**：两个线程同时改一个变量，结果丢了一次更新，而代码看起来完全正常。

这一课不追求讲全（并发能写一本书），目标是**让你不写出明显错误的并发代码**，并知道什么时候该去查更深的东西。

## 讲解

### 最基础的两种写法

```java
// 1) 实现 Runnable（推荐：不占继承位）
Runnable task = () -> System.out.println("跑在 " + Thread.currentThread().getName());
new Thread(task).start();

// 2) 继承 Thread（不推荐：Java 单继承，占了 extends 位就没法继承别的）
class MyTask extends Thread {
    @Override
    public void run() {
        System.out.println("hi");
    }
}
new MyTask().start();
```

**优先用 `Runnable` + lambda**：`Thread` 继承位很宝贵，而且 `Runnable` 能被线程池直接接收。

### 为什么不要 `new Thread()`

每次 `new Thread()` 都真的创建一个操作系统线程。代价：

- **创建慢**：一条线程约 1MB 栈空间，创建销毁都有系统调用开销；
- **数量不可控**：请求一多就是几千条线程，内存和上下文切换把机器拖垮；
- **没有复用**：任务执行完线程就销毁，下次再来重新创建；
- **没有拒绝策略**：撑不住的时候只能崩。

**正确做法：线程池**。提交任务，池子内部复用固定数量的线程。

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(() -> System.out.println("任务 1"));
pool.submit(() -> System.out.println("任务 2"));
pool.shutdown();      // 不再接受新任务，已有的跑完
```

`shutdown()` **必须调**。不调的话线程池里的线程是非守护线程，JVM 不会退出。

### 三种创建线程池的方式

```java
Executors.newFixedThreadPool(n)     // 固定 n 条线程，任务排队
Executors.newCachedThreadPool()     // 来多少开多少（60 秒空闲回收）
Executors.newSingleThreadExecutor() // 只有一条线程，任务串行
```

**生产代码不建议直接用 `Executors`**（阿里规约明确禁止 `newFixedThreadPool` / `newCachedThreadPool`）：前者用的是**无界队列**，任务堆积会 OOM；后者线程数无上限，来多少开多少。

规范做法是直接 `new ThreadPoolExecutor(...)`，把队列与拒绝策略都显式定下来：

```java
ExecutorService pool = new ThreadPoolExecutor(
        4,                          // 核心线程数
        8,                          // 最大线程数
        60, TimeUnit.SECONDS,       // 空闲线程存活时间
        new ArrayBlockingQueue<>(200),   // 有界队列
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.CallerRunsPolicy());   // 满了让提交者自己跑
```

### 核心问题：共享可变状态

先看这段代码：

```java
int[] counter = {0};
Runnable task = () -> {
    for (int i = 0; i < 10000; i++) {
        counter[0]++;      // 不是原子操作！
    }
};
```

两个线程各跑一遍，期望 `20000`，实际常常是 `19xxx`。

**为什么**：`counter[0]++` 是三步——读值、加一、写回。两个线程可能都读到 `5`，各自加一得到 `6`，都写回 `6`，于是两次自增只加了一次。这叫**读-改-写竞态**。

### 三种处理方式

**方式一：不共享。** 每个线程用自己的局部变量，最后汇总。这是最好的做法——**从源头消除问题**。

```java
// 每个任务算自己的和，最后在主线程相加
```

**方式二：加锁。** `synchronized` 保证同一时刻只有一个线程进临界区。

```java
class Counter {
    private int value;

    synchronized void increment() {
        value++;
    }

    synchronized int get() {
        return value;
    }
}
```

**方式三：用原子类。** `AtomicInteger` 内部用 CAS（比较并交换）实现，不用锁。

```java
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();    // 原子自增
```

**两者怎么选**：

| | `synchronized` | `AtomicInteger` |
| --- | --- | --- |
| 适用 | 多个操作要一起原子（读-改-写-再判断） | 单个变量的简单操作 |
| 阻塞 | 会阻塞其他线程 | 无锁（失败重试） |
| 性能 | 竞争激烈时开销大 | 竞争激烈时也在重试，但通常更快 |
| 能保护复杂逻辑 | 能 | 不能 |

**判据**：只有一个变量、一个操作 → 原子类；要保护"一串操作"或"多个变量必须一起变" → `synchronized`。

### `volatile`：可见性，不是原子性

```java
private volatile boolean running = true;
```

`volatile` 保证：**一个线程写了，其他线程立刻能看到**。

但它**不保证原子性**：

```java
volatile int count = 0;
count++;      // 仍然不是原子的！三步操作之间仍可能被打断
```

**用途**：一个线程写、其他线程读的**标志位**（停止信号、初始化完成标记）。计数不能用它。

### 不要用 `stop()` / `suspend()`

这两个方法已经被标记为弃用（`@Deprecated`），因为它们会让线程停在不确定的状态（锁没释放、数据半写）。

**停止线程的正确做法**：用标志位 + `interrupt()`。

```java
volatile boolean running = true;

void stop() {
    running = false;      // 让循环自己退出
}
```

### 一个具体场景：什么时候多线程反而更慢

多线程**不一定**更快。以下情况会变慢：

1. **任务是 CPU 密集且已经占满核**：再加线程只是增加切换开销；
2. **任务很短**：创建线程与调度的开销超过任务本身；
3. **大量锁竞争**：线程大部分时间在等锁；
4. **单核机器**：物理上无法并行。

**判断依据**：先看任务类型。**I/O 密集**（读文件、调接口、查数据库）多线程收益大，因为线程在等待时可以让出 CPU；**CPU 密集**（纯计算）线程数超过核数就没意义。

### 虚拟线程：Java 21+ 的新选择

JDK 25 有虚拟线程。它由 JVM 调度而不是操作系统，创建成本极低（一条几 KB），适合**大量 I/O 密集任务**：

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var task : tasks) {
        executor.submit(task);
    }
}
```

一个经验法则：**I/O 密集用虚拟线程，CPU 密集仍用固定大小的平台线程池**。

## 动手

这段代码演示竞态条件、`synchronized` 修复，以及原子类。

<!-- run -->
```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    /** 用 synchronized 保护的计数器。 */
    static class SafeCounter {
        private int value;
        synchronized void increment() { value++; }
        synchronized int get() { return value; }
    }

    public static void main(String[] args) throws InterruptedException {
        int threads = 4;
        int rounds = 10000;
        int expected = threads * rounds;

        // synchronized：结果必然准确
        SafeCounter safe = new SafeCounter();
        runInThreads(threads, rounds, safe::increment);
        System.out.println("synchronized：" + safe.get() + "（期望 " + expected + "）");

        // 原子类：结果必然准确，且不阻塞
        AtomicInteger atomic = new AtomicInteger();
        runInThreads(threads, rounds, atomic::incrementAndGet);
        System.out.println("AtomicInteger：" + atomic.get() + "（期望 " + expected + "）");

        // 可见性：volatile 让写立刻对其他线程可见
        Flag flag = new Flag();
        Thread reader = new Thread(() -> {
            while (!flag.stopped) {
                Thread.onSpinWait();
            }
            System.out.println("读到停止信号");
        });
        reader.start();
        Thread.sleep(50);
        flag.stopped = true;
        reader.join();
    }

    /** 停止标志：一个线程写、另一个线程读，正是 volatile 的用途。 */
    static class Flag {
        volatile boolean stopped;
    }

    /** 起 n 条线程各跑 rounds 次，等全部结束再返回。 */
    static void runInThreads(int n, int rounds, Runnable work) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(n);
        for (int i = 0; i < n; i++) {
            new Thread(() -> {
                try {
                    start.await();          // 一起开始，制造真实竞争
                    for (int j = 0; j < rounds; j++) {
                        work.run();
                    }
                } catch (InterruptedException failure) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();
    }
}
```

```text
synchronized：40000（期望 40000）
AtomicInteger：40000（期望 40000）
读到停止信号
```

**为什么示例里不放"无保护"那一版**：它的结果每次运行都不同（可能是 11563、23871……），
无法作为可断言的输出。这正是竞态的定义——**不确定**。上面两行则必须每次都是 40000；
如果你跑出来不是，说明保护没生效。

第三段演示 `volatile` 的正确用途：一个线程写标志、另一个线程读。去掉 `volatile`，
读线程可能永远看不到变化（一直在自己的 CPU 缓存里看旧值）。

## 常见误区

### 误区：多线程一定更快

不一定。I/O 密集有收益，CPU 密集超过核数就没意义。而且线程创建、调度、锁竞争都有开销。**先测量再优化。**

### 误区：`synchronized` 性能差，能用原子类就别用它

现代 JVM 对 `synchronized` 做了大量优化（偏向锁、轻量级锁）。**正确性优先**：需要保护多个变量一起变时，`synchronized` 是唯一靠谱的选择。原子类只能保护单个变量。

### 误区：`volatile` 能替代锁

只解决**可见性**，不解决**原子性**。计数、判断后修改（check-then-act）都不能靠它。

### 误区：`Thread.stop()` 是停止线程的方法

已弃用且危险：它会让线程停在任意位置，锁不释放、数据可能半写。正确做法是标志位配合 `interrupt()`，让线程自己在安全检查点退出。

### 误区：`shutdown()` 会立刻停掉正在跑的任务

不会。它只是"不再接受新任务"，已提交的会跑完。要立刻停用 `shutdownNow()`——它也只是发中断信号，任务是否响应取决于它自己有没有处理 `interrupt`。

## 小结

- 用 `Runnable` + 线程池，不要 `new Thread()`。
- 生产环境用 `new ThreadPoolExecutor(...)` 显式指定**有界队列 + 拒绝策略**。
- 竞态的根因是**共享可变状态**；最好的解法是不共享，其次是加锁或用原子类。
- `volatile` 保可见性，不保原子性；计数用 `AtomicInteger`。
- I/O 密集多线程有收益，CPU 密集线程数约等于核数；JDK 25 还可以用虚拟线程处理大量 I/O。
- `shutdown()` 不打断已在跑的任务，且**必须调用**。
