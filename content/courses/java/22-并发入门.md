# 22 · 并发入门：线程、线程池与共享状态

把这段存成 `PlainRace.java`，4 条线程各加 5 万次：

```java
import java.util.concurrent.CountDownLatch;

public class PlainRace {
    static int count;

    public static void main(String[] args) throws Exception {
        int threads = 4, rounds = 50_000;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);
        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();
                    for (int j = 0; j < rounds; j++) count++;
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();
        System.out.println("count=" + count + " expected=" + (threads * rounds));
    }
}
```

```text
count=57853 expected=200000
```

我原来以为 4 条线程各加各的，最后至少是 20 万；实际少了一大半。同样 4 条线程各 5 万次，我也见过一轮刚好 `200000`，所以一次跑对不能说明安全。

（下面除非另说，输出来自 Temurin JDK 25.0.4+7，代码用 `javac --release 21` 编译。命令里用 `JAVA_TOOL_OPTIONS` 固定英文 locale，JVM 会多打一行 `Picked up JAVA_TOOL_OPTIONS...`，下面的输出省略了这行。）

关键行为我在 JDK 21.0.3 上也复跑过：裸 `int` 计数仍少、`volatile` 仍少、`AtomicInteger` 仍是 200000、无 `volatile` 的循环仍停不下来、`-Xint` 能停；数字和 25 不同，结论一样。

下面有些片段只写关键行，省了 import；完整可运行的版本在「跑一遍」。

`count++` 不是一条原子指令。它至少是三步：

```java
int current = count;    // 1. 读
int next = current + 1; // 2. 改
count = next;           // 3. 写
```

两个线程可以都读到 `5`，各自算出 `6`，再都写回 `6`。两次自增只留下一次，这就是读-改-写竞态。

怎么自己验证：同一段代码连跑 10 轮，别只看一轮；把 `rounds` 从 5 万改成 50 万，少算会更明显。但某一轮刚好等于 200000 也不能证明没问题，竞态不是每次都出现。

## 加 volatile 还是少

最自然的修法是给 `count` 加 `volatile`：

```java
static volatile int count;
```

其余代码不动，跑出来：

```text
count=95527 expected=200000
```

还是少。`volatile` 保证的是：对 `count` 的写 happens-before 后续对 `count` 的读；读线程能看到写线程写进去的值，或者更晚的写。它没有把 `count++` 的三步合成一个整体。

两个线程仍然可以同时读到同一个旧值，再各自写回。`volatile` 只是让每次读都满足可见性语义，不负责“读和写之间没人插进来”。

怎么自己验证：把 `PlainRace` 的 `static int count` 改成 `static volatile int count`，连跑 10 轮。数字可能比裸 `int` 接近 200000，也可能更差；只要有一轮不是 200000，就说明它没有解决原子性。

## 换成 AtomicInteger

计数用 `AtomicInteger`：

```java
import java.util.concurrent.atomic.AtomicInteger;

static final AtomicInteger count = new AtomicInteger();

// 线程里
count.incrementAndGet();
```

```text
count=200000 expected=200000
```

`incrementAndGet()` 把读-改-写合成一个原子操作，底层是 CAS（compare-and-set）：算出一个新值，只有当前值还是旧值时才写进去；失败就重来。它不需要互斥锁，但竞争激烈时会重试。

不要写成 `count.set(count.get() + 1)`。那只是把 `count++` 拆得更明显，原子性还是没有。

`synchronized` 和 `AtomicInteger` 怎么选：

| | `synchronized` | `AtomicInteger` |
| --- | --- | --- |
| 保护范围 | 一个代码块里的多条语句、多个变量 | 一个变量的一次原子操作 |
| 竞争时 | 线程排队等锁 | CAS 失败重试，不排队 |
| 复合操作 | 能 | 不能直接做；要 CAS 循环或加锁 |
| 可见性 | 有，解锁 happens-before 后续加锁 | 有，带 volatile 语义 |
| 适合 | 转账、先检查后更新、多个字段一起变 | 计数、累加、序号 |
| 代价 | 竞争激烈时有锁开销 | 低竞争便宜；高竞争重试，需实测 |

判据：只有一个变量、一个操作，用原子类；要保护一串操作，或者多个变量必须一起变，用 `synchronized`。

怎么自己验证：把 `AtomicInteger` 换成裸 `int`，再换成 `volatile int`，各跑 10 轮；前两者都会少，`AtomicInteger` 应该每轮都是 200000。

### 锁对象必须是同一个

```java
class Counter {
    private int value;
    private final Object lock = new Object();

    void increment() {
        synchronized (lock) {
            value++;
        }
    }

    int get() {
        synchronized (lock) {
            return value;
        }
    }
}
```

两个方法锁的必须是同一个 `lock`。如果 `increment` 锁 `lockA`、`get` 锁 `lockB`，或者每个线程都 `synchronized (new Object())`，等于没锁。`synchronized` 锁的是对象，不是代码块的样子。

再补两个容易混的点：

- 实例方法 `synchronized void increment()` 锁的是 `this`；静态方法锁的是 `Counter.class`。一个用实例方法、一个用静态方法，不是同一把锁。
- 读也要进同一把锁。只给写加锁、读裸奔，读线程仍可能看到旧值。

4 条线程各加 5 万次，一半用 `lockA`、一半用 `lockB`：

```text
same lock   = 200000
two locks   = 180391
expected    = 200000
```

同一段代码在 JDK 21 上我也碰到过一轮 `two locks = 200000`；再跑 10 轮，全部少于 200000（188293–197879）。两把锁仍然没有互斥，只是那一次没撞上。

怎么自己验证：把上面的 `Counter` 复制成两个版本，一个所有线程共用 `lock`，一个每个线程 `synchronized (new Object())`；各跑 10 轮。前者应该每轮 200000；后者可能少，也可能碰巧 200000，跑 10 轮再判断。不要用一轮 200000 当证明。

## volatile 真正管什么：一个停不下来的循环

`volatile` 最典型的用途不是计数，是一个线程写、另一个线程读的停止标志。先看没有 `volatile` 的版本：

```java
public class Hoist {
    static boolean running = true;
    static long spins;

    public static void main(String[] args) throws Exception {
        Thread reader = new Thread(() -> {
            while (running) {
                spins++;
            }
            System.out.println("reader saw stop");
        });
        reader.start();
        Thread.sleep(500);
        running = false;
        reader.join(1000);
        System.out.println("alive=" + reader.isAlive());
        System.exit(0); // 读线程没停时，别让示例把 JVM 挂住
    }
}
```

默认 JIT 连跑 3 次，都是：

```text
alive=true
```

加 `-Xint` 关掉 JIT：

```text
reader saw stop
alive=false
```

把 `running` 改成 `static volatile boolean running`，默认 JIT 下也停：

```text
reader saw stop
alive=false
```

我原来以为这是“CPU 缓存里留了一份旧值”。这个解释不准确。真正的原因在 Java 内存模型：`running = false` 这次写和读线程的读之间没有建立 happens-before，JIT 可以把 `running` 的读提升到循环外，编译成近似“先检查一次，然后一直循环”。`-Xint` 关掉 JIT 后每次都重新读字段，所以停了。CPU 缓存一致性协议不是这里的关键，语言层面不给你这个保证，拿缓存解释会得出错误的修法。

`volatile` 写 happens-before 后续对同一字段的读，所以读线程能看到停止信号；它同时限制一部分重排。它仍然不保原子性。`synchronized` 同时保可见性和原子性；`AtomicInteger` 保一个变量的原子操作和可见性。

怎么自己验证：同一段代码分别用 `java Hoist`、`java -Xint Hoist`；再把 `running` 加上 `volatile` 跑一次，看 `alive`。`-Xint` 只是用来定位原因，不是修复方案；生产代码要加 `volatile` 或用锁。

## start() 不是 run()

```java
Thread worker = new Thread(() ->
        System.out.println("body runs in " + Thread.currentThread().getName()));
worker.run();
worker.start();
worker.join();
```

```text
body runs in main
body runs in Thread-0
```

`run()` 是普通方法调用，当前线程执行；`start()` 才让 JVM 创建新线程，再由新线程调用 `run()`。直接调 `run()` 不会开线程，线程状态还是 `NEW`。同一个 `Thread` 对象第二次 `start()` 会抛：

```text
java.lang.IllegalThreadStateException
```

`run()` 可以直接调多次，但它每次都只是当前线程里的一次普通调用。

怎么自己验证：在 `run()` 里打印 `Thread.currentThread().getName()`；或者在 `start()` 之后再 `start()` 一次。

## 线程池：不要每个任务都 new Thread()

每来一个任务就 `new Thread()`，问题不是“创建慢”这一句，而是三件事都没有上限：线程数没有上限，任务排队没有上限，撑不住时没有拒绝策略。线程池把这几个口子收回来。

`Executors` 的三个工厂方法先认识：

```java
Executors.newFixedThreadPool(n);     // 固定 n 条，队列无界
Executors.newCachedThreadPool();     // 线程数上限 Integer.MAX_VALUE
Executors.newSingleThreadExecutor(); // 1 条，队列无界
```

`newFixedThreadPool` 和 `newSingleThreadExecutor` 用的是无界 `LinkedBlockingQueue`（默认容量 `Integer.MAX_VALUE`），任务堆到 OOM 也不会拒绝；`newCachedThreadPool` 的最大线程数是 `Integer.MAX_VALUE`，忙起来线程数可以一直涨。入门可以先用，生产别把队列和线程上限交给默认值。

直接 `new ThreadPoolExecutor`，把队列和拒绝策略写明白：

```java
ExecutorService pool = new ThreadPoolExecutor(
        4,                              // 核心线程数
        8,                              // 最大线程数
        60, TimeUnit.SECONDS,           // 空闲线程存活时间
        new ArrayBlockingQueue<>(200),  // 有界队列
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.CallerRunsPolicy());
```

提交任务时的顺序不是“先扩容再排队”，而是：

| 顺序 | 条件 | 动作 |
| --- | --- | --- |
| 1 | 工作线程数 < core | 开新线程 |
| 2 | 工作线程数 ≥ core | 进队列 |
| 3 | 队列满且工作线程数 < max | 再开线程 |
| 4 | 队列满且已经到 max | 交给拒绝策略 |

`CallerRunsPolicy` 让提交任务的线程自己跑，形成背压；`AbortPolicy` 抛 `RejectedExecutionException`；`DiscardPolicy` 静默丢任务，线上最难查；`DiscardOldestPolicy` 丢队列里最老的任务。没有拒绝策略的线程池，就是把风险推给内存。

怎么自己验证：把 core 和 max 都设成 1、队列设成 1，提交 3 个睡 1 秒的任务；第 3 个会走你配置的拒绝策略（`CallerRunsPolicy` 就在提交线程里跑，`AbortPolicy` 就抛 `RejectedExecutionException`）。再把 max 改成 2，第 3 个会开第二条线程。把拒绝策略换成 `DiscardPolicy`，你会看到第 3 个任务没有报错，也没有执行。

## 为什么看不到异常

先跑这段：

```java
ExecutorService pool = Executors.newSingleThreadExecutor();
System.out.println("submit, Future discarded:");
pool.submit(() -> { throw new IllegalStateException("boom"); });
Thread.sleep(300);
System.out.println("main still alive");
pool.shutdown();
```

```text
submit, Future discarded:
main still alive
```

任务确实抛了 `IllegalStateException`，但控制台没有它。`submit` 把任务包进 `FutureTask`，异常被存进 `Future`；没人调用 `get()`，就没人处理。线程池的线程还活着，主线程也正常结束——线上看起来像“任务没执行”，实际是执行了然后静默失败。

这就是“为什么看不到异常”的根源：不是异常没发生，是异常被 `Future` 接住了，而你把 `Future` 丢了。

修法一：用 `execute`，在线程工厂里装 `UncaughtExceptionHandler`：

```java
ThreadFactory factory = task -> {
    Thread thread = Executors.defaultThreadFactory().newThread(task);
    thread.setUncaughtExceptionHandler((t, e) ->
            System.out.println(t.getName() + " caught: " + e));
    return thread;
};
ExecutorService pool = Executors.newSingleThreadExecutor(factory);
pool.execute(() -> { throw new IllegalStateException("boom"); });
Thread.sleep(300);
pool.shutdown();
```

```text
pool-1-thread-1 caught: java.lang.IllegalStateException: boom
```

`execute` 的异常会交给线程的未捕获异常处理器；不装 handler 时，默认打到 stderr。日志没接 stderr 的环境里，默认输出也可能看不到，所以显式 handler 更稳。

修法二：保留 `Future`，调用 `get()`：

```java
ExecutorService pool = Executors.newSingleThreadExecutor();
Future<?> future = pool.submit(() -> { throw new IllegalStateException("boom"); });
try {
    future.get();
} catch (ExecutionException e) {
    System.out.println("get() threw ExecutionException: " + e.getCause());
}
pool.shutdown();
```

```text
get() threw ExecutionException: java.lang.IllegalStateException: boom
```

`get()` 会把原始异常包在 `ExecutionException` 里，`getCause()` 才是 `IllegalStateException`。它还会阻塞到任务结束；批量任务不要在主线程一个个 `get()`，除非你就是要这个顺序。

怎么自己验证：把 `future.get()` 注释掉再跑，异常消失；加回来，`ExecutionException` 出现。把 `submit` 换成 `execute`，再对比有没有 handler 的输出。

## shutdown() 与 shutdownNow()

`shutdown()` 只是不再接受新任务，已经提交的任务会继续跑完；它本身不阻塞。要等它结束，用 `awaitTermination`。下面这段放在 `main` 里（`throws Exception`），一个睡 300 毫秒的任务：

```java
ExecutorService pool = Executors.newSingleThreadExecutor();
pool.submit(() -> {
    try {
        Thread.sleep(300);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    System.out.println("task done");
});
long start = System.nanoTime();
pool.shutdown();
System.out.println("shutdown returned after " + (System.nanoTime() - start) / 1_000_000 + " ms");
boolean ok = pool.awaitTermination(2, TimeUnit.SECONDS);
System.out.println("awaitTermination=" + ok + " after " + (System.nanoTime() - start) / 1_000_000 + " ms");
```

```text
shutdown returned after 0 ms
task done
awaitTermination=true after 302 ms
```

时间数字会变；关键是 `shutdown()` 立刻返回，`awaitTermination` 等到任务结束才返回。

`shutdownNow()` 做得更多。下面这个池只有 1 条线程，先塞一个阻塞任务，再排 3 个任务，然后立刻 `shutdownNow()`：

```java
ExecutorService pool = Executors.newFixedThreadPool(1);
CountDownLatch started = new CountDownLatch(1);
Set<String> ran = ConcurrentHashMap.newKeySet();
pool.execute(() -> {
    ran.add("blocker");
    started.countDown();
    try {
        Thread.sleep(5000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});
started.await();
for (int i = 1; i <= 3; i++) {
    int id = i;
    pool.submit(() -> ran.add("task-" + id));
}
List<Runnable> queued = pool.shutdownNow();
System.out.println("returned=" + queued.size());
Thread.sleep(300);
System.out.println("ran=" + new TreeSet<>(ran));
System.out.println("terminated=" + pool.awaitTermination(3, TimeUnit.SECONDS));
```

```text
returned=3
ran=[blocker]
terminated=true
```

我原来以为 `shutdownNow()` 只是给线程发个中断；实际它做了四件事：停止接收新任务、把队列里的任务排空并作为返回值交还、对正在跑的任务发中断、不等待结束。`returned=3` 就是三个排队任务；`ran=[blocker]` 说明它们一个都没跑。`terminated=true` 是因为这个 blocker 在 `catch` 里退出了；换个忽略中断的任务，这里会变成 `false`。把返回值丢掉，这三个任务就真的丢了。

`shutdownNow()` 也不保证正在跑的任务停下。它只发中断；任务不响应中断就继续跑，`awaitTermination` 可能一直等不到。**任务丢了**的常见事故，就是这里：调用方以为“取消”了，队列里的任务已经被取走，又没人处理返回值。

怎么自己验证：打印 `queued.size()` 和 `ran`；把 `shutdownNow()` 换成 `shutdown()`，三个排队任务会跑完，`returned` 那行自然也不存在。再写一个忽略 `InterruptedException` 的任务，看 `awaitTermination` 返回 `false`。

## stop() / suspend() 已经不能用

历史上这两个方法的问题不一样：

- `suspend()` 把线程停住，但不释放它已经拿到的锁，其他线程可能永远等下去。
- `stop()` 让线程在任意位置抛出 `ThreadDeath`，栈展开时释放监视器，但数据可能停在写了一半的状态。

从 JDK 20 起，这两个方法就被改成直接抛 `UnsupportedOperationException`。现在的结论不是“已弃用但还能用”，是根本不能用。下面这段放在 `main` 里（`throws Exception`），用 `javac --release 21` 编译：

```java
Thread worker = new Thread(() -> {
    while (true) {
        Thread.onSpinWait();
    }
});
worker.start();
Thread.sleep(100);
try {
    worker.stop();
} catch (Throwable e) {
    System.out.println("stop() -> " + e);
}
try {
    worker.suspend();
} catch (Throwable e) {
    System.out.println("suspend() -> " + e);
}
worker.interrupt();
worker.join(500);
System.out.println("alive after interrupt() = " + worker.isAlive());
System.exit(0);
```

JDK 21 上实测：

```text
stop() -> java.lang.UnsupportedOperationException
suspend() -> java.lang.UnsupportedOperationException
alive after interrupt() = true
```

JDK 25 上：

```text
stop() -> java.lang.UnsupportedOperationException
suspend() -> java.lang.NoSuchMethodError: 'void java.lang.Thread.suspend()'
alive after interrupt() = true
```

JDK 25 的 `javac` 直接编译 `worker.suspend()` 会报 `cannot find symbol`；上面是用 `javac --release 21` 编出的旧 class 在 25 上跑，才会看到 `NoSuchMethodError`。`stop()` 还在，但同样抛 `UnsupportedOperationException`。

停线程用“标志位 + `interrupt()`”，让线程自己在安全检查点退出：

```java
static volatile boolean running = true;

Thread worker = new Thread(() -> {
    while (running && !Thread.currentThread().isInterrupted()) {
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            break;
        }
    }
});
```

主线程停的时候：

```java
running = false;
worker.interrupt();
worker.join();
```

标志位负责“该不该停”，`interrupt()` 负责把 `sleep`、`wait`、`join` 里的线程叫醒。`interrupt()` 本身不会强制停；不检查标志、不处理 `InterruptedException` 的循环，照样一直跑。上面 `alive after interrupt() = true` 就是证据：那个循环只做 `Thread.onSpinWait()`，根本没看中断标志。

`Thread.interrupted()` 会清除中断标志，`isInterrupted()` 不会。catch 里如果不打算退出，要重新 `interrupt()`，把状态还给上层。

怎么自己验证：把 `while (true)` 换成 `while (running)`，再写一个 `stop()` 方法把 `running` 设成 `false`；或者在 catch 里打印 `Thread.currentThread().isInterrupted()`，看它是 `true` 还是已经被清掉。

## 虚拟线程：不拦住退出，不等于不用 close

JDK 21 起可以用虚拟线程。大量 I/O 等待的任务，用：

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // tasks 是你的任务列表
    for (var task : tasks) {
        executor.submit(task);
    }
}
```

虚拟线程适合 I/O 密集：等数据库、等 HTTP、等文件。CPU 密集仍用固定大小的平台线程池；开更多虚拟线程不会让 CPU 变快，只会让任务抢核。

关于关闭，我原来以为“线程池不 shutdown，JVM 一定不退出”。这只对默认的平台线程池成立。三个只提交一个打印任务、主线程睡 200 毫秒就结束的 `main`，分别用默认平台池、daemon 平台池、虚拟线程 executor；外面用 2 秒超时跑：

```text
PoolExit: TIMEOUT after 2s stdout='task done\nmain end'
DaemonExit: EXIT=0 stdout='task done\nmain end'
VExit: EXIT=0 stdout='task done\nmain end'
```

`PoolExit` 用默认的 `newFixedThreadPool(2)`，线程是非守护的，主线程结束后 JVM 还在等它，所以超时；`DaemonExit` 把线程工厂改成 daemon，`VExit` 用虚拟线程 executor，两者都正常 `EXIT=0`。`stdout` 里的 `\n` 是 Python repr 打出来的换行。

但虚拟线程/daemon 不拦住退出，不是“不用 close”的理由。不 close 就不等任务结束，资源也不释放；`try` 块结束时的 `close()` 会 shutdown 并等任务结束。一个睡 300 毫秒的任务，实测 `task done` 先打印，`closed` 在开始后 336 毫秒打印。

虚拟线程也不是“无限并发”。下游数据库连接池、HTTP 连接池仍然有上限；开太多虚拟线程，只是把压力推给下游。

怎么自己验证：写一个只提交一个打印任务、主线程睡 200 毫秒就结束的 `main`；分别用 `newFixedThreadPool(2)` 和 `newVirtualThreadPerTaskExecutor()`，用 2 秒超时跑，比较退出码。再把主线程的 `Thread.sleep(200)` 去掉，可能看不到 `task done`；加上 `try`，观察 `close` 是否等任务结束。

## 操作对工具

| 你要做的事 | 用什么 | 别用什么 |
| --- | --- | --- |
| 只读写一个停止标志 | `volatile boolean` | 普通 `boolean`，JIT 可能把读提出循环 |
| 多线程计数/累加 | `AtomicInteger` / `AtomicLong` | `volatile int` 加 `++` |
| 多步不变式（转账、先检查后更新） | `synchronized`（同一把锁）或 `ReentrantLock` | 多个原子变量各改各的 |
| 提交任务且不想吞异常 | `execute` + `UncaughtExceptionHandler`，或 `submit` 后 `get()` | 丢掉 `submit` 的 `Future` |
| 线程池满了 | 有界队列 + 明确拒绝策略 | 无界队列、静默丢弃 |

## 跑一遍

把原子计数、`synchronized` 和 `interrupt()` 拼成一个能直接跑的程序：

<!-- run -->
```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    static final AtomicInteger atomic = new AtomicInteger();
    static int guarded;
    static final Object lock = new Object();

    public static void main(String[] args) throws Exception {
        runWorkers(4, 50_000, atomic::incrementAndGet);
        System.out.println("atomic=" + atomic.get());

        runWorkers(4, 50_000, () -> {
            synchronized (lock) {
                guarded++;
            }
        });
        System.out.println("synchronized=" + guarded);

        CountDownLatch sleeping = new CountDownLatch(1);
        Thread worker = new Thread(() -> {
            try {
                sleeping.countDown();
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                System.out.println("sleep interrupted");
                Thread.currentThread().interrupt();
            }
            System.out.println("worker exit, interrupted=" + Thread.currentThread().isInterrupted());
        });
        worker.start();
        sleeping.await();
        worker.interrupt();
        worker.join();
    }

    static void runWorkers(int threads, int rounds, Runnable work) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);
        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();
                    for (int j = 0; j < rounds; j++) {
                        work.run();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();
    }
}
```

```text
atomic=200000
synchronized=200000
sleep interrupted
worker exit, interrupted=true
```

`atomic` 和 `synchronized` 每次都必须是 200000；`interrupt()` 把 `sleep` 叫醒，catch 里重新设置中断标志，所以最后打印 `true`。如果你跑出来不是这个结果，先检查是不是把 `synchronized` 的锁对象换掉了。

## 还差的

- 没讲死锁：两个锁的获取顺序、`jstack` 里怎么看到 BLOCKED、`tryLock` 超时后怎么退。这篇只到“同一把锁”的最小修法。
- 没讲 `CompletableFuture`、`invokeAll`、超时和异常传播；多任务有依赖时，`Future.get()` 会写得很别扭。
- 没讲并发容器和生产者消费者：`ConcurrentHashMap`、`BlockingQueue`、`Condition` 都只提了名字。
- 没讲虚拟线程的 pinning 和结构化并发；第 37 课会展开虚拟线程，这篇只到“什么时候该 close”。
- 没讲怎么写出可重复的并发测试。本文的实测都是“跑几次看结果”，能证明这一次发生了什么，不能证明代码没有竞态；更可靠的是 JCStress 这类工具。
