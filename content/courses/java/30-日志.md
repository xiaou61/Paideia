# 30 · 日志：程序出事了怎么查

## 四条一模一样的日志

四个线程，各打一条登录失败，真跑出来是这样：

```text
WARNING login failed
WARNING login failed
WARNING login failed
WARNING login failed
```

这就是日志最常见的死法：**信息量是零**。

我不知道是谁的登录失败、哪个请求、哪台机器、四条是不是同一个用户在重试。要查这件事，我得去数据库里找"最近几分钟所有失败记录"，然后猜哪条对应日志里哪一行。而如果这四行分散在几百万行日志里，连"四条"这个数字都数不出来。

问题不在"打了日志"，在于**这条日志只有结论，没有身份**。

这一课要解决的就是这件事：怎么让一条日志在你不在现场时替你说话。

## 一条日志得回答四个问题

```text
SEVERE pay failed orderId=1024 userId=7 reason=timeout
```

- **谁**：`userId=7`
- **做了什么**：`pay failed`
- **对哪个对象**：`orderId=1024`
- **为什么**：`reason=timeout`

注意写法：`key=value`，不是"用户 7 的订单 1024 支付失败了，因为超时"。

这是一条我花过时间才改过来的习惯。`key=value` 的好处是**可搜、可统计、可切分**：日志平台上直接搜 `orderId=1024` 就能捞出这个订单的一生；搜 `reason=timeout` 再按服务分组，就能看出"超时是不是只发生在某个下游"。而那句人话只能被人眼一行行读。

## `println` 到底缺什么

`println` 能打印，但它缺三样东西，恰好是出事时最需要的：

| 缺的 | 后果 |
| --- | --- |
| 时间 | 不知道"从几点开始变多" |
| 级别 | 分不清这是错误还是普通信息，没法只筛 ERROR 看 |
| 线程 / 上下文 | 并发场景下无法把若干行归到同一次请求 |

还有个更实际的麻烦：`println` **关不掉**。上线后想把日志量降下来、或者把 DEBUG 打开，得改代码重新发版。日志框架把"打不打、打到哪、什么格式"全变成配置，代码里只表达"这件事有多重要"。

## 级别：代码只声明重要性

| 级别（JDK / SLF4J） | 什么时候用 | 例子 |
| --- | --- | --- |
| `SEVERE` / `ERROR` | 功能失败了，需要人处理 | 支付回调验签失败 |
| `WARNING` / `WARN` | 还能继续，但明显不对 | 重试第 2 次、缓存没命中 |
| `INFO` | 关键业务节点 | 订单创建成功、用户登录 |
| `FINE` / `DEBUG` | 排查细节 | 入参、SQL、分支走向 |

默认输出 `INFO` 及以上。`DEBUG` 平时关着，出问题时在配置里打开——**不改代码、不重新编译**，这是框架相对 `println` 最实在的价值。

同一套东西两套名字，是因为 JDK 自带 `java.util.logging`（JUL）用了 `SEVERE/WARNING`，而 SLF4J 用 `ERROR/WARN`。业务里最常见的是 SLF4J + Logback，写法几乎一样：

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);

log.info("order created orderId={} userId={}", orderId, userId);
```

`{}` 占位符是重点：**字符串拼接只在日志真的会输出时才发生**。用 `"orderId=" + orderId` 的话，即使这条 INFO 被配置关掉了，拼接也已经执行完——在高频路径上是纯粹的浪费，而且会掩盖空指针。

## 跑一遍：不装任何依赖

JDK 自带的这套就够验证行为。下面把 `Handler` 写得最简，只输出级别和消息：

<!-- run -->
```java
import java.util.logging.Handler;
import java.util.logging.Level;
import java.util.logging.LogRecord;
import java.util.logging.Logger;

public class Main {
    public static void main(String[] args) {
        Logger logger = Logger.getLogger("demo");
        logger.setUseParentHandlers(false);
        logger.setLevel(Level.ALL);

        Handler out = new Handler() {
            @Override
            public void publish(LogRecord record) {
                System.out.println(record.getLevel() + " " + record.getMessage());
            }

            @Override
            public void flush() {
            }

            @Override
            public void close() {
            }
        };
        out.setLevel(Level.ALL);
        logger.addHandler(out);

        logger.info("order created orderId=1024 userId=7");
        logger.warning("retry 2/3 orderId=1024");
        logger.severe("pay failed orderId=1024 userId=7 reason=timeout");
    }
}
```
```text
INFO order created orderId=1024 userId=7
WARNING retry 2/3 orderId=1024
SEVERE pay failed orderId=1024 userId=7 reason=timeout
```

真实项目里这个 `Handler` 由配置提供（输出到控制台还是文件、什么格式、要不要 JSON）。业务代码只写 `logger.warning(...)`，不关心落到哪。

## 我在这上面犯过最贵的一个错：异常只塞 message

出事时看到过这样的日志：

```text
SEVERE pay failed: null
```

`null` 是 `e.getMessage()` 的返回值——`new NullPointerException()` 不带消息，它就返回 `null`。整条日志等于什么都没说。

更常见的情况是消息有内容，但**栈没了**：

```java
// 错：只把 message 拼进字符串
log.severe("pay failed orderId=1024: " + e.getMessage());
```

真跑对比一下（两个都是在 `Demo.java:32` 抛的 NPE）：

```text
--- 正确：log(Level, msg, throwable) ---
SEVERE pay failed orderId=1024
    java.lang.NullPointerException: Cannot invoke "Object.toString()" because "<local3>" is null
    	at Demo2.main(Demo2.java:32)
    	at java.base/jdk.internal.reflect.DirectMethodHandleAccessor.invoke(...)

--- 错误：只塞 message ---
SEVERE pay failed orderId=1024: Cannot invoke "Object.toString()" because "<local3>" is null
```

两版的**第一行字面值几乎一样**，区别在第二版没有 `at Demo2.main(Demo2.java:32)`。

没有行号，你就只能拿着这条日志去代码里猜。有了行号，三十秒定位。这就是"塞 message"和"传 Throwable"的全部差别，而它只在真出事那天才显现。

正确写法：

```java
catch (Exception e) {
    log.error("pay failed orderId={} userId={}", orderId, userId, e);
}
```

**最后一个参数是 `Throwable`，框架会自动展开栈**——不要再 `+ e.getMessage()`（丢栈），也不要 `+ e`（变成一行 `toString()`，同样丢栈）。

顺带一个坑：自己写的 `Handler`/`Formatter` 如果只 `println(record.getMessage())`，栈也会被吞掉，因为栈在 `record.getThrown()` 里，要不要打由消费者决定。我第一版示例就是这么写的，看着像"框架把栈弄丢了"，其实是我自己的输出没处理。

## 让每条日志自动带上身份

真跑出来的输出（两个线程交替）：

```text
WARNING req-2 login failed userId=2
WARNING req-1 login failed userId=1
WARNING req-2 login retry userId=2
WARNING req-1 login retry userId=1
```

现在"四条一样的日志"变成了两串可追踪的请求，而且业务代码里完全不用写 `req-2`。

两个必须知道的副作用：

- **`finally` 里必须 `remove()`**。线程池的线程会被复用，不清理等于把上一个请求的 id 交给下一个请求，日志会串号——这种错最难查，因为日志本身在骗你。
- **异步/新线程会丢**。`ThreadLocal` 只活在当前线程，丢进线程池的任务拿到的是空值。要跨线程就得显式传，或者用 `InheritableThreadLocal`（只在创建子线程那一刻继承一次，线程池不适用）。

## 绝对不能写进日志的东西

- 密码、验证码、token、Cookie、`Authorization` 头；
- 完整身份证号、银行卡号、手机号（必须记就脱敏：`138****1234`）；
- 完整的请求体——里面可能什么都夹着。

理由是权限：日志会被采集、跨机转发、存进搜索集群、长期保留，**访问权限通常比数据库松得多**。一条密钥进了日志，等于把它公开了；而且日志系统常有多个副本和备份，删一条比删数据库一行难得多。

我见过的真实做法是给日志框架挂一个脱敏 `Layout`/`Converter`，在输出前把 `password=...`、`token=...` 之类的字段替换成 `***`。这比"记得别打"可靠——人是会忘的。

## 这一课之后

日志是你不在现场时唯一的证人。判断一条日志够不够用，有个很土但很准的办法：**假设明天它出现在一条告警里，只有这一行，你能改代码吗？**

能改，说明它有身份、有位置；不能改，说明它只证明了"出过事"，没告诉你"出在哪"。
