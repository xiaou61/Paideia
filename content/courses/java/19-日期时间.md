# 19 · 日期时间：LocalDate、Instant 与跨时区

## 10 月怎么会打印成 11 月

```java
import java.time.LocalDate;
import java.util.Calendar;

public class Main {
    public static void main(String[] args) {
        Calendar calendar = Calendar.getInstance();
        calendar.clear();
        calendar.set(2026, 10, 20);
        System.out.println(calendar.getTime());

        LocalDate date = LocalDate.of(2026, 10, 20);
        System.out.println(date);
    }
}
```

```text
Fri Nov 20 00:00:00 CST 2026
2026-10-20
```

这是 JDK 25.0.4、英文 locale、默认时区 `Asia/Shanghai` 下跑出来的。`Calendar.set(2026, 10, 20)` 里的 `10` 是月份下标：0 是 January，10 是 November，所以你以为写的是十月，它给你的是十一月二十号。`calendar.clear()` 只是把时分秒和毫秒清零，不让当前时间掺进来。

`LocalDate.of(2026, 10, 20)` 的 `10` 才是 October。`java.time` 把月份改成 1 到 12，并且参数越界会直接抛异常，不会悄悄滚到下一年。能写 `Month.OCTOBER` 时别写裸 `10`。

## 五种类型，先看它带不带时区

| 类型 | 含义 | 例子 | 什么时候用 |
| --- | --- | --- | --- |
| `LocalDate` | 只有日期 | `2026-10-20` | 生日、账期、到期日 |
| `LocalTime` | 只有时间 | `14:30:00` | 每天几点开门 |
| `LocalDateTime` | 日期 + 时间，**没有时区** | `2026-10-20T14:30` | 本地日历上的一个刻度 |
| `Instant` | **时间轴上的一个点**（按 UTC 展示） | `2026-10-20T06:30:00Z` | 已发生的时刻、日志、审计 |
| `ZonedDateTime` | 时间点 + 具体时区 | `2026-10-20T14:30+08:00[Asia/Shanghai]` | 未来日历约定、按时区显示 |

`ZoneId` 是时区 ID，不是第六种时间类型。它回答的是「用哪套时区规则」，本身不表示某个时刻。

**最容易搞错的一对**是 `LocalDateTime` 与 `Instant`。

`LocalDateTime` 说「2026-10-20 14:30」，但它不知道自己属于哪个时区。同样写 `14:30`，在北京和伦敦是两个不同的时刻。

`Instant` 是时间轴上的一个点，唯一确定一个时刻，与时区无关。它内部不是「从 epoch 过了多少纳秒」，而是 `long seconds` 加 `int nanos` 两个字段，范围约正负 10 亿年。要秒用 `getEpochSecond()`，要毫秒用 `toEpochMilli()`；自己把秒乘 `1_000_000_000L` 当总纳秒，跨到 2300 年就会溢出。用 `Math.multiplyExact` 检查能抛 `ArithmeticException: long overflow`（我跑过），不检查则静默得到一个错数。

`LocalDate`、`LocalTime`、`LocalDateTime`、`Instant`、`ZonedDateTime`、`Duration`、`Period` 这些值类型不可变，所有加减都返回新对象。别把这句扩大成整个 `java.time` 包：`DateTimeFormatterBuilder` 是可变的构建器，`Clock` 的实现也可能有状态。

一条实用规则：

> 已发生、要写日志或审计的，用 `Instant`；生日、账期这类日历上的日期，用 `LocalDate`；「明天 9 点开会」这种未来日历约定，用 `ZonedDateTime`（或存 `LocalDateTime` 加 `ZoneId`）。

未来事件不能只存 `Instant`。会议约定的是「那天墙上时钟的 9 点」，不是「某个固定 UTC 秒数」。时区规则一更新，`Instant` 对应的本地时间可能变成 8 点或 10 点；`ZonedDateTime` 才能保住日历约定。

数据库也一样：存 UTC 值或 epoch 都行，但 `DATETIME` 本身不带时区，写进去的是 UTC 只是你们的约定；MySQL 的 `TIMESTAMP` 还会按会话 `time_zone` 换算。连接层要显式固定 UTC，别让驱动或会话的默认时区改变同一列的含义。

## 两个 9:00 相等，不代表同一时刻

```java
LocalDateTime tokyoNine = LocalDateTime.of(2026, 10, 20, 9, 0);
LocalDateTime beijingNine = LocalDateTime.of(2026, 10, 20, 9, 0);

System.out.println(tokyoNine.equals(beijingNine));

Instant tokyoInstant = tokyoNine.atZone(ZoneId.of("Asia/Tokyo")).toInstant();
Instant beijingInstant = beijingNine.atZone(ZoneId.of("Asia/Shanghai")).toInstant();
System.out.println(tokyoInstant);
System.out.println(beijingInstant);
System.out.println(Duration.between(tokyoInstant, beijingInstant));
```

```text
true
2026-10-20T00:00:00Z
2026-10-20T01:00:00Z
PT1H
```

`LocalDateTime.equals` 只比较年月日时分秒字段，两个 9:00 完全相同，所以第一行是 `true`。它没有时区，不能直接拿来做跨时区比较。

`atZone(ZoneId)` 给本地时间绑定时区，`toInstant()` 才把它放到时间轴上。东京 9 点是 `00:00Z`，北京 9 点是 `01:00Z`，东京早一个小时，`Duration.between` 得到 `PT1H`。

## 加一个月不是加 31 天

```java
LocalDate jan31 = LocalDate.of(2026, 1, 31);
LocalDate mar3 = LocalDate.of(2026, 3, 3);

System.out.println(jan31.plusMonths(1));
System.out.println(jan31.plusDays(31));
System.out.println(Period.between(jan31, mar3));
System.out.println(Duration.between(
        jan31.atStartOfDay(ZoneOffset.UTC).toInstant(),
        mar3.atStartOfDay(ZoneOffset.UTC).toInstant()));
```

```text
2026-02-28
2026-03-03
P1M3D
PT744H
```

`plusMonths(1)` 是日历月运算：目标月没有 31 号，落到 2 月最后一天；`plusDays(31)` 是固定加 31 天，落到 3 月 3 日。输出里的「加一个月」是 `2026-02-28`，不是 `2026-03-03`。

`Period` 按年、月、日三个分量算，得到 `P1M3D`；`Duration` 按时间轴上的秒和纳秒算，同一对日期是 `PT744H`。一个说「一个月零三天」，一个说「744 小时」，不是谁算错了。

## `GMT+8` 不是错，只是丢了历史规则

```java
ZoneId gmt8 = ZoneId.of("GMT+8");
ZoneId shanghai = ZoneId.of("Asia/Shanghai");

System.out.println(gmt8);
System.out.println(gmt8.getRules().isFixedOffset());
System.out.println(shanghai.getRules().isFixedOffset());
System.out.println(shanghai.getRules().getOffset(
        Instant.parse("1988-07-01T00:00:00Z")));
```

```text
GMT+08:00
true
false
+09:00
```

`GMT+8` 被归一成 `GMT+08:00`，它就是一个固定偏移，`getRules().isFixedOffset()` 返回 `true`。如果业务只需要「永远比 UTC 快 8 小时」，用 `ZoneOffset.ofHours(8)` 或这种固定偏移完全够。

需要民用时间、夏令时和历史规则，才用地区名。`Asia/Shanghai` 不是固定偏移：1988 年 7 月 1 日处在中国的夏令时期间，它的偏移是 `+09:00`。所以不是「`GMT+8` 一律判错」，而是先问自己要不要历史规则。

## 反向转换没有 `toInstant(ZoneId)`

```java
ZoneId shanghai = ZoneId.of("Asia/Shanghai");
Instant instant = Instant.parse("2026-10-20T06:30:00Z");

ZonedDateTime beijing = instant.atZone(shanghai);
Instant back = beijing.toInstant();
LocalDateTime local = LocalDateTime.ofInstant(instant, shanghai);
System.out.println(beijing);
System.out.println(back);
System.out.println(local);
```

```text
2026-10-20T14:30+08:00[Asia/Shanghai]
2026-10-20T06:30:00Z
2026-10-20T14:30
```

这里保留了 `Instant → ZonedDateTime → Instant` 这条三行转换。两边不对称的地方在另一头：`LocalDateTime.ofInstant` 收 `ZoneId`，但 `LocalDateTime` 没有 `toInstant(ZoneId)`。写成 `local.toInstant(ZoneId.of("Asia/Shanghai"))` 会编译失败，英文报错是：

```text
Bad.java:7: error: incompatible types: ZoneId cannot be converted to ZoneOffset
        Instant instant = local.toInstant(zone);
                                          ^
```

反向只有 `toInstant(ZoneOffset)`，所以先把本地时间绑到地区规则上：`local.atZone(zone).toInstant()`。

## 格式化器可以共用，`yyyy` 要小心

```java
private static final DateTimeFormatter FORMAT =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
```

`DateTimeFormatter` 不可变、线程安全，可以做成常量反复用；`SimpleDateFormat` 有内部状态，多线程共用会互相覆盖，不能这样放。

`yyyy` 是 year-of-era，`uuuu` 是 proleptic year。默认的 SMART 解析日常日期没问题；切到 `ResolverStyle.STRICT` 后，`yyyy-MM-dd` 会因为没有 era 解析失败，实测报 `Unable to obtain LocalDate from TemporalAccessor`，换成 `uuuu-MM-dd` 就正常。只有日期、没有纪元字段时，用 `uuuu` 更稳。

`Month` 和 `DayOfWeek` 也别写裸数字：`Month.OCTOBER`、`DayOfWeek.MONDAY` 比 `10`、`1` 更难看错。`DayOfWeek.getValue()` 里周一是 1，周日是 7，和 `Calendar` 的 `SUNDAY=1` 不是一套。

## 跑一遍

这段程序把同一时刻的三个时区表示、不可变、格式化和 `Duration` 放在一起跑；下面的输出与它逐字对应。

<!-- run -->
```java
import java.time.Duration;
import java.time.Instant;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;
import java.time.format.DateTimeFormatter;

public class Main {
    public static void main(String[] args) {
        // 1) 同一时刻，不同时区
        Instant instant = Instant.parse("2026-10-20T06:30:00Z");
        System.out.println("UTC     : " + instant);
        System.out.println("北京    : " + instant.atZone(ZoneId.of("Asia/Shanghai")));
        System.out.println("东京    : " + instant.atZone(ZoneId.of("Asia/Tokyo")));

        // 2) 不可变：加减返回新对象
        LocalDate base = LocalDate.of(2026, 1, 31);
        LocalDate plusMonth = base.plusMonths(1);
        System.out.println("原值    : " + base);
        System.out.println("加一个月: " + plusMonth);

        // 3) 格式化与解析
        DateTimeFormatter format = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
        LocalDateTime moment = LocalDateTime.of(2026, 10, 20, 14, 30, 5);
        String text = moment.format(format);
        System.out.println("格式化  : " + text);
        System.out.println("解析回来: " + LocalDateTime.parse(text, format));

        // 4) 时长：Duration 按秒算，不是按日历
        Instant start = Instant.parse("2026-10-20T06:30:00Z");
        Instant end = Instant.parse("2026-10-20T06:30:02Z");
        Duration spent = Duration.between(start, end);
        System.out.println("耗时毫秒: " + spent.toMillis());

        // 5) LocalDateTime 与 Instant 互转必须给时区
        ZonedDateTime beijing = instant.atZone(ZoneId.of("Asia/Shanghai"));
        LocalDateTime local = LocalDateTime.ofInstant(instant, ZoneId.of("Asia/Shanghai"));
        System.out.println("本地时间: " + local);
        System.out.println("回到 UTC: " + beijing.toInstant());
    }
}
```

```text
UTC     : 2026-10-20T06:30:00Z
北京    : 2026-10-20T14:30+08:00[Asia/Shanghai]
东京    : 2026-10-20T15:30+09:00[Asia/Tokyo]
原值    : 2026-01-31
加一个月: 2026-02-28
格式化  : 2026-10-20 14:30:05
解析回来: 2026-10-20T14:30:05
耗时毫秒: 2000
本地时间: 2026-10-20T14:30
回到 UTC: 2026-10-20T06:30:00Z
```

- 只验证了固定偏移和 1988 年上海夏令时，没有演示「凌晨 2:30 不存在」和「凌晨 1:30 出现两次」的夏令时缺口与重叠。
