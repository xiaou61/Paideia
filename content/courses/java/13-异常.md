# 13 · 异常

## 关闭也会失败：body-boom 与 close-boom

我原来以为 try-with-resources 只是「少写一个 finally」。直到资源和业务代码同时抛异常，才发现它真正保住的是哪一个。下面把 try-with-resources 简称 TWR。

下面这个 `Resource` 一关闭就抛 `close-boom`；两个方法都在 body 里抛 `body-boom`，一个用 TWR，一个用手写 finally：

```java
public class TwrVsFinally {
    static class Resource implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("close-boom");
        }
    }

    static void withTryWithResources() {
        try (Resource resource = new Resource()) {
            throw new IllegalStateException("body-boom");
        }
    }

    static void withFinally() {
        Resource resource = new Resource();
        try {
            throw new IllegalStateException("body-boom");
        } finally {
            resource.close();
        }
    }

    public static void main(String[] args) {
        try {
            withTryWithResources();
        } catch (IllegalStateException error) {
            System.out.println("TWR 保留：" + error.getMessage());
            System.out.println("TWR suppressed[0]：" + error.getSuppressed()[0].getMessage());
        }

        try {
            withFinally();
        } catch (IllegalStateException error) {
            System.out.println("finally 保留：" + error.getMessage());
            System.out.println("finally 还有 body 异常吗：" + (error.getSuppressed().length > 0));
        }
    }
}
```

```text
TWR 保留：body-boom
TWR suppressed[0]：close-boom
finally 保留：close-boom
finally 还有 body 异常吗：false
```

`AutoCloseable` 是 JDK 自带的接口，只有一个 `close()` 方法；TWR 在退出时调用它。

先把两个结果摆在一起：

- TWR：`body-boom` 是主异常，`close-boom` 挂在它的 `getSuppressed()` 里。
- 手写 finally：`close()` 抛出的 `close-boom` 成了主异常，`body-boom` 连 suppressed 都没进，直接丢了。

这就是 TWR 比「不容易漏 close」更值钱的地方：它定义了**两个异常同时发生时的保留规则**。Java 语言规范（JLS）的 try-with-resources 规则是：body 先抛，TWR 保留它；退出时调用 `close()`；如果 `close()` 也抛，就把 close 异常 `addSuppressed` 到 body 异常上；最后重抛 body 异常。手写 finally 没有这个规则，`finally` 里直接调用 `close()`，close 一抛，原来的异常就被覆盖。要保留得自己 catch 住 close 异常再 `addSuppressed`，很麻烦。

如果 body 正常结束、只有 `close()` 抛，TWR 会把 close 异常当主异常抛出去——没有 body 异常可挂。两种路径都要知道。

怎么自己验证：把 `withFinally()` 改成 `try (Resource resource = new Resource())`，再跑一次，最后两行会从 `close-boom` / `false` 变成 `body-boom` / `true`。

这台机器是 Windows + Temurin 25.0.4，源码用 `javac --release 21 -encoding UTF-8` 编译。下面的英文报错是给 `javac` / `java` 加 `-Duser.language=en -Duser.country=US`（`javac` 用 `-J` 前缀）跑出来的；等价于设置 `$env:JAVA_TOOL_OPTIONS='-Duser.language=en -Duser.country=US'`。

## 两大家族：Error 与 Exception 分家

```text
Throwable
├── Error                     OutOfMemoryError、StackOverflowError、AssertionError
└── Exception
    ├── RuntimeException      NullPointerException、IllegalArgumentException
    └── 其它                  IOException、SQLException
```

分界线只看继承链，不看「能不能恢复」：

- 受检异常：`Exception` 下，除 `RuntimeException` 及其子类之外的部分；编译器要求 `catch` 或在签名上 `throws`。
- 非受检异常：`RuntimeException` 及其子类，以及 `Error`；编译器不要求处理。

「能恢复就是受检异常」是错的。`IOException` 可能根本恢复不了（磁盘坏了），它仍然是受检；`InsufficientBalanceException` 可能很好恢复（让用户充值），但它可以继承 `RuntimeException` 而不强制每个调用方写 catch。受检与否是 API 契约，能不能恢复是你选基类时的设计判断。

`catch (Exception)` 也不会捕获 `Error`。我手动扔一个 OOM 来验证边界（不是把堆真的耗尽）：

```java
public class ErrorNotException {
    public static void main(String[] args) {
        try {
            throw new OutOfMemoryError("simulated-oom");
        } catch (Exception error) {
            System.out.println("catch Exception: " + error);
        }
    }
}
```

```text
Exception in thread "main" java.lang.OutOfMemoryError: simulated-oom
	at ErrorNotException.main(ErrorNotException.java:4)
```

`OutOfMemoryError` 直接冒到 `main` 外面，进程退出。`catch (Exception)` 捕获的是所有 `Exception`（包括 NPE、`IllegalArgumentException` 这些 `RuntimeException`），不是 `Error`。所以「catch Exception 会把不该恢复的错误也吞掉」要拆成两句：

- 它**不会**吞掉 OOM / StackOverflowError；这些是 `Error`，仍然会冒出去。
- 它会吞掉你本来不想恢复的 `RuntimeException`，比如空指针、参数错误——这些属于编程错误，应该让它们带着栈冒出来，而不是在宽泛的 catch 里变成一句「出错了」。

怎么自己验证：把 `OutOfMemoryError` 换成 `RuntimeException`，同一个 catch 就会接住；换回 `Error`，catch 不会执行。

## try / catch / finally 的基本形状

```java
public class ParseDemo {
    static void parse(String text) {
        try {
            int value = Integer.parseInt(text);
            System.out.println(value);
        } catch (NumberFormatException error) {
            System.out.println("不是数字：" + text);
        } finally {
            System.out.println("收尾");
        }
    }
}
```

catch 按**从具体到宽泛**排。Java 从上往下找第一个匹配的 catch；一旦匹配，后面的不再看。宽泛的放前面，后面的具体分支永远到不了，编译器直接拒绝：

```java
public class CatchOrder {
    public static void main(String[] args) {
        try {
            throw new NumberFormatException("bad");
        } catch (Exception error) {
            System.out.println("宽");
        } catch (NumberFormatException error) {
            System.out.println("窄");
        }
    }
}
```

```text
CatchOrder.java:7: error: exception NumberFormatException has already been caught
        } catch (NumberFormatException error) {
          ^
1 error
```

「第一个匹配的 catch 赢」还有一个常见后果：如果你写了 `catch (IllegalArgumentException)` 和 `catch (RuntimeException)`，`IllegalArgumentException` 必须在前；否则它永远轮不到。

怎么自己验证：把两个 catch 调换，编译就会报上面这行 `has already been caught`。

## 收尾不是「总是执行」

把说法改准确：**正常路径一定执行**。try 正常结束、catch 处理完、方法正常返回，这些路径上 `finally` 会跑；body 抛异常、没被 catch 住时，`finally` 也会先跑，再把异常往外抛。有两类例外：一类根本不跑，一类跑完也会把原来的异常盖掉。

### `System.exit(0)` 不走 finally

```java
public class ExitFinally {
    public static void main(String[] args) {
        try {
            System.out.println("try");
            System.exit(0);
        } finally {
            System.out.println("finally");
        }
    }
}
```

```text
try
```

`System.exit(0)` 发起 JVM 关闭，当前线程不会从 `System.exit` 返回，所以 `finally` 没机会执行。关闭钩子（shutdown hook）是另一套机制，和 `finally` 不是一回事。

怎么自己验证：把这行 `System.exit(0)` 删掉，再跑一次，`finally` 就会打印。

### `finally` 里 `return` 会吞掉异常

```java
public class FinallyReturn {
    static int run() {
        try {
            throw new IllegalStateException("body-boom");
        } finally {
            return 42;
        }
    }

    public static void main(String[] args) {
        System.out.println(run());
    }
}
```

```text
42
```

`body-boom` 没了。`finally` 里的 `return` 让整个 try 语句突然完成，原来的异常被丢弃；`break`、`continue` 和 `finally` 里再抛一个异常，也是同样的覆盖效果。

所以规矩很硬：**`finally` 只做清理，不要写 `return`、`break`、`continue`**。清理本身失败了，就让它抛，或者交给日志；不要用 `return` 把失败盖掉。

怎么自己验证：把 `return 42;` 换成 `System.out.println("finally");`，`body-boom` 就会照常抛到 `main`，程序以非 0 退出，栈里能看到 `java.lang.IllegalStateException: body-boom`。

## `throw new` 与 `throws` 是一对

```java
import java.io.IOException;

public class ThrowsDemo {
    static void read() throws IOException {   // 签名：告诉调用方「可能抛」
        throw new IOException("disk-boom");    // 方法体：实际抛出
    }

    public static void main(String[] args) {
        read();
    }
}
```

```text
ThrowsDemo.java:9: error: unreported exception IOException; must be caught or declared to be thrown
        read();
            ^
1 error
```

两行各管一件事：

| 写法 | 作用 |
| --- | --- |
| `throw new IOException(...)` | 在方法体里真正创建并抛出 |
| `void read() throws IOException` | 在方法签名上声明，调用方必须 catch 或继续 throws |

`throws` 本身不会抛异常；`throw` 也不会替调用方声明。编译器的检查落在**调用点**：`read()` 的签名里有受检异常，`main` 不 catch 也不 `throws`，就报 `unreported exception`。

调用方处理之后：

```java
public static void main(String[] args) {
    try {
        read();
    } catch (IOException error) {
        System.out.println("读取失败：" + error.getMessage());
    }
}
```

```text
读取失败：disk-boom
```

怎么自己验证：删掉 `read()` 签名上的 `throws IOException`，编译错误会移到 `throw new IOException(...)` 那一行；保留 `throws` 但不处理调用，错误就留在 `read()` 的调用行。

## 受检异常在 lambda 里：`unreported exception IOException`

下面这段借第 14 课的文件 API 看一个编译错误；`Files.lines` 的关闭和编码第 14 课再讲，这里只关心 lambda 的签名：

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class LambdaChecked {
    public static void main(String[] args) throws IOException {
        Path source = Path.of("in.txt");
        Path target = Path.of("out.txt");
        Files.lines(source).forEach(line -> Files.writeString(target, line));
    }
}
```

```text
LambdaChecked.java:9: error: unreported exception IOException; must be caught or declared to be thrown
        Files.lines(source).forEach(line -> Files.writeString(target, line));
                                                             ^
1 error
```

`main` 已经 `throws IOException`，`Files.lines(source)` 这步没问题；报错在 lambda 体里的 `Files.writeString`。原因是 `forEach` 收的是 `Consumer<T>`，它的抽象方法 `accept(T)` 没有 `throws`。lambda 必须实现这个方法，就不能凭空多抛一个受检异常。`Runnable.run()`、`Supplier.get()`、`Function.apply()` 也都是标准函数式接口，抽象方法没有 `throws`；传给它们的 lambda 不能抛受检异常。自定义接口可以声明 `throws`，后面的 `LineTask` 就是例子。

两条出路。

**出路一：lambda 里就地处理。**

```java
Files.lines(source).forEach(line -> {
    try {
        Files.writeString(target, line);
    } catch (IOException error) {
        System.out.println("写入失败：" + line + " / " + error.getMessage());
    }
});
```

适合「这一行失败就算了，继续处理下一行」。真实代码要把 `Files.lines` 返回的流关掉，外面得套 TWR；这部分第 14 课讲。

**出路二：包成 `UncheckedIOException` 再抛。**

```java
Files.lines(source).forEach(line -> {
    try {
        Files.writeString(target, line);
    } catch (IOException error) {
        throw new UncheckedIOException("写入失败：" + line, error);
    }
});
```

`UncheckedIOException` 是 `java.io` 里的 `RuntimeException`，所以 lambda 可以抛。上层 catch 到它时，`getCause()` 还是原来的 `IOException` 实例（可能是 `AccessDeniedException` 这类子类）——别写成 `throw new RuntimeException(error.getMessage())`，那样类型和 cause 都丢了。

如果你自己定义函数式接口，可以带 `throws`：

```java
@FunctionalInterface
interface LineTask {
    void run(String line) throws IOException;
}
```

但 `forEach` 只认 `Consumer`，不认 `LineTask`；要让 `LineTask` 可用，得自己写一个接收它的方法，并在方法签名上 `throws IOException`。标准的 `forEach` 不会替你处理这个受检异常。

怎么自己验证：把 `Files.writeString(target, line)` 换成 `System.out.println(line)`，编译立刻通过；说明问题不在 lambda 本身，而在被调用的方法抛了受检异常、函数式接口又没声明。

## `assert`：默认不执行

```java
public class AssertDemo {
    public static void main(String[] args) {
        int age = -3;
        assert age >= 0 : "age 不能为负：" + age;
        System.out.println("检查之后，age=" + age);
    }
}
```

```text
# 不带 -ea
检查之后，age=-3

# 带 -ea
Exception in thread "main" java.lang.AssertionError: age 不能为负：-3
	at AssertDemo.main(AssertDemo.java:4)
```

同一个 class 文件，不带 `-ea` 时 `assert` 那行等于不存在，`-3` 照常往下走；带 `-ea` 才检查，失败抛 `AssertionError`。`-ea` 是 `-enableassertions` 的缩写。

`assert` 是给**内部不变量**用的：某个状态在你的代码里应该不可能出现，出现了就是 bug。它不适合做参数校验，原因有三个：

- 它默认关闭，生产环境可能没带 `-ea`，校验等于没写。
- 失败抛的是 `AssertionError`，它继承 `Error`，`catch (Exception)` 不会接住它。
- 参数校验要给调用方一个可处理的异常（`IllegalArgumentException`），而不是一个「断言失败」。

参数校验写成这样：

```java
static int parseAge(String text) {
    int age = Integer.parseInt(text);
    if (age < 0) {
        throw new IllegalArgumentException("年龄不能为负：" + age);
    }
    return age;
}
```

还有一条：不要把有副作用的表达式放进 `assert`。`assert checkAndFix();` 在不带 `-ea` 时连 `checkAndFix()` 都不会调用。`assert` 的 detail 表达式也只在条件为 false 时求值，但整个 assert 在不带 `-ea` 时都不执行。

怎么自己验证：用 `java AssertDemo` 和 `java -ea AssertDemo` 各跑一次，对比输出与退出码；前者 0，后者 1。

## NPE 与日志：`getMessage()` 不够

Java 14 起（JEP 358），空指针的 helpful message 会尽量告诉你「哪个引用是 null、正在调用什么」：

```java
public class NpeDemo {
    static String trim(String text) {
        return text.trim();
    }

    public static void main(String[] args) {
        String name = null;
        System.out.println(trim(name));
    }
}
```

```text
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.trim()" because "text" is null
	at NpeDemo.trim(NpeDemo.java:3)
	at NpeDemo.main(NpeDemo.java:8)
```

这条消息比只有 `NullPointerException` 多了一层现场：调用的是 `String.trim()`，为 null 的是 `text`。但变量名不是白给的：我加 `-g` 编译才有 `text`，默认编译在这台机器上是 `because "<parameter1>" is null`。不同编译参数、不同表达式，消息会变；它是诊断辅助，不是新的异常类型。

真正容易丢信息的是 catch 之后只打 `getMessage()`：

```java
try {
    trim(null);
} catch (RuntimeException error) {
    System.out.println(error.getMessage());
}
```

```text
Cannot invoke "String.trim()" because "text" is null
```

类型 `java.lang.NullPointerException` 没了，`at NpeDemo.trim(NpeDemo.java:3)` 也没了。如果异常本身没带 message（`new NullPointerException()`），这里只会打印 `null`。

临时调试可以用 `error.printStackTrace();`，它会把类型、消息、栈打到 `System.err`。生产代码不要把 `printStackTrace` 当日志：它没有时间、级别、请求上下文，也不受日志配置控制。把 `Throwable` 整个交给日志框架，第 30 课会讲：

```java
log.error("trim failed", error);
```

不要写 `log.error("trim failed: " + error.getMessage())`，那等于把栈扔掉；也不要写 `+ error`，那只会得到一行 `toString()`。

怎么自己验证：去掉 `-g` 重新编译，消息里的 `text` 会变成 `<parameter1>`；把 catch 里的 `System.out.println(error.getMessage())` 换成 `error.printStackTrace()`，类型和 `at ...` 行都会回来。

## 自定义异常：继承谁

业务失败我自己的做法是让它继承 `RuntimeException`：

```java
class InsufficientBalanceException extends RuntimeException {
    InsufficientBalanceException(String message) {
        super(message);
    }
}
```

这样调用方不被强制 catch；在 service 层集中处理，或者让全局异常处理器转成 HTTP 响应。代价是编译器不再提醒你「这里可能失败」，所以方法名、文档和测试要补上。

如果调用方**必须**处理（比如一个可重试的远程读取，不处理就会丢数据），才继承 `Exception`：

```java
class RetryableReadException extends Exception {
    RetryableReadException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

注意这里的「必须处理」是 API 设计选择，不是「能恢复」的同义词。受检与否看继承链；「能不能恢复」只帮你决定继承 `RuntimeException` 还是 `Exception`。

能复用标准异常就别自定义：参数错用 `IllegalArgumentException`，状态错用 `IllegalStateException`，I/O 用 `IOException`。自定义异常留给调用方需要区分、需要单独处理的业务条件。构造器带 `cause` 可以把底层异常留住，别只传 message。

怎么自己验证：写一个调用方 `new InsufficientBalanceException("余额不足")`，把基类改成 `extends Exception` 后，调用方不 catch 就编译失败；改回 `extends RuntimeException` 又能过。编译器看的是继承链，不是你觉不觉得它能恢复。

## 跑一遍

把解析、catch、finally 和 TWR 放在一个程序里：

<!-- run -->
```java
public class Main {
    static class Resource implements AutoCloseable {
        @Override
        public void close() {
            throw new IllegalStateException("close-boom");
        }
    }

    static int parseAge(String text) {
        try {
            int age = Integer.parseInt(text);
            if (age < 0) {
                throw new IllegalArgumentException("年龄不能为负：" + text);
            }
            return age;
        } catch (NumberFormatException error) {
            throw new IllegalArgumentException("年龄必须是数字，收到：" + text, error);
        }
    }

    public static void main(String[] args) {
        for (String raw : new String[]{"18", "abc", "-3"}) {
            try {
                System.out.println("解析成功：" + parseAge(raw));
            } catch (IllegalArgumentException error) {
                System.out.println("解析失败：" + error.getMessage());
            }
        }

        try {
            System.out.println(1 / 0);
        } catch (ArithmeticException error) {
            System.out.println("不能除以 0");
        } finally {
            System.out.println("catch 处理完：finally 执行");
        }

        try (Resource resource = new Resource()) {
            throw new IllegalStateException("body-boom");
        } catch (IllegalStateException error) {
            System.out.println("TWR 保留：" + error.getMessage());
            System.out.println("suppressed：" + error.getSuppressed()[0].getMessage());
        }
    }
}
```
```text
解析成功：18
解析失败：年龄必须是数字，收到：abc
解析失败：年龄不能为负：-3
不能除以 0
catch 处理完：finally 执行
TWR 保留：body-boom
suppressed：close-boom
```

`parseAge` 把 `NumberFormatException` 包成 `IllegalArgumentException`，并把原异常作为 cause 传进去；`finally` 只打印，不 `return`；`Resource.close()` 故意抛异常，所以最后能看到 suppressed。

## 还差的

- `Files.lines` / `Files.writeString` 只在 lambda 那节借来展示编译错误；文件 I/O、编码、流的关闭第 14 课讲，这篇没有真正跑文件读写。
- 没讲 `try` / `finally` 在字节码里的异常表实现，也没讲 JVM 如何在栈帧里查 handler；这里只讲语言层行为。
- `assert` 只讲了 `-ea` 总开关；按包/类开启（`-ea:com.example...`）、类加载器的 `desiredAssertionStatus()` 没讲。
- 日志只到「把 `Throwable` 交给日志」；Logback 配置、MDC、异步 appender 没有展开，MDC 在第 30 课有例子。
- 没讲 `Error` 的各个子类（`ThreadDeath`、`LinkageError`、`StackOverflowError`），也没回答「OOM 之后进程还能不能安全继续」；只验证了 `catch (Exception)` 不会接住 `OutOfMemoryError`。
