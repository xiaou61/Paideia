# 37 · 虚拟线程

## 这一课你要会

- 用 `Thread.ofVirtual()` 创建虚拟线程；
- 说清它为什么能开几十万个，而平台线程不行；
- 知道它适合 IO 密集、不适合 CPU 密集；
- 知道"不要池化虚拟线程"和 JDK 21 的一个坑。

## 为什么

传统 Java 线程（现在叫**平台线程**）一个对应一个操作系统线程。系统线程很贵：栈默认占 1MB 左右，创建和切换都要内核参与。所以服务器上通常只能开几百到几千个。

但 Web 服务的大部分线程在干什么？**等**。等数据库、等下游接口、等磁盘。等的时候它占着内存，却什么也不做。

虚拟线程（Java 21 正式）把"线程"和"操作系统线程"拆开：成千上万个虚拟线程复用少量**载体线程**（carrier），只有在真正执行代码时才占用载体，一遇到阻塞就自动让出来。于是"一个请求一个线程"这种最简单直白的写法，又能支撑很高并发了。

## 讲解

### 创建与使用

<!-- run -->
```java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws Exception {
        AtomicInteger count = new AtomicInteger();
        Thread[] threads = new Thread[1000];

        for (int i = 0; i < threads.length; i++) {
            threads[i] = Thread.ofVirtual().start(count::incrementAndGet);
        }

        for (Thread thread : threads) {
            thread.join();
        }

        System.out.println(count.get());
        System.out.println(Thread.ofVirtual().unstarted(() -> {
        }).isVirtual());
        System.out.println(Thread.ofPlatform().unstarted(() -> {
        }).isVirtual());
    }
}
```
```text
1000
true
false
```

`Thread.ofVirtual()` 返回一个 builder，`.start(Runnable)` 立刻启动，`.unstarted(...)` 只创建不启动。虚拟线程的 `isVirtual()` 是 `true`。

1000 个虚拟线程在普通机器上毫无压力；同样的代码换成 `Thread.ofPlatform()`，在某些系统上会直接因为线程数上限而失败。

### 为什么便宜

| | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 对应关系 | 1 : 1 操作系统线程 | 多 : 1 载体线程 |
| 栈 | 预分配，较大 | 存在堆上，按需增长 |
| 阻塞时 | 占着系统线程 | 让出载体线程 |
| 数量级 | 几百 ~ 几千 | 几十万（取决于堆） |

关键在最后一行：虚拟线程遇到阻塞式 IO（网络、文件、`Thread.sleep`、`LockSupport.park`）时会**卸载**，载体线程去跑别的虚拟线程。等 IO 回来再挂回去。

### 不要池化

平台线程贵，所以要池化（`Executors.newFixedThreadPool(200)`）；虚拟线程便宜，池化反而有害：

- 池化会把"创建成本低"的优势浪费掉；
- 池里的虚拟线程数量固定后，并发度又被限制住了；
- 用完就丢，才是它的用法。

正确写法：

```text
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Task task : tasks) {
        executor.submit(task);
    }
}
```

`newVirtualThreadPerTaskExecutor()` 就是"每个任务一个虚拟线程"，不需要容量参数。

### 适合什么，不适合什么

**适合**：IO 密集——HTTP 调用、数据库访问、消息队列、文件读写。

**不适合**：CPU 密集。虚拟线程不会让 CPU 变快，它解决的是"等"的问题。纯计算任务开一万个虚拟线程，只是让 CPU 更忙地切换。

### JDK 21 的一个坑：`synchronized` 会钉住载体线程

在 JDK 21 里，虚拟线程在 `synchronized` 块中阻塞时**不会卸载**，会一直占着载体线程（叫 pinning）。如果大量虚拟线程都在同一个锁上等，载体线程会被占满，并发优势就没了。

规避办法：把 `synchronized` 换成 `ReentrantLock`。JDK 24 起这个问题已经修复（JEP 491），但如果你部署在 21，仍要注意。

## 常见误区

### 误区：虚拟线程比平台线程快

**你以为**：换了就能提升吞吐。
**其实**：单次执行的速度差不多，甚至略慢。它提升的是**并发容量**——同样内存能同时等待更多 IO。CPU 密集任务换虚拟线程没有收益。

### 误区：虚拟线程也要池化

**你以为**：线程都该池化，复用才省。
**其实**：池化是为"创建贵"设计的。虚拟线程创建极便宜，池化反而把并发度锁死。用 `newVirtualThreadPerTaskExecutor` 或直接 `Thread.ofVirtual().start`。

### 误区：虚拟线程能把阻塞变成非阻塞

**你以为**：代码里的阻塞调用会自动变成异步。
**其实**：代码仍然一行行往下写，只是 JVM 在底层把阻塞的虚拟线程挂起、让出载体。你不需要改异步写法；但底层驱动必须支持（JDK 的 socket/file API 已支持）。

## 小结

虚拟线程让"一个任务一个线程"重新可行：阻塞时让出载体，能开几十万个，适合 IO 密集，不适合 CPU 密集。不要池化。JDK 21 里注意 `synchronized` 的 pinning，用 `ReentrantLock` 规避。
