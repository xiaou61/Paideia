# 37 · 虚拟线程

两万个任务，每个只需要等 20 毫秒。同一段程序，只换最后一行传进去的执行器：

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Bench {
    static final int TASKS = 20_000;
    static final int DELAY_MS = 20;

    static void run(String label, ExecutorService pool) throws Exception {
        long start = System.nanoTime();
        try (pool) {
            for (int i = 0; i < TASKS; i++) {
                pool.execute(() -> {
                    try {
                        Thread.sleep(DELAY_MS);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            }
        }
        System.out.println(label + " = " + (System.nanoTime() - start) / 1_000_000 + " ms");
    }

    public static void main(String[] args) throws Exception {
        run("pool(200)      ", Executors.newFixedThreadPool(200));
        run("pool(400)      ", Executors.newFixedThreadPool(400));
        run("pool(2000)     ", Executors.newFixedThreadPool(2000));
        run("virtualPerTask ", Executors.newVirtualThreadPerTaskExecutor());
    }
}
```

Temurin 25.0.4+7，16 核、16 GB，`pool(200)` 那一行跑两次是 2130 / 2135 ms：

```text
pool(200)       = 2130 ms
pool(400)       = 1145 ms
pool(2000)      = 921 ms
virtualPerTask  = 133 ms
```

同一个 `.class` 用 Oracle GraalVM 21.0.3+7.1 再跑一遍：

```text
pool(200)       = 3136 ms
pool(400)       = 1650 ms
pool(2000)      = 1119 ms
virtualPerTask  = 289 ms
```

先看能算出来的那部分。两万个任务、池子 200 条，就是 `20000 / 200 = 100` 轮，每轮 20 ms，理论 2000 ms——实测 2130 ms，多出来的 130 ms 是提交任务和建线程。池子 2000 条呢？10 轮，理论 200 ms，实测 921 ms。**多出来的 700 多毫秒全花在建 2000 条平台线程上**，任务本身一秒没省。

我原来以为「线程池开大点总没坏处，至少不会更慢」。会慢：把池子从 400 加到 2000，任务需要的等待时间从 1000 ms 降到 200 ms，但创建线程的成本从约 280 ms 涨到约 700 ms，净亏。

（下面出现的数字都来自同一台机器上的这两个 JDK；Java 21 那个是 GraalVM 的构建，不是 Temurin。程序用各版本自己的 `javac` 编，没用到 22 以后的语法，所以两边都能跑。唯一例外是后面测原生帧的那段用了 FFM，它到 22 才转正。）

## 把虚拟线程塞回池子，数字立刻变回去

虚拟线程的工厂就是一个 `ThreadFactory`，所以能塞进任何线程池：

```java
run("virtual in pool(200)", Executors.newFixedThreadPool(200, Thread.ofVirtual().factory()));
```

```text
virtual in pool(200) = 2100 ms    // 25.0.4
virtual in pool(200) = 3061 ms    // 21.0.3
```

跟平台线程的 2130 / 3136 ms 基本重合。这不是虚拟线程失效，而是 `ThreadPoolExecutor` 的定义：同一个时刻最多 `corePoolSize` 个任务在跑，剩下的在队列里等。**谁在跑**由线程决定，**同时在跑几个**由池子决定。换线程类型改不了后者。

JEP 444 把这个坑写在正中间：不要池化虚拟线程，每个任务建一条；如果你的目的是限制并发，用 `Semaphore`。前任的直觉（线程贵，所以要复用）在虚拟线程上已经不成立，而池子限制并发的那半功能，本来就该由信号量承担。

## 限并发的是信号量，不是线程数

假设下游只给 20 个连接，你要跑 5000 个各等 10 ms 的请求：

```java
Semaphore conns = new Semaphore(20);
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 5_000; i++) {
        pool.execute(() -> {
            try {
                conns.acquire();
                try {
                    Thread.sleep(10);
                } finally {
                    conns.release();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

```text
A semaphore20_5000x10ms = 2716 ms    // 25.0.4
A semaphore20_5000x10ms = 3898 ms    // 21.0.3
```

理论是 `5000 / 20 × 10 = 2500` ms。虚拟线程开到 5000 条，同时在用连接的仍然是 20 个：**虚拟线程改变的是「谁在等」，不改变「下游能接几个」**。`acquire()` 阻塞时虚拟线程会卸载，所以剩下 4980 条并不是 4980 条平台线程在排队，它们只是堆里的对象。

这条对真实系统尤其要紧：数据库连接池 20、HTTP 客户端连接池 50、限流器 QPS——这些上限一个都没动。换虚拟线程之后把调用量放大 10 倍，压垮的是下游。

## 两万个平台线程不会 OOM，代价是十几秒

一开始我以为 2 万条平台线程会直接把 JVM 撑爆。没有。2 万条都建起来了，一起睡 3 秒：

| 2 万条线程，各睡 3 秒 | 创建耗时 | 全部 join 完 |
| --- | --- | --- |
| 虚拟线程 25.0.4 | 69 ms | 3040 ms |
| 平台线程 25.0.4 | 13973 ms | 3000 ms |
| 虚拟线程 21.0.3 | 104 ms | 3157 ms |
| 平台线程 21.0.3 | 16378 ms | 3017 ms |

`joinAll` 都是 3 秒左右——它们确实在睡。差别全在「创建」这一列：一条平台线程约 0.7–0.8 ms，两万条就是 14–16 秒；虚拟线程一条 3.5–5.2 µs，两万条 100 ms 上下。

内存上也没爆，但差得明显：同一程序采样进程 WorkingSet 峰值，25.0.4 上是虚拟线程 82 MB、平台线程 314 MB；21.0.3 上是 201 MB 和 319 MB。21 那侧虚拟线程的 201 MB 里有一大块是 GraalVM 自己的基线，别当成线程占用；能横向比的是同一 VM、同一列 82 与 314。

所以「平台线程几千条就崩」这句话，在我这台机器上不成立。真实约束是创建时间、栈内存和 GC 压力，不是某条固定条数上限——具体几万条，取决于你的 `-Xss`、堆大小和机器，得自己试。

## 二十万个虚拟线程躺着，堆里多 162 MB

把虚拟线程堆到 20 万条，全部 park 在一个 `CountDownLatch` 上，量堆增量：

```text
200000 parked virtual threads: heap delta = 162 MB, per thread ~ 849 B    // 25.0.4
200000 parked virtual threads: heap delta = 271 MB, per thread ~ 1421 B   // 21.0.3
```

一条大约 0.8–1.4 KB，是每个 JDK 版本、每个 VM 的具体实现值，不是规范承诺。20 万条两三百 MB，这个量级对「几十万」的说法是站得住的；再往上，先算堆，再算你的 GC 能不能扛。

这时候系统里到底多了多少条线程？20000 条虚拟线程全 park 住，打 `Thread.getAllStackTraces()`：

```text
B getAllStackTraces entries = 25        // 25.0.4
   ForkJoinPool-1-worker- x16
   ForkJoinPool-1-delayScheduler x1
   VirtualThread-unblocker x1
   main x1
   ...
B getAllStackTraces entries = 27        // 21.0.3
   ForkJoinPool-1-worker- x16
   VirtualThread-unparker x1
   main x1
   ...
```

16 条 `ForkJoinPool-1-worker-` 就是载体线程，等于 `availableProcessors()`。两万个虚拟线程只需要 16 条平台线程在它们之间来回切。

两个版本差异，都是实现细节，别拿名字写代码：辅助线程在 21 里叫 `VirtualThread-unparker`，25 里叫 `VirtualThread-unblocker`；25 多了 `delayScheduler`。另外从 21 起规范明确 `Thread.getAllStackTraces()` 只返回平台线程，所以虚拟线程根本不会出现在这张表里——想数虚拟线程，用 JFR，不是这个 API。

## 同一个 synchronized，在 21 上慢 20 多倍

这是这篇最该记住的一条，因为它跟版本号绑死。400 条虚拟线程，每条自己 new 一个锁对象（互不竞争），在锁里 `Thread.sleep(100)`：

```java
run("plain", i -> sleep(100));
run("synchronized(own obj)", i -> {
    Object o = new Object();
    synchronized (o) { sleep(100); }
});
run("reentrantLock(own)", i -> {
    ReentrantLock l = new ReentrantLock();
    l.lock();
    try { sleep(100); } finally { l.unlock(); }
});
```

```text
=== 21.0.3 ===
plain N=400 sleep=100ms -> 140 ms
synchronized(own obj) N=400 sleep=100ms -> 2681 ms
reentrantLock(own) N=400 sleep=100ms -> 109 ms
=== 25.0.4 ===
plain N=400 sleep=100ms -> 129 ms
synchronized(own obj) N=400 sleep=100ms -> 103 ms
reentrantLock(own) N=400 sleep=100ms -> 102 ms
```

400 条各睡 100 ms，本来应该 100 多毫秒一起结束。21 上是 2.7 秒 ≈ `400 / 16 × 100`——**同一时刻只有 16 条在跑**，其余的根本进不了阻塞状态，因为载体被钉住了，而载体只有 16 条。

这就是 pinning（JEP 444 里的 §Pinning）：虚拟线程在 `synchronized` 块里阻塞时无法卸载，会连载体一起卡住。JEP 444 同时写了两句容易被忽略的话：钉住时调度器**不会**通过扩大 parallelism 来补偿；`Object.wait()` 和原生帧也会钉。

21 上还能直接看到它。加上 `-Djdk.tracePinnedThreads=short`：

```text
Thread[#348,ForkJoinPool-1-worker-4,5,CarrierThreads]
    Pin3.lambda$main$1(Pin3.java:10) <== monitors:1
```

`monitors:1` 就是持有一个监视器；线程名里的 `CarrierThreads` 是载体线程所在的组。而同一个参数在 25.0.4 上跑，什么都不打印——24 起这个属性已经被移除，设了不生效（JEP 491）。

JDK 24 的 JEP 491 把这条路修掉了：`synchronized` 不再钉，阻塞在监视器上也能卸载。所以关于它的说法必须带版本：

| 症状 | 先看哪 |
| --- | --- |
| 400 个「同时」等待 100 ms 的任务跑了 2.7 秒 | JDK 是不是 < 24，阻塞是不是在 `synchronized` / `Object.wait()` 里 |
| 换成虚拟线程后耗时和固定池一模一样 | 任务是不是进了固定大小池子，或并发被 `corePoolSize`/信号量限住了 |
| 虚拟线程数上去了，下游开始超时 | 下游连接池、限流没动；虚拟线程只改了谁在等 |
| 线程数想再翻十倍 | 任务是不是 CPU 密集；换线程不改变核数 |

而且**升级到 24+ 不等于以后不用管**：`synchronized` 那条修了，原生帧那条没修。虚拟线程调 native 方法（JNI，或 FFM 下调），native 里阻塞时仍然钉住载体。25.0.4 上，200 条虚拟线程各调一次 `kernel32` 的 `Sleep(1000)`（这段只能在 Windows 上跑；FFM 在 21 还是预览 API，要用 `--enable-preview`，到 22 才转正，所以我只在 25 上测了）：

```text
native n=200 sleepMs=1000 wall=13334 ms
plain  n=200 sleepMs=1000 wall=1224 ms
```

`200 / 16 × 1000 = 12500` ms，跟实测的 13.3 秒对得上；同样的等待换成 `Thread.sleep` 只要 1.2 秒。JEP 491 留了三个不修的边角：native 帧、解析符号引用/加载类时阻塞、类初始化器里阻塞。它们少见，但都还在。

## CPU 密集的活，换不换一样

2000 个任务，每个在内存里空转 200 万次：

| 2000 个自旋任务 | 25.0.4 | 21.0.3 |
| --- | --- | --- |
| `fixedPool(16)` | 542 ms | 560 ms |
| `virtualPerTask` | 575 ms | 489 ms |

同一量级，互有胜负。虚拟线程解决的是「大量任务在等」，不是「任务算得快」；纯 CPU 的活它只会增加调度开销。第 22 课那句「开更多虚拟线程不会让 CPU 变快，只会让任务抢核」，在这里有数了。

调度器的两个旋钮，顺手记一下（默认值来自 JEP 444 和 JEP 491）：

| 参数 | 默认 | 什么时候才动 |
| --- | --- | --- |
| `jdk.virtualThreadScheduler.parallelism` | `availableProcessors()`（本文 16） | 基本别动；动它等于骗自己「核变多了」 |
| `jdk.virtualThreadScheduler.maxPoolSize` | 256 | 载体线程的硬上限。设得比 parallelism 小会直接把载体压下去（实测设成 3，载体就 3 条）；不是调优旋钮 |

注意载体池和 common pool 不是一个池：`ForkJoinPool.commonPool()` 的 parallelism 改不动载体数量。

## 跑一遍

把「同时在飞的任务数」打成峰值。2000 个任务看不出来，200 个就够：池子 4 条、虚拟线程池 4 条、每个任务一条虚拟线程，三种各跑 200 个任务：

<!-- run -->
```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    static final int TASKS = 200;
    static final int SLEEP_MS = 50;
    static final AtomicInteger inFlight = new AtomicInteger();
    static final AtomicInteger peak = new AtomicInteger();

    static void work() {
        peak.accumulateAndGet(inFlight.incrementAndGet(), Math::max);
        try {
            Thread.sleep(SLEEP_MS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        inFlight.decrementAndGet();
    }

    public static void main(String[] args) throws Exception {
        run("fixed pool(4)", Executors.newFixedThreadPool(4));
        run("virtual in pool(4)", Executors.newFixedThreadPool(4, Thread.ofVirtual().factory()));
        run("virtual per task", Executors.newVirtualThreadPerTaskExecutor());
    }

    static void run(String label, ExecutorService pool) throws Exception {
        inFlight.set(0);
        peak.set(0);
        try (pool) {
            for (int i = 0; i < TASKS; i++) {
                pool.execute(Main::work);
            }
        }
        System.out.println(label + " peak=" + peak.get() + " of " + TASKS);
    }
}
```

```text
fixed pool(4) peak=4 of 200
virtual in pool(4) peak=4 of 200
virtual per task peak=200 of 200
```

峰值是确定的，跟机器快慢无关：池子 4 条，无论底下是平台线程还是虚拟线程，同时在飞的就 4 个；每个任务一条虚拟线程，200 个才能一起进 `sleep`。这就是「池子限并发、虚拟线程不带来额外的并发额度」的最小证据。

`try (pool)` 会 `close` 并等所有任务结束，所以不需要再 `shutdown` + `awaitTermination`（第 22 课讲过这个 close 语义）。

## 还差的

- 结构化并发（`StructuredTaskScope`）没讲。在我用的 25.0.4 和 21.0.3 上它都还是预览 API，不加 `--enable-preview` 编译不过。任务之间有父子关系时的取消与异常传播，这篇只到「一条条提交」，真写起来还是得手工 join。
- 所有等待都是 `Thread.sleep` 模拟的，没测真实 socket/HTTP：DNS、TLS 握手、连接池借还、重试都会改变数字。JEP 444 列出的「阻塞时会卸载」的操作清单比我这张表长得多，哪些路径真能卸载，得用 JFR 的 `jdk.VirtualThreadPinned`（阈值 20 ms）在自己代码上确认。
- 21 上的 pinning 是在 Oracle GraalVM 21.0.3 上测的，不是 Temurin 21.0.x。钉住这件事发生在 HotSpot 运行时层，两个构建共用，但我没在 Temurin 21 上复跑，写文章时按「GraalVM 构建的 21.0.3」标注。
- 容器里没测：`parallelism` 默认跟着 `availableProcessors()` 走，cgroup CPU limit 与 JVM 看到的核数对不上时，载体线程数就会错。
- `ThreadLocal`、`getThreadGroup()` 返回 `null`、`setDaemon(false)` 抛 `IllegalArgumentException` 这些边角只确认了行为，没讲该怎么用。日志里的线程名默认是空串，要让可观测性可用，得用 `Thread.ofVirtual().name(...)` 显式起名。
