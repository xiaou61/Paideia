# 09 · 异常

## 四行成绩单，两个版本都是 170

本机 CPython 3.11.5（Windows）。成绩单是我手写的四行，玩具数据，不是谁家的日志。两个函数跑同一份数据：一个静默跳过坏行，一个把坏行打出来。

<!-- run -->
```python
RAW = """张三,90
李四,九十八
王五,80
赵六,缺考"""


def total_silent(text):
    total = 0
    for line in text.splitlines():
        name, raw = line.split(",")
        try:
            total += int(raw)
        except:
            pass
    return total


def total_precise(text):
    total = 0
    lineno = 0
    for line in text.splitlines():
        lineno += 1
        name, raw = line.split(",")
        try:
            total += int(raw)
        except ValueError as error:
            print(f"跳过第 {lineno} 行：{name} 的成绩 {repr(raw)}（{error}）")
    return total


print("静默版总分：", total_silent(RAW))
print("精确版总分：", total_precise(RAW))
```
```text
静默版总分： 170
跳过第 2 行：李四 的成绩 '九十八'（invalid literal for int() with base 10: '九十八'）
跳过第 4 行：赵六 的成绩 '缺考'（invalid literal for int() with base 10: '缺考'）
精确版总分： 170
```

我原来以为这段代码的问题是「数据脏」：`九十八`、`缺考` 确实不是整数，跳过它们不算错。跑完才发现两个版本总分都是 170——这才是该警惕的地方：**你没法从 170 判断异常处理写没写对**。静默版的结果和「这份成绩单本来就只有两个人有成绩」长得一模一样，等到对不上账，你只知道总数少了一个人的分，不知道少了谁、少在哪一行。

精确版多出来的那两行，就是排错时唯一能用的现场：第几行、谁、原始值长什么样。`repr(raw)` 把原始值的形状保住了——`'80'` 和 `80` 打印出来都像数字，`repr` 会让你看见它到底带不带引号。

所以 `except ValueError as error` 跟裸 `except:` 的差别不在「接不接得住」，而在**接住之后你手里有没有 `error` 这个东西**。`error` 就是解释器本来要打给你的那句话；不要它的写法也能跑，只是以后没人知道为什么跑出了这个数。

## 同一个笔误，被裸 except 变成了「业务结论」

给同一个统计函数加一行「成功行数」，本意是 `ok += 1`，手底下打成了 `okk += 1`。第一次用 `except ValueError:` 包着，直接跑（把这段存成 `09crash.py`）：

```python
RAW = """张三,90
李四,九十八
王五,80
赵六,缺考"""


def summarize(text):
    total = 0
    ok = 0
    for line in text.splitlines():
        name, raw = line.split(",")
        try:
            total += int(raw)
            okk += 1
        except ValueError:
            print("跳过坏行：", line)
    return total, ok


print(summarize(RAW))
```

```text
Traceback (most recent call last):
  File "C:\Users\Lenovo\AppData\Local\Temp\py09probe\09crash.py", line 20, in <module>
    print(summarize(RAW))
          ^^^^^^^^^^^^^^
  File "C:\Users\Lenovo\AppData\Local\Temp\py09probe\09crash.py", line 14, in summarize
    okk += 1
    ^^^
UnboundLocalError: cannot access local variable 'okk' where it is not associated with a value
```

`UnboundLocalError` 不是「值等于 0」：`okk` 在这一行之前从没被赋值过，`+=` 要先读再写，读的那一步就断了。它说明的是「我代码写错了」，跟成绩单里那两列脏数据毫无关系。

把第 15 行的 `except ValueError:` 换回裸 `except:`，同一份文件再跑一次：不报错，输出是 `(170, 0)`——总分是对的，成功行数是 0。

裸 `except:` 干的就是这件事：它不区分「数据坏」和「我写错了」，两类问题一起当异常跳过。于是程序跑完了，还交给你一个看着像业务结论的 `成功 0 行`。异常不是用来让程序跑完的，是用来决定「哪一类失败能继续、哪一类必须停下来」的；条件写宽了，你连这次该不该停都不知道。

## 有些东西根本不进 Exception 这一层

`KeyboardInterrupt`（按 Ctrl+C 时抛的）和 `SystemExit`（`sys.exit()` 抛的）不挂在 `Exception` 下面，而是直接挂在 `BaseException` 下。所以 `except Exception:` 接不到它们，裸 `except:` 接得到——裸 `except:` 等价于 `except BaseException:`：

<!-- run -->
```python
try:
    raise KeyboardInterrupt
except Exception:
    print("except Exception 接住了")
except BaseException:
    print("except Exception 没接住，只有 BaseException 接得住")

try:
    raise KeyboardInterrupt
except:
    print("裸 except 接住了 KeyboardInterrupt")

print("--- 裸 except 之后程序还在跑 ---")
```
```text
except Exception 没接住，只有 BaseException 接得住
裸 except 接住了 KeyboardInterrupt
--- 裸 except 之后程序还在跑 ---
```

这里的 `KeyboardInterrupt` 是我用 `raise` 手动抛的，不是真在终端按 Ctrl+C。两者抛的是同一个类，但「按下去停不下来」的手感得自己起个 `while True` 跑一次才算验过。

同一层还住着 `SystemExit`，后果更安静。`try: sys.exit(2)` 被裸 `except:` 接住之后，脚本继续往下跑完，退出码变成 0（实测输出 `裸 except 接住了 SystemExit，继续往下跑`，之后 `echo $?` 是 0 而不是 2）。CI 里「脚本自己写了 exit 2、流水线却是绿的」有一类成因就是这个——你写的那句退出码被自己的 `except` 吃了。

## 让错误带着因果走

`raise 新异常 from 原异常` 不是把两句话拼起来，而是把原异常挂到新异常的 `__cause__` 上：

<!-- run -->
```python
def parse_row(lineno, line):
    name, raw = line.split(",")
    try:
        return name, int(raw)
    except ValueError as error:
        raise ValueError(f"第 {lineno} 行 {name} 的成绩 {repr(raw)} 不是整数") from error


try:
    parse_row(2, "李四,九十八")
except KeyError:
    print("被 KeyError 接走")
except ValueError as error:
    print("错误消息：", error)
    print("直接原因：", repr(error.__cause__))
```
```text
错误消息： 第 2 行 李四 的成绩 '九十八' 不是整数
直接原因： ValueError("invalid literal for int() with base 10: '九十八'")
```

外层收到的还是 `ValueError` 一种类型，`from` 不改变抛出的类型、也不包一个容器，它只额外记下「我是被谁引起的」。不加捕获让它自己崩，stderr 会在两条 traceback 中间插一句（下面是实际输出的节选，中间那条 traceback 的帧省略了）：

```text
ValueError: invalid literal for int() with base 10: '九十八'

The above exception was the direct cause of the following exception:

...（第二条 traceback，这里省略帧）...

ValueError: 第 2 行 李四 的成绩 '九十八' 不是整数
```

两段各有各的用处：上面那段是「哪一行、哪个值坏了」，下面那段是「这个坏值传到了哪一步」。不写 `from` 直接 `raise` 一个新异常，3.11 里照样会把原异常链在后面，但连接句换成「During handling of the above exception, another exception occurred」——「处理一个异常时又出了异常」，和你主动声明的因果是两回事。

接住异常、做点清理、再原样往上抛，用不带参数的 `raise`：traceback 与压根没接住时逐字一致，不会多出「During handling」那一段（实测）。反过来，`from None` 会把原始那条彻底藏掉——traceback 里只剩新异常，`invalid literal...` 一个字都不剩。信息少了一半，适合「内部实现细节不该漏给调用方」的场合。

## finally 里别写 return

<!-- run -->
```python
def first_score():
    try:
        return 1 // 0
    finally:
        return "finally 里的 return 把异常盖掉了"


def close_up():
    try:
        raise ValueError("原始错误")
    finally:
        print("finally 照样执行")


print("返回值：", first_score())
try:
    close_up()
except ValueError as error:
    print("上层仍然收到：", error)
```
```text
返回值： finally 里的 return 把异常盖掉了
finally 照样执行
上层仍然收到： 原始错误
```

`first_score()` 里的 `1 // 0` 一次都没出现：`finally` 里的 `return` 直接把函数结束掉，正在往上抛的那个异常跟着没了。同一件事也发生在 `try` 里的 `return` 上——`finally` 的返回值盖掉它。`close_up()` 才是 `finally` 的本职：异常照常往上传（`原始错误` 原样到达上层），但收尾语句一定跑过。

顺带纠一句常见说法：「`finally` 一定执行」只在常规控制流里成立。`os._exit()` 直接结束进程、被 SIGKILL、解释器自己崩了，都不走 `finally`。这三种我没在进程级别验过，所以只当文档结论记着。

## 一次报一堆：3.11 的 except*

主循环遇到第一个坏行就退出的写法，在「要把坏行一次报全」时不够用。3.11 有 `ExceptionGroup` 和 `except*`：

<!-- run -->
```python
def parse_row(lineno, line):
    name, raw = line.split(",")
    try:
        return name, int(raw)
    except ValueError as error:
        raise ValueError(f"第 {lineno} 行 {name} 的成绩 {repr(raw)} 不是整数") from error


RAW = """张三,90
李四,九十八
王五,80
赵六,缺考"""

bad = []
lineno = 0
for line in RAW.splitlines():
    lineno += 1
    try:
        parse_row(lineno, line)
    except ValueError as error:
        bad.append(error)

try:
    raise ExceptionGroup(f"成绩单里有 {len(bad)} 行不能用", bad)
except* ValueError as group:
    for error in group.exceptions:
        print("收到：", error)
```
```text
收到： 第 2 行 李四 的成绩 '九十八' 不是整数
收到： 第 4 行 赵六 的成绩 '缺考' 不是整数
```

`ExceptionGroup` 是「一包异常」的容器，`except*` 拿到的不是单条异常，而是只装着匹配类型那些成员的一小群（`group.exceptions`）。所以第一次循环里所有的坏行都被攒进了同一个包里，一次报完。

两个容易掉进去的点。一是普通 `except ValueError` **接不到**组里的 `ValueError`：外层只能写 `except Exception` 拿到整包，`str()` 出来是 `成绩单里有 2 行不能用 (2 sub-exceptions)`（实测），不是某一行的消息。二是 `except*` 是 3.11 才有的语法，3.10 及更早的版本照抄会直接 `SyntaxError`——旧版本那条报错原文我没验，本机只有 3.11.5。

## 报错最后一行，先看哪

traceback 最后一行是类型加消息，它决定你先怀疑什么；中间那些帧只告诉你代码是怎么走到这里的。

| 最后一行长这样 | 它在说什么 | 先看哪 |
| --- | --- | --- |
| `UnboundLocalError: cannot access local variable 'okk'` | 这个名字在用之前从没被赋值 | 函数里这个名字的每一处拼写；它是不是只出现在 `+=` 左边 |
| `ValueError: invalid literal for int() with base 10: '九十八'` | 字符串类型没错，内容转不了 | 传给 `int()` 的那个值本身，以及它来自哪一列 |
| `KeyError: 'score'` | 字典里没有这个键 | 写入端用了哪些键；读取时是不是少了一层或拼错了 |
| `TypeError: 'NoneType' object is not subscriptable` | 你在对 `None` 取下标 | 返回它的那个函数：分支里是不是漏了 `return` |
| `ExceptionGroup: 成绩单里有 2 行不能用 (2 sub-exceptions)` | 一包里装着好几条 | 用 `except*` 按类型拆开看，别用 `except Exception` 当一件事处理 |

还有一件小事：`File "...", line 14` 里的行号是物理行号。它跟你编辑器里看到的对不上时，最先该怀疑的是粘贴时多算或少算了空行，而不是解释器。

## 还差的

- **自定义异常一个没写。** 要区分「业务失败」和「程序 bug」得自己定义异常类，那需要第 10 课的 `class`，这一课刻意绕开了。
- **Ctrl+C 只用手动 `raise` 模拟过。** 真按下去、裸 `except:` 吃住循环、第二次按才退出的手感，得自己起个 `while True` 试。
- **`finally` 的边界没在进程级别验。** `os._exit()`、SIGKILL、解释器崩溃都不走 `finally`，这三条我只有文档结论。
- **`except*` 的版本边界没实测。** 「3.10 会 SyntaxError」是文档结论，本机只有 3.11.5。
- **一条日志都没打。** 真实项目里 `except` 里该走 `logging.exception` 保住 traceback，比 `print` 强；日志怎么配是另一课的量。
