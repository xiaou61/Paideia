# 17 · 并发入门

## 这一课你要会

- 分清 CPU 密集与 I/O 密集，并说清它们分别该用什么方案；
- 知道 GIL 是什么、它让多线程在什么场景下没有收益；
- 写一个 `threading` 的最小例子，知道结果该用队列收集；
- 写一个 `asyncio` 的最小例子，理解 `async` / `await` 在等什么；
- 判断"这段代码到底需不需要并发"。

## 为什么

"慢"有两种完全不同的原因，解法相反：

- **CPU 密集**：算得多，比如压缩图片、跑模型、解析大 JSON。瓶颈在 CPU，多给几个核就能快。
- **I/O 密集**：在等，比如请求接口、读写数据库、下载文件。瓶颈在等待，CPU 大部分时间是闲的。

选错方案的结果是：给 I/O 任务开十个进程（内存翻十倍、启动慢），或者给 CPU 任务开十个线程（受 GIL 限制，一点没快）。

## 讲解

### 先判断：你的代码在算还是在等

一个简单的判据：

- 函数里大部分时间是 `for`、数学运算、字符串处理 → **CPU 密集**；
- 函数里大部分时间是 `requests.get`、`cursor.execute`、`open().read` → **I/O 密集**。

**先量再优化**：用 `time.perf_counter()` 把两段分别计时。很多"太慢"其实是某一次 SQL 慢，并发只会让它更慢。

### GIL：Python 线程的一个硬限制

CPython 有一个全局解释器锁（GIL）：**同一时刻只有一个线程在执行 Python 字节码**。

后果：

- 多线程做 CPU 计算**不会变快**，可能还因为切换变慢；
- 但线程在等 I/O 时会释放 GIL，所以**多线程做 I/O 是有效的**。

这不是"Python 线程没用"，而是"线程的用途被限定在 I/O 等待上"。

### 方案一：线程（适合 I/O）

```python
import threading

results = []
lock = threading.Lock()

def fetch(url):
    data = pretend_request(url)      # 这里大部分时间在等
    with lock:                       # 多个线程改同一个列表要加锁
        results.append(data)

threads = [threading.Thread(target=fetch, args=(url,)) for url in urls]
for t in threads:
    t.start()
for t in threads:
    t.join()                          # 等全部结束
```

三个要点：

- `start()` 才真正启动，`join()` 等它结束；
- **共享可变数据要加锁**，否则两个线程同时 `append` 可能丢数据；
- 结果收集用 `queue.Queue` 更省心——它自带锁，比手写 `Lock + list` 安全。

**什么时候别用线程**：任务数量几百上千时，线程本身的开销会变成瓶颈，改用线程池（`concurrent.futures.ThreadPoolExecutor`）限制并发数。

### 跑一遍

<!-- run -->
```python
import threading
from concurrent.futures import ThreadPoolExecutor


counter = 0
lock = threading.Lock()
seen = []


def work(n):
    global counter
    with lock:
        counter += n
        seen.append(n)
    return n * 10


with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(work, n) for n in range(1, 5)]
    results = [future.result() for future in futures]

print(results)
print(sorted(seen))
print(counter)
```
```text
[10, 20, 30, 40]
[1, 2, 3, 4]
10
```

`submit` 返回 `Future`，`future.result()` 按**提交顺序**取回返回值，所以 `results` 与线程实际谁先跑完无关。共享的 `counter` 和 `seen` 都在 `with lock` 里修改，结果才稳定可复现；不加锁，`counter += n` 的读-改-写可能交错，最终值就不再保证。

### 方案二：进程（适合 CPU）

```python
from concurrent.futures import ProcessPoolExecutor

def heavy(n):
    return sum(i * i for i in range(n))

with ProcessPoolExecutor() as pool:       # 默认按 CPU 核数开
    results = list(pool.map(heavy, [10**6] * 4))
```

每个进程有独立的解释器和内存，**绕开 GIL**，真正并行。代价：

- 进程启动比线程慢，内存占用成倍；
- 参数与返回值要能被 pickle（可序列化），不能直接传数据库连接、打开的文件、lambda；
- 共享状态要靠队列或共享内存，不能直接改同一个变量。

**判据**：单次任务要跑几百毫秒以上、任务数不超过核数几倍，才值得用进程；大量小任务用进程池反而更慢。

### 方案三：asyncio（适合大量 I/O）

```python
import asyncio

async def fetch(url):
    await asyncio.sleep(1)        # 模拟网络等待
    return f"{url} ok"

async def main():
    results = await asyncio.gather(
        fetch("a"), fetch("b"), fetch("c")
    )
    print(results)

asyncio.run(main())
```

读完这段要知道三件事：

1. `async def` 定义的是**协程**，调用它不会执行，只返回协程对象；
2. `await` 是"这里要等了，让别的协程先跑"；
3. `asyncio.gather` 同时跑多个协程，总耗时约等于最慢的那个，而不是相加。

asyncio 只有一个线程、一个事件循环，靠"等待时切换"实现并发。它适合**成百上千个网络请求**，不适合 CPU 计算——一个死循环会卡死整个事件循环。

**它不能直接和普通阻塞库混用**：`requests.get` 是阻塞的，放在协程里会卡住整个循环。要用支持异步的客户端（`httpx.AsyncClient`、`aiohttp`）。

### 三者的选择

| 任务 | 首选 | 理由 |
| --- | --- | --- |
| 几十个网络请求 | 线程池 | 简单，库都是同步的 |
| 上千个并发连接 | asyncio | 一个线程撑住大量等待 |
| 压缩、计算、图像处理 | 进程池 | 绕开 GIL，真并行 |
| 一次性的几个请求 | 直接顺序跑 | 引入并发只增加复杂度 |

**最后一行最重要**：三个请求各 100ms，顺序跑 300ms，用户根本感觉不到。并发代码的调试成本远高于 200ms。

## 常见误区

### 误区：加了线程就一定更快

**你以为**：并发等于加速。
**其实**：I/O 等待重叠才有收益；CPU 计算受 GIL 限制，任务太小还会被线程调度开销吃掉。
**怎么验证**：同一个函数分别用单线程与线程池跑，计时对比。

### 误区：`async` 函数调用后就开始执行

**你以为**：`fetch("a")` 已经在请求了。
**其实**：它只创建协程对象，必须 `await` 或者交给 `gather` / `create_task` 才会运行。忘了 await 的典型症状是"什么都没发生，也没有报错"。
**怎么验证**：调用后打印一句话，看是否只有这句话出现。

### 误区：多线程共享一个 list 直接 append 是安全的

**你以为**：append 是原子操作。
**其实**：单个 `append` 在 CPython 里通常不会崩，但"读-改-写"组合（比如 `if x not in lst: lst.append(x)`）一定会出竞态。规则是：**共享可变状态就加锁，或者改用队列**。

## 小结

先判断是 CPU 密集还是 I/O 密集，再选工具：I/O 用线程池或 asyncio，CPU 用进程池，任务很少就顺序跑。GIL 让多线程不适合计算。共享状态要加锁或用队列。asyncio 的关键是 `async def` 定义、`await` 让出。
