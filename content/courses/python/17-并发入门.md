# 17 · 并发入门

## 我先测了一遍，然后发现数字是假的

四个同样的计算任务，我在自己机器上（16 核，CPython 3.11）量了三遍：

| 写法 | 耗时 | 相对顺序 |
| --- | --- | --- |
| 顺序跑 | 0.69s | 1.00x |
| 4 个线程 | 0.53s | **1.30x** |
| 4 个进程 | 0.58s | 1.20x |

线程不算慢，居然还快了三成——这和我看到的「GIL 让多线程做计算没收益」直接冲突。

第二遍我加了预热（先空跑一次同一个函数），同样的代码变成：

| 写法 | 耗时 | 相对顺序 |
| --- | --- | --- |
| 顺序跑 | 0.61s | 1.00x |
| 4 个线程 | 0.61s | **1.00x** |
| 4 个进程 | 0.60s | 1.02x |

**1.30x 是假的。** 第一轮里"顺序"那组跑在冷启动上——字节码刚从文件读进内存、C 层的循环还没被预热，所以它偏慢，把后面的线程衬好看了。预热之后线程一点没快，1.00x，和 GIL 的预测一致。

这一课真正想教给你的，就是"先量一遍，再怀疑自己的量法"。我差点因为第一张表写下「线程也能提速」。

还有第二张表里的问题：4 个进程只有 1.02x，也不对。换成每个任务 0.97s 的重活再测：

```text
N=20,000,000 单个任务 0.97s
  顺序 4.17s | 4 线程 4.20s (0.99x) | 4 进程 1.72s (2.43x)
```

这次进程有收益了，但只有 2.43x 而不是 4x。原因很具体：Windows 上 `ProcessPoolExecutor` 用 spawn 起子进程，**每个子进程都要重新导入解释器和你的模块**，这一笔固定开销直接把小任务的收益吃光了。同一段代码在 Linux 上（fork）会好很多。

然后是 I/O：8 个「等 0.2 秒」的任务。

| 写法 | 耗时 | 相对顺序 |
| --- | --- | --- |
| 顺序跑 | 1.60s | 1.00x |
| 8 个线程 | 0.21s | **7.82x** |
| asyncio | 0.21s | 7.69x |

8 个任务的理想上限就是 8x，线程拿到 7.82x。**这就是全部区别：在算的，线程帮不上；在等的，线程几乎线性提速。**

## 先分清「在算」还是「在等」

判据不用背，看函数体里时间花在哪：

- 大片 `for`、数学、字符串处理、`json.loads` → **在算（CPU 密集）**
- `requests.get`、`cursor.execute`、`open().read()`、`socket.recv` → **在等（I/O 密集）**

拿不准就别猜，用 `time.perf_counter()` 把一段单独计时。我见过最多的误判是"接口太慢了，加并发"——结果一查是某条 SQL 少了索引，单次 2 秒；加并发只是让 100 个请求一起去挤那条 SQL。

## GIL：线程能干什么，被这一把锁定死了

CPython 里有一把全局解释器锁：**同一时刻只有一个线程在执行 Python 字节码**。

所以：

- 线程做纯计算，拿不到并行（实测 0.99x，甚至因为切换略慢）；
- 但线程在**等 I/O 时会释放 GIL**，别的线程接着跑——这才是线程的用武之地。

这不是"Python 线程没用"，而是"线程的用途被限定在等待上"。3.13 起有实验性的 free-threaded 构建（无 GIL），但生态还在适配，本课按常规构建讲。

## 方案一：线程池（在等的活）

```python
from concurrent.futures import ThreadPoolExecutor
import threading

counter = 0
lock = threading.Lock()
seen = []


def work(n):
    global counter
    with lock:
        counter += n
        seen.append(n)
    return n * 10


with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(work, n) for n in range(1, 5)]
    results = [f.result() for f in futures]

print(results)   # 按提交顺序取回返回值
```

<!-- run -->
```python
from concurrent.futures import ThreadPoolExecutor
import threading

counter = 0
lock = threading.Lock()
seen = []


def work(n):
    global counter
    with lock:
        counter += n
        seen.append(n)
    return n * 10


with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(work, n) for n in range(1, 5)]
    results = [f.result() for f in futures]

print(results)
print(sorted(seen))
print(counter)
```
```text
[10, 20, 30, 40]
[1, 2, 3, 4]
10
```

三个要点：

- `pool.submit` 返回 `Future`，`f.result()` **按提交顺序**取回返回值，与谁先跑完无关；
- 共享可变状态必须进 `with lock`：`counter += n` 是"读—改—写"三步，两个线程交错就会丢更新；
- 结果回传优先用 `queue.Queue` 或 `as_completed`，不要自己在锁里手搓列表。

**什么时候别用**：几百上千个阻塞任务时，线程自身栈（默认 8MB 虚拟内存）和切换开销会变成瓶颈，改用线程池限制并发数，或者走 asyncio。

## 方案二：进程池（在算的活）

```python
from concurrent.futures import ProcessPoolExecutor


def heavy(n):
    return sum(i * i for i in range(n))


if __name__ == "__main__":            # Windows / macOS 上的 spawn 必须有这一行
    with ProcessPoolExecutor() as pool:
        results = list(pool.map(heavy, [20_000_000] * 4))
```

每个进程有独立解释器和内存，绕开 GIL，真并行。代价三条，都是硬代价：

- **启动慢**：我实测 4 个 0.97s 的任务只拿到 2.43x，差距就在起进程；
- **参数和返回值必须能 pickle**：数据库连接、打开的文件、lambda、生成器都传不过去；
- **共享状态不能靠变量**：要用 `multiprocessing.Queue` / `Manager` / 共享内存，改动本身就有成本。

判据：单个任务要跑几百毫秒以上、任务数不超过核数的几倍，才值得起进程池。一堆几十毫秒的小任务丢进进程池，通常比顺序跑还慢。

### 我第一次跑进程池撞的墙

```text
RuntimeError:
        An attempt has been made to start a new process before the
        current process has finished its bootstrapping phase.

        This probably means that you are not using fork to start your
        child processes and you have forgotten to use the proper idiom
        in the main module:

            if __name__ == '__main__':
                freeze_support()
                ...
concurrent.futures.process.BrokenProcessPool: A process in the process pool
        was terminated abruptly while the future was running or pending.
```

上面那段代码里那行 `if __name__ == "__main__":` 不是装饰。Windows 用 **spawn** 起子进程：新进程会重新导入你的脚本，如果没有这层守卫，"导入脚本"就等于"又跑一遍建进程池"，无限递归。Python 检测到这个情况就抛上面那句。

这个错误特别容易出现在**脚本能跑、但 dot 一倍**的场景：写在一个函数里没事，一搬到模块顶层就炸。

## 方案三：asyncio（海量等待）

```python
import asyncio


async def fetch(url):
    await asyncio.sleep(0.2)          # 真实场景换成 httpx.AsyncClient
    return f"{url} ok"


async def main():
    print(await asyncio.gather(fetch("a"), fetch("b"), fetch("c")))


asyncio.run(main())
```

三件事要记牢：

1. `async def` 定义的是**协程**，调用它不执行，只得到协程对象；
2. `await` 的意思是"我要等了，让别的协程先跑"；
3. `gather` 并发跑，总耗时约等于最慢的那个，不是相加——我上面 8×0.2s 实测 0.21s，就是这条。

它是单线程单事件循环，靠"等的时候切走"实现并发。所以：

- **一个死循环会卡死整个循环**，任何 CPU 活都得丢进 `run_in_executor` 或进程池；
- **不能用阻塞库**：`requests.get` 放协程里会把整个事件循环堵住，必须换 `httpx.AsyncClient` 或 `aiohttp`。

## 三种方案怎么选

| 你的处境 | 选什么 | 为什么 |
| --- | --- | --- |
| 几十个请求，库都是同步的（requests、pymysql） | 线程池 | 改造成本最低，够用 |
| 上千个并发连接、长连接 | asyncio | 一个线程就能撑住大量等待 |
| 压缩、图像处理、解析大文件 | 进程池 | 绕开 GIL 真并行 |
| 就三个请求 | **顺序跑** | 省下的 200ms 用户感觉不到，调试成本却是实打实的 |

最后一行值得单独说。我现在的默认是**先顺序跑，量出耗时，再决定要不要并发**。并发代码的 bug 是偶发的：加锁漏一个分支、异常在子线程里被吞掉、`Future` 没取 result 于是错误静默消失——这三种我都踩过，而且都不是靠读代码能一眼看出来的。
