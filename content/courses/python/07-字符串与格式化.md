# 07 · 字符串与格式化

## `得分：` 后面不能直接加一个浮点数

```python
print("得分：" + 92.456)
```

```text
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: can only concatenate str (not "float") to str
```

我原来以为 `+` 会把 `92.456` 自动转成字符串。实际不会，`str + float` 直接抛 `TypeError`。报错最后一行已经把原因写全：`can only concatenate str (not "float") to str`。

把分数放进变量，用 f-string 再打印一次：

```python
name = "小林"
score = 92.456
print(f"{name} 得了 {score:.1f} 分")
```

```text
小林 得了 92.5 分
```

大括号里能放变量，也能跟格式说明。`:.1f` 保留一位小数；`:,` 加千分位；`>10` 右对齐到 10 个字符宽：

```python
print(f"{1_000_000:,}")
print(f"{'abc':>10}|")
```

```text
1,000,000
       abc|
```

`1_000_000` 里的下划线只是给人读的，Python 会忽略；`:,` 才把它打印成 `1,000,000`。`>10` 那行在 `abc` 前面补了 7 个空格，末尾的 `|` 用来确认宽度到哪里结束。

`+` 不是不能用：两边都是字符串时，`"a" + "b"` 得到 `"ab"`。但只要混进数字，先想 f-string。

## `text.upper()` 之后，`text` 还是原来的

第二个我猜错的地方是「方法会改原串」：

```python
text = "abc"
print(text.upper())
print(text)
```

```text
ABC
abc
```

`upper()` 返回了一个新串 `"ABC"`，`text` 没动。要留下结果，必须赋值回去：`text = text.upper()`。

字符串不可变，单个字符也不能原地替换：

```python
text = "abc"
text[0] = "x"
```

报错最后一行是：

```text
TypeError: 'str' object does not support item assignment
```

这不是写法问题，是 `str` 没有这个能力。要改一个字符，只能造新串，比如 `text = "x" + text[1:]`，让 `text` 指向 `"xbc"`；原来的 `"abc"` 仍然没变。

`strip()`、`replace()`、`lower()` 也一样，都返回新串。调用完不接返回值，等于白做。

## `repr()` 让我看见首尾的两个空格

成绩名单从表格里复制出来，长这样：

```python
raw = "  语文, 数学, 英语  "
print(repr(raw))
print(repr(raw.strip()))
```

```text
'  语文, 数学, 英语  '
'语文, 数学, 英语'
```

`print(raw)` 会把首尾空格直接打出来，和正文混在一起，肉眼很难确认。`repr()` 把引号和空白都显出来：第一行首尾各有两个空格，第二行调用 `strip()` 后没有了。

`repr()` 不是去空格工具，它只是把字符串表示成可读形式；真正去空格的是 `strip()`、`lstrip()`、`rstrip()`。排错时先 `repr()` 看一眼，再决定用哪个。

方法名不用背。在交互式解释器里敲 `help(str.split)`，它会给出签名 `split(self, /, sep=None, maxsplit=-1)` 和说明。`dir()` 列出全部方法时是一长串名字，很多是双下划线，初学阶段看不出该用哪个。

## `split()` 和 `split(" ")` 切出来的东西不一样

把名单按逗号拆开，去掉每段两边的空格：

```python
raw = "  语文, 数学, 英语  "
parts = []
for part in raw.strip().split(","):
    parts.append(part.strip())
print(parts)
print("、".join(parts))
```

```text
['语文', '数学', '英语']
语文、数学、英语
```

这里用 `for` 循环加 `append`，没有用列表推导式；推导式还没讲，先不引入。

`split(",")` 按逗号切。`join` 是分隔符在前面调用：`"、".join(parts)` 用「、」把列表接起来。`join` 的参数是可迭代对象，里面的元素必须都是字符串；列表里混进数字会抛 `TypeError`。

**`split` 与 `join` 不是无条件互逆。** 只有显式分隔符（非空）且不丢空段时，`sep.join(text.split(sep))` 才能还原原文。无参 `split()` 按任意连续空白切，还会丢掉空串：

```python
print("  a  b  ".split())
print(" ".join(["a", "b"]))
print("  a  b  ".split(" "))
print(repr(" ".join("  a  b  ".split(" "))))
```

```text
['a', 'b']
a b
['', '', 'a', '', 'b', '', '']
'  a  b  '
```

第一行把连续空格当成一个分隔符，开头和结尾的空格直接没了。第二行再用一个空格 `join`，只能得到 `a b`，原来的六个空格回不来。

第三行 `split(" ")` 是显式分隔符：每个空格都切一刀，连续空格之间会留下空字符串。最后一行用同一个分隔符 `join`，又能拼回原来的 `'  a  b  '`。处理 CSV 这种空字段有意义的数据时，别用无参 `split()` 把空字段吃掉。

## `find` 找不到时返回 `-1`，而 `-1` 是真值

常用方法先放一张「调用 → 结果」的表，别只看名字：

| 调用 | 结果 |
| --- | --- |
| `"  hi  ".strip()` | `'hi'` |
| `"a,b,c".split(",")` | `['a', 'b', 'c']` |
| `"、".join(["a", "b"])` | `'a、b'` |
| `"a-b".replace("-", "+")` | `'a+b'` |
| `"hello.py".startswith("hello")` | `True` |
| `"hello.py".endswith(".py")` | `True` |
| `"Hello".lower()` | `'hello'` |
| `"abc".find("b")` | `1` |
| `"abc".find("x")` | `-1`（找不到） |

`find` 单独说：它返回子串第一次出现的下标，找不到返回 `-1`，不是 `False`，也不是 `None`：

```python
print("abc".find("x"))
print("x" in "abc")
```

```text
-1
False
```

`-1` 在 `if` 里是真值。于是 `if text.find("x"):` 在没找到时反而会进入分支；更别扭的是，如果子串正好在下标 `0` 找到，`find` 返回 `0`，又会被当成假。判断有没有，直接用运算符 `in`：

```python
text = "abc"
if "b" in text:
    print("有")
```

```text
有
```

`in` 是运算符，不是方法，不能写成 `text.in("b")`：

```python
"abc".in("b")
```

报错最后一行是：

```text
SyntaxError: invalid syntax
```

非要用 `find`，就把条件写全：`if text.find("x") != -1:`。但判断有没有，`in` 更短，也不会踩 `-1` 的坑。

## Windows 默认 `cp936`：三种表现别混在一起

我在本机 CPython 3.11.5 上查了一下：

`import locale`、`import sys` 到第 12 课才讲；这里只用它们读环境信息，先照抄。

```python
import locale
import sys

print(sys.version.split()[0])
print(locale.getpreferredencoding(False))
```

```text
3.11.5
cp936
```

没有开 UTF-8 模式时，中文 Windows 的默认编码是 `cp936`（代码页 936，GBK 系），不是 UTF-8。读一个 UTF-8 文件、又没写 `encoding` 时，报错是这样的：

`open()` 的完整用法下一课才讲；这里只看编码报错，先照抄这两行。

```python
with open("utf8.txt") as file:
    print(file.read())
```

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0xad in position 2: illegal multibyte sequence
```

我用的是内容为「中文」的 UTF-8 文件，字节是 `e4 b8 ad e6 96 87`。第 3 个字节 `0xad` 在 GBK 里不是一个合法序列，所以这里不是「显示成乱码」，而是解码阶段直接抛异常。要读它，写 `open("utf8.txt", encoding="utf-8")`。

第二种是写文件时编码不对。`open(path, "w")` 不写 `encoding`，会按 `cp936` 写；别的程序按 UTF-8 读，就会在解码时报错。我这边读回来是：

```text
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd6 in position 0: invalid continuation byte
```

如果写的字符 GBK 根本表示不了，比如 emoji `🙂`，写入当场就会失败：

```text
UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f642' in position 0: illegal multibyte sequence
```

第三种是控制台码页。`chcp` 显示 936 时，终端按 936 解释字节；一个程序按 UTF-8 往外写，屏幕上就是乱码。反过来，把 UTF-8 终端里的输出交给只认 936 的旧工具，也会乱。Python 3.11 往 Windows 控制台打印走 Unicode 接口，这一层不按文件字节走；但把输出重定向到文件时，Python 按 `sys.stdout.encoding` 写字节。我这里重定向时 `sys.stdout.encoding` 是 `gbk`，实测 `print("中文")` 重定向出来的文件是 `d6 d0 ce c4`，不是 UTF-8 的 `e4 b8 ad e6 96 87`。

所以别靠「看起来没乱码」判断编码。读写文本文件时明确写 `encoding="utf-8"`，这是下一课文件读写的前提。

## 4,000,000 次拼接：不是平方，但也别依赖

我原来以为循环里 `s = s + x` 每次都造新串，数据一大就会慢成平方。实测在 Windows 上的 CPython 3.11.5 不成立。我跑了三个规模，`x` 是单个字符，每一档先预热一次，再计一次时间：

`import time` 和第 12 课的模块有关；这里只用 `perf_counter()` 读一个不断变大的秒数，先照抄。

```python
import time

def plus(n):
    s = ""
    for _ in range(n):
        s = s + "x"
    return len(s)

def via_join(n):
    parts = []
    for _ in range(n):
        parts.append("x")
    return len("".join(parts))

for n in (100_000, 1_000_000, 4_000_000):
    plus(n)
    via_join(n)
    t1 = time.perf_counter()
    plus(n)
    d1 = time.perf_counter() - t1
    t2 = time.perf_counter()
    via_join(n)
    d2 = time.perf_counter() - t2
    print(f"{n:>9,} plus={d1:.3f}s join={d2:.3f}s")
```

```text
  100,000 plus=0.008s join=0.003s
1,000,000 plus=0.069s join=0.041s
4,000,000 plus=0.883s join=0.193s
```

这是这台机器上的单次计时，换机器或换负载会变。从 100k 到 4M，规模乘 40，`plus` 从 0.008s 到 0.883s，约 110 倍，远不到平方级的 1600 倍。原因是 CPython 在这个场景里有原地扩容优化：只要这个串没有被别的变量共用，它可以直接在原缓冲区后面扩，不必每次都把整串复制一遍。这是**当前实现的行为，不是语言保证**。换 PyPy、换版本，或者 `s` 还有别的引用时，都可能退回每次复制。

所以「大量拼接用 `join`」的结论仍然成立，理由改成「不要依赖某个实现的临时优化」，而不是「`+` 一定是平方复杂度」。具体写法：先 `append` 到列表，最后 `"".join(parts)`。收集和拼接分成两步，读代码的人不用猜解释器会不会帮你优化。

## 还差的

- 只讲了 `strip`、`split`、`join`、`replace`、`startswith`、`endswith`、`lower`、`upper`、`find` 这一小撮方法；正则、`translate`、Unicode 规范化都没碰。
- 格式说明只用了 `:.1f`、`:,`、`>10`，没讲百分比、科学计数法、日期格式和 `str.format()` 的完整语法。
- 编码只讲到「读写文件显式写 utf-8」。`bytes` 与 `str` 的 `encode`/`decode`、`errors=` 的取舍、BOM 和换行符差异都没讲，下一课才真正读写文件。
- 拼接性能只测了本机 CPython 3.11.5、单字符、1 到 4 百万次；PyPy、长字符串、多线程下的数字不一样，本文没有外推。
- `find` 的 `start`/`end` 参数、`rfind`、`index`，以及 `split` 的 `maxsplit` 都没讲。
