# 11 · 继承与多态

## Invoice 的 super() 没走到 Record

```python
class Record:
    def __init__(self, number):
        self.number = number


class Audited(Record):
    def __init__(self, number, note):
        super().__init__(number)
        self.note = note


class Priced(Record):
    def __init__(self, number, amount):
        super().__init__(number)
        self.amount = amount


class Invoice(Audited, Priced):
    def __init__(self, number, note, amount):
        super().__init__(number, note)


try:
    inv = Invoice("INV-001", "已核对", 90.0)
except TypeError as error:
    print(f"{type(error).__name__}: {error}")

print([cls.__name__ for cls in Invoice.__mro__])
```

```text
TypeError: Priced.__init__() missing 1 required positional argument: 'amount'
['Invoice', 'Audited', 'Priced', 'Record', 'object']
```

`try` 只是为了在同一个脚本里继续打印 MRO；错误本身没有被修掉。我原来以为
`Audited.__init__` 里的 `super()` 会去调 `Record.__init__`。实际不是：
`Invoice` 的 MRO 是 `Invoice → Audited → Priced → Record → object`，
零参数 `super()` 从写它的类之后继续找，`Audited` 之后是 `Priced`，不是 `Record`。

这就是为什么 `super()` 不能简单记成「父类那一份」。在单继承里，「下一个」恰好是父类，
所以这个错误在单继承里看不出来；一到多重继承，`super()` 的下一站由 MRO 决定，
可能跳到兄弟类，也可能先停在某个 mixin，而不是你脑子里的「父类」。

具体顺序以 `__mro__` 为准。Python 3 的类创建用 C3 线性化算 MRO，
它不是简单的深度优先；合并规则不用背，`__mro__` 会给出结果。
基类顺序是输入的一部分，
把 `class Invoice(Audited, Priced)` 改成 `(Priced, Audited)`，前两项就会反过来。
MRO 不一致时，`class` 语句本身就会报 `TypeError`
（`Cannot create a consistent method resolution order ...`）。
对普通方法，属性查找也沿这条列表：实例字典没有，就按 MRO 依次看类字典；
方法调用找到的第一个函数，就是这次执行的代码。

如果你从 Java 来：Java 的类单继承、接口多实现；Python 的类可以多继承。
差别在冲突怎么解决——Java 要求实现类显式覆盖两个互不相关的接口里签名相同的 default 方法，
Python 直接调用时按 MRO 选第一个。不是谁更强，是规则不同。

## 把每一层接上

修法不是把 `Record.__init__` 写死到每个类里。`Audited` 直接调 `Record` 会绕过 MRO，
这条路径上 `Priced` 不会被走到；`Priced` 直接调 `Record` 也一样。
协作写法是每个 `__init__` 只处理自己的参数，把剩下的关键字参数交给 `super()`。
根类 `Record` 也保留 `super().__init__(**kwargs)`：这样把它放进别的 MRO 时，
链不会在它这里断掉。

`**kwargs` 前面的课没讲：它把没被形参接住的关键字参数收成一个字典，再原样转交。
第 15 课讲装饰器时会正式用到它，这里先照抄。

<!-- run -->
```python
class Record:
    def __init__(self, number, **kwargs):
        super().__init__(**kwargs)
        self.number = number


class Audited(Record):
    def __init__(self, number, note, **kwargs):
        super().__init__(number=number, **kwargs)
        self.note = note


class Priced(Record):
    def __init__(self, number, amount, **kwargs):
        super().__init__(number=number, **kwargs)
        self.amount = amount


class Invoice(Audited, Priced):
    def __init__(self, number, note, amount):
        super().__init__(number=number, note=note, amount=amount)

    def total(self):
        return self.amount * 1.06


inv = Invoice("INV-001", "已核对", 90.0)
print([cls.__name__ for cls in Invoice.__mro__])
print(Invoice.__mro__.count(Record))
print(inv.number, inv.amount, inv.note)
print(f"{inv.total():.2f}")
print(isinstance(inv, Audited), isinstance(inv, Priced), isinstance(inv, Record))
```

```text
['Invoice', 'Audited', 'Priced', 'Record', 'object']
1
INV-001 90.0 已核对
95.40
True True True
```

输出第二行是 `1`：`Record` 在 MRO 里只出现一次，所以 `Record.__init__` 只跑一次。
这是 `super()` 沿 MRO 走的结果，不是 Python 自动去重你的显式调用。
每个中间类都调用 `super()`，`Record` 才会被走到。
`super()` 不只用于初始化：`super().total()` 也按同一条 MRO 找下一个 `total`。

如果 `Priced.__init__` 忘了 `super()`：

```python
class Priced(Record):
    def __init__(self, number, amount, **kwargs):
        self.amount = amount
```

把上面跑一遍里的 `Priced` 换成这段，再运行 `print(inv.amount, inv.note)`
和 `print(inv.number)`；构造本身不报错，`inv.number` 没有：

```text
90.0 已核对
AttributeError: 'Invoice' object has no attribute 'number'
```

这是同一个 bug 的静默版本：构造能过，字段少一个。`super()` 在某一层断了，
它后面的类就整个被跳过。这也是为什么「菱形继承下共享基类只调一次」不是 bug：
共享基类只应在协作链末尾被走到一次；真正的问题是某一层没接上链，
或者你显式调了两次 `Record.__init__`。

## isinstance 不认鸭子

多态不要求继承。下面这个 `show_total` 只要求对象有 `number` 和 `total()`：

```python
class Record:
    def __init__(self, number):
        self.number = number

    def total(self):
        raise NotImplementedError


class Invoice(Record):
    def __init__(self, number, amount):
        super().__init__(number)
        self.amount = amount

    def total(self):
        return self.amount * 1.06


class FakeInvoice:
    def __init__(self, number, total):
        self.number = number
        self._total = total

    def total(self):
        return self._total


def show_total(bill):
    print(f"{bill.number}: {bill.total():.2f}")


show_total(Invoice("INV-001", 90.0))
show_total(FakeInvoice("FAKE-1", 12.5))
print(isinstance(FakeInvoice("FAKE-1", 12.5), Record))
```

```text
INV-001: 95.40
FAKE-1: 12.50
False
```

`FakeInvoice` 没有继承 `Record`，`show_total` 照样能处理它，
因为这次调用需要的 `number` 和 `total()` 都在。这就是鸭子类型：
不看它是什么，看它这次能不能做这件事。
同一个 `bill.total()`：传 `Invoice` 时执行 `Invoice.total`，
传 `FakeInvoice` 时执行 `FakeInvoice.total`。调用方只写一次调用，
对象各自决定执行哪份代码——这是多态；`isinstance` 判断的是类型关系，
不是这次调用走哪份代码。

`isinstance(fake, Record)` 是 False。对普通类，`isinstance` 看的是类型/继承关系，
不看方法集合。`hasattr(fake, "total")` 也只能说明属性在，不能说明它接受你的参数；
要验证就调用，让异常暴露。

ABC 把「必须实现」变成构造时的检查：

```python
from abc import ABC, abstractmethod


class Record(ABC):
    def __init__(self, number):
        self.number = number

    @abstractmethod
    def total(self):
        ...


class Draft(Record):
    pass


class Invoice(Record):
    def __init__(self, number, amount):
        super().__init__(number)
        self.amount = amount

    def total(self):
        return self.amount * 1.06


for cls, args in [(Record, ("R-1",)), (Draft, ("D-1",))]:
    try:
        cls(*args)
    except TypeError as error:
        print(f"{cls.__name__}: {type(error).__name__}: {error}")

print(f"Invoice: {Invoice('INV-001', 90.0).total():.2f}")
```

```text
Record: TypeError: Can't instantiate abstract class Record with abstract method total
Draft: TypeError: Can't instantiate abstract class Draft with abstract method total
Invoice: 95.40
```

`ABC` 本身没有抽象方法，`ABC()` 能建（`type(ABC()).__name__` 输出 `ABC`）；
不能建的是还有未实现抽象方法的
`Record` 和 `Draft`。`Draft` 继承了抽象方法但没实现，所以它仍然是抽象类。

`@abstractmethod` 单独写在普通类里不拦实例化：

```python
from abc import abstractmethod


class NotABC:
    @abstractmethod
    def total(self):
        ...


print(type(NotABC()).__name__)
print(NotABC().total())
```

```text
NotABC
None
```

拦截来自 `ABC`/`ABCMeta` 的实例化检查，不是 `@abstractmethod` 装饰器本身。
`...` 只是省略函数体；抽象方法可以有实现，子类可以 `super().total()` 调它。

`@abstractmethod`、`@runtime_checkable` 都是装饰器；第 15 课讲装饰器，这里先照抄。

如果你要的是「任何有 `total()` 的对象都能传」，而不是「必须继承我的基类」，
用 `typing.Protocol` 描述形状：

```python
from typing import Protocol, runtime_checkable


@runtime_checkable
class Billable(Protocol):
    def total(self):
        ...


class FakeInvoice:
    def __init__(self, number, total):
        self.number = number
        self._total = total

    def total(self):
        return self._total


class WeirdInvoice:
    def total(self, currency):
        return currency


print("正常签名:", isinstance(FakeInvoice("F-1", 12.5), Billable))
print("错误签名:", isinstance(WeirdInvoice(), Billable))

try:
    Billable()
except TypeError as error:
    print(f"Billable: {type(error).__name__}: {error}")
```

```text
正常签名: True
错误签名: True
Billable: TypeError: Protocols cannot be instantiated
```

`@runtime_checkable` 只检查成员在不在，不检查参数和返回类型：
`WeirdInvoice.total` 需要一个参数、返回字符串，`isinstance` 仍为 True。
`Protocol` 类本身不能实例化。不加 `@runtime_checkable` 就 `isinstance`，会报
`TypeError: Instance and class checks can only be used with @runtime_checkable protocols`。
如果 Protocol 里有数据成员，`issubclass` 还会报
`TypeError: Protocols with non-method members don't support issubclass()`；
`isinstance` 仍只查属性存在。

静态类型检查器（mypy/pyright）会按 Protocol 的签名检查；运行时不做。
类型注解本身在第 13 课。ABC 还可以 `register()` 一个虚拟子类，让 `isinstance` 为真，
但不会把方法实现复制过去；所以 `isinstance` 为真只说明类型系统认了这层关系，
不证明对象行为正确。

## 什么时候别把类型关系改掉

「是一个」用继承、「有一个」用组合，是个起点，不是判据。`Invoice` 是一种 `Record`，
所以 `Invoice(Audited, Priced)` 说得通；`Invoice` 有一个税率，
所以 `TaxRule` 该作为参数/属性，不该进基类列表。

如果为了拿 `TaxRule.apply` 就让 `Invoice(TaxRule)`，`isinstance(inv, TaxRule)` 会为真，
但发票不是一种税率。类型层级开始说谎，后面每个读代码的人都要重新猜。

多重继承不是「尽量不要用」这么简单的结论。标准库的 `socketserver.ThreadingTCPServer`
就是 `ThreadingMixIn` + `TCPServer` 的组合，`__mro__` 里两者都在；
这说明多继承本身不是错误，关键是每个基类是否真的表达了一种能力或关系、
协作链是否完整。

抽象基类也不是「更面向对象」的徽章。只有当你要在构造阶段拦住漏实现的方法，
并且这组类确实共享一个契约时，再考虑 ABC；只想描述「能传什么」，Protocol 更轻。

## 还差的

- `super()` 只讲了零参数、实例方法里的用法；两参数形式、在 `classmethod`/`staticmethod`
  里的行为，以及 `super(type, obj)` 的完整规则没讲。
- MRO 只给了一个四层菱形和基类换序的结果；C3 的完整推导、
  `TypeError: Cannot create a consistent method resolution order` 的各种冲突组合没展开。
- ABC 只讲了实例化检查；`register()` 虚拟子类、`abstractmethod` 与
  `classmethod`/`property` 组合、`__subclasshook__` 都没讲。
- `Protocol` 只讲了运行时成员检查；泛型 Protocol、`TypeVar`、mypy/pyright 的配置没讲，
  静态类型注解要到第 13 课。
- `**kwargs` 只在这里当转发工具用；它的完整规则和装饰器里的
  `*args, **kwargs` 在第 15 课。
