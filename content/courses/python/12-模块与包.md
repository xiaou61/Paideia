# 12 · 模块与包

## import 先执行了一遍模块

两个文件，放在同一目录：

```python
# service.py
print("service 顶层被执行")


def add(a, b):
    return a + b
```

```python
# main.py
import service

print("main 里 __name__ =", __name__)
print("service 里 __name__ =", service.__name__)
print(service.add(1, 2))
```

在 Python 3.11.5 的 Windows 上运行 `python main.py`：

```text
service 顶层被执行
main 里 __name__ = __main__
service 里 __name__ = service
3
```

我没有在 `main.py` 里写任何打印 `service 顶层被执行` 的代码，它还是出现了。原因是 `import service` 不只是「登记一个名字」，它会把 `service.py` 的顶层代码执行一遍。第二次再 import 同一个模块，Python 直接用 `sys.modules` 里的缓存，不会再执行。

## __name__ 决定这段代码是不是入口

被直接运行时 `__name__` 是 `"__main__"`；被 import 时是模块名。`if __name__ == "__main__":` 只保护它缩进内的代码，模块顶层的 `print`、常量、函数定义照样执行：

```python
# service.py
print("service 顶层还是会执行")


def add(a, b):
    return a + b


if __name__ == "__main__":
    print("只有直接运行才打印")
```

```text
# python main.py
service 顶层还是会执行

# python service.py
service 顶层还是会执行
只有直接运行才打印
```

所以那句话要说得准确：`if __name__ == "__main__":` 防的是「被 import 时执行入口代码」，不是「防 import 执行整个文件」。顶层代码永远会跑；想让它不跑，就把它放进函数或判断块里。

## 三种 import，以及 import math.sqrt 到底错在哪

```python
import math
from math import sqrt
import statistics as st

print(sqrt(16), math.sqrt(16), st.mean([1, 2, 3]))
```

输出：

```text
4.0 4.0 2
```

`import math` 引入整个模块，用 `math.sqrt`；`from math import sqrt` 只把 `sqrt` 这个名字拿进来；`import statistics as st` 起别名。标准库的小函数用第二种读起来最干净，第三方库用 `import x as y` 让前缀提醒你「这是外部依赖」。这里用标准库 `statistics` 做别名例子，不需要额外安装。

`import math.sqrt` 不是语法错误。`import` 后面可以跟点号，编译能过；运行时报：

```text
ModuleNotFoundError: No module named 'math.sqrt'; 'math' is not a package
```

原因是 import 机制先导入 `math`，再把 `sqrt` 当成 `math` 的子模块去找；`math` 是一个模块文件，不是包，所以没有 `sqrt` 子模块。要直接拿 `sqrt`，写 `from math import sqrt`。

避免 `from module import *`：它把模块里所有不以下划线开头的名字倒进当前命名空间。两个模块都有 `format` 时，后 import 的覆盖前面的；读代码时也看不出 `format` 来自哪。需要少数名字就显式列出来，或者 `import module` 用前缀。`__all__` 能限制 `*` 的范围，但同名覆盖的问题还在。

## python main.py 把脚本目录放在 sys.path[0]

`proj/tools/main.py` 里打印两个布尔值：

```python
# proj/tools/main.py
import sys
from pathlib import Path

print("脚本目录在 sys.path[0]:", sys.path[0] == str(Path(__file__).resolve().parent))
print("cwd 在 sys.path[0]:", sys.path[0] == str(Path.cwd()))
print("sys.path[0] 的名字:", Path(sys.path[0]).name)
```

在 `proj` 目录里分别用两种方式跑：

```text
PS> python tools\main.py
脚本目录在 sys.path[0]: True
cwd 在 sys.path[0]: False
sys.path[0] 的名字: tools

PS> python -m tools.main
脚本目录在 sys.path[0]: False
cwd 在 sys.path[0]: True
sys.path[0] 的名字: proj
```

`python proj\main.py` 无论你从哪个目录敲，`sys.path[0]` 都是**脚本所在目录**，不是当前工作目录。只有 `python -m`、`python -c` 和交互模式才把 cwd 放进 `sys.path`（`-c` 下第一项是空字符串，代表 cwd）。

这解释了一个很常见的 `ModuleNotFoundError`：

```text
proj/
  service.py
  tools/
    main.py   # 里面写 import service
```

从 `proj` 运行 `python tools\main.py`，`sys.path[0]` 是 `proj\tools`，不是 `proj`，所以 `service.py` 找不到：

```text
ModuleNotFoundError: No module named 'service'
```

修法不是在每个脚本开头 `sys.path.append(...)`。把入口放到 `proj/main.py`，从根目录按包的方式导入；或者把 `proj` 做成包，从上一层 `python -m proj.tools.main`；或者把自己的包正常安装进环境。

## 查找顺序：脚本目录、标准库、site-packages

这台 Windows 机器的 `sys.path` 顺序（安装前缀省略）：

```text
1. 脚本目录（python script.py）或当前目录（-m / -c / 交互）
2. <安装目录>\python311.zip
3. <安装目录>\DLLs
4. <安装目录>\Lib
5. <安装目录>
6. <用户目录>\...\site-packages
7. <安装目录>\Lib\site-packages
```

标准库在 `Lib`，排在 `site-packages` 前面；脚本目录又排在标准库前面。所以你在脚本旁边放一个 `random.py`，它会顶掉标准库的 `random`。

在一个空目录里放两个文件：

```python
# random.py
print("这是我写的 random.py")


def choice(seq):
    return "假随机"
```

```python
# main.py
import random

print("random.__file__ 以 random.py 结尾:", random.__file__.endswith("random.py"))
print(random.choice([1, 2, 3]))
```

运行 `python main.py`：

```text
这是我写的 random.py
random.__file__ 以 random.py 结尾: True
假随机
```

这不是「Python 找不到标准库」，是脚本目录先被找到，标准库根本没轮到。别把自己的文件命名成 `random.py`、`json.py`、`string.py` 这类标准库模块名；已经命名了就改掉，或者把脚本移出那个目录。

## 包：有 __init__.py 是常规包，没有也可能是命名空间包

```text
todo/
  __init__.py
  service.py   # 里面定义 def add(a, b): return a + b
main.py
```

`todo/` 里有 `__init__.py`（可以是空文件），它就是常规包：

```python
from todo import service
from todo.service import add

print(service.add(2, 3))
print(add(2, 3))
```

输出 `5` 和 `5`。`add` 必须在 `todo/service.py` 里真的定义；只建目录、没写函数，`from todo.service import add` 会报 `ImportError: cannot import name 'add' from 'todo.service'`。

`__init__.py` 的作用不只是「标记这是一个包」。它在包被 import 时执行，可以放包的初始化代码或公开接口；反过来，不建议在里面写大量导入，那会让 `import todo` 变慢，也容易造成循环导入。

Python 3.3 起还有命名空间包：目录没有 `__init__.py` 也能被 import。Python 3.11 下，建一个 `nsdemo/thing.py`，`import nsdemo` 仍然成功，但 `nsdemo.__file__` 是 `None`。这不是「旧版本的说法过时了所以不用写」——命名空间包适合把一个包拆到多个目录，代价是没有单个 `__init__.py`、`__file__` 为 `None`，一些工具和打包流程会不习惯。自己项目的包，放一个空的 `__init__.py` 更省事。

## 虚拟环境：先确认 python 和 pip 是同一套

```bash
python -m venv .venv
# Windows PowerShell:
.\.venv\Scripts\Activate.ps1
# macOS / Linux:
source .venv/bin/activate

python -m pip install requests
python -m pip freeze
```

为什么不在全局环境里装：不同项目可能要 `requests` 的不同版本，全装进同一个 `site-packages` 会互相覆盖。Windows 上具体风险不是「操作系统自己在用系统 Python」——Windows 不靠它跑系统；真正的坑是 PATH 里可能有多个 Python（Microsoft Store 的别名、厂商装的、conda 的），`python` 和 `pip` 指向不同的那一个，于是 `pip install` 成功、你的 `python` 还是 `ModuleNotFoundError`。

激活后命令行前面会出现 `(.venv)`，但提示符只是提示。确认同一套环境看路径：

```bash
where.exe python
where.exe pip
python -c "import sys; print(sys.executable)"
python -m pip -V
```

最后两条应该都指向 `.venv`。如果 `pip -V` 指向别的地方，用 `python -m pip install ...`，它强制用当前 `python` 的 pip。`python -m pip freeze` 的输出就是 `requirements.txt` 的内容；把这份输出存下来，别人才能装到同一组版本。

## 跑一遍

这段会在当前目录建 `demo_service.py`、`demo_todo/`、`demo_ns/`。用 `demo_` 前缀是为了不覆盖你项目里已有的 `service.py` 或 `todo/`；在空目录里跑，跑完删掉这几个演示文件。

<!-- run -->
```python
import subprocess
import sys
from pathlib import Path

Path("demo_service.py").write_text(
    "print('service 顶层被执行')\n"
    "def add(a, b):\n"
    "    return a + b\n"
    "if __name__ == '__main__':\n"
    "    print('只有直接运行才打印')\n",
    encoding="utf-8",
)

import demo_service

print("导入 service:")
print("  __name__ =", demo_service.__name__)
print("  add(1, 2) =", demo_service.add(1, 2))

print("直接运行 demo_service.py:")
result = subprocess.run(
    [sys.executable, "demo_service.py"],
    capture_output=True,
    text=True,
    encoding="utf-8",
    check=True,
)
print(result.stdout, end="")

try:
    import math.sqrt
except ModuleNotFoundError as error:
    print(f"ModuleNotFoundError: {error}")

Path("demo_todo").mkdir(exist_ok=True)
Path("demo_todo/__init__.py").write_text("", encoding="utf-8")
Path("demo_todo/service.py").write_text(
    "def add(a, b):\n"
    "    return a + b\n",
    encoding="utf-8",
)
Path("demo_ns").mkdir(exist_ok=True)
Path("demo_ns/thing.py").write_text("VALUE = 42\n", encoding="utf-8")

import demo_todo
from demo_todo import service as todo_service
from demo_todo.service import add

print("包内调用:", todo_service.add(2, 3), add(2, 3))
print("包目录有 __init__.py:", demo_todo.__file__.endswith("__init__.py"))

import demo_ns
import demo_ns.thing

print("命名空间包 __file__ is None:", demo_ns.__file__ is None)
print("demo_ns.thing.VALUE:", demo_ns.thing.VALUE)
```
```text
service 顶层被执行
导入 service:
  __name__ = demo_service
  add(1, 2) = 3
直接运行 demo_service.py:
service 顶层被执行
只有直接运行才打印
ModuleNotFoundError: No module named 'math.sqrt'; 'math' is not a package
包内调用: 5 5
包目录有 __init__.py: True
命名空间包 __file__ is None: True
demo_ns.thing.VALUE: 42
```

第一行 `service 顶层被执行` 出现在「导入 service:」之前，因为 `import demo_service` 在那一行就执行了模块顶层。直接运行 `demo_service.py` 时两行都打印，说明 `if __name__ == "__main__":` 里的代码只在直接运行的时候执行。`demo_todo.__file__` 以 `__init__.py` 结尾，`demo_ns.__file__` 是 `None`，两者的差别就是常规包和命名空间包。

## 还差的

- **打包和发布没讲**。`pyproject.toml`、wheel、entry points、`pip install -e .` 都没覆盖；本文只讲了本地 import，没讲怎么让自己的包被别人安装。
- **相对导入和循环导入没展开**。`from . import service` 什么时候能用、两个模块互相 import 时怎么拆，只有一句「容易循环导入」，没有可操作的排查步骤。
- **虚拟环境只讲了 venv**。conda、uv、poetry 的差异，以及依赖锁定文件怎么生成，都没讲；`requirements.txt` 只记了顶层版本。
- **命名空间包只验证了最小行为**。多目录拆分、`pkgutil`、打包工具对 `__file__ is None` 的处理，都没有实测。
- **`sys.path` 的顺序是 Windows 3.11 的实测**。macOS/Linux 的目录名和 `site-packages` 位置不同，别照抄路径，只记「脚本目录 → 标准库 → site-packages」这个先后。
