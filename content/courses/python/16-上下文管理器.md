# 16 · 上下文管理器

## 我把打开的文件 return 出去了

写了个读配置文件的小函数，看着挺干净：

```python
def load_config(path):
    with open(path, encoding="utf-8") as f:
        return f          # 想着「反正外面会关」，就把文件对象交出去
```

调用它的地方：

```text
$ python demo.py
Traceback (most recent call last):
  File "demo.py", line 9, in <module>
    print(load_config("app.ini").read())
ValueError: I/O operation on closed file.
```

文件是打开了，也确实读到了——但**它在我拿到之前就被关了**。`with` 的退出是函数返回前的一瞬间发生的，`return` 只是决定返回什么，不改变「离开 with 块」这个事实。

这个错误让我把 `with` 的边界搞清楚了：**`with` 管的是「这个对象在你手上这段时间」，一旦离开块，它的资源就没了**，哪怕你手里还攥着它。

## with 到底做了什么

```python
with open("a.txt", encoding="utf-8") as f:
    data = f.read()
```

展开成等价的 try/finally：

```python
f = open("a.txt", encoding="utf-8").__enter__()   # __enter__ 的返回值给 as 后面的名字
try:
    data = f.read()
finally:
    f.__exit__(None, None, None)                  # 正常结束传三个 None
```

中间抛异常时，`__exit__` 收到的是那三个异常参数，而不是三个 `None`。**它一定会执行**——正常结束、抛异常、`return`、`break`、`continue`，都是。

但有一处它不执行，这一处很多人不知道：

```python
class Bad:
    def __enter__(self):
        raise RuntimeError("进入就炸了")
    def __exit__(self, *a):
        print("__exit__ 被调用了")     # 这行永远不会打印
```

`__enter__` 自己抛异常时，**with 块根本没进去，`__exit__` 不会被调用**。所以如果你在 `__enter__` 里已经占了一半资源（比如拿了锁、开了文件）然后判断失败抛异常，收尾得自己写在 `__enter__` 里：

```python
def __enter__(self):
    self.f = open(self.path, encoding="utf-8")
    try:
        self.header = self.f.readline()
        if not self.header.startswith("v2"):
            raise ValueError("版本不支持")
    except Exception:
        self.f.close()        # 必须自己收
        raise
    return self
```

## 自己写一个类

一个计时器，五分钟就能写完：

```python
import time

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self          # 这个值给 as 后面的变量

    def __exit__(self, exc_type, exc_value, traceback):
        print(f"耗时 {time.perf_counter() - self.start:.3f}s")
        return False         # False / None = 不吞异常
```

`__exit__` 的三个参数：没异常时全 `None`；有异常时是类型、值、traceback。

**返回值决定异常去哪。** 返回 `False`（或什么都不返回，即 `None`）→ 异常继续往外抛。返回 `True` → 「我处理了」，外面看不到这个异常：

```text
$ python swallow.py
  exit got ValueError
Swallow: 静默过去了          ← 上层 except 没接到
```

这就是最容易埋雷的一个值。写 `return True` 通常只想表达「收尾成功」，实际语义是「把异常吃掉」——程序会带着坏掉的状态继续跑，日志里什么都没有。

`__exit__` 自己抛异常还有一层坑：**它会顶掉原始异常**。

```text
$ python mask.py
Mask: 看到的是 KeyError '收尾失败'
```

原始的 `ValueError("原始错误")` 不在 traceback 的主线上，而是挂在 `KeyError.__context__` 上（Python 3 的异常链）。所以 `__exit__` 里只做「关掉/回滚」，别在里面做可能失败的复杂逻辑。

## 生成器版本：更短，但有两个限制

```python
from contextlib import contextmanager
import time

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield                 # yield 之前 = __enter__，yield 处 = with 块
    finally:
        print(f"耗时 {time.perf_counter() - start:.3f}s")
```

`yield` 之前的代码是进入逻辑，`yield` 的返回值就是 `as` 拿到的值，`yield` 之后（含 `finally`）是退出逻辑。

**收尾必须放 `finally`**。放在 `yield` 后面的普通语句，在 with 块抛异常时会被跳过——异常从 `yield` 那一行抛出，后面的裸代码根本没机会执行。

第一个限制：**这个上下文管理器只能用一次**。第二次进同一个对象会报一个跟上下文管理器毫无关系的错：

```text
$ python reuse.py
  enter
  first R
  exit
写入再入: AttributeError '_GeneratorContextManager' object has no attribute 'args'
```

因为它本质是一个已经跑完的生成器，`_GeneratorContextManager` 内部还想从里面取点东西，取不到就炸在别处。所以别把 `@contextmanager` 的返回值存起来反复用——每次 `with` 都重新调用一次函数：

```python
with timer():        # 每次调用产生新对象
    ...
with timer():        # 正确
    ...
```

第二个限制：**入口逻辑不能太复杂**。`yield` 之前的代码如果抛异常，行为和类版本一样——退出逻辑不会执行。需要「开一半失败要自己回滚」时，在 `yield` 之前自己写好 try。

## 一次开多个：ExitStack

固定两个资源，一个 `with` 里用逗号连起来就够：

```python
with open("in.txt") as src, open("out.txt", "w") as dst:
    dst.write(src.read())
```

数量不固定（比如按配置列表打开若干文件）时就写不出来了，这时候用 `ExitStack`：

<!-- run -->
```python
from contextlib import ExitStack, contextmanager

def opener(name):
    @contextmanager
    def _open():
        print(f"open {name}")
        try:
            yield name
        finally:
            print(f"close {name}")
    return _open()

with ExitStack() as stack:
    names = [stack.enter_context(opener(n)) for n in ("a", "b", "c")]
    print("拿到:", names)
```
```text
open a
open b
open c
拿到: ['a', 'b', 'c']
close c
close b
close a
```

**关闭顺序是反的**，与 `with` 嵌套时的行为一致。这个顺序有意义：先开的资源可能被后开的依赖，反着关才不会关掉还在用的东西。

`ExitStack` 还有一个实用场景：**条件性地注册清理**。

```python
with ExitStack() as stack:
    if need_lock:
        stack.enter_context(lock)
    if need_tmpdir:
        tmp = stack.enter_context(tempfile.TemporaryDirectory())
    do_work()
```

不用为了「可能不需要」的资源写一堆嵌套 `if`。

## 三件我踩过、值得单独记住的事

**一、返回对象出去，等于把已关闭的资源交出去。** `with open(...) as f: return f` 是最典型的写法，也是最典型的 bug。要交出去，就在 with 块里把它读成数据（字符串、dict、bytes），或者让调用方自己管 `with`。

**二、`return True` 是藏错误，不是表达成功。** 我见过线上一个「保存失败但接口返回 200」的问题，根因就是 `__exit__` 返回了 True，异常被那层静默吞掉。

**三、`@contextmanager` 的返回值是一次性的。** 存成模块级变量、或者传给别人复用，就会得到那个莫名其妙的 `AttributeError`。

## 这一课之后

`with` 保证「进入调 `__enter__`、退出调 `__exit__`」，后者在正常结束和抛异常时都执行，但**进入失败时不会执行**。

`__exit__` 返回 `True` 是吞掉异常；它自己抛异常会顶掉原始异常（原始的在 `__context__` 里）。生成器版本必须把收尾放 `finally`，且只能用一次。数量不固定时用 `ExitStack`，它的关闭顺序是反的。
